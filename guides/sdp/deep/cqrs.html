Deep Dive: Inside the Mechanism

The lesson's diagram has three boxes and some arrows: write model, change stream, read models. In a design review, nearly every hard question is about the arrows. How does a change get from Postgres to Elasticsearch? What happens when two changes arrive in the wrong order? How does the orders page know whether it has caught up with the user's own write? This section follows one order, 7f3a, from checkout to the three read models, using the most common setup: Postgres as the write model, CDC into Kafka, and a projector per read model.

The command side: validate, commit, return a position

A command handler does four things inside one database transaction. It loads what it needs, checks the business rules, writes the change, and commits. With only 3 indexes left on the write tables, the commit is fast.

It then returns something the lesson does not mention, and that the read side will need: a position token. In Postgres this can be the WAL position of the commit, read with pg_current_wal_lsn() right after it. A simpler option is a per-order version number that the write increments. The client keeps the token and sends it with its next read. That one value is what turns read-your-writes from a guess ("wait a second and hope") into a check ("has the projection applied my change yet?").

Commands should also carry an idempotency key. When the orders page lags and the user does not see their order, the next thing they do is press "Place order" again. With a key, the second command finds the first result and returns it. Without one, lag becomes duplicate orders.

The change stream: logical decoding, slots and topics

Debezium is the usual CDC tool for Postgres, and its moving parts are worth naming, because each one is a knob and a failure mode.

  • Logical decoding turns WAL records into row-level changes (insert, update, delete, with column values). It needs wal_level = logical on the primary, which writes somewhat more WAL.
  • A publication lists which tables are captured. Capture the tables the read models need, not the whole database.
  • A replication slot remembers how far the consumer has read. Postgres keeps all WAL the slot has not confirmed. This is what makes CDC lossless across connector restarts. It is also what fills the primary's disk when the connector stops.
  • Kafka topics, usually one per table, keyed by primary key. Kafka preserves order only within a partition, so keying by primary key means all changes to order 7f3a land in one partition, in commit order. Changes to different rows have no shared order at all.
  • An initial snapshot. When the connector starts for the first time, it reads the existing tables and emits them as change events, then switches to streaming. Every new read model needs either this or a separate backfill.

Raw table CDC has one structural weakness: your read models now depend on your write schema. Rename a column and every projector sees a different event. The common answer is the outbox variant. The command handler writes an outbox row with a deliberate, versioned event (OrderPlaced v2) in the same transaction, and CDC captures only the outbox table. Debezium ships an "outbox event router" for exactly this. You get the safety of log-based capture and a contract you control.

The projector: idempotent, ordered per key, checkpointed

A projector consumes changes and writes one read model. Kafka delivers at least once, so every change may arrive twice. Partitions can also be reassigned mid-batch. The apply step must survive both. The standard tool is a version guard: each read row stores the version (or LSN) of the last change it applied, and an update only lands if it is newer.

-- orders_list: one flat row per order, no joins at read time
INSERT INTO orders_list (order_id, customer_id, status, total, item_count,
                         customer_name, placed_at, src_version)
VALUES ($1, $2, $3, $4, $5, $6, $7, $8)
ON CONFLICT (order_id) DO UPDATE
SET status        = EXCLUDED.status,
    total         = EXCLUDED.total,
    item_count    = EXCLUDED.item_count,
    customer_name = EXCLUDED.customer_name,
    src_version   = EXCLUDED.src_version
WHERE orders_list.src_version < EXCLUDED.src_version;   -- duplicates and stale changes do nothing

A duplicate has the same version, so the WHERE rejects it. A stale change has a lower version, so it is rejected too. The read model converges on the latest state no matter how many times or in what order a change for that row arrives.

Elasticsearch has the same idea built in. Index with version_type=external and pass the source version: Elasticsearch rejects any write whose version is not higher than the stored one. One Elasticsearch detail surprises people. A document is not searchable until the next refresh, which happens every second by default (refresh_interval). So search lag has a floor of about a second, however fast the projector is. Raising the interval to 30 s during a bulk rebuild makes indexing much cheaper. Forgetting to set it back makes search 30 s stale.

Offsets come last. Commit the Kafka offset only after the batch is applied. If the read model is a relational table, you can go one better: store the offset in the same transaction as the rows, and on startup resume from the stored offset instead of Kafka's.

Where the join went: denormalization fan-out

The lesson says the join "still happens, but only once, at write time." True, and it has a cost the lesson leaves out. The orders_list row contains customer_name. When customer 8412 changes their name, the projector must rewrite every order row that copied it. A customer with 2,000 orders turns one write into 2,000.

A projector that joins also has to cope with events from two topics that have no shared order. The customers change can arrive before or after the orders change that refers to it. There are three ways to handle this:

  • Fan out the update. The projector keeps a local customers table and, on a name change, rewrites that customer's order rows in batches. Correct, simple, and expensive for customers with huge histories.
  • Join inside the read store. Keep orders_list and a small customer_names table side by side in the read database, and join at query time on an indexed key. That join is cheap: two tables, one key, both shaped for it. It is nothing like the six-table join from the incident.
  • Do not copy volatile fields. If the orders page can show the name from the session, leave it out of the projection entirely.

The general rule: copy fields that rarely change (a product's title at purchase time, which should never change on an old order anyway), and reference fields that change often.

Read-your-writes, done precisely

With a position token from the command side, the read side can do better than "route to the primary for a few seconds":

  1. The client places order 7f3a and gets back version = 1 (or an LSN).
  2. It requests the orders page with min_version for that order, or min_lsn for the whole projection.
  3. The read service checks the projection's applied position. If it is far enough, it serves the read model.
  4. If not, it waits briefly (say up to 300 ms), polling the position. Past that budget, it falls back to the write model for this one read, or serves the read model plus the client's optimistic copy of the new order.

This sends almost no traffic to the write side, because the projection is usually already there. "Primary for five seconds after any write" is cruder. It sends every read in that window to the write side, which is fine at small scale and a real load at large scale.

Deep Dive: Sizing and the Numbers

Assumptions: the bookstore's peak is 300 orders per second. Each order commits the order row, three item rows, one payment row and one outbox row: 6 row changes. Change events average 1 KB on the wire.

The write-side saving, counted

Before the split, each insert into the orders table touched the heap plus 14 indexes: 15 writes. After, it touches the heap plus 3: 4 writes. That is about 73% fewer page writes for that table. Each index change also generates WAL, so the WAL volume for orders falls by a similar share. Part of that saving goes straight back into CDC, because wal_level = logical writes extra information and the outbox adds a row per command. Net, the write side still comes out well ahead, and, more important, it stops getting slower every time a reader wants something.

Change stream throughput

  • Raw table CDC: 300 orders/s × 6 changes = 1,800 events/s, about 1.8 MB/s. With the outbox variant only: 300 events/s. Either is small for Kafka.
  • Partitions are set by the slowest consumer, not by Kafka. Say the orders_list projector applies batches at about 1,500 changes per second per partition. Peak 1,800/s needs at least 2 partitions. Plan for 12, so a backlog drains in parallel and you can add projector instances later. Partitions are cheap to have and painful to change, because changing the count moves keys between partitions and breaks per-key order during the switch.
  • Retention: at 1.8 MB/s, a day of changes is about 155 GB. Seven days is about 1.1 TB, times the replication factor of 3: about 3.3 TB of Kafka disk. That retention is what lets a projector that broke on Friday replay from Kafka on Monday instead of re-snapshotting Postgres.

Write it down per read model: the orders page may need p99 under 1 s, search under 5 s, the warehouse under 15 minutes.

Read model storage and rebuild time

  • orders_list: 100 million orders × about 600 bytes with indexes ≈ 60 GB. One modest database, or a replicated pair for read volume.
  • Elasticsearch: source documents of about 1.5 KB, plus the inverted index, often land at 1–2× the source size, then × (1 primary + 1 replica). Call it 300–600 GB for 100 million orders. Measure on a real sample. Text-heavy fields swing it a lot.
  • Rebuild of orders_list from a Kafka topic or a snapshot at 20,000 rows/s with batched upserts: 100M / 20,000 = 5,000 s, under 1.5 hours. Elasticsearch bulk indexing speed varies too much with mapping and hardware to quote. Measure it, then plan the rebuild window with 2× margin.

Fan-out cost of a copied field

Suppose 0.05% of 20 million customers change their name each day: 10,000 changes. If the average customer has 40 orders, that is 400,000 extra row updates a day, about 5 per second. Harmless. Now copy the category name into every order item, and rename one category with 30 million items. One click becomes 30 million updates. At 20,000 per second that is 25 minutes, and if those updates share partitions with normal traffic, every orders-page read in that time is 25 minutes stale. Do this arithmetic for each copied field before you copy it.

Deep Dive: Failure Modes in Production

1. The primary's disk fills up because a read model stopped

Symptom: disk usage on the write primary climbs steadily all weekend. On Monday writes fail. Mechanism: the Debezium connector crashed on Friday, or a test connector was created and abandoned. Its replication slot still exists, so Postgres keeps every WAL segment since the slot's last confirmed position. The read side's outage has become a write-side outage. Detect: alert on retained WAL per slot, in bytes (the gap between pg_current_wal_lsn() and the slot's confirmed_flush_lsn in pg_replication_slots), and on inactive slots. Fix: restart the connector or drop the abandoned slot. Since Postgres 13, max_slot_wal_keep_size caps retained WAL. When the cap is hit, the slot is invalidated and the connector needs a fresh snapshot. That is the right trade: a slow rebuild of the read side beats a down write side.

2. An old status overwrites a new one

Symptom: some cancelled orders show "shipped" on the orders page. The write model says cancelled. Mechanism: the projector applies changes with plain UPDATE ... SET status = ?. During a consumer rebalance, a batch was processed twice: once by the old owner, then again by the new owner after a newer change had already landed. Or the read model is fed from two topics, and their changes interleave arbitrarily. The last write wins, and it was the older one. Detect: a reconciliation job that samples rows and compares read-model version and status with the write model. Fix: the version guard from the mechanism section, on every projector. Then rebuild or repair the drifted rows.

3. Lag turns into duplicate orders

Symptom: a spike in customers charged twice, all within a few seconds of each other, during a busy evening. Mechanism: projection lag rose from 200 ms to 4 s under load. Users placed an order, saw an empty orders page, assumed it failed, and placed it again. Each command was valid on its own. Detect: duplicate-order rate (same customer, same items, within 60 s) graphed next to projection lag. They move together. Fix: idempotency keys on commands, generated by the client per checkout attempt. Then position tokens, so the page waits for or patches in the user's own order. A lag spike should cause a slower page, never a second charge.

4. A harmless migration breaks every projector

Symptom: after a deploy that renamed orders.total to orders.total_amount, the search projector stops. Its lag grows, and so does the dead-letter queue. Mechanism: with raw table CDC, the table schema is the read side's contract. The projector cannot find total, fails, and retries the same event. If it uses a dead-letter queue, it skips ahead, and every order since the deploy is missing from search. Detect: projector error rate, DLQ depth, and stuck-offset alerts, split by projector. Fix: short term, update the projector to read both names. Long term, move read models to outbox events with a versioned contract, and add a schema compatibility check (a schema registry, or a CI test) that fails the write-side deploy before it breaks the read side.

5. A read model drifts and nobody notices for weeks

Symptom: finance notices that the dashboard's monthly revenue is 0.4% below the ledger. It has been for six weeks. Mechanism: a projector bug dropped partial refunds of a particular type. There was no error, because the code did exactly what it was written to do. This is the costliest failure in CQRS: a read model that is wrong and trusted. Detect: scheduled reconciliation. For each day, compare count and sum of key fields between the write model and each read model, by bucket (per day, per shard, per status). Alert on any difference above a small tolerance. Fix: fix the projector, rebuild the read model, and keep the reconciliation running. A read model with no reconciliation job is a read model you only hope is right.

6. A rebuild takes down production

Symptom: the team rebuilds the search index on a Tuesday afternoon. Checkout latency doubles, and search returns half-empty results for an hour. Mechanism: two mistakes at once. The rebuild used a fresh Debezium snapshot, which ran large scans against the write primary at peak. And it wrote into the live index after deleting it, so readers saw a half-built index. Detect: primary CPU and I/O during snapshots; search result counts against a baseline. Fix: rebuild from Kafka retention or a replica, never from the primary at peak. Build into a new index (orders_v7) behind an alias, let it catch up to the live stream, verify counts, then swap the alias in one atomic step. The old index stays as an instant rollback.

7. One rename makes the orders page stale for everyone

Symptom: lag on orders_list jumps from 200 ms to 25 minutes at 15:00. Writes look normal. Mechanism: a merchandiser renamed a category copied into 30 million rows (the sizing example). The fan-out updates queued in the same partitions as live order changes. Detect: lag per partition plus apply rate by change type. A sudden flood of one type is the giveaway. Fix: stop copying that field, or join it in the read store instead. If it must be copied, run bulk fan-out in a separate, lower-priority lane so live changes are never queued behind it.

Two strong opinions. First, the outbox is worth it as soon as a second team reads your changes. Raw CDC feels free. Then your table refactor needs four teams' sign-off, and you learn what "free" cost. Second, do not make commands asynchronous because you split the read side. CQRS splits models, not request styles. A checkout that returns 202 and asks the client to poll has added a second problem to fix the first.

And remember the lesson's spectrum. Many review discussions end, correctly, at Level 1 or a materialized view. The question to ask is "what is the freshness budget and the size?", not "which product should we add?"

Deep Dive: Design-Review Checklist

  1. What measured shape conflict justifies this split? Show the slow query, the index count and the write latency trend.
  2. Which level of the spectrum is proposed, and why would the level below it not work?
  3. How does every read model get its changes? Is there any code path that writes to two stores directly?
  4. Is the read side fed from raw tables or from a versioned outbox contract? Who must approve a write-side schema change?
  5. Is each projector's apply idempotent and order-safe (a version guard or external versioning)? What happens if a batch is processed twice after a rebalance?
  6. What is the freshness budget for each read model, and is lag measured end to end against it?
  7. Which pages need read-your-writes? Is it solved with tokens, routing or optimistic UI, and do commands carry idempotency keys?
  8. Which fields are copied into read rows, and what is the fan-out cost when each one changes?
  9. Is retained WAL per replication slot alerted on, and is max_slot_wal_keep_size set?
  10. How is each read model rebuilt, from where (not the primary at peak), how long does it take, and how do readers switch over?
  11. Is there a reconciliation job comparing each read model with the write model? What tolerance triggers an alert?
  12. Who owns each read model and its alerts when it is wrong at 3 AM?

Deep Dive: Senior Interview Follow-ups

"Kafka delivers at least once. How does your projection avoid double-applying a change?"

Make the apply idempotent rather than chasing exactly-once delivery. Each read row stores the source version of the last change applied, and the upsert only takes effect if the incoming version is higher. A duplicate has the same version and does nothing. A stale change has a lower one and does nothing. If the read store is relational, I also store the consumer offset in the same transaction, so a restart resumes exactly where the data is.

"How do you give a user read-your-writes without sending all their reads to the primary?"

The command returns a position: a version for the entity or the commit's WAL position. The client sends it with the next read. The read service compares it with the projection's applied position. If the projection is there, which is almost always, serve it. If not, wait up to a small budget, then fall back to the write side for that single read. The UI also shows the new item optimistically. Write-side load stays tiny because only the rare lagging read falls back.

"Your CDC connector was down for six hours. What happened to the read models and the database?"

Read models are six hours stale but not wrong, and they will catch up once the connector returns, because the replication slot held its place. The database kept six hours of WAL for that slot. That is the danger: if WAL growth outran free disk, the primary would have stopped accepting writes. So I alert on slot lag in bytes, cap it with max_slot_wal_keep_size, and accept that hitting the cap means re-snapshotting the read side. A stale read side is a much smaller incident than a stopped write side.

"Isn't a read replica a read model? Why not just add replicas?"

A replica is a read model with the same shape. It fixes volume: too many reads for one machine. It cannot fix shape: the six-table join is 300 ms on every copy, and full-text search is still bad. CQRS changes the shape. In practice you often use both. The orders_list projection is itself replicated when its read volume grows.

"A customer renames themselves. How many writes does that cause on your read side?"

It depends on where the name lives. If every order row copies it, one write per order they have ever placed: thousands for a heavy buyer. If the read store keeps names in a small table joined by an indexed key, one write. I copy only fields that rarely change and reference the rest. For fields that must be copied, I run the fan-out on a low-priority lane so it never delays live updates.

"How do you know a read model is correct, not just up to date?"

Low lag only proves the projector is running. Correctness needs reconciliation: a scheduled job that compares counts and sums of key fields between the write model and the read model, bucketed by day or shard, plus random row-level sampling. Any difference beyond tolerance opens an alert, and the fix is a rebuild from the stream. Without that job, a projector bug can stay silent for weeks.

"When is a materialized view enough?"

When the data is small enough to recompute on a schedule and the readers accept that much staleness. A nightly sales summary or a ten-minute dashboard fits. REFRESH MATERIALIZED VIEW CONCURRENTLY keeps readers unblocked, at the cost of a unique index and a full recompute each time. Once the data is large or needs to be fresh within seconds, an incremental projector fed by the change stream wins.

"Does CQRS require event sourcing, or async commands, or two databases?"

None of them. CQRS only requires that reads and writes use different models. Level 1 is separate query code in one database. CDC from a plain relational table is the most common way to feed separate read stores. Commands can stay synchronous. Event sourcing pairs well with CQRS because its events are a ready-made change stream, but each pattern works alone.
