Deep Dive: Inside the Mechanism

The lesson's checklist says where each kind of state goes. A design review goes one level down. How exactly does a session live in Redis? What makes a job run once and only once? What breaks while two versions of the code run side by side? Those details decide whether the fleet behaves like one service or like fifty slightly different ones.

The real contract: any request, any server, any time, any version

"Stateless" is shorthand for a contract with four parts. Each part rules out a different class of bug.

  • Any request. Nothing about a user lives only on one machine. This is the part the lesson covers: sessions, files, caches, counters.
  • Any server. Servers are configured identically. No server is "the one with the cron", "the one with the admin console" or "the one with the bigger disk". Config comes from the same source for all of them.
  • Any time. A server can be killed at any moment and replaced. So it must start from nothing: no hand-applied setup, no data that only exists after a warm-up script someone ran once. And it must stop cleanly when told to.
  • Any version. During a rolling deploy, old and new code serve traffic together for minutes. A session written by version 2 may be read by version 1 a second later. Shared state formats, cache entries and queue messages must be readable by both.

Teams usually get the first part right and discover the fourth in production. It is the subtlest, and it never shows up on a single machine.

Sessions: two ways out of the server

A server-side store. The browser keeps only a random session ID in a cookie. The data lives in a shared store, typically Redis, under a key like sess:<id>:

  • Create the session with a TTL: SET sess:9f2c... <data> EX 1800.
  • Read it on every request with GET. That is the lesson's ~1 ms hop.
  • Sliding expiry means extending the TTL as the user stays active. Doing an EXPIRE on every request doubles the store's write load. Most systems refresh only when the remaining TTL drops below half.
  • Logout or "sign out everywhere" is a DEL. Revocation is instant, which is this design's big advantage.

The store's settings now matter as much as the code. Redis's maxmemory-policy defaults to noeviction, which rejects writes when memory is full. A shared cache instance is usually set to an LRU policy. Put sessions on that same instance and memory pressure from cache entries will quietly evict logged-in users. Sessions want their own instance, sized to hold them all, with replication.

A signed token. The session data travels with the request, signed so the client cannot change it. A JWT or an HMAC-signed cookie are the usual forms. No server needs to look anything up. The costs are real, though:

  • Revocation is hard. A token is valid until it expires. The common answer is a short-lived access token (minutes) plus a refresh token checked against a store. That reintroduces a store, but only on refresh, not on every request.
  • Size. Every claim rides on every request. Browsers limit a cookie to about 4 KB, and proxies cap total header size. A token that grows with the user's roles will eventually break something.
  • Key rotation. Every server must verify with the same keys. Use a key ID (kid) in the token header, publish several keys at once, and retire old ones only after the last token signed with them has expired.

Neither is "the stateless one". Both move state out of the server. The store keeps it in one shared place. The token spreads it across every client.

Files: get the app servers out of the byte path

Moving uploads from local disk to object storage fixes the 404s. Routing every upload through the app servers still ties up a worker for the whole transfer, and a 200 MB video on a slow connection holds it for minutes.

The better shape is a presigned URL. The app server checks permissions and returns a short-lived URL that allows one PUT to one object key. The browser uploads straight to object storage, then tells the app the upload is done. Downloads work the same way, often through a CDN. The app server touches metadata only. Note also that S3 now gives strong read-after-write consistency for new objects and overwrites, so the old "upload then 404 on read" race is no longer a design concern there. Check the consistency model of whatever store you actually use.

Scheduled jobs: once, and only once

A cron on every server runs N times. The fix is mutual exclusion: one runner holds the right to run, and everyone else skips. Three common ways to get it:

  • A lease in Redis. SET lock:nightly-report <random-token> NX PX 600000 succeeds for exactly one caller and expires after 10 minutes. Release with a compare-and-delete, so a server never deletes a lock someone else now holds.
  • A Postgres advisory lock. SELECT pg_try_advisory_lock(42) returns true for one session only. A session-level advisory lock is released automatically when that connection drops, so a crashed runner frees it.
  • An external scheduler. A Kubernetes CronJob with concurrencyPolicy: Forbid, or a queue-based scheduler that enqueues one job per tick for one consumer. The app servers stop scheduling anything.

Every lease has the same hole. The holder can pause (a GC pause, a VM freeze, a network partition) past the lease time. A second server then takes the lock while the first still believes it holds it. For a report that only sends email, idempotency keyed by customer and date makes the double run harmless. For anything that writes, pass a fencing token: a number that increases with every grant, which the database checks and rejects if it is older than the last one it saw.

# Lease-based "run once" with stdlib only, using a Redis-like client passed in.
import uuid

RELEASE = """
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
"""

def run_once(r, name, ttl_ms, job):
    token = str(uuid.uuid4())
    if not r.set(f"lock:{name}", token, nx=True, px=ttl_ms):
        return False          # another server holds it this tick
    try:
        job()                 # must finish well inside ttl_ms, and be idempotent
    finally:
        r.eval(RELEASE, 1, f"lock:{name}", token)
    return True

Counters, rate limits and IDs

A counter in process memory counts 1/N of reality. The shared version is an atomic increment with a window: INCR rl:user:42:202611211405 with an EXPIRE set in the same transaction or Lua script, so a crash between the two cannot leave a key that never expires.

Two refinements come up in reviews. A hybrid limiter keeps a local allowance of limit/N per server and syncs with the store periodically. It saves a network hop per request and tolerates a small overshoot. And an atomic script (a token bucket in Lua) avoids the race where two servers read the same count and both allow the last request.

ID generation is the other hidden counter. An in-memory sequence or "timestamp plus a random suffix" can collide once N servers generate IDs in the same millisecond. Use database sequences, UUIDv7 (time-ordered and random), or a Snowflake-style scheme with a worker ID. If you choose worker IDs, assigning them is itself a coordination problem: two servers with the same worker ID will mint identical IDs.

The server lifecycle: start, serve, stop

A replaceable server needs a clean birth and a clean death. In Kubernetes terms, these settings carry the contract:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: store-web
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # extra pods allowed during the rollout
      maxUnavailable: 0    # never drop below 6 ready pods
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
      - name: web
        image: store-web:2.14.0
        readinessProbe:            # "send me traffic?" Gates admission.
          httpGet: {path: /healthz/ready, port: 8080}
          periodSeconds: 2
          failureThreshold: 3
        lifecycle:
          preStop:                 # give endpoint removal time to propagate
            exec: {command: ["sleep", "10"]}
  • maxSurge and maxUnavailable trade rollout speed against spare capacity. maxUnavailable: 0 keeps full capacity but needs room for extra pods.
  • The readiness probe keeps a new pod out of rotation until it has loaded config, opened its pools and warmed what it needs.
  • On shutdown the pod gets SIGTERM. The app must stop accepting new work, finish in-flight requests and exit within the grace period. The preStop sleep covers a race the load balancing deep dive explains: the pod can receive SIGTERM before every balancer has stopped sending it traffic. Newer Kubernetes versions also offer a built-in sleep action for preStop, so the image does not need a sleep binary.
  • A PodDisruptionBudget stops node maintenance from evicting too many replicas at once. It is the N+1 policy written as config.

Two versions at once: expand, then contract

Any change to a shared format needs two deploys, not one. The pattern is called expand and contract:

  1. Expand. Deploy code that can read both the old and new formats, but still writes the old one. Add new database columns as nullable.
  2. Switch. Once every server runs that version, deploy code that writes the new format.
  3. Contract. After old-format data has expired or been migrated, remove the old read path and old columns.

This applies to session payloads, cache entries, queue messages and database schemas alike. Skip it and the rollout itself causes the incident: version 2 writes a session that version 1 cannot parse, and users bounce between working and broken pages until the deploy finishes. Versioned serialisation (a v field in every stored blob) makes the expand step easy.

Deep Dive: Sizing and the Numbers

From requests per second to workers per server

"800 requests per second per server" hides a second number: concurrency. Little's law says in-flight requests = arrival rate × time in the system.

  • Fleet: 4,000 rps × 50 ms average latency = 200 requests in flight at peak.
  • Per server at 800 rps: 800 × 0.05 = 40 in flight.

So each server needs at least 40 concurrent workers (threads, processes or event-loop slots) just for the average. Latency has a tail. If p99 is 400 ms and a dependency slows down, in-flight work climbs toward 800 × 0.4 = 320. A thread-per-request server with a pool of 64 will queue long before its CPU is busy. Size the pool from Little's law with a slow-dependency case, not from the CPU count.

N+1 is per failure domain, not per server

The lesson's six servers (five for peak, plus one) survive one server failure. Clouds also lose whole zones. Spread across three zones, the question becomes "can two zones carry the peak?"

  • Peak 4,000 rps at 800 per server means 5 servers must survive.
  • Those 5 must fit in 2 zones: 2.5 per zone, so 3 per zone.
  • 3 zones × 3 servers = 9 servers, not 6.

Normal peak utilisation is then 4,000 / (9 × 800) ≈ 56%. That 56% is the price of surviving a zone. With two zones the price is higher: each zone must carry everything, so you need 10 servers at 50%. Three zones is the usual sweet spot for this reason.

Check one more thing: that the balancer actually spreads load evenly across zones. If one zone has 4 servers and another has 2 and the balancer splits traffic by zone, the small zone runs at twice the load.

Sizing the shared stores

The session store, for 2 million active sessions at about 1 KB each:

  • Memory: 2 million × 1 KB ≈ 2 GB of data, plus Redis per-key overhead. Plan on 3 to 4 GB, and size a replica the same.
  • Load: 4,000 reads per second, plus TTL refreshes. With refresh-at-half-TTL on a 30-minute session, a user active every minute triggers about one refresh per 15 minutes. Writes stay a small fraction of reads.
  • That load is far below what one Redis instance handles. Throughput is not the risk. Availability is: every request now depends on this store.

The database, for the lesson's 50 servers:

  • Opened: 50 servers × 20 pooled connections = 1,000 connections. In Postgres each one is a process using several MB, before any query runs.
  • Actually needed: 4,000 rps × 3 queries per request × 2 ms per query = 24 connections busy on average, by Little's law again.

That gap, 1,000 opened against about 24 used, is what connection pooling recovers. Scaling the app tier multiplies opened connections linearly while needed connections stay roughly the same.

Local caches get worse as you add servers

A local cache with a 60-second TTL works well on one server. Spread the same traffic across 50 servers and each server sees only 1/50 of it.

Take a product page requested 60 times a minute:

  • One server: about one miss a minute and 59 hits. A 98% hit ratio, and the database sees about 1 query a minute.
  • 50 servers: each sees about 1.2 requests a minute. Often the entry has expired before the next request arrives. With random arrivals, the hit ratio is λT / (1 + λT), where λT is the requests per server during one TTL. That is 1.2 / 2.2, or about 55%. Each server misses about 0.55 times a minute, so the database sees about 27 queries a minute for the same page.

Same traffic, same TTL, 27x the database load for that key. The same formula gives 98.4% for the single server (60 / 61), so you can redo it for any key's rate.

Popular keys survive this. The long tail does not. This is why a horizontally scaled tier usually puts a shared cache behind a small local one (two levels), or routes requests by key with consistent hashing so each server caches a distinct slice.

How long a rolling deploy takes

Assume 48 servers, and per replacement: 20 s to start, 10 s until readiness passes, 30 s to drain the old server. About a minute per wave.

  • maxSurge: 25% (12 at a time): 4 waves, about 4 minutes.
  • maxSurge: 1: 48 waves, about 48 minutes.

The slow rollout is safer per step, but it means two versions coexist for most of an hour, and rolling back takes just as long. Canary releases separate these concerns: a small slice first, a pause to compare metrics, then a fast rollout.

Fixed overhead per instance

Every instance pays a fixed tax: runtime memory, a logging and metrics agent, maybe a mesh sidecar, its own database pool. Suppose that is 1.5 GB and 0.5 vCPU per instance.

  • 48 small instances with 2 vCPU / 4 GB: overhead is 24 vCPU and 72 GB, a quarter of the CPU and over a third of the memory.
  • 12 large instances with 8 vCPU / 16 GB, same total: overhead is 6 vCPU and 18 GB.

The small-instance fleet has a smaller blast radius per failure. It also wastes a lot more on overhead and opens four times as many database connections. That is the "24 small or 6 large" tuning decision from the lesson, with numbers attached.

Deep Dive: Failure Modes in Production

1. The job that ran twice anyway

Symptom. The nightly billing job is behind a distributed lock, yet some customers are charged twice. It happens rarely, always on nights the job ran long.

Mechanism. The lease was 10 minutes. One night the job took 14 minutes, because of a slow database and a long GC pause. At minute 10 the lease expired, a second server acquired it and started from the beginning. Both ran for four minutes. The lock gave mutual exclusion only while the holder stayed fast.

Detect. Log the lock token and the start and end time on every run. Two overlapping runs with different tokens are proof. Alert on job duration approaching the lease TTL.

Fix. Make the work idempotent per item (charge keyed by customer and billing period). Renew the lease periodically while working, and abort if renewal fails. For writes that must not overlap, use fencing tokens checked by the database. A lock is a performance optimisation. Correctness comes from idempotency.

2. The rate limit that grew with the fleet

Symptom. An API advertises 100 requests per minute per key. A scraper sustains 4,800 a minute without a single 429. When the fleet scales to 60 servers, it gets 6,000.

Mechanism. The limiter is an in-process counter. With round-robin across 48 servers, each server sees about 1/48 of the key's traffic and allows up to 100 of it. The effective limit is 100 × N. Nothing errors, so nothing looks wrong.

Detect. Compare per-key request counts from access logs (fleet-wide) against the limit. Any key consistently above it means the limiter is local.

Fix. A shared counter (atomic Redis increment or a Lua token bucket), or a hybrid with local allowances of limit/N and periodic sync. Or move rate limiting to the edge, where one component sees every request. See rate limiting.

3. The deploy that broke sessions halfway through

Symptom. During a rolling deploy, errors climb steadily as the rollout progresses, then vanish when it completes. Rolling back causes the same spike again.

Mechanism. Version 2 added a field to the session object and changed its serialisation. Users who hit a version 2 server got a session that version 1 servers could not parse. Rolling back did the same thing in reverse, because version 1 cannot read sessions now written by version 2.

Detect. Error rate correlated with the share of new pods, not with traffic. Deserialisation exceptions in logs, only from old-version pods. Tag every log line and metric with the build version so this correlation is one query.

Fix. Expand and contract: ship a version that reads both formats first. Version every stored blob. Add a test that runs the previous release's reader against the new release's writer.

4. The mass logout

Symptom. Thousands of users are logged out at once, mid-afternoon. No deploy happened. Support tickets arrive before any alert fires.

Mechanism. Two common causes. Either the session store shares an instance with the cache and evicts sessions under an LRU policy when memory fills. Or the session primary failed and a replica was promoted. With asynchronous replication, the newest writes, including just-created sessions, never reached the replica.

Detect. Redis evicted_keys rising in INFO stats. A replication failover event in the store's logs. A spike in login requests right after either.

Fix. A dedicated session instance with noeviction and memory alerts well before full. Replication with automatic failover, and acceptance that a few seconds of new sessions may be lost. Or signed tokens for the common path, so a store outage does not log anyone out. The shared stores inherit the criticality, as the lesson warns. Monitor them like the database.

5. The scale-out that took down the database

Symptom. Traffic spikes, auto-scaling doubles the fleet, and a minute later the database starts refusing connections with "too many clients already". The new servers fail readiness, so they get replaced, and the new replacements also connect.

Mechanism. Each new server opens its full pool at startup. Doubling 30 servers with 20 connections each adds 600 connections in about a minute. The database was already busy, so each new connection's setup cost (in Postgres, forking a process) makes it slower. Failed readiness triggers restarts, which reconnect again. The scaling action multiplied the downstream load, exactly when the database had the least room for it.

Detect. Database connection count tracks the instance count step for step. Connection errors in app logs start right after a scaling event.

Fix. Put a pooler between the fleet and the database (PgBouncer in transaction mode, RDS Proxy and similar), so app scaling does not change database connections. Open pools lazily with a small minimum. Cap total connections in the fleet's config: per-server pool = budget / max instances. Cap how fast auto-scaling can add instances.

6. New servers are slow servers

Symptom. Each scale-out briefly makes latency worse. p99 jumps for a minute or two after new instances join, then settles.

Mechanism. A new server has an empty local cache, a JIT that has not compiled the hot paths, and pools that are not open yet. It passes a readiness check that only tests "is the port open", then receives a full share of traffic at once. Least-connections makes this worse if the new server looks idle: it gets a burst.

Detect. Latency broken down by instance age. New instances show higher latency and lower cache hit ratios for their first minutes.

Fix. Readiness checks that test real readiness (pools open, config loaded). A warm-up step before readiness, such as replaying a few hundred representative requests. Balancer slow start, which ramps a new server's weight over 30 to 60 seconds. Scale out a little earlier, so warm-up happens before the peak, not during it.

7. Scaling out that adds no capacity

Symptom. The fleet grows from 10 to 20 servers. The old 10 stay hot. The new 10 sit at 5% CPU. Latency barely improves.

Mechanism. Some hidden affinity pins existing traffic to existing servers. Sticky sessions left on after the migration. Long-lived HTTP/2 or gRPC connections from other services, balanced once at connect time and never again. Mobile clients that hold keep-alive connections for minutes. New servers only receive new connections, and there are not many.

Detect. Per-instance request rate, not just per-instance CPU. A wide spread between instances with the same configuration means affinity. Check the balancer's stickiness settings and connection age distribution.

Fix. Remove stickiness once sessions are shared. Balance per request (L7) rather than per connection for multiplexed protocols. Set a maximum connection age on servers, so clients reconnect and redistribute; for gRPC, servers can set MaxConnectionAge on their keepalive parameters.

What you scale: a tier, or a whole cell

The lesson scales one tier: more app servers in front of shared stores. At large scale, the shared stores become the limit and the blast radius. A cell-based architecture scales the whole stack instead. Each cell is a complete, independent copy (app servers, cache, database) serving a fixed slice of customers. A thin routing layer maps each customer to a cell.

Cells are sharding applied to the entire stack. They are worth it when a single shared store's failure is unacceptable or when deploys need a small first target. For the store in this course, a tier fleet with replicated stores is right for years.

Deep Dive: Design-Review Checklist

  1. Has every item of server-local state been found: sessions, files, caches, scheduled jobs, counters, rate limits, locks, ID generators, temp files? How was the search done?
  2. Where do sessions live, how are they revoked, and what happens to logged-in users if that store fails over?
  3. Is the session store separate from any cache with an eviction policy?
  4. For each scheduled job: what guarantees one run per tick, what happens if the runner pauses past its lease, and is the job idempotent?
  5. Are rate limits and counters enforced fleet-wide? What is the effective limit at the maximum instance count?
  6. Can version N and N+1 read each other's sessions, cache entries, messages and schema? Where is that tested?
  7. What is the per-server concurrency (Little's law at p99), and is the worker pool sized for it?
  8. Does N+1 hold per zone? How many servers survive a zone loss, and can they carry peak?
  9. What is the total database connection count at maximum fleet size, and what caps it?
  10. How does a new server warm up, and when does it start taking full traffic?
  11. Does shutdown stop accepting work, finish in-flight requests and exit within the grace period?
  12. Is any affinity left (stickiness, long-lived connections) that would stop new servers from taking load?

Deep Dive: Senior Interview Follow-ups

"JWTs make the service stateless, so why not use them everywhere?"

They move the state to the client rather than removing it, and they give up instant revocation. A stolen or stale token stays valid until it expires. The usual compromise is short-lived access tokens with a refresh token checked against a store, so revocation takes effect within minutes. Tokens also grow with every claim, ride on every request, and require key rotation across all servers. They are a good fit for APIs and multi-region setups. A plain Redis session store is simpler when you need "log out everywhere" to be instant.

"You put a distributed lock around the cron. Is it now guaranteed to run once?"

No. A lease-based lock guarantees exclusion only while the holder is fast. A GC pause, VM freeze or partition longer than the lease lets a second holder in while the first still thinks it owns the lock. You make it safe with idempotent work, lease renewal that aborts on failure, and for writes, fencing tokens that the storage layer checks. "Exactly once" comes from idempotency plus at-least-once execution, not from the lock.

"Rolling deploys are zero-downtime. What can still go wrong?"

Mixed versions. For several minutes old and new code share sessions, caches, queues and the schema. If the new version writes a format the old one cannot read, the rollout causes errors that scale with its progress, and rollback repeats them. The fix is expand and contract: first ship a version that reads both formats, then switch writes, then remove the old path. The other risks are capacity during the surge and draining that is shorter than the longest request.

"You need 5 servers at peak. How many do you run?"

It depends on the failure domain. N+1 in one zone is 6. Across three zones, two zones must carry peak, so 3 per zone and 9 total, which runs at about 56% at peak. Then check what the per-zone balancing does with uneven counts, how many extra pods a rolling deploy surges, and whether auto-scaling can replace a lost zone's capacity fast enough to justify running fewer.

"We doubled the fleet and the database fell over. Why didn't the database scale too?"

Because opened connections scale with servers, not with work. 50 servers × 20 connections is 1,000 opened, while Little's law says perhaps 24 are actually busy. In Postgres each connection is a process, so 1,000 idle ones cost memory and scheduling. And they all arrive at once on scale-out. Put a transaction-mode pooler in front, budget connections per server from the fleet maximum, and rate-limit scale-out.

"Why might adding servers lower your cache hit ratio?"

Local caches see 1/N of the traffic each. A key requested 60 times a minute with a 60-second TTL is a 98% hit on one server and about a 55% hit on 50 servers, by λT / (1 + λT). The database then sees about 27x the queries for that key. The fixes: a shared second-level cache, routing by key with consistent hashing so each server owns a slice, or longer TTLs with explicit invalidation where staleness allows.

"The fleet scaled out but the old servers stay hot. What's going on?"

Affinity. Sticky sessions left on, or long-lived connections. HTTP/2 and gRPC clients hold a few connections and multiplex everything over them, and an L4 balancer places each connection once. New servers only receive new connections. Balance per request at L7, set a maximum connection age on the server side so clients reconnect, and look at request rate per instance rather than CPU to confirm.

"When is horizontal scaling the wrong unit and you'd use cells instead?"

When the shared stores become the limit or the blast radius. A fleet of stateless servers still shares one session store, one cache and one database. A bad deploy or a store failure hits every customer. Cells copy the whole stack and assign each customer to one cell, so a failure or a bad canary hits only that cell's share. The cost is a routing layer, harder cross-customer features and N copies to operate. That trade usually pays off for large multi-tenant SaaS, not for one store.
