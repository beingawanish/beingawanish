Deep Dive: Inside the Mechanism

The lesson explains why a similarity query has no shard key, and the three ways to split around that. This section goes one level down. What does each shard actually hold? How does a vector get from a write to a searchable index? What does the coordinator do with the answers, and why are scores less comparable than they look?

What a shard holds: three index families

Every shard runs an approximate nearest neighbour (ANN) index over its slice of the vectors. Three families cover most real systems, and the choice decides memory, recall and how writes behave.

  • HNSW (graph, in RAM). Each vector is a node linked to about M near neighbours, with sparser layers on top for long jumps. A search enters at the top layer, walks greedily toward the query, drops a layer, and repeats. On the bottom layer it keeps a candidate list of size ef_search. Bigger M and ef_search raise recall and cost memory and time. HNSW gives excellent recall at low latency, but it wants the full vectors and the graph in RAM. Inserts are fairly expensive, and deletes are usually tombstones that the graph routes around until a rebuild.
  • IVF and IVF-PQ (clusters, often compressed). k-means finds nlist centroids. Each vector goes into the list of its nearest centroid. A search compares the query with the centroids, then scans the nprobe nearest lists. Product quantization (PQ) compresses each vector by splitting it into m sub-vectors and replacing each with a one-byte code, so a 1,536-dimension float vector (6 KB) can shrink to 96 bytes. Distances on codes are approximate, so systems usually rescore the best few hundred candidates with full vectors fetched from disk. This is the same geometry the lesson's centroid routing uses, applied inside one shard.
  • Disk-resident graphs. A graph index laid out on NVMe SSD, with compressed vectors in RAM to steer the walk and full vectors read from disk for the final ranking (the DiskANN line of work is the best-known example). It holds many times more vectors per node than HNSW in RAM, at the cost of a few SSD reads per query and more careful tuning.

The sharding decision and the index decision are linked. A compressed or disk-based index can push the single-node limit out by 10× or more, which is why the lesson says to quantize before sharding.

The write path: segments, not one big index

Graph and cluster indexes are expensive to update one vector at a time. Most vector databases therefore borrow the log-structured design from search engines and LSM-tree databases. The details differ by product, but the shape is common:

  1. A write lands in a write-ahead log and in a small mutable buffer, often called a growing segment. Queries search it by brute force, which is fine because it is small.
  2. When the buffer reaches a size or age limit, it is sealed. A background job builds a real ANN index for it.
  3. A query searches every sealed segment's index plus the growing buffer, and merges the results. A shard is really a small scatter-gather of its own.
  4. Deletes go into a bitmap or tombstone list checked during search. An update is a delete plus an insert.
  5. Compaction merges small segments into larger ones and drops deleted vectors. It rebuilds indexes, so it costs CPU and temporary memory.

Three operational facts follow from this design. First, freshness is "time until searchable", which is usually fast because the growing buffer is searched, but slows if index builds fall behind. Second, many small segments make every query slower, so compaction health is a latency metric. Third, a shard that deleted 30% of its vectors still pays memory for them until compaction runs.

The scatter-gather protocol

The coordinator's job sounds trivial: send the query everywhere, keep the best k. Several details decide whether it is correct and fast.

  • Per-shard k. If every shard searched exactly, asking each for k would be enough: the global top k must be inside the union of the local top k. But each shard is approximate. Asking for k' = 2k or so from each shard raises the chance that a true neighbour missed in one shard's top k still makes it into the merge. The cost is small, because the merge handles only N × k' candidates.
  • Same parameters everywhere. The coordinator sends the same filter, metric and ef_search or nprobe to every shard. A shard tuned differently returns a different quality of answer, and the merge cannot tell.
  • Hedging. If a shard has not answered by about its p95 latency, send the same request to its replica and take the first answer. This costs roughly 5% extra shard queries and removes most stragglers.
  • Partial results policy. If a shard and its replica both fail, the coordinator either fails the query or returns results from the other shards with a flag. For RAG, a partial answer is usually better than none, but it must be logged, because it silently lowers recall.
  • Merge. A heap of size k over all candidates, deduplicated by document ID if a vector can exist in two places during a rebalance.

When scores are not comparable

The lesson mentions normalising scores across shards. For pure vector search with one model and one metric, raw distances are already comparable, with two exceptions that bite in practice.

The first is quantized distances. A shard using PQ returns approximate distances. If shards use different codebooks, perhaps because one was trained on older data, their errors differ, and the merge ranks by error as much as by meaning. The fix is to rescore the merged candidates with exact distances before the final cut.

The second is hybrid search. Many RAG systems combine vectors with keyword scores such as BM25. BM25 uses inverse document frequency (how rare a term is), and each shard computes it from its own documents. The word "warranty" might be rare on one shard and common on another, so the same document would score differently depending on where it lives. Search engines handle this with a distributed frequency pass (in Elasticsearch and OpenSearch this is the dfs_query_then_fetch search type), or by fusing ranks instead of raw scores. Rank fusion sidesteps the problem because it uses only each shard's ordering.

Filtered search inside a shard

The lesson names the pre-filter versus post-filter trade-off. Here is why it is hard. An HNSW graph is navigable because each node links to nearby nodes. If a filter removes 99% of nodes, the walk keeps hitting excluded nodes and the surviving ones are poorly connected to each other. Recall collapses, or the search visits huge numbers of nodes looking for allowed ones.

Engines handle this in a few ways, and which ones a product uses varies:

  • Filter during the walk, skipping excluded nodes but still traversing through them. Works well when the filter keeps a large share of vectors.
  • Switch to brute force when the filter is very selective. If only 3,000 vectors pass, scanning them exactly takes well under a millisecond and is perfectly accurate.
  • Post-filter with oversampling. Ask the index for k / selectivity candidates, then filter. At 10% selectivity, that is 100 candidates for a top 10. At 0.1%, it is hopeless.
  • Partition by the filter. If one filter appears in almost every query, give it its own index. That is tenant sharding again, one level down.

Placement: directory, not hash

For tenant-keyed sharding, a hash of the tenant ID is the obvious placement, and it is usually the wrong one. Tenants differ in size by orders of magnitude. A hash places a giant tenant wherever it lands, and moving it later means changing the hash function.

Production systems keep a directory: a small table mapping tenant to shard group, cached in every coordinator. Small tenants are packed onto shared shards by size, as a bin-packing problem. Giants get dedicated shards. Moving a tenant becomes a controlled operation: build its index on the target, dual-write during the copy, flip the directory entry, drain, delete. The Consistent Hashing lesson's ring still fits the uniform design, where vectors have no natural owner.

Replication and index builds

Replicas give read capacity and availability. They also raise a question relational replicas do not: does each replica build its own index? Two designs exist.

  • Each replica applies the write log and builds its own segments. Simple, but index builds run on every replica, and replicas can briefly disagree about which vectors are searchable.
  • One node builds, others copy the finished segment files from shared object storage. Builds run once, and a new replica joins by downloading files rather than rebuilding. This is the main reason disaggregated designs, with compute separate from storage, have become common for large indexes.

The difference shows up most when a node dies. Rebuilding a 300 GB HNSW index from raw vectors can take hours. Downloading prebuilt segments takes minutes.

The graph overhead comes from the base layer holding about 2 × M links at 4 bytes each (128 bytes) plus a little for upper layers and IDs. Notice how small it is next to the vectors. The vectors themselves are the memory problem, so compressing them is the big lever.

Compression costs recall, and how much depends on the model and data. Binary codes work much better on some embedding models than others. Treat the rows as a menu to benchmark on your own data, not a promise. The common pattern is compressed vectors for the search and full vectors on SSD for rescoring the top few hundred candidates, which recovers most of the lost recall.

With float32 and HNSW, the 12-shard design matches the lesson. With two replicas per shard for reads and availability, that is 36 nodes. With int8 and three shards, it is 9. Quantization does not just postpone sharding. It changes the bill by a factor of four.

Tail amplification under scatter-gather

If one shard's latency exceeds its p99 one time in a hundred, and shards are independent, a query that waits for all N shards is slow whenever any of them is:

P(query slow) = 1 − 0.99^N

  • N = 4: 3.9%
  • N = 12: 11.4%
  • N = 50: 39.5%

So at 12 shards, the shard's p99 becomes roughly the coordinator's p89. To keep the coordinator's p99 near a target, each shard has to meet that target at about its p99.9 (1 − 0.999^12 ≈ 1.2%). That is the real cost of fan-out. It is why hedging exists, and why fewer, larger shards beat many small ones for latency.

The same formula can be run in a few lines, with a hedge added:

import random

def coordinator_p99(n_shards, hedge_ms=None, trials=100_000):
    def shard():                     # 99% fast (~8 ms), 1% slow (~80 ms)
        return random.gauss(8, 2) if random.random() < 0.99 else random.gauss(80, 20)
    def with_hedge():
        first = shard()
        if hedge_ms is None or first <= hedge_ms:
            return first
        return min(first, hedge_ms + shard())   # replica asked at hedge_ms
    lat = sorted(max(with_hedge() for _ in range(n_shards)) for _ in range(trials))
    return lat[int(0.99 * trials)]

print(coordinator_p99(12))                # roughly 100 ms: the tail dominates
print(coordinator_p99(12, hedge_ms=12))   # roughly 20-something ms

The exact numbers depend on the distribution you assume. The shape does not: without hedging, the slow tail of any one shard becomes the normal case for the coordinator.

Query capacity

Assume one HNSW query on one shard costs about 2 ms of CPU at ef_search = 100 on these dimensions. That number varies a lot with hardware, dimensions and recall targets, so benchmark it. A 32-core node then serves about 16,000 shard-queries per second at full use, call it 8,000 at a safe 50%.

  • Uniform scatter-gather, 12 shards: each user query costs 12 shard-queries, plus 5% for hedges. At 2,000 user queries per second, that is 25,200 shard-queries per second, spread over 12 shards: 2,100 per shard. One copy of each shard handles that. Replicas are for availability and for growth.
  • Tenant-keyed: each query costs one shard-query, so the same 2,000 per second costs 12× less CPU in total. The risk moves to skew: if one tenant sends 30% of traffic, its shard needs about 600 per second plus its replicas.
  • Centroid routing, 2 of 16 probed: about one-eighth of the uniform cost, but traffic follows topic popularity, as failure mode 4 shows.

The general rule: scatter-gather multiplies cost by N and keeps load even. Routing divides cost by N and concentrates load.

The re-embedding bill

The lesson says re-embedding is a projection rebuild. Here is the size of one. Assume 500 million chunks averaging 300 tokens, which is 150 billion tokens.

  • Through an embedding API at an assumed $0.02 per million tokens: about $3,000. Prices vary widely by provider and model, so recompute with your own. Rate limits usually matter more than price at this volume. Ask for a batch quota before you need it.
  • Self-hosted: assume one GPU embeds 3,000 chunks per second with a small model. That is about 46 GPU-hours, or roughly 2.5 hours on 20 GPUs.
  • Index build: HNSW insert throughput per node is often in the thousands to tens of thousands of vectors per second, depending on parameters. At 10,000 per second per node across 12 nodes, 500 million vectors take about 70 minutes.
  • Memory during the dual-run: v1 and v2 both serve, so you need twice the index memory for the duration. With float32 that is 36 extra nodes. Plan it, or migrate tenant by tenant so only a slice is doubled at once.

Deep Dive: Failure Modes in Production

1. The p99 that one shard owns

Symptom. Retrieval p99 jumps from 25 ms to 120 ms several times an hour, with no change in traffic. p50 is flat.

Mechanism. One shard at a time runs compaction, a segment index build, or a long garbage collection pause. Every query waits for every shard, so whichever shard is busy sets the latency for all queries during that window.

Detect. Per-shard latency histograms next to the coordinator's. The coordinator's spikes line up with one shard at a time, and that shard's logs show compaction or GC at the same moment.

Fix. Hedge to replicas after about the p95 delay. Throttle compaction and stagger it so only one replica of a shard compacts at a time, and route around it while it does. Keep segment counts low enough that query fan-out inside each shard stays small.

2. Recall that decays without anyone changing anything

Symptom. RAG answer quality slides over months. Retrieval latency is fine. No deploy lines up with the decline.

Mechanism. Two slow processes. In HNSW, heavy update and delete churn leaves tombstones that the graph must route around, and newly inserted nodes link less well than the original build. In IVF, the centroids were trained on last year's data. New content (a new product line) lands in lists that do not fit it well, and lists grow uneven.

Detect. Measure recall directly. For a small random sample of live queries, run an exact brute-force search on one shard in the background and compare its top 10 with the ANN result. Recall@10 against exact search is a metric you can graph and alert on.

Fix. Rebuild indexes on a schedule, or when tombstones exceed a set share. Retrain IVF centroids periodically and rebuild. Because the index is a read model (CQRS), a rebuild is routine, not risky.

3. The filter that empties the results

Symptom. Some queries return 2 or 3 results instead of 10. The assistant says "I don't have information on that" for products that clearly exist. It happens mostly to small tenants and narrow filters like "in stock, under $50".

Mechanism. Post-filtering on a shared index. The ANN search returns 20 candidates from the whole shard, and the tenant or stock filter removes most of them. With pre-filtering inside HNSW, a very selective filter leaves the graph poorly connected and the walk ends early.

Detect. A histogram of results returned per query, split by tenant size and filter selectivity. Queries returning fewer than k results should be a tracked metric, not something you hear about from support.

Fix. Partition by the filter that appears in every query (tenant). For other filters, use an engine that switches to exact search when the filtered set is small, or oversample by the inverse of selectivity. For range filters like price, a separate structured lookup followed by vector rescoring is sometimes simpler.

4. The hot cluster during a product launch

Symptom. On a centroid-routed index, the day a new phone launches, two shards hit 100% CPU while the rest idle. Latency on every query that probes them climbs.

Mechanism. Routing follows meaning. Every query about the new phone probes the same two clusters. Traffic per shard tracks topic popularity, which changes daily, while cluster placement changes only when someone re-clusters.

Detect. Per-shard query rate and CPU, and the share of probes landing on each cluster. A Gini coefficient or max/mean ratio of shard load is a useful single number.

Fix. Give hot shards more replicas, which can be automated from probe share. Split hot centroids during re-clustering. For predictable events, add replicas ahead of the launch, as the Autoscaling lesson does with scheduled scaling.

5. Two embedding models in one index

Symptom. During a re-embedding migration, results for some tenants turn to nonsense: a shipping question retrieves password-reset chunks. Other tenants are fine.

Mechanism. The migration rewrote vectors in place, tenant by tenant, in the same collection. Queries were embedded with v2 for migrated tenants, but a routing bug sent some of them to a shard that still held v1 vectors. Distances between vectors from different models mean nothing, and nearly random neighbours came back with normal-looking scores.

Detect. Store the model version on every vector and every query. Count, at the shard, every comparison whose versions differ. That counter must be zero. A drop in the mean top-1 score for a tenant is a weaker but useful signal.

Fix. Never migrate in place. Follow the zero-downtime migration shape. Put the model version in the collection or index name, so a v2 query physically cannot reach a v1 index. Cut over by flipping the directory entry for each tenant.

6. The node loss that takes all afternoon

Symptom. One node fails at 13:00. Its shards drop to one copy. By 17:00, replacement replicas are still rebuilding, and a second failure would mean partial results.

Mechanism. Each replica builds its own index from the raw vectors and the write log. Rebuilding a 300 GB HNSW index means re-inserting tens of millions of vectors. The rebuild also competes for CPU with live queries on the surviving replica, which slows both.

Detect. Under-replicated shard count and time to restore full replication, tracked as an SLO. Run a node-loss drill before the real one and write down how long it took.

Fix. Persist built segment files to object storage so new replicas download instead of rebuilding. Keep spare capacity so recovery does not starve queries. For the largest indexes, run three copies rather than two, so one rebuild is not a single point of failure.

7. Hybrid ranking that depends on where a document lives

Symptom. The same query returns a different top result after a rebalance. A document moved shards, and its rank changed even though its text did not.

Mechanism. Hybrid search combined vector scores with BM25 scores. BM25's term rarity is computed per shard. After the move, "warranty" was common on the document's new shard, so its keyword score fell.

Detect. A fixed evaluation set of queries with known best documents, run after every rebalance. Rank changes for unchanged documents are the giveaway.

Fix. Fuse by rank (reciprocal rank fusion) rather than by raw score, or compute term statistics globally. Then rescore the merged candidates consistently at the coordinator.

How to choose, in order

  1. Can it fit on one node? Do the memory table with quantization. If yes, run one node with replicas and stop.
  2. Does every query carry a filter? If yes, partition by it with a directory, and give giants dedicated shards.
  3. Otherwise, uniform plus scatter-gather, with oversampling, hedging, and as few shards as memory allows.
  4. Only at very large single-corpus scale, route by centroids, with recall measured against exact search as an SLO.
  5. Across all of these, version the index by embedding model, and make rebuilds cheap through segment files in object storage.

Deep Dive: Design-Review Checklist

  1. What is the memory per vector for the chosen index and precision, and have you checked whether quantization makes sharding unnecessary?
  2. Does every query carry a filter that could be the shard key? If not, why is scatter-gather acceptable for the cost and the tail?
  3. How many shards does a query touch, and what per-shard p99.9 does that require to meet the coordinator's p99?
  4. Is there a hedging policy, with what delay, and what does the coordinator return when a shard and its replica both fail?
  5. What per-shard k does the coordinator request, and are scores rescored or fused by rank before the final cut?
  6. How is recall measured in production: against exact search, on what sample, with what alert threshold?
  7. How are selective filters handled: partitions, exact-search fallback, or oversampling? What happens for the smallest tenants?
  8. Is placement a directory or a hash? What is the procedure to move a giant tenant, and how long does it take?
  9. How long does it take to restore full replication after losing a node, and has that been drilled?
  10. Is the embedding model version part of the index name, and is a cross-version comparison impossible rather than merely unlikely?
  11. What does a full re-embedding cost in money, GPU-hours, index build time and doubled memory, and is the quota in place?
  12. What are compaction and rebuild schedules, and do they avoid serving traffic from a node while it compacts?

Deep Dive: Senior Interview Follow-ups

"If each shard returns its top 10, is the merged top 10 exact?"

Only if each shard's search is exact. The global top 10 is always inside the union of the local exact top 10s, because any vector in the global top 10 is also in its own shard's top 10. But with ANN, each shard may miss some of its true neighbours, and those misses add up across shards. Asking each shard for 20 or 30 and rescoring the merged set raises recall cheaply, because the merge is tiny compared with the searches.

"Why not use more, smaller shards so each search is faster?"

Because the coordinator waits for the slowest shard. With N independent shards, the chance that at least one is in its slow tail is 1 − 0.99^N, about 11% at 12 shards and 40% at 50. Smaller shards are each faster, but the query's tail gets worse and the total CPU per query rises, since each shard has fixed per-query overhead. Use the fewest shards that memory allows, and get headroom from replicas.

"Your recall SLO is 95% at k = 10. How do you measure it in production?"

Sample a small share of live queries, say 0.1%, and run each against an exact brute-force search in the background, on one shard or on an offline copy. Compare the ANN top 10 with the exact top 10 and record the overlap. Graph it per shard and per tenant size class. This measures the index, not answer quality, so it catches graph decay, bad centroids and filter problems directly. Answer-level evals then sit on top.

"A tenant asks you to delete all their data within 30 days. What actually happens in the index?"

In a shared index, deletion usually writes tombstones. The vectors remain in memory and on disk until compaction rewrites the segments, and they may still sit in snapshots and backups. So "deleted" in the API is not "deleted" for compliance. Per-tenant partitions or collections make this simple: drop the partition, then handle backups by retention policy. If you must use a shared index, force compaction for affected segments and document the backup expiry, so the 30 days actually covers every copy.

"Pre-filter or post-filter for 'similar to this, in stock, under $50'?"

It depends on selectivity. If 60% of products pass, filtering during the graph walk works well. If 0.5% pass, the graph walk struggles, and post-filtering would need about 2,000 candidates for a top 10. The better plan there is to select the matching products first with a structured index, then score that small set exactly against the query vector. Good engines choose between these per query from an estimate of selectivity. If yours does not, the application has to.

"How do you move a giant tenant to a dedicated shard without downtime?"

With a directory, it is a small migration. Start dual-writing the tenant's new vectors to both the old and new location. Bulk-copy the existing vectors to the new shard and build its index. Verify counts and run the tenant's evaluation queries against both. Flip the directory entry so queries go to the new shard. Keep the old copy briefly for rollback, then delete it. With hash placement you cannot do this cleanly, which is the main reason to keep a directory.

"Is the vector database the source of truth?"

It should not be. The documents and the embedding model version are the source of truth, and the index is a read model derived from them. That is what makes re-embedding, re-clustering and rebuilding after corruption routine. If the index is the only place a vector or its metadata exists, every rebuild becomes a data recovery problem. Keep the chunk text and metadata in a durable store, and treat the index as something you can throw away and rebuild.

"When would you pick centroid routing over uniform scatter-gather?"

Only when the corpus is a single huge collection with no filter to route by, and the query rate makes full fan-out too expensive. For example, billions of vectors at thousands of queries per second, where 50-way fan-out would need far more hardware. You accept probabilistic recall, measured as an SLO, and you take on hot clusters and periodic re-clustering. Below that scale, uniform scatter-gather with a handful of large, quantized shards is simpler and more predictable.
