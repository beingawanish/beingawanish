Deep Dive: Inside the Mechanism

The lesson names five tools. In code they collapse into two pieces of state: what you store with each value, and how a rebuild is claimed and released. Get those two right and the tools are small branches in one read function. Get them wrong and you have built a new outage source with a lock in it.

The envelope: store more than the value

Plain cache-aside stores the value and lets the cache's TTL delete it. Every stampede tool needs the entry to outlive its freshness, so the value goes inside a small envelope:

product:8412 -> {
  "v":        { ...the product page data... },
  "soft_exp": 1767297600000,   // ms: after this, the value is stale
  "delta_ms": 48,              // how long the last rebuild took
  "ver":      9131             // source version the value was built from
}
Redis TTL on the key (the hard expiry) = soft TTL + grace, e.g. 3600 s + 600 s

Each field feeds one tool. soft_exp is the lesson's logical expiry: past it, the entry is served as stale while one refresh runs. The Redis TTL is the hard expiry, a safety net that removes data nobody refreshed. delta_ms feeds probabilistic early refresh, which needs to know how long a rebuild takes. ver stops a slow rebuild from overwriting a newer one, which comes up under the failure modes.

The gap between soft and hard expiry is the grace period. It is your answer to "how stale may this ever get if refresh keeps failing?" Pick it per data type, and write it down. It is the staleness sentence with a number in it.

The read path in one function

Here is the whole decision, as a sketch. cache is a Redis client and rebuild loads from the database:

import math, random, time, uuid

def get_product(pid, beta=1.0):
    env = cache.get_envelope(f"product:{pid}")          # None if hard-expired
    now = time.time() * 1000
    if env is not None:
        remaining = env.soft_exp - now
        if remaining > 0:
            # Tool 3: probabilistic early refresh (XFetch)
            if -env.delta_ms * beta * math.log(random.random()) < remaining:
                return env.v                             # fresh, no refresh
        # Early-refresh winner, or stale: Tool 2 + Tool 1
        try_refresh_in_background(pid)                   # lock-guarded
        return env.v                                     # never wait
    # Hard miss: Tool 1 only. Someone must wait.
    return rebuild_with_lock(pid, wait_ms=200)

Note the shape. Only the hard-miss branch ever blocks a user. Every other branch returns at cache speed. That is why the grace period matters so much: a key that is hot enough to stampede should never reach the hard-miss branch at all.

The lock, done properly

The lesson gives the acquire: SET lock:product:8412 <token> NX PX 3000. Three details decide whether it holds up in production.

  • The token is random and per attempt. A UUID, not the hostname. Release must check it: 
    -- release only if we still own it
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
    A plain DEL can remove a lock that expired and was then taken by someone else. Now two rebuilders run, and each believes it is alone. A release that returns 0 means your lock expired while you held it. Count that. It is a direct signal that the lock TTL is too short.
  • The TTL is sized from the slow tail, not the average. If rebuilds take 50 ms normally and 800 ms at p99.9 under load, a 100 ms lock fails exactly when it is needed. Start at several times the p99.9 rebuild time. For rebuilds that can run long, renew the lock from the holder every third of its TTL (a watchdog) and stop renewing if the rebuild is abandoned.
  • The write-back is conditional. The rebuilder read version 9131 from the database. Write the envelope only if the cached ver is lower, in one Lua script. Otherwise a slow rebuild that started before an update can land after a faster one and put old data back.

This is a lock for efficiency, not for correctness. If it fails, you get two rebuilds and some extra load, not corrupted data. That is the right kind of lock to build on a single Redis primary. If you ever find yourself needing a cache lock to be correct, the design has a different problem.

Two-tier single flight: in-process first, then shared

A distributed lock collapses the crowd across servers. It does nothing about the crowd inside one server. With 60 app instances, the 600 concurrent misses are about 10 per instance, and each of those 10 would hit Redis to try the lock and then poll.

So put an in-process coalescer in front. Go's singleflight.Group.Do runs a function once per key while other callers on the same key block and share the result. Java's Caffeine does the same in an AsyncLoadingCache, and its refreshAfterWrite gives you serve-stale-and-refresh inside the process. In Python, a dict of in-flight futures keyed by cache key does the job.

Now the funnel is 600 misses, then 60 lock attempts (one per instance), then 1 database query. The sizing section shows why that middle step is worth having.

How waiters learn the value is ready

Requests that lose the lock in the hard-miss branch need the result. Three ways to get it:

  • Poll. Sleep 10 to 20 ms with jitter, GET again, give up after a deadline. Simple and stateless. It costs extra reads on the hottest shard you have.
  • Notify. The rebuilder publishes on a channel such as ready:product:8412 after writing. Waiters subscribe before checking once more. Fewer reads, but more moving parts, and a lost message must still fall back to the deadline.
  • Don't wait. Return a degraded response at once: a stale copy from a local cache, a page without the recommendations strip, or a 503 with Retry-After. This is graceful degradation, and for anything non-critical it is usually the best answer.

The one thing a waiter must never do when its deadline passes is go to the database itself. That turns the deadline into a stampede with a delay on it.

Probabilistic early refresh, with the numbers

The XFetch rule is the one-liner in the code above. Each request computes gap = −δ · β · ln(rand) and refreshes if gap is at least the time left before soft expiry. Here δ is the rebuild time and β is a tuning knob, 1 by default. −ln(rand) is an exponential random number with mean 1, so the chance that one request triggers, with t left, is e^(−t / βδ). It is tiny far from expiry and climbs steeply as expiry gets close.

Plug in the bestseller: 12,000 requests a second, δ = 50 ms, β = 1. Summed over all requests, the expected number of triggers before expiry is R · β · δ = 600. The chance of reaching expiry with no trigger at all is e^(−600), which is zero for any practical purpose. The median trigger point comes from R·β·δ·e^(−t/βδ) = ln 2, which gives t = 0.05 · ln(866) ≈ 340 ms before expiry. That leaves plenty of time for a 50 ms rebuild.

Now a cold key at 1 request a second. R·β·δ = 0.05, so the chance of any early refresh is 1 − e^(−0.05), about 5%. The rest of the time it simply expires, and there is no crowd to worry about. That is the lesson's point, in numbers: the rule spends work only where traffic is.

Two practical notes. First, XFetch does not remove the need for the lock. Near the trigger point a hot key can see one or two more triggers during the 50 ms rebuild, so the refresh is still lock-guarded. Second, δ must be measured and stored with the entry. Guess it too low and keys refresh too late. Raise β to 2 or more if rebuild time is noisy. For the bestseller that moves the median trigger to about 750 ms early.

The same tools in proxies and CDNs

Often the cheapest place to stop a stampede is in front of the app. nginx has all three hot-key tools as directives:

proxy_cache_lock on;                 # single flight per cache key
proxy_cache_lock_timeout 5s;         # after this, waiters go to upstream (uncached!)
proxy_cache_use_stale updating error timeout http_503;
proxy_cache_background_update on;    # serve stale, refresh in the background

Read the comment on proxy_cache_lock_timeout carefully. When it fires, the waiting request goes to the upstream, and nginx does not cache that response. With a slow upstream, every waiter eventually reaches it. That is failure mode 2 below, built into a default.

HTTP origins can drive the same behaviour in shared caches with Cache-Control: max-age=60, stale-while-revalidate=30, stale-if-error=86400, from RFC 5861. Varnish coalesces concurrent misses for the same object by default and uses its grace setting for stale serving. Most CDNs offer request collapsing and an origin shield tier, though names and defaults vary by vendor.

Leases: when the cache itself coordinates

Facebook's memcache leases, from the paper the lesson cites, move single flight into the cache server. On a miss, the server hands out a lease token, and only a client holding a valid token may set the key. Other clients are told to wait briefly and retry. The server limits how often it issues tokens per key.

The clever part is that a delete invalidates any outstanding lease. A rebuilder that read the database before an update can no longer write its now-stale result. One mechanism handles both the thundering herd and the stale-set race. That is exactly what the ver check above does by hand.

Deep Dive: Sizing and the Numbers

Assumptions: 12,000 requests a second on the bestseller at peak, 60 app instances, a Redis cluster with consistent hashing, a database that runs comfortably at a few hundred queries a second and degrades past about 2,000.

The crowd is request rate times rebuild time

The lesson's core formula is N = R × d. It is worth tabulating, because the dangerous cell is often not the one people expect:

The top-right cell is the AI case from the lesson: a modest 10 requests a second, a 3-second generation, and already 30 duplicate paid generations per expiry. Rebuild cost multiplies the crowd, so slow rebuilds deserve protection at traffic levels where fast ones don't.

A useful threshold rule: protect a key when R × d is above about 1. Below that, two concurrent misses are rare, and the lock is overhead.

What waiting costs on the hot shard

Take the hard-miss case with a lock and polling at 20 ms. 599 losers each try SET NX once and poll about three times during a 50 ms rebuild. That is roughly 600 + 1,800 = 2,400 extra commands in 50 ms, all on the one shard that owns the bestseller. As a rate, that is about 48,000 commands a second, on top of the 12,000 reads it already serves. For 50 ms, the hot shard runs at five times its normal load.

Add in-process single flight and the losers drop from 599 to 59 (one per instance, minus the winner). Extra commands fall to about 240. That is the practical case for the two-tier design: it protects the cache, not only the database.

Now let the rebuild slow to 2 seconds under load, with no stale copy available. Waiters are 12,000 × 2 = 24,000, or 400 per instance. If each holds a worker thread or a connection, many servers run out. That is why the hard-miss branch needs a short deadline and a degraded answer, and why the grace period should be long enough that hot keys never land there.

Fleet numbers: steady expiry, jitter, cold start

Steady expiry load. With K active keys and TTL T, about K / T rebuilds happen each second, even with perfect protection. 30,000 active products at a one-hour TTL is about 8 rebuilds a second. At a 5-minute TTL it is 100. This is the floor that single flight protects. It doesn't make it smaller.

Jitter. 10,000 keys warmed in one minute with a 3,600-second TTL all expire in the same minute an hour later: about 170 rebuilds a second for 60 seconds. With ±10% uniform jitter, the expiries spread over 720 seconds, about 14 a second. Same total work, one-twelfth the peak.

Cold start. The lesson's drill warms 10,000 keys in about 40 seconds. That is itself 250 database queries a second, so the warmer should be rate-limited like any other client. Product traffic is skewed: if the top 10,000 keys carry 90% of requests, then at 12,000 requests a second the remaining 10% is 1,200 misses a second, mostly on distinct tail keys. Single flight can't merge distinct keys. So the database sees close to 1,200 queries a second, consistent with the lesson's "below 2,000." If that is too many, the traffic ramp is your control: start at 25% of traffic and step up as the hit ratio climbs.

Memory cost of the grace period

Stale serving keeps entries past their freshness. With a 600-second grace on a 3,600-second TTL, an entry that nobody reads lives about 17% longer. Expect resident memory to grow by up to that much for keys that would otherwise have expired. Under an LRU policy the cache will evict cold stale entries first anyway, so this is usually a small cost. Check it on the instance graph before and after.

Deep Dive: Failure Modes in Production

1. The lock expires under load, and the stampede comes back

Symptom. Protection works in tests and on normal days. During a slowdown, database load still spikes at each hot-key expiry.

Mechanism. The lock TTL was 100 ms, sized from the normal 50 ms rebuild. Under load, rebuilds took 600 ms. The lock expired mid-rebuild, a second request took it and started its own rebuild, then a third. The protection failed exactly when the database was slow, which is the only time it mattered. With plain DEL on release, the first rebuilder also deleted the second one's lock, opening the door further.

Detect. Rebuilds per key per expiry (should be 1). The compare-and-delete release returning 0. Lock TTL graphed against p99.9 rebuild time.

Fix. Size the TTL from the slow tail, renew it for long rebuilds, release with a token check, and make the hot key's normal path serve-stale so expiry of the lock costs latency at most, never a crowd.

2. Waiters give up and go to the database

Symptom. Database queries at an expiry show a delayed spike: one query at 8:00:00.000, then hundreds at 8:00:00.200.

Mechanism. Waiters had a 200 ms deadline, and the fallback on timeout was "load it yourself." The rebuild took 250 ms that day, so every waiter hit the database at once, 200 ms late. The nginx version is proxy_cache_lock_timeout: after it fires, waiting requests go upstream and their responses are not cached.

Detect. A counter for "waiter deadline exceeded," split by what the waiter did next. Database queries per key per second at sub-second resolution.

Fix. On deadline, return stale, a degraded page, or an error with Retry-After. In nginx, pair the lock with proxy_cache_use_stale updating so most waiters never wait, and set the lock timeout above the upstream's slow tail.

3. A write to a hot key causes the stampede

Symptom. No TTL expired, yet the bestseller's page stalls for a moment every time merchandising edits it.

Mechanism. Cache-aside invalidates by deleting the key. Deleting a hot key throws away the stale copy that serve-stale depends on, so every write drops straight into the hard-miss branch: 600 requests, one rebuild, 599 waiting. Expiry was protected. Invalidation was not.

Detect. Hard misses on keys that had a value a moment earlier. Correlate latency spikes with write events for that key.

Fix. Soft invalidation. On write, set soft_exp to now (and bump the expected version) instead of deleting. The next reader serves the old copy for one rebuild time and triggers the locked refresh. For a display price that means about 50 ms of the old price, which is fine while checkout reads the source. For data where even that is unacceptable, write the new value through instead of invalidating.

4. A slow rebuild puts old data back

Symptom. After a price change, the old price reappears on the page and stays for a full TTL.

Mechanism. Rebuild A read the price at 8:00:00.000 and then stalled. At 8:00:00.100 the price changed and the key was invalidated. Rebuild B read the new price and wrote it. At 8:00:00.300 rebuild A woke up and wrote the old price over it. The lock didn't help: A's lock had already expired, which is how B ran at all.

Detect. Periodic sampling that compares cached ver to the source version for hot keys. A cached version lower than one already seen for that key is this bug.

Fix. Conditional write-back on ver, in one script, as described above. Memcache leases solve the same problem by invalidating the lease on delete.

5. Stale forever: refresh keeps failing and nobody notices

Symptom. A product shows a price that was changed six hours ago. Every request is a fast hit.

Mechanism. Background refreshes for that key fail, perhaps because the loader throws on a new field. Serve-stale keeps returning the old envelope, exactly as designed, and the grace period was set to "never" because "stale is better than an error." From the outside, everything looks healthy.

Detect. Track age of the value served (now minus the build time) as a histogram, with a per-data-type alert on its maximum. Count refresh failures per key. A hit ratio of 100% on a key that should refresh every five minutes is a smell, not a success.

Fix. Always set a hard expiry. Past it, fail or degrade visibly. Alert on refresh failure rate. stale-if-error is valuable, but give it a bound you would defend in a postmortem.

6. A hot key melts one cache shard, with a perfect hit ratio

Symptom. During the sale, one Redis node is at 100% CPU or its network link is saturated. The others are idle. Hit ratio is 99.9%.

Mechanism. All traffic for one key goes to one shard, and consistent hashing can't spread a single key. If the bestseller's envelope is 50 KB, then 12,000 reads a second is 600 MB/s, close to 5 Gbit/s from one node. Stampede tools reduce database work. They do nothing for cache-side load.

Detect. Per-node CPU and network graphs, not cluster averages. redis-cli --hotkeys lists hot keys when the instance uses an LFU eviction policy. Client-side per-key request counters are more reliable.

Fix. A small in-process cache (an L1) for the top keys, with a TTL of 1 to 5 seconds. With 60 instances, the shard then sees about 60 reads a second for that key instead of 12,000. Alternatively, keep several copies under different keys, product:8412#0..7, and read one at random. The L1 adds up to its TTL of staleness, which goes in the staleness sentence.

7. Misses that no tool can merge: cache penetration

Symptom. Database load climbs while the hit ratio on real products is normal. The queries are for product IDs that don't exist.

Mechanism. A scraper, or a bug that builds IDs from a counter, requests random IDs. Each one misses, the database returns nothing, nothing is cached, and the next request misses again. Single flight merges duplicates, but these are all distinct. Serve-stale has nothing to serve.

Detect. Database queries returning zero rows, as a rate. Miss ratio split by "found" and "not found."

Fix. Negative caching: store a "not found" marker with a short TTL, say 30 to 60 seconds. For a known ID space, a Bloom filter of valid IDs in front of the cache rejects most bogus IDs in memory. Rate-limit the client that generates them, through the rate limiting layer.

Two opinions. First, push coalescing as far out as it will go. A CDN or proxy that collapses requests protects every service behind it, needs no application code, and is usually already deployed. Application-level locks are for what the edge can't see: fragments, per-user data, multi-source assembly.

Second, make serve-stale the default and the lock the backstop, not the other way round. A lock on its own still makes users wait and still fails ugly when the rebuild is slow. Serve-stale turns most expiries into a non-event. The lock then only has to cover the rare hard miss and keep refreshes to one.

Deep Dive: Design-Review Checklist

  1. Which keys have R × d above about 1 at peak? Show the measurement, not a guess.
  2. For each data type, what are the soft TTL, the grace period and the hard TTL? What is the staleness sentence at the end of the grace period?
  3. How is the lock TTL chosen, relative to p99.9 rebuild time under load? Is there renewal for long rebuilds?
  4. Does release check a per-attempt token? Is a failed release counted?
  5. What does a waiter do when its deadline passes? Show that the answer is not "query the database."
  6. How are writes to hot keys invalidated: delete, soft invalidation, or write-through? What happens to the hot key's traffic in the next 100 ms?
  7. Is the write-back conditional on a source version, so a slow rebuild can't restore old data?
  8. Is there in-process coalescing in front of the shared lock, and what extra load does the hard-miss case put on the hot cache shard?
  9. Are TTLs jittered everywhere, including keys written by bulk warmers and deploy-time preloads?
  10. What is the cold-start runbook: warm source, warmer rate limit, traffic ramp steps, and the expected database load at each step?
  11. Which metrics prove it works: concurrent misses per key, rebuilds per expiry, waiter timeouts, age of value served, refresh failures?
  12. Is there negative caching or a filter for IDs that don't exist?

Deep Dive: Senior Interview Follow-ups

"You've added a Redis lock. Why do you still need serve-stale?"

The lock bounds database work at one query, but everyone else waits. If the rebuild takes 50 ms, that is a blip. If the database is slow and the rebuild takes 2 seconds, 24,000 requests are waiting on the bestseller alone, holding threads and connections. Serve-stale removes the wait: users get the old copy in a millisecond and one refresh runs behind. The lock keeps that refresh to one. Each covers the other's weak spot.

"Isn't a Redis lock unsafe? What about Redlock and clock drift?"

It is unsafe as a correctness lock, and that is fine here. If the lock fails, two requests rebuild the same key and the database does a little extra work. Nothing is corrupted, because the write-back is conditional on the source version. You don't need consensus to avoid a duplicate read. If a lock were guarding something like a payment, it would need fencing tokens checked by the resource itself, and a cache lock would be the wrong tool.

"Explain why XFetch refreshes hot keys early but leaves cold keys alone."

Each request triggers with probability e^(−t/βδ), where t is time to expiry. The chance that someone has triggered grows with how many requests arrive. The expected number of triggers before expiry is R·β·δ. At 12,000 requests a second and a 50 ms rebuild that is 600, so the key almost surely refreshes, typically about 340 ms early. At 1 request a second it is 0.05, so 95% of the time the key just expires, which is harmless because there is no crowd. No per-key configuration is needed; traffic picks the keys.

"An editor changes the bestseller's price during the sale. Walk me through the next 100 ms."

With delete-on-write: the key vanishes, about 600 requests miss during the rebuild, one takes the lock, the rest wait or degrade, and the shard absorbs a burst of polling. With soft invalidation: the write sets the soft expiry to now. The next request sees a stale entry, triggers one locked refresh, and returns the old price. For about 50 ms, the page shows the old price. Checkout reads the database, so no order uses it. The rebuilt envelope carries the new version, and a straggling rebuild from before the change can't overwrite it.

"Your hit ratio is 99.9%. Why is one Redis node at 100% CPU?"

Because the stampede tools protect the database, not the cache. One hot key lives on one shard, and every read for it goes there. Fix it with a short-TTL in-process cache for the top keys, which cuts that shard's load to roughly one read per app instance per TTL, or with replicated copies of the key under different names. Then add the L1's TTL to the staleness budget.

"Requests time out waiting for the lock. What should they do?"

Anything except query the database. Return a stale copy if one exists anywhere (local cache, a replica, the CDN), return the page without that fragment, or return an error with Retry-After. If every timed-out waiter fetches for itself, the timeout just reschedules the stampede for later, when the database is already struggling. Also check why they timed out: usually the lock deadline is shorter than the rebuild's slow tail.

"How would you protect an LLM-backed answer cache from stampedes?"

The same tools, with the thresholds moved. With a 3-second generation, even 10 requests a second makes 30 duplicates per expiry, and each costs money. Coalesce identical prompts with in-process single flight plus a shared lock, serve the previous answer while one regeneration runs if the content allows, and use long, jittered TTLs. For hot prompts, refresh ahead on a schedule. Track duplicate generations per key as a cost metric. A semantic cache widens what counts as "identical," and it needs single flight on its cluster keys for the same reason.

"When is all of this over-engineering?"

When no key has R × d near 1. A service at 100 requests a second spread over thousands of keys never forms a crowd. Jitter on bulk-written TTLs is still worth one line. The rest should wait until metrics show concurrent misses on the same key. The opposite failure is more common: nobody measures until a flash sale does it for them.
