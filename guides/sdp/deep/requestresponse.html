Deep Dive: Inside the Mechanism

The lesson treats a synchronous call as one arrow. In production that arrow is a stack of moving parts: a connection pool, a wire protocol, a deadline, and a retry policy. Each part has knobs. Most outages that blame "the network" are really one of those knobs set wrong.

What a new connection really costs

Before the first byte of a request can travel, the client pays for setup. TCP needs one round trip for its handshake. TLS 1.3 adds one more round trip. TLS 1.2 adds two. Then the request itself takes a round trip.

Take checkout in one region calling a pricing service in another, with a 70 ms round trip:

  • New connection, TLS 1.3: 70 (TCP) + 70 (TLS) + 70 (request) = 210 ms.
  • New connection, TLS 1.2: 70 + 140 + 70 = 280 ms.
  • Reused connection: 70 ms.

So a cold connection triples or quadruples the cost of a cross-region call. TLS 1.3 also offers 0-RTT resumption, which sends data with the first handshake message. It comes with a catch: 0-RTT data can be replayed by an attacker, so servers should accept it only for idempotent requests. Inside a data center the round trip is well under a millisecond, so the handshake matters less for latency. It still costs CPU, and the TLS key exchange is the expensive part.

The pool and its four knobs

A connection pool keeps open connections per destination and lends them to requests. Every HTTP client has one, and each exposes roughly the same knobs:

  • Maximum connections per host. Caps concurrency to one destination. Too low, and requests queue inside your own process waiting for a connection. Too high, and a slow dependency can soak up thousands of sockets.
  • Maximum idle connections. How many open-but-unused connections to keep. Go's http.Transport keeps only 2 idle connections per host by default (MaxIdleConnsPerHost). Python's requests keeps 10 per host (pool_maxsize). Under real concurrency both defaults cause connection churn.
  • Idle timeout. How long an unused connection stays open. This must be shorter than the server's or load balancer's idle timeout, or you get the race described in failure mode 1.
  • Maximum lifetime. Closes connections after a fixed age even when busy. This lets DNS changes and new backend instances take effect. Without it, a long-lived pool keeps talking to the same few servers forever.

A fifth knob hides in most clients: the acquire timeout, or how long a request waits for a free connection. Many clients wait forever by default. That turns a slow dependency into a blocked caller, which is exactly what the Bulkhead lesson guards against.

HTTP/1.1, HTTP/2 and gRPC on the wire

HTTP/1.1 sends one request at a time per connection. Pipelining exists in the spec, but almost nothing uses it, because responses must come back in order. So concurrency means more connections. Browsers open about six per host. A service calling another at 500 requests in flight needs about 500 connections.

HTTP/2 splits one TCP connection into many streams. Each request and its response is a stream with its own ID. The protocol cuts everything into small binary frames (HEADERS, DATA, SETTINGS, WINDOW_UPDATE, RST_STREAM, GOAWAY) and interleaves frames from different streams. Three details matter in design reviews:

  • Concurrent stream limit. The server announces SETTINGS_MAX_CONCURRENT_STREAMS. A value of 100 is common, though it varies by server. Past that limit, the client must queue or open another connection.
  • Flow control. Each stream and the connection as a whole have a receive window. The default initial window is 65,535 bytes. A receiver that reads slowly stops the sender on that stream. Large transfers over high-latency links need bigger windows, or throughput collapses.
  • Cancellation. RST_STREAM cancels one request without closing the connection. On HTTP/1.1 the only way to abandon a request is to close the whole connection, which then has to be rebuilt.

HTTP/2 removes head-of-line blocking at the request level, but not at the TCP level. TCP delivers bytes in order. When one packet is lost, every stream on that connection waits for the retransmission. On clean data-center networks this rarely shows. On lossy mobile links it does, and that is the main reason HTTP/3 runs over QUIC, which keeps streams independent.

gRPC is a contract on top of HTTP/2: Protocol Buffers for the body, a method path like /pricing.Pricing/GetQuote, status codes in trailers, and four call shapes (unary, server streaming, client streaming, bidirectional). It also carries the call's deadline in a header, grpc-timeout. That one header is the most useful thing gRPC adds, as the next section shows.

Timeouts versus deadlines

A timeout is a duration that one hop picks for itself: "wait 2 s for pricing." A deadline is an absolute point in time that the whole request shares: "this checkout must be done by 12:00:00.800." The difference shows up as soon as the chain is more than one hop deep.

Clients usually have three separate timeouts. The connect timeout covers the TCP and TLS setup; keep it short, around a few round trips. The read timeout covers the gap between bytes and often resets every time a byte arrives. That means a server trickling one byte per second never trips it. The total timeout covers the whole call. Only the total timeout protects you, and it is the one most often left unset.

With deadline propagation, each hop forwards the time remaining, minus what it has already spent. gRPC does this for you when you pass the incoming context into the outgoing call. With plain HTTP you do it by hand, often with a header like X-Request-Deadline. The server should check the remaining budget before doing expensive work. A request whose caller has already given up is pure waste.

Which methods are safe to retry

HTTP semantics (RFC 9110) split methods into two groups that matter for retries. Safe methods (GET, HEAD, OPTIONS, TRACE) promise not to change state. Idempotent methods are the safe ones plus PUT and DELETE: sending them twice leaves the same result as sending them once. POST and PATCH promise neither.

The method is a promise, not a guarantee. A GET that increments a view counter breaks it. A POST can become safe to retry with an Idempotency-Key header, which the server stores alongside the result, as the Idempotency lesson builds. The rule that ties this together:

Whether a retry is safe depends on two things: whether the request could have reached the server, and whether running it twice is harmless.

A refused connection never reached the server, so any method can be retried. A timeout after the request was sent is ambiguous: the server may have done the work. Only idempotent requests, or ones carrying an idempotency key, can be retried after that.

gRPC lets you declare this per method in its service config: a retryPolicy with maxAttempts, backoff settings and retryableStatusCodes (usually just UNAVAILABLE), plus a retryThrottling token bucket that stops retries when the failure rate climbs. It also supports a hedgingPolicy, covered below.

Deep Dive: Sizing and the Numbers

Sizing the pool with Little's law

Little's law says that the number of requests in flight equals the arrival rate times the time each one spends in the system. It is the only formula you need for pool sizing.

Checkout calls pricing at 300 requests per second. Pricing's median latency is 40 ms and its p99 is 250 ms.

  • At the median: 300 x 0.040 = 12 connections in use.
  • During a slow minute where every call takes the p99: 300 x 0.250 = 75 connections.
  • If pricing hangs until your 2-second timeout: 300 x 2 = 600 connections.

Size the pool for the bad-but-normal case (here about 75 to 100), not the median. Then set the acquire timeout short, say 50 ms. If pricing degrades further, extra requests fail fast instead of piling up behind the pool. On HTTP/2 the same math gives streams, not connections. 75 concurrent streams fit on one connection with a 100-stream limit, though running two or more connections spreads the load across backends.

Ephemeral ports and connection churn

Every outbound connection uses a local port. Linux's default ephemeral range is 32768 to 60999, about 28,000 ports. When the client closes a connection, that port sits in TIME_WAIT for 60 seconds on Linux before reuse.

So one client host talking to one destination IP and port can sustain only about 28,000 / 60, or roughly 470 new connections per second. A service that opens a fresh connection per request at 1,000 requests per second runs out of ports within a minute. Pooling fixes this completely: 75 pooled connections serve the same traffic with no churn at all.

Fan-out and the tail

Suppose a product page fans out in parallel to N backends, and each backend is slow (past its p99) 1% of the time, independently. The page is slow whenever any backend is slow:

This is the core result of Dean and Barroso's "The Tail at Scale." With five parallel calls, your endpoint's p95 is roughly each backend's p99. With a search page that queries 100 index shards, the backend's p99 becomes the page's median. Improving the average does nothing here. Only the tail of each backend matters.

Utilization makes the tail worse. In a simple queueing model (M/M/1), time in the system is service time divided by (1 − utilization). A backend with a 10 ms service time takes about 20 ms at 50% utilization, 50 ms at 80%, and 100 ms at 90%. Run fan-out backends hot and the tail explodes first.

Hedged requests: buying the tail with load

A hedged request sends a second copy of a call to another replica if the first has not answered within some delay, then uses whichever answer comes first. Set the delay at the backend's p95, and only about 5% of calls send a second copy. You pay about 5% extra load and, for reads, cut the tail sharply. The Tail at Scale paper reports a large p99.9 reduction for a small load increase in Google's own tests.

Two limits apply. Hedge only idempotent reads. And cancel the loser (HTTP/2's RST_STREAM makes this cheap), or the extra load stays on the backend.

Retry amplification

Say each layer makes up to 3 attempts (1 try plus 2 retries). Checkout calls payment, payment calls fraud, fraud calls a feature store. When the feature store is down, every layer retries:

3 (checkout) x 3 (payment) x 3 (fraud) = 27 attempts on the feature store for one user click.

At 300 checkouts per second, that is 8,100 requests per second against a service that is already failing. Add a fourth layer and it becomes 81x. The fix is structural: retry at one layer only (usually the one closest to the user, or the one with the idempotency key), and cap retries as a share of traffic. A retry budget such as "retries may add at most 10% to normal request volume" keeps the worst case at 1.1x instead of 27x.

Splitting a latency budget

The store's checkout SLO is 800 ms at the edge. A workable split, with numbers you can redo:

  • Edge and auth: 50 ms.
  • Cart, pricing and inventory in parallel: the slowest p99 is 150 ms, so set the timeout at 200 ms.
  • Payment, which calls fraud: p99 300 ms, timeout 400 ms. One retry does not fit inside the budget, so payment gets zero retries here and relies on its idempotency key for a user-driven retry.
  • Remaining slack: 800 − 50 − 200 − 400 = 150 ms for serialization, network and margin.

Notice that the budget, not a habit, decided the retry count. A retry is only worth having if it can finish before the deadline.

Deep Dive: Failure Modes in Production

1. Random 502s during quiet periods

Symptom. A small, steady trickle of 502 errors at the load balancer. They get worse at night, when traffic is low, which feels backwards.

Mechanism. The load balancer keeps idle connections to the backend for 60 seconds (AWS ALB's default idle timeout). The backend is a Node.js server, whose keepAliveTimeout defaults to 5 seconds. After 5 idle seconds the backend closes the connection. If the load balancer sends a request on it at that same moment, the backend answers with a TCP reset and the load balancer returns 502. Low traffic means more idle connections hitting that window.

Detect. 502s at the load balancer with no matching error in the application log. Load balancer logs show the backend closed the connection or reset it. Packet captures show a RST right after the request.

Fix. The side that reuses a connection must give up on it first. Set the server's keep-alive timeout longer than the load balancer's (for Node.js, also raise headersTimeout above it). For your own clients, set the pool's idle timeout below the server's. Also allow an automatic retry when a reused connection fails before any response byte arrives, since the request never ran.

2. "Cannot assign requested address"

Symptom. Under load, outbound calls fail with EADDRNOTAVAIL, while the destination is perfectly healthy.

Mechanism. The client opens a new connection per request, or its idle pool is too small (Go's default of 2 idle connections per host is the classic case). Connections close as fast as they open. Closed ports pile up in TIME_WAIT, and the roughly 470-per-second limit from the sizing section is hit.

Detect. ss -s shows tens of thousands of sockets in TIME_WAIT. The connection-open rate per host is close to the request rate.

Fix. Raise the idle pool size to match concurrency and make sure response bodies are fully read and closed (an unread body often prevents the connection from returning to the pool). Kernel tweaks like widening the port range buy time, but they do not fix the cause.

3. One slow dependency takes down everything

Symptom. The recommendations service slows down. Minutes later, checkout, search and login all time out, even though they never call recommendations.

Mechanism. The web tier shares one worker pool, say 200 threads. Each recommendation call now takes 5 s instead of 50 ms. Little's law: at 50 calls per second, 250 threads are needed just for recommendations. They take every thread, and unrelated requests have nothing left to run on.

Detect. Thread pool or connection pool utilization near 100%, with the acquire-wait time climbing. A trace of a stuck login shows it waiting for a thread, not for any downstream service.

Fix. Give each dependency its own capped pool (Bulkhead), a short acquire timeout, a total timeout well below 5 s, and a circuit breaker. Async I/O frameworks move the limit from threads to memory and sockets, but the same math applies.

4. Retry storm keeps a service down

Symptom. The fraud service has a 30-second blip and recovers. But its traffic is now 10x normal and it falls over again, and again.

Mechanism. Nested retries multiply (27x in the sizing example). Retries without jitter also line up, so they arrive in synchronized waves. Every client's timeout fires at the same moment, retries go out together, and the recovering service sees a spike far bigger than normal load.

Detect. Compare requests received by the backend with unique user requests at the edge. A ratio far above 1 is amplification. Tracing shows the same call repeated many times inside one trace.

Fix. One retrying layer, exponential backoff with full jitter (see Retry with Exponential Backoff), a retry budget, and respect for Retry-After on 429 and 503. Servers should shed load early with a cheap 503 instead of slowly timing out.

5. New pods get no traffic

Symptom. You scale a gRPC service from 4 pods to 12 during a spike. The 4 old pods stay at 95% CPU. The 8 new ones sit idle.

Mechanism. A layer-4 load balancer, such as a Kubernetes ClusterIP service, balances connections, not requests. gRPC clients open one HTTP/2 connection and multiplex every call over it for hours. Existing connections never move, so new pods only get clients that connect after they start.

Detect. Per-pod request rate is badly skewed while connection counts stay flat. The pattern appears after every scale-out or deploy.

Fix. Balance per request at layer 7 (Envoy, a service mesh, or a gRPC-aware load balancer), or use client-side round-robin over a headless service. Also set a server-side maximum connection age (gRPC's MAX_CONNECTION_AGE), which sends GOAWAY so clients reconnect and spread out.

6. Work nobody is waiting for

Symptom. During an incident the database is at 100% CPU. Most of its queries belong to requests that already returned errors to users.

Mechanism. The edge times out at 1 s. But checkout uses its own fresh 3-second timeout toward inventory, and inventory gives the database 10 seconds. Nobody forwards the deadline. When the edge gives up, the work below keeps running for up to 10 seconds, and the user's retry adds a second copy on top. The system does more work the slower it gets.

Detect. Nginx logs status 499 (client closed request) in large numbers. Server-side spans finish long after their parent span was cancelled. gRPC logs CANCELLED and DEADLINE_EXCEEDED on the server side.

Fix. Propagate the deadline. Make every hop's timeout the minimum of its own limit and the time remaining. Check the remaining budget before queuing or starting expensive work, and drop requests from internal queues whose deadline has passed. Cancel downstream calls when the upstream request is cancelled.

7. The p99 nobody can find

Symptom. The search page's p99 is 900 ms. Every one of its 40 shard backends reports a p99 under 150 ms. Each team insists their service is fine.

Mechanism. Fan-out math. With 40 shards, 1 − 0.9940 = 33% of page loads hit at least one shard's p99. The page's p99 is therefore set by the shards' p99.9 and worse: garbage-collection pauses, cold caches, one noisy neighbor. Averages and per-service p99s hide this.

Detect. Look at the slowest span inside each slow trace, not at per-service dashboards. Distributed tracing with tail-based sampling keeps the slow traces you need. Rotate through shards: usually a different one is slowest each time.

Fix. Reduce fan-out where you can, hedge reads after the p95, return partial results when a few shards miss the deadline (with a flag saying so), and set alerts on backend p99.9, not p99.

Pick one layer per call path that owns retries, and turn them off elsewhere. Timeouts are the opposite: every layer needs one, all derived from the same propagated deadline.

Taming the tail: retry, hedge or tie

  • Retry after timeout. Cheap, but the user has already waited the full timeout. Good for rare failures, useless for tail latency.
  • Hedge after the p95. About 5% extra load, big tail improvement. Only for idempotent reads.
  • Tied requests. Send to two replicas at once, each told about the other. Whichever starts first cancels its twin. Best tail, but it needs server support and cross-replica messaging. Rare outside very large systems.
  • Partial results. Answer with what arrived by the deadline. Often the best choice for search and feeds, and the core of Graceful Degradation.

A deadline-aware retry, in code

This sketch shows the three rules together: retry only idempotent requests or ones with a key, never past the deadline, and only within a budget. It uses only the Python standard library.

import random, time, urllib.request, urllib.error

RETRYABLE = {429, 502, 503, 504}

def call(url, deadline, method="GET", body=None, key=None, budget=None):
    """deadline: absolute time.monotonic() value shared by the whole request."""
    safe_to_retry = method in {"GET", "HEAD", "PUT", "DELETE"} or key is not None
    attempt = 0
    while True:
        remaining = deadline - time.monotonic()
        if remaining <= 0.005:
            raise TimeoutError("deadline exceeded before sending")
        req = urllib.request.Request(url, data=body, method=method)
        req.add_header("X-Request-Deadline-Ms", str(int(remaining * 1000)))
        if key:
            req.add_header("Idempotency-Key", key)
        try:
            with urllib.request.urlopen(req, timeout=remaining) as resp:
                return resp.read()
        except urllib.error.HTTPError as e:
            if e.code not in RETRYABLE:
                raise
            err = e
        except (urllib.error.URLError, TimeoutError) as e:
            err = e
        attempt += 1
        if not safe_to_retry or attempt >= 3 or (budget and not budget.try_spend()):
            raise err
        backoff = random.uniform(0, 0.05 * 2 ** attempt)   # full jitter
        if time.monotonic() + backoff >= deadline:
            raise err
        time.sleep(backoff)

budget.try_spend() stands for a token bucket that refills by 0.1 token per normal request, which caps retries at about 10% of traffic. Note that urlopen's timeout applies per socket operation, not to the whole call. That is the read-timeout trap from the mechanism section, so production code needs a client with a true total timeout.

Deep Dive: Design-Review Checklist

  1. For each synchronous arrow, is there a total timeout, and is it derived from a propagated deadline rather than picked per hop?
  2. Is every client's pool idle timeout shorter than the idle timeout of the server or load balancer it talks to?
  3. Was the pool sized from Little's law at the dependency's p99 latency, and does it have a short acquire timeout?
  4. Which single layer owns retries on this path, and are retries off everywhere else?
  5. Is each retried call idempotent by method or by idempotency key? What happens on an ambiguous timeout for a POST?
  6. Is there a retry budget or token bucket, and do clients honor Retry-After?
  7. For gRPC or HTTP/2, how is load spread per request: L7 balancer, mesh or client-side? Is there a maximum connection age?
  8. What is the fan-out of the slowest endpoint, and what is the backend p99.9 that sets its tail?
  9. Can the endpoint return partial results, and does the response say when it did?
  10. Do servers check the remaining deadline before expensive work, and cancel downstream calls when the caller cancels?
  11. Are 499s, retry ratios and pool acquire-wait times on a dashboard?
  12. Does each dependency have its own pool or bulkhead, so one slow service cannot starve the rest?

Deep Dive: Senior Interview Follow-ups

"You moved from HTTP/1.1 to gRPC and p99 got worse. Why might that be?"

Three common causes. First, connection stickiness: all traffic rides a few long-lived HTTP/2 connections, so a few backends run hot while others idle, and hot backends have bad tails. Second, TCP head-of-line blocking: one lost packet now stalls every multiplexed call instead of one. Third, a stream limit: if the client hits MAX_CONCURRENT_STREAMS, calls queue on the client without obvious metrics. Check per-pod request skew first; it is the most common one.

"A call to payment timed out. Do you retry it?"

Only if the retry cannot double-charge. A timeout after sending is ambiguous: payment may have charged the card. So the retry must carry the same idempotency key as the first attempt, and the payment service must return the stored result for a repeated key. Without a key, do not retry automatically. Instead, query payment status, or mark the order "payment pending" and reconcile. Also check the deadline: if no retry can finish in time, fail and let the user-facing layer decide.

"Why not just set a generous timeout, like 30 seconds, so nothing fails?"

Because the timeout sets how many threads and connections a slow dependency can hold. By Little's law, 300 requests per second times 30 seconds is 9,000 requests in flight. That exhausts any pool, so a slow pricing service now takes down checkout. Also, the user left long before 30 seconds. A timeout should sit a little above the dependency's p99.9 and below the caller's remaining budget.

"An endpoint fans out to 50 services in parallel. Each has p99 of 100 ms. What is the endpoint's p99?"

Much worse than 100 ms. 1 − 0.9950 is about 39%, so 39% of requests hit at least one backend's p99. The endpoint's median is near the backends' p99, and its p99 is set by their p99.98 or so, assuming independence. To fix it: cut the fan-out, hedge reads after the p95, or return partial results at a deadline.

"What is the difference between a timeout and a deadline, and why does it matter in a chain?"

A timeout is relative and local to one hop. A deadline is absolute and shared by the whole request. With per-hop timeouts, inner hops can wait longer than the outer caller, so they keep working after the user got an error. With a propagated deadline, every hop knows how much time is left, skips work that cannot finish, and cancels its children when time runs out.

"Retries at every layer seem safer. What is wrong with that?"

They multiply. Three attempts at each of three layers means 27 attempts at the bottom for one user click, which hits the weakest service exactly when it is struggling. Retry at one layer, add jittered backoff, and cap retries with a budget, for example 10% of normal traffic. Then the worst case is 1.1x load, not 27x.

"Your clients see occasional connection-reset errors on idle connections. Is retrying them safe?"

It depends on when the reset happened. If the connection failed before any byte of the request was accepted, the server never saw it, so a retry is safe for any method. Many HTTP clients do this automatically for reused connections. If the reset came after the request was sent, the outcome is ambiguous again, and only idempotent requests can be retried. The real fix is to make the client's idle timeout shorter than the server's, so the race rarely happens.

"How do you size a connection pool for a new dependency?"

Little's law: rate times latency. Use the dependency's p99 latency, not its median, and peak rate, not average. At 300 requests per second and 250 ms p99, that is 75 concurrent connections. Round up for headroom. Then add a short acquire timeout so that when the dependency gets slower than planned, extra requests fail fast instead of queueing. Also check the server side: 50 client instances with 100 connections each is 5,000 connections at the server.
