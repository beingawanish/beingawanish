Deep Dive: The Capacity Plan, Box by Box

The lesson's headline is 50 requests per second at peak, which sounds small. For an LLM system, requests are the wrong unit. Tokens are what cost money and GPU time, and an agent task multiplies them in a way a chat turn does not. Here is the plan with its assumptions written down.

The extra assumptions

  • Mix at peak: 40 chat turns per second and 10 new agent tasks per second.
  • A chat turn: about 9,000 input tokens (system prompt and tool schemas ~3,000, retrieved context ~4,000, conversation history ~2,000) and about 400 output tokens. One model call.
  • An agent task: six model calls. The first starts at 5,000 input tokens. Each step adds about 1,500 tokens of tool results and model output to the context. Each call writes about 300 output tokens.
  • Daily average: about a third of peak.
  • Prices: illustrative only, $3 per million input tokens and $15 per million output tokens, with cached input billed at a tenth of that. Real prices vary by model and provider and change often. Redo the line with yours.

Agent context grows with every step

An agent's model calls are not the same size. Each one re-sends everything so far. The six calls in one task carry 5,000, 6,500, 8,000, 9,500, 11,000 and 12,500 input tokens. That is 52,500 input tokens for one task, almost six chat turns' worth, plus 1,800 output tokens.

The growth is quadratic in the number of steps. A 12-step task carries about 5,000 × 12 + 1,500 × 66 = 159,000 input tokens, three times the 6-step task for twice the steps. This is the single most important number in the plan. It is why a step cap is a cost control, not only a safety control, and why large tool results must not be pasted whole into context.

Two things stand out. Agents are a fifth of requests but most of the tokens. And input outnumbers output by about 26 to 1.

What it costs

At a third of peak on average, the day carries about 25 billion input tokens and 1 billion output tokens. At the illustrative prices, input is about $76,000 a day and output about $15,000. Input dominates, which surprises people who think of output as the expensive part. It is more expensive per token. There is just far more input.

That makes prefix caching the biggest cost lever in the design. The system prompt, tool schemas and the growing agent context are the same from one call to the next. If 60% of input tokens hit the provider's prompt cache at a tenth of the price, input cost drops from about $76,000 to about $35,000 a day. Getting that hit rate takes discipline. Keep the stable parts of the prompt first and byte-identical across calls. Put anything that changes per request (timestamps, the user's name) after them. One timestamp near the top of the system prompt can destroy the cache for every call.

Across 500K sellers, $50,000 a day is about $3 per seller per month. That is a real line on an invoice, which is why per-tenant metering is in the requirements.

If you serve the model yourself

Self-hosting changes the unit from dollars to GPU replicas. Output tokens set the size, because generating them is the slow, sequential part. Suppose one replica of the chosen model sustains about 2,500 output tokens per second across its batch while still streaming each user a readable speed. That number depends heavily on the model, hardware and serving stack, so measure it. Then 34,000 output tokens per second needs about 14 replicas for decode. Prefill for 885,000 input tokens per second adds its own load, and prefix caching inside the serving engine cuts that too. Plan around 20 replicas at peak with headroom, and autoscale on queue depth, as the GPU autoscaling lesson describes.

Deep Dive: Inside Durable Execution for an Agent

The lesson says the agent loop runs on durable execution and resumes instead of re-running. The mechanism has one detail that matters more for agents than for any other workflow.

Record the model's output, not only that it ran

Durable execution engines such as Temporal work by replay. The workflow code runs again from the start after a crash. Each step that already completed returns its recorded result from the history instead of running again. The code reaches the first unrecorded step and continues from there.

That only works if the workflow code is deterministic. An ordinary workflow keeps side effects in recorded steps and its own logic is plain code. An agent's logic is a model call, which is not deterministic. Run the same prompt twice and the model may choose a different tool with different arguments.

So every model call must be a recorded step, with its full output stored. On resume, step three's decision is read from the log, not asked again. If you only recorded "step three ran," the resumed task would ask the model again, get a different plan, and create a second promotion with a different idempotency key. The idempotency keys would not help, because the steps are genuinely different. Recording the decision is what makes resume mean resume.

Two practical notes. First, large tool results do not belong in the prompt or the log row. Store them as artifacts and give the model a summary and a handle, which also controls the quadratic context growth from the capacity plan. Second, the prompt and the workflow code will change while tasks are in flight. A task started on prompt version 12 should finish on version 12. Pin the version in the task's history and let new tasks pick up new versions. Durable engines call this workflow versioning, and agents need it more than most, since their behaviour lives in prompts.

Idempotency at the action service

The key (task_id, step_id) only helps if the action service honours it. The promotions service should store the key with the promotion it created and return that same promotion on a repeat. The messaging service needs the same, plus one more guard. Its send is the pivot, so it should write the message to an outbox keyed by the idempotency key in the same transaction that records the send. A crash between "sent to provider" and "recorded" then cannot cause a second send to 40K customers. These guarantees live in the action services, not in the agent. An action service that ignores idempotency keys cannot be offered to an agent.

Deep Dive: Authorisation the Model Cannot Touch

The lesson's rule is that runtime rules enforce authorisation and prompts do not. Three concrete mechanisms make that true.

Bind identity arguments in the runtime

A tool like get_sales(seller_id, start, end) invites a confused-deputy bug. The runtime has authority to read any seller's data. If the model fills in seller_id, a prompt injection or a plain mistake can ask for someone else's.

The fix is to remove identity from the model's view of the tool. The schema the model sees is get_sales(start, end). The runtime adds seller_id from the authenticated session before the call, and the read service checks it again against the caller's token. The model cannot pass what it cannot see. The same applies to the RAG filter: the tenant ID comes from the session, never from the query the model writes.

Approve the exact action, not a description of it

Approval gates have a time-of-check problem. The agent asks, "Launch a 10% promo on 12 slow movers?" The seller approves. Then the model, at execution time, produces arguments for 15 items at 20%. The seller approved a sentence. The runtime executed something else.

So the approval is bound to a hash of the exact, canonical arguments. The runtime executes only an action whose hash matches an approval token, and the token expires.

import hashlib, hmac, json, time

SECRET = b"rotate-me"            # from the runtime's secret store, never the prompt

def approval_token(task_id: str, tool: str, args: dict, ttl_s: int = 3600) -> str:
    body = json.dumps({"task": task_id, "tool": tool, "args": args,
                       "exp": int(time.time()) + ttl_s},
                      sort_keys=True, separators=(",", ":"))
    sig = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    return body + "." + sig

def may_execute(token: str, task_id: str, tool: str, args: dict) -> bool:
    body, _, sig = token.rpartition(".")
    want = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, want):
        return False
    claim = json.loads(body)
    return (claim["task"] == task_id and claim["tool"] == tool
            and claim["args"] == args and claim["exp"] > time.time())

The seller's approval screen renders from the same canonical arguments that were hashed, not from the model's prose. What the seller sees is what runs.

Track taint, and close the exfiltration channels

The lesson removes messaging tools from tasks that read customer messages. Generalise it as taint. A task's context becomes tainted the moment untrusted content enters it: a customer message, a seller-uploaded document, a web page. The runtime computes the allowed tool set from the task's taint and the seller's settings, at every step. Taint never decreases within a task.

The dangerous combination has three parts: access to private data, exposure to untrusted content, and a way to send data out. Some practitioners call it the lethal trifecta. Any two are manageable. All three in one task is how data leaks. A tainted task that can read sales figures must have no outbound channel.

Outbound channels are not only tools. If the chat UI renders Markdown images, an injected instruction can make the model write an image link whose URL contains private data, and the browser fetches it. Render model output with external images and links disabled, or restricted to an allowlist of domains. This is a front-end control, and it belongs in the threat model next to the tool allowlist.

Deep Dive: Caching and Fairness Across Tenants

The semantic cache has a tenant boundary

The lesson puts a semantic cache in front. Its scope decides whether it is safe. "How do I set up shipping rules?" has the same answer for every seller, and can be shared. "Why did my sales dip?" has an answer built from one seller's private data. If that answer is cached globally and another seller's similar question matches it, the cache leaks one seller's numbers to another.

So the cache key includes a scope. Answers built only from shared help docs are cached globally. Answers that used any private tool or document are cached per tenant, or not at all. The runtime knows which tools a turn called, so it can set the scope automatically. Do not ask the model whether its answer was private.

Expect the hit rate to be lower than in the RAG chatbot. Shared how-to questions cache well. Analytics questions are personal and time-sensitive, and should usually skip the cache. Measure the hit rate per scope before claiming savings from it.

Fairness in numbers

One large seller starts a batch of 500 agent tasks to rewrite every listing. At 52,500 input tokens each, that is 26M input tokens, about half a minute of the whole platform's peak input rate. Without controls, those calls fill the serving queue, and every other seller's chat waits.

The gateway enforces three layers. A per-tenant token budget per minute, a token bucket refilled at the seller's plan rate. A priority class per request, where interactive chat outranks background tasks. And a concurrency cap per tenant, so one seller's tasks take at most a few percent of in-flight calls. Batch tasks fill the spare capacity and yield when interactive traffic rises. On self-hosted serving, the same priority classes map to the scheduler's preemption, as the GPU lesson describes.

Deep Dive: Failure Drills

The lesson walks the main failures. These seven are the subtler ones that show up once agents act on real data.

Drill 1: A resumed task takes a different path

Symptom. After a worker restart, some sellers have two promotions where they asked for one, with different discounts. Mechanism. The runtime recorded that model step three ran but not its output. On resume it called the model again, which chose 15% instead of 10%, under a new step ID. The idempotency key did not match the first promotion. Detection. Compare action counts per task with the plan; count resumed tasks whose replayed steps called the model. Fix. Record every model output as a step result and replay it on resume. A model call is a side effect on your bill and your plan, so treat it like one.

Drill 2: The approved action is not the executed action

Symptom. A seller complains that the copilot discounted items they did not approve. Mechanism. Approval was given on the model's summary. The tool call was generated again after approval with different arguments. Detection. Log the hash of approved arguments and executed arguments for every gated action, and alert on any mismatch. There should be none. Fix. Approval tokens bound to canonical arguments, as above. Render approval screens from those arguments.

Drill 3: One seller sees another's numbers

Symptom. A seller reports an answer quoting revenue figures that are not theirs. Mechanism. A semantic cache keyed only on question meaning. Seller A asked about last week's dip, the answer was cached globally, and seller B's similar question matched it. Detection. Canary tenants: synthetic sellers with marker values in their data, and a monitor that searches every response for another tenant's markers. Fix. Scope cache entries by the data the answer used. Treat this as a security incident, because it is one.

Drill 4: A tool returns a 200,000-token CSV

Symptom. Cost per task spikes for some sellers. Some tasks fail with context-length errors. Mechanism. An export tool returns all order rows. The runtime pastes the result into context. Every later step re-sends it, so the quadratic growth now starts from 200,000 tokens. Detection. Tokens per tool result, and the distribution of input tokens per call. Fix. Cap tool result size in the runtime. Store large results as artifacts and give the model a summary, a schema and a handle. Give it tools to query the artifact (filter, aggregate) instead of reading it whole.

Drill 5: Retries amplify a provider's rate limit

Symptom. The provider starts returning 429 Too Many Requests. Within minutes, the gateway is sending three times its normal request rate and almost everything fails. Mechanism. Each layer retries: the SDK, the gateway and the agent runtime. Three layers of three retries is up to 27 attempts per call, all into a provider that is already refusing work. Detection. Attempts per logical call, and 429 rate per provider. Fix. Retry in exactly one layer, the gateway, with a retry budget (retries capped at, say, 10% of requests). Honour Retry-After. Queue background tasks instead of retrying them, and let interactive chat fall down the provider ladder. The retry lesson's rules apply, with tokens as the unit.

Drill 6: Data leaves through a rendered link

Symptom. A security review finds outbound requests from sellers' browsers to an unknown domain, with sales numbers in the query string. Mechanism. A customer message contained an instruction to "include this tracking image" with a URL template. The task was tainted but had no outbound tools, so it looked safe. The model wrote a Markdown image. The browser fetched it. Detection. Content Security Policy violation reports from the browser, and scans of model output for URLs to non-allowlisted domains. Fix. Disable external images in rendered output, restrict links to an allowlist, and set a strict Content Security Policy. The output renderer is part of the agent's capability set.

Drill 7: Billing disagrees with the provider's invoice

Symptom. Monthly provider cost is 8% higher than the sum of tenant usage. Mechanism. The metering pipeline recorded usage once per logical model call, keyed by (task_id, step_id). The provider billed every attempt, including retries that timed out after generating tokens. Detection. Reconcile metered tokens against the provider's usage report daily, as the payment design reconciles its books. Fix. Meter two things. Cost metering records every attempt, keyed by attempt ID, to match the provider. Billing metering records what the tenant is charged under your pricing policy, which may exclude your own retries. Each consumer gets the guarantee and the definition it needs.

The longest debate is usually build versus buy for durable execution. A homegrown step table looks like a weekend of work. Then come durable timers for approvals, replay on resume, versioning across prompt changes, and visibility into stuck tasks. That is the feature list of a workflow engine. If tasks are short and have no approvals, the table is fine. Once approvals arrive, adopt an engine.

A second debate is about how much autonomy to ship by default. The lesson's answer, autonomy by action class with seller-configured relaxations, is right. The numbers that inform the defaults come from the canary metrics: approval rate, rejection rate at approval, and compensation rate after execution. If sellers approve 99% of listing edits without changes, auto-approving that class with an undo window is a safe step. If they reject 15% of promotion plans, keep promotions gated.

Deep Dive: The Evolution Path

  1. Stage 1: read-only help assistant. RAG over shared help docs, SSE streaming, one hosted model behind a thin gateway with per-tenant token limits. No private data, no actions. Ship it and start collecting questions for the eval set.
  2. Stage 2: read tools. Seller analytics through projections, identity bound by the runtime, answers stamped with their data's as-of time. Cache scope rules arrive here, because answers now contain private data.
  3. Stage 3: compensable actions with approval for everything. Listing edits and promotions, each behind a bound approval token. Durable execution and the step log arrive, because approvals wait.
  4. Stage 4: budgets, taint and autonomy settings. Action budgets, loop detection, taint-based tool sets. Some action classes move to auto-approve with undo windows, based on measured approval rates.
  5. Stage 5: irreversible actions and the provider ladder. Customer messaging behind the pivot rules, outbox-backed sends, a secondary provider for text, and fail-closed actions on degradation. Metering splits into cost and billing.
  6. Stage 6: scale and cost. Self-hosted serving for the highest-volume model, prompt layout tuned for prefix caching, fair scheduling between interactive and batch tasks. Proactive tasks run on schedules, and the same runtime handles them.

Deep Dive: Design-Review Checklist

  1. What are input and output tokens per second at peak, and what share comes from agent tasks?
  2. How does context grow per step, and what caps it: step limits, result size limits, artifacts?
  3. What is the prefix cache hit rate, and is the prompt laid out to protect it?
  4. On resume, does a model step return its recorded output or call the model again?
  5. Does every action service honour the idempotency key, and which ones use an outbox?
  6. Which tool arguments does the runtime bind, and can the model ever supply a tenant or seller ID?
  7. Is each approval bound to the exact arguments that will execute? When does it expire?
  8. How is taint tracked, and which outbound channels (tools, links, images) are closed for tainted tasks?
  9. What scope does each semantic cache entry have, and who decides it?
  10. How many layers retry a model call? Where is the retry budget?
  11. Do metered tokens reconcile against the provider's usage report?
  12. Which canary metrics block a model or prompt rollout?

Deep Dive: Senior Interview Follow-ups

"It's only 50 requests per second. Why does this need a capacity plan?"

Because requests are the wrong unit. One agent task re-sends its growing context on every step, so six steps cost about 52,500 input tokens, and twelve steps cost three times that. At peak the system moves nearly 900,000 input tokens per second, which is tens of thousands of dollars a day at typical prices or a fleet of GPU replicas. The plan exists to show that step count and context size drive cost, and to put caps on both.

"Why record the model's output in the step log? Can't you just re-run the step?"

Re-running a model call is not idempotent. The same prompt can produce a different tool choice or different arguments, so a resumed task could follow a new plan and create resources the first plan already created under other keys. Durable execution only means "resume" if every nondeterministic step returns its recorded result on replay. For agents, the model is the main nondeterministic step.

"A seller asks the copilot to email customers who complained. The complaints contain injected instructions. Walk me through it."

Reading the complaints taints the task. From that step on, the runtime removes outbound tools from the model's schema. So the task can draft emails but not send them. The drafts go to an approval screen rendered from canonical arguments: recipients, subject, body. The seller approves the exact batch, which produces a token bound to that batch. A separate, untainted execution step sends exactly that batch through the messaging service's outbox. Injected text can change a draft, which the seller sees. It cannot change who receives it after approval, and it cannot trigger a send.

"How do you stop one tenant's batch job from slowing everyone's chat?"

Three controls at the gateway: a token bucket per tenant, a priority class per request, and a per-tenant concurrency cap. Interactive chat outranks background tasks, so batch work only uses spare capacity. On self-hosted serving, the scheduler preempts batch requests when interactive load rises. Cost attribution then shows the large tenant on their invoice. Fairness is enforced in the serving path, not requested in the prompt.

"The provider is down. Chat works on the fallback model. Do agent tasks continue?"

Their text steps can, labelled as coming from the fallback. Their action steps pause. The action boundary was evaluated with the primary model, and a different model's plan has not passed those evals. The task waits durably, with a status the seller can see, and resumes when the primary returns or the seller chooses to cancel. Durable execution makes pausing cheap: a paused task costs a row, not a thread.

"Can you guarantee the copilot never takes a wrong action?"

No, and saying yes would fail the interview. What you can guarantee is the size of the damage. Each action class has a budget, irreversible actions need bound approval, compensable actions have designed undos, and the step log records exactly what ran. Then you measure the rates that matter: actions compensated, approvals rejected, complaints per thousand tasks. Safety here is bounded and observable risk, the same way the payment platform treats money.

"Your per-seller cost is about $3 a month. Product wants to make the copilot free. What changes?"

The budgets become the product. Free tiers get a token budget per month, lower step caps and the smaller model for drafting. Heavy users see a usage meter, and the gateway enforces it. Engineering levers lower the baseline: better prefix caching, shorter tool schemas, summarised tool results, and routing easy questions to a small model. The architecture does not change. The cost numbers decide which levers are pulled, and the metering pipeline proves whether they worked.
