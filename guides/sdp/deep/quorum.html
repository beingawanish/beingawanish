Deep Dive: Inside the Mechanism

W + R > N is one line of arithmetic. A real leaderless store is a few thousand lines of machinery around it. Which machines hold a key? Which replicas does the coordinator actually contact? What counts as an acknowledgment? How do deletes work when any replica might have missed one? This section follows a cart write and a cart read through Cassandra, the most widely deployed Dynamo-style store, and notes where Riak and others differ.

Placement: which N machines hold a key

The cluster hashes each partition key onto a ring of token ranges, as described in the consistent hashing lesson. The first node clockwise from the key's token holds the first replica. Walking further around the ring gives the rest. The list of N nodes is the key's replica set (Dynamo's paper calls it the preference list).

The walk is not naive. In Cassandra, NetworkTopologyStrategy places replicas per datacenter and tries to put them on different racks:

CREATE KEYSPACE carts WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'eu-west': 3,      -- N = 3 in this datacenter
  'us-east': 3       -- and another 3 here
};

Rack awareness matters more than it looks. If all three replicas of a key share a rack or availability zone, one zone failure removes all of them at once. The availability math later assumes independent failures. Rack placement is what makes that assumption roughly true. Configure the snitch so each node reports its real zone as its rack.

Any node can coordinate any request. Token-aware client drivers send each request straight to a replica of the key, which saves a network hop. The coordinator is then itself one of the N.

The write path: send to all, wait for W

For a write, the coordinator sends the mutation to all N replicas, not just W of them. It replies to the client as soon as W acknowledge. The other replicas still receive the write a moment later. W only decides how long the client waits, not how many copies are written.

On each replica, an acknowledgment means the mutation is in the commit log and the in-memory memtable. Whether the commit log has been fsynced depends on commitlog_sync. The default periodic mode syncs on a timer (10 seconds by default), so a replica can acknowledge a write it would lose in a power failure. The defence is replication itself: losing W replicas at the same instant is unlikely. Treat that as a stated assumption, not a given. If your three replicas share one power domain, batch or group sync mode makes acknowledgments durable at the cost of latency.

Each written cell carries a timestamp, normally set by the coordinator or the client in microseconds. Conflicts resolve by last-write-wins on that timestamp, per cell. Cassandra has no vector clocks. Riak, by contrast, keeps causal context (dotted version vectors) and can return concurrent versions as siblings for the application to merge. The next lesson shows why that difference matters for the cart.

The read path: one data request, digests, and repair

The lesson's coordinator "asks all three replicas". Cassandra is more economical, and the difference explains some of its latency behaviour. At QUORUM with N = 3, the coordinator contacts only R = 2 replicas. It asks the fastest-looking one (by its dynamic snitch scores) for the full data. It asks the other for a digest, a hash of the data.

If the digest matches, the coordinator returns A's data. If it does not, the coordinator fetches full data from both, merges them cell by cell (newest timestamp wins), and writes the merged result back to whichever replica was behind. Since Cassandra 4.0 this read repair is blocking by default: the coordinator waits for the repair write to succeed before answering. The table option read_repair can be set to 'BLOCKING' or 'NONE'. Older versions also had probabilistic background repair (read_repair_chance), which 4.0 removed.

Blocking matters for a subtle reason covered in the isolation section below: it is what makes quorum reads monotonic. Without it, one read can return the new value and the next read, through a different pair, can return the old one.

What about the slow replica? Cassandra's speculative_retry table option (default 99p, the replica's 99th-percentile latency) sends an extra request to the third replica when one of the first two has not answered within that time. That is how the "fastest W" straggler benefit from the lesson shows up in practice. Disable speculative retry and a QUORUM read is only as fast as the slower of the two replicas the coordinator happened to pick.

Two details catch teams out. First, LOCAL_QUORUM writes and LOCAL_QUORUM reads overlap only within one datacenter. A user who writes in eu-west and then reads in us-east has no overlap guarantee. The cross-region copy arrives asynchronously. Second, Cassandra uses strict quorums: hints written for a down replica do not count toward W, except at ANY. The sloppy quorums from the lesson are a Dynamo and Riak behaviour. Riak exposes the distinction as PW and PR (primary write and read), which count only true replicas.

Hinted handoff, anti-entropy and the tombstone deadline

When a replica is down, the coordinator stores a hint, a copy of the write addressed to the missing replica, and replays it when that replica returns. Cassandra stops collecting hints for a node that has been down longer than max_hint_window (3 hours by default). Past that window, the only way to bring the replica back in line is repair.

Repair is Cassandra's anti-entropy. nodetool repair builds Merkle trees (trees of hashes over token ranges) on each replica, compares them, and streams only the ranges that differ. Incremental repair, made reliable in Cassandra 4.0, tracks which data was already repaired. Tools such as Cassandra Reaper schedule repairs so they run continuously in small slices rather than as one huge job.

Deletes are where repair becomes mandatory. A delete writes a tombstone, a marker saying "this cell is gone as of timestamp T". Compaction may drop a tombstone once it is older than the table's gc_grace_seconds (864,000 seconds, 10 days, by default). Now suppose replica C missed the delete and was not repaired within 10 days. A and B purge their tombstone. C still holds the old value. The next repair or read repair sees C's value as the only version and copies it back everywhere. The deleted item returns. This is data resurrection, and it makes the rule simple: every replica must be fully repaired more often than gc_grace_seconds.

Overlap is not linearizability

The lesson is careful to call W=2, R=2 "overlap visibility", not strong consistency. Here is a concrete case that shows the gap, even with no concurrent writers.

  1. A write of "sneakers" has reached replica A only. It is in progress; B and C are a few milliseconds behind.
  2. Reader 1 reads A and B. It sees "sneakers" on A, newer than B's value, and returns sneakers.
  3. Reader 2 starts after reader 1 finished. It reads B and C. Neither has the write yet. It returns the old cart.

Reader 2 started later but saw an older value. No completed write was missed, because the write was not complete yet. But a linearizable system would never show a value and then "un-show" it. The fix is the second half of the classic ABD algorithm. Before returning a value, a reader writes it back to a quorum. Then any later quorum read must see it. Blocking read repair is exactly that write-back, applied when replicas disagree. That is why Cassandra 4.0 made it the default. Even so, Cassandra's last-write-wins on client timestamps means it does not claim linearizability for ordinary reads and writes. Lightweight transactions (SERIAL) are the linearizable path, and they cost Paxos rounds.

Quorums inside leader-based systems

Quorum counting is not only a leaderless idea. Several leader-based systems use it for the durability half of a write.

  • Kafka with acks=all and min.insync.replicas=2 on a replication factor of 3: the leader acknowledges a write once 2 in-sync replicas have it. The leader orders writes, so there are no forks.
  • PostgreSQL quorum commit: synchronous_standby_names = 'ANY 1 (s1, s2)' makes a commit wait until any one of two standbys confirms it. With the primary, that is 2 of 3 copies.
  • Raft (etcd, and many distributed SQL stores) commits a log entry once a majority holds it. Reads go through the leader or a read index, which gives linearizability. That is the "consensus instead of overlap" route the lesson recommends for exactly-one-winner problems.
  • DynamoDB, despite its name, does not expose leaderless quorums. Each partition has a leader that orders writes. A strongly consistent read goes to the leader and costs twice the read capacity of an eventually consistent read, which may be served by any replica.

The common thread: a majority overlap guarantees that durable data survives a minority failure. What differs is whether something also orders the writes. In Raft and Kafka, the leader does. In Cassandra, the timestamps do, and that is weaker.

Deep Dive: Sizing and the Numbers

Assumptions for the bookstore cart: 10 million active carts, 2 KB each, 50,000 cart reads and 10,000 cart writes per second at peak, N = 3 in one region, and machines that are each up 99.9% of the time, failing independently.

Availability per consistency level

Let q = 0.001 be the chance a given replica is down. A request at level k out of 3 fails when more than 3 - k replicas are down.

Level (N = 3)Fails whenProbability of failureAvailabilityDowntime per year
ONE (k = 1)All 3 downq³ = 10⁻⁹99.9999999%Effectively none
QUORUM (k = 2)2 or more down3q² ≈ 3 x 10⁻⁶99.9997%About 1.6 minutes
ALL (k = 3)Any 1 down1 - 0.999³ ≈ 0.00399.7%About 26 hours

QUORUM keeps almost all the availability of ONE and avoids the cliff of ALL. With N = 5 and a quorum of 3, failure needs three replicas down at once: about 10q³ = 10⁻⁸. Going from 3 to 5 replicas buys tolerance of two simultaneous failures, which matters during rolling restarts. While one node is down for maintenance, N = 3 at QUORUM has no spare left. N = 5 still has one.

These numbers assume independence. A zone outage that takes out two replicas together turns 3q² into "the probability of a zone outage", which is far larger. Rack-aware placement is what keeps the table honest.

Tail latency: why the second-fastest of three is fast

Say each replica answers within 10 ms 99% of the time, so the chance that one replica is slower than 10 ms is s = 0.01. Treat replicas as independent.

  • Wait for one specific replica: slower than 10 ms with probability 1%.
  • Wait for all three (ALL): slower if any is slow, 1 - 0.99³ ≈ 2.97%. ALL turns a per-replica p99 into roughly a p97.
  • Wait for the fastest 2 of 3: slower only if at least two are slow, 3s²(1 - s) + s³ ≈ 0.03%. The per-replica p99 of 10 ms becomes roughly the request's p99.97.

That last number is the straggler benefit from the lesson, quantified. But note the condition: it holds only if the coordinator actually asks all three and takes the fastest two. Cassandra's write path does (it sends to all N). Its read path asks only R replicas, so the speculative retry is what recovers most of the benefit. Correlated slowness, like a GC pause on a shared host or a congested switch, also breaks the independence. Measure it rather than trusting the formula.

Request amplification

  • Writes: always sent to all 3 replicas. 10,000 writes per second become 30,000 replica writes, whatever W is.
  • Reads at QUORUM: 1 data request + 1 digest request = 2 replica requests. 50,000 reads become 100,000 replica reads. Speculative retries add a few percent more, roughly the share of requests that pass the p99 threshold.
  • Read repair: if 0.5% of reads find a mismatch, that is 250 extra full reads and 250 repair writes per second. Small, until a replica falls behind and the mismatch rate jumps.
  • Reads at ONE: 50,000 replica reads. Half the read load, at the price of the overlap guarantee.

So the cluster serves about 130,000 replica operations per second for 60,000 client operations. Size the nodes for the first number.

Storage and headroom

10 million carts x 2 KB = 20 GB of logical data. Times N = 3, that is 60 GB on disk before overhead. That is small. But compaction needs free space to rewrite SSTables. With size-tiered compaction, plan for large compactions temporarily needing about as much free space as the data being compacted. Tombstones from cart deletions and expired carts also stay on disk until gc_grace_seconds passes. A cart workload with heavy churn can carry more tombstones than live data. Leaving a disk at most about half full is a common rule for size-tiered tables. Leveled compaction needs less headroom but does more write I/O.

Hints during a node outage

Replica B goes down for 2 hours. In a three-node cluster with N = 3, every key has a replica on B, so every write produces a hint for it. At 10,000 writes per second, 2 hours is 72 million hints. At about 1 KB each, that is around 72 GB of hints spread over the coordinators.

When B returns, those hints replay at the rate set by hinted_handoff_throttle (it has been 1024 KB per second per delivery thread by default, and the setting name varies by version). At around 1 MB per second, 72 GB takes many hours to replay. So for long outages, repair is often faster than waiting for hints. And past the 3-hour max_hint_window, repair is the only option.

How stale is W = 1, R = 1 in practice?

The lesson says W=1/R=1 is "eventually consistent". You can put a number on "eventually". Suppose replication to the other replicas takes 2 ms at the median and 20 ms at p99, and a user rereads 500 ms after writing. Almost every reread is fresh, because 500 ms is far beyond replication delay. Now suppose a page fires a write and then a read 5 ms later. Some reads arrive before the write has reached their replica. With R = 1 that read has a 2 in 3 chance of hitting a replica other than the one that took the write. Research on "probabilistically bounded staleness" (PBS) shows how to estimate this from measured replication latencies. The practical lesson: W=1/R=1 is fine for "eventually", poor for "immediately after".

Deep Dive: Failure Modes in Production

1. The deleted item that came back

Symptom. Customers report items reappearing in carts they emptied weeks ago. It happens after a node was rebuilt or after a big repair run.

Mechanism. One replica missed the delete while it was down, and it was not repaired within gc_grace_seconds. The other replicas compacted their tombstones away. The stale replica's old value was then the only version left, and repair helpfully spread it.

Detect. Track the time since the last successful full repair per table and node, and alert when it approaches gc_grace_seconds. Tools like Reaper expose this directly. Resurrection itself is hard to detect; the alert has to fire before it happens.

Fix. Run repair continuously, finishing each full cycle well inside the grace period. Never bring back a node that has been down longer than gc_grace_seconds. Wipe it and rebuild it from its peers. For a cart, consider TTLs (expiring carts after 30 days) so stale data expires instead of relying only on deletes.

2. Writes that succeed and then vanish

Symptom. A customer adds an item, gets a success response, and the item never appears. Retries also "succeed" and also vanish. Only some app servers are affected.

Mechanism. Last-write-wins on timestamps. One app server's clock runs 3 seconds fast and sets client-side timestamps. Its writes carry timestamps from the future. For the next 3 seconds, every correctly-timed write to the same cell has an older timestamp and silently loses. The write was acknowledged by W replicas. It just lost the merge.

Detect. NTP or chrony offset per host, with an alert at tens of milliseconds, not seconds. Cell write timestamps compared with server receive time. A test that writes then reads at QUORUM and checks the value.

Fix. Keep clocks tightly synchronized. Prefer server-side timestamps unless you need client ones. Model the cart so concurrent changes do not overwrite each other: one row per cart item instead of one blob, or a merge-friendly data type. For true read-modify-write, use a lightweight transaction (IF condition) and accept its cost. The vector clocks lesson covers the causal alternative.

3. Read-your-writes broken by mixed consistency levels

Symptom. The flickering cart from the lesson returns, but only on one page. Every replica is healthy.

Mechanism. The "add to cart" endpoint writes at ONE for speed, a change someone made months ago. The cart page reads at QUORUM. 1 + 2 = 3, which is not greater than 3, so the read pair can miss the one replica that took the write. Each statement looks reasonable alone. The guarantee comes from the pair.

Detect. Audit consistency levels per statement, not per service. Driver metrics usually expose the level per request. Grep the code for statement-level overrides.

Fix. Set consistency levels in one place per dataset, as named profiles (most drivers support execution profiles), and review them as product decisions. Add a test that checks W + R > N for every write/read pair on a key that needs read-your-writes.

4. The driver that quietly lowered the consistency level

Symptom. During a node failure, error rates stay at zero, which looks great. Afterwards, support tickets show stale carts from exactly that window.

Mechanism. The client used a downgrading retry policy. When a QUORUM request could not get enough replicas, the driver retried at a lower level and reported success. Older DataStax Java drivers shipped such a policy, and the 4.x driver deprecated it for this reason. The application asked for overlap and silently received ONE.

Detect. Driver metrics for retries and the consistency level actually achieved. Any downgrade counter above zero is a finding.

Fix. Remove downgrading retries. If a dataset really should fall back to ONE during failures, make that an explicit, logged, per-operation decision, ideally with a degraded-mode signal in the response. That is honest graceful degradation rather than a hidden one.

5. Quorum lost to one zone outage

Symptom. One availability zone goes down and a fraction of carts become unwritable at QUORUM, although "we have three replicas".

Mechanism. Nodes were added over time without rack settings, so the snitch thought every node was in one rack. For some token ranges, two of the three replicas landed in the failed zone. Those keys lost their majority.

Detect. A placement audit: for each token range, count replicas per zone. Any range with more than one replica in a zone, when N equals the zone count, is a latent outage. nodetool status and describering output give the raw data.

Fix. Set each node's real zone as its rack, keep the number of nodes per zone balanced, and use NetworkTopologyStrategy. Fixing placement on a live cluster means streaming data, so plan it as a migration, not a config tweak.

6. The giant partition that times out every replica

Symptom. Requests for one key time out at every consistency level. The three nodes that hold it show long GC pauses. Everything else is fine.

Mechanism. A scraper bot built a cart with 200,000 items. Its partition grew to hundreds of megabytes. Every read of it loads a huge amount of data on each replica, so all replicas for that key are slow together. Quorum cannot help when all N replicas are overloaded by the same request. Their failure is correlated by design.

Detect. Cassandra logs warnings for large partitions during compaction, and nodetool tablehistograms shows partition size percentiles. Watch the max, not just the p99.

Fix. Cap cart size in the application. Split unbounded data across partitions, such as bucketing by time or by item ranges. Rate-limit the client that creates them.

7. The recovery that hurt more than the failure

Symptom. A node returns after a 2-hour outage. Cluster-wide p99 latency doubles for the next several hours.

Mechanism. Hint replay, read repair on every mismatched key, and a manually started full repair all compete for disk and network on the returning node and its peers. Meanwhile, the returning node is slow, and the dynamic snitch keeps routing some reads to it anyway.

Detect. Hint replay throughput, pending compactions, streaming throughput and read-repair rate, all plotted next to p99 latency.

Fix. Throttle hint delivery and streaming deliberately, and schedule repair rather than launching it in a hurry. For long outages, rebuilding the node from peers can be gentler than replaying hints. Make sure the drivers' load balancing avoids nodes that are still catching up.

Resolving conflicts

Last-write-wins is simple and loses data whenever two writes are concurrent or clocks drift. Siblings with vector clocks keep every concurrent version and push the merge to the application, which must then write a merge function. CRDTs (conflict-free replicated data types) build the merge into the type: an add-wins set for cart items, a counter for quantities. Choose by asking what a lost update costs. For a cart line, LWW on separate rows per item is often enough. For a whole-cart blob, it is not. The vector clocks lesson takes this decision further.

Deep Dive: Design-Review Checklist

  1. What are N, W and R for each operation, where are they set in code, and does every write/read pair that needs read-your-writes satisfy W + R > N?
  2. Are consistency levels LOCAL_ variants, and is it understood that overlap then holds only within one datacenter?
  3. Does the store use strict or sloppy quorums, and does any client retry policy downgrade the level?
  4. Are replicas spread across racks or zones, and has placement been audited per token range?
  5. How are concurrent writes resolved: last-write-wins, siblings, or CRDTs? What does a lost update cost for this data?
  6. If last-write-wins is used, who sets timestamps, and what is the alerting threshold on clock offset?
  7. Is repair scheduled so every replica completes a full cycle inside gc_grace_seconds? Who owns that schedule?
  8. What is the hint window, and what is the procedure for a node down longer than it, or longer than the grace period?
  9. Is read repair blocking, and is speculative retry enabled with a sensible threshold?
  10. Has capacity been sized for replica operations (writes x N, reads x R, plus repair), not client operations?
  11. Which operations need exactly one winner, and do they use lightweight transactions or a consensus store instead of plain quorums?
  12. Is there a limit on partition size, and an alert on the largest partitions?

Deep Dive: Senior Interview Follow-ups

"W = 2, R = 2, N = 3. Can a read return an older value than a previous read did?"

Yes, while a write is still in progress. If the write has reached only one replica, a read that includes that replica returns the new value, and a later read through the other two returns the old one. No completed write was missed, but the system went backwards from the reader's view. The fix is for readers to write back what they return to a quorum before answering. Cassandra's blocking read repair does this when replicas disagree, which gives monotonic quorum reads.

"Why does Cassandra send a write to all three replicas if W is only 2?"

Because W is about how long the client waits, not how many copies exist. Sending to all N keeps every replica as current as possible, so later reads mismatch less and repair has less to do. If it sent to only W replicas, the third would fall permanently behind and depend entirely on anti-entropy. Reads are different: Cassandra contacts only R replicas, because extra reads cost capacity and do not make data more durable.

"Why is N = 4 with quorum reads and writes a poor choice?"

A majority of 4 is 3. So W = R = 3, and the cluster tolerates only one replica failure, the same as N = 3 with a quorum of 2. You pay for a fourth copy, and every quorum operation waits for three answers instead of two, for no gain in fault tolerance. Odd replica counts give the best tolerance per copy. N = 5 tolerates two failures.

"Can quorum reads and writes implement a lock or a unique username?"

No. Two clients can both read "username free" and both write "taken by me", each reaching a quorum through different replicas. Quorum guarantees that a later reader sees a completed write, not that only one write wins. You need an atomic compare-and-set ordered by consensus: Cassandra's lightweight transactions (Paxos per partition), or a Raft store like etcd. Those cost extra round trips, so use them only for the operations that need one winner.

"What is the relationship between hinted handoff, read repair and full repair?"

They are three layers catching different gaps. Hints replay writes a replica missed while it was briefly down, up to the hint window. Read repair fixes keys that real traffic happens to read. Full anti-entropy repair, with Merkle trees, fixes everything else, including keys nobody reads and anything older than the hint window. Only full repair is required for correctness, because of tombstones and gc_grace_seconds. The other two make it cheaper and make most reads fresh sooner.

"You use LOCAL_QUORUM in two regions. A user writes in Europe and reads in the US a second later. What do they see?"

Maybe the old value. LOCAL_QUORUM overlaps only within one datacenter. The write was acknowledged by two European replicas, and its copy to the US replicas travels asynchronously, typically arriving within the cross-region latency but with no guarantee. Options: route each user to a home region, write at EACH_QUORUM for the data that needs it (paying WAN latency on writes), or carry the version the user last saw and reject older reads. Usually home-region routing is the cheapest.

"If W + R > N guarantees overlap, why did the cart still lose an item?"

List the exceptions and check each. Was some statement's level lower than you thought (mixed levels, a downgrading retry)? Was it a sloppy quorum during a partition? Were two writes concurrent, so last-write-wins dropped one? Did a clock skew give an older write a newer timestamp? Did a deleted item resurrect because repair missed the grace period? Overlap only promises that someone you ask has the latest completed write. Every one of these breaks a different part of that sentence.

"When would you pick N = 3, W = 1, R = 3 over W = 2, R = 2?"

When writes must survive heavy load or network trouble with the lowest latency, and reads are rare and can wait. Write-heavy telemetry that a few dashboards read is the classic case. The cost is that every read fails if any one replica is unavailable, because R = 3 needs all of them. In practice teams usually choose W = 1, R = 1 for such data and accept staleness, because R = 3 makes reads as fragile as ALL.
