Deep Dive: Inside the Mechanism

The lesson's version of the key store has two columns: the key and the saved result. A store that survives production has about ten, because it has to answer questions the simple version cannot. Is this really the same request, or a reused key? Is the first attempt still running, or did it crash halfway? Which part of the work already happened? This section builds that store, then looks at how the same idea appears inside Kafka, HTTP and DynamoDB.

The key record

Here is a Postgres table for the bookstore's checkout API. It lives in the same database as the orders, which matters, as the next subsection shows.

CREATE TABLE idempotency_keys (
  account_id      bigint      NOT NULL,
  idem_key        text        NOT NULL,
  request_hash    bytea       NOT NULL,        -- SHA-256 of method, path and canonical body
  state           text        NOT NULL,        -- 'started' | 'completed'
  recovery_point  text        NOT NULL DEFAULT 'start',
  locked_until    timestamptz,                 -- lease for the attempt that is running
  response_code   int,
  response_body   jsonb,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, idem_key)
);
CREATE INDEX ON idempotency_keys (created_at);  -- for the expiry sweep

Each column answers one question:

  • account_id in the primary key. Keys are scoped to a caller. Without the scope, two customers who happen to choose the same key would collide, and one could receive the other's saved response. That is a data leak, not just a bug.
  • request_hash. A fingerprint of what was asked. If a key arrives again with a different body, the client has a bug: it reused a key for a new operation. Replaying the old response would be wrong and dangerous. Reject it. Stripe returns an error in this case, and the IETF draft for the Idempotency-Key header suggests 422.
  • state and locked_until. Together they handle the in-progress case. A second request that finds started with an unexpired lease gets 409 Conflict, "still running, try again". One that finds an expired lease knows the first attempt died, and may take over.
  • recovery_point. Records how far a multi-step operation got. A takeover resumes from there instead of starting over. More on this below.
  • response_code, response_body. The saved answer that a duplicate receives.

The protocol, step by step

When the effect lives in the same database as the key, the whole thing is one transaction. That is the easy and best case:

BEGIN;
-- 1. Claim. Exactly one concurrent transaction can insert this row.
INSERT INTO idempotency_keys (account_id, idem_key, request_hash, state, locked_until)
VALUES ($1, $2, $3, 'started', now() + interval '30 seconds')
ON CONFLICT (account_id, idem_key) DO NOTHING
RETURNING idem_key;
-- 2. No row returned? Someone owns the key. ROLLBACK, then read the existing row:
--      hash differs            -> 422, key reused for a different request
--      state = 'completed'     -> replay response_code and response_body
--      lease still valid       -> 409, in progress
--      lease expired           -> take over (see recovery points)
-- 3. Row returned: we own it. Do the work in the same transaction.
INSERT INTO orders (...) VALUES (...);
UPDATE inventory SET reserved = reserved + 1 WHERE sku = $4;
-- 4. Save the answer and commit everything together.
UPDATE idempotency_keys
   SET state = 'completed', response_code = 201, response_body = $5
 WHERE account_id = $1 AND idem_key = $2;
COMMIT;

Because the claim, the effect and the saved response commit atomically, there is no window where one exists without the others. A crash before COMMIT rolls back all of it, including the claim, so the retry starts fresh. One note on concurrency: a second transaction inserting the same key while the first is still open will block on the unique index until the first commits or rolls back. So in this single-transaction design, concurrent duplicates wait rather than getting a 409. Keep the transaction short.

When the effect is external: recovery points

The payment call is the hard case. Charging a card is a call to the provider, so it cannot join your database transaction. Hold a transaction open across a network call and you hold row locks for its full duration, which is worse. The usual answer is to split the request into atomic phases, each a local transaction that ends by recording a recovery point:

  1. Phase start. Claim the key, create the order row as pending, set recovery_point = 'order_created'. Commit.
  2. External call. Charge the card, passing a key derived from yours, for example ord_7f3a:charge. This is outside any transaction.
  3. Phase charge_recorded. Store the charge ID, mark the order paid, set recovery_point = 'charge_recorded'. Commit.
  4. Phase finished. Enqueue the receipt email through an outbox row, save the response, set state = 'completed'. Commit.

If the process dies after step 2, the key is stuck in order_created with an expiring lease. The next attempt takes over and repeats step 2. The provider sees ord_7f3a:charge again and returns the original charge instead of creating a second one. Every phase is safe to repeat, so the whole request is. This is how an idempotent API calls a non-transactional world: pass a derived key to every downstream system that supports one, and record progress locally between calls.

Which outcomes to save

Not every result should be replayed forever. A working rule:

  • Save successes, and deterministic refusals that happened after execution began, such as "card declined". Retrying a decline with the same key should return the same decline, not try the card again.
  • Do not save validation failures that happened before any work, or "conflict, still in progress". Nothing was executed, so there is nothing to protect. Stripe documents behaviour along these lines.
  • Decide deliberately about 5xx. If the failure happened before any side effect, delete the claim so the retry can run again. Saving a transient 500 turns a 50 ms blip into a permanent failure for that key. If the failure happened after a side effect, keep the row and its recovery point so a retry resumes rather than restarts.

Random keys or derived keys

The lesson's key, ord_7f3a, is a random ID minted at click time. The alternative is a derived key: a deterministic function of the business identity, such as sha256("charge:" + order_id). Derived keys have one big advantage. Any process that knows the order ID computes the same key, even after a crash that lost all local state. Consumer code especially benefits: event_id + ":" + handler_name gives each handler its own key for the same event.

Their risk is the opposite of the random key's. A derived key may be too stable. If the customer really does want to pay for the same order twice (a second, separate attempt after a decline), charge:order_id blocks it. Include whatever makes the intent unique, such as an attempt number that the user's action increments. Random keys are simplest for API clients. Derived keys are best for internal pipelines.

Deep Dive: Sizing and the Numbers

How long to keep keys

The key must outlive every way a duplicate can arrive. Add up the windows rather than picking a round number:

retention ≥ client retry window
          + queue redelivery and dead-letter replay window
          + manual replay window (support re-running a job)
          + safety margin

For the bookstore's checkout API, client retries span at most a minute, and Stripe-style 24 hours is generous. For a webhook consumer, the provider may retry for 3 days, and a support engineer may replay a dead-letter queue a week later. That consumer needs at least 7 days of dedupe. A 24-hour TTL there is a duplicate waiting to happen.

Storage and write cost at a larger scale

The lesson's checkout needs about 100 MB. Scale it to a payment platform with these assumptions: 50 million idempotent writes a day, 2 KB per saved response including the row overhead and index, and 7 days of retention.

  • Rows held: 50 M × 7 = 350 million.
  • Storage: 350 M × 2 KB = 700 GB. That is real, but well within one database cluster. Compress response bodies or store only the fields needed to rebuild the response, and it shrinks by several times.
  • Write load: each request adds one insert and one update to the key table. At an average of about 580 writes per second (50 M / 86,400), that is about 1,160 extra row writes per second, doubling at peak. On a primary already busy with orders, measure this. It is often the largest real cost of the pattern.
  • Expiry: deleting 50 M rows a day row by row is expensive in Postgres, because each delete creates dead tuples for vacuum. Partition the table by day and drop whole partitions instead. Dropping a partition is nearly free.

Latency: what the claim adds

In the same-database design, the claim is one extra indexed insert inside a transaction you already have. Expect well under a millisecond on the database, plus nothing for the network. A separate store such as Redis adds a full round trip, typically 0.3 to 1 ms in the same zone, and a second failure domain. A replay is cheap: one read by primary key, then return the saved body. The lesson's 5 ms is mostly HTTP overhead.

Collision math for random keys

A UUIDv4 has 122 random bits. By the birthday bound, the chance of any collision among n keys is about n² / 2^123. For a trillion keys (10^12), that is about 10^24 / 10^37 = 10^-13. Collisions are not a real risk with a proper random source. Short keys are. A 6-character base-62 key has only about 5.7 × 10^10 values, and among a million keys the chance of some collision is near certainty. Scoping by account and keeping the full UUID removes the problem.

Estimating how many duplicates you will see

For capacity and alerting, estimate the duplicate rate per source. With the lesson's checkout figures: 0.5% of calls time out, and one retry follows each, so about 0.5% of requests are retries. Add double-clicks (often 0.1% to 1% of form submits on web clients without button disabling) and queue redeliveries (near zero on a healthy day, but bursts of 100% of a partition after a consumer crash). Alert when the replay rate jumps. A sudden rise from 0.5% to 5% means something upstream is retrying far more than it should.

Deep Dive: Failure Modes in Production

1. The client mints a new key on every attempt

Symptom: double charges continue after idempotency "shipped". The key store shows no replays at all. Mechanism: the key is generated inside the retry loop, or the HTTP client's middleware adds a fresh UUID per request. Every attempt looks new to the server. A variant: the mobile app generates the key in memory, the app is killed during the call, and on restart it creates a new one. Detect: a replay rate of exactly zero while the timeout rate is non-zero. Pairs of near-identical requests with different keys within seconds. Fix: generate the key when the user acts, persist it with the pending operation, and reuse it across attempts and restarts. Add a client test that kills the process mid-request and checks the key on restart.

2. One key, two different requests

Symptom: a customer buys a $20 gift card, then a $499 bundle. The second purchase "succeeds" instantly, but no charge appears and no bundle ships. Mechanism: the client used something too coarse as the key, such as the cart ID or the session ID. The second request carried the same key, and the server replayed the first response. Detect: fingerprint mismatches. If you store a request hash, count the cases where the key matches but the hash does not. Any non-zero count is a client bug. Fix: store and compare the request hash, and reject mismatches with 422. Document that a key names one operation, not one user or one cart.

3. Keys stuck "in progress" forever

Symptom: a small number of orders return 409 on every retry, for hours. Support cannot complete them. Mechanism: the first attempt claimed the key in its own transaction, called the provider, and then the process crashed. The key row says started and nothing ever changes it. Detect: a gauge of keys in started older than a few times the request timeout. It should be close to zero at all times. Fix: give each claim a lease (locked_until). A retry that finds an expired lease takes over, resuming from the recovery point. Run a sweeper that finishes or fails abandoned keys, and make every phase safe to repeat so a takeover can't double anything.

4. The key expired before the duplicate arrived

Symptom: after a consumer outage, an engineer replays the dead letter queue. Hundreds of customers get a second shipment. Mechanism: the consumer's dedupe TTL was 24 hours, copied from an API example. The DLQ replay happened on day 3. The keys were gone, so every replayed message was treated as new. Detect: compare the age of messages being processed with the dedupe TTL. Alert when any message older than the TTL is processed. Fix: derive retention from the longest replay window, not from habit. For effects that must never repeat, such as shipping, also guard with a natural constraint: a unique index on (order_id) in the shipments table survives any TTL.

5. A cache used as the key store forgets

Symptom: rare duplicates, clustered around Redis failovers and memory-pressure events. Mechanism: the claim was SET key NX EX 86400 in Redis, and the effect was written to Postgres. Two things can lose the key. Redis replication is asynchronous, so a failover can promote a replica that never received the SET. And with an eviction policy like allkeys-lru, Redis may evict keys before their TTL under memory pressure. Either way, the next duplicate finds nothing and executes. Detect: Redis evicted_keys rising, failover events, and duplicates found by a reconciliation job against the business table. Fix: keep the key in the same database as the effect, inside the same transaction. If you must use a cache for speed, treat it as a fast first check, with a unique constraint in the database as the real guarantee.

6. Your API is idempotent, but your call to the provider is not

Symptom: the bookstore's own logs show one execution per key, yet the payment provider shows two charges. Mechanism: inside the protected execution, the payment client has its own retry on timeout, without an idempotency key. One execution of your handler produced two provider calls. Or a takeover after a crash repeated the provider call with no key. Detect: reconcile your charge records against the provider's daily report. A provider charge with no matching local record is the sign. Fix: pass a derived key, such as ord_7f3a:charge, on every downstream call that accepts one. For providers that do not, record the intent before calling and check the provider's records before any repeat.

7. A transient error is replayed forever

Symptom: during a 30-second database blip, some checkouts failed. Hours later, those customers still get the same 500 every time they click Pay. Mechanism: the server saved every response, including the 500 from the blip. Every retry with the same key correctly replays that 500. Detect: saved 5xx responses in the key store, and replays of them. Fix: do not save failures that happened before any side effect; delete the claim instead, so a retry runs fresh. If the failure happened after a side effect, keep the row in started with its recovery point, so the retry resumes.

An opinion on the first row: try hard to make the key store unnecessary. Many operations that look like increments can be rewritten as sets with a version check. "Reserve one copy" becomes "set reservation row (order 42, SKU 9) to quantity 1" with a unique index on the pair. A natural constraint never expires, never needs a sweeper, and cannot be bypassed by a client that sends the wrong key.

And on the producer row: broker-level dedupe is transport hygiene, not business correctness. Kafka's idempotent producer stops duplicate batches in a partition. It does nothing if your consumer charges a card and then crashes before committing its offset. The consumer will see that message again, and only consumer-side idempotency saves you.

Deep Dive: Design-Review Checklist

  1. Which operations in this design are not naturally idempotent? Could any be rewritten as a set, an upsert or a conditional write instead?
  2. Who creates the key, at what moment, and where is it persisted so that it survives a client crash and restart?
  3. Is the key scoped to the caller (account or tenant) in the uniqueness constraint?
  4. Is the claim an atomic insert-if-absent? Show the statement. Is there any check-then-write path left?
  5. Do the claim, the effect and the saved response commit in one transaction? If not, what are the recovery points?
  6. Is a request fingerprint stored and compared? What happens when a key is reused with a different body?
  7. What does a concurrent duplicate receive? What happens to a key whose first attempt crashed mid-way?
  8. Which outcomes are saved and replayed? Are transient pre-execution failures excluded?
  9. How long are keys kept, and how was that derived from the longest retry, redelivery and replay windows?
  10. Is a derived key passed to every downstream system that accepts one (payment providers, other internal APIs)?
  11. Are side effects such as emails and webhooks inside the boundary, or idempotent on their own keys?
  12. Are replay rate, fingerprint mismatches and stuck started keys measured and alerted on?

Deep Dive: Senior Interview Follow-ups

"The first request claimed the key, charged the card, and then the server crashed. What does the retry see?"

It depends on whether the claim was committed separately from the work. If everything ran in one local transaction, the crash rolled back the claim too, and the retry runs fresh. But a card charge is external, so it cannot be in that transaction. In the phased design, the key is committed at order_created with a lease. The retry waits for the lease to expire, takes over, and repeats the charge call with the same derived key. The provider recognises it and returns the original charge. No double charge, and no stuck key.

"Why store a hash of the request body?"

To catch a key reused for a different operation. Without the hash, a buggy client that sends the same key with a new $499 body gets the saved response from an earlier $20 call. The client believes the purchase succeeded, and nothing was charged or shipped. With the hash, the server sees the mismatch and rejects it with 422, which surfaces the bug immediately.

"Can you use Redis SET NX as the key store?"

As a fast pre-check, yes. As the guarantee, not for money. Redis replication is asynchronous, so a failover can lose a recent SET, and some eviction policies drop keys before their TTL under memory pressure. Either way a duplicate executes. The claim and the effect also live in different systems, so they can't commit atomically. Put the real guarantee, a unique constraint, in the same database transaction as the effect.

"Kafka has exactly-once semantics. Why do consumers still need idempotency?"

Kafka's guarantee covers reads and writes inside Kafka: the idempotent producer stops duplicate batches, and transactions commit output records with consumer offsets atomically. An external effect, such as a card charge or an email, is outside that transaction. A consumer that performs the effect and then crashes before committing its offset will process the message again. Only an idempotent effect, keyed on the message, makes that safe.

"How long should idempotency keys live?"

Longer than the latest a duplicate can arrive. That is the sum of the client retry window, queue redelivery, dead-letter replay and any manual replay, plus a margin. For a synchronous API with short client retries, 24 hours is generous. For a webhook or queue consumer, it is often 7 days or more. Where the duplicate would be very costly, back the TTL with a permanent natural constraint, such as one shipment per order.

"Is PUT idempotent by definition? Then why do PUT endpoints still double things?"

HTTP defines PUT as idempotent, but that is a contract the server must honour, not something the protocol enforces. A PUT handler that appends a history row, sends an email or increments a counter breaks it. And a sequence of idempotent PUTs can still be reordered by retries, so an old value overwrites a new one. Conditional requests with If-Match and an ETag fix the ordering problem.

"Two identical requests with the same key arrive 1 ms apart. Walk me through the database."

Both run INSERT … ON CONFLICT DO NOTHING. The first takes the unique index entry. In Postgres, the second waits on that entry until the first transaction commits or rolls back. If the first commits, the second's insert does nothing and returns no row, so it reads the saved response and replays it. If the first rolls back, the second's insert succeeds and it executes. In a phased design where the claim is committed early, the second instead sees a started row with a live lease and returns 409.

"When is an idempotency key the wrong tool?"

When the operation can be made naturally idempotent, when duplicates are harmless downstream, or when the "duplicate" is a business rule. "Don't let the same user place the same order twice in a minute" is product policy. A key means "this is the same operation, retried", and a customer's deliberate second order is a new operation with a new key. Mixing the two produces either blocked real purchases or a dedupe rule that retries quietly bypass.
