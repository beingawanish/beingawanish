Deep Dive: Inside the Mechanism

The lesson's four mechanics (save before confirming, ack after finishing, competing consumers, depth as a signal) hold for every broker. How each broker implements them differs a lot, and the differences decide your failure modes. Three brokers cover most real systems: RabbitMQ, SQS and Kafka.

One message's life

Every queue tracks each message through the same few states. The names change by broker, but the shape is the same.

RabbitMQ: pushes, prefetch and quorum queues

RabbitMQ pushes messages to consumers. A consumer opens a channel (a lightweight session inside one TCP connection), subscribes with basic.consume, and receives messages tagged with a per-channel delivery tag. It then answers each one:

  • basic.ack: done, delete it.
  • basic.nack or basic.reject with requeue=true: put it back. RabbitMQ requeues it at or near its original position, which is usually the head of the queue.
  • Same with requeue=false: drop it, or route it to the queue's dead-letter exchange if one is set.

If the channel or connection closes, every unacked message on it goes back to Ready. That is the crash-redelivery mechanism. RabbitMQ also enforces a consumer timeout (30 minutes by default in recent versions): a delivery held unacked longer than that closes the channel, so a stuck consumer cannot hold messages forever.

The key knob is prefetch, set with basic.qos. It caps how many unacked messages a consumer may hold at once.

  • Prefetch 1 is perfectly fair: a consumer gets the next message only after acking the last. But every message pays a network round trip of idle time between ack and next delivery.
  • High prefetch (hundreds) keeps consumers busy, but one consumer can grab a large batch while others sit idle. When that consumer crashes, its whole batch is redelivered at once.
  • No prefetch limit, the default when you never call basic.qos, sends everything to whoever subscribes first. One consumer's memory then holds the whole backlog.

The sizing section shows how to pick a value. Note also that auto-ack mode ("acked on delivery") turns RabbitMQ into an at-most-once system: a crash after delivery loses the message.

On the producer side, publisher confirms are the "saved before confirming" step. The broker sends basic.ack to the producer once the message is safely stored. Without confirms, a publish that hits a broker restart can vanish with no error.

For durability, use quorum queues. A quorum queue is replicated across an odd number of nodes, usually three or five, using the Raft consensus protocol. A publish is confirmed once a majority has written it, so three nodes survive the loss of one. Quorum queues also count deliveries per message (the x-delivery-count header) and enforce a delivery limit. In RabbitMQ 4.0 and later that limit defaults to 20; past it, the message is dead-lettered or dropped. The older mirrored classic queues were removed in 4.0, so new designs should not use them.

SQS: pulls, visibility timeouts and redrive

SQS is pull-based and has no connections or channels. A consumer calls ReceiveMessage, which returns up to 10 messages. Each comes with a receipt handle, a token for that particular delivery. The consumer later calls DeleteMessage with the handle. That is the ack.

  • Visibility timeout. Received messages stay hidden for this long: 30 seconds by default, up to 12 hours. If not deleted by then, they reappear. A long job extends its own timeout with ChangeMessageVisibility, acting as a heartbeat.
  • Long polling. Set WaitTimeSeconds up to 20 so an empty queue holds the request open instead of returning nothing. Short polling an empty queue burns API calls (and money) for no work.
  • Receive count and redrive. SQS tracks ApproximateReceiveCount per message. A redrive policy on the source queue names a dead letter queue and a maxReceiveCount. After that many receives without a delete, the message moves to the DLQ. SQS can later move messages back from the DLQ to the source queue (DLQ redrive) once the bug is fixed.
  • Retention. Messages expire after 4 days by default, 14 days at most. A DLQ needs its own retention long enough for someone to look.

A redrive policy in its actual form:

{
  "deadLetterTargetArn": "arn:aws:sqs:us-east-1:123456789012:orders-dlq",
  "maxReceiveCount": "5"
}

Standard queues give at-least-once delivery and best-effort ordering with very high throughput. FIFO queues add strict ordering within a MessageGroupId and deduplicate sends that reuse a MessageDeduplicationId within a five-minute window. FIFO trades throughput for that; its per-queue limits are much lower than standard's, with a high-throughput mode that raises them. Check the current quotas rather than relying on remembered numbers. Both kinds also cap in-flight messages per queue, roughly 120,000 for standard and 20,000 for FIFO. A huge fleet with long visibility timeouts can hit that ceiling.

FIFO ordering has a sharp edge. While any message in a group is in flight, SQS will not deliver the next message of that group. A slow or failing message blocks its whole group until it is deleted or moves to the DLQ.

Kafka as a queue: offsets, not acks

Kafka stores messages in partitions, each an append-only log. A message's position in the log is its offset. A consumer group shares the partitions of a topic: each partition goes to exactly one consumer in the group. That makes the group behave like competing consumers, with three differences that matter:

  • Parallelism is capped by partition count. A topic with 12 partitions can keep at most 12 consumers in one group busy. Consumer 13 sits idle.
  • There is no per-message ack. A consumer commits one offset per partition, meaning "everything before this is done." If message 1,000 fails and 1,001 succeeds, you cannot ack 1,001 alone. Either the partition waits on 1,000, or the application moves 1,000 aside itself (to a retry or DLQ topic) and commits past it. Kafka has no built-in dead letter queue for consumers.
  • Deletion is by retention, not by ack. Messages stay for the configured retention (retention.ms, 7 days by default) whether consumed or not. That is what lets consumers replay. It also means lag in Kafka is a position, not a count of stored messages.

Consumer liveness has two timers. session.timeout.ms (45 s by default in current versions) detects a dead process through heartbeats. max.poll.interval.ms (5 minutes by default) detects a live but stuck one: if the consumer does not call poll() again within that window, it is removed from the group and its partitions are reassigned. max.poll.records (500 by default) controls how many messages each poll returns. Those three settings together cause the rebalance storm in failure mode 3.

Offsets commit automatically every 5 seconds by default (enable.auto.commit=true). Auto-commit can commit offsets for messages you have not finished, which loses them on a crash, or commit too late, which duplicates them. For a queue workload, turn it off and commit after processing.

Two newer pieces are worth knowing. The cooperative sticky assignor and static membership (group.instance.id) make rebalances incremental, so a deploy does not stop every consumer. And Kafka's share groups (KIP-932, early access in Kafka 4.0) add per-message acknowledgment, delivery counts and more consumers than partitions. This is Kafka growing real queue semantics. Check its maturity in your version before depending on it.

Redis Streams, briefly

Redis Streams sit between Kafka and RabbitMQ. A consumer group reads with XREADGROUP. Delivered entries go into a pending entries list (PEL) with a delivery count until the consumer calls XACK. Another consumer can take over stale entries with XAUTOCLAIM. That is per-message acking with Kafka-like log storage, held in memory, so durability depends on your Redis persistence and replication settings.

What delivery semantics really mean

Delivery guarantees come from where the ack sits relative to the work:

  • At-most-once: ack before processing (or auto-ack). A crash loses the message. Acceptable for metrics samples, never for orders.
  • At-least-once: ack after processing. A crash between the work and the ack repeats the work. This is the default for every serious queue.
  • Exactly-once effect: at-least-once delivery plus a consumer that makes repeats harmless. The repeat still arrives; it just changes nothing.

Kafka's "exactly-once" (idempotent producers plus transactions) is real, but its scope is narrow. It covers read-from-Kafka, write-to-Kafka pipelines, where the output and the offset commit land in one transaction. The moment a consumer charges a card or sends an email, you are back to at-least-once plus idempotency. The Exactly-Once Semantics lesson goes further.

The producer side has its own guarantee. In Kafka, durability needs acks=all, a replication factor of 3, and min.insync.replicas=2, so a write is confirmed only after two replicas have it. Idempotent producers (enable.idempotence, on by default since Kafka 3.0) stop producer retries from writing duplicates into the log.

The outbox pattern: getting messages in reliably

The lesson's API "validates, adds a message, and confirms." In practice the API also writes the order to its database. Now there are two writes to two systems, and no transaction covers both. This is the dual write problem.

  • Commit the database, then publish: if the process dies in between, the order exists but no worker ever hears of it.
  • Publish, then commit: if the commit fails, a worker fulfills an order that does not exist.

The transactional outbox removes the second system from the request. The API writes the order row and an outbox row (event ID, aggregate ID, payload) in the same database transaction. Either both exist or neither does. A separate relay then reads the outbox and publishes to the broker, marking rows sent after the broker confirms.

The relay has two common forms. A polling relay runs SELECT ... WHERE sent_at IS NULL ORDER BY id LIMIT 500 on a short interval. It is simple but adds query load and some delay. A log-tailing relay uses change data capture (for example, Debezium reading the Postgres WAL) and publishes each outbox insert as it commits. It is lower latency and lighter on the database, but it is another system to run.

Either way the relay can publish a row and crash before marking it sent, so the outbox is at-least-once too. The consumer still needs idempotency.

The mirror image on the consumer side is the inbox: record each processed message ID in the same transaction as the work.

import sqlite3

def handle(db: sqlite3.Connection, msg_id: str, order_id: str):
    """Apply a 'reserve inventory' message exactly once in effect."""
    with db:  # one transaction: inbox row and the effect commit together
        try:
            db.execute("INSERT INTO inbox(msg_id) VALUES (?)", (msg_id,))
        except sqlite3.IntegrityError:
            return "duplicate, skipped"          # already processed: ack and move on
        db.execute("UPDATE stock SET reserved = reserved + 1 "
                   "WHERE sku = (SELECT sku FROM orders WHERE id = ?)", (order_id,))
    return "applied"                             # ack only after the commit

The primary key on inbox.msg_id does the deduplication. Prune old inbox rows on a schedule longer than the broker's maximum redelivery window.

Deep Dive: Sizing and the Numbers

Backlog storage and drain time

From the lesson: the flash sale leaves a backlog of 552,000 messages. Assume each order message is 1 KB.

  • Storage: 552,000 x 1 KB, about 552 MB. On a quorum queue with three replicas, about 1.7 GB of disk across the cluster. Trivial.
  • Drain time = backlog / (processing rate − arrival rate). After the sale, orders drop back to 200 per second, so the backlog drains at 400 − 200 = 200 per second, not 400. That is 552,000 / 200 = 2,760 s, or about 46 minutes. The lesson's 23 minutes assumes arrivals stop entirely.

That difference matters for the promise to buyers. "Shipping today" survives 46 minutes. A "ships within 30 minutes" promise does not.

How many workers, and where the real ceiling is

Say the business wants the backlog cleared within 10 minutes of the sale ending. Processing must reach 552,000 / 600 + 200 = 1,120 orders per second. If each worker handles 20 orders per second (50 ms each), that is 56 workers.

But the original pipeline topped out at 400 per second because of the database, not the workers. Fifty-six workers would push 1,120 writes per second into a database that handles 400. They would get slower, time out, and get redelivered. So the honest answer is: the queue lets you choose the drain time, but only up to the slowest downstream resource. To drain faster you must raise that ceiling (batch the writes, shard, add capacity). Adding consumers past it only adds contention.

Write the worker cap into the autoscaler as a maximum, derived from the downstream limit: at 20 per second per worker and a 400-per-second database, cap at 20 workers.

Picking a RabbitMQ prefetch

Each consumer is idle for one network round trip between sending an ack and receiving the next message, unless more messages are already buffered. With processing time P and round trip R, prefetch 1 gives utilization P / (P + R).

  • P = 50 ms, R = 1 ms: 98% utilization at prefetch 1. Fine.
  • P = 2 ms, R = 1 ms: 67% at prefetch 1. One third of the fleet is waiting on the network.

A prefetch of roughly R / P + 1, plus a little headroom, removes the idle gap. For the 2 ms case that is about 2 to 5. Going far higher buys nothing and makes crashes and imbalance worse. Fast, uniform jobs want a moderate prefetch, perhaps tens. Slow or uneven jobs (an image resize that takes 50 ms or 20 s) want prefetch 1, so a slow message does not trap others behind it on one consumer.

Sizing visibility timeouts and poll intervals

SQS. Set the visibility timeout above the job's worst normal duration. If p99.9 processing is 40 s, a 30-second default guarantees duplicates. A rule of thumb is several times the p99.9, or a heartbeat that extends the timeout every third of its length. Too long has its own cost: a crashed worker's message waits the full timeout before anyone retries it.

Kafka. The rule is max.poll.records x worst-case time per record < max.poll.interval.ms. With 500 records per poll at 1 s each, one batch takes 500 s, which exceeds the 300 s default. The consumer gets evicted mid-batch every time. Either cut max.poll.records to 100 (100 s per batch) or process asynchronously and keep polling.

Kafka partitions for a queue workload

Partitions cap consumer parallelism, and you cannot easily lower the count later. Adding partitions also remaps keys to different partitions, which breaks per-key ordering during the change. So size up front:

partitions ≥ peak throughput / per-consumer throughput

At 1,120 orders per second and 20 per consumer, you need 56 partitions. Leave room to grow, for example 64 to 96. Do not go to thousands "just in case." Each partition adds broker metadata, open files and rebalance work.

Request math for SQS

SQS bills per API request, so batching matters more than message count. Each message needs at least a send, a receive and a delete: three requests. The flash sale's 600,000 orders cost 1.8 million requests unbatched. With batches of 10 on all three calls, that becomes about 180,000. Empty receives also count, which is why long polling matters: a worker short-polling an empty queue every 100 ms makes 864,000 requests a day doing nothing. Prices vary by region and queue type, so plug in the current per-million rate.

Scaling on backlog age

Depth says how much work is waiting. Age says how long the oldest has waited, which is what users feel. By Little's law, expected wait ≈ depth / processing rate. The same depth of 10,000 means 25 seconds of delay at 400 per second, but 8 minutes at 20 per second when workers slow down. Depth alone would not notice the difference.

A sound policy targets age with a ceiling and hysteresis:

  • Scale out when age of oldest message exceeds, say, 60 s for 2 minutes. On SQS that metric is ApproximateAgeOfOldestMessage. On Kafka, convert consumer lag into time lag.
  • Desired workers ≈ (arrival rate + backlog / target drain time) / per-worker rate, capped at the downstream limit.
  • Scale in slowly, for example only after 10 minutes with age under 10 s, so the fleet does not flap.

KEDA scalers and similar tools implement this for SQS, RabbitMQ and Kafka. Remember that a poison message inflates age without any real backlog. Failure mode 7 covers that.

Deep Dive: Failure Modes in Production

1. The poison message loop

Symptom. Consumer CPU at 100%, throughput near zero, depth climbing. The logs repeat the same exception, thousands of times per minute.

Mechanism. One message has a field the code cannot parse. The consumer throws, catches it, and nacks with requeue=true. RabbitMQ puts the message back at the head of the queue, and it is redelivered immediately. On a classic queue nothing counts deliveries, so the loop never ends. With prefetch 1, every consumer ends up spinning on poison messages instead of real work.

Detect. The redelivery rate (RabbitMQ's redeliver counter) is close to the delivery rate. The same message ID appears again and again in error logs.

Fix. Use quorum queues with a delivery limit and a dead-letter exchange, or on SQS a redrive policy. Separate error types in code. A permanent error (bad schema, missing record) is rejected without requeue straight to the DLQ. A transient error (timeout, 503) is retried with delay. Alert on DLQ depth above zero; see Dead Letter Queue.

2. The backlog that never drains

Symptom. Workers are busy and the fleet is scaled out, yet depth will not fall. Downstream sees each order processed two or three times.

Mechanism. A new step made jobs slower. p99 processing went from 10 s to 45 s, but the visibility timeout stayed at 30 s. Slow messages reappear while their first worker is still on them, and a second worker picks them up. Work multiplies, workers slow further, and more messages pass the timeout. Capacity goes to duplicates.

Detect. NumberOfMessagesReceived well above NumberOfMessagesDeleted for the same period. Many messages with ApproximateReceiveCount above 1. Delete calls failing because the receipt handle is stale.

Fix. Heartbeat with ChangeMessageVisibility during long jobs, or set the timeout from measured p99.9. Idempotent consumers make the duplicates harmless, but they do not give back the wasted capacity.

3. Kafka rebalance storm

Symptom. Lag rises in a sawtooth. Consumers keep logging that they left and rejoined the group. Throughput drops to a fraction of normal, and the same messages are processed repeatedly.

Mechanism. A downstream slowdown pushes one batch past max.poll.interval.ms. The consumer is evicted and its partitions move to others, which now have even more work and also miss the deadline. With the older eager assignment, every rebalance pauses all consumers. Uncommitted work from the evicted consumer is redone by its replacement.

Detect. Consumer logs: "consumer poll timeout has expired." Group coordinator metrics show a high rebalance rate. Lag graphs show the sawtooth.

Fix. Keep batch time well below the poll interval (fewer records per poll). Commit after each batch. Use the cooperative sticky assignor and static membership so rolling deploys do not trigger full rebalances. For truly slow jobs, pause the partition, process on a worker thread, and keep calling poll().

4. Prefetch hoarding

Symptom. Ten consumers, but one is at full load and nine are nearly idle. When that busy consumer is redeployed, a wave of redeliveries hits, along with a burst of duplicate side effects.

Mechanism. No basic.qos limit, or a very high one. The first consumer to connect after a deploy grabs thousands of messages into its buffer. Others get only what arrives afterward. Those buffered messages are all unacked, so a restart redelivers all of them.

Detect. RabbitMQ's management view shows unacked messages per consumer, heavily skewed. Ready count is low while unacked count is high.

Fix. Always set prefetch, sized with the formula above. Drain consumers gracefully on shutdown: stop consuming, finish and ack in-flight work, then close.

5. Ordering breaks on retry

Symptom. The lesson's refund-before-charge bug comes back, even after partitioning by customer ID.

Mechanism. The charge failed once with a transient error. To avoid blocking the partition, the consumer sent it to a retry topic with a 5-minute delay and moved on. The refund behind it processed right away. Any retry path that takes a message out of line breaks per-key order. The same happens with SQS standard queues, with RabbitMQ requeue on multiple consumers, and with prefetch above 1 across several consumers.

Detect. Downstream state checks: a negative balance, a "refund for unknown charge" error, a version conflict on write. Logs keyed by customer show events out of sequence.

Fix. Decide per stream whether order is required. If it is, a failing message must block its key: retry in place, and park the whole key (not just the message) when it gives up. Make consumers order-tolerant where possible, with sequence numbers and version checks that reject or defer stale updates. RabbitMQ's single active consumer, SQS FIFO groups and Kafka partition keys each give per-key order, but only if retries respect it. The Partitioned Consumption lesson covers hot keys.

6. The order with no fulfillment

Symptom. Every few days, support finds a paid order that was never shipped. No error was logged anywhere.

Mechanism. A dual write. The API committed the order, then the publish to the broker failed during a broker failover, or the pod was killed between the two calls. The code logged nothing because the process was gone.

Detect. Only a reconciliation job finds it: compare orders in the database with orders the fulfillment system has seen, for the last 24 hours. Build that job before you need it.

Fix. The transactional outbox, with idempotent consumers. Keep the reconciliation job anyway, as a safety net that proves the outbox works.

7. The autoscaler that makes it worse

Symptom. One of two variants. Either the worker fleet scales to its maximum at 3 a.m. while orders are near zero, or it scales to 60 workers during a spike and the database falls over.

Mechanism. In the first case, a single poison message stuck in the queue makes the age of the oldest message climb forever. The age-based scaler reads that as an ever-growing delay. In the second case, the scaler has no ceiling tied to the downstream limit, and the extra workers overload the shared database. On Kafka there is a third variant: scaling consumers past the partition count adds pods that receive nothing.

Detect. Worker count high while throughput is flat. Age is high but depth is tiny. Database connections or CPU saturated right after a scale-out. On Kafka, idle consumers with no assigned partitions.

Fix. Bound redeliveries so poison messages leave for the DLQ within minutes. Scale on age and depth together (both must be high). Cap the fleet from the downstream limit and the partition count. And watch completions per second, not just worker count.

Push versus pull

Push (RabbitMQ) gives the lowest latency and lets the broker spread work, but the consumer must set prefetch to avoid being flooded. Pull (SQS, Kafka) lets each consumer take only what it can handle, so backpressure is built in. The costs are polling overhead and, for Kafka, batch-shaped latency. If consumers vary widely in speed, pull or push with low prefetch both work. Push with no prefetch does not.

Where retries happen

  • Broker redelivery (requeue or visibility timeout): zero code, but immediate retries hit the same transient failure again. SQS adds delay naturally through the visibility timeout. RabbitMQ requeue does not.
  • In-consumer retry with backoff: good for short transient errors (a 503 that clears in a second). It holds the message, and with ordering, the whole key.
  • Delayed retry queues or topics (retry-1m, retry-10m, then DLQ): good for longer outages, but they break ordering.

Most teams combine a couple of quick in-consumer retries with broker redelivery and a bounded delivery count ending in the DLQ.

Deep Dive: Design-Review Checklist

  1. Is the producer confirmed only after the broker has durably stored (and replicated) the message: publisher confirms, acks=all with min.insync.replicas, or a successful SQS send?
  2. If the producer also writes a database, how is the dual write avoided? Is there an outbox, and what cleans it up?
  3. Where exactly is the ack: after the side effect commits, never before?
  4. How is each consumer idempotent? What is the dedupe key, and how long is it remembered compared with the maximum redelivery window?
  5. Is there a bounded delivery count, a DLQ, an alert on DLQ depth, and a written procedure for redriving it?
  6. Does the code separate permanent errors (straight to DLQ) from transient ones (retry with backoff)?
  7. Is the visibility timeout, consumer timeout or max.poll.interval.ms set from measured p99.9 job time, with a heartbeat for long jobs?
  8. For RabbitMQ: what prefetch, and why? Are queues quorum queues?
  9. Which streams need ordering, by which key, and what happens to a key's later messages when one fails?
  10. What does the autoscaler watch (age and depth), and what caps it: the downstream limit, the partition count, or both?
  11. What is the drain time for the worst expected spike, given arrivals do not stop afterward, and does it meet the product's promise?
  12. How will someone find a lost message: is there a reconciliation job between the source of truth and the consumer's results?

Deep Dive: Senior Interview Follow-ups

"Kafka says it supports exactly-once. Why do your consumers still need idempotency?"

Kafka's exactly-once covers reading from Kafka and writing back to Kafka, where the output records and the offset commit land in one transaction. Charging a card, sending an email or writing to Postgres is outside that transaction. A consumer can do the side effect and crash before committing, and the replacement does it again. So delivery is still at-least-once from the outside world's view, and the consumer must make repeats harmless, for example with an inbox table in the same database transaction as the effect.

"How do you choose an SQS visibility timeout for a job that usually takes 5 s but sometimes 10 minutes?"

Do not set one fixed number for both. Set a modest timeout, say 60 s, and have the worker extend it with ChangeMessageVisibility every 20 s while it is still working. A crashed worker's message then reappears within about a minute, while a slow but healthy job keeps its claim. A single 10-minute timeout would make every crash cost 10 minutes of delay. A 30-second timeout would duplicate every long job.

"You have 12 partitions and lag is growing. You add 10 more consumers. What happens?"

If the group already had 12 consumers, nothing good. Each partition goes to at most one consumer in a group, so the new consumers sit idle, and the group pays for a rebalance on top. To add parallelism, either increase partitions (which remaps keys and briefly breaks per-key ordering), or increase work per consumer: process records concurrently inside a consumer while keeping per-key order, or batch downstream writes. First check whether the real bottleneck is downstream; more consumers will not fix a saturated database.

"What is the difference between requeue in RabbitMQ and a visibility timeout in SQS, from a poison-message point of view?"

Requeue returns the message right away, usually to the head of the queue, so a poison message can loop thousands of times per minute and block consumers. A classic queue does not count those attempts. A visibility timeout adds a built-in delay between attempts, and SQS counts receives, so a redrive policy moves it to the DLQ after N tries. In RabbitMQ, quorum queues add the missing counter and a delivery limit, which is one reason to prefer them.

"Why scale on the age of the oldest message instead of queue depth?"

Because age is what users feel and depth is not. By Little's law, wait ≈ depth / throughput. The same 10,000 messages mean 25 seconds of delay with healthy workers and minutes when they slow down. Age tracks that directly. Its weakness is a single stuck message, which inflates age without real backlog, so pair it with depth and make sure poison messages leave for the DLQ quickly.

"Walk me through the outbox pattern's failure cases."

The order and outbox rows commit together, so the database and the intent to publish always agree. The relay can then fail in two places. If it crashes before publishing, the row stays unsent and is published on restart: a delay, not a loss. If it crashes after publishing but before marking the row sent, the message is published twice. So consumers must deduplicate on the event ID. Also watch the outbox's size: a stuck relay shows up as rising unsent rows, which is your alert. And per-aggregate order holds only if the relay publishes in commit order per key.

"Your consumers need strict per-customer ordering, and one message for a customer keeps failing. What do you do?"

You cannot skip it without breaking that customer's order, so you hold the key, not the queue. Retry in place with backoff a few times. If it still fails, park that customer: move the failing message and every later message for the same key to a holding area, and keep processing other customers. Alert a human, fix the cause, then replay the parked messages in order. If the domain allows it, the better long-term fix is consumers that tolerate disorder through version numbers.

"The flash sale backlog is 552,000 messages. The business wants it cleared in 10 minutes. Is that achievable?"

Do the math with arrivals included. After the sale, orders still arrive at 200 per second, so processing must reach 552,000 / 600 + 200 = 1,120 per second. That is 56 workers at 20 per second each. But the pipeline's database tops out at 400 writes per second, so more workers will not get there. The queue buys you the right to choose drain time, within the downstream ceiling. Either raise that ceiling (batched writes, more database capacity) or agree a longer drain, about 46 minutes at the current limit.
