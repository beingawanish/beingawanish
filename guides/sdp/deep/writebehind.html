Deep Dive: Inside the Mechanism

The lesson describes write-behind as four parts: dirty tracking, coalescing, a flush policy and failure handling. That is the right map. A design review needs the street-level view, though, because almost every write-behind bug lives in the gaps between those boxes. What happens to an increment that lands while the flusher is halfway through a batch? What if the flusher commits to the database and then dies before it marks the batch clean? This section builds the view counter as you would really run it on Redis and Postgres, then looks at how packaged products do the same job.

The keys: a display total, a pending delta, a dirty index

One counter is really three pieces of state, and keeping them apart is what makes the flush safe.

  • The display total, views:{17}:8412. This is what the product page reads. It holds the full count, so the page never has to add anything up.
  • The pending delta, delta:{17}:8412. This holds only the increments the database has not yet received. The flusher drains it. The page never reads it.
  • The dirty index, dirty:{17}, a sorted set. Each member is a product ID. Its score is the time that product first became dirty since its last flush. That score turns out to be the most useful number in the whole design, as you will see under the metrics.

The {17} is a Redis Cluster hash tag. Cluster places a key by hashing only the text inside the braces, so all three keys for bucket 17 land in the same slot on the same shard. That matters because the write path below runs as one Lua script, and a script may only touch keys in a single slot. The bucket is product_id mod 256 or similar. It also gives you per-key ordering for free: one flusher owns each bucket, so no two flushers ever race on the same product.

The write path: one atomic script

Each page view runs one script. It bumps the total, bumps the delta and records the dirty time, all in one step that no other command can interleave with:

-- KEYS[1] = views:{17}:8412   KEYS[2] = delta:{17}:8412   KEYS[3] = dirty:{17}
-- ARGV[1] = 8412 (product id)  ARGV[2] = now in ms
local total = redis.call('INCR', KEYS[1])
redis.call('INCR', KEYS[2])
redis.call('ZADD', KEYS[3], 'NX', ARGV[2], ARGV[1])   -- NX: keep the FIRST dirty time
return total

The NX flag on ZADD is doing real work. Without it, every increment would push the score forward, and a key written constantly would always look freshly dirty. Its oldest unflushed increment could then sit there indefinitely without your metrics noticing.

The script returns the new total, so the page can show the exact count right after its own view. In practice most teams don't bother: the page renders the total it read a moment ago, and nobody can tell.

The flush protocol, step by step

The flusher for bucket 17 wakes every 2 seconds (or sooner, if the dirty index passes a size threshold). It runs four steps. The order is the whole design.

  1. Pick the batch. ZRANGE dirty:{17} 0 499 returns up to 500 product IDs, oldest first.
  2. Move the deltas aside, atomically. A second script, per batch, does this for each ID: GETDEL delta:{17}:id, write the value into a hash inflight:{17}:F (where F is a fresh flush ID, such as a UUID), and ZREM the ID from the dirty index. It also adds F to a small set, inflight-index:{17}. New views that arrive a microsecond later simply create a fresh delta key and re-add the ID to the dirty index. Nothing is lost and nothing is counted twice, because the move is a single script.
  3. Apply to the database, idempotently. In one Postgres transaction: 
    INSERT INTO applied_flushes (flush_id) VALUES ($F) ON CONFLICT DO NOTHING;
-- only if that inserted a row:
UPDATE product_views pv
   SET views = pv.views + b.d
  FROM (VALUES (8412, 24000), (113, 3), (9001, 1) /* ... up to 500 */) AS b(id, d)
 WHERE pv.product_id = b.id;
COMMIT;
  4. Clean up. DEL inflight:{17}:F and SREM inflight-index:{17} F.

Now walk the crashes. If the flusher dies after step 2, the batch is safe in Redis as inflight:{17}:F. On restart, the flusher reads inflight-index:{17} and replays step 3 for every flush ID it finds. If it dies after the commit but before step 4, the replay hits the applied_flushes row and does nothing. The delta is applied exactly once either way.

That small applied_flushes table is the difference between a counter that drifts and one that doesn't. Prune it after a day or so. A flush ID older than that will never be replayed.

Deltas versus absolute values

The protocol above leans on one lucky property: increments commute. +3 then +5 lands in the same place as +5 then +3, so a replayed or reordered batch is harmless once it is deduplicated.

Absolute values do not commute. Suppose the cache buffers a product's status field, and two flushes carry active and then archived. If a retry lets the older flush land second, the product comes back to life. The fix is a version number on every buffered write and a conditional apply:

UPDATE products SET status = $s, version = $v
 WHERE id = $id AND version < $v;

An old flush then changes zero rows. Last-write-wins only works if "last" is decided by a version the writer stamped, never by the order flushes happen to reach the database.

Pinning dirty data in Redis

The lesson says dirty entries must be pinned. Redis has no per-key pin, so you get the same effect from the eviction policy and from instance layout.

  • maxmemory-policy allkeys-lru (or allkeys-lfu) may evict any key, deltas included. That is the wrong policy for a write-behind instance.
  • volatile-lru and its siblings evict only keys that have a TTL. Give read-cache keys a TTL, give deltas, totals and in-flight hashes none, and the dirty data is never a candidate. This works, but one stray key without a TTL in the read cache now also becomes un-evictable.
  • noeviction refuses writes once memory is full. For a counter store that is honest: the write path fails loudly and can fall back to a direct, slower path.

The cleanest answer is a separate Redis instance for write-behind state, with noeviction and persistence turned on, apart from the read caches running allkeys-lru. The two jobs want opposite settings, and one shared instance forces you to pick the wrong one for half your data.

The durability knobs, and what each really buys

The lesson lists AOF and replicas as ways to shrink the window. Here is what each setting actually covers.

  • appendonly yes with appendfsync everysec. Redis appends every write command to a log and fsyncs it about once a second. A crash loses roughly the last second of writes. It can stretch toward two seconds when the disk is slow, because Redis will delay rather than block on a lagging fsync. This is the usual production setting and costs little.
  • appendfsync always. Fsync on every write batch. The loss window drops to almost nothing, and throughput becomes disk-bound. At that point you have rebuilt a database's commit path inside the cache. Ask why the database itself wasn't the answer.
  • Replicas with Sentinel or Cluster failover. Replication is asynchronous. A promoted replica is missing whatever the old primary had not yet shipped, usually milliseconds of writes, more when the link lags. min-replicas-to-write 1 with min-replicas-max-lag 10 makes the primary refuse writes when no replica has acknowledged within 10 seconds, which caps how far a partitioned primary can run ahead.
  • WAIT 1 50 after a write blocks until one replica confirms it, or 50 ms pass. It narrows the window for that write. It does not make Redis a consensus store: a failover can still pick a replica that missed it, and the Redis documentation is explicit about that.

Notice that every knob is a dial between "cache" and "database." None of them is free, and none of them is total. That is why the loss sentence comes first and the knob settings follow from it.

Packaged write-behind: data grids and your own kernel

Data grids ship this pattern as configuration. In Hazelcast, a map backed by a MapStore becomes write-behind when write-delay-seconds is above zero (zero means write-through). write-batch-size sets how many entries go to one storeAll call. write-coalescing, on by default, keeps only the latest value per key. That last setting is the coalescing from the lesson, and turning it off makes the grid deliver every intermediate update, which is what you want when the store is an audit trail and not a table of current values.

The friendliest example is the one running under you right now. The Linux page cache is a write-behind cache in front of your disk. A write() returns once the bytes are in memory and the page is marked dirty. Kernel flusher threads write dirty pages back later: by default they wake every 5 seconds (vm.dirty_writeback_centisecs = 500) and write pages that have been dirty for more than 30 seconds (vm.dirty_expire_centisecs = 3000). fsync() is the "flush this now" escape hatch. Every database that promises durability calls it. Write-behind is not exotic. It is what every layer does by default unless someone pays to opt out.

Deep Dive: Sizing and the Numbers

Assumptions for this section, so you can redo the math with your own: the flash sale peaks at 18,000 page views per second. 12,000 hit the bestseller, as in the lesson. The other 6,000 are spread over about 30,000 other products, roughly 0.2 views per second each. Counters live in a narrow Postgres table, product_views(product_id, views).

Coalescing works on hot keys, barely on the tail

The lesson's 24,000x reduction is real, but it is a property of the bestseller, not of the catalog. A key coalesces only if it gets several writes inside one flush interval. A product with 0.2 views a second gets 0.4 views in a 2-second window. Most windows it is dirty once or not at all.

For a tail product with rate r and interval T, the chance it is dirty in a window is 1 − e^(−rT). Multiply by 30,000 products and divide by T to get row updates per second:

Read the 2-second row. The bestseller went from 12,000 row updates a second to 0.5. That was the incident, and it is solved. The tail went from 6,000 to about 4,950. Barely a dent.

The fix is not to stretch everything to 60 seconds. It is to notice that you can run two policies. Flush hot keys every 2 seconds, because they coalesce anyway and their loss window costs the most views. Flush the tail every 30 seconds, because there the interval is the only thing that buys coalescing. Write both loss sentences. "If we lose 30 seconds of tail views, then 180,000 views spread over 30,000 products go missing, about six each." For view counts that is still fine. For anything else, say it out loud before you agree.

Batching still helps the tail, just in a different way. At 500 rows per statement, 4,950 rows a second is about 10 statements a second instead of 6,000 single-row transactions. Fewer round trips, fewer commits, far fewer fsyncs. The rows themselves still each cost a new row version and a WAL record.

What each row update costs in Postgres

Postgres never updates a row in place. Each UPDATE writes a new row version and leaves the old one for vacuum. That is why the counter belongs in its own narrow table and not as a views column on the wide products row. On the wide table, every flush rewrites a row that carries the name, description and specs. On the narrow table, the new version is a few dozen bytes.

Two settings help further. Lower the table's fillfactor (say 70) so each page keeps free space. Keep views out of every index. Together they let most updates be HOT updates: the new version goes on the same page and no index entry has to change. Vacuum cost then stays proportional to what really changed.

Redis: memory is trivial, the hot shard is not

Memory first. Each counter is two small keys plus a sorted-set member. Small Redis keys cost on the order of 50 to 100 bytes each, depending on version and encoding. 100,000 products times three entries at 100 bytes is about 30 MB. The dirty index at its fullest holds 30,000 members, a few more MB. This is not where the money goes.

Throughput next. The write path is one script per view: 18,000 calls a second in total, 12,000 of them on whichever shard owns the bestseller's bucket. Redis runs commands on one main thread, so a single key cannot be spread across cores. A shard handling 12,000 short scripts a second has headroom on ordinary hardware, but the exact ceiling depends on the machine, the script and the client. Measure it, and know your multiple.

When one key needs more than one shard can give, two moves exist:

  • Pre-aggregate in the app. Each app instance keeps a local map of product → count and sends INCRBY every 100 ms. With 60 instances, the bestseller's shard sees 600 calls a second instead of 12,000. The price is a second, smaller loss window: an app crash loses up to 100 ms of its own views. That is write-behind in front of write-behind, and it is how very large counter systems are usually built.
  • Split the counter. Write to views:8412:#0 through #15, chosen at random, with hash tags that send them to different shards. Reads sum the 16 parts. Writes scale out. Reads get 16 times more expensive, so pair this with a short-lived cached sum.

Catch-up after a database outage

Suppose Postgres is unavailable for 10 minutes during the sale. The flusher keeps retrying, and the dirty index grows. How big does the backlog get?

For counters, the answer is pleasant. Deltas keep merging, so the backlog is bounded by the number of distinct keys, not the number of events. After 10 minutes, the dirty index holds at most the 30,001 products that got views. When the database returns, the flusher drains them. Capped at 5,000 rows a second, that takes about 6 seconds.

Now imagine the same outage for data that does not coalesce, such as new review submissions at 50 a second. The backlog is 30,000 separate entries, all sitting in cache memory, all acknowledged, all at risk. That asymmetry is the practical reason the lesson sends non-coalescing writes to a queue. A broker is built to hold a growing backlog on disk. A write-behind cache is built to hold a bounded set of hot keys in memory.

Deep Dive: Failure Modes in Production

Write-behind failures share one cruel property. They rarely raise errors. Numbers just come out a little wrong, and nobody looks until finance or a partner asks. So each failure below lists the metric that catches it, because without one you will not know.

1. Counts quietly drop during a traffic spike

Symptom. After a busy evening, several tail products show fewer views in the database than their dashboards showed during the day. No errors anywhere.

Mechanism. The counters share a Redis instance with the read caches, under allkeys-lru. The sale filled memory with product descriptions, and Redis evicted the least recently used keys. Some of those were pending deltas for quiet products. The flusher found the ID in the dirty index, ran GETDEL, got nothing and moved on.

Detect. evicted_keys in INFO stats rising on any instance that holds dirty state. Count "dirty ID with no delta" in the flusher as its own metric. It should be zero, always.

Fix. Separate instance for write-behind state, noeviction, memory alarm at 70%. If they must share, use volatile-lru and give every read-cache key a TTL.

2. Undercounting under load: the read-then-reset race

Symptom. The bestseller's database count trails the cache by a steady few percent, more on busier days.

Mechanism. An early flusher did GET delta, wrote the value to the database, then SET delta 0. Every increment that landed between the GET and the SET was wiped. At 12,000 a second and a 3 ms gap, that is about 36 lost views per flush. Classic lost update.

Detect. A reconciliation job: for a sample of keys, compare views in the cache against the database value plus pending delta plus any in-flight batches. A steady gap that grows with traffic is a race. A gap that shows up in steps is a crash.

Fix. Never read and reset in two commands. Use GETDEL (Redis 6.2 and later), RENAME, or a Lua script that moves the value aside atomically, as in the protocol above.

3. Overcounting after a flusher restart

Symptom. Counts jump by one batch's worth after deploys of the flusher service. The bestseller suddenly has 24,000 extra views.

Mechanism. The flusher committed the batch to Postgres, was killed before it deleted the in-flight hash, and replayed the batch on restart. The database got the same +24,000 twice.

Detect. The same reconciliation job, this time showing the database ahead of the cache. Correlate the jumps with flusher restarts in your deploy log.

Fix. Flush IDs recorded in the same transaction as the update, as in applied_flushes above. This is the idempotency lesson applied to your own internal pipeline. At-least-once delivery plus an idempotent apply is how you get "exactly once" in practice.

4. A failover loses writes the replica never saw

Symptom. After an automatic Redis failover, the display counters for a few hundred products step backwards by a small amount.

Mechanism. Replication is asynchronous. The old primary had acknowledged increments it had not yet shipped. The promoted replica never saw them. Worse, during a network partition, an old primary can keep accepting writes from clients on its side, and those writes are discarded when it rejoins as a replica.

Detect. Sentinel or Cluster failover events, plus replication offset lag (master_repl_offset versus each replica's offset) graphed in bytes and seconds. Lag that is usually near zero but spikes under load tells you how big the loss can be.

Fix. Decide whether it matters, using the loss sentence. If it does, set min-replicas-to-write and min-replicas-max-lag to bound the partition case, and accept that a few milliseconds of loss remain. If even that is unacceptable, the data does not belong in write-behind.

5. One bad row stalls a whole bucket

Symptom. Oldest-dirty age for bucket 17 climbs from 2 seconds to 40 minutes. Other buckets are fine.

Mechanism. A product was deleted, and product_views has a foreign key to products. Actually the update simply matches no row for that ID, which is harmless. The real stall came from a different row whose batch hit a check constraint after a schema change. The batch statement is all-or-nothing, so the flusher retried the same 500 rows forever. Every later batch in that bucket waited behind it.

Detect. Oldest-dirty age per bucket (the ZRANGE … WITHSCORES of the first member), and consecutive flush failures per bucket. Alert on age, not on errors. Age is what the loss sentence is written in.

Fix. On a batch failure, split it in half and retry each half, recursively, until the bad row is isolated. Move that row to a quarantine table with its error and keep going. A 500-row batch finds its poison row in about nine splits. This is the dead letter queue idea for a flusher.

6. The counter goes backwards on the page

Symptom. A user refreshes and sees "12,483 viewed today" drop to "12,105," then climb back a few seconds later.

Mechanism. The display total was lost (a restart without persistence, or a well-meant TTL on the total). The read path treated it as a normal cache miss and reloaded it from the database, cache-aside style. But the database is behind by whatever sits in the delta and in-flight batches. The page showed the lagging value until the next flush caught up. This is truth inversion biting the cache's own refill path.

Detect. Log when a display total is rebuilt from the database while a delta exists for the same key. Any such event is this bug.

Fix. Rebuild as database value plus pending delta plus in-flight batches, in one script. Better still, never expire display totals on the write-behind instance, and persist it.

7. Flush surges: synchronized timers and post-outage catch-up

Symptom. Database CPU shows a sawtooth with a spike every 2 seconds. Separately, after a 10-minute database outage, the database falls over again within a minute of coming back.

Mechanism. All 256 bucket flushers started from the same deploy and wake on the same clock tick, so their batches arrive together. After an outage, every flusher has a full backlog and drains it at full speed into a database that is still warming its own caches.

Detect. Database transactions per second at one-second resolution (one-minute averages hide the sawtooth). Flush rows per second during recovery.

Fix. Add random jitter to each flusher's start offset, and cap the total drain rate with a shared token bucket. Drain hot keys first, oldest dirty first. The catch-up should be paced like any other backpressure problem: the database sets the speed, not the backlog.

The four numbers to put on one dashboard

  • Oldest dirty age, per bucket and overall. This is your real durability window, measured. If the design says 2 seconds and this says 90, the design is not what is running.
  • Dirty key count, and in-flight batch count. Rising without traffic rising means the flusher is losing.
  • Reconciliation drift: cache total minus (database + delta + in-flight), sampled. It should be zero. Negative is lost data. Positive is double application.
  • Quarantine size and evicted_keys on the write-behind instance. Both should stay at zero.

The decision that matters most is the third row, and it deserves an opinion. When the same data feeds both a live display and money, split it. The token-metering example in the lesson is the template. Every event goes to a durable log first. One consumer keeps the Redis counters current for dashboards. Another computes invoices from the log. Now the display can be as lossy and fast as you like, because it is a view and not the record. The record never lived in a cache.

A smaller opinion on the second row. App-side pre-aggregation is underrated. Teams reach for Redis Cluster resharding or split counters when the cheapest fix is a 100 ms local buffer. It cuts the hot shard's load by the number of app instances, and its loss window is shorter than the flush window you already accepted.

Deep Dive: Design-Review Checklist

  1. Is the loss sentence written down for every data type in the buffer, with N set to the real worst case: flush interval plus fsync lag plus replica lag plus time to detect a stuck flusher?
  2. Do the operations commute? If not, where does the version come from, and does the apply refuse older versions?
  3. What makes the flush idempotent? Show what happens if the flusher dies after the database commit and before it clears the batch.
  4. How are deltas moved aside without losing increments that arrive mid-flush? Is it one atomic command or script?
  5. Can any key holding unflushed data be evicted? Which instance, which maxmemory-policy, and what happens at full memory?
  6. What is the persistence and replication setting, and what loss does a failover add on top of the flush window?
  7. Who else reads the database copy directly? Do they know it lags, and do their outputs carry an "as of" time?
  8. How is a lost display total rebuilt? Does the rebuild include pending and in-flight deltas, or will counters go backwards?
  9. What happens to one batch that keeps failing? Is there a split-and-quarantine path, and an alert on oldest-dirty age per bucket?
  10. How does the flusher drain a backlog after a database outage, and what caps its rate?
  11. Do graceful shutdowns flush, and is the shutdown grace period (for example Kubernetes' terminationGracePeriodSeconds, 30 s by default) longer than a worst-case flush?
  12. Is any of this data ever used for money, limits or compliance, now or in the roadmap? If yes, which durable path does that use carry?

Deep Dive: Senior Interview Follow-ups

"Your flusher writes to the database and then crashes before it marks the entries clean. What happens?"

With a naive flusher, the restart re-sends the batch and the counts are applied twice. The fix is to give each batch an ID and record it in the same database transaction as the update, with a unique key. The replay then inserts nothing and skips the update. The batch itself has to survive the crash too, so it is moved into an in-flight structure in Redis before the database call, not held only in the flusher's memory.

"Can't you make Redis durable with AOF and call it a database?"

You can narrow the window, but you can't close it cheaply. appendfsync everysec still allows about a second of loss, sometimes more when the disk lags. always closes most of it but makes throughput disk-bound, which removes the reason you came. Replication is asynchronous, so a failover can drop acknowledged writes, and WAIT narrows that without making it a consensus guarantee. If the data needs every write to survive, keep it on a path designed for that: the database or a replicated log.

"The view count is fine, but now product wants 'top 10 most viewed this hour' computed from the database. Problems?"

Two. The database is behind by the flush window, so the ranking lags slightly, which is probably fine if labelled. The bigger one is the tail interval: if tail products flush every 30 seconds, a product that trends in the last 30 seconds is invisible to the database. Either compute the ranking from the cache side, for example a Redis sorted set updated in the same write script, or compute it from the durable event stream if one exists. Don't build it on the lagging copy and then wonder why it misses fast movers.

"Why not just batch in the application and skip Redis?"

For a single-instance service, that is fine and simpler. With 60 instances, each holds a partial count, so no single place has the live total for the page to read. You'd need to sum across instances on every read, or accept that the page shows the stale database value. Redis is there to be the one live, shared total. The good design often uses both: a 100 ms in-process buffer to cut write load, and Redis as the shared live view.

"How does write-behind handle updates to the same key arriving out of order from two app servers?"

For increments, order doesn't matter, because addition commutes. For absolute values it matters a lot. The writer must stamp a version (a database sequence, a hybrid logical clock, or a per-key counter in Redis assigned by the same script that buffers the write). The flush applies with WHERE version < $v. Ordering by arrival at the cache is not enough, because a slow app server can deliver an older write later.

"Redis memory is full. What should the write path do?"

It depends on the policy you chose, and you should have chosen deliberately. With noeviction, writes fail. The client should then fall back to a direct, rate-limited database increment, or drop the view and count the drop, depending on the loss sentence. What must not happen is silent eviction of dirty data, which is what allkeys-lru gives you. Losing data you acknowledged, with no error, is the worst outcome on the menu.

"The 24,000x reduction sounds great. Does it hold across the whole catalog?"

No, and saying so is the point of the question. Coalescing depends on how many writes a key gets per flush interval. The bestseller gets 24,000 in 2 seconds. A long-tail product getting 0.2 writes a second gets 0.4, so it barely coalesces at all: catalog-wide, a 2-second flush cuts tail row updates by only about 20%. You either accept that, run a longer interval for cold keys with its own loss sentence, or rely on batching (500 rows per statement) to cut transaction overhead even where coalescing doesn't help.

"When would you pick write-behind over a queue even with no live reads?"

Rarely. The one strong case is heavy coalescing on hot keys where the downstream store charges per write, such as a metered database. Merging 24,000 events into one write saves real money, and a queue consumer can do the same merge but holds every event first. Even then, many teams put a log first and coalesce in the consumer, because replay from the log is worth more than the memory saved. If nobody reads the live value, the cache's main advantage is gone.
