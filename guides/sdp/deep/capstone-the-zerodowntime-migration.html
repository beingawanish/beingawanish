Deep Dive: Inside the Mechanism

The capstone's five stages are the right plan. A review panel will accept the plan in five minutes and then spend an hour on what each stage does inside the database. This section uses Postgres, since its behaviour is well documented, and walks the stages at that level. MySQL has equivalents for most of it, and the differences are noted where they matter.

Stage 1: the cheap ALTER and the lock queue behind it

ALTER TABLE orders ADD COLUMN total_cents BIGINT NULL is a metadata-only change in Postgres. No rows are rewritten, and it finishes in milliseconds. That is why the lesson can call it free.

The trap is the lock. Every ALTER TABLE of this kind needs an ACCESS EXCLUSIVE lock, if only for a moment. If a long-running query holds even a weak lock on orders (a 40-minute analytics query, say), the ALTER waits. And while it waits, every new query on orders queues behind the ALTER, because Postgres grants locks in order. Reads and writes stop. At 400 writes a second, the connection pool is exhausted in seconds. A millisecond change has caused an outage.

The defence is two settings and a retry loop:

SET lock_timeout = '2s';           -- give up quickly instead of blocking everyone
SET statement_timeout = '15s';
ALTER TABLE orders ADD COLUMN total_cents BIGINT NULL;
-- on lock_timeout: wait a few seconds, retry, up to N times, then page a human

The migration tool should do this for every DDL statement, not just the scary ones. This is the "unexpected locks" the lesson mentions, and it is the most common way a "change that changes nothing" pages someone.

Notice what Stage 1 deliberately avoids. ALTER TABLE orders ALTER COLUMN total TYPE BIGINT USING round(total*100) would do the whole migration in one statement. It also rewrites all 200 million rows while holding ACCESS EXCLUSIVE the whole time. That is the maintenance window the brief says does not exist.

The rounding question nobody asks until Stage 3

"Set total_cents = round(total × 100)" sounds like one rule. In practice it is three, and they disagree.

  • Floating-point input. total is a binary float, so the value stored for 1.005 is slightly below 1.005. Multiply by 100 and you get 100.49999999999999, which rounds to 100, not 101. The stored float already lost the half-cent.
  • Tie rules. Postgres rounds numeric ties away from zero, but its round(double precision) follows the platform, which is usually round-half-to-even. Python's round() is half-to-even. Java's Math.round rounds half up. A value like 0.125, which is exact in binary, becomes 12.5 cents, and then 12 or 13 depending on who rounded it.
  • Two writers. The backfill runs in SQL. The dual-write runs in application code. If they use different rules, the comparison job in Stage 3 will find mismatches that are not bugs in either path, only disagreements between them.

So the migration needs a written rounding rule before Stage 2, and both writers must implement it identically. The safest version converts through decimal first: round(total::numeric * 100) in SQL, and Decimal(repr(total)) * 100 quantised with the same tie rule in Python. Then ask the harder question, which is a finance question: is round(total × 100) even the right value? The column is being replaced because it drifted from the payment provider's records. For orders where provider data exists, the provider's amount in cents may be the truth, and total is the suspect.

Stage 2: a backfill that is safe against concurrent writes

The backfill walks the table in primary-key order, one batch per transaction:

UPDATE orders
SET    total_cents = round(total::numeric * 100)::bigint
WHERE  id > $last_id AND id <= $last_id + 5000
  AND  total_cents IS NULL;
-- save $last_id + 5000 to the checkpoint table, commit, sleep per throttle

The detail that makes this safe is that the new value is computed inside the UPDATE, from the row's own total. If the application updates an order while the batch is running, Postgres' row locking makes one of them wait. Under the default READ COMMITTED isolation, the backfill then re-checks the updated row and recomputes from the new total. The IS NULL guard means rows the dual-write already set are skipped.

Compare the tempting alternative: an application job that SELECTs a batch, computes cents in Python, and writes them back. Between the read and the write, a customer's order total can change and the dual-write can set the new cents. The job then overwrites it with cents computed from the old total. That is a lost update, and it produces exactly the kind of mismatch Stage 3 is designed to find. Keep the computation in the statement.

Two more details. Keyset batches (id > $last_id) stay fast across the whole table, while OFFSET pagination gets slower with every batch. And each batch should be small enough to hold row locks for well under a second, so it never makes a customer's checkout wait noticeably.

Dual-write here is atomic, and that is a gift

Both columns are in the same row of the same table, so the dual-write is one INSERT or UPDATE that sets both. It succeeds or fails as a unit. There is no window where total is written and total_cents is not.

This is worth saying out loud in the review, because it is the reason this capstone's dual-write is safe at all. The general dual-write problem, writing to two different systems, has no such guarantee. If the new form lived in a different table in another database, or in a new service, the dual-write would need an outbox or change data capture, as the webhooks and event-driven lessons explain. The "Evolution path" below comes back to this.

Tightening the new column without a table scan under lock

Once every row has a value, the new column should become NOT NULL. The obvious ALTER TABLE orders ALTER COLUMN total_cents SET NOT NULL scans all 200 million rows while holding ACCESS EXCLUSIVE. The safe sequence takes three steps:

ALTER TABLE orders ADD CONSTRAINT total_cents_not_null
  CHECK (total_cents IS NOT NULL) NOT VALID;          -- instant, enforced for new writes
ALTER TABLE orders VALIDATE CONSTRAINT total_cents_not_null;
  -- scans, but under a lock that still allows reads and writes
ALTER TABLE orders ALTER COLUMN total_cents SET NOT NULL;
  -- Postgres 12+ uses the validated CHECK and skips the scan
ALTER TABLE orders DROP CONSTRAINT total_cents_not_null;

The NOT VALID check also works as a tripwire. Any old code path that inserts an order without setting total_cents now fails loudly. Whether that is what you want depends on stage: before the comparison job has found every old writer, a loud failure on a checkout path is an outage. Add it once the comparison count is zero, not before.

Stage 5: what dropping a column actually breaks

ALTER TABLE orders DROP COLUMN total is also metadata-only in Postgres. The column is marked dropped, and its space is reclaimed later as rows are rewritten. The database side is easy. The application side is where drops go wrong:

  • ORMs that list every column. A model that still declares total will generate INSERT and SELECT statements naming it. Those fail the moment the column is gone. Before the drop, deploy code that tells the ORM to ignore the column (Rails has ignored_columns; other ORMs have equivalents), and let it run everywhere.
  • Cached prepared statements. A server-side prepared SELECT * FROM orders has a fixed result shape. After the drop, Postgres can reject it with "cached plan must not change result type." Drivers that auto-prepare repeated queries hit this even if your code never says PREPARE.
  • Consumers you did not know about. A finance export, a BI tool's saved query, a CDC consumer whose schema mapping lists total. The tracing lesson's dependency map helps with services. Query logs and pg_stat_statements help with everything else.

Deep Dive: Sizing and the Numbers

A review panel will ask "how long, and what does it cost the database?" These numbers use stated assumptions: 200 million rows, about 200 bytes per row, six indexes on orders, 400 production writes a second, one primary with two streaming replicas, and twelve consumers, several fed by change data capture.

Backfill rate: set by the slowest downstream, not by the primary

The primary can probably update 20,000 rows a second in batches. That is not the limit. Every backfilled row is an UPDATE, and every update goes everywhere a normal write goes: the WAL, both replicas, and every CDC consumer.

Backfill rateTime for 200M rowsRow changes vs production (400/s)What it risks
20,000 rows/s2.8 h50×Replica lag in minutes, CDC consumers hours behind, WAL disk pressure
5,000 rows/s11 h12.5×Likely too fast for consumers sized for peak plus 2× headroom
2,000 rows/s28 h5×Manageable if consumers have the headroom; check
1,000 rows/s2.3 days2.5×Safe for most setups

Take a CQRS projection sized for 800 events a second (twice production). At a 2,000 rows/s backfill it receives 2,400 a second and falls behind by 1,600 a second. After one hour it is 5.8 million events behind. After the full 28 hours it is days behind, and the read side it feeds is stale for everyone. That is a user-visible incident caused by a step the lesson calls invisible.

So the throttle should be adaptive. Measure replica lag and the lag of each CDC consumer, and slow the backfill when any of them crosses a budget (say 5 seconds for replicas and 60 seconds for consumers). Pause entirely during the daily peak. Two to three days for the backfill is a perfectly good answer. If CDC consumers can recognise backfill updates, for example because the only changed column is total_cents, they can skip the work quickly, which raises the safe rate.

WAL, bloat and vacuum

Postgres never updates a row in place. Each backfilled row writes a new row version and leaves a dead one. With the default fill factor of 100, pages are usually full, so most new versions land on other pages and every index gets a new entry too. That is seven writes per row (heap plus six indexes), before full-page images after each checkpoint.

Rough WAL volume is therefore on the order of the table's size or more: the 40 GB table could easily generate 50 to 100 GB of WAL over the backfill. Treat that figure as an estimate to check on a staging copy, not a promise. The practical consequences:

  • WAL disk and archiving. Backups and point-in-time recovery archive every byte. Check the archive's throughput and storage at the backfill rate.
  • Replication slots. A CDC consumer that falls behind holds WAL on the primary through its slot. A slow consumer plus a fast backfill can fill the primary's disk. Alert on slot lag in bytes.
  • Bloat. 200 million dead row versions is roughly another table's worth of dead space until vacuum reclaims it. Throttled batches give autovacuum time to keep up. Watch dead-tuple counts and run a manual VACUUM between large chunks if needed.

Verification cost

A full comparison pass reads 200 million rows. At a scan rate of 50,000 rows a second on a replica, that is about 67 minutes per pass. Run full passes daily on a replica, and incremental passes every few minutes over rows whose updated_at is recent.

Running on a replica creates false positives: the replica may have the new total but not yet the new total_cents if they arrived in different transactions. (In this migration they do not, because the dual-write sets both in one statement. But the backfill sets total_cents later than the original total.) The rule is simple: re-check every mismatch on the primary before counting it. Only confirmed mismatches go on the dashboard.

Shadow reads are cheap here, because both values are already in the same row the read fetched. The cost is computing the comparison and logging mismatches, which is negligible. They can run on 100% of reads.

Deep Dive: Failure Drills

A good review runs drills: "it is Tuesday of week 2, this happens, what do you do?" For each, the answer should name the signal that fires and the undo button from the capstone's debrief table.

1. The ALTER freezes checkout for 40 seconds

Signal. Connection pool saturation on every orders service, p99 latency spikes, then a burst of timeouts. pg_stat_activity shows dozens of sessions waiting on a lock, all behind the ALTER, which itself waits behind one long analytics query.

Mechanism. The lock queue described in Stage 1. The migration tool did not set lock_timeout.

Response. Cancel the ALTER (pg_cancel_backend); the queue drains at once. Re-run with lock_timeout and retries. Long-term: every migration sets a lock timeout by default, and analytics queries run on a replica.

2. The backfill makes the order-history page stale

Signal. Customer reports that new orders are missing from "My orders." The CQRS projection's consumer lag is at 3 million events and rising.

Mechanism. The backfill's updates flow through CDC to the projection at five times its normal rate.

Response. Pause the backfill. It is checkpointed, so it resumes where it stopped. Let the projection catch up, then restart at a rate tied to consumer lag. Undo cost: zero. Lesson: the backfill's throttle needs every downstream's lag as an input, not just the primary's load.

3. The comparison job finds 40,000 mismatches of exactly one cent

Signal. The mismatch count is large, stable, and every difference is ±1 cent. The mismatched rows cluster on totals with a third decimal place, often from tax calculations.

Mechanism. The backfill rounded in SQL, the dual-write rounded in Python, and their tie rules differ.

Response. Nothing user-facing has changed, because reads still use total. Pick one rounding rule, fix the writer that disagrees, and re-run the backfill for those rows with the IS NULL guard removed for that range. This is the drill that justifies Stage 3: without it, 40,000 orders would have silently changed by a cent at read-switch time.

4. Rows keep appearing with total_cents NULL

Signal. After the backfill, a small trickle of new rows (a few hundred a day) has total_cents IS NULL.

Mechanism. The lesson's "one old path": here, a nightly job for manual refunds that inserts orders with raw SQL, bypassing the code with the dual-write flag.

Response. Find the writer. pg_stat_statements lists every statement shape touching orders; the application_name on the session names the client. Fix the job, re-backfill its rows. Then add the NOT VALID check constraint, so any further unknown writer fails loudly instead of silently. A database trigger that fills total_cents would have caught this path automatically, which is the strongest argument for the trigger option below.

5. At 10% of reads, disputes on refunds rise

Signal. The read ramp's business gate shows refund disputes in the canary group at twice baseline. Errors and latency are flat.

Mechanism. The refund service computes partial refunds as a fraction of the total. With cents it truncates instead of rounding, so customers get one cent less. The data is right; one consumer's arithmetic is wrong.

Response. Flip the read flag back to 0%. Because dual-write is still on, total is current and the flip is safe. Fix the refund arithmetic, add a test, ramp again. This is the drill that shows why Stage 5a waits for every consumer to be confirmed, not just for the column to be correct.

6. A bug is found two days after old writes stopped

Signal. A reporting consumer, missed by the inventory, still reads total. Its revenue report has been flat for two days because total stopped changing.

Mechanism. The one-way door was entered with an incomplete consumer list.

Response. Roll forward, as the lesson says. Do not turn dual-write back on as a rollback: that would only fix new rows. Two days of rows would have a stale total, and any consumer reading it would see a mix. Instead, migrate the report to total_cents and re-run it for the two days. If a rollback were truly needed, it would mean a reverse backfill of total from total_cents for every row changed since the flip: a project, not a button. Name that in the runbook before the door, so nobody improvises it under pressure.

7. The drop breaks a service that never reads the column

Signal. Seconds after DROP COLUMN, one service logs "cached plan must not change result type" on every request.

Mechanism. The service used SELECT * FROM orders through a driver that prepares repeated statements on the server. The result shape changed under it.

Response. Restarting the service's pods clears the cached plans and fixes it. Before the next drop, grep for SELECT * on the table, and check that drivers or poolers handle plan invalidation. There is no undo for the drop itself short of restoring from the snapshot, which is why the drop is last and the code changes come first.

Deep Dive: Design Variations and the Panel's Debates

The capstone picks one route: application dual-write behind a flag. There are others, and the panel will want to know why this one.

Debate 1: trigger or application dual-write?

The trigger's case is strong in this exact capstone. The Stage 3 surprise was "an old code path that writes orders without the dual-write flag." A trigger would have covered it from the first second. The application's case is control: the flag can turn dual-write off in 30 seconds if it causes latency, and the logic sits in reviewed, tested code.

A good compromise uses both, briefly. The application dual-writes behind the flag. A trigger fills total_cents only when it arrives NULL, and increments a counter every time it fires. The counter is the inventory of unknown writers. When it has read zero for a week, drop the trigger. You get the trigger's coverage and the application's control, and the trigger becomes a detector rather than a hidden piece of business logic.

Debate 2: INTEGER or BIGINT?

Finance asked for INTEGER. The capstone uses BIGINT. A 32-bit signed integer tops out at 2,147,483,647 cents, which is $21.4 million. No single bookstore order gets near that, so INTEGER is safe for one order's total.

The trouble is everywhere else the value goes. Sums of totals in reports, in a CQRS projection, in a downstream language with 32-bit ints, can overflow quietly. Postgres' own SUM over an integer column returns a bigint, but not every consumer is Postgres. BIGINT costs 4 more bytes per row, about 800 MB on 200 million rows before alignment, which often absorbs some of it. Most panels take the 800 MB to never have this conversation again. Whatever you choose, write it in the consumer contract.

Debate 3: what does "verified" mean?

The comparison job proves that total_cents equals round(total × 100). It does not prove that either is right. The audit that started all this found total drifting from the payment provider. A stronger verification adds a third check: for each order with a provider record, compare total_cents with the provider's captured amount. Mismatches there are not migration bugs. They are the original data defect, and finance has to decide which side to trust for each class of difference.

The panel point: separate "the migration preserved the data" from "the data is correct." The migration can be signed off on the first. The second is a data-repair project that the migration makes possible, because integer cents can finally be compared exactly.

Evolution path: when the new form lives somewhere else

This capstone is the easy case: same row, same database, atomic dual-write. The same five stages scale up, but each gets harder.

  • New table, same database. Dual-write is still atomic if both writes share a transaction. The backfill becomes INSERT ... SELECT in batches. Shadow reads now cost a second lookup.
  • New database or new service. Dual-write is no longer atomic. Use an outbox or CDC so the new side is fed from the old side's committed changes, and accept that the new side lags. Shadow reads must allow for that lag, as the capstone's multi-region extension anticipates. Ramp reads only for data older than the measured lag, or read-your-writes from the old side.
  • Event formats. The capstone's "queue-format" extension maps cleanly: publish both formats (dual-write), compare consumers' results on both (shadow read), move consumers one at a time behind flags (switch reads), stop publishing the old format after every consumer is confirmed (contract). The schema registry's compatibility rules enforce the expand step.

In every version, the undo column from the capstone's debrief is the design tool. Write it before you write code. If a stage has no undo button, either redesign it or move it to the end and put gates in front of it.

Deep Dive: Design-Review Checklist

  1. Does every DDL statement run with a lock_timeout and retry, and are long-running queries kept off the primary during it?
  2. What is the written rounding rule, and do the backfill and the dual-write implement it identically? Who in finance signed it?
  3. Does the backfill compute new values inside the UPDATE statement, use keyset batches, checkpoint its progress, and skip rows already written?
  4. What sets the backfill rate: replica lag, CDC consumer lag, WAL disk and archive throughput? Is the throttle adaptive and paused at peak?
  5. How will you find every writer that bypasses the dual-write flag: a counting trigger, pg_stat_statements, a NOT VALID constraint?
  6. Does the comparison job re-check mismatches on the primary before counting them, and what count, for how long, gates Stage 4?
  7. Which business metrics gate each step of the read ramp, and does the group have enough orders at each step to see a one-cent change in disputes?
  8. Is there a complete list of the twelve consumers, plus a query-log check for unlisted ones, with an owner confirming each migration?
  9. What exactly gates the one-way door at Stage 5a, and what does the runbook say to do for a bug found after it?
  10. Before the drop: is the column ignored in every ORM, are SELECT * queries gone, and is the snapshot's retention documented?
  11. Who deletes both migration flags, the trigger if any, and the dead code paths, and when?

Deep Dive: Senior Interview Follow-ups

"Adding a nullable column is instant in Postgres. Why can it still cause an outage?"

Because it still needs a brief ACCESS EXCLUSIVE lock. If any long transaction holds a lock on the table, the ALTER waits, and every new query queues behind the ALTER. At 400 writes a second, the pools fill in seconds. Set a short lock_timeout so the ALTER gives up and retries instead of blocking everyone, and keep long queries off the primary.

"Your backfill reads rows in Python, computes cents and writes them back. What's wrong?"

A lost update. Between the read and the write, the application can change the order's total and dual-write new cents. The backfill then overwrites them with cents from the old total. Compute the value inside the UPDATE from the row's own column, so the database's row locking and re-check on concurrent update keep it consistent, and guard with total_cents IS NULL.

"Why can the backfill not just run as fast as the database allows?"

Every backfilled row is a real update. It goes to the WAL, to every replica and to every CDC consumer. A rate the primary handles easily can put replicas minutes behind and leave a projection days behind, which users see as stale pages. The safe rate is set by the slowest downstream's headroom, so the throttle should watch replica and consumer lag, not just primary CPU.

"Stage 4's rollback is a flag flip. Why is that safe here when the blue-green lesson's rollback broke things?"

Because dual-write is still on. The old column receives every write in its old form, so the old read path finds current, correctly shaped data. In the blue-green failure, the new version had written data the old version could not read. The safety comes from the order of stages: reads move only while writes still go to both shapes.

"The comparison job reports thousands of one-cent mismatches. Is the migration broken?"

Probably not; it is probably working. One-cent differences clustered on values with three decimals point at two writers using different rounding or tie rules, such as SQL versus Python. Nothing user-facing changed, because reads still use the old column. Agree one rule, fix the writer that differs, re-backfill those rows. This is exactly what Stage 3 exists to catch.

"Would you use a trigger instead of application dual-write?"

I would use both, briefly. The application dual-write gives a flag and reviewed code. A trigger that only fills NULLs, and counts how often it fires, catches writers that bypass the application and tells you how many there are. When the counter stays at zero for a week, drop the trigger. Pure trigger dual-write works too, but its logic is harder to see and harder to switch off fast.

"What changes if total_cents lives in a new payments service instead of the same table?"

Dual-write stops being atomic, because two systems cannot commit together cheaply. Feed the new service from the old database's committed changes through an outbox or CDC. The new side is then eventually consistent, so the comparison job and shadow reads must allow for its lag, and the read ramp must handle read-your-writes. The stages stay the same; each one needs a lag budget.

"After old writes stop, a missed consumer turns up. Why not just turn dual-write back on?"

Because it only fixes rows written from now on. Every row changed since the flip has a stale old column, and turning dual-write back on would leave a mix of fresh and stale values with nothing to tell them apart. The honest options are roll forward (migrate the consumer and re-run its output) or a reverse backfill of the old column, which is a project. That is why the gate before the flip demands a confirmed consumer list.
