Deep Dive: Inside the Mechanism

The lesson puts the hard work in the two tiers above the socket. That is the right priority, but many production incidents start below it, in the handshake, the frames and the buffers.

The WebSocket handshake

A WebSocket (RFC 6455) begins life as an ordinary HTTP/1.1 GET. The client sends Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Version: 13 and a Sec-WebSocket-Key, which is 16 random bytes in base64. The server answers 101 Switching Protocols. Its Sec-WebSocket-Accept header is the base64 SHA-1 of the client's key joined to a fixed GUID from the RFC.

import base64, hashlib
GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"
def accept(key: str) -> str:
    return base64.b64encode(hashlib.sha1((key + GUID).encode()).digest()).decode()
# accept("dGhlIHNhbXBsZSBub25jZQ==") == "s3pPLMBiTxaQ9kYGzzhZRbK+xOo="  (RFC 6455 example)

That accept value is not security. It only proves the server understood the upgrade. Real security happens in the same request, before the 101. Check the Origin header, because browsers send cookies on WebSocket upgrades and a missing check is a cross-site hijack. Authenticate with a short-lived token rather than a long-lived cookie alone. Pick a subprotocol with Sec-WebSocket-Protocol and put your schema version in it (chat.v3), so old clients fail at the handshake instead of mid-conversation.

After the 101, the HTTP layer is gone: your load balancer logs one "request" that lasted four hours.

Frames on the wire

Every WebSocket message travels as one or more frames. The header is small: 2 bytes for payloads up to 125 bytes, 4 bytes up to 64 KB, 10 bytes beyond that, plus a 4-byte masking key on every client-to-server frame.

Four details here cause real bugs.

  • Masking stops a malicious page from making socket bytes look like cacheable HTTP to a naive proxy. Servers must reject unmasked client frames.
  • Fragmentation lets one message span many frames, and control frames may arrive between the fragments. This is how a ping can still get through during a 50 MB upload. Your parser must reassemble, and it must enforce a maximum message size while doing so. Otherwise one client can stream a "single message" until the gateway runs out of memory. Close code 1009 (message too big) exists for this.
  • Close is a handshake, not a hang-up. Each side sends a close frame with a code, then the TCP connection ends. Code 1000 is normal, 1001 is going away, 1011 is internal error, and 1012 (service restart) and 1013 (try again later) are what a draining gateway should send. Code 1006 never appears on the wire. A client library reports it when the TCP connection died without a close frame, so a spike in 1006 means networks or crashes, not your drain logic.
  • Compression (permessage-deflate, RFC 7692) can halve chat traffic. With context takeover, each connection keeps a zlib dictionary in both directions, often tens to hundreds of KB per socket depending on window and memory settings. At 50,000 sockets that can exceed everything else in the memory budget below. Either negotiate server_no_context_takeover and smaller window bits, or skip compression for small messages.

Browsers add one more constraint. JavaScript cannot send a protocol-level ping. The browser answers server pings automatically, but the page has no API to send its own. So the client side of dead-connection detection must be an application message, like {"t":"hb"}.

gRPC bidi streams and HTTP/2 flow control

A gRPC bidirectional call is one HTTP/2 stream. Each message is a 5-byte prefix (a compressed flag and a 4-byte length) followed by protobuf bytes, carried in DATA frames. Many calls share one TCP connection, up to the peer's SETTINGS_MAX_CONCURRENT_STREAMS. Many servers set this around 100, but defaults vary by implementation.

The part that matters for backpressure is HTTP/2's credit-based flow control. Each stream has a receive window, and so does the whole connection. Both start at 65,535 bytes. A sender may only send DATA up to the window. The receiver hands credit back with WINDOW_UPDATE frames as it consumes data. Stream credit typically returns when the application reads the message. Connection credit typically returns sooner, when bytes leave the socket into the stream's buffer, so one stalled stream does not freeze its neighbours.

The effect is backpressure you get for free. If the receiver's application stops reading, its stream window drains to zero, and the sender's Send() blocks (in grpc-go) or its isReady() goes false (in grpc-java). Contrast this with WebSocket. A WebSocket has no flow control of its own, only TCP's. The gateway's write succeeds into a user-space buffer, and that buffer grows until you cap it.

A 64 KB window is also a throughput ceiling. Throughput per stream is roughly window ÷ round-trip time. At 64 KB and 100 ms RTT, a stream tops out near 640 KB/s, however fat the link. Most gRPC implementations grow windows automatically by probing the bandwidth-delay product. If yours does not, raise the initial window for cross-region streams.

Heartbeats and dead-connection detection

TCP will not tell you a peer has vanished. If a phone enters a tunnel, no FIN or RST ever arrives. The server's socket stays "established" until it tries to send and the retransmissions give up, which takes many minutes with Linux defaults. If the server never sends, it waits forever. Linux TCP keepalive does not save you either: the default first probe comes after 7,200 seconds of idle.

So you run heartbeats at the application layer, and you size them against three numbers:

  • The shortest idle timeout on the path. Load balancers and proxies close idle connections, commonly at 60 seconds (the AWS ALB default and nginx's default proxy_read_timeout). Mobile carrier NATs can be shorter. The heartbeat interval must sit below the smallest of these, or the path kills healthy connections.
  • Detection time. With interval i and declare-dead after k missed beats, detection takes up to k × i. At 25 s and 2 misses, a dead socket is noticed within about 50 s.
  • Cost. A heartbeat is tiny, but 1 million sockets at 25 s is 40,000 frames per second per direction across the fleet. Cheap for gateways, but on phones it costs battery, which is why mobile apps often close the socket in the background and rely on OS push.

gRPC has the same machinery as HTTP/2 PING frames, configured with keepalive time and timeout. The server side has an enforcement policy. In grpc-go, a client that pings more often than the server's minimum (5 minutes by default) receives GOAWAY with ENHANCE_YOUR_CALM, and the connection closes. Teams hit this when they set aggressive client keepalives without changing the server. Set both ends together.

One more knob is worth knowing. TCP_USER_TIMEOUT caps how long unacknowledged sent data may sit before the kernel kills the connection. It turns "many minutes of retransmission" into a number you choose.

Sticky routing and draining on deploy

Stickiness for a socket is not a cookie. Once upgraded, the TCP connection simply stays on its gateway, so the real routing decision happens once per connect. Least-connections is the usual choice. Round-robin looks fine until a deploy: the new gateway joins with zero sockets, every other gateway is full, and round-robin only gives it its share of new arrivals, so imbalance lasts for hours.

A clean drain has a sequence:

  1. Fail the readiness check, so the load balancer stops sending new connections.
  2. Send each client an application "reconnect" message, or a close with 1012, spread across a drain window with random delay per client.
  3. Clients reconnect elsewhere and resume from their last sequence number.
  4. After the window, close what is left and exit.

For gRPC, the equivalent is GOAWAY: the server tells the client to finish in-flight streams and open new ones on a fresh connection. A related setting, max_connection_age, makes servers send GOAWAY periodically. Use it behind L4 load balancers. Without it, long-lived HTTP/2 connections never rebalance after you scale out.

Presence and session state

Presence looks like a boolean and behaves like a write-heavy distributed counter. A user can have three devices, so "online" means "at least one live connection." The usual shape is a key per user in a shared store (often Redis). The key holds the set of connection IDs, each with an expiry refreshed by heartbeats. A connection that dies silently simply ages out. You never depend on a disconnect event arriving.

The expensive part is fan-out. If each user has 200 contacts and every change is pushed to all of them, one phone flapping in a tunnel produces 400 messages a minute. Two habits keep this bounded:

  • Subscribe to presence lazily. A client only tracks users currently on screen, like the open conversation or the visible part of the member list.
  • Debounce offline transitions. Mark "away" only after a grace period, say 30 to 60 s, so a reconnect is invisible.

Session state is what resume needs: user ID, rooms, and last sequence per room. The client holds the authoritative "last sequence I saw," so a crashed gateway loses nothing anyone needs.

The backplane, concretely

Redis Pub/Sub and core NATS are fire-and-forget: a message reaches whoever is subscribed at that instant and is never stored. That is fine here, because history lives elsewhere. In a Redis Cluster, classic PUBLISH goes to every node. Redis 7's sharded pub/sub (SPUBLISH/SSUBSCRIBE) keeps a channel on its own shard. Kafka is a poor per-room router, because consumers read whole partitions, so it belongs behind the backplane, feeding history.

Whatever you pick, each gateway keeps a reference count per room. It subscribes when its first local member joins and unsubscribes when its last one leaves. A count that drifts too high wastes traffic. One that drifts too low makes members silently stop receiving.

Deep Dive: Sizing and the Numbers

Per-connection memory

The lesson's 50,000 sockets per gateway is a planning number. Here is where it comes from. The figures below are assumptions for an async gateway with TLS terminated in-process. Measure your own stack, because every runtime differs.

ComponentIdle socket (assumed)Notes
Kernel TCP state and buffers~4-10 KBLinux grows buffers on demand. A busy socket can take hundreds of KB (tcp_wmem max is 4 MB by default).
TLS session state~20-40 KBMostly record buffers. Libraries that release buffers on idle (OpenSSL's SSL_MODE_RELEASE_BUFFERS) cut this.
Read and write buffers in the app~8 KBCommon library defaults are 4 KB each.
Connection object, subscriptions, session~2-5 KBGrows with rooms per user.
Goroutine or task stacks~4-16 KBGo starts stacks at 2 KB, and they grow. Two goroutines per socket is typical.
Outbound queue (average)~1-2 KBNear zero for healthy clients.
Total~40-80 KBWithout per-message compression context.

At 60 KB average, 50,000 sockets use 3 GB. That fits comfortably on a 16 GB machine, which leaves room for the part that actually kills gateways: the tail. Suppose the per-connection outbound cap is 1 MB and a backplane hiccup makes 5% of clients fall behind at once. That is 2,500 × 1 MB = 2.5 GB, nearly doubling the footprint in seconds. Add permessage-deflate with full context at 200 KB per socket and the baseline alone becomes 13 GB.

So you need two caps. One is per connection (1 MB, or less). The other is a gateway-wide outbound budget, like 4 GB. When the gateway crosses it, it starts shedding the slowest connections with a resync hint before the garbage collector or the OOM killer decides for you.

File descriptors are the other hard limit. 50,000 sockets need ulimit -n well above 50,000, plus headroom for backplane and store connections. There is also a subtle port limit when an L7 proxy sits in front of the gateways. Each proxy-to-gateway connection uses one source port, and one source IP talking to one destination IP and port gets roughly 28,000 to 64,000 ports depending on the ephemeral range. A single proxy IP cannot carry 100,000 sockets to one gateway port. Add source IPs or gateway listeners.

Fan-out through the backplane

Assume 1 million connected users on 20 gateways, 50,000 each. Users send on average one durable message per minute, about 16,700 messages per second fleet-wide. Average room size is 8 members.

  • Publishes into the backplane: 16,700/s. Each one is also a history write, so the history store must take 16,700 writes/s plus resume reads.
  • Deliveries out of the backplane: one per gateway that holds at least one member. Eight members spread over 20 gateways usually touch 6 to 8 gateways, so about 7 × 16,700 ≈ 117,000 backplane deliveries/s.
  • Socket writes: 8 × 16,700 ≈ 134,000/s fleet-wide, or 6,700/s per gateway. Easy.

Now add one 100,000-member all-hands room that gets 10 messages per second during a launch. Every gateway is subscribed. That is 20 backplane deliveries per message, which is nothing. But each gateway then writes about 5,000 sockets per message, or 50,000 writes/s each, on top of normal load. The pressure moves from the backplane to gateway CPU and outbound buffers. Large rooms often get special handling: slower typing indicators, no read receipts, and several messages batched into one frame.

Reconnect storms and drain math

A gateway with 50,000 sockets drained over 5 minutes produces about 170 reconnects per second: a TLS handshake, a token check, a presence write and a history query per room, each. Spread over 19 gateways, that is under 10 per second each. Trivial.

Now the bad version. A gateway crashes, and its 50,000 clients all retry within one second. That is 50,000 handshakes and perhaps 250,000 history queries (5 rooms each) in one second, mostly aimed at the history store. Jitter over 30 s brings that to about 8,300 history queries per second.

State the rolling deploy's duration too. Twenty gateways, one at a time, at 5 minutes of drain plus a minute to start, take two hours. Four at a time takes 30 minutes but removes 20% of capacity while it runs.

Deep Dive: Failure Modes in Production

1. The thundering reconnect

Symptom. One gateway dies, then two more fall over within a minute. The history database's CPU hits 100%.

Mechanism. Clients reconnect with fixed or no backoff. The surviving gateways take the handshake load, and every client fires its resume queries at the same moment. Slow resumes time out, clients retry, and the load compounds.

Detect. Watch the connection-accept rate per gateway, TLS handshakes per second, and resume-query latency. A spike in close code 1006 shows the original crash.

Fix. Use full jitter on the first retry, not only later ones. Add a server-sent "retry after" hint during overload, and admission control on the accept path. Cap resume to "last N messages per room, then refetch," so a long gap is one bounded query.

2. Disconnects at exactly 60 seconds

Symptom. Quiet users drop and reconnect once a minute, while busy rooms are fine.

Mechanism. A proxy or load balancer on the path has a 60-second idle timeout, and the heartbeat interval is longer, or heartbeats are sent only from one side.

Detect. Plot a histogram of connection lifetimes. A sharp spike at one value is always a timeout somewhere.

Fix. Set the heartbeat well under the smallest idle timeout on the path, and raise the proxy timeouts deliberately (for nginx, proxy_read_timeout and proxy_send_timeout on the WebSocket location).

3. Ghost presence and half-open sockets

Symptom. Users appear online for minutes after closing a laptop lid. Messages "delivered" to them never arrive.

Mechanism. The connection is half-open. The server's socket is still established, and writes succeed into kernel buffers, so the gateway believes the client is there.

Detect. Compare heartbeat-age distributions with the set of connections marked live. Rising socket send-queue bytes (ss -tn shows Send-Q) on idle connections is the signature.

Fix. Use application heartbeats with a hard deadline, presence keys with a TTL, and TCP_USER_TIMEOUT. Remember that a successful socket write never means "delivered." Client acks do.

4. The slow consumer that becomes a GC outage

Symptom. Gateway latency climbs for everyone. Then the process is OOM-killed, taking 50,000 users with it.

Mechanism. A few slow clients in a hot room accumulate megabytes of queued frames each. Heap growth makes garbage-collection pauses longer. Longer pauses slow every socket, which makes more clients fall behind.

Detect. Track the per-connection outbound queue as a histogram (p99 and max, not the mean), gateway heap, and GC pause time.

Fix. Use the per-connection and gateway-wide caps from the sizing section. Coalesce ephemeral messages before they enter the queue, not after.

5. The backplane silently drops a gateway

Symptom. Every user on one gateway stops receiving room messages. Sending still works, and nothing logs an error at the application level.

Mechanism. With Redis Pub/Sub, a subscriber that reads too slowly hits client-output-buffer-limit pubsub (default 32 MB hard, or 8 MB sustained for 60 s). Redis disconnects it. If the gateway's client reconnects but does not resubscribe to every room, those rooms go dark for its users.

Detect. Watch Redis's client-disconnect logs, and compare the subscribed-channel count per gateway with its local room count. A synthetic canary that publishes to a test room every few seconds and checks delivery on every gateway catches it directly.

Fix. Resubscribe the full room set on every backplane reconnect. Then trigger a client resync for affected rooms, since messages in the gap were lost. Give the gateway's backplane reader its own thread or task, so socket writes cannot stall it.

6. Gaps and reordering on resume

Symptom. After reconnect, a client occasionally misses one message or shows two in the wrong order.

Mechanism. There are two common races. First, the gateway publishes to the backplane before the history write commits, and a resuming client queries history in between. Second, sequence numbers are assigned by each gateway instead of one authority per room, so two senders produce the same number or an order that conflicts with history.

Detect. Have clients report gaps they cannot fill (a sequence jump after resume) as a metric. It should be zero.

Fix. Assign sequence numbers in one place per room, such as an atomic counter or the history store's insert. Write history first, then publish. During resume, subscribe to the live stream first, buffer it, fetch history up to the first buffered sequence, then drain the buffer. That ordering closes the window.

7. gRPC streams that never rebalance

Symptom. After scaling a backend from 4 to 8 replicas, the 4 new replicas sit nearly idle for days.

Mechanism. An L4 load balancer balances connections, and HTTP/2 puts every stream on the same long-lived connection. A related failure is GOAWAY ENHANCE_YOUR_CALM from mismatched keepalive settings, which drops streams in bursts.

Detect. Compare active streams and requests per replica, and count GOAWAY reasons in client logs.

Fix. Set max_connection_age (with a grace period) on servers, use client-side or L7 balancing that understands streams, and align keepalive policy across both ends.

Two choices deserve a stronger opinion.

Do not make the backplane durable just because durability sounds safer. If history is written before publish, the backplane can lose messages and resume still repairs every gap. A durable bus adds latency and cost for nothing, unless it is also your history pipeline.

Per-message acks are a protocol you will maintain forever: ack IDs, redelivery timers, an outstanding window per client. Sequence-based resume gets at-least-once with far less machinery. Use acks when the sender must act on non-receipt.

Deep Dive: Design-Review Checklist

  1. Does the client actually send often enough to justify a socket? What fraction of traffic is client-to-server?
  2. Where is the single source of truth for messages, and is it written before the backplane publish?
  3. Who assigns sequence numbers, and is it one authority per room?
  4. What are the heartbeat interval and dead threshold, and how do they compare with every idle timeout on the path (load balancer, proxy, carrier NAT)?
  5. What is the per-connection outbound cap, the gateway-wide cap, and the shedding order when the gateway-wide cap is hit?
  6. What is the per-connection memory budget, measured, including TLS and any compression context?
  7. How are reconnects jittered, and what happens to the history store when a full gateway's clients reconnect at once?
  8. What does a drain look like, step by step, and how long does a full rolling deploy take?
  9. How does a gateway recover its backplane subscriptions after a backplane disconnect, and how do you detect a gateway that silently stopped receiving?
  10. How are authentication and authorization rechecked during a session that lasts hours? What happens when a user is removed from a room or banned?
  11. What is the largest room you support, and has it been load-tested separately from total message volume?
  12. How is the protocol versioned, and how do old clients fail?

Deep Dive: Senior Interview Follow-ups

Why can't you rely on TCP to tell you a client has gone away?

A vanished peer sends nothing, so there is no FIN or RST to observe. The server only learns when it sends and retransmissions run out, which takes many minutes by default. If it never sends, it never learns. Linux keepalive starts probing after two hours by default. So you need application heartbeats with a deadline on both sides, and optionally TCP_USER_TIMEOUT to bound how long unacknowledged data can sit.

gRPC has flow control and WebSocket does not. What does that change in your gateway design?

With gRPC, a slow receiver drains its stream window, and the sender's Send blocks or its readiness flips. Backpressure reaches the producer automatically, and you decide whether to block, buffer or drop. With WebSocket, a write succeeds into your own buffer until TCP's send buffer fills, so slow clients turn into growing memory. You must build the cap, the coalescing and the disconnect-with-resync yourself.

Your gateway holds 50,000 sockets at 60 KB each. Why is that not the number you size the machine for?

Because the average hides the tail. A burst that makes a few percent of clients fall behind fills their outbound queues to the cap. At a 1 MB cap, 5% of 50,000 is 2.5 GB in seconds. Compression context can multiply the baseline. Size for baseline plus a gateway-wide outbound budget, and enforce that budget by shedding the slowest clients first.

A client reconnects and resumes from history. How do you guarantee no gap and no duplicate?

Sequence numbers come from one authority per room. History is committed before publish. On reconnect, the client subscribes to the live stream first and buffers it. It fetches history after its last sequence, up to the first buffered sequence, then drains the buffer and drops anything at or below the highest sequence it has applied. Subscribe-then-fetch closes the race that fetch-then-subscribe leaves open.

Why might Redis Pub/Sub be a better backplane than Kafka here, even though Kafka is durable?

The backplane only routes. Durability already lives in the history store, and resume repairs any gap. Redis or NATS give per-room channels that are cheap to create and destroy, and the latency is low. Kafka topics are heavyweight, and consumers read whole partitions, so per-room routing turns into "every gateway reads everything" or a room-assignment scheme. Kafka shines behind the backplane, feeding history, search and analytics.

How do you deploy 20 gateways without a reconnect storm or a two-hour rollout?

Fail readiness, then spread reconnect notices over a drain window with random delay per client. Each client resumes from its sequence. Drain several gateways at once, sized to the spare capacity you keep: with 25% headroom you can drain four of 20 at a time. Watch accept rate and resume latency as the gate for the next batch. Graceful drain is planned work. A crash is the case your jitter and admission control must survive.
