Deep Dive: Inside the Mechanism

The lesson gives you the shape: proxies with caches in 200 cities, fingerprinted assets, short-TTL HTML, a shield. This section opens one edge and follows a request through it. A CDN decision in a design review almost always comes down to one of four things: how the user reaches an edge, what the cache key is, what the cache does when an entry is stale or missing, and how you remove something on purpose.

Step 1: reaching an edge, by DNS or by anycast

There are two ways to send Sydney to the Sydney edge, and they fail differently.

  • DNS steering. The CDN's authoritative DNS answers shop.example.com with an address chosen for the asker. The catch is that the asker is the user's DNS resolver, not the user. A Sydney user on a public resolver whose nearest instance is in Singapore can be sent to Singapore. The EDNS Client Subnet extension lets resolvers pass part of the user's address along, but not every resolver sends it. DNS answers are also cached for their TTL, so moving traffic away from a sick edge takes as long as the TTL, and some resolvers hold answers longer than they should.
  • Anycast. Every edge announces the same IP prefix over BGP, and the internet's routing picks the nearest one, measured in network hops and policy rather than kilometres. Failover is fast: withdraw the route and traffic moves within seconds to minutes. The catch is that "nearest by BGP" is not always nearest by latency. A routing change in the middle of a long TCP connection can also send its packets to a different edge, which does not know the connection and resets it. Providers mitigate this, and it is rare, but it is why anycast is easiest for short HTTP requests.

Many large CDNs use anycast for the front door and DNS for finer steering. For a reviewer the question is simple: if one edge goes bad, how long until users stop going there, and who decides?

Step 2: the cache key and the Vary header

The edge turns the request into a cache key. By default that is roughly scheme, host, path and query string. Everything about hit ratio and most of CDN security lives in this one value.

  • Query strings. /cover.jpg?utm_source=newsletter and /cover.jpg are different keys unless you tell the CDN to ignore or sort parameters. A marketing campaign that adds tracking parameters can halve your hit ratio overnight. Most CDNs let you include only an allowlist of parameters in the key.
  • Vary. The origin's Vary response header names request headers that change the response, and caches add their values to the key. Vary: Accept-Encoding is normal: you store a gzip copy and a Brotli copy. Vary: User-Agent is a disaster, because there are thousands of distinct user-agent strings, so every copy is shared by almost nobody. Vary: Cookie makes the response effectively per-user. Normalise first: collapse Accept-Encoding to two or three values, map user agents to "mobile" or "desktop" in edge logic, then vary on the normalised header.
  • Unkeyed inputs. This is the subtle one. If the origin uses a request header that is not in the key to build the response (say it writes X-Forwarded-Host into an absolute URL), an attacker can send one request with a poisoned header. The edge caches the poisoned response under the normal key and serves it to everyone. Anything the origin reads must be in the key, or the origin must ignore it.

Step 3: freshness, revalidation and the stale extensions

Once the edge has a key, it looks for a stored response. HTTP caching (RFC 9111) gives every stored response an age and a freshness lifetime. For a shared cache, the lifetime comes from s-maxage if present, else max-age, else Expires. Three outcomes follow.

  1. Fresh hit. Age is below the lifetime. Serve it. The response carries an Age header, which is your best debugging clue for "how old is this copy?".
  2. Stale hit. Age has passed the lifetime. The cache should revalidate: send the origin a conditional request with If-None-Match (the stored ETag) or If-Modified-Since. If nothing changed, the origin replies 304 Not Modified with no body, and the edge resets the entry's age. A 304 costs a round trip but almost no bandwidth or origin work, if the origin computes ETags cheaply.
  3. Miss. Nothing stored, or it was evicted. Fetch from upstream.

The RFC 5861 extensions change what happens in the stale case. stale-while-revalidate=300 lets the edge serve the stale copy at once and revalidate in the background, so no user waits for the origin. stale-if-error=86400 lets the edge serve the stale copy when the origin returns 5xx or cannot be reached. Support varies by provider, and some expose these as their own settings rather than honouring the header, so check before you rely on them.

Watch out for heuristic freshness. If a response has no explicit lifetime but does have a Last-Modified header, HTTP lets a cache pick its own lifetime, commonly 10% of the time since last modification. An image last modified a year ago could then be cached for about 36 days without anyone asking for that. Always send an explicit Cache-Control, even if it is no-cache.

Two newer headers help separate the layers. Surrogate-Control (supported by several CDNs) and CDN-Cache-Control (RFC 9213) give the CDN its own policy, which is stripped before the response reaches the browser. That lets you cache HTML at the edge for 5 minutes and purge it on change, while browsers keep it for 0 seconds.

Step 4: request collapsing and the tiers

When 10,000 Sydney users request a cold hero image in the same second, the edge should not send 10,000 fetches. It sends one, parks the other requests on that fetch, and answers them all when it returns. Varnish calls this the waiting list. Fastly, Cloudflare and CloudFront each have their own form of it, usually called request collapsing or coalescing. It only works for responses the edge believes are cacheable. If the response comes back private or with a Set-Cookie, the parked requests must each go to the origin in turn, and you get a serialised stampede. Varnish's "hit-for-pass" (or hit-for-miss) object exists to remember "this URL is not cacheable, don't wait for it next time".

The shield is the same idea one level up. Each edge's misses go to one designated mid-tier location instead of the origin. Some providers build deeper hierarchies (regional tiers, then a shield), but the effect is the same: the origin sees roughly one fetch per object per freshness period, not one per edge.

Step 5: what "cache forever" really means

An edge is a finite cache, typically RAM for the hottest objects and SSD for the rest, with an LRU-like eviction policy. max-age=31536000, immutable means "you may keep this for a year". It does not mean the edge will. A rarely requested product image in a small city edge may be evicted within hours. That is the long-tail problem: hit ratio is excellent for the top 1% of objects and much worse for the bottom 80%, and tiers exist mostly to give the long tail a second chance before the origin.

This is also why the lesson's deploy drill keeps old assets on the origin after a deploy. A user with a cached old HTML page can still ask for app.3f9a2c.js, and if the edge has evicted it and the origin deleted it, that user gets a 404 and a broken page.

Step 6: purge, soft purge and surrogate keys

A purge is a message fanned out to every edge: "drop this key". Speed and semantics vary by provider, from well under a second to minutes, so treat the published figure as a target rather than a guarantee.

  • URL purge drops one key. It misses variants: the gzip and Brotli copies, the mobile variant, the URL with a tracking parameter that was cached separately.
  • Tag purge (Fastly's Surrogate-Key, Cloudflare's Cache-Tag on some plans, and similar features elsewhere) lets the origin label responses, for example Surrogate-Key: product-4521 author-88. Purging product-4521 drops the product page, its JSON, and every listing page that included it. This is how event-driven invalidation works at the edge: the catalog service emits "product 4521 changed" and a worker purges the tag.
  • Soft purge marks entries stale instead of deleting them. The next request revalidates, and stale-while-revalidate or stale-if-error can still serve the old copy. A hard purge of a popular object sends every edge to the origin at once. A soft purge does not.

Deep Dive: Sizing and the Numbers

Use the bookstore after the Australian launch. Assumptions:

  • 30 million page views a day worldwide, peaking at 3 times the mean.
  • Each page view: 1 HTML document (60 KB), 60 assets averaging 25 KB (1.5 MB), and 5 API calls.
  • About 200,000 distinct cacheable objects (product images in several sizes, JS, CSS, fonts).
  • 300 edge locations, of which the bookstore's traffic touches about 120 often.

Requests and bytes

  • Requests per day: 30M × 66 ≈ 2 billion. Mean rate: about 23,000 per second; peak about 70,000 per second.
  • Bytes per day: 30M × (1.5 MB + 60 KB) ≈ 47 TB. Most of it is assets.

Two hit ratios matter, and they are different numbers. The request hit ratio counts requests served from cache. The byte hit ratio counts bytes. Fingerprinted assets are most of the bytes and cache very well, so byte hit ratio is often higher than request hit ratio. API calls are many requests and few bytes, and mostly uncacheable. Report both. Request hit ratio drives origin CPU; byte hit ratio drives origin bandwidth and egress cost.

Suppose assets hit 97%, HTML hits 80% (60 s s-maxage with SWR), and APIs hit 10% (only public catalog endpoints). Origin requests per second at peak:

  • Assets: 70,000 × (60/66) × 0.03 ≈ 1,900/s
  • HTML: 70,000 × (1/66) × 0.20 ≈ 210/s
  • API: 70,000 × (5/66) × 0.90 ≈ 4,800/s

The origin now sees about 6,900 requests per second instead of 70,000, and 70% of what remains is API traffic. That is the honest picture: after a CDN, your origin capacity plan is almost entirely an API capacity plan. The asset misses are mostly long-tail images, which the shield (next) cuts further.

Why the shield matters: revalidation math

Take one product page HTML with s-maxage=60. Without a shield, each of the 120 busy edges revalidates it once a minute while it is popular. That is 120 conditional requests per minute, or 2 per second, for one URL. Multiply by the 5,000 product pages that are popular at any moment and the origin sees about 10,000 revalidations per second, more than all the other traffic combined.

With a shield, the edges revalidate against the shield and only the shield revalidates against the origin: 5,000 pages × 1/60 s ≈ 83 per second. The shield turns a cost that scales with the number of edges into one that scales with the number of objects. That is the single most important number in this section, and it is why a short TTL on HTML is affordable.

The same arithmetic applies to purges. A hard purge of a hot object across 120 edges is up to 120 origin fetches in the next second without a shield, and one with it.

Latency for uncacheable requests

The lesson says even dynamic requests benefit. Here is how much, for a Sydney user calling a Virginia API:

  • Without a CDN: TCP (1 RTT) + TLS 1.3 (1 RTT) + request (1 RTT) at 200 ms each = 600 ms for the first API call on a new connection.
  • With an edge: TCP + TLS to the edge at 15 ms each = 30 ms. The edge forwards on an already-open, warm connection to the origin: one 200 ms round trip, often a little less, because the provider's backbone can be faster than the public internet. Total about 250 ms.

The gain on repeat calls over an open connection is small, since the ocean round trip is still there. The big win is the handshake, which is why mobile apps that open many short connections benefit most.

Cost

CDN pricing varies widely by provider, region and commitment, so take any rate as an assumption. At an illustrative $0.02 to $0.08 per GB, 47 TB a day is roughly 1,400 TB a month, or about $28,000 to $110,000 a month in delivery fees before discounts. Two things move this number more than the provider choice: image formats and sizes (serving a 400 KB JPEG where a 60 KB WebP would do), and the share of traffic in expensive regions. Per-request fees and fees for purge calls, edge compute and logs also exist on many plans. Origin egress to the CDN still costs money too, which is another reason the shield pays for itself.

Deep Dive: Failure Modes in Production

1. Web cache deception: the account page cached as a stylesheet

Symptom: a security researcher reports that /account/orders/x.css returns another customer's order history. Mechanism: the CDN has a rule "cache anything ending in .css". The origin's router ignores the trailing segment and serves the logged-in user's orders page. An attacker tricks a victim into loading that URL, the edge caches the victim's page under a public key, and the attacker fetches it. Detect: responses cached at the edge that also carry Set-Cookie, private or personal data; scan the edge logs for cache hits on authenticated paths. Fix: let the origin's Cache-Control decide cacheability, rather than file extensions. Make the origin return 404 for paths it does not recognise instead of falling back to a parent route, and send private, no-store on every authenticated response.

2. Cache poisoning through an unkeyed header

Symptom: the homepage loads scripts from a strange host for everyone in one region, for exactly the TTL of the page. Mechanism: the origin builds absolute URLs from X-Forwarded-Host, which the CDN does not include in the cache key. One request with X-Forwarded-Host: evil.example produced a page that pointed at the attacker's scripts, and the edge cached it for everyone. Detect: monitoring that fetches key pages from several regions and checks script origins; alerts on responses whose body references unexpected hosts. Fix: make the origin ignore forwarding headers from anything but the CDN, strip them at the edge, and audit every request header the origin reads against the cache key. Purge the poisoned entries.

3. Hit ratio collapses after a harmless-looking deploy

Symptom: origin traffic triples within an hour of a release; the CDN dashboard shows hit ratio falling from 95% to 30%. Mechanism: the new release added a session or analytics middleware that sets a cookie on every response, including assets. Many CDNs will not cache a response with Set-Cookie, and if collapsing was on, the parked requests now fall through one by one. A similar effect comes from Vary: User-Agent added by a framework, or a new query parameter appended to asset URLs. Detect: alert on hit ratio per content type, not only overall; log the cache status header (cf-cache-status, x-cache or similar) and break down "pass" and "miss" by reason. Fix: strip Set-Cookie from static routes at the origin or edge, normalise Vary, and put a CI check on response headers for a sample of asset and page URLs.

4. A purge takes down the origin

Symptom: someone purges "everything" to fix one wrong image, and the origin falls over for ten minutes. Mechanism: a hard purge empties every edge at once. The next requests for every popular object miss together. With no shield, or a shield that was also purged, the origin receives a share of global peak traffic it was never sized for. Detect: origin request rate jumping right after a purge API call; keep purge calls in an audit log with who and what. Fix: prefer tag purges and soft purges; restrict "purge all" to a break-glass role; size the shield to absorb a cold start; keep stale-if-error on so the edge can serve stale copies while the origin recovers.

5. Broken pages for a few minutes after every deploy

Symptom: right after each release, some users see an unstyled page or a JavaScript error, then it fixes itself. Mechanism: a deploy-order race. New HTML referencing app.8c1d4e.js went live before the asset was uploaded to the origin. An edge requested the asset, got a 404, and some CDNs cache that 404 for a while (negative caching). The opposite race exists too: old assets deleted while cached HTML still points at them. Detect: 404 rate on fingerprinted asset paths, broken out by deploy time. Fix: upload assets first, then switch the HTML; keep old assets for at least the longest HTML lifetime plus a margin (a week is common); set a short or zero TTL on 404s for asset paths.

6. Attackers skip the CDN and hit the origin directly

Symptom: the CDN shows nothing unusual, but the origin is overloaded with requests from many IP addresses. Mechanism: the origin's address leaked: an old DNS record, a mail server on the same host, a certificate transparency log, or a historical DNS database. The CDN's DDoS protection only protects traffic that goes through the CDN. Detect: origin traffic that does not come from the CDN's published address ranges, or lacks the shared secret header. Fix: lock the origin firewall to the CDN's ranges, and also require proof that the request came through your account. Authenticated origin pulls (mutual TLS from the CDN) or a secret header checked by the origin are the usual options, because CDN address ranges are shared by all its customers.

7. An error is cached and served for an hour

Symptom: the origin had a 30-second blip, but users in some regions see an error page for an hour. Mechanism: the origin returned a 500 or a 200 error page with the normal Cache-Control: s-maxage=3600, because the header was set by middleware that ran regardless of status. The edge cached the failure. Detect: cache hits on 5xx responses; synthetic checks from several regions. Fix: send no-store on error responses at the origin, configure the CDN not to cache 5xx (or only for a few seconds, to protect the origin from a stampede), and use stale-if-error so the edge serves the last good copy instead.

The most consequential choice is HTML. Short TTL plus SWR is simple and fails safe: the worst case is one minute of staleness. Long TTL plus tag purge gives better hit ratios and instant updates, but it depends on every change reliably producing a purge. A lost purge event means stale content that never fixes itself. If you choose it, add a ceiling TTL (an hour, say) as a safety net, so a missed purge is a bounded bug.

The second is personalisation. A page that is 95% shared and 5% personal (a cart count, a greeting) should not be uncacheable. Serve the shared page from cache and fetch the personal fragment with a small client-side API call, or assemble it at the edge. Making the whole page private because of a cart badge gives up most of the CDN's value.

Deep Dive: Design-Review Checklist

  1. What is the cache key for each route class (assets, HTML, public API)? Which query parameters and headers are in it, and which are stripped?
  2. Does every response carry an explicit Cache-Control, including errors, redirects and 404s? Is anything relying on heuristic freshness?
  3. What is the default for authenticated routes, and what stops a framework or middleware change from making them cacheable?
  4. Which request headers does the origin read to build a response, and is each one either in the cache key or ignored?
  5. Can a URL with an unexpected suffix on an authenticated path be cached (web cache deception)?
  6. Is there a shield or tiered cache, and what is the origin's request rate on a fully cold cache?
  7. In what order are assets and HTML deployed, and how long are old assets kept on the origin?
  8. How do you purge: by URL, by tag, soft or hard? Who may purge everything, and is it logged?
  9. Are stale-while-revalidate and stale-if-error configured and actually honoured by this provider?
  10. Is the origin reachable only through the CDN, with proof beyond source IP ranges?
  11. Are hit ratio (request and byte) and cache status reasons monitored per content type, with alerts on sudden drops?
  12. What happens if the CDN provider has a global outage: is there a DNS fallback, a second provider, or an accepted risk?

Deep Dive: Senior Interview Follow-ups

"Your HTML has s-maxage=60 and you have 300 edges. How many requests per minute does the origin get for one popular page?"

Without a shield, up to one revalidation per edge per minute, so up to 300, and that scales with edge count, not with traffic. With a shield, one per minute. Revalidations can be cheap 304s if the origin computes ETags without rendering the page. This is why short HTML TTLs need tiering: otherwise the origin load is proportional to the size of the CDN.

"You set max-age=31536000, immutable on assets. Why does the origin still see asset requests?"

Because "may keep for a year" is not "will keep for a year". Edges are finite and evict cold objects, so long-tail images and assets in small edges get re-fetched. New deploys produce new URLs that miss once per tier. Variants (compression, image sizes) are separate keys. A shield cuts these to roughly one fetch per object per tier, and the number to watch is shield hit ratio, not just edge hit ratio.

"What is the difference between no-cache and no-store?"

no-cache allows storing but requires revalidation with the origin before every reuse, so a 304 can still save bandwidth. no-store forbids storing at all. For personal data in shared caches you want private, no-store. no-cache on a personal page still allows a shared cache to hold it, and a revalidation bug would then expose it.

"How does request collapsing go wrong?"

Collapsing makes later requests wait on the first fetch for the same key. If that response turns out to be uncacheable (private, Set-Cookie), the waiters cannot share it and each goes to the origin in turn, so you get a serialised queue and very high latency. Caches remember such URLs as "pass" objects to avoid waiting next time. The fix is to make cacheability predictable by route, so the edge knows before the first fetch.

"An attacker sends a request with a weird header and every user gets a defaced page. Explain."

Cache poisoning. The origin used a request header that was not part of the cache key, such as X-Forwarded-Host, to build the response. The edge stored that response under the normal key and served it to everyone until it expired. Prevent it by making the cache key include everything the origin varies on, or by stripping and ignoring such headers at the edge. Treat any unkeyed input that affects the body as a vulnerability.

"Should a personalised API go through the CDN at all?"

Often yes, but not for caching. Users far from the origin save most of the handshake cost because TLS terminates at a nearby edge and the edge reuses warm connections to the origin. You also get edge DDoS protection and rate limits. Mark the responses private, no-store so nothing is stored. If users are close to the origin and connections are long-lived, the benefit is small and the extra layer may not earn its debugging cost.

"Marketing wants a price change visible worldwide within ten seconds, but the product page has a 5-minute edge TTL. Options?"

Three. Tag the page with Surrogate-Key: product-4521 and purge the tag from the pricing service's change event, which gives fast updates with a long TTL, as long as the purge path is reliable. Or drop the edge TTL to a few seconds with SWR and accept more revalidations, which the shield absorbs. Or render the price client-side from a small, short-TTL price API. For prices that matter legally, the checkout must read the price from the pricing service anyway, so the page is a display copy and a few seconds of staleness there is a product decision.

"Why might moving to anycast break long downloads for a few users?"

Anycast routes each packet to the nearest announcing location by BGP. If routing changes mid-connection, packets for an existing TCP connection can land at a different edge that has no state for it, and the connection resets. Short requests rarely notice. Long downloads and long-lived connections can. Providers reduce this with stable routing and connection handling between nearby machines, and clients should support resumable downloads with range requests.
