Deep Dive: Inside the Mechanism

The lesson explains why batching works: weights stream once per step, so more requests per step means more tokens per byte moved. This section opens the engine. It covers the arithmetic that says where "memory-bound" turns into "compute-bound," the memory layout that decides how many requests fit, and the scheduler loop that decides which ones run. It also names the configuration knobs that control each.

Two phases, two bottlenecks

Every LLM request runs in two phases with opposite characters.

  • Prefill processes the whole prompt in one pass. A 1,200-token prompt is 1,200 tokens of matrix multiplication against the same weights, all at once. That is a lot of arithmetic per byte of weights loaded, so prefill is compute-bound. Its output is the KV cache for the prompt and the first generated token. Prefill time is most of TTFT.
  • Decode generates one token per step per request. Each step multiplies one token's activations by every weight. That is very little arithmetic per byte loaded, so decode is bandwidth-bound. Decode time per token is called TPOT (time per output token) or inter-token latency.

A useful way to see the boundary is arithmetic intensity: FLOPs done per byte moved from memory. A forward pass for one token costs about 2 FLOPs per parameter. With 16-bit weights, each parameter is 2 bytes. So one token per step does about 1 FLOP per byte of weights. A batch of B decode tokens does about B FLOPs per byte, because the weights are shared.

An A100-class GPU offers on the order of 300 TFLOPS of dense 16-bit compute and about 2 TB/s of memory bandwidth. Divide one by the other and the chip balances at roughly 150 FLOPs per byte. Below that, memory is the limit. Above it, compute is. So for the weight-multiplication part of decode, batches up to around 100–150 ride almost free. That is the precise version of "batch-32 is barely slower than batch-1." The real crossover comes earlier, for a reason the next section explains: the KV cache.

The KV cache: what it is and how big

Attention needs every earlier token's key and value vectors, at every layer. Recomputing them each step would make generation quadratic, so the engine stores them. That store is the KV cache. Its size per token is:

bytes per token = 2 (K and V) x layers x kv_heads x head_dim x bytes_per_value

For a 7B model in the Llama-2 shape (32 layers, 32 KV heads, head dimension 128, 16-bit values), that is 2 x 32 x 32 x 128 x 2 = 524,288 bytes. Half a megabyte per token. A 1,600-token conversation holds 800 MB of KV cache. Models with grouped-query attention (GQA) share each KV head across several query heads. An 8B model with 8 KV heads instead of 32 needs a quarter of that: 128 KB per token. Architecture choices like this move serving cost as much as any engine setting.

KV cache also costs bandwidth. Every decode step reads each active request's whole cache. At large batches, those reads outgrow the weight reads, and decode stays bandwidth-bound well past the batch size the weight arithmetic alone predicts. The sizing section works through the numbers.

Paged KV memory

Before paging, engines reserved one contiguous slab per request, sized for the maximum possible length. A request allowed 4,096 tokens that stopped at 300 wasted over 90% of its slab. PagedAttention, introduced by vLLM, borrows the operating system's answer.

  • The KV pool is cut into fixed blocks, each holding a small number of tokens (16 by default in vLLM, set by block_size).
  • Each sequence has a block table mapping its logical token positions to physical blocks, which can be anywhere in the pool.
  • Blocks are allocated as tokens are generated. Waste is limited to the partly filled last block of each sequence.
  • Blocks can be shared. Two sequences with the same prefix (the same system prompt, or parallel samples of one prompt) point at the same physical blocks, with copy-on-write when they diverge. Prefix caching extends this across requests: the engine hashes full blocks of prompt tokens, so a later request with the same system prompt reuses them and skips that part of prefill.

The continuous-batching scheduler loop

An engine like vLLM runs a loop. Each iteration is one forward pass, and before each one the scheduler decides what goes in:

  1. Keep the running set. Every running sequence needs one more token. If any of them needs a new KV block and none is free, the scheduler preempts the most recently admitted sequence. It either frees the sequence's blocks and recomputes them later, or swaps them to CPU memory. Recompute is the common default.
  2. Admit from the waiting queue, first come first served, while three limits hold: free KV blocks for the new prompt, the cap on concurrent sequences (max_num_seqs), and the per-step token budget (max_num_batched_tokens).
  3. Run the step. Decode tokens for running sequences and prompt tokens for newly admitted ones go into one batch.
  4. Retire finished sequences (stop token, stop string, or max_tokens reached) and free their blocks at once. Streamed tokens go back to clients as they are produced.

With chunked prefill, step 2 can admit part of a long prompt. A 30,000-token prompt is fed in pieces that fit the remaining token budget, interleaved with everyone else's decodes. That is the lesson's Q3 fix. Whether it is on by default has varied across vLLM versions and settings, so check yours.

Dynamic batching for fixed-shape models

For the embeddings endpoint, the mechanism is much simpler. A request queue, a timer and a size cap. Triton's model configuration states it directly:

max_batch_size: 64
dynamic_batching {
  preferred_batch_size: [ 16, 32 ]
  max_queue_delay_microseconds: 5000
}
instance_group [ { count: 2, kind: KIND_GPU } ]

The server launches a batch as soon as it can form a preferred size, or when the oldest request has waited 5 ms. Two model instances on the GPU let one batch run while the next forms. The one subtlety is padding. If inputs vary in length (texts of 20 and 500 tokens), a batch pads everything to its longest member. Sorting or bucketing by length before batching can recover a large share of wasted compute, and the cost is a little added queueing delay.

Deep Dive: Sizing and the Numbers

Assumptions: a 7B model in 16-bit (about 14 GB of weights), the Llama-2 shape (0.5 MB of KV per token), one 80 GB A100-class GPU with about 2 TB/s of bandwidth and about 300 TFLOPS of dense 16-bit compute. Real kernels reach perhaps 60–80% of peak bandwidth, so real numbers land below these ceilings. The point is the shape of the curve, which holds.

How many conversations fit

With gpu_memory_utilization = 0.9, the engine claims 72 GB. Weights take 14 GB. Activations, CUDA graphs and runtime overhead take a few more; call it 4 GB. That leaves about 54 GB for the KV pool.

  • 54 GB / 0.5 MB per token ≈ 108,000 tokens of context, across all running requests.
  • An average support conversation at generation time holds 1,200 prompt tokens plus up to 400 output tokens, so about 1,600 tokens.
  • 108,000 / 1,600 ≈ 67 concurrent conversations.

That is where the lesson's "batch around 64" comes from. The ceiling is memory, not compute. With a GQA model at 128 KB per token, the same pool holds about 430,000 tokens, around 270 conversations. Then the limit moves to latency.

Three things come out of this table.

First, batch 64 lands at about 2,800 tokens per second, which matches the lesson's 2,500–3,000. Second, per-user pace falls from 140 to 43 tokens per second. People read at perhaps 5–10 tokens per second, so 43 is still comfortably faster than reading. That is why the lesson can say pace is "roughly unchanged" from the user's point of view. Third, at batch 64 the KV reads (32 GB) already outweigh the weights (14 GB). The cache, not the weights, now sets the cost of each extra request.

A note on the incident's 50 tokens per second at batch 1: the bandwidth ceiling is about 140. Plain framework serving loses the difference to kernel launches, Python overhead and unoptimized attention. Engines close much of that gap even at batch 1, which is part of why "use vLLM-class engines" is the advice.

Compute check at GQA batch 128: 128 tokens x 14 GFLOPs each ≈ 1.8 TFLOPs per step, about 6 ms at 300 TFLOPS. The step is 15 ms. Still bandwidth-bound, as the arithmetic-intensity argument predicted.

Picking the batch cap from a latency target

Don't set max_num_seqs from throughput alone. Set it from a TPOT target. If product wants at least 25 tokens per second per user, TPOT must stay under 40 ms. From the table, that allows a batch of about 100 on the non-GQA model, if memory allowed it. Memory caps it at about 67. So memory binds first here, and the GPU will run near its memory limit. That is exactly where preemption lives (failure mode 1). Leave margin: a cap around 48–56 with real traffic's length distribution is safer than 67.

Fleet size by Little's law

Concurrency equals arrival rate times time in system. At 20 requests per second, with TTFT around 0.3 s and 400 output tokens at 23 ms each (9.2 s), each request lives about 9.5 s. So the fleet holds 20 x 9.5 = 190 conversations at once. At 64 per GPU, that is three GPUs at the limit. The lesson's "4 plus one for headroom" is the same answer from the throughput side (2,800 tokens per second / 400 tokens ≈ 7 requests per second per GPU). Two methods, one answer: a good sign the model is right.

The pasted contract, in numbers

Prefill costs about 2 x parameters FLOPs per prompt token, plus attention, which grows with the square of length. A 30,000-token contract on a 7B model is at least 2 x 7B x 30,000 ≈ 4.2 x 1014 FLOPs. At an effective 150 TFLOPS (half of peak), that is around 3 seconds. Without chunking, that is one 3-second step for everyone in the batch: every running user's stream freezes for 3 seconds. That is the lesson's Q3 spike.

Chunked prefill with a 2,048-token budget per step splits it into about 15 chunks. Each chunk adds roughly 2 x 7B x 2,048 ≈ 29 TFLOPs, about 0.2 s at 150 TFLOPS, to its step. So everyone's TPOT rises to about 200 ms for those 15 steps, instead of one 3-second freeze. A 512-token budget means about 60 chunks of ~50 ms each: smoother for everyone else, slower TTFT for the contract. The chunk size is a fairness dial between the big request and the rest. Prefill/decode disaggregation exists to stop trading one against the other.

What prefix caching saves

The support assistant sends the same 800-token system prompt on every request. Without prefix caching, every request prefills it: 800 x 14 GFLOPs ≈ 11 TFLOPs, about 75 ms at 150 TFLOPS, and 400 MB of KV per request. With prefix caching, that prefix lives once per replica. TTFT drops by most of that 75 ms, and running conversations share 400 MB instead of each holding a copy. That is only true if requests reach a replica that has the prefix cached, which is why routing becomes part of serving.

Deep Dive: Failure Modes in Production

1. The preemption storm

Symptom. Throughput drops by half during peak, and TPOT becomes jagged. GPU utilization still looks high.

Mechanism. The batch cap was tuned on short test prompts. Real conversations are longer, and the KV pool fills. Each time a running sequence needs a block, the scheduler preempts another and later recomputes its whole prefix. The GPU spends its time recomputing work it already did. Long conversations get preempted repeatedly, so they are the ones that suffer most.

Detect. The engine's preemption counter, and KV cache usage pinned near 100%. vLLM logs a warning when it preempts and exposes both as metrics. Watch the ratio of prompt tokens computed to prompt tokens received; above 1 means recompute.

Fix. Lower max_num_seqs until preemption is rare. Cap max_model_len and max_tokens to what the product needs. Use a GQA model or a quantized KV cache if quality allows. Admission control at the router should queue requests rather than let the engine overcommit.

2. The generation that never stops

Symptom. A handful of requests take two minutes. Their responses end in the same phrase repeated hundreds of times.

Mechanism. The model fell into a repetition loop and nothing stopped it. The request had no max_tokens, so the engine's limit was the model's full context length. Each looping request held a batch slot and a growing pile of KV blocks for thousands of steps.

Detect. The distribution of output tokens per request. A long tail out at the context limit is the signature. Also count finish reasons: "length" versus "stop."

Fix. Always set max_tokens from the product's real need. The support assistant needs perhaps 800. Set stop sequences that fit the chat template. Add a wall-clock deadline at the router. Repetition penalties help some models, at some cost to quality, so test them.

3. Abandoned generations still running

Symptom. The fleet runs hot but delivered tokens per second are well below generated tokens per second.

Mechanism. A user closes the tab. The browser drops the SSE stream. But the proxy in front of the engine does not propagate the disconnect, or the gateway buffers, so the engine keeps generating 400 tokens to nobody. On a support assistant where users often leave mid-answer, this can waste a large share of capacity.

Detect. Compare tokens generated by the engine with tokens written to clients, per route. Count engine-side aborts. Zero aborts on a chat product means disconnects are not arriving.

Fix. End-to-end cancellation. Every hop (load balancer, gateway, engine API server) must close its upstream request when its downstream closes, and the engine must abort the sequence and free its blocks. Test it: start a stream, kill the client and watch the engine's running count drop.

4. The replica that gets all the long ones

Symptom. One replica has a deep queue and preempts constantly. Its neighbours sit half empty. Average TTFT looks fine; p99 does not.

Mechanism. Least-connections routing sees equal connection counts. It cannot see that one replica's connections are 20,000-token document sessions and another's are short chats. The variance the lesson calls Constant 1 defeats connection-count balancing.

Detect. Per-replica KV cache usage, waiting-queue length and running-sequence count, side by side. Healthy fleets show them close together.

Fix. Route on the engine's own load signals: waiting requests, KV usage, or outstanding tokens. Prefix-aware routing adds a second goal, sending requests that share a system prompt or a conversation to the replica that holds its blocks. The two goals conflict at the margin, so routers score both, for example by preferring the warm replica unless its queue is much deeper than average.

5. The silent template mismatch

Symptom. After a routine upgrade to a newer model version, answer quality drops. Responses sometimes continue the user's message, or include stray role markers. No errors.

Mechanism. Chat models are trained on a specific chat template: special tokens and markers around system, user and assistant turns. The serving code formatted prompts with the old model's template, hard-coded. The new model reads the conversation slightly wrong and has no way to say so.

Detect. An evaluation set run against every model version through the real serving path, not a notebook. Watch for responses that end with "length" when they should end with "stop."

Fix. Take the template and stop tokens from the model's own tokenizer configuration, not from serving code. Pin tokenizer and model together as one artifact. Treat a model swap as a release with an evaluation gate, as in Canary Deployment.

6. Temperature zero, different answers

Symptom. The evaluation suite flickers. The same prompt at temperature 0 gives different outputs from run to run, and a regression test fails one day in ten.

Mechanism. Batched GPU kernels can change the order of floating-point additions depending on batch size and composition. Addition in floating point is not associative, so logits differ in the last bits. When two candidate tokens are nearly tied, the argmax flips, and from that token on the whole continuation differs. Under continuous batching, the batch around your request is never the same twice.

Detect. Run one prompt a hundred times under load and count distinct outputs.

Fix. Don't build tests or caches that assume exact determinism. Evaluate with tolerance: graded quality scores, not string equality. Some engines and kernel libraries now offer batch-invariant modes, at a throughput cost. Use them only where reproducibility is a hard requirement, such as audits.

7. Two engines, one GPU, one crash loop

Symptom. After a deploy that added an embedding model to the chat GPUs to save money, pods crash on start with out-of-memory errors, intermittently.

Mechanism. Each engine claims a fraction of total GPU memory at start. Two engines each set to 0.9 cannot both get it. Which one wins depends on start order, so the failure looks random.

Detect. Startup logs show the memory each process claimed. Track GPU memory per process.

Fix. Give each engine an explicit share that sums under 1.0, or better, keep separate pools, or use hardware partitioning where the GPU supports it. Co-location saves money only when the claims are deliberate.

Deep Dive: Design-Review Checklist

  1. What are the TTFT and TPOT targets, at which percentile, and was the batch cap derived from them?
  2. What is KV bytes per token for this model, and how many tokens of context does one GPU hold after weights and overhead?
  3. What are the real prompt and output length distributions, and was the configuration load-tested with them rather than with fixed-size prompts?
  4. Is max_tokens always set, and is max_model_len no larger than the product needs?
  5. Is chunked prefill on, and what caps or tiering keep very long inputs from dominating a shared pool?
  6. Does cancellation propagate end to end, from the client's closed stream to the engine aborting the sequence?
  7. What does the router balance on: engine queue depth and KV usage, or just connections? Is it prefix-aware?
  8. Which engine metrics are dashboarded and alerted: preemptions, KV usage, waiting queue, finish reasons, generated versus delivered tokens?
  9. Do the chat template and stop tokens come from the model's own configuration, versioned with the weights?
  10. Is every model or engine upgrade gated by an evaluation run through the real serving path?
  11. Is bulk work kept off the interactive fleet, by a rule rather than by convention?

Deep Dive: Senior Interview Follow-ups

"At what batch size does decode stop being memory-bound?"

For the weight multiplications alone, around the GPU's compute-to-bandwidth ratio: roughly 150 FLOPs per byte on an A100-class part, and each batched token adds about 1 FLOP per weight byte in 16-bit. So somewhere past 100. In practice you usually never get there. Each sequence's KV cache must also be read every step, and those reads grow with batch size and context length. Memory capacity or KV bandwidth binds first, so decode stays bandwidth-bound across the batch sizes you can actually fit.

"How much KV cache does one token cost, and why does grouped-query attention matter for serving?"

Two (K and V) times layers times KV heads times head dimension times bytes. For a Llama-2-shaped 7B in 16-bit, that is about 0.5 MB per token, so 1,600 tokens is 800 MB. GQA cuts the KV heads, often by 4x or more, which cuts both the memory per conversation and the bytes read per step. On the same GPU that means several times more concurrent conversations at similar per-user speed. It is an architecture choice with a serving price tag.

"KV usage is at 100% and throughput just halved. What is happening?"

Preemption. Running sequences need new blocks, none are free, so the scheduler evicts some and later recomputes their prefixes. The GPU redoes work. Confirm with the preemption counter and recomputed prompt tokens. Lower the concurrent-sequence cap, cap output and context lengths, and queue at admission instead of overcommitting the engine.

"Why is least-connections routing bad for LLM serving, and what replaces it?"

Connections hide a hundredfold variance in work per request: one connection can be a 20,000-token document, another a ten-token reply. Balance on what the engine reports: waiting queue, KV usage, outstanding tokens. Then add affinity: a conversation or shared prefix should return to the replica holding its blocks, unless that replica is much busier than the rest. The router trades cache warmth against load.

"A user closes the tab halfway through. What should happen, and what usually happens?"

The stream closes, each proxy closes its upstream, the engine aborts the sequence and frees its blocks within a step. What usually happens is that some hop does not propagate the disconnect, and the GPU keeps generating to nobody. Measure generated versus delivered tokens to find it.

"Your temperature-zero regression test is flaky. Is the engine broken?"

Probably not. Batched kernels can sum in different orders depending on what else is in the batch. Floating-point addition is not associative, so near-tied tokens can flip, and the continuation diverges from there. Under continuous batching the batch is never the same twice. Test with graded evaluations and tolerances, not string equality. Use batch-invariant modes only where exact reproducibility is required and the throughput cost is accepted.

"When would you use tensor parallelism instead of more replicas?"

When the model does not fit on one GPU with room for a useful KV pool, or when the per-token latency target is below what one GPU can do. Otherwise replicas win. They scale linearly, fail independently and need no fast interconnect. Tensor parallelism splits each layer across GPUs and pays communication on every layer of every step.

"Would quantizing to 4-bit fix the incident's cost problem?"

It would help a little and miss the cause. At batch 1, 4-bit weights stream about a quarter of the bytes, so one GPU might go from 50 to well over 100 tokens per second. That's maybe a 2–3x saving. Batching gave 30x without touching quality. Fix batching first; then quantize if evaluations show the quality loss is acceptable, and spend the freed memory on KV cache.
