Deep Dive: Inside the Mechanism

The lesson's sequence is: database first, then the cache, then the ack. That is right, and it answers the two single-write failures. A real design review asks harder questions. What if two writes to the same key overlap? What if the database times out and nobody knows whether it committed? What if the cache's own replica loses the update? The lesson's claim that the cache is "never stale" for data written through it holds only if the cache layer handles each of these.

The write path, step by step

Here is the full sequence for one price change, with the decisions at each step.

  1. Receive the write. The cache layer gets put(product:8412, price=$45).
  2. Write the database. It runs the UPDATE and waits for the commit. Ideally the statement also returns a version, for example UPDATE … SET price = 45, version = version + 1 WHERE id = 8412 RETURNING version on Postgres.
  3. Branch on the result.
    • Committed: continue to step 4.
    • Rejected (constraint, conflict): change nothing in the cache, return the error.
    • Unknown (timeout, dropped connection): invalidate the key, then return an error that says the outcome is unknown. Never write the new value into the cache, and never leave the old one.
  4. Update the cache. Store the new value with its version and a TTL.
  5. Branch again. If the cache update fails, invalidate. If the invalidation also fails, record the key for repair (more on that below).
  6. Acknowledge. Return success once the database has committed, whatever happened to the cache.

Step 3's "unknown" case is the one teams forget. A commit that times out may have landed. If the cache keeps the old value, it is now stale. If the cache takes the new value, it may hold a value the database never stored. Deleting is the only safe move, because the next read goes to the database and finds whichever answer is true.

Why the database goes first

Some designs update the cache first, then the database. It feels faster, because readers see the new value sooner. It is a trap. If the database write then fails, the cache holds a value that does not exist anywhere else. Readers see a price that was never saved, and the TTL is the only thing that eventually removes it.

The same trap appears in a subtler form: updating the cache inside the database transaction, before COMMIT. If the commit fails or the transaction rolls back, the cache already has the new value. Readers can also see it before other database readers do. The cache update belongs after the commit returns, never before.

Concurrent writes still race

The cache-aside lesson rejected "update the cache on write" because two concurrent writes can reach the cache in the opposite order from their commits. Write-through updates the cache on write. So, by default, it has the same race.

There are three ways to close it.

  • Serialise writes per key in the cache layer. If all writes to a key pass through one owner that does "database, then cache" one write at a time, the cache sees them in commit order. Data grids work this way: in Hazelcast, an IMap.put with a write-through MapStore runs on the partition that owns the key, and that partition handles its operations in sequence. The cost is that a slow database write blocks the next write to every key in that partition.
  • Version-conditional updates. Carry the database's version with the value, and let the cache accept an update only if its version is newer than what it holds. This is cheap and works with many independent writers.
  • Invalidate instead of updating when in doubt. Some layers update the cache only when they hold a per-key lock, and delete otherwise.

In Redis, the version check is a short Lua script, which Redis runs atomically:

-- KEYS[1] = cache key; ARGV[1] = version; ARGV[2] = value; ARGV[3] = TTL seconds
local cur = redis.call('HGET', KEYS[1], 'v')
if cur and tonumber(cur) >= tonumber(ARGV[1]) then
  return 0                          -- an equal or newer version is already cached
end
redis.call('HSET', KEYS[1], 'v', ARGV[1], 'd', ARGV[2])
redis.call('EXPIRE', KEYS[1], ARGV[3])
return 1

Write-through layers usually serve reads through the same cache, so reader fills need care too. A reader that missed and loaded the old row can arrive after the writer's update. The same version check handles it: the reader's fill carries v7, the cache holds v8, and the fill is rejected. Without versions, filling with "store only if absent" (Redis SET … NX, Memcached add) while writers always overwrite closes most of that window.

When the invalidation cannot reach the cache

The lesson's fallback for a failed cache update is "invalidate". But the most common reason a cache update fails is that the cache is unreachable, and then the invalidation fails too. The old value stays in the cache, and when the cache comes back it serves that stale value.

A careful layer has a third line of defence. Options, roughly in order of effort:

  • A short TTL. The stale value lasts at most one TTL. This is why the lesson insists TTLs stay.
  • A repair log. Append the key to a durable list (a database table, a queue) when invalidation fails, and replay it when the cache is healthy again.
  • Change-data capture as a backstop. A process tailing the database's change log deletes or updates keys for every commit. It catches failed invalidations and bypassing writers alike.
  • Flush or bump a generation after a cache outage. Crude but certain: when a cache node returns after a partition, treat its contents as suspect.

The cache's own replicas

Redis replicates asynchronously. A write-through update can be acknowledged by the Redis primary and lost if the primary fails before its replica receives it. After the failover, the new primary holds the previous value. The database has the new one. Nothing on the write path will touch that key again until the next write.

With cache-aside this rarely matters: a lost SET is a later miss. With write-through, a lost update leaves a stale value that looks valid. A TTL bounds it. WAIT in Redis can make the writer wait for replicas to acknowledge, at a latency cost, and it still does not make Redis a strongly consistent store. The honest fix is to treat a cache failover as an event that requires cleanup: flush, bump the key generation, or rely on short TTLs.

Many keys, no transaction

A database transaction can change a product price and the total of a bundle that contains it, atomically. The cache layer then updates two keys one after the other. Between those updates, a reader can see the new product price with the old bundle total. Most caches do not offer transactions that span the database and the cache together. Redis MULTI makes a group of cache commands atomic among themselves, but the database commit and the cache update are still two separate steps.

Usually this brief inconsistency is acceptable. When it is not, cache the composite as one entry (the bundle with its items' prices inside), or put a version on the parent and have readers reject children with a mismatched version.

Where real systems put the logic

  • JCache (JSR-107). setWriteThrough(true) plus a CacheWriter. A put calls the writer, and a writer exception means the cache entry is not updated. Ehcache and other providers implement this.
  • Data grids. Hazelcast's MapStore is write-through when its write delay is 0 and write-behind when it is positive. Apache Ignite and Oracle Coherence have equivalent CacheStore hooks. The grid owns each key on one member, which is what makes per-key ordering possible.
  • DAX. Writes through DAX go to DynamoDB and then update DAX's item cache. Its query cache is not updated by writes, and writes made directly to DynamoDB are not seen by DAX until entries expire.
  • Your own data-access layer. Most teams with Redis build write-through as a repository class: one function per entity that commits, then updates the cache with a version. That works, provided every writer uses it.

Deep Dive: Sizing and the Numbers

The running assumptions: a database commit takes 5 ms at p50 and 25 ms at p99. A cache update takes 1 ms at p50 and 5 ms at p99. The cache has 6 GB of usable memory. It holds the 2,000,000-item catalog at about 2 KB per item, plus per-locale variants, sellers and review summaries, so it is always full and relies on eviction.

Write latency

The two steps run in sequence, so their latencies add. At the median, 5 + 1 = 6 ms. At the tail, adding p99s gives an upper bound, not the exact p99: up to 25 + 5 = 30 ms. If the two are independent, the real combined p99 is a little below that.

The cache step is small compared with the commit. But it is a second dependency on every write's critical path, and its tail is what matters. A Redis node doing a background save, or a cache client waiting on a full connection pool, can add hundreds of milliseconds to writes that the database finished in 5 ms. Give the cache step its own short timeout, and on timeout, invalidate and acknowledge.

Write availability

Suppose the database is available 99.95% of the time and the cache 99.9%. A month has about 43,200 minutes.

  • If a cache failure fails the write: availability ≈ 0.9995 × 0.999 ≈ 99.85%. That allows about 65 minutes of failed writes per month.
  • If a cache failure only causes an invalidation (or a repair-log entry) and the write succeeds: availability stays near the database's 99.95%, about 22 minutes per month.

The difference, around 43 minutes a month, is the price of letting the cache block writes. That is why the lesson's rule is "invalidate and return success". The cache is an optimisation, so it must not reduce write availability.

Cache churn

Every write puts its value into the cache, whether anyone reads it or not. Memory taken by written-but-unread values is roughly write rate × value size × the time they stay before eviction or expiry.

  • The activity log. 5,000 click events per second × 500 bytes × a 1-hour TTL = 9 GB. That is more than the whole product cache. Under allkeys-lru, those fresh but useless entries push out hot products, and the product hit ratio falls.
  • The nightly price import. 2,000,000 updates of 2 KB each is 4 GB written in 10 minutes. On a full 6 GB cache, the import's entries look like the most recently used data, so they push out hot entries that were read less recently. The cache fills with whatever the import touched, in import order. The morning's traffic then starts with a partly cold cache.

The fix for both is the same: bulk and write-only paths should write around the cache. They write to the database and invalidate the keys that exist, rather than inserting every value. Redis LFU eviction (allkeys-lfu) also resists this kind of churn better than LRU, since a key written once has a low frequency count.

What write-through actually buys

Write-through does not reduce database load much. Every write still goes to the database, and delete-on-write costs only one extra read per written key that is read again. For profile edits at 50 per second, where most edits are viewed right away, delete-on-write adds about 50 extra database reads per second. That is trivial next to the 12,000 reads per second a cache absorbs.

The real gains are elsewhere. The user who just saved sees the saved value from the cache in 1 ms instead of 16 ms. There is no window in which a delete has happened but a refill has not. Write paths need no invalidation code, provided they go through the layer. Judge the pattern on those gains, because judged on load alone it rarely wins.

Write amplification on the cache

Each write-through update touches the cache primary and every cache replica. A cache with two replicas turns 2,000 writes per second of 2 KB into 2,000 × 2 KB × 3 = 12 MB/s of cache writes and replication traffic. That is small for a product catalog. It becomes significant for write-heavy entities like inventory counters or session-like state, which is another reason those paths often skip the cache or use a different pattern.

Deep Dive: Failure Modes in Production

1. Two quick edits, the wrong one wins

Symptom. A merchant changes a price twice within a second. The database shows the second price. The site shows the first, until the TTL expires.

Mechanism. Two write-through requests ran on different application servers. Both committed in order, but the first one's cache update was delayed by a GC pause and landed after the second's. A plain SET let the older value overwrite the newer one, exactly the race the cache-aside lesson warned about.

Detect. A sampled consistency checker that compares cache values with the database for recently written keys. Logging the version written on each cache update makes the reversal visible.

Fix. Version-conditional cache updates, or per-key serialisation in the cache layer. Keep the TTL as a bound for anything the version check misses.

2. The write that failed, and also succeeded

Symptom. The user gets an error on save and tries again. Both attempts show up in the database. Meanwhile the cache shows the price from before either attempt.

Mechanism. The database commit took longer than the layer's timeout. The commit actually landed, but the layer treated the timeout as a failure: it skipped the cache update and returned an error. The cache kept the old value. The retry then committed again.

Detect. Count database timeouts on the write path separately from rejections. Compare against rows that were in fact written.

Fix. Treat "unknown" as its own outcome. Invalidate the key so the next read finds the truth, and tell the caller the result is unknown rather than failed. Make the write idempotent with a request key, so a retry cannot apply twice; see Idempotency.

3. The cache was down during the write

Symptom. After a five-minute network partition between the application and one cache node, a handful of products show prices that were changed during the partition. The prices are wrong until their TTLs expire.

Mechanism. During the partition, writes committed to the database. Their cache updates failed, and so did the invalidations, because the node was unreachable. The node still held the old values. When the partition healed, it served them as valid entries.

Detect. Count failed invalidations as a metric, not a log line. Any non-zero count means stale entries may exist.

Fix. Record failed invalidations in a durable repair log and replay it when the node recovers, or tail the database's change log as a backstop. Keep TTLs short enough that the worst case is tolerable.

4. The update that a failover undid

Symptom. Right after a Redis primary failover, a few recently edited products revert to their previous values on the site. The database is correct.

Mechanism. Redis acknowledged those cache updates on the old primary, which failed before replicating them. The promoted replica had the older values. Write-through assumes that a successful cache update stays updated, so nothing corrected them. If the team had removed TTLs, they would stay wrong until the next write to each product.

Detect. Treat failover events as triggers for a consistency check on keys written in the last few seconds before it. The replication offset gap reported at failover tells you how much was lost.

Fix. Keep TTLs. After a failover, flush or bump the generation of the affected key range, or replay recent writes from the database's change log. Use WAIT only if you have measured that the extra write latency is worth it.

5. The import that evicted the hot set

Symptom. Every morning after the nightly price import, the product hit ratio drops from 99% to about 70% and slowly recovers by noon. Database load is highest at the start of the business day.

Mechanism. The import was moved onto the write-through layer, so it would stop bypassing the cache. That fixed staleness, but it wrote 2,000,000 entries into a cache that was already full. Hot entries that had not been read for a while (overnight, most of them) were evicted to make room for cold products the import touched.

Detect. Evictions per second and hit ratio plotted against batch job schedules. A sharp eviction spike during the job is the signature.

Fix. Bulk jobs write around the cache: commit to the database, then invalidate only keys that are present. Or update a key only if it already exists (Redis SET … XX), so the import refreshes cached entries without adding cold ones. Consider LFU eviction.

6. The bundle total that did not add up

Symptom. For a few seconds after a price change, a bundle page shows item prices that do not sum to the bundle total. Customers screenshot it.

Mechanism. One database transaction changed the item and the bundle. The write-through layer then updated the item key and the bundle key separately. A reader between those updates saw one new and one old. Under load, the gap stretched to seconds because the second update queued behind others.

Detect. An invariant check on rendered pages, or a synthetic test that changes a price and reads the bundle in a loop.

Fix. Cache the bundle as one composite entry, compute the total at read time from cached items, or version the parent and have readers reject children from a different version. Accept brief inconsistency where it does not matter, and say so in the design.

7. Writes got slow and the database was fine

Symptom. Save latency p99 rises from 30 ms to 800 ms. Database commit latency is unchanged.

Mechanism. The cache step sits on every write's critical path. A cache node was busy with a large key deletion and a background save, and its clients' connection pool was exhausted. Writes waited for a cache connection after their commit was already done.

Detect. Trace spans for the database step and the cache step separately. The cache client's pool wait time.

Fix. A tight timeout on the cache step (a few times its normal p99), after which the layer invalidates (or logs for repair) and acknowledges. A circuit breaker that skips the cache update when the node is unhealthy. The database's commit is the durable part; the cache step must never hold the user hostage.

Deep Dive: Design-Review Checklist

  1. Is the order strictly "database commit, then cache update", and never inside the transaction?
  2. What does the layer do when the commit outcome is unknown (timeout, dropped connection)? Does it invalidate, and what does it tell the caller?
  3. How are two concurrent writes to the same key ordered in the cache: per-key serialisation, version checks, or nothing?
  4. Do reader fills check versions, or use "store only if absent", so a late fill cannot overwrite a newer write?
  5. When both the cache update and the invalidation fail, where is the key recorded, and who repairs it?
  6. Does a cache failure ever fail the user's write? What is the cache step's timeout?
  7. Which writers bypass the layer: bulk imports, other services, manual fixes? What catches them: change-data capture, TTLs, or both?
  8. What TTL remains on every entry, and has anyone proposed removing it?
  9. What happens after a cache primary failover? Is there a cleanup step for updates the replica may have missed?
  10. Which write paths should not insert into the cache at all (logs, metrics, bulk jobs), and do they write around it?
  11. Where does a single database transaction update several cached keys, and is the brief mixed state acceptable?
  12. Which metrics exist: cache-step latency and failures, failed invalidations, version rejections, evictions during batch jobs, sampled cache-versus-database mismatches?

Deep Dive: Senior Interview Follow-ups

"With write-through, can the cache ever be stale for a key written through it?"

Yes, unless the layer orders updates. Two concurrent writes can commit in one order and reach the cache in the other, which leaves the older value cached. It is the same race that makes "update on write" risky in cache-aside. The fixes are per-key serialisation in the cache layer, as data grids do with partition owners, or version-conditional updates that reject older versions. Add to that ambiguous commits, failed invalidations and cache failovers, and the honest claim is "fresh, provided the layer handles these cases, with TTLs as the bound when it does not".

"The database commit times out. What does the cache layer do?"

It does not know whether the write landed, so it must not update the cache with the new value or leave the old one trusted. It deletes the key, so the next read fetches whatever the database actually holds. It then returns an "unknown outcome" error, and the client retries with an idempotency key so a commit that did land is not applied twice.

"Why not update the cache first? Readers would see the change sooner."

Because if the database write then fails, the cache holds a value that exists nowhere else, and readers see a price that was never saved. Database first means a database failure leaves the cache untouched, and the user gets an error that matches reality. The cost is about a millisecond before readers see the new value, which is nothing.

"Should the nightly bulk import go through the write-through layer?"

It should go through the layer's invalidation logic, but it should not insert every row into the cache. Writing 2 million cold entries through the cache evicts the hot set and starts the next morning with a poor hit ratio. Better: commit in batches, then invalidate the keys that exist, or update only keys already present (SET XX). That keeps the import from leaving stale data and from flushing the cache.

"Redis fails over right after a write-through update. What can go wrong?"

Redis replication is asynchronous, so the primary may have acknowledged the update without its replica receiving it. The promoted replica then serves the previous value while the database holds the new one, and nothing on the write path revisits that key. A TTL bounds the damage. Beyond that, treat failover as a cleanup event: flush or bump the generation for recent keys, or replay recent commits from the change log. WAIT can reduce the window at a latency cost, but it does not make Redis strongly consistent.

"With write-through and change-data capture in place, can we remove TTLs?"

I would not. TTLs cost almost nothing, and they bound every failure you have not thought of: a bug in the change-log tailer, a lost cache update in a failover, a race the version check missed, an old key format nobody reads. Make them long if freshness comes from the write path, say a day for product descriptions. The lesson's misuse case is exactly a team that removed TTLs and then could not explain why some values never updated.

"Inventory counts change on every purchase. Write-through, write-behind or neither?"

Usually neither for the authoritative count. The purchase must check the database, so the cache cannot be the source of truth, and write-behind would risk losing acknowledged decrements. For the displayed "only 3 left" number, a short TTL or update-if-present write-through is fine, because a few seconds of staleness is acceptable there. The real decision is to separate the count that decides a sale from the count that decorates a page.

"Write-through doesn't cut database load. So why use it?"

For read-after-write and for structure. The user who just saved sees the saved value in about 1 ms, with no delete-then-refill gap. Write paths that go through the layer need no invalidation code, so the forgotten-delete bug cannot happen there. If neither matters, for example for data users rarely read right after writing, delete-on-write is simpler and works with any cache. I would not choose write-through to save database capacity.
