Deep Dive: Inside the Mechanism

The lesson's rule is short: append the record, fsync it, then acknowledge. A real database needs a few more rules to make that safe. It has to stop a data page from reaching disk before its log record does. It has to survive a torn data page, not only a torn log record. It needs to know where replay starts, and it has to decide what "fsync" means on hardware that sometimes lies. PostgreSQL shows all of this clearly, so we start there, then compare InnoDB, SQLite, LSM engines and the systems that skip fsync on purpose.

PostgreSQL: records, LSNs and the page rule

Postgres writes its log as a sequence of 16 MB segment files in pg_wal/ (the size is set at initdb). Every record has a log sequence number (LSN), its byte position in the endless logical log. A record's header carries its total length, the transaction ID, the LSN of the previous record, which subsystem it belongs to (heap, B-tree index, transaction commit and so on) and a CRC-32C checksum over the whole record. The previous-record pointer and the checksum together let recovery tell a valid next record from leftover bytes.

Every 8 KB data page also stores an LSN in its header: the LSN of the last record that changed it. That enables the rule that makes the whole design work, usually called the WAL rule. Before the buffer manager writes a dirty page to disk, it makes sure the WAL is flushed at least up to that page's LSN. So a data page can never be on disk with changes whose log record is not. Pages can be written lazily, in any order, at any time, and recovery can always redo them.

In database theory this is the "steal, no-force" policy from the ARIES family of algorithms. Steal: dirty pages may be written before their transaction commits. No-force: committed pages need not be written at commit. The log makes both safe. ARIES also uses an undo log to roll back stolen pages of transactions that aborted. Postgres does not need undo for that, because MVCC never overwrites a row in place. An aborted transaction's new row versions simply stay invisible until vacuum removes them.

Torn data pages: full-page writes and doublewrite

The lesson's checksum protects log records. But the WAL rule lets data pages be written at any time, and an 8 KB database page is several 4 KB disk sectors. A power cut mid-write can leave a page half old and half new. Redo cannot fix that by replaying a small "change byte 312" record, because the rest of the page is garbage.

Postgres solves it with full-page writes (full_page_writes = on, the default). The first time a page is modified after each checkpoint, the WAL record carries a full image of the page. Recovery restores that image and replays later changes on top, so a torn page is simply overwritten. The cost is WAL volume, and the sizing section shows how large it can get. wal_compression (with lz4 or zstd in PostgreSQL 15 and later) shrinks these images.

InnoDB takes a different route, the doublewrite buffer. Before writing pages into their real places, it writes them sequentially to a doublewrite area and syncs that. If a real write tears, recovery takes the intact copy from the doublewrite area. Both designs pay to make torn pages repairable. Postgres pays in log volume, InnoDB in a second data write.

Checkpoints and where replay starts

A Postgres checkpoint does not stop the world. It records a redo point (the current WAL position), then writes out every page that was dirty at that moment, spreading the writes over time. When done, it writes a checkpoint record and updates pg_control, a small file that tells recovery where the latest checkpoint is. On restart, recovery reads pg_control, jumps to that checkpoint's redo point, and replays forward until the next record fails to validate. That is the end of the log.

The knobs:

  • checkpoint_timeout (5 minutes by default): the longest time between checkpoints.
  • max_wal_size (1 GB by default): a soft limit on WAL between checkpoints. Reaching it triggers a checkpoint early. If that happens more often than checkpoint_warning (30 seconds), the log says "checkpoints are occurring too frequently."
  • checkpoint_completion_target (0.9 by default since PostgreSQL 14): spread the page writes over 90% of the interval to avoid I/O bursts.

These three settings trade four things: recovery time, full-page-write volume, I/O smoothness and disk used by pg_wal. The sizing section works through them.

The commit path and group commit

Backends do not each write their own WAL file. Each one inserts its records into shared WAL buffers in memory. At commit, the backend asks for WAL to be flushed up to its commit record. If another backend's flush already covered that position, it is done without any disk work. Group commit therefore happens on its own: one fdatasync covers every commit record written before it. (wal_sync_method defaults to fdatasync on Linux.) commit_delay can make a backend wait a few microseconds to gather more company, but on modern hardware the natural batching is usually enough.

synchronous_commit = off lets a commit return before its flush. A background WAL writer flushes every wal_writer_delay (200 ms by default), and the documentation puts the worst-case loss at three times that, about 600 ms. The database stays consistent after a crash; only the most recent commits may be missing. This is a session-level setting, so you can use it for the click log and keep full durability for orders.

Other engines, other defaults

  • MySQL/InnoDB keeps a redo log (sized by innodb_redo_log_capacity since 8.0.30) and separate undo logs for rollback and MVCC. innodb_flush_log_at_trx_commit decides durability: 1 (the default) writes and flushes at every commit; 2 writes to the OS at commit and flushes about once a second, so it survives a MySQL crash but not a power cut; 0 writes and flushes about once a second. MySQL also has the binlog, a second log for replication. sync_binlog = 1 is needed for the binlog to be durable too, and an internal two-phase commit keeps the two logs in agreement.
  • SQLite in WAL mode appends to a -wal file and copies pages back into the database at checkpoints (by default once the WAL reaches 1,000 pages). With synchronous=FULL each commit is fsynced. With synchronous=NORMAL in WAL mode, the database stays consistent after a power loss, but the most recent commits may roll back.
  • LSM engines such as RocksDB write to a WAL, then a sorted in-memory table (memtable). When the memtable is flushed to an on-disk sorted file, the WAL it covers can be deleted. RocksDB's WriteOptions.sync defaults to false. A write then survives a process crash, because it is in the OS page cache, but not a machine crash. Applications that need power-loss durability must ask for it.
  • Cassandra appends to a commit log, but by default (commitlog_sync: periodic, every 10 seconds) it acknowledges before fsync. Durability comes from replication: a write acknowledged at QUORUM sits in the memory of several machines. batch and group modes fsync before acknowledging.
  • Kafka does not fsync each message by default either. It relies on replication (acks=all with min.insync.replicas) and the OS page cache. A message is safe once several brokers have it, even if none has flushed it.
  • etcd fsyncs its WAL for every batch, because Raft's safety depends on it. Its documentation treats disk fsync latency as a primary health signal and suggests p99 wal_fsync_duration under about 10 ms.
  • Redis AOF offers appendfsync always, everysec (the default) and no. With everysec, Redis documents a typical loss of up to one second of writes, and up to about two seconds if fsync is slow.

The pattern across that list: "durable" can mean on one disk, or in the memory of several machines. Both are legitimate. What fails is assuming one when the system does the other.

What fsync actually promises

fsync(fd) asks the kernel to push a file's dirty data and metadata to the device and wait for the device to confirm. Four details catch people who write their own logs:

  • New files need a directory fsync. Creating or renaming a file changes the directory. If you fsync the file but not its parent directory, a crash can leave a perfectly synced file with no name pointing at it. Log rotation must fsync the directory.
  • Device write caches. Many drives have a volatile cache. The kernel sends a cache-flush command on fsync, and correct drives honour it. Some consumer devices, some RAID controllers without batteries, and virtual disks configured with an unsafe cache mode do not. They make fsync fast by not doing it. Enterprise SSDs with power-loss protection (capacitors that let the drive finish cached writes) are both fast and honest.
  • fsync errors are not retryable. In 2018 PostgreSQL developers found that on Linux, after a failed write-back, the kernel could mark the pages clean and clear the error. A retried fsync then "succeeded" even though data was lost. Since PostgreSQL 12 (and matching minor releases of older versions) Postgres treats an fsync failure as fatal (PANIC) and recovers from the WAL instead of retrying. The episode is often called "fsyncgate."
  • O_DIRECT is not durability. Bypassing the page cache does not bypass the device cache. You still need O_DSYNC or an explicit flush.

Here is the lesson's write path as runnable Python, with group commit and torn-tail handling. It is a teaching sketch, not a storage engine; a real one also needs the directory fsync above, segment rotation and checkpoints.

import os, struct, zlib

HEADER = struct.Struct(">II")   # payload length, CRC-32 of payload

def append(fd, records: list[bytes]) -> None:
    """Group commit: write every record in the batch, then one fsync."""
    buf = b"".join(HEADER.pack(len(r), zlib.crc32(r)) + r for r in records)
    os.write(fd, buf)
    os.fsync(fd)            # only now may the callers hear "saved"

def recover(path: str) -> list[bytes]:
    """Replay complete records; stop at the first torn or corrupt one."""
    out, data, pos = [], open(path, "rb").read(), 0
    while pos + HEADER.size <= len(data):
        length, crc = HEADER.unpack_from(data, pos)
        body = data[pos + HEADER.size : pos + HEADER.size + length]
        if len(body) < length or zlib.crc32(body) != crc:
            break           # torn tail: never acknowledged, safe to drop
        out.append(body)
        pos += HEADER.size + length
    return out

path = "orders.wal"
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_APPEND, 0o644)
append(fd, [b'{"order":"7f3a","status":"paid"}', b'{"order":"7f3b","status":"paid"}'])
os.write(fd, HEADER.pack(40, 12345) + b'{"order":"7f3c"')   # crash mid-write
os.close(fd)
print(recover(path))   # the two acknowledged records, nothing else

Note the one judgement call in recover: it stops at the first bad record. That is right for a torn tail. A bad record in the middle of the log, followed by valid ones, means real corruption, and silently stopping there would discard acknowledged writes. Production engines tell the two apart (Postgres checks the previous-record pointer and page headers) and refuse to start rather than guess.

Deep Dive: Sizing and the Numbers

We use shard 2 from the lesson: 625 order writes per second, each transaction touching one table row and two indexes.

fsync latency sets the commit budget

Rough orders of magnitude for one small fsync; measure yours with pg_test_fsync or fio, because they vary widely:

A consumer SSD reporting 50,000 fsyncs per second is a warning sign. It probably is not flushing its cache.

Group commit is what makes a slow device usable. With a 1 ms fsync, one connection committing serially gets at most 1,000 commits per second. With 64 connections committing at once, each fsync covers many commit records, and the same disk can sustain tens of thousands of commits per second, until CPU or WAL bandwidth limits it. Shard 2's 625 commits per second is easy either way. The latency floor still applies to every single commit: a client never hears "saved" in less than one fsync.

WAL volume: where full-page writes dominate

The raw change records for one order transaction (row, two index entries, commit record) come to roughly 500 bytes. At 625 per second, that is about 0.3 MB per second.

Now add full-page images. Assume the hot set touched within any few minutes is 250,000 pages (2 GB of table and index pages). After every checkpoint, the first change to each of those pages logs the whole 8 KB page.

  • Checkpoint every 5 minutes: up to 250,000 × 8 KB = 2 GB of page images per 300 seconds, about 6.7 MB per second.
  • Checkpoint every 30 minutes: the same 2 GB per 1,800 seconds, about 1.1 MB per second.

At 5-minute checkpoints, page images are about 20 times the size of the actual changes. That surprises most teams the first time they look. You can see it in pg_stat_wal (wal_fpi against wal_records), or per record type with pg_waldump --stats. Longer checkpoint intervals and wal_compression are the two big levers. Both also shrink what replicas must receive and what archives must store.

Recovery time from checkpoint settings

Recovery replays all WAL from the last checkpoint's redo point. In the worst case that is about one full checkpoint interval of WAL, more if the crash hits while a spread checkpoint is still writing. Replay speed depends heavily on whether pages it touches are in memory. Postgres replays in one process, and reading cold pages is the slow part. Assume 100 MB per second as a planning figure and measure your own.

  • Defaults (5 minutes, max_wal_size 1 GB) at about 7 MB per second of WAL: around 2 GB of WAL per cycle. Since max_wal_size caps it near 1 GB, checkpoints trigger early, every couple of minutes. Replay: about 10 seconds.
  • Tuned for less WAL (30 minutes, max_wal_size 8 GB) at 1.4 MB per second: about 2.5 GB per cycle. Replay: about 25 seconds.
  • Over-tuned (2 hours, max_wal_size 64 GB) during a bulk load producing 20 MB per second: up to 64 GB to replay. At 100 MB per second that is 11 minutes, and much longer if replay is reading cold pages from disk.

The middle row is usually the sweet spot: far less WAL than the defaults, and recovery still under a minute. Set the target from the recovery-time objective, then confirm it by killing a test instance under load and timing the restart.

Point-in-time recovery storage

Archived WAL plus base backups let you restore to any second. Assume shard 2 produces about 1.4 MB per second of WAL after tuning, around 120 GB per day.

  • 14 days of WAL archive: about 1.7 TB before compression. WAL often compresses well; how well depends on the data, so measure.
  • Base backups of the 1 TB shard: weekly, keeping two, is 2 TB. Daily, keeping 14, is 14 TB, though incremental backups (native in PostgreSQL 17, and in tools like pgBackRest) cut that sharply.
  • Restore time is base restore plus replay to the target time. With weekly base backups, restoring to day 6 replays about 720 GB of WAL: roughly 2 hours at 100 MB per second. With daily backups, under 20 minutes.

So backup frequency is really a restore-time decision, not a storage decision. Storage is cheap; hours of replay during an incident are not.

Deep Dive: Failure Modes in Production

1. The disk that says yes too quickly

Symptom. After a power cut in a small office deployment, Postgres starts, but orders acknowledged in the last few seconds are missing. A week later, another power cut leaves an index that returns wrong rows.

Mechanism. The SSD has a volatile write cache and no power-loss protection, and it acknowledges cache flushes before data reaches flash. Or a virtual machine's disk is set to a cache mode that ignores guest flushes. fsync returns in microseconds, so the database believes the WAL rule holds. The power cut erases the cache, and with it log records the database already promised, sometimes along with data pages written in the wrong order.

Detect. Before production, run pg_test_fsync: tens of thousands of flushes per second on a device without power-loss protection is not believable. For a real check, run a pull-the-plug test with a tool such as diskchecker.pl, which records acknowledged writes on a second machine and verifies them after power returns.

Fix. Use drives with power-loss protection, or turn off the volatile write cache. Use a safe hypervisor cache mode. In the cloud, trust the provider's block storage semantics, but never a local ephemeral disk as the only copy.

2. A write error that a retry "fixed"

Symptom. Weeks after a storage hiccup, a query returns a row with old data. Checksums flag a page. Nobody remembers any database error.

Mechanism. A transient storage error made a write-back fail during a checkpoint. On older kernels and database versions, the first fsync reported the error, and the database retried the checkpoint. The second fsync succeeded, because the kernel had already dropped the failed dirty pages and cleared the error flag. The checkpoint completed, the WAL before it was recycled, and the lost page write could no longer be redone.

Detect. Kernel logs with I/O errors (dmesg, "Buffer I/O error", "lost async page write") should page someone even when the database looks fine. Enable data checksums (initdb --data-checksums) so damaged pages are detected on read.

Fix. Run a PostgreSQL version that panics on fsync failure, and leave data_sync_retry off. A panic forces crash recovery from WAL, which redoes the lost writes. For anything homegrown, the lesson is the same: never treat a failed fsync as retryable. Crash, and recover from the log.

3. A broken archive fills the WAL disk

Symptom. Writes start failing with "could not write to file pg_wal/…: No space left on device", and the database shuts down. The data volume has plenty of room.

Mechanism. archive_command copies each finished WAL segment to object storage. A rotated credential made it fail on every segment. Postgres must keep every segment until it is archived, so pg_wal grew at the full WAL rate for two days. An abandoned replication slot does the same thing (see Primary-Replica).

Detect. pg_stat_archiver: alert when failed_count rises or last_archived_time is more than a few minutes old. Alert on pg_wal volume use at 50 to 60%, with an estimate of hours left at the current WAL rate.

Fix. Monitor the archive like a production dependency, because it is one. Put WAL on its own volume, sized for a day or more of archive outage at peak WAL rate. Test the archive with real restores, not just successful uploads.

4. Latency spikes every few minutes

Symptom. p99 query latency jumps on a steady rhythm, every 2 to 5 minutes. The log contains "checkpoints are occurring too frequently."

Mechanism. A write-heavy period fills max_wal_size quickly, so checkpoints trigger early and close together. Each one must write out dirty pages fast to finish in time, competing with queries for I/O. Each also restarts full-page writes, so WAL volume jumps right after it, which fills max_wal_size again even sooner. That feedback loop is why the spikes repeat.

Detect. log_checkpoints = on (default in recent versions) shows each checkpoint's trigger, duration and pages written. In pg_stat_bgwriter (or pg_stat_checkpointer in PostgreSQL 17), checkpoints requested by WAL size should be rare next to timed ones.

Fix. Raise max_wal_size so checkpoints are time-driven, keep checkpoint_completion_target at 0.9, and re-check the recovery-time math. Enable wal_compression if CPU allows.

5. Slow fsync, and the cluster starts electing leaders

Symptom. Commit latency p99 goes from 2 ms to 300 ms in the afternoon, with no change in traffic. In the Kubernetes control plane on the same storage class, etcd logs leader elections and "slow fdatasync" warnings.

Mechanism. The cloud volume ran out of burst credits, or a noisy neighbour saturated the shared storage. Every commit waits for one fsync, so commit latency is fsync latency. etcd is stricter: a leader that cannot persist its log in time misses heartbeats, followers call an election, and the cluster churns.

Detect. fsync latency as a first-class metric: etcd's etcd_disk_wal_fsync_duration_seconds, and in Postgres pg_stat_wal sync time with track_wal_io_timing on (moved to pg_stat_io in newer versions). Also watch the volume's burst balance and queue depth.

Fix. Provisioned-IOPS volumes, or local disks with power-loss protection for the log. Put WAL on its own volume so data-file I/O cannot delay commits. For etcd, follow its hardware guidance and keep it off shared, burstable storage.

6. The restart that took 40 minutes

Symptom. After a kernel panic, the machine is back in 2 minutes, but Postgres takes 40 minutes before it accepts connections. Failover did not trigger because this was a single-node analytics database "that doesn't need it."

Mechanism. Someone set checkpoint_timeout to 1 hour and max_wal_size to 100 GB to cut WAL volume during nightly loads. The crash came near the end of a load. Recovery had 80 GB to replay in one process, reading data pages that were no longer in memory after the reboot.

Detect. Measure, before production: crash a staging instance at peak write rate and time the restart. In production, watch the WAL distance since the last checkpoint's redo point; that is the replay you would face right now.

Fix. Choose checkpoint settings from the recovery-time objective. Enable recovery_prefetch (PostgreSQL 15 and later) to overlap page reads during replay. Where minutes matter, run a replica and fail over, so recovery time stops being user-facing.

7. The store that was durable "per process," not per power cut

Symptom. After a host reboot in a power event, a service built on an embedded key-value engine has lost the last several seconds of acknowledged writes. The engine "has a WAL."

Mechanism. The engine wrote every record to its WAL, but with its default sync = false, so records went to the OS page cache and fsync happened later. That survives the process crashing, since the kernel still has the data. It does not survive the kernel or the power going away. The same gap exists with Redis appendfsync everysec, Cassandra's periodic commit log sync, and Kafka's default flush policy. Those last two are designed around replication; a single-node deployment of them has no such backstop.

Detect. Read the durability settings of every store in the request path, and write down what each acknowledgement means: in memory, in the page cache, on one disk, or on a quorum. Kill-and-power-cut tests in staging confirm it.

Fix. Turn on per-write sync where the data matters (WriteOptions.sync = true, appendfsync always, commitlog_sync: batch or group), or make replication the durability mechanism and acknowledge only after a quorum has the write. Either is fine. Not knowing which one you have is the bug.

Deep Dive: Design-Review Checklist

  1. For each store in the write path, what does an acknowledgement mean: in memory, in the page cache, on one disk, or on a quorum? Is it written down?
  2. Which data is allowed relaxed durability (async commit, periodic fsync), and who signed off on the loss window?
  3. Has the storage been checked for honest flushes: power-loss protection, write-cache settings, hypervisor cache mode? Has anyone pulled the plug in staging?
  4. What is the measured fsync latency, p50 and p99, on the production volume, and is it alerted on?
  5. Is the WAL on its own volume, sized for the worst write burst plus a day of archive or replica outage?
  6. What are the checkpoint settings, and what recovery time do they imply at peak write rate? Has a crash-restart been timed?
  7. How much of WAL volume is full-page images, and is wal_compression or a longer checkpoint interval worth it?
  8. Is WAL archived continuously, monitored for failure, and proven by a recent restore to a chosen timestamp?
  9. What is the restore-time objective, and does the base-backup frequency meet it given replay speed?
  10. Are data checksums on, and do kernel I/O errors page someone?
  11. Does anything in the system write its own append-only log? If so, does it fsync directories, distinguish a torn tail from mid-log corruption, and crash on fsync failure?

Deep Dive: Senior Interview Follow-ups

"The WAL is fsynced at commit, but data pages are written later in any order. What stops a page from reaching disk with changes the log doesn't have?"

The WAL rule in the buffer manager. Each page stores the LSN of the last record that changed it. Before writing a dirty page, the database flushes the WAL up to that LSN. So the log is always at least as new as any page on disk, and recovery can redo every change it finds on a page. Without that rule, a page could hold changes from a transaction whose commit record never made it, and redo-only recovery would have nothing to undo them with.

"The log record has a checksum. Why does Postgres also need full-page writes?"

The checksum protects log records. Full-page writes protect data pages. A data page write can tear halfway, leaving a page mixed from old and new versions. A small redo record like "insert this tuple at offset 312" cannot repair a page whose other half is garbage. So after each checkpoint, the first change to a page logs its full image; recovery restores that image and replays from there. InnoDB solves the same problem with its doublewrite buffer instead.

"Kafka doesn't fsync every message by default. Is it less durable than Postgres?"

It uses a different durability mechanism. With acks=all and min.insync.replicas=2, a message is acknowledged once several brokers have it in memory or page cache, so losing one machine loses nothing. It would lose data if all in-sync replicas lost power at once before flushing, which is why they should sit in different zones. Postgres defaults to "on this disk," so a single machine survives power loss, but losing the disk itself needs replication. Each is durable against a different failure; neither is durable against everything without the other.

"How does group commit raise throughput without breaking the 'fsync before ack' rule?"

One fsync makes every byte written to the log before it durable. If 50 commit records are in the WAL buffer when one backend flushes, all 50 are durable after that single fsync, and all 50 clients can be acknowledged. Nobody is told "saved" before their record is on disk; they just share the flush. The cost is that a commit may wait a little for the flush already in progress, so per-commit latency rises slightly while throughput rises a lot.

"Recovery hits a record with a bad checksum in the middle of the log, with valid records after it. What should happen?"

Stop and refuse to start, rather than treat it as the end of the log. A bad record at the tail is expected after a crash: it was being written, so it was never acknowledged. A bad record followed by valid ones means the log itself was damaged after it was written. Truncating there would discard acknowledged commits; skipping it would replay later changes without an earlier one. Either silently corrupts data. The correct move is to fail loudly and restore from a replica or backup plus archived WAL.

"Why can't you just retry a failed fsync?"

Because on Linux the failed pages may already be gone. After a write-back error, the kernel could mark the dirty pages clean and clear the error, so the next fsync reports success with nothing written. A database that retries then believes data is on disk that never got there, and may recycle the WAL that could have redone it. Since 2018 Postgres panics on fsync failure, and recovery replays from the WAL, which still holds the changes. Any system with its own log should do the same.

"An LSM engine also has a WAL. How is its job different from Postgres's?"

In an LSM engine, writes go to the WAL and an in-memory table, then the memtable is written out as an immutable sorted file. Files are never modified in place, so torn data pages are not a problem, and the WAL only needs to cover the current memtable; once flushed, that part of the WAL is deleted. Recovery means replaying a short WAL into a new memtable. The write amplification that Postgres pays in full-page writes and checkpoints, an LSM pays later in compaction, rewriting sorted files as they merge.
