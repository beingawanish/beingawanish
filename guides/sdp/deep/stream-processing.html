Deep Dive: Inside the Mechanism

The lesson names five ideas: keyed state, checkpoint plus rewind, windows, event time, and watermarks. Each one is a concrete data structure or protocol inside the engine. This section uses Apache Flink's names, because Flink exposes the most of the machinery. Kafka Streams and Spark Structured Streaming come at the end, since they make different choices that change how they fail.

Where keyed state lives: key groups

The lesson says "all events for card X go to the instance that holds card X's state." Flink does not map keys to instances directly. It adds a layer in between called key groups.

  • Each key is hashed into one of N key groups, where N is the job's max parallelism.
  • Each parallel instance of the operator (a subtask) owns a contiguous range of key groups.
  • State is stored and checkpointed per key group.

The indirection exists for rescaling. Moving from 8 to 12 subtasks reassigns key-group ranges; it never rehashes individual keys. Each new subtask downloads only the key groups it now owns. The cost is that max parallelism is fixed for the life of the state. You can scale up to it, never past it, without starting state from scratch. Flink derives a default from the initial parallelism, with a floor of 128. Set it explicitly, with headroom, before the first production deploy.

State backends: heap or RocksDB

The state itself sits in a state backend. Flink offers two kinds, and the choice decides your memory profile and your recovery time.

  • Heap (HashMapStateBackend) keeps state as Java objects. Reads and writes are fast. State must fit in memory, and large heaps bring long garbage-collection pauses.
  • RocksDB (EmbeddedRocksDBStateBackend) keeps state in an embedded key-value store on local disk, with a memory cache in front. State can be far larger than memory. Every access serializes and deserializes, so per-event cost is higher. It also supports incremental checkpoints, which upload only the files that changed since the last checkpoint.

The lesson's fraud job has megabytes of state and should use the heap. A sessionization job with millions of open sessions should use RocksDB. Kafka Streams uses RocksDB by default for its state stores. Spark Structured Streaming has a default store kept in executor memory and an optional RocksDB store for large state.

State TTL belongs in the same decision. Keyed state lives until code clears it. A dedupe set of order IDs, or a "last seen" timestamp per device, grows forever unless you configure a time-to-live or register a timer that deletes it. Most unbounded-state incidents come from state nobody planned to expire.

Checkpoints: barriers through the dataflow

"Snapshot all state with the matching log position" sounds simple, until you notice that the job never stops. Different operators are processing different events at every instant. Flink's answer is asynchronous barrier snapshotting, a variant of the Chandy–Lamport distributed snapshot algorithm.

  1. The checkpoint coordinator tells every source to start checkpoint n. Each source records its current offsets and injects a barrier into its output stream. The barrier is a marker that flows with the data.
  2. When an operator receives barrier n on an input, every event before it belongs to checkpoint n, and every event after belongs to n+1.
  3. An operator with several inputs aligns: it waits until barrier n has arrived on all inputs, buffering post-barrier events from the faster ones. Then it snapshots its state and forwards the barrier.
  4. The snapshot is written asynchronously, usually to object storage, so processing resumes immediately.
  5. When every operator and sink has acknowledged, the coordinator marks checkpoint n complete.

The result is a consistent cut. Every operator's state reflects exactly the events before the barrier, and the sources' offsets say where to resume. On failure, the job restores all state from the last completed checkpoint and rewinds each source to its recorded offset.

The knobs, and what each trades:

  • Checkpoint interval. Shorter means less replay after a crash and, with transactional sinks, lower output latency. It also means more upload traffic and more time spent aligning.
  • Minimum pause between checkpoints. Guarantees processing time between them, so a slow checkpoint does not start the next one immediately.
  • Checkpoint timeout and tolerable failed checkpoints. How long one may take, and how many may fail in a row before the job restarts.
  • Unaligned checkpoints. Instead of waiting, the operator forwards the barrier at once and stores the in-flight buffered events as part of the snapshot. Checkpoints stay fast under backpressure. Snapshots get larger, and recovery has more to restore.

A savepoint uses the same mechanism, triggered by a person and kept until deleted. Upgrades, rescaling and migrations go through savepoints: stop with a savepoint, deploy the new code, start from it. For this to work, each stateful operator needs a stable ID (uid() in Flink). Without one, a code change can renumber operators, and the new job will not find its state.

How sinks turn replay into exactly-once output

A checkpoint makes state exactly-once. After a crash, state is as if each event was applied once. Output is different. Anything the sink emitted after the last checkpoint is emitted again on replay. The lesson's duplicate alerts are this. There are three ways to deal with it:

  1. At-least-once with idempotent writes. The sink writes with a deterministic key, such as an upsert on (card_id, window_id). A replayed write overwrites itself. Latency stays low.
  2. Transactional, two-phase commit. The sink opens a transaction per checkpoint, writes into it, pre-commits when the barrier arrives, and commits only when the checkpoint completes. Flink's Kafka sink does this with Kafka transactions, and downstream consumers must read with isolation.level=read_committed.
  3. At-least-once, and the consumer copes. Fine for metrics where a brief double count is harmless, and wrong for alerts and money.

Option 2 has a cost people miss: output becomes visible only at checkpoint completion. With a 30-second interval, a read-committed consumer sees results up to 30 seconds late, even though processing took 200 ms. A fraud alert path should use option 1. Option 2 suits pipelines feeding other pipelines, where correctness matters more than seconds.

Transactional sinks also have a timeout trap. Kafka aborts a transaction that stays open longer than its transaction.timeout.ms, and brokers cap that at transaction.max.timeout.ms (15 minutes by default). If a job fails and takes longer than the timeout to restart, the pre-committed data is gone when it tries to commit. Size the timeout above the checkpoint interval plus your worst realistic recovery time, within the broker's cap. The Exactly-Once Semantics lesson goes further into these protocols.

Watermarks as data, not a clock

A watermark is not computed centrally. It is a special record that flows through the job, like a barrier.

  • Each source partition generates watermarks from the timestamps it sees. The common strategy is bounded out-of-orderness: watermark = largest event time seen − allowed delay.
  • An operator with several inputs takes the minimum of their watermarks. It can only claim "seen everything through 9:05" if every input agrees.
  • When an operator's watermark passes a window's end, it fires the window's event-time timer and emits the result.

The minimum rule has a nasty corollary. One Kafka partition with no traffic stops advancing its watermark, and it holds back the watermark for the entire job. Windows stop closing everywhere. Flink's withIdleness() marks a quiet partition as idle so the others can advance without it. The failure modes section covers what goes wrong in both directions.

Lateness is then handled in three tiers. Events before the watermark are on time. Events after it but within allowed lateness re-fire the window with an updated result; the window's state is kept that long. Events later than that go to a side output for reconciliation, or are dropped and counted.

What windows cost in state

Window types are a modelling choice in the lesson. In the engine they are a state-size choice.

  • A tumbling window holds one accumulator per key per open window.
  • A sliding window of size S and slide D assigns each event to S / D windows. "10 minutes every 30 seconds" puts every event into 20 windows, so it holds 20 accumulators per key.
  • A session window starts as a window per event and merges windows when they overlap within the gap. Merging is more work, and one late event can glue two sessions into one.

For "more than 5 orders in any 10 minutes", the built-in sliding window is not the only option. A keyed process function can keep a small ring of per-minute counts per card, ten buckets, and check the sum on every event. That is one structure per key instead of 20 windows, and it alerts on the triggering event instead of on the next slide boundary.

Kafka Streams and Spark Structured Streaming

Kafka Streams is a library, not a cluster. Your service instances form a consumer group, and each instance processes some partitions. State lives in local RocksDB stores. Every store is backed by a compacted changelog topic in Kafka, which is the durability mechanism; there are no separate checkpoints. Recovery means replaying the changelog into a fresh local store, which can take a long time for large state. num.standby.replicas keeps warm copies on other instances to make failover fast. Re-keying an operation writes through an internal repartition topic, so a groupBy on a new key costs an extra round trip through Kafka. Exactly-once is a setting (processing.guarantee=exactly_once_v2) built on Kafka transactions, and it applies only to Kafka-to-Kafka flows.

Spark Structured Streaming runs a micro-batch per trigger. Each batch first writes the offset range it will read to an offset log in the checkpoint location, then processes it, then writes a commit log entry. On restart, a batch logged but not committed is rerun with the same offsets. State lives in a per-partition state store, versioned per batch. Watermarks are set with withWatermark(), and the output mode (append, update, complete) decides whether a window's result is emitted once after the watermark passes, or on every change. The latency floor is the trigger interval plus batch planning, typically around a second at best. Spark also offers a continuous processing mode, but it supports a limited set of operations.

Deep Dive: Sizing and the Numbers

The running example is the fraud job plus a heavier neighbour: a clickstream sessionization job. Assumptions are stated each time.

Throughput and parallelism

Assume orders peak at 4,000 events/s on sale days, ten times the normal 400/s. Suppose one subtask of the fraud operator handles 20,000 events/s with heap state (a simple keyed count is cheap). The job needs one subtask for throughput. Run at least 4 for fault isolation and headroom, and make the orders topic's partition count a multiple of that, say 12.

The clickstream is bigger: 100,000 events/s at peak, 1 KB each, so 100 MB/s into the job. With RocksDB state, assume one subtask handles 10,000 events/s. That gives 10 subtasks at full load; plan for 20, so peak runs at 50%. The source topic should have at least as many partitions as source subtasks, or some subtasks will sit idle. 40 partitions leaves room to double.

State size and checkpoint size

Fraud job. 200,000 active cards. With a built-in sliding window (10 min, every 30 s), that is 20 windows per card. At an assumed 100 bytes per window entry with overhead: 200,000 × 20 × 100 B = 400 MB. With a ring of ten one-minute counters per card, about 200 bytes per card: 200,000 × 200 B = 40 MB. The modelling choice is a 10x state difference.

Clickstream sessions. 5 million open sessions × 2 KB each (page list, counters, timestamps) = 10 GB of state. Spread across 20 subtasks, that is 500 MB each, which suits RocksDB. A full checkpoint uploads 10 GB. Incremental checkpoints upload only the changed RocksDB files. If 15% of state changes per minute, a 60-second checkpoint uploads about 1.5 GB, which is 25 MB/s of steady object-storage traffic. That is a real line in the network budget.

Recovery time

Recovery has three parts. Write them down separately, because each has its own fix.

  1. Detect and restart: heartbeat timeout plus scheduling. Commonly tens of seconds.
  2. Restore state: 500 MB per subtask from object storage. At 100 MB/s per subtask, about 5 s. With 10 GB on a single instance it would be 100 s. Local recovery (keeping a copy of state on local disk) can skip most of this.
  3. Replay the gap: the events since the last checkpoint, plus the events that arrived during steps 1 and 2.

Step 3 is where headroom matters. Suppose arrival rate λ = 100,000/s, the job's maximum rate μ = 200,000/s, and the outage lasted 60 s (a 30 s average checkpoint age plus 30 s of restart). The backlog is 60 × 100,000 = 6 million events. It drains at μ − λ = 100,000/s, so catching up takes 60 s. At 80% utilization (μ = 125,000/s), the same backlog drains at 25,000/s and takes 240 s. At 95% it takes 20 minutes. The general form:

catch_up_seconds = outage_seconds × λ / (μ − λ)

A streaming job that runs near full capacity in steady state cannot recover in any useful time. Plan for 50–70% utilization at peak.

Choosing the watermark delay from data

Do not guess the delay. Measure lateness: for each event, compute processing time − event time, and look at the distribution. Suppose for orders it is:

PercentileLatenessWatermark delay that covers itWindow results emitted after
p500.3 s1 sWindow end + 1 s
p998 s10 sWindow end + 10 s
p99.945 s60 sWindow end + 60 s
p99.9912 min15 minWindow end + 15 min

Each row is a different product. A 10-second delay means about 1 in 100 events arrives after its window closed. For a per-minute chart that is fine. For a billing aggregate it is not: use a long allowed lateness or a side output, and reconcile. The fraud rule can use the 10-second delay and still re-fire on late events, because the lesson's policy updates the count anyway.

Allowed lateness also costs state. Every window stays in state until watermark + allowed lateness. A 15-minute allowed lateness on one-minute windows keeps about 16 windows per key alive instead of one.

End-to-end latency budget

The lesson's 200 ms path, broken down with assumed values:

  • Producer batching (linger.ms) and broker write with replication: 5–20 ms.
  • Consumer fetch wait (fetch.max.wait.ms when traffic is light) and network: 5–100 ms.
  • Network buffers between operators: Flink flushes buffers on a timeout (execution.buffer-timeout, 100 ms by default), so a quiet stream can wait that long at each exchange.
  • Operator work: under 1 ms for a counter.
  • Sink write: 5–50 ms.

Two things can add far more. A transactional sink adds up to a full checkpoint interval. A window result waits for its watermark, so it adds the watermark delay plus whatever is left of the window. If the product needs a sub-second alert, check that neither sits on the alert's path.

Deep Dive: Failure Modes in Production

1. The dashboard that froze at 3 AM

Symptom. The orders-per-minute chart stops updating overnight. The job is healthy, consumer lag is zero, and events are flowing.

Mechanism. The orders topic has 12 partitions, keyed by region. At 3 AM one region has no orders, so its partition receives nothing and its watermark stops moving. The window operator's watermark is the minimum of its inputs, so it stops too. No window can close, so no results come out.

Detect. Watermark lag: wall clock minus the operator's current watermark (Flink reports currentOutputWatermark per operator). Alert when it grows past a few times the configured delay. Per-partition event rates show one at zero.

Fix. Configure idleness on the source (withIdleness(Duration.ofMinutes(1))), so a quiet partition stops holding the watermark back. Know the trade: when the idle partition wakes up, its first events may already be behind the advanced watermark and count as late. Pair idleness with allowed lateness or a side output for the paths that care.

2. One phone from the future

Symptom. From mid-morning, the late-events counter jumps and the dashboard drops nearly every event. Totals for the day come out at a fraction of the real numbers.

Mechanism. A client with its clock set a year ahead sent events timestamped next year. Bounded out-of-orderness takes the maximum event time seen, so that partition's watermark jumped forward a year. Every normal event behind it became "late" and was dropped by the late-data policy. Event time trusts timestamps, and a single bad one can poison the watermark.

Detect. Max event time minus wall clock, per partition. Any positive value beyond a small tolerance is suspicious. Flink's late-record counter (numLateRecordsDropped) jumping from near zero. Watermark lag going negative.

Fix. Never trust client timestamps raw. Clamp event time to the ingest timestamp plus a small tolerance, or reject and side-output events too far ahead. Use broker or server receive time as the bound. Keep both timestamps on the event, so you can reprocess with a corrected rule.

3. The restart loop under load

Symptom. During a sale, the job restarts every 20 minutes. Each restart replays more data, lag grows, and output goes quiet for minutes at a time.

Mechanism. A slow sink caused backpressure. Buffers filled, so barriers queued behind data and alignment took minutes. Checkpoints began to time out. After the tolerated number of failed checkpoints, the job restarted from the last good one, which was now old. The replay added more load, which caused more backpressure. The system was spending its capacity re-doing work.

Detect. Checkpoint duration and alignment time trending up. Backpressure metrics (backPressuredTimeMsPerSecond high on the operators upstream of the slow one, busyTimeMsPerSecond high on the slow one). Checkpoint failure count rising before each restart.

Fix. Treat the slow operator first: batch sink writes, add sink parallelism, or put the sink behind an async I/O operator with a bounded queue. Enable unaligned checkpoints so snapshots complete under backpressure. Raise tolerable checkpoint failures so a short spike does not cause a restart. And keep the utilization headroom from the sizing section. The Backpressure lesson covers the signal itself.

4. The merchant that saturated one subtask

Symptom. A per-merchant revenue job falls behind on a flash-sale day. Eleven subtasks are idle; one is at 100% busy. Adding parallelism changes nothing.

Mechanism. Keyed routing sends all events for one key to one subtask. One merchant running a flash sale produced 60% of the events. More subtasks do not help, because the key cannot be split. This is the stream form of the hot-key problem from Sharding and the skewed reducer in MapReduce.

Detect. Per-subtask records-in rate and busy time: one outlier. Consumer lag concentrated on the partitions that carry that key.

Fix. Two-phase aggregation. First key by (merchant, hash(order_id) mod 16) and pre-aggregate per short window; then key by merchant and sum the 16 partials. The second stage sees 16 events per merchant per window instead of thousands. Flink SQL has this built in for some aggregations (local-global aggregation and split-distinct). This works for associative aggregates; it does not work for per-key logic that must see every event in order, such as a state machine.

5. State that never stops growing

Symptom. Over six weeks, checkpoint size climbs from 2 GB to 400 GB. Checkpoints take longer each week, local disks fill, and finally a restore takes 40 minutes.

Mechanism. A dedupe step keeps every order ID it has seen, so replayed events are dropped. Nobody gave the state a TTL. Each new key adds a few dozen bytes, forever. A similar leak comes from keying by something unbounded, like session ID, with no timer to clear state when the session ends.

Detect. Checkpoint size as a time series. Healthy state plateaus; a leak grows in a straight line with traffic. RocksDB's estimated number of keys, if exposed.

Fix. Give every piece of keyed state a lifetime: state TTL set to the longest replay or duplicate window you need (for dedupe, a bit longer than the producer's retry horizon), or an event-time timer that clears state when a session or window can no longer change. Fixing a leak in a running job may need a savepoint, a code change, and a one-time cleanup, so add the TTL on day one.

6. The deploy that reset every counter

Symptom. After a routine deploy, fraud alerts stop for 10 minutes, then resume. Investigation shows the ring's first six orders after the deploy did not trigger an alert.

Mechanism. The deploy pipeline cancelled the job and started the new version from the latest Kafka offsets, not from a savepoint. Or it did use a savepoint, but a refactor changed the operator graph, the stateful operator had no explicit uid(), and the new job could not match it. The deploy pipeline was configured to allow unmatched state, so it started empty. Every card's count was zero again.

Detect. Job startup logs say whether the job was restored from a savepoint and how much state was matched. A state-size metric that drops to near zero right after a deploy. Fraud alert rate dropping right after each release.

Fix. Deploy only through stop-with-savepoint, then start from it. Give every stateful operator a stable uid(). Do not allow non-restored state unless a human approves it for that release. Test state compatibility in CI by restoring the previous release's savepoint into the new build. Schema changes to state types need the serializer to support evolution.

7. The rolling restart that took all afternoon

Symptom. A Kafka Streams service with large state is restarted one pod at a time. Each pod takes 30 minutes to become useful, the group rebalances again with every pod, and processing is degraded for hours.

Mechanism. When a pod leaves, its partitions move to other instances, which must rebuild those state stores from the changelog topics before they can process. When the pod comes back, partitions move again. Without standby replicas, every move replays changelogs. With eager rebalancing, every move also pauses the whole group.

Detect. Restoration metrics (records restored, restore time per store). Rebalance count during deploys. Lag rising on every partition each time a pod restarts.

Fix. Set num.standby.replicas to at least 1 so a warm copy is ready. Use static membership (group.instance.id) so a quick restart does not trigger a rebalance at all. Recent versions warm up state on the new owner before moving the active task (KIP-441), which helps if you let it finish. Keep state stores on persistent volumes, so a restarted pod reuses its local RocksDB instead of rebuilding it.

Idempotent upserts are the default worth reaching for. They need only a deterministic key, which windowed results naturally have: (key, window_start). Use transactions where the output is itself a log that others consume, and where an extra few seconds do not matter.

Choosing the notion of time

  • Event time for anything about what users did: fraud, billing, behaviour features, funnels. You must handle lateness and clock problems.
  • Ingestion time (the broker or gateway's receive timestamp) when client clocks are untrustworthy and the question can tolerate network delay inside its windows. It is monotonic per partition and immune to the phone from the future.
  • Processing time for operational questions about the pipeline itself: throughput, lag, rate limits. Never for business metrics.

A common sound design records all three on every event, uses event time for windows, and clamps it with ingestion time.

Stream joins and their state

Joins are where streaming state gets expensive, so it is worth naming the three kinds.

  • Stream–table (enrichment) join. Each order looks up the current customer record. The table side is kept as keyed state, often fed by CDC. State size is the table size. The catch is timing: a customer updated a second before the order may not have arrived yet.
  • Interval join. Orders joined to payments within 30 minutes of each other. Each side buffers its events for the interval, so state is rate × interval × event size for both sides.
  • Unbounded join. Join any two events ever seen with the same key. State grows forever unless you set a TTL. In SQL engines this is the default for a plain JOIN between two streams, so check the plan.

Deep Dive: Design-Review Checklist

  1. What is the staleness budget for each output, and is per-event streaming actually required, or would a one-minute micro-batch do?
  2. What is the key for each stateful operator, what are its ten largest values at peak, and what happens on the subtask that owns the largest?
  3. How big is state per key and in total, including window multiplication and allowed lateness? Which state backend, and why?
  4. Does every piece of keyed state have a lifetime: a TTL or a timer that clears it?
  5. Which timestamp drives windows? How are client clocks clamped? What is the measured lateness distribution, and which percentile does the watermark delay cover?
  6. What happens to a late event on each output: dropped, re-fired, or side-output? Who decided, and is the dropped count monitored?
  7. How do idle partitions affect the watermark? Is idleness configured, and what does it do to late events?
  8. What are the checkpoint interval, timeout and tolerable failures? What does checkpoint duration look like under peak backpressure?
  9. For each sink: what happens on replay? Is it idempotent on a deterministic key, transactional, or does a consumer dedupe?
  10. What is the recovery time budget, broken into detect, restore and catch-up? What peak utilization makes catch-up fit?
  11. How is the job deployed: stop-with-savepoint, stable operator IDs, a CI test that restores the previous savepoint?
  12. How far back can the source be replayed (topic retention), and is that longer than the longest outage plus the longest backfill you would want?

Deep Dive: Senior Interview Follow-ups

"How does Flink take a consistent snapshot without stopping the job?"

Sources inject barriers into the stream and record their offsets. Each operator, on receiving the barrier from all of its inputs, snapshots its state asynchronously and forwards the barrier. Everything before the barrier is in the snapshot; everything after is not. When every operator and sink has acknowledged, the checkpoint is complete. Recovery restores every operator's state and rewinds every source to the recorded offsets, which gives a consistent cut across the whole job. Under backpressure, alignment is slow, so unaligned checkpoints forward the barrier at once and include in-flight buffers in the snapshot.

"You turned on the exactly-once Kafka sink and alert latency went from 200 ms to 30 seconds. Why?"

A transactional sink writes each checkpoint's output inside a Kafka transaction and commits only when the checkpoint completes. Consumers reading with read_committed cannot see uncommitted records, so they see results only at checkpoint boundaries. With a 30-second interval, that is up to 30 seconds of delay. For alerts, use an at-least-once sink that writes idempotently on (card_id, window_id), or have the alert consumer dedupe. Keep transactions for pipelines that feed other pipelines.

"One Kafka partition stops receiving events. What happens to your windows, and what is the trade-off in fixing it?"

The operator's watermark is the minimum across its inputs. The silent partition's watermark stops, so the operator's watermark stops, and no event-time window closes anywhere in the job. Marking the source idle after a timeout lets the other partitions advance the watermark without it. The trade-off: when the idle partition resumes, its first events may be behind the watermark and treated as late. So idleness has to come with an allowed-lateness or side-output policy for the outputs that cannot lose those events.

"How do you rescale a stateful job from 8 to 32 subtasks, and what limits you?"

Take a savepoint, then restart the job at the new parallelism from it. Flink redistributes key-group ranges, so each new subtask loads the key groups it now owns. Keys are never rehashed individually. The hard limit is max parallelism, which fixes the number of key groups: you cannot go past it without discarding state. The practical limits are the source partition count, since extra source subtasks would be idle, and the restore time, since every subtask downloads its share of state at startup.

"Your watermark is 10 seconds. How did you choose that, and how do you know it is right?"

From a measured lateness distribution: processing time minus event time, per event, over normal and bad days. A 10-second delay might cover the 99th percentile. Then I check the product consequences: about 1% of events will arrive after their window closes, so each output needs a late policy. I monitor the late-event rate and the watermark lag continuously. If late events rise, either the network got worse or a client clock went bad, and both need attention. It is not a number you set once.

"Why does a streaming job need spare capacity in steady state?"

Because recovery is replay. After an outage of T seconds, the job has T × λ events of backlog, and it can drain them only at μ − λ, its spare capacity. Catch-up time is T × λ / (μ − λ). At 50% utilization, catching up takes as long as the outage. At 95%, it takes nineteen times as long, and any further hiccup compounds. The same headroom absorbs traffic spikes and the extra cost of checkpoints. A job sized to 100% of peak has no recovery story.

"Kafka Streams or Flink for the fraud job? Defend the choice."

For the fraud job as described, Kafka Streams. Input and output are Kafka topics, state is tens of megabytes, and the logic is a keyed counter with a simple window. Running it as a library in a normal service means normal deploys and no new cluster to operate. I would move to Flink if state grew into hundreds of gigabytes, where changelog restoration becomes slow, if I needed non-Kafka sources or sinks with exactly-once, or if the event-time logic needed idleness handling, side outputs and allowed lateness that Kafka Streams handles less directly.

"How do you join an order stream with a customer table that keeps changing?"

Feed the customer table into the job as a changelog stream, typically from CDC, and keep it as keyed state. Each order looks up the current record for its customer. The subtle part is time. If the customer's update and the order happen a second apart, they may arrive in the other order. If correctness needs the version that was current at the order's event time, use a temporal (versioned) join that keeps recent versions and waits for the watermark. Otherwise accept "latest known" and document it. Either way, the table state is as large as the table, so it sets the state backend choice.
