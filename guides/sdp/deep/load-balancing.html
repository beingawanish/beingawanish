Deep Dive: Inside the Mechanism

The lesson gives the balancer four jobs. Each job is a small state machine with timers and thresholds. Those numbers, more than the product you pick, decide whether a bad server costs six seconds or eleven minutes, and whether a deploy is invisible or a spike on the error graph.

One backend's life inside the balancer

For every backend, the balancer keeps a little record: its address, its weight, its current in-flight count, recent check results, and a state. The states and the transitions between them are the same in every serious balancer, though the names vary.

The three inputs are separate on purpose:

  • Active probes (the probe loop) run on a timer whether or not traffic flows. In HAProxy the knobs are inter (interval), fall (failures to mark down) and rise (successes to mark up). The gap between fall and rise is hysteresis. It stops a server that passes one probe in three from flapping in and out.
  • Passive checks watch real responses. Envoy calls this outlier detection: by default, 5 consecutive 5xx responses eject a host for a base time of 30 seconds, and the ejection time grows each time the same host is ejected again. HAProxy does it with observe layer7 plus error-limit and on-error. Open-source nginx has passive checks only (max_fails and fail_timeout on the upstream server, defaulting to 1 failure and 10 seconds); active health checks are part of NGINX Plus.
  • Administrative state comes from the deploy system: drain this server, add that one. In HAProxy, the runtime API's set server store_web/web2 state drain. In AWS, deregistering a target. In Kubernetes, the pod leaving the Service's endpoints.

The safety valves: when "unhealthy" is wrong

The lesson's 3:07 AM incident, where a deep check removed every server, has a mechanical defence built into good balancers. They refuse to believe that everything is broken.

  • Envoy's panic threshold (default 50%). If fewer than half the hosts in a cluster are healthy, Envoy stops trusting health and balances across all hosts. Some requests fail, but most succeed, which beats sending them all nowhere.
  • Envoy's max_ejection_percent (default 10%) caps how much of the cluster passive outlier detection may eject at once.
  • AWS load balancers fail open. If every target in a group is unhealthy, they route to all targets anyway.

Know which behaviour your balancer has. "Remove everything and return 503" and "ignore health and try everything" are both valid choices. They produce very different outages.

Algorithms, one level deeper

Round-robin and least-connections are the textbook pair. Production balancers have a few more, each answering a specific weakness.

  • Smooth weighted round-robin (nginx's weighted mode). Weights 5, 1, 1 give the sequence a a b a c a a rather than a a a a a b c, so the heavy server never receives a burst.
  • Least outstanding requests. Least-connections, but counting requests rather than TCP connections. That matters with keep-alive and HTTP/2, where one connection carries many requests. AWS ALB offers it as an option next to round-robin.
  • Power of two choices (P2C). Pick two backends at random and send to the one with fewer in-flight requests. It sounds like a shortcut. It is actually better than strict least-connections when there are many balancer nodes. Each node sees only its own in-flight counts, so strict least-connections makes all of them pile onto the same "emptiest" server at the same moment. Random pairs break that herd, and the theory shows the maximum load is still close to the best possible. Envoy's LEAST_REQUEST uses P2C by default.
  • Latency-weighted (EWMA). Score each backend by an exponentially weighted moving average of its response time, multiplied by its in-flight count. Linkerd and Finagle use this family. It reacts to a slow server before its queue grows.
  • Hashing. A ring hash (the consistent hashing ring) or Maglev hashing, which builds a fixed-size lookup table (65,537 entries in Google's paper) so that every balancer node maps the same key to the same backend with no shared state. Plain hashing can overload one backend when a key is hot. "Consistent hashing with bounded loads" caps each backend at, say, 1.25 times the average and spills over to the next one.

Most balancers also offer slow start. A new or recovered backend's weight ramps from near zero to full over a set time (HAProxy's slowstart, Envoy's slow start config, ALB's slow_start.duration_seconds). Without it, least-connections sends a burst to the server with the emptiest queue, which is exactly the one with the coldest cache.

What L4 and L7 actually do with your packets

An L4 balancer sees TCP or UDP. It picks a backend when a connection opens and then forwards that connection's packets. Two forwarding styles:

  • NAT / full proxy. The balancer rewrites addresses in both directions, so replies come back through it. Simple, works anywhere, and the balancer sees all bytes both ways.
  • Direct server return (DSR). The balancer forwards only the incoming packets. The backend replies straight to the client from the shared virtual IP, which it holds on a loopback interface. Responses are usually much larger than requests, so the balancer handles a fraction of the bytes. The cost is backend network configuration and no visibility into responses.

Large L4 tiers scale out with ECMP: the routers spread packets for one virtual IP across many balancer nodes by hashing each flow's addresses and ports. If a node is added or removed, some flows rehash onto a different node. That node has no record of the connection. Consistent hashing like Maglev means it picks the same backend anyway, so most connections survive. Google's Maglev, Facebook's Katran (built on XDP/eBPF) and GitHub's GLB are public designs of this kind.

An L7 balancer terminates the client's connection, parses HTTP and opens its own connections to backends. So there are always two connections per request path. The consequences:

  • It can balance per request, which is the only way to spread HTTP/2 and gRPC traffic. Those protocols multiplex many requests over one long-lived connection, and an L4 balancer would place that whole connection on one backend forever.
  • It keeps a pool of keep-alive connections to backends. Their timeouts must line up with the backends' (see failure mode 1).
  • It can retry a failed request on another backend. That is powerful and dangerous (see failure mode 5).
  • It holds TLS state and HTTP buffers per connection. It is the more expensive layer to run.

Draining, step by step

Draining sounds like one action. On the wire it is several, and each protocol needs a different signal.

  1. Stop new work. The balancer marks the backend Draining and picks other backends for new requests.
  2. Close idle keep-alive connections politely. For HTTP/1.1, the backend adds Connection: close to its next response on each connection. For HTTP/2, it sends a GOAWAY frame naming the last stream it will process. Clients open new connections, which land on other backends.
  3. Let in-flight requests finish. Up to a deadline: deregistration_delay on AWS target groups, which defaults to 300 seconds, or the pod's termination grace period in Kubernetes.
  4. Tell long-lived streams. SSE and WebSocket connections will not end by themselves. The server sends a reconnect hint and closes them, ideally spread over the drain window.
  5. Exit. Anything still open at the deadline is cut.

In Kubernetes, step 1 and the shutdown signal happen at the same time on different paths. The kubelet sends SIGTERM to the pod. In parallel, the endpoint removal travels to kube-proxy, ingress controllers and external balancers, which can take seconds. If the app stops accepting at SIGTERM, it refuses requests that balancers are still sending. The common fix is a preStop hook that sleeps for a few seconds before SIGTERM arrives, so the removal can propagate first.

The lesson's design as HAProxy config

defaults
    mode http
    timeout connect 3s
    timeout client  60s
    timeout server  30s
    timeout http-keep-alive 10s

backend store_web
    balance leastconn
    option httpchk
    http-check send meth GET uri /healthz/ready
    http-check expect status 200
    # probe every 2 s; 3 failures mark down, 2 successes mark up;
    # ramp new servers over 30 s; mark down after 10 consecutive real errors
    default-server inter 2s fall 3 rise 2 slowstart 30s observe layer7 error-limit 10 on-error mark-down
    server web1 10.0.1.11:8080 check
    server web2 10.0.1.12:8080 check
    server web3 10.0.1.13:8080 check

Every number in that block is a decision. The next section shows how to pick them.

Who balances the balancer, mechanically

  • Active/passive pair with a floating IP. Keepalived runs VRRP between the two nodes. The active node holds the virtual IP and sends advertisements every second or so. When they stop, the standby claims the IP and announces it with gratuitous ARP. Existing TCP connections break unless connection state was synchronised (conntrackd for L4). For an L7 proxy, they break regardless and clients reconnect.
  • Active/active with ECMP and BGP. Each node announces the same virtual IP to the routers. A node that fails stops announcing and the routers drop it. All nodes carry traffic, so none sits idle.
  • Anycast. The same address is announced from many sites. Internet routing picks the nearest. A site failure withdraws its route and traffic shifts to the next nearest.
  • Managed balancers do some of this for you. They run as fleets of nodes, which is why their DNS names resolve to several changing addresses. Clients that cache one IP forever (old JVM DNS caching is the classic) defeat it.

Deep Dive: Sizing and the Numbers

Detection time and its price

The worst-case time to mark a server down is about inter × fall + timeout. With 2 s, 3 and a 1 s probe timeout, that is about 7 seconds. In the lesson's replay it came to about 6.

Price the difference. One server of six takes one-sixth of 4,000 rps, about 667 rps:

  • Removed in 6 s: about 4,000 failed or slow requests.
  • Removed by hand in 11 minutes: about 667 × 660 ≈ 440,000.

Faster detection is not free. Lower inter and fall mark servers down on brief hiccups: a 2-second GC pause can fail two probes. Each false removal shifts load onto the others, which can then hiccup in turn. A reasonable range for web backends is 1 to 5 s intervals with fall 2 to 3. Passive checks cover the fast cases, because real traffic samples a server hundreds of times per second, while probes sample it once every few seconds.

What the health checks themselves cost

Every balancer node probes every backend. A managed balancer may run many nodes across zones, and each one probes independently.

  • 10 balancer nodes × 200 backends ÷ 2 s interval = 1,000 probes per second across the fleet.
  • Each backend sees 10 / 2 = 5 probes per second. Cheap, if the probe is shallow.
  • If each probe runs two database queries "to be thorough", that is 2,000 queries a second hitting the database for health alone, at all times.

Deep checks are expensive as well as dangerous. A shallow readiness check, with dependency health reported separately to monitoring, costs almost nothing.

Least-connections and the fast-failing server

Least-connections assumes a busy server is a slow server. A broken server can be very fast. Suppose server 3 starts returning a 500 error in 1 ms, while healthy servers take 50 ms.

Least-connections equalises in-flight counts. By Little's law, in-flight = rate × latency. Equal in-flight counts therefore mean each server's request rate is inversely proportional to its latency. Server 3 is 50x faster, so it gets 50x the rate of each healthy server:

  • Share for server 3: 50 / (50 + 5 × 1) = 50 / 55 ≈ 91% of all traffic.

The algorithm that protects you from a slow server sends nearly everything to a broken one. Round-robin would have sent it one-sixth. This is why least-connections must be paired with passive error detection: ejection on consecutive 5xx catches it within milliseconds of real traffic. Active probes may miss it entirely, because the health endpoint might still return 200.

Connection reuse and ephemeral ports

An L7 balancer opens connections to backends from its own IP. Each connection to one backend IP and port needs a distinct local port. Linux's default ephemeral range is 32768 to 60999, which is 28,232 ports. A closed connection holds its port in TIME_WAIT for 60 seconds on the side that closed first.

  • Without keep-alive, sustainable new connections per backend ≈ 28,232 / 60 ≈ 470 per second from one balancer IP.
  • The lesson's fleet sends about 667 rps to each backend. One connection per request would exhaust ports within about a minute of peak.

With keep-alive, a few dozen connections per backend carry the same load. So upstream keep-alive is not a tuning nicety. Without it, the balancer fails at a traffic level well below its CPU limit. The symptoms are connect errors such as "cannot assign requested address" on the balancer.

Sizing drain windows

  • Short API calls. Drain timeout above the p99.9 request duration, plus the propagation delay. If p99.9 is 2 s and endpoint removal takes up to 5 s, 15 to 30 s is plenty. AWS's default of 300 s makes a 48-server rolling deploy crawl for no benefit.
  • Uploads and reports. Long requests set the floor. Either raise the drain window for that route, or move long work to a background job so the request returns quickly.
  • Streams. A server holding 50,000 SSE streams must not close them all at once. Spread the closes across 30 s and the survivors receive about 50,000 / 30 ≈ 1,700 reconnects a second. Close them together and they get 50,000 in one second, each paying TLS and auth. Client-side jitter on reconnect spreads them further.

TLS termination cost

Full TLS handshakes dominate an L7 balancer's CPU, not request parsing. Two levers matter most:

  • Session resumption (tickets or session IDs, and TLS 1.3 resumption) lets returning clients skip the expensive key exchange. A high resumption rate cuts handshake CPU sharply.
  • Certificate key type. ECDSA certificates are much cheaper to sign with than RSA-2048 on the server side. Measure on your hardware with openssl speed rather than trusting a remembered number.

The practical sizing rule: estimate new connections per second (not requests), multiply by the measured cost of a full handshake times the share of non-resumed connections, and keep that below about half the balancer's cores. Long-lived keep-alive from clients helps here too.

Deep Dive: Failure Modes in Production

1. The steady trickle of 502s

Symptom. A low, constant rate of 502 Bad Gateway errors, around 0.01% to 0.1% of requests. They are worse at low traffic, oddly. Backend logs show no errors at all.

Mechanism. A keep-alive timeout race. The backend closes idle connections after 5 seconds; Node.js's default keepAliveTimeout is 5,000 ms. The balancer keeps idle upstream connections for 60 seconds, the ALB default idle timeout. At second 5, the balancer sends a request on a connection the backend is closing at that instant. The request gets a reset, and the balancer returns 502. It never reached the application, so nothing is logged there. Low traffic makes it worse because more connections sit idle long enough to hit the race.

Detect. 502s in balancer logs with zero bytes received from the backend. On AWS, the ELB 502 count rising while target 5xx stays flat. Errors cluster on connections that were idle for about the backend's timeout.

Fix. The backend's keep-alive timeout must be longer than the balancer's idle timeout, so the balancer always closes first. For a 60 s balancer timeout, set the backend to 65 s or more (in Node, raise headersTimeout above it as well). Allow idempotent requests to retry once on a connection reset.

2. The broken server that took all the traffic

Symptom. One server's database credentials expire. Instead of losing one-sixth of traffic, the site's error rate jumps to around 90%.

Mechanism. The sizing section's black hole. The broken server fails each request in 1 ms. Least-connections sees it as the least busy server and sends it most new requests. The health endpoint only checks the process, so it still returns 200 and active probes never remove it.

Detect. Per-backend request rate: one backend at many times its peers. Per-backend error rate near 100% for that backend. Response time for that backend far below the others, which is the giveaway.

Fix. Passive outlier detection on consecutive 5xx, so real traffic ejects it in milliseconds. Cap ejection with a max percentage so it cannot remove the fleet. Count errors into the selection score, as EWMA balancers do. And make the readiness check include the server's own critical local resources, like whether it can load its credentials, without probing shared dependencies.

3. gRPC traffic that never spreads

Symptom. A gRPC service scales from 4 to 12 pods. The original 4 stay at 80% CPU; the new 8 sit idle. Kubernetes reports all 12 as ready.

Mechanism. A Kubernetes ClusterIP Service balances at L4: it picks a pod per connection. Each gRPC client opens one HTTP/2 connection and multiplexes every call over it for hours. The callers' connections were placed when there were 4 pods, and no new connections are being opened.

Detect. Per-pod request rate wildly uneven while per-pod connection counts are tiny. Connection ages in hours.

Fix. Balance per request at L7: a mesh sidecar, an L7 proxy, or gRPC's client-side balancing with a headless Service so clients see every pod. Or set a server-side maximum connection age (gRPC's MaxConnectionAge) so clients reconnect periodically and re-spread.

4. Errors at every deploy, despite draining

Symptom. Draining is configured, yet every rolling deploy produces a burst of connection-refused or 502 errors lasting a few seconds per pod.

Mechanism. On Kubernetes, SIGTERM reaches the pod at the same time the endpoint removal starts travelling to kube-proxy and the ingress. The app stops listening immediately on SIGTERM. For the next few seconds, balancers that have not yet heard about the removal keep sending it requests, which are refused.

Detect. Errors aligned to pod termination timestamps, lasting about the endpoint propagation delay. Ingress logs show upstream connect failures to the terminating pod's IP.

Fix. A preStop sleep of 5 to 15 seconds, so the pod keeps serving while removal propagates. Then handle SIGTERM gracefully: stop accepting, finish in-flight work, exit. Keep the grace period longer than the sleep plus the longest request.

5. The retry storm

Symptom. A backend tier slows down briefly. Within a minute, its request rate is several times normal and it collapses completely. Clients see timeouts everywhere.

Mechanism. Retries at every layer multiply. The browser retries 3 times, the edge balancer retries each attempt 3 times, the service's client library retries 3 times. One user action becomes up to 3 × 3 × 3 = 27 attempts at the bottom. And retries arrive exactly when the backend is weakest.

Detect. Backend request rate rising while user traffic is flat. The ratio of upstream attempts to downstream requests climbing well above 1. Balancer retry counters (Envoy's upstream_rq_retry) spiking.

Fix. Retry at one layer only, usually the one closest to the caller with the best context. Use a retry budget instead of a fixed count: Envoy's retry budget allows retries up to a percentage of active requests (20% by default when a budget is configured). Retry only idempotent requests, with backoff and jitter. Combine with a circuit breaker, so a failing tier gets rest instead of more load.

6. The server that flaps

Symptom. A backend toggles between up and down every few seconds. Its peers' load swings with it. Logs show a ladder of "server down" and "server up" lines.

Mechanism. The server is degraded, not dead. It fails one probe in two or three, perhaps from periodic GC or a saturated thread pool. With fall 1 rise 1, each single result flips its state. Each time it comes back, it receives a burst of traffic, which pushes it into failing again.

Detect. State-change events per backend per minute. Any backend with more than a couple of transitions an hour deserves a look.

Fix. Hysteresis: fall 3 and rise 2 or more. Slow start on recovery, so a returning server ramps up rather than taking a burst. Growing ejection time on repeat offenders, as Envoy does. Then fix the server: flapping is a symptom of something else.

7. One zone overloaded, two zones idle

Symptom. After an auto-scaling event, servers in one zone run hot while servers in other zones are cool. Latency is bad for about a third of users.

Mechanism. The balancer's nodes are per zone, and DNS spreads clients roughly evenly across those nodes. With cross-zone balancing off, each node sends traffic only to backends in its own zone. If zone A has 2 backends and zones B and C have 4 each, each zone A backend takes twice the load. On AWS, cross-zone balancing is on by default for ALB but off by default for NLB.

Detect. Per-zone request rate per backend. Uneven backend counts per zone in the target group.

Fix. Enable cross-zone balancing (accepting cross-zone data transfer cost where it applies). Or keep backend counts equal per zone, which auto-scaling groups can enforce with zone balancing. Or use zone-aware routing that prefers the local zone only while it has enough capacity, as Envoy's zone-aware routing does.

Deep Dive: Design-Review Checklist

  1. What does the health endpoint test? Could one shared dependency failing make every backend fail it?
  2. What are the probe interval, fall, rise and timeout, and what worst-case detection time do they give?
  3. Are passive checks on, and what caps how much of the fleet they can eject?
  4. What does the balancer do when every backend is unhealthy: fail closed, fail open, or panic mode?
  5. Which algorithm, and what happens with a server that fails fast? With a new, cold server?
  6. Is balancing per request or per connection, and does any traffic use long-lived multiplexed connections (HTTP/2, gRPC, WebSocket)?
  7. Is the backend keep-alive timeout longer than the balancer's idle timeout?
  8. How does draining work end to end: stop new work, close keep-alives, finish in-flight, warn streams? Is there a preStop delay for propagation?
  9. Is the drain timeout set from measured request duration, not left at a default?
  10. Which layer retries, how many times, and with what budget? Are only idempotent requests retried?
  11. How is the balancer itself redundant, and what happens to open connections when it fails over?
  12. Is cross-zone balancing configured to match how backends are spread across zones?

Deep Dive: Senior Interview Follow-ups

"Least-connections is the better default. When does it make things worse?"

When a server fails fast. Least-connections equalises in-flight counts, and in-flight = rate × latency, so a server answering errors in 1 ms while others take 50 ms gets about 50x the rate of each healthy server. In a fleet of six that is around 91% of all traffic. It also herds: many balancer nodes with local counts all pick the same emptiest server. The fixes are passive outlier detection on 5xx, power-of-two-choices instead of a global minimum, and slow start for new servers.

"Why do you see 502s when the backend logs show no errors?"

The request never reached the application. The usual cause is a keep-alive race: the backend closes an idle connection at the same moment the balancer reuses it. With Node's 5 s default against a 60 s balancer idle timeout, that happens constantly at low volume. Make the backend's timeout longer than the balancer's, so the balancer always closes first. Other causes are a backend crashing mid-response or the balancer running out of source ports when upstream keep-alive is off.

"We scaled our gRPC service and the new pods get no traffic. Why?"

gRPC multiplexes all calls over a long-lived HTTP/2 connection, and a Kubernetes ClusterIP Service balances at L4, once per connection. The existing clients' connections stay on the old pods. Balance per request: an L7 proxy or mesh, or gRPC client-side balancing against a headless Service. Server-side maximum connection age also helps, by making clients reconnect and re-spread over time.

"Strict least-connections or power of two random choices?"

With one balancer, strict least-connections is fine. With many balancer nodes, each sees only its own in-flight counts, and they all pick the same minimum at once, which overloads it. Picking two at random and taking the less loaded breaks that synchronisation. The theory shows two choices already bring the maximum load close to optimal, and it costs O(1) per decision. That is why Envoy's least-request balancer uses P2C by default.

"How does an L4 tier scale beyond one machine without breaking connections?"

Routers spread flows for one virtual IP across many L4 nodes with ECMP. When a node joins or leaves, some flows hash to a different node that has no state for them. If every node uses the same consistent hash, such as Maglev's lookup table, that new node picks the same backend and the connection continues. Connection tracking handles the usual case; consistent hashing handles the change. DSR reduces load further by letting backends reply to clients directly.

"How long should the drain timeout be?"

Longer than the slowest request you want to complete, plus the time for the removal to propagate to every balancer. For a JSON API with a p99.9 of 2 s, 15 to 30 s. The 300 s AWS default makes rolling deploys slow for no gain. Long uploads either get a longer window on their route or move to background jobs. Streams are closed deliberately over the window, with client reconnect jitter, so the survivors receive a steady trickle rather than a reconnect storm.

"Should the balancer retry failed requests?"

Yes, but only in one layer, only for idempotent requests or ones that never reached the backend, and within a budget. A connection reset before any bytes were sent is safe to retry anywhere. A timeout on a POST is not, unless the API takes an idempotency key. Fixed retry counts at several layers multiply into a storm during exactly the incidents you want to survive. A budget, such as retries capped at a percentage of active requests, keeps the extra load bounded.

"Every backend fails its health check at once. What should the balancer do?"

Almost never return 503 for everything. A fleet-wide failure is far more likely to be a broken check or a shared dependency blip than six servers dying in the same second. Envoy's panic threshold balances across all hosts when fewer than half are healthy. AWS balancers fail open. Either way, some requests succeed instead of none. Pair that with an alert, because fail-open hides a real outage if nobody is told.
