Deep Dive: Inside the Mechanism

The lesson lists the gateway's jobs: key custody, budgets, routing, reliability, fallback, streaming, safety. This section follows one request through them in order and shows the state each step keeps. Provider APIs differ in their request shapes, headers and limits, and they change often. So everything here is described in provider-neutral terms. Check each provider's current documentation for the specifics.

One request, step by step

  1. Authenticate the caller. The service presents its workload identity: a mesh mTLS certificate, or a short-lived signed token. The gateway maps it to a team, a feature and an environment. No provider key ever leaves the gateway.
  2. Resolve the logical model. chat-premium looks up a route: an ordered list of deployments, each one a (provider, model version, region, credential) tuple with a weight and limits.
  3. Admission checks. Is the caller inside its rate limit (requests per minute and tokens per minute)? Can its budget cover this request's worst-case cost? Do input guardrails pass?
  4. Pick a deployment. Skip any whose circuit breaker is open or whose upstream limit is exhausted. Choose among the rest by weight, latency or cost.
  5. Translate and call. An adapter turns the gateway's request format into the provider's, and starts the call with per-phase timeouts.
  6. Stream back. Forward each chunk as it arrives, translated into the gateway's response format, while counting tokens.
  7. Settle. Record the provider-reported usage, convert it to cost, release the budget reservation, emit the trace and the audit record.

Steps 3 and 7 are where most of the gateway's interesting state lives. Step 6 is where most of its bugs live.

The route table

The heart of the gateway is a configuration that maps names to deployments. Products differ in syntax, but the shape is the same. Here it is in a neutral form:

routes:
  chat-premium:
    deployments:
      - id: provA-large-east     # provider A, large model, pinned version
        weight: 95
        limits: {rpm: 3000, tpm: 2000000}
      - id: provA-large-next     # canary of the next model version
        weight: 5
    fallbacks: [provB-large-west, semantic-cache, error-labeled]
    timeouts: {connect: 2s, first_token: 8s, idle_between_chunks: 20s, total: 120s}
    retries: {max: 1, on: [connect_error, 5xx_before_first_token], honor_retry_after: true}
    breaker: {window: 30s, min_requests: 50, error_rate_open: 0.5, half_open_probe: 5}
  classify-fast:
    deployments:
      - {id: provA-small, weight: 100}
    fallbacks: [selfhosted-7b, keyword-rules]
budgets:
  team/growth:              {monthly_usd: 20000, soft_alert: 0.8}
  feature/agent-experiments: {daily_usd: 500, hard: true}

Three things in it are worth pausing on. Model versions are pinned, so "the model changed" only ever happens through an edit you can review. The canary is a weight, not a separate code path. And the timeouts come in four kinds, because a single "request timeout" can't describe a stream.

Timeouts for streams

A streamed generation that takes 90 seconds may be perfectly healthy. A total timeout of 30 seconds would kill it; a total timeout of 300 seconds would let a hung connection hold a slot for five minutes. Split the timeout into phases instead.

  • Connect: a couple of seconds. Fails fast on network trouble.
  • Time to first token: set from the provider's measured p99 TTFT for this route, with room for long prompts. This is the timeout that catches a brownout.
  • Idle between chunks: the longest gap allowed between two pieces of a stream. It catches a stream that started and then stalled.
  • Total: a ceiling set from max_tokens and normal generation speed. A safety net, not the main control.

The first-byte rule for retries and fallback

Before the first chunk reaches the caller, a failed upstream call can be retried or moved to the next deployment, and the caller never knows. After the first chunk has been sent, it cannot. The caller has already shown "The refund policy for" to a user. A second provider will not continue that exact sentence, and starting over would duplicate text on screen.

So the gateway's reliability logic has two regimes. Before the first byte: retry, fail over, try the next fallback. After the first byte: finish, or end the stream with an explicit error event that the client can show and offer to retry. Some gateways buffer the first few chunks to widen the safe window. That trades TTFT for failover options, and it should be a per-route decision, never a default.

Metering and budgets, with reservations

Token accounting has two sources, and they disagree in useful ways.

  • Provider-reported usage. Most providers return input and output token counts with each response, and in streams usually in the final event. Some require you to ask for it in streaming mode. This is the number you are billed on, so it is the number you record.
  • Gateway estimates. Before the call, the gateway can estimate input tokens with a tokenizer (or roughly, from characters) and knows the requested max_tokens. That gives a worst-case cost before anything is spent.

A hard budget cap needs both. A check-then-call design reads the remaining budget, sees money left, and calls. But fifty concurrent requests all read the same remaining budget at once, and all pass. The fix is a reservation, like a hotel's card hold:

  1. At admission, atomically subtract the request's worst-case cost (estimated input plus max_tokens output) from the remaining budget. If the result would go below zero, reject.
  2. At settlement, add back the difference between the reservation and the actual cost.
  3. If a stream aborts and no usage arrives, settle at an estimate from tokens counted so far, and flag the record for reconciliation.

The counters live in a fast shared store, such as Redis, using atomic increments or a short script. Budgets are hierarchical: a request draws on the user, the feature, the team and the organization together, and any of them can refuse. The price table that turns tokens into money is itself versioned configuration. Prices change, some providers charge differently for cached input or batch traffic, and a cost report is only as right as the price row that produced it.

Living inside upstream limits

Providers usually limit each account or key by requests per minute and tokens per minute, and answer excess with HTTP 429. Many also send headers saying how much of the limit remains and when it resets; the header names differ by provider. A gateway that waits for 429s to discover its limits is driving by the sound of the guardrail. Better:

  • Keep a local token bucket per deployment, sized a little under the provider's published limit.
  • Read the remaining-limit headers when present and adjust the bucket.
  • Honor Retry-After on a 429. Do not retry sooner, and add jitter so many callers do not retry together.
  • When one deployment's bucket is empty, route to the next deployment in the same route before treating it as a failure.

When the gateway is the only caller using those keys, its local view is accurate. That is one quiet benefit of key custody: the limits become something you can plan, instead of something fourteen services share without knowing.

What counts as a failure

A circuit breaker per (provider, model, region) opens when the error rate crosses a threshold. The subtle part is deciding which responses count. Get it wrong and one team's bug can open the breaker for everyone.

Adapters and the common format

Providers differ in how they represent messages, system prompts, tool calls, streaming events, stop reasons and usage. The gateway picks one internal format (often one modeled on a widely used provider's API) and translates both ways. Translation is where meaning gets lost. A provider-specific feature (a special caching control, a particular tool-call mode, a new content type) either has no slot in the common format or gets a pass-through field. The cleaner the abstraction, the more features it hides. Most gateways end up with a common core plus an escape hatch for provider-specific options, used sparingly and visible in review.

Streaming passthrough, concretely

Every hop between the provider and the user must forward chunks as they arrive. The usual culprits:

  • Reverse-proxy buffering. nginx buffers upstream responses by default. For SSE routes, turn it off with proxy_buffering off; (or have the upstream send X-Accel-Buffering: no), and use HTTP/1.1 to the upstream with keep-alive.
  • Compression. A gzip middleware waits to fill its window before emitting anything. Exclude text/event-stream.
  • Framework response objects that collect the body before writing. The gateway's handler must write and flush per event.
  • Output guardrails. Scanning output for policy violations needs some text to scan. Hold back a small window (a sentence, or a few dozen tokens), and release text as it clears. That costs a little latency per chunk, but it is far better than scanning the whole response at the end.
location /v1/stream/ {
    proxy_pass http://gateway_upstream;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 120s;    # at least the idle-between-chunks timeout
    gzip off;
}

Logging without leaking

The gateway sees every prompt and every answer, which makes it the most sensitive log source in the company. Default to metadata: caller, route, deployment, token counts, cost, latency phases, finish reason, trace ID. Store prompt and response content only where a policy says so, with its own retention period, access controls and redaction. The gateway is also the natural place to propagate trace context into provider calls and to attach the trace ID to the audit record. Then "why did this answer cost $4?" is one query.

Deep Dive: Sizing and the Numbers

Assumptions for this section: 14 services, 200 model calls per second at peak, average prompt 1,500 tokens, average output 300 tokens, average stream duration 8 seconds. Prices and provider limits below are illustrative round numbers, not any provider's actual figures.

Concurrent streams and gateway memory

By Little's law, 200 calls per second x 8 seconds = 1,600 streams open at once. Each stream holds two connections: one from the caller and one to the provider. That is 3,200 sockets. An async proxy might keep tens of kilobytes of buffers and state per stream; at 64 KB, that's about 100 MB. CPU is light, since the gateway mostly copies bytes and counts tokens.

So the gateway is not a capacity problem. It is an availability problem. Its unusual load is long-lived connections. Deploying a new gateway version means draining streams that last seconds to minutes. Set connection draining and grace periods from the longest normal stream, exactly as for the GPU fleet's scale-down. Run at least three instances across zones, so losing one drops a third of streams, not all of them.

Overhead

The lesson's 3–8 ms per call comes from a few small steps: authentication (cached), a route lookup, one or two calls to a shared counter store, and the extra network hop. Against a TTFT of 500 ms to 2 s, that is under 1%. The one step that can grow is the budget check. If the counter store is in another region, it can add tens of milliseconds. Keep it local, and make admission fail open or closed by an explicit choice, per route, when the counter store is down.

How much a hard cap can overspend

Take the weekend agent: about $40K over 60 hours, or roughly $670 an hour. Say each of its calls has a worst case of 20,000 input tokens and 4,000 output tokens. At illustrative prices of $3 per million input and $15 per million output, that is $0.06 + $0.06 = $0.12 per call.

  • Check-then-call, no reservation: overspend is bounded by in-flight calls times worst-case cost. At 20 concurrent calls, that is $2.40 past the cap. Small, but only because max_tokens was set. Without it, the worst case per call is the model's full output length.
  • With reservations: overspend is zero, by construction, except for aborted streams settled on estimates.
  • With only an end-of-day batch job comparing spend to budget: overspend is up to a day of spend, about $16K at that rate. That isn't a cap. It is a report.

Upstream limits and the failover reserve

Peak demand: 200 calls per second x 1,800 tokens = 360,000 tokens per second, or 21.6M tokens per minute. Suppose a provider deployment allows 4M tokens per minute. Then the primary route needs six deployments (keys, regions or a higher tier) just to carry normal load.

Now the failover. The lesson's walkthrough moves 80% of traffic to the secondary provider during a brownout. That is about 17M tokens per minute arriving at a provider that normally carries a small share. If its limits were sized for that small share, it starts returning 429s within seconds, and the failover becomes a second outage. A fallback is only real if its quota was provisioned for the failover load. That costs money or negotiation in advance. The alternative is to decide, also in advance, which tiers fail over and which degrade straight to the cache or a labeled error.

Retry amplification

Fourteen services, each with its own three retries, calling through a gateway that also retries three times, can turn one failed call into sixteen upstream attempts. During a brownout, that multiplies load on the struggling provider exactly when it can least take it. Put retries in one place, the gateway, and give them a budget: retries may add at most, say, 10% to upstream traffic over a rolling window. Callers then send each request once and trust the gateway to retry. Each retry also costs tokens. A retried 20,000-token prompt is paid twice if the first attempt reached the model before failing.

Log volume

200 calls per second is about 17M calls a day. Metadata at around 1 KB per call is about 17 GB a day, easy to keep for a year. Full prompts and responses at 8 KB per call add roughly 140 GB a day, and that data is also the most sensitive in the company. That is why content logging is a sampled, policy-driven exception, with short retention, rather than the default.

Deep Dive: Failure Modes in Production

1. The buffering regression

Symptom. After a routine gateway release, users say the assistant "thinks for a long time, then dumps the whole answer." Average total latency is unchanged; TTFT as seen by users has tripled.

Mechanism. The release added a response-compression middleware for the gateway's admin API. It applied to every route. The compressor holds output until its window fills, so SSE events now arrive in a few large clumps.

Detect. A synthetic probe that measures TTFT through the gateway and directly against the provider, side by side, every minute. Gateway-side metrics alone will not see it, because the gateway thinks it wrote each chunk on time.

Fix. Exclude text/event-stream from compression and buffering at every layer. Add a CI test that asserts the first event arrives within a small bound of the upstream's first event. The lesson calls passthrough a standing duty; this test is how you keep it.

2. The answer that started twice

Symptom. A few users see answers that begin, break off, and start again with different wording, all in one message.

Mechanism. The primary provider dropped the connection 3 seconds into a stream. The gateway's retry logic did not check whether bytes had already gone to the client. It retried on the secondary and kept writing to the same stream.

Detect. Count retries and failovers where the first byte had already been sent. The number should be zero.

Fix. Enforce the first-byte rule in code. After the first byte, a failure ends the stream with an explicit error event, and the client offers a retry. If a route truly needs mid-stream recovery, the client must handle it, for example by asking the model to continue from the text it already has. The gateway should not do this silently.

3. Failover into a wall

Symptom. The primary has a brownout. Within a minute, the secondary returns 429s, the self-hosted fallback is saturated, and the error rate is worse than if the gateway had done nothing.

Mechanism. Every route failed over at once, at full volume. The secondary's limits were sized for normal share. The cheap tiers, which could have waited or used rules, competed with premium chat for the same scarce fallback.

Detect. Per-deployment 429 rates and bucket levels during failover drills. The drill is the detector. Without one, the outage is the first test.

Fix. Provision fallback quota for the load you actually plan to move there. Give routes a failover priority, so premium chat moves first and batch-ish tiers degrade to their own end of chain. Shift traffic gradually, which also lets the half-open probes find recovery on the primary. Run the drill quarterly.

4. One team's bug opens everyone's breaker

Symptom. Chat fails over to the secondary provider in the middle of a normal afternoon. The primary provider's status page is green.

Mechanism. A new feature began sending prompts over the model's context limit. The provider returned 400s. The breaker counted every non-2xx response as a failure, crossed 50%, and opened the shared (provider, model) circuit for all callers.

Detect. Breaker openings broken down by response class and by caller. One caller with one error class is the signature.

Fix. Count only provider-side failures toward the breaker: 5xx, timeouts, resets. Return 4xx to the caller. Validate prompt length at admission, with the model's limit in the route table, so a bad request never leaves the gateway.

5. The meter and the invoice disagree

Symptom. Month-end: the provider invoice is 9% higher than the gateway's metered total. Finance trusts neither.

Mechanism. Several causes add up. Aborted streams never received a final usage event, so they were metered at zero. A price changed mid-month, and the price table did not. Retried attempts that reached the model before failing were billed but not metered. Some traffic still used an old key outside the gateway.

Detect. Daily reconciliation against the provider's usage reports, per key, where the provider offers them. Count records with estimated or missing usage.

Fix. Meter every upstream attempt, not just the successful one. Estimate usage for aborted streams from tokens counted. Version the price table with effective dates. Revoke any key not held by the gateway. Where invoices are recharged to teams, make the metering pipeline exactly-once, as the lesson notes.

6. The synchronized retry storm

Symptom. A short burst of 429s turns into ten minutes of 429s. Traffic to the provider is higher than before the burst started.

Mechanism. Services retried immediately, ignoring Retry-After, and the gateway retried as well. Every retry used the same fixed delay, so the retries arrived together, hit the limit together, and failed together.

Detect. Upstream attempts per caller request above about 1.1. The 429 rate that rises after the first 429s, instead of falling.

Fix. Retries only at the gateway, with exponential backoff and jitter, honoring Retry-After, under a retry budget. Before retrying on a 429, try another deployment in the same route that still has headroom. See Retry with Exponential Backoff.

7. The stop reason nobody mapped

Symptom. After a provider's API update, some summaries end mid-sentence, and the calling service treats them as complete.

Mechanism. The provider introduced a new finish reason, or renamed one. The adapter's mapping had a default branch that translated anything unknown to the normal "stop." Truncated outputs now looked finished.

Detect. A counter for unmapped values in every adapter field: finish reasons, event types, content types. Contract tests against each provider's live API on a schedule, not only at build time.

Fix. Unknown values map to an explicit "unknown," never to a success value, and they trigger an alert. Pin API versions where providers offer it. Keep adapters in a maintained open-source core, so you share this churn with others, as the lesson's buy-first advice says.

A learned router is a product feature, not infrastructure. If you build one, the product team owns its quality, and the gateway only hosts it.

Fail open or fail closed

When a gateway dependency is down (the budget counter store, the guardrail service), each check needs a declared behavior. Budget checks usually fail open for short outages with a tight time limit, since a few minutes of uncounted spend is cheaper than a full AI outage. Safety checks that protect users or data, such as PII redaction on regulated routes, fail closed. Decide per route, write it in the route table, and test it in drills.

Deep Dive: Design-Review Checklist

  1. Are all provider keys held only by the gateway, and is there a way to detect a key used from anywhere else?
  2. Does every route pin model versions, and does every change go through a canary judged by evaluations?
  3. Are timeouts split into connect, first token, idle between chunks and total, each set from measured percentiles?
  4. Is the first-byte rule enforced: no retry or failover after content has been sent?
  5. Does the breaker count only provider-side failures, per (provider, model, region)?
  6. Are hard budgets enforced with reservations, and is max_tokens required on every call?
  7. Is each fallback's quota provisioned for the load the plan sends to it, and when was the failover drill last run?
  8. Do retries happen in one place, with backoff, jitter, Retry-After and a retry budget?
  9. Is streaming passthrough tested in CI and probed in production, comparing TTFT through the gateway against direct?
  10. Is metered usage reconciled against provider usage reports, with the price table versioned?
  11. What is logged by default, what content is stored, for how long, and who can read it?
  12. Is there a written rule for what does not belong in the gateway (prompts, templates, product logic), and who enforces it?

Deep Dive: Senior Interview Follow-ups

"The primary provider fails 3 seconds into a stream. What does the gateway do?"

It cannot fail over transparently, because the user has already seen part of an answer and a different model will not continue it exactly. Before the first byte, retry or fail over freely. After it, end the stream with an explicit error event, record the partial usage, and let the client offer a retry. If wider failover windows matter for a route, buffer the first few chunks on purpose, and accept the TTFT cost for that route only.

"How do you enforce a hard $500 daily cap when 50 requests are in flight?"

Reserve before calling. At admission, atomically subtract each request's worst-case cost (estimated input plus max_tokens output at current prices) from the remaining budget, and reject if it would go negative. At settlement, return the difference using the provider-reported usage. Plain check-then-call lets all 50 pass on the same reading. An end-of-day job isn't a cap at all.

"Your fallback plan sends traffic to a second provider. What makes that plan fail?"

Quota, mostly. If the secondary's limits were sized for its normal share, a full failover hits 429s within seconds and becomes a second outage. Provision for the planned failover load, give routes a failover priority, shift gradually, and let cheaper tiers degrade to their own chain ends instead of competing. Then drill it, because the secondary's model also behaves differently with your prompts, and you want to learn that before the outage.

"Should a content-policy refusal open the circuit breaker?"

No. The provider worked correctly; the model declined. Counting refusals, or 400s from bad requests, as failures lets one caller's traffic open the circuit for everyone. The breaker counts 5xx, timeouts and resets. Retrying a refusal on another provider is a policy decision about shopping for a different answer, and most organizations should not make it automatically.

"Why put retries in the gateway and not in the services?"

Because retries multiply across layers. Three in each service times three in the gateway turns one failure into many upstream attempts, exactly when the provider is struggling. In one place, retries can honor Retry-After, try another deployment with headroom first, and stay under a global retry budget. Each retry also costs tokens, which only the gateway can see and meter.

"The gateway's metered spend is 9% below the invoice. Where do you look?"

Aborted streams with no final usage event, metered as zero. Retried attempts that were billed but not recorded. Stale prices in the price table. Keys still in use outside the gateway. Fix by metering every attempt, estimating usage for aborts, versioning prices, revoking stray keys and reconciling daily against provider usage reports.

"Users say the assistant feels slower after a gateway release, but your latency dashboards are flat. What happened?"

Probably buffering. Total latency is unchanged, but chunks now arrive in clumps, so TTFT as users feel it has grown. The gateway's own metrics record when it wrote each chunk, not when the client got it. Probe TTFT end to end, through the gateway and direct, and check every layer for buffering or compression on event streams.

"A team asks to add a prompt template to the gateway 'just for consistency.' What do you say?"

No, and offer the right home. Templates are product behavior; they change with the feature, and their owners must ship them without a platform ticket. They belong in the service or a product-owned prompt registry, versioned there. The gateway keeps identity, keys, metering, budgets, routing, reliability, safety checks and streaming. A useful test: if a rule mentions a product word, it does not belong in the gateway.
