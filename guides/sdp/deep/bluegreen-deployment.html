Deep Dive: Inside the Mechanism

The lesson draws blue-green as a router with a switch. In a design review the switch is the least interesting part. The questions that matter are what exactly flips, how long the flip takes to reach every path into the system, and which parts of the system never flip at all. This section takes those in order.

Where the switch lives

There are four common places to put the switch. They differ in how fast the flip spreads and in what happens to connections that are already open.

  • An L7 load balancer rule. An AWS ALB listener rule pointing at a target group, an nginx or Envoy route, an ingress. The balancer picks a backend per request, so after the change new requests go to green almost at once. The change still has to reach every balancer node, which typically takes a few seconds. ALB weighted target groups also let you do the switch as 0/100 to 100/0, or stop halfway.
  • A Kubernetes Service selector. Change selector: {app: shop, slot: blue} to slot: green. The EndpointSlices change and every node's kube-proxy rewrites its rules. This is an L4 switch. It affects new TCP connections only. A connection that was open to a blue pod stays on that blue pod.
  • DNS. Point shop.example.com at the green load balancer. Simple, and the slowest and least predictable option. Resolvers and clients cache past the TTL, and some long-running clients resolve once at start-up and never again. Traffic decays from blue over minutes to hours, never cleanly.
  • A deployment controller. Argo Rollouts' blue-green strategy, AWS CodeDeploy for ECS, or Spinnaker (Netflix called the same idea red/black). These wrap one of the switches above with the steps around it: a preview service for testing green, pre-promotion checks, automatic or manual promotion, and a delay before scaling blue down (Argo's scaleDownDelaySeconds, 30 seconds by default). Look up your tool's version-specific defaults before relying on them.

The practical rule: choose the switch by what your clients do with connections. Browsers behind a CDN and an L7 balancer flip within seconds. A gRPC service called by other services over long-lived HTTP/2 connections may not flip at all, which is failure mode 1 below.

How atomic is "atomic"?

The lesson says the switch is atomic and versions never mix. That is true in the sense that matters most: there is no half-hour period where both versions take a large share of traffic. It is not true at the millisecond level, and a senior reviewer should say so.

  • Propagation. For a few seconds, some balancer nodes or kube-proxies send new requests to green while others still send them to blue.
  • Draining. Requests that began on blue finish on blue, after green has started taking new ones.
  • Clients. A browser that loaded v1.41's JavaScript before the switch keeps running it and calls v1.42's API. A mobile app on last month's release calls whatever is live. The client fleet is always mixed.
  • Background workers. Unless they are switched too, blue's queue consumers and scheduled jobs keep running after the web traffic moves.

So blue-green removes prolonged version mixing in the request path. It does not remove the need for v1.41 and v1.42 to tolerate each other's requests and data for a short period. Teams that believe the switch is perfectly atomic skip compatibility work, and the edges bite them.

The full sequence, with the parts the diagram leaves out

  1. Expand the schema. Run the additive migration while blue is live. Blue must run correctly against the expanded schema. This step happens before green exists, and it is the first thing the lesson's expand-contract rule controls.
  2. Bring up green from the same artefact and config source. Same image digest that passed CI, same infrastructure-as-code module, environment-specific values only where they must differ. Green scales to full production capacity, not a token size. If green will receive 100% of traffic in one step, it has to be ready for 100%.
  3. Keep green's background work switched off. Consumers, schedulers and cron jobs on green stay disabled, or blue and green would both process the same queue and both send the 9 a.m. reminder email.
  4. Verify through a private route. Argo calls it a preview service, CodeDeploy a test listener. Smoke tests run against green on real infrastructure, using marked test accounts so that test orders do not mix with real ones.
  5. Warm. Readiness gates pass, as in the health check lesson. For JIT runtimes and large caches, warm-up traffic or replayed reads bring latency down to steady-state before real users arrive.
  6. Switch request traffic. Flip the router. Watch error rate and latency on green for the first minutes, compared with blue's numbers from just before.
  7. Switch background work. Pause blue's consumers and schedulers, start green's. Order matters for jobs that must not run twice: stop the old one first, accept a short gap.
  8. Drain blue and keep it. Blue finishes in-flight requests, then stays running (or scaled to a warm minimum) for the rollback window.
  9. Close the window and contract. When v1.42 is trusted, scale blue down. Only then, in a later release, run the contract migration that removes the old structures.

Everything that does not switch

The lesson names the database. In practice there is a list, and each item needs the same two-version rule.

The enum row is the subtle one. Expand-contract is usually taught as a schema rule. But the schema can be perfectly compatible while the data is not. A new value in a text column, a new JSON field that blue's strict parser rejects, a new row type. The general rule is: the old version must be able to read anything the new version might write during the window. Often that means a release before v1.42 that only adds tolerance.

Deep Dive: Sizing and the Numbers

Use the bookstore's checkout service: 40 instances at 4 vCPU each in steady state, with a p99 request of 600 ms and a few long requests up to 30 seconds (report exports).

What 2x actually costs

Assume each instance costs about $0.20 per hour on demand. The live environment is 40 × $0.20 = $8/hour. The question is how long green and blue overlap.

PolicyOverlap per releaseReleases per monthExtra cost per month
Cloud, 3-hour window~3.5 h (start-up, verify, window)4040 × 3.5 × $8 = $1,120
Cloud, 24-hour window~24.5 h40Two releases a day means blue and green almost always both run: close to $5,800, a permanent 2x
On-prem, permanent pairalwaysanyThe full cost of a second set of hardware, used for minutes a day

Now compare with the outage it prevents. If checkout handles $50,000 per hour of orders and the lesson's in-place rollback takes 20 minutes, one bad release costs about $16,000 in lost orders, before counting reputation. One avoided incident a quarter pays for the 3-hour policy several times over. A 24-hour window at two releases a day is where the maths starts to argue for a warm minimum (scale blue down to 25% and scale it up on rollback) or for a canary.

Note the interaction between release frequency and window length. If you release every 4 hours with a 24-hour window, you would need several old environments to keep every rollback target alive. In practice you keep only the previous version, and the rollback window is effectively "until the next release".

Database connections double too

This number catches teams who budgeted for compute but not for the database. Each instance has a connection pool of 20. One environment opens 40 × 20 = 800 connections. During the overlap, both environments are connected: 1,600. Postgres' max_connections is often set in the low hundreds to low thousands, and each connection is a backend process with its own memory. A fleet that sat at 60% of the limit now needs 120%.

Options, in order of preference: put a pooler such as PgBouncer in front, sized for total demand rather than per-environment demand, as in the connection pooling lesson. Or make idle blue shrink its pool after draining, since an idle environment needs only a few connections. Or size max_connections for the overlap explicitly. Whatever you choose, the review should see the 1,600.

How long the switch really takes

  • L7 rule change reaching all balancer nodes: typically a few seconds.
  • Kubernetes selector change to all kube-proxies: usually a few seconds on a healthy cluster, longer on a large one under load.
  • Draining blue: the longest in-flight request. With 30-second exports, about 30 seconds. With SSE or WebSocket connections, as long as you let them live. More on that next.
  • DNS: minutes to hours. Treat it as a gradual shift, not a switch.

Rollback is the same path in reverse, so a "10-second rollback" is honest for an L7 switch with short requests. Promising 10 seconds over DNS is not.

Long-lived connections and the reconnect wave

Suppose the bookstore's order-status page holds 200,000 SSE connections on blue. They will not move on their own. To retire blue you must close them, and every client reconnects to green.

Close them all at once and green receives 200,000 connection attempts within a second or two, each with TLS handshake and authentication. That is a self-inflicted thundering herd. Spread the closes over a drain period instead. At 2,000 closes per second the migration takes 100 seconds and green sees a manageable reconnect rate. Clients should also add jitter to their reconnect delay, as the SSE lesson recommends. Size green for the reconnect handshake rate, not only for steady-state connections.

Deep Dive: Failure Modes in Production

The lesson's Check Yourself covers the destructive migration. These are the failures teams meet after they have learned that one.

1. The switch that did not switch

Symptom. Dashboards show green live, yet 30% of requests from internal callers still reach blue an hour later. Scaling blue down causes a burst of errors in those callers.

Mechanism. The switch was a Kubernetes Service selector, which is an L4 change. Callers hold long-lived HTTP/1.1 keep-alive or HTTP/2 connections to blue pods, opened before the switch. Those connections are still valid, so requests keep flowing over them. gRPC clients are the classic case. They open a few connections and reuse them for hours.

Detection. Request rate on blue after the switch, broken down by caller. It should fall to zero within the drain period. A long tail means sticky connections.

Fix. Switch at L7 where possible, so routing happens per request. If not, have servers cap connection lifetime (gRPC's MaxConnectionAge on the server, or an idle and maximum age in the proxy) so clients reconnect regularly. During blue's drain, actively close connections with Connection: close or an HTTP/2 GOAWAY so clients reconnect and land on green.

2. Rollback crashes on new data, with a compatible schema

Symptom. v1.42 adds partial refunds. Thirty minutes after the switch an unrelated bug forces a rollback. Blue starts throwing on the order history page for some customers only.

Mechanism. No column was renamed. The schema was additive and correct. But green wrote status = 'partially_refunded' into an existing text column, and blue's code maps status strings to an enum that throws on unknown values. The data is the incompatibility, not the schema.

Detection. Errors on blue after rollback, concentrated on rows created or updated during green's live period. A query for rows whose values are outside blue's known set confirms it.

Fix. Short term: roll forward with a fix, or ship a blue patch that tolerates the new value. Long term: any new value, field or message type goes out in two releases. First a release that reads and ignores (or safely displays) the new value. Then the release that writes it. Make the review question explicit: "can the previous version read everything this version writes?"

3. Everything happens twice

Symptom. On release day, customers receive two "your order shipped" emails. A nightly report runs twice and double-counts.

Mechanism. Blue-green was applied to the whole deployment, including queue consumers and the scheduler. Green's consumers started as soon as green was deployed, so both versions consumed the same queue. Or both environments ran the same cron schedule during the overlap.

Detection. Consumer group membership showing instances from both versions. Duplicate side effects keyed by the same event or job ID.

Fix. Separate web traffic switching from background work switching. Background work in green starts disabled and is enabled by the cutover runbook after blue's is stopped. Scheduled jobs take a distributed lock or run from a single scheduler outside both environments. Consumers should be idempotent anyway, so a short overlap does no harm.

4. Green passed verification on a different world

Symptom. Green's smoke tests passed. Five minutes after the switch, payment calls fail with TLS errors, or green writes to the wrong database.

Mechanism. Environment drift. Blue was hand-patched months ago: a firewall rule, a newer CA bundle, a secret rotated in blue only. Green was built from infrastructure-as-code that never had the patch. Or worse, a copy-paste config gave green the staging database URL, and the smoke tests passed because staging works.

Detection. A drift check that diffs the two environments' rendered configuration (excluding the expected slot-specific values) before every switch. Smoke tests that assert identity, such as "which database cluster am I connected to?", not just "does a request succeed?".

Fix. Build both environments from the same code with no manual changes allowed. Rebuild blue from scratch periodically rather than patching it in place. Make the smoke test check identity as well as function.

5. Green is cold, and 100% arrives at once

Symptom. Right after the switch, p99 latency jumps from 600 ms to 3 seconds for several minutes. The database CPU spikes. Then it settles.

Mechanism. Green passed readiness, but its local caches were empty and the JIT had not optimised hot paths. Every request missed the local cache and went to the database at once. A rolling deploy hides this, because only a few instances are cold at any moment. Blue-green sends all traffic to an all-cold fleet in one step. It is a small cousin of the cache stampede.

Detection. Latency and cache hit rate on green over the first minutes after each switch, compared with blue's steady state.

Fix. Warm before the switch: replay a sample of recent read traffic, or pre-load the hottest keys. Or shift in two steps with weighted target groups, 10% for a few minutes then 100%. That is a small step towards canary, and often worth it.

6. Broken pages during the switch, and again at rollback

Symptom. For a minute around each switch, a few percent of page loads show unstyled pages or a JavaScript error. Rollback produces the same burst.

Mechanism. HTML rendered by green references new hashed asset files. During propagation, or because a CDN fetched from whichever environment answered, some asset requests reach blue, which does not have those files. The same thing happens in reverse after rollback, while browsers still hold green's HTML.

Detection. 404 rate on static asset paths, spiking at switch times.

Fix. Publish assets to a shared bucket or CDN origin that both environments read, before the switch, and keep old versions for days. Long-lived single-page apps should also tolerate an API that is a version ahead or behind.

7. Smoke tests that touched production

Symptom. The finance team finds 30 orders from "Test User" in yesterday's revenue. A partner receives webhook events for orders that never existed.

Mechanism. Green shares the production database and integrations, which is the point of blue-green. So smoke tests that place an order really place one. The lesson's "verify against real infrastructure" has a cost: the infrastructure is real.

Detection. Orders from known test accounts appearing in reporting or outbound events.

Fix. Dedicated test accounts with a flag that every downstream system respects: reporting excludes them, outbound webhooks and emails skip them, payment uses the provider's test mode for them. Prefer read-only smoke tests where possible, and keep write tests small and labelled.

Deep Dive: Design Variations and How to Choose

The lesson compares blue-green with rolling deploys. In real systems the choice has more axes than that, and many teams end up with a hybrid.

VariationHow it worksGood forWatch out for
Classic per-service blue-greenOne service has two slots; L7 or selector switchStateless services with fast rollback needsShared state rules; sticky connections at L4
Whole-stack or whole-cluster blue-greenTwo complete clusters; switch at DNS or a global balancerCluster upgrades, platform migrations, Kubernetes version jumpsDNS slowness; cost of a second cluster; data stores still shared or replicated
Blue-green with a weighted first stepSwitch 5–10% first, watch, then 100%Warming green and catching obvious errors with small exposureIt is now a short canary; needs version-mixing tolerance
Blue-green with shadow trafficMirror a copy of live requests to green before the switch, discard green's responsesTesting performance and error rate on real traffic with zero user impactWrites must not be mirrored, or must go to a sandbox; doubles load on shared dependencies
Warm-minimum blueAfter the switch, scale blue to 20–25% and keep it; scale up on rollbackLong rollback windows at lower costRollback takes as long as scaling up; blue can be overwhelmed if switched back too early
Rolling deploy plus feature flagsDeploy in place; risky behaviour stays behind a flagLarge fleets where 2x is expensive; behaviour risk rather than infrastructure riskMixed versions during rollout; flag debt, as in the feature flags lesson

How to choose

Ask what risk you are actually managing.

  • If the main risk is the new build not working in production at all (bad config, missing secret, broken dependency, platform upgrade), blue-green is strong. It verifies the whole environment with zero users, and rolls back in seconds.
  • If the main risk is new behaviour hurting a fraction of users, you need gradual exposure: canary, or flags. Blue-green sends 100% at once.
  • If the main risk is the data (migrations, new value types, backfills), the deployment strategy hardly matters. Expand-contract and two-release tolerance do the work, and the zero-downtime migration capstone is the right frame.
  • If versions cannot coexist at all (a protocol change between tightly coupled components, a license server, a singleton), blue-green's near-atomic switch is the main reason to use it. Be honest that "near" still leaves seconds of overlap.

A sensible default for many teams: rolling deploys for routine releases, blue-green for platform changes and high-risk releases where instant rollback is worth paying for, and flags for behaviour changes. One release process does not have to fit every release.

Deep Dive: Design-Review Checklist

  1. Where is the switch (L7 rule, selector, DNS, controller), and how long does it take to reach every path into the service?
  2. What happens to long-lived connections at the switch: keep-alive, HTTP/2, gRPC, SSE, WebSocket? How are they moved, and at what rate?
  3. Can v1.41 read every row, cache entry, message and cookie that v1.42 might write during the rollback window? Show the tolerance release if one was needed.
  4. When does the contract migration run, and what enforces that it waits for the rollback window to close?
  5. Are queue consumers, schedulers and cron jobs switched separately from web traffic? What prevents both versions processing the same work?
  6. Is green built from the same artefact and infrastructure code as blue? How is drift detected before each switch?
  7. Do smoke tests prove identity (right database, right region, right secrets) as well as function? What stops test data reaching reports, partners or payments?
  8. Is green sized and warmed for 100% of traffic, including the reconnect rate of long-lived clients?
  9. What does the overlap do to shared limits: database connections, rate limits with third parties, licence counts?
  10. Which metrics decide "keep" or "roll back" in the first minutes, and who or what makes that call?
  11. How long is the rollback window, what does it cost per month at your release frequency, and is there a warm-minimum option?
  12. Where do static assets live, and are both versions' assets available throughout the switch and rollback?

Deep Dive: Senior Interview Follow-ups

"You flipped the Kubernetes Service selector to green, but blue still gets traffic an hour later. Why?"

A selector change is an L4 switch. It only affects new connections. Callers holding keep-alive or HTTP/2 connections to blue pods keep using them, and gRPC clients may hold connections for hours. Fix it by switching at L7, by capping server connection age so clients reconnect, or by closing connections from blue during its drain with GOAWAY or Connection: close.

"The migration was purely additive. Why did rollback still break blue?"

Because compatibility is about data as well as schema. Green can write values blue does not understand into perfectly compatible columns: a new enum value, a new JSON field for a strict parser, a new message type. The rule is that the old version must read anything the new one writes during the window. New values need a release that tolerates them before the release that writes them.

"Is the blue-green switch atomic?"

Close enough to remove prolonged mixing, not truly atomic. For a few seconds the routing change is still spreading, requests already on blue finish on blue, and clients running old JavaScript or old mobile builds call the new API anyway. So you still need short-term compatibility between adjacent versions. What blue-green removes is the long period of mixed versions a rolling deploy has.

"How do you handle the queue consumers in a blue-green deploy?"

Separately from web traffic. Green's consumers start disabled. After the request switch, stop blue's consumers and start green's. Consumers stay idempotent so a short overlap or a redelivery does no harm. Message formats follow the same additive rule, because during rollback blue's consumers will meet messages green produced.

"Two releases a day, 24-hour rollback window. What does that do to cost and to the design?"

The environments almost always overlap, so you pay close to a permanent 2x, and you could need more than one old environment to keep every rollback target. In practice you keep only the previous version, so the effective window is until the next release. To cut cost, scale blue to a warm minimum after the switch and scale it up on rollback, accepting a slower rollback. Or move routine releases to rolling and keep blue-green for risky ones.

"The switch went fine, but latency tripled for five minutes. What happened and how do you prevent it?"

Green was ready but cold. Every instance had empty local caches and unoptimised code, and all traffic arrived at once, so cache misses hit the database together. Rolling deploys hide this because only a few instances are cold at a time. Warm green before the switch with replayed reads or preloaded hot keys, or switch in two weighted steps so green warms on a small share first.

"When would you choose blue-green over canary even though canary limits blast radius?"

When the risk is the environment rather than the behaviour: a runtime or platform upgrade, a new cluster, new infrastructure. Blue-green tests all of it with zero users and rolls back in seconds. Also when two versions cannot safely serve side by side for long, which a canary requires by design. Many teams combine them: bring up green fully, verify, then shift weight gradually.

"Blue-green doubles your database connections. How do you plan for that?"

Count it. Forty instances with pools of 20 is 800 connections per environment, 1,600 during overlap. Either a pooler in front of the database sized for total demand, or shrink idle blue's pool after it drains, or raise max_connections knowingly with the memory that costs. The same overlap applies to anything with a shared limit: third-party rate limits, licence seats, broker connections.
