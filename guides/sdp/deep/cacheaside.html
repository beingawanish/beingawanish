Deep Dive: Inside the Mechanism

The lesson's version of cache-aside fits in four lines: check, fetch, set, return. A production version is closer to forty. The extra lines are where the real decisions live: what happens when the cache is slow, what a key looks like, how expiry actually works inside Redis, and which races the delete-on-write rule still leaves open.

The read path, written out properly

Here is the product read with the details that matter in production. It uses the redis-py client API; the shape is the same in any language.

import json, random

TTL = 3600            # one hour for product records
JITTER = 0.10         # spread expiries by +/- 10%
NEG_TTL = 60          # remember "no such product" for a minute
MISSING = b"__none__"

def get_product(pid):
    key = f"product:v3:{pid}"            # namespace + schema version + id
    try:
        raw = cache.get(key)             # client socket timeout ~10-20 ms
    except CacheError:
        raw = None                       # a slow or dead cache is a miss, not an outage
    if raw == MISSING:
        return None
    if raw is not None:
        return json.loads(raw)

    row = db.query("SELECT ... FROM products WHERE id = %s", pid)
    try:
        if row is None:
            cache.set(key, MISSING, ex=NEG_TTL)
        else:
            ttl = int(TTL * random.uniform(1 - JITTER, 1 + JITTER))
            cache.set(key, json.dumps(row), ex=ttl)
    except CacheError:
        pass                             # failing to fill never fails the read
    return row

Each line answers a question the four-line version skips.

  • Cache errors become misses. The cache is an optimisation, so a broken cache must never break a read. That is also why the client timeout must be short. A cache hit takes about 1 ms, so a 10–20 ms timeout is generous. A 1-second timeout turns a sick cache into a 1-second outage on every request.
  • The key carries a schema version. When the record's shape changes, you bump v3 to v4. New code reads new keys and never parses old blobs. The old keys simply expire.
  • TTLs get jitter. Without it, every key filled in the same minute (after a deploy, a restart or a warm-up script) expires in the same minute an hour later.
  • Absence gets cached too. A request for a product that does not exist is a miss every time, unless you remember the absence. This is called negative caching, and it uses a short TTL so a newly created product appears quickly.

What Redis does with your keys

Three Redis behaviours decide how cache-aside behaves under pressure. They are configuration, not code, so they are easy to miss in review.

Eviction policy. Redis evicts only when maxmemory is set and full. What it does then depends on maxmemory-policy, and the default is noeviction. With that default, a full cache does not drop old keys. It rejects new writes with an out-of-memory error. For a pure cache that is almost never what you want.

PolicyEvictsGood forTrap
noeviction (default)Nothing; writes fail when fullRedis used as a primary storeA cache that silently stops filling
allkeys-lruLeast recently used key, any keyMost cachesOne big scan of cold keys pushes out hot ones
allkeys-lfuLeast frequently used key, any keySkewed catalogs with a stable hot setSlower to adapt when popularity shifts suddenly

volatile-ttlThe key closest to expiryRarely the best choiceIgnores how hot a key is

Redis's LRU and LFU are approximations. On each eviction it samples a few keys (maxmemory-samples, 5 by default) and evicts the best candidate among them. Raising the sample size makes eviction closer to true LRU and costs CPU. For most caches the default is fine.

Expiry is lazy plus sampled. An expired key is removed when someone touches it, or when the background expiry cycle samples it (that cycle runs at a rate set by hz, 10 times per second by default). So expired keys can sit in memory for a while. Readers never see them, but your memory graph does. If millions of keys expire in the same minute, the active cycle also spends noticeable CPU deleting them.

Replication is asynchronous. A Redis primary acknowledges a SET or DEL before its replicas have it. For cache-aside this rarely matters, because a lost SET is just a later miss. A lost DEL is different: after a failover, the promoted replica may still hold the value you deleted. The TTL is what bounds that.

Memcached differs in ways worth knowing. It has no persistence and no replication, which suits a cache well. It stores items in a slab allocator: memory is split into size classes, and each class has its own LRU. Items are capped at 1 MB by default (the -I flag raises it). Older versions could get "calcified", with memory stuck in size classes the workload no longer used. Modern versions rebalance slabs automatically. Memcached also has add (store only if absent) and cas (store only if unchanged since you read it), which are the building blocks for the race fixes below.

Key design

Keys look trivial until three teams share a cluster. A good key has four parts: a namespace (product), a version (v3), the identity (8412), and any variant that changes the value (:en-GB for a localised description). Missing the variant is a real bug. If the key for a localised page omits the locale, the first reader's language wins for an hour.

Keys should be computable from the write side too. The write path must delete exactly the keys the read path fills. If the read path caches product:v3:8412:en-GB and product:v3:8412:de-DE, the writer must know every locale, or must use a different scheme. Two schemes are common.

  • Generation keys. Store a small counter, product:8412:gen, and include its value in every derived key: product:v3:8412:g17:en-GB. A writer increments the counter once. Every derived key becomes unreachable at once, and the old entries age out through eviction or TTL. This costs one extra cache read per lookup.
  • Tags. Some frameworks keep a set of keys per tag and delete the set. This works, but the tag set itself is a cache entry that can be evicted or go stale. Generation keys are usually simpler.

The races delete-on-write still leaves

The lesson shows why DEL beats SET on write. Deleting removes the write-write race. It does not remove every race, and it helps to see the remaining ones on a timeline.

The window is narrow: the reader must pause between its database read and its cache fill, and a write must land inside that pause. At 12,000 reads per second that still happens. Three related races share the same shape.

  • Delete before commit. If the writer deletes inside its transaction and commits afterwards, any reader in between refills the cache with the old row. The delete must come after the commit.
  • Replica lag. The writer commits on the primary and deletes the key. A reader misses, reads a replica that is 200 ms behind, and refills the cache with the old row. This one is common, because replica lag is often longer than any GC pause.
  • Lost delete. The writer commits, then crashes or times out before the DEL. Nothing retries it.

The fixes, from cheapest to strongest:

  1. Short TTLs on data that matters. This does not prevent anything. It bounds the damage, which for a product description is often enough.
  2. Delayed double delete. Delete after commit, then delete again after a delay longer than replica lag plus a slow read (say 1–2 seconds). It catches most repopulation races cheaply. It is a heuristic, not a guarantee.
  3. Fill from the primary after a recent write. Facebook's memcache paper describes a "remote marker": a writer sets a marker key, and a reader that sees it reads from the primary instead of a lagging replica.
  4. Leases. Also from the Facebook paper. On a miss, the cache hands the reader a lease token. A DEL on that key invalidates outstanding tokens. The reader's later fill succeeds only with a valid token, so step 5 in the diagram is rejected. Memcached does not ship leases as a feature, but you can build the same thing with cas, or with a small Lua script in Redis.
  5. Versioned fills. Store a version (an updated_at or a row version column) with the value, and let a fill replace an entry only if its version is newer. This stops stale fills that arrive after a newer fill. It does not stop a stale fill into an empty slot, which is the diagram's case, so it pairs with leases or a short TTL.

Moving invalidation out of the application

The lesson's worst bug was the write path that forgets to delete. The structural fix is to stop asking write paths to remember. Instead, a separate process reads the database's change log and deletes keys for every committed change.

On MySQL that means tailing the binlog; on Postgres, logical decoding of the WAL (see Write-Ahead Log). Debezium is a common off-the-shelf choice. Facebook's paper describes the same idea: a daemon called mcsqueal reads the MySQL commit log and broadcasts deletes.

This catches every writer: the admin panel, the bulk import, the manual UPDATE someone runs at 2 a.m. It also deletes strictly after commit, which removes the delete-before-commit race. The costs are a new component to run, invalidation lag (usually milliseconds to a second, and much worse if the tailer falls behind), and a mapping from table rows to cache keys that someone has to maintain. Monitor the tailer's lag as carefully as replica lag, because it is the cache's staleness.

Deep Dive: Sizing and the Numbers

The numbers below use the lesson's bookstore: 2,000,000 products, 12,000 reads per second at peak, a 15 ms database read, a 1 ms cache hit, and eight database replicas before the cache.

How much memory

Start with the bytes you store, then add overhead.

  • Value size. A serialised product record is about 2 KB. Measure it; JSON with long field names can easily double this. Compression (zstd, or just shorter field names) often halves it.
  • Per-key overhead. Redis adds its own bookkeeping per key: the key string, the dictionary entry, expiry metadata. Plan on tens of bytes to around 100 bytes per key, and measure with MEMORY USAGE on real keys.
  • Fragmentation. The allocator never packs memory perfectly. Watch mem_fragmentation_ratio in INFO memory; values around 1.1–1.5 are typical for churny caches.

The whole catalog: 2,000,000 × (2,048 + 100) bytes ≈ 4.3 GB. With a fragmentation allowance of 1.3, that is about 5.6 GB. A node with 8 GB and maxmemory at 6 GB fits the entire catalog.

That result changes the question. When the full data set fits in one modest machine, you are not choosing what to cache. You are choosing TTLs. Eviction policy only matters once the data outgrows memory, for example when you add per-locale and per-currency variants. Ten variants per product makes it 56 GB, and then the hit-ratio curve below starts to matter.

Predicting the hit ratio

Two separate effects set the hit ratio. Capacity decides which keys can stay. TTL decides how often even a resident key misses.

The TTL effect. Suppose a key receives λ requests per second and its TTL is T seconds, with no invalidations. Each TTL window starts with one miss followed by about λT hits. So its miss ratio is about 1 / (1 + λT).

  • Item 8412: λ = 4,000 per minute ≈ 67 per second, T = 3,600 s. λT ≈ 240,000, so the miss ratio is about 0.0004%. This is the lesson's "next 240,000 reads".
  • A long-tail product read twice an hour: λT = 2, so one read in three misses.
  • The same tail product with a 5-minute TTL: λT ≈ 0.17, and 86% of its reads miss. Short TTLs barely cost anything on hot keys and wipe out the benefit on cold ones.

The capacity effect. Popularity in catalogs is often roughly Zipf-shaped: the k-th most popular item gets traffic proportional to 1/k. Under a pure Zipf curve with exponent 1, caching the top k of N items captures about H(k) / H(N) of requests, where H(n) ≈ ln n + 0.577.

  • Top 200,000 of 2,000,000 (10%): (ln 200,000 + 0.577) / (ln 2,000,000 + 0.577) ≈ 12.78 / 15.09 ≈ 85%.
  • To reach 99%, you need H(k) ≈ 14.94, so k ≈ 1.7 million: about 86% of the catalog.

That second number surprises people. Under a pure 1/k curve, the last few percent of hit ratio are expensive. Real traffic is often more skewed than that, and requests repeat in short bursts, which helps. Even so, never assume a 99% hit ratio from a back-of-envelope cache size. Measure it: replay a day of access logs against simulated cache sizes and plot hit ratio against memory. That plot is called a miss-ratio curve, and it is the honest way to size a cache.

Fan-out turns rare misses into common slow pages

The lesson's average of 1.1 ms is per lookup. Pages rarely do one lookup. A product page might fetch the product, its seller, three recommendations, stock status and reviews: say 20 keys.

If each lookup hits independently with probability 0.992, the page sees at least one miss with probability 1 − 0.99220 ≈ 15%. If the lookups are sequential, a miss adds about 16 ms. So roughly one page in seven pays at least one database round trip, even with a "99.2% cache".

The fixes are structural. Fetch keys in parallel, or with one MGET, so a miss costs one database read instead of a chain. And for the hottest pages, cache the composed page fragment, so one key replaces twenty.

Throughput and the hot key

A single Redis process handles on the order of 100,000 simple GETs per second on one core; the exact figure depends on value size, pipelining and hardware. The bookstore's 12,000 per second is far below that. Bandwidth is the more likely ceiling: 12,000 × 2 KB = 24 MB/s, which is also fine.

Now imagine a flash sale where one product takes 200,000 reads per second. In Redis Cluster, a key maps to one of 16,384 hash slots, and each slot lives on exactly one primary. Every one of those reads goes to the same node. 200,000 × 2 KB = 400 MB/s, about 3.2 Gbps of response traffic, from one process on one core. Adding shards does nothing, because the key does not split.

There are two usual fixes. The first is a small in-process cache in front of Redis for the hottest keys. Even a 1-second TTL removes almost all of that load, since each server then asks Redis about once a second. The second is spreading copies of the hot key across several keys (product:8412#0 to #7) and picking one at random on read. Copies make invalidation harder, because a write must delete all of them.

The question nobody sizes: the database without the cache

The lesson says six of the eight replicas were shut down. Before that decision, do this calculation.

Eight replicas served 12,000 reads per second, so each handles at least 1,500. Two replicas handle about 3,000. If the cache cluster is lost or restarted empty, 12,000 reads per second arrive at a database sized for 3,000. That is a 4× overload. Queues grow, latency climbs from 15 ms to seconds, and timeouts plus retries make the load worse.

You have three honest options, and you should write down which one you chose:

  1. Keep enough database capacity to survive a cold cache at peak. Expensive, but simple.
  2. Make the cache highly available (replicas, multiple nodes, a spare "gutter" pool as Facebook did) so that losing all of it is very unlikely, and accept the risk.
  3. Shed load when cold. Rate-limit database reads, serve degraded pages, and warm the cache gradually. See Graceful Degradation and Cache Stampede Prevention.

Teams that remove replicas without picking one have quietly made the cache part of the database's capacity. That is a reasonable choice, but it should be a deliberate one.

The cost comparison

Assume a database replica is a large machine and the cache is one 8 GB node with one replica for failover. Two small cache nodes replace six large database machines. The exact prices vary by provider, but the ratio is usually lopsided: RAM in a cache node is cheap per gigabyte compared with a full database replica's CPU, memory, storage and licence. The cache wins on cost as long as the hit ratio is high. The fan-out and cold-start sections are what keep that true.

Deep Dive: Failure Modes in Production

1. The price that changes back

Symptom. An admin changes a price. The new price shows briefly, then the old price comes back and stays for up to an hour. It happens only sometimes, and mostly at peak.

Mechanism. The write goes to the primary, and the app deletes the key. The next reader misses and reads a replica that has not yet applied the update. It fills the cache with the old price, which now lives for a full TTL. Under peak load, replica lag grows, so the window grows.

Detect. Compare the cache's value against the primary for recently written keys, using a sampled checker job. Correlate the incidents with the replica lag metric (on MySQL, Seconds_Behind_Source; on Postgres, the replay lag in pg_stat_replication).

Fix. Fill from the primary for a short window after a write (a remote marker), or delete again after a delay longer than worst-case lag, or invalidate from the change log of the replica the readers use. Keep TTLs short on prices.

2. The cache that is slow, not down

Symptom. p99 page latency jumps from 40 ms to 1.2 s. The database looks idle. Nothing reports an error.

Mechanism. One Redis node is struggling: a slow command such as KEYS * or a large DEL blocks its single thread, a background save forks a large process, or the host is swapping. Clients wait for their full timeout, which someone set to 1 second, before treating it as a miss. A dead cache would have been faster: connection refused returns in microseconds.

Detect. Client-side cache latency histograms, split by node. On the server, SLOWLOG GET and the latency monitor. Watch the client's connection pool wait time too; pool exhaustion looks exactly like this.

Fix. Tight client timeouts (a few times the normal p99, so 10–20 ms), a circuit breaker around the cache so a sick node is skipped quickly (see Circuit Breaker), and banning KEYS in production (use SCAN). Use UNLINK instead of DEL for large values, so the memory is freed in the background.

3. The cache that stopped filling

Symptom. Hit ratio drifts down over days. Database load creeps up. The application logs show occasional OOM command not allowed errors, swallowed by the "cache errors are misses" handler.

Mechanism. maxmemory was set and the policy was left at noeviction, or it was volatile-lru and a new feature wrote keys without TTLs. Either way, memory filled with keys that cannot be evicted, and every new SET fails. Reads still work for old keys, so nothing looks broken.

Detect. Alert on used_memory approaching maxmemory combined with evicted_keys staying at zero. Count failed cache writes as a metric instead of only logging them. Track the share of keys without a TTL (an INFO keyspace line shows keys and expires per database).

Fix. Set allkeys-lru or allkeys-lfu on cache clusters. Keep data that must not be evicted (sessions, rate-limit counters, locks) on a separate cluster with its own policy.

4. The hourly wave

Symptom. Database CPU spikes at roughly the same minute every hour after a deploy. The spike shrinks over the day, then returns after the next deploy.

Mechanism. The deploy flushed or changed the cache keys (a version bump, a new namespace), so the hot set was refilled within a few minutes. Every key got the same fixed 3,600-second TTL. An hour later they all expire together, and their refills land together. Each cycle spreads out a little, because refill times vary.

Detect. Plot cache misses per minute and database queries per minute on the same chart. A sawtooth with an exact 60-minute period is the signature.

Fix. TTL jitter of ±10–20%. For the hottest keys, refresh before expiry rather than after (probabilistic early refresh, covered in Cache Stampede Prevention). Roll out key-version bumps gradually, or warm the new keys before switching readers to them.

5. One shard on fire

Symptom. During a promotion, one Redis node runs at 100% CPU and its network interface is saturated. The other nodes are calm. Timeouts appear only for keys on that node, which includes many unrelated products that happen to share it.

Mechanism. One key gets a large share of all traffic, and a key cannot be split across shards. The node's single thread or its NIC becomes the bottleneck for everything stored there.

Detect. Per-node ops and bandwidth on a dashboard, not just cluster totals. redis-cli --hotkeys works when the policy is LFU. Client-side sampling of keys per second is more reliable.

Fix. A short-TTL in-process cache for the hottest keys, or several copies of the hot key under different names. Detect hot keys automatically and promote them to the local tier, because the hot key during a sale is rarely the one you predicted.

6. The deploy that broke reads

Symptom. Halfway through a rolling deploy, product pages start returning errors on some servers. Rolling back does not fully fix it.

Mechanism. The new code changed the cached object: it renamed a field or switched serialisation. New servers write the new format into the same keys that old servers read, and vice versa. Each version crashes on the other's blobs. After rollback, the new-format entries are still in the cache, so old code keeps failing until they expire.

Detect. Deserialisation errors as a named metric. Errors that correlate with the deploy's progress rather than with traffic.

Fix. Put the schema version in the key. During a rolling deploy, the two versions then use separate keys and never read each other's data. The cost is a temporary drop in hit ratio while the new keys fill, so do it off-peak.

7. The scraper that missed every time

Symptom. Database load doubles overnight while cache hit ratio for real users looks normal. The slow-query log is full of lookups that return zero rows.

Mechanism. A scraper or a buggy client requests product IDs that do not exist. Nothing is cached for "not found", so every request is a miss that reaches the database. Overall hit ratio drops, and the cache gives no protection at all for this traffic.

Detect. Count database lookups that return no row, and miss ratio split by response status.

Fix. Negative caching with a short TTL, as in the read-path snippet. For very large ID spaces, a Bloom filter of valid IDs in front of the cache rejects most invalid lookups without storing each one. Rate-limit the client as well.

A two-tier design needs a story for L1 invalidation. The simplest is a short L1 TTL (1–5 seconds), which bounds staleness and still absorbs hot-key traffic. Redis 6 and later can also push invalidations to clients that opt in with CLIENT TRACKING, so the client's local copy is dropped when the key changes. Pub/sub broadcasts of deletes work too, but a dropped message leaves one server stale, so keep the short TTL anyway.

Redis or Memcached

For plain cache-aside of serialised objects, both work well. Memcached is multi-threaded, so one node can use many cores. It has no persistence or replication to manage, and its slab allocator gives predictable memory behaviour. Redis has richer data types (hashes, sorted sets), Lua scripting for things like leases and versioned fills, replication, and client-side tracking. Choose Redis if you need any of those features. Choose Memcached if you want a simple, very fast, disposable cache and you will use none of them. Running both is common, and it is fine.

Deep Dive: Design-Review Checklist

  1. What is the measured or simulated hit ratio, from real access logs, and what memory does it need? Is there a miss-ratio curve, or only a guess?
  2. Can the database survive the full read load if the cache restarts empty at peak? If not, which choice was made: spare capacity, a highly available cache, or load shedding?
  3. Which code paths write each cached entity? Do all of them go through one module that invalidates, and what about bulk imports, migrations and manual fixes?
  4. Is the delete strictly after the commit, and what happens when it fails or times out?
  5. Do readers fill from replicas? If so, how is the replica-lag repopulation race handled for data where staleness matters?
  6. What is the TTL for each data type, and what is the business cost of serving a wrong value for that long?
  7. Do TTLs have jitter? What happens to load an hour after a deploy that changes key versions?
  8. What is maxmemory-policy? Are cache keys separated from data that must not be evicted?
  9. What are the client timeouts and pool sizes for cache calls, and does a slow cache degrade to a miss quickly?
  10. Does the key include a schema version and every input that changes the value (locale, currency, user tier)?
  11. Is "not found" cached? Is there protection against lookups for IDs that never exist?
  12. Which metrics exist: hit ratio per key prefix, per-node ops and bandwidth, evictions, failed cache writes, deserialisation errors?

Deep Dive: Senior Interview Follow-ups

"You delete on write. Can the cache still end up stale? Show me how."

Yes, in three ways. First, the read-repopulation race: a reader misses, reads the old row, pauses, and fills the cache after the writer's delete. Second, replica lag: the reader misses after the delete but reads a replica that has not applied the write yet, then caches the old row. Third, a lost delete: the writer commits and dies before deleting. All three leave a wrong value for one TTL. Short TTLs bound them; a delayed second delete catches most fill races; filling from the primary after recent writes handles lag; leases or change-data-capture invalidation close the gaps properly.

"Why delete after the commit and not before? Deleting first seems safer."

Deleting first opens a window between the delete and the commit. Any reader in that window misses, reads the still-old committed row, and refills the cache with it. The commit then lands, and nothing deletes the stale copy. Deleting after commit means any refill sees the new row, apart from replica lag. Some teams delete both before and after to shrink stale reads during the write, but the after-commit delete is the one that matters.

"The cache cluster dies at peak. Walk me through the next five minutes."

Every read becomes a miss, so the database sees the full 12,000 reads per second. If it was sized for the miss load only, it overloads: latency rises, connection pools fill, application timeouts trigger retries, and the retries add more load. Meanwhile the cache client may be adding its own timeout to every request. What should happen instead: the client's circuit breaker trips quickly, so reads skip the dead cache. The database tier rate-limits or sheds low-priority reads, and pages degrade. When the cache returns, it refills gradually, with stampede protection so each hot key is fetched once. The real answer is the capacity decision made beforehand.

"How would you choose TTLs if you had no business guidance?"

From two numbers per data type: the cost of serving a stale value and the read rate. The miss ratio per key is about 1 / (1 + λT), so a hot key gets nearly all its benefit from even a short TTL, while cold keys need long TTLs to be worth caching at all. With invalidation in place, the TTL is insurance, so set it to the longest staleness you could tolerate if invalidation silently failed. Then add jitter. Then measure the hit ratio by key prefix and adjust.

"One product is getting 200,000 reads a second. Adding Redis shards doesn't help. Why, and what do you do?"

A key maps to one hash slot on one node, so all its reads land on one Redis thread and one network interface, no matter how many shards exist. At 2 KB per read that is around 3 Gbps from one node. Put a small in-process cache with a 1–2 second TTL in front of Redis for hot keys. Each of 40 servers then asks Redis about once a second instead of thousands of times. Or store several copies of the key and read one at random. Both trade a little staleness or invalidation complexity for removing the single-node bottleneck.

"When would you rather not have the application do invalidation at all?"

When you cannot list every writer: several services share the tables, a data pipeline backfills prices, or operators run manual fixes. Then I would tail the database's change log (binlog or logical decoding, often with Debezium) and delete keys from there. It sees every committed change, always after commit. The cost is a component whose lag becomes the cache's staleness, plus a mapping from rows to keys that has to stay current as the cache layout changes.

"Is a 99% hit ratio good?"

It depends on fan-out and on what the misses cost. Per lookup, 99% gives an average near 1.2 ms against 15 ms. But a page with 20 lookups has an 18% chance of at least one miss, so p90 page latency may be set by misses. And if the remaining 1% is 120 reads per second of expensive queries, that might still be most of the database's load. I would look at hit ratio per key prefix, miss cost per prefix, and page-level latency, not one global number.

"How do you deploy a change to the cached object's format without an outage?"

Version the key. New code reads and writes product:v4:*; old code keeps product:v3:*. During the rolling deploy each version only sees its own format, and a rollback is safe because the old keys are still there. The cost is a temporary drop in hit ratio while v4 fills. Do it off-peak, consider warming the hottest v4 keys first, and check that the database can absorb the extra misses.
