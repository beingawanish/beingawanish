Deep Dive: Inside the Mechanism

The lesson settles what goes inside an event. A real system has to settle four more things before the design holds up. What kind of event is this, and who is it for? How does its format change over time without breaking anyone? How does it leave the producer's database without being lost or invented? And when something goes wrong three hops later, how do you find out why? We will take them in order.

Three kinds of event, three different audiences

The lesson's three levels describe how much state an event carries. A second axis is just as important: who the event is for.

  • Notification events say "something changed, ask me if you care." {order_id} and nothing else. They are fine for low-volume triggers where the consumer would call the owner anyway, like a cache invalidation.
  • Event-carried state transfer (ECST) ships the current state of an entity. order.updated carries the whole order, every time. Consumers overwrite their local copy and do not need to know what changed.
  • Domain events describe a business fact in the language of the domain: OrderPlaced, PaymentCaptured, ShipmentDelayed. They carry the data relevant to that fact, and the name itself carries meaning. A domain event is what a fraud model or an auditor actually wants to know.

Domain-driven design adds one more split, and it saves a lot of pain. Internal domain events live inside one service's boundary. They can change whenever that team likes. Integration events are the public subset published to other teams, with a schema under governance. Most "we cannot change anything" situations come from publishing internal events directly, so that every refactor becomes a cross-team negotiation. Translate at the boundary. Checkout's internal CartLineAdjusted should never reach the public topic.

A practical way to tell them apart: ECST answers "what is the order now?" and a domain event answers "what just happened to it?" Many good designs carry both. OrderCancelled names the fact and includes the order's state after the change, so consumers do not need to apply diffs.

The envelope: metadata every event needs

Separate the envelope from the payload. The payload is the business data. The envelope is what infrastructure and debugging need. CloudEvents is a CNCF specification for this, and its core attributes are a good checklist even if you do not adopt it:

{
  "specversion": "1.0",
  "id": "evt_01HZX4K9M2",              // unique per event: the dedup key
  "source": "/checkout",                // who produced it
  "type": "com.bookstore.order.placed.v1",
  "subject": "ord_7f3a",                // the entity it is about
  "time": "2026-11-20T14:03:11.204Z",   // when it happened, at the source
  "dataschema": "registry://order-placed/7",
  "data": { "order_id": "ord_7f3a", "items": 3, "total_cents": 14200, ... },

  // extensions worth adding
  "traceparent": "00-4bf92f35...-00f067aa0ba902b7-01",
  "correlationid": "req_88c1",          // the user action that started it all
  "causationid": "evt_01HZX4K7QA",      // the event that directly caused this one
  "entityversion": 42                   // per-order version, for ordering
}

Three fields deserve emphasis. The id is what consumers dedupe on, so it must be assigned once, at the source, and survive retries. The per-entity entityversion lets a consumer ignore anything older than what it already applied. That defends against reordering from any cause. And correlationid plus causationid let you rebuild the chain of events after the fact, which we return to under tracing.

On Kafka, put envelope fields in record headers where practical. Tracing libraries and routers can then read them without deserializing the payload.

Schema registries: how compatibility is actually checked

A schema registry stores every version of each event schema and refuses to register a new one that breaks the configured rule. In the Confluent-style wire format, each serialized record starts with a magic byte and a 4-byte schema ID. The consumer reads the ID, fetches that schema once (then caches it), and decodes the payload. So every record says exactly which schema wrote it. That is what makes mixed versions in one topic workable.

The compatibility mode is the knob that matters:

ModeGuaranteeSafe changes (Avro terms)Deploy order
BACKWARDNew readers can read old dataDelete a field; add a field with a defaultUpgrade consumers first
FORWARDOld readers can read new dataAdd a field; delete a field that had a defaultUpgrade producers first
FULLBothAdd or remove fields that have defaultsEither order
*_TRANSITIVESame, checked against every past version, not just the lastAs aboveNeeded when consumers replay old history
NONENo checksAnythingAvoid on shared topics

For pub/sub with unknown consumers, the producer usually deploys first and nobody can upgrade every consumer. That points to FORWARD or FULL. If consumers replay months of history, add TRANSITIVE, because a replaying consumer will meet version 3 and version 9 in the same run. BACKWARD is a common registry default. It suits a topic whose consumers you control, and it is worth checking deliberately rather than inheriting.

The rules depend on the format. In Avro, defaults are what make a field optional. In Protobuf, field numbers are the contract: never reuse one, and mark removed numbers as reserved. JSON Schema is the hardest to check well, because whether extra fields are allowed (an open or closed content model) changes what "compatible" means. Teams that choose JSON for convenience often end up with weaker checks than they think.

One limit no registry fixes: it checks shape, not meaning. Change total from dollars to cents and keep it an integer, and every check passes. Failure mode 3 below is that incident.

The outbox: one transaction, then a relay

Checkout must update its database and publish order.placed. Doing those as two separate writes is the dual write problem. Commit, then crash before publishing, and the order exists with no event. Publish, then fail the commit, and consumers act on an order that never existed. No retry ordering fixes this, because the two systems cannot commit together.

The transactional outbox moves the event into the same database transaction as the state change:

BEGIN;
  INSERT INTO orders (id, customer_id, total_cents, status, version)
       VALUES ('ord_7f3a', 'c_91', 14200, 'placed', 1);
  INSERT INTO outbox (event_id, aggregate_id, type, payload, created_at)
       VALUES ('evt_01HZX4K9M2', 'ord_7f3a', 'order.placed.v1', '{...}', now());
COMMIT;

Either both rows exist or neither does. A separate relay then reads the outbox and publishes to the broker. The relay can crash and retry, so it is at-least-once. That is why consumers dedupe on event_id. There are two ways to build the relay.

Polling relay. A worker selects unpublished rows in order, publishes them, and marks or deletes them. It is simple and portable. Its weak points are latency (the poll interval), load on the primary database, and a subtle ordering trap described in failure mode 2.

Log-based CDC relay. A connector such as Debezium reads the database's own change log (the Postgres WAL through a logical replication slot, or the MySQL binlog) and publishes outbox inserts as events. Debezium ships an outbox event router that turns outbox rows into properly keyed records on the right topic. Changes come out in commit order, with latency in the tens to hundreds of milliseconds and no polling queries. The cost is one more piece of infrastructure, plus replication-slot care (failure mode 4). The Change Data Capture lesson covers the log reading itself.

Why not CDC directly on the orders table and skip the outbox? You can, but then your table structure is your public event schema, which is the exact coupling the pub/sub lesson warned about. The outbox lets you publish a deliberate integration event while keeping the table free to change.

Choreography and orchestration, mechanically

The pub/sub lesson gave the rule: choreograph independent reactions, orchestrate dependent steps. Here is what each looks like when it runs.

In choreography, the "workflow" is the sum of subscriptions. Payment listens for OrderPlaced and emits PaymentCaptured. Inventory listens for that and emits StockReserved. Shipping listens for that. No single component holds the state "order ord_7f3a is at step 2 of 4." To answer "where is this order?", you have to read every service's state or rebuild the chain from events.

In orchestration, a coordinator holds that state explicitly. It sends commands (CapturePayment) and waits for replies or events. Workflow engines such as Temporal, AWS Step Functions or Camunda persist the coordinator's state at every step. A crashed coordinator then resumes exactly where it was, timers included. The coordinator knows when a step is overdue, which choreography cannot know without extra machinery.

The usual production shape is a hybrid. The order saga is orchestrated, because its steps depend on each other and must be undone in order. Each step publishes domain events, and email, analytics and loyalty choreograph off those. The orchestrator handles "must happen". The events handle "may want to know".

Tracing across asynchronous hops

Synchronous tracing works because each call carries the trace context in an HTTP header. With events, the broker sits in the middle and does not forward anything by itself. So the producer must write the W3C traceparent into the event (a Kafka header or a message attribute), and each consumer must read it when it starts processing.

The next question is how to link the spans. A consumer that processes one event can make its span a child of the producer's span. That gives the familiar single tree. But a consumer that processes a batch of 500 events has 500 parents, and a fan-out to 20 subscribers produces a tree of hours-long gaps. OpenTelemetry's messaging conventions handle this with span links. The consumer's span starts a new trace, or joins its own, and links to each producer span. You can still navigate between them without pretending a two-hour backlog was one request.

Traces get sampled, so they will not hold every event. The durable record is the correlation and causation chain in the envelope. Log event_id, correlationid and causationid on every handler, and "show me everything that happened because of request req_88c1" becomes a log query that works even for events whose traces were sampled away. The Distributed Tracing lesson covers sampling and propagation in general.

Deep Dive: Sizing and the Numbers

A consistency-window budget

"Eventually consistent" is not a requirement anyone can test. "The fraud view reflects an order within 2 seconds at p99, under 5,000 orders per second" is. Build the window from its parts and give each a budget:

StagePolling relay (500 ms interval)CDC relayWhat makes it worse
Commit → relay picks upavg 250 ms, max 500 mstens of msRelay down, slot lagging, long transactions
Relay → broker ack~5 ms~5 ms (batched)ISR shrink, broker overload
Broker → consumer readsms when caught upsameAny backlog: lag ÷ drain rate
Apply to view1–20 mssameSlow view store, lock contention
Healthy total~300–550 ms~50–150 ms

The healthy number is not the one that hurts. The third row is. If fraud is 480,000 events behind and drains at 1,200 per second net, every new order waits 400 seconds. The consistency window is now almost seven minutes, and nothing is technically broken. So the alert to set is on the end-to-end window, measured as "view updated at" minus the event's time. Watch the p99 per consumer.

Clock skew contaminates that measure. If the producer's clock is 300 ms ahead, every window looks 300 ms shorter. Keep hosts on NTP, and treat sub-second readings as approximate. For exact numbers, compare broker append timestamps with consumer timestamps on the same clock source.

Outbox table growth

At 5,000 orders per second and 2 KB per outbox row, the outbox grows at 10 MB/s. That is 36 GB per hour of sale. Rows that are never deleted cost more than the disk they use. They bloat indexes, slow the relay's "next unpublished" query and lengthen vacuum. Plan for it:

  • With a CDC relay, the outbox row is only needed long enough to reach the WAL. A common pattern inserts and then deletes the row in the same transaction, since the insert is already in the WAL. Or you delete it shortly afterwards. The table stays near empty.
  • With a polling relay, delete in batches right after publishing, or partition the table by hour and drop old partitions. Dropping a partition is much cheaper than deleting millions of rows.

Rebuild time is a recovery objective

The lesson says a new view replays 500 million events "in several hours." Make that a number you test. If one consumer instance applies 20,000 events per second with batched writes to its view store, 500 million events take 25,000 seconds, about seven hours. Twelve partitions and twelve instances in parallel bring that to about 35 minutes, if the view store can take 240,000 writes per second. Usually it cannot, so the view store sets the rebuild time, not Kafka.

That rebuild time is your recovery time when a view is corrupted. If the product needs that view back within 30 minutes, you need a faster store, a periodic snapshot to replay from, or a compacted topic that holds only the latest state per key.

The cost of a breaking change

Suppose order.placed must change incompatibly, for example splitting address into structured fields. Dual-publishing v1 and v2 for a 90-day deprecation window doubles the topic's write and storage costs for those 90 days. At 200 events per second and 2 KB, that is an extra 35 GB per day before replication. It is affordable. What is not cheap is the coordination: every subscriber in the catalog must confirm migration before v1 stops. With 20 subscribers, the slowest team sets the date. That is the argument for spending design effort up front on a schema you will not need to break.

Deep Dive: Failure Modes in Production

1. Ghost and missing events from dual writes

Symptom. Fraud scored an order that the orders database does not contain. Elsewhere, a handful of orders a day never reach email or analytics.

Mechanism. Checkout writes the database and calls the broker separately. A timeout after the publish but before the commit produces ghost events. A crash after the commit but before the publish produces missing ones.

Detect. A daily reconciliation job comparing order IDs in the database with event IDs in the topic. Both directions should be empty. Most teams discover this only when someone builds that job.

Fix. A transactional outbox, with a CDC or polling relay. Keep the reconciliation job afterwards as a permanent check.

2. The polling relay that skips rows

Symptom. With the outbox in place, a few events per million still go missing, mostly during peak load.

Mechanism. The relay runs SELECT ... WHERE id > :last_seen ORDER BY id. Sequence values are assigned when a row is inserted, not when its transaction commits. Transaction A takes id 101 and commits slowly. Transaction B takes id 102 and commits first. The relay reads 102, advances last_seen to 102, and never sees 101.

Detect. Gaps in published IDs that later appear in the outbox table. A reconciliation query for outbox rows older than a minute that are still unpublished.

Fix. Track a "published" flag per row instead of a high-water mark, so any unpublished row is found whatever its ID. Or only read rows older than a safety lag that is longer than your longest transaction. Or use CDC, which reads in commit order and does not have this problem.

3. A compatible schema change that breaks everyone

Symptom. The day after a release, loyalty awards 100 times the usual points and the finance dashboards show revenue up 100×. The registry check passed. No consumer threw an error.

Mechanism. Checkout changed total from dollars to cents. The type stayed an integer, so the change was structurally compatible and semantically breaking.

Detect. Data-quality checks on the consumer side: distributions of key fields compared to yesterday's. Contract tests that run consumers' sample expectations against the producer's new events in CI.

Fix. A meaning change is a new field (total_cents) or a new version, never an in-place change. Put units in field names. Make consumer-driven contract tests part of the producer's build for its most important subscribers.

4. A stalled CDC slot fills the primary's disk

Symptom. The checkout Postgres primary's disk usage climbs for hours, then the database stops accepting writes. Checkout is down, caused by a component that only publishes events.

Mechanism. A logical replication slot makes Postgres keep WAL until the slot's consumer confirms it. The Debezium connector stopped (a bad config deploy, an expired credential), so the slot stopped advancing, and Postgres kept every WAL segment since.

Detect. Retained WAL per replication slot (from pg_replication_slots) and the connector's own lag metric. Alert on retained WAL size, not just on connector health. A connector can look "running" while it confirms nothing.

Fix. Alert early. Set max_slot_wal_keep_size (Postgres 13 and later) so a dead slot is invalidated before it can fill the disk. You then have to re-snapshot that connector, which is much better than an outage. Drop slots you are not using.

5. Out-of-order events resurrect a cancelled order

Symptom. A customer cancels within seconds of ordering. The order shows "cancelled" in checkout but "active" in the support view, and the warehouse ships it.

Mechanism. order.placed and order.cancelled are on separate topics, or the same topic keyed differently. The cancel is processed first. Then the placed event arrives and upserts the order as active. Each event was valid. Their order was not.

Detect. Count events that arrive with an entityversion lower than the view's stored version. Today you are not counting them, which is why it looks random.

Fix. Keep one entity's lifecycle on one topic, keyed by its ID. In every view, store the last applied version and ignore anything older. Make the warehouse check the owner's current status before an irreversible step. That is the "exactly current reads go to the owner" rule from the lesson.

6. A choreographed order that nobody notices is stuck

Symptom. Customers write in about orders that were paid but never shipped. Every service's dashboards are green.

Mechanism. Inventory had a bug and stopped emitting StockReserved for orders containing pre-order items. Payment did its job. Shipping waits for an event that will never come. In choreography, "nothing happened" emits no signal, so no component is responsible for noticing.

Detect. A process monitor. That is a small consumer that tracks expected sequences (placed → paid → reserved → shipped) per order and raises an alert when a step is overdue. Or count orders by stage and alert on age.

Fix. Add the monitor, or recognise that this sequence is a workflow and move it to an orchestrator that owns timeouts and compensation. Then keep choreography for the independent reactions.

7. The trace stops at the broker

Symptom. A slow-receipt investigation finds checkout's trace ends at "publish order.placed, 4 ms". Email's handler appears as separate root traces with no link back. Nobody can prove where the 6 minutes went.

Mechanism. Only the producer was instrumented, or an intermediate hop (a stream processor, an SNS-to-SQS bridge, a retry topic) dropped the headers. Context crosses async hops only if every hop copies it.

Detect. The share of consumer spans with a link or parent. Aim for near 100% for each topic, and track it as a metric.

Fix. Instrument every hop with the messaging conventions. Make header pass-through a requirement for any component that republishes, including retry and dead-letter handlers. Log correlationid everywhere so investigations still work when traces were sampled away.

The default for a service that owns a relational database is outbox plus CDC once you have more than a couple of event types, and outbox plus polling before that. Dual write is acceptable only when losing or inventing an event is harmless, such as a metrics side channel.

Work down the table in order and stop as early as you can. Most changes should be the first row. The second row is the standard tool for a genuine break, because it keeps per-key order intact. Reach for a new topic only when the key or partitioning must change.

Choreography, orchestration or both

Ask three questions about a sequence. Does a later step depend on an earlier step's result? Must a failure undo earlier steps? Does anyone need to answer "where is order X?" in real time? Two or more yeses mean orchestration for that sequence. Everything that merely reacts to its outcomes stays choreographed. If you choreograph anyway, budget for the process monitor from failure mode 6. Without it you have an orchestrator-shaped hole and no orchestrator.

Thin, fat, or a reference to the payload

A third option sits between notification and full state: the event carries the important facts plus a link to a large or sensitive payload in an object store, sometimes called the claim-check pattern. A product's 2 MB description stays out of the topic, and access to it can be controlled and audited. Use it for large blobs or tightly regulated fields. Keep the fields most consumers need inline, or you have rebuilt the callback storm with a different endpoint.

Deep Dive: Design-Review Checklist

  1. Is each published event an integration event, separate from internal domain events? What translates between them?
  2. How does the event leave the producer? If the answer is "we publish after commit", where is the reconciliation proving nothing is lost?
  3. What is the dedup key, and is it assigned once at the source? Does it survive relay retries?
  4. Does every event carry a per-entity version, and does every view refuse older versions?
  5. Which registry compatibility mode, and is it transitive? Who can override it, and what does that require?
  6. How would a change in meaning (units, currency, timezone) be caught? Is there a contract test for the top subscribers?
  7. What is the consistency window budget per consumer, and how is it measured end to end? What is the p99 alert?
  8. Which reads must be exactly current, and do they go to the owner? Which screens show an "as of" time?
  9. For each multi-step sequence: who notices when it stalls? Name the orchestrator or the process monitor.
  10. Do traceparent and the correlation ID survive every hop, including retry and dead-letter paths?
  11. If the CDC connector stops for a weekend, what happens to the primary database's disk?
  12. How long does rebuilding the largest view take, and is that tested at production size?

Deep Dive: Senior Interview Follow-ups

"Why not just publish to Kafka after the database commit, with retries?"

Because there is a crash window between commit and publish that retries cannot cover. The process that would retry is the one that died. In the other order, publishing before commit can announce an order that then fails to commit. The two systems cannot commit together, so you make the event part of the database transaction (an outbox) and publish it from there, at least once. Consumers dedupe on the event ID.

"What is the difference between a domain event and event-carried state transfer, and when would you publish both?"

A domain event names a business fact (OrderCancelled) with the data relevant to it. ECST ships the entity's current state so consumers can overwrite their copy. Publish both when consumers need to know what happened (to send a cancellation email) and to keep a correct view without applying diffs. A common design is one event that carries the fact's name plus the post-change state.

"The registry says the change is compatible. Can it still break consumers?"

Yes. A registry checks shape, not meaning. Changing units, reusing a field for a new purpose, or narrowing an enum's real values all pass structural checks. Prevent it with explicit units in names, new fields for new meanings, and consumer-driven contract tests in the producer's pipeline. A non-transitive mode also lets a chain of individually compatible changes break a consumer replaying old data.

"How do you tell a user their order is placed if the views are eventually consistent?"

Read-your-writes for the writer. The checkout response returns the order from the owner's write, so the confirmation page never depends on a view. On later screens, either read from the owner for that user's recent orders, or have the view return its version and wait briefly until it reaches the version from the write. Other users and other services can live with the window, as long as the window is measured and bounded.

"How do you trace a request through a topic with a six-minute backlog?"

Put the W3C trace context and a correlation ID in the event headers at the producer, and copy them at every hop. Consumers start their own span and add a span link to the producer's span, rather than pretending six minutes is one request. Traces are sampled, so also log the event ID, correlation ID and causation ID in every handler. The full chain is then always one log query away.

"Choreography looks simpler. When does it stop being simpler?"

When steps depend on each other, need compensation, or need a status answer. At that point the workflow's state is spread across services and nobody owns timeouts, so stalls are silent. You then add a process monitor that tracks expected sequences, and that monitor is a read-only orchestrator. Usually it is cleaner to orchestrate the dependent core and choreograph the side reactions.

"An event schema must change incompatibly. Walk me through it."

First, try to make it compatible: add a new field instead of changing one. If it truly must break, publish the new version as a new event type on the same topic, so per-key order holds, and dual-publish from the outbox. Use the subscriber catalog to track each consumer's migration, set a deprecation date, and watch consumption of the old type fall to zero before you stop emitting it. Only re-keying or re-partitioning justifies a new topic.

"What can take down the producer in an event-driven design that should have decoupled it?"

The publishing path. A dual write with a synchronous broker call puts broker latency in checkout's request path. A stalled CDC replication slot can fill the primary's disk. An outbox table that is never trimmed slows every insert. A min.insync.replicas refusal blocks publishing if checkout treats it as fatal. Decoupling covers consumers. The path from the producer's database to the broker has to be engineered and monitored like part of the producer.
