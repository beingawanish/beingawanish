Deep Dive: Inside the Mechanism

The lesson's design has three parts: a shard key, a routing rule and something that does the routing. A real sharded system needs four more things the diagram leaves out. It needs a layer between keys and machines so data can move. It needs a way to find rows by something other than the shard key. It needs IDs that are unique without a single counter. And it needs a way to move data while the system runs. Every mature sharded database has an answer for each, and the answers are surprisingly similar.

Logical shards: the layer that makes moving possible

The lesson routes with hash(customer_id) % 4, so the formula names a machine. Almost no production system does that. Instead, they hash keys into a large, fixed number of logical shards (also called buckets, partitions, chunks, vshards or slots), and keep a small map from logical shards to physical machines.

This one idea removes most of the resharding pain from the lesson. Adding a fifth host means moving some whole logical shards to it and editing a few directory rows. No key's logical shard ever changes, so nothing is re-hashed. It also gives operators a handle for hot spots: a busy logical shard can be moved to a quiet host on its own.

The real systems all do a version of this:

  • Instagram (as described in its 2012 engineering post) created several thousand logical shards as Postgres schemas spread over far fewer physical servers. Its 64-bit IDs pack 41 bits of milliseconds, 13 bits of logical shard ID and 10 bits of per-shard sequence, so any ID tells you where its row lives.
  • Vitess divides a keyspace by ranges of a hashed key, written as keyranges such as -80 and 80- (the lower and upper halves of the hash space). The function that maps a column to that hash is a vindex. The VTGate proxy routes queries, and the shard map lives in a topology service such as etcd.
  • Citus splits each distributed table into shards (citus.shard_count, 32 by default) placed on worker nodes. Tables sharded on the same column with the same count are co-located: shard 7 of orders and shard 7 of order_items sit on the same node, so joins on the key stay local.
  • MongoDB splits a collection into chunks of key ranges (128 MB target size since 6.0), and a balancer moves chunks between shards. Config servers hold the map; mongos routers cache it.
  • DynamoDB hides the layer entirely. It splits partitions as they grow and documents limits per partition of about 3,000 read units, 1,000 write units and 10 GB. Your partition key's spread is what lets it split usefully.

Pick the logical shard count once, and pick it large. It caps how many hosts you can ever spread across, and changing it later is the same painful re-hash you were avoiding. 1,024 to 16,384 is a common range. The cost of too many is small: a larger directory, and per-shard overhead if each logical shard is a real database object like a schema.

Finding rows by something other than the key

The store is sharded by customer_id. Then login arrives: "find the customer with this email." The email does not tell you the shard. You have three options.

  • Local index, scatter the query. Each shard indexes email for its own rows. A lookup asks every shard. Correct and simple, but every login now costs N queries.
  • Global index as its own sharded table. Keep a table email → customer_id, sharded by email. A login does two single-shard lookups: email to customer, then customer to data. Vitess calls this a lookup vindex, and DynamoDB's global secondary indexes are the managed version. The catch is that the index lives on a different shard from the row, so keeping it consistent is a cross-shard write. DynamoDB updates GSIs asynchronously; Vitess can update lookup tables in the same transaction using its own multi-shard commit. Either way, think about what a stale index entry does.
  • Embed the shard in the identifier. Instagram-style IDs carry the shard, so any ID routes itself. This works for IDs you generate, never for email or phone numbers.

The same problem appears as uniqueness. A UNIQUE (email) constraint on each shard guarantees uniqueness per shard only. Two sign-ups with the same email that hash to different customer IDs land on different shards, and both succeed. Global uniqueness needs the global index table, with the unique constraint on its shard key.

IDs without one counter

An auto-increment column is a single counter on a single machine. Sharded systems need IDs that every shard can mint independently. The usual choices:

  • Snowflake-style: 41 bits of timestamp, 10 bits of machine ID and 12 bits of sequence. IDs sort roughly by time, which keeps B-tree inserts at the right edge of the index and cheap. Machine IDs must be assigned without collision, and a clock that jumps backward can mint duplicates unless the generator refuses to run.
  • Shard-embedded, as at Instagram: the shard bits double as routing.
  • UUIDv7: 128 bits with a timestamp prefix. No coordination at all, and it still sorts by time. Random UUIDv4 keys scatter inserts across the whole index, which costs cache and write amplification on large tables.

Note the trap: time-ordered IDs are good for index locality but terrible as a range shard key. Every new row has the largest ID, so every insert goes to the last range. Hash them if you shard on them.

What scatter-gather really does

A query without the shard key goes to every shard, and the router merges the answers. Some operations merge cleanly, and some do not:

  • Filters, counts and sums merge exactly: add the per-shard results.
  • Averages merge only if each shard returns sum and count, not its own average.
  • ORDER BY … LIMIT 10 needs the top 10 from each shard, then a merge. Fine for page 1. For page 50 with 20 rows per page, each shard must return its top 1,000 rows, which the router sorts to keep 20.
  • Distinct counts and percentiles do not merge from per-shard answers. You need sketches (HyperLogLog for distinct counts, t-digest for percentiles) or a separate analytics system.
  • Joins work only when both tables are co-located on the join key, or when one side is a small reference table copied to every shard (Citus's term; countries, currencies, product categories).

Moving data while the system runs

Every online move, whether Vitess's Reshard workflow, MongoDB's chunk migration or a hand-built one, follows the same five steps:

  1. Copy a consistent snapshot of the moving logical shard to the target, throttled to protect production.
  2. Catch up by streaming changes from the source's log (binlog, WAL, oplog) that happened after the snapshot. Keep streaming until the target is seconds behind.
  3. Verify by comparing row counts and checksums between source and target. Vitess ships VDiff for this.
  4. Cut over. Briefly stop writes to that logical shard, let the target apply the last changes, flip the directory, and resume. Done well, writes pause for seconds, and only for keys in the moving shard.
  5. Keep a way back. Vitess starts reverse replication from new to old at cutover, so rolling back is another directory flip. Delete the source copy only after a quiet period.

The dangerous step is cutover, because routing state is cached in many places. Any router that missed the directory change keeps writing to the old location. Correct systems attach a version (an epoch) to the directory and make the old shard reject writes for keys it no longer owns. The failure modes section shows what happens without that.

Deep Dive: Sizing and the Numbers

Choosing the shard count from three limits

The lesson split 2,500 writes per second and 4 TB over four shards. That sizes for today. A design review asks what the system needs in two years, and what each shard can hold. Assumptions: writes grow 50% a year, data grows 1.5 TB a year, and one primary handles about 2,000 writes per second of this workload before latency degrades.

  • Writes. In two years: 2,500 × 1.5 × 1.5 = about 5,600 per second. Run each primary at no more than half its limit, so 1,000 per second, leaving room for spikes and failover. That needs 6 shards.
  • Data. In two years: 4 + 3 = 7 TB. Cap each shard at about 1 TB so hot indexes fit in memory and a full restore stays short (see below). That needs 7 shards.
  • Memory. If the hot working set is 15% of data, 1 TB per shard means 150 GB of hot pages, which fits a 256 GB machine. At 2 TB per shard it would not.

The largest answer wins, rounded up: 8 physical shards, on 4,096 logical shards, 512 per host. Each physical shard is a primary with two replicas, so the cluster runs 24 databases. That count is the operational cost: 24 backup schedules, and at a rough two failovers per host per year, a failover about every two weeks somewhere in the fleet. Automation is not optional at this size.

Why shard size is a recovery decision

Restoring a shard from backup is mostly copying bytes. At a sustained 500 MB per second, which is optimistic for many cloud volumes:

  • 1 TB restores in about 35 minutes, plus log replay.
  • 4 TB, the unsharded table, takes about 2.3 hours, plus log replay.

The blast radius shrinks too. A failed 1 TB shard out of 8 affects one-eighth of customers for 35 minutes. Small shards make every bad day smaller and shorter. That benefit is often worth as much as the write capacity.

The floor that no shard count can lower

Hashing spreads keys, not load. Suppose the largest tenant produces 12% of all traffic. With 8 shards, the average shard carries 12.5%. The shard holding the big tenant carries the tenant's 12% plus its share of everyone else: 12% + 88% / 8 = 23%. That shard runs at 1.84 times the average.

Now go to 64 shards. The average falls to 1.6%, but the big tenant's shard still carries 12% + 88% / 64 = 13.4%, more than 8 times the average. Adding shards makes the hot shard relatively worse. Once one key exceeds roughly 1/N of the load, the fix has to change how that key is stored. More shards will not help.

Scatter-gather: load and tail latency

Fan-out multiplies load. A dashboard query without the shard key, at 500 requests per second across 8 shards, is 4,000 shard queries per second. Move to 32 shards and it becomes 16,000, with no new users.

Fan-out also multiplies tail latency. A scatter-gather query is as slow as its slowest shard. If each shard independently has a 1% chance of a slow response (its p99), the chance at least one is slow is 1 − 0.99N:

At 64 shards, a shard's p99 has become nearly the query's median. Hedged requests (send to a replica too if the first is slow) and per-shard timeouts with partial results help. Keeping hot queries single-shard helps more.

Deep pagination is the same effect in rows. Page 50 at 20 rows per page means each of 8 shards returns 1,000 rows, so the router sorts 8,000 rows to return 20. Use keyset pagination ("after this sort value") instead, as in Cursor-Based Pagination; each shard then returns only 20 rows past the cursor.

How long a resharding move takes

Going from 4 to 8 hosts with logical shards moves half the logical shards: 2 TB, rather than re-hashing everything.

  • Throttle each copy to 100 MB per second so production latency holds. Four source hosts copying in parallel give 400 MB per second.
  • 2 TB / 400 MB/s is about 1.4 hours of pure copy. In practice, plan for a day or two: copies pause at peak, verification takes time, and you cut over a few logical shards at a time.
  • Catch-up must outrun new writes. Each source produces its normal change stream (about 1/4 of 2,500 writes per second) while the copy runs, so the stream to catch up on is small compared with copy bandwidth.
  • Each cutover pauses writes for one logical shard (1/4,096 of keys) for a few seconds. Users almost never notice.

Deep Dive: Failure Modes in Production

1. The giant tenant's shard

Symptom. Shard 5 runs at 90% CPU while the other seven idle at 20%. Latency is fine for most customers and terrible for everyone who happens to share shard 5 with one large account.

Mechanism. The key is company_id, and one company grew to a seventh of total traffic. Every one of its rows hashes to the same logical shard. The balancer can move that logical shard to an empty host, but it cannot split it, because every key in it is the same key.

Detect. Per-shard QPS, CPU and p99 on one dashboard, so the outlier is obvious. Then find the key: sample queries and count the top shard-key values (top-k), or use the database's per-key stats where available. A shard whose load is high while its row count is normal points to a hot key, not a big one.

Fix. In order of effort: cache the tenant's hot reads; move its logical shard to a dedicated host; then change the key for that tenant only, for example (company_id, user_id) for its large tables, so its data spreads across many logical shards. Budget for the last step whenever tenants vary by orders of magnitude, which in B2B they always do.

2. The newest shard does all the work

Symptom. After moving the events table to range sharding on created_at, one shard handles all writes. The balancer moves data all day, and inserts slow down whenever it does.

Mechanism. Every new row has the largest timestamp, so it lands in the last range. MongoDB keeps splitting that last chunk and migrating the pieces, but writes always chase the newest one. The cluster pays migration costs and still writes to one machine. The same happens with an auto-increment ID or a Snowflake ID used as a range key.

Detect. Per-shard insert rate (one shard near 100%), chunk migration count, and range boundaries that keep growing at the top.

Fix. Hash the key, or put a well-spread field first: (device_id, created_at) keeps each device's history in time order while spreading devices across shards. If you need time-range scans, accept scatter-gather for them or send them to a separate analytics store.

3. One deploy multiplies the whole cluster's load

Symptom. Right after a release, CPU rises on all 8 shards at once. No single shard is hot. Database QPS has gone up eightfold for one endpoint.

Mechanism. A new "recent orders" widget queries orders by status and updated_at, without customer_id. The router cannot pick a shard, so it scatters every call to all shards. On a single database this would be one index scan; here it is eight, and it will be thirty-two after the next expansion.

Detect. Track fan-out per query shape. Vitess exposes scatter query counts; with your own router, log the number of shards each query touched and alert on new query shapes that touch all of them. A code review rule helps: every query on a sharded table names the shard key or justifies why not.

Fix. Add the key to the query if the caller knows it. If not, build a global index table for the access path, or serve the widget from a read model fed by change data capture.

4. Writes split across two shards during a move

Symptom. After a resharding cutover, a few hundred customers see missing orders, and some carts show two different states depending on which page they load.

Mechanism. The directory flipped logical shard 1,377 from host B to host E. Most routers refreshed within a second. Three application instances had a routing cache with a 5-minute TTL and kept writing to host B. Those writes landed on a copy no reader consulted any more, and reverse replication later conflicted with them.

Detect. Writes arriving at a shard for keys it no longer owns. That is cheap to check on the database side if each shard knows its own key ranges. Also compare row counts and checksums between old and new locations after cutover.

Fix. Version the directory. Every request carries the version its router used, and each shard rejects requests with a stale version or for keys it does not own. MongoDB does this with shard versioning: a mongos with a stale map gets an error and refreshes. Routers then retry with the new map. Rejecting is safe; silently accepting is how data forks.

5. Two accounts with the same email

Symptom. Password reset emails go to the wrong person. Support finds pairs of accounts with the same email address, even though the column has a unique constraint.

Mechanism. The unique index exists on each shard, so it only checks rows on that shard. Two sign-ups with the same email got different customer IDs, which hashed to different shards. Each shard saw a unique email. The constraint that used to be global became per-shard the day the table was split, and nobody noticed because tests run against a single database.

Detect. A periodic job that joins all shards' emails and counts duplicates. The first run after sharding usually finds some.

Fix. A global uniqueness table sharded by the unique value itself (email → customer_id), with the unique constraint there. Sign-up claims the email first, then creates the customer. If the second step fails, release or reuse the claim. Also run integration tests against a multi-shard setup, so per-shard semantics show up before production.

6. The migration that reached 23 of 24 shards

Symptom. One customer in eight gets errors on checkout after a release. The errors mention a missing column.

Mechanism. A migration added a column on every shard, one after another. Shard 6 was mid-failover when its turn came, the migration timed out, and the deploy pipeline logged a warning and continued. The new code assumes the column exists everywhere.

Detect. A schema fingerprint per shard (a hash of the catalog for the sharded tables), compared across the fleet and checked before deploys.

Fix. Treat schema changes as fleet operations with all-or-nothing reporting. Use an expand-and-contract sequence: add the column everywhere, verify every shard, deploy code that uses it, then remove old columns later. Tools such as Vitess's online DDL track migration state per shard for exactly this reason.

7. The partition that cannot be split

Symptom. In Cassandra, reads for one sensor time out and compaction falls behind on three nodes. In MongoDB, the balancer reports a jumbo chunk it cannot move.

Mechanism. All rows for one key value live in one partition. A sensor that has reported every second for three years has about 95 million rows in a single Cassandra partition, far past the commonly cited guideline of keeping partitions around 100 MB or less. In MongoDB, a chunk whose rows all share one shard key value cannot be split, so it cannot be balanced either.

Detect. Partition size histograms (nodetool tablehistograms in Cassandra), warnings about large partitions in logs, and jumbo flags in MongoDB's chunk metadata.

Fix. Add a bucket to the key so no single value grows without bound: (sensor_id, month) for time series, or (key, hash(id) % 16) for write-heavy single keys. Reads then query the few buckets they need. Choose the bucket size from the expected rows per key per period.

Deep Dive: Design-Review Checklist

  1. Have vertical scaling, replicas, archiving and a functional split been exhausted, with numbers showing which limit (writes, data, memory) forces sharding?
  2. What is the shard key, and what fraction of queries by volume include it? List the top queries that do not.
  3. Is there a logical shard layer, how many logical shards, and what is the maximum host count that implies?
  4. What is the largest single key's share of load and data today, and what happens when it doubles?
  5. How are secondary lookups and unique constraints handled across shards: global index tables, scatter, or embedded IDs? Who keeps global indexes consistent?
  6. How are IDs generated without a central counter, and what happens on clock skew?
  7. Which operations cross shards, and what replaces the transaction: a saga, an outbox, or a database-native distributed commit? See Saga and Two-Phase Commit.
  8. What is the resharding procedure (copy, catch up, verify, cut over, roll back), and has it been run in staging with production-sized data?
  9. How do routers learn about directory changes, and what stops a stale router from writing to the old location?
  10. How are schema migrations applied across the fleet, and how is a partial migration detected?
  11. Is there a per-shard dashboard (QPS, CPU, p99, size) and a top-k view of hot keys?
  12. Where do analytics and cross-shard reports run, so they do not scatter against production shards?

Deep Dive: Senior Interview Follow-ups

"Why not just pick 64 shards on day one so you never have to reshard?"

Because physical shards cost money and operations from day one: 64 primaries with replicas, 64 backup schedules, failovers every few days, and every scatter-gather query fanning out 64 ways, with worse tail latency. The right version of that instinct is logical shards: create 4,096 logical shards on day one and place them on 4 hosts. Growth then means moving logical shards, not re-hashing, and you pay for physical hosts only as you need them.

"How do you look up a user by email when you shard by user ID?"

Either scatter the lookup to all shards, which is fine for rare queries but not for login, or keep a global index table email → user_id, sharded by email. Login becomes two single-shard reads. The unique constraint on email moves to that table, because a per-shard constraint only checks one shard. The cost is a cross-shard write at sign-up and email change. Decide what a temporarily stale index entry means, and order the writes so a failure is harmless, for example by claiming the email first.

"Walk me through moving a logical shard to a new host without downtime."

Snapshot-copy it to the new host, throttled. Stream changes from the source's log to catch up. Verify with counts and checksums. Then cut over: pause writes for that logical shard only, apply the final changes, flip the directory entry with a new version, and resume. Start reverse replication so rollback is another flip. The part people miss is stale routers. Each shard must reject writes for keys it no longer owns, or with a stale directory version. A router with an old cache then gets an error and refreshes, instead of writing to the old copy.

"Your top tenant is 15% of traffic. Will doubling the shard count help?"

No. That tenant's shard carries at least 15% of load at any shard count, so going from 8 to 16 shards lowers the average to about 6% while the hot shard stays above 15%. You need to change how that tenant is stored: cache its reads, give it a dedicated host, or shard its large tables by a finer key such as (tenant_id, user_id). Many SaaS companies end up with a tenant directory, so big tenants can be placed by hand.

"A transfer debits an account on shard A and credits one on shard B. The credit fails. Now what?"

First, notice it should be rare: a good key keeps most transactions single-shard. When it is unavoidable, there are two families. A distributed commit (two-phase commit, which Citus and some Vitess setups provide) makes both shards commit or neither, at the cost of locks held across a network round trip and blocking if the coordinator dies. A saga records the debit, then the credit, each as a local transaction, with a compensating refund if the credit fails permanently. Each step must be idempotent, and the intent should be written to an outbox in the same local transaction as the debit, so a crash cannot leave the debit without the follow-up.

"Hash or range for an orders table that is queried by customer and by date?"

Hash on customer_id, because customer queries are the hot path and need to stay single-shard. Inside each shard, index (customer_id, created_at) so "this customer's orders this month" is a short range scan on one shard. Date queries across all customers belong in analytics, fed by change data capture, not on the production shards. Range-sharding on date would send all new orders to one shard and scatter every customer query.

"What changes about testing once you shard?"

Single-database tests stop representing production. Per-shard unique constraints, scatter queries, cross-shard transactions and routing changes all behave differently with more than one shard. Run integration tests against at least two or three shards, include a test that moves a logical shard mid-run, and fail tests that issue queries without the shard key on sharded tables unless they are explicitly allowed.
