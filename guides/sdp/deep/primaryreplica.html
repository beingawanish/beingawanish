Deep Dive: Inside the Mechanism

The lesson describes replication as log shipping: the primary sends its log, and replicas replay it. That sentence is true for every database in this section. What differs is how the log is shipped, how far each replica has got with it, and what the primary waits for before it says "saved." Those details decide your lag, your data-loss window and your failover story. We will look at PostgreSQL first, because its view of replication is the easiest to see, then MySQL and MongoDB.

Four positions on one log

Every change in PostgreSQL gets a place in the write-ahead log, identified by a log sequence number (LSN). An LSN is a byte position in the log, shown as two hex numbers like 3/A1B2C3D0. Because it is a position, you can subtract two LSNs and get a distance in bytes. That simple fact makes most replication monitoring possible.

On the primary, a process called the walsender streams log records to each replica. On the replica, a walreceiver writes them to the replica's own log, and a separate startup process replays them into the data files. So one change passes through four positions on its way to a reader:

  1. sent_lsn: the primary has sent the record over the network.
  2. write_lsn: the replica has written it to its operating system, not yet forced to disk.
  3. flush_lsn: the replica has fsynced it. It now survives a crash of the replica.
  4. replay_lsn: the replica has applied it. Only now can a query on the replica see it.

The primary reports all four in pg_stat_replication, one row per replica, along with write_lag, flush_lag and replay_lag as time intervals. When someone says "the replica is 2 seconds behind," ask which of these they mean. A replica can have every byte safely flushed and still be minutes behind on replay.

PostgreSQL: the knobs that matter

The diagram maps directly onto the setting that controls the data-loss window, synchronous_commit. It decides what a commit waits for before the client hears "saved":

  • off: not even the primary's own fsync. A crash can lose recent commits on a single machine, though the data stays consistent.
  • local: the primary's fsync only. Replication is fully asynchronous.
  • remote_write: the synchronous replica has written the record to its OS. That survives a Postgres crash on the replica, but not a power loss there.
  • on: the synchronous replica has flushed the record. Nothing acknowledged is lost if the primary dies. This is the usual meaning of "synchronous replication."
  • remote_apply: the synchronous replica has replayed it. A read on that replica right after the commit will see the write. This is the only level that gives read-your-writes on a replica for free, and it is the slowest.

Which replicas count as synchronous is set by synchronous_standby_names. If it is empty, on behaves like local. Two forms are worth knowing. FIRST 1 (r1, r2) waits for r1 by priority, with r2 as the fallback. ANY 1 (r1, r2) waits for whichever answers first, which is the quorum version of semi-sync from the lesson. A nice property: synchronous_commit can be set per session or per transaction. The checkout transaction can run with on while the page-view counter runs with local, on the same database.

Three more knobs shape day-to-day behaviour:

  • Replication slots. A slot makes the primary keep every WAL segment a replica has not yet confirmed. Without one, a replica that falls far behind finds its log already deleted and must be rebuilt from scratch. With one, an abandoned replica makes the primary keep WAL forever. max_slot_wal_keep_size (PostgreSQL 13 and later; unlimited by default) caps that, at the cost of breaking the slow replica instead of the primary.
  • hot_standby_feedback (off by default). Replay sometimes wants to remove row versions that a long query on the replica is still reading. By default, the replica waits up to max_standby_streaming_delay (30 seconds by default) and then cancels the query with "canceling statement due to conflict with recovery." Turning feedback on tells the primary to keep those row versions instead. Queries stop being cancelled, but a 2-hour analytics query on the replica now stops vacuum on the primary for 2 hours, and the primary's tables bloat.
  • Single-threaded replay. One startup process replays all WAL. A primary with 64 cores running writes in parallel can generate WAL faster than one process can apply it. That is the most common root cause of lag that "nobody can explain."

Promotion is pg_promote() or pg_ctl promote. The promoted replica starts a new timeline, a numbered branch of history. If the old primary comes back, its history has forked from the new one. pg_rewind can wind it back to the fork point so it can rejoin as a replica, which is far faster than a full copy.

MySQL: binlog, relay log and a semi-sync trap

MySQL replicates its binary log (binlog), not InnoDB's internal redo log. The binlog is a logical log: with binlog_format=ROW (the default since 5.7) it records the before and after images of each changed row. On the replica, a receiver thread copies the binlog into a local relay log, and one or more applier threads replay it. Since 8.0.27, replica_parallel_workers defaults to 4, so replay can run in parallel for transactions that did not conflict on the primary. That is a real advantage over Postgres's single replay process for write-heavy primaries.

With GTIDs enabled (global transaction IDs, one per committed transaction), each replica knows exactly which transactions it has. Failover tools can then pick the most complete replica and repoint the others without counting byte offsets by hand.

Semi-synchronous replication is a plugin, and its defaults hide the trap in this section. Two settings matter (renamed from master to source in 8.0.26):

  • rpl_semi_sync_source_wait_point: AFTER_SYNC (the default, called "lossless") waits for a replica's acknowledgement before committing in the storage engine. AFTER_COMMIT commits first, so other sessions can see a transaction that could still vanish on failover.
  • rpl_semi_sync_source_timeout: 10,000 ms by default. If no replica acknowledges within that time, the primary silently falls back to asynchronous and keeps going. Writes do not stall, which is the point. But your "zero data loss" guarantee is now off, and only the Rpl_semi_sync_source_status variable tells you.

Also be wary of Seconds_Behind_Source. It compares the timestamp of the event being applied with the replica's clock. If the receiver thread is stuck, the applier finishes its relay log, and the value happily reports 0 while the replica falls hours behind. Production teams write a heartbeat row on the primary every second (Percona's pt-heartbeat is the classic tool) and measure lag as "now minus the newest heartbeat the replica can see."

MongoDB: the oplog, write concern and rollback

A MongoDB replica set replicates through the oplog, a capped collection of idempotent operations. Secondaries pull from it, and they can pull from each other, not only from the primary. The durability question appears as write concern:

  • w: 1 acknowledges once the primary has the write. It is the asynchronous mode.
  • w: "majority" acknowledges once a majority of voting members have it. It has been the default since MongoDB 5.0 for most deployments.

The failure case shows why the default changed. Suppose the primary accepted writes with w: 1, then got cut off before they replicated. The rest elect a new primary, and the old one later rejoins. Its unreplicated writes conflict with the new history, so MongoDB rolls them back. It writes them to rollback files for a person to inspect, and they disappear from the database. With w: "majority", an acknowledged write is on a majority, and any electable new primary must have it.

Elections use a Raft-like protocol with terms, which are numbered epochs. electionTimeoutMillis defaults to 10 seconds, and MongoDB's documentation says a typical election completes within about 12 seconds. Reads have their own knobs. readPreference chooses primary or secondaries, readConcern: "majority" returns only data that cannot be rolled back, and causally consistent sessions make a secondary wait until it has caught up to the session's last write. That last feature is read-your-writes built into the driver.

Failover managers and fencing

Postgres and MySQL do not elect a new primary by themselves. Something outside the database decides. The common choices are Patroni for Postgres, Orchestrator or MySQL InnoDB Cluster for MySQL, and the cloud's own controller on RDS or Cloud SQL.

Patroni is a good model of how this is done safely. Each node runs a Patroni agent. The agents share a small strongly consistent store, usually etcd, Consul or ZooKeeper. The primary holds a leader key in that store with a time to live (ttl, 30 seconds by default) and renews it every loop_wait (10 seconds by default). Two rules then give you fencing:

  1. If the primary's agent cannot renew the key, for example because it is cut off from the store, it demotes its own database before the key expires. An isolated primary stops accepting writes on its own.
  2. A replica may promote itself only after it wins the expired key. Patroni also refuses to promote a replica more than maximum_lag_on_failover behind (1 MB of WAL by default), so it will not quietly promote a replica that would lose minutes of data.

The first rule depends on the old primary's agent being alive enough to demote. If the whole machine hangs and then wakes up, it could miss the deadline. That is why Patroni can use a hardware or kernel watchdog, which reboots the machine if the agent stops checking in. The general name for this is STONITH, "shoot the other node in the head": you prove the old primary is dead, rather than hoping it is.

The final piece is routing. Applications must find the new primary. Options include a DNS name the manager updates, a virtual IP, a proxy such as HAProxy that health-checks each node's role, or a driver that tries several hosts. In Postgres, libpq's target_session_attrs=read-write makes the client skip any host that is not the primary, and prefer-standby (PostgreSQL 14 and later) sends read sessions to replicas when one is up. Whichever you use, it is part of the fence. A client still connected to the old primary can keep writing to it, so the old primary must refuse writes, not just stop being advertised.

Deep Dive: Sizing and the Numbers

All the math below uses the bookstore's Tuesday numbers from the lesson: 8,000 reads per second, 300 writes per second, and machines that top out at 5,000 queries per second. Change the inputs to yours; the shape of each calculation is the point.

How many replicas, really

The lesson's two replicas each run at 4,000 of their 5,000 queries per second. That is 80% utilisation, and it has no room for failure. If one replica dies, the other gets 8,000 reads per second and falls over too. Worse, during a primary failover one replica becomes the primary, so you are a replica short at the exact moment things are already going wrong.

A sounder sizing rule has two parts. Plan each replica to run at most around 60% at peak, because queueing delay climbs steeply above that. Then add one replica so the plan still holds with one machine lost.

  • Usable capacity per replica: 5,000 × 0.6 = 3,000 reads per second.
  • Replicas for today's peak: 8,000 / 3,000 = 2.7, so 3.
  • Plus one for failure or promotion: 4 replicas.
  • If reads grow 40% a year, next year's peak is 11,200, which needs 4 + 1 = 5.

Four replicas at 2,000 reads per second each sit at 40%. Lose one and the other three run at 2,667 each, about 53%. That is the cluster you can sleep through.

Log volume, network and retention

Replication cost scales with WAL bytes, not with queries. Assume an average of 1.5 KB of WAL per write transaction (a row, two index entries and a commit record; full-page writes after each checkpoint can push this much higher).

  • Normal WAL rate: 300 × 1.5 KB = 450 KB per second, or about 39 GB per day.
  • Four replicas each pull a full copy: 1.8 MB per second of egress from the primary. That is trivial on a 10 Gbps link.
  • Cross-zone transfer is usually billed per GB. 39 GB × 4 replicas × 30 days is about 4.7 TB a month. Check your provider's price; it is small but not zero, and cross-region is more.

Now the bulk import. Say it generates 50 MB per second of WAL for 10 minutes. Four replicas pull 200 MB per second, about 1.6 Gbps. Still fine on the network.

The real risk is slot retention. Suppose one replica is down and its slot holds WAL. At the normal 450 KB per second, a 50 GB WAL volume lasts about 31 hours. During the import, the same 50 GB lasts under 17 minutes. Size WAL disk and max_slot_wal_keep_size against your worst write burst, not your average.

Lag is a queue: when it grows and how long it drains

Replay lag behaves like any queue. It grows when WAL arrives faster than the replica applies it, and it drains at the difference.

Assume one replay process applies about 30 MB per second of this workload's WAL. The real number varies a lot with record types and disk speed, so measure yours. During the 10-minute import, WAL arrives at 50 MB per second:

  • Backlog grows at 50 − 30 = 20 MB per second, reaching 12 GB at the end of the import.
  • By then the replica has applied 30 × 600 = 18 GB of the 30 GB generated. It is replaying WAL that the primary wrote around minute 6, so it is about 4 minutes behind in time.
  • After the import, WAL arrives at 0.45 MB per second. The backlog drains at about 29.5 MB per second: 12 GB / 29.5 MB/s is roughly 7 minutes.

So a 10-minute import produces up to 4 minutes of read staleness and 17 minutes of elevated lag in total. Chunking the import into batches with pauses, or throttling it to 25 MB per second, keeps lag near zero. That is a cheap fix, and it belongs in the import job's design, not in an incident review.

The data-loss window in writes, not milliseconds

The exposure from asynchronous replication is lag times write rate:

  • Normal lag of 50 ms × 300 writes per second = 15 acknowledged writes at risk.
  • During an 8-second lag spike: 8 × 300 = 2,400 writes at risk.
  • During the 4-minute import lag above: the import's own writes plus every order taken in those minutes.

That is why "async loses about 200 ms" is a typical number, not a bound. It is also why Patroni's maximum_lag_on_failover exists. Refusing to fail over automatically to a replica that is minutes behind is often the right call; a human should choose between "down for a while" and "lose four minutes of orders."

What synchronous replication costs per commit

Synchronous commit adds one network round trip, plus the replica's fsync for on, plus replay for remote_apply. Rough round-trip times (they vary by provider and region):

Second, cross-region synchronous replication is a business decision, not a config tweak. A checkout that makes four sequential commits gains 200 to 400 ms at cross-region distances.

The failover time budget

Break the lesson's 45 seconds into its parts. With Patroni defaults:

  • Detection: the leader key must expire. Up to 30 seconds after the primary's last renewal.
  • Election and promotion: a replica's agent notices on its next loop (up to 10 seconds) and promotes. Promotion itself takes a few seconds, longer if replay was behind.
  • Rerouting: proxies see the new role on their next health check. If routing uses DNS, add the record's TTL, and add the time for application pools to drop dead connections. Pools with long timeouts on dead TCP connections can add a minute by themselves.

So 30 to 60 seconds is realistic, and lowering the TTL trades faster failover for more false failovers on a brief network blip. At four unplanned failovers a year at 45 seconds each, write downtime is 3 minutes a year. Planned switchovers for upgrades usually add more than that, so practise them too.

Deep Dive: Failure Modes in Production

1. The replica that reports zero lag and serves yesterday

Symptom. Customers on some page loads see orders from hours ago. Others see current data. The lag dashboard says every replica is at 0 seconds.

Mechanism. One replica's receiver thread disconnected after a network change, or its slot was dropped. Its applier finished the local relay log and went idle. MySQL's Seconds_Behind_Source compares the event being applied with the clock; with nothing to apply, it shows 0 (or NULL, which many dashboards render as 0). The load balancer keeps sending it a quarter of all reads, because the replica is up and answering queries.

Detect. A heartbeat table: write now() on the primary every second and alert when any replica's newest heartbeat is more than a few seconds old. In Postgres, also alert when a replica disappears from pg_stat_replication, or its replay_lsn stops moving while the primary's position advances.

Fix. Make the read router health-check on heartbeat lag, not on "accepts connections." Remove a replica from the read pool above a lag threshold, say 5 seconds, and put it back only after it catches up.

2. The primary's disk fills from a replica nobody uses

Symptom. At 3 AM the primary stops accepting writes with "could not write to file pg_wal/…: No space left on device". Checkout is down. Every replica that is still running looks healthy.

Mechanism. Weeks ago someone created a replica for a one-off data migration, with a replication slot. The replica was deleted; the slot was not. The slot pins every WAL segment since its last confirmed position, so the primary kept all of it. Last night's import produced 50 MB per second of WAL and used the last of the disk.

Detect. Watch pg_replication_slots: alert on any slot with active = false for more than a few minutes, and on retained WAL per slot (pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)). Alert on WAL volume usage at 60%, not 95%.

Fix. Set max_slot_wal_keep_size so a dead replica breaks itself, not the primary. Give WAL its own volume. Make slot creation and deletion part of the replica's provisioning code, so they live and die together.

3. Split brain after a partition

Symptom. After a network incident, two machines report being primary. A day later, finance finds orders that exist in neither database's final state, and some customer records have two different versions.

Mechanism. A network partition separated the primary from the failover manager but not from half of the application servers. The manager promoted a replica. The old primary had no self-fencing, so it kept accepting writes from the application servers that could still reach it. Both histories advanced. When the partition healed, the old primary's writes were on a timeline the new primary never saw.

Detect. Alert whenever more than one node reports pg_is_in_recovery() = false (or MySQL read_only = OFF) in the same cluster. Track the timeline ID or term; a node accepting writes on an old timeline is a red alarm.

Fix. Fencing before promotion, always: leader leases where the primary demotes itself when it cannot renew, a watchdog for the frozen-machine case, and clients that verify the role on connect (target_session_attrs=read-write). Recovering the lost writes is manual. Extract them from the old primary's WAL or binlog, then reconcile by business key. Practise this once, so you know it is painful enough to prevent.

4. Semi-sync that quietly became async

Symptom. The design document says the payments database has zero data loss on failover. After a primary hardware failure, 90 seconds of acknowledged payments are missing on the promoted replica.

Mechanism. Earlier that day, both semi-sync replicas were slow for a few seconds during a backup. MySQL waited the default 10-second rpl_semi_sync_source_timeout, then switched to asynchronous replication so writes would not stall. Replication caught up, but the switch back only happens once a replica acknowledges again, and the failure hit during a second slow period. For those 90 seconds the cluster was async.

Detect. Alert on Rpl_semi_sync_source_status = OFF and on increases in Rpl_semi_sync_source_no_tx (commits that were not acknowledged by a replica). In Postgres, the equivalent check is sync_state in pg_stat_replication: a cluster with no row in state sync or quorum is not synchronous.

Fix. Decide explicitly which failure you prefer. For true zero loss, set a very high timeout and accept that writes stall when no replica can acknowledge. Then run at least two candidate replicas so one slow machine does not stall you. Otherwise, document the guarantee honestly as "zero loss except during degraded periods, which page us."

5. One sick replica stops every write

Symptom. Checkout hangs. The primary's CPU is idle. Connections pile up in state "waiting for SyncRep" until the pool is exhausted.

Mechanism. The team turned on synchronous replication with synchronous_standby_names = 'r1': one named replica. Its disk failed and the replica stopped acknowledging. With synchronous_commit = on, every commit now waits forever for an acknowledgement that cannot come. The safety feature became the outage.

Detect. Wait events in pg_stat_activity (SyncRep), commit latency p99, and the sync replica's absence from pg_stat_replication.

Fix. Never depend on exactly one synchronous replica. Use ANY 1 (r1, r2) or FIRST 1 (r1, r2) so a second replica can take over the role. Patroni's synchronous_mode manages this list for you. Keep synchronous_commit at local for tables that do not need the guarantee, so a stall only blocks what must block.

6. Analytics on the replica: cancelled queries or a bloated primary

Symptom. Either the data team complains that reports fail with "canceling statement due to conflict with recovery," or, after someone "fixed" that, the primary's tables grow 30% in a week and its queries slow down.

Mechanism. A 2-hour report on a replica reads old row versions. Vacuum on the primary removes those versions, and the removal arrives in the WAL. Replay must either wait for the query, which grows replay lag past max_standby_streaming_delay, or cancel the query. Turning on hot_standby_feedback asks the primary not to remove those versions, which blocks vacuum for the length of the longest replica query.

Detect. pg_stat_database_conflicts on the replica for cancellations. On the primary, n_dead_tup growth and the age of backend_xmin reported for replicas in pg_stat_replication.

Fix. Separate the jobs. Serve user reads from replicas with feedback off and a short delay limit. Give analytics its own replica with a long max_standby_streaming_delay, accept that it lags during long reports, and keep it out of the user read pool. Better still, feed analytics from change data capture into a warehouse.

7. The failover that works, then the new primary falls over

Symptom. Failover completes in 40 seconds. Then write latency stays 10 times normal for 15 minutes, and connection errors spike.

Mechanism. Two effects stack. The promoted replica's memory held the pages its read traffic used, not the pages the write path uses, so the write path runs from disk until the cache warms. Meanwhile, every application instance reconnects at once. Hundreds of pools open their full connection count in the same second, and each new Postgres connection is a process to fork. The replica also lost its old read traffic to the survivors, which are now one machine short.

Detect. Buffer cache hit ratio and disk reads on the new primary, connection rate, and per-replica CPU right after failover. Failover drills should record these, not just "promotion succeeded."

Fix. Put a pooler such as PgBouncer between the application and the database, so reconnects hit the pooler, not Postgres. Add jitter to client reconnects. Use pg_prewarm where it helps, and size replicas with the N+1 headroom from the sizing section so losing one to promotion does not overload the rest.

Where the read/write split lives

There are three common places. The application holds two connection pools and picks one per query; this is explicit and easy to reason about, but every service must do it right. A proxy such as ProxySQL (MySQL) or Pgpool-II (Postgres) inspects queries and routes them; applications stay simple, but the proxy guesses intent from SQL and is one more hop to run. A driver (libpq's target_session_attrs, MongoDB's readPreference) handles role discovery but leaves query choice to you. Most teams end up with explicit routing in the application's data layer, because only the application knows which reads must be fresh.

Deep Dive: Design-Review Checklist

  1. Is the bottleneck reads, writes or data size? Show the read/write ratio and growth rate, not an impression.
  2. How many replicas, at what utilisation, and does the plan still hold with one replica lost or promoted?
  3. Which data needs zero loss on failover, and which replication mode and setting (synchronous_commit, write concern, semi-sync timeout) delivers it? What happens to writes when the synchronous replica is unavailable?
  4. How is lag measured: heartbeat or LSN difference, not a single built-in "seconds behind" value? What threshold removes a replica from the read pool?
  5. Which reads must see the user's own writes, and which technique handles them? What happens during a 60-second lag spike?
  6. What fences the old primary: lease, watchdog, STONITH? Can a client still connected to it keep writing?
  7. What is the failover time budget, broken into detection, promotion and rerouting? When was it last measured in a drill?
  8. Will automatic failover refuse a replica that is too far behind? Who decides in that case, and how are they paged?
  9. Are replication slots tied to replica lifecycle, capped, and alerted on? Is WAL disk sized for the worst write burst?
  10. Where do analytics and backups run, and how are recovery conflicts handled without bloating the primary?
  11. How do bulk jobs (imports, backfills, migrations) avoid creating minutes of lag?
  12. After failover, how does the old primary rejoin (pg_rewind, rebuild), and how would you recover writes it accepted after the split?

Deep Dive: Senior Interview Follow-ups

"Your replica lag graph says 0 ms, yet users see stale data. How can both be true?"

Because the metric measures the wrong thing. MySQL's Seconds_Behind_Source compares the event being applied with the clock, so a replica whose receiver has stopped shows 0 once its relay log is empty. In Postgres, a dashboard might show flush_lag while reads depend on replay_lag. The robust measure is end-to-end: write a heartbeat timestamp on the primary every second and read it on each replica. Lag is the age of the newest heartbeat the replica can see. That catches a stopped stream, a stuck replay and clock-based artefacts with one check.

"Why not just make all replication synchronous and be done with data loss?"

Because every write then waits for the slowest required replica, and a replica problem becomes a write outage. Fully synchronous to every replica also means one sick replica stalls everything. The practical answer is quorum: wait for one of two or more candidates (ANY 1), keep others async for read scaling, and set the guarantee per transaction, so a page-view counter does not pay the checkout's price. And remember the latency cost: cross-zone adds a few milliseconds per commit, cross-region adds tens.

"The primary dies. Replica A is 2 MB behind, replica B is 40 MB behind. Walk me through failover."

First fence the old primary so it cannot come back writing. Then promote the replica with the most WAL: A. Its flush position, not its replay position, decides what survives, though it must finish replaying before it serves as primary. Then repoint B to follow A; with GTIDs or Postgres timelines B can stream the difference rather than rebuild. Anything the old primary acknowledged beyond A's position is lost under async replication, so log the old primary's last known LSN to size the loss. If even the best replica is minutes behind, an automatic manager should stop and page a human rather than promote silently.

"How do you give read-your-writes without sending all of a user's reads to the primary?"

Capture the commit position after the write: pg_current_wal_lsn() in Postgres, the GTID in MySQL. Store it in the user's session or a cookie. On each read, pick a replica whose pg_last_wal_replay_lsn() is past that position, or ask the replica to wait briefly (WAIT_FOR_EXECUTED_GTID_SET with a timeout), and fall back to the primary if none is ready. Reads stay on replicas almost always, and correctness no longer depends on guessing how long lag lasts. MongoDB gives you this through causally consistent sessions.

"What exactly prevents split brain in a Patroni cluster? What could still go wrong?"

A leader key with a TTL in a consensus store. Only the holder may be primary. A primary that cannot renew the key demotes itself before it expires, and a replica can promote only after winning the expired key. What can still go wrong: a machine that freezes (a long GC-like pause, a hung hypervisor) and wakes up after the TTL, still believing it is primary. That is why Patroni supports a watchdog that reboots the node if the agent misses its deadline. Clients should also check the role on connect, so a stale primary that does wake up finds no one willing to write to it.

"A team adds replicas, and the primary's write throughput drops. Why?"

Each replica is another walsender streaming the full WAL, another consumer of network and CPU on the primary. With synchronous or quorum settings, more replicas in the synchronous set can mean waiting on slower ones. With slots, a slow new replica makes the primary keep more WAL. And with hot_standby_feedback, long queries on any replica block vacuum on the primary, so tables bloat and every write does more work. Replicas are never free for the primary; they are cheap when async and well-behaved.

"When would you deliberately delay a replica?"

As protection from humans, not hardware. A replica with recovery_min_apply_delay = '1h' in Postgres (or SOURCE_DELAY in MySQL) applies changes an hour late. If someone runs DROP TABLE orders at 14:00, every normal replica drops it within milliseconds, but the delayed one still has it until 15:00. You pause its replay, copy the table out, and restore. It is cheaper and faster than a point-in-time restore from backups, and it must never serve user reads.
