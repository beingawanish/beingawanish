Deep Dive: Inside the Mechanism

The lesson explains what a trace is and why you want one. This section follows a single span from the line of code that creates it to the screen that shows it. Most tracing problems in production live in one of these hops, and the knobs on each hop decide what you keep, what you lose, and what it costs.

The header, byte by byte

W3C Trace Context defines two headers. The one that matters most is traceparent:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └ flags: 01 = sampled
             │  │                                └ parent span ID: 16 hex chars (8 bytes)
             │  └ trace ID: 32 hex chars (16 bytes)
             └ version

Every hop reads it, creates its own span with a fresh span ID, and sends a new traceparent downstream with the same trace ID and its own span ID in the parent slot. That is the whole tree-building protocol. The collector never has to guess. Each span names its parent explicitly.

The second header, tracestate, carries vendor-specific key-value pairs alongside. A third, separate W3C header, baggage, carries application key-values such as tenant=acme to every downstream service. Baggage is useful and dangerous in equal measure. Every byte you add rides on every downstream call, and anything you put there leaves your process boundary, including to third parties if you are careless.

Older systems use Zipkin's B3 headers (X-B3-TraceId and friends, or the single b3 header). OpenTelemetry propagators can read and write several formats at once, which is how mixed fleets migrate without breaking traces.

What a span actually contains

A span in the OpenTelemetry data model holds:

  • Identity: trace ID, span ID, parent span ID.
  • Name: a low-cardinality label such as GET /orders/{id}, never GET /orders/8812.
  • Kind: SERVER, CLIENT, PRODUCER, CONSUMER or INTERNAL. The backend uses kind to pair a client span with the server span it caused and to draw service-map edges.
  • Start and end timestamps. The duration is measured with one process's clock, which matters for clock skew below.
  • Status: unset, ok, or error, plus a message.
  • Attributes: typed key-values following semantic conventions (http.request.method, db.system, server.address and so on). Conventions are what let a backend recognise "this is a database call" across languages.
  • Events: timestamped points inside the span, such as an exception with its stack trace.
  • Links: references to spans in other traces. A batch consumer that processes 50 messages from 50 different producers cannot have 50 parents, so it links to them instead.
  • Resource: who emitted it, such as service.name, version, host, pod.

SDKs cap attributes, events and links per span (128 each by default in OpenTelemetry) so that one buggy loop cannot build a 50 MB span.

Inside the process: context, not headers

Headers carry context between processes. Inside a process, the SDK keeps the "current span" in a context object: thread-local storage in Java, contextvars in Python, AsyncLocalStorage in Node, an explicit context.Context argument in Go. Instrumentation reads the current span to set the parent of each new one.

This is where most broken traces really break. When work hops to another thread, an executor, a callback or a coroutine the runtime does not know about, the context does not follow automatically. The new span has no parent and starts a fresh trace. Auto-instrumentation wraps common executors to carry context across, but a homemade thread pool or a reactive library it does not recognise will silently drop it.

The export path: SDK, collector, sampler, store

In the SDK. Ending a span does not send it. The span goes into a BatchSpanProcessor with a bounded queue. The OpenTelemetry defaults are a queue of 2,048 spans, batches of up to 512, and an export every 5 seconds. When the queue is full, new spans are dropped. That is deliberate: tracing must never block or crash the application. It also means a traffic spike can quietly thin your traces exactly when you need them. The SDK reports dropped-span counts. Graph them.

To the agent. The SDK exports over OTLP, gRPC on port 4317 or HTTP on 4318, usually to a collector on the same node or in a sidecar. Exporting locally keeps the application's export fast and moves retries, batching and authentication out of the app.

To the gateway. If you only head-sample, agents can export straight to storage. Tail sampling changes that. The sampler needs every span of a trace before it can judge the trace, and those spans come from twelve services on twelve nodes. So agents use a load-balancing exporter that hashes the trace ID and sends all spans of one trace to the same gateway collector.

The tail sampler. The OpenTelemetry Collector's tail_sampling processor holds each trace in memory for decision_wait (30 s by default) after its first span arrives, up to num_traces traces (50,000 by default). Then it evaluates policies such as status_code (keep errors), latency (keep anything over a threshold), probabilistic (keep a baseline), rate_limiting and attribute matches, often combined in a composite policy with budgets per rule. A span that arrives after the decision has been made is handled on its own, so very long traces can end up partly kept.

Metrics before sampling. A good pipeline computes request rate, error rate and latency histograms from all spans before the sampler discards most of them. The Collector's span-metrics connector does this. Computing latency percentiles from tail-sampled traces is a classic mistake. You deliberately kept the slow ones, so the stored data says your p50 is terrible.

How head sampling stays consistent across services

Head sampling only produces complete traces if every service makes the same decision. Two mechanisms make that happen. The root decides and sets the sampled flag in traceparent, and downstream services use a ParentBased sampler that simply follows the flag. And the ratio sampler (TraceIdRatioBased) derives its decision from the trace ID itself rather than a random number, so two services that both root-sample the same ID agree.

The flag also creates a trust question. A request from the public internet can arrive with traceparent already set and the sampled flag on. If your edge honours it, anyone can force you to record and store every request they send. Gateways should usually restart the trace at the edge, or at least ignore the external sampled flag, and keep the external ID as an attribute or link if partners need correlation.

Queues, batches and fan-in

The lesson says context travels in message metadata. In practice that means Kafka record headers, AMQP message properties, or SQS message attributes, each carrying traceparent. Three details matter in review:

  • Parent or link. For one message handled by one consumer, making the consumer span a child of the producer span gives a single waterfall with the queue wait visible as a gap. For batch consumers, or when a message waits hours, use span links instead. Otherwise you get traces that last a day and never complete.
  • Retries and dead letters. A redelivered message carries the same context, so every attempt appears in the same trace. That is exactly what you want when debugging a poison message.
  • Header loss. Anything that copies a message's body without its headers breaks the chain: a bridge to another broker, a stream processor that re-emits records, a CDC pipeline. Those hops need explicit propagation.

Joining the three pillars

The lesson's left-to-right diagnosis flow needs physical joins between pillars, not just a shared idea. Two mechanisms provide them. Log correlation: the logging library writes the current trace ID and span ID into every log line, so a span links to exactly its logs. Exemplars: a latency histogram bucket stores the trace ID of one example request that landed in it. Clicking the spike on a p99 graph then opens a real trace from that spike. For exemplars to be useful, the exemplar trace must have been kept, which is one more argument for keeping slow traces in tail sampling.

Deep Dive: Sizing and the Numbers

The lesson's fleet does 40,000 requests per second with about 40 spans per request: 1.6 million spans per second. Here is what that means for each tier. Assume an average encoded span of about 1 KB with attributes. Real spans range from a few hundred bytes to several KB, so measure yours.

Ingest bandwidth

1.6 M spans/s × 1 KB = 1.6 GB/s leaving the applications, before any sampling. OTLP over gRPC with compression typically shrinks that several-fold on the wire, but the collectors still have to decompress and process every span. Agent-to-gateway traffic is the same volume again. If that traffic crosses availability zones, the cross-zone transfer charge alone can rival the storage bill. Keep gateways zone-local where you can.

Tail-sampler memory

The sampler has to hold every trace until its decision. Memory needed is roughly ingest rate times decision wait:

decision_waitSpans in bufferRaw memory (1 KB/span)With 2x overhead for in-memory structures
30 s (default)48 M48 GB~96 GB
10 s16 M16 GB~32 GB
5 s8 M8 GB~16 GB

The 2x overhead is an assumption. Decoded spans in memory are larger than their wire form, so measure under load. Spread over 16 gateways, a 10-second wait is about 2 GB of buffer each, plus headroom. Also check the num_traces limit. At 40,000 traces per second and a 10-second wait you have 400,000 live traces. The default of 50,000 would evict traces before they are decided.

How long should the wait be? Longer than nearly all your traces. If checkout's p99.9 is 6 seconds, a 10-second wait captures almost every trace whole. The 4.2-second outliers the lesson hunts are covered with room to spare. A 30-second default buys little except memory.

Storage after sampling

The lesson keeps about 2,000 spans per second in normal periods:

2,000 spans/s × 1 KB × 86,400 s ≈ 173 GB/day before compression. With 14 days of retention that is about 2.4 TB raw. Columnar or object-storage backends such as Grafana Tempo often compress span data by several times, so a few hundred GB to 1 TB on disk is a plausible range. During an incident the error and latency policies keep far more. Size for 5 to 10 times normal for a few hours, or put a rate limit on each policy so an outage cannot fill the store.

Compare with keeping everything: 1.6 GB/s × 86,400 ≈ 138 TB/day. That is why the lesson calls 100% retention a misuse.

Overhead inside the application

Creating a span, setting a few attributes and queueing it costs on the order of a microsecond to a few microseconds in most SDKs. At 40 spans per request that is well under a millisecond. Export work happens on a background thread. In practice teams usually see low single-digit percent CPU overhead from tracing, but it varies with language, attribute count and how much auto-instrumentation is on. Two things cost far more than span creation: capturing large attributes (full SQL text, request bodies) and creating spans inside hot loops. Both are design choices you can review.

Propagation cost

A traceparent header is 55 characters of value. Nothing. Baggage is different. Ten baggage entries of 40 bytes each add 400 bytes to every downstream call. On a request that fans out to 40 calls, that is 16 KB of extra headers for one user action. Some proxies also cap total header size (often around 8 to 16 KB depending on the server), and baggage growth is a common way to hit 431 errors in deep call chains.

Deep Dive: Failure Modes in Production

The lesson's Check Yourself covers one service that stopped forwarding traceparent. These are its relatives.

1. Traces that end at a thread pool

Symptom. Traces for the order service show the inbound request span and nothing else, even though it calls three services. Separate root traces appear for those calls, each with a single span.

Mechanism. The service hands work to a custom executor or reactive scheduler that auto-instrumentation does not wrap. The worker thread has no current span, so the outbound client creates a root span and a new trace ID. This is propagation failure inside the process, not across the network.

Detection. Rising count of root spans whose kind is CLIENT. A real root is almost always a SERVER or CONSUMER span at the edge. A client span as root means a parent was lost.

Fix. Wrap the executor with the SDK's context-propagating wrapper, or capture the context when submitting the task and restore it in the worker. Add the root-CLIENT count to the trace-completeness dashboard the lesson recommends.

2. Children that start before their parents

Symptom. In the waterfall, the payment server span begins 40 ms before the checkout client span that called it. Or a child appears to outlast its parent.

Mechanism. Each span's start and end times come from its own host's clock. Durations within one span are fine, because they use one clock. Positions between spans from different hosts carry the hosts' clock offset. NTP usually keeps that within a few milliseconds, but a misconfigured or recently started host can be off by much more. This is the same problem the incident's log-matching engineers hit, and the reason the vector clocks lesson distrusts wall time.

Detection. Count server spans that start before their client parent. Track clock offset per host as a metric (from chronyc tracking or the node exporter).

Fix. Fix the clocks first. Some backends, including Jaeger, apply a skew adjustment that shifts a child to fit inside its parent. That makes the picture tidy but can hide a real problem. Read durations as reliable and cross-host positions as approximate to within your clock error.

3. Tail sampling keeps half a trace

Symptom. Error traces are kept, but many are missing whole branches. The fraud service's spans are absent even though fraud was called.

Mechanism. One of three causes. Agents are not routing by trace ID, so different spans of the same trace reach different gateways and each gateway decides on its fragment. Or the gateway tier just scaled up or down, the hash ring moved, and traces in flight were split. Or spans from a slow branch arrived after decision_wait, after the decision had been made without them.

Detection. Kept traces with a child span whose parent ID points at a span that is not in the trace. Track that as a percentage of kept traces. Correlate with gateway scaling events.

Fix. Use the load-balancing exporter keyed on trace ID. Scale the gateway tier slowly and accept a brief dip during changes. Set decision_wait above your long-tail trace duration. For pipelines with very long traces, use span links to cut them into shorter linked traces.

4. Spans dropped exactly when it matters

Symptom. During last night's spike, which is the thing you are investigating, traces are sparse and incomplete. In quiet hours they are perfect.

Mechanism. The SDK's batch queue (2,048 spans by default) filled faster than the exporter could drain it, so it dropped new spans. Or the collector's memory_limiter refused data under memory pressure, which is correct behaviour that protects the collector, but the data is gone. Tracing pipelines are designed to lose data rather than hurt the application. That is the right default, and it biases your evidence towards calm periods.

Detection. SDK dropped-span counters, collector refused-span and queue-size metrics, exporter failure counts. Alert when drops exceed a small fraction of throughput.

Fix. Size the queue and collectors for peak, not average. Export to a local agent so the app's export path is short. Keep the metrics pipeline separate from traces, so your alerts never depend on the tracing pipeline staying healthy under load.

5. Span names that explode cardinality

Symptom. The service list in the tracing UI lists hundreds of thousands of operations. The span-metrics pipeline runs out of memory. The metrics bill jumps.

Mechanism. Someone named spans with raw paths: GET /orders/88121, GET /orders/88122. Span names should be route templates. Span metrics then create one time series per unique name, so a million order IDs means a million series.

Detection. Count distinct span names per service per day. Anything that grows with traffic rather than with code is wrong.

Fix. Use the framework's route template (GET /orders/{id}) as the span name and put the ID in an attribute. Have the collector drop or rewrite span names that match an ID pattern, as a safety net.

6. Personal data in the trace store

Symptom. An audit finds email addresses, session tokens and card fragments in span attributes, searchable by everyone with tracing access and kept for 14 days.

Mechanism. Auto-instrumentation recorded full URLs with query strings (?email=…&token=…), SQL statements with literal values, or request headers including Authorization. Each looked harmless to the engineer who switched it on. Baggage can also leak: an entry set for internal routing gets sent to a third-party API along with the outbound call.

Detection. Run a scanner over a sample of stored spans for patterns such as emails, tokens and card numbers. Review the list of attribute keys per service.

Fix. Scrub in the collector with attribute and redaction processors, using an allowlist of keys rather than a blocklist. Turn off SQL literal capture or use sanitised statements. Strip baggage at the edge of your network on outbound calls. Treat the trace store as a production data store with access control and retention policy, as the lesson's link to the EDA privacy rule implies.

7. Dashboards built on sampled data

Symptom. The tracing UI's latency chart for checkout shows a p50 of 2.1 seconds. Real users and the metrics system say 140 ms.

Mechanism. The chart is computed from stored traces, and the tail sampler deliberately kept the slow ones. The stored set is a biased sample by design. The same bias affects error rates computed from traces.

Detection. Compare trace-derived percentiles with metric-derived ones for the same service and window.

Fix. Compute rate, error and duration metrics from all spans before sampling, using span metrics in the collector or ordinary application metrics. Use stored traces for examples and structure, never for population statistics.

Choosing a sampling design

Start from the questions you need traces to answer. "Why did this specific customer's request fail?" needs tail sampling on errors, and possibly forced sampling for flagged customers or debug headers from trusted callers. "What is the shape of normal traffic?" is answered well by a small head baseline. "How many requests did X?" should not be answered by traces at all. That is a metrics question.

A design that works at the lesson's scale: ParentBased head sampling at 100% at the edge (so every service creates spans), a tail-sampling gateway that keeps all errors, everything over the route's latency objective, a 0.1% baseline and a per-route rate limit, and span metrics computed before the sampler. If the tail tier is too expensive, drop the edge head rate to 10% and accept that one in ten outliers is visible. That is still enough to find a systematic problem like the fraud retries, which affected many requests.

Where traces stop and profiling starts

The lesson sends monoliths to a profiler. The boundary also runs inside a microservice. A span says "pricing took 400 ms". It does not say which function burned the CPU. Continuous profilers sample stacks across the fleet, and some can tag samples with the active span ID. That lets you go from a slow span to the code that was running during it. Treat it as the next step after tracing, for CPU-bound spans that have no child spans to explain them.

Deep Dive: Design-Review Checklist

  1. Where is the root span created, and what does the edge do with a traceparent that arrives from the public internet?
  2. Which propagation formats are enabled (W3C, B3), and do they match every language, proxy and gateway in the request path?
  3. How does context cross queues, stream processors, CDC pipelines and broker bridges? Is the consumer a child or a link, and why?
  4. Which in-process boundaries could drop context: custom executors, reactive schedulers, callbacks? How would you notice?
  5. What is the sampling policy, written down per rule, and what is the cost at peak traffic and at incident traffic?
  6. If tail sampling: how are spans routed by trace ID, what are decision_wait and num_traces, and how much memory does the gateway tier need?
  7. Are request, error and latency metrics computed before sampling? Which dashboards read from stored traces, and are they biased?
  8. What do the SDK and collectors do when they are overloaded, and which metrics show dropped or refused spans?
  9. Which attributes may contain personal data or secrets, and where in the pipeline are they removed? Is it an allowlist?
  10. What limits apply to baggage size and content, and is baggage stripped before calls leave your network?
  11. How are span names kept low-cardinality, and what catches a regression?
  12. How do metrics and logs link to traces: trace IDs in log lines, exemplars on latency histograms?

Deep Dive: Senior Interview Follow-ups

"How do all twelve services agree on whether to keep a head-sampled trace?"

The root makes the decision and writes it into the sampled flag of traceparent. Downstream services use a parent-based sampler that follows the flag instead of deciding again. Ratio samplers also derive the decision from the trace ID itself, so two roots that see the same ID agree. If one service ignores the flag and samples independently, you get traces with random holes.

"Why does tail sampling need a separate collector tier? Can't each service decide on its own spans?"

A service only sees its own part of the trace. The payment service cannot know that checkout later returned an error, or that the whole request took 4 seconds. The decision needs the complete trace, so all spans of one trace must meet in one place and wait there until the trace is probably finished. That means routing by trace ID and buffering in memory, which is a stateful tier you have to size.

"Your trace shows a child span starting before its parent. Is the trace wrong?"

The structure is right and the alignment is off. Each host stamps its spans with its own clock, so cross-host positions include clock offset. Durations within a span are trustworthy, because one clock measured them. Check NTP offset on both hosts. Treat positions as accurate only to within that offset. A backend's skew correction may tidy the picture, but fix the clock rather than rely on it.

"Can you compute the p99 latency of checkout from your trace store?"

Not if you tail-sample. You kept the slow and failed traces on purpose, so the stored set is biased towards the tail. Compute latency histograms from every span before sampling, in the collector or in application metrics. Use the stored traces as examples, linked from the histogram through exemplars.

"A Kafka consumer processes messages in batches of 200 from different producers. How do you trace it?"

A span can have only one parent, so the batch span cannot be a child of 200 producers. Create one consumer span for the batch and add a span link to each message's producer context. If per-message processing matters, create a child span per message under the batch span, each linking to its own producer. Each producer's trace then shows a link out to where its message was processed.

"A customer reports a failed request and gives you a request ID. Head sampling is at 1%. What are your options?"

Most likely the trace was not kept. Options from cheapest: logs with the trace ID in every line still exist at full volume, so search those. If failures must always be traceable, add tail rules that keep every error. For live debugging, let trusted internal callers force sampling with a debug header, but never let the public internet set it. The underlying lesson is that head sampling answers aggregate questions, not "what happened to this one request".

"Tracing costs are growing faster than traffic. Where do you look?"

Spans per request first. New auto-instrumentation, or a loop creating spans, raises it without anyone noticing. Then bytes per span: large attributes such as SQL text, bodies or stack traces. Then span-name cardinality, which inflates the span-metrics bill. Then sampling rules that keep too much during long incidents, and cross-zone transfer between agents and gateways. Usually one of these explains most of the growth.

"Should the trace context go through to third-party APIs you call?"

The traceparent itself is low risk and some providers use it to correlate support cases. Baggage and tracestate are another matter. They can carry tenant IDs or internal routing data that should not leave your network. Strip baggage on egress by default, allow specific keys deliberately, and never put secrets or personal data in it in the first place.
