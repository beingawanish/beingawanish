Deep Dive: Inside the Mechanism

The lesson lists six jobs a reverse proxy does. In a design review, the useful question is how it does them. Every job is a buffer, a timer or a pool with a size. Each size is a decision someone made, or left at a default. This section follows one request through a proxy such as nginx, HAProxy or Envoy and names the state it touches on the way.

The process model: few threads, many sockets

A modern proxy runs a small number of worker processes or threads, usually one per CPU core. Each worker runs an event loop over epoll (Linux) or kqueue (BSD, macOS). The worker asks the kernel "which of my 20,000 sockets have data?" and handles only those. An idle client therefore costs a file descriptor, a little kernel memory and a few kilobytes of proxy state. It costs no thread.

That is the whole reason buffering works. The application server has a thread pool, perhaps 200 threads, and every thread is expensive. The proxy has sockets, and sockets are cheap. Whoever holds the slow part of the conversation should be the one for whom waiting is cheap.

Two limits sit underneath this. nginx caps each worker with worker_connections, and each proxied request uses two connections: one to the client and one to the upstream. The operating system caps open files per process (ulimit -n, or worker_rlimit_nofile in nginx). A proxy that hits either limit stops accepting connections. The symptom looks like a network problem, but it is a configuration number.

Request path: headers, body, and when the upstream is chosen

Here is the order of events for one HTTP/1.1 request in nginx, with the knobs that govern each step.

  1. Accept and TLS. The worker accepts the TCP connection and runs the TLS handshake. With TLS 1.3 that is one round trip, or zero on resumption. The expensive part is the key exchange and the certificate signature, which is real CPU. Session tickets or a session cache let a returning client skip most of it.
  2. Read the headers. A timer, client_header_timeout (60 s by default in nginx), limits how long a client may take to send its headers. Header buffers are small and fixed (large_client_header_buffers). A request with an enormous cookie gets a 400 here, before any application code runs.
  3. Read the body. With proxy_request_buffering on (the default), nginx reads the whole body before it contacts the upstream. Bodies up to client_body_buffer_size stay in memory. Larger ones spill to a temporary file. client_max_body_size (1 MB by default) rejects anything bigger with a 413. client_body_timeout limits the gap between two reads, not the total time. A client that sends one byte every 59 seconds keeps the connection open.
  4. Pick the upstream. Only now does the proxy choose a backend and take a connection from its pool. If the pool has an idle keep-alive connection, the request goes out at once. If not, the proxy opens a new TCP connection, limited by proxy_connect_timeout.
  5. Wait for the response. proxy_read_timeout (60 s by default) is the gap allowed between two reads from the upstream. It is also not a total deadline. A backend that streams a byte every 50 seconds never trips it.
  6. Buffer the response. With proxy_buffering on (the default), nginx reads the response into proxy_buffers as fast as the upstream sends it. If the response outgrows them, it goes to a temp file, up to proxy_max_temp_file_size. The upstream connection goes back to the pool as soon as the last byte arrives. The slow client drains the buffer at its own speed.
  7. Log. The access log line is written when the client side finishes. That is why the log has two clocks worth comparing: $request_time (the whole exchange as the proxy saw it) and $upstream_response_time (just the backend). A big gap between them means the client was slow, not your service.

Buffering is not always right. Turn request buffering off for large streaming uploads you want to process as they arrive, and turn response buffering off for Server-Sent Events, long polling and token streams. Otherwise the proxy holds the events until a buffer fills. nginx honours an X-Accel-Buffering: no response header for exactly this, so the application can opt out per response.

The upstream pool and the keep-alive contract

Connection reuse toward the backends does not happen by itself in nginx. You need an upstream block with a keepalive directive, HTTP/1.1 to the upstream, and a cleared Connection header. Without those three lines, nginx opens and closes a TCP connection per request. HAProxy and Envoy pool by default, but they have their own limits. Envoy, for example, applies per-cluster circuit-breaker thresholds for connections, pending requests and active requests, and the defaults are modest (1,024 each) for a busy cluster.

upstream bookstore_app {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;              # idle connections kept per worker
    keepalive_timeout 30s;     # must be SHORTER than the app's idle timeout
}

server {
    listen 443 ssl;
    client_max_body_size 10m;
    client_body_timeout 15s;   # gap between reads, not a total
    client_header_timeout 10s;

    location / {
        proxy_pass http://bookstore_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;   # overwrite, never append
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID $request_id;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
        proxy_next_upstream error timeout;   # retry only failures before a response
    }
}

Pay attention to the keepalive_timeout comment. A pooled connection is a shared contract between two idle timers, and the side with the shorter timer closes first. If the application closes an idle connection at 5 seconds (the default in Node.js's HTTP server, for example) and the proxy keeps it for 30, the proxy will sometimes send a request on a socket the backend is closing at that instant. The result is a sporadic 502 that no load test reproduces. The rule: the upstream's idle timeout must be longer than the proxy's. The same rule applies one layer out, between a cloud load balancer and nginx.

Client identity: building a trusted X-Forwarded-For

The lesson states the rule: one header, set by one party, trusted from one source. The implementation detail that trips people is a chain of proxies. Each hop appends the address it saw, so the header looks like X-Forwarded-For: 203.0.113.9, 198.51.100.4, 10.0.0.5. Only the right-hand entries were written by machines you control. The leftmost entry is whatever the client typed.

The correct parse walks from the right, skipping addresses that belong to your own proxies, and takes the first address that does not. nginx does this with the realip module:

set_real_ip_from 10.0.0.0/8;        # our load balancers
set_real_ip_from 2001:db8::/32;
real_ip_header X-Forwarded-For;
real_ip_recursive on;               # walk right-to-left past trusted hops

Envoy has the same idea as xff_num_trusted_hops: trust exactly N hops from the right. Both work only if the list of trusted sources is complete and stays complete. Add a new load balancer subnet and forget this list, and every request appears to come from the balancer. That is the lesson's 99%-from-one-client incident, caused by an infrastructure change rather than a code change.

Two alternatives are worth knowing. The standard Forwarded header (RFC 7239) carries the same data in a structured form, but most tooling still reads X-Forwarded-For. For TCP-level proxies that cannot add HTTP headers, the PROXY protocol (from HAProxy, supported by nginx, Envoy and most cloud balancers) prepends the original addresses to the TCP stream itself. It must be enabled on both sides at once. A listener that expects it rejects connections that lack it, and a listener that does not expect it treats the prefix as garbage.

Configuration reload without dropping traffic

A proxy that sits on every request has to change config without a restart. nginx does it by starting new worker processes with the new config on SIGHUP. Old workers stop accepting and drain their in-flight requests. Long-lived connections (WebSockets, SSE, large downloads) keep old workers alive, sometimes for hours, so memory grows with each reload. worker_shutdown_timeout caps how long an old worker may linger before it closes its remaining connections.

Envoy takes a different path. Its routes, clusters and endpoints arrive over the xDS APIs from a control plane, and it applies them in place, without a new process. That makes changes cheap, which is good. It also means a bad config can reach every proxy in seconds, which is the failure mode to design for.

Deep Dive: Sizing and the Numbers

Take the bookstore at a realistic busy hour. Assumptions, all round numbers you can swap for your own:

  • Peak 6,000 requests per second, 30% of them static files served by the proxy itself.
  • 40,000 concurrent client connections, most of them idle keep-alive connections from browsers and apps.
  • Median client is fast, but the p95 mobile client takes 2 s to send its request or receive a 200 KB response.
  • Application processing time 40 ms; two application servers behind the proxy pair.

Connections and memory

An idle keep-alive connection in nginx costs a few kilobytes of user-space state plus kernel socket memory. A TLS connection costs more, because the TLS library keeps its own read and write buffers. Budget in the range of 20 to 50 KB per idle TLS connection, and measure your own build, because it varies a lot with library and settings. At 40 KB, 40,000 connections is 1.6 GB. That is comfortable on one machine and a reason not to run the proxy on a 1 GB container.

Active requests cost buffer memory on top. With the default proxy_buffers 8 4k (or 8k on some platforms), a request that is streaming a large response holds 32 to 64 KB. If 2,000 requests are in flight, that is 64 to 128 MB. The thing that can surprise you is temp files: if 500 users download 50 MB reports through a proxy with buffering on, the proxy writes 25 GB to local disk. Either serve large downloads from object storage, raise the buffers for that one route, or turn buffering off there.

What buffering buys the application

The lesson's formula is threads = rate × time a thread is held. Apply it to the 4,200 dynamic requests per second:

  • Without buffering, a thread is held for the client's transfer time. If 5% of clients take 2 s and the rest take 50 ms on top of the 40 ms of work: 4,200 × (0.95 × 0.09 + 0.05 × 2.04) ≈ 4,200 × 0.188 ≈ 790 threads.
  • With buffering, a thread is held only for the 40 ms of work plus about 1 ms of fast internal transfer: 4,200 × 0.041 ≈ 172 threads.

Notice where the 790 comes from: the 5% of slow clients account for about 430 of them. Tail clients, not average clients, size an unbuffered thread pool. That is the general shape of this whole pattern.

Ephemeral ports: the number that bites without keep-alive

Every new TCP connection from the proxy to a backend uses a local port. On Linux the default ephemeral range is 32768 to 60999, about 28,000 ports per destination address and port. When the proxy closes a connection first, the socket sits in TIME_WAIT for 60 seconds and keeps its port.

Now run the numbers with upstream keep-alive switched off. 4,200 dynamic requests per second across 2 backends is 2,100 new connections per second to each. Over 60 seconds that is 126,000 sockets in TIME_WAIT per backend, against 28,000 ports. The proxy runs out in about 13 seconds of peak traffic and starts failing connects with "cannot assign requested address".

With a pool of 64 idle connections per worker on an 8-worker proxy, the steady-state count is a few hundred long-lived connections and almost no churn. This is why "reuses connections" is not a nice-to-have. You can widen the port range, add backend IPs or enable tcp_tw_reuse, but those treat the symptom.

CPU: TLS dominates

Plain HTTP forwarding is cheap: a proxy core can move many thousands of small requests per second. TLS changes the picture in two ways. New handshakes cost a signature and a key exchange each, so a burst of new connections (an app release, a reconnect wave) costs far more CPU than the same number of requests on warm connections. Bulk encryption is cheap on CPUs with AES instructions, so long downloads cost little.

The practical sizing rule: measure handshakes per second per core on your hardware with your certificate type, then size the proxy for the reconnect storm, not the steady state. An ECDSA certificate is usually much cheaper to sign with than a 2048-bit RSA one, which is why many sites serve both and let the client choose. Session resumption turns most of the returning traffic into cheap handshakes.

Latency: the hop is small, the misconfigured hop is not

On the same network, a warm proxy hop adds tens to a few hundred microseconds. The real latency costs come from misconfiguration: a new upstream TCP connection per request (one extra round trip, plus a TLS handshake if the upstream is TLS), request buffering that waits for a 10 MB body before forwarding, or response buffering that holds an event stream. If your proxy adds more than a millisecond at p50, look for one of those before blaming the proxy.

Deep Dive: Failure Modes in Production

1. Sporadic 502s that no load test reproduces

Symptom: a steady trickle of 502s, perhaps 0.01% of requests, worse at low traffic, and none in the application logs. Mechanism: the keep-alive race from the mechanism section. The backend's idle timer fires and it closes a pooled connection just as the proxy sends a request on it. Low traffic makes it worse, because connections sit idle long enough to hit the backend's timer. Detect: proxy error logs show "upstream prematurely closed connection" or "connection reset by peer" on reused connections. Compare the 502 rate against connection idle time; it rises with idle time. Fix: make the proxy's upstream idle timeout shorter than the backend's (for example, proxy 30 s, app 65 s). Allow a retry on a connection error only for idempotent requests.

2. A handful of clients exhausts the proxy

Symptom: the proxy stops accepting new connections. CPU is idle and bandwidth is low. Mechanism: a slow-read or slow-send attack (Slowloris and relatives). Each attacker connection sends headers or reads responses one byte at a time, just under the per-read timeout. Because the timers measure gaps between reads, not totals, each connection lives for minutes. A few thousand of them fill worker_connections. Detect: active connections near the limit while requests per second fall; many connections in the "reading" state in nginx's stub_status; connection age histograms with a fat tail. Fix: short header and body timeouts on the public listener (10 to 15 s), per-IP connection limits (limit_conn), a minimum data rate where your proxy supports one, and enough connection headroom. A CDN or managed edge in front absorbs most of this before it reaches you.

3. Duplicate orders from a timeout and a retry

Symptom: customers occasionally see two identical orders, both placed within a few seconds. Mechanism: the timeouts are in the wrong order. The proxy's read timeout is 30 s, the app's database call takes 35 s under load, so the proxy gives up and returns 504 while the app is still working. The app finishes and commits the order. Meanwhile the client retries, or the proxy is configured to retry on timeout for all methods, and a second order is created. Detect: 504s at the proxy that line up with 200s or commits in application logs for the same request ID. Fix: order the timeouts so each inner layer gives up before the outer one (client > CDN > proxy > app > database). Never retry non-idempotent requests at the proxy; nginx refuses to by default unless you add non_idempotent to proxy_next_upstream, and that default is right. Use idempotency keys on order creation so a client retry is safe.

4. Request smuggling through a header disagreement

Symptom: strange requests in backend logs that no client sent. One user occasionally receives another user's response. Mechanism: HTTP/1.1 has two ways to mark where a body ends: Content-Length and Transfer-Encoding: chunked. If a crafted request contains both, or a malformed one, the proxy and the backend may disagree on where the first request ends. The leftover bytes become the start of the "next" request on a pooled, shared connection, so the attacker's prefix is glued to a victim's request. Detect: hard to spot in metrics. Look for 400s at the backend with odd request lines, mismatched request IDs between proxy and app logs, and run a desync scanner in security testing. Fix: keep the proxy patched; configure it to reject ambiguous framing rather than normalise it; use HTTP/2 to the backend where you can, because it frames requests explicitly. Make sure every hop in the chain uses the same HTTP parser rules, which is one more reason not to stack proxies.

5. The live feed arrives in lumps

Symptom: the order-tracking page, built on SSE, updates in bursts every 30 seconds instead of live. Locally it works perfectly. Mechanism: response buffering. The proxy waits to fill a buffer before sending anything to the client, and a 200-byte event does not fill 4 KB. Compression on the proxy can do the same, because gzip waits for enough data to compress. Detect: time to first byte equals the buffer fill time; events arrive at the client in batches. Fix: disable proxy buffering and compression for the streaming route (proxy_buffering off or the X-Accel-Buffering: no header), and raise proxy_read_timeout above your heartbeat interval so the proxy does not cut idle streams.

6. Memory climbs with every deploy

Symptom: proxy memory grows after each config reload and only falls hours later. Eventually the out-of-memory killer takes a proxy. Mechanism: each reload starts a fresh set of workers, and the old set lingers until its last long-lived connection closes. Ten reloads in an hour with WebSocket traffic means eleven generations of workers. Detect: count proxy worker processes over time, and alert when old-generation workers exist more than N minutes after a reload. Fix: set worker_shutdown_timeout so old workers close their connections after a bounded time, and make clients reconnect gracefully (with jitter). Batch config changes instead of reloading on every small edit.

7. Uploads fail with a 413 nobody can explain

Symptom: a customer's 12 MB book-cover upload fails. The application allows 20 MB. Mechanism: each layer has its own body limit, and the smallest one wins. The CDN might allow 100 MB, the cloud balancer has its own cap, nginx defaults to 1 MB, and the framework has another. The error page often comes from whichever layer refused, so its format is a clue. Detect: look at which server produced the 413 (headers, page body, the Server header); proxy logs record a 413 with no upstream time. Fix: keep a single table of limits (body size, header size, timeouts) for every layer, owned by one team and checked in CI. Set each limit deliberately, per route, rather than raising the global default.

The decision that most often goes wrong is the one in the last row of the lesson's "When Not to Use It": stacking. Before adding a proxy, write down its one job that no existing layer does. If you cannot name it, every layer you add multiplies the timeout table, the body-size table and the header trust chain, and adds one more parser for request smuggling to exploit.

On L4 versus L7, a practical rule: put an L4 balancer (or anycast) at the very front for scale and DDoS absorption, and L7 proxies behind it where HTTP decisions happen. That split is what most large edges converge on, and it keeps TLS keys on a tier you control.

Deep Dive: Design-Review Checklist

  1. What single job does this proxy do that no layer in front of or behind it already does?
  2. Write out the timeout ladder from client to database. Does each inner layer give up before the layer outside it?
  3. Is upstream keep-alive enabled, and is the proxy's upstream idle timeout shorter than every backend's idle timeout?
  4. Which addresses are trusted to set X-Forwarded-For? Where is that list maintained, and what updates it when a new balancer subnet appears?
  5. Does the proxy overwrite or strip client-supplied identity headers (X-Forwarded-*, X-User-*, X-Real-IP)?
  6. Which routes stream (SSE, WebSockets, large downloads), and is buffering off for exactly those routes?
  7. What are the body and header size limits at every layer, and is there one table that lists them?
  8. What does the proxy retry, on which errors, and is any non-idempotent method in that list?
  9. How many handshakes per second can the fleet absorb in a reconnect storm, and what is that number at peak?
  10. How is config changed, validated and rolled back? How long do old workers or old config versions live after a change?
  11. Are the proxy instances spread across failure domains, and what happens to in-flight connections when one dies?
  12. Do access logs record request time, upstream time, upstream address and a request ID, so a slow client can be told apart from a slow service?

Deep Dive: Senior Interview Follow-ups

"The proxy has a 60-second read timeout. Does that mean no request takes longer than 60 seconds?"

No. In nginx, proxy_read_timeout and client_body_timeout limit the gap between two successive reads, not the whole exchange. A backend or client that sends a byte every 50 seconds can keep a request open indefinitely. If you need a total deadline, enforce it in the application or with a feature that measures total time, and protect the public side with short header timeouts and connection limits.

"You see 502s only at night, when traffic is lowest. Why would low traffic cause errors?"

Most likely the keep-alive race. At low traffic, pooled upstream connections sit idle longer, long enough to cross the backend's idle timeout. The backend closes the socket while the proxy is sending on it. The fix is to make the proxy's idle timeout shorter than the backend's, so the proxy always closes first, and to allow a retry on connection reset only for idempotent requests.

"Why not just take the leftmost address in X-Forwarded-For? That is the original client."

Because the leftmost entry is the only one the client wrote. Each proxy appends to the right, so you can trust entries only from the right-hand side, back to the first address that is not one of your own proxies. Take the leftmost and any client can claim any address, which bypasses IP rate limits and poisons audit logs. Walk right to left over a known list of trusted hops, as nginx's real_ip_recursive or Envoy's xff_num_trusted_hops do.

"Upstream keep-alive is off. What breaks first as traffic grows?"

Usually ephemeral ports. Every request opens a new connection to the backend, and each closed connection sits in TIME_WAIT for 60 seconds. With about 28,000 ports per backend address, a little under 470 new connections per second per backend is the steady-state ceiling. Above it, connects fail with "cannot assign requested address". You also pay an extra round trip per request, and TLS handshakes if the backend link is encrypted. Turn on pooling; port tuning only buys time.

"When would you turn response buffering off, and what do you lose?"

For streaming responses: SSE, long polling, chunked token streams, and live progress. Buffering would hold small events until a buffer fills. You lose the protection buffering gives the backend. A slow client now holds the upstream connection, and an app thread if the backend is threaded, for the life of the stream. That is fine when the streaming backend is built on an event loop and sized for long connections, and a problem when it is a thread-per-request server.

"L4 or L7 for the front of a large public site?"

Both, in layers. An L4 tier (or anycast with ECMP) at the front spreads connections and absorbs volumetric attacks cheaply, because it does not parse HTTP. L7 proxies behind it terminate TLS and make HTTP decisions: routing, buffering, header policy. Choosing only L7 at the front makes every packet pay for HTTP parsing. Choosing only L4 means no path routing, no buffering and no HTTP-aware retries. If the L4 tier hides client addresses, pass them with the PROXY protocol.

"How can a reverse proxy cause one user to receive another user's response?"

Two ways. Request smuggling: the proxy and backend disagree on where a request ends on a shared pooled connection, so an attacker's bytes are prefixed to the next user's request and responses get misaligned. And caching: if the proxy caches responses and the cache key does not include what makes the response personal (a cookie or authorization header), it serves one user's page to another. Fix the first with strict framing, consistent parsers and HTTP/2 to the backend. Fix the second by never caching authenticated responses unless the key is designed for it.

"A colleague wants to add nginx behind the cloud load balancer 'for flexibility'. How do you decide?"

Ask for the one job the cloud balancer cannot do: per-route buffering, a specific rewrite, local static serving, a module you need. If there is one, add nginx and own the consequences: a second timeout ladder, a second body limit, a second trusted-header hop, a second idle-timeout pair to align. If the answer is "flexibility", decline. Every unowned layer adds incident time, because during an outage someone has to check its config too.
