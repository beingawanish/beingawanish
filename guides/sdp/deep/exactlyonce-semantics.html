Deep Dive: Inside the Mechanism

The lesson gives the rule: at-least-once delivery underneath, plus two atomic couplings. This section opens the boxes. Each coupling is a small protocol with its own state, its own timeouts and its own way of going wrong. Kafka, Flink and Spark build them differently, and the differences decide what you will debug at 3 a.m.

The idempotent producer: sequence numbers per partition

Start at the lowest layer. A producer sends a batch, the broker writes it, and the acknowledgment is lost. The producer retries. Without help, the partition now holds the batch twice.

The idempotent producer fixes this with three pieces of state:

  • Producer ID (PID). The broker hands each producer session a 64-bit ID when it starts.
  • Epoch. A small counter attached to the PID. It matters for transactions, below.
  • Sequence number. Per PID and per partition, every batch carries the sequence of its first record. The next batch must continue exactly where the last one ended.

The broker remembers the last few batches it accepted for each (PID, partition) pair. Kafka keeps five. A retried batch whose sequence it has already seen is acknowledged and not written again. A batch that skips ahead means something was lost in between, and the broker rejects it with an out-of-order sequence error.

That "five" is why max.in.flight.requests.per.connection must be 5 or less when idempotence is on. With more batches in flight, the broker could not tell a retry from a gap. Since Kafka 3.0, enable.idempotence=true and acks=all are the producer defaults, so most clients get this layer for free. Check older clients and non-Java libraries explicitly. The defaults differ.

Notice what this layer does not cover. The sequence lives in one producer session. If the producer process restarts, it gets a new PID and its retries of old data are new data. It also says nothing about the consumer side. So the idempotent producer removes network-retry duplicates on one hop, and nothing more.

Kafka transactions: the coordinator, the markers and the last stable offset

Transactions add the second coupling for a read-process-write loop: consume from Kafka, compute, produce to Kafka, and commit the consumed offsets, all as one unit. The moving parts are:

  • transactional.id. A stable name you give the producer. It survives restarts, unlike the PID.
  • Transaction coordinator. A broker role. The coordinator for a given transactional.id is the leader of one partition of the internal __transaction_state topic, chosen by hashing the ID. That topic is the coordinator's write-ahead log, so a new coordinator can pick up after a broker dies.
  • Control markers. Special records written into each data partition the transaction touched. A COMMIT or ABORT marker tells readers how to treat the records before it.

One transaction runs like this:

  1. initTransactions(). The producer registers its transactional.id. The coordinator bumps the epoch and finishes or aborts anything the previous holder of that ID left open. Any older producer with the same ID and a lower epoch is now fenced: its next write fails with a fencing error. This is how a zombie, such as an old instance waking from a long GC pause, is kept out.
  2. beginTransaction(). Local only. Nothing goes over the network yet.
  3. Sends. Before the first write to a new partition, the producer tells the coordinator, which records the partition in the transaction's state. The records are written to the partitions immediately, with the PID, epoch and sequence. They are in the log, but not yet decided.
  4. sendOffsetsToTransaction(). The consumed offsets go to the consumer group's coordinator as part of the same transaction. They are held pending, not applied.
  5. commitTransaction(). The coordinator writes PREPARE_COMMIT to its log. From this moment the commit is decided, even if the coordinator dies. It then writes COMMIT markers into every partition in the transaction, including the offsets partition, and finally writes COMPLETE_COMMIT.

That is the two-phase commit from the 2PC lesson, with one important difference. The coordinator and the participants are all replicated brokers in one system, so a coordinator crash does not leave participants blocked forever. The new leader of the __transaction_state partition reads the log and finishes the job.

On the read side, the key idea is the last stable offset (LSO). It is the offset of the first record that belongs to a still-open transaction. A consumer with isolation.level=read_committed reads only up to the LSO. When it reaches records from a transaction that later aborted, it skips them using an index of aborted transactions that the broker keeps alongside each log segment.

Two consequences follow, and both come up in production:

  • One open transaction holds back every read_committed reader of that partition, including records from other producers written after it. A slow or stuck transaction is a partition-wide stall.
  • The default isolation.level is read_uncommitted. A consumer that never set it sees aborted records as if they were real. Exactly-once on the write side means nothing to a reader that did not opt in.

Two timeouts bound all of this. The producer's transaction.timeout.ms (60 seconds by default) is how long the coordinator waits before aborting an open transaction on its own. The broker's transaction.max.timeout.ms (15 minutes by default) caps what any producer may ask for. Keep both in mind for Flink, below.

Kafka Streams: exactly_once_v2

Kafka Streams wraps all of the above behind one setting, processing.guarantee=exactly_once_v2. Each stream thread runs one transactional producer. Every commit puts three things in one transaction: output records, changelog records for local state stores, and input offsets. The changelog part is the first coupling, state with position, done through the log instead of a snapshot.

The "v2" matters. The first version needed one producer per input partition, because fencing worked per transactional.id. A busy application with hundreds of partitions ran hundreds of producers. Since brokers 2.5, the consumer group's generation travels with the offset commit. The group coordinator can then reject a commit from a consumer that has lost its partitions in a rebalance. One producer per thread is enough. The old exactly_once setting is deprecated.

The other knob that changes under exactly-once is commit.interval.ms. Its default drops from 30 seconds to 100 ms. That is the freshness of read_committed outputs, and it is also how often you pay the transaction's fixed cost.

Flink: barriers plus a two-phase-commit sink

Flink does the first coupling with a consistent snapshot. The JobManager injects a numbered barrier at every source. Each source records its offsets in the snapshot, then forwards the barrier. When an operator has received barrier n on all its inputs, it snapshots its state and forwards the barrier. The snapshot for checkpoint n is complete when every operator, sinks included, has reported in.

An operator with several inputs must wait for the barrier on all of them. While it waits, it stops reading from the inputs that have already delivered their barrier. This is alignment, and under backpressure it can take a long time. Unaligned checkpoints remove the wait by letting the barrier overtake the in-flight data and storing that data in the snapshot instead. Checkpoints then finish quickly under pressure, at the price of bigger snapshots.

The second coupling lives in the sink. Flink's two-phase-commit sinks follow a fixed lifecycle:

  1. Between checkpoints, the sink writes into an open external transaction (for Kafka, an open Kafka transaction).
  2. When the barrier reaches the sink, it pre-commits: it flushes, records the transaction's handle in its checkpoint state, and opens a new transaction for the next interval.
  3. When the JobManager declares the checkpoint complete, every sink commits the transaction it pre-committed.
  4. If the job fails after the checkpoint completed but before a commit happened, the restored sink finds the handle in its state and commits it on recovery. Commit must therefore be safe to retry.

Here is the trap. The Kafka transaction stays open from the start of one checkpoint interval until the commit after the checkpoint completes. If the job is down longer than the transaction's timeout, the broker aborts it. The recovering job then tries to commit a transaction that no longer exists, and that interval's output is gone. Flink's Kafka sink documentation calls this out directly. The broker's 15-minute cap and the sink's own default can disagree, so set transaction.timeout.ms deliberately: longer than the checkpoint interval plus the longest outage you expect to recover from, and within the broker's cap.

The Kafka sink also needs a transactionalIdPrefix that is unique per job. Two jobs sharing a prefix fence each other's producers.

Spark Structured Streaming: the offset log and the commit log

Spark runs micro-batches, and each one has an integer batchId. In the checkpoint directory it keeps two logs. The offset log records, before a batch runs, exactly which offsets it will read. The commit log records that the batch finished. On restart, a batch that appears in the offset log but not in the commit log runs again over exactly the same offsets.

So Spark guarantees that the same batch is replayed, with the same input. The sink must make the replay harmless. Built-in file and Delta sinks do this by recording the batchId they have written. In foreachBatch you write your own code, and it receives the batchId for exactly this reason. Delta Lake's writer options txnAppId and txnVersion let a write be skipped if that (application, version) pair has already been committed.

The sink-side options: guarded upserts and offsets in the sink

Not every sink is Kafka. For a database sink there are two well-worn mechanisms, and both are simpler than distributed transactions.

A guarded upsert. The lesson's UPSERT (partner, day) = count works because the job emits the whole current value. Add a monotonic version, such as the source offset or the checkpoint ID, and the database can also refuse to go backwards:

INSERT INTO usage_daily (partner_id, day, calls, src_version)
VALUES ($1, $2, $3, $4)
ON CONFLICT (partner_id, day) DO UPDATE
  SET calls = EXCLUDED.calls,
      src_version = EXCLUDED.src_version
  WHERE usage_daily.src_version < EXCLUDED.src_version;

A replay writes the same value with the same version, and the WHERE clause makes it a no-op. A slow, stale writer (a zombie) with an older version cannot overwrite newer data.

Offsets stored in the sink. If the results and the consumer's position live in the same database, one local transaction couples them. The consumer writes its results and the new offset in the same BEGIN ... COMMIT. On startup it reads its offset from the database and seeks there, ignoring Kafka's committed offsets. This is exactly-once with nothing but a relational database. The cost is that you take over offset management, including during rebalances: a consumer that has lost a partition must not commit for it. Guard the offset row with the partition's owner generation, or with a version check like the one above.

Deep Dive: Sizing and the Numbers

Exactly-once costs latency, throughput and storage. Each cost has a formula, and a review should see them filled in. The running example is the billing pipeline. Assume 20,000 API-call events per second at peak, 400-byte events, 3,000 partners, and 24 input partitions.

Freshness of committed outputs

A read_committed reader sees an output only after the transaction containing it commits. An event arriving at a random moment waits, on average, half a commit interval, then the commit itself.

  • Average added delay ≈ interval / 2 + commit time.
  • Worst case ≈ interval + checkpoint duration + commit time.

With Flink checkpoints every 2 seconds that take 300 ms, and a commit of about 20 ms (an assumption; measure yours), the average delay is about 1.3 seconds and the worst about 2.3 seconds. For invoices this is irrelevant. For a fraud feature with a sub-second budget, it rules out read_committed outputs entirely. That is why the lesson's dashboard reads with plain at-least-once.

Under backpressure the checkpoint duration grows, because barriers move with the data. A checkpoint that takes 40 seconds makes the committed output 40 seconds stale. Freshness of an exactly-once sink is a backpressure metric in disguise.

Transaction overhead

Each transaction has a roughly fixed cost: a few coordinator round trips, plus one marker record in every partition it touched. The cost per event is that fixed cost divided by the events in the transaction.

At 100 ms, a thousand control records per second is noticeable but not alarming. The lesson's "3-5% of throughput" is a reasonable order of magnitude for second-scale intervals. It grows when transactions get small. The lever is the interval, and it trades directly against freshness. A pipeline that writes to many output partitions per transaction pays more markers, so fan-out matters too.

Replay after a crash

On failure the job rewinds to the last completed checkpoint. The work redone is, at most, one checkpoint interval of input plus whatever arrived during the outage.

  • Redo at most: 2 s × 20,000/s = 40,000 events.
  • Plus the outage backlog: a 60-second restart adds 1.2 million events.
  • Catch-up time: if the job can run at 60,000/s when unthrottled, the 1.24 million events clear in 1,240,000 / (60,000 − 20,000) = 31 seconds, because new events keep arriving.

Short checkpoint intervals reduce redo but not the outage backlog, which usually dominates. Do not tune the interval down for recovery speed; tune it for freshness and for state-snapshot cost.

The cost of deduplicating by event ID

The lesson's Q3 fix, a client-generated event ID, needs a dedupe stage that remembers IDs it has seen. That memory is often the biggest state in the pipeline.

  • IDs per day: 20,000/s × 86,400 s ≈ 1.73 billion. (Peak rate all day is pessimistic; use your daily total.)
  • Bytes per remembered ID: a 16-byte UUID, plus key overhead in a RocksDB-backed state store. Assume about 64 bytes including timestamps and overhead.
  • One day's window: 1.73 billion × 64 B ≈ 110 GB of state.
  • One hour's window: 72 million × 64 B ≈ 4.6 GB.

The window must cover the longest gap between a client's first send and its last retry. A browser retries for seconds. A mobile SDK that buffers offline may resend days later. Size the window from the SDK's retry policy, not from guesswork, and do something explicit with events older than the window. Rejecting them to a quarantine topic is better than counting them blind.

If 110 GB is too much, cut it. Dedupe per partner only where billing needs it. Use a Bloom filter as a first pass and check the exact store only on a hit. Or move the dedupe key into the sink as a unique constraint, if the sink can hold it.

Choosing the transaction timeout

For a Flink job writing to Kafka, the transaction timeout must outlast the worst gap between opening a transaction and committing it:

transaction.timeout.ms > checkpoint interval + max checkpoint duration + max time to detect failure and restart.

With a 2-second interval, checkpoints that can take up to 60 seconds under pressure, and a restart that takes up to 5 minutes, you need more than about 6 minutes. Fifteen minutes, the broker's default cap, leaves room. An outage longer than the timeout loses the open interval's output. That is a real, if rare, loss path. Know your number, alert on job downtime approaching it, and keep a reconciliation job that would catch the gap.

The flip side: a long timeout means a crashed producer's open transaction blocks read_committed readers for that long, unless a restarted producer with the same transactional.id fences and aborts it first. Stable IDs keep that window short.

Deep Dive: Failure Modes in Production

Most exactly-once failures are not protocol bugs. They are scope errors: a part of the pipeline that someone believed was inside the guarantee and was not.

1. The zombie that kept writing

Symptom. After a rebalance or a deploy, some partners' counts jump by a whole batch. Logs from two different hosts show the same input offsets processed.

Mechanism. The application derived its transactional.id from the hostname or a random UUID. The replacement instance got a different ID, so the coordinator saw two unrelated producers. The old instance, frozen in a long GC pause, woke up and committed its transaction. Fencing works only when the new producer reuses the old one's ID.

Detect. Duplicate source offsets in the output (store the source offset in each output record). No ProducerFencedException in the logs when you would have expected one.

Fix. Make the transactional.id stable for the work it does, or use exactly_once_v2 semantics, where the group generation fences stale consumers. In Flink, a unique, stable transactionalIdPrefix per job.

2. The interval that vanished after a long outage

Symptom. The job was down for 25 minutes during a cluster maintenance. It recovered cleanly and reported no errors that anyone noticed. A month later, reconciliation shows one partner's invoice short by two seconds' worth of calls.

Mechanism. Checkpoint n had completed, but the sink's commit was still pending when the cluster went down. The Kafka transaction's timeout was 15 minutes. The broker aborted it. On recovery, Flink restored from checkpoint n, so it did not replay those events, and tried to commit a transaction that had been aborted. The output was lost silently: exactly-once became at-most-once for one interval.

Detect. Errors on commit during recovery about invalid or fenced transactions. A reconciliation job comparing raw input counts against committed output per hour.

Fix. Set the timeout from the formula in the sizing section. Alert when a job's downtime approaches it. Treat any commit failure during recovery as a page, not a warning.

3. The hanging transaction that froze a partition

Symptom. Every read_committed consumer of partition 9 stops making progress. Its consumer lag climbs. Producers are healthy and the partition's high watermark keeps rising. A read_uncommitted tool shows new data arriving.

Mechanism. One transaction on partition 9 was never committed or aborted. The usual causes are a client bug or a producer whose ID will never be reused, combined with a long timeout. The last stable offset stays pinned at that transaction's first record, so committed readers cannot pass it, whoever wrote the data after it.

Detect. The gap between the high watermark and the LSO for a partition, which shows up as lag only for read_committed groups. Kafka ships kafka-transactions.sh, which can list open transactions and find hanging ones.

Fix. Abort the transaction with the same tool. Then fix the root cause: stable transactional IDs, a sane timeout, and current client and broker versions, since newer releases add server-side checks against this class of bug.

4. The downstream reader that never opted in

Symptom. The finance team's reconciliation export runs about 0.3% higher than the invoices, mostly on days with deploys.

Mechanism. The export was a plain consumer with default settings, so it read with read_uncommitted. On every abort (each deploy and crash produced one), it read records that the invoice tables never saw. The same thing happens with connectors and stream tools that default to uncommitted reads.

Detect. Compare a read_committed count with a read_uncommitted count for the same range; they differ only by aborted data. Audit every consumer group on transactional topics for its isolation level.

Fix. Set isolation.level=read_committed on every reader of a transactional topic. Make it a lint rule in your client wrapper. A topic written with transactions should be documented as such, because nothing on the topic itself forces readers to honour it.

5. The replay that wrote a different answer

Symptom. Idempotent upserts are in place, yet the dashboard's 14:00 value changes after a restart. A partner screenshot from before the restart disagrees with the invoice.

Mechanism. Idempotent sinks assume that a replay produces the same output. Several things break that assumption. Windows on processing time put replayed events into different windows. The code reads the wall clock or a random number. Enrichment looks up a mutable table, whose value changed between the two runs. Each one makes the replay write a different value under the same key.

Detect. Log a hash of each output value together with its key and source version. On replay, a key whose hash changes is a determinism bug. Run a nightly "replay one hour into a scratch sink and diff" job.

Fix. Event time everywhere, as the stream lesson recommends. No wall clock or randomness in business logic. Version reference data: join against the catalog version effective at the event's time, or capture the looked-up value in state so the replay reuses it.

6. Duplicates older than the dedupe window

Symptom. Client event IDs are in place and dedupe is on. Partner C still shows a small number of doubled calls, all with event times two to four days old.

Mechanism. Their SDK queues events on the device when offline and retries after reconnecting, with the same event ID. The dedupe state keeps IDs for 24 hours. After that, a retry looks like a new event and is counted again.

Detect. A histogram of (arrival time − event time). Any mass to the right of the dedupe window is at risk. Count events that arrive after the window by partner.

Fix. Size the window from the client's real retry horizon. If that horizon is unbounded, cap it: the SDK drops events older than N days, and ingestion routes anything older than the window to a quarantine topic for a batch dedupe against the warehouse.

7. Committed output frozen by checkpoint timeouts

Symptom. The invoice tables stop updating for 20 minutes. The job is running, consuming and not erroring. Flink's UI shows checkpoints expiring one after another.

Mechanism. A slow downstream stage causes backpressure. Barriers queue behind data, alignment waits grow, and checkpoints hit their timeout. With a two-phase-commit sink, no checkpoint means no commit, so nothing reaches read_committed readers. The transaction keeps growing and creeps toward its own timeout, which brings back failure mode 2.

Detect. Checkpoint duration and alignment time per operator. The age of the last completed checkpoint, alerted well below the transaction timeout. Per-operator backpressure metrics to find the slow stage.

Fix. Unaligned checkpoints and buffer debloating to keep checkpoints moving under pressure. Put a log seam in front of the slow sink, as the backpressure lesson shows. Make the checkpoint failure tolerance explicit, so the job fails over instead of sitting stuck forever.

"Exactly-once" is several different mechanisms with one name. A review should ask which one, and what it does not cover.

How to choose

Work from the sink backwards, because the sink decides what is possible.

  1. Is the output a value per key? Then a keyed upsert, with a version guard if zombies are possible, is the default. It costs nothing in freshness and works with almost any database.
  2. Is the sink a relational database you own? Store offsets in it and commit both in one local transaction. This is the most underrated option: real atomicity, no coordinator, easy to reason about.
  3. Is the output Kafka, and is it non-keyed or spread across topics? Use Kafka transactions, and make every reader read_committed.
  4. Does the job have large state and a complex topology? Flink or Kafka Streams with their built-in exactly-once. You are buying the snapshotting more than the sink.
  5. Is the output an external effect? None of the above applies. Send with an idempotency key the receiver dedupes on, as in Idempotency and Webhooks.

Then, separately, check the front of the pipeline. Every mechanism in the table starts at the log. Duplicates born before the log need a client-generated ID and a dedupe stage, whatever you chose above.

Deep Dive: Design-Review Checklist

  1. Which outputs need the guarantee, and who audits them? Which outputs are fine with at-least-once?
  2. Where is the guarantee's boundary drawn, by name? List every external effect the pipeline produces and how each one is made idempotent.
  3. Where are event IDs generated? Are they created before the first send and reused on every retry, all the way back to the client SDK?
  4. How long is the dedupe window, what client retry horizon is it sized from, and what happens to events older than it?
  5. Is processing deterministic on replay: event time, no wall clock, no randomness, versioned reference data?
  6. Is each output a full value per key (upsert) or a delta? If a delta, what makes it safe to replay?
  7. Is every transactional.id (or Flink prefix) stable across restarts and unique across jobs?
  8. Is every consumer of a transactional topic set to read_committed, including connectors, exports and ad hoc tools?
  9. What is the transaction timeout, how was it derived, and what alerts fire before a job's downtime reaches it?
  10. What is the committed-output freshness at p99, and does it fit every reader's budget, including during backpressure?
  11. Is there a reconciliation job comparing input and output counts per period, independent of the pipeline?
  12. When the logic is wrong, what is the replay plan, and does it keep the guarantee while it reprocesses history?

Deep Dive: Senior Interview Follow-ups

"Kafka's idempotent producer is on by default. Why isn't that exactly-once?"

It covers one hop: a producer's network retries into one partition, within one producer session. It does not cover a producer restart, because the new session has a new producer ID and its resends look like new data. It does not cover the consumer side at all. A consumer that processes, crashes before committing, and replays will produce its outputs again. Exactly-once effect needs the offsets and the outputs coupled, which takes transactions or an idempotent sink.

"What exactly does read_committed wait for, and what's the risk?"

It reads up to the last stable offset: the first record of the earliest transaction still open on that partition. It also filters out records from aborted transactions using the broker's aborted-transaction index. The risk is that one slow or hanging transaction holds back every committed reader of the partition, including data from unrelated producers written after it. So you watch the high-watermark-to-LSO gap, keep transaction timeouts sane, and know how to abort a hanging transaction.

"How does Kafka stop a zombie producer from committing?"

By epoch fencing. When a producer calls initTransactions() with a transactional.id, the coordinator bumps that ID's epoch and aborts anything left open. Writes and commits carrying the old epoch are rejected. That only works if the replacement uses the same ID, so IDs must be stable per unit of work. With exactly_once_v2, the consumer group generation is also checked on the offset commit, so a consumer that lost its partitions in a rebalance cannot commit offsets for them.

"Your Flink job was down for 20 minutes. Can it lose data even with exactly-once on?"

Yes. A checkpoint can complete while its sink transaction is still waiting to commit. If the job dies then and stays down past the Kafka transaction timeout, the broker aborts the transaction. On recovery Flink restores from that checkpoint, so it does not replay the interval, and the commit fails. That interval's output is lost. The fix is a timeout longer than the worst outage you expect, within the broker's transaction.max.timeout.ms, plus alerts on downtime and a reconciliation job.

"Can you get exactly-once into Postgres without Flink or Kafka transactions?"

Yes, two ways. First, store the consumer's offsets in Postgres and write results and offsets in one local transaction. On startup, seek to the stored offset. Second, if each output is a full value per key, use an upsert with a version guard, such as the source offset, so replays and stale writers are no-ops. Both depend on deterministic processing. The first also requires you to handle partition ownership during rebalances yourself.

"Why does an idempotent sink fail for a counter but work for a total?"

An upsert of "total = 987" is idempotent: writing it twice leaves 987. An output of "count += 412" is a delta, and applying it twice adds 824. Idempotent sinks need the job to emit the whole current value per key, which means the state that computed it must itself have been rewound with the offset. If the job emits deltas, you need either a transactional sink or a dedupe key per delta, such as (partition, offset range).

"Exactly-once is on everywhere. The numbers are still wrong after a code fix. What now?"

Exactly-once computes your bug faithfully. Fixing the logic needs a replay: run the fixed job from an older offset into a new output, compare, then switch readers. The replay must itself be deterministic and keep the guarantee, which is easiest if it writes to a fresh table or topic instead of overwriting in place. That is the Kappa move from Lambda & Kappa. Also check the replay window: you can only replay what the log still retains.

"Where would you not spend on exactly-once, even for money?"

Where a simpler mechanism already gives the effect. If the billing output is a daily total per partner, a keyed upsert with a version guard is exactly-once in effect, with no transactions and no freshness penalty. Spend on transactions when outputs are non-keyed, go to several topics atomically, or must move with offsets. And no amount of spending covers effects outside the log system; those need idempotency keys at the receiver.
