Deep Dive: Inside the Mechanism

"The app talks plaintext over localhost to its sidecar" hides a real question: how does the app's traffic get to the sidecar at all? The Checkout code still calls http://inventory:8080. Nobody changed it to call localhost. This section follows one call from Checkout to Inventory through a Kubernetes pod with an Envoy sidecar, the way Istio and similar meshes wire it. Then it covers lifecycle, protocol handling and the helper sidecars that are not proxies.

One pod, one network namespace

All containers in a Kubernetes pod share one network namespace. They share one IP address, one loopback interface, and one set of iptables rules. That shared namespace is what makes a transparent sidecar possible. Anything you do to the pod's network rules applies to the app container too, without touching the app.

Before the app starts, a setup step installs NAT rules in that namespace. In Istio this is either an init container (istio-init, which needs the NET_ADMIN capability) or a CNI plugin that does the same work on the node, so that application pods do not need elevated privileges. The rules say, roughly:

  • Outbound TCP from any process except the proxy's own user ID gets redirected to the proxy's outbound listener (port 15001 in Istio).
  • Inbound TCP to the pod gets redirected to the proxy's inbound listener (port 15006).
  • Traffic from the proxy's user ID (1337 by default) is excluded. Without that rule, the proxy's own outbound connections would be redirected back into itself in an endless loop.

So the Checkout app opens a TCP connection to Inventory's service IP, and the kernel quietly delivers it to Envoy on port 15001 instead. Envoy asks the kernel for the original destination (the SO_ORIGINAL_DST socket option) and learns the app meant inventory:8080. From there it acts as a normal reverse proxy:

  1. Listener and filter chain. Envoy matches the original destination to a listener configuration. For HTTP, the HTTP connection manager parses the request, which is where retries, timeouts and header-based routing can apply.
  2. Route and cluster. The route maps the request to a cluster, Envoy's name for a group of upstream endpoints (all healthy Inventory pods).
  3. Load balancing and pooling. Envoy picks an endpoint (round robin or least-request, for example) and takes a connection from its pool for that endpoint, or opens a new one.
  4. mTLS. The upstream connection uses the pod's workload certificate. The other side presents its own. Each side checks the peer's identity, often a SPIFFE ID such as spiffe://cluster.local/ns/shop/sa/inventory.

On the Inventory side, the inbound rule sends the connection to port 15006. Envoy ends TLS, records the caller's verified identity, applies any inbound policy, and forwards plaintext to 127.0.0.1:8080. The Inventory app sees a local connection.

The same intercept also catches calls to things outside the mesh, such as a payment provider or a managed database. Every sidecar configuration needs a rule for those: pass them through untouched, send them through an egress gateway, or block them.

Inside Envoy: workers and per-worker pools

Envoy runs a small number of worker threads. Each one owns its own connections and its own connection pools, so there is no locking on the hot path. The number of workers is the concurrency setting. Sidecar deployments usually set it low, often 2, because the sidecar's CPU limit is small and one worker per node core would be wasteful.

Per-worker pools have a side effect that surprises people. A sidecar with 2 workers, calling a service with 40 healthy endpoints, can hold up to 2 × 40 = 80 upstream connections for that one service over HTTP/1.1. HTTP/2 between sidecars multiplexes many requests per connection, which keeps the count closer to one per worker per endpoint. That is one reason meshes upgrade sidecar-to-sidecar traffic to HTTP/2 when they can.

Knowing what protocol it is carrying

To apply HTTP retries, the proxy has to know the bytes are HTTP. There are two ways it finds out:

  • Explicit declaration. In Kubernetes, the Service port's appProtocol field (or a port name prefix such as http- or grpc-) tells the mesh what to expect. This is reliable and costs nothing.
  • Sniffing. The proxy reads the first bytes of the connection and guesses. This works for client-first protocols such as HTTP, where the client speaks first. It does not work for server-first protocols such as MySQL or SMTP, where the server sends a greeting before the client says anything. The proxy waits for client bytes that never come, gives up after a timeout, and then treats the stream as plain TCP. Connections are slow to start, or fail.

Declare protocols explicitly for every port. Treat sniffing as a convenience for prototypes.

Startup and shutdown order

The lesson names the startup race. The mechanism is simple: by default, containers in a pod start in parallel. If the app is faster, its first outbound calls hit iptables rules that point at a proxy that is not listening yet, and they fail with connection refused.

There are three generations of fixes:

  • Hold the app. Istio's holdApplicationUntilProxyStarts injects the proxy first and uses a post-start hook that blocks until Envoy is ready. Kubernetes waits for that hook before starting the next container. It works, but it relies on container ordering details.
  • Native sidecar containers. Kubernetes added sidecars as a first-class concept. They are init containers with restartPolicy: Always. They start before the app containers, they must pass their startup probe before the app starts, and they keep running for the life of the pod. The feature was beta and on by default from Kubernetes 1.29 and became stable in 1.33. Check what your cluster version and mesh release support.
  • Shutdown order. On deletion, every container gets SIGTERM. If the sidecar exits first, the app's in-flight calls and its shutdown hooks (flush the last metrics, ack the last message) lose their network. Native sidecars are terminated after the app containers. With the older model, you configure a drain period on the proxy, or a preStop hook that waits for the app to finish.

Native sidecars also fix a long-standing problem with Kubernetes Jobs. With an ordinary sidecar container, the batch container finishes, but the proxy keeps running, so the pod never completes. Teams used to work around this with scripts that told the proxy to quit. A native sidecar is shut down automatically when the main containers finish.

Health checks through the proxy

Kubelet sends liveness and readiness probes to the pod IP. With strict mTLS on inbound traffic, a plaintext probe from the kubelet would be rejected, because the kubelet holds no workload certificate. Meshes therefore rewrite probes. The probe goes to an agent port on the sidecar (15020 or 15021 in Istio), and the agent calls the app's real health endpoint locally. The consequence matters in an incident: a failing probe can mean the app is sick, or that the sidecar's agent is. The health check lesson's distinction between shallow and deep checks now has a third layer.

Sidecars that are not proxies

The proxy is the famous sidecar, but the pattern is older and wider. In each case below, the helper shares the pod's lifecycle and its local resources, such as the network namespace or a shared volume.

  • Log shippers. The app writes to a file or stdout. A Fluent Bit or Vector sidecar tails it and ships it. Many clusters use a per-node agent instead, which is cheaper. A sidecar is the right choice when a pod needs its own parsing or its own destination.
  • Secret agents. A Vault Agent sidecar authenticates with the pod's service account, fetches short-lived secrets, writes them to a shared in-memory volume, and renews them. The app reads a file and never handles the auth flow.
  • Database auth proxies. Cloud SQL Auth Proxy, for example, runs beside the app and handles IAM authentication and TLS to the managed database. The app connects to localhost:5432.
  • Config reloaders. A small container watches a ConfigMap and signals the main process to reload when it changes.

Deep Dive: Sizing and the Numbers

Memory is mostly configuration

The lesson's 50 MB per sidecar is a reasonable baseline for a small mesh. The part that grows is configuration. By default, many meshes send every sidecar the routes, clusters and endpoints for every service, because any pod might call any other. Memory then grows with the size of the whole mesh, not with what this pod actually does.

A rough model for capacity planning:

sidecar_memory ≈ baseline + (services_known × per_service_cost)
               + (endpoints_known × per_endpoint_cost)

The coefficients depend heavily on the proxy version and on how much routing and telemetry is configured, so measure them on your own fleet. Two snapshots tell the story. At 11 services with 40 pods each, the per-service term is small and 50 MB holds. At 800 services with 20,000 endpoints, the same sidecar can need several times that, multiplied across every pod. The fix is scoping: tell each sidecar which services it actually calls. Istio's Sidecar resource does this, and other meshes have equivalents. A checkout pod that knows about 12 services instead of 800 uses close to baseline memory again, and receives far fewer config updates.

Reserved, not just used

Kubernetes schedules on requests, not on actual usage. If every sidecar requests 100 millicores of CPU and 64 MB of memory, the bookstore's 440 sidecars reserve:

CPU:    440 × 0.1 core = 44 cores reserved
Memory: 440 × 64 MB    ≈ 28 GB reserved

Those 44 cores are unavailable to anything else even if the sidecars idle at 10 millicores. At, say, 4 usable cores per node, that is 11 nodes of capacity you pay for. The usual tuning is per workload: small requests for quiet services, larger ones for the few hot paths. Set CPU requests from measured p95 usage, and watch for throttling if you also set CPU limits. A throttled proxy shows up as latency spikes, not as errors.

CPU per request

Proxy CPU scales with request rate, TLS work, and how much each request is inspected (telemetry, header manipulation, policy). A planning figure in the range of a few tenths of a vCPU per 1,000 requests per second, per proxy hop, is common for HTTP with telemetry enabled. Treat it as a starting point and load-test your own configuration.

Apply it to the bookstore. Internal east-west traffic peaks at 30,000 requests per second, and each request crosses two proxies. At 0.4 vCPU per 1,000 requests per second per hop:

30,000 / 1,000 × 2 hops × 0.4 vCPU = 24 vCPU at peak

That is spread across the fleet, and it is real money, but it is predictable. TLS handshakes are the spiky part. Each new mTLS connection costs an asymmetric signature on both sides. A mass reconnect after a deploy or a certificate rotation can briefly cost far more CPU than steady-state traffic. Long-lived pooled connections are what keep the steady state cheap.

Latency adds per hop, not per call

The lesson's figure is about 0.5 ms per sidecar, or 1 ms per call across two. How that adds up depends on the call graph's depth, not on its width.

  • The mobile BFF fans out 6 calls in parallel. Each pays about 1 ms extra, but they overlap, so the BFF's response gets about 1 ms slower, not 6.
  • Checkout calls Pricing, which calls Promotions, which calls Catalog. That is a chain of depth 4, so it adds about 4 ms to the end-to-end time.

The p99 grows more than the p50, because proxy queueing, CPU throttling and garbage pauses in the app now have one more place to land. When you set a latency budget, measure p99 per hop with and without the sidecar on a canary, and multiply by the depth of your deepest critical path.

Deep Dive: Failure Modes in Production

1. Retries multiply across layers

Symptom. Inventory has a 30-second slowdown. Its request rate jumps to 27 times normal, and the slowdown becomes an outage that lasts ten minutes.

Mechanism. The Checkout code still has its old client library with 3 attempts. The new sidecar policy also does 3 attempts. That is 9 requests per logical call. Checkout's caller, the BFF, also retries 3 times, so each user action can now produce 27 calls to Inventory. Moving retries into the sidecar only helps if you remove them from the code.

Detect. Compare request rate at the receiver with request rate at the original caller. Envoy also exports per-cluster retry counters (upstream_rq_retry and related stats). A retry ratio above a few percent during an incident is a warning.

Fix. Retry in exactly one layer, usually the sidecar nearest the failing call, and remove application retries as you migrate. Use retry budgets, which cap retries at a share of live traffic (Envoy supports a budget as a percentage of active requests), instead of a fixed count. Then retry only idempotent calls. The retry lesson's amplification math applies to every layer you add.

2. 503s under load, with healthy upstreams

Symptom. During a sale, Checkout gets bursts of 503s from Inventory. Inventory's own metrics show it is healthy and under half its capacity.

Mechanism. Envoy's per-cluster circuit breakers have thresholds, and they reject requests locally once a threshold is crossed. Envoy's defaults are 1,024 maximum connections, 1,024 pending requests and 1,024 active requests per cluster, plus a limit of 3 concurrent retries. A busy caller with slow responses can cross the pending-request limit while the upstream is fine. The 503 never leaves the calling pod.

Detect. Envoy access logs carry response flags. UO means upstream overflow: the local circuit breaker rejected the request. Compare that with UF (upstream connection failure), UH (no healthy upstream) and URX (retry limit reached). Put response flags into your logs and dashboards before your first incident. They answer "app or proxy?" in seconds.

Fix. Set circuit-breaker thresholds deliberately for hot paths, sized from Little's law: concurrent requests ≈ request rate × latency. At 3,000 requests per second and 300 ms latency during a slowdown, that is 900 in flight, uncomfortably close to 1,024. Raise the limits for that path, and keep the breaker as a real bulkhead rather than a hidden default.

3. Sporadic 503s on reused connections

Symptom. A low, steady rate of 503s, around 0.05%, between two services. They cluster after quiet periods. Retrying always works.

Mechanism. The upstream app server closes idle keep-alive connections after 5 seconds. The sidecar's pool keeps connections idle longer than that. Now and then, the sidecar sends a request on a connection at the exact moment the server closes it. The request dies with a connection reset.

Detect. Response flag UC (upstream connection termination) in the caller's sidecar logs, and the clustering after idle periods.

Fix. Make the proxy's upstream idle timeout shorter than the app server's keep-alive timeout, so the proxy always closes first. Or raise the app's keep-alive above the proxy's. This class of bug was already possible with any load balancer. A sidecar fleet just makes it appear between every pair of services at once.

4. Database connections hang after sidecar injection

Symptom. After a namespace is added to the mesh, a service's connections to MySQL take several seconds to establish, or time out. HTTP traffic is fine.

Mechanism. MySQL is server-first: the server sends its handshake greeting before the client speaks. The sidecar is sniffing the protocol and waits for client bytes. The client is waiting for the greeting. Both wait until the sniffing timeout passes.

Detect. Connection-establishment latency on the database client, and sidecar logs showing protocol detection timeouts. Ports with no declared protocol are a lint finding.

Fix. Declare the port as TCP (appProtocol: tcp, or a tcp- port name), or exclude that destination port from interception. Make "every port declares its protocol" a deploy-time check.

5. Sidecars OOM as the mesh grows

Symptom. Months after rollout, sidecars across unrelated services start getting OOMKilled. Nothing changed in those services.

Mechanism. Every new service and every new endpoint in the mesh adds configuration to every sidecar, as the sizing section showed. The memory limit that fit at 11 services does not fit at 200. And a config push for a big change hits all sidecars at once.

Detect. Sidecar memory usage plotted against mesh size (services and endpoints), not against the pod's own traffic. A slow upward drift in every pod at once is the tell. Also watch config push size and push frequency from the control plane.

Fix. Scope configuration so that each sidecar only knows what it calls. Then size limits from measured usage plus headroom, per workload class. This is a mesh concern, but it shows up as a sidecar crash.

6. The app sees every caller as 127.0.0.1

Symptom. After injection, the admin service's IP allowlist blocks everyone or allows everyone. Access logs show every request coming from 127.0.0.1.

Mechanism. The inbound sidecar ends the caller's connection and opens a new one to the app over localhost. The app now sees the sidecar as its peer. Its source-IP logic is checking the wrong thing.

Detect. A sudden collapse in the number of distinct client IPs in app logs after injection.

Fix. Stop authorising by IP inside the mesh. Authorise by the verified workload identity, which the sidecar can enforce or pass along in a header the app trusts only from localhost. For logging, read the forwarded-for header the proxy adds. Some meshes offer a transparent mode (TPROXY) that preserves the original source address, at the cost of more complex setup.

7. The last messages are lost on every deploy

Symptom. A queue consumer loses a few acknowledgements on each rolling deploy. Those messages are redelivered and processed twice.

Mechanism. On pod deletion, both containers get SIGTERM. The sidecar drains and exits within a second or two. The consumer is still finishing its batch, and its final ack call to the broker fails because the network path is gone.

Detect. Connection errors in app logs in the last seconds before exit, aligned with deploy events. Redelivery counts that spike on deploys.

Fix. Use native sidecars, which stop after the app. On older setups, give the proxy a drain period longer than the app's graceful shutdown, or add a preStop hook that waits for the app. And keep the handlers idempotent anyway, because redelivery will happen for other reasons too.

How to choose

  • Need only encryption and identity? A per-node L4 option gives mTLS without a proxy in every pod. That is much cheaper at 440 pods.
  • Need HTTP-aware behaviour for a few services? Add L7 processing only where you need it: a waypoint, or sidecars on those workloads alone. Not every service needs header-based routing.
  • Mostly gRPC, in languages with good xDS support? Proxyless gRPC gives sidecar-like policy with no extra hop. You lose uniformity for non-gRPC traffic.
  • Few languages, one team? The library remains the right answer, as the lesson says. None of these options is free.
  • Multi-tenant nodes with strict isolation? Per-pod sidecars keep each workload's keys and failure inside its own pod. A shared node proxy holds keys for every workload on that node. Some security teams will accept that and some will not, so ask early.

Deep Dive: Design-Review Checklist

  1. How is traffic intercepted: init container with NET_ADMIN, CNI plugin, or explicit localhost calls? Who is allowed to bypass it?
  2. Does every Service port declare its protocol? Which ports are server-first, and how are they handled?
  3. How is startup ordered (native sidecar or hold-until-ready), and how is shutdown ordered for long-running and batch workloads?
  4. Which layer owns retries now? Have application retries been removed, and is there a retry budget?
  5. What are the per-cluster circuit-breaker thresholds on the hot paths, and how were they sized?
  6. Are idle and keep-alive timeouts set so the proxy always closes first?
  7. What are the CPU and memory requests per workload class, measured from real usage? How much cluster capacity do they reserve in total?
  8. How does sidecar configuration size scale with the mesh, and is it scoped per workload?
  9. Do access logs include proxy response flags, and can on-call tell app errors from proxy errors in one query?
  10. How are health probes routed with strict mTLS, and what does a failed probe mean now?
  11. What does the app use for client identity now that the source IP is localhost?
  12. What is the rollout and rollback plan for a sidecar version upgrade across the fleet?

Deep Dive: Senior Interview Follow-ups

"The app calls inventory:8080 and was never changed. How does the traffic reach the sidecar?"

The containers in a pod share a network namespace. Before the app starts, an init container or CNI plugin installs iptables NAT rules in that namespace. Outbound TCP is redirected to the proxy's outbound port, and inbound TCP to its inbound port. Traffic from the proxy's own user ID is excluded, so its upstream connections are not looped back. The proxy reads the original destination from the socket and routes from there. The app never knows.

"You moved retries into the sidecar. Why did the incident get worse?"

Because the application's own retries were still there, so the attempts multiplied: 3 in the app times 3 in the sidecar is 9 per call, and more if a caller further up also retries. A short slowdown became a self-inflicted overload. Retries must live in exactly one layer, with a budget capped as a share of traffic, and only for idempotent operations.

"Inventory is healthy but Checkout sees 503s. How do you tell whether it's the proxy?"

Look at the proxy's access log response flags on the calling side. UO means the local circuit breaker rejected the request: upstream overflow. UF means the connection to the upstream failed. UC means the upstream closed a connection mid-request. UH means no healthy endpoints. A 503 with no flag came from the upstream app itself. Then compare with the upstream's request count. If the requests never arrived, it is the proxy.

"Why do sidecars use more memory in a big mesh even when the pod's traffic didn't change?"

Because by default each sidecar is given config for every service and endpoint in the mesh, in case the pod calls any of them. Memory and config-push volume grow with the mesh, not with the pod's own work. Scope each sidecar to the services it actually calls. That brings memory back near baseline and cuts the control plane's push traffic.

"What changed with native sidecar containers in Kubernetes?"

A sidecar can now be declared as an init container with restartPolicy: Always. It starts before the app containers and must pass its startup probe first. It keeps running alongside them, and it is stopped after they finish. That fixes the startup race, the shutdown race where the proxy dies before the app's final calls, and Jobs that never complete because the proxy keeps running.

"When would you choose a per-node proxy instead of a sidecar?"

When the requirement is mostly mTLS and workload identity, and per-pod cost matters. A per-node L4 proxy gives both with far less memory and no per-pod lifecycle. Add L7 proxies only for the services that need HTTP routing or retries. The trade-offs are a shared failure and key domain per node, and a newer operational model. If a security review requires per-workload key isolation, stay with sidecars.

"A team says the sidecar adds 1 ms, so their 6-call fan-out will add 6 ms. Right?"

Not if the calls are parallel. Each call pays about 1 ms, but they overlap, so the fan-out adds roughly 1 ms plus a little p99 widening. What adds up is depth: a chain of 4 sequential hops adds about 4 ms. Budget sidecar overhead by the depth of the critical path, and measure p99, not p50, on a canary with and without the sidecar.
