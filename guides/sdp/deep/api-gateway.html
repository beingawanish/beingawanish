Deep Dive: Inside the Mechanism

The lesson sets the boundary: routing, authentication once, shared policy, the observability root, and "policy yes, product no". A design review goes one level down. What does the gateway hold in memory? What does it check on each request, in what order? And how does a change to its config reach a fleet of instances without breaking everyone at once? Products differ (Kong, Envoy-based gateways, AWS API Gateway, Apigee), but they all share the same few moving parts.

Two planes: the config you write and the proxy that runs it

Every serious gateway splits into a control plane and a data plane. The control plane holds the desired config: routes, upstream services, plugins, consumers and their credentials. The data plane is the fleet of proxy instances that receive traffic. Each instance holds a compiled, in-memory copy of the config and never consults a database on the hot path.

  • Envoy-based gateways receive config over the xDS APIs: listeners (LDS), routes (RDS), clusters (CDS) and endpoints (EDS). An update replaces the in-memory route table without a restart.
  • Kong can run with a database, where nodes poll for changes, or DB-less, where each node loads a declarative YAML file. Hybrid mode puts the database behind a control plane that pushes config to data-plane nodes.
  • Managed gateways hide the split, but it is still there. A "deploy" of a stage is a config push to the provider's fleet.

This matters for two reasons. If the control plane is down, the data plane should keep serving the last good config, so check that it does. And config pushes are the most common way gateways cause outages, because one bad push reaches every instance. More on that in the failure modes.

The request pipeline, in order

A request passes through a fixed sequence of filters (Envoy's term) or plugin phases (Kong's). The order is a design decision. Cheap checks that reject the most traffic go first, so attackers pay before you do.

  1. TLS and connection limits. Terminate TLS, apply per-IP connection caps. Clients that cannot finish a handshake never reach the router.
  2. Normalise the path. Decode percent-encoding once, collapse //, resolve /./ and /../, and decide on case and trailing slashes. Do this before matching routes and auth rules. Envoy exposes options such as normalize_path and merge_slashes; other gateways have equivalents. Skipping this step is how /%61dmin slips past a rule written for /admin.
  3. Match the route. Routes are matched by host, then path (exact, prefix or regex), sometimes method and headers. Most gateways evaluate routes in a defined order or by specificity, and the first match wins. A broad prefix such as / placed too early swallows everything after it.
  4. Coarse limits. Request size, header size, and an IP-level rate limit for anonymous traffic. These are cheap and need no identity.
  5. Authenticate. Validate the credential (details below) and attach the identity to the request context.
  6. Identity-based limits and quotas. Now the limiter can key on the API key or account, which is the key the rate limiting lesson recommends.
  7. Validate. Optional schema validation of the body against an OpenAPI or JSON Schema document. Useful for public APIs, but it costs CPU per byte. Most teams validate only shape and size at the gateway and leave semantic checks to the service.
  8. Rewrite and forward. Strip any client-supplied identity headers, add the verified identity, add traceparent and a request ID, rewrite the path for the upstream, pick an endpoint, forward with a per-route timeout.
  9. Log and emit metrics after the response, tagged with route, consumer, status and upstream latency.

Authenticating once: JWTs, JWKS and the revocation problem

The lesson's incident was a service that ignored revocation. Fixing it at the gateway means deciding how the gateway knows a token is revoked, and that depends on the token type.

Self-contained tokens (JWTs). The gateway verifies the signature locally with the issuer's public key, then checks exp, nbf, iss and aud. Keys come from the issuer's JWKS endpoint. The gateway caches them and picks one by the token's kid header. Verification is local and costs microseconds of CPU, with no network call. The catch is that a valid signature says nothing about revocation. A stolen JWT works until it expires. You have three tools:

  • Short lifetimes. Access tokens of 5 to 15 minutes, renewed with a refresh token that the identity provider can revoke. Revocation takes effect within one access-token lifetime.
  • A denylist. The identity provider publishes revoked token IDs (jti) or "revoked before time T for user U" events. The gateway keeps them in memory or a shared store until each token's expiry. The list stays small because entries expire with the tokens.
  • Introspection for sensitive routes. For admin or payment routes, call the issuer's introspection endpoint (RFC 7662) and cache the answer for a few seconds.

Opaque tokens. The token is a random string, and only the issuer knows what it means. The gateway must introspect, which costs a network call, so it caches results for a short time. Revocation is as fast as that cache TTL. Opaque tokens are simpler to revoke and leak less information. JWTs are cheaper to verify. Many systems use opaque tokens on the outside and mint a short-lived internal JWT at the gateway.

API keys. For partners, a key is looked up in a local cache of hashed keys pushed from the control plane. Store hashes, not keys, so a leaked config does not leak credentials.

Passing identity inward without making it forgeable

After authentication, the gateway tells the service who the caller is. The naive way is a plain header, X-User-Id: 4521. It is safe only if two conditions both hold. The gateway must strip any X-User-Id the client sent. And the service must accept traffic only from the gateway. Break either one and any client, or any compromised internal service, can claim to be anyone.

Stronger options, in order of effort:

  • mTLS between gateway and services, so a service can verify the header came from the gateway's workload identity. A mesh gives you this.
  • A signed internal token. The gateway mints a short-lived JWT (a minute or so) with the user ID, tenant, scopes and the original token's ID, signed with a key only the gateway holds. Services verify it locally. This is a form of token exchange (RFC 8693 describes the standard flow). It survives hops: service A can forward it to service B, and B still knows the original user.

Either way, the external token should not travel past the gateway. Services that never see raw customer tokens cannot leak them into logs.

Timeouts, retries and the budget

The gateway is the outermost server-side layer, so it owns the outermost deadline. Give each route its own timeout, sized from that route's latency SLO, not one global 60 s. Pass the remaining deadline inward (gRPC does this with grpc-timeout; for HTTP, a header such as X-Request-Deadline is a common convention) so services stop working on requests the client has given up on.

Retries at the gateway need a cap. Envoy's retry_budget limits retries to a percentage of active requests (for example 20%) rather than a fixed count per request, which stops a struggling service from receiving 3 times its traffic. And retry only idempotent methods, or requests with an idempotency key, which is the same rule as for the reverse proxy.

A route, written as code

The lesson says routing should be team-owned and self-service. In practice that means each team owns a small declarative file, and CI validates and merges it into the gateway config. A Kong-style example for the orders split from the walkthrough:

services:
  - name: orders
    url: http://orders.internal:8080
    connect_timeout: 1000      # ms
    read_timeout: 3000
    retries: 0                 # Kong defaults to 5; POST /orders is not idempotent
    routes:
      - name: orders-public
        paths: ["/v1/orders"]
        strip_path: false
    plugins:
      - name: jwt
      - name: rate-limiting
        config: { minute: 600, policy: redis, limit_by: consumer }
      - name: request-size-limiting
        config: { allowed_payload_size: 1 }   # MB

  - name: fulfillment
    url: http://fulfillment.internal:8080
    routes:
      - name: fulfillment-public
        paths: ["~/v1/orders/(?<id>\\d+)/shipments"]   # "~" marks a regex path

A CI job should reject a file that adds a route outside the team's path prefix, removes authentication from a route, or sets a timeout above the route's SLO. Those three checks catch most of the dangerous changes.

Deep Dive: Sizing and the Numbers

Assumptions for the bookstore's gateway:

  • Peak 20,000 requests per second of north-south traffic, after the CDN has absorbed static content.
  • Mostly small JSON requests and responses (2 KB / 8 KB).
  • Per request: TLS on a warm connection, route match, JWT verify, one rate-limit check in Redis, header rewrite, forward, log.
  • Three availability zones.

CPU per request and instance count

Measure on your hardware, but a reasonable first budget for that pipeline is 0.2 to 0.5 ms of CPU per request. A plain proxy hop is a fraction of that. Verifying an RS256 or ES256 signature costs tens of microseconds. Logging, metrics and plugins written in a scripting language (Lua in Kong, for example) add the rest.

  • At 0.4 ms per request: 20,000 × 0.0004 = 8 cores busy at peak.
  • Run cores at no more than about 50% at peak so latency stays flat and a zone can fail: 16 cores in total.
  • Spread across three zones, if one zone fails the other two must carry everything. So each zone needs 8 cores' worth of headroom: 3 zones × 8 cores = 24 cores, for example 6 instances of 4 cores.

Two things can blow this budget up. New TLS handshakes during a reconnect storm, such as a mobile release, cost far more CPU than requests on warm connections. And body-level work, like schema validation or response transformation, costs CPU per byte rather than per request. A 1 MB body validated against a schema can cost more than a thousand ordinary requests.

Where the 1 to 2 ms goes

The lesson quotes 1 to 2 ms per request. A typical breakdown:

  • Proxy processing and route match: under 0.2 ms.
  • JWT verification with cached keys: well under 0.1 ms.
  • Rate-limit check in shared Redis in the same zone: about 0.5 ms round trip.
  • Hop to the service over a pooled connection: a few hundred microseconds inside a zone, more across zones.

The biggest single item is usually the rate-limit call. If 0.5 ms matters, use local buckets with periodic sync for protection limits and keep Redis only for exact quota counting. The other trap is synchronous calls to an external auth service on every request. That turns 1 ms into 10 ms and makes the auth service's availability your API's availability.

Connections

The gateway holds two sets of connections. Downstream: one per active client, which can be large for mobile apps with long keep-alive, plus long-lived WebSocket or SSE connections that pin memory and file descriptors for hours. Upstream: pools to each service. With 40 routes to 11 services, 6 gateway instances and, say, 8 worker threads each holding 32 idle connections per service, that is 6 × 8 × 32 = 1,536 connections into each service. Check that number against the service's own connection limits and its database pool. Gateways can overload services just by holding connections open.

Availability arithmetic

The gateway sits in series with everything. If each service has 99.95% availability and the gateway has 99.95%, a request that needs one service sees about 99.9%. That is why the gateway's own target is usually set higher than any service's, and why "keep it thin" is an availability argument. Most gateway downtime comes from changes, not hardware. Fewer, safer changes are the cheapest nines you can buy.

Deep Dive: Failure Modes in Production

1. One config push breaks every route

Symptom: every API call returns 404 or 503 within a minute of a routine change. Mechanism: a team added a route with a broad prefix (/v1) that matched before more specific ones. Or a typo in an upstream name produced a cluster with no endpoints. The control plane validated the syntax, not the effect, and pushed it to every instance at once. Detect: a sharp change in 404/503 rates per route right after a config version change. Tag every metric with the config version so the correlation is obvious. Fix: validate routing changes in CI against a suite of known requests ("GET /v1/orders/7 must reach orders"). Roll config out to one instance or one zone first, watch error rates, then continue. Keep the previous config one command away.

2. Key rotation logs everyone out

Symptom: a burst of 401s across all routes, starting when the identity team rotated signing keys. Mechanism: new tokens carry a new kid. The gateway's cached JWKS does not contain it, and either it does not refetch on an unknown kid, or it refetches but the identity provider published the key only at the moment of rotation. Some gateway instances got the new set and some did not. Detect: 401s broken down by reason ("unknown kid" versus "expired" versus "bad signature"). Without the reason, this looks like an attack. Fix: publish new keys in the JWKS well before signing with them, and keep old keys until every token they signed has expired. Make the gateway refetch on an unknown kid, rate-limited so attackers cannot force a refetch on every request. Serve from the last good key set if the JWKS endpoint is down.

3. A client becomes another user with one header

Symptom: a penetration test reads another customer's orders by sending X-User-Id: 1. Mechanism: the gateway added X-User-Id for authenticated routes but did not remove one sent by the client on a route where auth was optional. Or a service was reachable without going through the gateway, through an internal load balancer or a debug port. Detect: a test in CI that sends forged identity headers to every route and expects them gone; network policy audits for service ports reachable from outside the gateway. Fix: strip all identity headers unconditionally at the first filter. Prefer a signed internal token over plain headers. Enforce with network policy or mTLS that services accept requests only from the gateway or the mesh.

4. An admin route is reachable through an encoded path

Symptom: requests to /internal/admin are blocked, but /internal/%61dmin or /internal//admin reach the admin handler. Mechanism: the gateway matched the raw path against its deny rule, then forwarded it. The service's framework decoded and normalised the path and routed it to the admin handler. Two parsers disagreed. Detect: fuzz tests with encoded, doubled-slash and dot-segment paths against protected routes; logs showing non-normalised paths reaching services. Fix: normalise once at the gateway before matching, reject ambiguous paths (encoded slashes, for example) rather than guessing, and forward the normalised path. Better still, do not rely on path-based deny rules for internal endpoints. Keep them off the public listener entirely.

5. A slow service becomes a dead service

Symptom: the reviews service slows from 50 ms to 2 s, and within minutes its traffic is several times normal and it stops responding entirely. Mechanism: retry amplification. The client SDK retries 3 times, the gateway retries 2 times, and the service's own client retries its database. One user action becomes up to 3 × 3 = 9 requests at the service, all arriving while it is already struggling. Detect: compare requests received at the service with unique request IDs; a ratio well above 1 means retries. Envoy reports retry counters per cluster. Fix: retry at one layer only, usually the client with backoff and jitter. If the gateway retries, use a retry budget (a percentage of traffic) and never retry on timeout for non-idempotent methods. Add a circuit breaker per upstream so the gateway fails fast while the service recovers.

6. One route's traffic slows every route

Symptom: a partner's bulk export endpoint is busy, and checkout latency at the gateway rises even though the checkout service is healthy. Mechanism: the gateway's workers or connection slots are shared. Large, slow responses from the export route hold workers, buffers and upstream connections. Envoy's per-cluster limits apply per upstream, but CPU and memory are shared by the whole process. Detect: gateway-side latency (total time minus upstream time) rising for routes whose upstreams are fine; per-route active request counts. Fix: cap concurrency per route or per consumer; move bulk and streaming traffic to a separate gateway pool or listener; serve large exports from object storage with a signed URL instead of streaming them through the gateway.

7. The identity provider's outage becomes a full outage

Symptom: the identity provider has a 10-minute incident, and the entire API returns 401 or 503 for 10 minutes, including public catalog reads. Mechanism: the gateway calls an external auth service or introspection endpoint on every request, with no cache and no fallback. Public routes went through the same auth plugin with "optional" auth that still made the call. Detect: correlation between auth-service latency and gateway error rate; the auth call's share of gateway latency. Fix: verify JWTs locally with cached keys; cache introspection results for a short time; skip auth entirely on public routes rather than making it optional; decide per route whether to fail open or fail closed when the auth dependency is down, and write that decision down.

The decision that matters most over time is topology. A single gateway owned by a platform team works well while that team says no to product logic and makes routing self-service. It fails when it becomes the approval queue the lesson warns about. If you split into per-domain gateways, keep one thing shared: a common authentication and identity module, versioned and enforced in CI. Otherwise you rebuild the eleven-implementations incident, with gateways instead of services.

On fail-open versus fail-closed: there is no universal answer, so decide per policy. Authentication fails closed. Nobody gets in on a broken token check. Protection rate limits usually fail open, because an unavailable Redis should not block all customers. Billing quotas often fail open with reconciliation later. Write the choice for each dependency into the design doc, because during the incident nobody will have time to debate it.

Deep Dive: Design-Review Checklist

  1. List every plugin or filter on a typical route, in order. Do the cheapest rejections run first?
  2. Where is the path normalised, and do the gateway and the services interpret paths identically?
  3. How does a revoked token stop working, and within how many seconds? What happens on signing-key rotation?
  4. How is identity passed to services, and what prevents a client or another service from forging it?
  5. Can any service be reached without going through the gateway or the mesh?
  6. What is each route's timeout, and is it shorter than the client's and longer than the service's? Which layer retries, with what budget?
  7. How is config changed: who can change it, how is it tested, how is it rolled out in stages, and how fast can it be rolled back?
  8. What happens when the control plane, the identity provider or the rate-limit store is down? Fail open or closed, per policy?
  9. What is the CPU budget per request, and what is the headroom after losing one zone and during a reconnect storm?
  10. Which routes carry large bodies or long-lived connections, and are they isolated from interactive traffic?
  11. What is in the gateway that uses a domain word? Who approved it, and when will it move out?
  12. Do logs carry route, consumer, config version, upstream latency and the request ID that traces use?

Deep Dive: Senior Interview Follow-ups

"JWTs are verified locally. How do you revoke a stolen one before it expires?"

Keep access tokens short (5 to 15 minutes) so the problem is bounded, and revoke the refresh token at the identity provider. For faster revocation, the provider publishes revoked token IDs or "revoked before T for user U" events, and the gateway holds them in memory until the tokens' expiry, so the list stays small. For the most sensitive routes, introspect with a short cache. You cannot get instant revocation and zero network calls at the same time; pick per route.

"The gateway forwards X-User-Id. Why isn't that enough?"

A plain header is only as trustworthy as the path it travelled. If the gateway fails to strip a client-supplied copy on any route, or a service is reachable without the gateway, anyone can claim any identity. Strip unconditionally, and either enforce gateway-only reachability with mTLS or network policy, or send a short-lived token signed by the gateway that services verify. The signed token also survives service-to-service hops.

"Where should the request timeout be set: client, gateway or service?"

All three, nested. The client's deadline is the longest, the gateway's per-route timeout sits inside it, and the service's calls to its dependencies sit inside that. The gateway should pass the remaining deadline inward so services stop working on abandoned requests. If the order is reversed, the gateway returns 504 while the service carries on, and a client retry can duplicate a write.

"Should the gateway retry failed requests?"

Only in a limited way. Retrying a connection failure before any bytes were sent is safe and hides instance churn. Retrying timeouts or 5xx on non-idempotent methods can duplicate writes. Retrying at several layers multiplies load on a struggling service. If the gateway retries, use a budget (for example, retries may add at most 20% to traffic) and make the client the main retry layer, with backoff and jitter.

"Gateway CPU is 30% but p99 latency is up. What do you look at?"

First, split total time into gateway time and upstream time in the logs. If upstream time is up, it is not the gateway. If gateway time is up, look at synchronous calls made by plugins (rate-limit store, auth service, introspection), connection pool exhaustion toward one upstream (requests waiting for a connection), large bodies being buffered or validated, and garbage collection or scripting overhead in plugins. A shared resource held by one noisy route is a common cause.

"How do you stop the gateway from becoming a release bottleneck for 30 teams?"

Make routine changes self-service. Each team owns a config file for its own path prefix. CI checks it (no routes outside the prefix, auth required, timeouts within limits) and merges it without the platform team. The platform team owns the pipeline, the shared plugins and the rules. It does not own each route. Anything that needs a custom plugin with domain logic gets redirected to a BFF or the service.

"The identity provider is down. Should the gateway fail open?"

Not for authentication. If you cannot verify a credential, you cannot let the request in. But design so that an identity provider outage does not stop verification. Verify JWTs locally with cached keys, keep the last good JWKS if the endpoint is unreachable, and cache introspection results briefly. Then the outage blocks only new logins, not existing sessions. Public routes should not touch auth at all.

"A rule says 'premium customers get the fast search index'. Gateway or service?"

Service, or a BFF. "Premium" and "search index" are domain words, so the rule is product behaviour. The gateway can forward the verified plan as part of the identity, and it can apply a higher rate limit for the premium tier, because that is policy stated without domain words. But choosing which index to query belongs in the search service, where the search team can test and change it.
