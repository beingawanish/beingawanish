Deep Dive: Inside the Mechanism

The lesson gives you the two verdicts. A design review goes one level lower: who actually sends the probes, what they do with the answer, and how long each step takes. Most health-check incidents are not bad ideas. They are a sensible idea meeting a prober whose behaviour nobody looked up.

Three probers, three different reactions

A typical service on Kubernetes behind a cloud load balancer is probed by at least three separate systems. Each one reads a different endpoint and takes a different action.

  • The kubelet, the agent on each node. It runs the liveness, readiness and startup probes defined in the pod spec. A liveness failure makes it kill and restart the container. A readiness failure makes the control plane remove the pod from the Service's EndpointSlices, so kube-proxy and any mesh stop sending it new connections.
  • The external load balancer. An AWS target group, a GCP backend service or an nginx upstream runs its own active checks on its own schedule. Its only action is to stop routing to the target. It knows nothing about the kubelet's verdict unless you wire the two to the same endpoint.
  • The mesh sidecar or client-side balancer. Envoy and gRPC clients often do passive health checking, called outlier detection. They watch real responses and eject a host that returns, say, five consecutive 5xx responses, for a base ejection time that grows with each repeat.

The practical consequence: you cannot reason about "the health check" as one thing. Write down each prober, which path it calls, its interval, its timeout and its action. That table is usually the first artefact a reviewer asks for, and it is often missing.

The Kubernetes probe knobs, and what each one trades

Every Kubernetes probe has the same five fields. The defaults are worth knowing because many teams never change them.

FieldDefaultWhat it trades
periodSeconds10Faster detection against more probe load. Halving it doubles the probe rate fleet-wide.
timeoutSeconds1A short timeout catches hangs quickly, but a 1.2 s GC pause becomes a failure. Too long, and a stuck handler holds the probe for seconds.
failureThreshold3How many consecutive failures before acting. Higher means fewer false restarts and slower reaction.
successThreshold1Consecutive passes before a failed readiness probe counts as ready again. Must be 1 for liveness and startup.
initialDelaySeconds0A fixed wait before the first probe. Mostly replaced by a startup probe, which adapts to actual start time.

Probes come in four kinds: httpGet (any status from 200 to 399 passes), tcpSocket (the port accepts a connection), grpc (the standard grpc.health.v1.Health/Check call), and exec (run a command inside the container). The exec kind deserves suspicion. It forks a process every period on every pod. On a busy node with dozens of pods that is real CPU, and a slow fork looks exactly like a failed check.

The startup probe: a third verdict the lesson implies

The lesson says readiness starts false while the instance warms up. There is a related problem on the liveness side. A JVM service that takes 90 seconds to load its caches will fail a liveness probe with default settings after about 30 seconds (three failures, ten seconds apart). The kubelet kills it. It starts again, takes 90 seconds again, and is killed again. That is a crash loop with nothing actually broken.

The old fix was a big initialDelaySeconds. That delays deadlock detection on every start, even fast ones. The better fix is a startup probe. While it is still failing, the kubelet does not run liveness or readiness at all. Once it passes once, it never runs again for that container and the normal probes take over. Its budget is failureThreshold × periodSeconds, so 30 × 10 allows up to 300 seconds to start, and a fast start hands over after the first pass.

So in practice there are three questions, asked in sequence: "have I finished starting?", then continuously "am I alive?" and "should I get traffic?"

The lifecycle, step by step, including the shutdown race

The lesson describes the readiness lifecycle in words. Here it is as a timeline, because the shutdown half contains a race that catches almost everyone once.

When Kubernetes deletes a pod, two things start at the same moment. The control plane begins removing the pod from EndpointSlices, and the kubelet runs the pod's preStop hook and then sends SIGTERM. Removal is not instant. kube-proxy on every node has to rewrite its rules, ingress controllers have to reload, and an external load balancer has to deregister the target. That takes from a second to several seconds.

If the process exits on SIGTERM straight away, callers that have not yet heard about the removal keep sending it requests. They get connection refused. Every deploy then produces a small burst of 502s that nobody can reproduce. Failing readiness on SIGTERM does not fix this on its own, because readiness only matters to the same slow propagation path.

The standard fix is boring and effective. Put a short sleep in preStop (5 to 15 seconds is common), so the process keeps serving while the removal spreads. Recent Kubernetes versions offer a built-in sleep action for this; older setups run sleep in an exec hook. Then on SIGTERM, stop accepting new connections, finish in-flight requests, close keep-alive connections, and exit. Set terminationGracePeriodSeconds (default 30) larger than the sleep plus your longest normal request. If the grace period runs out, the kubelet sends SIGKILL and whatever was in flight is lost.

What the handler itself should look like

The lesson's rule is "be nearly free". In code that means the probe handler reads state, it does not compute it. Background tasks maintain a few flags and timestamps. The handler only looks at them.

import threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

state = {"started": False, "draining": False, "db_pool_ok": False,
         "worker_heartbeat": time.monotonic()}

class Health(BaseHTTPRequestHandler):
    def do_GET(self):
        now = time.monotonic()
        if self.path == "/livez":
            # Only what a restart fixes: the main loop is still turning.
            ok = now - state["worker_heartbeat"] < 30
        elif self.path == "/readyz":
            ok = state["started"] and not state["draining"] and state["db_pool_ok"]
        else:
            self.send_response(404); self.end_headers(); return
        self.send_response(200 if ok else 503)
        self.send_header("Cache-Control", "no-store")
        self.end_headers()

    def log_message(self, *args):  # probes would flood the access log
        pass

# Served on its own port and thread pool, so request overload
# cannot starve the probe.
threading.Thread(target=ThreadingHTTPServer(("0.0.0.0", 8081), Health).serve_forever,
                 daemon=True).start()

Three details in that sketch matter more than the language. The liveness check reads a heartbeat that the real work loop updates, so a deadlocked worker fails it even while the HTTP server is fine. The readiness flag for the database is set by the connection pool's own event hooks, not by a query in the probe. And probes are served on a separate port and thread pool, which is the subject of the first failure mode below.

Some ecosystems give you this shape ready-made. Spring Boot Actuator exposes /actuator/health/liveness and /actuator/health/readiness as separate groups. gRPC services implement grpc.health.v1 and can report NOT_SERVING per service name. Kubernetes' own API server uses /livez and /readyz, which is where the naming convention comes from.

Fail-open: what the balancer does when everyone is red

There is one more mechanism that changes the lesson's "deep check removes the whole fleet" story, and it is easy to miss. Several load balancers refuse to believe that every backend is down.

  • Envoy has a panic threshold, 50% by default. If fewer than half the hosts in a cluster are healthy, Envoy ignores health and spreads traffic across all hosts.
  • AWS Application and Network Load Balancers fail open: if no target in any zone is healthy, they route to all targets.
  • Kubernetes Services do not. An endpoint that is not ready receives no traffic from kube-proxy, even if that leaves zero endpoints.

Fail-open is a safety net, not a design. It means a deep readiness check that goes red fleet-wide may cause a full outage behind kube-proxy and almost nothing behind an ALB. Same code, different blast radius. Know which one you are behind before you decide what readiness may include.

Deep Dive: Sizing and the Numbers

Health checks look free until you add up the probers, the detection delays and the drain windows. Here is the arithmetic for the lesson's example fleet: 30 services, 40 instances each, 1,200 instances in all.

Probe load, counted honestly

The lesson counts one prober at one probe every 2 seconds: 600 checks per second. Count every prober and the number grows quickly.

ProberPer instanceFleet (1,200 instances)
kubelet liveness, every 10 s0.1/s120/s
kubelet readiness, every 5 s0.2/s240/s
Cloud load balancer, every 10 s, from 3 nodes0.3/s360/s
Mesh sidecar active checks, every 5 s, from 20 client pods4/s4,800/s
Total~4.6/s~5,500/s

Two rows surprise people. Cloud load balancers run one checker per load balancer node, so a target sees the configured rate times the number of nodes. And a mesh that does active checks from every client to every server grows with clients times servers. That is why most meshes lean on passive outlier detection and leave active probing to the kubelet.

At about 1 ms of in-memory work each, 5,500 checks per second costs about 5.5 CPU-seconds per second across the fleet. That is fine. Now put a 5 ms database query inside the readiness path and the database receives an extra 240 queries per second from the kubelet alone, forever, carrying no user value. Put it in the mesh path and it is thousands. This is the lesson's "be nearly free" rule in real numbers.

Detection time and recovery time

The time from "instance breaks" to "prober acts" is roughly:

detection ≈ periodSeconds × failureThreshold + timeoutSeconds

With Kubernetes defaults that is 10 × 3 + 1 = 31 s. For readiness with a 5-second period, about 16 seconds. Add EndpointSlice propagation (a few seconds) and the real de-routing time is around 20 seconds. During that time the broken instance still gets its share of traffic. With 40 instances, that is 2.5% of requests failing for 20 seconds.

Recovery is asymmetric. A de-routed instance comes back after successThreshold × periodSeconds. A restarted one has to start, warm and pass its startup probe first. If start-up takes 60 seconds, a single false liveness restart costs a minute of that instance's capacity. Repeated false restarts back off: the kubelet waits 10 s, 20 s, 40 s and so on between restarts, capped at five minutes. That cap is how a 90-second database failover turns into the lesson's 20-minute outage. The pods are still sitting in back-off long after the database is fine.

Choosing thresholds from the worst pause you expect

Pick liveness settings from the longest legitimate stall, not from how fast you would like to detect deadlocks. Suppose the service's worst observed stop-the-world GC pause is 2 seconds and a traffic spike can stretch probe latency to 3 seconds. Then:

  • timeoutSeconds: 5 keeps one slow answer from counting as failure.
  • failureThreshold: 3 with periodSeconds: 10 means a stall must last about 30 seconds to trigger a restart.
  • A real deadlock is caught in about 35 seconds. That is slow, and that is fine. A deadlock that costs 35 seconds of one instance's capacity is cheap. A false restart storm across the fleet is not.

Readiness can be tighter, because its action is reversible: period 5, threshold 2, timeout 2. You want an overloaded or draining instance out of rotation quickly, and back quickly once it recovers.

Drain timing for a deploy

Take a service whose p99 request is 800 ms and whose slowest legitimate request, a large export, takes 20 seconds. Endpoint removal takes up to 5 seconds to reach every node and the external balancer.

  • preStop sleep: 10 s, double the observed propagation.
  • Drain after SIGTERM: up to 20 s for the longest request.
  • terminationGracePeriodSeconds: 10 + 20 + 5 s margin = 35 s, just above the default 30.

Now the deploy cost. A rolling deploy of 40 pods with maxSurge: 25% and maxUnavailable: 0 replaces about 10 pods at a time. Each wave takes start-up (say 40 s) plus readiness passing (5 s) plus termination (up to 35 s), so roughly 80 seconds per wave and about 5 to 6 minutes for the fleet. If the external load balancer uses a 300-second deregistration delay (the AWS target group default), each wave can stretch to five minutes. Tune that delay down to match your real drain time.

Deep Dive: Failure Modes in Production

The lesson covers the classic: a database check inside liveness. These are the ones that show up after the team has already fixed that.

1. The probe waits in the same queue as the traffic

Symptom. Under a traffic spike, pods start restarting one after another. Each restart pushes more load onto the survivors, and they restart too. The liveness check contains no dependencies at all.

Mechanism. The probe is served by the same thread pool or event loop as user requests. When the pool is saturated, the probe waits behind 500 queued requests and times out after 1 second. The kubelet reads "not alive" and restarts a process that was merely busy. Restarted pods come back cold and slower. The overload gets worse, not better.

Detection. Container restart count rises together with request latency and CPU saturation. Kubernetes events show Liveness probe failed: ... context deadline exceeded rather than a non-200 status.

Fix. Serve probes on a separate port with a dedicated small thread pool or a separate listener. Base liveness on a heartbeat from the work loop rather than on whether an HTTP request gets through the main queue. Handle overload with load shedding and rate limiting, not with restarts.

2. Readiness that tracks load, and the cascade it causes

Symptom. A moderate spike turns into a full outage within a minute. Ready pod count drops from 40 to 30, then 15, then 0.

Mechanism. Someone made readiness fail when the in-flight count exceeds a limit, which sounds sensible. An overloaded pod goes unready. Its traffic moves to the other 39, which pushes several of them over the limit. They go unready, and the remaining pods receive even more. Readiness has become positive feedback.

Detection. Ready endpoint count falls in steps while total traffic is flat or only mildly up. Each step follows a spike in per-pod in-flight requests.

Fix. Readiness answers "can I serve", not "am I busy". An overloaded instance should stay in rotation and reject the excess quickly with 429 or 503, which balancers and clients handle better than disappearing capacity. If you must signal load, use a weighting mechanism (least-request balancing, or Envoy's outlier detection with max_ejection_percent capped, which defaults to 10%), not a binary in/out switch.

3. Flapping between ready and unready

Symptom. One pod's readiness toggles every 10 to 20 seconds. Its connection pool is constantly being rebuilt by callers. Error rates show a sawtooth.

Mechanism. The readiness condition sits right on a threshold, for example "replication lag under 1 second" on a read service. Each de-routing removes load, lag drops, the pod comes back, load returns, lag rises. With successThreshold: 1 and failureThreshold: 1 there is no damping.

Detection. Count readiness transitions per pod per hour. More than a handful is a signal on its own.

Fix. Add hysteresis. Fail at one threshold and recover at a stricter one (fail above 5 s of lag, recover below 1 s). Raise successThreshold to 2 or 3 so recovery needs sustained evidence.

4. A burst of 502s on every deploy

Symptom. Each rolling deploy produces a few dozen 502 or connection-reset errors at the ingress, always during termination of old pods.

Mechanism. The shutdown race from the mechanism section. The process exits on SIGTERM while kube-proxy rules or the ingress still point at it. A second version of the same bug is keep-alive: the ingress holds a pooled connection to the old pod, sends a request on it just as the pod closes it, and gets a reset.

Detection. Correlate ingress 502s with pod termination timestamps. Ingress logs will show "upstream prematurely closed connection" or connection refused to a pod IP that no longer exists.

Fix. A preStop sleep longer than propagation. On SIGTERM, stop accepting new connections but keep serving existing ones. Send Connection: close on responses during drain, or an HTTP/2 GOAWAY, so clients stop reusing the connection cleanly. Make sure the server's keep-alive idle timeout is longer than the ingress's, so the ingress always closes first.

5. The dependency that sneaked in through a library

Symptom. A Redis outage de-routes every instance of a service that was designed to degrade without Redis.

Mechanism. The framework's health endpoint auto-registers a check for every client it sees on the classpath: database, Redis, message broker, mail server. A library upgrade added the Redis client. The aggregated status turned DOWN when Redis did, and readiness was wired to the aggregate. Nobody wrote the check. It arrived with a dependency bump.

Detection. Probe responses that include a component list. Diff the list between releases. A new component appearing in a release that "only upgraded libraries" is the red flag.

Fix. Configure readiness and liveness as explicit groups with an allowlist of checks, never "everything the framework found". Add a test that fails the build when a new component joins the readiness group. This is the lesson's "probe code needs an owner" rule turned into automation.

6. Green from a cache, or green from the wrong process

Symptom. The balancer keeps sending traffic to an instance whose application has crashed. Every request fails, yet the target shows healthy.

Mechanism. One of two things. The health path is answered by something other than the application: an nginx sidecar that returns a static 200, or a CDN or proxy that cached the 200 response. Or the probe is a tcpSocket check, and the port belongs to a sidecar proxy that stays up when the app dies.

Detection. High 5xx rate from one target while its health check stays green. Request traces end at the sidecar.

Fix. The health path must reach the application process. Send Cache-Control: no-store on probe responses. Prefer HTTP or gRPC probes over TCP. With a sidecar, the readiness check should cover the app itself, as the sidecar lesson notes, and the app should not report ready before its sidecar is.

7. The health endpoint as an attack surface

Symptom. The security review finds the public internet can reach /health, and the response lists the database hostname, versions of every library, and the build commit. Or an attacker floods it and, because it does real work, takes the service down.

Mechanism. Diagnostic detail that was meant for operators went to every caller. A deep endpoint that runs queries turns into an unauthenticated amplifier.

Detection. External scanning of your public routes. Request rate to the health path from non-prober IP addresses.

Fix. Serve probes on an internal port that the ingress does not route. Return a bare status to unauthenticated callers. Put rich diagnostics behind authentication on a separate path.

The lesson settles shallow against deep. A design review usually has to settle five more choices.

The "warn" state, and why the prober must never see it

Many health formats have a third state between pass and fail: degraded, or warn. It is genuinely useful for operators. The cache is down, we are serving from the database, latency is up. The mistake is letting that state change the status code. Probers only understand two answers, so warn must map to 200. Send the detail to metrics and dashboards, where a human or an alert rule can decide what it means.

Workers and consumers

The lesson says queue consumers need liveness plus backlog age. Two details make that work. First, liveness should check that the consumer loop has polled recently, not that the broker connection is open. A consumer stuck inside one poison message still has a healthy connection. Second, backlog age belongs to the consumer group, not to one instance. Alert on it centrally. A per-pod probe on backlog would restart the whole group when the backlog grows, which is the opposite of what you want. Consumer lag scaling, as in the auto-scaling lesson, is the right reaction.

A default worth defending

If you need one recommendation for a typical HTTP service: three probes on an internal port. A startup probe sized to the slowest start. A liveness probe that reads a heartbeat, period 10 s, timeout 5 s, threshold 3. A readiness probe that reads start-up, drain and essential-pool flags, period 5 s, threshold 2. Passive outlier detection in the mesh. Deep checks only in central monitoring. Deviations from that should come with a reason written down.

Deep Dive: Design-Review Checklist

  1. List every prober (kubelet, load balancer, mesh, service registry). For each: path, interval, timeout, threshold and action. Does anyone own this table?
  2. What exactly does liveness check, and can a restart fix every condition in it? Show the code, not the config.
  3. Which dependencies does readiness include? For each one, what happens fleet-wide when it fails, and is that what you want?
  4. Is the readiness and liveness check list an explicit allowlist, or does the framework add checks automatically when libraries appear?
  5. Are probes served on a path that user overload cannot starve: separate port, separate thread pool?
  6. What is the slowest observed start-up, and does the startup probe budget cover it with margin?
  7. What is the longest legitimate pause (GC, compaction, cold cache) and are the liveness timeout and threshold set above it?
  8. Walk through termination: preStop sleep, endpoint propagation time, SIGTERM handling, keep-alive closing, grace period. Do the numbers add up?
  9. Does readiness change with load? If so, what stops the cascade when one pod goes out?
  10. Does the balancer in front of this service fail open or closed when every target is red, and does that match the service's risk?
  11. Can the public internet reach the probe paths, and what does an unauthenticated response reveal?
  12. Which metrics prove the probes behave: restart counts, readiness transitions per pod, ready endpoint count, probe latency?

Deep Dive: Senior Interview Follow-ups

"Your liveness check has no dependencies, yet pods restart in a cascade during traffic spikes. Why?"

The probe is queued behind user requests. When the server's thread pool or event loop saturates, the probe times out and the kubelet reads that as death. Restarts remove capacity and bring back cold pods, so load per survivor rises and more probes time out. Fix it by serving probes on a separate listener with its own threads, and basing liveness on a work-loop heartbeat. Handle overload by shedding load, never by restarting.

"Should readiness fail when the instance is overloaded?"

Usually no. Binary removal moves all of that pod's traffic onto the others, which pushes them over the same limit, and the fleet collapses in steps. An overloaded instance should stay in rotation and reject excess fast with 429 or 503, so the system degrades smoothly. If you want load-aware routing, use least-request balancing or outlier ejection with a cap on the ejected percentage.

"We mark readiness false on SIGTERM. Why do we still see 502s during deploys?"

Because readiness changes travel the same slow path as pod deletion. Endpoint removal takes seconds to reach every kube-proxy, ingress and external balancer, while SIGTERM arrives immediately. If the process stops serving on SIGTERM, late callers hit a closed port. Add a preStop sleep longer than the propagation delay, keep serving during it, then drain, and close keep-alive connections with Connection: close or GOAWAY.

"Why do we need a startup probe if readiness already starts false?"

Readiness protects users from a cold instance. It does nothing to stop liveness from killing a slow starter. Without a startup probe, a 90-second start meets a 30-second liveness budget and the pod crash-loops forever. The startup probe holds liveness and readiness off until start-up succeeds, with its own budget of threshold times period. Fast starts hand over immediately, so you do not slow down deadlock detection for everyone.

"Your database proxy includes the database in readiness. The database fails over. What happens behind kube-proxy versus behind an ALB?"

Behind kube-proxy, every pod goes unready and the Service has zero endpoints. Callers get connection errors immediately, which is honest and lets their breakers trip fast. Behind an ALB, once every target is unhealthy the balancer fails open and routes to all of them anyway, so callers get slow errors from the proxy instead. Same check, different behaviour. You should choose deliberately, and probably make the proxy return fast 503s itself during the failover.

"How do you health-check a Kafka consumer that has no HTTP traffic?"

Liveness is a heartbeat: the poll loop updated a timestamp in the last N seconds. That catches a deadlock or an endless stall on one message, which a restart can fix. Readiness barely applies, because nothing routes to it. Consumer lag and the age of the oldest unprocessed record are group-level signals. They feed alerts and lag-based scaling centrally, never a per-pod restart. Restarting consumers because lag is high causes rebalances and makes lag worse.

"An engineer proposes probing every 1 second for faster failover. What do you ask?"

What failover time they actually need, and what it costs. Detection is period times threshold, so going from 10 s to 1 s cuts 30 seconds to about 3, but raises probe load tenfold and makes every short GC pause a candidate for a false verdict. Passive outlier detection usually gives faster, more accurate removal for real failures, because it reacts to real errors within a few requests. Keep active probes moderate and let traffic itself be the fast signal.

"Where should the 'is checkout working end to end?' check live, and what does it trigger?"

In central monitoring, as a synthetic transaction run every minute or so from a few locations. It triggers alerts and pages, never routing or restarts, because a failure there says nothing about which instance to act on. Link it to distributed tracing so a failed synthetic run comes with a trace that shows where it broke.
