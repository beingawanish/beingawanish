Deep Dive: Inside the Mechanism

The lesson treats SSE as "one HTTP response that never ends." That is accurate, and it hides most of what goes wrong in production. Under it sit a small text protocol with some sharp edges, a resume protocol that only works if your servers share a log, and a chain of proxies that each have opinions about long responses. This section takes them in that order, using the food-delivery tracking page from the lesson.

The wire format, line by line

An SSE stream is UTF-8 text, split into lines (LF, CR or CRLF all count). A blank line ends an event. Every other line is a field:

  • data: is the payload. Several data: lines in one event are joined with newlines, so multi-line JSON is legal but costs bytes. Most teams send one line of compact JSON.
  • event: names the type. With no name the browser fires message. Named events only reach listeners added with addEventListener("status", …), not onmessage. This catches out almost every team once.
  • id: sets the stream's last event ID. The browser remembers it and sends it back as Last-Event-ID on reconnect. It persists: an event without an id: line leaves the previous value in place.
  • retry: is an integer in milliseconds. It sets how long the browser waits before reconnecting.
  • A line starting with : is a comment. The browser ignores it. That makes it the standard heartbeat.

Two rules finish the parser. An event with no data is not dispatched at all, so a block holding only id: just updates the ID. Unknown field names are ignored, which gives you room to extend the protocol safely.

The browser side has its own rules, and they matter for failure handling:

  • After a network error or a clean end of the response, EventSource reconnects automatically, waiting the retry time.
  • If the server answers with a status other than 200, or with the wrong Content-Type, the browser fails the connection permanently. The readyState goes to CLOSED and nothing reconnects. That includes a 503 from an overloaded load balancer. Your app code must notice the error event with CLOSED state and reopen with its own backoff.
  • A 204 No Content is the documented way for a server to say "stop reconnecting."
  • EventSource cannot set request headers or use POST. Authentication goes through cookies (with withCredentials for cross-origin streams) or a short-lived token in the URL. URLs end up in access logs, so keep such tokens single-use or a few minutes long.

That last limit is why LLM APIs, which need a POST body and an Authorization header, use the SSE format without the EventSource client. Their SDKs open a fetch() request and parse the stream themselves. Do the same when you need headers. Just remember you then own reconnect and Last-Event-ID.

What the server must do on every write

Three headers and one habit. Send Content-Type: text/event-stream, Cache-Control: no-cache, and, behind nginx, X-Accel-Buffering: no. Do not send Content-Length. On HTTP/1.1 the body is then chunked or runs until close; on HTTP/2 it is just an open stream. The habit is to flush after every event. Many frameworks buffer writes until a few KB accumulate. A response compressor does the same unless it flushes per event, which is why turning on gzip for the whole site is a classic way to break SSE.

Last-Event-ID resume needs a shared log

The lesson's replay buffer sounds like a per-server ring of recent events. That design has a hole. When a node dies, its 50,000 clients reconnect through the load balancer and land on other nodes. Those nodes never held their buffers. So the replay buffer has to live outside the SSE nodes, in a store every node can read by ID range.

Redis Streams fits this well. Each order's stream is a key. XADD order:7f3a MAXLEN ~ 200 * status … appends and trims. On reconnect, XRANGE order:7f3a (<last-id> + returns everything after the client's ID. The ( makes the start exclusive. Stream IDs (<ms>-<seq>) are ordered, so they work directly as SSE id: values. Kafka offsets work too when the stream maps to a partition, though per-entity streams with Kafka mean filtering a shared partition.

The subtle part is the order of operations on resume. Suppose the node first reads the replay range and then subscribes for live events. Any event published between those two steps is lost: too late for the read, too early for the subscription. The safe sequence is:

  1. Subscribe to live events for the stream and hold them in a local queue.
  2. Read the replay range after Last-Event-ID from the log.
  3. Send the replayed events, then drain the queued live events, skipping any ID already sent.
  4. Switch to forwarding live events directly.

If Last-Event-ID is older than the oldest entry in the log, send an explicit reset (a named reset event, or close with a 204 and let the app refetch). The client then loads current state from the ordinary API and opens a fresh stream.

Here is a toy version of the protocol with Python's standard library. The server holds events 41 to 44 in its buffer. The client drops after two events, resumes with Last-Event-ID: 42, and finally asks with an ID far too old.

import http.client, http.server, threading

# Replay buffer for one order's stream: event ids 41..44 are still held.
BUFFER = {i: f'{{"order":"7f3a","status":"step{i}"}}' for i in range(41, 45)}

class Stream(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def log_message(self, *args): pass
    def do_GET(self):
        last = int(self.headers.get("Last-Event-ID") or 0)
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Cache-Control", "no-cache")
        self.send_header("X-Accel-Buffering", "no")   # ask nginx not to buffer
        self.end_headers()                             # no Content-Length: open-ended body
        out = ["retry: 3000\n\n", ": heartbeat\n\n"]
        if last and last + 1 < min(BUFFER):            # gap older than the buffer
            out.append("event: reset\ndata: {}\n\n")
        else:
            out += [f"id: {i}\nevent: status\ndata: {d}\n\n"
                    for i, d in BUFFER.items() if i > last]
        for chunk in out:                              # a real server would keep the
            self.wfile.write(chunk.encode())           # response open; this one ends
            self.wfile.flush()
        self.close_connection = True

def listen(last_id, drop_after=None):
    conn = http.client.HTTPConnection("127.0.0.1", server.server_port)
    headers = {"Accept": "text/event-stream"}
    if last_id:
        headers["Last-Event-ID"] = last_id
    conn.request("GET", "/orders/7f3a/stream", headers=headers)
    resp = conn.getresponse()
    print(f"GET Last-Event-ID={last_id or '-'} -> {resp.status}")
    fields, seen, count = {}, last_id, 0
    for raw in resp:
        line = raw.decode().rstrip("\n")
        print("  |", line)
        if line == "":                                 # blank line = dispatch
            if "data" in fields:
                seen, count = fields.get("id", seen), count + 1
                print(f"  => {fields.get('event', 'message')} (last id {seen})")
                if count == drop_after:
                    break                              # simulate a dropped connection
            fields = {}
        elif not line.startswith(":"):                 # ':' lines are comments
            name, _, value = line.partition(":")
            fields[name] = value.removeprefix(" ")
    conn.close()
    return seen

server = http.server.ThreadingHTTPServer(("127.0.0.1", 0), Stream)
threading.Thread(target=server.serve_forever, daemon=True).start()
last = listen(None, drop_after=2)   # receives 41, 42, then the connection drops
listen(last)                        # resumes: server replays 43, 44
listen("12")                        # far too old: server sends a reset event
server.shutdown()

Notice the last line. The reset event carried no id:, so the client's last ID is still 12. That is the persistence rule from the wire format. A real client must clear its stored ID when it handles a reset. Otherwise its next reconnect asks for the same impossible range and loops.

Fan-out: pub/sub behind the SSE nodes

SSE nodes should hold connections and nothing else. Business services never talk to them directly. They publish to a bus, and each SSE node subscribes to what its connected clients need. The bus can be Redis pub/sub, NATS, or Kafka with a consumer per node. The main design choice is topic granularity:

  • Per-entity topics (order.7f3a). A node subscribes to exactly the orders its clients watch and unsubscribes when the last viewer leaves. No wasted traffic, but subscription churn tracks connection churn. A reconnect storm becomes a subscribe storm on the bus.
  • Sharded topics (orders.shard-17 of 64). Every node subscribes to all shards and filters locally against a map of order_id → connections. Subscriptions are static. The cost is that every node receives every event. That is fine at 1,000 events per second and wasteful at 1,000,000.
  • Broadcast topics (one live score, a million viewers). The bus sends one message per node. The expensive fan-out happens inside each node, as one write per connection.

Redis pub/sub is fire-and-forget: a node that is disconnected for a second misses those messages. That is acceptable only because the replay log above catches them on the client's next resume. Treat the bus as the fast path and the log as the truth, the same "speed from push, truth from the log" split the webhooks lesson makes.

Proxies, buffering and timeouts

Every hop between the server and the browser can break a stream in one of two ways. It can buffer, holding output until a size threshold or the end of the response. Or it can time out, closing a connection that has been quiet too long. The defaults are usually wrong for SSE. nginx's proxy_read_timeout defaults to 60 seconds. AWS Application Load Balancer's idle timeout also defaults to 60 seconds. CDNs have their own limits, and they vary by vendor and plan.

A typical nginx location for the stream route:

location /orders/ {
    proxy_pass http://sse_nodes;
    proxy_http_version 1.1;
    proxy_set_header Connection "";   # keep upstream connection open, no "close"
    proxy_buffering off;              # or send X-Accel-Buffering: no per response
    proxy_cache off;
    gzip off;                         # compression buffers unless it flushes per event
    proxy_read_timeout 1h;            # longer than any expected quiet period
}

upstream sse_nodes {
    least_conn;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    keepalive 64;
}

The heartbeat closes the gap the config cannot. Send a comment line every 15 seconds and every idle timer on the path keeps resetting, including ones you do not control, such as a mobile carrier's NAT. Pick the interval from the shortest timeout you know of, then halve it. At 15 seconds and 200,000 connections, heartbeats cost about 13,300 tiny writes a second across the fleet. That is real but small, and it buys you streams that survive quiet periods.

Buffering you cannot configure, such as a corporate proxy or an antivirus product inspecting HTTPS, needs detection instead. Put a server timestamp in each event and have the client report lag. If lag arrives in 30-second steps, fall back to long polling for that client.

HTTP/1.1 connection limits vs HTTP/2

Over HTTP/1.1, browsers cap concurrent connections per host, at about 6 in Chrome and Firefox. The cap is shared across all tabs. One SSE stream per tab means the seventh tab's stream never opens. Worse, the six open streams also take every slot for ordinary API calls to that host, so the whole app freezes, not just the live view. Chrome and Firefox have treated this as working as intended, so it will not be fixed for you.

HTTP/2 fixes it by multiplexing many streams over one TCP connection. Each SSE stream becomes one HTTP/2 stream. The limit becomes SETTINGS_MAX_CONCURRENT_STREAMS, which servers commonly set at 100 or more (nginx's http2_max_concurrent_streams defaults to 128). Two caveats:

  • HTTP/2 to the browser does not mean HTTP/2 to the backend. A load balancer that terminates HTTP/2 often speaks HTTP/1.1 upstream. That is fine, but each client stream is still one backend connection. Your SSE nodes count the same number of sockets either way.
  • TCP head-of-line blocking. All streams on one HTTP/2 connection share one TCP connection. A lost packet stalls every stream on it until retransmission. On lossy mobile networks that adds latency spikes. HTTP/3 over QUIC removes this, because loss on one stream does not block the others.

If you must support HTTP/1.1 clients, open one stream per browser, not per tab. One tab owns the stream, chosen by leader election over BroadcastChannel or held in a SharedWorker, and relays events to the others.

Deep Dive: Sizing and the Numbers

Memory per connection

The lesson says "a few tens of kilobytes" per connection. Here is where that comes from, for an idle stream on a Go or Node-style async server. These are assumptions to check with a load test, not constants:

ComponentIdle cost (rough)Notes
Kernel socket state and buffers4–20 KBLinux sizes socket buffers dynamically; idle sockets sit near the low end of tcp_rmem/tcp_wmem. Grows when a client reads slowly.
TLS session state0 or ~10–40 KBZero if TLS ends at the load balancer. Otherwise depends heavily on the library and whether idle read/write buffers are released.
Runtime per connection4–16 KBExample: a Go goroutine stack (starts at 2 KB, grows) plus HTTP read/write buffers.
Application state1–4 KBUser ID, subscribed topics, last ID sent, a bounded send queue.

Take 40 KB all-in with TLS on the node. Then 50,000 connections use about 2 GB, and the lesson's 200,000 viewers need about 8 GB across the fleet. Memory is not the binding limit here. The binding limits are usually these three:

  • File descriptors. Each connection is one. A default soft ulimit -n of 1,024 stops a node at about a thousand streams. Raise it (and fs.nr_open if needed) to well above your target.
  • Ephemeral ports between proxy and node. Each proxied stream uses a source port on the proxy. Linux's default ip_local_port_range is 32768–60999, which is 28,232 ports per (proxy IP, node IP, node port) combination. A single proxy talking to a node on one port caps that node at about 28,000 streams, well below the 50,000 you planned. Fix it with more proxy source IPs, several listening ports per node, or a wider port range.
  • Write fan-out CPU, covered next.

Fan-out cost

For the tracking page: 200,000 active orders, about 12 status events each over 40 minutes. That is 200,000 × 12 / 2,400 s = 1,000 events per second in total. With sharded topics and 4 nodes, the bus carries 4,000 messages a second. Each node writes about 250 events a second to clients. Trivial.

Broadcast is different. Say the bookstore streams a live "flash sale stock remaining" counter to 200,000 viewers, updating twice a second. Each update becomes 50,000 writes per node. Assume about 5 µs of CPU per small write, including the syscall and TLS encryption. That is 50,000 × 5 µs = 0.25 CPU-seconds per update per node, or half a core at 2 updates a second. Ten updates a second needs 2.5 cores just to write. Two cheap fixes: coalesce, sending the latest value at most every 500 ms per connection, and batch several pending events into one write.

Reconnect storm math

A node holding 50,000 streams crashes. Every client waits its retry time, say a fixed 3 seconds, and reconnects. Those 50,000 reconnects arrive within roughly a second at the remaining three nodes. Each costs a TLS handshake, roughly 1 ms of CPU for a full handshake (less with ECDSA certificates and session resumption), plus an auth check and a replay-log read. That is about 50 CPU-seconds of handshakes landing in one second, on nodes that were already busy. Add 50,000 XRANGE calls hitting Redis at once.

Now spread it. Have the server send each connection a random retry between 1 and 30 seconds when the stream opens. It has to be sent in advance, because a crashed node cannot send anything. The arrival rate drops to about 50,000 / 30 ≈ 1,700 per second, or under 600 per surviving node. That is an ordinary load. The price is that some users wait up to 30 seconds after a crash. Replay hides the missed events, so they see a short pause, not a gap.

Replay log size

Size the log by time, not by count. The window must cover the longest disconnect you want to resume from: a deploy of one node plus the worst-case jittered retry, say 5 minutes. At 1,000 events a second, 5 minutes is 300,000 entries. At about 300 bytes each in Redis, including overhead, that is around 90 MB. Per-order streams trimmed with MAXLEN ~ 50 also bound it, and an order with only 12 events never comes near the cap. This is cheap enough that the replay window is rarely worth skimping on.

Deep Dive: Failure Modes in Production

1. Events arrive in bursts

Symptom: some users see 30 to 60 seconds of updates arrive at once. Mechanism: something on the path buffers the response: a proxy with buffering on, a compressor that does not flush, a framework write buffer, or a corporate inspection proxy. Detect: put a server timestamp in each event and have clients report receive lag. Chart lag by network or region; buffering shows as a sawtooth, not noise. Fix: proxy_buffering off or X-Accel-Buffering: no, no compression on the route (or flush per event), and explicit flushes in the handler. For networks you cannot change, detect the sawtooth and switch that client to long polling.

2. Streams die at exactly 60 seconds

Symptom: a burst of reconnects every minute, and quiet orders show "connection lost" banners. Mechanism: an idle timeout on a proxy or load balancer, often a 60-second default, closes streams with no traffic. Detect: a histogram of stream duration. A sharp spike at 60.0 seconds is a timer, not a network. Fix: heartbeat comments every 15 seconds, and raise the idle timeouts you control above the heartbeat interval with margin.

3. The seventh tab freezes the whole app

Symptom: users with many tabs report that the site "hangs" and even the buttons stop working. Mechanism: HTTP/1.1's per-host limit of about 6 connections, shared across tabs. Open streams take every slot, so ordinary API requests queue behind them forever. Detect: the negotiated protocol in your edge access logs (look for HTTP/1.1 on stream routes) and client-side timing for requests stuck in "stalled." Fix: HTTP/2 at the edge, and one stream per browser shared across tabs for clients that still arrive on HTTP/1.1.

4. Events go missing after a reconnect

Symptom: an order sits at "preparing" though the driver has already picked it up. A refresh fixes it. Mechanism: one of two races. Either the replay buffer was in memory on a node the client did not reconnect to, or the node read the replay range before subscribing to live events, losing whatever was published in between. Detect: give events a per-stream sequence number and have clients report gaps (received 44 after 42). Without this you will only hear about it from support. Fix: a shared replay log, subscribe-then-replay with ID dedupe, and a client that refetches state when it sees a gap.

5. A deploy turns into a reconnect storm, then an outage

Symptom: after a rolling deploy, CPU on the remaining nodes spikes, the load balancer starts returning 503s, and streams stay dead after the spike passes. Mechanism: each restarted node dropped 50,000 streams at once with a fixed retry. The surge overloaded the survivors. Then the 503s, being non-200 responses, made EventSource close permanently. Users who hit a 503 never reconnect until they reload the page. Detect: new streams per second, TLS handshakes per second, and the count of clients in CLOSED state (report it from the client). Fix: jittered retry values set at stream open. Drain in waves: before shutdown, close streams in batches over a minute or two, rather than all at once. Wrap EventSource so a permanent failure reopens with backoff. Shed load at the edge with a rate limit on new streams rather than failing streams already open.

6. New nodes sit idle while old ones run out of memory

Symptom: autoscaling adds two nodes during the Friday peak. They stay nearly empty, and the original nodes keep climbing toward their limits. Mechanism: long-lived connections never rebalance. Least-connections routing only affects new streams, and existing ones may stay open for hours. Detect: connections per node, and the ratio of busiest to least busy. Fix: cap stream lifetime: close each stream after a randomised 20 to 40 minutes. The client resumes with Last-Event-ID and lands wherever the balancer sends it. The cost is a steady, small reconnect rate, which is far easier to plan for than a storm.

7. One slow client grows a node's memory

Symptom: node memory climbs during broadcast-heavy periods, without an increase in connection count. Mechanism: clients on poor mobile networks read slowly. Their kernel send buffers fill, then the server's per-connection queue grows without limit. Detect: per-connection queued bytes, with a histogram and the top 10 offenders, next to process RSS. Fix: a bounded queue per connection. When it is full, either drop to the latest state (for counters and positions) or close the stream so the client resumes from its last ID. This is backpressure with a delivery guarantee behind it: closing is safe precisely because resume exists.

The row that matters most in reviews is the replay store. Teams start with an in-memory buffer because it works in a single-node demo, and it keeps working until the first crash. Put the log outside the nodes from day one; with Redis Streams it costs a few lines.

The TLS row is a quieter win. Terminating at the balancer means the expensive handshakes of a reconnect storm land on a tier built for them, and SSE nodes shrink to sockets plus application state.

Deep Dive: Design-Review Checklist

  1. Where does the replay buffer live, and does a client that reconnects to a different node still resume correctly?
  2. On resume, does the node subscribe before reading the replay range, and dedupe by ID across the two?
  3. What exactly happens when Last-Event-ID is older than the buffer? Show the reset event and the client's refetch path, including clearing its stored ID.
  4. List every hop between server and browser. For each, what are its buffering behaviour and idle timeout, and is the heartbeat interval below the shortest one?
  5. Is compression disabled on the stream route, or proven to flush per event?
  6. Do clients reach the edge over HTTP/2? What happens for an HTTP/1.1 user with eight tabs open?
  7. What is the planned connections-per-node figure, and have file descriptor limits and proxy-to-node ephemeral ports been checked against it?
  8. What is the reconnect rate when one node, or all nodes, restart? Are retry values jittered and sent at stream open?
  9. Does the client wrapper reopen the stream after a non-200 response closes EventSource for good?
  10. How are connections rebalanced after scale-out? Is there a maximum stream lifetime?
  11. Is every connection's send queue bounded, and what happens to a slow client when it fills?
  12. How is authorisation re-checked on a stream that stays open for hours, and are events filtered per user before they reach the socket?

Deep Dive: Senior Interview Follow-ups

"The replay buffer is in memory on each node. What breaks?"

Resume after a node failure. The dead node's clients reconnect through the load balancer to other nodes, which never saw their events. Sticky sessions do not help, because the node they were stuck to is gone. The buffer must live in a shared log that any node can read by ID range, such as Redis Streams or a Kafka topic.

"Walk me through a resume without losing an event."

Subscribe to live events first and queue them locally. Then read the log from Last-Event-ID exclusive. Send the replayed events, then the queued live ones, skipping any ID already sent. Then forward live. Reading first and subscribing second loses whatever was published in between. If the ID is older than the log, send a reset and let the client refetch state.

"Why do you send a random retry value with every new stream?"

Because the reconnect delay must be set before the failure. A crashed node cannot tell 50,000 clients to back off. With a fixed 3-second retry, they all return within about a second. With a random 1 to 30 seconds, the surge drops to under 2,000 per second, which the survivors can absorb. EventSource does not reliably add its own backoff or jitter, so the server has to.

"Your load balancer returns 503 during overload. What does that do to SSE clients?"

It ends them for good. A non-200 response makes EventSource fail the connection and stop reconnecting. Only a reload brings the user back, so overload turns into a lasting outage for those users. Wrap EventSource to reopen with backoff after a permanent close. At the edge, prefer rate-limiting new streams, or holding them briefly, over error responses.

"Does HTTP/2 remove the need to think about connection counts?"

For the browser, mostly: many streams share one connection, so the 6-per-host limit stops mattering. For your servers, no. A balancer that terminates HTTP/2 usually opens one backend connection per stream, so nodes still hold one socket per viewer. And all streams on one HTTP/2 connection share TCP, so packet loss stalls them together. HTTP/3 is what removes that.

"You autoscaled from 4 to 6 nodes but the old 4 are still overloaded. Why, and what do you change?"

Long-lived streams do not move. Least-connections only routes new streams, and existing ones can stay open for hours. Add a maximum stream lifetime with jitter (say 20 to 40 minutes). Each close is cheap because the client resumes with Last-Event-ID. Over one lifetime period the fleet rebalances on its own. During a sudden scale-out you can also close a slice of streams on the busiest nodes deliberately.

"Where does the CPU go on a node with 50,000 idle streams? And with a broadcast?"

Idle, almost nowhere: heartbeats are one tiny write per connection every 15 seconds, about 3,300 writes a second per node. A broadcast is 50,000 writes for one event, roughly a quarter of a CPU-second at 5 µs a write. So the expensive case is broadcast frequency times audience per node. Coalesce updates per connection and batch writes rather than adding nodes.

"Why not put the access token in the SSE URL and be done?"

URLs land in access logs, proxy logs and browser history, so a long-lived token there leaks. If you must use a URL token because EventSource cannot send headers, make it single-use or valid for a minute, and exchange it at connect time. Better options are a cookie scoped to the stream route, or a fetch()-based client that can send an Authorization header. Either way, re-check authorisation during the stream, not only at connect.
