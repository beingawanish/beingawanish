Deep Dive: Inside the Mechanism

The sidecar deep dive followed one request through two proxies. This one goes up a level, to the control plane. It covers how it builds each proxy's configuration, how that configuration travels over xDS, how identities are minted and rotated, and how authorization and outlier detection actually decide things. Istio and Envoy are used for concrete names, because their knobs are well documented. Other meshes make the same decisions under different names.

From cluster state to per-proxy config

The control plane is a translator with a cache. In Kubernetes it runs a set of watches on the API server, which are long-lived streams of changes:

  • Services and EndpointSlices tell it which services exist and which pod IPs currently back them, and whether each is ready.
  • Pods and service accounts tell it which identity each workload runs as.
  • Mesh resources (in Istio: VirtualService, DestinationRule, AuthorizationPolicy, PeerAuthentication, Sidecar) carry the declared policy.

From these it builds one internal model of the mesh. For each connected proxy, it then computes the slice of that model the proxy needs. A checkout sidecar needs listeners for its own ports, routes for the services it calls, endpoint lists for those services, and its own certificate. It does not need the routes for the warehouse's internal batch services.

The key property is that the control plane is not on the request path. It never sees a request. It only changes what proxies believe. That is why the lesson can say the data plane fails static: the proxies already hold everything a request needs.

xDS: five resource types on one stream

Envoy's configuration API is a family of discovery services, collectively called xDS. Each one carries one resource type:

ServiceCarriesChanges when
LDS (listeners)Ports the proxy listens on, and their filter chainsPorts or protocol settings change; rare
RDS (routes)HTTP routing: hosts, paths, weights, retries, timeoutsSomeone edits a traffic policy
CDS (clusters)Upstream service groups, with load balancing, circuit breakers and outlier detectionServices are added or their policy changes
EDS (endpoints)The current IPs in each cluster, with health and localityConstantly: every deploy, scale event and failing pod
SDS (secrets)Certificates and trust bundlesOn every certificate rotation

A proxy usually opens one gRPC stream for all of them, the Aggregated Discovery Service (ADS). One stream lets the control plane control the order of updates, and order matters. Picture a route pointing at a cluster the proxy has not heard of yet. Requests matching that route fail until the cluster arrives. The safe order is "make before break": send new clusters and their endpoints first, then the routes that use them. Remove old clusters only after no route references them.

Each response carries a version_info and a nonce. The proxy replies with an ACK (it applied the update) or a NACK (it rejected it, with an error message). A NACKed update is simply not applied. The proxy keeps running on its last accepted config. That is fail-static at the level of a single update, and it is why a malformed config does less damage than a valid but wrong one.

There are two flavours of protocol. In state of the world, every update for a type resends the full set of resources of that type. In incremental (delta) xDS, only the resources that changed are sent. With 2,000 endpoints in a cluster and one pod restarting, the difference is resending 2,000 entries versus 1. At scale, incremental xDS for endpoints is what keeps pushes cheap.

Debouncing: batching changes before pushing

A rolling deploy of 40 pods produces dozens of endpoint changes within seconds. Pushing after each one would recompute and resend config hundreds of times. Control planes therefore debounce. They wait a short quiet period after a change, typically on the order of 100 ms, and push everything that changed in that window at once, with a ceiling so a constant trickle of changes cannot delay pushes forever. Istio exposes both values as settings.

That knob trades freshness against load. A longer debounce means fewer, larger pushes and less control-plane CPU. But it also means a terminated pod stays in callers' endpoint lists slightly longer. During that window, readiness-based draining on the pod being removed carries the weight. This is the reason graceful shutdown still matters inside a mesh.

Identity: how a pod gets its certificate

The mesh's identity system is a small PKI that runs automatically. In Istio, the flow for each pod is:

  1. An agent inside the sidecar container generates a private key locally. The key never leaves the pod.
  2. The agent sends a certificate signing request (CSR) to the control plane's CA. It authenticates with the pod's Kubernetes service-account token.
  3. The CA verifies the token with the API server, and issues a certificate whose subject alternative name is a SPIFFE ID, such as spiffe://cluster.local/ns/shop/sa/checkout.
  4. The agent hands the key, the certificate and the trust bundle to Envoy over SDS on a local socket.
  5. Before the certificate expires, the agent repeats the process and Envoy swaps the new one in without dropping connections.

Identity is tied to the service account, not the pod or IP. Every checkout replica shares one identity. That is what makes "only checkout may call payments" a short rule. It also means service accounts must be per service. If ten services share the default account, they share one identity, and authorization cannot tell them apart.

Lifetimes are a policy choice. The lesson uses hourly rotation. Istio's default workload certificate lifetime is 24 hours, with renewal well before expiry. Shorter lifetimes limit how long a stolen key works. They also shorten how long the mesh can survive without its CA, which the sizing section works out.

Above workload certificates sits the root of trust. Rotating a workload certificate is routine. Rotating the root is not, because every proxy must trust the new root before any workload presents a certificate signed by it. The safe sequence: distribute a trust bundle containing both old and new roots, wait until every proxy has it, switch issuance to the new root, wait for all workload certificates to roll over, then remove the old root. In practice, many organisations plug the mesh CA into their existing PKI as an intermediate, so the root's lifecycle is someone else's well-rehearsed job.

Authorization: how a decision is made

The lesson's rule ("only checkout and refunds may call payments") looks like this in Istio:

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments-callers
  namespace: payments
spec:
  selector:
    matchLabels:
      app: payments
  action: ALLOW
  rules:
  - from:
    - source:
        principals:
        - cluster.local/ns/shop/sa/checkout
        - cluster.local/ns/shop/sa/refunds
    to:
    - operation:
        methods: ["POST"]
        paths: ["/v1/charges", "/v1/refunds"]

The payments sidecar evaluates it on every inbound request, after mTLS has verified the caller's certificate. The evaluation order is worth knowing exactly, because it explains several outages. In Istio, CUSTOM policies are checked first, then DENY policies, then ALLOW policies. If any DENY matches, the request is denied. If at least one ALLOW policy applies to the workload, and none of them match, the request is denied. Adding the first ALLOW policy to a workload therefore turns it from "allow everything" into "allow only this". A policy that is meant to add one caller can, by existing, cut off every other caller.

Mutual TLS itself has a migration mode. PERMISSIVE accepts both plaintext and mTLS on the same port, so pods inside and outside the mesh can both connect. STRICT accepts only mTLS. Every rollout passes through permissive mode first. Moving to strict is the step that breaks things, as failure mode 4 shows.

Outlier detection and panic mode

The lesson describes outlier detection as the mesh's circuit breaker. Envoy's defaults show how it behaves. An endpoint is ejected after 5 consecutive 5xx responses (consecutive_5xx). Detection runs every 10 seconds (interval). The first ejection lasts 30 seconds (base_ejection_time), and it grows each time the same host is ejected again. At most 10% of a cluster's hosts can be ejected at once (max_ejection_percent).

That 10% cap exists for a reason. Outlier detection is built to remove a few bad hosts, not to react to a whole service failing. A related safety valve, the panic threshold, decides what happens when too many hosts look unhealthy. Envoy's default is 50%. Once fewer than half the hosts in a cluster are healthy, Envoy stops trusting its health data and spreads traffic across all hosts, healthy or not. The reasoning is that sending everything to the few remaining hosts would overload them too. Both behaviours surprise people in incidents, and failure mode 5 shows one.

Deep Dive: Sizing and the Numbers

Push volume and convergence

Take the bookstore at 440 proxies and imagine growth to 5,000 proxies across 300 services. Assume each proxy's full config is around 200 KB when unscoped (every service visible) and around 20 KB when scoped to the dozen services it actually calls. Real sizes vary a lot with features and versions, so treat these as placeholders and measure.

Full push, unscoped:  5,000 × 200 KB = 1 GB of config to serialise and send
Full push, scoped:    5,000 ×  20 KB = 100 MB

A full push happens when global policy changes, or when the control plane restarts and every proxy reconnects. An endpoint change, with incremental xDS and scoping, goes only to proxies that call that service and carries only the changed endpoints. That is kilobytes, not gigabytes.

Track convergence time, which means the time from a change in the cluster to every affected proxy having ACKed it. Istio exports it as pilot_proxy_convergence_time. For a deploy, the budget is simple. Convergence plus the debounce window must stay well inside the terminating pod's drain period. If pods drain for 15 seconds and convergence is at 20 seconds during big rollouts, callers will send traffic to pods that already shut down.

CA load, and how long fail-static really lasts

Certificate issuance is cheap in steady state. At 5,000 pods with 24-hour certificates, that is 5,000 / 86,400 ≈ 0.06 signatures per second. With 1-hour certificates, it is 5,000 / 3,600 ≈ 1.4 per second. Bursts come from deploys and node failures. A 500-pod rollout over 2 minutes asks for about 4 certificates per second on top. All of this is easily handled by one CA replica. The burst that hurts is a control-plane restart, when every agent may try to renew at once.

The more important number is how long the mesh survives with the control plane down. Existing traffic flows on cached config, but certificates keep ageing. Suppose renewal happens when a certificate reaches 80% of its lifetime. The pod closest to renewal at the moment of the outage has 20% of its lifetime left:

Certificate lifetimeTime left on the most urgent pod (20%)What that means for control-plane recovery
24 hours~4.8 hoursA bad night, but time to restore from backup or rebuild
1 hour~12 minutesThe control plane is effectively on the request path
15 minutes~3 minutesAny control-plane outage becomes a mesh-wide mTLS outage

So the security goal (short certificates) and the availability goal (long fail-static window) pull against each other. Pick the lifetime from the control plane's recovery time objective, not from a security slogan. That holds for the lesson's hourly rotation too: an hourly scheme needs a control plane you can restore in minutes, which means multiple replicas across zones, tested failover, and a CA key that survives losing them.

Telemetry cardinality

"Observability with no extra work" is free for application teams. It is not free for whoever runs the metrics system. Standard mesh request metrics are labelled by source workload, destination workload, response code, reporter (source or destination side) and more. Estimate the series for one latency histogram:

30 services × 5 callees each      = 150 service pairs
× 6 distinct response codes        = 900
× 2 reporters                      = 1,800
× ~20 histogram buckets            = 36,000 series

That is manageable. Now add a per-pod label, which the default setup often includes for each scraped proxy. With 40 pods per service it multiplies to around 1.4 million series, and a single Prometheus starts to struggle. The usual remedies are to aggregate per workload before storage (recording rules or federation), drop pod-level labels from request metrics, and trim histogram buckets. Decide this during design. The default is often fine at 11 services and painful at 300.

The team cost, in people

The lesson says the main cost is organisational. Put a rough number on it. A mesh at this scale typically needs on-call coverage for the control plane, upgrades every few months (each one a fleet-wide sidecar restart), policy review, and support for application teams. That adds up to two to four engineers' sustained attention. It is also why the capstone defers the full mesh for a team of two. The infrastructure bill is visible on an invoice. The people bill shows up as a platform team that never gets to its roadmap.

Deep Dive: Failure Modes in Production

1. A new ALLOW policy cuts off every other caller

Symptom. A team adds a policy letting a new reporting service read from inventory. Minutes later, checkout's inventory calls fail with 403 RBAC: access denied.

Mechanism. Inventory had no authorization policies, so it allowed everything. The first ALLOW policy changed its default to deny-unless-matched. Only the reporting service matched. Checkout, which had always worked without a rule, was now denied.

Detect. Denied-request counters on the receiving sidecar, broken out by source principal. A jump in 403s right after a policy apply is unambiguous. Envoy's RBAC filter keeps its own allowed and denied stats.

Fix. Write the full caller list for a service in one policy, not one policy per caller. Roll policies out in dry-run mode first: Istio supports an annotation that evaluates and logs a policy without enforcing it. Treat policy as code, with review and a staged rollout, exactly as the lesson's retry incident concludes.

2. Slow convergence during a large rollout

Symptom. During a big deploy, callers see 503s with "no healthy upstream" or connection failures for 20 to 40 seconds. Small deploys are fine.

Mechanism. Hundreds of pods change at once. The control plane is CPU-bound computing and sending config to thousands of proxies, many of which get unscoped, full-size updates. Endpoint updates lag. Callers keep sending to pods that already terminated, and they learn about the new pods late.

Detect. Convergence time and push queue time on the control plane. Look also at its CPU during deploys, and at the share of 503s with UF or UH flags at callers, correlated with deploy events.

Fix. Scope config so most proxies are not affected by a given change. Use incremental xDS for endpoints. Add control-plane replicas so that proxy connections spread across them. And make terminating pods drain for longer than the worst observed convergence time, so stale endpoints still answer during the gap.

3. The root certificate expires

Symptom. On an otherwise quiet day, every mTLS connection in the mesh starts failing with certificate verification errors at once.

Mechanism. The mesh was installed with a self-signed root generated at install time. Workload certificates rotated perfectly for years, but nobody owned the root. When it expired, every certificate chaining to it became invalid at the same moment. Early mesh releases that generated short-lived roots made this a real, recurring incident across the industry.

Detect. An alert on the expiry date of every root and intermediate in the trust bundle, months in advance. Workload-certificate expiry alerts do not catch this.

Fix. Use an intermediate CA issued from the organisation's managed PKI, with a documented rotation runbook. Rehearse a root rotation with overlapping trust bundles in staging before you need it in production.

4. Switching to STRICT mTLS breaks callers outside the mesh

Symptom. After a namespace moves from PERMISSIVE to STRICT, a nightly batch job and the metrics scraper start failing. Everything in the mesh works.

Mechanism. Those callers have no sidecar, so they speak plaintext. Permissive mode had been accepting them quietly. Strict mode rejects them.

Detect. Before switching, look at the security-policy label on inbound connection metrics (Istio reports whether each connection used mutual TLS or none). Every source still sending plaintext is a client that strict mode will break.

Fix. Switch to strict only when plaintext inbound traffic has been at zero for a full business cycle, long enough to cover weekly and monthly jobs. Give out-of-mesh callers a path in, such as an ingress gateway or their own sidecar, or exempt specific ports deliberately and in writing.

5. Outlier detection plus panic mode spreads a failure

Symptom. A bad Inventory release fails on 60% of pods. The errors seen by checkout do not drop to 0% as expected. They stay around 50%, even though 40% of pods are healthy.

Mechanism. Outlier detection could eject at most 10% of hosts. The failing pods' readiness checks still passed, because the bug was in one endpoint and the health check never touched it. And because fewer than 50% of hosts looked healthy to some proxies during the churn, panic mode kicked in. Traffic spread evenly across every host, broken ones included.

Detect. Ejection counts and the "panic" counters per cluster on caller proxies. Look at error rate per destination pod: if errors cluster on specific pods while traffic is evenly spread, the safety valves are not removing them.

Fix. This is a release problem first: a canary would have caught a 60% failure on 5% of traffic. On the mesh side, raise max_ejection_percent for services with many replicas, and make readiness checks exercise the critical path. Know that panic mode exists, so nobody spends an incident wondering why the healthy pods are not getting all the traffic.

6. Version skew during a mesh upgrade

Symptom. After a control-plane upgrade, a new routing feature works for some services and not others. Control-plane logs show config rejections.

Mechanism. The new control plane sends config fields that older sidecars do not understand. Those proxies NACK the update and keep their old config, which is fail-static doing its job. But they stay stuck on stale routes until their pods restart with the new proxy version.

Detect. The control plane's xDS reject counter (pilot_total_xds_rejects in Istio), and an inventory of proxy versions across the fleet.

Fix. Upgrade with revisions. Run the new control plane alongside the old one, move namespaces to it gradually, and restart their pods to pick up the matching proxy. Stay inside the mesh's supported version-skew window, and do not use new features until the fleet has rolled.

7. The mesh takes down the metrics system

Symptom. A week after the mesh reaches the last 100 services, Prometheus runs out of memory and dashboards go blank in the middle of an unrelated incident.

Mechanism. The series math from the sizing section. Per-pod labels on per-service-pair histograms grow as services × callees × pods × buckets. Each service added to the mesh adds series to everything it calls.

Detect. Active series count and ingestion rate in the metrics system, tracked as a capacity metric. Also the top series by label, to see which label is exploding.

Fix. Aggregate to workload level before storage, drop pod labels from request metrics, reduce buckets, and set per-job series limits so one source cannot take down the whole system.

Deep Dive: Design Variations and How to Choose

The choice of product matters less than five decisions that every mesh design has to make.

DecisionOption AOption BChoose B when
Data plane shapeSidecar per podPer-node L4 proxy plus L7 proxies only where neededMost services need only mTLS and identity, and per-pod cost matters
Feature breadthBroad (many policy types, many knobs)Narrow (mTLS, metrics, retries, little else)The platform team is small and the goal is identity plus observability
Certificate authorityBuilt-in, self-signed rootIntermediate from the organisation's PKIAlmost always in production; A is for labs
Multi-clusterOne control plane per cluster, shared root of trustOne control plane managing several clustersClusters are tightly coupled and the team can accept a wider blast radius
Policy locationMesh enforces coarse service-to-service rulesMesh also enforces fine-grained, per-route, per-user rulesRarely; user-level authorization usually belongs in the service

How to choose

  • Start narrow. The lesson says to adopt for one measurable goal. In practice that is usually workload identity with mTLS, plus the standard golden-signal metrics. Every policy type you turn on is one more thing that can push a bad global change.
  • Keep user authorization out of the mesh. The mesh knows which service is calling. It does not know which customer, or whether this customer may refund this order. That logic stays in the service, as the gateway lesson says for AuthZ.
  • One control plane per cluster is the default. Each cluster's mesh can fail and be upgraded on its own. Cross-cluster calls use a shared root of trust and an east-west gateway. A single control plane for many clusters makes one bad push global across all of them.
  • Sidecar-less modes change the cost curve, not the control plane. They cut per-pod memory and lifecycle problems. They do not remove convergence, CA management, policy governance or telemetry cardinality, which is where most of the operating work is.
  • Retries and timeouts belong to the mesh only after you remove them from the code. Pick one owner per call path, as the sidecar deep dive explains.

Deep Dive: Design-Review Checklist

  1. What is the single measurable goal for phase one, and which features stay off until it is met?
  2. Who owns the control plane on call? How many replicas run, across how many zones, and what is its recovery time objective?
  3. What is the workload certificate lifetime, and is the fail-static window it implies longer than that recovery objective?
  4. Where does the root of trust come from, when does it expire, and has a root rotation been rehearsed?
  5. Does every service have its own service account, so identities are distinct?
  6. Is sidecar configuration scoped per workload? What is convergence time during the largest normal rollout, and is it shorter than pod drain time?
  7. How are policy changes reviewed, dry-run and staged? Can one change reach the whole fleet at once?
  8. For each authorization policy, is the full caller list in one place? What happens to unlisted callers?
  9. Which callers are still plaintext, and what is the plan before switching to strict mTLS?
  10. Are retries owned by exactly one layer, limited to idempotent calls, and capped by a budget?
  11. How many metric series will mesh telemetry add at full adoption, and which labels are dropped or aggregated?
  12. What is the upgrade procedure (revisions, skew window), and how often will the fleet restart for proxy upgrades?

Deep Dive: Senior Interview Follow-ups

"Walk me through what happens between 'a pod is deleted' and 'callers stop sending to it'."

The pod is marked terminating, and its readiness drops. The EndpointSlice controller removes or marks the endpoint, and the control plane's watch sees the change. The control plane debounces for a short window, recomputes EDS for proxies that call that service, and pushes. Each proxy ACKs and stops picking the endpoint. Until then, the terminating pod must keep serving, which is why its drain period has to exceed debounce plus push plus convergence. In-flight connections then finish or are closed by the proxies.

"Your certificates are valid for one hour. The control plane is down. How long do you have?"

Less than the lifetime, because renewal starts before expiry. If agents renew at 80% of lifetime, the pod closest to renewal has about 12 minutes left when the outage begins. After that, its certificate expires, and its mTLS connections start failing. With one-hour certificates the control plane is nearly on the request path, so it needs multi-zone replicas and a restore measured in minutes. With 24-hour certificates the same calculation gives several hours.

"A team added an AuthorizationPolicy for one new caller and broke all the others. Why?"

Because a workload with no ALLOW policies allows everything, and a workload with at least one ALLOW policy allows only what matches. Their policy flipped the default to deny. The fix is to keep each service's complete caller list in one policy, roll out new policies in dry-run first, and alert on denials by source identity.

"What does a NACK do, and why does it matter for safety?"

A NACK is the proxy telling the control plane "I rejected this update", along with the error. The proxy keeps its last accepted config. So malformed or unsupported config fails safe: nothing changes. The dangerous case is config that is valid but wrong, such as a bad retry policy or a deny-all rule. That is accepted everywhere at configuration speed. Safety therefore comes from review and staged rollout of policy, not from the protocol.

"Why does the mesh tie identity to service accounts and not IP addresses?"

IPs are reused constantly as pods come and go, can be spoofed inside a flat network, and say nothing about what code is running. A service account is a stable name for a workload, and the CA only signs certificates for it after verifying the pod's token with the API server. The certificate proves "this is checkout" wherever the pod runs. That is what lets policy be written in terms of services and survive rescheduling and autoscaling.

"Half of Inventory's pods are broken but readiness passes. What does the mesh do?"

Outlier detection ejects hosts that return consecutive 5xx errors, but by default only up to 10% of the cluster. And if too many hosts look unhealthy, Envoy's panic threshold (50% by default) makes it spread traffic across all hosts, because overloading the remaining few would be worse. So the mesh limits the damage but does not fix it. The real fixes are a canary that catches the release at 5% traffic, and readiness checks that cover the critical path.

"Should the mesh enforce that a customer can only see their own orders?"

No. The mesh verifies which workload is calling. Whether customer 42 may read order 8412 depends on the user's token and on domain data that only the orders service has. Put coarse service-to-service rules in the mesh ("only the BFFs may call orders"). Keep per-user and per-object authorization in the service. Doing it in the mesh means copying domain data into policy, and that is the drift problem again.

"How would you upgrade the mesh across 5,000 pods without a big-bang risk?"

Use revisions. Install the new control plane next to the old one, under a revision label. Move one low-risk namespace to the new revision, restart its pods so they get the matching proxy, and watch error rates, convergence and xDS rejects. Then move namespaces in waves. Keep the old revision running until the last namespace has moved, so rollback is just relabelling and restarting. Stay within the supported skew between control plane and proxy versions throughout.
