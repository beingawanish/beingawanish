Deep Dive: Inside the Mechanism

The lesson treats a topic as one stream and a subscription as one team's copy. That is the right mental model. Underneath, the two big families of brokers build it in very different ways, and the difference explains almost every operational surprise you will meet. Kafka is the log-based case. SNS feeding SQS is the copy-per-subscriber case. We will take them in turn.

Kafka: a topic is a set of partitioned logs

A Kafka topic is not one log. It is a fixed number of partitions, and each partition is an ordered, append-only log on disk. Our order.placed topic might have 12 partitions. Each partition is stored as a series of segment files, and Kafka deletes or compacts whole segments, never single records.

Every record in a partition gets an offset, a number that only goes up: 0, 1, 2, and so on. Offsets are per partition. Offset 500 in partition 3 has nothing to do with offset 500 in partition 7. There is no global order across the topic, and Kafka never claims one.

Which partition does a record land in? The producer decides. With a key, the default partitioner hashes the key (murmur2) and takes it modulo the partition count. So every event keyed ord_7f3a lands in the same partition, in the order the producer sent them. That is the whole of Kafka's ordering promise: order per key, because order per partition. Records without a key get spread across partitions, with no ordering relationship at all.

Here is the consequence people miss. The key-to-partition mapping depends on the partition count. Grow the topic from 12 to 24 partitions and most keys move to a new partition. Events for one order can then sit in two partitions at once, and a consumer can read the newer one first. Pick the partition count with headroom on day one, because changing it later breaks per-key ordering during the transition.

Consumer groups, committed offsets and rebalancing

A Kafka subscription is a consumer group, named by group.id. Within a group, each partition is assigned to exactly one member at a time. That single rule produces both halves of the wiring rule. Two different groups each read every partition, which is broadcast. Workers in one group split the partitions, which is competing consumers.

It also sets a ceiling. A group can never use more workers than there are partitions. With 12 partitions, worker 13 sits idle. So the partition count is the maximum parallelism for every subscriber, including ones that do not exist yet.

Progress is a committed offset per group per partition, stored in an internal compacted topic called __consumer_offsets. The broker does not track which individual records you processed. It only knows "group fraud has committed offset 41 on partition 0", which means "everything before 41 is done." When the consumer restarts, it resumes from there. This is cheap (one number per partition, not one ack per message), and it is why a single stuck record blocks everything behind it in that partition.

When the commit happens matters more than any other consumer setting:

  • Commit after processing gives at-least-once. A crash between processing and commit replays the records, so the handler must be idempotent.
  • Commit before processing gives at-most-once. A crash after commit skips records forever.
  • Auto-commit (enable.auto.commit=true, on by default in the Java client) commits on a timer during poll(). If your code hands records to another thread pool and returns, the timer can commit records that have not been processed yet. Turn it off when processing is asynchronous.

Membership is kept alive two ways. A background heartbeat tells the group coordinator the process is alive, and session.timeout.ms bounds how long silence is tolerated. Separately, max.poll.interval.ms (five minutes by default) bounds the time between poll() calls. If your loop takes longer than that to process one batch, the member is considered stuck and is removed.

Any change in membership triggers a rebalance: partitions are reassigned across the members. The classic "eager" protocol revokes every partition from every member, then hands them back out, so the whole group pauses. The cooperative-sticky assignor moves only the partitions that need to move. Static membership (group.instance.id) lets a restarting pod rejoin as itself within the session timeout, so a rolling deploy does not cause one rebalance per pod. Newer Kafka releases add a broker-side group protocol (KIP-848) that does incremental assignment on the server. Whatever version you run, the goal is the same: fewer, smaller rebalances.

Durability: replicas, ISR and acks

Each partition has a replication factor, usually 3. One replica is the leader and takes all writes. The followers fetch from it. The in-sync replica set (ISR) is the leader plus every follower that has caught up within replica.lag.time.max.ms. A follower that falls behind drops out of the ISR. It rejoins once it catches up.

The producer's acks setting chooses when a write counts as done:

  • acks=0: do not wait at all. Fast, and you will lose data without knowing.
  • acks=1: the leader has written it. If the leader dies before a follower copies the record, a new leader is elected without it. The producer was told "success" for a record that no longer exists.
  • acks=all: every member of the current ISR has it. This is the default in modern clients.

Here is the trap. acks=all means "all of the current ISR." If the ISR has shrunk to just the leader, acks=all is no stronger than acks=1. The topic setting min.insync.replicas closes that gap. With replication factor 3 and min.insync.replicas=2, the broker refuses writes (the producer gets NotEnoughReplicas) whenever fewer than two replicas are in sync. You trade availability for durability, which is the right trade for order events.

Two more settings finish the picture. unclean.leader.election.enable=false (the default) stops an out-of-sync replica from becoming leader and silently truncating history. And the idempotent producer (enable.idempotence=true, also on by default in modern clients) tags each batch with a producer ID and sequence number. The broker drops duplicate retries and rejects out-of-order batches. That is what lets you keep up to five in-flight requests per connection without retries reordering a key's events.

Note what Kafka does not do by default: it does not fsync each write before acknowledging. Durability comes from copies on several machines, not from one disk flush. That is a sound design, but only if replicas really are on different machines, racks or zones.

Retention and compaction

A Kafka topic keeps records until a cleanup policy removes them. The two policies answer different questions.

Delete (cleanup.policy=delete) removes whole segments older than retention.ms (seven days by default) or beyond retention.bytes. This suits order.placed: a history of facts, read in order, replayable for 30 days if you set it so.

Compact (cleanup.policy=compact) keeps at least the latest record for each key and removes older ones in the background. A compacted product.current topic is a changelog of the catalog: replay it from the start and you get the current price of every product, not every price it ever had. To delete a key, you publish a tombstone, a record with that key and a null value. Tombstones stay readable for delete.retention.ms so slow consumers see them, then they go too.

You can combine both (compact,delete) to keep the latest value per key but drop anything very old. Compaction is not instant. The active segment is never compacted, and min.compaction.lag.ms holds back recent records, so a consumer may still see several versions of a key. Write consumers that tolerate that.

SNS plus SQS: a copy per subscriber

The AWS version works the other way round. SNS keeps no log. When checkout publishes, SNS pushes a copy of the message into every subscribed SQS queue, and each queue holds its own copy until a consumer deletes it. Fan-out happens at publish time, not read time.

The behaviour follows from that:

  • No replay of the past. A queue created today receives only messages published from today. History has to come from somewhere else, such as an archive in S3.
  • Per-message acks. SQS hides a received message for the visibility timeout (30 seconds by default). Delete it and it is gone. Do not, and it reappears for another consumer. After maxReceiveCount attempts, a redrive policy moves it to that queue's dead letter queue. One bad message does not block the others, which is a real advantage over Kafka's offset model.
  • Filtering at the topic. A subscription filter policy lets the fraud queue receive only orders over a threshold. Filtering on message attributes is the classic form, and SNS can also filter on the message body.
  • Ordering is opt-in. Standard topics and queues are at-least-once with best-effort ordering. SNS FIFO feeding SQS FIFO preserves order per MessageGroupId, which plays the same role as a Kafka key. FIFO comes with lower throughput limits than standard, so check the current quotas before choosing it.
  • Retention is short. SQS keeps a message four days by default and 14 days at most. That is a backlog buffer, not a history.

Use SNS+SQS when you want per-message retries and dead-lettering, managed scaling, and no need to replay months of history. Use Kafka (or a managed log like Kinesis or Pub/Sub with retention) when replay, long retention or very high throughput per topic matters.

Deep Dive: Sizing and the Numbers

Let us size the bookstore's order.placed topic properly. The lesson's 200 orders per second is the normal load. The flash sale from the next lesson peaks at 5,000 per second. Assume 2 KB per event (a full-state event), replication factor 3, five subscriber groups today, and 30 days of retention. Redo the math with your own numbers; the shape of it is what carries over.

Bandwidth: fan-out multiplies reads, not writes

FlowNormal (200/s)Flash sale (5,000/s)How it is computed
Producer ingress0.4 MB/s10 MB/srate × 2 KB

Disk writes, whole cluster1.2 MB/s30 MB/singress × RF
Consumer egress, 5 groups2 MB/s50 MB/singress × groups
Consumer egress, 20 groups8 MB/s200 MB/singress × groups

The producer's cost stays flat no matter how many groups subscribe. That is the lesson's promise, and it holds. The broker's cost does not stay flat. Every new group adds a full copy of egress. At 20 groups during the flash sale, the cluster sends 200 MB/s to consumers, which is 1.6 Gbit/s. That is fine spread over several brokers, but it is no longer a rounding error.

The good news is that a caught-up consumer reads from the operating system's page cache, not the disk. Kafka sends those bytes with very little copying. A lagging group is different. Fraud replaying yesterday's data reads cold segments from disk and competes with everyone else's I/O. A big replay is a capacity event, so schedule it, throttle it, or point it at follower replicas where your setup supports that.

Storage: retention sets the bill

At a steady 200 events per second, one day is 200 × 86,400 = 17.3 million events, or about 35 GB. Thirty days is about 1 TB. With replication factor 3, the cluster stores about 3.1 TB. Add headroom for the flash-sale days and for disks you never want above roughly 70% full. Plan on 5 TB or more of raw disk for one topic.

Retention is the dial. Seven days costs about 0.7 TB replicated. Ninety days costs about 9.3 TB. If only data science wants the long history, a cheaper design keeps 7 days in the broker and archives the rest to object storage, either through Kafka's tiered storage or a sink connector. The broker then holds the hot tail. Old history becomes a file read, not a broker read.

Partition count: work backward from the slowest consumer

People size partitions from producer throughput. That is usually the wrong end. A partition can absorb several MB/s of writes, so 10 MB/s of ingress needs only a handful. The constraint is the slowest subscriber, because one partition is processed by one thread at a time (unless the consumer adds its own parallelism).

Fraud scoring takes 20 ms per event, including a model call. One thread handles 50 events per second. At 5,000 events per second, fraud needs 100 events in flight at once. With one thread per partition, the topic needs at least 100 partitions just for fraud. Plan for 2× growth, and 200 partitions looks right.

There are three ways out if that number feels too high:

  1. Parallelism inside the consumer. Read a partition, then process different keys concurrently while keeping each key in order. Libraries such as Confluent's parallel consumer do this. It decouples processing parallelism from partition count, at the cost of trickier offset tracking.
  2. Batching. Score 50 orders in one model call instead of 50 calls.
  3. Accept lag. If fraud may run 10 minutes behind during a two-hour sale, compute the backlog and check it fits the retention window comfortably.

Do not overshoot wildly, either. Every partition adds replicas, open files, leader elections on failover, and metadata. Thousands per topic is a smell unless you know why you need them.

Lag in time, not messages

Lag in messages is hard to reason about. Turn it into time. If fraud is 480,000 events behind and drains at 1,200 per second net (it consumes 1,400 while 200 keep arriving), it catches up in 400 seconds, under seven minutes. Now suppose it is 2 billion events behind, with seven days of retention, and falling further behind every hour. The question is not "how far behind?" It is "when does the oldest unread segment get deleted?" Alert on that time, with a margin of days.

Deep Dive: Failure Modes in Production

1. A poison message stops one partition

Symptom. Fraud's total lag climbs steadily, but only one partition's lag is growing. The other eleven are at zero.

Mechanism. One event fails to deserialize, or it triggers a bug, so the handler throws on every attempt. Kafka's progress is a single committed offset, so the consumer cannot skip that record without deciding to. It retries forever. Every order behind it on that partition waits.

Detect. Per-partition lag, not just group totals. A repeating stack trace with the same partition and offset in the logs.

Fix. Catch the error, write the raw record plus the error to a dead letter topic, commit past it, and alert. Separate the two kinds of error. Retry transient ones (a timeout from a dependency) in place with backoff. Dead-letter permanent ones (bad schema, validation failure) immediately.

2. Rebalance storms

Symptom. Throughput collapses. Consumer logs show members joining and leaving every few minutes. The same records get processed again and again.

Mechanism. A batch of 500 records takes longer than max.poll.interval.ms to process, perhaps because a dependency slowed down. The member is evicted. Its partitions go to others, who start from the last committed offset and hit the same slow batch. Meanwhile the evicted member rejoins, which triggers another rebalance. With the eager protocol, every rebalance pauses the whole group.

Detect. The rebalance rate and the join and sync counts on the consumer coordinator metrics. Log lines saying the poll timeout expired. A rise in duplicate processing at the idempotency layer.

Fix. Make each poll loop bounded: lower max.poll.records, put timeouts on downstream calls, and size max.poll.interval.ms to the worst realistic batch. Switch to the cooperative-sticky assignor. Use static membership for rolling deploys.

3. The group that came back to an empty mailbox

Symptom. A batch consumer that runs weekly, or a service that was off for a long outage, starts up and reports zero lag. It has silently skipped a week of events.

Mechanism. Committed offsets themselves expire. An empty group loses them after offsets.retention.minutes (seven days by default in current Kafka). With no committed offset, the consumer falls back to auto.offset.reset. The default is latest, which means "start from now."

Detect. This one is quiet. Watch for consumer start-up logs that reset offsets, and compare processed counts with produced counts per day.

Fix. Set auto.offset.reset=earliest for consumers where missing data is worse than reprocessing. Raise offset retention above your longest planned downtime. Most important, make "the subscriber catalog lists this group" mean someone gets paged when it stops.

4. A hot key overloads one partition

Symptom. One broker's CPU and network are much higher than the others. One partition in every subscriber group lags while the rest are idle.

Mechanism. The key is skewed. Key by seller_id and one marketplace seller with 30% of the volume puts 30% of the traffic in one partition. Adding partitions does not help: the hot key still hashes to just one of them.

Detect. Bytes-in and messages-in per partition, not per topic. A per-key count from a sample of the topic.

Fix. Key by the entity whose order actually matters. For orders that is order_id, which spreads evenly. If you truly need per-seller order, split the hot key (seller_42#0 to #7) and accept that order now holds only within each sub-key. That is a real semantic change, so make it with the consumers, not to them.

5. Retries break per-key order

Symptom. A loyalty view shows an order as "placed" even though it was cancelled. The log shows order.cancelled was processed before order.placed.

Mechanism. There are two common paths. On the producer, an old client with idempotence off and several requests in flight retries batch 1 after batch 2 succeeded, so the broker stores them reversed. On the consumer, a "retry topic" pattern parks a failing order.placed in order.placed.retry and moves on. The order.cancelled that follows is then processed first.

Detect. Store the last applied version or offset per key in the view, and count events that arrive older than what you already have.

Fix. Keep the idempotent producer on. On the consumer, a retry-topic design must also park every later event for the same key until the earlier one succeeds, or it must apply events by version and discard stale ones. "Move on and retry later" and "strict order per key" cannot both hold for the same key.

6. ISR shrink turns acks=all into acks=1

Symptom. After a broker failure and a fast leader election, a few hundred orders that the producer logged as acknowledged are missing from the topic.

Mechanism. A slow disk dropped two followers out of the ISR. With min.insync.replicas=1, the leader kept accepting acks=all writes alone. When that leader died, a follower without those records became leader. Or unclean leader election was enabled, and an out-of-sync replica took over.

Detect. Under-replicated partitions, and partitions under the min ISR. These should be zero in steady state and should page someone when they are not.

Fix. Replication factor 3, min.insync.replicas=2, acks=all, unclean election off, replicas spread across zones. Then decide what the producer does when writes are refused. Checkout should fail or buffer the order visibly, never drop the event.

7. Two services share a group id by copy-paste

Symptom. This is the lesson's Q3 incident, at the Kafka level. Loyalty receives roughly half the orders. Its logs show partitions being assigned and revoked whenever the analytics team deploys.

Mechanism. The loyalty service was started from analytics' template and kept group.id=analytics. Kafka sees one group with more members and splits the partitions between two different programs.

Detect. List the group's members and look at the client IDs and hosts. Two different applications in one group is always a bug.

Fix. Derive the group id from the service name in config, never from a template default. Use broker ACLs so a service may join only its own group.

At-least-once, at-most-once, "exactly-once"

Every serious pub/sub system gives you at-least-once by default, and that is what you should design for. Kafka's transactions add exactly-once for a specific shape: read from Kafka, process, write to Kafka, and commit the input offsets in the same transaction. Consumers then read with isolation.level=read_committed. The guarantee stops at Kafka's edge. The moment your handler sends an email or charges a card, you are back to at-least-once plus idempotency. The Exactly-Once Semantics lesson goes through the details. In a design review, "we use Kafka so it is exactly-once" is a claim to challenge.

Choose the key by asking which consumer state must never see events out of order, and key by the entity that owns that state. If two consumers need different keys, that is a sign you have two topics, or one topic plus a stream processor that re-keys it.

Push or pull

Kafka consumers pull, so a slow consumer simply reads less. Backpressure is free. SNS pushes into SQS, and SQS consumers then pull, so the queue absorbs bursts. Pure push to HTTP endpoints (SNS to HTTPS, or webhooks) needs the receiver to keep up or the sender's retry policy decides your fate. Prefer pull wherever the consumer is your own service.

One topic per event type, or one per entity

Separate topics (order.placed, order.cancelled) are easy to subscribe to selectively. But order across them is not guaranteed, so a consumer can see the cancel before the place. One topic per entity (orders, with an event type field) keeps all of one order's events in one partition and in order. If consumers care about lifecycle order, prefer the entity topic and let them filter by type.

Deep Dive: Design-Review Checklist

  1. What is the partition key, and which consumer's correctness depends on order per that key? If the answer is "nobody's", why is there a key at all?
  2. How many partitions, and how was that derived? Show the slowest consumer's per-event time and the peak rate. What happens to ordering if you grow it later?
  3. What are acks, replication factor and min.insync.replicas? What does the producer do when the broker refuses a write?
  4. When does each consumer commit, relative to its side effects? Is auto-commit on with asynchronous processing?
  5. Where is idempotency enforced for each subscriber, and what is the dedup key? How long does the dedup record live compared to the longest possible redelivery?
  6. What happens to a message that always fails? Name the dead letter topic or queue, who is alerted, and how a replay from it works.
  7. What is the retention, and what is the alert threshold on backlog age? How many days of margin does that leave?
  8. What is auto.offset.reset, and what is offset retention? What happens if this group is down for ten days?
  9. How is a rebalance kept cheap? Assignor, static membership, bounded poll loop.
  10. Who owns each subscription, and where is that written down? Can a new group join without review if the topic carries personal data?
  11. What does a full replay cost the cluster? Is there a throttle or a separate read path so a backfill does not hurt live consumers?
  12. Is this topic broadcast of facts, or is it secretly a job queue or a request-response channel?

Deep Dive: Senior Interview Follow-ups

"Why can't I just add more consumers to a Kafka group to go faster?"

Each partition is owned by one member of a group at a time, so useful parallelism stops at the partition count. Members beyond that sit idle. To go faster you add partitions, which remaps keys and disturbs order during the change, or you add parallelism inside each consumer while keeping per-key order. Batching the expensive call is often the cheapest win.

"Does acks=all guarantee no data loss?"

Only together with the right topic settings. acks=all waits for the current ISR, which can shrink to the leader alone. You need replication factor 3, min.insync.replicas=2, unclean leader election off, and replicas in different failure domains. Even then, the producer has to handle a refused write correctly, and a correlated failure of every replica can still lose unflushed data, because Kafka acknowledges on replication, not on fsync.

"Fraud's group shows zero lag, yet fraud is missing a day of orders. How?"

Lag is measured against the committed offset, and the committed offset can be wrong in a way that looks healthy. There are three usual causes. The group was inactive past offset retention and reset to latest. Or auto-commit committed records that an async worker pool then dropped in a crash. Or the service shares its group id with another application, so the other app processed those partitions. Check the reset logs, the commit strategy and the group's member list, in that order.

"How do you guarantee order for one order's events and still scale?"

Key by order_id so every event of one order shares a partition, keep the idempotent producer on so retries do not reorder, and keep all lifecycle events on one topic. On the consumer, never "skip and retry later" for a key whose order matters: either block that key or apply by version and drop stale events. Scale comes from many orders across many partitions, not from parallelism within one order.

"When would you choose SNS plus SQS over Kafka?"

When consumers do independent per-message work that needs its own retries and dead-lettering, volume is modest, and nobody needs months of replay. You get per-message acks (no head-of-line blocking), filter policies and no cluster to run. You give up replay, long retention and cheap high throughput. If a new team will want last quarter's events, archive them separately or pick a log.

"Is a compacted topic a database?"

It is a durable changelog that can rebuild a key-value view: replay it and you get the latest value per key. It is not a query engine. There are no secondary indexes and no reads by key without building a store from it. Compaction is also asynchronous, so readers may see several versions of a key and must handle that. Treat it as the source for a materialised view, which a stream processor or the consumer itself maintains.

"The topic must go from 12 to 48 partitions. How do you do it without breaking consumers?"

Adding partitions moves most keys, so for a while one key's events can sit in an old and a new partition. If consumers need strict per-key order, create a new topic with 48 partitions instead. Mirror into it, keyed the same way, while keeping order per key. Move consumers one group at a time, each starting from a known point, then cut the producer over and retire the old topic. If consumers apply events by version and ignore stale ones, adding partitions in place is acceptable, with a short window of discarded stale events.

"What is the real cost of the twentieth subscriber?"

To the producer: nothing. To the broker: one more full copy of egress, so during the flash sale another 10 MB/s, plus a replay's cold reads when it joins. To the organisation: another consumer of the schema, which makes every future change slower, another idempotency boundary, and another backlog that can outrun retention. That last cost is why a subscriber catalog with named owners is part of the pattern, not paperwork.
