Deep Dive: The Capacity Plan

The capstone ends with a confident number: database reads below 400 queries a second while traffic tripled. A review panel's first job is to check that number. This section rebuilds it from the per-data-type decisions. Doing so turns up one decision that, as written, would blow the budget several times over. Finding that kind of thing is exactly why you do the arithmetic before 8 PM.

Assumptions

  • Traffic. A normal evening runs 6,000 page views a second. The sale triples it to 18,000. The bestseller takes 12,000 of those, as in the lessons. The other 6,000 spread over about 30,000 products that get any views in the hour, roughly 0.2 views a second each.
  • Catalog. 100,000 products in total.
  • Checkout. 300 orders a second at peak, half of them for the bestseller.
  • Infrastructure. 60 app instances. A Redis cluster for read caches, a separate small Redis for write-behind counters. A Postgres primary with replicas.

How many misses does a TTL cause?

For a hot key the answer is easy: about one rebuild per TTL. With single flight it can't be more.

The long tail is where the load hides. A product with r views a second and a TTL of T seconds misses at most once per TTL window, and only if anyone looks at it in that window. Its miss rate is (1 − e^(−rT)) / T. When rT is large, that is just 1/T. When rT is small, nearly every view is a miss. Multiply by 30,000 products.

The badge is the problem. Its 10-second TTL is right for the bestseller, which rebuilds once every 10 seconds. It is wrong for 30,000 quiet products, where it acts almost like no cache at all. Nobody notices in a load test that hammers one product page.

There are two good fixes. Both follow the capstone's own rule that the cost of being wrong sets the correctness mechanism.

  • Make the TTL depend on the value. The badge only shows when stock is 10 or fewer. For a product with 400 in stock, the cached answer is "no badge," and it stays true for a long time. Cache "no badge" for 5 minutes. Cache an actual count for 10 seconds. Have the checkout path delete the key when a decrement crosses the threshold, which happens once per product, not once per sale. If 1,000 of the 30,000 active products are low on stock, the badge costs about 1,000 × 0.086 + 29,000 / 300 ≈ 185 misses a second.
  • Stop reading the database for it at all. Push stock levels into the cache from change data capture on the inventory table. Every committed decrement becomes a cache write within a second or so. That is 300 cache writes a second at peak and zero database reads. It also makes the badge more accurate than a 10-second TTL. This is the better end state. It is listed in the evolution path because it needs a CDC pipeline first.

With the first fix, the cache-driven read load is about 8 + 100 + 185 + 1 ≈ 295 queries a second. That is inside the 400 target, with some headroom for price changes and the occasional rebuild of a recommendations strip.

Checkout is outside that number, on purpose. 300 orders a second means 300 price reads and 300 conditional decrements against the primary. Count them separately in the capacity plan. They are the reads that must never be cached, and they need their own headroom.

Redis: operations, memory and bandwidth

Operations. Each page reads four keys (description, price, badge, recommendations) and runs one counter script. At 18,000 views a second that is 72,000 reads plus 18,000 counter scripts. The reads go to the read-cache cluster. The counter scripts go to the write-behind instance.

Memory. Descriptions average about 4 KB each, so 100,000 of them is 400 MB. Recommendation strips at about 2 KB are another 200 MB. Prices and badges are tiny. Add the stampede envelope and Redis's per-key overhead, and plan for about 1 GB of data. That fits one node. The cluster exists for throughput, hot-key isolation and failure blast radius, not for memory. Six primaries, each with one replica, is a sensible start.

Bandwidth for the hot product. One bestseller page pulls about 6.5 KB from the cache. At 12,000 views a second, that is 78 MB/s, a little over 600 Mbit/s. A modern network link handles it, but all of it lands on whichever shards own those keys. The next section is about that.

The write side

Writes are small, and that is the point of the design. The view counter's flusher sends the bestseller's count once every 2 seconds. The tail is more interesting. With a 2-second flush, 6,000 tail views a second still produce about 4,950 row updates a second, because quiet keys barely coalesce. Run the tail on a 30-second flush and it drops to about 1,000. Write the second loss sentence: "if we lose 30 seconds of tail views, about six views per product go missing." Put the counters in their own narrow table, so each update rewrites a small row and not the whole product record.

Then there is the checkout decrement: 150 a second on one inventory row for the bestseller. That one row is a lock queue, just like the view counter in the write-behind incident. The difference is that here, every write matters individually. The failure drills come back to it.

Putting both on one instance forces a bad choice. LRU will evict unflushed counts during the sale, which is write-behind's worst silent failure. noeviction will make every read-cache write fail once memory is full. Two small deployments are cheaper than either outage.

Co-locate a product's keys, or spread them?

Redis Cluster places keys by hash slot. A hash tag such as {p8412} in every key name for one product puts all its keys on one shard. Then one MGET fetches the whole page in one round trip.

The cost is concentration. Every read for the bestseller now hits one shard: 48,000 reads a second, all on one main thread. Spread the keys instead, and four shards share the load at 12,000 each. The page then needs four parallel round trips.

The way out of the trade-off is an in-process L1 cache in front of both. Each app instance keeps the top few hundred products' entries in memory for 1 second. The bestseller's Redis traffic drops from 48,000 reads a second to about 60 instances × 4 keys = 240. With the hot load gone, co-location is cheap and the one-round-trip MGET wins for everyone else.

The L1 adds up to 1 second of staleness. That fits every staleness budget on the page except the two "zero" rows, and those never touch a cache. Write it into the sentences anyway: "display price may be up to one rebuild plus 1 second old."

Invalidating 60 local caches

An L1 has its own invalidation problem. A price change deletes the Redis key, but 60 processes still hold the old value in memory. Two options:

  • Let the L1 TTL do it. With a 1-second TTL, the worst case is one extra second. For this page that is enough, and it has no moving parts.
  • Broadcast invalidations. Publish the key on a Redis Pub/Sub channel, and every instance drops its local copy. Pub/Sub is fire-and-forget: an instance that is reconnecting misses the message. So the short TTL stays as the backstop. Redis 6 and later also offer client-side caching with server-assisted invalidation (the CLIENT TRACKING feature), which does this bookkeeping for you if your client library supports it.

Start with the TTL. Add broadcast only if a staleness sentence needs it.

Why not just cache the whole page?

Someone in every review asks this. Cache the rendered HTML once and skip four lookups. The answer is in the second column of the final architecture table. A cached page is only as fresh as its freshest part needs to be. The badge needs 10 seconds, so the whole page gets a 10-second TTL, and the description and recommendations rebuild 360 and 4,320 times more often than they need to.

The pattern that does work is a split by staleness. Cache the page shell, description and recommendations at the edge or in one fragment, with a long TTL and stale-while-revalidate. Fetch the price, badge and counter as a small JSON call with their own short budgets. The CDN then serves most of the bytes, and the app serves only the parts that change.

Deep Dive: Failure Drills

A review panel will run the design through specific bad evenings. Here are five, each with a timeline, what the design does, and what it still gets wrong.

Drill 1: the bestseller's price changes at 8:05

8:05:00.000. Merchandising lowers the price in the admin panel. The admin service commits to the database and invalidates price:{p8412}.

The trap. If invalidation means DEL, the key vanishes and the stale copy goes with it. 12,000 requests a second meet a 50 ms rebuild: 600 misses. Single flight keeps the database at one query, but 599 requests wait, and the hot shard absorbs a burst of lock attempts and polls. This happens on every price edit, which during a sale may be often.

The better move. Soft invalidation: mark the entry stale (set its logical expiry to now) instead of deleting it. The next request serves the old price, triggers one locked refresh, and the new price is live about 50 ms later. Add the L1's 1 second. Checkout reads the database, so no order is placed at the old price.

What still goes wrong. The bulk-pricing tool writes straight to the database and skips invalidation. Those prices can be wrong for up to 5 minutes. The capstone accepts that with the TTL, but the panel will ask whether customers can see a price at the product page that differs from checkout for 5 minutes. Answer it before they ask: either show "price confirmed at checkout," or route the bulk tool's writes through CDC invalidation (evolution stage 3).

Drill 2: the read-cache shard holding the bestseller dies at 8:10

8:10:00. The primary of one of six read-cache shards stops responding. Failure detection takes a few seconds to tens of seconds, depending on configuration (Sentinel's down-after-milliseconds, Cluster's cluster-node-timeout). Then its replica is promoted.

During detection. Every request for a key on that shard gets an error or a timeout. The bestseller is safe: its entries are in 60 L1 caches, which keep serving and simply don't refresh. The tail is not. About a sixth of tail keys live on that shard, so about 1,000 requests a second need data the cache can't give.

The trap. A client that treats "cache error" like "cache miss" sends all 1,000 to the database. They are distinct keys, so single flight can't merge them. Database reads jump from 295 to about 1,300 a second, during a sale, for as long as detection takes.

The better move. Put a circuit breaker on each cache shard and a bulkhead on database fallback: at most, say, 200 concurrent fallback queries across the fleet, with a short timeout on the cache call itself (a few milliseconds, not the client default). Beyond that, degrade. The recommendations strip disappears, and the description renders from the CDN shell. Price and badge fall back to the database within the bulkhead, because they matter most.

After failover. The promoted replica already holds the data, so the hit ratio recovers at once. That is the reason a read cache gets replicas, even though losing it loses no data. A cold replacement would trigger the full cold-start runbook.

Drill 3: the counter instance fails over at 8:15

The write-behind Redis loses its primary. The promoted replica is missing whatever was not yet replicated, usually milliseconds of increments. The last unflushed deltas on the old primary may also be gone if its AOF had not been fsynced. Worst case is a couple of seconds of views, about 36,000 on the bestseller.

This is the drill where the loss sentence earns its place. "If we lose 2 seconds of view counts, the numbers are imperceptibly lower." The panel nods and moves on. What they should check is the next part: does the display total on the new primary go backwards? If the totals were replicated too, it dips by the lost amount and nobody can tell. If the totals are rebuilt from the database without adding pending deltas, the bestseller's counter drops by tens of thousands on screen. That is the bug to rule out.

Drill 4: the bestseller sells out at 8:12

The display. The badge says "only 3 left!" From the threshold rule in the capacity plan, it was cached with a 10-second TTL. When the count hits zero, the checkout path invalidates the badge key, and the page shows "sold out" within one rebuild. Without that invalidation, the badge could advertise stock for 10 seconds after there is none. That is annoying, not dangerous, because of the next part.

The decision. Each checkout runs, in its own short transaction:

UPDATE inventory SET qty = qty - 1
 WHERE sku = $1 AND qty >= 1;
-- 1 row: reserved.   0 rows: sold out, tell the customer.

No cache is involved, so overselling is impossible regardless of what the badge said.

The hot row. 150 checkouts a second for the bestseller all update the same row. Each one holds that row's lock until its transaction commits. If the transaction is just the decrement and a commit, a couple of milliseconds, the row can handle a few hundred a second. If someone wraps the payment API call in the same transaction, the lock is held for hundreds of milliseconds and throughput collapses to a handful of orders a second. The flash sale then fails at checkout, not at the cache.

Keep the reservation a separate, tiny transaction. Take payment afterwards. Release the reservation on payment failure or timeout, as a saga step. If one row still isn't enough, split stock into several rows (say 10 rows of 100 units each) and decrement a random non-empty one. That is the same trick as splitting a hot counter, applied where every write must be durable.

Drill 5: a bulk import touches 50,000 descriptions at 8:20

The merchandising team, as promised in the brief, runs its bulk tool mid-sale. It rewrites 50,000 product descriptions directly in the database.

As designed. No invalidation fires. Descriptions are stale for up to an hour, by the TTL. That is inside the budget. Nothing breaks.

After you add CDC invalidation (evolution stage 3). Now each changed row produces an invalidation, so 50,000 arrive within seconds. About 30,000 of those products are active, each viewed every 5 seconds or so. Within about 10 seconds, almost all of them miss and rebuild: a few thousand database reads a second, on distinct keys, which single flight cannot merge. The fix for one problem has created a mass-invalidation stampede.

Two guards make CDC invalidation safe. First, invalidate only what changed: bulk tools often rewrite rows with identical content, and CDC events carry before and after images, so compare them and drop no-op updates. Second, rate-limit the invalidation consumer, for example to 500 keys a second, and use soft invalidation so each key serves its old copy until it is rebuilt. 50,000 invalidations then spread over 100 seconds, and the database never sees more than the consumer's rate.

One opinion to defend in the room: the staleness budget table is the specification, so review it like one. It multiplies the bestseller's badge rebuilds by five and nearly doubles misses on low-stock tail products, and the plan has to be redone. Make that cost visible when the request arrives, not after the sale.

Deep Dive: Observability

The design makes a different promise for each data type, so measure each one separately. A single cluster-wide hit ratio will hide almost every failure in the drills above.

  • Database queries per second by data type. Tag each query with its source (description, price, badge, recommendations, checkout). This is the number the capacity plan predicted, and the badge row is where it will be wrong first.
  • Hit ratio by data type, and by hot versus tail. The bestseller will be near 100% whatever happens. The tail ratio tells you whether TTLs fit traffic.
  • Age of the value served, as a histogram per data type, against its staleness budget. This is the direct check of the staleness sentences.
  • Concurrent rebuilds per key and waiter timeouts. Either above zero for long means stampede protection is leaking.
  • Per-shard CPU and network on both Redis roles. Averages hide the hot shard.
  • Oldest dirty age on the counter instance, and reconciliation drift between cache totals and the database.
  • Invalidation lag: time from database commit to cache invalidation, once CDC is in place. In multi-region, per region.
  • Inventory row lock waits on the bestseller's SKU during the sale. That is where checkout will fail first.

Deep Dive: The Evolution Path

No team builds the final architecture on day one, and they shouldn't. Each stage below is triggered by a measurement, not by ambition.

  1. Stage 0: cache-aside everywhere, one Redis. Delete on write, fixed TTLs. Right for a store at a few hundred requests a second. Move on when database CPU tracks page traffic.
  2. Stage 1: per-type budgets and write-behind counters. The table from the capstone, plus a separate counter instance. Trigger: a hot row (the view counter) shows up in lock waits.
  3. Stage 2: stampede protection. Envelopes with soft and hard expiry, single flight, TTL jitter, the cold-start runbook. Trigger: database spikes aligned with expiries or deploys, or the first planned flash sale.
  4. Stage 3: L1 caches and CDC-driven invalidation. Trigger: one Redis shard running hot, or the bulk tool causing stale-data tickets. Bring the rate limit and the no-op filter with it.
  5. Stage 4: edge split. Shell and description at the CDN with stale-while-revalidate; live fields through a small API. Trigger: cache bandwidth or app CPU spent rendering identical HTML.
  6. Stage 5: multi-region. Each region gets its own Redis. Invalidations, not values, travel between regions over the CDC stream through a durable log (Module 2's publish/subscribe, typically on Kafka), each carrying the source version. Values are rebuilt locally from each region's replica, so a region can never cache a value newer than its own database copy. The TTL stays as the backstop for a lagging stream, and invalidation lag per region becomes a paged alert. Prices on the order are still read from the primary.
  7. Stage 6: personalized prices. Don't cache 500 million results that rarely repeat. Cache the inputs instead: base prices (100,000 keys) and each enterprise customer's contract terms (thousands of keys). Compute the final price at request time, which takes microseconds. When outputs don't repeat, caching them only fills memory with keys read once.

Deep Dive: Design-Review Questions

  1. Show the database read budget per data type at peak, including the long tail. Which row dominates, and what happens to it if traffic doubles?
  2. Which TTLs were chosen from a staleness sentence, and which were chosen because "five minutes sounds right"?
  3. Which writers bypass invalidation today (bulk tools, scripts, other services), and what bounds their staleness?
  4. When the bestseller's price changes mid-sale, what happens in the next 100 ms, in Redis, in the L1 caches and at checkout?
  5. Are read caches and write-behind state on separate instances, with opposite eviction and persistence settings?
  6. What does the client do when a cache shard is unreachable? What caps database fallback, and what degrades first?
  7. How long does the inventory reservation hold its row lock? Is anything slow, such as a payment call, inside that transaction?
  8. What is the cold-start plan for each Redis role, and how long does a replacement node take to reach its normal hit ratio?
  9. If CDC invalidation is added, what limits a 50,000-row bulk import from becoming a mass-invalidation stampede?
  10. Which metrics prove each staleness sentence is true in production, per data type?
  11. Which numbers on this page could a customer screenshot and hold you to, and which path serves each of them?
