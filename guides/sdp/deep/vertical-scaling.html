Deep Dive: Inside the Mechanism

The lesson treats "a bigger machine" as one dial. In a design review it is four dials, and they do not move together: cores, memory, storage I/O and network. Each one hits its own limit. And the software on the machine decides how much of the new hardware it can actually use. So the real question is never "how big?" but "bigger in which dimension, and can this program use it?"

What "bigger" buys, dimension by dimension

  • Cores. Cloud instances add vCPUs, and a vCPU is usually one hardware thread, so two vCPUs share one physical core. Going from 16 to 64 vCPUs gives 4x the threads, not 4x the speed of any one request. A single-threaded hot path runs exactly as fast as before. Clock speed rarely changes inside one instance family.
  • Memory. More RAM matters in two ways. Capacity decides whether the working set (the data touched in a typical hour) fits in memory. Bandwidth decides how fast many cores can read it at once. On big multi-socket hosts the second one becomes the limit long before the first.
  • Storage I/O. On network block storage the disk is a separate product. AWS gp3 volumes, for example, start at 3,000 IOPS and 125 MiB/s whatever instance they are attached to, and you provision more separately. The instance also has its own cap on block-storage bandwidth, which grows with instance size. A bigger CPU does nothing for a database that is waiting on its volume.
  • Network. Instance network bandwidth scales with size too. Smaller sizes are often listed as "up to" some figure, which means a burst allowance, not a sustained rate. A cache or proxy box can saturate its NIC while the CPU sits at 30%.

The practical consequence: before resizing, find which of the four is saturated. A memory-bound database wants a memory-optimised family (more GB per vCPU), not twice the cores. A compression job wants a compute-optimised family. Picking the right family is often worth more than going up a size.

NUMA: the big machine is secretly two machines

Past a certain size, a server has more than one CPU socket. Each socket has its own memory controller and its own bank of RAM. A core reading memory attached to its own socket is fast. Reading memory attached to the other socket crosses an interconnect and is noticeably slower, and the interconnect has limited bandwidth. This layout is called NUMA, non-uniform memory access.

What this means in practice:

  • Linux reports the layout with numactl --hardware and per-node hit and miss counts with numastat. A high numa_miss or other_node count means threads keep reading the far bank.
  • The kernel's automatic NUMA balancing migrates pages toward the threads that use them. It helps many workloads and hurts some, so databases sometimes document their own advice on it.
  • A big JVM or database buffer pool spread across both sockets pays the remote penalty on a large share of reads. Running two smaller processes, each pinned to one socket, can beat one process on the whole box.
  • Cloud instances that span sockets expose NUMA too. The very largest sizes in a family usually do. The one-socket sizes below them often give better per-core results for memory-heavy work.

This is the first reason a 2x machine can give less than 2x. It is also why "just get the biggest box" deserves a benchmark before it gets a purchase order.

Why returns fall: contention and coherency

The lesson's "a database limited by lock contention gains little from core #96" has a formal shape. Neil Gunther's Universal Scalability Law (USL) models throughput on N cores as:

C(N) = N / (1 + σ(N - 1) + κN(N - 1))
  • σ (sigma), contention: the share of work that must happen one at a time. A hot lock, a single log writer, one busy row. This is Amdahl's law. It flattens the curve.
  • κ (kappa), coherency: the cost of cores keeping each other's view consistent. Cache lines bouncing between cores, lock handoffs, cross-socket traffic. It grows with the number of pairs of cores, so past a peak it makes the curve go down.

The peak sits at N* = √((1 - σ) / κ). Past that, adding cores makes the system slower. That is not a theoretical oddity. It is what a hot-row workload looks like on a big box: CPU climbs, throughput falls, and spinlock time dominates the profile.

You can fit σ and κ from a few load tests at different core counts (restrict cores with taskset or container CPU limits). The next section works an example.

How a resize actually happens

"Change the instance type" is a sequence of steps, and each step has its own way to go wrong.

  1. Stop. On most clouds you cannot change the type of a running VM. The instance stops. Anything on local instance-store (ephemeral NVMe) disks is gone. Network block volumes survive.
  2. Change type and start. The provider must find a host with room for the new size. Near the top of a catalog, or in a busy zone, it may not. You then have a stopped production server and an "insufficient capacity" error.
  3. Warm up. The OS page cache, the database buffer pool and the JIT all start cold. The first minutes after a resize can be slower than the old, smaller box was.

Because of steps 2 and 3, teams that resize often stop resizing in place. They build the new machine beside the old one and switch. For a stateless box that means launching the larger instance, warming it, then moving traffic. For a database it means upgrading a replica first, letting it catch up, and promoting it in a controlled failover. Managed databases with a standby often do this for you: they resize the standby, fail over, then resize the old primary. The downtime is the failover, usually seconds to a minute or two, rather than a full stop-start-warm cycle. Measure it in a rehearsal. Don't trust a number from a slide.

Containers have their own version. Kubernetes historically resized a pod by replacing it. In-place pod resize (beta as of Kubernetes 1.33) can change CPU and memory limits on a running pod, though memory decreases and some runtimes still have caveats. The Vertical Pod Autoscaler recommends or applies requests, and in its default mode it applies them by evicting pods. Vertical scaling of one pod is cheap. Vertical scaling of a stateful pod is still a failover.

Deep Dive: Sizing and the Numbers

How much time does one resize buy?

Take the lesson's Q2: a primary database at 80% CPU, growing 5% a month. The question a review panel asks is "how many months until we are back here?" The answer depends on how well the software scales, so do it three ways. The target is to stay below 70% CPU.

After a resize by factor f with scaling efficiency e, utilisation becomes 80% / (f × e). Load grows by 1.05 each month, so the months until 70% are ln(70 / new utilisation) / ln(1.05).

MoveAssumed efficiencyUtilisation afterMonths until 70% again
2x, perfect scaling100%40%about 11.5
2x, realistic85%47%about 8
4x, realistic for a big jump75%27%about 20

Three things stand out. First, the honest 2x buys eight months, not a year. That is still plenty of time to plan a shard key, but not to execute a migration at a relaxed pace. Second, the 4x move buys well over a year, which is why the lesson says "one or two instance sizes". Third, the efficiency number matters as much as the size. Measure it before quoting a runway.

Growth also compounds. At 5% a month, load nearly doubles every 14 months (ln 2 / ln 1.05 ≈ 14.2). A team that resizes 2x each time is resizing about once a year forever, with each step pricier than the last.

On this workload the ceiling is not the catalog at all. It is the software, at about 13x the single-core rate, and no purchase moves it. Only reducing σ (shorter transactions, fewer hot rows) or κ (less shared state, socket pinning) does.

Here is the calculator, Python standard library only:

import math

def usl(n, sigma, kappa):
    return n / (1 + sigma * (n - 1) + kappa * n * (n - 1))

def peak_cores(sigma, kappa):
    return math.sqrt((1 - sigma) / kappa)

def months_of_runway(util_now, factor, efficiency, target=0.70, growth=0.05):
    util_after = util_now / (factor * efficiency)
    return math.log(target / util_after) / math.log(1 + growth)

for n in (8, 16, 32, 64, 96, 128):
    print(n, round(usl(n, 0.05, 0.0002), 1))
print("peak at", round(peak_cores(0.05, 0.0002)), "cores")
print("2x at 85%:", round(months_of_runway(0.80, 2, 0.85), 1), "months")

The memory cliff

Memory is where a resize pays most, and where its absence hurts most. Consider a query that touches 50 pages. Assume a page served from RAM costs almost nothing, and a miss to network block storage costs about 0.5 ms.

Buffer hit ratioMisses per queryAdded I/O time per queryReads/s at 2,000 queries/s
99.9%0.05~0.025 ms100
99%0.5~0.25 ms1,000
95%2.5~1.25 ms5,000

A drop from 99.9% to 95% sounds small. It is 50x the disk reads. At 5,000 reads a second, a volume at the gp3 baseline of 3,000 IOPS is already queueing, and queueing makes the 0.5 ms miss cost much worse. This is the cliff: the working set grows a little past RAM, and latency jumps far more than the growth suggests.

The fix is often a memory-optimised instance with the same core count. It costs less than going up a general-purpose size, and it targets the actual bottleneck. Watch the buffer hit ratio (Postgres: blks_hit and blks_read in pg_stat_database) as a leading indicator. It starts sliding months before latency does.

Where the price curve really bends

A precise point, because reviewers get it wrong in both directions. On the major clouds, price per vCPU inside one general-purpose family is close to linear. The largest size costs about its multiple of the smallest. So in the cloud the "steep curve" is not mostly the sticker price. It comes from three other places:

  • Software efficiency. In the USL example, the 64-core box costs 2x the 32-core box and delivers 1.11x. The effective price per unit of work rose about 80%.
  • Specialised tiers. Very high-memory machines (terabytes of RAM) are their own families, with their own pricing and limited availability.
  • Licences and support. Commercial databases often license per core, so the bill scales with cores whether the software uses them or not.

On-premises hardware is different. Top-bin CPUs and four- or eight-socket servers do carry a real price premium per core. Either way, the number to compare is cost per unit of measured throughput, not cost per core.

The cost of idling a big box

The lesson's spiky-load case, priced. Say the peak is 5x the daily average and you size for peak with 30% headroom. Average utilisation is then about 100% / (5 × 1.3) ≈ 15%. You pay for about seven units to use one on an average hour.

A horizontal fleet that follows load might average 50% to 60%. That is roughly a 3x to 4x difference in spend for the same work. Below a few hundred dollars a month nobody should care. At a six-figure monthly bill the gap pays for the statelessness work many times over.

Availability arithmetic for one machine

A single VM's availability is bounded by its host and its zone. Provider SLAs for a single instance are typically lower than for a multi-zone deployment, and the credits they pay are tiny next to the cost of an outage. Add your own causes:

  • Two planned resizes a year at 10 minutes each: 20 minutes.
  • One unplanned host failure with a 40-minute recovery, as in the lesson's Q3: 40 minutes.
  • Kernel and database patching that needs a reboot, four times a year at 5 minutes: 20 minutes.

That is about 80 minutes a year, or roughly 99.985%, if nothing else goes wrong. It fits a 99.9% target (8.8 hours a year) with room to spare. It cannot meet 99.99% (53 minutes) with any honesty, because one bad host recovery uses the whole budget. That is the sizing argument in one line: a single big machine can be "three nines", rarely "four".

Deep Dive: Failure Modes in Production

1. The upgrade that changed nothing

Symptom. The team doubles the cores. Latency and throughput stay exactly where they were. Overall CPU drops from 60% to 30%, which looks like headroom.

Mechanism. The hot path is single-threaded. Redis's main thread, a Node.js event loop, one Python process held by the GIL, or one lock everyone queues on. That one core was already at 100%. The average hid it, because the other cores were idle.

Detect. Look per core, never on average: mpstat -P ALL 1 or top with per-CPU view shows one core pinned. Per-thread CPU (top -H, pidstat -t) names the thread. For Redis, the main thread's CPU in INFO cpu tells the same story.

Fix. More processes, not a bigger process: Node cluster mode, more gunicorn workers, several Redis instances or Redis Cluster. Or remove the serial section. Always ask "is it one core or all cores?" before approving a resize.

2. The bigger box that got slower

Symptom. A move from a 32-vCPU to a 96-vCPU instance makes p99 latency worse, not better. Throughput rises a little, nowhere near 3x.

Mechanism. The new size spans two sockets. The buffer pool and the hot data structures sit mostly on one NUMA node. Half the threads now read through the interconnect, and the interconnect saturates. Lock handoffs between sockets are slower too, so the coherency term κ jumped.

Detect. numastat shows large numa_miss or other_node counts. perf shows more cycles stalled on memory. A benchmark pinned to one socket (numactl --cpunodebind=0 --membind=0) beats the unpinned run.

Fix. Choose the largest single-socket size instead. Or run one instance per socket, each pinned. Or enable the engine's NUMA settings where it has them. This is why a resize needs a load test on the target size, not on the current one scaled up on paper.

3. Nobody retuned the config

Symptom. After a 4x memory upgrade the database still reads from disk at the old rate. Free memory reports 150 GB unused. The cache hit ratio did not move.

Mechanism. Configuration was sized for the old box. shared_buffers, the JVM heap, connection pools and worker counts are all explicit numbers. The upgrade changed the hardware and none of the numbers. Some engines do benefit indirectly through the OS page cache, which hides the problem partly and makes it harder to notice.

Detect. Compare the config against the instance size as part of the change. Watch buffer hit ratio, heap usage and pool saturation before and after.

Fix. Treat a resize as a config change too. Keep sizing formulas in config management, tied to the instance's cores and memory, rather than literal numbers. Review the diff of effective settings, not just the instance type.

4. The heap that grew into a pause

Symptom. A JVM service moves from a 16 GB heap to a 96 GB heap. Average latency improves. Every few minutes there is a multi-second stall, and health checks time out during it.

Mechanism. Collectors that copy or mark the old generation in a stop-the-world phase take time roughly proportional to the live data they scan. Six times the live heap means a much longer worst-case pause. The tuning that worked at 16 GB is wrong at 96 GB.

Detect. GC logs (-Xlog:gc*) show pause times and their causes. Latency spikes line up with the pauses to the second.

Fix. Use a low-pause collector designed for large heaps (ZGC, Shenandoah), or tune G1's pause target. Or do not give it all to the heap: leave memory to the OS page cache or run two smaller JVMs. Large memory and short pauses do not come together by default.

5. The resize that could not start

Symptom. In a planned window, the instance stops for its resize. The start fails with an insufficient-capacity error. Production is down, and the "10-minute maintenance" turns into an hour of trying other zones and sizes.

Mechanism. Stop-change-start gives up the old host before securing the new one. Large and specialised sizes have the thinnest supply. Anything on local instance-store disks was also lost at the stop.

Detect. You find out at the worst moment, unless you rehearse. Check the API error in the start call, and audit which volumes are ephemeral before the window.

Fix. Build beside, then switch. Launch the new size first, warm it, then move traffic or promote it. For large sizes, use a capacity reservation for the window. Never keep anything you need on instance-store without a copy elsewhere.

6. The credits ran out

Symptom. A service on a small burstable instance runs fine for days, then slows to a crawl every afternoon. Nothing changed in traffic. The team's response is to "scale up", which does not obviously help either.

Mechanism. Burstable families (AWS T-series and similar) give a baseline CPU share and bank credits for bursts above it. Sustained load drains the bank, and the instance drops to its baseline, which can be a small fraction of a core. Storage can burst the same way on some volume types.

Detect. CPU credit balance metrics (on AWS, CPUCreditBalance) trend to zero before the slowdown. CPU "steal" time rises in the guest.

Fix. Move steady workloads to a fixed-performance family, or enable unlimited mode and budget for it. Burstable sizes suit spiky, low-average work. They are a trap for anything that runs hot all day.

7. Consolidation's bigger blast radius

Symptom. To save money, three services move onto one large host. Months later, a memory leak in the reporting job triggers the kernel's OOM killer, which kills the database process. Checkout goes down because of a report.

Mechanism. A big machine shared by many workloads makes them one failure domain. The Linux OOM killer picks a victim by its own scoring, and the biggest process is often the most important one. CPU and disk contention leak across workloads the same way.

Detect. dmesg or the journal shows "Out of memory: Killed process". Per-process memory in your metrics climbs before it.

Fix. Isolate with cgroups (container memory and CPU limits), set oom_score_adj so the database is the last choice, or keep critical stateful services on their own hosts. That is the bulkhead pattern, applied inside one machine.

Up, out, or diagonal

Real fleets scale diagonally. They pick a server size that suits the workload, then change the count. The size decision follows a few rules:

  • Stateful, single-writer components (a primary database, a single-leader queue) scale up first. Splitting them is the expensive last resort the sharding lesson describes.
  • Stateless compute prefers many units, because each failure costs a smaller share. But not too small. Every instance has fixed overhead: runtime memory, sidecars, agents, connections to the database. Ten tiny servers can waste more than three medium ones.
  • Per-instance caches and JIT warm-up push toward fewer, larger units, because each unit warms once and sees more of the traffic.
  • Failure-domain math pushes the other way. With three zones, at least three units, and often six, so one zone loss leaves enough.

A sensible middle: medium-to-large units, sized so one unit is no more than about 10% to 20% of fleet capacity once the fleet is big enough to allow it.

Deep Dive: Design-Review Checklist

  1. Which of the four dimensions is saturated (cores, memory, storage I/O, network)? Show the metric, per core where it matters.
  2. Can the software use the new hardware? Is any hot path single-threaded or behind one lock?
  3. What scaling efficiency do we expect, and where does it come from: a load test on the target size, or an assumption?
  4. Does the target size cross a NUMA boundary, and have we benchmarked it?
  5. Which config values must change with the size (buffer pool, heap, pools, worker counts), and are they in the same change?
  6. How many months of runway does this buy at the measured growth rate, and what is the next step when it runs out?
  7. How is the resize performed: in place, or build beside and switch? What happens if the new size cannot start?
  8. Is any data on ephemeral instance storage? Where is its copy?
  9. What is the availability target, and can a single machine meet it, counting resizes, patching and one host failure a year?
  10. What else shares this host, and what stops one workload from killing another?
  11. Are we on a burstable or "up to" tier for a sustained load?
  12. What work is scheduled during the runway to make horizontal scaling possible (statelessness, shard key, read replicas)?

Deep Dive: Senior Interview Follow-ups

"We doubled the cores and throughput went up 10%. What happened?"

Either the bottleneck was not CPU, or the work does not parallelise. Check per-core CPU first: one pinned core means a single-threaded path. If all cores are busy but throughput is flat, it is contention or coherency, the σ and κ terms of the Universal Scalability Law. Lock waits, a hot row, a single log writer or cross-socket traffic on a NUMA box. A profile showing time in spinlocks or waiting on locks confirms it. The fix is to reduce the serial part, not to buy more cores. Past the USL peak, more cores make it slower.

"Isn't the cloud price per vCPU linear? Then where is the 'steep curve'?"

Within a general-purpose family, close to linear, yes. The steepness is in cost per unit of work. If 64 cores deliver 11% more than 32 cores, the effective price per request rose about 80% even though the per-core price did not move. Add the specialised high-memory tiers, per-core software licences and thinner capacity at the top of a catalog. On-prem, the sticker price itself bends upward for top-bin and multi-socket parts.

"How would you resize a primary database with minimal downtime?"

Resize a replica, not the primary. Bring up a replica on the larger instance, or resize an existing one, and let it catch up. Warm its cache if you can. Then do a controlled failover: stop writes briefly or wait for lag to reach zero, promote the replica, repoint clients through DNS or a proxy. The old primary becomes a replica, which is also the rollback path. Downtime is the failover, seconds to a minute or two, and clients need retry logic for the reconnect. Rehearse it on staging first and time it.

"The working set is 300 GB and the biggest box has 256 GB. Now what?"

First check whether it really has to be in memory. A 95% hit ratio may be acceptable if the misses go to fast local NVMe. Then cut the working set: archive cold rows, drop unused indexes, use partial indexes, compress. If it still does not fit, move the excess somewhere else. Read replicas can serve different query types, so each caches a different subset. A cache can sit in front. Or shard, so each shard's working set fits its own RAM. Look at memory-optimised families too, since general-purpose catalogs top out well below them.

"Three small servers or one big one, same total capacity, for a stateless API?"

Three, mostly for availability. One failure leaves two-thirds instead of zero. But check the fixed cost per instance. If each instance carries a 2 GB runtime, agents, a sidecar and 20 database connections, many tiny units waste memory and multiply downstream connections. And size so N−1 survivors can carry peak. Three servers at 70% each cannot absorb one loss, because two would need to run at 105%. Either run them cooler or run four.

"When does vertical scaling make availability worse?"

When it concentrates more onto fewer failure domains. Consolidating services onto one big host turns a reporting bug into a checkout outage. A larger node in a small cluster means losing one node loses a bigger share. Resizes themselves are planned outages. And a larger heap or buffer pool can lengthen recovery: longer GC pauses, longer crash recovery, longer cache warm-up after a restart. Bigger units should come with stronger isolation and a rehearsed failover.

"How do you decide that it's time to stop scaling up?"

Set the exit condition in advance, in numbers. For example: the next size up buys less than six months at measured growth. Or the measured scaling efficiency of the next step is under 60%. Or the availability target rises above what one machine can meet. Any one of those triggers the move to horizontal or sharding. The point is to decide the threshold while you have runway, so the migration starts with a year left, not a week.

"Redis is at 100% CPU on a 4-core box. Do you move it to 16 cores?"

Not before checking which core. Redis executes commands on one main thread, so "100%" on a 4-core box is often one core pinned. More cores will not speed up command execution. I/O threads can offload network reads and writes, which helps when many clients send small commands. Beyond that, look for expensive commands in SLOWLOG (a KEYS or big SMEMBERS can dominate), then split the keyspace across several instances or Redis Cluster. That is horizontal scaling, done for a single-threaded engine.
