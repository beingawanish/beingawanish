Deep Dive: Inside the Mechanism

The lesson reduces read-through to one idea: the cache owns the miss path. That is true, but "the cache" can mean very different things. It might be a library inside each server's memory, a framework layer in your ORM, a separate service your team runs, or a managed product. These differ in where the loader runs, how far coalescing reaches, and what happens when the cache itself is the thing that breaks.

The loader contract

Every read-through implementation asks you for the same thing: a function from key to value. The details of that contract decide most of the behaviour.

  • Load one. load(key) returns the value, or signals "not found", or throws. The cache stores the result and hands it to every waiting caller.
  • Load many. Most libraries also accept a bulk loader, loadAll(keys). Without it, a page that asks for 50 products triggers 50 single-row queries on a cold cache. With it, the cache can turn those misses into one WHERE id IN (…).
  • Not found. Libraries differ here, and it matters. In Caffeine, a loader that returns null means "store nothing", so the next caller loads again. If you want to remember absence, return an explicit empty value, such as an Optional, and give it a short lifetime.
  • Errors. A loader that throws usually stores nothing. Every waiting caller gets the exception, and the next caller tries again. That is usually right, but see the failure modes for what it does under a database outage.

A typical Caffeine configuration looks like this:

LoadingCache<Long, Optional<Product>> products = Caffeine.newBuilder()
    .maximumSize(100_000)                       // bound memory per server
    .expireAfterWrite(Duration.ofMinutes(10))   // hard limit on staleness
    .refreshAfterWrite(Duration.ofMinutes(1))   // reload hot keys in the background
    .recordStats()                              // hit ratio, load time, load failures
    .build(new CacheLoader<>() {
        public Optional<Product> load(Long id) {
            return productRepo.findById(id);    // empty Optional = cached "not found"
        }
        public Map<Long, Optional<Product>> loadAll(Set<? extends Long> ids) {
            return productRepo.findAllById(ids);  // one IN query for a batch of misses
        }
    });

The JCache standard (JSR-107) expresses the same idea with configuration: setReadThrough(true) plus a CacheLoader factory. Ehcache, Hazelcast and other JCache providers then call your loader on a miss. Hazelcast's own API calls the loader a MapLoader, and it runs on the cluster member that owns the key.

How coalescing actually works

Coalescing is the main reason to choose read-through, so it is worth knowing what happens inside.

A loading cache keeps a map from key to either a value or an in-progress load. When a caller misses, the cache atomically installs a placeholder for that key and runs the loader. A second caller for the same key finds the placeholder and waits on it, instead of starting its own load. When the load finishes, every waiter gets the same result.

Caffeine's synchronous cache does this with per-key atomic computation on top of a concurrent hash map: the first thread computes, and the others block until it finishes. Its asynchronous cache stores a future in the map instead. Waiters then attach to the future and do not block a thread at all. Go's singleflight package does the same job as a standalone tool: concurrent calls with the same key share one execution and one result. Spring's @Cacheable does not coalesce by default. Setting sync = true adds per-key locking, within one JVM.

The key phrase is "within one process". A library cache coalesces only the callers in its own memory. Forty servers with their own Caffeine caches send up to forty loads for one hot key, one each. That is still far better than 600, but it is not one.

Getting to one load across the fleet takes one of two designs.

  • Route each key to an owner. groupcache, written by Brad Fitzpatrick for use at Google, hashes each key to one peer in the fleet. Every server asks the owner, and the owner coalesces with singleflight. One load per key per fleet, by design. groupcache deliberately has no expiry or invalidation; it suits immutable data like versioned blobs.
  • A distributed lock around the load. The first server to miss takes a short lock in the shared cache, for example SET lock:product:8412 <token> NX PX 5000. Others see the lock and either wait briefly and re-read, or serve a stale value if one exists. This is the bridge to Cache Stampede Prevention.

Expire versus refresh

A loading cache usually offers two clocks, and confusing them causes real outages.

  • Expire (expireAfterWrite) removes the entry. The next caller blocks on a fresh load. This is a hard upper bound on staleness.
  • Refresh (refreshAfterWrite) marks the entry as due. The next caller still gets the current value immediately, and a reload runs in the background. If the reload fails, Caffeine keeps the old value and logs the error.

Refresh removes blocking misses on hot keys entirely, because nobody ever waits for a load. Two details are easy to miss. Refresh is triggered by a read, so a key that nobody reads is never refreshed; it just sits there until it expires or is evicted. And because a failed refresh keeps the old value, refresh without expire can serve the same stale value for as long as the database is unhappy, possibly days. Use both: refresh at the freshness you want, expire at the staleness you can tolerate.

Eviction inside a library cache

An in-process cache has a hard memory budget: the server's heap. Caffeine evicts with an algorithm called W-TinyLFU. New entries land in a small "window" area. To move into the main area, a candidate must beat the entry it would replace on estimated access frequency. Caffeine tracks frequency in a compact probabilistic sketch rather than a counter per key. The effect is that a one-off scan of cold keys cannot flush the hot set, which plain LRU allows. Guava's cache uses an LRU-like policy per segment, and generally gets lower hit ratios on skewed workloads.

ORM caches and managed read-through

Hibernate's second-level cache sits under the ORM's session. It has separate regions for entities, collections and query results, each with a concurrency strategy. READ_ONLY is for data that never changes. NONSTRICT_READ_WRITE allows short staleness. READ_WRITE uses soft locks so a reader does not cache a row that a transaction is changing. The entity cache behaves well. The query cache is subtler: Hibernate invalidates every cached query result touching a table whenever that table is written through Hibernate. On a table with steady writes, the query cache hit ratio collapses, and it costs more than it saves.

DynamoDB Accelerator (DAX) is a managed read-through and write-through cache in front of DynamoDB. The client talks to DAX with the DynamoDB API. DAX keeps an item cache for GetItem and BatchGetItem and a separate query cache for Query and Scan. Each has a TTL, five minutes by default. Writes through DAX update the item cache, but they do not update the query cache, so a query can return results older than the item you just wrote. Strongly consistent reads skip the cache and go to DynamoDB. And writes made directly to DynamoDB, not through DAX, are invisible to DAX until its entries expire.

A loader must not call its own cache

One more mechanical rule. A loader for key A must not read key B from the same loading cache. Inside a per-key atomic computation, a nested computation on the same map can deadlock or fail. Caffeine documents this; the underlying Java map can throw IllegalStateException with "Recursive update". If loading a product needs its seller, load the seller from a different cache, or directly from the database inside the loader.

Deep Dive: Sizing and the Numbers

The running numbers: the bookstore fleet has 40 application servers, the catalog has 2,000,000 products of about 2 KB each, and a database load takes 15 ms on a calm day.

What coalescing saves, and at what scope

Take a hot key at 20,000 reads per second across the fleet. That is 500 per second on each of 40 servers. The key expires, and its reload takes L seconds. During that window, requests keep arriving.

DesignLoads per expiry, L = 15 msLoads per expiry, L = 500 ms (database stressed)

Refresh-ahead on a hot key0 blocking loads; 1 background load per server per refreshSame; callers keep getting the old value

The right-hand column is what matters. Uncoordinated misses scale with load time, and load time grows exactly when the database is struggling. That is a feedback loop: slower database, more duplicate queries, slower database. Coalescing breaks the loop, because the number of loads stops depending on load time.

The cost of waiting

Coalesced callers do not query the database, but they do wait. By Little's law, the number of callers waiting at once equals the arrival rate times the wait. Per server, for that 500-per-second key:

  • Normal load time, 15 ms: 500 × 0.015 ≈ 8 waiting requests. Harmless.
  • Database in trouble, 2 s per load: 500 × 2 = 1,000 waiting requests. With a synchronous cache, each one holds a thread. A server with a 200-thread request pool is now stuck, and every other endpoint on it stops too.

That is why a synchronous loading cache needs a timeout on the loader that is shorter than the caller's own deadline, and why high-traffic services prefer the asynchronous form. Waiting on a future costs memory, not a thread. Refresh-ahead avoids the problem for hot keys, because nobody waits at all.

Memory per server, and the fleet multiplier

A local cache of the 100,000 hottest products holds 100,000 × 2 KB = 200 MB of serialised data. Deserialised objects on a JVM are often larger than their serialised bytes, frequently by 1.5–3×, so budget 300–600 MB of heap per server. Measure it with a heap dump. That memory also adds work for the garbage collector, because a large, long-lived cache lives in the old generation and gets rescanned.

Multiply by the fleet: 40 servers × 200 MB = 8 GB of data, all duplicates. Background refresh multiplies too. Suppose 10,000 hot keys refresh every 60 seconds:

  • One shared cache: 10,000 / 60 ≈ 170 loads per second.
  • Forty local caches refreshing independently: 40 × 170 ≈ 6,700 loads per second.

The second number is more than half of the bookstore's original 12,000 reads per second, created by the cache itself. Local read-through scales its load with fleet size. A two-tier design fixes this: the local cache's loader reads from a shared cache, and only the shared tier talks to the database.

Cold starts on every deploy

Local caches start empty on every restart. A rolling deploy of 40 servers, five at a time, restarts each batch cold. If each server's working set is the 100,000 hot products and its own hit rate is 1,500 reads per second, a cold server sends most of its 1,500 reads to the database for its first few minutes. Five cold servers send around 7,500 per second. Coalescing does not help much here, because these are different keys, not one hot one. Bulk loading, a warm-up step before the server takes traffic, or a shared L2 tier underneath all reduce the hit.

A managed example: what DAX saves in read capacity

DynamoDB charges reads in read capacity units. One eventually consistent read of an item up to 4 KB costs half a unit. The bookstore's 12,000 product reads per second of 2 KB items cost 12,000 × 0.5 = 6,000 units per second. Behind a read-through cache with a 99% hit ratio, DynamoDB sees 120 reads per second: 60 units. The cache cluster has its own cost, priced per node-hour, so the saving depends on your read rate and hit ratio. Run this calculation with current prices before assuming the cache pays for itself.

Deep Dive: Failure Modes in Production

1. One slow query fails 600 requests

Symptom. Error rate spikes in sharp bursts. Each burst is hundreds of timeouts for the same product at the same moment, followed by quiet.

Mechanism. Coalescing means shared fate. One loader call hit a slow query plan or a lock, and took 3 seconds. Every caller attached to that load waited for it, and all of them crossed their 1-second deadline together. When they retried, the retries found no value and started a new load, which joined the same slow query.

Detect. Loader latency and loader failures as metrics (Caffeine's recordStats() gives load time and load failure counts). Timeouts grouped by cache key in traces.

Fix. Bound the loader with a timeout shorter than the callers' deadline. Serve the previous value on load failure where staleness is acceptable (refresh-ahead does this for you). And use jittered backoff on retries, so a burst of failures does not become a burst of retries; see Retry with Exponential Backoff.

2. The cache tier went down, and took the data with it

Symptom. A shared read-through cache service is redeployed or loses a node. Every product read fails, even though the database is healthy.

Mechanism. With cache-aside, a dead cache means slow but correct reads, because the application can still go to the database. With a read-through service, the application has no path to the database. The cache is the only door. Its availability is now the data's availability.

Detect. This one is found in design review or in a game day, before production does it for you. Ask: "if this service returns 503 for ten minutes, what do product pages show?"

Fix. Run the read-through tier with the same availability standards as the database: several replicas, spread across zones, deployed gradually. Or give clients a fallback path that reads the database directly, rate-limited, when the cache tier is unreachable. That fallback is cache-aside in an emergency, and it needs its own capacity plan.

3. The price that never updated

Symptom. A product shows a price from four days ago on some servers. Restarting the server fixes it.

Mechanism. The cache used refreshAfterWrite without expireAfterWrite. A schema change broke the loader for a subset of products, so every refresh failed. On a failed refresh, the cache keeps the old value. Nothing ever forced the entry out, so it was served for days, with errors only in a log nobody watched.

Detect. Alert on loader failure rate, not just on request errors. Export entry age, or the age of the value's updated_at, for sampled keys.

Fix. Always pair refresh with an expire that is the true staleness limit. Treat repeated refresh failures as an alert.

4. The missing-key storm

Symptom. Database queries per second double. Cache hit ratio drops. The new queries all return zero rows.

Mechanism. The loader returns null for missing products, and the library treats null as "store nothing". A crawler walking through product IDs, or a stale link from a partner feed, hits non-existent keys over and over. Each one becomes a load. Coalescing only helps when the same missing key is requested concurrently.

Detect. Loader calls that return empty, as a separate counter. Miss ratio split by "found" and "not found".

Fix. Return an explicit empty value and cache it briefly (seconds to a minute). Some managed caches do this for you; DAX, for example, caches negative GetItem results. For huge ID spaces, check a Bloom filter of valid IDs before loading.

5. Autoscaling made the database busier

Symptom. Traffic rises, the autoscaler doubles the fleet from 40 to 80 servers, and database load rises faster than traffic did. Page latency gets worse after scaling out.

Mechanism. Each new server starts with an empty local cache and misses heavily for its first minutes. Background refresh also doubles, because each server refreshes its own hot keys. Per-process coalescing limits duplicate loads to one per server, so doubling servers doubles the load floor.

Detect. Database queries per second plotted against fleet size. Per-server hit ratio by server age; new servers stand out.

Fix. Put a shared tier under the local caches, so new servers warm from Redis instead of the database. Warm new servers before they enter the load balancer. Count database load per server in the capacity model, not only per request.

6. The price that changes on every refresh of the page

Symptom. A customer reloads a product page and sees $45, then $40, then $45. Support cannot reproduce it.

Mechanism. Each server's local cache loaded the product at a different time. After a price change, some servers hold the new value and others hold the old one until they expire or refresh. The load balancer sends each request to a different server, so the customer sees each server's version in turn.

Detect. Sampled comparison of the same key across servers. Customer reports that mention "flickering" are a strong hint.

Fix. Broadcast invalidations to every server (pub/sub, or Redis client-side tracking), and keep local TTLs short as a backstop for missed messages. For data where flip-flopping is unacceptable, skip the local tier and read only from a shared cache. Sticky routing per user hides the symptom but does not fix it.

7. The query cache that either lies or never hits

Symptom. Two opposite reports from two teams. On Hibernate, the query cache shows a hit ratio near zero and adds latency. On DAX, a listing query returns a product that was deleted minutes ago.

Mechanism. Caching a query result is harder than caching an item, because any write might change it. Hibernate chose correctness: any write to a table invalidates every cached query on that table, so a table with steady writes keeps its query cache empty. DAX chose speed: writes update the item cache but not the query cache, so query results stay until their TTL.

Detect. Per-region hit ratios (Hibernate's statistics expose them). For DAX, compare query results against strongly consistent reads in a canary.

Fix. Cache items, not queries, wherever you can. Cache the list of IDs a query returns with a short TTL, then read each item through the item cache. If you do cache queries, use them only on tables that rarely change, or with TTLs short enough that the staleness is acceptable.

The first choice is about scope. If one service reads the data, an in-process loading cache with refresh is cheap and very fast. If many services read it, a shared tier stops each from reinventing the loader. The lesson's forty-service catalog is the classic case.

The second choice is about failure. A library or ORM cache degrades to the database when it is empty. A separate service does not, unless you build that path. Choose a separate service only if you are ready to run it like a database.

A good default for hot, read-mostly data: refresh at the freshness you would like, expire at the staleness you can tolerate, and invalidate on write if the data's owner can publish change events.

Synchronous or asynchronous loading

A synchronous cache blocks a thread per waiting caller. It is simple and fine for low-concurrency services or fast loaders. An asynchronous cache returns a future and lets waiters attach without blocking, which is safer under a slow database. Choose async when the service handles high concurrency on a thread-per-request model, or when the loader calls a network service that can stall. Choose sync when the code is simpler that way and the waiter math in the sizing section stays small.

Deep Dive: Design-Review Checklist

  1. Where does the loader run: in each process, in a shared tier, or in a managed service? What is the coalescing scope as a result?
  2. If the cache tier is unavailable, what do callers do? Is there a fallback path to the database, and can the database handle it?
  3. Does the loader have a timeout shorter than the callers' deadlines? What happens to all the waiters when one load fails?
  4. Is there an expire time on every entry, separate from any refresh interval, so a failing loader cannot serve stale data forever?
  5. How is "not found" represented and cached, and for how long?
  6. Is there a bulk loader, so a page with 50 misses makes one query, not 50?
  7. For local caches: how much heap per server, how many duplicate copies across the fleet, and what refresh load does the fleet generate in total?
  8. How do writes reach the cache: invalidation from the write path, change events, or TTL only? Where is that written down?
  9. If several servers hold local copies, can a user see different values on consecutive requests? Is that acceptable for this data?
  10. Does any loader read from its own cache, directly or indirectly?
  11. Are query results cached, or only items? If queries, how are they invalidated?
  12. Which metrics exist: hit ratio, load time, load failures, eviction count, entry age, waiters per key?

Deep Dive: Senior Interview Follow-ups

"You said read-through coalesces misses. Across 40 servers, how many database queries happen when a hot key expires?"

With an in-process loading cache, up to 40: one per server that sees a request during the load. That is coalescing per process, not per fleet. To get one load per fleet, either route each key to an owner peer that coalesces for everyone (the groupcache design), or take a short lock in the shared cache so only the first server loads while others wait or serve the stale value. Refresh-ahead also helps: hot keys reload in the background, so no caller blocks at all.

"Coalescing sounds strictly better. What does it cost?"

Shared fate. Every waiter depends on one load. If that load is slow, all of them are slow; if it fails, all of them fail together. With a synchronous cache, each waiter also holds a thread, so a 2-second load at 500 requests per second ties up about 1,000 threads on one server. So the loader needs a timeout below the callers' deadline, failures should fall back to the previous value where possible, and high-concurrency services should use the async form.

"What's the difference between refreshAfterWrite and expireAfterWrite, and why would you set both?"

Expire removes the entry, so the next caller blocks on a load. Refresh keeps serving the current value and reloads in the background on the next read after the interval. Refresh alone has no staleness bound: a failing loader leaves the old value in place indefinitely, and a key that is never read is never refreshed. Setting both gives non-blocking reads for hot keys and a hard limit on how old any value can be.

"Your company builds a shared read-through product cache service for 40 teams. What's the biggest risk?"

That it becomes the single point of failure for product data. With cache-aside, a cache outage means slow reads; with a read-through service, it means no reads, because clients have no direct path to the database. It needs database-grade availability: replicas across zones, careful rollouts, load shedding. And either clients get a rate-limited fallback to the database or the team accepts that the service's SLO caps every consumer's SLO. The second risk is coupling: the service now owns query logic and schema knowledge for data other teams write.

"Does read-through give you read-your-writes consistency?"

Not by itself. Read-through only defines the miss path. If a user saves a change and the write goes straight to the database, the cache still holds the old value until it is invalidated or expires, so the user's next read can show the old data. You get read-your-writes by invalidating on write, by pairing it with write-through so the write updates the cache, or by routing that user's next read past the cache. With local caches on many servers, invalidation must reach every server, or the user can land on one that has not heard.

"A loader for products needs the seller's name. Can it call sellers.get() on the same cache?"

Not on the same loading cache. The product load runs inside a per-key atomic computation, and starting another computation on the same map from inside it can deadlock or throw. Load the seller from a separate cache, or fetch it in the same database query. It is also worth asking whether the seller's name belongs inside the cached product at all, since a change to the seller then requires invalidating every product they sell.

"When would you turn off the Hibernate query cache?"

On any table with steady writes. Hibernate invalidates every cached query result for a table whenever that table changes through it, so writes keep the query cache nearly empty while you still pay to store and check it. Keep the entity cache, which invalidates per row. If a list query is hot, cache the list of IDs with a short TTL and fetch each entity through the entity cache.

"When does read-through stop being worth it compared to a cache-aside helper?"

When the cached thing is not a single entity by key: a dashboard composed from three databases, a personalised feed, a search result. A per-key loader cannot express those naturally. It also stops paying off when there is one small service, since a helper function already centralises the code, or when your cache is a plain shared store with nowhere to run a loader. Read-through earns its keep at organisational scale, on hot entity reads, where one implementation and coalescing protect a shared database.
