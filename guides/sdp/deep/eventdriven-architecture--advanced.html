Deep Dive: Orchestrating Order → Payment → Inventory → Fulfilment → Shipping

The first deep dive gave the rule: orchestrate the steps that depend on each other, and choreograph the reactions that don't. This part builds the order workflow that rule points at. One order, five services, every message named and keyed, and every failure branch walked through. The aim is a design you could hand to five teams on Monday.

The running example is the bookstore again. Customer c_91 places order ord_7f3a: three books, $142.00, shipping to Austin.

Commands and events: two kinds of message, two naming rules

A workflow needs both kinds of message, and mixing them up is the most common design error in event-driven systems. They differ in who decides.

A command asks one specific service to do something. It is named in the imperative: AuthorizePayment, ReserveStock, CreateShipment. It has exactly one intended handler, the service that owns that capability. And it can be refused. Payment may answer "declined", and that is a normal outcome, not an error.

An event records something that already happened. It is named in the past tense: PaymentAuthorized, StockReserved, ShipmentDispatched. The publisher does not know or care who listens. Nobody can refuse it, because it is already true.

The naming is not cosmetic. A past-tense name on a message that is really an instruction (SendReceiptRequested, say) hides a dependency. The publisher expects a specific consumer to act, so it is a command dressed as an event. When that consumer is down, the publisher's workflow silently stalls, and nobody owns the timeout.

PropertyCommandEvent
GrammarImperative: ReserveStockPast tense: StockReserved

Who owns the schemaThe receiver (it defines what it accepts)The publisher (it defines what it states)

Notice the schema-ownership row. It decides where a command's schema lives. ReserveStock belongs to inventory, which publishes it in its own contract: "send me this and I will reserve". The orchestrator is a client of that contract, in the same way an HTTP client is a client of an API.

A good test in review: read each message name aloud and ask "who decided?" If the sender decided what must happen, it's a command. If the sender is reporting what did happen, it's an event.

Who holds the workflow: orchestrator, choreography, and the hybrid

The order workflow has every property that pushes toward orchestration. Inventory should not reserve stock for an order whose payment failed. A late failure must undo earlier steps in reverse order. And customer support needs to answer "where is order ord_7f3a?" right now, not by reading five services.

So something owns the workflow's state. That something is called a process manager (the enterprise-integration term) or an orchestrator. It holds one record per order: the current step, what has been done, what must be undone if things go wrong, and when the current step is overdue. It reacts to events and sends commands. It contains no business rules about payments or stock. Those stay in the services that own them.

Pure choreography would wire the same steps as a chain of subscriptions: payment listens for OrderPlaced, inventory listens for PaymentAuthorized, and so on. It works on the happy path and gets awkward fast. Inventory now needs to know that a payment authorization is the trigger for reservation, which is order-workflow knowledge leaking into the stock service. Compensation needs every service to listen for every later failure. And the "where is it?" question needs a separate process monitor, which is an orchestrator that is not allowed to act.

The shape most companies land on is a hybrid, and it is worth stating precisely:

  • The spine is orchestrated. Payment, inventory, fulfilment and shipping are steps of one saga. The orchestrator sends them commands and listens for their outcome events.
  • Every step still publishes domain events. PaymentAuthorized goes to payment.events, where the orchestrator is just one subscriber.
  • Everything else is choreographed. Email, analytics, loyalty, the fraud model and the search index subscribe to those event topics. The orchestrator never hears of them, and adding a sixth reaction needs no change to the workflow.
  • The orchestrator publishes its own events too. OrderConfirmed, OrderCancelled and OrderShipped are facts about the order as a whole. Most downstream consumers want these, not the step events.

The line between the two halves is one question: if this consumer did nothing, would the order be wrong? If yes, it is a step and belongs to the orchestrator. If the order would be fine but someone would miss a receipt, it is a reaction and should be choreographed.

Three ways to build the orchestrator

"Use an orchestrator" still leaves the build choice. There are three common answers, and they differ mostly in where the workflow state lives and who writes the timer code.

A durable workflow engine such as Temporal (or Cadence, the Uber project it grew out of). You write the workflow as ordinary code: call authorize_payment, then reserve_stock, wrap them in try/except for compensation, and sleep for a deadline. The engine records every step's result in an event history. If the worker crashes, another worker replays that history through the same code and continues from the same point. This is why workflow code must be deterministic: no wall-clock reads, random numbers or direct I/O outside the engine's APIs. Activities (the steps that touch the outside world) are retried by the engine with policies you configure. The engine owns timers, so a seven-day deadline is one line of code.

A database-backed state machine. The orchestrator is a normal service with a saga table, an outbox and an inbox. Each incoming event loads the saga row, checks the transition is legal, updates the row, and writes the next command to the outbox, all in one transaction. Timers are a deadline_at column scanned by a small poller. Nothing is magic, so everything is visible in SQL. You also write everything yourself, including the bugs in the timer scanner.

A managed state-machine service such as AWS Step Functions or a BPMN engine like Camunda. The workflow is a declared graph (JSON or a diagram) rather than code. These fit well when the steps are mostly calls to other managed services and the team wants the console view for free. Long-running waits on external events need a callback-token style integration, which is more ceremony than a Temporal signal.

ConcernDurable workflow engineDB-backed state machineManaged state machine

A sensible default: if the company already runs a workflow engine, use it. If not, and there are only one or two sagas, a DB-backed state machine is less to operate and easier for new engineers to read. Move to an engine when the third or fourth long-running workflow arrives, or the first one that needs waits measured in days. The rest of this section uses the DB-backed version, because it shows every moving part. A Temporal workflow does the same things with less code you can see.

Topic design, keys and ordering

The message plan below uses Kafka terms. The same shape works on most log-based brokers.

Four decisions sit inside that table.

Separate command and event topics per service. Commands are private traffic between the orchestrator and one service. Events are public. Mixing them on one topic forces every event subscriber to skip commands, and it tempts other teams to send commands they have no business sending. Separate topics also let you give them different retention and access control: only the orchestrator may write payment.commands.

Key everything in the workflow by order_id. Kafka orders records only within a partition, and the key picks the partition. Keying every command and event about one order by its ID puts them in one partition per topic. So payment will see AuthorizePayment before VoidAuthorization for the same order, and the orchestrator will see PaymentAuthorized before PaymentCaptured.

That guarantee is narrower than it sounds. It holds within one topic. Across topics there is no order at all. The orchestrator might read StockReserved (from inventory.events) before an earlier PaymentAuthorized (from payment.events), if the two topics' consumers run at different speeds. A correct orchestrator never relies on cross-topic arrival order. It checks each incoming event against the saga's state, and an event that arrives "early" is either handled or held, never assumed impossible. In the design here the orchestrator sends one command at a time, so a step's reply cannot really overtake the previous step's reply. Parallel steps are where this bites.

Watch for services whose natural key is something else. Inventory thinks in SKUs and warehouses. Its own stock-level events (StockLevelChanged) should be keyed by SKU, so that every change to one SKU's count is ordered. Its replies to the order workflow should be keyed by order_id. Those are different facts about different entities, so they go on different topics or at least carry different keys. Forcing one key onto both breaks one of the two orderings.

Size the partitions for the slowest step. Ordering per key is bought with parallelism limited by partition count, and per-key serial processing. If the warehouse adapter takes 200 ms per command (it calls an external warehouse system), one consumer thread handles 5 commands per second per partition. At 300 orders per second you need at least 60-way parallelism on fulfilment.commands: more partitions, or a consumer that processes different keys within a partition concurrently while keeping each key serial. The Partitioned Consumption lesson covers the second technique.

Correlation, causation, and the saga state table

Every message in the workflow carries three identifiers in its envelope, plus its own ID:

  • message_id: unique per message, assigned once when the message is written to the outbox. This is the dedup key.
  • correlation_id: the same for every message in this order's workflow. Use the saga ID (here, the order ID with a prefix) so a single search returns the whole story.
  • causation_id: the message_id of the message that directly caused this one. ReserveStock's causation ID is the PaymentAuthorized event that triggered it. Following causation links rebuilds the workflow as a tree, including retries and compensations.
  • traceparent: the W3C trace context, so the hops appear in distributed tracing.

The correlation ID answers "everything about this order". The causation ID answers "why did this message exist?" You need both. When a refund goes out twice, correlation finds the 40 messages for that order. Causation shows that both RefundPayment commands trace back to the same ShipmentFailed event, which points straight at a non-idempotent compensation handler.

The orchestrator's state lives in one table:

CREATE TABLE order_saga (
  saga_id          text PRIMARY KEY,          -- 'saga_ord_7f3a'
  order_id         text NOT NULL UNIQUE,
  state            text NOT NULL,             -- AWAITING_PAYMENT, AWAITING_STOCK, ...
  version          bigint NOT NULL,           -- optimistic concurrency
  payment_auth_id  text,                      -- filled as steps complete
  reservation_id   text,
  fulfilment_id    text,
  shipment_id      text,
  compensations    jsonb NOT NULL DEFAULT '[]',  -- stack of undo actions owed
  attempt          int NOT NULL DEFAULT 0,    -- retries of the current step
  step_deadline_at timestamptz,               -- when the current step is overdue
  saga_deadline_at timestamptz NOT NULL,      -- when the whole order must be resolved
  last_message_id  text,                      -- causation for the next command
  created_at       timestamptz NOT NULL,
  updated_at       timestamptz NOT NULL
);
CREATE INDEX order_saga_due ON order_saga (step_deadline_at)
  WHERE state NOT IN ('COMPLETED', 'CANCELLED', 'FAILED');

CREATE TABLE inbox (                          -- one row per handled message
  consumer    text NOT NULL,
  message_id  text NOT NULL,
  handled_at  timestamptz NOT NULL,
  PRIMARY KEY (consumer, message_id)
);

Handling one event is one database transaction with four parts:

  1. Insert the message ID into inbox. A primary-key conflict means it was already handled: commit nothing and acknowledge.
  2. Load the saga row FOR UPDATE (or compare version on update). Check that the event is legal in the current state. StockReserved while in AWAITING_PAYMENT is not, so it is logged and parked for investigation.
  3. Update the saga row: the new state, the new step deadline, and a push onto the compensation stack if the step created something that must be undone later.
  4. Insert the next command into the outbox, with causation_id set to the incoming event's ID.

Commit, then acknowledge the broker offset. A crash anywhere before the commit means the event is redelivered and the whole thing runs again. A crash after the commit but before the ack means it is redelivered and step 1 stops it. That is exactly-once effect on the orchestrator's state, built from at-least-once delivery, without any broker transaction.

The compensation stack deserves a word. Undo actions are recorded as the steps succeed, not derived at failure time. When payment is authorized, the orchestrator pushes VoidAuthorization(auth_id). When capture succeeds, it replaces that with RefundPayment(capture_id). When stock is reserved, it pushes ReleaseStock(reservation_id). On failure, the orchestrator pops and sends them in reverse order. Recording them up front means the failure path cannot forget a step that the happy path added last month.

Timeouts, deadlines and compensations

Every step needs a timeout, and the whole saga needs a deadline. They protect against different things.

A step timeout covers a lost or slow reply: the command went out and nothing came back. For a step that should take milliseconds, like a stock reservation, a timeout of 30 seconds to a few minutes is generous. On expiry the orchestrator does not assume failure. It retries the command (with the same message_id semantics underneath, so the handler's idempotency absorbs it) a bounded number of times with backoff. Only then does it escalate.

A saga deadline covers a workflow that keeps making slow progress, or keeps waiting on something external. "Every order is either shipped or cancelled within 72 hours" is a business rule. It belongs in the saga row as a timestamp, so a scanner can find orders that are about to break it.

Some deadlines are imposed from outside, and they should drive the design. A card authorization is a hold, and holds expire. Card networks and issuers set how long an authorization stays valid, and it varies by network, card type and merchant category, from a few days to a few weeks. If fulfilment can take longer than that, the workflow needs a branch that re-authorizes before capture, or it must capture earlier. Treat the authorization's expiry as a deadline field, filled from the payment provider's response rather than hard-coded.

When a step does fail, the decision is between three moves:

  • Retry, when the failure is transient (a timeout, a 503, a broker hiccup) and the step is idempotent.
  • Compensate, when the failure is a business answer (declined, out of stock) or retries are exhausted. Pop the compensation stack and run it backwards.
  • Escalate to a human, when compensation itself fails or the outcome is ambiguous. A refund that the provider keeps rejecting is not something to retry forever. The saga moves to NEEDS_ATTENTION, and a ticket opens with the correlation ID.

Compensations are commands like any other. They need idempotency, timeouts and retries too. And they are semantic undos, not rollbacks. A refund is a new movement of money that the customer sees on their statement. A void before capture is invisible to most customers. That difference is the reason step order matters, which the next part shows.

Choosing the step order: where to put the point of no return

The saga literature calls the step after which you can no longer undo cleanly the pivot. Steps before it are compensatable. Steps after it must be retried until they succeed. A good order pushes cheap, reversible steps early and the expensive, irreversible ones late.

In this workflow, the irreversible-ish actions are capturing money (undo means a visible refund) and handing a parcel to a carrier (undo means an interception or a return). So the order below authorizes payment first, which is cheap to void. It reserves stock, which is cheap to release. It lets the warehouse pick and pack. Only then does it capture, and finally it books the shipment.

The reader's original sequence put payment before inventory, and that is fine with authorization instead of capture. If your payment provider or market does not support separate authorization and capture, the first row is what you get. Then the out-of-stock branch below becomes a refund, and you should reserve stock first.

Two fields carry real weight. The deadline tells payment not to start work that the orchestrator has already given up on. A command that sat in a backlog for 10 minutes should be dropped with a payment.authorize_expired reply, not executed. The idempotency_key is built from the saga, the step and the attempt generation, not from the message ID. A retry of the same step reuses the same key, so the payment provider collapses duplicates. A deliberate re-authorization later (after expiry, say) bumps the generation to :2 and gets a new key.

  }
}

The orchestrator moves to AWAITING_STOCK, pushes VoidAuthorization(auth_5521) onto the compensation stack, and sends ReserveStock with the order lines. Inventory reserves (decrementing available stock, recording a reservation with its own TTL as a safety net) and replies StockReserved with a reservation_id. The orchestrator pushes ReleaseStock and sends RequestFulfilment.

Fulfilment is the slow step. A warehouse management system works in minutes or hours, not milliseconds. The adapter acknowledges quickly with FulfilmentAccepted, and the orchestrator resets its step deadline to the warehouse's service level, say 8 hours. Later the warehouse reports FulfilmentPacked with parcel weight and dimensions. Now the orchestrator sends CapturePayment. On PaymentCaptured it swaps the stack entry VoidAuthorization for RefundPayment(capture_id), sends CreateShipment, and on ShipmentDispatched marks the saga COMPLETED and publishes order.shipped.v1 to order.events.

The orchestrator also publishes an order.status_changed event at every state change. That one event feeds the "where is my order?" page, the support console and the stuck-order dashboard. None of them needs to know the saga's internals.

Failure branches

The happy path is the easy 95%. The design is judged on four branches.

Branch 1: payment declined. Payment replies with an event, not an error:

{ "type": "payment.declined.v1", "causation_id": "cmd_01J8QF2C",
  "data": { "order_id": "ord_7f3a", "reason": "insufficient_funds", "retryable": false } }

The compensation stack is empty, because nothing succeeded yet. The orchestrator moves to CANCELLED and publishes order.cancelled.v1 with reason: payment_declined. Email sends the "please update your card" message by choreography. Two details matter. First, the provider's decline code decides retryable. A soft decline (a provider outage, a "try again" code) should go through bounded retries. A hard decline must not be retried, and repeated attempts on a declined card can attract scheme penalties. Second, some businesses give the customer a window to fix the card. That is a AWAITING_CUSTOMER state with its own deadline, not a retry loop.

Branch 2: out of stock after payment. Payment is authorized. Inventory replies StockUnavailable for bk_sre. Perhaps the last two copies sold in the same second, or the stock count was simply wrong. The orchestrator now has a business choice, and it belongs in a product decision, not an engineer's default:

  • Cancel the order. Pop the stack: send VoidAuthorization(auth_5521), wait for AuthorizationVoided, publish order.cancelled.v1 with reason: out_of_stock.
  • Partially fulfil. Reserve what is available, then send AdjustAuthorization (or capture only the smaller amount later). This needs a payment provider that supports partial capture, and a customer-facing policy.
  • Backorder. Move to AWAITING_RESTOCK with a deadline before the authorization expires. Listen for StockReplenished for that SKU. On the deadline, cancel or re-authorize.

Whatever the choice, the void is idempotent at the provider (keyed by auth_5521), and a void that fails after retries sends the saga to NEEDS_ATTENTION. Money held on a customer's card with no order behind it is a support call waiting to happen, so it gets a page, not a log line. If the payment had been captured already, the same branch would send RefundPayment, which is why the step order put capture late.

Branch 3: the warehouse times out. RequestFulfilment went out, FulfilmentAccepted came back, and then nothing for 8 hours. This is the dangerous branch, because the outcome is ambiguous. The warehouse may have lost the request. It may have packed the parcel and failed to tell anyone. Or the event may be sitting in a backlog behind a broken consumer.

The wrong move is to compensate straight away. Releasing the stock and voiding the payment for a parcel that is already on a truck turns a delay into a loss. The right sequence is:

  1. Ask before acting. Send QueryFulfilmentStatus, or call the warehouse adapter's status API directly. Timeouts are where synchronous reads to the owner earn their place.
  2. If the warehouse says "never heard of it", resend RequestFulfilment with the same fulfilment idempotency key. The warehouse adapter must dedupe on that key, so a late original and the resend cannot create two pick lists.
  3. If it says "in progress", extend the step deadline once, record why, and alert if it slips again.
  4. If it cannot answer at all, retry the query with backoff until the saga deadline approaches. Then escalate to NEEDS_ATTENTION. A human checking the warehouse floor is cheaper than an automated compensation that might be wrong.

One more trap: the late reply. Suppose the orchestrator gave up and cancelled, and then FulfilmentPacked arrives. The saga is in CANCELLED, where that event is not a legal transition. The handler must not drop it silently. A packed parcel for a cancelled order needs action: return it to stock and record the reason. So "event in an unexpected state" is a first-class path with its own handling and an alert, never a pass.

Branch 4: duplicate delivery. The orchestrator's consumer crashed after committing the saga update for PaymentAuthorized but before committing its Kafka offset. On restart it reads PaymentAuthorized again. Three layers stop the duplicate from doing damage:

  1. The inbox insert of evt_01J8QF3K conflicts. The handler acknowledges and does nothing.
  2. Even without the inbox, the saga is now in AWAITING_STOCK, where PaymentAuthorized is not a legal transition. The state check rejects it.
  3. Even if the orchestrator somehow sent ReserveStock twice, inventory dedupes on its own inbox, and its reservation is keyed by (order_id, line), so a second reserve for the same order is a no-op returning the same reservation_id.

Defence in depth is not paranoia here. Each layer catches a different bug. The inbox catches redelivery. The state check catches redelivery after inbox rows were cleaned up, and replays. Downstream idempotency catches bugs in the orchestrator itself. The Idempotency lesson covers the handler side in general, and the Saga lesson covers compensation semantics.

For completeness, here is the orchestrator's handler in the DB-backed style, using Python's standard-library sqlite3 to keep it self-contained. A production version would use Postgres and SELECT ... FOR UPDATE, but the shape is identical.

import json, sqlite3, uuid

TRANSITIONS = {   # (state, event type) -> (next state, command to send, undo to push)
    ("AWAITING_PAYMENT", "payment.authorized.v1"): ("AWAITING_STOCK", "inventory.reserve.v1", "payment.void.v1"),
    ("AWAITING_STOCK",   "stock.reserved.v1"):     ("AWAITING_PACK",  "fulfilment.request.v1", "inventory.release.v1"),
    # ... the rest of the happy path, plus the failure transitions
}

def handle(db: sqlite3.Connection, msg: dict) -> None:
    with db:  # one transaction: inbox, saga, outbox
        try:
            db.execute("INSERT INTO inbox VALUES ('orchestrator', ?, datetime('now'))", (msg["message_id"],))
        except sqlite3.IntegrityError:
            return                                    # duplicate: already handled
        row = db.execute("SELECT state, version, compensations FROM order_saga WHERE order_id = ?",
                         (msg["data"]["order_id"],)).fetchone()
        state, version, comps = row
        step = TRANSITIONS.get((state, msg["type"]))
        if step is None:
            park_unexpected(db, msg, state)           # illegal in this state: record and alert
            return
        nxt, command, undo = step
        stack = json.loads(comps) + [{"type": undo, "ref": msg["data"]}]
        updated = db.execute(
            "UPDATE order_saga SET state=?, version=version+1, compensations=?, attempt=0, "
            "step_deadline_at=datetime('now', '+2 minutes'), last_message_id=? "
            "WHERE order_id=? AND version=?",
            (nxt, json.dumps(stack), msg["message_id"], msg["data"]["order_id"], version)).rowcount
        if updated != 1:
            raise RuntimeError("concurrent update; let the broker redeliver")
        db.execute("INSERT INTO outbox (message_id, topic, key, type, causation_id, payload) "
                   "VALUES (?, ?, ?, ?, ?, ?)",
                   ("cmd_" + uuid.uuid4().hex, command.split(".")[0] + ".commands",
                    msg["data"]["order_id"], command, msg["message_id"], json.dumps(msg["data"])))
    # only after commit: acknowledge the broker offset

The transition table is the workflow. Reviewers can read it, tests can enumerate it, and a missing row (an event with no legal transition in some state) shows up as a parked message rather than a silent drop.

Deep Dive: Large Payloads

Sooner or later someone asks to put a 4 MB thing in an event. A scanned invoice, a product's full image set, a model's feature vector, a 3,000-line order from a wholesale customer. The broker refuses, or worse, accepts it and gets slower for everyone. This section covers why the limits exist, what to do instead, and how the alternatives fail.

Broker limits, and why they exist

Every broker caps message size. The exact numbers change between versions and providers, so check current documentation before you design around them. The order of magnitude is stable, though:

BrokerDefault or hard cap (approximate)Notes

The limits are not arbitrary. A broker is built around the assumption that messages are small and many, and large ones break that assumption in five places.

  • Memory per request. Producers batch records in memory, and brokers and consumers allocate fetch buffers sized by configuration. A 50 MB record forces every one of those buffers up, on every client, for one outlier.
  • Replication. Followers copy the leader's log in fetch requests. A huge record makes those fetches slow, which can push followers out of the in-sync set and, with acks=all, slow every producer on the partition.
  • Head-of-line blocking. A partition is consumed in order. One 40 MB record that takes 2 seconds to download and parse delays every small record queued behind it, including ones for other keys.
  • Timeouts. Request and session timeouts are tuned for kilobyte-scale messages. A large message plus a slow network can exceed them, causing retries that resend the same large message, and sometimes consumer-group rebalances.
  • Page cache and retention cost. Brokers serve recent data from the OS page cache. A topic full of multi-megabyte records pushes hot small data out of cache. And every byte is stored times the replication factor for the whole retention period.

So raising the limit is a real option, but it is a trade. A topic that carries 2–5 MB records with its own tuned clients can work fine. Raising the cluster-wide default so one team can send blobs puts the cost on everyone else.

A quick sanity check before deciding: size the topic. At 200 events per second and 3 MB each, the topic ingests 600 MB/s. With replication factor 3, that is 1.8 GB/s of disk writes and replication traffic, and about 155 TB per day before retention. The same events at 3 KB with a claim check cost 1,000 times less on the broker, plus 600 MB/s into object storage. That is still large, but object storage is built for it.

The claim check, done properly

The claim-check pattern stores the large payload in object storage and sends an event that carries a reference to it, like a coat-check ticket. The first deep dive introduced the idea. Here are the details that decide whether it works.

Write order. Upload the object first. Only after the upload succeeds, write the event (through the outbox, as usual). The other order publishes a reference to something that does not exist yet. If the upload fails after the event commits, every consumer hits a missing object. An upload that succeeds with no event behind it is an orphan, which the lifecycle rule cleans up. Orphans cost a little storage. Dangling references cost incidents.

Keys. Two schemes work well.

  • Content-addressed: the key is the SHA-256 of the bytes, for example blobs/sha256/9f/86d0…. Identical payloads dedupe for free, retries of the upload are naturally idempotent, and the key itself proves integrity. The cost is that you cannot tell from a key what owns it, so deletion for privacy needs an index.
  • Entity-addressed: orders/ord_7f3a/invoice/evt_01J8QF2A.pdf. Easy to reason about, easy to delete everything for one customer or order, and easy to scope access by prefix. Include the event ID or a version so a newer payload never overwrites one a slow consumer has yet to read.

Never reuse a key for different bytes. A consumer that fetches "the invoice for this order" and gets a newer one than the event describes has a correctness bug that only shows up under lag.

What the event carries. The reference alone is not enough. Carry what a consumer needs to decide whether to fetch, and to check what it got:

"data": {
  "order_id": "ord_7f3a",
  "invoice": {
    "uri": "s3://bookstore-events-blobs/orders/ord_7f3a/invoice/evt_01J8QF2A.pdf",
    "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "size_bytes": 4194304,
    "content_type": "application/pdf",
    "encryption": "kms:alias/orders-blobs",
    "expires_at": "2027-02-18T00:00:00Z"
  },
  "total_cents": 14200, "currency": "USD", "line_count": 3    // the facts most consumers need, inline
}

The hash catches truncated uploads, the wrong object, and tampering. The size lets a consumer refuse something absurd before downloading it. expires_at tells a replaying consumer up front that the object may be gone, so it can choose a different recovery path.

Encryption and access control. Encrypt at rest with a managed key (on AWS, SSE-KMS with a key dedicated to this data set). Then access needs both bucket permission and key permission, which gives you two independent controls and an audit trail of decrypt calls. Grant each consuming service read access to the prefixes it needs, using its own identity. Avoid putting pre-signed URLs in events: they are bearer tokens that live as long as the topic retains the event, and anyone who can read the topic can use them. If you must pass a pre-signed URL, keep its expiry short and accept that replay will need a fresh one.

Lifecycle and TTL. Set an object lifecycle rule that deletes objects after a period. That period must be longer than three things added together: the topic's retention, the longest replay you might run, and a margin. If order.events keeps 30 days and you replay at most 7 days behind real time, a 45-day lifecycle is reasonable. If the topic is compacted and keeps the latest event per key forever, the object it points to must live as long as that event does. Then a time-based lifecycle is wrong, and deletion has to follow the event (see the GC race below).

Consistency. Amazon S3 has provided strong read-after-write consistency for new objects since late 2020, and Google Cloud Storage and Azure Blob Storage offer strong consistency for object reads too. So a consumer that reads the event after the upload completes will find the object. Older advice about "retry the GET a few times because S3 is eventually consistent" is out of date for these services. Other object stores and caching layers in front of them may behave differently, so check yours.

Chunking, and why it is usually wrong

The other obvious approach is to split a large payload into chunks, send them as separate messages, and reassemble at the consumer. Some systems have done this. LinkedIn's engineers, for example, have spoken publicly about weighing chunking against reference-based approaches for large Kafka messages. It works only under narrow conditions, and the costs are easy to underestimate:

  • Every chunk must land in the same partition, so they share a key. A partition carrying a 200-chunk message is blocked for every other key in it until the last chunk arrives.
  • The consumer must hold reassembly state: which chunks it has, in memory or on disk. A rebalance moves the partition to another instance that has none of that state, so it must either re-read from the first chunk or keep state externally.
  • Offset commits get subtle. You cannot commit past the first chunk until the last one is processed, or a crash loses the half-assembled message.
  • Partial failure is a new state. A producer crash after chunk 37 of 80 leaves a message that will never complete. The consumer needs timeouts and cleanup for it.
  • Compaction and retention break it. Log compaction keeps the latest record per key, which destroys chunk sequences. Time-based retention can delete the first chunks of a message whose last chunks are still retained.
  • Every consumer needs the reassembly logic, in every language the company uses. A claim check needs only an object-store client, which every language already has.

Chunking is defensible when object storage is unavailable or forbidden and the payloads are only a few times the limit. Otherwise, use a claim check.

Compression: the cheap first step

Before any of this, turn on compression. Kafka producers compress whole batches with compression.type set to gzip, snappy, lz4 or zstd. JSON events with repeated field names compress well, often by several times; zstd tends to give the best ratio for reasonable CPU and lz4 the lowest latency. Measure on your own data, because ratios vary a lot.

Two caveats. First, the size checks are applied at different points. In Kafka the broker's limit applies to the record batch as written, which is compressed. The producer's max.request.size check applies to the serialized record before batching, and that check is on the uncompressed size in common client versions. So a record that compresses under the broker limit can still be rejected by the producer. Second, compression helps throughput and storage, not head-of-line blocking or consumer memory: the consumer still decompresses the full record. Compression turns a 1.5 MB problem into a 300 KB non-problem. It does not make a 50 MB payload a good idea.

Encrypted or already-compressed payloads (images, PDFs, ciphertext) do not compress further. If a team encrypts payloads at the field level, compression of those fields does nothing, which is one more reason to keep large blobs out of the event.

Event-carried state, thin events, and fetch-on-read

The lesson framed this as notification versus full state. With large payloads, the decision becomes per field, and there are four options rather than two:

OptionEvent carriesConsumer gets the rest byGood forFailure it invites
Full state inlineEverythingNothing to fetchSmall entities, many consumersSize creep; personal data spread
Key facts + claim checkCommon fields, plus a blob referenceObject storage GETLarge, immutable attachmentsDangling references; access sprawl
Key facts + reference by IDCommon fields, plus an entity IDCalling the owner's APISensitive or rarely needed detailCallback storm if many consumers fetch
Thin notificationID and type onlyCalling the owner's APICache invalidation, low volumeCallback storm; reads newer state than the event

The last row hides a correctness trap worth naming. A thin event says "order 7f3a changed". By the time the consumer calls the API, the order may have changed again. The consumer reads version 5 while processing the event for version 3. For a cache invalidation that is fine, even desirable. For an audit trail it is wrong: you have recorded the wrong facts against the event. So fetch-on-read needs a way to ask for a specific version (GET /orders/ord_7f3a?version=3), or the consumer must accept that it sees the latest state, not the state at the event.

Reference by ID versus snapshot. When an order event mentions the customer, should it carry customer_id or a copy of the customer's name and tier? A reference keeps the event small and avoids copying personal data. It also means the consumer sees the customer as they are now. A snapshot records the customer as they were when the order was placed. For many business facts that is what you want: the shipping address at the time of the order, the price at the time of the order, the loyalty tier that determined the discount. A useful rule: snapshot the values that the fact depends on, and reference everything else.

Designing schemas that stay small

Most oversized events were not designed big. They grew, one "just add it" field at a time. A few habits keep them in check.

  • Set a size budget per event type, and enforce it in CI: serialize a realistic worst-case example and fail the build above, say, 64 KB. Track the p99 size in production as a metric per type.
  • Bound every collection. An order with 3 lines is 2 KB. A wholesale order with 4,000 lines is 2 MB. Decide the maximum in the schema. Above it, switch to a summary event plus a claim check for the line list, or emit per-line events.
  • Don't embed related entities. An order event should not contain the full product records for each line. Carry the SKU and the price that applied. Product details live on the product topic.
  • Use a binary format at volume. Avro and Protobuf drop field names from every record and encode numbers compactly. The registry keeps the schema, so the record does not have to.
  • Prefer IDs and enums over free text. "reason": "out_of_stock", not a paragraph.
  • Keep derivable data out. If total_cents is in the event, the consumer does not need total_dollars_formatted as well.

Costs and failure modes

Dangling references. The event says the invoice is at a key, and the object is not there. Causes: the producer wrote the event before the upload finished; a lifecycle rule shorter than a replay; a manual cleanup; a cross-region consumer reading a bucket that has not replicated yet. Detect with a counter of 404s on claim-check fetches, per producer and per event type. A healthy system has zero. Fix by enforcing upload-before-event in the producer library, lifecycle periods derived from retention, and replication-aware reads in other regions (wait for replication, or read from the source region).

The GC race. A garbage-collection job deletes objects that "nobody needs any more", decided by checking whether the latest event still references them. Meanwhile a consumer is 3 days behind and about to read an older event that points at the deleted object. The fix is to make the deletion condition about consumers, not events: an object can go once its event is older than the slowest consumer group's committed position on every topic that references it, plus margin. Most teams settle for the simpler rule: time-based lifecycle well beyond retention, and accept the storage cost.

Privacy deletion. A deletion request for customer c_91 now covers object storage too. Entity-addressed keys make this a prefix delete. Content-addressed keys need an index from customer to hashes. One technique worth knowing is crypto-shredding: encrypt each customer's blobs with a per-customer key, and delete the key to make every copy unreadable at once, including copies in backups. It is more machinery, but it is often the only practical way to cover retained topics and backups.

Cost shape. Claim checks move cost from broker storage to object storage requests. Object storage is cheap per byte but charges per request, and a fan-out to 10 consumer groups means 10 GETs per event. At 1,000 events per second with 10 consumers, that is 10,000 GETs per second, around 26 billion a month. At typical published request prices that is a five-figure monthly bill, often more than the storage. Check your provider's pricing. If many consumers need the same blob, a shared cache or a consumer that fetches once and republishes the needed fields can be cheaper.

Latency and availability. Every claim-check consumer now depends on object storage being available and fast. Its p99 latency (tens to hundreds of milliseconds) enters the consumer's processing time. And an object-storage outage stops consumers even while the broker is healthy. Consumers should keep processing events that do not need the blob, and retry the ones that do through a retry topic, rather than blocking the partition.
