Deep Dive: Orchestrating Order → Payment → Inventory → Fulfilment → Shipping

The first deep dive gave the rule: orchestrate the steps that depend on each other, and choreograph the reactions that don't. This part builds the order workflow that rule points at. One order, five services, every message named and keyed, and every failure branch walked through. The aim is a design you could hand to five teams on Monday.

The running example is the bookstore again. Customer c_91 places order ord_7f3a: three books, $142.00, shipping to Austin.

Commands and events: two kinds of message, two naming rules

A workflow needs both kinds of message, and mixing them up is the most common design error in event-driven systems. They differ in who decides.

A command asks one specific service to do something. It is named in the imperative: AuthorizePayment, ReserveStock, CreateShipment. It has exactly one intended handler, the service that owns that capability. And it can be refused. Payment may answer "declined", and that is a normal outcome, not an error.

An event records something that already happened. It is named in the past tense: PaymentAuthorized, StockReserved, ShipmentDispatched. The publisher does not know or care who listens. Nobody can refuse it, because it is already true.

The naming is not cosmetic. A past-tense name on a message that is really an instruction (SendReceiptRequested, say) hides a dependency. The publisher expects a specific consumer to act, so it is a command dressed as an event. When that consumer is down, the publisher's workflow silently stalls, and nobody owns the timeout.

Notice the schema-ownership row. It decides where a command's schema lives. ReserveStock belongs to inventory, which publishes it in its own contract: "send me this and I will reserve". The orchestrator is a client of that contract, in the same way an HTTP client is a client of an API.

A good test in review: read each message name aloud and ask "who decided?" If the sender decided what must happen, it's a command. If the sender is reporting what did happen, it's an event.

Who holds the workflow: orchestrator, choreography, and the hybrid

The order workflow has every property that pushes toward orchestration. Inventory should not reserve stock for an order whose payment failed. A late failure must undo earlier steps in reverse order. And customer support needs to answer "where is order ord_7f3a?" right now, not by reading five services.

So something owns the workflow's state. That something is called a process manager (the enterprise-integration term) or an orchestrator. It holds one record per order: the current step, what has been done, what must be undone if things go wrong, and when the current step is overdue. It reacts to events and sends commands. It contains no business rules about payments or stock. Those stay in the services that own them.

Pure choreography would wire the same steps as a chain of subscriptions: payment listens for OrderPlaced, inventory listens for PaymentAuthorized, and so on. It works on the happy path and gets awkward fast. Inventory now needs to know that a payment authorization is the trigger for reservation, which is order-workflow knowledge leaking into the stock service. Compensation needs every service to listen for every later failure. And the "where is it?" question needs a separate process monitor, which is an orchestrator that is not allowed to act.

The shape most companies land on is a hybrid, and it is worth stating precisely:

  • The spine is orchestrated. Payment, inventory, fulfilment and shipping are steps of one saga. The orchestrator sends them commands and listens for their outcome events.
  • Every step still publishes domain events. PaymentAuthorized goes to payment.events, where the orchestrator is just one subscriber.
  • Everything else is choreographed. Email, analytics, loyalty, the fraud model and the search index subscribe to those event topics. The orchestrator never hears of them, and adding a sixth reaction needs no change to the workflow.
  • The orchestrator publishes its own events too. OrderConfirmed, OrderCancelled and OrderShipped are facts about the order as a whole. Most downstream consumers want these, not the step events.

The line between the two halves is one question: if this consumer did nothing, would the order be wrong? If yes, it is a step and belongs to the orchestrator. If the order would be fine but someone would miss a receipt, it is a reaction and should be choreographed.

Three ways to build the orchestrator

"Use an orchestrator" still leaves the build choice. There are three common answers, and they differ mostly in where the workflow state lives and who writes the timer code.

A durable workflow engine such as Temporal (or Cadence, the Uber project it grew out of). You write the workflow as ordinary code: call authorize_payment, then reserve_stock, wrap them in try/except for compensation, and sleep for a deadline. The engine records every step's result in an event history. If the worker crashes, another worker replays that history through the same code and continues from the same point. This is why workflow code must be deterministic: no wall-clock reads, random numbers or direct I/O outside the engine's APIs. Activities (the steps that touch the outside world) are retried by the engine with policies you configure. The engine owns timers, so a seven-day deadline is one line of code.

A database-backed state machine. The orchestrator is a normal service with a saga table, an outbox and an inbox. Each incoming event loads the saga row, checks the transition is legal, updates the row, and writes the next command to the outbox, all in one transaction. Timers are a deadline_at column scanned by a small poller. Nothing is magic, so everything is visible in SQL. You also write everything yourself, including the bugs in the timer scanner.

A managed state-machine service such as AWS Step Functions or a BPMN engine like Camunda. The workflow is a declared graph (JSON or a diagram) rather than code. These fit well when the steps are mostly calls to other managed services and the team wants the console view for free. Long-running waits on external events need a callback-token style integration, which is more ceremony than a Temporal signal.

Four decisions sit inside that table.

Separate command and event topics per service. Commands are private traffic between the orchestrator and one service. Events are public. Mixing them on one topic forces every event subscriber to skip commands, and it tempts other teams to send commands they have no business sending. Separate topics also let you give them different retention and access control: only the orchestrator may write payment.commands.

Key everything in the workflow by order_id. Kafka orders records only within a partition, and the key picks the partition. Keying every command and event about one order by its ID puts them in one partition per topic. So payment will see AuthorizePayment before VoidAuthorization for the same order, and the orchestrator will see PaymentAuthorized before PaymentCaptured.

That guarantee is narrower than it sounds. It holds within one topic. Across topics there is no order at all. The orchestrator might read StockReserved (from inventory.events) before an earlier PaymentAuthorized (from payment.events), if the two topics' consumers run at different speeds. A correct orchestrator never relies on cross-topic arrival order. It checks each incoming event against the saga's state, and an event that arrives "early" is either handled or held, never assumed impossible. In the design here the orchestrator sends one command at a time, so a step's reply cannot really overtake the previous step's reply. Parallel steps are where this bites.

Watch for services whose natural key is something else. Inventory thinks in SKUs and warehouses. Its own stock-level events (StockLevelChanged) should be keyed by SKU, so that every change to one SKU's count is ordered. Its replies to the order workflow should be keyed by order_id. Those are different facts about different entities, so they go on different topics or at least carry different keys. Forcing one key onto both breaks one of the two orderings.

Size the partitions for the slowest step. Ordering per key is bought with parallelism limited by partition count, and per-key serial processing. If the warehouse adapter takes 200 ms per command (it calls an external warehouse system), one consumer thread handles 5 commands per second per partition. At 300 orders per second you need at least 60-way parallelism on fulfilment.commands: more partitions, or a consumer that processes different keys within a partition concurrently while keeping each key serial. The Partitioned Consumption lesson covers the second technique.

Correlation, causation, and the saga state table

Every message in the workflow carries three identifiers in its envelope, plus its own ID:

  • message_id: unique per message, assigned once when the message is written to the outbox. This is the dedup key.
  • correlation_id: the same for every message in this order's workflow. Use the saga ID (here, the order ID with a prefix) so a single search returns the whole story.
  • causation_id: the message_id of the message that directly caused this one. ReserveStock's causation ID is the PaymentAuthorized event that triggered it. Following causation links rebuilds the workflow as a tree, including retries and compensations.
  • traceparent: the W3C trace context, so the hops appear in distributed tracing.

The correlation ID answers "everything about this order". The causation ID answers "why did this message exist?" You need both. When a refund goes out twice, correlation finds the 40 messages for that order. Causation shows that both RefundPayment commands trace back to the same ShipmentFailed event, which points straight at a non-idempotent compensation handler.

The orchestrator's state lives in one table:

CREATE TABLE order_saga (
  saga_id          text PRIMARY KEY,          -- 'saga_ord_7f3a'
  order_id         text NOT NULL UNIQUE,
  state            text NOT NULL,             -- AWAITING_PAYMENT, AWAITING_STOCK, ...
  version          bigint NOT NULL,           -- optimistic concurrency
  payment_auth_id  text,                      -- filled as steps complete
  reservation_id   text,
  fulfilment_id    text,
  shipment_id      text,
  compensations    jsonb NOT NULL DEFAULT '[]',  -- stack of undo actions owed
  attempt          int NOT NULL DEFAULT 0,    -- retries of the current step
  step_deadline_at timestamptz,               -- when the current step is overdue
  saga_deadline_at timestamptz NOT NULL,      -- when the whole order must be resolved
  last_message_id  text,                      -- causation for the next command
  created_at       timestamptz NOT NULL,
  updated_at       timestamptz NOT NULL
);
CREATE INDEX order_saga_due ON order_saga (step_deadline_at)
  WHERE state NOT IN ('COMPLETED', 'CANCELLED', 'FAILED');

CREATE TABLE inbox (                          -- one row per handled message
  consumer    text NOT NULL,
  message_id  text NOT NULL,
  handled_at  timestamptz NOT NULL,
  PRIMARY KEY (consumer, message_id)
);

Handling one event is one database transaction with four parts:

  1. Insert the message ID into inbox. A primary-key conflict means it was already handled: commit nothing and acknowledge.
  2. Load the saga row FOR UPDATE (or compare version on update). Check that the event is legal in the current state. StockReserved while in AWAITING_PAYMENT is not, so it is logged and parked for investigation.
  3. Update the saga row: the new state, the new step deadline, and a push onto the compensation stack if the step created something that must be undone later.
  4. Insert the next command into the outbox, with causation_id set to the incoming event's ID.

Commit, then acknowledge the broker offset. A crash anywhere before the commit means the event is redelivered and the whole thing runs again. A crash after the commit but before the ack means it is redelivered and step 1 stops it. That is exactly-once effect on the orchestrator's state, built from at-least-once delivery, without any broker transaction.

The compensation stack deserves a word. Undo actions are recorded as the steps succeed, not derived at failure time. When payment is authorized, the orchestrator pushes VoidAuthorization(auth_id). When capture succeeds, it replaces that with RefundPayment(capture_id). When stock is reserved, it pushes ReleaseStock(reservation_id). On failure, the orchestrator pops and sends them in reverse order. Recording them up front means the failure path cannot forget a step that the happy path added last month.

Timeouts, deadlines and compensations

Every step needs a timeout, and the whole saga needs a deadline. They protect against different things.

A step timeout covers a lost or slow reply: the command went out and nothing came back. For a step that should take milliseconds, like a stock reservation, a timeout of 30 seconds to a few minutes is generous. On expiry the orchestrator does not assume failure. It retries the command (with the same message_id semantics underneath, so the handler's idempotency absorbs it) a bounded number of times with backoff. Only then does it escalate.

A saga deadline covers a workflow that keeps making slow progress, or keeps waiting on something external. "Every order is either shipped or cancelled within 72 hours" is a business rule. It belongs in the saga row as a timestamp, so a scanner can find orders that are about to break it.

Some deadlines are imposed from outside, and they should drive the design. A card authorization is a hold, and holds expire. Card networks and issuers set how long an authorization stays valid, and it varies by network, card type and merchant category, from a few days to a few weeks. If fulfilment can take longer than that, the workflow needs a branch that re-authorizes before capture, or it must capture earlier. Treat the authorization's expiry as a deadline field, filled from the payment provider's response rather than hard-coded.

When a step does fail, the decision is between three moves:

  • Retry, when the failure is transient (a timeout, a 503, a broker hiccup) and the step is idempotent.
  • Compensate, when the failure is a business answer (declined, out of stock) or retries are exhausted. Pop the compensation stack and run it backwards.
  • Escalate to a human, when compensation itself fails or the outcome is ambiguous. A refund that the provider keeps rejecting is not something to retry forever. The saga moves to NEEDS_ATTENTION, and a ticket opens with the correlation ID.

Compensations are commands like any other. They need idempotency, timeouts and retries too. And they are semantic undos, not rollbacks. A refund is a new movement of money that the customer sees on their statement. A void before capture is invisible to most customers. That difference is the reason step order matters, which the next part shows.

Choosing the step order: where to put the point of no return

The saga literature calls the step after which you can no longer undo cleanly the pivot. Steps before it are compensatable. Steps after it must be retried until they succeed. A good order pushes cheap, reversible steps early and the expensive, irreversible ones late.

In this workflow, the irreversible-ish actions are capturing money (undo means a visible refund) and handing a parcel to a carrier (undo means an interception or a return). So the order below authorizes payment first, which is cheap to void. It reserves stock, which is cheap to release. It lets the warehouse pick and pack. Only then does it capture, and finally it books the shipment.

The orchestrator moves to AWAITING_STOCK, pushes VoidAuthorization(auth_5521) onto the compensation stack, and sends ReserveStock with the order lines. Fulfilment is the slow step. A warehouse management system works in minutes or hours, not milliseconds. The adapter acknowledges quickly with FulfilmentAccepted, and the orchestrator resets its step deadline to the warehouse's service level, say 8 hours. Later the warehouse reports FulfilmentPacked with parcel weight and dimensions. Now the orchestrator sends CapturePayment. On PaymentCaptured it swaps the stack entry VoidAuthorization for RefundPayment(capture_id), sends CreateShipment, and on ShipmentDispatched marks the saga COMPLETED and publishes order.shipped.v1 to order.events.

The orchestrator also publishes an order.status_changed event at every state change. That one event feeds the "where is my order?" page, the support console and the stuck-order dashboard. None of them needs to know the saga's internals.

Failure branches

The happy path is the easy 95%. The design is judged on four branches.

Branch 1: payment declined. Payment replies with an event, not an error:

{ "type": "payment.declined.v1", "causation_id": "cmd_01J8QF2C",
  "data": { "order_id": "ord_7f3a", "reason": "insufficient_funds", "retryable": false } }

The compensation stack is empty, because nothing succeeded yet. The orchestrator moves to CANCELLED and publishes order.cancelled.v1 with reason: payment_declined. Email sends the "please update your card" message by choreography. Two details matter. First, the provider's decline code decides retryable. A soft decline (a provider outage, a "try again" code) should go through bounded retries. A hard decline must not be retried, and repeated attempts on a declined card can attract scheme penalties. Second, some businesses give the customer a window to fix the card. That is a AWAITING_CUSTOMER state with its own deadline, not a retry loop.

Branch 2: out of stock after payment. Payment is authorized. Inventory replies StockUnavailable for bk_sre. Perhaps the last two copies sold in the same second, or the stock count was simply wrong. The orchestrator now has a business choice, and it belongs in a product decision, not an engineer's default:

  • Cancel the order. Pop the stack: send VoidAuthorization(auth_5521), wait for AuthorizationVoided, publish order.cancelled.v1 with reason: out_of_stock.
  • Partially fulfil. Reserve what is available, then send AdjustAuthorization (or capture only the smaller amount later). This needs a payment provider that supports partial capture, and a customer-facing policy.
  • Backorder. Move to AWAITING_RESTOCK with a deadline before the authorization expires. Listen for StockReplenished for that SKU. On the deadline, cancel or re-authorize.

Whatever the choice, the void is idempotent at the provider (keyed by auth_5521), and a void that fails after retries sends the saga to NEEDS_ATTENTION. Money held on a customer's card with no order behind it is a support call waiting to happen, so it gets a page, not a log line. If the payment had been captured already, the same branch would send RefundPayment, which is why the step order put capture late.

Branch 3: the warehouse times out. RequestFulfilment went out, FulfilmentAccepted came back, and then nothing for 8 hours. This is the dangerous branch, because the outcome is ambiguous. The warehouse may have lost the request. It may have packed the parcel and failed to tell anyone. Or the event may be sitting in a backlog behind a broken consumer.

The wrong move is to compensate straight away. Releasing the stock and voiding the payment for a parcel that is already on a truck turns a delay into a loss. The right sequence is:

  1. Ask before acting. Send QueryFulfilmentStatus, or call the warehouse adapter's status API directly. Timeouts are where synchronous reads to the owner earn their place.
  2. If the warehouse says "never heard of it", resend RequestFulfilment with the same fulfilment idempotency key. The warehouse adapter must dedupe on that key, so a late original and the resend cannot create two pick lists.
  3. If it says "in progress", extend the step deadline once, record why, and alert if it slips again.
  4. If it cannot answer at all, retry the query with backoff until the saga deadline approaches. Then escalate to NEEDS_ATTENTION. A human checking the warehouse floor is cheaper than an automated compensation that might be wrong.

One more trap: the late reply. Suppose the orchestrator gave up and cancelled, and then FulfilmentPacked arrives. The saga is in CANCELLED, where that event is not a legal transition. The handler must not drop it silently. A packed parcel for a cancelled order needs action: return it to stock and record the reason. So "event in an unexpected state" is a first-class path with its own handling and an alert, never a pass.

Branch 4: duplicate delivery. The orchestrator's consumer crashed after committing the saga update for PaymentAuthorized but before committing its Kafka offset. On restart it reads PaymentAuthorized again. Three layers stop the duplicate from doing damage:

  1. The inbox insert of evt_01J8QF3K conflicts. The handler acknowledges and does nothing.
  2. Even without the inbox, the saga is now in AWAITING_STOCK, where PaymentAuthorized is not a legal transition. The state check rejects it.
  3. Even if the orchestrator somehow sent ReserveStock twice, inventory dedupes on its own inbox, and its reservation is keyed by (order_id, line), so a second reserve for the same order is a no-op returning the same reservation_id.

Defence in depth is not paranoia here. Each layer catches a different bug. The inbox catches redelivery. The state check catches redelivery after inbox rows were cleaned up, and replays. Downstream idempotency catches bugs in the orchestrator itself. The Idempotency lesson covers the handler side in general, and the Saga lesson covers compensation semantics.

For completeness, here is the orchestrator's handler in the DB-backed style, using Python's standard-library sqlite3 to keep it self-contained. A production version would use Postgres and SELECT ... FOR UPDATE, but the shape is identical.

import json, sqlite3, uuid

TRANSITIONS = {   # (state, event type) -> (next state, command to send, undo to push)
    ("AWAITING_PAYMENT", "payment.authorized.v1"): ("AWAITING_STOCK", "inventory.reserve.v1", "payment.void.v1"),
    ("AWAITING_STOCK",   "stock.reserved.v1"):     ("AWAITING_PACK",  "fulfilment.request.v1", "inventory.release.v1"),
    # ... the rest of the happy path, plus the failure transitions
}

def handle(db: sqlite3.Connection, msg: dict) -> None:
    with db:  # one transaction: inbox, saga, outbox
        try:
            db.execute("INSERT INTO inbox VALUES ('orchestrator', ?, datetime('now'))", (msg["message_id"],))
        except sqlite3.IntegrityError:
            return                                    # duplicate: already handled
        row = db.execute("SELECT state, version, compensations FROM order_saga WHERE order_id = ?",
                         (msg["data"]["order_id"],)).fetchone()
        state, version, comps = row
        step = TRANSITIONS.get((state, msg["type"]))
        if step is None:
            park_unexpected(db, msg, state)           # illegal in this state: record and alert
            return
        nxt, command, undo = step
        stack = json.loads(comps) + [{"type": undo, "ref": msg["data"]}]
        updated = db.execute(
            "UPDATE order_saga SET state=?, version=version+1, compensations=?, attempt=0, "
            "step_deadline_at=datetime('now', '+2 minutes'), last_message_id=? "
            "WHERE order_id=? AND version=?",
            (nxt, json.dumps(stack), msg["message_id"], msg["data"]["order_id"], version)).rowcount
        if updated != 1:
            raise RuntimeError("concurrent update; let the broker redeliver")
        db.execute("INSERT INTO outbox (message_id, topic, key, type, causation_id, payload) "
                   "VALUES (?, ?, ?, ?, ?, ?)",
                   ("cmd_" + uuid.uuid4().hex, command.split(".")[0] + ".commands",
                    msg["data"]["order_id"], command, msg["message_id"], json.dumps(msg["data"])))
    # only after commit: acknowledge the broker offset

The transition table is the workflow. Reviewers can read it, tests can enumerate it, and a missing row (an event with no legal transition in some state) shows up as a parked message rather than a silent drop.

Deep Dive: Large Payloads

Sooner or later someone asks to put a 4 MB thing in an event. A scanned invoice, a product's full image set, a model's feature vector, a 3,000-line order from a wholesale customer. The broker refuses, or worse, accepts it and gets slower for everyone. This section covers why the limits exist, what to do instead, and how the alternatives fail.

Broker limits, and why they exist

Every broker caps message size. The exact numbers change between versions and providers, so check current documentation before you design around them. The order of magnitude is stable, though:

The limits are not arbitrary. A broker is built around the assumption that messages are small and many, and large ones break that assumption in five places.

  • Memory per request. Producers batch records in memory, and brokers and consumers allocate fetch buffers sized by configuration. A 50 MB record forces every one of those buffers up, on every client, for one outlier.
  • Replication. Followers copy the leader's log in fetch requests. A huge record makes those fetches slow, which can push followers out of the in-sync set and, with acks=all, slow every producer on the partition.
  • Head-of-line blocking. A partition is consumed in order. One 40 MB record that takes 2 seconds to download and parse delays every small record queued behind it, including ones for other keys.
  • Timeouts. Request and session timeouts are tuned for kilobyte-scale messages. A large message plus a slow network can exceed them, causing retries that resend the same large message, and sometimes consumer-group rebalances.
  • Page cache and retention cost. Brokers serve recent data from the OS page cache. A topic full of multi-megabyte records pushes hot small data out of cache. And every byte is stored times the replication factor for the whole retention period.

So raising the limit is a real option, but it is a trade. A topic that carries 2–5 MB records with its own tuned clients can work fine. Raising the cluster-wide default so one team can send blobs puts the cost on everyone else.

A quick sanity check before deciding: size the topic. At 200 events per second and 3 MB each, the topic ingests 600 MB/s. With replication factor 3, that is 1.8 GB/s of disk writes and replication traffic, and about 155 TB per day before retention. The same events at 3 KB with a claim check cost 1,000 times less on the broker, plus 600 MB/s into object storage. That is still large, but object storage is built for it.

The claim check, done properly

The claim-check pattern stores the large payload in object storage and sends an event that carries a reference to it, like a coat-check ticket. The first deep dive introduced the idea. Here are the details that decide whether it works.

Write order. Upload the object first. Only after the upload succeeds, write the event (through the outbox, as usual). The other order publishes a reference to something that does not exist yet. If the upload fails after the event commits, every consumer hits a missing object. An upload that succeeds with no event behind it is an orphan, which the lifecycle rule cleans up. Orphans cost a little storage. Dangling references cost incidents.

Keys. Two schemes work well.

  • Content-addressed: the key is the SHA-256 of the bytes, for example blobs/sha256/9f/86d0…. Identical payloads dedupe for free, retries of the upload are naturally idempotent, and the key itself proves integrity. The cost is that you cannot tell from a key what owns it, so deletion for privacy needs an index.
  • Entity-addressed: orders/ord_7f3a/invoice/evt_01J8QF2A.pdf. Easy to reason about, easy to delete everything for one customer or order, and easy to scope access by prefix. Include the event ID or a version so a newer payload never overwrites one a slow consumer has yet to read.

Never reuse a key for different bytes. A consumer that fetches "the invoice for this order" and gets a newer one than the event describes has a correctness bug that only shows up under lag.

What the event carries. The reference alone is not enough. Carry what a consumer needs to decide whether to fetch, and to check what it got:

"data": {
  "order_id": "ord_7f3a",
  "invoice": {
    "uri": "s3://bookstore-events-blobs/orders/ord_7f3a/invoice/evt_01J8QF2A.pdf",
    "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "size_bytes": 4194304,
    "content_type": "application/pdf",
    "encryption": "kms:alias/orders-blobs",
    "expires_at": "2027-02-18T00:00:00Z"
  },
  "total_cents": 14200, "currency": "USD", "line_count": 3    // the facts most consumers need, inline
}

The hash catches truncated uploads, the wrong object, and tampering. The size lets a consumer refuse something absurd before downloading it. expires_at tells a replaying consumer up front that the object may be gone, so it can choose a different recovery path.

Encryption and access control. Encrypt at rest with a managed key (on AWS, SSE-KMS with a key dedicated to this data set). Then access needs both bucket permission and key permission, which gives you two independent controls and an audit trail of decrypt calls. Grant each consuming service read access to the prefixes it needs, using its own identity. Avoid putting pre-signed URLs in events: they are bearer tokens that live as long as the topic retains the event, and anyone who can read the topic can use them. If you must pass a pre-signed URL, keep its expiry short and accept that replay will need a fresh one.

Lifecycle and TTL. Set an object lifecycle rule that deletes objects after a period. That period must be longer than three things added together: the topic's retention, the longest replay you might run, and a margin. If order.events keeps 30 days and you replay at most 7 days behind real time, a 45-day lifecycle is reasonable. If the topic is compacted and keeps the latest event per key forever, the object it points to must live as long as that event does. Then a time-based lifecycle is wrong, and deletion has to follow the event (see the GC race below).

Consistency. Amazon S3 has provided strong read-after-write consistency for new objects since late 2020, and Google Cloud Storage and Azure Blob Storage offer strong consistency for object reads too. So a consumer that reads the event after the upload completes will find the object. Older advice about "retry the GET a few times because S3 is eventually consistent" is out of date for these services. Other object stores and caching layers in front of them may behave differently, so check yours.

Chunking, and why it is usually wrong

The other obvious approach is to split a large payload into chunks, send them as separate messages, and reassemble at the consumer. Some systems have done this. LinkedIn's engineers, for example, have spoken publicly about weighing chunking against reference-based approaches for large Kafka messages. It works only under narrow conditions, and the costs are easy to underestimate:

  • Every chunk must land in the same partition, so they share a key. A partition carrying a 200-chunk message is blocked for every other key in it until the last chunk arrives.
  • The consumer must hold reassembly state: which chunks it has, in memory or on disk. A rebalance moves the partition to another instance that has none of that state, so it must either re-read from the first chunk or keep state externally.
  • Offset commits get subtle. You cannot commit past the first chunk until the last one is processed, or a crash loses the half-assembled message.
  • Partial failure is a new state. A producer crash after chunk 37 of 80 leaves a message that will never complete. The consumer needs timeouts and cleanup for it.
  • Compaction and retention break it. Log compaction keeps the latest record per key, which destroys chunk sequences. Time-based retention can delete the first chunks of a message whose last chunks are still retained.
  • Every consumer needs the reassembly logic, in every language the company uses. A claim check needs only an object-store client, which every language already has.

Chunking is defensible when object storage is unavailable or forbidden and the payloads are only a few times the limit. Otherwise, use a claim check.

Compression: the cheap first step

Before any of this, turn on compression. Kafka producers compress whole batches with compression.type set to gzip, snappy, lz4 or zstd. JSON events with repeated field names compress well, often by several times; zstd tends to give the best ratio for reasonable CPU and lz4 the lowest latency. Measure on your own data, because ratios vary a lot.

Two caveats. First, the size checks are applied at different points. In Kafka the broker's limit applies to the record batch as written, which is compressed. The producer's max.request.size check applies to the serialized record before batching, and that check is on the uncompressed size in common client versions. So a record that compresses under the broker limit can still be rejected by the producer. Second, compression helps throughput and storage, not head-of-line blocking or consumer memory: the consumer still decompresses the full record. Compression turns a 1.5 MB problem into a 300 KB non-problem. It does not make a 50 MB payload a good idea.

Encrypted or already-compressed payloads (images, PDFs, ciphertext) do not compress further. If a team encrypts payloads at the field level, compression of those fields does nothing, which is one more reason to keep large blobs out of the event.

Event-carried state, thin events, and fetch-on-read

The lesson framed this as notification versus full state. With large payloads, the decision becomes per field, and there are four options rather than two:

The last row hides a correctness trap worth naming. A thin event says "order 7f3a changed". By the time the consumer calls the API, the order may have changed again. The consumer reads version 5 while processing the event for version 3. For a cache invalidation that is fine, even desirable. For an audit trail it is wrong: you have recorded the wrong facts against the event. So fetch-on-read needs a way to ask for a specific version (GET /orders/ord_7f3a?version=3), or the consumer must accept that it sees the latest state, not the state at the event.

Reference by ID versus snapshot. When an order event mentions the customer, should it carry customer_id or a copy of the customer's name and tier? A reference keeps the event small and avoids copying personal data. It also means the consumer sees the customer as they are now. A snapshot records the customer as they were when the order was placed. For many business facts that is what you want: the shipping address at the time of the order, the price at the time of the order, the loyalty tier that determined the discount. A useful rule: snapshot the values that the fact depends on, and reference everything else.

Designing schemas that stay small

Most oversized events were not designed big. They grew, one "just add it" field at a time. A few habits keep them in check.

  • Set a size budget per event type, and enforce it in CI: serialize a realistic worst-case example and fail the build above, say, 64 KB. Track the p99 size in production as a metric per type.
  • Bound every collection. An order with 3 lines is 2 KB. A wholesale order with 4,000 lines is 2 MB. Decide the maximum in the schema. Above it, switch to a summary event plus a claim check for the line list, or emit per-line events.
  • Don't embed related entities. An order event should not contain the full product records for each line. Carry the SKU and the price that applied. Product details live on the product topic.
  • Use a binary format at volume. Avro and Protobuf drop field names from every record and encode numbers compactly. The registry keeps the schema, so the record does not have to.
  • Prefer IDs and enums over free text. "reason": "out_of_stock", not a paragraph.
  • Keep derivable data out. If total_cents is in the event, the consumer does not need total_dollars_formatted as well.

Costs and failure modes

Dangling references. The event says the invoice is at a key, and the object is not there. Causes: the producer wrote the event before the upload finished; a lifecycle rule shorter than a replay; a manual cleanup; a cross-region consumer reading a bucket that has not replicated yet. Detect with a counter of 404s on claim-check fetches, per producer and per event type. A healthy system has zero. Fix by enforcing upload-before-event in the producer library, lifecycle periods derived from retention, and replication-aware reads in other regions (wait for replication, or read from the source region).

The GC race. A garbage-collection job deletes objects that "nobody needs any more", decided by checking whether the latest event still references them. Meanwhile a consumer is 3 days behind and about to read an older event that points at the deleted object. The fix is to make the deletion condition about consumers, not events: an object can go once its event is older than the slowest consumer group's committed position on every topic that references it, plus margin. Most teams settle for the simpler rule: time-based lifecycle well beyond retention, and accept the storage cost.

Privacy deletion. A deletion request for customer c_91 now covers object storage too. Entity-addressed keys make this a prefix delete. Content-addressed keys need an index from customer to hashes. One technique worth knowing is crypto-shredding: encrypt each customer's blobs with a per-customer key, and delete the key to make every copy unreadable at once, including copies in backups. It is more machinery, but it is often the only practical way to cover retained topics and backups.

Cost shape. Claim checks move cost from broker storage to object storage requests. Object storage is cheap per byte but charges per request, and a fan-out to 10 consumer groups means 10 GETs per event. At 1,000 events per second with 10 consumers, that is 10,000 GETs per second, around 26 billion a month. At typical published request prices that is a five-figure monthly bill, often more than the storage. Check your provider's pricing. If many consumers need the same blob, a shared cache or a consumer that fetches once and republishes the needed fields can be cheaper.

Latency and availability. Every claim-check consumer now depends on object storage being available and fast. Its p99 latency (tens to hundreds of milliseconds) enters the consumer's processing time. And an object-storage outage stops consumers even while the broker is healthy. Consumers should keep processing events that do not need the blob, and retry the ones that do through a retry topic, rather than blocking the partition.

Transactional outbox and CDC, the operational layer

Part one covered why the outbox exists and how the two relay styles work. What remains is the operational detail that decides whether it is predictable.

Give the outbox row everything the relay needs to route without parsing. A Debezium-style outbox router expects columns like aggregatetype (used to pick the topic), aggregateid (used as the record key) and payload, and can map extra columns to headers. Add columns for traceparent, correlation_id and causation_id, mapped to Kafka headers. Then the relay never needs to understand the payload, and tracing works from the first hop.

Order is per aggregate, and only because of the key. CDC emits changes in commit order for the whole database, but the topic partitions by key. So two events for the same order stay in order (same key, same partition), while events for different orders may interleave. That is the guarantee you want. Don't promise more.

Measure outbox age, not just relay health. The one number that tells you the relay is healthy is the age of the oldest unpublished event. For a polling relay that is a SQL query. For CDC it is the connector's lag (in Debezium, the time since the last event it processed, or the gap between the source position and the slot's confirmed position). Alert when outbox age exceeds the consistency budget, for example 5 seconds.

Plan the snapshot. A new CDC connector, or one recovering from an invalidated replication slot, may take a snapshot of existing rows. For an outbox table that is usually small (rows are deleted quickly), which is one more reason to keep it trimmed. For CDC on business tables, the snapshot can emit millions of synthetic "read" events. Consumers must tolerate them, and you should know how long one takes before you need it.

The inbox and dedupe: three ways to absorb duplicates

Every consumer of an at-least-once stream sees duplicates. Redelivery after a crash, a relay retry, a producer retry, a rebalance mid-batch, a deliberate replay. There are three ways to make that harmless, and they are not interchangeable.

Natural idempotency. Make the operation produce the same result however many times it runs. "Set the order's status to shipped, if the stored version is below 7" is naturally idempotent. "Add 50 loyalty points" is not. Upserts guarded by a per-entity version are the cheapest dedupe there is, because they need no extra table. They also handle replays and reordering. Prefer this wherever the operation can be phrased as "set" rather than "add".

An inbox table in the consumer's own database. Insert the message ID in the same transaction as the business change, as the orchestrator above does. If the insert conflicts, skip. This is exact, because the dedupe record and the effect commit together. Its costs are a write per message and a table that grows. Retention is the real design decision. Keep inbox rows at least as long as a duplicate could plausibly arrive. If you might replay from the start, that means the topic's retention. A shorter window (7 days, say) works if replays always start from a known later offset and the version guard covers anything older.

A dedupe cache such as Redis SET key NX EX 86400. It is fast and keeps the database clean. It is also not transactional with the effect. Set the key and crash before the effect, and the retry is wrongly skipped: a lost message. Do the effect and crash before setting the key, and the retry runs twice. A cache is a good first filter in front of a natural-idempotency or inbox check. On its own it gives "mostly once", and the failures cluster at exactly the moments (crashes, failovers) when you most need correctness.

Which ID to dedupe on also matters. Use the message_id assigned at the source, carried through every hop, never a broker offset. Offsets change when a message is copied to a retry topic, mirrored to another cluster, or replayed into a new topic. An ID that changes on retry defeats the whole point.

Idempotency keys for side effects you don't own

The inbox protects your database. It cannot protect a payment provider, an email service or a carrier's booking API. For those you pass an idempotency key the external system understands. Stripe's API is the well-known example: a client sends an Idempotency-Key header, and the provider returns the stored result of the first request for any retry with the same key within a retention window.

The design question is what the key is made of. Three rules cover most cases.

  1. Derive it from the business intent, not the message. saga_ord_7f3a:capture:1 is the same for every retry of that capture, whichever message carried it. A random UUID generated in the handler is different on every retry, which makes it useless.
  2. Include a generation for deliberate repeats. If the business genuinely wants a second capture (a re-authorization after expiry, a split shipment), it is a new intent with a new key. Bump the generation in the saga state, in the same transaction that decides to repeat.
  3. Keep the key's lifetime inside the provider's window. Providers keep idempotency records for a limited time; check yours. A retry after that window is a new request. For long-delayed retries, query the provider's state first ("does a capture for this auth already exist?") instead of trusting the key.

When the external system offers no idempotency key, you need a check-then-act with a recorded intent. Write "about to book shipment for ord_7f3a" to your database. Call the carrier with your own reference (most carrier APIs take a customer reference field). On retry, search the carrier for that reference before booking again. That narrows the duplicate window to the carrier's own consistency, which is usually the best you can do.

Schema registry: subjects, multiple types per topic, and versioning

Part one covered compatibility modes. Two practical questions come up as soon as a real system uses a registry.

How are schemas grouped? In Confluent's registry the unit of compatibility is a subject, and a subject name strategy maps each record to one. The default, TopicNameStrategy, uses one subject per topic (order.events-value). That allows only one evolving schema per topic. The order topic above carries order.placed, order.cancelled and order.shipped, which are different shapes. You have two options:

  • RecordNameStrategy or TopicRecordNameStrategy: one subject per record type (optionally per topic). Each type evolves on its own, and many types share a topic. This is the natural fit for an entity topic carrying its whole lifecycle.
  • One schema that is a union (Avro) or a oneof (Protobuf) of every event type, under the default strategy. Adding a new type is a compatible change to the union. This keeps one subject per topic, at the cost of one big schema.

Keeping a whole entity's lifecycle on one topic matters more than the registry's convenience, because it keeps per-key ordering across event types. Choose the strategy to fit the topic design, not the other way round.

Where does the version live? The registry versions schemas automatically, on every compatible change. Those versions are for machines. The version in the event type name (order.placed.v1) is for people, and should change only on a breaking change. When it does, the new type gets a new subject and the dual-publish migration from part one applies. Treat the registry's numbers as an implementation detail, and the name's major version as the contract.

Gate the registry from CI, not by hand. The producer's build should run the compatibility check against the target environment's registry and fail before merge. Most registries expose a "test compatibility" endpoint for exactly this. Turn off automatic schema registration in production producers, so a schema reaches the registry only through the pipeline.

Consumer contract tests

A registry checks the shape. A contract test checks what a specific consumer actually relies on. With consumer-driven contracts (Pact is the common tool, and it supports message contracts, not just HTTP), each consumer team writes down the messages it expects: "an order.placed with total_cents as an integer and currency as a three-letter code". The tool turns that into a contract file. The producer's build verifies its real serializer against every consumer's contract. If checkout's change would break loyalty's expectations, checkout's build fails, before anyone deploys.

Three things make them worth the effort:

  • Test the important consumers, not all of them. Contracts for payment, finance and the orchestrator; registry checks for the long tail.
  • Encode meaning where you can. Contracts can assert value ranges and formats (an amount in cents is an integer below a sane maximum). That catches some of the semantic breaks a registry cannot, like the dollars-to-cents change from part one.
  • Make "can I deploy?" a pipeline step. A contract broker records which versions verified against which. The deploy step asks whether this producer version is compatible with the consumer versions currently in production.

Retry topics and dead-letter queues, with backoff

A consumer that fails on one message has three bad options if it has only one topic. Retry forever, and the partition stops. Skip it, and the message is lost. Crash, and the whole consumer group rebalances around it. Retry topics give it a fourth option: move the message aside, keep going, and come back to it later.

Uber's engineering blog described this design for Kafka in a widely read 2018 post on reliable reprocessing: a chain of retry topics with increasing delays, ending in a dead-letter topic. Many frameworks now ship it, including Spring Kafka's non-blocking retries. The mechanics:

  • Classify the error first. A deserialization failure, a schema violation or a business-rule rejection will fail every time. Send it straight to the DLQ. A timeout, a 503 or a lock conflict may succeed later. Send it to the first retry tier.
  • Implement the delay by pausing, not sleeping. Each retry message records when it becomes due. The retry consumer reads one, sees it is not due yet, and pauses that partition until it is (Kafka consumers have pause and resume). Messages in one retry topic all have the same delay, so they become due in the order they arrived. That is why tiers have fixed delays rather than one topic with variable ones.
  • Copy everything forward. The retry record keeps the original key, payload and headers (message_id, traceparent, correlation and causation), and adds the attempt count, original topic, partition and offset, and the last error. A DLQ entry without the original offset and error is a mystery to whoever opens it.
  • Add jitter at the source of the failure. If a downstream dependency was down for 10 minutes, thousands of messages land in retry-1 together and all become due in the same second. Spread them, or rate-limit the retry consumer, so recovery does not knock the dependency over again. The Retry with Exponential Backoff lesson covers the arithmetic.
  • Build the redrive tool before you need it. A DLQ is only useful if someone can inspect messages, fix the cause, and republish them, one at a time or by filter, with the original IDs so consumers still dedupe. Track DLQ depth and age as alerts. A DLQ that only grows is a slow data-loss incident.

The catch: non-blocking retries break per-key order. When order.placed for ord_7f3a goes to retry-1, the main consumer moves on. If order.cancelled for the same order arrives a second later, it is processed first. When the placed event comes back from retry, it can resurrect the order, which is failure mode 5 from part one, now caused by your own retry design. There are three answers:

  1. Make the consumer order-insensitive. Version guards (ignore anything older than the stored version) make a late order.placed harmless. This is the best answer where it applies.
  2. Retry in place for ordering-critical consumers. Retry inside the partition with backoff, blocking it, and accept the stall. The orchestrator and ledger consumers often choose this, with a short bound before escalating to quarantine.
  3. Quarantine the key, not just the message. See the next section.

Poison-message quarantine

A poison message fails every time it is processed. Without handling, it is redelivered forever and the partition stops. With a naive DLQ, it is moved aside, and later messages for the same key are processed as if nothing happened. For an entity stream, that second behaviour can be worse than stopping.

Sequence-preserving quarantine fixes this. When a message for key K is sent to the DLQ, the consumer records K in a "parked keys" table. Every later message for K is parked too, behind it, until someone resolves the first one. Other keys continue normally. On redrive, the parked messages for K are replayed in their original order. You lose availability for one order instead of correctness for one order, or availability for a whole partition.

Quarantine also needs a breaker. If 5% of messages are suddenly going to the DLQ, the problem is not the messages, it is a bad deploy or a broken dependency. Shovelling half a partition into the DLQ makes recovery harder. Stop the consumer when the DLQ rate crosses a threshold, page someone, and roll back.

The Dead-Letter Queue lesson covers DLQ basics. The parts that are specific to event-driven architecture are the per-key parking and the rule that a DLQ'd fact is still a fact that some view has not applied.

Replay and backfill strategy

Replay is the lesson's headline benefit: rebuild a view, or onboard a new consumer, by reading history. It is also how many teams cause their worst incidents. A replay is safe when four questions have good answers.

Which consumer group? Never rewind a live group's offsets to rebuild a view. Start a new group (fraud-view-rebuild-2026-11-21) that writes to a new table. When it has caught up, switch reads to the new table and retire the old group. The live consumer keeps working throughout, and rollback is switching reads back.

From where? From the earliest offset for a full rebuild. From a timestamp (Kafka's offsetsForTimes maps a time to offsets per partition) to repair a known bad window. From a snapshot plus the tail if the topic does not retain enough history. That last one is common: a compacted "latest state per key" topic or a database snapshot gives the starting state, and the live topic supplies the rest. Version guards make the overlap between the two harmless.

What must not happen again? A consumer that sends emails, charges cards or books shipments must not repeat them during replay. The lesson already said to separate state-building consumers from side-effecting ones. Back that up with a mechanism: a replay flag in the consumer's config that disables side effects, and idempotency keys that would catch them anyway. Do not rely on side-effecting consumers "knowing" they are in a replay.

How fast? A replay can read far faster than the view store can write, and faster than a downstream API can absorb if the consumer calls one. Rate-limit it. Part one estimated a 500-million-event rebuild at about 35 minutes with 12 parallel consumers, if the store takes 240,000 writes per second. If it shares that store with production traffic, cap the replay at a fraction of headroom and accept the longer run.

Backfill is different from replay. Replay reads events that exist. Backfill creates events that never existed: publishing history for data that predates the topic, or adding a field to old events. Publish backfills to a separate topic, or mark them with a header, so consumers can treat them differently (no emails for 2019 orders). And make sure a backfilled "old" event cannot overwrite newer live state. The per-entity version guard is again the tool.

Ordering and exactly-once: what you actually get

Claims about ordering and exactly-once are where design documents most often overstate. Here is what the mechanisms really provide in Kafka. Other brokers differ in detail, not in spirit. The Exactly-Once Semantics lesson goes deeper.

Idempotency keys at external systemsExactly-once effect at that system, within its key windowSystems that ignore or expire the key

The honest phrase is effectively once: at-least-once delivery, plus idempotent effects, gives exactly-once results. Every link in the chain needs its own idempotency. When someone says "we use Kafka exactly-once, so the consumer doesn't need to dedupe", ask what the consumer writes to. If it is anything other than Kafka, the claim does not cover it.

Ordering has a similar trap. Kafka's ordering per partition holds for records as written. Producer retries can reorder records unless the producer is idempotent (or limits in-flight requests to one), and consumers that process a partition with a thread pool reorder records unless they keep each key on one thread. Repartitioning a topic (adding partitions) changes which partition most keys map to, so for a while old and new records for one key sit in different partitions. Add partitions with care on ordered topics, or create a new topic and migrate.

End-to-end tracing that survives the broker

Part one explained trace context in headers and span links. Four further details decide whether traces are actually usable.

  • Propagate traceparent and tracestate as message headers, not payload fields. OpenTelemetry's messaging instrumentation for Kafka, RabbitMQ and the cloud brokers reads and writes headers. A trace ID buried in the JSON payload is invisible to it.
  • Use the messaging semantic conventions so every service names spans and attributes the same way: the messaging system, the destination name, the operation (publish, receive, process), the message ID and the consumer group. Then "show me every process span on payment.commands slower than 1 s" works across teams.
  • Decide sampling at the start and honour it downstream. Head sampling records the decision in the traceparent flags. Consumers that respect it keep whole workflows. Consumers that re-sample independently keep random fragments. Tail sampling across asynchronous hops is hard, because the "trace" can take hours to finish. A common compromise is to keep 100% of traces for the orchestrator's workflow messages (low volume, high value), and sample the high-volume analytics paths.
  • Link the saga, not just the hops. The saga takes hours. No tracing backend shows that well as one trace. Give each step its own trace, linked to the previous one, and let the correlation ID tie the whole saga together in logs and in the saga table's history.

The Distributed Tracing lesson covers propagation in general.

Event catalog, AsyncAPI and lineage

Every pattern above assumes you know who produces and consumes each event. In a company with 200 topics, that knowledge has to live somewhere other than people's heads.

AsyncAPI is a specification for describing event-driven interfaces, playing the role for channels and messages that OpenAPI plays for HTTP. A producer's AsyncAPI document lists its channels (topics), the messages on each, their schemas (inline or by reference to the registry), and bindings such as the Kafka key. It can be generated from code or written by hand and checked in CI. A trimmed example:

  orderEvents:

      orderPlaced:

      headers:
        type: object

          traceparent: { type: string }

          $ref: 'registry://order.placed/latest'   # illustrative: point at your registry or a schema file

A catalog sits on top: one page per event type with its owner, schema, AsyncAPI document, data classification (does it contain personal data?), freshness SLO, retention, and its consumers. The consumer list is the part teams forget to keep current. Generate it from reality instead: the broker knows which consumer groups read which topics, and ACLs (access-control lists) know which service identities may. A catalog that merges declared consumers with observed consumer groups, and flags differences, stays honest.

Lineage answers "where did this value come from, and where does it go?" At the topic level, lineage is the graph of services and topics: checkout writes order.events, the orchestrator reads it and writes payment.commands, and so on. It can be drawn from the same producer and consumer metadata. At the record level, lineage is the causation chain: this refund was caused by that event, which was caused by that command. The envelope's causation IDs, logged consistently, give you record-level lineage for free. For data pipelines that land events in a warehouse, OpenLineage is an emerging standard for recording job-level lineage.

SLOs on consumer lag and event age

Consumer lag is the most-watched number in event-driven systems, and on its own it is a poor one. "Lag 120,000" means nothing without the drain rate. At 2,000 records per second it is one minute behind. At 50 per second it is 40 minutes. And a consumer that is completely stuck has constant lag on a quiet topic, which looks healthy.

Measure in time. Two time-based signals cover most needs:

  • Time lag: for each partition, how long ago the oldest unconsumed record was written. Tools such as Burrow, and many managed-Kafka dashboards, estimate it from offsets and timestamps.
  • Event age at processing: in the consumer, record now − occurred_at as a histogram when each event is handled. This is the user-visible delay, end to end, including the outbox and relay. It is the number that belongs in an SLO.

Deep Dive: Industry Use-Case Analysis

The lesson named LinkedIn, Uber, banks and Netflix in a sentence each. This section looks at five organisations that have written publicly, in engineering blogs, conference talks and open-source projects, about how they run event-driven systems. The descriptions summarise those public write-ups. Systems change after a post is published, and companies rarely publish everything, so treat these as accounts of published designs at a point in time, not as current architecture diagrams. Where the details are uncertain, the text says so.

The value is not in copying any of them. It is in noticing that companies with very different products kept arriving at the same few decisions.

Uber: retry topics as a platform, and workflows as code

What they built. Uber has described Kafka as a central piece of its infrastructure, carrying trip, pricing, payment and logging traffic between many services. Two published pieces are directly relevant to this deep dive. The first is the 2018 engineering-blog post on reliable reprocessing and dead-letter queues with Kafka, which described the tiered retry-topic design shown earlier, using a payments-related processing flow as the example. The second is Cadence, a workflow orchestration engine built at Uber and open-sourced. Cadence's original authors later founded Temporal, whose engine started as a fork of Cadence. Uber has also written about a consumer proxy that sits between Kafka and services, pushing messages to them over RPC and handling retries and dead-lettering centrally.

Why. The reprocessing post's argument was the one this deep dive made: a consumer that retries in place blocks its partition, and one that drops failures loses money-relevant events. Tiered retry topics let healthy messages flow while failed ones wait. Cadence came from a different need: long-running business processes, with timers and compensation, that were painful to express as chains of queue consumers.

Trade-offs. Non-blocking retries give up strict per-key order, which is acceptable for some flows and not others. Centralising consumption in a proxy makes retry policy consistent across hundreds of services, and adds a component that every consumer now depends on. A workflow engine makes long processes readable and durable, and imposes determinism rules on workflow code that teams must learn.

Lessons. At scale, retry and dead-letter handling become platform features, not something each team writes. And the company that ran one of the largest Kafka deployments still built an orchestrator for its multi-step processes. Events and workflows are complements.

Netflix: orchestration for media pipelines, CDC to avoid dual writes

What they built. Netflix open-sourced Conductor in 2016, an orchestration engine in which workflows are declared as JSON definitions of tasks, executed by workers that poll for work. Their posts described it coordinating content-processing workflows, such as the steps involved in ingesting and encoding media. Netflix has since stepped back from maintaining the open-source project, and community and commercial forks continue it. Separately, Netflix's engineering blog described Keystone, a Kafka- and Flink-based pipeline that routes event data to many sinks. A later post described Delta, a data-synchronisation platform built on change data capture (using their DBLog CDC framework). Delta keeps stores such as search indexes in step with a source database.

Why. Media workflows are long, branching and expensive to redo. A failed step deep into a multi-hour encode should be retried, not restarted from the top, and operators need a view of where every title is. That is the orchestration case exactly. Delta's write-up, as summarised publicly, was motivated by the dual-write problem: applications writing to a database and to a search index or cache separately, and those copies drifting.

Trade-offs. A central orchestrator becomes critical infrastructure with its own scaling work. JSON workflow definitions are easy to visualise and harder to test than code. CDC removes dual writes from application code, and couples the downstream stream to the database's change log, which needs its own care (the replication-slot failure in part one).

Lessons. The same company used orchestration for its dependent, long-running steps and log-based streaming for data distribution. And "read the database's log instead of writing twice" was a conclusion reached by a team with no shortage of engineering capacity. It is not a workaround for small teams.

Zalando: governance through a platform and published guidelines

What they built. Zalando, a large European online fashion retailer, open-sourced Nakadi, an event bus that put an HTTP API in front of Kafka. Producers register an event type with a schema and a category, and Nakadi validates each published event against its schema before accepting it. Zalando also published its RESTful API and Event Guidelines, a public style guide that includes rules for events. One is to distinguish business events (a process step happened) from data change events (an entity was created, updated or deleted). Others: include standard metadata such as an event ID and occurrence time, evolve schemas compatibly, use partition keys for ordering where it matters, and design consumers to tolerate duplicates and out-of-order delivery.

Why. Zalando's public material describes a large number of autonomous teams. In that setting, governance by review meetings does not scale. A platform that refuses invalid events, plus a written standard every team can point to, does.

Trade-offs. An HTTP front door is easy for any language to use, and adds a hop and some loss of Kafka's client-side features. Schema validation at publish time catches errors early, and makes the platform's validation path part of every producer's critical path. Guidelines are only as good as their enforcement, which is why the platform checks what it can.

Lessons. The business-event versus data-change-event split is the same distinction part one drew between domain events and event-carried state. Zalando made it a required property of every event type. If you adopt one thing, adopt the habit of writing your event rules down and having the platform enforce the mechanical ones.

Stripe: idempotency keys and ledgers for money movement

What they built. Stripe's public API is designed around idempotency. Clients send an Idempotency-Key header on mutating requests, and retries with the same key return the original result. Stripe's engineering blog explained the reasoning in a 2017 post on designing robust and predictable APIs with idempotency. A related, widely cited write-up by the same author showed how to implement Stripe-like idempotency keys in Postgres, splitting a request into atomic phases with recovery points so a retry resumes rather than repeats. That is the saga-state-table idea applied to a single API call. Stripe also exposes an events API and webhooks, retrying webhook delivery over an extended period when the receiver fails. More recently Stripe's blog described an internal ledger system that records money movement as immutable double-entry records and runs automated checks to detect discrepancies. The details of that system are less public than the API design, so take this summary as approximate.

Why. In payments, "retry and hope" is not acceptable. A network timeout on a charge request leaves the client unsure whether money moved. Idempotency keys turn that ambiguity into a safe retry. Immutable ledgers make every balance a derived view of facts, which is the lesson's bank-ledger point, and make discrepancies detectable rather than silent.

Trade-offs. Idempotency keys push work to clients: generating keys correctly, and understanding that keys expire. Immutable ledgers mean corrections are new entries, never edits, which complicates reporting and requires tooling to explain a balance.

Lessons. Two of the patterns in this deep dive, idempotency keys and append-only facts with derived balances, are standard practice where money is involved. The order saga above passes Stripe-style keys to its payment provider for exactly this reason. Reconciliation (independently checking that the facts add up) is a first-class feature, not an afterthought.

DoorDash: from task queues to Kafka, with a workflow engine as a safety net

What they built. DoorDash's engineering blog has described several steps in its asynchronous architecture. One post covered replacing a Celery-on-RabbitMQ task-processing setup with Kafka after a series of outages, and doing the migration without downtime. Another described using Cadence as a fallback for event-driven processing in a delivery-related flow: when the primary event-driven path failed or stalled, a durable workflow ensured the work still completed. DoorDash has also written about Iguazu, its real-time event processing system for moving large volumes of events to analytics and other consumers.

Why. Food delivery has hard real-time constraints. An order that silently stalls means a customer waiting and food going cold. The task-queue migration was framed around reliability and operability at growing volume. The Cadence post, as summarised publicly, addressed exactly the stuck-choreography problem from part one: event chains have no built-in owner for "this should have happened by now".

Trade-offs. Moving from a task queue to a log changes semantics: per-message acknowledgement becomes offset commits, and a slow message can hold up its partition. Running a workflow engine beside an event pipeline adds a second system, in return for guaranteed completion and timeouts.

Lessons. The hybrid shape again: events for throughput and fan-out, a workflow engine for "this must finish". DoorDash's framing of the engine as a fallback is a useful middle path for teams that already have a working choreographed flow and need durability without a rewrite.

Deep Dive: Design-Review Checklist (Workflows, Payloads and Operations)

These questions extend the checklist in part one. They are aimed at a design that coordinates several services through events.

  1. For every message, is it a command or an event, and does its name say so? Who owns each command's schema?
  2. Which steps are orchestrated and which reactions are choreographed? For each choreographed reaction, would the order be wrong if it did nothing? If yes, why is it not a step?
  3. Where does the workflow's state live, and can support answer "where is order X?" from it in one query?
  4. What is the partition key on every topic in the workflow? Does any step rely on order across topics?
  5. Where is the pivot step? Which earlier steps are compensated, which later steps are retried until they succeed, and why is the step order the cheapest one?
  6. Is the compensation stack recorded as steps succeed, or worked out at failure time?
  7. Every step has a timeout and the saga has a deadline. What happens on expiry when the outcome is ambiguous? Who gets paged?
  8. What does each handler do with an event that is illegal in the current state, such as a late reply after cancellation?
  9. What are the idempotency keys for external side effects, what are they derived from, and how long does each provider honour them?
  10. What is the largest event each type can produce, and what enforces the budget? For claim checks: write order, key scheme, hash, encryption, access, and lifecycle relative to retention and replay?
  11. Which consumers retry in place and which use retry topics? For the latter, how is per-key order protected?
  12. When a message is dead-lettered, are later messages for the same key parked? Who owns the DLQ, what is its age alert, and does the redrive tool exist yet?
  13. How is a view rebuilt: which consumer group, which starting point, how are side effects suppressed, and what rate limit protects production?
  14. What are the event-age SLOs per consumer, measured from occurred_at, and are they alerted per partition?
  15. Which game-day drills have been run against this design, and what did they find?

Deep Dive: Senior Follow-ups on Workflows and Operations

"Why authorize first and capture later, instead of just charging the card?"

Because it moves the expensive, customer-visible undo out of the common failure paths. Before capture, cancelling is a void, which usually never appears as a completed charge on the customer's statement. After capture, cancelling is a refund, a new money movement with fees, delay and a support conversation. Authorizing first, reserving stock, and capturing after pick and pack puts the pivot late. The cost is handling authorization expiry for slow fulfilment, and needing a provider and market that support separate authorization and capture.

"Your orchestrator crashes between updating the saga row and publishing the next command. What happens?"

Nothing is lost, because there is no separate publish. The saga update and the command's outbox row commit in one transaction, and the relay publishes the outbox later. If the crash is before commit, neither exists, and the incoming event is redelivered because its offset was not committed. If the crash is after commit but before the offset commit, the redelivered event hits the inbox's primary key and is skipped. The relay may publish the command twice, so the receiving service dedupes on the command's message ID.

"The warehouse has not answered for eight hours. Do you cancel the order?"

Not yet. A timeout means the outcome is unknown, not that the step failed. Compensating could release stock and void payment for a parcel that has already shipped. First ask the warehouse for the status directly. If it never received the request, resend with the same fulfilment key so a late original cannot create a duplicate. If it is in progress, extend the deadline once and record why. If it cannot answer, escalate to a person before the saga deadline. And handle the late reply that arrives after any decision explicitly, never by dropping it.

"Retry topics keep the partition moving. Why wouldn't you use them everywhere?"

Because they break per-key order. While order.placed waits in a retry topic, order.cancelled for the same order can be processed first, and the late retry can resurrect the order. They are safe where handlers are order-insensitive, typically because every write is guarded by a per-entity version. For order-critical consumers such as the orchestrator or a ledger, retry in place with a short bound, then quarantine the whole key so later messages for it wait behind the failed one.

"Someone wants to put 8 MB product media in the product.updated event. What do you say?"

Put the media in object storage and send a claim check: key, SHA-256, size, content type, and the facts most consumers need inline. Upload before publishing, so the event never points at nothing. Use a key per version so a slow consumer never reads newer bytes than its event describes. Encrypt with a dedicated key and grant each consumer read access by identity rather than putting pre-signed URLs in events. Set the lifecycle beyond retention plus the longest replay. Don't chunk it, and don't raise the cluster's message limit for one producer.

"We use Kafka transactions, so we have exactly-once. Do consumers still need idempotency?"

If they write anywhere other than Kafka, yes. Kafka transactions make consumed offsets and produced records commit together, for readers using read_committed. A database write, an email or a payment call sits outside that transaction, and a crash between the side effect and the offset commit repeats it. The real guarantee is effectively-once: at-least-once delivery plus an idempotent effect at every system that is touched, through an inbox, a version guard or an idempotency key.

"How would you rebuild the fraud view without touching production?"

Start a new consumer group writing to a new table, from the earliest offset or from a snapshot plus the topic tail. Version guards make the overlap harmless. Rate-limit it so the view store keeps headroom for live traffic, and run it with side effects disabled by configuration. When it has caught up and its event age matches the live consumer's, switch reads to the new table. Keep the old group and table for a while so rollback is just switching back. Measure the rebuild time, because that is your recovery time objective for this view.

"Consumer lag is 120,000. Is that bad?"

It depends on the drain rate, which is why lag in records is the wrong unit. At 2,000 records per second it is a minute. At 50 per second it is 40 minutes. A stuck consumer on a quiet topic can even show steady, small lag. Measure time instead: time lag per partition, and event age at processing (now minus occurred_at) as a histogram. Set SLOs per consumer according to what staleness costs it, alert on burn rate, and check per partition so one stuck partition cannot hide inside a group average.

"Inventory keys its events by SKU. The orchestrator needs them by order. Who wins?"

Neither, because they are different facts. Stock-level changes are facts about a SKU and need per-SKU order, so they are keyed by SKU on inventory's own topic. Replies to the order workflow (StockReserved, StockUnavailable) are facts about an order's reservation and should be keyed by order ID on the topic the orchestrator reads. Forcing one key onto both breaks one of the two orderings. Inventory publishes both, from the same transaction, through its outbox.

"What would you drill first on a game day for this design?"

Deliver every message twice. It is cheap to build (a wrapper that duplicates a fraction of consumed messages), safe in staging, and it exercises the property everything depends on. Then reconcile: one charge, one reservation, one shipment, one email per order. Next, stop the CDC connector to prove the outbox-age alert fires before the database's disk is at risk, and inject a poison message to check that only its key parks while the partition flows. Each drill should have a written expected outcome, and the finding goes into the backlog with an owner.
