Deep Dive: Inside the Mechanism

The lesson describes MapReduce as two functions plus a framework. This section opens the framework. Most of what makes a batch job fast, slow, correct or quietly wrong happens in four places: how the input is split, what the map side does with its output, how the shuffle moves it, and how results are committed. The names below are Hadoop's, because Hadoop exposed every step as a setting. Spark and the warehouses do the same steps with different names.

Splits, tasks and waves

The framework never sees "2 TB of orders". It sees a list of input splits. A split is a byte range of one file that one map task will read. By default a split is one storage block, and the HDFS block size has been 128 MB since Hadoop 2. On object storage there are no blocks, so the framework picks a split size, usually in the same range.

Each split becomes one map task. The scheduler, which is the ApplicationMaster on YARN, places tasks on machines with free slots. It prefers a machine that holds a replica of the split, then one on the same rack, then anything. That preference is the "move compute to the data" property in practice. On cloud object storage every read crosses the network anyway, so locality means "same region", and the network is the bottleneck you size for.

A cluster rarely has a slot for every task at once. With 8,000 tasks and 3,200 slots, tasks run in waves: about two and a half waves here. Waves matter for two reasons. The job's end time is set by the slowest task of the last wave. And a partial last wave wastes capacity, because most slots sit idle while a few tasks finish.

Line-based formats need one more detail. A split boundary usually lands in the middle of a row. The convention is that each reader skips the partial first line (unless it starts at byte zero) and reads past its end to finish the last line. Every row is then read exactly once. Compressed files that cannot be split, such as a single large gzip file, become one task no matter how big they are. That is a common cause of one task running for an hour.

The map side: buffer, partition, sort, spill

A mapper does not send records over the network as it emits them. It writes them into an in-memory ring buffer, 100 MB by default (mapreduce.task.io.sort.mb). When the buffer is 80% full (mapreduce.map.sort.spill.percent), a background thread spills it to local disk. Each spill does three things in order:

  1. Partition. Every record gets a reducer number, by default hash(key) mod R, where R is the number of reducers. This is the step that decides which reducer owns "electronics".
  2. Sort. Records are sorted by partition, then by key within each partition.
  3. Combine. If a combiner is set, it runs over each sorted run of equal keys before the bytes hit disk.

When the map finishes, its spill files are merged into one sorted, partitioned file plus an index that says where each reducer's segment starts. The merge reads at most 10 files at a time (mapreduce.task.io.sort.factor), so a mapper that spilled 40 times pays for extra merge passes. The combiner may run again during this merge.

That last point is a contract, not an accident. The framework may run the combiner zero, one or many times on any subset of a key's values. A combiner must therefore be associative and commutative, and its output type must match its input type. Summing passes. Averaging does not, which is the lesson's Q1. A combiner that counts how often it ran is wrong in a way no test will catch on small data.

Map output goes to the local disk of the machine that ran the map, not to the distributed file system. This choice saves a replicated write for data that lives only minutes. It also means a machine that dies after its maps finished takes their output with it. The failure modes section comes back to this.

The shuffle, from the reducer's side

Each reducer owns one partition. It learns from the ApplicationMaster which maps have finished and fetches its segment from each one over HTTP, served by a shuffle handler that runs on every node. Five fetches run in parallel by default (mapreduce.reduce.shuffle.parallelcopies). Small segments are merged in memory; larger ones go to the reducer's disk and are merged there.

The count of fetches is the hidden cost. With M map tasks and R reducers, the shuffle is M × R separate transfers. 8,000 maps and 400 reducers is 3.2 million fetches. With combiners, most of those segments are a few hundred bytes. The job is then bound by request overhead and disk seeks, not bandwidth. Too many reducers hurts in a way that never shows up as "bytes shuffled".

Reducers start copying early: by default once 5% of maps have finished (mapreduce.job.reduce.slowstart.completedmaps). But reduce() itself cannot run until every map is done. The last map could still emit a value for any key. That barrier is the structural reason a batch job has a latency floor, and why the slowest map holds up the whole job.

Inside the reducer, values arrive grouped and sorted by key. The framework hands reduce() an iterator, so a reducer that sums values streams through them in constant memory. A reducer that copies values into a list, to sort them or pick the top ten, holds the whole key in memory. That is fine for a normal key and fatal for a hot one.

Committing output: why reruns are safe

The lesson says reruns are safe because tasks are pure. That is half the story. The other half is the output committer. Each task attempt writes into its own temporary directory, such as _temporary/attempt_…_r_000042_1. Only when the framework decides that attempt is the winner does it commit, by renaming the files into place. A losing speculative copy, or a failed attempt, is deleted. When the whole job succeeds, a _SUCCESS marker is written.

So the guarantee is: one committed output per task, no matter how many attempts ran. That only holds for output that goes through the committer. If a map task writes rows to a database or calls an API as a side effect, every attempt does it. Speculative execution then doubles those writes, and a retry triples them.

Object storage complicates the commit. On HDFS a rename is a cheap metadata operation. On S3 a "rename" is a copy and a delete, file by file, and is not atomic. A job that commits 10,000 files by renaming can take a long time at the end and can leave partial output if the driver dies mid-commit. This is why Hadoop added S3-specific committers (the S3A "magic" and staging committers), and why table formats such as Iceberg, Delta Lake and Hudi commit by atomically swapping a metadata pointer instead of moving files.

Who detects failure, and what reruns

  • A map task fails (exception, out of memory, spot reclaim). It is retried, by default up to 4 attempts (mapreduce.map.maxattempts), preferably on another node. After that the job fails, unless the job allows a percentage of failed tasks.
  • A node is lost after its maps finished. The maps succeeded, but their output was on that node's disk. Reducers report fetch failures. Once enough reports arrive, the framework marks those maps as lost and reruns them. This is the most surprising rule in the system: completed work can be undone.
  • A reduce task fails. It reruns and fetches all its segments again. The map outputs are still there, so this is cheap unless the reducer was a hot key that took an hour.
  • The ApplicationMaster fails. YARN restarts it, and it can recover the state of completed tasks from its job history so the job does not start over. In the 2004 Google design the master was a single point of failure, and the paper simply aborted the job if it died.
  • A task is slow. Speculative execution launches a backup copy once the framework sees a task well behind its peers, near the end of a phase. The 2004 paper reported that a sort benchmark took 44% longer with backup tasks disabled.

The same machinery in Spark

Spark keeps the structure and changes the plumbing. A job is a DAG of stages, and a stage boundary is exactly a shuffle: any operation that needs data grouped by key across partitions (groupBy, join, repartition). Within a stage, operations are pipelined in memory with no intermediate files. That is where the 10–100x speedup on multi-step jobs comes from.

At a stage boundary, Spark does what Hadoop did. The upstream tasks write sorted, partitioned shuffle files to local disk, and downstream tasks fetch them. A lost shuffle file causes a FetchFailedException and a rerun of the parent stage's affected tasks, which is lineage recovery in practice. An external shuffle service keeps those files available when an executor exits, which matters for dynamic allocation.

The knobs worth knowing:

  • spark.sql.shuffle.partitions is the R of Spark SQL. It defaults to 200, which is too many for small jobs and far too few for terabyte shuffles.
  • Adaptive query execution (on by default since Spark 3.2) measures shuffle output at runtime. It coalesces tiny partitions, splits skewed join partitions, and can switch a join to a broadcast join once it sees the real sizes.
  • spark.sql.autoBroadcastJoinThreshold (10 MB by default) decides when a small table is copied to every executor instead of shuffled. Broadcast joins skip the shuffle for the big side entirely.
  • spark.speculation is off by default. Turn it on only when your output path is safe against duplicate attempts.

Spark SQL also builds the combiner for you. A SUM … GROUP BY plan shows a partial aggregate before the exchange and a final aggregate after it. Look for that pair in EXPLAIN output. If it is missing, as with some user-defined aggregates, your shuffle is moving raw rows.

The input format matters more than the cluster

The lesson's arithmetic assumes the job reads all 2 TB. A row format such as CSV or JSON forces that. A columnar format such as Parquet or ORC stores each column separately, compressed, with min/max statistics per row group. The revenue query needs two columns, category and amount. If orders have 20 columns of similar width, the job reads about a tenth of the bytes, and dictionary-encoded categories compress far below that.

Two more effects follow. Column pruning skips columns the query never mentions. Predicate pushdown uses those statistics to skip row groups that cannot match a filter, such as WHERE order_date >= '2026-01-01' on data sorted by date. Partitioning the files by date in the directory layout skips whole files. Together these often cut a scan by 10–100x. No amount of extra machines does that.

Deep Dive: Sizing and the Numbers

All numbers here use the lesson's job: 5 billion order rows, 2 TB as stored, 200 machines. Assumptions are stated each time. Swap in your own.

How many tasks, and how big

Assume 256 MB splits. 2 TB / 256 MB ≈ 8,000 map tasks. With 16 task slots per machine, the cluster runs 3,200 at once, so the map phase takes 2.5 waves.

How long is one task? At 100 MB/s per task from object storage, 256 MB takes about 2.5 s to read. That is too short. Per-task overhead (scheduling, starting a JVM in Hadoop, opening the file) is roughly a second or more, so overhead would be a large share of the job. A common target is tasks that run from half a minute to a few minutes. Here that argues for larger splits, around 1–2 GB, which gives 1,000–2,000 tasks.

The opposite limit is failure cost. When a task fails, the work lost averages half a task. A 2-minute task loses about a minute per failure. A 2-hour task loses an hour, and on spot instances that will happen. Choose task size between these two forces:

Shuffle volume, with and without a combiner

Assume each emitted record is about 30 bytes after serialization: a category string plus an amount, plus framing.

  • Without a combiner: 5 × 109 records × 30 B = 150 GB shuffled. Each of 200 machines sends and receives about 750 MB. The bytes are written to map-side disk, read back, sent, written to reducer disk and merged. Expect minutes, not seconds, and heavy disk I/O.
  • With a combiner: each of 2,000 tasks emits one record per category. With 50 categories, that is 2,000 × 50 × 30 B = 3 MB in total. The shuffle disappears as a cost.

The ratio is the number of input rows per distinct key per task. That ratio is huge for "revenue by category" and close to 1 for "revenue by order ID". A combiner helps only when keys repeat within a task. If they do not, it costs CPU and saves nothing.

How many reducers

Size reducers from the shuffle bytes, not the machine count. A workable target is 100 MB to 1 GB of input per reduce task. Spark's AQE defaults aim at about 64 MB per coalesced partition, which leans small.

  • 150 GB without a combiner, at 500 MB each: about 300 reducers.
  • 3 MB with a combiner: one reducer is plenty. Using 400 would create 2,000 × 400 = 800,000 fetches of nearly empty segments.

Output files follow reducers. 400 reducers writing into 30 date partitions can produce 12,000 small files, and the next job pays for them. Plan the output layout at the same time as R.

Skew, in numbers

Take the lesson's Q3 case without a combiner: "electronics" is 40% of the 150 GB, so one reducer receives 60 GB. If a reducer merges and processes about 100 MB/s, that is 600 s of work, while the other 299 reducers finish in about 3 s each. The job's reduce phase is 600 s, set by one task.

Salting splits the key into 16 sub-keys: 60 GB / 16 = 3.75 GB each, about 38 s. A second, tiny stage adds the 16 partial sums. The reduce phase drops from 600 s to about 40 s.

Speculative execution does not help here. A backup copy of the hot reducer gets the same 60 GB and runs just as long. Speculation fixes slow machines, not heavy keys.

Failure arithmetic

Assume each machine fails independently about once a month, which is roughly 1 in 720 per hour. For a 10-minute job on 200 machines, the expected number of failures is 200 × (10 / 60) / 720 ≈ 0.05. Failure is rare at this scale. Run the same cluster for a 6-hour job and it is 200 × 6 / 720 ≈ 1.7 expected failures. Now failure is routine, and the framework's reruns are the difference between finishing and not.

Spot instances change the inputs, not the method. If reclaims run at a few percent of machines per hour, a large cluster loses a machine every few minutes. The job still finishes, but only if tasks are short. Each reclaim costs about half a task's duration for every task that was running on that machine.

Cost, and the single-machine comparison

200 machines for 10 minutes is about 33 machine-hours. At an assumed $0.50 per machine-hour, the run costs around $17, plus a few minutes of cluster startup on both ends.

Now try one large machine. Suppose the 2 TB is Parquet, and the two needed columns are 5% of it: 100 GB. A machine with fast local NVMe or a high-bandwidth link to object storage might scan 2–3 GB/s. That is 35–50 seconds of I/O, and a vectorized engine (DuckDB, Polars, DataFusion) can usually aggregate two columns at that speed. The single machine plausibly wins on time and on cost.

The cluster wins when the bytes you must actually read, after pruning, are many terabytes, or when the job needs a large shuffle that will not fit in one machine's memory and disk. Do the pruning arithmetic first. It decides more architecture reviews than any other number in this lesson.

Deep Dive: Failure Modes in Production

1. The join that stalls at 99%

Symptom. A join of orders to customers reaches 199 of 200 tasks in four minutes. The last task runs for three hours, then fails out of memory. The input data looks healthy.

Mechanism. Guest checkouts have customer_id = NULL, and they are 25% of orders. In a shuffle join, every NULL hashes to the same partition. One reducer receives a quarter of all orders, and the join tries to match them all to each other's side. This is skew, but it hides well: nobody thinks of NULL as a hot key.

Detect. In the Spark UI, the stage's task-duration and shuffle-read distributions show one huge max next to a small median. In Hadoop, one reducer's "reduce input records" counter dwarfs the rest. Then run a quick GROUP BY join_key ORDER BY count DESC LIMIT 10 on the input.

Fix. Filter NULL keys out before the join and union them back afterwards; they cannot match an inner join anyway. For real hot keys, salt them, or broadcast the small side. Spark's AQE skew-join handling splits oversized partitions automatically if it is on and the plan qualifies. Do not rely on that for keys that are a quarter of the data.

2. The job that charged twice

Symptom. A nightly batch sends a "your loyalty points" email from inside a map task. Some customers get two emails, a few get three. The job reports success.

Mechanism. The email is a side effect, outside the output committer. Speculative execution launched backup copies of slow tasks, and a spot reclaim forced a few retries. Every attempt sent its emails. The framework's "rerun is safe" promise covers committed output only. Here the task was not pure, so the promise did not apply.

Detect. Count sends per customer per run in the email provider's logs. In the job history, look for tasks with more than one attempt (speculative or failed) and check whether those customers match.

Fix. Make the batch job produce a file of emails to send, committed like any other output. A separate sender then reads it and deduplicates on (customer, run ID) with an idempotency key. As a rule, a batch job's only side effect should be its committed output.

3. Different answers on a rerun

Symptom. A data-sampling job that keeps "a random 1% of users" produces a training set with some users duplicated and others missing. It happens only on runs where an executor was lost.

Mechanism. The task used an unseeded random number, or a round-robin repartition() whose output depends on the order rows arrive in. When an executor died, Spark recomputed its lost partitions from lineage. The recomputed tasks made different choices than the originals, but downstream tasks had already consumed some of the original output. The result mixes two inconsistent runs. Spark has had real bugs in this area with round-robin repartitioning, and later versions added safeguards; the lesson for your own code still stands.

Detect. Hard after the fact. Check that the job is deterministic: run it twice on the same input and diff the output, including a run where you kill an executor mid-stage. Look for rand(), now(), uuid(), or iteration over unordered collections in task code.

Fix. Derive randomness from the data: sample by hash(user_id) mod 100 = 0, which picks the same users every time. Pass the run's logical time in as a parameter instead of calling now(). Partition by a key, not round-robin, when the downstream result depends on placement.

4. The cascade of fetch failures

Symptom. A 40-minute job takes two hours. The logs fill with fetch failures, map stages rerun repeatedly, and the job sometimes fails at the very end with "too many fetch failures".

Mechanism. One node's local shuffle disk filled up, or the node kept losing its network. Its completed map outputs became unreadable, so reducers reported fetch failures, and the framework reran those maps elsewhere. If the reruns landed back on the bad node, or the node flapped, the cycle repeated. On autoscaled Spark clusters, a similar effect happens when executors are removed while they still hold shuffle files and no external shuffle service keeps them.

Detect. Fetch-failure counts per source host: one host at the top of the list is the tell. Node-level disk usage on the shuffle directories. Stage attempt numbers above 0 in the Spark UI.

Fix. Exclude bad nodes (Spark's exclude-on-failure settings, YARN node health checks with a disk-usage threshold). Give shuffle directories their own disks with headroom. Use an external or remote shuffle service with dynamic allocation. Most of all, reduce what you shuffle, since every byte shuffled is a byte at risk.

5. The report that was missing Tuesday's last hour

Symptom. Monthly revenue is 0.4% below finance's number. Rerunning the job later gives the right answer.

Mechanism. The batch job started at 02:00 and listed the input directory. The upstream export that writes Tuesday's files was still running because it had been delayed. The job read the files that existed at listing time and finished cleanly. Batch frameworks process exactly what they are given. They have no idea that input was incomplete.

Detect. Row counts per input partition compared against the source system's own count. A data-quality check that compares today's totals with a trailing average and alerts on a gap.

Fix. Never start on a directory listing. Start on a completion signal: the upstream job's _SUCCESS marker, an orchestrator dependency (an Airflow sensor, a dbt source freshness check), or a table snapshot ID from Iceberg or Delta that pins exactly which files belong to the input. Record the snapshot ID with the output, so the result is reproducible.

6. The job that is slower on a bigger cluster

Symptom. A job over one day of click logs takes 25 minutes. Doubling the cluster makes no difference. The driver or ApplicationMaster sits at 100% CPU while executors are mostly idle.

Mechanism. The upstream streaming writer flushed a file every few seconds per partition, so one day is 1.5 million files of about 1 MB each. Each file becomes at least one task. Listing them takes minutes on object storage, and scheduling 1.5 million tasks takes longer than processing them. On HDFS, the NameNode holds metadata for every file in memory, so small files also strain the cluster for everyone.

Detect. Average input file size (total bytes divided by file count). Task count far above "data size / 1 GB". Long gaps before the first task starts, which is listing and planning time.

Fix. Compact upstream: a scheduled job that rewrites small files into 256 MB–1 GB files. Table formats such as Iceberg and Delta have built-in compaction operations. Readers can also combine many small files into one split (Spark does this with spark.sql.files.maxPartitionBytes and its file-open cost estimate). And limit the files the writer produces in the first place.

7. The reducer that dies on one customer

Symptom. A "build each customer's full order history" job fails every night with an out-of-memory error, always in the same reduce task, after hours of garbage-collection pauses.

Mechanism. The reducer collects each customer's orders into a list so it can sort them by date. One customer is a reseller account with 30 million orders. The reducer holds all 30 million in memory. Streaming reducers are safe at any key size. Collecting reducers are safe only up to the largest key you will ever see.

Detect. GC time as a share of task time, visible in the Spark UI and in Hadoop task counters. The max-records-per-key from a quick count query.

Fix. Push the sort into the shuffle instead of the reducer. Hadoop's secondary sort uses a composite key (customer, date) with a partitioner and grouping comparator on customer only, so values arrive already sorted. In Spark, a window function or repartition plus sortWithinPartitions does the same. Cap or special-case the outlier keys if the output per key must be bounded.

Hash or range partitioning

Hash partitioning is the default. It spreads keys evenly and needs no knowledge of the data. Its output is sorted only within each partition.

Range partitioning assigns key ranges to reducers, so the concatenated output is globally sorted. The framework must first sample the input to choose boundaries that give each reducer a similar amount of data. Hadoop's TeraSort benchmark works this way, and so does Spark's orderBy. Use it when the output must be globally ordered, such as files sorted by date for fast range reads later. Watch the sample: if it misses a hot range, one reducer gets far more than its share.

Full recompute or incremental

The lesson's job recomputes "all time" from scratch every run. That is simple, and it self-heals, because yesterday's bug disappears on today's run. But the cost grows with history: ten years of data scanned every night to add one day.

The alternative is incremental batch: compute today's partial sums, then merge them into a stored running total. It is cheap, but it no longer self-heals. A bad day is baked in until someone runs a backfill for that date. Late-arriving rows for past days also need a rule: either reprocess the last N days every run, or track which past partitions changed.

A sound middle ground is to partition the output by day, recompute only the days whose input changed, and keep a tested full-rebuild path. That rebuild path is the batch layer of Lambda, so it pays to keep it working.

Deep Dive: Design-Review Checklist

  1. How many bytes must the job read after column pruning and partition filters? Has someone checked whether one machine can do it?
  2. Is the input a columnar format, partitioned by the field most queries filter on? What is the average file size?
  3. What starts the job: a completion marker, an orchestrator dependency, or a table snapshot? Or a clock and a directory listing?
  4. Where is the combiner or partial aggregation? Does EXPLAIN show a partial aggregate before every exchange?
  5. What are the ten largest keys for every group-by and join, including NULL? What happens to the task that gets the largest?
  6. How were the reducer count and output file count chosen? What file sizes will the next job read?
  7. Is every task deterministic? Is there any rand(), now(), or external call whose result can differ on a rerun?
  8. Does any task have a side effect outside the committed output: database writes, emails, API calls? If so, how are duplicate attempts handled?
  9. How is output committed on this storage? Can a reader ever see half of a run's output?
  10. How long is the longest task, and what does one failure of it cost? Is the job on spot capacity, and does the task size suit that?
  11. How is a past day reprocessed after a bug fix: is there a tested backfill command, and does it overwrite cleanly?
  12. Which data-quality checks run on the output before anyone reads it: row counts, totals compared to a trailing average, NULL rates?

Deep Dive: Senior Interview Follow-ups

"Why is map output written to local disk instead of the distributed file system? What does that cost you?"

Map output is temporary. It lives only until the reducers have fetched it. Writing it to HDFS would replicate it, usually three times, for data that is deleted minutes later. Local disk is much cheaper. The cost is that the output now dies with its machine. If a node is lost after its maps finished, reducers get fetch failures and those completed maps must rerun. So completed work is not durable until the stage that consumes it has finished. Spark makes the same trade with its shuffle files, and remote shuffle services exist to buy back durability when executors come and go.

"You enabled speculative execution and the job's output now has duplicate rows. How is that possible if the framework only commits one attempt?"

Only output that goes through the committer is protected. Three things break it. First, a task that writes directly to an external system such as a database or a queue; each attempt writes. Second, a committer that is not safe on the storage, such as rename-based commits on object storage, where a slow cleanup or a partial rename can leave a losing attempt's files in place. Third, a custom output format that writes to the final location instead of the attempt directory. The fix is to route everything through a committer that is correct for that storage, or a table format with atomic commits, and to keep tasks free of external side effects.

"A combiner made the job wrong. Give an example and the rule it broke."

A combiner that computes an average, or one that emits count + 1 to record that it ran. The framework may call the combiner zero, one or many times on any subset of a key's values, so the function must be associative and commutative, with the same input and output type. Sums, counts, min and max qualify. Averages qualify only if you carry (sum, count) and divide at the very end. Distinct counts qualify only through mergeable sketches such as HyperLogLog, which trade exactness for that property.

"Your job's reduce phase has one task running 40x longer than the median. Walk me through the diagnosis."

First, is it the machine or the data? Compare that task's input bytes and records with the median. If the input is similar, it is a slow node: check its disk and GC, and speculation will usually fix it. If the input is much larger, it is skew. Find the key with a count by key. NULL and default values such as 0 or "unknown" are common culprits. Then choose a fix by cause: filter keys that cannot match, broadcast the small side of a join, add or check the combiner, or salt the hot key and merge in a second stage. Speculation does nothing for skew, because the backup gets the same data.

"Why can't reduce() start until every map has finished, and what does that imply for latency?"

Any map task can still emit a value for any key, so no key's final value is known until the last map is done. Reducers can fetch and merge early, but they cannot call reduce(). That barrier means the job's time is the sum of its phases' slowest tasks, plus scheduling. It is the structural reason batch has a latency floor. Streaming removes the barrier by giving up on "final" in the absolute sense: windows plus watermarks decide when a partial answer is good enough to emit. That is the jump to Stream Processing.

"The 2 TB job takes 10 minutes on 200 machines. Someone proposes DuckDB on one large box. How do you decide?"

Compute the bytes the query actually reads. If the data is Parquet and the query touches two of twenty columns, the scan may be 100 GB or less. One machine with fast NVMe or a fast network link can read that in under a minute, and vectorized engines aggregate at that speed. Then check the shuffle: a group-by with few keys has almost none, but a large join may need more memory and disk than one box has. Also weigh what the cluster gives you that the box does not, such as concurrent jobs, shared scheduling, and tolerance of one node failing. For a single recurring aggregation, the single box often wins on both time and cost.

"How would you make a nightly all-time aggregation cheaper without losing its ability to self-heal?"

Partition the output by day. Each night, recompute only the days whose input changed: today, plus the last few days that can still receive late rows. Merge those into the stored totals. Keep a tested full-rebuild command and run it on a schedule, perhaps weekly, and after any logic change. The incremental run is cheap. The periodic full rebuild is what limits the lifetime of any incremental bug. That is the Lambda overwrite idea applied inside a single batch system.

"In Spark, an executor dies in the middle of the last stage. What exactly gets recomputed?"

The tasks that were running on that executor rerun. If the executor also held shuffle files from an earlier stage, and no external shuffle service serves them, downstream tasks hit fetch failures. Spark then marks those map outputs as lost and reruns the parent stage's tasks that produced them, and only those. Lineage tells Spark exactly which partitions to rebuild. If the parent was cached data that is also gone, Spark walks further back. The recompute is correct only if those tasks are deterministic, which is why nondeterministic partitioning is dangerous.
