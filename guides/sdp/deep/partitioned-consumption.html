Deep Dive: Inside the Mechanism

The lesson's contract rests on two promises. The producer puts every event for a key in the same lane. The group lets only one consumer read a lane at a time. Each promise is kept by a specific piece of code with specific defaults, and each one can be broken quietly. This section follows Kafka closely, then shows how other systems keep the same contract with different trade-offs.

The partitioner: which bytes get hashed

In the Java client, the default partitioner takes the serialized key bytes, hashes them with murmur2, clears the sign bit, and takes the result modulo the partition count. Three details hide in that sentence.

  • It hashes bytes, not values. Customer 8412 as the string "8412" and as a 64-bit integer are different bytes, so they land in different partitions. So does the same value serialized by a different serializer. Many schema-registry serializers prefix the payload with a schema ID. If the key's schema changes, the prefix changes, and every key moves.
  • Different clients use different hashes. librdkafka, the C library behind most Python, Go, .NET and Node clients, defaults to a CRC32-based partitioner called consistent_random. A Java producer and a Python producer writing the same key to the same topic will usually choose different partitions. librdkafka offers murmur2_random to match Java.
  • No key means no lane. A record with a null key is not hashed. Since Kafka 2.4 the client uses a "sticky" partitioner that fills a batch for one partition, then moves to another, which is good for throughput and useless for ordering.

So the key is not just "customer ID". It is "customer ID, serialized by this exact serializer, hashed by this exact partitioner". Write that down in the topic's contract, because every producer must agree on all three.

The group protocol: how the exclusive lease is granted

Every consumer group has a group coordinator. It is the broker that leads the partition of the internal __consumer_offsets topic chosen by hashing the group's name. In the classic protocol, a rebalance works like this:

  1. Something changes: a consumer joins, leaves, misses heartbeats, or the topic gains partitions.
  2. Every member sends JoinGroup. The coordinator waits for all of them, picks one as the group leader, and starts a new generation, a counter that increases with each rebalance.
  3. The leader runs the assignor on the client side and computes who owns what.
  4. Every member sends SyncGroup and receives its partitions.
  5. Members commit offsets tagged with their generation. A commit from an older generation is rejected, which is what keeps a consumer that lost a partition from committing for it.

Failure detection runs on three timers, and confusing them causes most rebalance trouble:

SettingDefault (recent Java client)What it detectsTrade-off
heartbeat.interval.ms3 sNothing by itself; it is how often a background thread proves livenessMust be well below the session timeout
session.timeout.ms45 sA dead or partitioned processLower detects crashes faster, but GC pauses and network blips cause false evictions
max.poll.interval.ms5 minA live process whose processing loop is stuck or too slowHigher tolerates slow batches, but a hung consumer holds its partitions longer

The assignor decides what happens to ownership during the rebalance.

  • Eager assignors (range, round-robin, the original sticky) make every member give up all partitions, then hand them out again. The whole group stops processing for the duration.
  • Cooperative rebalancing (CooperativeStickyAssignor) takes two rounds instead. Only partitions that actually move are revoked. Everyone else keeps processing.
  • Static membership gives each consumer a fixed group.instance.id. A member that restarts within the session timeout gets its old partitions back, with no rebalance at all. That is the tool for rolling deploys.

Kafka 4.0 made a new group protocol generally available (enabled on the client with group.protocol=consumer). The broker computes assignments and moves them incrementally, without the group-wide join barrier. It removes much of the classic protocol's fragility, but check that your clients and any tooling support it before you rely on it.

Why the range assignor still matters: co-partitioning

The range assignor sorts partitions per topic and gives each consumer a contiguous range. For two topics with the same partition count, consumer A gets partitions 0 to 3 of both. That is co-partitioning: if orders and payments are both keyed by customer ID, with the same partitioner and the same count, customer 8412's orders and payments reach the same consumer. A local join then needs no network lookup.

Kafka Streams depends on this. A join between two streams requires both inputs to have the same number of partitions and the same key, and it refuses to start otherwise. If you re-key a stream, for example from session_id to product_id, Kafka Streams writes it to an internal repartition topic first. That is a full extra produce-and-consume hop, and it is often the biggest hidden cost in a topology.

Offsets: what is stored and for how long

A committed offset is the offset of the next record to read, stored per (group, topic, partition) in __consumer_offsets. That topic is compacted, so only the latest commit per partition survives. Three defaults deserve attention.

  • enable.auto.commit=true, every 5 seconds. The commit happens inside poll() and covers everything the previous poll returned. If your code hands records to another thread and polls again, auto-commit will commit work that has not finished. With a simple poll-process loop it is at-least-once. With anything asynchronous it is not.
  • auto.offset.reset=latest. A group with no committed offset starts at the end of the log and skips everything already there.
  • offsets.retention.minutes, 7 days by default on recent brokers. A group with no active members for longer than that loses its committed offsets. When it comes back, auto.offset.reset applies.

Put the second and third together and a consumer group that was switched off for a long holiday comes back, silently skips a week, and reports zero lag.

Stateful consumers: what moves with the partition

For a stateless consumer, a rebalance moves an offset, which is a few bytes. For a stateful one, it moves the state.

In Kafka Streams, each input partition becomes a task. Each task owns a local state store, usually RocksDB, and every write to it is also sent to a compacted changelog topic. When a task moves, the new owner rebuilds the store by reading the changelog from the start. Standby replicas (num.standby.replicas, 0 by default) keep warm copies on other instances, so a failover only replays the tail.

Flink adds a layer that solves the modulo problem. Keys are hashed into a fixed number of key groups, equal to the job's maximum parallelism. Key groups, not keys, are assigned to subtasks, in contiguous ranges. When you rescale from 8 subtasks to 12, whole key groups move between subtasks. No key ever changes key group, so state moves cleanly and no key is split. The price is that maximum parallelism is fixed when the job's state is first created. Changing it later means rewriting the state offline.

This is the same idea as virtual nodes in consistent hashing: route keys to a large, fixed number of buckets, and move buckets between workers. Kafka's partitions are those buckets for the log. Flink's key groups are those buckets for the processing. Kafka has no equivalent layer between key and partition, which is why adding partitions moves keys.

The same contract elsewhere

Other systems keep "order per key, parallelism across keys" while moving the trade-offs.

  • Amazon Kinesis Data Streams uses shards, each with a fixed write limit (1 MB/s or 1,000 records per second) and read limit (2 MB/s shared across standard consumers). Keys hash into a 128-bit space, and each shard owns a range of it. Resharding splits or merges ranges, and the shards keep a parent-child lineage. The Kinesis Client Library finishes a parent shard before it starts the children, so per-key order survives a reshard. That is the piece Kafka's partition increase lacks.
  • Apache Pulsar offers a Key_Shared subscription. Many consumers share one topic or partition, and the broker assigns hash ranges of keys to consumers. Order per key holds, and the number of consumers is not capped by the number of partitions.
  • SQS FIFO orders messages within a message group ID. While a group has messages in flight, no other consumer gets that group's later messages. You never see partitions at all. Throughput is governed by quotas instead, and FIFO has a high-throughput mode that raises them.
  • Key-level concurrency inside a partition. Libraries such as Confluent's Parallel Consumer process many keys from one partition at once while keeping each key in order. The offset to commit is then the lowest offset not yet finished, and the library tracks the completed offsets above it.

Deep Dive: Sizing and the Numbers

The lesson sized the partition count from consumer throughput. That is the first number. A review also wants the skew, the rebalance cost, the per-partition latency limit and the cost of growing later.

How hot is the hot partition?

Hashing spreads keys evenly, not load. Suppose 50,000 events per second, 48 partitions, and one enterprise customer producing 8% of all events. Everyone else is spread evenly.

  • Average partition share: 100% / 48 ≈ 2.1%, about 1,040 events per second.
  • Hot partition share: 8% + 92% / 48 ≈ 9.9%, about 4,960 events per second.
  • That is 4.8 times the average, and more than twice what one consumer can do at 2,000 per second.

This partition's lag grows forever, at about 2,960 events per second, no matter how many consumers you add. More partitions do not help either: the 8% is one key and stays in one partition. Only changing the key's routing or making that key's processing faster fixes it.

Check this before launch. Take a day of real traffic, group by key, and compute the largest key's share. If it exceeds 1 / (partition count) by a lot, you have a hot-key design problem, not a scaling problem.

The ceiling inside one partition

Strict per-partition processing handles one record at a time. Its throughput is 1 / (processing time per record).

  • A handler that makes a 20 ms call to a payment API: 1 / 0.02 = 50 records per second per partition.
  • With 96 partitions: 4,800 per second in total, however many machines you have.
  • With key-level concurrency, say 100 keys in flight per partition: up to 100 / 0.02 = 5,000 per second per partition, as long as there are enough distinct keys.

This is the hidden reason teams end up with "too few partitions". The count was sized for CPU-bound processing. Then the handler gained an I/O call, and per-partition throughput fell by a factor of 50. Batch the I/O, or move to key-level concurrency, before you repartition.

What a rebalance costs

Take a stateful job: 96 partitions on 12 instances, 8 tasks each, with 5 GB of state per task. Restoring from a changelog runs at about 100 MB/s per instance, which is an assumption; measure yours.

  • A crash, no standbys. Detection takes up to the 45-second session timeout. The 8 orphaned tasks move to other instances, which together must restore 40 GB. Spread over 11 instances that is about 3.6 GB each, roughly 36 seconds. Those 8 partitions are down for about 80 seconds plus the join time.
  • A rolling deploy, eager assignor, no static membership. Each of the 12 restarts causes two rebalances: one when the instance leaves and one when it comes back. That is 24 group-wide stops. If tasks also move and restore each time, a deploy takes most of an hour of degraded processing.
  • The same deploy with static membership, cooperative rebalancing and one standby. Each instance returns within the session timeout and keeps its tasks. There are no rebalances, no restores, and a short pause per instance.

The cost of growing later

With modulo routing, a key keeps its partition only if hash mod new = hash mod old.

  • 12 → 24 partitions: a key stays where it is only if hash mod 24 is below 12. Half the keys move.
  • 12 → 13: almost every key moves, about 12 out of 13.
  • Any key that moves risks the reorder in the diagram and loses its local state on the consumer.

Compare that with the cost of extra partitions now. Each partition is replicated, typically 3 times, so 128 partitions are 384 replicas, each with open log segments and some metadata on the controller. A cluster handles tens of thousands of replicas, with the practical limit depending on version and hardware. For one topic, 128 instead of 32 is a rounding error. The asymmetry is the whole argument for overprovisioning.

One caution: do not overprovision without limit. Very high counts slow down leader elections and rebalances, raise end-to-end latency when producers spread small batches thinly, and multiply consumer fetch memory. Size for about three years of growth, not for forever.

Consumer memory per partition

A consumer can buffer up to max.partition.fetch.bytes (1 MiB by default) per assigned partition, capped by fetch.max.bytes (50 MiB) per fetch request. A consumer that owns 40 partitions after a failover can therefore hold tens of megabytes of fetched data before processing any of it. For stateful consumers, add the local state store's block cache and memtables per task. When a failover doubles the tasks on an instance, its memory needs roughly double too, so size instances for the post-failure assignment, not the steady one.

Deep Dive: Failure Modes in Production

1. Two producers, two partitioners

Symptom. A new Python service starts publishing order updates next to the old Java service. A week later, some customers' refunds are processed before their charges, and the keyed fraud state shows two different running totals for the same card.

Mechanism. The Java producer hashes key bytes with murmur2. The Python client, built on librdkafka, defaulted to its CRC32-based partitioner. The same customer ID went to two different partitions, read by two different consumers. Order and state locality both broke for every customer the two services touched.

Detect. An audit job that reads a sample and records which partitions each key appears in. Any key in more than one partition is a routing bug. Keyed state that should be unique per key appearing on two instances.

Fix. Set partitioner=murmur2_random in librdkafka clients, or compute the partition explicitly in a shared library that every producer uses. Make the partitioner part of the topic's documented contract.

2. A key schema change that moved every key

Symptom. After a deploy that "only added an optional field to the key schema", per-key order breaks for a few minutes across all customers, and stateful consumers start rebuilding state for keys they already had.

Mechanism. The key was serialized with a schema-registry serializer. The new schema got a new ID. The ID is part of the serialized bytes, the partitioner hashes the bytes, and so every key hashed to a new partition. It was a repartition with no partition count change.

Detect. The key-to-partition audit above. A sudden jump in state store misses on stateful consumers.

Fix. Use simple, stable key encodings, such as a UTF-8 string or a fixed-width integer, for partition keys. Keep rich schemas in the value. If a structured key is unavoidable, partition on an explicit, stable field rather than on the serialized bytes.

3. Growing the partition count under load

Symptom. Ops raised the topic from 12 to 24 partitions during a busy afternoon to get more parallelism. Over the next half hour, the ledger service rejected thousands of events as out of order.

Mechanism. Half the keys moved to new partitions. The new partitions were empty, so their consumers processed new events immediately. The old partitions still had 30 minutes of backlog for the same keys. Newer events overtook older ones, as in the diagram. Stateful consumers for the moved keys also started with empty state.

Detect. Sequence checks per key in consumers (a per-key version or sequence number in each event). A spike in out-of-order rejections right after a partition change.

Fix. Treat the partition count as a migration, not a setting. One safe recipe: pause producers briefly, let consumers drain the old partitions to zero lag, change the count, then resume. Another: create a new topic with the larger count, switch producers over, and let consumers finish the old topic before they read the new one, like Kinesis's parent-before-child rule. Better still, size the count so that you never do this.

4. Every deploy is a rebalance storm

Symptom. Each rolling deploy of a stateful consumer takes 40 minutes. Lag climbs throughout, and dashboards lag by tens of minutes during every release.

Mechanism. No static membership, an eager assignor, and no standbys. Every instance restart triggered two group-wide stop-the-world rebalances. Tasks moved, and each moved task restored gigabytes of state from its changelog before it could process again.

Detect. Rebalances per deploy, which should be close to zero. Restore time and restoring-task count per instance. Lag correlated with deploy times.

Fix. Static membership with a session timeout longer than one instance's restart time. Cooperative rebalancing, or the newer broker-side protocol. One standby replica per task. Deploy one instance at a time and wait for it to rejoin before moving on.

5. The group that came back and skipped a week

Symptom. A monthly reconciliation consumer is started after being stopped for 10 days. It reports zero lag right away. The reconciliation then finds nothing to reconcile.

Mechanism. The group had no active members for longer than offsets.retention.minutes (7 days by default), so the broker deleted its committed offsets. On return, auto.offset.reset=latest sent every partition to the end of the log. The skipped data was still there. The consumer just never looked.

Detect. A group that starts with no committed offsets when you expected some (log the starting offsets on assignment). Zero lag immediately after a long stop is suspicious, not reassuring.

Fix. For consumers that must not skip, set auto.offset.reset=none, so a missing offset is an error a human must resolve. Keep infrequent jobs' groups alive, or store their offsets externally. Know your broker's offset retention.

6. Parallel processing that committed past unfinished work

Symptom. To speed things up, a team added a thread pool inside the consumer. Throughput rose sharply. After the next crash, about 200 events were never processed, and a few customers saw events applied out of order.

Mechanism. The poll loop handed records to the pool and polled again, and auto-commit committed the offsets returned by the previous poll. When offset 1,000 was committed, offsets 950 to 999 were still running on slow threads. The crash lost them. And because the pool ran records from one partition in parallel, two events for the same key could finish in either order.

Detect. Gaps between committed offsets and the offsets that handlers actually completed (log both). Per-key sequence violations after the change.

Fix. Commit only the lowest offset below which everything has completed. Keep per-key order by routing records to workers by key hash, not round-robin. Or use a library that does both. Turn auto-commit off whenever processing is asynchronous.

7. One stuck lane hidden by total lag

Symptom. Customers on one partition see their order status frozen for two hours. Total consumer lag looked normal, so no alert fired.

Mechanism. A poison message at the head of partition 31 failed on every attempt, and the consumer was configured to pause-and-fix. Partition 31 stopped. The other 95 partitions were healthy, so total lag rose only about 1%. That is well inside normal noise.

Detect. Lag per partition, as time rather than messages. Alert on the maximum per-partition backlog age, not the sum. Alert separately on a partition whose committed offset has not moved while new data arrives.

Fix. Per-partition alerts, plus a clear runbook: inspect, fix or skip the poison record with an audit trail, then resume. Where the ordering requirement allows it, dead-letter the record and park later events for the same key only, so the rest of the lane keeps moving. See Dead Letter Queue.

Deep Dive: Design-Review Checklist

  1. What is the smallest entity whose events must stay in order, and does the partition key match it exactly?
  2. Is the key's serialized form stable, and do all producers, in every language, use the same serializer and partitioner?
  3. What share of traffic does the largest key carry, from real data? Is it below one partition's capacity, with headroom?
  4. How was the partition count derived: throughput per consumer, growth rate, years of headroom? What is the plan if it must change?
  5. What is the per-record processing time, and does one partition's sequential throughput still meet the target if a handler gains an I/O call?
  6. Which assignor, static membership settings and timeouts are used? How many rebalances does one rolling deploy cause?
  7. For stateful consumers: how big is state per partition, how long does restoration take, and are there standby replicas?
  8. Are offsets committed only after processing completes, including with any internal concurrency? Is auto-commit off where processing is asynchronous?
  9. What happens if a group's offsets are missing: is auto.offset.reset a deliberate choice for this consumer?
  10. What is the poison-message policy per topic, pause-and-fix or dead-letter, and who is paged when a lane stops?
  11. Is lag monitored per partition, in time, with alerts on the maximum rather than the total?
  12. Do joins rely on co-partitioning, and is it enforced (same count, same key, same partitioner)?

Deep Dive: Senior Interview Follow-ups

"You need more parallelism, and partitions are maxed out. What are your options short of repartitioning?"

First check where the time goes. If handlers are I/O-bound, process several keys from one partition at once while keeping each key in order, and commit the lowest fully completed offset. If the work is CPU-bound, make each record cheaper or batch the sink writes. If one hot key is the limit, split that key alone. Only after those, migrate to a topic with more partitions by draining or by a new topic, rather than changing the count in place.

"Why does adding partitions break order, when Kafka doesn't move existing data?"

Existing records stay where they are. But new records for a moved key go to a different partition, read by a different consumer with its own lag. If the old partition still has a backlog for that key, the new partition's consumer can process newer events first. The reorder window equals the old partition's backlog at the moment of the change. Keyed state on the consumer is also split between the old and new owners.

"How does Flink rescale a keyed job without breaking per-key state?"

Keys are hashed into a fixed number of key groups, equal to the job's maximum parallelism. Subtasks own ranges of key groups. Rescaling reassigns whole key groups, so a key never changes group and its state moves as a unit. The catch is that the maximum parallelism is fixed when state is first created, so it must be chosen with growth in mind.

"What's the difference between session.timeout.ms and max.poll.interval.ms?"

The session timeout detects a dead process: a background thread sends heartbeats, and if none arrive for that long, the member is evicted. The poll interval detects a live process that has stopped making progress: if the application does not call poll() in time, the client leaves the group itself. Slow processing triggers the second, not the first, which is why raising the session timeout does not fix evictions caused by slow batches.

"A Java and a Go service both produce to the same keyed topic. What do you check?"

That they produce identical key bytes and use the same hash. The Java client hashes with murmur2. librdkafka-based clients default to a CRC32-based partitioner, and some native Go clients have their own defaults. Use the murmur2-compatible option everywhere, or compute partitions in a shared library. Then verify it: sample the topic and check that every key appears in exactly one partition.

"How do you make rolling deploys of a stateful consumer cheap?"

Static membership, so a restarting instance keeps its identity and partitions within the session timeout and no rebalance happens. Cooperative rebalancing, so if one does happen only moved partitions pause. A standby replica per task, so a moved task restores only the tail of its changelog. Then deploy one instance at a time and wait for it to rejoin. Count rebalances per deploy; the target is zero.

"Total lag is fine, but some customers say their orders are stuck. What's going on?"

Probably one lane is stopped, by a poison message under a pause-and-fix policy, or by a hot key. With many partitions, one stuck partition barely moves the total. Look at lag per partition, as time, and at partitions whose committed offset has not moved. Alert on the maximum backlog age across partitions, never on the sum alone.

"Can you have exactly-once with partitioned consumption when a consumer processes records concurrently?"

Yes, if the commit point is right and the effects are idempotent or transactional. You may only commit an offset when every record before it has finished, so you track completions and commit the lowest contiguous point. A crash then replays the records after it, including some that already finished, so their effects must be safe to repeat, as in Exactly-Once Semantics. Per-key order also needs routing by key to workers, never round-robin.
