Deep Dive: Inside the Mechanism

The lesson gives the shape: embed, search, threshold, serve. A production semantic cache has more moving parts than that. It has an entry format that carries everything a hit must be checked against, a lookup ladder with several exits, a write path that decides what deserves to be cached at all, and an index whose own behaviour (deletes, rebuilds, versions) leaks into correctness. This section walks through each one.

What one cache entry holds

An exact cache stores a key and a value. A semantic cache entry has to carry its own evidence, because every hit is a judgement call that later checks will want to audit. A workable entry looks like this:

FieldWhy it is there
embeddingThe vector the index searches. Normalised to unit length, so cosine similarity becomes a plain dot product.
embed_modelModel name and version. Lookups filter on it, so a query embedded by v2 never compares against a v1 vector.
query_textThe canonical question that produced the answer. Needed for audits, for the entity guard, and for re-embedding during a migration.
answerThe response to serve, plus any citations it carried.
scopeTenant, locale, and permission scope. A lookup searches only inside its own scope.
prompt_version, gen_modelThe system prompt and model that wrote the answer. Changing the prompt changes what a correct answer is.
entitiesOrder numbers, SKUs, dates, amounts and negations pulled from the query. The entity guard compares these.
tags, source_docsTopic tags, and the document IDs and versions the answer was built from. Both drive invalidation.
created_at, ttl, hitsExpiry, plus a hit counter that tells eviction and auditing which entries matter most.

Two of these fields are easy to forget, and both cause real incidents. prompt_version matters because a new system prompt ("always mention the 30-day window") makes every old answer subtly wrong. source_docs matters because it turns fuzzy invalidation back into precise invalidation, which the variations section returns to.

The lookup ladder

A lookup is not one comparison. It is a ladder of cheap checks, and a request can drop to generation at any rung. The order matters: cheap and certain checks first, expensive and fuzzy ones last.

  1. Cacheability. A small intent classifier, or a set of rules, decides whether this question may use the shared cache at all. "Where's my order?" and anything carrying personal data stops here and goes to the tool-call path. Doing this first matters. A personal question that never reaches the index can never false-hit.
  2. Exact tier. Normalise the text (case, whitespace, punctuation) and look up a hash. This catches copy-pastes and repeated suggested questions for the price of one key-value read, with zero false-hit risk.
  3. Embed and search. Embed the query and ask the index for the top few neighbours, say k = 5, filtered by scope and embed_model. The filter is part of the search, not a check afterwards. A neighbour from another tenant must never even be a candidate.
  4. Threshold and margin. Take the best neighbour. Its score must clear the threshold. A useful extra test is the margin: the gap between the best and second-best entries when they hold different answers. If "cancel my order" scores 0.95 and "cancel my subscription" scores 0.94, the query sits between two meanings, and the cache should decline.
  5. Guards. Compare extracted entities (order numbers, SKUs, amounts, dates, and negation words like "not" or "without"). Check that the entry's prompt_version is current and its source documents have not changed. Only then serve.

Each rung has a latency cost, and the whole ladder needs a budget. Something like 50 ms for rungs 3 to 5 is reasonable. If the embedder or index is slow, the ladder times out and the request generates normally. That is failing open, and the miss path is always correct.

The decision in code

The decision logic is short enough to read in full. This sketch uses only the standard library and leaves the embedder and index as plain inputs. The point is the order of checks and what each one refuses.

import re
from dataclasses import dataclass

ENTITY = re.compile(r"#?\d{3,}|\b(?:not|no|without|never|cancel\w*)\b", re.I)

def entities(text):
    return {m.group(0).lower().lstrip("#") for m in ENTITY.finditer(text)}

@dataclass
class Entry:
    query: str
    answer: str
    score: float          # similarity to the incoming query
    prompt_version: str
    docs_current: bool    # source documents unchanged since write

def decide(query, neighbours, threshold=0.94, margin=0.02, prompt_version="p7"):
    """Return an answer to serve, or None to generate."""
    if not neighbours:
        return None
    best = neighbours[0]
    if best.score < threshold:
        return None
    rival = next((n for n in neighbours[1:] if n.answer != best.answer), None)
    if rival and best.score - rival.score < margin:
        return None                       # ambiguous: two meanings nearby
    if entities(query) != entities(best.query):
        return None                       # different order number or negation
    if best.prompt_version != prompt_version or not best.docs_current:
        return None                       # answer was written under old rules
    return best.answer

A real entity extractor is better than a regular expression. It should understand product names, dates and currency. But the structure stays the same: every check can only refuse.

What a similarity score actually means

The lesson's 0.94 threshold is a number for one model on one workload. It does not transfer. Embedding models differ a lot in how their scores spread. With many models, two unrelated sentences already score fairly high, because the vectors crowd into a narrow cone of the space. With others, paraphrases score lower than you would expect. So 0.94 can be conservative for one model and loose for another.

The practical rule: a threshold is valid only for the model it was tuned on, and only on a labelled set from your own traffic. When the model changes, the threshold is retuned as part of the migration. It is never copied.

Scores also vary by intent. Short queries ("returns?") produce noisier embeddings than long ones. Policy questions with fixed answers tolerate a looser threshold than questions whose answers branch on a detail. Mature caches end up with per-intent thresholds, tuned separately, rather than one global number.

The index underneath

A semantic cache is usually small by vector-database standards. Even a busy one holds hundreds of thousands to a few million entries. That changes the index choice.

  • Flat (brute force). Compare the query with every entry. At 200,000 entries of 768 dimensions, that is about 150 million multiply-adds, a few milliseconds on a modern CPU core with vector instructions. Recall is exact, deletes are instant, and there is no index to rebuild. For many caches this is the right answer.
  • HNSW. A layered graph that finds near neighbours by walking from a coarse layer to a fine one. Lookups stay around a millisecond into the millions. The knobs are M (links per node: more links, better recall, more memory), ef_construction (build effort), and ef_search (how many candidates a lookup keeps; the main recall versus latency dial). Deletes in most HNSW implementations mark nodes as removed rather than repairing the graph, so a cache with high churn slowly degrades and needs periodic rebuilds.
  • Where it lives. Redis, Postgres with pgvector, a library like FAISS inside the gateway process, or a dedicated vector database. All of these work. The deciding factors are whether you already run it, whether it supports filtered search on scope, and how it handles deletes and TTLs.

One subtlety: ANN search is approximate. If the index misses the true nearest entry, you get a false miss, which is cheap. It will not produce a false hit by itself, because the threshold still applies to whatever it returns. Approximation costs hit ratio, not correctness.

The write path and admission

Writing every miss into the cache sounds natural, and it is usually wrong. Most questions in a long tail are asked once. Caching them fills the index with entries that will never hit, slows lookups, and gives the false-hit lottery more tickets.

Better policies, roughly in order of sophistication:

  • Admit on second sighting. Keep a small, short-lived record of recent miss embeddings. Write a full entry only when a second question lands near one. This is the semantic cousin of the "doorkeeper" in admission-controlled caches. It filters one-off questions and costs little.
  • Admit only validated answers. Run a cheap grounding or policy check before writing. A bad generation that is served once is one bad answer. A bad generation that is cached may be served ten thousand times.
  • Curated answers. For the top few hundred meanings, the ones that make up the bulk of the 40%, have a person or a review process approve the cached answer. The cache becomes partly a managed FAQ with a fuzzy front door.

Never write an answer whose generation included personal context, tool results, or user-supplied text. Those answers belong to one person.

Single-flight by meaning

The lesson mentions that the cache collapses a viral question into one generation. The mechanism needs its own small index. When a miss starts generating, register its embedding in an in-flight table with a future (a placeholder the result will fill). The next miss checks the in-flight table with the same threshold and guards. If it matches, it waits on the future instead of starting a second generation.

Two details make this work. First, the wait needs a timeout shorter than the user's patience, after which the waiter generates on its own. Second, waiters should receive the stream as it is produced, not just the final text. Otherwise the second asker sees nothing for 2.5 seconds while the first sees tokens arrive.

Deep Dive: Sizing and the Numbers

The running numbers from the lesson: about 1,000,000 queries a day, $0.002 and 2.5 seconds per generation, a 27% hit ratio at a 0.94 threshold, and a 0.05% false-hit rate in sampled audits. The assumptions below are stated so you can swap in your own.

Break-even hit ratio

Every query pays for the lookup. Only hits save money. So the cache pays for itself when

hit_ratio × cost_generation > cost_embed + cost_index_per_query

Assume embedding a short query costs about 1% of a generation, roughly $0.00002, and the index and its servers cost $50 a day, or $0.00005 per query at a million queries. The total lookup cost is about $0.00007 per query. Divide by $0.002 and the break-even hit ratio is 3.5%.

Two consequences follow. First, the exact cache's 4% barely beat break-even, which is why it felt useless. Second, the business case is almost always decided by the repetition rate, not by the embedding price. Measure that first.

The cost of false hits, in money

The lesson treats the threshold as a product decision. Here is the arithmetic that makes the decision concrete.

  • At 27% hits on a million queries, the cache serves 270,000 hits a day.
  • At 0.05% false hits, that is 135 wrong answers a day. At the looser 0.92 threshold, 0.3% of 310,000 hits is 930 a day.
  • Assume 10% of wrong answers lead to a support contact that costs $5, and ignore lost trust for now. That is $68 a day at 0.94 and $465 a day at 0.92.
  • The looser threshold earned 40,000 extra hits, worth $80 a day in generation savings.

So the four extra hit-ratio points cost about $400 a day in support contacts to save $80 in inference. The threshold choice is not close. And this count ignores the customer who acts on wrong instructions without calling. A domain where one wrong answer costs hundreds of dollars (a refund dispute, a compliance breach) pushes the threshold higher still, or out of the cache entirely.

How many audits you need

A false-hit rate of 0.05% is small, and small rates are hard to measure. Two rules from basic statistics help.

  • The rule of three. If you grade n hits and find zero false hits, the 95% upper bound on the rate is about 3 / n. To claim "below 0.1%" you need 3,000 clean grades. To claim "below 0.05%" you need 6,000.
  • Seeing enough events. To estimate a 0.05% rate to within roughly ±30%, you want about 10 or more observed false hits. That means about 20,000 graded hits.

Humans cannot grade 20,000 pairs a week. The usual design is an LLM grader that compares each sampled (query, cached query, answer) triple and flags doubtful ones, with people reviewing the flags and a small random slice of the passes. Calibrate the grader against human labels first, and recheck it every time you change the grader prompt or model.

Sample by hit count, not uniformly. One entry hit 9,000 times a day deserves far more scrutiny than one hit twice.

Memory and throughput

Assume 2,000,000 entries, a 768-dimension embedding model, and answers averaging 1.5 KB.

  • Vectors: 2,000,000 × 768 × 4 bytes ≈ 6.1 GB at float32, 3.1 GB at float16.
  • HNSW graph with M = 16: the base layer holds about 32 links per node at 4 bytes each, roughly 128 bytes, plus a little for upper layers. That is about 0.3 GB.
  • Answers and metadata: 2,000,000 × 2 KB ≈ 4 GB, which can live in a key-value store next to the index.

The total fits comfortably on one machine with a replica. A semantic cache does not need the sharding of the next lesson unless it is shared by a very large number of tenants.

Throughput is modest too. A million queries a day averages about 12 per second. A peak of 10× is 120 per second. A small embedding model on a single GPU, or a few CPU cores for short texts, handles that with room to spare. Batch the embedding calls in windows of a few milliseconds to keep the per-query cost low.

Latency, averaged honestly

Every miss pays the lookup too. Assume the ladder costs 25 ms on a miss and a hit is served in 40 ms.

mean = 0.27 × 40 ms + 0.73 × (2,500 + 25) ms ≈ 1,854 ms

Without the cache, the mean is 2,500 ms. So the cache cuts mean latency by about a quarter, and it adds 25 ms (1%) to every miss. That is a good trade. But notice where the risk sits. If the index slows to 300 ms under load and nobody enforces the timeout, the cache adds 12% to every miss while saving nothing extra. The fail-open budget is not optional.

Deep Dive: Failure Modes in Production

1. One bad answer, served ten thousand times

Symptom. A burst of complaints about the same wrong statement, for example "orders over $50 ship free" a week after the threshold moved to $75. They arrive from many users within hours.

Mechanism. One generation was wrong, perhaps a hallucination or a retrieval of an outdated page. The cache admitted it. The question was popular, so the entry collected thousands of hits. A semantic cache amplifies errors in exactly the way it amplifies savings.

Detect. Per-entry hit counts joined with feedback signals: thumbs-down, "that's wrong" follow-ups, escalations. An entry with high hits and a rising negative rate is the one to look at. Weighted audit sampling (by hit count) finds these entries early.

Fix. Purge by entry ID within seconds, through an admin tool someone has already practised using. Gate admission on validation. Give new entries a short probation TTL and a higher audit rate before they earn a full TTL.

2. The near-miss that means the opposite

Symptom. Sampled audits show a cluster of false hits with one shape: "can I return opened items?" served the answer to "can I return unopened items?", and "cancel my order" served the subscription answer.

Mechanism. Embedding models capture topic well and small logical words poorly. Negations, quantities and qualifiers move a sentence only a little in the space, so pairs with opposite answers sit very close together.

Detect. Audit results grouped by intent, and a test set of hard negative pairs (same topic, different answer) that runs on every threshold or model change.

Fix. Add negation words and qualifiers to the entity guard. Use the margin test so ambiguous queries decline. For high-risk intents, add a verifier: a small cross-encoder that reads both questions together and judges whether they ask the same thing. It costs perhaps 10 to 30 ms on a hit, and it catches what geometry cannot.

3. Follow-ups answered from someone else's conversation

Symptom. A user who was asking about shoes types "what about the blue ones?" and gets an answer about blue jackets.

Mechanism. The cache embedded the last message alone. "What about the blue ones?" means nothing without its conversation, and the cache matched it to a fragment from a different conversation with a cached answer.

Detect. False hits concentrated on short queries with pronouns or no nouns. A metric for the share of hits whose query is under, say, five words is a cheap early warning.

Fix. Cache only standalone questions. Rewrite follow-ups into a standalone form first ("what is the return window for blue running shoes?") and use the rewrite as the cache key. If no rewrite is available, skip the cache for any turn that depends on earlier turns.

4. The policy changed, and the tag purge missed

Symptom. After the shipping threshold changed, most shipping answers are correct, but a few phrasings still return the old number for days.

Mechanism. The purge removed everything tagged shipping-policy. Some entries about shipping were tagged orders or promotions at write time, because the tagger saw the question, not the answer. Those survived until their TTL.

Detect. After every policy change, replay a set of probe questions against the cache and diff the answers against fresh generations. A canary per policy (a probe that must reflect the new value within minutes) turns this into an alert.

Fix. Record the source_docs an answer was built from, and invalidate by document ID when CDC reports a change to that document. This is precise, because it tracks what the answer actually used. Keep tags for broader purges, and keep the TTL backstop.

5. A cross-tenant hit

Symptom. A B2B partner's customer receives an answer naming the store's own return policy, or worse, another partner's.

Mechanism. The index was shared, and scope was checked after the search instead of inside it. Under load, someone raised k or removed the post-check for speed, and a neighbour from another tenant was served. Or the scope key omitted locale or brand, so two partners with similar questions collided.

Detect. Log the scope of the served entry next to the scope of the request, and alert on any mismatch. That count must be zero. It is a security metric, not a quality one.

Fix. Make scope a hard partition: a separate index or namespace per tenant, or a mandatory filter inside the search that the code cannot omit. Build the scope key from every dimension that changes the correct answer: tenant, brand, locale, permission tier.

6. The cold cache after a restart

Symptom. Inference spend jumps 35% for a few hours after a deploy. The provider's rate limits start returning errors during the busy hour.

Mechanism. The cache lived in process memory, or the index was rebuilt from empty after a migration. The 27% that used to hit now generates. Capacity planned with the cache in place is not enough without it.

Detect. Hit ratio by minute next to generation rate and spend rate. A drop in the first coincides with a jump in the other two.

Fix. Persist the cache outside the gateway process and warm a new index before cutting over. Plan provider quota for the no-cache case, or at least for a partially warm one. Treat the cache's hit ratio as a capacity dependency, just as you would treat a database replica.

7. The hit ratio that rises for no reason

Symptom. The hit ratio climbs from 27% to 33% over two weeks. The cost dashboard looks great. Then a sampled audit shows the false-hit rate has tripled.

Mechanism. Two common causes. The query mix changed (a holiday season brings many questions near, but not equal to, cached ones). Or the provider updated the embedding model behind an unchanged name, and scores shifted upward across the board.

Detect. Track the distribution of best-neighbour scores, not just the hit ratio. A shift in the median score with no change in traffic points at the model. Pin embedding model versions explicitly where the provider allows it.

Fix. Treat an unexplained rise in hit ratio as an incident to investigate, not a win. Re-run the labelled threshold set weekly. If the model changed, follow the migration playbook and retune the threshold.

Deep Dive: Design Variations and How to Choose

What to cache: the answer, or the retrieval

The lesson caches whole answers. In a RAG system there is a less risky option one layer down: cache the retrieval result, meaning the list of chunk IDs for a question, and still generate the answer fresh.

Cache the answerCache the retrievalCache curated answers only
SavesGeneration, the expensive partEmbedding, search, rerank (~75 ms, a little money)Generation, for the top meanings
Cost of a false hitA wrong answerWeaker context; the model may still answer well or say it does not knowA wrong but reviewed answer, so rare
FreshnessInvalidate on source changeChunk IDs re-read current text, so edits apply at onceReviewed on policy change
ThresholdHighCan be looserModerate, the answer is vetted
FitsStable, impersonal, high repetitionLatency-sensitive RAG, moderate repetitionRegulated or brand-sensitive domains

Retrieval caching saves little money, because generation dominates the cost. Its value is safety and latency. Curated answers trade coverage for near-zero risk. Many teams run both: curated answers for the top 200 meanings, and guarded answer caching for the rest.

How the match is decided

ApproachAdded latency on a hitFalse-hit controlOperational cost
One global cosine thresholdNoneWeak, the number is not portableLowest
Per-intent thresholdsClassifier, a few msBetter, tuned to how answers branchOne labelled set per intent
Threshold plus entity and negation guardA few msCatches the most common false hitsMaintain the extractor
Cross-encoder verifier on candidates~10 to 30 msStrong, reads both questions togetherA second model on the hot path
LLM judge on every hitHundreds of msStrongEats much of the saving

The usual production stack is the third row everywhere, plus the fourth for intents where a false hit is expensive. Using an LLM to judge every hit is a trap. It spends a fair share of the generation cost to avoid paying for a generation.

Where the cache sits, and what goes in the key

  • At the gateway, as the lesson recommends, so every team shares one cache and one audit process. The cost is that the gateway must know scopes and intents, which pulls product knowledge into a platform component.
  • In each application, when the products are very different (support answers and marketing copy share nothing). Simpler ownership, no cross-product sharing.
  • The key namespace should include everything that changes the correct answer: tenant, locale, permission scope, prompt version, generation model family, and embedding model version. Leave one out and the cache will eventually serve an answer that was right under different rules.

Next to provider prompt caching

The two caches stack, and they work on different things. Prompt caching keeps the model's attention state (the KV cache) for a byte-identical prefix, such as a long system prompt and a fixed policy document. A request that shares the prefix skips recomputing it, which saves input cost and time to first token. It never changes the answer, because the model still reads the rest of the prompt and generates.

The design consequence: keep the stable parts of the prompt at the front and identical across requests, so semantic-cache misses still get prefix-cache hits. Put per-request material (retrieved chunks, the question) at the end. Exact pricing, minimum prefix lengths and cache lifetimes vary by provider, so check the current documentation rather than designing around a remembered number.

Deep Dive: Design-Review Checklist

  1. What is the measured repetition rate by meaning on real traffic, and what hit ratio does the business case assume?
  2. Which intents are allowed into the shared cache, and what stops personal or account questions before they reach the index?
  3. Which embedding model and version are used, is the version pinned, and is it stored on every entry and used as a search filter?
  4. How was the threshold chosen: on which labelled set, of what size, with which hard negatives, and who signed off on the false-hit rate?
  5. What does the entity guard compare (order numbers, SKUs, amounts, dates, negations), and is there a margin test for ambiguous queries?
  6. Is tenant and permission scope a hard partition or mandatory search filter, and is a scope mismatch logged as a security event?
  7. How are follow-up turns handled: rewritten to standalone questions, or excluded from the cache?
  8. What is the admission policy? Can an unvalidated or one-off answer enter the cache?
  9. How are entries invalidated when a source document, the system prompt, or the generation model changes? Is there a TTL backstop?
  10. What is the audit design: sample size, weighting by hit count, grader calibration, and who reads the results each week?
  11. What is the lookup's latency budget, and does a slow or failed index fail open to generation?
  12. Is provider quota sized for a cold or partly warm cache after a restart or migration?

Deep Dive: Senior Interview Follow-ups

"Why not ask an LLM whether the cached question matches before serving?"

Because it spends a large share of what the cache saves. A judge call adds hundreds of milliseconds and a real fraction of a generation's cost to every hit. The cache exists to avoid that. The better tool is a small cross-encoder verifier, which reads both questions together, runs in tens of milliseconds, and is used only for intents where a false hit is costly. Keep the LLM judge for offline audits, where its cost buys measurement rather than sitting on the hot path.

"Your audits found zero false hits in 1,000 samples. Is the false-hit rate zero?"

No. By the rule of three, zero in 1,000 only says the rate is probably below 0.3%, which is six times the lesson's target. To support "below 0.05%" you need about 6,000 clean samples. And sample by hit count, because the entries served most often carry most of the risk. A popular entry that is wrong does more damage than a hundred rare ones.

"How do you invalidate when one paragraph of the returns policy changes?"

Store the source documents and their versions on each entry when you write it. When CDC reports a change to the returns policy document, delete every entry whose source_docs include it. That is a precise, indexed delete, not a fuzzy one. Topic tags remain for broader purges, such as "everything about shipping", and the TTL catches anything both missed. Without source tracking you are relying on the tagger having guessed correctly at write time.

"Hit ratio went from 27% to 33% overnight with no change on our side. Good news?"

Probably not. Real repetition does not jump overnight. Check the distribution of best-neighbour scores. If the whole distribution moved up, the embedding model probably changed behind its name, and the threshold now admits pairs it used to reject. Pull a weighted audit sample immediately, pin the model version, and treat it as a migration. If the scores did not move, look at the traffic: a single viral question can produce a real but temporary jump.

"How does single-flight work when the key is fuzzy?"

Keep a small in-flight index of the embeddings of questions currently being generated, each with a future. A new miss searches that index with the same threshold and guards it would use on the main cache. If it matches, it subscribes to the in-flight stream and waits, with a timeout, instead of generating. When the generation finishes, the entry moves to the main cache, subject to admission, and the in-flight record is removed. The timeout matters: if the first generation hangs, waiters must not hang with it.

"Could an attacker poison a shared semantic cache?"

Yes, if user-controlled text can shape a cached answer. Suppose answers are generated with user-supplied context, such as a pasted document or a product review that contains injected instructions. A crafted request could then produce a harmful answer to a common question and get it cached for everyone. The defences are structural. Never cache answers whose prompt contained user-supplied or personal content. Validate before admission. Put new entries on a probation period with heavier auditing. Keep a fast purge by entry ID.

"Where does this cache sit relative to retrieval in a RAG pipeline, and why?"

Before retrieval, so a hit skips embedding the question against the corpus, the search, the rerank and the generation. That also means a hit must respect everything retrieval would have enforced. The cache key includes the tenant and permission scope, so a hit never returns an answer built from documents the asker could not retrieve. A cheaper variant caches the retrieval result after the ACL filter and still generates. It saves less, but a false hit there only weakens the context instead of serving a wrong answer.

"You are moving to a better embedding model. Walk through the cache side of the migration."

Build a v2 index beside v1 by re-embedding every entry's stored query_text with the new model. Retune the threshold on the labelled set using v2 scores. Do not reuse 0.94. Run v2 in shadow: for live queries, look up in both and log where the decisions differ, then audit the differences. Cut over by intent or tenant, keep v1 readable for rollback, and retire it when v2's audited false-hit rate matches. Every lookup filters on model version throughout, so a v2 query never scores against a v1 vector.
