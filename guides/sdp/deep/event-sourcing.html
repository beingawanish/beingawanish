Deep Dive: Inside the Mechanism

The lesson describes an event store as "an append-only place to keep events, one stream per entity." That sentence hides most of the engineering. A real event store has to do four things at once: append without losing a race, load one entity fast, let projections read every event in a stable order, and keep working while the event formats change under it. This section takes them in that order, using order 7f3a from the bookstore.

The events table

Many teams start with an event store inside Postgres, and it is a good way to see the moving parts. Libraries such as Marten (for .NET) work this way, and purpose-built stores such as EventStoreDB (now KurrentDB) keep the same logical fields.

CREATE TABLE events (
  global_position  BIGSERIAL PRIMARY KEY,     -- order across ALL streams
  stream_id        TEXT        NOT NULL,      -- 'order-7f3a'
  stream_version   INT         NOT NULL,      -- 1, 2, 3 ... within the stream
  event_type       TEXT        NOT NULL,      -- 'OrderCancelled'
  schema_version   SMALLINT    NOT NULL,      -- 1, 2 ... of that event type
  payload          JSONB       NOT NULL,
  metadata         JSONB       NOT NULL,      -- actor, correlation_id, causation_id
  occurred_at      TIMESTAMPTZ NOT NULL,      -- business time
  recorded_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (stream_id, stream_version)
);

Every column earns its place:

  • (stream_id, stream_version) unique is the concurrency control. More on that next.
  • global_position is the order projections read in. Entity loads never use it.
  • schema_version says which shape the payload has. You will need it the first time a field changes, which is sooner than anyone expects.
  • metadata holds who did it and why. correlation_id ties all events from one user request together. causation_id points at the event or command that caused this one. During an incident these two fields let you follow a chain like "the cancel at 14:02 caused a refund, which caused an email" without guessing.
  • occurred_at versus recorded_at are two clocks. A courier scan that happened at 09:10 but reached you at 11:40 is one event with two times. Keep both, or "what did we know at 10:00?" becomes unanswerable.

Appending with an expected version

Two requests touch order 7f3a at the same moment. A customer clicks cancel. The shipping job marks it dispatched. That is exactly the race from the lesson's incident, and the event store is where you stop it.

Each writer loads the stream, notes the version it saw (say 4), decides what to append, and then appends at version 5. Only one of them can win, because the unique key on (stream_id, stream_version) rejects the second insert. The loser gets a concurrency error. It reloads the stream, now at version 5, and runs its decision again against the new state. The shipping job now sees OrderCancelled and refuses to dispatch.

This is optimistic concurrency: no locks are held while the code thinks, and conflicts are caught at write time. EventStoreDB exposes it as an "expected revision" on every append, with special values for "the stream must not exist yet" and "any version is fine." The second one is an escape hatch. Using it on a stream that has business rules quietly brings back the lost-update bug the pattern exists to remove.

The whole command cycle is small enough to read in one go. Here it is with Python's standard library and SQLite, so you can run it:

import json, sqlite3

db = sqlite3.connect(":memory:")
db.execute("""CREATE TABLE events (
  pos INTEGER PRIMARY KEY AUTOINCREMENT,
  stream TEXT, version INT, type TEXT, data TEXT,
  UNIQUE (stream, version))""")

def evolve(state, etype, data):            # pure: state + event -> state
    if etype == "OrderPlaced":     return {"status": "placed", "total": data["total"]}
    if etype == "CheckedOut":      return {**state, "status": "checked_out"}
    if etype == "OrderCancelled":  return {**state, "status": "cancelled"}
    if etype == "ShipmentDispatched": return {**state, "status": "shipped"}
    return state                           # unknown types are ignored, not fatal

def load(stream):
    state, version = None, 0
    for v, t, d in db.execute(
            "SELECT version, type, data FROM events WHERE stream=? ORDER BY version",
            (stream,)):
        state, version = evolve(state, t, json.loads(d)), v
    return state, version

def decide(state, command):                # pure: state + command -> new events
    if command == "dispatch":
        if state["status"] == "cancelled":
            raise ValueError("order was cancelled")
        return [("ShipmentDispatched", {"carrier": "UPS"})]
    if command == "cancel":
        if state["status"] == "shipped":
            raise ValueError("already shipped")
        return [("OrderCancelled", {"by": "customer"})]

def handle(stream, command, retries=3):
    for _ in range(retries):
        state, version = load(stream)
        new = decide(state, command)
        try:
            with db:                       # one transaction for the whole batch
                for i, (t, d) in enumerate(new, start=1):
                    db.execute("INSERT INTO events (stream, version, type, data) "
                               "VALUES (?,?,?,?)", (stream, version + i, t, json.dumps(d)))
            return new
        except sqlite3.IntegrityError:     # someone appended first: reload, re-decide
            continue
    raise RuntimeError("too much contention on " + stream)

Two design choices in that snippet matter more than they look. evolve and decide are pure functions, so replay is deterministic and both are trivial to unit test. And evolve never calls the outside world. A replay that sends an email or reads today's exchange rate gives a different answer every time you run it. Anything the decision needed from outside (a price, a tax rate, a fraud score) gets copied into the event when it is written.

The global order, and the gap that bites projections

A projection reads "every event after position N" and saves N as its checkpoint. That sounds safe. On Postgres it has a famous hole.

A BIGSERIAL hands out the number at insert time, not at commit time. Transaction A takes position 101 and is slow to commit. Transaction B takes 102 and commits first. A projection polls, sees 102, processes it, and stores checkpoint 102. Then A commits 101. The projection never asks for anything below 102 again, so event 101 is skipped forever. No error, no log line, just a wrong read model.

There are three common fixes, each with a cost:

  • Serialize appends with a single lock (for example a Postgres advisory lock held during the insert). Positions then commit in order. Simple and correct, but it caps the whole store at one append at a time, which may be a few thousand per second.
  • Read only below a safe high-water mark. The projection treats a gap as "not yet committed" and waits a short time for it to fill before moving past it. Marten's async daemon does a version of this. The cost is a little extra lag and some care around gaps that never fill (a rolled-back transaction leaves one forever).
  • Use a store that assigns positions at commit. Purpose-built event stores write a single log in commit order, so the problem does not arise.

Whatever you pick, write it down in the design doc. "We checkpoint on global_position" without one of these three is a bug report waiting to be filed.

Snapshots are a cache, so treat them like one

A snapshot row looks like (stream_id, stream_version, snapshot_schema, state). Loading becomes: read the latest snapshot, then read events where stream_version > snapshot.stream_version, then apply the tail.

The trap is that a snapshot is the output of today's evolve code. If you fix a bug in evolve, every snapshot written by the old code is now wrong, and the events are still right. So a snapshot needs a version stamp tied to the code that produced it. On load, a snapshot whose stamp does not match the current one is ignored and rebuilt from events. Deleting every snapshot must always be safe. If it is not, your snapshots have become a second source of truth.

When should you snapshot? Most order streams never need one. Twelve events load in about a millisecond. Snapshots matter for long-lived streams: a wallet, a warehouse bin, a subscription that has run for six years. A rule like "write a snapshot when the tail exceeds 200 events" keeps loads bounded without snapshotting every stream on every write.

Projections: subscriptions, checkpoints and rebuilds

A projector is a loop: read a batch after the checkpoint, apply each event to the read table, save the new checkpoint. The single most important detail is where the checkpoint lives.

If the read table and the checkpoint sit in the same database, update both in one transaction. Then a crash either keeps both changes or neither, and each event takes effect exactly once in the read model. If they live in different systems (the checkpoint in Kafka, the table in Elasticsearch), a crash between the two replays some events. The apply step must then be idempotent, usually by storing the last applied stream_version per row and ignoring anything older or equal.

Rebuilds should be boring. The safe routine is blue-green:

  1. Create current_orders_v2 next to the live current_orders_v1.
  2. Start a second projector for v2 at position 0, with its own checkpoint.
  3. Let it catch up to the head. Compare row counts and a sample of rows against v1.
  4. Point readers at v2 (a view rename or a config flag), then drop v1.

Readers never see a half-built table, and if v2 is wrong you simply never switch.

Projectors versus reactors

Not every subscriber builds a table. Some do things: send the cancellation email, call the refund API, publish to Kafka. Call those reactors (or process managers when they coordinate several steps). Keep them on their own subscription with their own checkpoint, and never run them during a projection rebuild. The failure mode is covered below, and it is the one that ends up in the news.

The Kafka publisher is also a reactor. This is how the event store doubles as the outbox: the events are committed once, and a subscriber forwards them. One refinement is worth making early. The events inside your store (domain events) are an internal format you will change freely. What other teams consume should be integration events: a smaller, stable public contract, translated by the publisher. Publish domain events raw and every internal refactor becomes a cross-team migration.

Changing event formats when old events live forever

Events written in 2026 will be replayed in 2031. Three tools cover nearly every change:

  • Tolerant reading. New optional fields get defaults when absent. Unknown fields are ignored. This covers most changes, and it is why the lesson insists on additive changes.
  • Upcasting. For a real shape change, write a small function that turns OrderPlaced v1 into v2 as it is read. Chain them: v1 to v2, v2 to v3. Domain code only ever sees the newest shape. The stored bytes never change.
  • Copy and transform the stream. The last resort, for mistakes too big to upcast (a wrong stream boundary, say). Write a new stream from the old one, then switch. It is a data migration with all the risk that implies, so it is rare.

Renaming an event type is the change people underestimate. To an event store, OrderShipped and ShipmentDispatched are different types. A rename is an upcaster that maps the old name, kept for as long as the old events exist. In practice that means forever.

Deep Dive: Sizing and the Numbers

The assumptions, stated once: the bookstore takes 400,000 orders a day, each order stream averages 12 events of about 300 bytes (the lesson's numbers), and the evening peak runs at 5 times the daily average.

Append rate and storage

  • Events per day: 400,000 × 12 = 4.8 million. Average rate: 4.8M / 86,400 ≈ 56 events per second. Peak: about 280 per second. A single Postgres instance does this without noticing, even with serialized appends.
  • Raw bytes per day: 4.8M × 300 B ≈ 1.4 GB. With the primary key, the stream index and row overhead, budget roughly double: about 3 GB a day, or about 1 TB a year.
  • After five years: about 5 TB of events plus projections. That is the 10–15× multiplier from the lesson, made concrete. Five terabytes on one machine is workable but uncomfortable, and it is why big event stores partition the events table by time (old partitions become cheap, read-only, and can sit on slower storage) or shard by stream.

Load latency and the snapshot threshold

Loading a stream is one index range scan plus deserialization. Assume about 10 µs to read and apply each event (it varies a lot with payload size and language). Then:

StreamEventsReplay cost at 10 µs/eventNeeds a snapshot?
A typical order120.12 ms (the query round trip dominates)No
A busy customer wallet5,00050 msYes, threshold around 200 events
A warehouse bin stream, 6 years2,000,00020 sYes, and consider closing the books (below)

With a threshold of 200, the worst load is one snapshot read plus 200 events: about 2 ms of apply work. The cost is one snapshot write per 200 events, which is noise. The threshold is a dial between write amplification (snapshot often) and load latency (snapshot rarely). Set it from your p99 load budget, not from habit.

Contention: when optimistic concurrency stops being optimistic

A command takes some time between loading and appending. Call that the window, w. If commands for one stream arrive at rate r, the chance that another one lands inside your window is roughly r × w when that number is small.

  • An order stream gets a command every few minutes. With w = 10 ms, conflicts are essentially zero.
  • A single stream for "stock of the bestselling title" during a launch gets 50 commands a second. With w = 10 ms, r × w = 0.5. Half of all attempts collide, retries add more load, and throughput falls exactly when demand peaks.

The fix is never "retry harder." It is a smaller consistency boundary. Split the stock into per-warehouse or per-bin streams, or model reservations as their own streams and reconcile against stock in the background. As a rule of thumb, if one stream needs more than a few writes per second, its boundary is too wide.

Projection rebuild time: the number that decides your design

Take the lesson's 100 million orders: 1.2 billion events. How long does rebuilding current_orders take?

  • A naive projector that does one read-modify-write per event, at about 1 ms each, manages 1,000 events per second. 1.2 billion events at that rate is 1.2 million seconds: about 14 days. Unusable.
  • Batch it. Read 5,000 events, fold them in memory into row changes, write with one multi-row upsert. A realistic rate is 20,000 events per second on one worker: 60,000 s, about 17 hours.
  • Partition it. Events for different streams are independent, so run 8 workers, each owning hash(stream_id) % 8. If the target database keeps up, that is a little over 2 hours.

So the rebuild plan is part of the design, not an afterthought. Decide up front whether a projection can be rebuilt in parallel, and measure the real rate on a copy of production before you promise anyone "we can always rebuild it."

Projection lag

Normal lag is the poll interval plus batch time: tens to a few hundred milliseconds. The number to watch is how lag behaves after a stall. If a projector was down for 10 minutes at 280 events/s, it returns to a backlog of 168,000 events. Draining at 20,000/s while new events still arrive at 280/s takes 168,000 / (20,000 − 280) ≈ 9 seconds. Fine. A projector that can only manage 400/s needs 168,000 / 120 = 23 minutes. Catch-up headroom (drain rate divided by arrival rate) is the metric that tells you which one you have.

Deep Dive: Failure Modes in Production

1. A projection quietly skips events

Symptom: a handful of orders show the wrong status on the orders page forever. Replaying their streams gives the right answer. Nothing errored. Mechanism: the out-of-order commit described above. Position 101 committed after 102, and the checkpoint had already moved past it. It shows up only under concurrent load, so tests rarely catch it. Detect: a reconciliation job that compares, per stream, the latest stream_version in the events table with the version stored in the read model row. Any row that stays behind for more than a few minutes is a skip, not lag. Fix: serialize appends or read below a high-water mark, then rebuild the affected projection. Keep the reconciliation job running afterwards. It is cheap and it catches the next bug too.

2. A rebuild re-sends every email from the last three years

Symptom: customers receive "your order was cancelled" for orders from 2024. Support lines light up. Mechanism: the email sender was registered as one more handler on the same subscription as the projections. Someone reset that subscription's checkpoint to 0 to rebuild a table. The handler did what it was told. Detect: before anything else, an outbound-email rate alarm. Then trace a sample email's causation_id back to an old event. Fix: separate reactors from projectors, give reactors their own checkpoints, and make "reset checkpoint" impossible for a reactor without a deliberate override. Reactors should also refuse to act on events older than a sane age (say 24 hours) unless asked, and pass the event ID to the email provider as an idempotency key.

3. A rebuild stops at an event nobody can read

Symptom: the v2 projection rebuild runs for six hours and then stops at position 384,112,907. Its lag is flat and growing. Mechanism: an event written in 2023 by a version of the code that put the amount in a string. The upcaster for that shape was deleted last year because "nothing writes that any more." The projector throws, retries, and throws again. It is a poison message, and because order matters, it blocks everything behind it. Detect: projector error rate and a "stuck position" alert (the checkpoint has not moved in N minutes while the head has). Fix: restore the upcaster. Then prevent the class of bug: keep a corpus of real production events of every type and schema version, anonymized, and replay it in CI against current code. Never delete an upcaster while events of that version exist.

4. Concurrency errors spike on one stream during a launch

Symptom: checkout errors climb from 0.01% to 8% at 09:00, all for one title. p99 checkout latency triples. Mechanism: stock for the title is one stream, and the contention math from the sizing section has crossed 0.5. Retries pile onto the same stream and make it worse. Detect: concurrency-conflict count by stream (or by stream category, to keep cardinality sane), and retry count per command. Fix: short term, cap retries with jittered backoff and shed load gracefully. Long term, split the stream (per warehouse, or a pool of stock buckets) or move to a reservation model. This is a modeling bug that only looks like a capacity bug.

5. Snapshot and replay disagree after a deploy

Symptom: a wallet shows $412 on the account page. A support engineer replays the stream by hand and gets $398. Mechanism: a deploy fixed how evolve handles partial refunds. Snapshots written before the deploy still contain the old, wrong balance, and the loader trusts them. Detect: a background job that picks random streams, loads them both ways (snapshot plus tail, and full replay), and alerts on any difference. Fix: stamp snapshots with a version that changes whenever evolve changes, and ignore mismatches on load. Then let snapshots rebuild lazily. For money, add the shadow-replay job to the release checklist.

6. One entity's load time grows without limit

Symptom: p99 latency for one merchant's payout command creeps from 5 ms to 900 ms over two years. Mechanism: the merchant's ledger is one stream with millions of events. Snapshots help, but the stream itself, its index and every rebuild keep growing. Detect: events-per-stream distribution and load time by stream; watch the top 0.1%, not the average. Fix: close the books, which is what accountants do every period. At month end, append a PeriodClosed event with the closing balance to the old stream, and start a new stream whose first event is PeriodOpened with that balance. Loads read only the current period. History is still all there, one stream per month.

7. An erasure request leaves plaintext behind

Symptom: an audit after a deletion request finds the customer's name and address in the search index and in the analytics warehouse. Mechanism: crypto-shredding was applied in the event store, but projections decrypted the fields and stored plaintext. Destroying the key does nothing to a copy that is no longer encrypted. Detect: an automated erasure test. Create a synthetic customer, let data flow everywhere, shred, then search every store for the canary values. Fix: keep personal data out of projections that do not need it. Where a projection does need it, either store it still encrypted with the same per-person key, or make the projector subscribe to a PersonErased event and delete its copy. Backups of projections age out on a schedule shorter than the legal deadline.

The row that causes the most arguments is the Kafka one, so it deserves a plain opinion. Teams say "Kafka is a log, event sourcing needs a log, done." The log they need is per entity, with conditional append. Kafka gives you a per-partition log with unconditional append. Those are different tools. The "Kafka-centric" architectures in the lesson's examples use Kafka as the company's shared history and let each service keep its own decision state. That is a perfectly good design. It just is not the same thing as storing orders as event streams.

The second argument is about aggregate size. Big streams feel natural ("everything about a customer in one place") and they make some rules easy. They also turn every write for that customer into a queue, and they grow without limit. When in doubt, go smaller and pay with a process manager for the occasional cross-stream rule.

Deep Dive: Design-Review Checklist

  1. Which domains are event-sourced, and what is the business reason for each one? Which domains are deliberately not?
  2. Do the event names read as business facts (OrderCancelled) rather than row changes (OrderUpdated)? Show five real ones.
  3. Does every append carry an expected version? Where, if anywhere, is "any version" used, and why is that safe?
  4. What is the largest stream you expect, and what is its write rate? Have you done the contention math for the hottest one?
  5. How do projections read in order? If it is a sequence column, how do you handle out-of-order commits?
  6. Where is each projection's checkpoint stored, and is it updated in the same transaction as the read table? If not, how is apply idempotent?
  7. How long does a full rebuild of the biggest projection take, measured, and can it run in parallel? How do readers switch to the rebuilt version?
  8. Which subscribers have side effects? Can a rebuild ever trigger them?
  9. Is every external input to a decision (price, rate, score) captured in the event, so replay is deterministic?
  10. How does each event type evolve? Where are the upcasters, and is there a CI job replaying real historical events of every version?
  11. Which fields are personal data, which key encrypts them, and which projections and backups hold copies? Has an erasure been tested end to end?
  12. What do other teams consume: stored domain events or a translated integration contract?

Deep Dive: Senior Interview Follow-ups

"Two requests modify the same order at once. How does your event store stop a lost update?"

Each append states the version it was decided against. The store enforces uniqueness on (stream_id, stream_version), so only one append at version 5 can succeed. The loser gets a conflict, reloads the stream including the winner's event, and runs its decision again. That re-decision is the point: the shipping job sees OrderCancelled and refuses. Retrying the same append blindly would be wrong. You retry the decision, not the write.

"Why not just use Kafka as your event store?"

Three gaps. No conditional append per entity, so the concurrency check above is not available. No cheap read of one entity's history, because a partition interleaves many entities and you would scan it. And compaction keeps only the latest record per key, which is the opposite of keeping history. Kafka is excellent for distributing events after they are decided. The decision needs a store with per-stream versions.

"Your projection lags by 30 seconds after a deploy. Is it lag or is it broken?"

Look at two numbers: the checkpoint position over time and the head position over time. If the checkpoint is moving and the gap is shrinking, it is catching up, and catch-up headroom tells you how long it will take. If the checkpoint is flat while the head moves, it is stuck, usually on a poison event, and the error log will name the position. A third case is silent: the checkpoint is current but rows are wrong. That is a skip or a logic bug, and only a reconciliation job against the event store finds it.

"How do you guarantee that a username is unique if each user is its own stream?"

A stream only guards its own invariants, so a cross-stream rule needs something else. If the event store lives in a relational database, insert into a usernames table with a unique constraint in the same transaction as the UserRegistered append. If it cannot share a transaction, use a reservation: claim the name in a reservation stream keyed by the name itself, then register, then confirm, with a timeout that releases abandoned claims. Saying "check the projection first" is the wrong answer, because the projection lags and two registrations can both pass the check.

"You fix a bug in how refunds are applied. What happens to existing state?"

The events are unchanged and still correct, because they record what happened, not the computed result. Replaying with the fixed evolve gives correct state. Three things need attention: snapshots written by the old code (invalidate them by version), projections built by the old code (rebuild), and any decision already made on the wrong state (for example a refund paid twice). That last group is handled with compensating events, plus a query over the event log that lists exactly which streams were affected.

"An event-sourced account has ten years of history. Walk me through a balance read."

Normally no replay happens at request time at all: the balance comes from a projection kept current by a subscriber. For the command path, the handler loads the latest snapshot and the tail since it, bounded by a threshold such as 200 events. If the stream itself has become huge, close the books periodically. A PeriodClosed event carries the closing balance into a new stream, so the live stream only covers the current period.

"What is the difference between occurred_at and recorded_at, and when does it matter?"

occurred_at is when the thing happened in the world. recorded_at is when your system learned about it. They split whenever data arrives late: offline devices, courier scans, bank settlements. "What was the order's status at 10:00?" uses occurred_at. "What did support see on screen at 10:00?" uses recorded_at. Disputes and audits often need the second, and you can only answer it if both clocks were stored from the first event.

"When would you event-source only part of a service?"

Most of the time. In the bookstore, orders and payments are ledgers, so they are event-sourced. The product catalog, customer preferences and content pages are current-state data, so they stay as tables, maybe with CDC for history. The boundary follows the question "will someone ever dispute or audit how this value got here?" A service with one event-sourced aggregate and five plain tables is normal and healthy.
