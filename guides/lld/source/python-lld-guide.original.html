Python LLD Type-Along Guide

Six low-level design problems, typed end to end — the enterprise-grade follow-up to the Python Study Guide. Written against Python 3.13, standard library only.

Chapter 0: Before You Type a Line

What this guide is

Six problems. One method: you type every line.

This is the type-along companion to the Python Study Guide. That guide taught you the language — functions, classes, dataclasses, typing, exceptions, testing, the material of its chapters 1 through 8. This guide teaches you what to build with it.

Each of the six chapters takes one low-level design problem — parking lot, elevator system, traffic light, library management, vending machine, car rental — and walks you through a complete, working, tested solution. Nothing is pasted. You type it all.

That is the whole method, and it works for one reason: it is how you learned Java. You did not learn Java by reading about it. You typed it for years, until the patterns lived in your hands. Python gets the same treatment here. By the sixth problem, the moves — the injected clock, the boundary validation, the explicit state table — should feel as automatic as a Java constructor chain.

The Study Guide's chapters 1 through 8 are the entire toolkit this guide needs. Functions and classes are the skeleton of every design. Dataclasses carry the domain objects and the config. Typing makes the API surface honest — every signature says what it takes and what it returns. Exceptions become the custom hierarchies. Testing becomes the checkpoints. If any of those feel rusty, revisit the chapter before you start typing. This guide builds on them without re-teaching them.

One more thing this guide assumes: you are preparing for senior backend interviews. Every chapter is shaped the way interviewers actually grade LLD rounds. You will see how in the section on scoring below.

How to use a type-along guide

Type every line yourself. Do not copy-paste.

Copy-paste lets your eyes skim. Typing forces you to parse each construct — the colon after the method signature, the self you almost forgot, the import at the top of the file. Your fingers catch what your eyes skip. That is not a metaphor. When you retype def __post_init__(self) -> None: ten times across six chapters, your hands know it before your head does, and in an interview your hands are what the interviewer is watching.

Run the checkpoint at each step. Every chapter carries two or three checkpoints: small, runnable milestones with a precise expected result. When a checkpoint passes, the ground under you is solid and you can build on it. When it fails, you know exactly where to look instead of debugging a whole system at once. Never skip a checkpoint. A skipped checkpoint is a bug you will meet again, worse, at the next one.

When you get stuck — and you will — compare, find the difference, and retype the fix. Do not paste it. Open the reference, find where your code diverges, understand the divergence, close the reference, and type the fix yourself. The point is not the green test run. The point is the second pass through the same construct. The first pass taught you nothing because you were following; the second pass is where the learning happens.

Keep a mistakes note. One file, one line per mistake: what went wrong, what the fix was. A forgotten field(default_factory=...) here, a lock acquired in the wrong order there. Your own bug list beats any textbook, because every entry in it is something you actually did. Read it before interviews. It is the shortest path to not repeating yourself under pressure.

One problem per sitting. A sitting is the type-along plus the stretch tasks at the end of the chapter. If a sitting runs long, stop at a checkpoint — the chapters are built so the checkpoints are safe stopping points. Come back fresh. Typing tired teaches typos, not design.

The six problems

A word on what each one is really about, beneath the domain dressing.

Parking lot is allocation under constraints: who fits where, who pays what, and what happens when the lot is full. Elevator system is concurrency: many requests, many cabs, one dispatcher, and the queue in between. Traffic light is state machines with real-world consequences: phases, transitions, and the clearance that keeps people safe. Library management is repositories and reservations: catalogs, copies, holds, and the notifications that close the loop. Vending machine is state plus money: collect, validate, dispense, return change, and never lose a coin. Car rental is intervals and pricing: who has which car when, and what the time was worth.

Different stories, same moves. By the third chapter you will start predicting the design before you read it. That feeling is the whole point.

How LLD interviews are scored

Interviewers rarely say this out loud, but an LLD round is graded on five things. They map directly onto this guide's chapter structure, so you are practicing the scoring rubric every time you type.

Requirements elicitation. The interview starts before you design. A strong candidate asks clarifying questions: how many floors, which vehicle types, how is pricing charged, what happens when the lot is full. This is not stalling. Production systems fail on assumed requirements, and the interviewer is checking whether you think like someone who has been burned by that. Each chapter opens with the questions to ask and the answers the interviewer would give, so you practice the asking.

Domain modeling. Nouns become classes, and each class gets exactly one responsibility. The interviewer watches how you carve up the problem: is there a Ticket, or does ParkingLot do everything? A clean model reads like the business talking about itself. Sloppy models read like a procedure wearing a class costume. The domain-model section of each chapter is where this skill gets its reps.

Extensibility. Then the interviewer moves the goalposts. "Now add electric-vehicle charging." "Now a new payment method." Your design should absorb the change as a new class, not as surgery on old ones. This is the Open/Closed principle made visible, and it is usually the highest-weighted signal in the round. The stretch tasks at the end of each chapter are exactly these goalpost moves.

Trade-off discussion. Every design sacrifices something. Name what you sacrificed and why. "I chose an in-memory store for simplicity; a real deployment would need persistence, and the Repository seam is where we would add it." Interviewers trust candidates who see the cost of their own choices. The design-moves section of each chapter models this out loud so you can borrow the phrasing.

Working code and tests. Finally, it has to run. Not pseudocode, not a whiteboard sketch — code that executes, with tests covering the edge cases. A design that cannot survive contact with an interpreter is just an opinion. The checkpoints and the test suite in each chapter are your rehearsal for this.

The enterprise checklist

Every chapter in this guide is built against the same checklist. It is printed here once, canonically, so the chapters can reference it by name instead of re-explaining it. For each item: what it is, and why it matters in production.

Single Responsibility. Each class does one job. When the job changes, one class changes — and nothing else breaks by accident.

Open/Closed. New behavior arrives as new code, not edits to old code. Editing working code is how regressions are born; extending it is how systems grow.

Liskov substitutability. A subclass must be usable wherever its parent is expected. If it cannot be, the abstraction is lying, and callers cannot trust the type.

Dependency inversion via constructor injection. High-level code depends on abstractions, and those abstractions are passed in at construction time. This is what makes the code testable and its wiring visible instead of hidden inside constructors.

Custom exception hierarchies, no bare excepts. Each failure mode gets its own exception type, so callers can catch exactly what they can handle. A bare except: swallows real bugs along with expected errors — in Python it even catches KeyboardInterrupt, which is language behavior, not a style opinion.

Stdlib logging in library code; print only in __main__ demos. A library that prints decides the operator's output. Logging lets the deployer route it, filter it, and silence it. That distinction is a convention, not a language rule — Python will happily let you print from anywhere — and production code follows the convention.

Input validation at boundaries. Public methods reject bad input immediately: negative minutes, unknown ids, empty strings. An error caught at the door carries context; one discovered deep inside has already corrupted state.

Config via dataclass, no magic numbers. Every tunable lives in one named place with a validated type. A reviewer can audit behavior without reading the logic, and a deployment can change behavior without touching code.

Composition over inheritance. Behavior varies by plugging in collaborators, not by growing subclass trees. Subclass trees freeze choices at class-definition time; composition keeps them open at runtime.

Thread-safety with locks around shared mutable state, documented. Concurrent access to shared state without a lock is a race, and races are the bugs that never reproduce on your machine. The lock's scope is documented at the declaration site so the next reader knows exactly what it protects.

Repository pattern for persistence — in-memory, swappable. Business code talks to a repository interface. The implementation behind it is in-memory today and a database tomorrow, and the callers never change.

unittest stdlib tests with edge cases. The stdlib test runner works anywhere Python runs, with zero installs. Edge cases are where interview bugs live: the full lot, the empty queue, the expired ticket, the midnight boundary.

How each problem chapter is structured

Every chapter follows the same ten-part arc. Once you have done one, you know the shape of the other five, and you can pace yourself against it.

  1. The problem. What you are building, in plain words, with the scope pinned down. No code yet.
  2. Requirements. Functional and non-functional, written the way a strong candidate elicits them — practice asking these before you read the answers.
  3. From nouns to classes. The domain nouns, each with one job. This is the domain model, still without bodies.
  4. Class diagram. A hand-drawn map of the classes and how they relate. Design the seams before the bodies.
  5. Key design decisions. The moves that matter and the reasons behind them — each pattern named, each tied to the enterprise checklist above.
  6. Type along. Numbered steps, one file or one class per step. Goal first, then the complete file, then what to notice. Every step ends with a runnable checkpoint.
  7. Test results. The full unittest suite, executed, with real output. Concurrency, edge cases, the invariants that must hold.
  8. Enterprise checklist, mapped to the code. Each checklist item pointed at the actual class or method where it shows up.
  9. Common interview follow-ups. The goalpost moves, rehearsed in advance, with short answers.
  10. Stretch tasks. Extensions to try on your own after the type-along. Unsolved on purpose.

Read steps 1 through 5 before you start typing. Then type steps 6 through 8. Then attempt 9 before looking at any hints. Then read 10 and notice how much of it you already knew.

Setup

Python 3.13, the same version as the Study Guide. Everything here uses the standard library only — no pip installs, ever. If a chapter ever needed a third-party package, that would be a bug in the chapter.

Each problem lives in its own directory under code/, with its tests beside it under tests/. Run the suite for the problem you are working on from the repository root:

python3 -m unittest discover -s tests -v

The -v flag matters while you are learning: it names each test as it runs, so a failure tells you exactly which behavior broke.

Check your version first: python3 --version should report 3.13.x. Every problem mirrors the same directory layout — source under code/<problem>/, tests under tests/ — so once you learn one, you know all six. A problem is done when its full suite is green and you have attempted the stretch tasks with the reference closed.

Suggested pace: one problem per sitting — the type-along first, the stretch tasks after. Six problems, six sittings, and at the end a set of moves your hands know. The outro chapter then shows you how those moves connect across problems and hands you fifteen interview questions to test the understanding behind them.

Type the first line whenever you are ready.

Chapter 1: Parking Lot

Type along with this chapter. You will build a working multi-floor parking lot: entry panel, exit panel, tickets, hourly pricing, and a free-spot display. Every file is complete and runnable. Type each one, run the checkpoint, and move on.

1. The problem

A garage has several floors of parking spots. Vehicles arrive at the entry panel: a motorcycle, a car, or a truck. The system assigns each vehicle a spot it can fit in, hands the driver a ticket, and records the entry time. At the exit panel, the driver pays for the time parked and gets change. The system must never assign one spot to two vehicles, even when cars arrive at the same moment.

2. Requirements

Functional

  • Park a motorcycle, car, or truck and receive a ticket with entry time.
  • Assign the smallest spot that fits the vehicle, nearest the entrance.
  • Spot sizes: COMPACT takes motorcycles only; REGULAR takes motorcycles and cars; LARGE takes anything.
  • Search floors bottom-up: the lowest floor with a fitting spot wins.
  • Close a ticket at exit: compute the fee, accept payment, return change.
  • Reject underpayment without closing the ticket.
  • Show free-spot counts per floor for the entrance display board.

Non-functional

  • Thread-safe entry and exit: concurrent park() calls must never double-book a spot.
  • Pricing must be replaceable without touching the lot (tomorrow it could be a flat daily rate).
  • Ticket storage must be replaceable (in-memory today, a database later).
  • Every domain failure gets a catchable exception type, never a bare except and never a stringly error code.
  • Money is integer cents everywhere. Floats never touch money.

3. From nouns to classes

Read the problem statement and circle the nouns. Each noun that carries behavior becomes a class.

Noun Class Responsibility
Vehicle (bike/car/truck) Vehicle Immutable fact: plate + type, validated
Parking spot Spot Knows its size; tracks its occupant; enforces fit
Floor Floor Ordered spots, nearest first; finds a fitting spot
Ticket Ticket Entry time, spot, vehicle; closes with exit time + fee
Parking lot ParkingLot Facade: park, exit, display; owns the lock
Pricing rule PricingStrategy / HourlyPricing Fee from entry/exit times; swappable
Ticket storage TicketRepository / InMemoryTicketRepository Save/find/remove tickets; swappable
Failure modes ParkingError hierarchy One catchable type per domain failure
Deployment settings LotConfig Floors, layout, rates, grace period; no magic numbers

Notice what is missing: no EntryPanel or ExitPanel classes. Panels are just the public methods park() and exit(). A class earns its place by owning behavior, not by mirroring a noun.

4. Class diagram

Study this before you type. ParkingLot is the only class a caller touches. Everything else hangs off it.

5. Key design decisions

Strategy for pricing. ParkingLot depends on the PricingStrategy interface, not on HourlyPricing. A flat daily rate arrives as a new class implementing one method. ParkingLot never changes. That is the Open/Closed principle doing real work, not recited.

Repository for tickets. Same idea for storage. ParkingLot talks to TicketRepository; the in-memory dict is one implementation. A Postgres version implements save/find/remove and slots in untouched.

Facade, not god object. ParkingLot coordinates but does not compute. Spot-fit logic lives in Spot, floor search in Floor, fee math in the pricing strategy, ticket lifecycle in Ticket. The facade owns exactly one hard thing: the lock.

One lock, held for the whole operation. park() and exit() each take self._lock for their entire body. Two entry panels can never interleave between "find a free spot" and "mark it taken". That is the whole concurrency design, and it is enough because every operation is fast.

Clock injection. ParkingLot takes a clock callable. Production passes datetime.now(timezone.utc). Tests pass a fake they can fast-forward. Without this, fee tests would need time.sleep and luck.

Money in cents, always int. fee_cents, payment_cents, change: all integers. Floating point never appears near money, so $1.10 + $2.20 style drift is impossible by construction.

Frozen dataclasses for values. Vehicle and LotConfig are frozen. A vehicle is a fact about the world; nothing should mutate it after creation. Config validated in __post_init__ fails fast at startup, not mid-parking.

Exceptions, not error codes. Each failure mode is its own type under ParkingError. Callers catch precisely. LotFullError is distinct from PaymentError because the entry panel and the exit panel handle them differently.

6. Type along

Work from the code/ directory. Each step adds one file. Type it fully, then run the checkpoint before continuing.

Step 1 — parking_lot/config.py: the vocabulary of the lot

Goal: define the enums and the one config object everything else reads.

"""Shared configuration and enumerations for the parking lot.

Everything a deployment might change lives here: how many floors, how many
spots per floor, how they are laid out, and what each vehicle type pays per
hour. Nothing else in the package holds a magic number.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from enum import Enum, auto


class VehicleType(Enum):
    """Kind of vehicle. Order matters: smaller values are smaller vehicles."""

    MOTORCYCLE = auto()
    CAR = auto()
    TRUCK = auto()


class SpotSize(Enum):
    """Kind of parking spot. Order matters: smaller values are smaller spots."""

    COMPACT = auto()   # motorcycle only
    REGULAR = auto()   # motorcycle or car
    LARGE = auto()     # any vehicle


# Which spot sizes each vehicle type is allowed to use.
_FIT: dict[VehicleType, frozenset[SpotSize]] = {
    VehicleType.MOTORCYCLE: frozenset({SpotSize.COMPACT, SpotSize.REGULAR, SpotSize.LARGE}),
    VehicleType.CAR: frozenset({SpotSize.REGULAR, SpotSize.LARGE}),
    VehicleType.TRUCK: frozenset({SpotSize.LARGE}),
}


def fits(vehicle_type: VehicleType, spot_size: SpotSize) -> bool:
    """Return True when a vehicle of *vehicle_type* may occupy a spot of *spot_size*."""
    return spot_size in _FIT[vehicle_type]


@dataclass(frozen=True)
class LotConfig:
    """Deployment-time settings for one parking lot.

    *floors*: number of floors, floor 1 is closest to the entrance.
    *spots_per_floor*: ordered list of spot sizes; index 0 is nearest the entrance.
    *hourly_rates_cents*: price per hour, in cents, per vehicle type.
    *grace_minutes*: free minutes after entry before the first hour is charged.
    """

    floors: int = 2
    spots_per_floor: tuple[SpotSize, ...] = (
        SpotSize.COMPACT,
        SpotSize.COMPACT,
        SpotSize.REGULAR,
        SpotSize.REGULAR,
        SpotSize.LARGE,
    )
    hourly_rates_cents: dict[VehicleType, int] = field(
        default_factory=lambda: {
            VehicleType.MOTORCYCLE: 100,
            VehicleType.CAR: 200,
            VehicleType.TRUCK: 400,
        }
    )
    grace_minutes: int = 15

    def __post_init__(self) -> None:
        if self.floors < 1:
            raise ValueError("floors must be at least 1")
        if not self.spots_per_floor:
            raise ValueError("spots_per_floor must not be empty")
        missing = set(VehicleType) - set(self.hourly_rates_cents)
        if missing:
            raise ValueError(f"hourly_rates_cents is missing rates for {missing}")
        if any(rate < 0 for rate in self.hourly_rates_cents.values()):
            raise ValueError("hourly rates must not be negative")
        if self.grace_minutes < 0:
            raise ValueError("grace_minutes must not be negative")

What to notice. The fit rules live in one table, _FIT, not scattered across ifs. LotConfig is frozen and validates itself: a bad config fails at startup with a clear message, not halfway through parking a car.

Checkpoint:

$ python3 -c "from parking_lot.config import LotConfig, fits, VehicleType, SpotSize; print(fits(VehicleType.CAR, SpotSize.COMPACT))"
False

Step 2 — parking_lot/exceptions.py: the failure vocabulary

Goal: give every domain failure its own catchable type.

"""Domain exceptions for the parking lot.

Every failure a caller can reasonably handle gets its own type, so callers
can catch precisely what they mean instead of parsing message strings.
All of them derive from ParkingError, so a caller that does not care about
the details can catch that one base class. No bare ``except`` anywhere.
"""
from __future__ import annotations


class ParkingError(Exception):
    """Base class for every domain error in the parking lot."""


class LotFullError(ParkingError):
    """Raised by park() when no spot fits the vehicle."""


class TicketNotFoundError(ParkingError):
    """Raised by exit() for an unknown or already-closed ticket id."""


class PaymentError(ParkingError):
    """Raised when the payment offered at exit is invalid or too small."""


class InvalidVehicleError(ParkingError):
    """Raised when the vehicle handed to park() fails validation."""

What to notice. Four subclasses, one base. The entry panel catches LotFullError; the exit panel catches PaymentError and TicketNotFoundError. Nobody parses message strings.

Checkpoint:

$ python3 -c "from parking_lot.exceptions import LotFullError, ParkingError; print(issubclass(LotFullError, ParkingError))"
True

Step 3 — parking_lot/domain.py: vehicles, spots, floors, tickets

Goal: the domain objects with their own invariants. No pricing, no threads here.

"""Core domain objects: Vehicle, Spot, Floor, Ticket.

These classes hold state and enforce their own invariants. They know nothing
about pricing, persistence, or threads; those concerns live elsewhere.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from datetime import datetime

from .config import SpotSize, VehicleType, fits
from .exceptions import InvalidVehicleError


@dataclass(frozen=True)
class Vehicle:
    """A vehicle that wants to park. Immutable: it describes a fact."""

    license_plate: str
    vehicle_type: VehicleType

    def __post_init__(self) -> None:
        if not self.license_plate or not self.license_plate.strip():
            raise InvalidVehicleError("license_plate must be a non-empty string")
        if not isinstance(self.vehicle_type, VehicleType):
            raise InvalidVehicleError("vehicle_type must be a VehicleType")


class Spot:
    """One parking spot. Tracks which vehicle (if any) occupies it."""

    def __init__(self, spot_id: str, size: SpotSize) -> None:
        self.spot_id = spot_id
        self.size = size
        self._vehicle: Vehicle | None = None

    @property
    def is_free(self) -> bool:
        return self._vehicle is None

    def can_fit(self, vehicle: Vehicle) -> bool:
        return self.is_free and fits(vehicle.vehicle_type, self.size)

    def assign(self, vehicle: Vehicle) -> None:
        if not self.can_fit(vehicle):
            raise InvalidVehicleError(
                f"spot {self.spot_id} ({self.size.name}) cannot take {vehicle.vehicle_type.name}"
            )
        self._vehicle = vehicle

    def release(self) -> Vehicle:
        vehicle = self._vehicle
        self._vehicle = None
        if vehicle is None:
            raise InvalidVehicleError(f"spot {self.spot_id} is already free")
        return vehicle

    def __repr__(self) -> str:
        occupant = self._vehicle.license_plate if self._vehicle else "free"
        return f"Spot({self.spot_id}, {self.size.name}, {occupant})"


class Floor:
    """One floor of the lot. Spots are stored nearest-to-entrance first."""

    def __init__(self, number: int, sizes: tuple[SpotSize, ...]) -> None:
        self.number = number
        self.spots: list[Spot] = [
            Spot(f"F{number}-S{i + 1:02d}", size) for i, size in enumerate(sizes)
        ]

    def find_free_spot(self, vehicle: Vehicle) -> Spot | None:
        """First free spot that fits, nearest the entrance. None when full."""
        for spot in self.spots:
            if spot.can_fit(vehicle):
                return spot
        return None

    def free_counts(self) -> dict[SpotSize, int]:
        counts: dict[SpotSize, int] = {size: 0 for size in SpotSize}
        for spot in self.spots:
            if spot.is_free:
                counts[spot.size] += 1
        return counts


@dataclass
class Ticket:
    """Proof of parking. Created at entry, closed at exit."""

    ticket_id: int
    vehicle: Vehicle
    spot_id: str
    entry_time: datetime
    exit_time: datetime | None = field(default=None)
    fee_cents: int | None = field(default=None)

    def close(self, exit_time: datetime, fee_cents: int) -> None:
        if self.exit_time is not None:
            raise InvalidVehicleError(f"ticket {self.ticket_id} is already closed")
        if exit_time < self.entry_time:
            raise InvalidVehicleError("exit_time cannot be before entry_time")
        if fee_cents < 0:
            raise InvalidVehicleError("fee_cents must not be negative")
        self.exit_time = exit_time
        self.fee_cents = fee_cents

What to notice. Spot.assign refuses a bad fit even if the caller forgot to check: the invariant lives with the data. Floor stores spots nearest-first, so "nearest to the entrance" falls out of a plain linear scan. No sorting, no distance math.

Checkpoint:

Goal: the Strategy pattern — fee math behind an interface.

"""Pricing strategies. The lot depends on the PricingStrategy interface,
never on a concrete implementation, so new pricing rules arrive as new
classes instead of edits to ParkingLot (Open/Closed in practice).
"""
from __future__ import annotations

import math
from abc import ABC, abstractmethod
from datetime import datetime

from .config import LotConfig, VehicleType


class PricingStrategy(ABC):
    """How a ticket's fee is computed from entry and exit times."""

    @abstractmethod
    def fee_cents(
        self, vehicle_type: VehicleType, entry: datetime, exit: datetime
    ) -> int:
        ...


class HourlyPricing(PricingStrategy):
    """Ceiling-hour billing with a grace period.

    A stay inside *grace_minutes* is free. Otherwise the parked time rounds
    UP to the next whole hour and multiplies by the vehicle type's rate.
    """

    def __init__(self, config: LotConfig) -> None:
        self._config = config

    def fee_cents(
        self, vehicle_type: VehicleType, entry: datetime, exit: datetime
    ) -> int:
        if exit < entry:
            raise ValueError("exit cannot be before entry")
        parked = exit - entry
        if parked.total_seconds() <= self._config.grace_minutes * 60:
            return 0
        hours = math.ceil(parked.total_seconds() / 3600)
        return hours * self._config.hourly_rates_cents[vehicle_type]

What to notice. math.ceil is the entire billing rule: partial hours round up, always in the garage's favor. A new FlatDailyPricing class would implement the same one method. Nothing else changes.

Step 5 — parking_lot/repository.py: the swappable storage

Goal: ticket persistence behind an interface.

"""Ticket persistence behind a Repository interface.

ParkingLot only talks to TicketRepository. The in-memory version below is
what tests and demos use; a Postgres version would implement the same three
methods and slot in without touching ParkingLot.
"""
from __future__ import annotations

from abc import ABC, abstractmethod

from .domain import Ticket
from .exceptions import TicketNotFoundError


class TicketRepository(ABC):
    """Storage contract for tickets."""

    @abstractmethod
    def save(self, ticket: Ticket) -> None:
        ...

    @abstractmethod
    def find(self, ticket_id: int) -> Ticket:
        ...

    @abstractmethod
    def remove(self, ticket_id: int) -> None:
        ...


class InMemoryTicketRepository(TicketRepository):
    """Dict-backed repository. NOT thread-safe on its own.

    Thread safety is owned by ParkingLot, which holds its lock across every
    repository call. Sharing this repository across lots without an external
    lock is not supported.
    """

    def __init__(self) -> None:
        self._tickets: dict[int, Ticket] = {}

    def save(self, ticket: Ticket) -> None:
        self._tickets[ticket.ticket_id] = ticket

    def find(self, ticket_id: int) -> Ticket:
        try:
            return self._tickets[ticket_id]
        except KeyError:
            raise TicketNotFoundError(f"unknown ticket id {ticket_id}") from None

    def remove(self, ticket_id: int) -> None:
        try:
            del self._tickets[ticket_id]
        except KeyError:
            raise TicketNotFoundError(f"unknown ticket id {ticket_id}") from None

What to notice. The docstring states the thread-safety contract plainly: this class is not thread-safe, and that is fine, because ParkingLot holds its lock across every call. Documenting who owns the lock matters more than the lock itself.

Step 6 — parking_lot/parking_lot.py: the facade with the lock

Goal: the one class callers use. Entry, exit, display — all under one lock.

"""The ParkingLot facade: the one class callers talk to.

Thread safety: every public method takes ``self._lock`` for its whole body,
so a spot can never be handed to two vehicles at once and the free-spot
display can never be read mid-assignment. Spot/Floor/Ticket objects are only
touched while the lock is held, so they stay simple and lock-free.
"""
from __future__ import annotations

import itertools
import logging
import threading
from collections.abc import Callable
from datetime import datetime, timezone

from .config import LotConfig, SpotSize
from .domain import Floor, Spot, Ticket, Vehicle
from .exceptions import LotFullError, ParkingError, PaymentError
from .pricing import PricingStrategy
from .repository import TicketRepository

logger = logging.getLogger(__name__)


class ParkingLot:
    """Coordinates floors, pricing, tickets, and the entry/exit panels.

    Dependencies arrive through the constructor (dependency inversion):
    a repository, a pricing strategy, a config, and a clock. Tests inject
    fakes for each; production code passes the real ones.
    """

    def __init__(
        self,
        repository: TicketRepository,
        pricing: PricingStrategy,
        config: LotConfig | None = None,
        clock: Callable[[], datetime] | None = None,
    ) -> None:
        self._config = config or LotConfig()
        self._repository = repository
        self._pricing = pricing
        self._clock = clock or (lambda: datetime.now(timezone.utc))
        self._floors = [
            Floor(n + 1, self._config.spots_per_floor)
            for n in range(self._config.floors)
        ]
        self._ids = itertools.count(1)
        self._lock = threading.Lock()

    # -- entry panel --------------------------------------------------------

    def park(self, vehicle: Vehicle) -> Ticket:
        """Park a vehicle. Returns its ticket.

        Picks the smallest spot that fits, on the lowest floor, nearest the
        entrance. Raises LotFullError when nothing fits.
        """
        with self._lock:
            spot = self._find_spot(vehicle)
            if spot is None:
                logger.warning("lot full for %s", vehicle.vehicle_type.name)
                raise LotFullError(f"no free spot fits {vehicle.vehicle_type.name}")
            spot.assign(vehicle)
            ticket = Ticket(
                ticket_id=next(self._ids),
                vehicle=vehicle,
                spot_id=spot.spot_id,
                entry_time=self._clock(),
            )
            self._repository.save(ticket)
            logger.info("parked %s at %s", vehicle.license_plate, spot.spot_id)
            return ticket

    # -- exit panel ----------------------------------------------------------

    def exit(self, ticket_id: int, payment_cents: int) -> int:
        """Close a ticket and free its spot. Returns change in cents.

        Raises TicketNotFoundError for a bad id, PaymentError when the
        payment is negative or below the fee.
        """
        with self._lock:
            if payment_cents < 0:
                raise PaymentError("payment_cents must not be negative")
            ticket = self._repository.find(ticket_id)
            now = self._clock()
            fee = self._pricing.fee_cents(
                ticket.vehicle.vehicle_type, ticket.entry_time, now
            )
            if payment_cents < fee:
                logger.warning(
                    "underpayment on ticket %d: paid %d, fee %d",
                    ticket_id, payment_cents, fee,
                )
                raise PaymentError(f"paid {payment_cents}c, fee is {fee}c")
            ticket.close(now, fee)
            self._repository.remove(ticket_id)
            self._spot(ticket.spot_id).release()
            logger.info("ticket %d closed, fee %dc, change %dc",
                        ticket_id, fee, payment_cents - fee)
            return payment_cents - fee

    # -- display panel -------------------------------------------------------

    def free_spots(self) -> dict[int, dict[SpotSize, int]]:
        """Free-spot counts per floor, for the entrance display board."""
        with self._lock:
            return {floor.number: floor.free_counts() for floor in self._floors}

    # -- internals (always called with the lock held) ------------------------

    def _find_spot(self, vehicle: Vehicle) -> Spot | None:
        for floor in self._floors:
            spot = floor.find_free_spot(vehicle)
            if spot is not None:
                return spot
        return None

    def _spot(self, spot_id: str) -> Spot:
        for floor in self._floors:
            for spot in floor.spots:
                if spot.spot_id == spot_id:
                    return spot
        raise ParkingError(f"spot {spot_id} does not exist")  # pragma: no cover

What to notice. The allocation rule is one loop: floors in order, first fitting spot wins. Smallest-fit comes free because spots are stored nearest-first and can_fit rejects oversized vehicles for small spots. Wait — check that claim. Spots ordered nearest-first: COMPACT, COMPACT, REGULAR, REGULAR, LARGE. A motorcycle takes the first free spot it fits, which is the nearest COMPACT. A car skips COMPACTs (cannot fit) and takes the nearest REGULAR. So "smallest fitting, nearest entrance" really is one linear scan. Also note: a failed exit (underpayment) leaves the ticket open — the driver can pay properly without losing the ticket.

class TestConcurrency(unittest.TestCase):
    def test_concurrent_park_never_double_books(self):
        capacity = 10
        lot, _ = make_lot(
            floors=1, spots_per_floor=(SpotSize.LARGE,) * capacity
        )
        barrier = threading.Barrier(20)
        results: list = []
        errors: list = []

        def worker(i: int) -> None:
            barrier.wait()  # release all threads at once
            try:
                results.append(lot.park(Vehicle(f"T-{i}", VehicleType.TRUCK)))
            except ParkingError as exc:
                errors.append(exc)

        threads = [threading.Thread(target=worker, args=(i,)) for i in range(20)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()

        # exactly `capacity` succeeded, each on a distinct spot
        self.assertEqual(len(results), capacity)
        self.assertEqual(len({t.spot_id for t in results}), capacity)
        # the rest were cleanly rejected, not crashed
        self.assertEqual(len(errors), 10)
        self.assertTrue(all(isinstance(e, LotFullError) for e in errors))

8. Enterprise checklist, mapped to the code

  1. Single Responsibility. Spot owns fit + occupancy; Floor owns ordering + search; Ticket owns lifecycle; HourlyPricing owns fee math; ParkingLot owns coordination + the lock. Each has one reason to change.
  2. Open/Closed. New pricing = new PricingStrategy subclass (pricing.py). New storage = new TicketRepository (repository.py). ParkingLot is never edited.
  3. Liskov. InMemoryTicketRepository and HourlyPricing are usable anywhere their interfaces are expected — the tests prove it by injecting them into ParkingLot.
  4. Dependency inversion. ParkingLot.__init__ takes repository, pricing, config, and clock. It creates none of them.
  5. Custom exception hierarchy. ParkingError with LotFullError, TicketNotFoundError, PaymentError, InvalidVehicleError (exceptions.py). No bare except anywhere.
  6. logging, not print. Library code logs (parking_lot.py); print appears only in __main__.py.
  7. Input validation at boundaries. Vehicle.__post_init__ rejects blank plates; LotConfig.__post_init__ rejects bad configs; exit() rejects negative payments; Ticket.close rejects time travel.
  8. Config via dataclass. LotConfig: floors, layout, rates, grace period. Zero magic numbers elsewhere.
  9. Composition over inheritance. ParkingLot has floors, a repository, and a strategy. The only inheritance is interface → implementation.
  10. Thread-safety. One threading.Lock in ParkingLot, held for whole public methods (parking_lot.py). InMemoryTicketRepository documents that it is not thread-safe alone.
  11. Repository pattern. TicketRepository ABC + InMemoryTicketRepository (repository.py); swappable.
  12. unittest suite. 24 tests, stdlib only, edge cases included (underpayment keeps the ticket; truck vs. compact-only lot).

9. Common interview follow-ups

Why one lock instead of a lock per floor? Simplicity beats granularity here. Every operation is microseconds of in-memory work; lock contention is negligible. Per-floor locks would add deadlock risk (a truck scan touches every floor) for no measurable gain.

What if two lots share one repository? Documented as unsupported: InMemoryTicketRepository is not thread-safe alone. A shared repository would need its own lock or a real database.

How would you add EV charging spots? New SpotSize.CHARGING, extend the _FIT table, done. Allocation, pricing, and display all read the same table. No existing code changes.

Hourly ceiling — is that fair to the customer? It is the stated business rule, encoded in one place (HourlyPricing). Changing to per-minute billing is a new strategy class.

Where does the ticket id come from in production? itertools.count is fine for a demo. Production would use a database sequence or UUID from the repository, so ids survive restarts.

Type along. Every line in this chapter is yours to type — no step asks you to read code you didn't write yourself. By the end you will have a working elevator controller for a building with N floors and M elevators, with dispatching, LOOK scheduling, and a full test suite. All 24 tests pass on CPython 3.13.16.

1. The problem

Design the control software for the elevators in an office building. Passengers press hall buttons on landings (floor plus desired direction) and car buttons inside the elevator (destination floor). The system assigns each hall call to the best elevator, moves every car efficiently, and never strands a request. The simulation must be deterministic so every behavior is exactly testable.

2. Requirements

Functional

  • The building has N floors and M elevators, both configurable.
  • A hall call names a floor and a direction (up/down). The dispatcher assigns it to exactly one elevator.
  • A car call names an elevator and a destination floor.
  • An elevator serves all its targets using the LOOK algorithm: it keeps moving in its current direction while requests remain ahead, then reverses.
  • Doors open when the car reaches a target floor and close after a configured number of ticks.
  • Observers can subscribe to arrival and floor-passed events.

Non-functional

  • Deterministic simulation: movement advances on tick(), never on wall-clock time or sleeps. Tests must be exact.
  • Thread-safe dispatch: concurrent hall calls from many threads must not corrupt the queues or the request log.
  • Invalid input fails fast with a domain exception, never silently.
  • The dispatch policy must be swappable without editing the dispatcher.
  • Persistence of the request history goes behind an interface, so a database can replace the in-memory log later.

5. Key design decisions

LOOK, not SCAN, moves the cars. Both algorithms serve requests in the current direction of travel. They differ at the turnaround: SCAN keeps going to the terminal floor (top or bottom) before reversing, even with no requests up there. LOOK reverses at the last outstanding request. That saves empty travel, so real controllers use LOOK. The test test_look_reverses_at_last_request_not_terminal_floor pins this: a car with one target at floor 5 in a 10-floor building never rises above 5.

The car is a state machine, not a pile of flags. ElevatorState has four states: IDLE, MOVING_UP, MOVING_DOWN, DOORS_OPEN. Every tick() moves through exactly one transition. A boolean like is_moving would have let "moving with doors open" exist as a representable state. The enum makes illegal states unrepresentable.

Strategy for dispatch. Dispatcher owns the process (validate → log → assign) and DispatchStrategy owns the policy (which car). A new policy — say, "fewest stops" or a machine-learned scorer — is a new class. The dispatcher never changes. That is the Strategy pattern earning its place, and the Open/Closed principle along with it.

Observer for events. Elevator publishes arrived / passed events to ElevatorListeners. The car never knows who listens — tests, a dashboard, a future analytics feed all attach the same way. One broken listener can't stop the car: _notify catches and logs listener failures.

Repository for the request log. The dispatcher logs every hall call through RequestRepository. The in-memory version is enough for tests; a database-backed one slots in without touching dispatch logic. Dependency inversion: the dispatcher receives the repository in its constructor instead of building one.

Deterministic time. tick() advances the simulation. No time.sleep anywhere in library code. This is what makes 24 tests run in 11 milliseconds and assert exact floors.

Frozen dataclasses for requests. HallCall and CarCall can't be mutated after creation, so they're safe to share across threads and to store in the log.

Facade. Building is the front door. Callers never construct an Elevator or Dispatcher themselves.

"""Request value objects: what a passenger asks for.

Two kinds exist in every real elevator system, and confusing them is the

Step 3 — listeners.py: the Observer seam

Goal: define how the elevator publishes events without knowing its audience.

"""Observer support for elevator events.

An Elevator never knows who is watching it. It just publishes events --
"arrived" when the doors open, "passed" when it moves through a floor --
and every registered listener gets called. Tests, dashboards, and
dispatchers all listen the same way, which keeps the car decoupled from
its observers.
"""

from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass(frozen=True)
class ElevatorEvent:
    elevator_id: int
    kind: str  # "arrived" or "passed"
    floor: int


class ElevatorListener(ABC):
    """Anything that wants elevator events implements this one method."""

    @abstractmethod
    def update(self, event: ElevatorEvent) -> None:
        """Called synchronously by the elevator, on the ticking thread.

        Keep it fast and never call back into the elevator from here:
        the elevator holds its internal lock while notifying.
        """

What to notice: one method on the interface, not two (on_arrived / on_passed). A single update(event) keeps the interface small — new event kinds don't change the interface. The docstring warns about the lock: notifying while holding the lock is a deliberate choice for determinism, and the price is that listeners must not call back in.

Step 4 — elevator.py: the car

Goal: build the state machine and LOOK movement — the heart of the chapter.

"""One elevator car.

Movement is deterministic: each call to tick() advances the car by exactly
one floor, or counts down the door timer. No sleeps, no background
threads inside this class. That is what makes the behaviour exactly
testable -- the test, not the wall clock, drives time.
"""

import logging
import threading

from elevator_types import Direction, ElevatorState, InvalidFloorError
from listeners import ElevatorEvent, ElevatorListener

log = logging.getLogger(__name__)


class Elevator:
    """A single car serving a set of target floors.

    Scheduling uses LOOK: the car keeps moving in its current direction
    while targets remain ahead, and reverses only when nothing is left
    ahead. It does NOT travel to the terminal floor first -- that would
    be SCAN. LOOK wastes less travel, which is why real controllers and
    this chapter use it.
    """

    def __init__(
        self, elevator_id: int, num_floors: int, door_open_ticks: int = 2
    ) -> None:
        if not isinstance(num_floors, int) or isinstance(num_floors, bool) or num_floors < 2:
            raise InvalidFloorError(
                f"num_floors must be an int >= 2, got {num_floors!r}"
            )
        if (
            not isinstance(door_open_ticks, int)
            or isinstance(door_open_ticks, bool)
            or door_open_ticks < 1
        ):
            raise InvalidFloorError(
                f"door_open_ticks must be an int >= 1, got {door_open_ticks!r}"
            )
        self.id = elevator_id
        self.num_floors = num_floors
        self.floor = 1
        self.state = ElevatorState.IDLE
        self.direction = Direction.UP
        self._door_open_ticks = door_open_ticks
        self._targets: set[int] = set()
        self._listeners: list[ElevatorListener] = []
        self._door_timer = 0
        self._lock = threading.Lock()

    # ------------------------------------------------------------------
    # Public API
    # ------------------------------------------------------------------

    def add_target(self, floor: int) -> None:
        """Record a floor the car must visit (from a hall call or car call)."""
        self._validate_floor(floor)
        with self._lock:
            self._targets.add(floor)
            log.debug("elevator %s: target added (floor %s)", self.id, floor)

    def add_listener(self, listener: ElevatorListener) -> None:
        with self._lock:
            self._listeners.append(listener)

    @property
    def targets(self) -> frozenset[int]:
        """Snapshot of outstanding targets (a copy -- safe to read)."""
        with self._lock:
            return frozenset(self._targets)

    def tick(self) -> None:
        """Advance the simulation by one step."""
        with self._lock:
            if self.state is ElevatorState.DOORS_OPEN:
                self._door_timer -= 1
                if self._door_timer <= 0:
                    self._resume_after_doors()
                return
            if self.floor in self._targets:
                self._open_doors()
                return
            if not self._targets:
                self.state = ElevatorState.IDLE
                return
            if self.state is ElevatorState.IDLE:
                self._choose_initial_direction()
            self._move_one_floor()

    # ------------------------------------------------------------------
    # Internals -- every method below runs with self._lock held.
    # ------------------------------------------------------------------

    def _validate_floor(self, floor: int) -> None:
        if (
            not isinstance(floor, int)
            or isinstance(floor, bool)
            or not 1 <= floor <= self.num_floors
        ):
            raise InvalidFloorError(
                f"floor must be an int in 1..{self.num_floors}, got {floor!r}"
            )

    def _open_doors(self) -> None:
        self._targets.discard(self.floor)
        self.state = ElevatorState.DOORS_OPEN
        self._door_timer = self._door_open_ticks
        log.info("elevator %s: doors open at floor %s", self.id, self.floor)
        self._notify(ElevatorEvent(elevator_id=self.id, kind="arrived", floor=self.floor))

    def _resume_after_doors(self) -> None:
        if not self._targets:
            self.state = ElevatorState.IDLE
            return
        # LOOK keeps the current direction after the doors close.
        # _move_one_floor() reverses only if nothing remains ahead.
        self.state = (
            ElevatorState.MOVING_UP
            if self.direction is Direction.UP
            else ElevatorState.MOVING_DOWN
        )

    def _choose_initial_direction(self) -> None:
        above = [t for t in self._targets if t > self.floor]
        below = [t for t in self._targets if t < self.floor]
        if above and below:
            nearest_up = min(above) - self.floor
            nearest_down = self.floor - max(below)
            # Tie goes up: an arbitrary but deterministic rule.
            self.direction = (
                Direction.UP if nearest_up <= nearest_down else Direction.DOWN
            )
        elif above:
            self.direction = Direction.UP
        elif below:
            self.direction = Direction.DOWN

    def _move_one_floor(self) -> None:
        if self.direction is Direction.UP:
            if not any(t > self.floor for t in self._targets):
                self.direction = Direction.DOWN  # LOOK reversal
        else:
            if not any(t < self.floor for t in self._targets):
                self.direction = Direction.UP  # LOOK reversal
        self.floor += 1 if self.direction is Direction.UP else -1
        self.state = (
            ElevatorState.MOVING_UP
            if self.direction is Direction.UP
            else ElevatorState.MOVING_DOWN
        )
        log.debug(
            "elevator %s: passing floor %s (%s)",
            self.id,
            self.floor,
            self.direction.name,
        )
        self._notify(ElevatorEvent(elevator_id=self.id, kind="passed", floor=self.floor))

    def _notify(self, event: ElevatorEvent) -> None:
        for listener in list(self._listeners):
            try:
                listener.update(event)
            except Exception:
                # One broken listener must not stop the car or the others.
                log.exception("elevator %s: listener %r failed", self.id, listener)

What to notice: three things. First, the tick() order matters: doors first, then arrival check, then idle check, then move. Each branch returns, so exactly one thing happens per tick. Second, the LOOK reversal lives in exactly one place — _move_one_floor flips direction only when no target remains ahead. The car never "decides" to go to the top floor. Third, targets returns a frozenset copy: callers can read the car's mind but can't reach in and mutate it. That's encapsulation doing its job.

One honest note: _notify catches Exception, not bare except:. Catching Exception still lets KeyboardInterrupt and SystemExit through — that's the point. A bare except: would swallow those too, which is why the checklist bans it.

from elevator_types import ElevatorState

for _ in range(6): car.tick()
print('floor:', car.floor, '| state:', car.state.name)

Step 5 — repository.py: the persistence seam

Goal: log hall calls behind an interface so storage can change later.

"""Persistence seam for request history (Repository pattern).

The dispatcher logs every hall call it receives. Where the log goes is
not the dispatcher's business -- that decision lives behind this
interface. The in-memory version serves tests and the demo; a database
version could be dropped in later without touching the dispatcher.
"""

from abc import ABC, abstractmethod
import threading

from request import CarCall, HallCall

LoggedRequest = HallCall | CarCall


class RequestRepository(ABC):
    @abstractmethod
    def save(self, request: LoggedRequest) -> None:
        """Append one request to the log."""

    @abstractmethod
    def all(self) -> list[LoggedRequest]:
        """Return every logged request, oldest first."""


class InMemoryRequestRepository(RequestRepository):
    """Thread-safe list-backed log. Good for tests, demos, and interviews."""

    def __init__(self) -> None:
        self._items: list[LoggedRequest] = []
        self._lock = threading.Lock()

    def save(self, request: LoggedRequest) -> None:
        with self._lock:
            self._items.append(request)

    def all(self) -> list[LoggedRequest]:
        with self._lock:
            return list(self._items)

What to notice: all() returns list(self._items) — a copy. If it returned the live list, any caller could corrupt the log. Defensive copies at boundaries are cheap and kill a whole class of bugs. HallCall | CarCall in the type alias needs Python 3.10+; on 3.13 it's native syntax.

Step 6 — dispatch.py: assigning hall calls

Goal: validate, log, and assign each hall call to the best car — safely from many threads.

"""Hall-call dispatch: choosing which elevator serves a request.

The Dispatcher owns the decision *process* (validate, log, assign) while
a DispatchStrategy owns the *policy* (which car is best). Swapping the
policy never touches the process -- that is the Strategy pattern, and it
is also the Open/Closed principle in action.
"""

import logging
import threading
from abc import ABC, abstractmethod

from elevator_types import (
    Direction,
    ElevatorState,
    InvalidFloorError,
    InvalidRequestError,
)
from elevator import Elevator
from repository import InMemoryRequestRepository, RequestRepository
from request import HallCall

log = logging.getLogger(__name__)


class DispatchStrategy(ABC):
    @abstractmethod
    def choose(
        self, elevators: list[Elevator], floor: int, direction: Direction
    ) -> Elevator:
        """Return the elevator that should serve this hall call."""


class NearestDispatchStrategy(DispatchStrategy):
    """Pick the car with the lowest service cost.

    An idle car costs its distance. A car already moving toward the caller
    in the same direction costs its distance too -- it will pass the floor
    anyway. Anything else pays its distance plus a full building height as
    a penalty, so it only wins when nothing better exists.
    """

    def choose(
        self, elevators: list[Elevator], floor: int, direction: Direction
    ) -> Elevator:
        def cost(car: Elevator) -> int:
            distance = abs(car.floor - floor)
            if car.state is ElevatorState.IDLE:
                return distance
            moving_toward = car.direction is direction and (
                (direction is Direction.UP and car.floor <= floor)
                or (direction is Direction.DOWN and car.floor >= floor)
            )
            if moving_toward:
                return distance
            return distance + 2 * car.num_floors

        return min(elevators, key=cost)


class Dispatcher:
    """Receives hall calls and assigns each to one elevator.

    Thread-safety: a single lock serializes hall_call(). The strategy's
    reads of elevator state assume one simulation thread drives tick();
    run tick() from exactly one thread and this class is safe.
    """

    def __init__(
        self,
        elevators: list[Elevator],
        strategy: DispatchStrategy | None = None,
        repository: RequestRepository | None = None,
    ) -> None:
        if not elevators:
            raise InvalidRequestError("dispatcher needs at least one elevator")
        self._elevators = list(elevators)
        self._num_floors = max(car.num_floors for car in elevators)
        self._strategy = strategy or NearestDispatchStrategy()
        self._repository = (
            repository if repository is not None else InMemoryRequestRepository()
        )
        self._lock = threading.Lock()

    @property
    def repository(self) -> RequestRepository:
        return self._repository

    def hall_call(self, floor: int, direction: Direction) -> int:
        """Assign a hall call; return the chosen elevator's id."""
        if not isinstance(direction, Direction):
            raise InvalidRequestError(
                f"direction must be a Direction, got {direction!r}"
            )
        if (
            not isinstance(floor, int)
            or isinstance(floor, bool)
            or not 1 <= floor <= self._num_floors
        ):
            raise InvalidFloorError(
                f"floor must be an int in 1..{self._num_floors}, got {floor!r}"
            )
        with self._lock:
            call = HallCall(floor=floor, direction=direction)
            self._repository.save(call)
            chosen = self._strategy.choose(self._elevators, floor, direction)
            chosen.add_target(floor)
            log.info(
                "hall call floor %s %s -> elevator %s",
                floor,
                direction.name,
                chosen.id,
            )
            return chosen.id

What to notice: the cost function is the whole policy in ten lines. Read it as plain English: idle cars cost their distance; cars already coming toward you cost their distance; everyone else pays a penalty of two building-heights. The penalty is deliberately huge — a car moving away only wins if it's the only car. And the lock: hall_call() is the one method many threads can hit at once, so it's the one method that takes the lock. Locking is surgical, not blanket.

Checkpoint:

python3 -c "

from elevator_types import Direction

print('chosen elevator:', d.hall_call(9, Direction.UP))
"

Expected: chosen elevator: 0 — both cars idle at floor 1, a tie, and min keeps the first.

Step 7 — building.py: the facade

Goal: wire everything together behind one front door, with all tunables in a config dataclass.

"""Facade: a building with N floors and M elevators.

Building is the front door of the system. Callers never touch Elevator
or Dispatcher directly -- they talk to the building, and the building
wires everything together from one config object.
"""

import logging
from dataclasses import dataclass

from dispatch import Dispatcher, DispatchStrategy
from elevator import Elevator
from elevator_types import (
    Direction,
    ElevatorState,
    InvalidFloorError,
    InvalidRequestError,
)
from listeners import ElevatorListener
from repository import InMemoryRequestRepository, RequestRepository

log = logging.getLogger(__name__)


@dataclass(frozen=True)
class BuildingConfig:
    """Every tunable number in the system lives here -- no magic numbers
    scattered through the code."""

    num_floors: int = 10
    num_elevators: int = 2
    door_open_ticks: int = 2

    def __post_init__(self) -> None:
        for name, value, minimum in (
            ("num_floors", self.num_floors, 2),
            ("num_elevators", self.num_elevators, 1),
            ("door_open_ticks", self.door_open_ticks, 1),
        ):
            if not isinstance(value, int) or isinstance(value, bool) or value < minimum:
                raise InvalidFloorError(
                    f"{name} must be an int >= {minimum}, got {value!r}"
                )


class Building:
    """Owns the elevators and the dispatcher; the type-along entry point.

    Thread-safety: safe for many threads to call hall_call()/car_call()
    at once. Drive tick() from a single thread -- the elevator and
    dispatcher locks are built around that model, and the chapter says so
    wherever it matters.
    """

    def __init__(
        self,
        config: BuildingConfig = BuildingConfig(),
        strategy: DispatchStrategy | None = None,
        repository: RequestRepository | None = None,
    ) -> None:
        self.config = config
        self.elevators = [
            Elevator(i, config.num_floors, config.door_open_ticks)
            for i in range(config.num_elevators)
        ]
        self.dispatcher = Dispatcher(
            self.elevators,
            strategy=strategy,
            repository=repository or InMemoryRequestRepository(),
        )

    def hall_call(self, floor: int, direction: Direction) -> int:
        """A passenger on a landing presses the button. Returns the car's id."""
        return self.dispatcher.hall_call(floor, direction)

    def car_call(self, elevator_id: int, floor: int) -> None:
        """A passenger inside a car presses a destination floor."""
        if (
            not isinstance(elevator_id, int)
            or isinstance(elevator_id, bool)
            or not 0 <= elevator_id < len(self.elevators)
        ):
            raise InvalidRequestError(
                f"elevator_id must be in 0..{len(self.elevators) - 1}, "
                f"got {elevator_id!r}"
            )
        self.elevators[elevator_id].add_target(floor)

    def add_listener(self, elevator_id: int, listener: ElevatorListener) -> None:
        self.elevators[elevator_id].add_listener(listener)

    @property
    def request_log(self) -> list:
        """Every hall call received so far, oldest first."""
        return self.dispatcher.repository.all()

    def tick(self) -> None:
        """Advance every elevator by one simulation step."""
        for car in self.elevators:
            car.tick()

9. Common interview follow-ups

Why LOOK instead of SCAN? SCAN rides to the terminal floor before reversing, even with no requests there. LOOK reverses at the last outstanding request. Less empty travel, same fairness within a sweep. Our test pins the difference: target at 5 in a 10-floor building, car never passes 5.

How do you prevent starvation? Pure LOOK can starve a floor if new requests keep arriving ahead of it. Production fixes: cap how long a request waits and then force-serve it, or age requests into higher priority. Our dispatcher could take request age into the cost function — that's a natural Strategy upgrade.

What if two elevators tie? min() keeps the first, so the lower id wins. Deterministic, which is what you want in a test. A production system might break ties by least recent use.

How would this handle 100 elevators? Dispatch is O(M) per hall call — fine. The real scaling question is the strategy: with many cars you'd add zoning (cars serve floor ranges) as another DispatchStrategy, no dispatcher changes.

Why is tick() better than threads + sleeps? Determinism. With tick(), a test asserts the exact floor after N steps. With sleeps, tests are flaky and slow. The tradeoff: a real deployment needs a timer loop calling tick() once per second — the simulation core stays identical.

Where would persistence actually go? The request log behind RequestRepository. A Postgres implementation would save() each hall call in a transaction. The dispatcher wouldn't change — that's the point of the seam.

Chapter 3: Traffic Light System

Type along. This chapter builds the controller for a two-road intersection (north-south and east-west) as a proper state machine: every legal transition written down in a table, illegal transitions refused with an exception. Pedestrian buttons, an emergency override, and a full 23-test suite included. All tests pass on CPython 3.13.16.

1. The problem

Control the signals at an intersection of two roads, NS and EW. The lights cycle NS green → yellow → all-red → EW green → yellow → all-red, repeating forever. A pedestrian button must get walkers across safely. An emergency vehicle must be able to force the intersection. And like the elevator chapter, everything runs on injected virtual time so tests are exact.

2. Requirements

Functional

  • The controller cycles NS_GREEN → NS_YELLOW → ALL_RED → EW_GREEN → EW_YELLOW → ALL_RED, forever.
  • The transition table is explicit: any transition not in the table raises IllegalTransitionError.
  • ALL_RED is a real phase with a real duration — the intersection must empty before cross traffic moves.
  • A pedestrian button records a request; the design serves it by extending a green phase (choice stated in §5).
  • Emergency override forces all-red except the emergency route, which holds green until a human clears it. Clearing returns through ALL_RED.
  • Observers are notified on every phase change.

Non-functional

  • Deterministic timing: the controller advances on tick(seconds), never on wall-clock time. Tests run the whole cycle in virtual seconds.
  • All durations come from a validated config dataclass — no magic numbers.
  • Shared state is guarded by a lock; concurrent ticks and button presses must be safe.
  • Invalid input (bad road name, negative seconds, impossible transition) raises a domain exception.

5. Key design decisions

The transition table is data, not code. _TRANSITIONS maps each phase to the set of phases it may move to. transition_to() checks membership and raises IllegalTransitionError otherwise. The automatic cycle (_next_phase) routes through the same check, so the machine can't drift from its own table. Why data? A table is auditable at a glance; an if-chain hides the machine's shape. In an interview, pointing at the table and reading the whole state machine aloud is a strong moment.

Why ALL_RED exists. When NS goes yellow then red, cars are still inside the intersection — someone always runs the yellow. If EW went green the instant NS went red, cross traffic would meet the stragglers. ALL_RED is the clearance interval: every direction red for a few seconds so the intersection empties before anyone new enters. It's a safety invariant, not politeness. That's why skipping yellow straight to ALL_RED is illegal in our table — the yellow warning is part of the same safety story.

Pedestrian choice: extend the green. Two honest options exist: insert a dedicated WALK phase, or make the next green longer. This design extends the green — if the road is green now, it grows immediately; otherwise the request waits and extends that road's next green. Why this one? No new states, no interruption of a green already flowing, and the extension is one number added to one duration. A WALK phase would add states, transitions, and a second timer to the table. Simpler machine, same safety.

Emergency override is a command, not a transition. emergency_override() doesn't go through the transition table — it forces the phase directly, because an emergency doesn't ask the machine's permission. But clear_emergency() DOES go through the table (emergency → ALL_RED only), so recovery is still disciplined. After clearing, the road that did NOT have the emergency gets the next green: the emergency route just held green for a long time, so fairness gives cross traffic the next turn.

Injected time. tick(seconds) is the whole clock. Tests run a full cycle in virtual seconds; a deployment calls tick(1) from a one-second timer loop. Same code, two time sources. This is dependency inversion applied to time.

Observer for phase changes. SignalListener.update(phase) fires on every transition, including emergency overrides. A listener that throws can't break the controller — _notify catches and logs.

"""Timing configuration for the signal controller.

Every duration the controller uses comes from here. Nothing in
controller.py hard-codes a number of seconds, which means a test can run
the whole cycle in milliseconds and a city engineer can retime the
intersection without touching logic.
"""

from dataclasses import dataclass

from exceptions import InvalidConfigError


@dataclass(frozen=True)
class SignalConfig:
    ns_green: int = 30       # north-south green, seconds
    ew_green: int = 30       # east-west green, seconds
    yellow: int = 4          # clearance warning before red
    all_red: int = 2         # both directions red: intersection empties
    ped_extension: int = 10  # extra green when a pedestrian is waiting

    def __post_init__(self) -> None:
        for name in ("ns_green", "ew_green", "yellow", "all_red", "ped_extension"):
            value = getattr(self, name)
            if (
                not isinstance(value, int)
                or isinstance(value, bool)
                or value <= 0
            ):
                raise InvalidConfigError(
                    f"{name} must be a positive int of seconds, got {value!r}"
                )

What to notice: frozen means nobody can retime the intersection by mutating the config mid-cycle — a new config means a new controller, which is exactly the semantics you want. The validation loop reads each field with getattr instead of repeating five near-identical ifs. And 1.5 seconds is rejected: durations are ints, because the controller counts whole seconds and a float would silently truncate somewhere.

Step 3 — controller.py: the state machine

Goal: build the controller — transition table, tick, pedestrian, emergency.

"""A deterministic traffic-signal controller: a real state machine.

The normal cycle is:

    NS_GREEN -> NS_YELLOW -> ALL_RED -> EW_GREEN -> EW_YELLOW -> ALL_RED -> ...

Every arrow above is written down in _TRANSITIONS. There is no "next
phase" arithmetic hiding in an if-chain: if a transition is not in the
table, transition_to() refuses it with IllegalTransitionError.

Time is injected, not read: tick(seconds) advances the clock by whatever
the caller says. Tests drive the whole cycle in virtual seconds, so they
are exact and instant. A real deployment would call tick() from a timer
loop once per second.
"""

import logging
import threading
from abc import ABC, abstractmethod

from config import SignalConfig
from exceptions import (
    IllegalTransitionError,
    InvalidRoadError,
    Phase,
    SignalError,
)

log = logging.getLogger(__name__)

ROADS = ("NS", "EW")


class SignalListener(ABC):
    """Observer: notified on every phase change."""

    @abstractmethod
    def update(self, phase: Phase) -> None:
        """Called synchronously on the ticking thread; keep it fast."""


class TrafficController:
    """Owns the current phase and moves it forward on tick().

    Pedestrian choice (stated up front): a button press extends the green
    phase for that road by config.ped_extension seconds. If the road is
    green right now, the current green grows immediately; otherwise the
    request waits and extends that road's next green. No separate WALK
    phase, no new states -- just a longer green.

    Emergency rule: emergency_override() forces every direction red except
    the emergency route, which goes green and stays green until
    clear_emergency(). Clearing returns to ALL_RED, then the OTHER road
    gets the green -- the emergency route just had an extended green, so
    fairness gives the cross road the next one.
    """

    _TRANSITIONS: dict[Phase, set[Phase]] = {
        Phase.NS_GREEN: {Phase.NS_YELLOW},
        Phase.NS_YELLOW: {Phase.ALL_RED},
        Phase.ALL_RED: {Phase.NS_GREEN, Phase.EW_GREEN},
        Phase.EW_GREEN: {Phase.EW_YELLOW},
        Phase.EW_YELLOW: {Phase.ALL_RED},
        Phase.EMERGENCY_NS: {Phase.ALL_RED},
        Phase.EMERGENCY_EW: {Phase.ALL_RED},
    }

    def __init__(self, config: SignalConfig = SignalConfig()) -> None:
        self._config = config
        self._phase = Phase.NS_GREEN
        self._elapsed = 0
        self._after_all_red = Phase.EW_GREEN  # which green follows ALL_RED
        self._ped_waiting = {"NS": False, "EW": False}
        self._green_extension = 0  # extra seconds on the current green
        self._listeners: list[SignalListener] = []
        self._lock = threading.Lock()

    # ------------------------------------------------------------------
    # Public API
    # ------------------------------------------------------------------

    @property
    def phase(self) -> Phase:
        with self._lock:
            return self._phase

    def add_listener(self, listener: SignalListener) -> None:
        with self._lock:
            self._listeners.append(listener)

    def tick(self, seconds: int = 1) -> None:
        """Advance the clock. Deterministic: the caller owns time."""
        if (
            not isinstance(seconds, int)
            or isinstance(seconds, bool)
            or seconds < 0
        ):
            raise SignalError(f"seconds must be a non-negative int, got {seconds!r}")
        with self._lock:
            if self._phase in (Phase.EMERGENCY_NS, Phase.EMERGENCY_EW):
                return  # emergency holds until a human clears it
            # _enter() resets _elapsed, so carry the leftover in a local.
            remaining = self._elapsed + seconds
            while remaining >= self._duration(self._phase):
                remaining -= self._duration(self._phase)
                self._enter(self._next_phase(self._phase))
            self._elapsed = remaining

    def transition_to(self, phase: Phase) -> None:
        """Force a phase change -- but only one the table allows."""
        with self._lock:
            self._enter(phase)

    def request_pedestrian(self, road: str) -> None:
        """Record a pedestrian waiting to cross `road` ("NS" or "EW").

        If that road is green right now, its green is extended immediately.
        Otherwise the request waits and extends that road's next green.
        """
        self._check_road(road)
        with self._lock:
            current_green = (
                "NS"
                if self._phase is Phase.NS_GREEN
                else "EW"
                if self._phase is Phase.EW_GREEN
                else None
            )
            if current_green == road:
                self._green_extension = self._config.ped_extension
                log.info(
                    "pedestrian crossing %s: green extended by %ss",
                    road,
                    self._green_extension,
                )
            else:
                self._ped_waiting[road] = True
                log.info("pedestrian waiting to cross %s", road)

    def emergency_override(self, road: str) -> None:
        """Give `road` a held green; everything else goes red."""
        self._check_road(road)
        target = Phase.EMERGENCY_NS if road == "NS" else Phase.EMERGENCY_EW
        with self._lock:
            if self._phase is target:
                return
            self._phase = target
            self._elapsed = 0
            self._green_extension = 0
            # Fairness: after the clear, the other road goes first.
            self._after_all_red = (
                Phase.EW_GREEN if road == "NS" else Phase.NS_GREEN
            )
            log.warning("EMERGENCY override: %s green, all else red", road)
            self._notify(target)

    def clear_emergency(self) -> None:
        """End the override; the intersection drains through ALL_RED."""
        with self._lock:
            if self._phase not in (Phase.EMERGENCY_NS, Phase.EMERGENCY_EW):
                raise SignalError("no emergency is active")
            self._enter(Phase.ALL_RED)

    # ------------------------------------------------------------------
    # Internals -- every method below runs with self._lock held.
    # ------------------------------------------------------------------

    @staticmethod
    def _check_road(road: str) -> None:
        if road not in ROADS:
            raise InvalidRoadError(f'road must be "NS" or "EW", got {road!r}')

    def _duration(self, phase: Phase) -> int:
        cfg = self._config
        if phase is Phase.NS_GREEN:
            return cfg.ns_green + self._green_extension
        if phase is Phase.EW_GREEN:
            return cfg.ew_green + self._green_extension
        if phase in (Phase.NS_YELLOW, Phase.EW_YELLOW):
            return cfg.yellow
        if phase is Phase.ALL_RED:
            return cfg.all_red
        return 0  # emergency phases: tick() returns before reading this

    def _next_phase(self, phase: Phase) -> Phase:
        if phase is Phase.NS_GREEN:
            return Phase.NS_YELLOW
        if phase is Phase.NS_YELLOW:
            self._after_all_red = Phase.EW_GREEN
            return Phase.ALL_RED
        if phase is Phase.EW_GREEN:
            return Phase.EW_YELLOW
        if phase is Phase.EW_YELLOW:
            self._after_all_red = Phase.NS_GREEN
            return Phase.ALL_RED
        if phase is Phase.ALL_RED:
            return self._after_all_red
        raise SignalError(f"no automatic successor for {phase.name}")

    def _enter(self, phase: Phase) -> None:
        allowed = self._TRANSITIONS[self._phase]
        if phase not in allowed:
            raise IllegalTransitionError(
                f"illegal transition: {self._phase.name} -> {phase.name}"
            )
        self._phase = phase
        self._elapsed = 0
        if phase in (Phase.NS_GREEN, Phase.EW_GREEN):
            road = "NS" if phase is Phase.NS_GREEN else "EW"
            if self._ped_waiting[road]:
                self._green_extension = self._config.ped_extension
                log.info(
                    "pedestrian crossing %s: green extended by %ss",
                    road,
                    self._green_extension,
                )
            self._ped_waiting[road] = False
        else:
            self._green_extension = 0
        self._notify(phase)

    def _notify(self, phase: Phase) -> None:
        for listener in list(self._listeners):
            try:
                listener.update(phase)
            except Exception:
                log.exception("signal listener %r failed", listener)

8. Enterprise checklist, mapped to the code

  1. Single Responsibility. TrafficController owns phase transitions. SignalConfig owns timing. SignalListener is just notification. The table owns the legal moves.
  2. Open/Closed. New behavior (a WALK phase, a flashing-yellow mode) means new phases and new table rows — the _enter gate and tick() logic don't change.
  3. Liskov. Any SignalListener implementation can be registered; the controller only calls update(phase).
  4. Dependency inversion. The controller receives its SignalConfig in the constructor. Time is injected via tick(seconds) — the controller never reads a clock.
  5. Custom exception hierarchy; no bare excepts. SignalError → IllegalTransitionError / InvalidConfigError / InvalidRoadError (exceptions.py). The one except is except Exception in _notify, so KeyboardInterrupt propagates.
  6. logging, never print, in library code. controller.py logs at INFO/WARNING. print appears only in the if __name__ == "__main__" demo.
  7. Input validation at boundaries. Road names checked in request_pedestrian/emergency_override (_check_road); tick rejects negative/non-int seconds; config rejects non-positive durations; transitions checked against the table.
  8. Config via dataclass. SignalConfig — frozen, validated in __post_init__, no magic numbers in the controller.
  9. Composition over inheritance. The controller composes config + listeners + table. Inheritance appears only for the listener ABC and the exception hierarchy.
  10. Thread-safety. One threading.Lock guards phase, elapsed time, pedestrian flags, and listeners. Documented contract: tick(), button presses, and overrides are all safe from any thread. Proven by test_concurrent_ticks_and_requests_are_safe.
  11. Repository pattern. Doesn't apply here — there's no persistence in a signal controller. (The checklist says "where it applies"; a controller with no stored state needs no repository, and inventing one would be design theater.)
  12. unittest suite incl. edge cases. 23 tests: full cycle, illegal transitions, pedestrian extension and its consumption, emergency hold/clear/switch, concurrency, negative ticks.

9. Common interview follow-ups

Why is ALL_RED a separate phase instead of just "both red"? Because it has a duration and a purpose: the clearance interval. "Both red" as an emergent property of two lights could be zero seconds long. Making it a phase forces the timing plan to account for it and the tests to assert it.

Why is the transition table data instead of if-statements? Readability and enforcement. The table is the complete spec of legal moves in seven lines, and _enter enforces it in one place. Adding a phase means adding rows, not re-reading a chain of conditionals for missed cases.

Pedestrian: why extend the green instead of a WALK phase? Fewer states, no interruption of flowing traffic, one number added to one duration. The tradeoff is honesty: pedestrians don't get a dedicated signal, and a button pressed mid-green for the cross road still waits a full cycle. For a real intersection with heavy foot traffic, the WALK phase would win — and the table is ready for it.

What happens if the pedestrian button is pressed during ALL_RED? The flag waits and extends the next green for that road. The request is never lost: _ped_waiting is only cleared when its road's green is entered.

How would you handle a sensor (cars waiting) instead of fixed timing? The config stays, but green durations become maximums: tick() would also end a green early when the sensor reports no waiting cars. The table doesn't change — only _duration gains a sensor input. That's the table-as-data paying off again.

Emergency during a pedestrian extension? emergency_override zeroes the extension and forces the phase. Safety hierarchy: emergency > pedestrian > normal cycle. The pedestrian flag for the interrupted road survives and extends its next normal green.

Chapter 4: Library Management System

Type every file in order. Run each checkpoint before moving on. All commands run from the project folder (the one holding library/ and tests/). You need Python 3.13 and nothing else — this is stdlib only.

1. The problem

A neighborhood library needs software to track its collection and its lending. Each title can have many physical copies. Members check copies out for 14 days and pay $0.50 for every overdue day when they return late. When every copy of a title is checked out, members can reserve it; the first reserver in line gets notified and a short hold when a copy comes back. Staff need to find books by title, author, or ISBN.

2. Requirements

Functional

  • Register books (ISBN, title, author) and individual lendable copies (barcode).
  • Register members.
  • Check out a copy to a member. Due date = checkout date + 14 days.
  • Return a copy. Compute the overdue fine at $0.50/day.
  • Enforce a maximum of 5 active loans per member, checked at checkout time.
  • Reserve a title only when no copy is available. One FIFO queue per title.
  • On return, if reservations exist: notify the first reserver and hold the copy for 3 days. Only the hold's owner can check it out.
  • Search the catalog by title, author, or ISBN (case-insensitive substring).

Non-functional

  • Time must be injectable. Domain logic never calls date.today() directly, so tests freeze time instead of depending on the real calendar.
  • Checkout and return must be safe under concurrent threads.
  • Storage lives behind repository interfaces. In-memory today, a database tomorrow, with no changes to the business rules.
  • Domain failures use a typed exception hierarchy. No bare except.
  • Stdlib only: dataclasses, threading, logging, unittest, abc.

5. Key design decisions

  1. Book and BookCopy are separate classes. A library lends physical items, not titles. One class can't say "2 of 5 copies are out" without turning into a mess of counters. The split also matches how real library systems model the world: bibliographic record vs. item record.
  2. Loan is a first-class record, not a flag on the copy. A status flag can't answer "who had this last month, and was it late?" The loan carries the dates, so history and fines have a home.
  3. The fine is a Strategy (FinePolicy). Rates change. A new policy is a new class implementing fine_for; the service never gets edited. That is the Open/Closed principle doing actual work.
  4. The clock is injected. Loan.overdue_days takes the date as an argument, and the service takes a Clock. Tests freeze time with FixedClock. Without this, every fine test would depend on the real calendar — slow, flaky, unreadable.
  5. Reservations are FIFO queues with an Observer notifier. FIFO is the fairness rule. The notifier is an observer: the service announces "hold ready" and doesn't care whether that's a log line today or an email tomorrow.
  6. Holds expire lazily. When checkout runs, it flips expired holds back to available. No background sweeper thread for something this small — simpler to reason about, nothing to schedule.
  7. The service owns cross-aggregate rules; repositories own storage. "Max 5 loans" touches members and loans, so it lives in the service. "Find copies of this ISBN" is storage, so it lives in the catalog.
  8. One RLock in the service. Checkout touches three repositories. The lock makes the whole operation atomic, so two threads can't take the last copy at once.

Patterns, and why each earns its place. Strategy for fines: rates vary independently of lending. Observer for hold notifications: the service shouldn't know how members get told. Repository for all persistence: the in-memory dicts become SQL later without touching rules. The service itself is a thin facade over those pieces.

is a physical item (one row per barcode). A library lends copies, not titles.
"""
from dataclasses import dataclass
from datetime import date

from .config import CopyStatus


@dataclass
class Book:
    isbn: str
    title: str
    author: str


@dataclass
class BookCopy:
    barcode: str
    isbn: str
    status: CopyStatus = CopyStatus.AVAILABLE
    held_for: str | None = None      # member_id, when status is RESERVED
    hold_until: date | None = None   # hold expires after this date


@dataclass
class Member:
    member_id: str
    name: str
    email: str


@dataclass
class Loan:
    loan_id: str
    barcode: str
    member_id: str
    checkout_date: date
    due_date: date
    return_date: date | None = None

    @property
    def is_active(self) -> bool:
        return self.return_date is None

    def overdue_days(self, on: date) -> int:
        """Days past the due date as of `on` (or as of the return date)."""
        end = self.return_date if self.return_date is not None else on
        return max(0, (end - self.due_date).days)


@dataclass
class Reservation:
    isbn: str
    member_id: str
    placed_on: date

What to notice. overdue_days takes the date as a parameter instead of calling date.today(). That single choice is what makes fines testable: the caller decides what "today" means. Also note the models hold no references to each other — Loan stores barcode, not a BookCopy object. That keeps the models serializable and free of object-graph cycles; the service joins them when it needs to.

Step 4 — The strategies: fine policy, clock, notifier

Goal: type the three replaceable behaviors the service will depend on — how fines compute, what time it is, and how reservers get told.

Type library/policies.py:

"""Pluggable strategies: fine policy, clock, reservation notifier.

These exist for one reason: the service needs them, but the *choice* of each
should be replaceable without touching the service. That is the Strategy
pattern, and dependency inversion in practice.

The Clock deserves a callout. Domain code must never call date.today()
directly. A hidden call to the system clock makes every test that touches
time depend on the real calendar. Injecting a Clock lets tests freeze time.
"""
import logging
from abc import ABC, abstractmethod
from datetime import date, timedelta

log = logging.getLogger(__name__)


class FinePolicy(ABC):
    """Strategy: how an overdue loan converts to a fine."""

    @abstractmethod
    def fine_for(self, overdue_days: int) -> float:
        ...


class FlatDailyFinePolicy(FinePolicy):
    """$X per overdue day. Swap in a tiered policy later without edits."""

    def __init__(self, rate_per_day: float):
        if rate_per_day < 0:
            raise ValueError("rate_per_day must not be negative")
        self._rate = rate_per_day

    def fine_for(self, overdue_days: int) -> float:
        if overdue_days <= 0:
            return 0.0
        return round(overdue_days * self._rate, 2)


class Clock(ABC):
    @abstractmethod
    def today(self) -> date:
        ...


class SystemClock(Clock):
    def today(self) -> date:
        return date.today()


class FixedClock(Clock):
    """A clock tests can set and move. Production never uses this."""

    def __init__(self, today: date):
        self._today = today

    def today(self) -> date:
        return self._today

    def advance(self, days: int) -> None:
        self._today += timedelta(days=days)


class ReservationNotifier(ABC):
    """Observer: told when a returned copy is held for a reserver."""

    @abstractmethod
    def notify_hold_ready(self, member, book, copy, hold_until: date) -> None:
        ...


class LoggingNotifier(ReservationNotifier):
    """Default observer: records the notification in the logs."""

    def notify_hold_ready(self, member, book, copy, hold_until: date) -> None:
        log.info(
            "Hold ready: '%s' (copy %s) for %s until %s",
            book.title, copy.barcode, member.name, hold_until,
        )

What to notice. Three patterns share one file because they're all "the service needs X, but X varies." The notifier's parameters are duck-typed (no imports from models) — the ABC only promises when it's called, not what the objects are. And FixedClock.advance mutates: that's fine for a test double, but note it isn't thread-safe. Test doubles don't need to be.

Checkpoint:

from datetime import date

Step 5 — Repositories: storage behind interfaces

Goal: type the four repository ABCs plus their in-memory implementations, so the service depends on abstractions, not dicts.

Type library/repositories.py:

"""Persistence behind abstract repositories.

The service talks only to the ABCs. These in-memory implementations can be
swapped for a database-backed set later without the service noticing. Each
repository guards its own dict with a lock, so single-repo operations are
thread-safe; multi-repo operations (checkout touches three) are serialized
by the service-level lock instead.
"""
import threading
from abc import ABC, abstractmethod
from collections import deque

from .errors import DuplicateReservationError
from .models import Book, BookCopy, Loan, Member, Reservation


class BookCatalog(ABC):
    """Books, copies, and search. One ABC because copies belong to books."""

    @abstractmethod
    def add_book(self, book: Book) -> None: ...
    @abstractmethod
    def get_book(self, isbn: str) -> Book | None: ...
    @abstractmethod
    def add_copy(self, copy: BookCopy) -> None: ...
    @abstractmethod
    def get_copy(self, barcode: str) -> BookCopy | None: ...
    @abstractmethod
    def copies_of(self, isbn: str) -> list[BookCopy]: ...
    @abstractmethod
    def save_copy(self, copy: BookCopy) -> None: ...
    @abstractmethod
    def search(self, query: str) -> list[Book]: ...


class InMemoryBookCatalog(BookCatalog):
    def __init__(self):
        self._lock = threading.Lock()
        self._books: dict[str, Book] = {}
        self._copies: dict[str, BookCopy] = {}

    def add_book(self, book: Book) -> None:
        with self._lock:
            self._books[book.isbn] = book

    def get_book(self, isbn: str) -> Book | None:
        with self._lock:
            return self._books.get(isbn)

    def add_copy(self, copy: BookCopy) -> None:
        with self._lock:
            self._copies[copy.barcode] = copy

    def get_copy(self, barcode: str) -> BookCopy | None:
        with self._lock:
            return self._copies.get(barcode)

    def copies_of(self, isbn: str) -> list[BookCopy]:
        with self._lock:
            return [c for c in self._copies.values() if c.isbn == isbn]

    def save_copy(self, copy: BookCopy) -> None:
        with self._lock:
            self._copies[copy.barcode] = copy

    def search(self, query: str) -> list[Book]:
        needle = query.casefold()
        with self._lock:
            return [
                b for b in self._books.values()
                if needle in b.title.casefold()
                or needle in b.author.casefold()
                or needle in b.isbn.casefold()
            ]


class MemberRepository(ABC):
    @abstractmethod
    def add(self, member: Member) -> None: ...
    @abstractmethod
    def get(self, member_id: str) -> Member | None: ...


class InMemoryMemberRepository(MemberRepository):
    def __init__(self):
        self._lock = threading.Lock()
        self._members: dict[str, Member] = {}

    def add(self, member: Member) -> None:
        with self._lock:
            self._members[member.member_id] = member

    def get(self, member_id: str) -> Member | None:
        with self._lock:
            return self._members.get(member_id)


class LoanRepository(ABC):
    @abstractmethod
    def add(self, loan: Loan) -> None: ...
    @abstractmethod
    def get(self, loan_id: str) -> Loan | None: ...
    @abstractmethod
    def active_for_member(self, member_id: str) -> list[Loan]: ...
    @abstractmethod
    def active_for_copy(self, barcode: str) -> Loan | None: ...
    @abstractmethod
    def save(self, loan: Loan) -> None: ...


class InMemoryLoanRepository(LoanRepository):
    def __init__(self):
        self._lock = threading.Lock()
        self._loans: dict[str, Loan] = {}

    def add(self, loan: Loan) -> None:
        with self._lock:
            self._loans[loan.loan_id] = loan

    def get(self, loan_id: str) -> Loan | None:
        with self._lock:
            return self._loans.get(loan_id)

    def active_for_member(self, member_id: str) -> list[Loan]:
        with self._lock:
            return [l for l in self._loans.values()
                    if l.member_id == member_id and l.is_active]

    def active_for_copy(self, barcode: str) -> Loan | None:
        with self._lock:
            for loan in self._loans.values():
                if loan.barcode == barcode and loan.is_active:
                    return loan
            return None

    def save(self, loan: Loan) -> None:
        with self._lock:
            self._loans[loan.loan_id] = loan


class ReservationRepository(ABC):
    """One FIFO queue per ISBN."""

    @abstractmethod
    def add(self, reservation: Reservation) -> None: ...
    @abstractmethod
    def peek(self, isbn: str) -> Reservation | None: ...
    @abstractmethod
    def pop_next(self, isbn: str) -> Reservation | None: ...
    @abstractmethod
    def remove(self, isbn: str, member_id: str) -> bool: ...
    @abstractmethod
    def count(self, isbn: str) -> int: ...
    @abstractmethod
    def has(self, isbn: str, member_id: str) -> bool: ...


class InMemoryReservationQueue(ReservationRepository):
    def __init__(self):
        self._lock = threading.Lock()
        self._queues: dict[str, deque[Reservation]] = {}
        self._members: dict[str, set[str]] = {}

    def add(self, reservation: Reservation) -> None:
        with self._lock:
            members = self._members.setdefault(reservation.isbn, set())
            if reservation.member_id in members:
                raise DuplicateReservationError(
                    f"member {reservation.member_id} already reserved {reservation.isbn}"
                )
            self._queues.setdefault(reservation.isbn, deque()).append(reservation)
            members.add(reservation.member_id)

    def peek(self, isbn: str) -> Reservation | None:
        with self._lock:
            queue = self._queues.get(isbn)
            return queue[0] if queue else None

    def pop_next(self, isbn: str) -> Reservation | None:
        with self._lock:
            queue = self._queues.get(isbn)
            if not queue:
                return None
            reservation = queue.popleft()
            self._members[isbn].discard(reservation.member_id)
            return reservation

    def remove(self, isbn: str, member_id: str) -> bool:
        with self._lock:
            queue = self._queues.get(isbn)
            if not queue or member_id not in self._members.get(isbn, set()):
                return False
            kept = deque(r for r in queue if r.member_id != member_id)
            self._queues[isbn] = kept
            self._members[isbn].discard(member_id)
            return True

    def count(self, isbn: str) -> int:
        with self._lock:
            return len(self._queues.get(isbn, ()))

    def has(self, isbn: str, member_id: str) -> bool:
        with self._lock:
            return member_id in self._members.get(isbn, set())

What to notice. The ABCs are small on purpose: each lists only what the service actually calls. A repository interface should be shaped by its consumer, not by every operation a database could do. The reservation queue uses a deque per ISBN for FIFO, plus a set per ISBN so duplicate checks stay O(1).

Step 6 — The service: where the rules live

Goal: type LibraryService, the only class callers touch. It enforces loan limits, computes fines through the policy, and runs the reservation flow.

Type library/service.py:

"""The use-case layer: checkout, return, reserve, search.

Everything the outside world does goes through LibraryService. It owns the
business rules; the repositories own storage; the policies own the
replaceable bits. Dependencies arrive through the constructor, so tests can
hand in fakes. One RLock serializes the multi-repo operations, which makes
checkout and return atomic against concurrent threads.
"""
import logging
import threading
import uuid
from datetime import date, timedelta

from .config import CopyStatus, LibraryConfig
from .errors import (
    BookAlreadyExistsError,
    BookNotFoundError,
    CopiesAvailableError,
    CopyNotFoundError,
    DuplicateBarcodeError,
    DuplicateReservationError,
    LibraryError,
    LoanLimitExceededError,
    LoanNotFoundError,
    MemberNotFoundError,
    NoCopiesAvailableError,
)
from .models import Book, BookCopy, Loan, Member, Reservation
from .policies import Clock, FinePolicy, FlatDailyFinePolicy, ReservationNotifier, SystemClock, LoggingNotifier
from .repositories import (
    BookCatalog,
    InMemoryBookCatalog,
    InMemoryLoanRepository,
    InMemoryMemberRepository,
    InMemoryReservationQueue,
    LoanRepository,
    MemberRepository,
    ReservationRepository,
)

log = logging.getLogger(__name__)


def _require_text(value: str, name: str) -> str:
    if not value or not value.strip():
        raise ValueError(f"{name} must not be blank")
    return value.strip()


def _new_id() -> str:
    return uuid.uuid4().hex[:8]


class LibraryService:
    def __init__(
        self,
        *,
        catalog: BookCatalog | None = None,
        members: MemberRepository | None = None,
        loans: LoanRepository | None = None,
        reservations: ReservationRepository | None = None,
        clock: Clock | None = None,
        fine_policy: FinePolicy | None = None,
        notifier: ReservationNotifier | None = None,
        config: LibraryConfig | None = None,
    ):
        self._config = config or LibraryConfig()
        self._catalog = catalog or InMemoryBookCatalog()
        self._members = members or InMemoryMemberRepository()
        self._loans = loans or InMemoryLoanRepository()
        self._reservations = reservations or InMemoryReservationQueue()
        self._clock = clock or SystemClock()
        self._fine_policy = fine_policy or FlatDailyFinePolicy(self._config.fine_per_day)
        self._notifier = notifier or LoggingNotifier()
        self._lock = threading.RLock()

    # -- catalog management -------------------------------------------

    def register_book(self, isbn: str, title: str, author: str) -> Book:
        isbn = _require_text(isbn, "isbn")
        title = _require_text(title, "title")
        author = _require_text(author, "author")
        if self._catalog.get_book(isbn) is not None:
            raise BookAlreadyExistsError(f"book {isbn} is already registered")
        book = Book(isbn=isbn, title=title, author=author)
        self._catalog.add_book(book)
        log.info("registered book %s '%s'", isbn, title)
        return book

    def add_copy(self, isbn: str, barcode: str) -> BookCopy:
        barcode = _require_text(barcode, "barcode")
        if self._catalog.get_book(isbn) is None:
            raise BookNotFoundError(f"no book with ISBN {isbn}")
        if self._catalog.get_copy(barcode) is not None:
            raise DuplicateBarcodeError(f"copy {barcode} already exists")
        copy = BookCopy(barcode=barcode, isbn=isbn)
        self._catalog.add_copy(copy)
        log.info("added copy %s of %s", barcode, isbn)
        return copy

    def register_member(self, name: str, email: str) -> Member:
        name = _require_text(name, "name")
        email = _require_text(email, "email")
        member = Member(member_id=_new_id(), name=name, email=email)
        self._members.add(member)
        log.info("registered member %s (%s)", member.member_id, name)
        return member

    # -- lending -------------------------------------------------------

    def checkout(self, isbn: str, member_id: str) -> Loan:
        with self._lock:
            member = self._members.get(member_id)
            if member is None:
                raise MemberNotFoundError(f"no member {member_id}")
            if self._catalog.get_book(isbn) is None:
                raise BookNotFoundError(f"no book with ISBN {isbn}")
            active = self._loans.active_for_member(member_id)
            if len(active) >= self._config.max_loans_per_member:
                raise LoanLimitExceededError(
                    f"member {member_id} already has {len(active)} active loans"
                )
            today = self._clock.today()
            copy = self._pick_copy(isbn, member_id, today)
            if copy is None:
                raise NoCopiesAvailableError(f"no lendable copy of {isbn} right now")
            loan = Loan(
                loan_id=_new_id(),
                barcode=copy.barcode,
                member_id=member_id,
                checkout_date=today,
                due_date=today + timedelta(days=self._config.loan_period_days),
            )
            copy.status = CopyStatus.ON_LOAN
            self._catalog.save_copy(copy)
            self._loans.add(loan)
            log.info("checkout: copy %s -> member %s, due %s",
                     copy.barcode, member_id, loan.due_date)
            return loan

    def return_copy(self, barcode: str) -> float:
        """Return a copy. Returns the fine owed (0.0 when on time)."""
        with self._lock:
            loan = self._loans.active_for_copy(barcode)
            if loan is None:
                raise LoanNotFoundError(f"no active loan for copy {barcode}")
            copy = self._catalog.get_copy(barcode)
            if copy is None:
                raise CopyNotFoundError(f"no copy {barcode}")
            today = self._clock.today()
            fine = self._fine_policy.fine_for(loan.overdue_days(today))
            loan.return_date = today
            self._loans.save(loan)

            next_in_line = self._reservations.pop_next(copy.isbn)
            if next_in_line is not None:
                holder = self._members.get(next_in_line.member_id)
                book = self._catalog.get_book(copy.isbn)
                copy.status = CopyStatus.RESERVED
                copy.held_for = next_in_line.member_id
                copy.hold_until = today + timedelta(days=self._config.hold_window_days)
                self._catalog.save_copy(copy)
                self._notifier.notify_hold_ready(holder, book, copy, copy.hold_until)
                log.info("return: copy %s held for %s until %s",
                         barcode, next_in_line.member_id, copy.hold_until)
            else:
                copy.status = CopyStatus.AVAILABLE
                copy.held_for = None
                copy.hold_until = None
                self._catalog.save_copy(copy)
                log.info("return: copy %s available again", barcode)
            return fine

    def _pick_copy(self, isbn: str, member_id: str, today: date) -> BookCopy | None:
        copies = self._catalog.copies_of(isbn)
        for copy in copies:
            if (copy.status is CopyStatus.RESERVED
                    and copy.hold_until is not None
                    and today > copy.hold_until):
                copy.status = CopyStatus.AVAILABLE  # lazy hold expiry
                copy.held_for = None
                copy.hold_until = None
                self._catalog.save_copy(copy)
        for copy in copies:
            if copy.status is CopyStatus.AVAILABLE:
                return copy
        for copy in copies:  # the member's own unexpired hold
            if copy.status is CopyStatus.RESERVED and copy.held_for == member_id:
                copy.held_for = None
                copy.hold_until = None
                return copy
        return None

    # -- reservations ---------------------------------------------------

    def reserve(self, isbn: str, member_id: str) -> Reservation:
        with self._lock:
            if self._members.get(member_id) is None:
                raise MemberNotFoundError(f"no member {member_id}")
            if self._catalog.get_book(isbn) is None:
                raise BookNotFoundError(f"no book with ISBN {isbn}")
            if any(c.status is CopyStatus.AVAILABLE
                   for c in self._catalog.copies_of(isbn)):
                raise CopiesAvailableError(
                    f"copies of {isbn} are on the shelf; check one out instead"
                )
            if self._reservations.has(isbn, member_id):
                raise DuplicateReservationError(
                    f"member {member_id} already reserved {isbn}"
                )
            reservation = Reservation(
                isbn=isbn, member_id=member_id, placed_on=self._clock.today())
            self._reservations.add(reservation)
            log.info("reservation: member %s queued for %s", member_id, isbn)
            return reservation

    def cancel_reservation(self, isbn: str, member_id: str) -> bool:
        with self._lock:
            return self._reservations.remove(isbn, member_id)

    # -- queries --------------------------------------------------------

    def search(self, query: str) -> list[Book]:
        return self._catalog.search(_require_text(query, "query"))

    def active_loans(self, member_id: str) -> list[Loan]:
        if self._members.get(member_id) is None:
            raise MemberNotFoundError(f"no member {member_id}")
        return self._loans.active_for_member(member_id)

What to notice. The constructor takes everything as keyword-only arguments with working defaults. That means the demo can say LibraryService(clock=FixedClock(...)) and get in-memory everything else — dependency inversion without a DI framework. The RLock (re-entrant) wraps checkout, return_copy, reserve, and cancel_reservation because each touches several repositories; the lock makes each method atomic. And _pick_copy expires holds lazily: no sweeper thread, no cron — the next checkout that looks at the copy cleans it up.

def main() -> None:

    clock = FixedClock(date(2026, 10, 15))
    svc = LibraryService(
        catalog=InMemoryBookCatalog(),
        members=InMemoryMemberRepository(),
        loans=InMemoryLoanRepository(),
        reservations=InMemoryReservationQueue(),
        clock=clock,
        config=LibraryConfig(),
    )

    svc.register_book(ISBN, "Effective Java", "Joshua Bloch")
    svc.add_copy(ISBN, "EJ-001")
    svc.add_copy(ISBN, "EJ-002")

    m2 = svc.register_member("Shyam Miyatra", "shyam@example.com")
    m3 = svc.register_member("Jacob", "jacob@example.com")

9. Common interview follow-ups

Why separate Book and BookCopy? Couldn't a book just have a copies_available count? A counter can't say which copy is out, who has it, or when it's due. The moment you need per-copy history — fines, holds, a damaged copy — the counter design collapses. Copies are entities with identity (the barcode); model them.

Why can't I reserve a book that has copies on the shelf? Because the queue means "tell me when one comes back." Letting people reserve available copies turns the queue into a second checkout line and starves walk-in borrowers. The rule keeps the reservation's meaning intact.

What happens when the first reserver never picks up the hold? The hold expires after 3 days (_pick_copy flips it back to available on the next checkout attempt). The current design then frees the copy to anyone; a stricter library would cascade it to the next reserver — see the stretch tasks.

How would you persist this in Postgres? One table per model: books, copies, members, loans, reservations. Each repository ABC gets a SQL implementation; the service doesn't change — that's exactly what the seam is for. The FIFO queue becomes ORDER BY placed_on.

Why is the fine logic not a method on Loan? Because the rate varies independently of the loan. Students vs. public members, promotional amnesties, tiered rates — all of those are new FinePolicy classes. If the formula lived on Loan, every rate change would edit the class that also owns dates and identity.

Is this thread-safe? Checkout, return, reserve, and cancel are atomic under the service RLock, and each repository guards its own dict. What's not covered: two service instances sharing repositories, and FixedClock under threads. Both are documented, not hidden.

Chapter 5: Vending Machine

Type along with this chapter. You will build a coin-operated vending machine driven by a real State pattern: three state classes, greedy change-making, sold-out handling, and cancel-with-refund. Every file is complete and runnable.

1. The problem

A vending machine sells snacks for coins. The customer inserts coins, picks a product by code, and the machine dispenses it with change. The customer can cancel any time before dispensing and get every coin back. Selecting a sold-out product is refused with a clear error, and the machine never swallows money it cannot make change for.

2. Requirements

Functional

  • Accept coins of configured denominations; reject anything else.
  • Track the inserted balance across multiple coins.
  • Dispense the selected product when balance covers the price; return change, largest coins first.
  • Refuse sold-out selections and unknown codes with distinct errors.
  • Cancel refunds every inserted coin, exactly.
  • If exact change cannot be made, refund everything and raise — never trap the customer's money.
  • Money in integer cents. No floats.

Non-functional

  • Model the machine as proper State pattern: IDLE, AWAITING_PAYMENT, DISPENSING as classes behind one interface. No string flags, no if self.state == "idle" anywhere.
  • A failed vend must never strand the machine in DISPENSING.
  • Thread-safe public methods: two threads hitting buttons cannot interleave a dispense.
  • Prices, denominations, and the operator's coin float come from a config dataclass.
  • Every domain failure is a catchable exception type.

3. From nouns to classes

The key modeling choice: the machine never asks which state it is in. Each state object decides what each button press means. That is the whole pattern, and it is why adding a fourth state later is a new class rather than surgery on a nest of conditionals.

5. Key design decisions

State pattern, properly. MachineState is an ABC with insert_coin, select, cancel, and an on_enter hook. The three concrete states each implement the contract. VendingMachine holds _state and delegates every public call to it. There is no state string, no enum switch, no if-chain. An OutOfServiceState later would be one new file.

The machine is the context, states are the flow. Product validation and money math live in VendingMachine helpers (validate_selection, _make_change, dispense). The states own what is legal right now and what comes next. Behavior and flow stay in separate hands.

Dispensing always returns to IDLE. complete_dispense wraps the vend in try/finally. If change-making fails, the customer is refunded, the exception propagates, and the next customer still finds a working machine. A stuck DISPENSING state would be a bricked machine.

Greedy change, honestly documented. Largest denomination first. This is optimal for canonical coin systems (US, Euro, INR — the default config is one), but not for every conceivable denomination set. The limitation is written in the docstring rather than hidden.

The operator loads a coin float. A real machine cannot make change from an empty box, so MachineConfig.coin_float models the coins the operator places at opening time. This fell out of testing: the first test run showed the first customer could never get change. The config models reality instead of the test faking it.

Money as int cents. Prices, balances, and change are integers. The config rejects non-positive prices and duplicate denominations at construction.

Cancel is exact. Inserted coins go straight into the inventory, so a refund is just greedy change for the full balance — guaranteed exact, because the machine is handing back the very coins it took.

"""Machine configuration: coin denominations, product catalog, limits.

All money is in integer cents. Floats never appear, so a price of $1.25 is
exactly 125 and change math can never drift by a fraction of a cent.
"""
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass(frozen=True)
class ProductSpec:
    """One product as configured: what it is, what it costs, how many loaded."""

    code: str
    name: str
    price_cents: int
    quantity: int

    def __post_init__(self) -> None:
        if not self.code or not self.code.strip():
            raise ValueError("product code must be a non-empty string")
        if self.price_cents <= 0:
            raise ValueError("price_cents must be positive")
        if self.quantity < 0:
            raise ValueError("quantity must not be negative")


@dataclass(frozen=True)
class MachineConfig:
    """Deployment-time settings for one vending machine."""

    coins: tuple[int, ...] = (100, 50, 25, 10, 5, 1)
    products: tuple[ProductSpec, ...] = field(
        default_factory=lambda: (
            ProductSpec("A1", "Cola", 150, 5),
            ProductSpec("A2", "Chips", 100, 5),
            ProductSpec("B1", "Water", 125, 5),
        )
    )
    max_balance_cents: int = 2000
    # Operator-loaded float: coins placed in the box before opening, so the
    # machine can make change for the first customers of the day.
    coin_float: dict[int, int] = field(default_factory=dict)

    def __post_init__(self) -> None:
        if not self.coins:
            raise ValueError("coins must not be empty")
        if any(c <= 0 for c in self.coins):
            raise ValueError("coin denominations must be positive")
        if len(set(self.coins)) != len(self.coins):
            raise ValueError("coin denominations must be unique")
        codes = [p.code for p in self.products]
        if len(set(codes)) != len(codes):
            raise ValueError("product codes must be unique")
        if self.max_balance_cents <= 0:
            raise ValueError("max_balance_cents must be positive")
        for coin, count in self.coin_float.items():
            if coin not in self.coins:
                raise ValueError(f"coin float holds {coin}c, not an accepted denomination")
            if count < 0:
                raise ValueError("coin float counts must not be negative")

Step 3 — vending_machine/state.py: the State interface

Goal: the contract every state implements. This is the pattern's seam.

"""The State interface. Every machine state implements this contract.

The point of the pattern: the machine never asks "which state am I in?".
Each state object decides what each action means, so adding a state (say,
an OutOfServiceState) is a new class, not an edit to a tangle of ifs.
"""
from __future__ import annotations

from abc import ABC, abstractmethod
from typing import TYPE_CHECKING

if TYPE_CHECKING:  # pragma: no cover
    from .machine import VendingMachine


class MachineState(ABC):
    """What the machine can do while it is in this state."""

    @property
    @abstractmethod
    def name(self) -> str:
        """Human-readable state name, used by the status display."""

    @abstractmethod
    def insert_coin(self, machine: VendingMachine, coin_cents: int) -> str:
        """Take a coin. Returns a short message for the display."""

    @abstractmethod
    def select(self, machine: VendingMachine, code: str) -> dict:
        """Choose a product. Returns the purchase receipt on success."""

    @abstractmethod
    def cancel(self, machine: VendingMachine) -> dict[int, int]:
        """Abort the transaction. Returns refunded coins."""

    def on_enter(self, machine: VendingMachine) -> None:
        """Hook run once when the machine enters this state. Default: no-op."""

What to notice. The state methods take the machine as a parameter. States are behavior objects; the machine holds the data (balance, inventory, stock). The TYPE_CHECKING import avoids a circular import at runtime while keeping type checkers happy — state.py never imports machine.py for real.

"""The three concrete states of the vending machine.

Each state decides what insert/select/cancel mean. Validation of products
and money lives in the machine's helpers; the states own the *flow*:
what is legal right now, and which state comes next.
"""
from __future__ import annotations

from typing import TYPE_CHECKING

from .exceptions import InsufficientFundsError, MachineBusyError
from .state import MachineState

if TYPE_CHECKING:  # pragma: no cover
    from .machine import VendingMachine


class IdleState(MachineState):
    """No money inserted yet. Only insert_coin does anything useful."""

    @property
    def name(self) -> str:
        return "IDLE"

    def insert_coin(self, machine: VendingMachine, coin_cents: int) -> str:
        machine.validate_coin(coin_cents)
        machine.add_coin(coin_cents)
        machine.transition_to(AwaitingPaymentState())
        return f"balance: {machine.balance_cents}c"

    def select(self, machine: VendingMachine, code: str) -> dict:
        raise InsufficientFundsError("insert coins before selecting")

    def cancel(self, machine: VendingMachine) -> dict[int, int]:
        return {}  # nothing inserted, nothing to refund


class AwaitingPaymentState(MachineState):
    """Money is in. More coins, a selection, or cancel are all legal."""

    @property
    def name(self) -> str:
        return "AWAITING_PAYMENT"

    def insert_coin(self, machine: VendingMachine, coin_cents: int) -> str:
        machine.validate_coin(coin_cents)
        machine.add_coin(coin_cents)
        return f"balance: {machine.balance_cents}c"

    def select(self, machine: VendingMachine, code: str) -> dict:
        machine.validate_selection(code)  # raises on bad code / sold out
        price = machine.price_of(code)
        if machine.balance_cents < price:
            raise InsufficientFundsError(
                f"{code} costs {price}c, only {machine.balance_cents}c inserted"
            )
        dispensing = DispensingState(code)
        machine.transition_to(dispensing)
        dispensing.on_enter(machine)
        return machine.last_receipt

    def cancel(self, machine: VendingMachine) -> dict[int, int]:
        refund = machine.refund_all()
        machine.transition_to(IdleState())
        return refund


class DispensingState(MachineState):
    """Mid-dispense. No user action is legal until on_enter finishes."""

    def __init__(self, code: str) -> None:
        self._code = code

    @property
    def name(self) -> str:
        return "DISPENSING"

    def on_enter(self, machine: VendingMachine) -> None:
        machine.complete_dispense(self._code)

    def insert_coin(self, machine: VendingMachine, coin_cents: int) -> str:
        raise MachineBusyError("machine is dispensing, please wait")

    def select(self, machine: VendingMachine, code: str) -> dict:
        raise MachineBusyError("machine is dispensing, please wait")

    def cancel(self, machine: VendingMachine) -> dict[int, int]:
        raise MachineBusyError("machine is dispensing, please wait")

The state decides the choreography; the machine does the work. DispensingState carries the product code because a state can hold data — it is an object, not a label.

"""VendingMachine: the state-machine context plus inventory and money.

Public methods take ``self._lock`` for their whole body, so two threads
hammering the buttons cannot interleave a dispense. The state objects hold
no locks of their own; they run inside the machine's lock.

Change-making is greedy: largest denomination first. That is optimal for
canonical coin systems (US, Euro, INR) but not for every possible
denomination set. The config's default set is canonical, and the limitation
is documented rather than hidden.
"""
from __future__ import annotations

import logging
import threading
from collections import Counter
from dataclasses import dataclass

from .config import MachineConfig
from .exceptions import (
    ChangeUnavailableError,
    InvalidCoinError,
    InvalidSelectionError,
    SoldOutError,
)
from .state import MachineState
from .states import IdleState

logger = logging.getLogger(__name__)


@dataclass
class Product:
    """One stocked product. Quantity mutates as items are dispensed."""

    code: str
    name: str
    price_cents: int
    quantity: int


class VendingMachine:
    """A coin-operated vending machine driven by the State pattern."""

    def __init__(self, config: MachineConfig | None = None) -> None:
        self._config = config or MachineConfig()
        self._products: dict[str, Product] = {
            spec.code: Product(spec.code, spec.name, spec.price_cents, spec.quantity)
            for spec in self._config.products
        }
        self._coins: Counter[int] = Counter(dict(self._config.coin_float))
        self._balance_cents = 0
        self._state: MachineState = IdleState()
        self._last_receipt: dict = {}
        self._lock = threading.Lock()

    # -- public API: every call delegates to the current state --------------

    def insert_coin(self, coin_cents: int) -> str:
        with self._lock:
            return self._state.insert_coin(self, coin_cents)

    def select(self, code: str) -> dict:
        with self._lock:
            return self._state.select(self, code)

    def cancel(self) -> dict[int, int]:
        with self._lock:
            return self._state.cancel(self)

    def status(self) -> dict:
        """Snapshot for the front-panel display. Read-only copy."""
        with self._lock:
            return {
                "state": self._state.name,
                "balance_cents": self._balance_cents,
                "products": [
                    {
                        "code": p.code,
                        "name": p.name,
                        "price_cents": p.price_cents,
                        "quantity": p.quantity,
                    }
                    for p in self._products.values()
                ],
            }

    # -- state plumbing ------------------------------------------------------

    def transition_to(self, state: MachineState) -> None:
        logger.debug("state %s -> %s", self._state.name, state.name)
        self._state = state

    @property
    def balance_cents(self) -> int:
        return self._balance_cents

    @property
    def last_receipt(self) -> dict:
        return dict(self._last_receipt)

    # -- helpers used by states (called with the lock held) ------------------

    def validate_coin(self, coin_cents: int) -> None:
        if coin_cents not in self._config.coins:
            raise InvalidCoinError(f"{coin_cents}c is not an accepted denomination")

    def add_coin(self, coin_cents: int) -> None:
        if self._balance_cents + coin_cents > self._config.max_balance_cents:
            raise InvalidCoinError(  # the slot physically rejects the coin
                f"coin rejected: balance would exceed {self._config.max_balance_cents}c"
            )
        self._coins[coin_cents] += 1
        self._balance_cents += coin_cents

    def validate_selection(self, code: str) -> None:
        product = self._products.get(code)
        if product is None:
            raise InvalidSelectionError(f"unknown product code {code!r}")
        if product.quantity == 0:
            raise SoldOutError(f"{product.name} ({code}) is sold out")

    def price_of(self, code: str) -> int:
        return self._products[code].price_cents

    def complete_dispense(self, code: str) -> None:
        """Dispense and return to IDLE, even when dispensing fails.

        A failed vend must never strand the machine in DISPENSING: the
        finally guarantees the next customer finds a working machine.
        """
        try:
            self.dispense(code)
        finally:
            self.transition_to(IdleState())

    def dispense(self, code: str) -> None:
        """Run the vend: stock down, change out, balance reset.

        Raises ChangeUnavailableError (after refunding everything) when the
        coin box cannot make exact change.
        """
        product = self._products[code]
        change_due = self._balance_cents - product.price_cents
        try:
            change_coins = self._make_change(change_due)
        except ChangeUnavailableError:
            refund = self.refund_all()
            logger.warning("cannot make %dc change; refunded %s", change_due, refund)
            raise ChangeUnavailableError(
                f"cannot make {change_due}c change; money refunded"
            ) from None
        for coin, count in change_coins.items():
            self._coins[coin] -= count
        product.quantity -= 1
        self._balance_cents = 0
        self._last_receipt = {
            "product": product.name,
            "code": product.code,
            "price_cents": product.price_cents,
            "change_cents": change_due,
            "change_coins": dict(change_coins),
        }
        logger.info("dispensed %s, change %dc", product.name, change_due)

    def refund_all(self) -> dict[int, int]:
        """Return every inserted cent. Always succeeds: the inserted coins
        are already in the inventory, so exact change is guaranteed."""
        refund = self._make_change(self._balance_cents)
        for coin, count in refund.items():
            self._coins[coin] -= count
        self._balance_cents = 0
        return dict(refund)

    def _make_change(self, amount_cents: int) -> dict[int, int]:
        """Greedy change: biggest denomination first.

        Optimal for canonical coin systems (the config default is one).
        Raises ChangeUnavailableError when the inventory cannot cover the
        amount exactly.
        """
        remaining = amount_cents
        change: dict[int, int] = {}
        for coin in sorted(self._config.coins, reverse=True):
            use = min(remaining // coin, self._coins[coin])
            if use:
                change[coin] = use
                remaining -= coin * use
        if remaining != 0:
            raise ChangeUnavailableError(
                f"cannot make {amount_cents}c change from available coins"
            )
        return change

What to notice. Three things earn their keep here. First, complete_dispense's try/finally: the state machine can never get stuck, even on the error path. Second, dispense refunds before raising ChangeUnavailableError: the customer's money is safe before the error reaches the caller. Third, status() returns a plain-dict copy — the display panel gets data, never a live reference to internals.

8. Enterprise checklist, mapped to the code

  1. Single Responsibility. States own flow; VendingMachine owns data and money math; MachineConfig owns settings. One reason to change each.
  2. Open/Closed. A fourth state (say OutOfServiceState) is a new class implementing MachineState. No existing file changes.
  3. Liskov. Every state is substitutable for MachineState — the machine never branches on concrete type. The tests exercise all three through the same three public methods.
  4. Dependency inversion. VendingMachine takes a MachineConfig; states take the machine as a parameter rather than constructing one.
  5. Custom exception hierarchy. VendingError with six subclasses (exceptions.py). No bare except.
  6. logging, not print. Library code logs (machine.py); print lives only in __main__.py.
  7. Input validation at boundaries. validate_coin rejects bad denominations; validate_selection rejects bad codes and sold-out stock; add_coin rejects slot overfill; config validates in __post_init__.
  8. Config via dataclass. MachineConfig: coins, products, balance cap, coin float. No scattered literals.
  9. Composition over inheritance. The machine has a state; states are separate objects. Inheritance appears only as interface → implementation.
  10. Thread-safety. One lock in VendingMachine, held across whole public methods (machine.py). States are lock-free and only run inside it.
  11. Repository pattern. Not needed here — inventory is the machine's intrinsic state, not external persistence. (The parking lot chapter shows the pattern; not every problem needs every tool.)
  12. unittest suite. 19 tests, stdlib only, edge cases included.

9. Common interview follow-ups

Why classes for states instead of an enum + if-chain? The if-chain centralizes every transition in one method that every new state edits. State classes distribute the logic: each state knows its own legal actions. The machine code never changes when a state is added.

Why does select in IDLE raise instead of returning an error string? Errors are values the caller must handle, and exceptions force handling at the type level. A returned string is easy to ignore; a raised InsufficientFundsError is not.

Is greedy change always optimal? No — only for canonical coin systems. For arbitrary denominations it can fail where a solution exists (classic example: coins of 1, 3, 4 and amount 6 — greedy takes 4+1+1, optimal is 3+3). The docstring says so. An interviewer loves that you know the boundary of your algorithm.

What if two customers use the machine at once? They cannot interleave: the lock serializes whole public calls. A real machine is single-user anyway; the lock is cheap insurance for the shared coin inventory.

How would you add card payments? A new payment path alongside coins: the states would need a pay_by_card action on the interface. That changes MachineState — an honest answer: the pattern makes states cheap to add, but actions touch the interface. Name the tradeoff.

Chapter 6: Car Rental System

Type every file in order. Run each checkpoint before moving on. All commands run from the project folder (the one holding car_rental/ and tests/). Python 3.13, stdlib only.

1. The problem

A car rental agency runs a fleet grouped into Economy, SUV, and Luxury, each category with its own daily rate. Customers reserve a car for a date window. The same car can never be double-booked: a new reservation conflicts exactly when its window overlaps an existing one. Pricing is daily rate × days, plus optional insurance and GPS charged per day, plus a per-day fee for late returns. Cancelling frees the window. Staff search for available cars by category and date range.

2. Requirements

Functional

  • Manage a fleet: vehicle id, category (ECONOMY/SUV/LUXURY), make, model, year. Daily rates come from config, not from code.
  • Reserve a vehicle for [start_date, end_date). Reject the reservation if the window overlaps any active reservation for that vehicle.
  • Boundary rule, stated exactly: one reservation ending Nov 5 and another starting Nov 5 do not conflict.
  • Search available vehicles by category + date range.
  • Quote a price before or after booking: days × daily rate + add-ons (insurance, GPS per day) + late-return fee per day.
  • Cancel a reservation. Cancellation frees its window.
  • Validate: end must be after start; start must not be in the past.

Non-functional

  • Time is injectable (same reasoning as the library chapter): no date.today() in domain logic.
  • Reserving must be atomic under concurrent threads — two customers, one car, one window, exactly one winner.
  • Fleet and reservations persist behind repository interfaces.
  • Typed exception hierarchy; no bare except.
  • Stdlib only.

5. Key design decisions

  1. Date windows are half-open: [start, end). This is the decision the whole design hangs on. The car is yours from the start date up to — but not including — the end date. Back-to-back bookings then work by construction: one ends Nov 5, the next starts Nov 5, no special-casing. Inclusive end dates ("is Nov 5 part of both bookings?") are where double-booking bugs are born.
  2. The overlap rule lives on Reservation, in one predicate. new.start < existing.end and existing.start < new.end — two half-open intervals overlap exactly when each starts before the other ends. The repository delegates to it, so the rule has exactly one home and the tests pin it case by case.
  3. The factory validates; the service checks conflicts. Building a reservation (are the dates sane? does the vehicle exist?) is a different job from booking it (is the window free?). Splitting them keeps each method short and each failure precisely typed.
  4. Pricing is a Strategy. Daily rates, add-ons, and late fees change more often than booking rules. A new formula is a new class; the service never gets edited for a pricing change.
  5. Cancelled reservations are kept, and excluded from overlap checks. Deleting them would lose history ("who cancelled what, when"). A cancelled flag keeps the audit trail and frees the window in one move.
  6. The clock is injected, again. Same reasoning as the library: tests freeze time. Two chapters, one rule — "no date.today() in domain logic" is now a habit, not a one-off.

Patterns, and why each earns its place. Strategy for pricing: formulas vary independently of booking. Repository for the fleet and the bookings: the dicts become tables later. Factory for reservation creation: every "is this window even valid?" check in one place, so the service never holds a half-checked reservation.

"""Injectable clock. Same idea as in the library: domain code never calls
date.today() directly, so tests freeze time with FixedClock."""
from abc import ABC, abstractmethod
from datetime import date, timedelta


class Clock(ABC):
    @abstractmethod
    def today(self) -> date:
        ...


class SystemClock(Clock):
    def today(self) -> date:
        return date.today()


class FixedClock(Clock):
    def __init__(self, today: date):
        self._today = today

    def today(self) -> date:
        return self._today

    def advance(self, days: int) -> None:
        self._today += timedelta(days=days)

What to notice. Yes, this is the same shape as the library's clock. That's deliberate: some seams are worth repeating in every domain rather than sharing through a "common" package that couples the two problems together. Each problem's code stands alone.

Step 4 — The models, and the one predicate that matters

Goal: type Vehicle, AddOns, and Reservation — including conflicts_with, the half-open overlap test this whole chapter rests on.

Type car_rental/models.py:

"""Domain models.

A reservation holds a half-open date window: [start_date, end_date). The car
is yours from the start date up to, but not including, the end date. That
one choice makes back-to-back bookings fall out naturally: a reservation
ending Nov 5 and another starting Nov 5 do not overlap, because the end is
exclusive.
"""
from dataclasses import dataclass, field
from datetime import date

from .config import VehicleCategory


@dataclass
class Vehicle:
    vehicle_id: str
    category: VehicleCategory
    make: str
    model: str
    year: int


@dataclass(frozen=True)
class AddOns:
    insurance: bool = False
    gps: bool = False


@dataclass
class Reservation:
    reservation_id: str
    vehicle_id: str
    customer_name: str
    start_date: date  # inclusive
    end_date: date    # exclusive: [start_date, end_date)
    add_ons: AddOns = field(default_factory=AddOns)
    cancelled: bool = False

    @property
    def days(self) -> int:
        return (self.end_date - self.start_date).days

    def conflicts_with(self, start: date, end: date) -> bool:
        """True iff window [start, end) overlaps this reservation's window.

        Two half-open intervals overlap exactly when each one starts before
        the other ends: new.start < existing.end and existing.start < new.end.
        Touching at a boundary (one ends Nov 5, the other starts Nov 5) is
        not a conflict.
        """
        return self.start_date < end and start < self.end_date

What to notice. Read the predicate slowly — it's worth memorizing. self.start_date < end: the existing booking starts before the new window ends. start < self.end_date: the new window starts before the existing booking ends. Both must hold. If the new window starts exactly when the old one ends, start < self.end_date is false, so no conflict. One line, no branches, no off-by-one.

Step 5 — Repositories

Goal: type the fleet and reservation-book ABCs with in-memory implementations. has_overlap is the query the design hinges on.

Type car_rental/repositories.py:

"""Repositories: the fleet and the reservation book, behind ABCs.

has_overlap is the query the whole design hinges on: it skips cancelled
reservations (a cancellation frees its window) and delegates the interval
math to Reservation.conflicts_with, so the rule lives in exactly one place.
"""
import threading
from abc import ABC, abstractmethod
from datetime import date

from .models import Reservation, Vehicle


class FleetRepository(ABC):
    @abstractmethod
    def add(self, vehicle: Vehicle) -> None: ...
    @abstractmethod
    def get(self, vehicle_id: str) -> Vehicle | None: ...
    @abstractmethod
    def by_category(self, category) -> list[Vehicle]: ...


class InMemoryFleet(FleetRepository):
    def __init__(self):
        self._lock = threading.Lock()
        self._vehicles: dict[str, Vehicle] = {}

    def add(self, vehicle: Vehicle) -> None:
        with self._lock:
            self._vehicles[vehicle.vehicle_id] = vehicle

    def get(self, vehicle_id: str) -> Vehicle | None:
        with self._lock:
            return self._vehicles.get(vehicle_id)

    def by_category(self, category) -> list[Vehicle]:
        with self._lock:
            return [v for v in self._vehicles.values() if v.category is category]


class ReservationRepository(ABC):
    @abstractmethod
    def add(self, reservation: Reservation) -> None: ...
    @abstractmethod
    def get(self, reservation_id: str) -> Reservation | None: ...
    @abstractmethod
    def save(self, reservation: Reservation) -> None: ...
    @abstractmethod
    def for_vehicle(self, vehicle_id: str) -> list[Reservation]: ...
    @abstractmethod
    def has_overlap(self, vehicle_id: str, start: date, end: date) -> bool: ...


class InMemoryReservations(ReservationRepository):
    def __init__(self):
        self._lock = threading.Lock()
        self._reservations: dict[str, Reservation] = {}

    def add(self, reservation: Reservation) -> None:
        with self._lock:
            self._reservations[reservation.reservation_id] = reservation

    def get(self, reservation_id: str) -> Reservation | None:
        with self._lock:
            return self._reservations.get(reservation_id)

    def save(self, reservation: Reservation) -> None:
        with self._lock:
            self._reservations[reservation.reservation_id] = reservation

    def for_vehicle(self, vehicle_id: str) -> list[Reservation]:
        with self._lock:
            return [r for r in self._reservations.values()
                    if r.vehicle_id == vehicle_id and not r.cancelled]

    def has_overlap(self, vehicle_id: str, start: date, end: date) -> bool:
        with self._lock:
            return any(r.conflicts_with(start, end)
                       for r in self._reservations.values()
                       if r.vehicle_id == vehicle_id and not r.cancelled)

What to notice. has_overlap filters not r.cancelled before calling conflicts_with. Cancellation frees the window because the query can't see cancelled rows — the service never has to remember to exclude them. One filter, in one place.

Step 6 — Pricing as a strategy

Goal: type the PricingStrategy ABC and the standard formula: days × rate, plus per-day add-ons, plus the late fee.

Type car_rental/pricing.py:

"""Pricing as a Strategy.

The service asks "what does this cost?" without knowing the formula. A new
formula (weekend rates, loyalty discounts) is a new class implementing
PricingStrategy, not an edit to existing code.
"""
from abc import ABC, abstractmethod

from .config import RentalConfig
from .models import AddOns, Reservation, Vehicle


class PricingStrategy(ABC):
    @abstractmethod
    def quote(self, vehicle: Vehicle, reservation: Reservation,
              config: RentalConfig) -> float:
        ...

    @abstractmethod
    def late_fee(self, late_days: int, config: RentalConfig) -> float:
        ...


class StandardPricing(PricingStrategy):
    """daily rate x days, plus per-day add-ons, plus a per-day late fee."""

    def quote(self, vehicle: Vehicle, reservation: Reservation,
              config: RentalConfig) -> float:
        days = reservation.days
        total = days * config.daily_rates[vehicle.category]
        if reservation.add_ons.insurance:
            total += days * config.add_ons.insurance_per_day
        if reservation.add_ons.gps:
            total += days * config.add_ons.gps_per_day
        return round(total, 2)

    def late_fee(self, late_days: int, config: RentalConfig) -> float:
        if late_days <= 0:
            return 0.0
        return round(late_days * config.add_ons.late_fee_per_day, 2)

What to notice. round(total, 2) at the boundary. Float arithmetic on money accumulates dust like 314.91000000000003; rounding at the point of quote keeps every price clean. (A real ledger would use Decimal, but for quoting, rounding at the edge is the honest, simple choice.)

Step 7 — The factory: validated construction in one place

Goal: type ReservationFactory, the only place that builds a Reservation. Every "is this window even valid?" check lives in create().

Type car_rental/factory.py:

"""Factory: the one place that builds a valid Reservation.

Construction plus validation live together here, so the service never holds
a half-checked reservation. Every rule about "what counts as a reservable
window" is in create(); the service only asks "does it conflict?".
"""
import uuid
from datetime import date

from .clock import Clock
from .errors import InvalidDateRangeError, ReservationInPastError, VehicleNotFoundError
from .models import AddOns, Reservation
from .repositories import FleetRepository


class ReservationFactory:
    def __init__(self, fleet: FleetRepository, clock: Clock):
        self._fleet = fleet
        self._clock = clock

    def create(self, vehicle_id: str, customer_name: str,
               start: date, end: date, add_ons: AddOns | None = None) -> Reservation:
        if not customer_name or not customer_name.strip():
            raise ValueError("customer_name must not be blank")
        if self._fleet.get(vehicle_id) is None:
            raise VehicleNotFoundError(f"no vehicle {vehicle_id}")
        if end <= start:
            raise InvalidDateRangeError(
                f"end {end} must be after start {start}")
        if start < self._clock.today():
            raise ReservationInPastError(
                f"start {start} is in the past (today is {self._clock.today()})")
        return Reservation(
            reservation_id=uuid.uuid4().hex[:8],
            vehicle_id=vehicle_id,
            customer_name=customer_name.strip(),
            start_date=start,
            end_date=end,
            add_ons=add_ons or AddOns(),
        )

What to notice. The factory checks the vehicle too, not just the dates — "fail fast on an unknown vehicle before anyone checks for conflicts." And note what the factory does not do: it never looks at other reservations. Conflict detection is the service's job, because it needs the reservation repository. Creation vs. coordination, separated.

Step 8 — The service: search, reserve, cancel, return, quote

Goal: type RentalService. It orchestrates the factory, the repositories, and the pricing strategy — and owns the one lock that makes booking atomic.

Type car_rental/service.py:

"""The use-case layer: search, reserve, cancel, return, quote.

The service orchestrates; it does not validate dates (the factory does),
does not compute prices (the strategy does), and does not store anything
(the repositories do). One RLock makes reserve-then-check atomic, so two
threads cannot book the same window.
"""
import logging
import threading
from datetime import date

from .clock import Clock, SystemClock
from .config import RentalConfig, VehicleCategory
from .errors import (
    AlreadyCancelledError,
    DuplicateVehicleError,
    InvalidDateRangeError,
    RentalError,
    ReservationConflictError,
    ReservationNotFoundError,
)
from .factory import ReservationFactory
from .models import AddOns, Reservation, Vehicle
from .pricing import PricingStrategy, StandardPricing
from .repositories import (
    FleetRepository,
    InMemoryFleet,
    InMemoryReservations,
    ReservationRepository,
)

log = logging.getLogger(__name__)


def _require_text(value: str, name: str) -> str:
    if not value or not value.strip():
        raise ValueError(f"{name} must not be blank")
    return value.strip()


class RentalService:
    def __init__(
        self,
        *,
        fleet: FleetRepository | None = None,
        reservations: ReservationRepository | None = None,
        pricing: PricingStrategy | None = None,
        factory: ReservationFactory | None = None,
        clock: Clock | None = None,
        config: RentalConfig | None = None,
    ):
        self._config = config or RentalConfig()
        self._fleet = fleet or InMemoryFleet()
        self._reservations = reservations or InMemoryReservations()
        self._clock = clock or SystemClock()
        self._pricing = pricing or StandardPricing()
        self._factory = factory or ReservationFactory(self._fleet, self._clock)
        self._lock = threading.RLock()

    # -- fleet ----------------------------------------------------------

    def add_vehicle(self, vehicle_id: str, category: VehicleCategory,
                    make: str, model: str, year: int) -> Vehicle:
        vehicle_id = _require_text(vehicle_id, "vehicle_id")
        if not isinstance(category, VehicleCategory):
            raise ValueError("category must be a VehicleCategory")
        if self._fleet.get(vehicle_id) is not None:
            raise DuplicateVehicleError(f"vehicle {vehicle_id} already exists")
        vehicle = Vehicle(vehicle_id=vehicle_id, category=category,
                          make=_require_text(make, "make"),
                          model=_require_text(model, "model"), year=year)
        self._fleet.add(vehicle)
        log.info("added vehicle %s (%s %s)", vehicle_id, make, model)
        return vehicle

    # -- booking --------------------------------------------------------

    def search_available(self, category: VehicleCategory,
                         start: date, end: date) -> list[Vehicle]:
        self._check_range(start, end)
        return [v for v in self._fleet.by_category(category)
                if not self._reservations.has_overlap(v.vehicle_id, start, end)]

    def reserve(self, vehicle_id: str, customer_name: str,
                start: date, end: date, add_ons: AddOns | None = None) -> Reservation:
        with self._lock:
            reservation = self._factory.create(
                vehicle_id, customer_name, start, end, add_ons)
            if self._reservations.has_overlap(vehicle_id, start, end):
                raise ReservationConflictError(
                    f"{vehicle_id} is already booked for part of "
                    f"{start}..{end}")
            self._reservations.add(reservation)
            log.info("reserved %s: %s %s..%s",
                     reservation.reservation_id, vehicle_id, start, end)
            return reservation

    def cancel(self, reservation_id: str) -> None:
        with self._lock:
            reservation = self._reservations.get(reservation_id)
            if reservation is None:
                raise ReservationNotFoundError(f"no reservation {reservation_id}")
            if reservation.cancelled:
                raise AlreadyCancelledError(f"{reservation_id} is already cancelled")
            reservation.cancelled = True
            self._reservations.save(reservation)
            log.info("cancelled reservation %s", reservation_id)

    def return_vehicle(self, reservation_id: str, actual_return: date) -> float:
        """Close out a rental. Returns the late fee (0.0 when on time)."""
        reservation = self._reservations.get(reservation_id)
        if reservation is None:
            raise ReservationNotFoundError(f"no reservation {reservation_id}")
        if reservation.cancelled:
            raise RentalError(f"cannot return cancelled reservation {reservation_id}")
        late_days = max(0, (actual_return - reservation.end_date).days)
        fee = self._pricing.late_fee(late_days, self._config)
        log.info("return %s: %d day(s) late, fee $%.2f",
                 reservation_id, late_days, fee)
        return fee

    def quote(self, reservation_id: str) -> float:
        reservation = self._reservations.get(reservation_id)
        if reservation is None:
            raise ReservationNotFoundError(f"no reservation {reservation_id}")
        vehicle = self._fleet.get(reservation.vehicle_id)
        return self._pricing.quote(vehicle, reservation, self._config)

    # -- helpers --------------------------------------------------------

    def _check_range(self, start: date, end: date) -> None:
        if end <= start:
            raise InvalidDateRangeError(f"end {end} must be after start {start}")

What to notice. reserve is the money method: factory-build, then conflict-check, then store — all under one lock. The lock matters because "check then act" is the classic race: without it, two threads could both see a free window and both book it. Also note search_available validates the range too. Every public entry point guards its own inputs; no method trusts its caller.

class ConcurrencyTests(unittest.TestCase):
    def test_same_window_goes_to_exactly_one_thread(self):
        svc, _ = make_service()
        barrier = threading.Barrier(2)
        outcomes = []

        def attempt(name):
            barrier.wait()
            try:
                svc.reserve("SUV-01", name, EXISTING_START, EXISTING_END)
                outcomes.append("ok")
            except ReservationConflictError:
                outcomes.append("conflict")

        threads = [threading.Thread(target=attempt, args=(n,))
                   for n in ("Awanish Singh", "Shyam Miyatra")]
        for t in threads:
            t.start()
        for t in threads:
            t.join()
        self.assertEqual(sorted(outcomes), ["conflict", "ok"])

9. Common interview follow-ups

Why half-open [start, end) instead of inclusive dates? Inclusive ends make back-to-back bookings ambiguous: is Nov 5 part of the old booking, the new one, or both? Half-open gives one clean predicate with no special cases, and it's how most real booking systems model ranges internally.

Why reject start == end? Couldn't that be a same-day rental? A zero-day window has zero days to charge for and breaks the "days × rate" math. Minimum one day keeps pricing coherent. If the business ever wants hourly rental, that's a new concept — not a tweak to this one.

How would you add weekend pricing? New PricingStrategy subclass that walks the reservation's dates and multiplies weekend days by 1.2. The service, factory, and repositories don't change — that's the Strategy seam doing its job.

Two app servers behind a load balancer — still no double-booking? Not with in-memory repos; locks don't cross processes. In Postgres you'd add an exclusion constraint: EXCLUDE USING gist (vehicle_id WITH =, daterange(start_date, end_date) WITH &&) WHERE (NOT cancelled). The database becomes the atomic check-then-act. Worth saying in an interview before being asked.

Why does the factory need the fleet repository? So an unknown vehicle fails at creation time, before any conflict check runs. Validation at the boundary, with the precise error (VehicleNotFoundError vs ReservationConflictError), instead of a vague failure downstream.

Where would you put a "minimum 2-day rental on holidays" rule? In the factory — it's a "is this window valid?" rule, same family as end-after-start. The service never learns about holidays.

The design moves that repeat

Patterns are the vocabulary. These six moves are the grammar — the small decisions that showed up in every chapter, in almost the same form, because they solve problems that every LLD problem has.

Inject the clock. Every chapter that touched time took it as a constructor argument instead of calling date.today() or datetime.now() inside the logic. The reason is testability, but the deeper reason is honesty: time is an input, and inputs belong in the signature where everyone can see them. Production passes the real clock; tests pass a fixed one; the logic never knows the difference. Once you have done this three times, a hardcoded now() inside business logic starts to look like a global variable — because that is what it is.

Validate at the boundary. Public methods guard; private helpers trust. Every chapter put its input checks at the outermost layer — negative minutes rejected, unknown ids rejected, empty strings rejected — and then wrote the inner logic as if the inputs were already clean. An error caught at the door carries full context: which argument, which call. The same error discovered three layers down has already half-mutated the state, and the stack trace reads like a riddle. Boundaries validate so internals can stay readable.

Half-open intervals for bookings. Whenever two things could not overlap in time — rental reservations, and anywhere else a resource is held for a span — the chapters used [start, end): inclusive start, exclusive end. Back-to-back bookings then never collide, and the overlap test is a single clean comparison instead of a nest of endpoint special cases. Every special case you avoid is a double-booking bug that never gets written.

Smallest-fit allocation. The parking lot gives each vehicle the smallest spot it fits in: motorcycle to compact, car to regular, truck to large. First-free would park the motorcycle in the large spot and leave the truck circling. It is greedy best-fit — preserve the scarce resource for the demand that actually needs it. The same instinct transfers anywhere capacity comes in tiers: thread pools, connection pools, warehouse bins.

Explicit transition tables. The vending machine, the traffic light, and the elevator cab all keep their states and legal transitions as data — a table you can read — instead of nested if statements scattered through methods. An impossible transition then fails loudly at the table instead of silently doing nothing inside a branch you forgot. When the interviewer asks "what happens if X arrives while in state Y," you point at one row instead of tracing five methods.

Locks around shared queues, documented. The elevator's request queue, the parking lot's spot map — anywhere two threads could touch the same mutable state, the chapters guarded it with one lock, kept the locked section short, and wrote down exactly what the lock protects at the declaration site. The documentation is part of the move: a lock whose scope lives only in the author's head is a deadlock waiting for the next person who touches the code.

Fifteen questions to test the understanding

Short answers. If you can answer these out loud, without the book open, the six chapters did their job. If one stalls you, go back to its chapter — the answer is in your fingers already.

1. Why inject a clock instead of calling date.today() directly?

A hardcoded call to the real clock makes time untestable. An injected clock turns time into an ordinary input: tests pass a fixed clock and get deterministic results, production passes the system clock and gets real behavior. The logic never knows which one it got. Time stops being hidden global state and becomes a visible parameter.

2. When does composition beat inheritance in these designs?

When the varying behavior belongs to the instance, not the class. Pricing rules, dispatch algorithms, fine calculators — these change per object or at runtime, and inheritance would fix the choice at class-definition time and multiply subclasses. Composition plugs a strategy object into a stable host. Inherit when the variation defines what the thing is; compose when it defines what the thing does. These six problems were almost always the second case. The tell is the word "kind" in the requirements — "what kind of pricing?" means the kind varies per instance, so compose.

3. How do you prevent double-booking — two cars in one spot, two patrons with the same book?

Make check-and-reserve one atomic step under a single lock. The spot map is the single source of truth; the "is it free?" check and the "mark it taken" write happen inside the same critical section, so no thread can slip between them. Then prove it: the test suite hammers the same spot from many threads and asserts exactly one winner.

4. LOOK vs SCAN for elevator dispatch — what's the difference, and when does it matter?

SCAN sweeps the shaft end to end, reversing only at the top and bottom floors. LOOK reverses at the farthest requested floor in the current direction. The difference is wasted travel: SCAN rides empty shaft to the roof; LOOK turns around where the work actually ends. It matters when requests cluster — office rush hour — and it costs nothing extra once the request set is kept explicitly. In an interview, name both algorithms, pick LOOK, and say why in one sentence. The trade-off sentence is the point being graded.

5. Why does the traffic light need an ALL_RED clearance phase?

Give cross traffic green the instant your light turns red, and you assume every vehicle stopped on time. ALL_RED gives the intersection a beat to fully clear — the late runner, the slow truck — before conflicting approaches move. It trades a second or two of throughput for a safety margin, and the transition table makes that trade explicit instead of burying it in timing constants.

6. How do you make the elevator dispatcher thread-safe?

One lock guards the request queue and the cab state together. Every mutation — enqueue a request, assign a cab, update a position — happens under it, and the locked sections stay short: no I/O, no sleeping inside the lock. Code that only needs a snapshot copies under the lock and works on the copy. And the lock's scope is documented where it is declared, because the next person to touch the dispatcher should read the invariant, not guess it. If you find yourself reaching for a second lock, stop — lock-ordering bugs are worse than contention, and one lock with short sections beats two clever ones.

7. What breaks if you store mutable default config — say a plain dict default in a dataclass?

Every instance shares the same dict, because the default expression is evaluated once at class-definition time. That is Python language behavior, not a style opinion. One lot's runtime tweak to its rates then leaks into every lot created afterward. field(default_factory=...) gives each instance its own fresh dict. The chapters go one step further and freeze config where possible, so a typo cannot mutate it silently.

8. How do you add a new vehicle type without touching existing code?

The fit rules and the pricing rules both branch on the VehicleType abstraction, never on concrete classes. A new type means one new enum member, one row in the fit table, one row in the rate table — additions, never edits. The dispatch code never names the concrete types, so it never changes. That is the Open/Closed principle with the seams placed before they were needed.

9. How do you add a new payment method to the vending machine the same way?

Payment sits behind an interface — authorize this amount, report success or failure — and the machine only knows the interface. A new method is a new class implementing it, registered in the one place where payment methods are listed. The vend logic, the change calculation, and the state machine never open for edits. Same principle as the vehicle type, different chapter.

10. Why half-open intervals — [start, end) — for bookings?

With half-open intervals, back-to-back bookings never overlap: one ends at 10:00, the next starts at 10:00, and a single comparison detects any real collision. Closed intervals need special-casing everywhere two endpoints touch, and every special case is a future double-booking bug. Pick the representation that makes the illegal state unrepresentable, and the checks write themselves.

11. Why raise custom exceptions instead of returning None or an error code?

None is silent. The caller can ignore it — and often does — and the failure surfaces three calls later with no context. A custom exception type names the failure and carries the details with it; callers catch precisely what they can handle and everything else propagates. And never a bare except:: it swallows the bugs you need to see along with the errors you expected.

12. Why logging in library code and print only in __main__ demos?

A library that prints has made decisions that belong to the operator: the output stream, the format, the verbosity. logging hands those decisions over — the deployer routes, filters, and silences per module. Python will happily let you print from anywhere; that is language behavior. Keeping print out of library code is the convention production follows, and print survives only in the __main__ demo blocks where the operator is you reading a terminal.

13. How does the Repository pattern keep storage swappable?

The business code depends on the repository's interface — find the available spots, save the ticket — never on the dict or the database behind it. The in-memory implementation satisfies the interface today; a database-backed one replaces it tomorrow without touching a single caller. Persistence becomes a deployment decision instead of a design decision, which is exactly where it belongs. The chapters prove the seam with tests: the suites run against the in-memory repository, and nothing in the business logic knows or cares.

14. Why validate at the boundary instead of deep inside?

Context. An error caught at a public method's door knows which argument was wrong and which call made it. The same error discovered three layers down has already partially mutated state, and by the time you find it you are debugging the corruption, not the cause. Boundaries validate so that internals can trust — and trusted internals stay readable, because they are not cluttered with defensive checks.

15. What is smallest-fit allocation, and why not just take the first free spot?

Smallest-fit gives each vehicle the smallest spot it fits in. First-free would park the motorcycle in the large spot and leave the truck circling the lot. It is greedy best-fit: preserve the scarce resource for the demand that needs it. The rule is three lines, the payoff is utilization, and the same instinct applies wherever capacity comes in tiers.
