Deep dive: what "the resolver walks the tree" hides

The module gave you the phone-book tree and the stub/recursive/authoritative split. That picture is right, and it is also where most people stop. It hides the part that decides how DNS behaves in production: state. Every box in the diagram is a cache with its own keys, its own expiry rules, its own caps, and its own failure behaviour. "DNS is slow", "DNS is stale" and "DNS works on my laptop but not in the pod" are almost always questions about which cache answered and why.

This deep dive goes under the analogy. It covers what each resolver role actually stores, the TTL arithmetic that follows, negative caching, a full dig +trace read line by line, what happens when an answer outgrows a UDP datagram, the DNSSEC chain of signatures, encrypted transports, and the two traps that bite modern infrastructure hardest: split-horizon views and the Kubernetes ndots search list.

Deep dive: the real mental model — caches all the way down

The three roles, as machines with state

Think of each role in terms of what it keeps in memory and what it does on a miss.

The stub resolver lives on your machine. It holds configuration, not knowledge: a list of nameservers, a search list, and options such as ndots, timeout and attempts. Whether it caches depends entirely on the OS.

  • glibc on Linux does not cache at all. Every getaddrinfo() goes to the network unless something local (systemd-resolved on 127.0.0.53, nscd, dnsmasq) sits in front.
  • macOS routes lookups through mDNSResponder, which does cache and also holds per-domain resolver rules (scutil --dns prints them, including /etc/resolver/<domain> files and VPN-pushed scopes).
  • Applications and runtimes often cache on top. Browsers keep their own host cache. The JVM caches successful lookups for 30 seconds by default when no security manager is installed, controlled by networkaddress.cache.ttl. Go, Node and Python have their own quirks; none of them sees the TTL through getaddrinfo().

The recursive resolver is where the real state lives. A production resolver such as Unbound or BIND keeps several separate structures:

  • The RRset cache. Key: (owner name, type, class). Value: the record set plus an absolute expiry time. The resolver never stores "TTL 300"; it stores "expires at 14:05:00" and computes the remaining TTL on every answer.
  • The negative cache. NXDOMAIN entries keyed by name, and NODATA entries keyed by (name, type). Each one also carries an expiry derived from the zone's SOA (more below).
  • The infrastructure cache. For every authoritative server it has talked to: a smoothed RTT estimate, whether it handles EDNS, whether it has been lame or timing out. Resolvers use the RTT numbers to pick the fastest of a zone's nameservers, which is why the second query to a zone is often faster than the first even when the answer itself was not cached.
  • The delegation cache. NS records and glue for every zone cut it has crossed. A warm resolver jumps straight to example.com's servers without touching root or .com.
  • The key cache (validating resolvers only). DNSKEY and DS sets plus their validation status: secure, insecure or bogus.
  • The in-flight request list. If 500 clients ask for the same name in the same millisecond, a good resolver sends one upstream query and fans the answer out to all of them.

The authoritative server keeps no cache at all for its own zones. It holds the zone in memory, answers from it, and sets the aa flag. Its state is the zone data plus a serial number in the SOA, which secondaries poll to know when to transfer a new copy.

TTL arithmetic: remaining TTL flows downstream

Because each cache stores an absolute expiry, the TTL it hands downstream is the remaining time, not the original value. A stub that caches a resolver's answer expires at the same instant as the resolver's copy. Layers do not add up. That is the rule that makes migrations predictable.

Two things do break the rule. First, any layer that ignores the TTL and pins its own value: an application cache, a JVM, a client library with a fixed refresh interval. Second, resolver caps. Resolvers clamp TTLs to a configured maximum and sometimes a minimum. Unbound's defaults are cache-max-ttl: 86400 and cache-max-negative-ttl: 3600. BIND's are max-cache-ttl 604800 (one week) and max-ncache-ttl 10800 (three hours). Operators can and do change these, and some public resolvers enforce a floor. Treat any specific number as a default that varies.

The script below does this arithmetic with a fake clock. Real output from the sandbox:

"""TTL arithmetic a resolver actually does: absolute expiry, remaining TTL handed
downstream, resolver caps, and RFC 2308 negative-cache TTL. Fake clock, no network."""
from dataclasses import dataclass

@dataclass
class Entry:
    data: str
    expires: float          # absolute time, not a countdown

class Cache:
    def __init__(self, name, max_ttl=86400, max_neg_ttl=3600):   # Unbound's defaults
        self.name, self.max_ttl, self.max_neg = name, max_ttl, max_neg_ttl
        self.store = {}

    def put(self, key, data, ttl, now, negative=False):
        ttl = min(ttl, self.max_neg if negative else self.max_ttl)
        self.store[key] = Entry(data, now + ttl)

    def get(self, key, now):
        e = self.store.get(key)
        if e and e.expires > now:
            return e.data, int(e.expires - now)  # remaining TTL is what goes downstream
        return None, 0

def negative_ttl(soa_ttl, soa_minimum):
    return min(soa_ttl, soa_minimum)             # RFC 2308 section 5

print("      both copies die at t=300: worst-case staleness is 300s, not 300+300s")

app_pin = 30

Read the migration line twice. Lowering the TTL is itself a DNS change, so it is subject to the old TTL. If you lower from 86400 to 300 at noon on Tuesday, a resolver that fetched the record at 11:59 still holds it, with the old TTL, until 11:59 on Wednesday. Change the address before then and that resolver serves the old one for up to a day.

The last block is the other side of the trade. Each busy resolver cache refetches a record roughly once per TTL, so authoritative load scales as (number of independent caches) ÷ TTL. It is an upper bound, because idle caches don't refetch. Note "independent caches": a large public resolver is not one cache. It is many anycast sites, and often several cache instances per site, so it can count as hundreds of caches against your authority.

Negative caching, precisely

A "no" comes in two shapes, and resolvers cache them differently.

Response Header Means Cached per Typical cause
NXDOMAIN status: NXDOMAIN (RCODE 3) The name does not exist, for any type name typo, deleted record, record not created yet
NODATA status: NOERROR, ANSWER: 0 The name exists, but not with this type (name, type) asking AAAA for an IPv4-only host

Both carry the zone's SOA record in the authority section. RFC 2308 says the negative TTL is the smaller of two numbers: the SOA record's own TTL and the SOA's MINIMUM field (the last number in the record). The script above shows the three common combinations. A resolver cap can only shorten the result.

Two refinements matter in 2026. RFC 8020 says an NXDOMAIN means nothing exists below that name either, so a resolver may answer NXDOMAIN for a.b.gone.example.com straight from a cached NXDOMAIN for gone.example.com. And RFC 8198 ("aggressive NSEC") lets a validating resolver use signed NSEC ranges it already holds to synthesize NXDOMAIN for names it has never asked about. Both make "it doesn't exist" stickier than people expect.

Deep dive: what the wire actually shows

dig +trace, read line by line

dig +trace does not ask your resolver to recurse. It asks your resolver once for the root NS set, then plays recursive resolver itself: it queries a root server, follows the referral to .com, follows the next referral to the zone's servers, and prints each response. Constructed illustration (realistic shape and numbers, your output will differ; signatures and digests elided):

;; Received 191 bytes from 203.0.113.53#53(ns1.example.com) in 18 ms
  1. The root NS set came from your local resolver's cache. You can tell because the TTL is 517913, not the root zone's 518400 (six days). The resolver fetched it 487 seconds ago and is counting down.
  2. "Received … from 192.168.1.1" confirms it. Every later block comes from a different server, picked at random by dig.
  3. The root's referral. The root zone serves .com's NS records with TTL 172800 (two days). These sit in the authority section of a non-authoritative response. dig +trace hides the glue A/AAAA records in the additional section; add +additional to see them.
  4. The DS record is the DNSSEC link from root to .com: a hash of .com's key-signing key, signed by the root (algorithm 8 is RSA/SHA-256, labels 1). The two long numbers in every RRSIG are the expiration and inception times. A signature outside that window is invalid, no matter how good the math.
  5. .com's referral to the zone, with the zone's own DS. Notice the RRSIG on this DS has signer com.: each parent signs the link to its child.
  6. The authoritative answer, with its own signature by example.com. (labels 3 = www.example.com). The 18 ms is one RTT to the zone's nameserver.

What the trace does not show is just as useful. It bypasses your resolver's cache, so it shows what the world will see after caches expire, not what your users see now. That makes it the right tool after a change ("is the delegation right?") and the wrong tool for "why is my laptop still getting the old IP?" For that, dig www.example.com against your normal resolver and watch the TTL count down.

One macOS warning. The dig that ships with macOS is BIND 9.10.6, and it reads /etc/resolv.conf directly. It ignores the per-domain rules that mDNSResponder applies to every real application, such as VPN split DNS and /etc/resolver/* files. To see what applications see, use dscacheutil -q host -a name www.example.com. For newer dig features used below (+https, Extended DNS Error output), install a current BIND with brew install bind. On Linux, getent ahosts www.example.com follows the same path as getaddrinfo(), and resolvectl query does the same when systemd-resolved is in use.

An NXDOMAIN, and the number that controls it

$ dig newapi.example.com                    # constructed illustration
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 60120
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; AUTHORITY SECTION:
example.com.  3412  IN  SOA  ns1.example.com. hostmaster.example.com. 2026101601 7200 3600 1209600 3600

The SOA fields after the two names are serial, refresh, retry, expire and MINIMUM. Here MINIMUM is 3600 and the SOA's TTL was also 3600, so the negative TTL is 3600 seconds. The resolver has held this "no" for 188 seconds, which is why the SOA's TTL now reads 3412. If you create newapi right now, this resolver keeps saying it doesn't exist for another 57 minutes. The fix is not to flush everything. It is to never query a name before creating it: health checks and deploy scripts that "probe whether the record is live yet" poison the cache they are waiting on.

EDNS0: how a 12-byte header asks for bigger answers

The original limit for DNS over UDP was 512 bytes. EDNS0 (RFC 6891) lifts it with a pseudo-record called OPT, placed in the additional section. OPT reuses the record fields for new meanings:

Field Normal meaning In OPT
NAME owner name always root (one zero byte)
TYPE record type 41
CLASS IN (1) the sender's UDP payload size
TTL (32 bits) cache time extended RCODE (8) · version (8) · DO bit (1) · zero (15)
RDATA record data options: cookies, padding, client subnet, EDE…

The script below builds a query by hand, runs a tiny authoritative server on localhost, and serves an answer too big for the advertised buffer. The server sets TC; the client retries the same query over TCP, where every message gets a 2-byte length prefix (RFC 1035 §4.2.2). Real output:

"""A tiny authoritative server on localhost that answers over UDP and TCP.
The client advertises an EDNS0 buffer of 1232 bytes; the answer is bigger,
so the server sets TC=1 over UDP and the client retries over TCP."""
import socket, socketserver, struct, threading, time

def qname(name):
    return b"".join(bytes([len(p)]) + p.encode() for p in name.rstrip(".").split(".")) + b"\0"

def build_query(qid, name, qtype=16, bufsize=1232, do=False):
    hdr = struct.pack("!HHHHHH", qid, 0x0100, 1, 0, 0, 1)      # RD=1, QD=1, AR=1
    q = qname(name) + struct.pack("!HH", qtype, 1)
    ttl_field = 0x00008000 if do else 0                           # ext-rcode|ver|DO|Z
    opt = b"\0" + struct.pack("!HHIH", 41, bufsize, ttl_field, 0) # root name, TYPE=OPT
    return hdr + q + opt

def parse_header(msg):
    qid, flags, qd, an, ns, ar = struct.unpack("!HHHHHH", msg[:12])
    names = [n for b, n in [(15, "qr"), (10, "aa"), (9, "tc"), (8, "rd"), (7, "ra")] if flags >> b & 1]
    return qid, " ".join(names), flags & 0xF, an

def client_bufsize(query):
    # OPT RR is the last 11 bytes of our query: name(1) type(2) class(2) ttl(4) rdlen(2)
    return struct.unpack("!H", query[-8:-6])[0] if len(query) > 12 else 512

# Zone data: eight 200-byte TXT strings, like a domain with lots of verification tokens.
TXT = [("v%d=" % i + "x" * 196).encode() for i in range(8)]

def answer(query):
    qid = struct.unpack("!H", query[:2])[0]
    end = query.index(b"\0", 12) + 5
    question = query[12:end]
    rrs = b"".join(b"\xc0\x0c" + struct.pack("!HHIH", 16, 1, 300, len(t) + 1) + bytes([len(t)]) + t
                   for t in TXT)
    hdr = struct.pack("!HHHHHH", qid, 0x8500, 1, len(TXT), 0, 0)  # QR AA RD, NOERROR
    return hdr + question + rrs

class UDP(socketserver.BaseRequestHandler):
    def handle(self):
        data, sock = self.request
        full = answer(data)
        limit = client_bufsize(data)
        if len(full) > limit:  # truncate: header + question only, TC bit set
            end = data.index(b"\0", 12) + 5
            hdr = bytearray(full[:12]); hdr[2] |= 0x02; hdr[6:8] = b"\0\0"
            full = bytes(hdr) + data[12:end]
        sock.sendto(full, self.client_address)

class TCP(socketserver.BaseRequestHandler):
    def handle(self):
        n = struct.unpack("!H", self.request.recv(2))[0]   # 2-byte length prefix (RFC 1035 4.2.2)
        data = b""
        while len(data) < n:
            data += self.request.recv(n - len(data))
        resp = answer(data)
        self.request.sendall(struct.pack("!H", len(resp)) + resp)

udp = socketserver.UDPServer(("127.0.0.1", 0), UDP)
port = udp.server_address[1]
tcp = socketserver.TCPServer(("127.0.0.1", port), TCP)
for s in (udp, tcp):
    threading.Thread(target=s.serve_forever, daemon=True).start()

q = build_query(0x4d2a, "big.example.test", bufsize=1232, do=True)
print(f"query: {len(q)} bytes, EDNS bufsize={client_bufsize(q)}, DO=1")
print("  hex:", q.hex(" "))

t0 = time.perf_counter()
u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u.settimeout(2)
u.sendto(q, ("127.0.0.1", port))
r, _ = u.recvfrom(65535)
qid, flags, rcode, an = parse_header(r)
print(f"UDP reply: {len(r)} bytes  id={qid:#06x} flags=[{flags}] rcode={rcode} answers={an}")

if "tc" in flags:
    t = socket.create_connection(("127.0.0.1", port), timeout=2)
    t.sendall(struct.pack("!H", len(q)) + q)
    n = struct.unpack("!H", t.recv(2))[0]
    r = b""
    while len(r) < n:
        r += t.recv(n - len(r))
    qid, flags, rcode, an = parse_header(r)
    print(f"TCP reply: {len(r)} bytes  id={qid:#06x} flags=[{flags}] rcode={rcode} answers={an}")
print(f"total {1000*(time.perf_counter()-t0):.2f} ms on loopback (one extra RTT + TCP handshake on a real path)")

Decode the last 11 bytes of the query: 00 (root name), 00 29 (TYPE 41), 04 d0 (1232), 00 00 80 00 (extended RCODE 0, version 0, DO bit set), 00 00 (no options). The UDP reply is 34 bytes: header plus question, zero answers, tc set. Over TCP the same answer is 1730 bytes. On a real path the fallback costs a TCP handshake plus one more round trip, so roughly two RTTs on top of the wasted UDP exchange.

Why 1232? It is the payload that fits an IPv6 minimum-MTU packet without fragmentation: 1280 − 40 (IPv6 header) − 8 (UDP header). DNS Flag Day 2020 made it the recommended default, and current BIND and Unbound ship with it. Larger buffers (4096 was the old habit) invite IP fragmentation. Fragments get dropped by firewalls that can't see the UDP header in non-first fragments, and fragmented answers have been used for cache-poisoning attacks. A truncated answer that falls back to TCP is slower; a fragmented answer that vanishes is a timeout. Resolvers prefer the first.

This is also why TCP/53 is not optional. RFC 7766 requires DNS implementations to support TCP, and RFC 9210 makes it an operational requirement for servers and the networks in front of them.

The DNSSEC chain, as a validator walks it

DNSSEC adds signatures, not encryption. Answers are still readable on the wire; they just become unforgeable. A validating resolver proves www.example.com A like this:

  1. It holds one trust anchor: the root zone's key-signing key (KSK), configured locally and updated automatically under RFC 5011.
  2. It fetches the root's DNSKEY set and checks that the set is signed by the anchored KSK. That makes the root's zone-signing key (ZSK) trusted.
  3. It checks the RRSIG on the root's com. DS record with the root ZSK. The DS is a hash of .com's KSK.
  4. It fetches .com's DNSKEY set, hashes the KSK, and compares to the DS. Match: .com's keys are trusted. Repeat one level down for example.com's DS and DNSKEY.
  5. It checks the RRSIG on the A record with example.com's ZSK, and checks the inception/expiration window against its own clock.
  6. If every link holds, it sets AD (authenticated data) in the reply. If any link fails, it returns SERVFAIL, not the unverified data.

Unsigned zones are fine: the parent proves, with a signed NSEC or NSEC3 record, that no DS exists, and the validator marks the child "insecure" and answers normally. The dangerous state is a DS in the parent that no longer matches the child's keys. That happens after a DNS provider move or a botched key rollover, and it makes the whole zone SERVFAIL for every validating resolver at once.

Proving a DNSSEC failure takes two queries. The +cd flag (checking disabled) tells the resolver to skip validation:

$ dig www.broken.example                    # constructed illustration, BIND 9.18+ dig
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 3301
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
; EDE: 7 (Signature Expired)

$ dig +cd www.broken.example
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 3302
;; flags: qr rd ra cd; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

SERVFAIL without +cd and an answer with it means validation is failing. The EDE line is an Extended DNS Error (RFC 8914) that modern resolvers attach to explain the failure: 6 is "DNSSEC Bogus", 7 "Signature Expired", 9 "DNSKEY Missing", 22 "No Reachable Authority". macOS's built-in dig is too old to print EDE.

Encrypted transports: DoT, DoH, DoQ

Classic DNS is plaintext UDP, so anyone on the path can read and rewrite it. Three transports fix that between the stub and the resolver. None of them changes the resolver-to-authoritative leg, which is still mostly plaintext.

Transport RFC Port What it looks like on the wire
DNS over TLS (DoT) 7858 TCP 853 a TLS session carrying length-prefixed DNS messages; easy to identify and block
DNS over HTTPS (DoH) 8484 TCP 443 (or UDP 443 with HTTP/3) HTTP POST or GET of application/dns-message; blends into web traffic
DNS over QUIC (DoQ) 9250 UDP 853 QUIC streams, one query per stream

The operational consequence is who chooses the resolver. With DoH, the application can pick its own resolver and bypass the OS entirely. A browser doing that will not see your corporate split-horizon zone, and your network's DNS logs go quiet. Firefox checks a canary name, use-application-dns.net: if the network's resolver returns NXDOMAIN for it, Firefox does not enable DoH by default. Managed browsers can be pinned by policy. RFC 9462 (Discovery of Designated Resolvers) goes the other way: a client asks its plain resolver for _dns.resolver.arpa SVCB records and learns an encrypted endpoint for the same resolver.

To try DoH without any special tool, curl can resolve its own target over DoH: curl --doh-url https://1.1.1.1/dns-query -sv https://example.com -o /dev/null (run on your Mac — your output will differ).

Cache hit at a public anycast resolver ~5–30 ms depends on distance to the nearest site
Cold full walk ~50–300 ms root and TLD referrals are usually cached, so the zone's own RTT dominates
TCP fallback cost +2 RTT handshake plus the retried query
Route 53 Resolver per-ENI limit 1024 packets/s AWS-documented; exceeding it drops queries silently

Hit-rate math is simple once you see that misses are per TTL, not per query. A resolver receiving 100 queries per second for one name with TTL 60 misses about once a minute: a hit rate of 1 − (1/60)/100 ≈ 99.98%. The same name at 0.01 queries per second (once every 100 s) misses every time. Low-traffic names get almost nothing from caching, which is why a cold internal service can see full-walk latency on most lookups while the popular ones are instant.

Deep dive: production failure modes

"We changed the record an hour ago and half the traffic still goes to the old IP." Mechanism: the old answer was cached with a long TTL, or something above the resolver pins answers. Prove it: dig api.example.com against the resolvers your clients use and read the TTL column; compare with dig @ns1.example.com api.example.com (authoritative, aa set). If the resolver is right but clients are wrong, look at application caches: JVM networkaddress.cache.ttl, connection pools that never re-resolve, HTTP keep-alive connections still open to the old IP. Fix: lower TTLs one old-TTL ahead; make long-lived clients re-resolve on reconnect.

"The new record works for me but not for the monitoring system." Mechanism: the monitor queried the name before it existed and cached NXDOMAIN for the SOA's negative TTL. Prove it: dig the name against the monitor's resolver and look for status: NXDOMAIN with a counting-down SOA TTL. Fix: create before you probe; keep SOA MINIMUM modest (300–3600 s is common).

"Some lookups time out, but only for one domain, and only from the office." Mechanism: the answer is large (DNSSEC, many TXT records, long SPF chains), the network drops UDP fragments or blocks TCP/53, so either the fragmented reply vanishes or the TCP retry fails. Prove it: dig +dnssec +bufsize=4096 TXT example.com (likely times out), then dig +tcp TXT example.com (fails if TCP/53 is blocked), then dig +bufsize=1232 TXT example.com (when the answer exceeds 1232 bytes, dig prints ;; Truncated, retrying in TCP mode.). Fix: allow TCP/53; use 1232-byte buffers; trim bloated TXT sets.

"Everything in one zone is SERVFAIL, everywhere, at once." Mechanism: DNSSEC broke. Signatures expired because the signer stopped, or the DS in the parent no longer matches after a provider change. Prove it: the +cd test above; check the RRSIG expiration timestamps; compare dig DS example.com @a.gtld-servers.net with dig DNSKEY example.com @ns1.example.com. Fix: re-sign, or update/remove the DS at the registrar. Remember the DS has its own TTL (86400 s in .com), so the repair propagates at that speed.

"Pods take 5 seconds to resolve, randomly." Mechanism: glibc sends the A and AAAA queries in parallel from the same socket. In kube-proxy's iptables mode both UDP packets are DNAT-ed to a CoreDNS pod, and a race in conntrack insertion can drop one. glibc then waits its full 5-second timeout before retrying. Prove it: conntrack -S on the node and watch insert_failed climb; CoreDNS sees only one of the two queries. Fix: NodeLocal DNSCache (a node-local resolver on 169.254.20.10 that talks TCP upstream), or options single-request-reopen in the pod's dnsConfig.

"Every external call from the cluster makes ten DNS queries." Mechanism: the ndots:5 search list. The next section shows the arithmetic. Prove it: enable the CoreDNS log plugin briefly and watch api.vendor.example.payments.svc.cluster.local NXDOMAINs scroll past. Fix: trailing dots on external FQDNs in config, or dnsConfig: {options: [{name: ndots, value: "2"}]} for workloads that mostly call out.

"It resolves in the VPC but the record we just added in the public zone doesn't." Mechanism: split-horizon shadowing. In AWS, if a Route 53 private hosted zone for example.com is associated with the VPC, the VPC resolver answers every example.com name from the private zone. A name missing there gets NXDOMAIN; it does not fall through to the public zone. Prove it: compare dig from inside the VPC with dig @8.8.8.8 from outside. Fix: create the record in both zones, or make the private zone a narrower subdomain.

"dig says one thing, the app does another" (on a Mac). Mechanism: macOS dig reads /etc/resolv.conf and bypasses mDNSResponder's scoped resolvers, so VPN split DNS and /etc/resolver/* rules don't apply to it. Prove it: scutil --dns lists the per-domain resolvers; dscacheutil -q host -a name <host> shows what applications get. Fix: debug with the tool that follows the same path as the app. Flush with sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder.

Deep dive: 2026 context

Kubernetes: the ndots search list

A pod's /etc/resolv.conf usually looks like the one in the script below: the cluster DNS service IP, a search list starting with the pod's own namespace, and options ndots:5. The rule (glibc and most stubs) is: if the name has fewer dots than ndots and no trailing dot, try every search domain first and the literal name last. Real output:

"""What a glibc-style stub actually sends for one getaddrinfo() call,
given a Kubernetes pod's /etc/resolv.conf. Pure computation, no network."""

RESOLV_CONF = """\
nameserver 10.96.0.10
search payments.svc.cluster.local svc.cluster.local cluster.local us-west-2.compute.internal
options ndots:5
"""

def parse(text):
    search, ndots = [], 1                      # ndots defaults to 1 when unset
    for line in text.splitlines():
        key, *vals = line.split()
        if key == "search":
            search = vals
        elif key == "options":
            for v in vals:
                if v.startswith("ndots:"):
                    ndots = int(v.split(":")[1])
    return search, ndots

def candidates(name, search, ndots):
    if name.endswith("."):                     # fully qualified: no search list at all
        return [name]
    absolute = name + "."
    expanded = [f"{name}.{d}." for d in search]
    # dots >= ndots: try the name as-is first; otherwise walk the search list first
    return [absolute] + expanded if name.count(".") >= ndots else expanded + [absolute]

search, ndots = parse(RESOLV_CONF)
for name in ["ledger", "ledger.payments", "api.vendor.example", "api.vendor.example."]:
    tries = candidates(name, search, ndots)
    # the real answer exists only for the last candidate in the external case;
    # every earlier try is an NXDOMAIN, and glibc asks A and AAAA for each.
    hit = next((i for i, c in enumerate(tries)
                if c in ("ledger.payments.svc.cluster.local.", "api.vendor.example.")), None)
    used = tries[: hit + 1]
    print(f"{name!r:22} dots={name.rstrip('.').count('.')}  "
          f"queries={2*len(used):2d} (A+AAAA x {len(used)})  NXDOMAIN rounds={len(used)-1}")
    for c in used:
        print("    ", c)
'ledger'               dots=0  queries= 2 (A+AAAA x 1)  NXDOMAIN rounds=0
     ledger.payments.svc.cluster.local.
'ledger.payments'      dots=1  queries= 4 (A+AAAA x 2)  NXDOMAIN rounds=1
     ledger.payments.payments.svc.cluster.local.
     ledger.payments.svc.cluster.local.
'api.vendor.example'   dots=2  queries=10 (A+AAAA x 5)  NXDOMAIN rounds=4
     api.vendor.example.payments.svc.cluster.local.
     api.vendor.example.svc.cluster.local.
     api.vendor.example.cluster.local.
     api.vendor.example.us-west-2.compute.internal.
     api.vendor.example.
'api.vendor.example.'  dots=2  queries= 2 (A+AAAA x 1)  NXDOMAIN rounds=0
     api.vendor.example.

ndots:5 exists so that ledger.payments (service.namespace) and deeper short names resolve inside the cluster. The cost lands on external names. api.vendor.example has two dots, so it walks four search domains, each producing an NXDOMAIN for A and for AAAA, before the real query: ten queries and four wasted round trips per lookup. CoreDNS's 30-second cache soaks up some of that, but each of those NXDOMAINs is a separate cache entry, and the last search domain (here the cloud's compute.internal) may be forwarded to the VPC resolver, which then counts against the per-interface packet limit. The trailing dot (api.vendor.example.) skips the walk completely. Musl-based images (Alpine) have historically handled search lists differently from glibc, so test with the image you ship.

Cloud VPC resolvers

Every major cloud gives a VPC a built-in recursive resolver at a link-local or reserved address (in AWS, the VPC base address plus two, and 169.254.169.253). It merges private zones, public DNS and forwarding rules, which makes it the place split-horizon lives in the cloud. It also has quotas. AWS documents 1024 packets per second per network interface to the Route 53 Resolver. A busy node running many pods, all doing ndots expansion, can hit that and see dropped queries that look like random timeouts. Node-local caching is the standard fix.

HTTPS/SVCB records

RFC 9460 added the SVCB and HTTPS record types. An HTTPS record tells a client, before it connects, which ALPN protocols the service speaks (alpn="h3,h2"), alternative endpoints and ports, address hints, and the public key for Encrypted ClientHello. Browsers query HTTPS alongside A and AAAA, which is how a first visit can go straight to HTTP/3 without a prior Alt-Svc header (Module 12's deep dive). It also works at the zone apex, where CNAME is illegal. dig HTTPS cloudflare.com with a current dig shows one (run on your Mac with Homebrew BIND — your output will differ).

Resilience features that change what "expired" means

RFC 8767 "serve-stale" lets a resolver answer from expired cache entries when every authoritative server for the zone is unreachable. It recommends a short TTL on stale answers (30 s) and a limit of one to three days. Major public resolvers and recent BIND and Unbound support it. That turns some authoritative outages into non-events. It also means "TTL expired" no longer guarantees "the old answer is gone" while your authority is down. EDE 3 ("Stale Answer") flags it.

Root key rollover

The root KSK is being rolled from KSK-2017 to KSK-2024. ICANN's published plan scheduled the new key to start signing in October 2026. Resolvers that track trust anchors automatically (RFC 5011) or ship updated anchors handle this without action. A validating resolver frozen on an old image with a hard-coded anchor does not, and it will SERVFAIL everything once the old key is gone. If you run validators in long-lived appliances or air-gapped networks, check their anchors.

Deep dive: senior interview questions

Q1: A resolver caches an answer with TTL 300. A stub behind it caches it too. What is the worst-case staleness after you change the record? 300 seconds, not 600. The resolver passes down the remaining TTL, so both copies expire at the same instant. The stub can only add staleness if it ignores the TTL it was given. Application-level caches and resolver minimum-TTL floors are the usual culprits.

Q2: Why must you wait a full old TTL after lowering a TTL before making the real change? The TTL change is itself a cached record. Any resolver that fetched the record just before you lowered it holds it, with the old TTL, for that long. Only after one old-TTL has passed is every cached copy guaranteed to carry the short TTL.

Q3: How long is an NXDOMAIN cached, and who decides? The zone owner, through the SOA returned in the authority section: min(SOA TTL, SOA MINIMUM), per RFC 2308. Resolvers may cap it lower (Unbound 3600 s, BIND 10800 s by default). NXDOMAIN applies to the name for all types; NODATA applies only to the (name, type) asked.

Q4: A query works with dig +tcp but times out without it. What's happening? The UDP response is large and is being lost, almost always as IP fragments dropped by a middlebox. The client never sees a truncated reply, so it never falls back. Lowering the EDNS buffer to 1232 makes the server truncate instead, which triggers a TCP retry that works.

Q5: What does dig +trace tell you that dig doesn't, and when is it the wrong tool? It shows the delegation chain from the root, with each server's referral, DS records and RRSIGs. That verifies what the world will see once caches expire. It skips your resolver's cache, so it cannot explain what your users see now. Use plain dig against their resolver for that.

Q6: Walk me through DNSSEC validation of one A record. What fails if the parent's DS doesn't match? Trust anchor (root KSK) → root DNSKEY set → signed DS for .com → .com DNSKEY set matching that DS → signed DS for example.com → example.com DNSKEY set matching it → RRSIG over the A record within its validity window. A DS mismatch breaks the chain at that zone cut, so every name in and below the zone returns SERVFAIL from validating resolvers. dig +cd succeeding proves it.

Q7: Why does a pod calling api.vendor.example produce ten DNS queries? ndots:5 and a four-domain search list. The name has two dots, fewer than five, so the stub tries all four search suffixes first, each as A and AAAA, and each returning NXDOMAIN, then the literal name. A trailing dot or a lower ndots removes the walk.

Q8: Your company's internal zone stops resolving for some laptops after a browser update. Nothing changed in DNS. Why? The browser turned on DNS over HTTPS to a public resolver, bypassing the OS resolver and with it the split-horizon view. The public resolver has never heard of the internal names. Fixes: enterprise policy to disable or pin DoH, the use-application-dns.net canary for Firefox, or offering an internal DoH endpoint.

Q9: DoH, DoT and DoQ: what do they protect, and what don't they? They encrypt the stub-to-resolver leg, so the local network can't read or rewrite queries. The resolver still sees everything, and the resolver-to-authoritative leg is usually still plaintext. The destination IP and, without ECH, the TLS SNI of the connection that follows still reveal where you went.

Q10: Why 1232 bytes? The IPv6 minimum MTU is 1280 bytes. Subtract 40 for the IPv6 header and 8 for UDP, and 1232 bytes of DNS payload fits any compliant path without fragmentation. Answers bigger than that are truncated and retried over TCP instead of risking fragments.

Standards cited in this deep dive: RFC 1035 (TCP length prefix), RFC 2308 (negative caching), RFC 5011 (trust-anchor updates), RFC 6891 (EDNS0), RFC 7766 and RFC 9210 (DNS over TCP), RFC 7858 (DoT), RFC 8020 (NXDOMAIN cut), RFC 8198 (aggressive NSEC), RFC 8484 (DoH), RFC 8767 (serve-stale), RFC 8914 (Extended DNS Errors), RFC 9250 (DoQ), RFC 9460 (SVCB/HTTPS), RFC 9462 (DDR). Resolver defaults (Unbound, BIND, CoreDNS, glibc) and the AWS limit are vendor behaviour and can change by version.
