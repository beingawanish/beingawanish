Deep dive: VLANs and spanning tree as the switch actually runs them

Painted ports are the right first picture. They hide the part that explains every VLAN bug: a VLAN isn't a property of a cable or a port. It's a number the switch attaches to each frame on the way in, and it becomes half the key of every forwarding-table lookup. Get the per-port rules for attaching and removing that number wrong, and frames quietly change color.

The fire marshal hides something too. Spanning tree isn't a person walking the building. It's a distributed algorithm. Every switch compares small vectors of numbers it hears in BPDUs, keeps the best one per port, and gates forwarding on the result. Its convergence time falls straight out of its timers, and its failure modes come from the cases where a switch stops hearing BPDUs it should hear.

The last section explains why most new data centers don't run either one between switches anymore.

Deep dive: the real mental model — a lookup keyed by (VLAN, MAC)

Three settings per port

IEEE 802.1Q describes a VLAN-aware bridge port with three pieces of configuration. Vendors hide them behind "access" and "trunk," but every switch implements them:

  • PVID (port VLAN ID). The VLAN given to an untagged frame that arrives on this port. On an access port, this is "the port's VLAN." On a trunk, it's the native VLAN.
  • Acceptable frame types. Admit all frames, only tagged frames, or only untagged and priority-tagged frames. An access port should admit only untagged. Many don't enforce it, which matters for VLAN hopping.
  • Member set, split into tagged and untagged. The VLANs this port may send, and for each one whether it leaves with a tag or without. An access port is untagged in one VLAN. A trunk is tagged in many and untagged in, at most, its native VLAN.

"Native VLAN" is therefore not a special mechanism. It is just "PVID = N, and N is in the untagged egress set." A native-VLAN mismatch is two switches with different PVIDs on the two ends of one cable.

The pipeline every frame goes through

Inside the switch ASIC, every frame passes the same stages:

  1. Ingress classification. If the frame carries an 802.1Q tag, its VID comes from the tag. If not, the VID is the port's PVID. If the port isn't a member of that VID, the frame is dropped (ingress filtering).
  2. Spanning-tree gate. The port's STP state, for the spanning-tree instance that owns this VID, decides what happens next. Discarding: drop the frame, but still read BPDUs. Learning: learn the source address, don't forward. Forwarding: both.
  3. Learning. Write FDB[(VID, source MAC)] = ingress port, and reset that entry's age. The default aging time is 300 seconds (802.1D's recommended value; configurable on every switch).
  4. Lookup. Read FDB[(VID, destination MAC)]. A hit gives one egress port. A miss, a broadcast or an unknown multicast floods to every port in the VID's member set, except the one it came in on.
  5. Egress. For each output port, look up whether this VID is tagged or untagged on that port. Add or keep the tag, or strip it, and recompute the FCS.

The VID is half the key in steps 3 and 4. The same MAC address in VLAN 20 and VLAN 310 is two independent entries. Most switches work this way, which 802.1Q calls independent VLAN learning. That is what isolation means mechanically: a frame classified into VLAN 20 can only ever match VLAN 20's entries and flood to VLAN 20's member ports. Nothing reads the color sticker again until egress.

Spanning tree is a comparison of priority vectors

Every BPDU carries a priority vector: root bridge ID, root path cost, sender's bridge ID, sender's port ID. (The receiving port's own ID is the final tiebreaker.) Each switch keeps the best vector it has heard on each port. "Best" means lowest, compared field by field from left to right, like a tuple compare in Python.

From those stored vectors, everything follows:

  • The root bridge is the lowest root ID anyone has heard.
  • A switch's root port is the port holding the best vector after adding that port's own path cost.
  • On each link, the port that would send the best vector is designated for that link.
  • Every other port is alternate (a backup path to the root) or backup (a second port onto a link this switch already serves). Both discard.

The bridge ID is 8 bytes. In practice, the top 4 bits are the configurable priority, so priority comes in steps of 4096. The next 12 bits are the extended system ID, which per-VLAN implementations set to the VLAN number. The last 48 bits are a MAC address. That's why a switch configured with priority 32768 shows "32778" in VLAN 10's spanning tree: 32768 + 10.

Path cost comes from link speed. 802.1D-1998 used 16-bit costs (1G = 4, 10G = 2), which ran out of room above 10G. 802.1D-2004 adopted 32-bit "long" costs from 802.1t: 20,000,000,000 divided by the speed in kbit/s, so 1G = 20,000, 10G = 2,000, 100G = 200. Some vendors still default to short costs. Mix the two methods in one network and the "shortest" path becomes nonsense, so check which one each platform uses.

Instances. 802.1Q's MSTP runs several trees and maps groups of VLANs to each one. Cisco's PVST+ and Rapid-PVST+ (vendor protocols) run one tree per VLAN, which costs a BPDU stream per VLAN per trunk. Either way, the STP gate in step 2 is per (port, instance), so a port can forward VLAN 20 while it blocks VLAN 310.

  • 98 → 102 → 106. A capture length excludes the 4-byte FCS. On the wire these frames are 102, 106 and 110 bytes. Each tag adds exactly 4 bytes, and nothing above Layer 2 changes. The IP header, TTL and ID are identical in every line.
  • Size limits move with the tag. 802.3 allows a 1518-byte untagged frame and a 1522-byte tagged one (the "baby giant" allowance from 802.3ac). Going the other way, a minimum 64-byte tagged frame becomes 60 bytes when its tag is stripped on egress. That's below the Ethernet minimum, so the switch must pad it back to 64.
  • p 5 is the PCP field. It's the only QoS marking Ethernet carries. It exists only while the frame is tagged, so a switch that strips the tag toward an access port also strips the priority. That's why phones are put on a tagged voice VLAN even though the PC behind them stays untagged.
  • 0x88a8 then 0x8100 is QinQ: provider S-tag 1001 outside, customer C-tag 310 inside.
  • The last frame has two 0x8100 tags: VLAN 1 outside, VLAN 20 inside. It's the double-tagging attack, covered in failure modes. A frame like this should never arrive from a host.

To see tags yourself: run on your Mac — your output will differ.

A Linux subtlety: most NICs strip the tag in hardware on receive (ethtool -k eth0 | grep vlan shows rx-vlan-offload). The kernel keeps the VID as packet metadata, and libpcap reinserts it, so tcpdump on the parent interface still shows the tag. If you ever see tags missing from a capture, offload is the first suspect.

RSTP proposal and agreement

A new 1G link comes up between dist-1 (the root, priority 4096) and acc-3 (priority 32768). Four BPDUs later it's forwarding:

    message-age 0.00s, max-age 20.00s, hello-time 2.00s, forwarding-delay 15.00s
    root-id 1000.00:11:22:33:44:01, root-pathcost 20000, port-role Root
  • Not even EtherType. BPDUs are 802.3 frames with a length field (39) and an LLC header (DSAP/SSAP 0x42), sent to 01:80:c2:00:00:00. Switches never forward that address; every bridge consumes it. The 39 bytes are 3 of LLC plus a 36-byte RSTP BPDU, padded to the 60-byte minimum on the wire.
  • Bridge IDs are hex. 1000 is 4096 and 8000 is 32768. The trailing .8018 is the port ID: port priority 128 (0x80) and port number 24 (0x18).
  • root-pathcost 20000. acc-3 adds its 1G long-format cost to the root's 0. That's the cost it advertises downstream.
  • Proposal → Agreement in 412 µs. dist-1 proposes that its port be designated. Before agreeing, acc-3 runs sync: it puts every non-edge designated port of its own into discarding, so the new path can't create a loop downstream. Then it answers with Agreement on its new root port. dist-1 can forward at once. No 15-second timer was involved. The handshake ripples outward one switch at a time, so convergence time scales with hops times BPDU processing, not with timers.
  • Topology change. As soon as acc-3's root port began forwarding, it sent TC. In RSTP only a non-edge port moving to forwarding triggers a TC. Each switch that receives it flushes the MAC entries learned on its other non-edge ports and passes the TC on. That flush is why a topology change causes a burst of unicast flooding, even when the change itself was harmless.

Deep dive: by the numbers

Where 50 seconds comes from, and where it doesn't

The module adds 20 + 15 + 15 to get classic STP's ~50 seconds. That sum is the worst case, the indirect failure. A port that simply comes up skips max-age and takes 30 seconds. The breakdown:

"""Classic STP vs RSTP convergence, from the 802.1D timers."""
hello, max_age, fwd_delay = 2, 20, 15          # 802.1D defaults (seconds)

# 802.1D's sanity rule for the three timers
assert 2 * (fwd_delay - 1) >= max_age >= 2 * (hello + 1)

# Where 20 and 15 come from (simplified formulas Cisco publishes, assuming diameter 7)
dia = 7
print("derived max_age   =", 4 * hello + 2 * dia - 2)
print("derived fwd_delay =", (4 * hello + 3 * dia) / 2, "-> rounded to", fwd_delay)

cases = {
    "802.1D, port comes up (non-edge)":           2 * fwd_delay,             # listening + learning
    "802.1D, root port link goes down (direct)":  2 * fwd_delay,             # blocked port must listen+learn
    "802.1D, upstream failure (indirect)":        max_age + 2 * fwd_delay,   # wait for stored BPDU to age out
}
for name, secs in cases.items():
    print(f"{name:45s} {secs:>3} s")
print(f"{'RSTP, root port link down, alternate ready':45s}  <1 s (no timer: alternate becomes root port)")
print(f"{'RSTP, upstream failure (indirect)':45s} {3 * hello:>3} s to detect (3 missed hellos), then handshake")

# MAC table flushing after a topology change
print("802.1D TC: aging cut from 300 s to", fwd_delay, "s for", max_age + fwd_delay, "s")
print("RSTP TC: non-edge ports flushed at once; TC flag sent for", 2 * hello, "s (tcWhile)")

The timers are not arbitrary. They come from assumptions about the network's diameter, the maximum number of bridges between any two hosts, which 802.1D assumed was 7. Max-age has to outlast the time for a BPDU to cross the whole network. Forward delay has to outlast the time for the news of a change to propagate everywhere, so that no port forwards while another still holds a stale view. That's also why "just lower the timers" is dangerous on classic STP: shrink them below what your real diameter needs and you get transient loops.

The 6 seconds for RSTP's indirect case is the slow path. It applies only when a neighbor goes silent without the link going down: a hung control plane, or a media converter that keeps light up. When the link goes down, detection is immediate and the alternate port takes over in milliseconds.

How fast a loop eats a link

"Broadcasts multiply exponentially" is true for some loops and false for others. Whether frames multiply depends on how many looped ports each switch has:

"""How fast a Layer-2 loop fills a 10G link."""

def copies_after(adj: dict[str, list[str]], start: str, hops: int) -> list[int]:
    """Flood one broadcast: every switch sends it out every loop port except the one it came in on."""
    inflight = [(start, n) for n in adj[start]]              # (from, to) pairs on the wire
    counts = [len(inflight)]
    for _ in range(hops):
        inflight = [(to, n) for frm, to in inflight for n in adj[to] if n != frm]
        counts.append(len(inflight))
    return counts

ring = {"A": ["B", "C"], "B": ["A", "C"], "C": ["A", "B"]}
mesh = {s: [t for t in "ABCD" if t != s] for s in "ABCD"}
print("triangle, copies in flight per hop:", copies_after(ring, "A", 8))
print("4-switch mesh, copies per hop:     ", copies_after(mesh, "A", 8))

# Line-rate math for a minimum-size broadcast (an ARP request: 64 bytes incl. FCS)
wire_bytes = 64 + 8 + 12                    # + preamble/SFD + inter-frame gap
pps_10g = 10e9 / (wire_bytes * 8)
hop_s = wire_bytes * 8 / 10e9 + 1e-6        # serialization + ~1 us store-and-forward switch latency
lap_s = 3 * hop_s                           # once around the triangle
per_copy = 1 / lap_s                        # times per second one looping copy crosses each link
print(f"10G line rate, 64 B frames: {pps_10g / 1e6:.2f} Mpps")
print(f"one looping copy crosses each link {per_copy / 1e3:.0f}k times/s")
print(f"looping broadcasts that fill each direction of each link: {pps_10g / per_copy:.0f}")

Real output:

triangle, copies in flight per hop: [2, 2, 2, 2, 2, 2, 2, 2, 2]
4-switch mesh, copies per hop:      [3, 6, 12, 24, 48, 96, 192, 384, 768]
10G line rate, 64 B frames: 14.88 Mpps
one looping copy crosses each link 312k times/s
looping broadcasts that fill each direction of each link: 48

In a simple ring, each broadcast becomes two immortal copies going opposite ways. That's linear, not exponential. But each copy passes every switch about 312,000 times a second, and every pass floods it to every host port in the VLAN. So 48 ordinary ARP requests, a few seconds of normal chatter on a busy VLAN, are enough to fill a 10G link. Every host's NIC then receives hundreds of thousands of broadcasts per second, and the switches' CPUs drown in the copies they must inspect. Add a switch with three looped ports and growth turns exponential, doubling every hop: saturation within microseconds. Either way, the outcome is the same within seconds. The ring just takes a moment longer.

Deep dive: production failure modes

Native VLAN mismatch

Symptom. Intermittent, one-directional leaks. A device on VLAN 1 on one side gets a DHCP address from VLAN 10's scope on the other. Some flows work, some don't.

Mechanism. Switch A sends VLAN 1 untagged because its PVID is 1. Switch B classifies every untagged frame into its PVID, 10. Tagged VLANs are unaffected, which is why the trunk "mostly works."

Prove it. Compare PVIDs on both ends: show interfaces trunk on Cisco (vendor), or bridge vlan show on a Linux bridge, where PVID Egress Untagged marks the native VLAN. Neighbor-discovery protocols often catch it first. CDP logs a native VLAN mismatch, and Rapid-PVST+ puts the port into a "PVID inconsistent" blocking state because its BPDUs carry the sender's VLAN (both vendor behaviours). LLDP can carry the port VLAN ID too (802.1 TLV), so lldpctl on Linux shows the neighbor's PVID.

Fix. Same native VLAN on both ends, set to an unused ID that carries no hosts. Better, tag the native VLAN too (Cisco vlan dot1q tag native, vendor), so nothing crosses the trunk untagged at all.

VLAN hopping: double tagging and switch spoofing

Double tagging. An attacker on an access port whose VLAN equals the trunk's native VLAN (VLAN 1 in the capture) sends the double-tagged frame shown above. The first switch classifies it into VLAN 1 (either by its outer tag, or by the port's PVID if it accepts tagged frames there). It sends it out the trunk untagged, because VLAN 1 is native, so the outer tag disappears. The next switch sees the inner tag, VLAN 20, and delivers the frame into the victim VLAN. It's one-way, since replies won't come back, but one-way is enough for a UDP exploit or a spoofed packet. The fixes are the native-VLAN rules above. On top of them, set access ports to admit only untagged frames.

Switch spoofing. Cisco's DTP (vendor) lets a port negotiate trunking. A port left in "dynamic desirable" or "dynamic auto" will become a trunk if a laptop speaks DTP to it, and then the laptop is on every VLAN. Fix: hard-code access ports as access and disable negotiation (switchport nonegotiate).

The loop that STP didn't catch

Symptom. Everything in one VLAN or more is down at once. Switch CPUs are at 100%. Interface counters show broadcast and multicast rates in the hundreds of thousands per second. Logs fill with MAC-move (MAC-flap) messages: the same MAC learned on alternating ports. Exact message text is vendor-specific.

Mechanism. STP only stops loops it can see, and it sees them only through BPDUs. The usual ways BPDUs disappear:

  • A unidirectional link. One fiber strand fails, or a transceiver half-dies. The alternate port at the far end stops receiving BPDUs, decides the path is gone, and moves to forwarding while traffic still flows the other way. Loop.
  • A device that drops BPDUs but forwards data: some unmanaged switches, some hypervisor vSwitches, a misconfigured bridge on a server.
  • BPDU filter configured on a port that later got patched to another switch.

Prove it. From a host in the VLAN, watch the broadcast rate and look for the same frame repeating:

# Run on your Mac: packets per second on en0 (a storm shows 10^5+)
netstat -I en0 -w 1
# A sample of broadcasts: a loop shows the same ARP request over and over
sudo tcpdump -nn -e -t -i en0 -c 200 ether broadcast | sort | uniq -c | sort -rn | head
# Linux equivalents
ip -s link show eth0          # RX broadcast/multicast counters
sar -n DEV 1                  # rxpck/s per interface (sysstat package)

(-t drops timestamps so identical frames print identical lines.) On the switches, follow the MAC-move messages. The two ports a MAC flaps between bracket the loop.

Fix. Do it in layers. Edge ports with BPDU guard on every host port. Loop guard on root and alternate ports, which puts a port that stops hearing BPDUs into a "loop-inconsistent" discarding state instead of forwarding. UDLD (vendor) or a bidirectional detection protocol on fiber. Storm control on access ports, which caps broadcast and multicast at a percentage of line rate, so a loop degrades a VLAN instead of killing a building. And root guard on ports where a better root should never appear.

Topology-change storms

Symptom. Periodic bursts of unicast flooding. Hosts see traffic not meant for them, and links run hot for a few seconds at a time, without any loop.

Mechanism. Every topology change flushes MAC tables, and until addresses are relearned, unicast floods. A host port that isn't configured as an edge port generates a TC every time a laptop docks or a server reboots. On a 48-port access layer, that can be a TC every few seconds.

Prove it. Spanning-tree detail on the switches shows the TC count and the port that last sent one (vendor command; on Cisco, show spanning-tree detail includes "occurred X ago from Gi1/0/12"). Follow that port.

Fix. Mark every host port as edge. Edge ports don't generate TCs.

Unicast flooding from mismatched timers

Symptom. A steady flood of one server's traffic out every port in the VLAN, with no loop and no topology change. Often found by someone running a capture who sees backup traffic that isn't theirs.

Mechanism. Asymmetric routing. Router R1 sends traffic to the server, but the server replies via R2. R1's ARP entry for the server lives for hours (Cisco IOS's default ARP timeout is 4 hours; vendor value), so R1 keeps sending frames to the server's MAC. But the server never sends a frame that passes the switch ports on R1's side, so the switch's MAC entry for it ages out after 300 seconds. From then on, every frame to that MAC is an unknown unicast and floods.

Fix. Make the ARP timeout shorter than the MAC aging time (or lengthen MAC aging), or fix the asymmetry.

Deep dive: 2026 context — why data centers stopped bridging

What spanning tree costs at data-center scale

Campus access layers in 2026 still run VLANs with RSTP or MSTP, and that's fine. Data centers moved away for reasons that are all visible in this module:

  • Blocked bandwidth. A tree uses one path. Every redundant uplink is idle until something fails. MSTP spreads VLANs across trees but still blocks per instance.
  • Failure domain. A VLAN is a broadcast domain. One loop or one chatty host affects every port in it, and a VLAN stretched across a whole data center makes every rack share the risk.
  • Flooding and table scale. Every unknown unicast, broadcast and multicast floods the whole VLAN. And every switch in a Layer-2 domain must learn every MAC in it. Thousands of VMs or containers per rack can exceed a top-of-rack switch's MAC table.
  • Convergence that depends on everybody. RSTP is fast on point-to-point links, but its failure modes (unidirectional links, devices that drop BPDUs) end in loops. A routing protocol's failure modes end in dropped packets, which TTL bounds.

The replacement is a routed leaf-spine (Clos) fabric. Every leaf connects to every spine. Every link is a routed point-to-point link running BGP or OSPF (eBGP per RFC 7938 is the common choice), and traffic between two leaves spreads across all spines with ECMP. Failure detection uses BFD, typically 3 missed packets at 50–300 ms intervals, so routes withdraw in well under a second. No link is ever blocked.

Sizing a fabric

    overhead = 14 + ip_hdr + 8 + 8
    print(f"VXLAN over {name}: +{overhead} B; a 1500-byte inner IP packet needs underlay IP MTU >= "
          f"{1500 + 14 + ip_hdr + 8 + 8}")

# The VTEP hashes the inner flow into the outer UDP source port so spines can ECMP on it.
def src_port(flow: str) -> int:
    h = int.from_bytes(hashlib.sha256(flow.encode()).digest()[:4])
    return 49152 + h % 16384                  # RFC 7348 suggests the dynamic range 49152-65535

def spine_for(sport: int) -> int:             # stand-in for the spine-facing ECMP hash
    return int.from_bytes(hashlib.sha256(f"10.0.0.11>10.0.0.12:{sport}>4789".encode()).digest()[:2]) % spines

flows = [f"10.20.7.{h}:{p}>10.20.9.20:443/tcp" for h in range(1, 101) for p in range(40000, 40100)]
spread = Counter(spine_for(src_port(f)) for f in flows)
print(f"{len(flows)} inner flows over {spines} spines:", sorted(spread.values()))
print("same flows with a constant source port:", Counter(spine_for(4789) for _ in flows))

max leaves = spine ports = 64; server ports = 3072
any leaf-to-leaf path: 2 hops; equal-cost paths between two leaves: 8

Notice the properties. Every pair of servers is the same distance apart. Capacity grows by adding spines (more bandwidth) or leaves (more ports). A spine failure costs one-eighth of capacity, not a reconvergence. The last line shows why VXLAN puts a hash of the inner flow in the outer UDP source port. Without that entropy, every tunneled packet between two leaves would look like one flow and pin to one spine.

VXLAN on the wire

The fabric is routed, but applications still sometimes need Layer 2: VM live migration, legacy clusters that use broadcast heartbeats, appliances that insist on a shared subnet. VXLAN (RFC 7348) carries the Ethernet frame inside UDP across the routed fabric. Here is the same ping from the start of this section, bridged from leaf 11 to leaf 12:

09:02:11.000000 00:1c:73:11:00:01 > 00:1c:73:5f:00:01, ethertype IPv4 (0x0800), length 148: (tos 0x0, ttl 64, id 0, offset 0, flags [DF], proto UDP (17), length 134)
    10.0.0.11.53211 > 10.0.0.12.4789: VXLAN, flags [I] (0x08), vni 10310
3a:1f:9c:52:07:e4 > f0:2f:74:1b:c4:20, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 7471, offset 0, flags [none], proto ICMP (1), length 84)
    10.20.7.144 > 10.20.7.200: ICMP echo request, id 20931, seq 1, length 64
  • 98 + 50 = 148. The inner frame (98 bytes, without its FCS) gains 8 bytes of VXLAN header, 8 of UDP, 20 of IP and 14 of outer Ethernet. The outer IP length, 134, is 98 + 8 + 8 + 20.
  • vni 10310. The VXLAN Network Identifier is 24 bits, so about 16 million segments instead of 4094 VLANs. The inner frame carries no 802.1Q tag. The leaf mapped the access port's VLAN 310 to VNI 10310 on the way in and will map it back on the way out. VLAN numbers are now only locally significant, per leaf port.
  • flags [DF]. Tunnel endpoints (VTEPs) must not fragment. If the underlay MTU is below 1550, large inner frames are silently dropped: the classic "ping works, SSH hangs at key exchange" overlay symptom. Fabrics run the underlay at a jumbo MTU, commonly 9216, for exactly this reason.
  • Source port 53211 is the flow hash from the sizing script. Destination 4789 is VXLAN's IANA port. Linux's kernel vxlan driver historically defaulted to 8472, and Flannel in Kubernetes still uses 8472, so check both when a firewall "blocks VXLAN."

EVPN: a control plane instead of flooding

Plain VXLAN still learns like a switch: flood unknown destinations to every VTEP, learn source MACs from what comes back. EVPN (BGP EVPN, RFC 7432, applied to VXLAN by RFC 8365) replaces flood-and-learn with BGP advertisements:

  • Route type 2 (MAC/IP advertisement). When a leaf learns a local host, it advertises "MAC 3a:1f:…, IP 10.20.7.144, VNI 10310, behind VTEP 10.0.0.11." Every other leaf installs that directly, so there's no flooding for known hosts. Because the leaves know IP-to-MAC bindings, they can also answer ARP locally (ARP suppression), and broadcast ARP stops crossing the fabric.
  • Route type 3 (inclusive multicast). Each leaf announces which VNIs it serves, building the list of VTEPs that must receive the remaining broadcast, unknown unicast and multicast (BUM) traffic, usually by ingress replication.
  • Route type 5 (IP prefix, RFC 9136) carries routed prefixes, for traffic between subnets and to the outside.
  • Multihoming with Ethernet segments (route types 1 and 4) lets a server attach to two leaves, all links active, without vendor MLAG.
  • Distributed anycast gateway. Every leaf owns the same gateway IP and MAC for each subnet, so a host's first hop is always its own leaf, and a migrated VM keeps working without re-ARPing.

The net result is Layer-2 service with Layer-3 machinery underneath: no spanning tree between switches, BGP convergence, ECMP everywhere, and floods confined to what really must flood. You can build a tiny VTEP on Linux to see the moving parts: sudo ip link add vxlan10310 type vxlan id 10310 dstport 4789 local 10.0.0.11 nolearning. FRR adds the EVPN control plane.

Clouds and Kubernetes went further

Public-cloud VPCs don't expose Layer 2 at all. There's no broadcast or multicast between instances, ARP is answered by the hypervisor's virtual network, and every packet is encapsulated by the host and routed through a mapping service that knows where each address lives. The cloud runs EVPN's idea at planetary scale: a control plane that knows every endpoint, so nothing needs to flood. Some of those overlays use Geneve (RFC 8926), VXLAN's extensible successor, which is also what OVN and AWS Gateway Load Balancer speak.

Kubernetes networking follows the same split. A CNI either routes pod CIDRs natively (Calico or Cilium announcing routes over BGP, cloud VPC routes) or runs an overlay: VXLAN in Flannel, Calico and Cilium; Geneve in OVN-Kubernetes and as a Cilium option. Spanning tree has no role anywhere in that picture. The leftover Layer 2 in a 2026 data center is the single link between a server and its leaf.

Deep dive: senior interview questions

Q1. An access port receives a frame that already carries an 802.1Q tag. What happens?

It depends on the port's acceptable-frame-types setting, and that's the point of the question. A strict port admits only untagged frames and drops it. A permissive one may accept it, classify it by its tag or by its PVID, and forward it. That permissiveness is what makes double-tag VLAN hopping work. On a correctly configured network, access ports drop tagged frames, except for an explicitly configured voice VLAN.

Q2. Why does the same MAC address on two VLANs not confuse the switch?

Because the forwarding table is keyed on (VLAN, MAC), not on MAC alone, under independent VLAN learning. The two addresses are separate entries that never meet. On a switch with shared VLAN learning the MAC would collide, which is one reason almost all modern switches use independent learning.

Q3. Classic STP takes 30 seconds when a port comes up, but the textbook says 50. Which is right?

Both, for different events. A port coming up goes listening (15 s) then learning (15 s): 30 s. An indirect failure, where a switch loses its root path but its own links stay up, first waits for the stored BPDU to age out (max age, 20 s), then listens and learns: 50 s. RSTP removes the timers from both. An alternate port takes over immediately on link-down, and indirect failures are detected after 3 missed hellos (6 s) and then resolved by handshake.

Q4. What does RSTP's sync step do, and why is it necessary?

Before a switch agrees to a proposal on its new root port, it puts all its non-edge designated ports into discarding. Otherwise the new forwarding path could join up with the switch's old downstream forwarding ports and create a momentary loop. Downstream switches then get their own proposals, and the agreement ripples outward one hop at a time. That's how RSTP gets sub-second convergence without timers and still never forwards into a loop.

Q5. A switch shows bridge priority 32778. What is it configured to?

Priority 32768 on VLAN 10. The 16-bit priority field is really a 4-bit priority (in steps of 4096) followed by a 12-bit extended system ID, which per-VLAN spanning tree sets to the VLAN number.

Q6. How can an STP-protected network still loop?

STP can't see a loop if BPDUs don't flow around it. Unidirectional links let a blocked port stop hearing BPDUs and start forwarding while traffic still flows the other way. Devices that forward data but drop BPDUs hide a loop completely. BPDU filtering on the wrong port does the same. Defences: loop guard, UDLD or equivalent on fiber, BPDU guard on edge ports, storm control as the last line.

Q7. Why do modern data centers use VXLAN's UDP source port for anything?

Spines balance traffic with ECMP by hashing the outer headers. Between two VTEPs the outer IPs and destination port are constant, so the only entropy is the source port. VTEPs set it from a hash of the inner flow, so different inner flows take different spines and the same flow stays on one path. If every packet had the same source port, the fabric would collapse onto one spine.

Q8. You're asked to stretch a VLAN between two data centers for VM migration. What do you push back on, and what would you build?

A stretched VLAN is a shared broadcast and failure domain across a WAN. A loop or a broadcast storm in one site takes out both, and a split between sites can leave both halves thinking they own the gateway. If Layer 2 is truly required, carry it over a routed interconnect with EVPN-VXLAN: no spanning tree across the WAN, ARP suppression, BUM traffic controlled, an anycast gateway in each site. Then question the requirement itself, because most applications that "need Layer 2" really need a stable IP, which routing and DNS can provide.
