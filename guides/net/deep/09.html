Deep dive: what the relay race leaves out

The relay-race picture is right about one thing: every router decides alone, one hop at a time. It hides almost everything else. A "runner with a card" is really two machines in one box. One is a slow, argumentative control plane that collects candidate routes from several protocols and picks winners. The other is a fast, dumb forwarding plane that does one lookup per packet in a table built for speed. The card is not one list either. Before any table is consulted there is a policy step that chooses which table. And the "best matching line" is often a set of equal lines, with a hash function choosing between them.

ICMP gets the same simplification. In the module it is a polite "return to sender" stamp. In practice it is a side effect of the slow path: generated by a CPU, rate-limited, filtered, and sometimes load-bearing. Traceroute only works because of it, and Path MTU Discovery quietly breaks without it.

This deep dive goes under the analogy. Most of the output below is real: it comes from a small Linux lab built from network namespaces on the guide's sandbox (kernel 6.18). Each block says whether it is real or illustrative.

Deep dive: the real mental model

Two planes: RIB and FIB

Every router, from a Linux box to a chassis switch, keeps two different structures that are both loosely called "the routing table".

The RIB (Routing Information Base) is the control plane's notebook. It holds every candidate route each source has offered: connected interfaces, static config, OSPF, BGP, DHCP, the kernel. Several entries for the same prefix are normal. The RIB manager picks one winner per prefix. First it compares administrative distance (which source is trusted more). Then it compares the protocol's own metric. Only the winner, plus any equal-cost siblings, goes into the forwarding table.

The FIB (Forwarding Information Base) is that winner list compiled for lookups. It has exactly one answer per prefix: a next hop, or a group of next hops. On a hardware router it lives in the switch ASIC, either in TCAM or in an algorithmic longest-prefix-match structure in SRAM. On Linux it is the kernel's fib_trie (an LC-trie), which you can dump from /proc/net/fib_trie.

On a Linux router running FRR, the split is visible. The zebra daemon holds the RIB and pushes winners into the kernel over netlink. FRR marks them with two flags: > means "selected in the RIB" and * means "installed in the FIB". Illustrative FRR output:

router# show ip route 203.0.113.0/24 longer-prefixes
Codes: K - kernel route, C - connected, S - static, O - OSPF, B - BGP,
       > - selected route, * - FIB route, q - queued, r - rejected
B>* 203.0.113.0/24 [20/0] via 10.0.12.2, eth1, weight 1, 02:14:07     <- eBGP, distance 20: wins, in FIB
O   203.0.113.0/24 [110/30] via 10.0.13.2, eth2, weight 1, 02:14:11   <- OSPF knows it too: loser, kept as backup
S   203.0.113.0/24 [1/0] via 10.0.99.1 inactive, weight 1, 00:03:40   <- static would win (distance 1), but its next hop is unreachable

Read the static row carefully. It has the best distance on the box, and it still forwards nothing, because its next hop cannot be resolved. "The route is in the config" and "the route is forwarding" are two different claims. Many outages live in the gap between them. A RIB winner can also fail to reach the FIB because the hardware table is full (FRR marks it r, rejected) or because programming is still in progress (q, queued). Installing a full internet table into an ASIC can take tens of seconds to minutes on some platforms.

The FIB has a second layer that matters for convergence. Prefixes do not store a MAC address and port directly. They point at a next-hop object, which holds the rewrite information. A million BGP prefixes may share a handful of next-hop objects. When a link dies, the router rewrites one object instead of a million prefixes. Vendors call this prefix-independent convergence (PIC). Linux has the same idea in ip nexthop objects, available since kernel 5.3.

The forwarding path, step by step

Here is what Linux does for each forwarded IPv4 packet. Hardware routers follow the same order, with most steps done in the ASIC pipeline.

  1. TTL check. If TTL is 1 or less, the packet will not be forwarded. It goes to the slow path, which may send ICMP Time Exceeded (type 11, code 0).
  2. Policy rules. The kernel walks the routing policy database (ip rule) in priority order. Each rule has a selector (source, destination, incoming interface, firewall mark, user ID, protocol, ports) and an action, usually "look up table N". The first rule whose table gives an answer wins.
  3. Longest-prefix match in the chosen table.
  4. Multipath selection. If the winning route has several next hops, a hash of header fields picks one.
  5. Neighbour resolution. The next hop's IP becomes a MAC address through the ARP or ND cache (Module 06).
  6. MTU check. If the packet is larger than the egress MTU and DF is set, it is dropped and ICMP Fragmentation Needed (type 3, code 4) goes back. For IPv6 the message is Packet Too Big, ICMPv6 type 2. IPv6 routers never fragment.
  7. Rewrite and queue. Decrement TTL, patch the header checksum, write the new Ethernet header, enqueue on the egress qdisc.

Steps 1 and 6 are the interesting ones for this module. Both branch off the fast path into code that builds a brand-new ICMP packet. On a hardware router that means punting the packet through a policer to a general-purpose CPU. That one fact explains most of traceroute's quirks.

Policy routing: choosing the table before the route

Linux ships with three rules. Real output from the lab router before any changes:

0:      from all lookup local      <- your own addresses and broadcasts
32766:  from all lookup main       <- the table `ip route` shows
32767:  from all lookup default    <- empty on most systems

Add a rule and the source address starts to matter. In this real lab run, clients in 10.0.3.0/24 should leave through a second uplink, and everyone else uses the main table's default:

$ ip route add default via 10.0.1.2                     # main table: uplink 1
$ ip route add default via 10.0.2.2 table 100           # table 100: uplink 2
$ ip rule add from 10.0.3.0/24 lookup 100 priority 1000
$ ip route get 198.51.100.9 from 10.0.3.5 iif eth3
198.51.100.9 from 10.0.3.5 via 10.0.2.2 dev eth2 table 100
    cache iif eth3
$ ip route get 198.51.100.9 from 10.0.1.2 iif eth1
198.51.100.9 from 10.0.1.2 via 10.0.1.2 dev eth1
    cache <redirect> iif eth1

Same destination, two different exits, decided by the source. ip route get is the most useful routing command on Linux because it runs the real lookup, rules included. Add from, iif, mark, ipproto, sport and dport to reproduce exactly what a given packet sees.

You meet policy routing in production more often than you configure it:

  • WireGuard's wg-quick sends everything through the tunnel using a firewall mark, a dedicated table, and a rule with suppress_prefixlength 0. That last rule means "use the main table, but ignore its default route". Run ip rule on a machine with a full-tunnel VPN and you will see it.
  • Multi-homed servers need source-based rules so replies leave through the interface the request arrived on. Without them, the reply follows the main table's default out of the wrong NIC.
  • The AWS VPC CNI for Kubernetes gives pods addresses from secondary network interfaces. It installs per-pod rules so each pod's traffic leaves through its own interface.

macOS has no ip rule. It does have interface-scoped routes (the I flag in netstat -rn), and route -n get -ifscope en0 <addr> queries one scope. For general policy routing on a Mac you would reach for pf and its route-to option.

ECMP: when the best match is a set

When a route has several equal next hops, the router must not spray the packets of one TCP flow across them. Different paths have different delays, and TCP reads reordering as loss. So routers hash header fields and send every packet of a flow the same way.

Which fields go into the hash is a setting, and the Linux default surprises people. Real output from a lab router with two next hops for 203.0.113.0/24:

$ ip route show 203.0.113.0/24
203.0.113.0/24
        nexthop via 10.0.1.2 dev eth1 weight 1
        nexthop via 10.0.2.2 dev eth2 weight 1

net.ipv4.fib_multipath_hash_policy = 0        <- default: hash source and destination IP only
policy 0: 1000 flows (sport 40001-41000) -> via 10.0.1.2: 0, via 10.0.2.2: 1000

net.ipv4.fib_multipath_hash_policy = 1        <- hash the 5-tuple (adds protocol and ports)
$ ip route get 203.0.113.7 from 10.0.3.5 iif eth3 ipproto tcp sport 40001 dport 443
203.0.113.7 from 10.0.3.5 via 10.0.2.2 dev eth2
$ ip route get 203.0.113.7 from 10.0.3.5 iif eth3 ipproto tcp sport 40002 dport 443
203.0.113.7 from 10.0.3.5 via 10.0.1.2 dev eth1
policy 1: 1000 flows (sport 40001-41000) -> via 10.0.1.2: 490, via 10.0.2.2: 510

With the default layer-3 hash, a thousand connections between one client and one server all land on one link. That is correct behaviour, and it is useless for spreading load between two busy hosts. With the 5-tuple hash the split is 490/510. Policy 2 adds the inner headers of encapsulated traffic, and policy 3 lets you pick the fields. IPv6 has its own sysctl, net.ipv6.fib_multipath_hash_policy.

Three consequences follow, and each one is an interview question.

ECMP balances flows, not bytes. One 10 Gbit/s backup stream and a thousand tiny API calls each count as one flow. A link can be saturated while its sibling idles.

Hash polarisation. Suppose every tier of a network uses the same hash function on the same fields. The second tier then only sees the subset of flows the first tier already sent its way, and it splits that subset in a correlated way. Some links get nothing. Vendors fix this with a per-device hash seed.

Membership changes move flows. When a next hop dies or is added, some flows hash somewhere new. That hurts when the router sits in front of stateful servers, such as an anycast address or a Kubernetes LoadBalancer advertised over BGP. A moved flow hits a server with no record of the connection, and that server answers with a RST. How many flows move depends on the mapping scheme. This stdlib script compares three schemes when one of four next hops fails:

"""ecmp_rehash.py - how many flows move when one ECMP next hop dies?

Compares three ways a router maps a flow hash onto N next hops:
  modulo N        - hash % N (naive)
  hash-threshold  - split the hash space into N equal ranges (RFC 2992; Linux default)
  resilient       - fixed bucket table; only the dead hop's buckets get reassigned
"""
import hashlib
import random

random.seed(7)
FLOWS = [(f"10.0.{random.randrange(256)}.{random.randrange(256)}",
          random.randrange(32768, 61000), "203.0.113.7", 443) for _ in range(100_000)]
HASH_SPACE = 2**32


def flow_hash(flow):
    """Stand-in for the router's 5-tuple hash: 32 uniform bits."""
    return int.from_bytes(hashlib.blake2b(repr(flow).encode(), digest_size=4).digest())


def modulo(h, hops):
    return hops[h % len(hops)]


def hash_threshold(h, hops):
    return hops[h * len(hops) // HASH_SPACE]


def make_resilient(hops, buckets=128):
    return [hops[i % len(hops)] for i in range(buckets)]


def resilient_remove(table, dead, alive):
    """Reassign only the dead hop's buckets, round-robin over the survivors."""
    out, k = [], 0
    for hop in table:
        if hop == dead:
            hop, k = alive[k % len(alive)], k + 1
        out.append(hop)
    return out


def resilient(h, table):
    return table[h % len(table)]


before = ["A", "B", "C", "D"]
after = ["A", "B", "D"]                       # next hop C failed
hashes = [flow_hash(f) for f in FLOWS]

table_before = make_resilient(before)
table_after = resilient_remove(table_before, "C", after)
schemes = {
    "modulo N": lambda h, hs: modulo(h, hs),
    "hash-threshold": lambda h, hs: hash_threshold(h, hs),
    "resilient": lambda h, hs: resilient(h, table_before if hs is before else table_after),
}
print(f"{len(FLOWS):,} flows over 4 next hops; next hop C fails "
      "(about 25% of flows sat on C and must move whatever the scheme)")
for name, fn in schemes.items():
    moved = sum(1 for h in hashes if fn(h, before) != fn(h, after))
    print(f"  {name:15s} flows that changed next hop: {moved / len(FLOWS):6.1%}")

Real output (Python 3.13):

100,000 flows over 4 next hops; next hop C fails (about 25% of flows sat on C and must move whatever the scheme)
  modulo N        flows that changed next hop:  75.0%
  hash-threshold  flows that changed next hop:  33.4%
  resilient       flows that changed next hop:  25.1%

Modulo-N is a disaster: three quarters of all connections move, including flows whose next hop was perfectly healthy. Hash-threshold (RFC 2992, which Linux uses for plain multipath routes) disturbs a third. A resilient table moves only the flows that had to move. Linux has had resilient groups since kernel 5.13. Data-centre switches offer the same thing under names like "resilient hashing". Software load balancers go further, with consistent hashing schemes such as Maglev plus connection tracking. That way even the flows that must move can be handled gracefully.

Deep dive: what the wire and the kernel actually do

Traceroute, packet by packet

The lab is four Linux network namespaces wired in a line: h1 (10.1.0.10) → r1 → r2 → h2 (10.2.0.10). The r1–r2 link has an MTU of 1400. Everything else is 1500. Any Linux VM or privileged container can rebuild it; on a Mac, use a Linux VM. The core of the setup:

for n in h1 r1 r2 h2; do ip netns add $n; done
ip link add eth0 netns h1 type veth peer name eth0 netns r1
ip link add eth1 netns r1 type veth peer name eth0 netns r2
ip link add eth1 netns r2 type veth peer name eth0 netns h2
# ...addresses, links up, default routes on h1/h2, static routes on r1/r2...
ip -n r1 link set eth1 mtu 1400; ip -n r2 link set eth0 mtu 1400
ip netns exec r1 sysctl -w net.ipv4.ip_forward=1    # same for r2

To see the mechanism with no tool in the way, here is classic UDP traceroute in about 60 lines of stdlib Python. It needs root, because reading ICMP requires a raw socket. It runs on macOS too.

"""mini_traceroute.py - classic UDP traceroute in about 60 lines of stdlib Python.

Sends UDP probes with TTL 1, 2, 3 ... to ports 33434+n and reads the ICMP
errors that come back on a raw socket. Needs root (raw socket).
    sudo python3 mini_traceroute.py 10.2.0.10
"""
import select
import socket
import struct
import sys
import time

BASE_PORT = 33434


def parse_icmp(packet):
    """Return (type, code, quoted_dst_port) from a raw IPv4+ICMP packet."""
    ihl = (packet[0] & 0x0F) * 4                 # outer IP header length
    icmp_type, icmp_code = packet[ihl], packet[ihl + 1]
    if icmp_type not in (3, 11):                  # only errors quote our probe
        return icmp_type, icmp_code, None
    inner = packet[ihl + 8:]                      # quoted original IP header ...
    inner_ihl = (inner[0] & 0x0F) * 4
    _sport, dport = struct.unpack("!HH", inner[inner_ihl:inner_ihl + 4])  # ... + first 8 bytes
    return icmp_type, icmp_code, dport


def trace(dest, max_hops=8, probes=3, timeout=1.0):
    recv = socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP)
    send = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    print(f"traceroute to {dest}, {max_hops} hops max")
    for ttl in range(1, max_hops + 1):
        send.setsockopt(socket.IPPROTO_IP, socket.IP_TTL, ttl)
        line, reached, last = f"{ttl:2d} ", False, None
        for probe in range(probes):
            port = BASE_PORT + (ttl - 1) * probes + probe   # unique port = probe id
            t0 = time.perf_counter()
            send.sendto(b"\x00" * 32, (dest, port))
            deadline = t0 + timeout
            while True:
                left = deadline - time.perf_counter()
                if left <= 0 or not select.select([recv], [], [], left)[0]:
                    line += " *"
                    break
                packet, (src, _) = recv.recvfrom(1500)
                itype, icode, qport = parse_icmp(packet)
                if qport != port:                  # an answer to some other probe
                    continue
                rtt = (time.perf_counter() - t0) * 1000
                if src != last:                    # name the hop once, like traceroute
                    line += f" {src} (ICMP {itype}/{icode})"
                    last = src
                line += f"  {rtt:.3f} ms"
                reached = itype == 3               # dest unreachable: we arrived
                break
        print(line)
        if reached:
            return


if __name__ == "__main__":
    trace(sys.argv[1])

Details worth carrying away:

  • Matching is done through the quote. The ICMP error carries the original IP header plus at least the first 8 bytes of its payload (RFC 792). For UDP, those 8 bytes are the whole UDP header, so the destination port tells traceroute which probe this was. That is why classic traceroute uses a new port for every probe. Linux quoted the entire 60-byte probe (ICMP length 68 = 8 + 60). RFC 1812 encourages routers to quote as much as fits in 576 bytes; many hardware routers quote only the minimum 28.
  • The ICMP's own TTL describes the return path. 64, 63, 62: each reply crossed one more router on the way back. When a hop's reply TTL jumps unexpectedly, the return path differs from the forward path.
  • tos 0xc0. Linux sends ICMP errors with the "internetwork control" precedence bits set.
  • flags [DF] on UDP probes. Linux sets DF on UDP by default when the datagram fits the known path MTU. More on that under PMTUD below.

Probe types and why they matter

Probe Who uses it Arrival signal Notes
UDP to 33434+ traceroute on macOS and Linux (default) ICMP 3/3 port unreachable The port changes per probe, so ECMP may split one run's probes across paths. Destination firewalls often drop high UDP ports.
ICMP Echo Windows tracert, traceroute -I, mtr default ICMP Echo Reply Some networks rate-limit or block echo. Routers may hash ICMP on L3 only.
TCP SYN to a real port traceroute -T -p 443 (Linux), mtr -T -P 443, tcptraceroute SYN-ACK or RST from the destination Looks like application traffic, so it follows the same ECMP path and firewall rules as your users. Usually the most honest probe.

Paris traceroute fixes the ECMP problem another way. It keeps the 5-tuple constant for a whole run and encodes the probe ID in a field routers do not hash on. For UDP that field is the checksum, steered by adjusting the payload. All probes then follow one path, and you stop seeing "links" between routers that are not actually adjacent.

Why hops show *, and why one hop shows 300 ms

A * means "no matching ICMP came back before the timeout". There are at least six distinct reasons:

  1. The router does not send Time Exceeded at all. That is policy, as in the lab. Forwarding is fine.
  2. ICMP generation is rate-limited. Hardware routers police punted traffic (control-plane policing). Linux limits per destination with net.ipv4.icmp_ratelimit (a 1000 ms token bucket for the types in icmp_ratemask) and globally with icmp_msgs_per_sec (1000, burst 50). Linux traceroute fires up to 16 probes at once by default (-N 16), which makes a hop look patchy: 12.1 ms * 11.9 ms.
  3. The reply is filtered on the way back. Routers often answer from an address on a transit link. That address may be RFC 1918 or unannounced, and bogon filters or uRPF checks on the return path drop it.
  4. The return path is broken or asymmetric in a way that loses the ICMP, while forward traffic works.
  5. The destination drops the probe type. If the last lines show * * * until the hop limit, your UDP probes have probably reached a firewall that drops them. Rerun with TCP to the service port before concluding anything.
  6. MPLS hides hops. If the provider does not copy TTL into the label stack, the whole core counts as one hop. You see a gap in addresses rather than stars. When the routers do answer, mtr -e can show the RFC 4950 label extensions.

Latency has the same trap. The time shown for hop n is the forward path to n, plus the time n's CPU took to build an ICMP message, plus n's return path. A busy router's control plane may take 100 ms to get round to it, while its forwarding ASIC moves your traffic in microseconds. The rule: loss or latency at one hop that does not persist to later hops is not real. Only a step change that carries through to the destination counts.

One more subtlety: which address names a hop. Linux answers from the address of the interface the ICMP leaves through (net.ipv4.icmp_errors_use_inbound_ifaddr = 0 by default). Many hardware routers use the interface the probe arrived on. With asymmetric routing, the name you see can belong to an interface your probe never crossed.

PMTUD working, and PMTUD black-holed

The same lab shows Path MTU Discovery working. Real output from h1; Linux uses -M do to set DF, and on macOS it is ping -D -s 1472:

The ICMP message carries the next-hop MTU in its second word (RFC 1191). The kernel stores it as a per-destination exception, and every TCP socket to that destination shrinks its segments. Linux removed its general route cache in 3.6; the cache line you see now is one of these exceptions.

And the socket's view from ss -tin six seconds in (real, trimmed):

ESTAB 0 79640 10.1.0.10:52326 10.2.0.10:8080
   bbr rto:3264 backoff:4 rtt:0.21/0.122 mss:1448 pmtu:1500 cwnd:1 bytes_retrans:5792
   bytes_acked:28 unacked:12 retrans:1/4 lost:12 notsent:62264

That is the textbook black-hole signature. The handshake works, and so do small requests. The first full-size segment, and everything after it, vanishes. pmtu:1500 shows the kernel never learned the real path MTU. backoff:4 shows exponential RTO backoff, and bytes_acked:28 shows that only the request got through. The server reported received 27 bytes in 20.0s. Users see this as "the page loads its header and then hangs", "SSH connects and then freezes", or "TLS handshake times out after ClientHello" (the server's certificate flight is the first big packet).

Linux has a fallback: Packetization-Layer PMTUD (RFC 4821), which finds the MTU by probing with real data instead of trusting ICMP. Here is the real result with net.ipv4.tcp_mtu_probing=1 on h1, the same black hole, and a 1 MB transfer:

client: sendall returned after 6.51s
   bbr rto:204 rtt:0.3/0.337 mss:1347 pmtu:1500 ... bytes_retrans:25837 bytes_acked:1000001 retrans:0/28
server: received 1000000 bytes in 6.82s

The connection survived. After the timeouts it dropped to tcp_base_mss (1024), searched upward, and settled at mss:1347, just under the true 1348 (1400 minus 40 bytes of headers and 12 of timestamps). It cost about 6.5 seconds of stalls. That beats hanging forever, but it is a safety net, not a fix. The default is 0 (off); 2 probes all the time.

Deep dive: by the numbers

MTU budget. Every encapsulation eats into the 1500 bytes. Real output from mtu_budget.py, a 20-line stdlib script that subtracts the overheads listed below:

path                             inner MTU  IPv4 MSS  +TS opt  IPv6 MSS
plain Ethernet                        1500      1460     1448      1440
PPPoE (DSL)                           1492      1452     1440      1432
IP-in-IP (Calico IPIP)                1480      1440     1428      1420
GRE over IPv4                         1476      1436     1424      1416
VXLAN over IPv4                       1450      1410     1398      1390
WireGuard over IPv4                   1440      1400     1388      1380
WireGuard over IPv6                   1420      1380     1368      1360
VXLAN inside WireGuard (IPv4)         1390      1350     1338      1330

The overheads it uses: PPPoE 8. Outer IPv4 20 (IPv6 40). GRE 4. VXLAN 8 + UDP 8 + the inner Ethernet header 14. WireGuard UDP 8 + a 16-byte header + a 16-byte authentication tag. This is why wg-quick defaults to MTU 1420: it assumes the worst case, an IPv6 underlay. The "+TS opt" column is what ss reports as mss on Linux, because the timestamp option takes 12 bytes from every segment.

Cloud MTUs differ (defaults; check your provider's current docs). AWS supports 9001-byte jumbo frames inside a VPC but 1500 through an internet gateway. GCP VPC networks default to 1460. Azure defaults to 1500. A path from a 9001-byte instance to the internet depends entirely on PMTUD working.

IPv6 guarantees 1280 bytes on every link and never fragments in routers. A filtered Packet Too Big means a guaranteed black hole, because there is no DF-clear fallback. RFC 4890 lists the ICMPv6 types a firewall must not drop.

Table sizes. In 2026 the global BGP table is roughly a million IPv4 prefixes and well over 200,000 IPv6 prefixes. Check a live source such as the CIDR Report or bgp.potaroo.net for today's count. An IPv6 entry usually costs two to four times the TCAM width of an IPv4 entry, so "how many routes fit" depends on the mix.

Timers that set convergence speed (common defaults, vendor-dependent):

Mechanism Default Failure detected after
OSPF hello / dead (broadcast links) 10 s / 40 s up to 40 s
BGP keepalive / hold (FRR and Cisco traditional profile) 60 s / 180 s up to 3 min
BFD, typical data-centre setting 50–300 ms × 3 missed 150–900 ms
Linux PMTU exception lifetime 600 s n/a: how long a learned MTU is trusted
Linux ICMP error rate limit 1 per 1000 ms per destination (token bucket); 1000/s global, burst 50 n/a

Convergence is the sum of four parts: detect the failure, tell the neighbours, recompute, and reprogram the FIB. Without BFD, detection usually dominates. That is why a fibre cut on a BGP session with default timers can black-hole traffic for minutes.

Traceroute defaults. Linux traceroute uses 30 hops, 3 probes per hop, 60-byte packets, base port 33434, a 5 s wait, and up to 16 probes in flight. macOS defaults to 64 hops. Initial TTLs of 64 (Linux, macOS), 128 (Windows) and 255 (many routers) are conventions, and they let you guess what answered. A reply arriving with TTL 243 probably started at 255 and crossed 12 routers.

Deep dive: production failure modes

1. Large responses hang; small ones work (PMTUD black hole). Mechanism: a link on the path has a smaller MTU (tunnel, overlay, PPPoE), DF is set, and the Fragmentation Needed or Packet Too Big message is dropped by a firewall, security group or ACL that blocks ICMP. Prove it: ping -D -s 1472 host on macOS, or ping -M do -s 1472 host on Linux. Then bisect the size: 1372, 1422, and so on. Linux's tracepath host reports pmtu per hop. In ss -ti, look for retransmits with pmtu:1500 on a path you know is smaller. In a capture, full-size segments are retransmitted again and again and never acknowledged. Fix: allow ICMP type 3 code 4 and ICMPv6 type 2 everywhere. AWS documents adding that rule to security groups for exactly this reason. Clamp MSS wherever you add encapsulation (iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu, or in nftables tcp option maxseg size set rt mtu). Set overlay and tunnel MTUs correctly. Enable tcp_mtu_probing=1 as a net. MSS clamping only helps TCP; UDP, QUIC and IPsec are still exposed.

2. Replies vanish on a multi-homed host. Mechanism: a request arrives on eth1, but the main table's default routes the reply out of eth0. Upstream drops it (stateful firewall, source checks). Or the host's own strict reverse-path filter (rp_filter=1) drops traffic arriving on an interface it would not use to reply. Prove it: ip route get <client> from <eth1 address> shows the reply's exit. tcpdump -ni any host <client> shows the request in on one NIC and the reply out of the other. nstat -az TcpExtIPReversePathFilter counts the rp_filter drops. Fix: a per-source table and rule (ip rule add from <eth1 addr> lookup 101), or loose rp_filter=2.

3. "Some connections fail" (one bad ECMP member). Mechanism: one of eight parallel links or next hops is corrupting or dropping traffic. Every flow that hashes onto it fails, and every other flow is fine. So it looks random, and ping, which is one fixed flow, cannot see it. Prove it: hold everything constant except the source port: for p in $(seq 40000 40015); do curl --local-port $p -so /dev/null -m 3 -w "$p %{http_code} %{time_connect}\n" https://host/; done. A stable subset of ports fails. mtr -T -P 443 with different source ports draws different paths. On the routers, check each member's interface error counters. Fix: drain the bad member, then repair it.

4. A scaling event resets connections (ECMP rehash). Mechanism: a router does ECMP across several stateful servers (anycast VIPs, Kubernetes LoadBalancer IPs advertised over BGP). Adding or removing one server re-maps flows. Moved flows reach a server with no state and get a RST. With hash-threshold, about a third of all flows can move when one of four next hops changes (see the simulation above). Prove it: a spike in RSTs (nstat TcpOutRsts on the servers, "connection reset" errors on clients) that lines up with BGP session changes. Fix: resilient hashing on the router; a consistent-hashing load-balancer tier that tracks connections; and graceful drain (withdraw the route, wait for connections to finish, then stop the server).

5. A more-specific route steals traffic. Mechanism: longest-prefix match is doing its job on a route nobody remembered. Common culprits are Docker's default bridge 172.17.0.0/16 overlapping a corporate range, a VPN client pushing a /24, or a leaked /32 host route. Prove it: route -n get <addr> on macOS or ip route get <addr> on Linux names the route that actually wins. Fix: remove or renumber it, for example with Docker's default-address-pools.

6. "Traceroute shows loss at hop 7" (a false alarm). Mechanism: hop 7 rate-limits ICMP generation. Later hops show 0% loss. Prove it: run mtr -rwc 200 host and look at the last hop. Loss that does not reach the destination is not loss, and nobody should open a ticket against hop 7.

Deep dive: 2026 context

Cloud VPCs. A VPC route table does longest-prefix match too; the provider's virtual network implements it instead of a box you can log in to. Two habits change. First, you often cannot traceroute the fabric, because hops inside the virtual network commonly do not appear at all. Second, routes are often attached to subnets rather than devices. Since 2021, AWS has let you add routes more specific than the VPC's own local route, which is how you put a firewall appliance in the path between two subnets. Get the return route wrong in such a design and you have failure mode 2 at cloud scale.

Kubernetes. Every node is a router for its pods. Calico can advertise pod CIDRs over BGP. Cilium and others replace parts of the kernel forwarding path with eBPF. Overlays (VXLAN, Geneve, IP-in-IP, WireGuard encryption) are the most common source of MTU mismatch in clusters. The pod MTU must be the node MTU minus the encapsulation, as in the table above. MetalLB in BGP mode and cloud load balancers bring ECMP into the cluster, so membership changes become failure mode 4.

CDNs and anycast. The same address lives in hundreds of places, and ECMP inside each site spreads flows across servers. A Packet Too Big message is addressed to the anycast address but carries different header fields from the TCP flow, so it can hash to the wrong server. RFC 7690 documents this, and large operators work around it by relaying PTB messages to every server behind the router. QUIC has its own answer: it never relies on ICMP. Clients must send Initial datagrams of at least 1200 bytes (RFC 9000), and endpoints may probe upward with DPLPMTUD (RFC 8899).

Zero trust and tunnels. ZTNA agents and mesh VPNs, WireGuard-based ones especially, rely on policy routing: firewall marks, dedicated tables and suppress_prefixlength. A traceroute through such a tunnel shows the tunnel endpoints and nothing in between. Each tunnel layer is also another MTU subtraction.

Route security. RPKI route-origin validation is widely deployed among large networks in 2026. It stops a network from originating a prefix it does not own. It does not stop every leak, because a valid origin can still be propagated along the wrong path. Longest-prefix match is still the reason one bad more-specific route can pull traffic across the internet.

Deep dive: senior interview questions

Q1. What is the difference between the RIB and the FIB, and how can a route appear in show ip route without carrying traffic? The RIB holds every candidate route from every source. The FIB holds only the winners, compiled for per-packet lookup in the kernel or ASIC. A route can sit in the RIB unselected, because it lost on administrative distance or metric, or because its next hop cannot be resolved (FRR prints inactive). It can also be selected but not installed, because the hardware table is full or programming is still queued. So the "is this route forwarding?" check is the FIB (ip route get, show ip cef, or the * flag in FRR), not the config.

Q2. Traceroute shows 250 ms at hop 6 and 30 ms at hops 7 to 12. Is hop 6 a problem? No. Each hop's time includes that router's own effort to generate an ICMP Time Exceeded message, which runs on a slow, policed CPU path. Transit traffic through hop 6 is forwarded in hardware, and the lower times after it prove the path through it is fast. Only latency or loss that persists to the destination matters.

Q3. Why might two runs of classic traceroute show different routers at the same TTL, and how would you get a consistent answer? Classic UDP traceroute changes the destination port for each probe so it can match replies. That changes the 5-tuple, so ECMP routers may send each probe down a different equal-cost path. Use a Paris-style tool, which keeps the flow identifiers fixed and varies a field that is not hashed. Or use TCP probes to the real service port, which follow the same path as real traffic.

Q4. How does traceroute know which reply belongs to which probe, and which reply means "done"? Every ICMP error quotes the original IP header plus at least 8 bytes of payload. For a UDP probe that is the full UDP header, so the destination port identifies the probe. Intermediate routers send Time Exceeded (11/0). The destination sends Port Unreachable (3/3) for UDP probes, an Echo Reply for ICMP probes, or a SYN-ACK or RST for TCP probes. Any of those ends the trace.

Q5. TCP connects and small API calls work, but large responses hang. Walk me through it. Suspect a PMTUD black hole. The handshake and small segments fit every link. The first full-size segment exceeds a smaller MTU somewhere, and the router drops it because DF is set. The Fragmentation Needed message never arrives because something filters ICMP. The sender then retransmits the same full-size segment with exponential backoff, forever. Confirm with a DF ping bisection, tracepath, or ss -ti (retransmits, pmtu still 1500). Fix it by allowing ICMP 3/4 and ICMPv6 2 and clamping MSS at the tunnel, with tcp_mtu_probing as a safety net.

Q6. A server has two NICs on different networks. Clients on the second network time out. What is happening? The replies follow the main routing table's default route, which points out of the first NIC. A stateful firewall or source-address filter drops them, or the host's strict reverse-path filter drops the inbound side. Show it with ip route get <client> from <second-NIC address>. Fix it with source-based policy routing: one rule per source address, pointing at a table whose default uses the matching NIC.

Q7. Why does adding a fifth server behind an ECMP router break existing connections, and what would you change? The router's flow-to-next-hop mapping depends on the number of next hops. Changing N moves some existing flows to servers that have no state for them, and those servers answer with RSTs. With modulo-N hashing most flows move, and with hash-threshold a large fraction still does. Resilient hashing on the router keeps the mapping fixed except for the buckets that must change. Better still, put a consistent-hashing L4 load-balancer tier with connection tracking in front of the servers, and drain servers before removing them.

Q8. Your security team wants to block all ICMP. What do you insist on keeping? For IPv4: type 3 (destination unreachable, especially code 4 for PMTUD) and type 11 (time exceeded, for traceroute and loop diagnosis). Echo can be rate-limited rather than blocked. For IPv6, Packet Too Big (type 2) is mandatory because routers never fragment. Keep types 1, 3 and 4 too, plus the neighbour discovery types 133–137 on the local link, or IPv6 stops working outright. RFC 4890 is the reference. Blocking these adds no security. It creates outages that are very hard to diagnose.
