Deep dive: what the submarine hid

The submarine is a good picture of architecture. Compartments, hatches, hull plating. What it can't show you is the machinery inside each hatch, and that's where attacks actually land.

A SYN flood is not "a storm of packets." It's an attack on one specific kernel data structure, and SYN cookies beat it by doing arithmetic on a 32-bit sequence number. Amplification is a ratio of bytes, and you can compute it. BCP 38 is a lookup in a forwarding table. Zero trust, once you strip the slides away, is a certificate check plus a policy lookup on every connection. Microsegmentation is a set of maps in a kernel or hypervisor that something has to keep in sync with a cluster that changes every second.

This deep dive goes under the module's analogies to that machinery. It covers the state each attack targets and the exact packets involved. It also covers the numbers that decide whether a defence holds, and how each control fails in production.

Deep dive: the real mental model

Every attack in this module is an attempt to make a defender spend a scarce resource faster than it refills. The resource is always concrete: entries in a queue, bytes on a link, CPU cycles per packet, or trust attached to an attribute the attacker can forge. Defences work by moving that resource somewhere bigger, or by refusing to spend it until the sender has proved something.

Hold that frame and the module's topics line up.

  • SYN flood targets the listener's queue of half-open connections. SYN cookies stop spending queue entries at all.
  • Amplification targets your link's bandwidth, using someone else's server to multiply the attacker's bytes. The defence is to absorb it somewhere bigger (anycast, scrubbing) or to make spoofing impossible at the source (BCP 38).
  • Spoofing targets trust in the source address. uRPF refuses packets whose source doesn't match the routing table.
  • Zero trust targets the same weakness from the other side. It stops granting trust based on the address at all and asks for a cryptographic identity instead.
  • Microsegmentation limits the reach of any identity that does get compromised.

The listener: two queues, not one

On Linux, a listening TCP socket owns two separate structures. People blur them all the time. Don't.

The SYN queue holds request sockets: small records for connections where the server has received a SYN and sent a SYN-ACK, but hasn't yet seen the final ACK. These are the connections ss shows in state SYN-RECV. Each one remembers the client's initial sequence number, its options (MSS, window scale, SACK, timestamps), and a retransmit timer. If the ACK never comes, the kernel resends the SYN-ACK. With net.ipv4.tcp_synack_retries = 5 (the Linux default) that is five retransmits with exponential backoff, about a minute of holding the slot.

The accept queue holds fully established connections that the application hasn't yet picked up with accept(). Its limit is the backlog argument to listen(), capped by net.core.somaxconn (4096 by default since Linux 5.4; it used to be 128).

A SYN flood fills the first queue. A slow application fills the second. The symptoms look similar from the client — new connections hang — but the counters, the causes and the fixes are completely different.

SYN cookies: state folded into a sequence number

When the SYN queue is full and net.ipv4.tcp_syncookies = 1 (the Linux default), the kernel stops allocating request sockets. It still answers every SYN with a SYN-ACK. But the server's initial sequence number in that SYN-ACK is no longer random. It is a cookie: a keyed hash of the connection's 4-tuple, a coarse clock, and an index that encodes the client's MSS. Then the server forgets the connection completely.

A real client answers with an ACK whose acknowledgement number is cookie + 1. The server subtracts one, recomputes the hash from the 4-tuple in that ACK, and checks two things. Was the cookie minted in the last couple of minutes? Does the hash match? If both hold, the server rebuilds the connection from the cookie and creates a full socket directly in the accept queue. A spoofed source never receives the SYN-ACK, so it can never produce the right ACK. The flood costs the server CPU and outbound bandwidth, but no memory.

Linux packs the cookie like this (from net/ipv4/syncookies.c): the top 8 bits are a minute counter, and the low 24 bits hold a second keyed hash plus the MSS index. A first keyed hash and the client's ISN are added on top so the cookie looks random. The MSS has to fit in two bits, so it is rounded down to one of four values: 536, 1300, 1440 or 1460 for IPv4.

What does the server lose? Everything else from the SYN. Window scaling, SACK and ECN don't fit into 32 bits. Linux gets them back only when the client also sent TCP timestamps: it hides those options in the low bits of its own timestamp value, and the client echoes the timestamp in every ACK. Without timestamps, a cookie connection runs with no window scaling, which caps the window at 64 KB. That is fine for an emergency, and it's why cookies are a fallback, not the normal path.

The simulation below follows the same layout. Linux uses SipHash with a random boot-time secret; this uses HMAC-SHA256 so it runs on the standard library.

d17_syncookie.py:

"""SYN cookies, Linux-style layout: stateless SYN-ACK, state rebuilt from the ACK.

Linux uses siphash with a boot-time secret; this demo uses HMAC-SHA256.
The bit layout (8-bit minute counter on top, 24-bit keyed hash + MSS index
below) follows net/ipv4/syncookies.c.
"""
import hashlib
import hmac

SECRET = bytes.fromhex("5e" * 32)         # per-boot random secret in real life
MSS_TABLE = [536, 1300, 1440, 1460]       # IPv4 table in syncookies.c
COOKIEBITS = 24
COOKIEMASK = (1 << COOKIEBITS) - 1
MAX_AGE = 2                               # minutes a cookie stays valid


def h(*parts) -> int:
    msg = "|".join(map(str, parts)).encode()
    return int.from_bytes(hmac.digest(SECRET, msg, hashlib.sha256)[:4], "big")


def make_cookie(four_tuple, client_isn, minute, client_mss):
    idx = max(i for i, m in enumerate(MSS_TABLE) if m <= client_mss)
    low = (h(*four_tuple, minute, 2) + idx) & COOKIEMASK
    return (h(*four_tuple, 1) + client_isn + (minute << COOKIEBITS) + low) % 2**32


def check_cookie(four_tuple, ack_minus_1, client_isn, now_minute):
    """Return the MSS the client asked for, or None if the cookie is bad."""
    c = (ack_minus_1 - h(*four_tuple, 1) - client_isn) % 2**32
    minute = c >> COOKIEBITS
    if (now_minute - minute) % 256 > MAX_AGE:
        return None
    idx = ((c & COOKIEMASK) - h(*four_tuple, minute, 2)) & COOKIEMASK
    return MSS_TABLE[idx] if idx < len(MSS_TABLE) else None


tup = ("192.0.2.44", 51544, "203.0.113.10", 443)
isn, now = 1_829_441_017, 117
cookie = make_cookie(tup, isn, now, client_mss=1460)
print(f"SYN    seq={isn}  mss=1460   -> server stores NOTHING")
minute = (cookie - h(*tup, 1) - isn) % 2**32 >> COOKIEBITS
print(f"SYN-ACK seq={cookie}  <- the cookie (minute counter {minute})")
print(f"ACK    ack={(cookie + 1) % 2**32}")
print("  valid ACK, same minute     ->", check_cookie(tup, cookie, isn, now))
print("  valid ACK, 2 minutes later ->", check_cookie(tup, cookie, isn, now + 2))
print("  valid ACK, 3 minutes later ->", check_cookie(tup, cookie, isn, now + 3))
print("  guessed ack (cookie+999)   ->", check_cookie(tup, (cookie + 999) % 2**32, isn, now))
spoof = ("192.0.2.99", 51544, "203.0.113.10", 443)
print("  same ack, other source IP  ->", check_cookie(spoof, cookie, isn, now))
for mss in (1400, 1220, 9001):
    c = make_cookie(tup, isn, now, client_mss=mss)
    print(f"client mss {mss:>4} -> recovered {check_cookie(tup, c, isn, now)}")

Read the last three lines carefully. A client advertising MSS 1400 gets 1300, because 1400 isn't in the table and the cookie rounds down. That's a little throughput lost per segment, and it's the price of statelessness. A jumbo-frame client asking for 9001 gets 1460. The forged and replayed ACKs fail because the attacker would have to guess a 24-bit keyed value bound to the exact 4-tuple. A random guess passes about 4 times in 16.7 million.

Here is how to read those numbers together. 1.8 million cookies went out. About 3,900 came back valid: those are real clients who connected during the flood and never noticed. The 112 failures are late or forged ACKs. ListenOverflows is zero, so the accept queue never filled — the application kept up. On a listening socket, ss shows the accept queue's current length in Recv-Q and its limit in Send-Q. Zero out of 4096 is healthy.

Now compare a different incident with the same client symptom. There, ListenOverflows and ListenDrops climb and Recv-Q sits at 4096, while the cookie counters stay at zero. That isn't an attack. The application stopped calling accept() fast enough — a stuck event loop, a thread pool at its limit. No firewall setting helps. Two queues, two fixes.

Amplification on the victim's wire

Reflection looks strange from the victim's side: answers to questions you never asked.

$ sudo tcpdump -nn -i eth0 'udp src port 53 or (ip[6:2] & 0x1fff != 0)'
10:03:41.220114 IP 192.0.2.53.53 > 203.0.113.10.47212: 4823 28/0/1 TXT "v=spf1 ...", ... (3410)
10:03:41.220119 IP 192.0.2.53 > 203.0.113.10: ip-proto-17
10:03:41.220131 IP 198.51.100.8.53 > 203.0.113.10.47212: 4823 28/0/1 TXT "v=spf1 ...", ... (3410)
10:03:41.220135 IP 198.51.100.8 > 203.0.113.10: ip-proto-17

The DNS responses arrive at port 47212 from hundreds of resolvers. Every one carries the same query ID, because the attacker forged one query and sprayed it. They are 3,410 bytes, so each one shows up as a first fragment plus a trailing fragment (ip-proto-17 is tcpdump's name for a non-first UDP fragment, which has no port numbers). Your own resolver logs show no matching outbound query. That mismatch — inbound responses with no outbound request — is the signature of reflection.

Fragments matter for the defence. A filter that matches "UDP source port 53" misses every trailing fragment, because those carry no UDP header. Scrubbing gear handles this by tracking fragments or by dropping non-initial UDP fragments to the target outright, which is safe for most services.

Spoofing and the reverse-path check

BCP 38 (RFC 2827) says an edge network should drop outbound packets whose source address it doesn't own. The usual implementation is unicast reverse-path forwarding (uRPF), described in RFC 3704. For each arriving packet, the router looks up the source address in its forwarding table as if it were a destination. Then it applies one of two tests.

  • Strict mode. The best route back to the source must point out the same interface the packet came in on. If a customer port receives a packet from 8.8.8.8, the route to 8.8.8.8 points upstream, not to the customer, so the packet is dropped.
  • Loose mode. Any route to the source is enough, through any interface. This only drops sources that aren't routable at all: bogons, unallocated space.

Strict mode is the one that stops spoofing, and it breaks on asymmetric paths. A multihomed customer can legitimately send traffic out link A while your route back to them prefers link B. Strict uRPF drops that traffic. So operators fall back to loose mode on such links, and loose mode lets nearly every spoofed packet through, because nearly every address is routable somewhere. RFC 8704 ("enhanced feasible-path uRPF") tries to fix this by also accepting sources that the customer could legitimately use, based on all the BGP routes the customer announced, not only the best ones.

Linux has the same check in miniature as net.ipv4.conf.*.rp_filter: 0 is off, 1 is strict, 2 is loose. Many distributions ship with 1 or 2; the test container this guide was built on had 0. Drops show up in one counter:

$ nstat -az TcpExtIPReversePathFilter
TcpExtIPReversePathFilter       2291               0.0

Remember that counter. Module 18's deep dive comes back to it, because strict rp_filter on a host with two interfaces causes one of the most confusing incidents in Linux networking.

TLS interception, seen from the client

A TLS-inspecting proxy runs two TLS sessions. It accepts your ClientHello, reads the SNI to learn which site you want, and opens its own TLS connection to that site. Then it mints a certificate for the same hostname on the fly, signed by an issuing CA whose root your company's device management installed on your laptop. Your browser validates that chain against the installed root and is satisfied. The proxy now has the plaintext of both sides.

Here is the same host seen from a managed laptop on the corporate network (constructed, with names changed):

$ openssl s_client -connect www.example.com:443 -servername www.example.com </dev/null 2>/dev/null \
    | grep -E '^ *[0-9] s:|^ *i:'
 0 s:CN = www.example.com
   i:C = US, O = Corp IT, CN = Corp TLS Inspection Issuing CA 2026
 1 s:C = US, O = Corp IT, CN = Corp TLS Inspection Issuing CA 2026
   i:C = US, O = Corp IT, CN = Corp Root CA

From a phone on cellular, the issuer is a public CA. That difference is the whole test: compare the issuer, or the certificate's SHA-256 fingerprint (openssl x509 -noout -fingerprint -sha256), from two vantage points.

Interception has precise, predictable breakages. Knowing them is what separates someone who has run it from someone who has read about it.

  • Client certificates (mTLS) cannot pass through. In the handshake, the client signs the handshake transcript with its private key. The proxy's transcript with the server is a different transcript, and the proxy doesn't hold your key. So mTLS destinations must be on a bypass list, or the proxy has to present its own client certificate, which means the server authenticates the proxy, not you.
  • Certificate pinning breaks. Apps that pin a public key or a specific CA reject the minted certificate. Mobile apps and some CLIs fail with errors that look like network faults.
  • Encrypted Client Hello hides the SNI. With ECH, the visible SNI names only the provider's shared front end. The proxy can no longer choose a policy per site. Enterprise deployments usually respond by making sure managed clients never receive ECH configurations, or by blocking it.
  • The proxy becomes the weakest validator. Your browser is no longer checking the origin's certificate; the proxy is. Measurement studies have repeatedly found inspection products that accept weaker ciphers or validate upstream certificates less strictly than the browsers behind them.

There's also a history lesson hidden in every TLS 1.3 handshake. Early TLS 1.3 drafts failed in the field because middleboxes dropped anything that didn't look like TLS 1.2. So RFC 8446 Appendix D.4 defines a "middlebox compatibility mode." The ClientHello still claims version 0x0303 (TLS 1.2) and carries the real version in the supported_versions extension. It sends a non-empty legacy session ID and a dummy ChangeCipherSpec message. A TLS 1.3 handshake on the wire is dressed up as a TLS 1.2 resumption so that broken inspection boxes leave it alone.

mTLS and identity-aware access, as code

Zero trust between services usually means mutual TLS with a workload identity in the certificate. SPIFFE standardises the format: the identity is a URI such as spiffe://prod.example/ns/payments/sa/api, carried as a URI subject alternative name in a short-lived X.509 certificate called an SVID. Two separate checks happen, and conflating them is the most common design bug.

  1. Authentication, inside the TLS handshake: the peer's certificate chains to the trust domain's CA, it's within its validity window, and the peer proved it holds the matching private key.
  2. Authorization, after the handshake: this identity may call this service. TLS libraries do not do this for you. "Any valid certificate from our CA" is authentication only, and it lets every workload in the trust domain talk to every other one. That is a flat network rebuilt in cryptography.

The demo issues certificates with openssl (the standard library can't create certificates). Then a Python server requires a client certificate and checks the SPIFFE ID against an allowlist.

# d17_mk_pki.sh — a trust-domain CA, three workload certs, and a forged one
set -e
# Trust-domain CA (in production: SPIRE, Istio, or a cloud CA)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 7 \
  -keyout ca.key -out ca.pem -subj "/O=prod.example/CN=prod.example workload CA" -addext "keyUsage=critical,keyCertSign,cRLSign" 2>/dev/null
leaf() {  # name, URI SAN, signing CA prefix
  openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout $1.key \
    -subj "/O=prod.example" -out $1.csr 2>/dev/null
  printf "subjectAltName=%s\nextendedKeyUsage=serverAuth,clientAuth\nkeyUsage=critical,digitalSignature\nauthorityKeyIdentifier=keyid\n" "$2" > $1.ext
  openssl x509 -req -in $1.csr -CA $3.pem -CAkey $3.key -CAcreateserial -days 1 \
    -extfile $1.ext -out $1.pem 2>/dev/null
}
leaf db     "URI:spiffe://prod.example/ns/data/sa/payments-db,DNS:payments-db" ca
leaf api    "URI:spiffe://prod.example/ns/payments/sa/api" ca
leaf report "URI:spiffe://prod.example/ns/analytics/sa/report" ca
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 7 \
  -keyout rogue.key -out rogue.pem -subj "/CN=attacker CA" -addext "keyUsage=critical,keyCertSign,cRLSign" 2>/dev/null
leaf forged "URI:spiffe://prod.example/ns/payments/sa/api" rogue

d17_mtls_authz.py:

"""mTLS + identity authorization: the server trusts a CA, then a SPIFFE ID.

Authentication = "the certificate chains to our CA and the peer holds the key."
Authorization  = "this identity may call this service." Two separate checks.
"""
import socket
import ssl
import threading

ALLOWED = {"spiffe://prod.example/ns/payments/sa/api"}   # the policy

srv_ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
srv_ctx.minimum_version = ssl.TLSVersion.TLSv1_3
srv_ctx.load_cert_chain("db.pem", "db.key")
srv_ctx.load_verify_locations("ca.pem")
srv_ctx.verify_mode = ssl.CERT_REQUIRED                   # the "m" in mTLS

listener = socket.create_server(("127.0.0.1", 0))
port = listener.getsockname()[1]
log = []


def serve_one():
    raw, _ = listener.accept()
    try:
        with srv_ctx.wrap_socket(raw, server_side=True) as tls:
            sans = tls.getpeercert().get("subjectAltName", ())
            ids = [v for k, v in sans if k == "URI"]
            if ids and ids[0] in ALLOWED:                 # authorization
                tls.sendall(f"200 hello {ids[0]}".encode())
            else:
                tls.sendall(f"403 {ids[0] if ids else '?'} not allowed".encode())
    except ssl.SSLError as e:
        log.append(f"  server: rejected handshake: {e.reason}")


def call(label, cert=None):
    ctx = ssl.create_default_context(cafile="ca.pem")
    ctx.check_hostname = True
    if cert:
        ctx.load_cert_chain(f"{cert}.pem", f"{cert}.key")
    try:
        with socket.create_connection(("127.0.0.1", port)) as raw:
            with ctx.wrap_socket(raw, server_hostname="payments-db") as tls:
                log.append(f"  client: handshake complete ({tls.version()})")
                log.append(f"  client: reply = {tls.recv(200).decode()!r}")
    except (ssl.SSLError, ConnectionResetError) as e:
        log.append(f"  client: first read fails: {getattr(e, 'reason', e)}")


cases = [("no client certificate", None), ("cert from attacker CA", "forged"),
         ("payments/api (valid, allowed)", "api"),
         ("analytics/report (valid, denied)", "report")]
for label, cert in cases:
    t = threading.Thread(target=serve_one)
    t.start()
    call(label, cert)
    t.join()
    print(label)
    print("\n".join(sorted(log, key=lambda x: "server" in x)))
    log.clear()

Look at the first two cases. The client reports "handshake complete" and only fails on its first read. That isn't a bug in the demo. In TLS 1.3 the client sends its certificate in its final flight and considers the handshake finished. The server validates it afterwards and replies with an alert. So a client without a valid certificate sees success from connect() and then an error on its first recv(). Expect this when you debug mTLS: the client logs say "connected," the server logs say "rejected," and both are telling the truth.

The fourth case is the one zero-trust designs exist for. The analytics workload holds a perfectly valid certificate from the right CA, and it is still refused, because policy names identities, not CAs.

Deep dive: by the numbers

Packet rates and amplification

A flood is measured in two units, and they stress different things. Bits per second fill links. Packets per second exhaust CPUs, interrupt budgets and lookup tables. A minimum-size Ethernet frame is 64 bytes, and the preamble and inter-frame gap occupy another 20 byte-times on the wire, so a 10 Gbps link carries at most 14.88 million minimum-size packets per second.

Bandwidth amplification factors come from US-CERT alert TA14-017A, with memcached added after the 2018 attacks. They measure UDP payload out divided by UDP payload in. Real reflectors vary widely, and many NTP servers no longer answer monlist at all.

d17_flood_math.py:

"""Back-of-envelope DDoS numbers: packet rates and reflection output."""

# Smallest Ethernet frame is 64 bytes; preamble+SFD (8) and the
# inter-frame gap (12) also occupy the wire, so 84 byte-times per packet.
WIRE_BYTES_MIN = 64 + 8 + 12

for gbps in (1, 10, 100):
    pps = gbps * 1e9 / (WIRE_BYTES_MIN * 8)
    print(f"{gbps:>3} Gbps of minimum-size SYNs = {pps / 1e6:6.2f} Mpps")

# Bandwidth amplification factor = UDP payload out / UDP payload in.
# Ranges from US-CERT TA14-017A (memcached added 2018). Real servers vary.
factors = {
    "DNS (open resolver, ANY)": 54,
    "NTP (monlist)": 556.9,
    "CLDAP": 70,
    "SSDP": 30.8,
    "memcached (UDP 11211)": 51_000,
}
attacker_gbps = 1.0
print(f"\nattacker sends {attacker_gbps} Gbps of spoofed requests:")
for name, f in factors.items():
    out = attacker_gbps * f
    unit = f"{out / 1000:,.1f} Tbps" if out >= 1000 else f"{out:,.1f} Gbps"
    print(f"  {name:<26} x{f:>9,}  -> {unit} at the victim (if reflectors can send it)")

# The cap in practice is the reflectors' own uplinks, not the factor.
reflectors, uplink_mbps = 20_000, 100
print(f"\n{reflectors:,} DNS reflectors x {uplink_mbps} Mbps usable each "
      f"= {reflectors * uplink_mbps / 1e3:,.0f} Gbps ceiling")

  DNS (open resolver, ANY)   x       54  -> 54.0 Gbps at the victim (if reflectors can send it)
  NTP (monlist)              x    556.9  -> 556.9 Gbps at the victim (if reflectors can send it)
  CLDAP                      x       70  -> 70.0 Gbps at the victim (if reflectors can send it)
  SSDP                       x     30.8  -> 30.8 Gbps at the victim (if reflectors can send it)
  memcached (UDP 11211)      x   51,000  -> 51.0 Tbps at the victim (if reflectors can send it)

20,000 DNS reflectors x 100 Mbps usable each = 2,000 Gbps ceiling

The memcached line is deliberately absurd. No attacker gets 51 Tbps from a 1 Gbps uplink, because the factor is only an upper bound: each reflector can send only what its uplink allows. The largest memcached attacks of 2018 measured in the low terabits. The binding constraint is the population of reflectors and their combined capacity, which is why cleaning up open resolvers and exposed memcached servers mattered as much as any filter.

Why short-lived certificates beat revocation

Here's a calculation that settles a design debate. Suppose a workload certificate leaks. With a 90-day certificate and no working revocation, the attacker's window is up to 90 days. With a one-hour certificate rotated every 30 minutes, the window is at most an hour, and nobody had to build or check a revocation list. That is why service meshes and SPIRE issue short-lived certificates by default. The cost moves to the issuing CA: a cluster with 5,000 workloads rotating every 30 minutes signs about 2.8 certificates per second, around the clock. The CA becomes a tier-zero dependency. If it's down for longer than a certificate's remaining lifetime, workloads stop being able to talk to each other.

Deep dive: production failure modes

The flood that isn't a SYN flood. Symptom: new connections hang, CPU is fine, and someone turns on more cookies. Mechanism: the accept queue is full because the application is slow; SYN cookies do nothing for that queue. Proof: nstat -az TcpExtListenOverflows rising while TcpExtSyncookiesSent stays flat, and ss -lnt showing Recv-Q equal to Send-Q on the listener. Fix: find what blocks the accept loop, and raise the backlog only as a buffer.

SYN-ACK retransmits as an amplifier. Symptom: a server with cookies disabled (some appliances and tuned hosts do this) becomes part of an attack on someone else. Mechanism: each spoofed SYN creates a request socket, and the server retransmits the SYN-ACK five more times to the spoofed victim. That's six packets out for one in. Proof: outbound SYN-ACK packet rate far above inbound SYN rate in tcpdump or NetFlow. Fix: leave tcp_syncookies at 1, which never retransmits cookie SYN-ACKs because it holds no state to retransmit from.

Strict uRPF on an asymmetric edge. Symptom: after a routing change, some customers lose connectivity, and only in one direction. Mechanism: strict uRPF drops their packets because the best return route now points out a different interface. Proof: the router's uRPF drop counters on that interface; on Linux, TcpExtIPReversePathFilter. Fix: feasible-path uRPF (RFC 8704) or loose mode on that link, with explicit ACLs for the customer's prefixes so you don't give up BCP 38 entirely.

The identity-aware proxy with an open side door. Symptom: a penetration test reaches an internal app without logging in. Mechanism: the app trusted an identity header (such as X-User or the proxy's signed assertion) but also accepted connections that didn't come through the proxy. An attacker who can reach the backend directly just sets the header. Proof: curl -H 'X-User: admin' http://backend:8080/ from inside the network. Fix, both halves: verify the proxy's signed assertion (a JWT: check signature, audience, issuer and expiry) on every request, and allow backend ingress only from the proxy — by mTLS between proxy and backend, or at minimum by firewall.

Default-deny that broke DNS. Symptom: you apply a Kubernetes default-deny egress policy to a namespace, and every pod starts failing with name-resolution timeouts, even to allowed services. Mechanism: DNS is egress too. Pods talk to CoreDNS on UDP and TCP 53, and the policy now denies it. Proof: kubectl exec into a pod and run getent hosts kubernetes.default; it hangs. Fix: an explicit egress rule to the DNS pods on both protocols, applied before the deny.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-plus-dns, namespace: payments}
spec:
  podSelector: {}                 # every pod in the namespace
  policyTypes: [Ingress, Egress]  # nothing in, nothing out, except:
  egress:
  - to:
    - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
      podSelector: {matchLabels: {k8s-app: kube-dns}}
    ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]

Policy changes that don't cut existing flows. Symptom: you tighten a rule during an incident, and the attacker's session keeps working. Mechanism: most enforcement is stateful. The allow decision was made on the first packet and cached as a connection-tracking entry; later packets match the entry, not the rule. Whether a policy change flushes existing entries depends on the implementation. Proof: conntrack -L -s <attacker-ip> on the node (or the vendor's flow table) still shows the session. Fix: delete the tracked flows explicitly (conntrack -D -s <ip>), or kill the workload. Put this step in the incident runbook, because nobody remembers it at 3 AM.

The IP-based policy that lags pod churn. Symptom: brief, random connection failures right after deployments; sometimes a pod briefly reaches something it shouldn't. Mechanism: the enforcement layer compiles label-based policy into IP sets. A new pod gets an IP before every node has updated its sets, and a recycled IP briefly carries the previous pod's permissions. Proof: correlate the drops with pod creation times; check the CNI agent's sync latency metrics. Fix: identity-based enforcement where the data path checks a security identity rather than a raw IP, and readiness gates that wait for policy to be programmed.

Deep dive: 2026 context

Microsegmentation is maps, not rules. In current Kubernetes networking the enforcement point is usually eBPF. Cilium, for example, gives each distinct set of pod labels a numeric security identity, keeps an IP-to-identity map on every node, and looks up policy by (identity, port, protocol) in an eBPF map on each packet. Calico can run as eBPF or iptables. Either way, the scaling question is the same: how fast does a change in the cluster reach every node's map? Policy correctness is now partly a distributed-systems problem.

Cloud security groups are hypervisor microsegmentation. On AWS, security groups are enforced outside the instance, in the virtualisation layer, and they are stateful, so the hypervisor keeps its own connection-tracking table per network interface. It has a limit, and on Nitro instances the ENA driver exposes a conntrack_allowance_exceeded counter in ethtool -S. That table is separate from the Linux kernel's. Module 18's deep dive shows how both can fill up.

DDoS moved to layer 7 and to protocol abuse. The largest attacks of recent years have been HTTP/2 request floods rather than raw bandwidth. The 2023 "Rapid Reset" attack (CVE-2023-44487) opened and immediately cancelled streams, so one connection could generate huge request rates while staying under the concurrent-stream limit. The defence was in HTTP/2 implementations — counting resets and closing abusive connections — not in any packet filter. It's the module's "match the tool to the layer" rule, one layer up.

QUIC brings its own anti-amplification rule. QUIC runs over UDP, so a QUIC server could become a reflector. RFC 9000 forbids that: until the client's address is validated, a server may send at most three times the bytes it has received. It can also send a Retry packet carrying an address-validation token — SYN cookies again, in a new protocol.

Zero trust is now mostly identity plumbing. NIST SP 800-207's policy engine and enforcement points show up as an identity-aware proxy for people (single sign-on plus device posture, often with a device certificate held in a TPM or Secure Enclave) and as a mesh or SPIFFE-based mTLS for workloads. The hard problems are the boring ones. You have to inventory every workload's identity, write least-privilege policy, and keep the issuing CA highly available.

ECH and DNS encryption shrink the network's view. With ECH and encrypted DNS spreading, network-based security tools see less: no SNI, no plaintext DNS. Network inspection is shifting toward the endpoint (EDR, managed browsers) and toward the identity layer, which is where zero trust said the decisions belonged anyway.

Deep dive: senior interview questions

Q1: The server's SYN queue is full. Explain exactly how SYN cookies let a real client still connect.

The server answers each SYN with a SYN-ACK whose sequence number is a keyed hash of the 4-tuple, a minute counter and an MSS index, and it stores nothing. A real client ACKs with cookie + 1. The server recomputes the hash from that ACK, checks the counter is recent, recovers the MSS, and creates the socket straight into the accept queue. Spoofed sources never see the SYN-ACK, so they can't produce the ACK. The cost is lost options: MSS is rounded to one of four values, and window scaling and SACK survive only if the client used timestamps.

Q2: Connections are timing out under load. How do you tell a SYN flood from a slow application, using only the server?

Look at the two queues separately. A SYN flood shows SyncookiesSent and TCPReqQFullDoCookies climbing and a large SYN-RECV population, while the accept queue stays empty. A slow application shows ListenOverflows and ListenDrops climbing, with ss -lnt showing the listener's Recv-Q at its Send-Q limit, and no cookies at all. Different queue, different fix.

Q3: Amplification factor for DNS is around 50. Why don't attackers with 1 Gbps get 50 Gbps?

The factor is per-request. The output is capped by the reflectors' own uplinks and how many open reflectors the attacker can find. It's also capped by the fact that many resolvers rate-limit responses or refuse ANY queries now. Attack size is the sum of reflector capacity, not the attacker's bandwidth times a constant.

Q4: Why is strict uRPF rarely deployed at peering and transit edges?

Because paths there are routinely asymmetric. Strict mode requires the best route back to the source to use the arrival interface, and multihomed networks legitimately violate that, so strict mode drops real traffic. Loose mode doesn't drop anything routable, so it barely prevents spoofing. That gap is why BCP 38 is most effective at the customer edge, where a single-homed customer's prefixes are known exactly, and why RFC 8704 exists.

Q5: Your company runs TLS inspection. A team's mTLS integration with a partner fails only on the office network. Why?

mTLS requires the client to sign the handshake transcript with its private key. The proxy terminates TLS, so the partner sees the proxy's handshake, and the proxy doesn't have the client's key. The partner either gets no client certificate or the proxy's own. The fix is a bypass rule for that destination. Proof: compare openssl s_client -showcerts issuers from the office and from outside.

Q6: You've deployed mTLS everywhere. Have you implemented zero trust?

Only authentication. mTLS proves which workload is on the other end. If every service accepts any certificate from the cluster CA, any compromised workload can still call everything. Zero trust also needs per-identity authorization policy, least privilege, and a fast way to revoke or stop issuing an identity, plus device and user context where people are involved.

Q7: An identity-aware proxy fronts an internal app. What's the classic bypass, and what are the two halves of the fix?

The backend trusts an identity header but is also reachable without going through the proxy, so an attacker inside the network calls it directly and forges the header. The fix is to verify the proxy's signed assertion on every request (signature, audience, expiry), and to accept backend connections only from the proxy, ideally over mTLS.

Q8: You apply a stricter NetworkPolicy during an incident, but the suspicious connection stays up. Why, and what do you do?

Enforcement is stateful. The connection was allowed at its first packet, and later packets match the tracked flow rather than re-evaluating policy. Depending on the implementation, policy changes may not flush existing entries. Delete the flow from the tracking table (conntrack -D on iptables-based nodes, the CNI's own tooling otherwise) or restart the workload, then confirm with a capture that packets stop.
