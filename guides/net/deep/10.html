Deep dive: what registered mail leaves out

Registered mail is a good picture of TCP's promise: everything arrives, in order, or you hear about it. It says nothing about the machine that keeps the promise. Behind every connected socket the kernel keeps a small state machine with real fields: sequence pointers, two windows, a smoothed RTT estimate, a retransmission queue, an out-of-order queue, two buffers and half a dozen timers. Almost every TCP performance problem you will debug is one of those fields holding a number you did not expect.

The analogy also hides the fact that TCP has to guess. It cannot see the network. It infers capacity from ACK timing and infers loss from silence or from gaps. Those guesses have defaults, and the defaults have consequences: a 40 ms stall on small requests, a 15-minute wait to notice a dead peer, a 200 ms queue that only one congestion controller fills.

UDP gets the opposite treatment. "A postcard" sounds harmless. In practice UDP means that nothing pushes back on a fast sender, so the receiver's socket buffer overflows and the kernel quietly counts the losses.

Most output below is real. It comes from a three-namespace Linux lab (client c 10.10.0.2, router r, server s 10.20.0.2) on the guide's sandbox, kernel 6.18, plus stdlib Python scripts. The lab has no artificial propagation delay; where RTTs are large, a queue made them large, and the text says so.

Deep dive: the real mental model

A connection is a struct with pointers into a byte stream

Each direction of a TCP connection is a numbered byte stream. The sender tracks three positions in it (RFC 9293 names):

  • SND.UNA: the oldest byte sent but not yet acknowledged.
  • SND.NXT: the next byte it will send.
  • The send limit: SND.UNA plus the effective window.

Bytes between SND.UNA and SND.NXT are in flight. The sender may keep sending until in-flight bytes reach the effective window, which is the smaller of two numbers that come from opposite ends of the path:

  • rwnd, the receive window, comes from the receiver. It is the free space in the receiver's socket buffer, advertised in every ACK. It protects the receiving application.
  • cwnd, the congestion window, lives only in the sender. It is the sender's running guess at how much the network can hold without loss. It protects the path.

Everything else in this deep dive hangs off this picture. Slow start, CUBIC and BBR are rules for moving cwnd. Flow-control stalls are rwnd hitting zero. A retransmission is SND.UNA refusing to move. And the bandwidth-delay product tells you how big the window must be for the pipe to stay full.

The textbook says "fast retransmit after three duplicate ACKs" (RFC 5681). This sender retransmitted after two. Modern Linux decides loss with RACK-TLP (RFC 8985): a segment counts as lost when a segment sent after it has been acknowledged and a short reordering window has passed. The rule is based on time, not on a fixed count. SACK blocks (RFC 2018) tell the sender exactly which bytes are missing, so it resends one segment instead of everything after the hole. The whole repair took one round trip and no timeout.

The spacing is 1, 1, 1, 1, 1, then 2, 4, then a final 8-second wait. Recent kernels add net.ipv4.tcp_syn_linear_timeouts (default 4), which keeps the first retries one second apart before exponential backoff begins. Those linear retries are added on top of tcp_syn_retries, which is why three "retries" put eight SYNs on the wire. With the default tcp_syn_retries=6, the same schedule works out to about 131 seconds before connect() fails. Older kernels used pure doubling (1 + 2 + 4 + ... + 64 = 127 s). Always set your own connect timeout instead of inheriting either number.

The "21 seconds" in the module comes from Windows: an initial 3 s timeout and two retries, 3 + 6 + 12 = 21 s. When you see a round number like that in a latency histogram, work out the retransmission schedule before blaming the application.

import math

MSS = 1448                       # 1500 MTU - 20 IP - 20 TCP - 12 timestamp option

print("1. Bandwidth-delay product (bytes that must be in flight to fill the pipe)")
for gbps, rtt_ms in [(0.1, 20), (1, 20), (1, 100), (10, 100)]:
    bdp = gbps * 1e9 / 8 * rtt_ms / 1000
    print(f"   {gbps:>5} Gbit/s x {rtt_ms:>3} ms = {bdp / 1e6:7.2f} MB  ({bdp / MSS:9,.0f} segments)")

print("2. Throughput ceiling = window / RTT")
for window, label in [(65_535, "64 KiB (no window scaling)"), (6 * 2**20, "6 MiB (common tcp_rmem max)")]:
    for rtt_ms in (20, 100):
        print(f"   {label:28s} @ {rtt_ms:>3} ms -> {window * 8 / (rtt_ms / 1000) / 1e6:8.1f} Mbit/s")

print("3. Loss ceiling for Reno-style AIMD (Mathis: rate <= MSS/RTT * 1.22/sqrt(p))")
for p in (1e-4, 1e-3, 1e-2):
    rate = MSS * 8 / 0.1 * 1.22 / math.sqrt(p)
    print(f"   RTT 100 ms, loss {p:.2%}: {rate / 1e6:7.1f} Mbit/s, whatever the link speed")

print("4. Slow start from IW10: round trips to deliver a response (no loss)")
for size in (14_480, 100_000, 1_000_000, 10_000_000):
    cwnd, sent, rtts = 10, 0, 0
    while sent < size:
        sent += cwnd * MSS
        cwnd *= 2
        rtts += 1
    print(f"   {size:>10,} bytes -> {rtts:2d} RTTs")

print("5. RTO from RTT samples (RFC 6298: alpha 1/8, beta 1/4, K 4)")
srtt = rttvar = None
for r in (100, 102, 98, 250, 101, 99):
    if srtt is None:
        srtt, rttvar = r, r / 2
    else:
        rttvar = 0.75 * rttvar + 0.25 * abs(srtt - r)
        srtt = 0.875 * srtt + 0.125 * r
    rto = srtt + 4 * rttvar
    print(f"   sample {r:3d} ms -> srtt {srtt:6.1f}  rttvar {rttvar:5.1f}  rto {rto:6.1f} ms")

print("6. Give-up time for an established connection, tcp_retries2 = 15")
total, rto = 0.0, 0.2
for _ in range(16):
    total += min(rto, 120)
    rto *= 2
print(f"   200 ms doubling, capped at 120 s, 16 timeouts: {total:.1f} s (~{total / 60:.1f} min)")

print("7. 32-bit sequence space: time to wrap (why PAWS/timestamps exist)")
for gbps in (1, 10, 100):
    print(f"   {gbps:>3} Gbit/s: {2**32 * 8 / (gbps * 1e9):6.2f} s")

print("8. TIME_WAIT budget: one client IP -> one server ip:port")

Sequence space

Sequence numbers are 32 bits and count bytes. The initial sequence number is randomised per connection (RFC 6528), so the numbers in two captures never line up. At 10 Gbit/s the whole space wraps in 3.4 seconds, which is shorter than the time an old duplicate segment can survive in the network. The timestamp option (RFC 7323) fixes this: PAWS (Protection Against Wrapped Sequences) rejects segments whose timestamp is older than the last one seen. That is one reason Linux sends 12 bytes of timestamps on every segment.

The 16-bit window field can describe at most 65,535 bytes. Window scaling, agreed once in the SYN and SYN-ACK, shifts it left by up to 14 bits, for a maximum window of about 1 GiB. If either side's SYN lacks the option, the connection is stuck at 64 KiB for its whole life. Row 2 shows what that costs: 5.2 Mbit/s at 100 ms, however fast the link. Middleboxes that strip TCP options used to cause exactly this.

rwnd versus cwnd, and buffer sizing

The bandwidth-delay product (row 1) is the number of bytes that must be in flight to keep a path busy. Both windows must reach it. On a 1 Gbit/s, 100 ms path that is 12.5 MB.

rwnd is bounded by the receiver's socket buffer. Linux sizes it automatically (tcp_moderate_rcvbuf=1) within net.ipv4.tcp_rmem. That is three numbers: min, default and max. A common distro maximum is 6 MiB; this sandbox uses 32 MiB. With 6 MiB, a single connection on a 100 ms path tops out near 500 Mbit/s (row 2). The send side has tcp_wmem in the same way.

Two traps live here. First, setting SO_RCVBUF yourself switches off autotuning for that socket, and the kernel doubles the value you ask for to cover its bookkeeping. A hard-coded 64 KiB buffer in an old library will quietly cap a long-distance transfer. Second, net.core.rmem_max caps what setsockopt may request, but it does not cap autotuning, which follows tcp_rmem[2].

Loss sets a ceiling of its own. For Reno-style AIMD, the Mathis formula (row 3) says a 100 ms path with 0.1% random loss cannot exceed about 4.5 Mbit/s per connection, whatever the link speed. CUBIC does better than Reno on long fat paths, and BBR does not treat loss as its main signal at all. That difference is why lossy long-haul links were where BBR first paid off.

Slow start

A new connection starts with an initial window of 10 segments (IW10, RFC 6928): 14,480 bytes with timestamps. Each ACK grows cwnd by the amount acknowledged, so cwnd doubles every round trip. Row 4 shows the consequence. A 100 KB response needs 3 round trips and a 1 MB response needs 7, even on an infinitely fast link. On a 100 ms path that is 300 ms and 700 ms of pure ramp-up. This is the strongest argument for reusing connections: a warm connection keeps its cwnd.

Slow start ends at ssthresh, at the first loss, or when HyStart notices RTT rising (Linux CUBIC uses HyStart; RFC 9406 standardises HyStart++). Watch one more Linux default: net.ipv4.tcp_slow_start_after_idle=1 collapses cwnd after the connection has been idle for longer than one RTO. A long-lived HTTP/2 or gRPC connection with bursty traffic therefore pays slow start again after every pause. Many operators set it to 0 on servers.

Both algorithms deliver the full 19 Mbit/s. The difference is what they do to everyone else. CUBIC is loss-based: it keeps growing cwnd until a packet drops, so it fills the router's 200 ms queue. Its cwnd of 351 segments is about 508 KB, which is roughly the bottleneck rate times the queue delay. Every other flow sharing that link now waits 210 ms. This is bufferbloat, and the ping column shows it.

BBR builds a model instead. It tracks the bottleneck bandwidth (bw:19.2 Mbit/s, the maximum delivery rate over recent round trips) and the minimum RTT (mrtt). It then paces packets at that bandwidth (pacing_rate) and caps cwnd near cwnd_gain × bandwidth × min RTT, so the queue stays almost empty. Here 18 segments were enough. Every ten seconds or so BBR briefly drops to a tiny window (ProbeRTT) to re-measure the minimum RTT. The pacing_gain:1 shown is its steady cruise phase.

The mechanics of CUBIC (RFC 9438) are worth knowing too. After a loss it cuts cwnd to 70% (β = 0.7), not 50% as Reno does. It then grows along a cubic curve, W(t) = C(t − K)³ + W_max with C = 0.4: fast at first, flattening as it nears the window where the last loss happened, then probing beyond it. The curve depends on time since the last loss, not on RTT, which makes it fairer between short- and long-RTT flows than Reno.

BBR has honest caveats. Version 1, which mainline Linux ships as tcp_bbr, can be unfair to CUBIC flows and can cause heavy retransmission on shallow buffers. Later versions add responses to loss and ECN; check which one your kernel or QUIC library actually runs. The real fix for bufferbloat is in the router: an AQM such as fq_codel (CoDel target 5 ms, interval 100 ms) keeps queues short whatever the senders do.

RTO and the 15-minute timeout

Row 5 is RFC 6298 in action. The timeout is the smoothed RTT plus four times its variance, so one 250 ms outlier pushes the RTO from 216 ms to 356 ms. RFC 6298 asks for a 1-second floor. Linux uses a 200 ms floor instead and in practice comes out near SRTT + 200 ms on a stable path. The lab shows exactly that: rtt:210.5 gave rto:412, and rtt:6.9 gave rto:208.

Each consecutive timeout doubles the RTO, which the PMTUD black-hole capture in the Module 09 deep dive shows on the wire: +0.22 s, +0.41 s, +0.84 s, +1.66 s, +3.29 s. With tcp_retries2=15, an established connection whose peer has vanished keeps retrying for about 924.6 seconds (row 6) before the application sees ETIMEDOUT. That is over fifteen minutes. TCP_USER_TIMEOUT (RFC 5482) caps it per socket, and application-level deadlines cap it from above.

TIME_WAIT and port exhaustion

A connection is identified by its 4-tuple. A client talking to one server address and port can only vary its own port, and every port it closed first is held for 60 seconds. Row 8 gives the budget: 28,232 ephemeral ports divided by 60 s is about 471 new connections per second, sustained, per destination. macOS has 16,384 ephemeral ports (49152–65535) but a 30-second TIME_WAIT.

connection 6: local port 50000 ok

EADDRNOTAVAIL ("Cannot assign requested address") on connect() is the signature. tcp_tw_reuse=1 lets outgoing connections take over a TIME_WAIT entry that is more than one second old. It is safe because timestamps let the kernel tell old segments from new ones. The default on current kernels is 2, which means loopback only. The old tcp_tw_recycle broke clients behind NAT and was removed in Linux 4.12. Do not go looking for it.

Nagle and delayed ACK

Nagle's algorithm (RFC 896) holds back a small segment while any earlier data is unacknowledged. Delayed ACK (RFC 1122) lets a receiver wait up to 500 ms (Linux: 40 ms minimum) before acknowledging, hoping to piggyback the ACK on a reply. Each is sensible alone. Together they deadlock briefly whenever an application does write, write, read:

"""nagle_delack.py - the write-write-read stall, measured.

The client sends each request as two small writes (header, then body) and waits
for a reply. With Nagle on, the body waits for the ACK of the header; the server
delays that ACK because it has nothing to send yet. Run on loopback:
    python3 nagle_delack.py
"""
import socket
import statistics
import threading
import time

HEADER, BODY, ROUNDS = b"LEN 5\n", b"hello", 40


def server(listener):
    conn, _ = listener.accept()
    with conn:
        while True:
            data = b""
            while len(data) < len(HEADER) + len(BODY):   # wait for a whole request
                chunk = conn.recv(64)
                if not chunk:
                    return
                data += chunk
            conn.sendall(b"ok")


def run(nodelay):
    listener = socket.create_server(("127.0.0.1", 0))
    threading.Thread(target=server, args=(listener,), daemon=True).start()
    client = socket.create_connection(listener.getsockname())
    client.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, nodelay)
    samples = []
    for _ in range(ROUNDS):
        t0 = time.perf_counter()
        client.sendall(HEADER)          # write 1
        client.sendall(BODY)            # write 2 - Nagle holds this back
        client.recv(2)                  # read
        samples.append((time.perf_counter() - t0) * 1000)
    client.close()
    listener.close()
    return samples


for nodelay in (0, 1):
    s = run(nodelay)
    label = "TCP_NODELAY=1 (Nagle off)" if nodelay else "TCP_NODELAY=0 (Nagle on) "
    print(f"{label}  median {statistics.median(s):7.3f} ms   "
          f"max {max(s):7.3f} ms   total for {ROUNDS} requests {sum(s):7.1f} ms")

Real output on Linux loopback:

TCP_NODELAY=0 (Nagle on)   median  43.980 ms   max  44.195 ms   total for 40 requests  1712.4 ms
TCP_NODELAY=1 (Nagle off)  median   0.041 ms   max   0.138 ms   total for 40 requests     2.0 ms

A thousandfold difference on a path with no latency at all. The header goes out at once. The body waits for the header's ACK (Nagle). The server will not ACK yet, because it is waiting for the whole request before replying (delayed ACK). After about 40 ms the delayed-ACK timer fires and everything moves. The first few requests are fast because Linux starts each connection in "quick ACK" mode; that is why the total is less than 40 × 44 ms.

The best fix is to write each message in one call, by buffering or with writev/sendmsg. The common fix is TCP_NODELAY, which many frameworks set by default (Go's net package does). TCP_CORK (Linux) and MSG_MORE go the other way: they tell the kernel to hold data until you say the message is complete. On macOS the delayed-ACK behaviour differs in detail, but the write-write-read pattern stalls there too.

Keepalive

An idle TCP connection sends nothing at all. If the peer's machine loses power, or a NAT box forgets the mapping, neither side notices until it next sends. Keepalive probes fix that, but the Linux defaults (7200 s idle, then 9 probes 75 s apart) mean a dead peer is noticed after 7,875 seconds: more than two hours. Set the timers per socket:

"""keepalive.py - turn on TCP keepalive with timers short enough to matter."""
import socket
import subprocess
import sys

listener = socket.create_server(("127.0.0.1", 0))
s = socket.create_connection(listener.getsockname())
peer, _ = listener.accept()

s.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
idle_opt = socket.TCP_KEEPALIVE if sys.platform == "darwin" else socket.TCP_KEEPIDLE
s.setsockopt(socket.IPPROTO_TCP, idle_opt, 60)               # first probe after 60 s idle
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)   # then every 10 s
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)      # give up after 3 misses
print("dead peer detected after at most", 60 + 10 * 3, "s of silence")

if sys.platform.startswith("linux"):
    port = s.getsockname()[1]
    out = subprocess.run(["ss", "-tno", f"sport = :{port}"], capture_output=True, text=True)
    print(out.stdout.strip())

Real output on Linux; ss -o shows the armed timer:

dead peer detected after at most 90 s of silence
State Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
ESTAB 0      0          127.0.0.1:58832    127.0.0.1:40437 timer:(keepalive,59sec,0)

TCP keepalive is not HTTP keep-alive. HTTP keep-alive means "reuse this connection for another request". TCP keepalive means "send an empty probe so the path stays known to be alive".

UDP: nothing pushes back

UDP has no window, no ACKs and no congestion control. A sender can always send faster than a receiver reads, and the excess is dropped at the receiver's socket buffer. Nobody tells the sender.

"""udp_drops.py - UDP has no flow control: a slow reader loses datagrams silently.

The sender fires 10,000 x 1,200-byte datagrams at a receiver that is busy.
Nothing tells the sender; the kernel drops what does not fit in the socket buffer.
"""
import socket
import time

N, SIZE = 10_000, 1200

rx = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
rx.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 256 * 1024)
rx.bind(("127.0.0.1", 0))
print(f"receive buffer: asked 262144, kernel granted "
      f"{rx.getsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF)} bytes")

tx = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
payload = b"x" * SIZE
sent_ok = 0
for _ in range(N):                 # receiver is "busy": it reads nothing meanwhile
    sent_ok += tx.sendto(payload, rx.getsockname()) == SIZE
print(f"sender: {sent_ok} sendto() calls succeeded, no errors reported")

time.sleep(0.2)
rx.setblocking(False)
got = 0
try:
    while True:
        rx.recv(2048)
        got += 1
except BlockingIOError:
    pass
print(f"receiver: {got} datagrams delivered, {N - got} silently dropped "
      f"({(N - got) / N:.1%})")

Real output on Linux, followed by the kernel's UDP counters (grep Udp: /proc/net/snmp):

receive buffer: asked 262144, kernel granted 524288 bytes
sender: 10000 sendto() calls succeeded, no errors reported
receiver: 227 datagrams delivered, 9773 silently dropped (97.7%)

Udp: InDatagrams NoPorts InErrors OutDatagrams RcvbufErrors SndbufErrors InCsumErrors IgnoredMulti MemErrors
Udp: 263 0 9773 10036 9773 0 0 0 0

Three lessons are packed in here. First, every one of the 10,000 sendto() calls succeeded, because success only means "handed to the kernel". Second, RcvbufErrors counted all 9,773 drops; on Linux, nstat -az UdpRcvbufErrors reads the same counter, and ss -uamn shows per-socket drops in the d field of skmem. On macOS, netstat -s -p udp reports them as "dropped due to full socket buffers". Third, a 512 KiB buffer held only 227 datagrams of 1,200 bytes. That is about 2.3 KB each, because the kernel charges each datagram's full in-memory size (its truesize), not just its payload. Size UDP buffers in packets times overhead, not in payload bytes.

Deep dive: production failure modes

1. Small RPCs take 40 ms (or 200 ms) no matter what. Mechanism: Nagle plus delayed ACK on a write-write-read pattern, as measured above. Prove it: in a capture, the second small segment leaves exactly when the peer's ACK arrives, about 40 ms after the first. In strace -e trace=write,sendto, one logical message goes out in two syscalls. Fix: coalesce writes, or set TCP_NODELAY.

2. connect: Cannot assign requested address under load. Mechanism: ephemeral ports to one destination are all in TIME_WAIT or in use. Prove it: ss -tan state time-wait dst <ip> | wc -l approaches the size of ip_local_port_range. ss -s shows the totals. Fix: connection pooling and keep-alive, first and foremost. Then tcp_tw_reuse=1, a wider port range, or more destination IPs or ports. Do not use SO_LINGER with a zero timeout to dodge TIME_WAIT: it turns every close into a RST.

3. CLOSE_WAIT climbs forever. Mechanism: the peer closed and the kernel ACKed its FIN, but your application never called close(). This is a file descriptor leak, not a network problem. Prove it: ss -tanp state close-wait names the process. ls /proc/<pid>/fd | wc -l keeps rising. Fix: close sockets on every error path. Use context managers in Python, and defer conn.Close() in Go.

4. Throughput is far below the link speed on a long path. Mechanism: a window smaller than the BDP. Either rwnd is capped (a fixed SO_RCVBUF, a low tcp_rmem max, window scaling missing) or cwnd keeps collapsing because of loss. Prove it: ss -ti on the sender. If snd_wnd is small, or the rwnd_limited / sndbuf_limited time fields are large, a buffer is the cap. If cwnd is small with rising retrans, loss is the cap. Look at wscale in the SYN. Fix: raise tcp_rmem/tcp_wmem maxima, stop hard-coding socket buffers, find and fix the loss, or try BBR on the sender.

5. Latency spikes under load, while throughput stays fine. Mechanism: bufferbloat. Loss-based senders fill a deep queue at the bottleneck, as in the CUBIC run above. Prove it: ping (or ss -ti rtt against minrtt) while a bulk transfer runs. RTT jumps from its idle value to hundreds of milliseconds. Fix: AQM at the bottleneck (fq_codel, cake), or rate-limit just below the bottleneck so the queue forms where you control it. BBR on the senders helps their own traffic.

6. A pooled database connection hangs for 15 minutes after a quiet night. Mechanism: a NAT gateway or load balancer dropped the idle mapping. Common idle timeouts are 350 s for AWS NAT Gateway and NLB, and 4 minutes for an Azure load balancer by default; check current docs. The next query's segments vanish into nothing, and TCP retransmits for about 924 s before giving up. Prove it: ss -ti shows retrans and backoff rising on that socket, and the capture shows retransmissions with no reply. Fix: keepalive idle time below the middlebox timeout (for example 60 s); a pool max-idle-time below it too; TCP_USER_TIMEOUT to bound the hang.

7. A UDP service loses data and nobody logs an error. Mechanism: receive-buffer overflow, as shown above. Prove it: nstat -az UdpRcvbufErrors rises; per socket, look at the d field in ss -uamn. Fix: drain faster (more reader threads with SO_REUSEPORT, batching with recvmmsg), a bigger SO_RCVBUF (raise net.core.rmem_max first), or backpressure in the protocol itself.

Deep dive: 2026 context

QUIC moved congestion control into user space. HTTP/3 runs CUBIC or BBR inside the QUIC library, not in the kernel, so ss -ti cannot see it. Use the library's qlog output instead. The UDP-buffer lesson above applies in full. QUIC stacks routinely warn at startup when they cannot get a receive buffer of several megabytes, and the fix is to raise net.core.rmem_max on the host. Kernel UDP segmentation offload (GSO/GRO) is what makes QUIC's CPU cost competitive with TCP.

Kubernetes multiplies connection state. A sidecar proxy turns one logical connection into two or three TCP connections, each with its own TIME_WAIT. Node-level SNAT funnels many pods through one source IP, so the per-destination port budget from row 8 is shared by every pod on the node. A full conntrack table shows up as nf_conntrack: table full, dropping packet in dmesg. One famous UDP case: parallel A and AAAA DNS lookups sent from the same socket could race in conntrack, so one was dropped and glibc retried only after a 5-second timeout. Workarounds include options single-request-reopen in resolv.conf and a node-local DNS cache.

Cloud middleboxes have idle timers and port budgets. An AWS NAT gateway supports up to 55,000 simultaneous connections to each unique destination (IP, port, protocol) per NAT IP, and both it and the NLB drop idle flows after 350 s by default. GCP Cloud NAT allocates a fixed number of ports per VM (64 by default). These are TIME_WAIT and keepalive problems wearing a cloud badge.

Congestion control keeps evolving. Large content providers run BBR on their edges. Low-latency signalling (L4S, RFC 9330–9332) is in early deployment on some access networks: routers mark packets with ECN instead of building a queue, and senders back off gently. Kernel TCP remains the default for service-to-service traffic, so the ss -ti skills in this deep dive still pay off every week.

Deep dive: senior interview questions

Q1. A 1 Gbit/s link with 100 ms RTT gives one TCP connection only 5 Mbit/s. What is your first hypothesis, and how do you check it? A 64 KiB window: 65,535 bytes ÷ 0.1 s ≈ 5.2 Mbit/s. Window scaling is missing (an option stripped from the SYN by a middlebox, or disabled), or the application pinned a small SO_RCVBUF. Check wscale in the SYN and SYN-ACK, and snd_wnd in ss -ti on the sender. The BDP is 12.5 MB, so both windows need to reach that size.

Q2. What is the difference between rwnd and cwnd, and which one shows in a packet capture? rwnd is the receiver's free buffer space, advertised in every ACK's window field, so it is on the wire. cwnd is the sender's private estimate of what the network can hold, and it never appears in a packet. You infer it from bytes in flight, or read it from ss -ti on the sender. The sender may have min(rwnd, cwnd) bytes in flight. A zero rwnd points at the receiving application; a small cwnd points at the path.

Q3. CUBIC and BBR both reach full throughput through the same bottleneck. Why might users prefer one? CUBIC is loss-driven, so it keeps filling the bottleneck queue until a drop occurs. Every flow sharing that queue then sees the added delay; in the lab it was about 210 ms instead of under 1 ms. BBR estimates bottleneck bandwidth and minimum RTT and paces at that rate, keeping the queue nearly empty (7 ms in the same lab). The caveats: BBRv1 can be unfair to CUBIC and can retransmit heavily on shallow buffers. The router-side fix is AQM.

Q4. Fast retransmit is "three duplicate ACKs". Is that what Linux does? Not any more. Linux uses SACK with RACK-TLP (RFC 8985). A segment is declared lost when a later-sent segment has been acknowledged and a reordering window has passed, so recovery can start after one or two duplicate ACKs. The lab capture retransmitted after two. Tail loss probes send a probe segment after about two RTTs of silence, so that a loss at the end of a burst produces SACK information instead of waiting for a full RTO.

Q5. A client gets EADDRNOTAVAIL on connect() at about 500 new connections per second to one backend. Explain and fix. Each connection to the same destination IP and port needs a unique local port. The client closes first, so each used port sits in TIME_WAIT for 60 s. 28,232 ports ÷ 60 s ≈ 470 per second. Fix it with connection pooling and keep-alive, then tcp_tw_reuse=1 (safe for outgoing connections because of timestamps), a wider port range, or more backend addresses. Not with tcp_tw_recycle, which broke NAT and was removed in Linux 4.12.

Q6. The peer's machine loses power mid-connection. How long until your application finds out? It depends on whether you have data in flight. With unacknowledged data, the RTO backs off exponentially, and with tcp_retries2=15 the connection fails after about 924.6 s. With an idle connection and default keepalive, it takes 7200 s plus 9 × 75 s, over two hours. With no keepalive it is never. Bound it with TCP_USER_TIMEOUT, sensible keepalive timers and application-level deadlines.

Q7. Small request/response calls on a fast LAN take a steady 40 ms. What is happening? Nagle plus delayed ACK. The application writes a request in two pieces. Nagle holds the second piece until the first is acknowledged, and the receiver delays that ACK (40 ms minimum on Linux) because it has nothing to send until it has the whole request. Fix it by writing each message in one call, or by setting TCP_NODELAY.

Q8. A UDP metrics collector is missing data, but the senders report no errors. How do you diagnose it? UDP has no flow control or feedback, so sendto() succeeding proves nothing about delivery. On the receiver, check UdpRcvbufErrors (nstat) and the per-socket drop field in ss -uamn; on macOS, netstat -s -p udp. If they rise, the reader is too slow for its buffer. Remember the buffer is charged per datagram's in-memory size, not its payload. Raise rmem_max and SO_RCVBUF, add readers with SO_REUSEPORT, batch with recvmmsg, or add application-level acknowledgement and rate control.
