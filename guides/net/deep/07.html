Deep dive: DHCP and SLAAC as the machines they really are

The hotel desk is a good first picture. It hides three things you need once something breaks.

First, there is no single "desk." DHCP state lives in four places: the client's state machine and lease file, the access switch's snooping table, the relay on the gateway, and the server's lease database. Each one can be wrong independently. Second, anyone on the wire can play clerk. The protocol has no authentication, so the network has to impose trust from outside. Third, IPv6 doesn't have one desk at all. The host builds its configuration from two sources, Router Advertisements and DHCPv6, and the host decides how to combine them. Different operating systems decide differently.

The sections below go under the analogy: where the state lives, what the packets look like on a real VLAN, the timer arithmetic, how it fails, and where it shows up in 2026.

Deep dive: the real mental model — where the state lives

The client is a state machine with a lease file

RFC 2131 (section 4.4) defines the client as eight states: INIT, SELECTING, REQUESTING, BOUND, RENEWING, REBINDING, INIT-REBOOT and REBOOTING. DORA is just the INIT → SELECTING → REQUESTING → BOUND path. Two of the other paths matter far more in daily life.

INIT-REBOOT is what your laptop does when it rejoins a network it already has a lease for. It skips DISCOVER entirely. It broadcasts a REQUEST with option 50 (requested IP address) and no server identifier, which means "I believe 10.20.7.144 is still mine here." If the server agrees, it ACKs and the whole exchange is two packets. If the client moved to a different network, the server NAKs and the client falls back to INIT. That is why reconnecting to the office Wi-Fi feels instant while joining a new café network takes a little longer.

RENEWING and REBINDING are the T1 and T2 states from the module. In both, the address stays fully usable. The client is just trying to extend it.

The lease survives reboots because the client writes it to disk. Where depends on the client:

Client Lease state lives in
macOS configd / IPConfiguration /var/db/dhcpclient/leases/ (read it with ipconfig getpacket en0)
Linux systemd-networkd /run/systemd/netif/leases/<ifindex>
Linux ISC dhclient /var/lib/dhcp/dhclient.leases (path varies by distro)
Linux NetworkManager (internal client) /var/lib/NetworkManager/internal-*.lease

The server is a database keyed by client identity

A DHCP server is a small database with one table that matters: leases. Each row is keyed by client identity, which is option 61 (client identifier) when the client sends it, else the hardware address in chaddr. The row holds the address, the expiry time, a state (free, offered, active, expired, abandoned) and, in an HA pair, which peer owns it.

The server picks the scope from where the packet came from, not from who sent it. For a relayed packet, the deciding field is giaddr. For a packet that arrived directly, it is the receiving interface's subnet. Only after it has the scope does it look up the client.

Some servers check before offering. ISC dhcpd pings the candidate address and skips it if anyone answers; Windows Server has a "conflict detection attempts" setting that is off by default. These are vendor behaviours, not protocol rules.

The relay is a stateless rewriter

The relay (the gateway's SVI, with ip helper-address on Cisco or the equivalent elsewhere) holds no lease state at all. On each client broadcast it does four things:

  1. Sets giaddr to the address of the interface the broadcast arrived on — unless giaddr is already non-zero, because then an earlier relay already set it.
  2. Increments hops. Servers and relays drop packets past a configured hop limit (often 4 to 16).
  3. Optionally appends option 82 with its own circuit ID and remote ID.
  4. Unicasts the packet to each configured server, source port 67, destination port 67.

On the way back, the server sends to giaddr, port 67. The relay strips option 82 and delivers the reply on the client's link. If the client didn't set the broadcast flag, the relay sends it as a unicast to yiaddr, addressed at Layer 2 to chaddr. It can't ARP for the client, because the client doesn't own the address yet. It writes the MAC straight into its forwarding path from the packet.

The access switch keeps the only trustworthy table

DHCP has no authentication. RFC 3118 defined authentication in 2001, and practically nobody deployed it. So the network imposes trust from outside, at the access switch, with DHCP snooping (a vendor feature, implemented by every enterprise switch vendor under roughly the same name).

The switch keeps two pieces of state. One is a list of trusted ports, normally just the uplinks toward the relay. Server messages (OFFER, ACK, NAK) arriving on any other port are dropped. The other is a binding table: (VLAN, MAC) → (IP, port, lease expiry), filled by watching ACKs go past and emptied by RELEASE, by lease expiry, or by the port going down.

That binding table then feeds two more features. Dynamic ARP Inspection drops ARP packets whose sender IP/MAC pair doesn't match a binding on that port. IP Source Guard drops IP packets whose source address doesn't match. Together they turn "whoever shouts first wins" into "only addresses the real server handed out, only from the port they were handed out on."

IPv6: the host keeps the lists, and the RA writes most of them

An IPv6 host has no single lease. RFC 4861 gives it a set of lists, each with its own timers:

  • Prefix list — prefixes that are on-link (from the PIO's L flag), each with a valid lifetime.
  • Default router list — routers from RAs with a non-zero router lifetime.
  • Address list — each address carries a preferred lifetime (use it for new connections) and a valid lifetime (keep it at all). Between the two, the address is deprecated: existing connections keep working, new ones pick another source address.
  • DNS servers — from the RA's RDNSS option (RFC 8106), from DHCPv6, or both.
  • DHCPv6 state — a DUID, and per-IA (identity association) addresses or prefixes with their own T1/T2.

The RA flags M and O are hints to this machinery, not commands. RFC 4861 says hosts "may" act on them, and real systems disagree. Windows starts DHCPv6 when M=1. macOS does stateful DHCPv6 when M=1. Android has never implemented stateful DHCPv6 address assignment at all, so an M=1, A=0 network leaves an Android phone with only a link-local address. Design for the weakest host on the network, not for the RFC.

Read it line by line, because almost every field tells you something:

  • Lengths add up. 300 bytes of DHCP + 8 UDP + 20 IP = 328 on the IP line, plus 14 Ethernet = 342 for the frame. The DISCOVER is padded to exactly 300 bytes, the BOOTP-era minimum.
  • Flags [none]. The broadcast flag is clear. Modern macOS, Linux and Windows clients can accept a unicast before their address is configured, so they don't ask for broadcast replies.
  • So the OFFER is unicast: Ethernet destination is the client's MAC, IP destination is 10.20.7.144, an address the client doesn't hold yet. The relay took the MAC from chaddr and skipped ARP.
  • Source 10.20.6.1, TTL 255. The client never sees the real server's address in the IP header. It sees the relay, which originated this packet. The real server appears only in option 54, and that is where the client will send its renewal.
  • Gateway-IP 10.20.6.1 is giaddr, echoed back by the server. Its presence on the client's VLAN tells you instantly that a relay is involved.
  • Options 58 and 59 state T1 = 14,400 s and T2 = 25,200 s explicitly: exactly 0.5 and 0.875 of the 28,800 s lease. A server may set them to anything, and clients must honour them.
  • The parameter request list (55) is the client asking. Option 121 (classless static routes, RFC 3442) comes before option 3 for a reason: RFC 3442 says that if a client receives 121, it must ignore option 3. Option 108 is "IPv6-Only Preferred" (RFC 8925). Option 114 is the captive-portal URL (RFC 8910). tcpdump 4.99 prints several of these as Unknown, and the order and contents of this list are distinctive enough that NAC products use them to fingerprint the operating system.

The REQUEST and ACK that follow are the same shape. The REQUEST adds Requested-IP (50): 10.20.7.144 and Server-ID (54): 10.20.0.10; that server ID is the broadcast "I chose this one" that tells other servers to withdraw. The ACK repeats the OFFER's option set with message type 5.

  • Port 67 to port 67. Relay-to-server traffic uses the server port on both ends. A firewall rule that only permits "UDP 68 → 67" between relay and server silently breaks every relayed client. This is one of the commonest "DHCP is down for one building" causes.
  • hops 1, giaddr 10.20.6.1. The server selects the 10.20.6.0/23 scope from giaddr, not from the IP source. Here they happen to match. On many routers they don't, because the relay sources the packet from a loopback or the egress interface.
  • TTL 254: the relay originated the packet with 255 and one router hop sat in between.
  • Option 82 is 38 bytes: two sub-options, each 2 bytes of type/length plus a 25-byte and a 9-byte value. 4 + 25 + 9 = 38. The DHCP payload grew from 300 to 320 bytes. The client's own options ended at byte 280 and the rest was zero padding. The relay added 40 bytes (code, length and 38 bytes of sub-options), so the padding was no longer needed.

The format of the circuit ID is vendor-specific. Many switches encode VLAN, module and port as binary rather than readable text. The server treats it as an opaque string to match against policy.

This is the detail the hotel analogy erases. The renewal is an ordinary routed unicast from 10.20.7.144 to the server's own address, through the default gateway (Ethernet destination is the gateway MAC). It does not pass through the relay function. So:

  • ciaddr (Client-IP) is filled in, and options 50 and 54 are absent. RFC 2131 forbids them in RENEWING.
  • No option 82. If the server's policy depends on circuit ID (a per-port lease time, a "building B gets the guest scope" rule), a renewal arrives without that information. RFC 5107 added option 82 sub-option 11, server identifier override: the relay tells the server "put my address in option 54," so that renewals come back through the relay and get option 82 again.
  • TTL 63 on the ACK: the server sent 64 and one router forwarded it.

  • hlim 255 on both RS and RA. RFC 4861 requires hosts to drop any RA whose hop limit isn't 255. A router decrements hop limit, so 255 proves the RA was sent on this link. A rogue RA therefore can't come from the internet. It has to come from a device on your VLAN.
  • Flags [other stateful] is tcpdump's name for the O flag. M is clear. The PIO says onlink, auto: L=1, A=1. So the host forms its own address from 2001:db8:7:310::/64 and asks DHCPv6 only for "other" configuration.
  • Lifetimes. Valid 2,592,000 s (30 days) and preferred 604,800 s (7 days) are the RFC 4861 defaults, and they are a problem when a prefix changes (see failure modes). Router lifetime 1800 s is 3 × the default 600 s maximum RA interval.
  • RDNSS is already here. This RA carries the DNS server itself. A host that understands RDNSS (Android, macOS, iOS, Windows 10 1703+, Linux with systemd-resolved or NetworkManager) has DNS before DHCPv6 says a word. The DHCPv6 exchange that follows is for hosts that don't, and for the search list.
  • The DHCPv6 Information-Request goes from link-local to ff02::1:2 (all DHCP relay agents and servers) with hop limit 1. Note what's missing from the reply: no address, no prefix length, no default router. DHCPv6 has no router option. The default gateway in IPv6 always comes from an RA. Option 32 (information refresh time, 86,400 s) tells the client when to ask again.
  • The DUID (hwaddr/time type 1, DUID-LLT) is the DHCPv6 client identity. It's generated once and stored. It is not the MAC, even though it contains one, which is why DHCPv6 reservations keyed on MAC often don't work as people expect.

Deep dive: by the numbers

Lease timer arithmetic

RFC 2131 section 4.4.5 says how hard the client tries before giving up. In RENEWING it waits half the remaining time until T2 before retrying, and in REBINDING half the remaining time until expiry. Neither wait goes below 60 seconds. Section 4.1 sets the DISCOVER backoff: 4 seconds, doubling to a 64-second cap, each with ±1 s of jitter.

"""DHCPv4 client timers per RFC 2131 sections 4.1 and 4.4.5 (no randomization, for clarity)."""

def hms(s: float) -> str:
    s = round(s)
    return f"{s // 3600:02d}:{s % 3600 // 60:02d}:{s % 60:02d}"

def retransmits(start: float, deadline: float, floor: float = 60.0) -> list[float]:
    """Wait half the remaining time to the deadline, never less than `floor` seconds."""
    t, out = start, []
    while True:
        wait = max((deadline - t) / 2, floor)
        if t + wait >= deadline:
            return out
        t += wait
        out.append(t)

lease = 8 * 3600
t1, t2 = 0.5 * lease, 0.875 * lease      # defaults when the server omits options 58/59
print(f"lease {hms(lease)}  T1 {hms(t1)}  T2 {hms(t2)}")

renew = [t1] + retransmits(t1, t2)
print(f"RENEWING  unicast REQUESTs at: {', '.join(hms(t) for t in renew)}  ({len(renew)} sent)")
rebind = [t2] + retransmits(t2, lease)
print(f"REBINDING broadcast REQUESTs at: {', '.join(hms(t) for t in rebind)}  ({len(rebind)} sent)")

# INIT state: DISCOVER retransmission starts at 4 s and doubles to a 64 s cap (each +/-1 s jitter).
waits, w = [], 4
while sum(waits) < 120:
    waits.append(w)
    w = min(w * 2, 64)
print("DISCOVER waits (s):", waits, "-> cumulative", [sum(waits[:i + 1]) for i in range(len(waits))])

Three operational conclusions fall out of these numbers.

Your outage budget is T2 − T1 plus the lease − T2. With an 8-hour lease, a dead DHCP server is invisible to existing clients for three hours (RENEWING) and noticeable only to new arrivals. Clients begin dropping addresses at hour 8. With a 1-hour guest lease, you have 60 minutes. That's why short leases make DHCP server HA mandatory, not optional.

Configuration changes propagate at T1, not instantly. Change the DNS server in a scope and existing clients learn about it at their next renewal: up to half a lease later. The professional move is to drop the lease time a full old-lease-length ahead of a planned change, make the change, then raise it again. There is a FORCERENEW message (RFC 3203), but it requires authentication that almost nothing implements.

A dead network looks slow before it looks dead. A client that gets no OFFER retries at 4, 12, 28 and 60 seconds. Most operating systems give up on the first round after somewhere between 10 and 60 seconds and self-assign a 169.254.0.0/16 address (RFC 3927). They keep retrying DHCP in the background. The exact timing varies by OS.

The DAD second is easy to miss. Every new IPv6 address waits about a second before it's usable, unless the host uses Optimistic DAD (RFC 4429). It's one reason IPv6 sometimes lags IPv4 by a beat right after joining a network, and Happy Eyeballs hides it.

Interface identifiers and temporary addresses

The module named EUI-64 and privacy extensions. In 2026 there are really three kinds of interface identifier, and a laptop typically uses two of them at once:

"""Three ways to pick the low 64 bits of a SLAAC address, plus temporary-address lifetime math."""
import hashlib
import ipaddress
import secrets

PREFIX = ipaddress.IPv6Network("2001:db8:7:310::/64")
MAC = "3a:1f:9c:52:07:e4"

def eui64(mac: str) -> int:                      # RFC 4291 appendix A
    b = bytearray(bytes.fromhex(mac.replace(":", "")))
    b[0] ^= 0x02                                  # flip the universal/local bit
    return int.from_bytes(b[:3] + b"\xff\xfe" + b[3:])

def stable(prefix, iface: str, net_id: bytes, dad_counter: int, key: bytes) -> int:  # RFC 7217 shape
    h = hashlib.sha256(prefix.network_address.packed[:8] + iface.encode() + net_id
                       + dad_counter.to_bytes(1) + key).digest()
    return int.from_bytes(h[:8])

def addr(iid: int) -> ipaddress.IPv6Address:
    return PREFIX[iid]

key = bytes(16)                                   # per-host secret; fixed here so output is repeatable
print("EUI-64        ", addr(eui64(MAC)))
print("RFC 7217 home ", addr(stable(PREFIX, "en0", b"corp-wifi", 0, key)))
other = ipaddress.IPv6Network("2001:db8:99:1::/64")
print("RFC 7217 cafe ", other[stable(other, "en0", b"cafe-wifi", 0, key)], "(unrelated low 64 bits)")
print("temporary     ", addr(int.from_bytes(secrets.token_bytes(8))), "(random; changes every run)")

# RFC 8981 lifetimes. Defaults: preferred 1 day, valid 2 days. Many OSes still use valid = 7 days.
pref = 86400
for valid in (2 * 86400, 7 * 86400):
    for desync in (0, 0.4 * pref):                # DESYNC_FACTOR is random in [0, 0.4 * pref]
        period = pref - desync                    # a new temporary address roughly this often
        alive = int(valid // period)             # addresses still valid (deprecated + 1 preferred)
        print(f"valid {valid // 86400}d desync {desync / 3600:4.1f}h: new temp every "
              f"{period / 3600:4.1f}h, up to {alive + 1} temp addresses on the interface")

valid 2d desync  0.0h: new temp every 24.0h, up to 3 temp addresses on the interface
valid 2d desync  9.6h: new temp every 14.4h, up to 4 temp addresses on the interface
valid 7d desync  0.0h: new temp every 24.0h, up to 8 temp addresses on the interface

  • EUI-64 puts the MAC in the address. Notice 381f where the MAC starts 3a1f: flipping bit 0x02 turned the locally administered 3a into 38. RFC 8064 (2017) recommends against EUI-64 as the default.
  • Stable-privacy (RFC 7217) hashes the prefix, the interface, a network ID and a host secret. The address is stable on one network, so firewall rules and logs still work, but unrelated across networks, so it can't be used to track you. The real PRF and inputs differ by OS; this is the shape, not Linux's exact function. macOS labels this address secured in ifconfig; Linux uses it when addr_gen_mode is 2 or 3.
  • Temporary (RFC 8981, which replaced RFC 4941 in 2021) is random and short-lived. It's preferred for outgoing connections (RFC 6724 source-address rule 7).

The lifetime table explains a puzzle every IPv6 user hits: why does ifconfig show five or more global addresses? Each temporary address stays valid (still usable by old connections) long after it stops being preferred. With the RFC 8981 defaults you carry up to three or four at once. With a 7-day valid lifetime — still the default on macOS (sysctl net.inet6.ip6.temppvltime is 604800) and in the Linux kernel's temp_valid_lft (604800) — you can carry eight to twelve. Each one is a Neighbor Cache entry on the router, which matters on large Wi-Fi networks.

Deep dive: production failure modes

A rogue DHCP server

Symptom. Some clients on one VLAN get 192.168.0.x or 192.168.1.x with a gateway nobody recognises. They have "internet" in the sense that the rogue box NATs them somewhere, or they have nothing at all. It's random which clients are affected, because each client takes whichever OFFER arrives first.

Mechanism. Someone plugged a consumer router into a wall port LAN-side first. Its DHCP server answers every DISCOVER on the VLAN. It's on the same segment, so it usually beats the relayed real server by a millisecond or two.

Prove it.

# Run on your Mac — every OFFER/ACK, with the server that sent it
sudo tcpdump -nn -v -i en0 'udp src port 67' | grep -E 'Server-ID|Your-IP|Default-Gateway'
# Which server gave *you* your lease
ipconfig getpacket en0 | grep -E 'server_identifier|router|yiaddr'
# Linux: same tcpdump; or ask every server on the segment to answer (nmap is not preinstalled)
sudo nmap --script broadcast-dhcp-discover -e eth0

Two different Server-ID values on one VLAN is the proof. The source MAC of the rogue OFFER, looked up in the switch's MAC table, gives you the port.

Fix. DHCP snooping, with only the uplinks trusted. Here is the logic of the switch from the mental-model section, as a toy:

"""A toy access switch running DHCP snooping + Dynamic ARP Inspection.

State: a set of trusted ports and a binding table {(vlan, mac): (ip, port, expires)}.
"""
SERVER_MSGS = {"OFFER", "ACK", "NAK"}
trusted = {"Gi1/0/48"}                       # uplink toward the relay / real server
bindings: dict[tuple[int, str], tuple[str, str, int]] = {}

def dhcp(now, port, vlan, msg, mac, ip=None, lease=0):
    if msg in SERVER_MSGS and port not in trusted:
        return f"DROP  {msg} from untrusted {port} (rogue server)"
    if msg == "ACK":
        bindings[(vlan, mac)] = (ip, client_port[mac], now + lease)
        return f"BIND  vlan {vlan} {mac} -> {ip} on {client_port[mac]} for {lease}s"
    if msg == "RELEASE":
        bindings.pop((vlan, mac), None)
        return f"UNBIND vlan {vlan} {mac}"
    return f"FWD   {msg} from {port}"

def arp(now, port, vlan, mac, claimed_ip):
    b = bindings.get((vlan, mac))
    ok = b is not None and b[0] == claimed_ip and b[1] == port and b[2] > now
    return f"{'FWD ' if ok else 'DROP'}  ARP on {port}: {claimed_ip} is-at {mac}" + ("" if ok else "  (no matching binding)")

client_port = {"3a:1f:9c:52:07:e4": "Gi1/0/7"}
events = [
    dhcp(0, "Gi1/0/7", 310, "DISCOVER", "3a:1f:9c:52:07:e4"),
    dhcp(0, "Gi1/0/19", 310, "OFFER", "3a:1f:9c:52:07:e4", "192.168.0.50"),   # home router plugged in
    dhcp(0, "Gi1/0/48", 310, "OFFER", "3a:1f:9c:52:07:e4", "10.20.7.144"),
    dhcp(0, "Gi1/0/7", 310, "REQUEST", "3a:1f:9c:52:07:e4"),
    dhcp(0, "Gi1/0/48", 310, "ACK", "3a:1f:9c:52:07:e4", "10.20.7.144", 28800),
    arp(5, "Gi1/0/7", 310, "3a:1f:9c:52:07:e4", "10.20.7.144"),
    arp(6, "Gi1/0/19", 310, "b2:44:10:9e:3c:01", "10.20.6.1"),               # gateway spoof attempt
    arp(28801, "Gi1/0/7", 310, "3a:1f:9c:52:07:e4", "10.20.7.144"),           # lease lapsed, no renew seen
]
print("\n".join(events))
print("binding table:", bindings)

Real output:

FWD   DISCOVER from Gi1/0/7
DROP  OFFER from untrusted Gi1/0/19 (rogue server)
FWD   OFFER from Gi1/0/48
FWD   REQUEST from Gi1/0/7
BIND  vlan 310 3a:1f:9c:52:07:e4 -> 10.20.7.144 on Gi1/0/7 for 28800s
FWD   ARP on Gi1/0/7: 10.20.7.144 is-at 3a:1f:9c:52:07:e4
DROP  ARP on Gi1/0/19: 10.20.6.1 is-at b2:44:10:9e:3c:01  (no matching binding)
DROP  ARP on Gi1/0/7: 10.20.7.144 is-at 3a:1f:9c:52:07:e4  (no matching binding)
binding table: {(310, '3a:1f:9c:52:07:e4'): ('10.20.7.144', 'Gi1/0/7', 28800)}

The last line is a failure mode of the fix. If a binding expires, perhaps because the renewal was unicast along a path the switch didn't see, or the switch rebooted and lost its table, DAI starts dropping a legitimate host's ARP. Production switches mitigate this by saving the binding table to flash or a remote file, and by watching renewals that cross the access switch. When a host "loses the network at exactly the lease time," check DAI drop counters before you check the server.

A newer variant uses the rogue server differently. TunnelVision (CVE-2024-3661, disclosed 2024) is a rogue DHCP server that hands out option 121 classless static routes more specific than the VPN's routes, such as 0.0.0.0/1 and 128.0.0.0/1 via the attacker. Many VPN clients install their tunnel as a default route, so the longer prefixes win and traffic leaves outside the tunnel. Android was unaffected because it doesn't implement option 121. The defence is the same snooping on the network side. On the client side it's a VPN that enforces its routing with firewall rules or a separate network namespace, not just with the routing table.

Snooping is on and every client gets 169.254

Symptom. Someone enables DHCP snooping on access switches, and every relayed client stops getting addresses. The server sees nothing.

Mechanism. Several vendors' snooping inserts option 82 by default when it forwards a DISCOVER, but an access switch is a Layer-2 device, so it leaves giaddr at zero. The packet reaches the Layer-3 relay carrying option 82 with giaddr = 0. RFC 3046 section 2.1 tells a relay that receives exactly that on an untrusted circuit to discard it, because it looks like a client forging relay information. The two features are each doing the right thing.

Prove it. A capture on the client VLAN shows DISCOVERs leaving the access switch's uplink with option 82 present and Gateway-IP absent. The relay's DHCP statistics show a rising count of dropped packets with relay information (exact counter names are vendor-specific).

Fix. Either stop the access switch inserting option 82, or tell the relay to trust option 82 from that interface. On Cisco those are no ip dhcp snooping information option and ip dhcp relay information trusted respectively (vendor commands; other vendors have equivalents).

The server answers but the client never hears it

Symptom. Server logs show DISCOVER → OFFER for the client's MAC, repeatedly. The client sits in INIT and ends up on 169.254.

Mechanism. The server sends the OFFER to giaddr. If the server has no route back to the client's subnet, or a firewall between them passes 68→67 but not 67→67, or the relay sources from a loopback that isn't advertised, the OFFER dies on the return path. The DISCOVER direction proves nothing about the return direction.

Prove it. Capture on the server: you see OFFERs leaving toward giaddr. Capture on the relay's server-facing side: they never arrive. traceroute -n <giaddr> from the server usually shows where it stops.

Fix. Route giaddr's subnet back to the server. Permit UDP 67↔︎67 between relays and servers in both directions.

A rogue Router Advertisement

Symptom. IPv6 is "flaky" for some hosts. Connections to dual-stacked sites stall for a few hundred milliseconds and then succeed over IPv4. A few hosts show an unexpected prefix or a second default router.

Mechanism. A device on the VLAN sends RAs: a Windows box with Internet Connection Sharing, a VM bridged with a misconfigured router image, or an attacker. Hosts install it as a default router. Traffic sent to it goes nowhere. Happy Eyeballs (RFC 8305) masks most of the damage by racing IPv4, which is exactly why the problem lingers for months.

Prove it.

# Run on your Mac: the default routers and prefixes you've learned, and who sent them
ndp -rn
ndp -pn
# Every RA on the link, with its source
sudo tcpdump -nn -v -e -i en0 'icmp6 and ip6[40] == 134'
# Linux equivalents
ip -6 route show default
sudo rdisc6 wlan0          # from the ndisc6 package: send an RS and print every RA

More than one router in ndp -rn when you expected one, or an RA from a MAC that isn't your gateway's, is the proof.

Fix. RA Guard (RFC 6105) on access ports: drop RAs except from the router-facing ports. Implementations must look past IPv6 extension headers to find the ICMPv6 type, because the classic evasion hides the RA behind a fragment header; RFC 7112 now requires the full header chain in the first fragment, and RFC 7113 gives RA Guard implementation advice. On the remediation side, an RA from the same link-local source with router lifetime 0 tells hosts to drop that router immediately.

Renumbering leaves hosts with a dead prefix

Symptom. After an ISP changes your home or branch prefix, IPv6 breaks for hours or days. Hosts still have addresses in the old prefix, prefer them, and their packets go nowhere.

Mechanism. The old RA said valid 30 days, preferred 7 days. When the CPE router reboots with a new delegated prefix, it often just stops advertising the old one. It doesn't send a final RA with the old prefix's preferred lifetime set to 0. RFC 4862's "two-hour rule" adds to this: an unauthenticated RA can't cut an existing prefix's valid lifetime below 2 hours, to stop an attacker from wiping your addresses.

Fix. RFC 9096 (2021) tells CE routers to advertise much shorter lifetimes (it caps valid at 5,400 s and preferred at 2,700 s) and to deprecate stale prefixes explicitly. In an enterprise, keep prefixes static and plan renumbering by lowering lifetimes in advance, just as you'd lower a DNS TTL.

Deep dive: 2026 context

Cloud VPCs. In AWS, Azure and GCP, a NIC's private address is assigned by the cloud's API when the NIC is created. DHCP inside the guest is only a delivery channel: the hypervisor answers the guest's DISCOVER with the address the control plane already chose. There is no broadcast domain to share, so your own DHCP server can't hand out VPC addresses and a rogue one can't hijack neighbours. Azure answers DHCP (and DNS) from the virtual IP 168.63.129.16. GCP gives instances a /32 netmask and a route to the gateway, so every packet, even to a "neighbour," goes through the virtual router. What you control is the option set: AWS calls it a DHCP options set (DNS servers, domain name, NTP). Changing it reaches running instances only at their next renewal, which is the T1 point from above, with a cloud name on it.

Kubernetes. Pods don't use DHCP. The CNI plugin's IPAM assigns addresses: host-local ranges carved from the node's pod CIDR, or cloud-native IPAM that attaches secondary addresses or prefixes to the node's NIC (AWS VPC CNI, Azure CNI). The node itself still gets its address by DHCP from the cloud. There is a CNI dhcp IPAM plugin, used with Multus when pods must sit on a real Layer-2 network; then you're back to DHCP leases, now held on the pod's behalf by a daemon on the node.

IPv6-mostly networks. Option 108 (RFC 8925) lets a client say "I can live without IPv4." The server answers with option 108 and a wait time and offers no address. The client then runs IPv6-only, reaching IPv4 destinations through NAT64 (it learns the NAT64 prefix from the PREF64 RA option, RFC 8781, or DNS64). Legacy devices that don't send 108 still get IPv4. That's how large networks are draining their IPv4 scopes in 2026 without a flag day. Look for 108 in your Mac's parameter request list with ipconfig getpacket en0.

One prefix per device. RFC 9663 (2024) describes giving each client its own /64 by DHCPv6 prefix delegation, instead of many addresses out of a shared /64. The host can then hand addresses to its containers, VMs or tethered devices without Neighbor Discovery tricks, and the router keeps one route per device instead of a growing neighbour cache. Support is still uneven across client OSes.

MAC randomization. iOS, Android, Windows and macOS all use private Wi-Fi addresses by default, typically one per SSID, and some modes rotate them. Every new MAC is a new client identity to the DHCP server: a new lease, a broken reservation, a new row in the snooping table. Guest networks with long leases fill up faster than the visitor count suggests. Network access control that tracks "this MAC is this device" breaks. Identity has to come from 802.1X or the application layer instead.

Zero trust. DHCP gives a device an address. It doesn't establish who the device is. In a zero-trust design, the address is just a locator. Authorization comes from device certificates and user identity at each request. DHCP data still earns its keep as telemetry: the snooping binding table and the server's lease log answer "which device had 10.20.7.144 at 14:32," and option 55 fingerprints feed device classification.

Deep dive: senior interview questions

Q1. A client's T1 renewal never passes through the relay. What breaks because of that, and how is it fixed?

The renewal is a routed unicast to the address in option 54, so the relay doesn't touch it and option 82 isn't added. Any server policy keyed on circuit ID or remote ID — per-port leases, location-based scopes, subscriber accounting — sees renewals without that context. RFC 5107's server-identifier-override sub-option makes the relay put its own address in option 54, so renewals go back through the relay and pick up option 82 again.

Q2. Why does the server choose the scope from giaddr rather than from the IP source address of the relayed packet?

Because the source address names the relay's outgoing interface, which can be a loopback or an uplink, not the client's link. giaddr explicitly names the interface the broadcast arrived on, which is the subnet the client needs an address in. When giaddr can't be an address in the client subnet (unnumbered interfaces, VRFs), the relay adds option 82 sub-option 5, link selection (RFC 3527), to name the subnet separately.

Q3. What exactly does DHCP snooping store, and why do other security features depend on it?

A binding per (VLAN, MAC): the IP, the port and the lease expiry, built only from server messages that arrived on trusted ports. It's the only place on the network where an IP-to-MAC-to-port mapping is backed by the authoritative server rather than by whatever a host claims. Dynamic ARP Inspection uses it to reject forged ARP, and IP Source Guard uses it to reject spoofed source addresses. Without snooping, both have nothing to check against.

Q4. An RA arrives with M=1 and A=1. What does the host end up with, and where does its default gateway come from?

Potentially two global addresses per prefix: one from SLAAC (because A=1) and one from DHCPv6 (because M=1), if the OS honours M. The default gateway comes only from the RA's router lifetime and source address. DHCPv6 has no router option, and it doesn't carry a prefix length either: on-link prefixes come from the RA's PIO with L=1. An RA with router lifetime 0 means "I am not a default router," even if it carries prefixes.

Q5. Why must an RA have a hop limit of 255?

Every router decrements hop limit, so a packet that arrives with 255 can't have been forwarded. RFC 4861 makes hosts drop RAs (and other ND messages) without it. That limits RA spoofing to devices on the same link, which is exactly the scope RA Guard defends.

Q6. Your temporary IPv6 address gets deprecated in the middle of a long SSH session. What happens?

Nothing visible. Deprecated means "don't pick this for new connections," not "stop using it." The session keeps its source address until the address's valid lifetime ends, which with common OS defaults is days later. New connections pick the newer preferred temporary address. Only when the valid lifetime expires does the address disappear and the session break.

Q7. Why can't an RA shorten a prefix's valid lifetime below two hours, and what problem does that cause?

RFC 4862 section 5.5.3 ignores an unauthenticated RA that would cut a remaining valid lifetime below 2 hours, so an on-link attacker can't wipe everyone's addresses with one packet. The cost is slow cleanup after a legitimate renumbering: hosts keep a dead prefix's addresses for at least 2 hours, or for the full advertised lifetime if the router simply stops advertising the prefix. That's why RFC 9096 asks CE routers to use short lifetimes in the first place.

Q8. Design DHCP for a 20,000-person campus with 200 VLANs. What do you decide, and what do you monitor?

Two servers in an HA or failover pair, central, with relays on every SVI pointing at both. Lease length per VLAN class: hours for guest and conference Wi-Fi, a day or more for wired desks. Snooping, DAI and IP Source Guard on every access switch, uplinks trusted, binding tables persisted. Option 82 only where policy needs it, with relay trust configured so the two features don't fight. IPv6 with SLAAC plus RDNSS for Android's sake, stateless DHCPv6 for search lists, RA Guard on access ports. Monitor scope utilisation per VLAN (alert near 80%), NAK and DECLINE rates, DAI drop counters, and the count of distinct server identifiers seen per VLAN. That last one should always be one.
