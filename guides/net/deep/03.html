Deep dive: inside the switch

The module gave you a switch as a learning table and a rule: learn the source, look up the destination, flood if unknown. That is correct, and it is the right place to start. But it hides the machine.

A real switch is a pipeline etched into silicon. A frame passes through a fixed series of stages, each with a few nanoseconds to do its job. The MAC table is a hash table with buckets that can fill up early. Frames wait in a packet buffer that every port shares, and that buffer is small — tens of microseconds of traffic, not seconds. When several ports talk to one port at once, the buffer fills in microseconds and the switch drops frames while your monitoring graph says the link is nearly idle. And when two cables are bundled into one logical link, a hash function decides which cable each flow uses, forever.

Those four things — the table, the timers, the buffer and the hash — are where switching problems in production actually live. This deep dive goes through each of them.

Deep dive: the real mental model — a pipeline with a shared buffer

Follow one frame through the diagram.

Ingress MAC and PHY. The port turns symbols on the wire back into bytes, strips the preamble and SFD, and runs the CRC-32 over the frame as it streams in. The CRC result is only known once the last byte has arrived. Keep that fact in mind; it decides the store-and-forward versus cut-through question below.

Parser. The parser pulls fields out of the first bytes of the frame: destination and source MAC, any 802.1Q tag, the EtherType, and — on most modern switches — the IP and TCP/UDP headers too, because ACLs and hashing need them. The parser reads a fixed window of bytes. Anything beyond that window is invisible to the rest of the pipeline. Module 04's deep dive shows how IPv6 extension headers fall foul of exactly this limit.

L2 lookup and learning. Two lookups happen against the same table, keyed by (VLAN, MAC), not by MAC alone. The key includes the VLAN because the same MAC may legitimately appear in two VLANs on two different ports.

  • The source lookup is the learning step. A miss means a new address: insert (VLAN, src MAC) → ingress port. A hit on a different port means the station moved, or something is wrong: update the port. A hit on the same port just refreshes the entry's age.
  • The destination lookup is the forwarding step. A hit gives one egress port. A miss gives the VLAN's flood list: every port in that VLAN except the one the frame came in on.

ACL / TCAM. Policies that match on masks — "drop TCP to port 23 from this /24" — live in TCAM, a ternary memory that compares the key against every entry in parallel. TCAM is fast, power-hungry and small, so it holds thousands of entries, not millions. The big exact-match MAC table is usually not TCAM. Despite the name "CAM table", most switch ASICs store MACs in hashed SRAM, with a small true CAM or overflow area for collisions.

Traffic manager. This is where the frame waits. The switch writes the frame into a shared packet buffer and puts a pointer to it on a queue for the chosen egress port (one queue per traffic class, usually eight). A scheduler drains each port's queues at that port's line rate. If the destination is a flood, the frame is written once and the pointer is queued on many ports.

Egress. On the way out, the egress pipeline adds or strips VLAN tags, applies egress ACLs and recomputes the FCS if the frame changed. Then the MAC serialises it onto the wire.

The MAC table is a hash table, and it behaves like one

A switch vendor's datasheet might promise "64K MAC addresses". What the chip has is a hash table: the hash of (VLAN, MAC) picks a bucket, and each bucket holds a few entries (often four or eight; it varies by chip). When every slot in a bucket is full, a new address that hashes there cannot be learned, even if the table as a whole is half empty. Designs use tricks — several hash functions, cuckoo-style moves — to push usable capacity close to the nominal number, but the exact behaviour varies by chip and is rarely documented in detail.

What happens to a frame from an address the switch failed to learn? It is still forwarded. But replies to that address become unknown unicast and get flooded. One unlearnable MAC turns into a steady trickle of flooded traffic. That is the same end state as the CAM overflow attack in the module, reached by accident.

Ageing is a timer per entry, and it disagrees with ARP

Every entry carries a timestamp of when the switch last saw that MAC as a source. A background sweep deletes entries older than the ageing time. IEEE 802.1Q's default is 300 seconds, with an allowed range of 10 to 1,000,000 seconds. Most vendors and the Linux bridge use 300 s by default.

Notice what refreshes an entry: frames from the station. Frames to the station do not count. A host that only receives — a syslog collector, a backup target receiving a UDP stream, a server behind an asymmetric path — will age out of the table while traffic is still flowing to it. From then on, every frame sent to it is flooded. The lab output below shows this happening.

Topology changes shorten ageing on purpose. Under classic STP, a topology change notification makes switches use the forward delay (15 s by default) as their ageing time for a while, so stale entries vanish quickly. RSTP goes further and flushes entries learned on affected ports immediately. Both trade a burst of flooding for faster recovery.

Store-and-forward versus cut-through

A store-and-forward switch receives the whole frame, checks the FCS, and only then starts sending it out. Corrupt frames die at the first switch. The cost is that every hop adds one full frame's serialisation time before the first bit leaves.

A cut-through switch starts transmitting once it has read enough header to decide the egress port. The destination MAC is in the first 6 bytes, but in practice the switch waits for the L3/L4 headers too, so ACLs and hashing work. It can begin sending before the tail of the frame has even arrived.

That saves real time. Serialising a 1,518-byte frame takes 12.1 µs at 1 Gb/s, 1.2 µs at 10 Gb/s and 0.12 µs at 100 Gb/s. A 9,018-byte jumbo frame takes 7.2 µs at 10 Gb/s. Cut-through switches commonly forward in a few hundred nanoseconds whatever the frame size (exact figures are vendor-specific).

Three catches make cut-through less magic than the marketing:

  1. It cannot drop a bad frame. By the time the CRC check fails, the head of the frame is already on the next link. The switch can only end the frame with a deliberately wrong FCS — usually called CRC stomping — so the next store-and-forward device drops it. The error counter then increments on a link that is perfectly healthy. You have to trace the error back to the hop where it first appeared.
  2. It only works when the egress port is idle. If anything is queued for that port, the frame waits in the buffer like any other. Under load, a cut-through switch is a store-and-forward switch.
  3. It cannot go from slow to fast. A frame arriving at 10 Gb/s cannot be streamed out at 100 Gb/s; the egress would run out of bytes mid-frame. Switches fall back to store-and-forward for slow-to-fast speed changes.

At 100 Gb/s and above, the serialisation saving is tens of nanoseconds per hop, so the choice matters less than it did at 1 and 10 Gb/s. It still matters for trading networks and some HPC fabrics.

The buffer is shared, small, and policed by a formula

A frame waits in the buffer only while its egress port is busy. The buffer exists to absorb short collisions in time, when two inputs want the same output at once.

The sizes are smaller than most engineers guess. Data-centre switches built on merchant silicon typically carry a few tens of megabytes of on-chip buffer, shared by every port on a chip that moves terabits per second. Take 32 MB on a 12.8 Tb/s switch: that is 32 × 8 / 12,800,000 seconds, or 20 µs of the switch's full throughput. Spread evenly over 128 ports of 100 Gb/s, each port gets 250 KB, again about 20 µs of its own line rate. "Deep-buffer" routers exist, with gigabytes of external memory, and they cost and consume accordingly.

Because the buffer is shared, the switch needs a rule for how much one queue may take. The common answer is a dynamic threshold: a queue may grow up to α × (free buffer), where α is a configurable factor such as 1 or 2. When the buffer is mostly empty, one congested port can borrow a large share. As the buffer fills, every queue's limit shrinks together. It stops one hot port from starving all the others. It also means a queue's real limit depends on what every other port is doing at that microsecond.

Microbursts: congestion that your graphs cannot see

Put the pieces together. Eight servers reply to one request at the same moment (a scatter-gather query, a distributed cache read, a storage stripe). Each sends 256 KB at 25 Gb/s toward one 25 Gb/s port. The port can drain 25 Gb/s; 200 Gb/s is arriving. The queue grows at the difference, 175 Gb/s, which is about 21.9 KB every microsecond. With a 1 MB share of the buffer, the queue is full in about 48 µs. Everything after that is dropped.

The simulation below runs that scenario in 1-µs steps:

"""Microburst on one 25 Gb/s egress port: 8 senders answer one request at once.

Time advances in 1-microsecond steps. Each sender bursts 256 KB at line rate.
The egress queue drains at 25 Gb/s and may hold at most BUFFER bytes.
"""
LINE = 25e9 / 8          # bytes per second on every port
STEP = 1e-6              # 1 microsecond
SENDERS = 8
BURST = 256 * 1024       # bytes each sender sends
BUFFER = 1024 * 1024     # bytes this queue may use (its shared-buffer share)

per_step = LINE * STEP   # 3125 bytes per port per microsecond
left = [BURST] * SENDERS
queue = dropped = sent = 0.0
peak = 0.0
t = 0
first_drop = None
while any(left) or queue > 0:
    arriving = 0.0
    for i in range(SENDERS):
        chunk = min(left[i], per_step)
        left[i] -= chunk
        arriving += chunk
    room = BUFFER - queue
    accepted = min(arriving, room)
    if arriving > room and first_drop is None:
        first_drop = t
    dropped += arriving - accepted
    queue += accepted
    out = min(queue, per_step)
    queue -= out
    sent += out
    peak = max(peak, queue)
    t += 1

total = SENDERS * BURST
print(f"offered          : {SENDERS} x {BURST//1024} KB = {total/1e6:.2f} MB")
print(f"burst duration   : {BURST/per_step:.0f} us at line rate per sender")
print(f"queue fill rate  : {(SENDERS-1)*per_step:.0f} B/us ({(SENDERS-1)*25} Gb/s excess)")
print(f"first drop at    : {first_drop} us")
print(f"peak queue       : {peak/1e6:.2f} MB")
print(f"dropped          : {dropped/1e6:.2f} MB ({100*dropped/total:.1f}% of offered)")
print(f"drained after    : {t} us")
busy = sent / LINE                       # seconds the port was busy
print(f"1-second average : {100*busy:.3f}% utilisation  <- what a 1 s counter shows")
print(f"1-ms window peak : {100*min(1.0, sent/(LINE*1e-3)):.0f}% utilisation")

Read the last two lines twice. More than a third of the burst was dropped. The port's one-second average utilisation was 0.04 %. Even a one-millisecond window shows only 42 %. A monitoring system polling interface counters every 30 or 60 seconds will never see this. It will see drop counters creeping up on a link that looks empty.

The cost lands on TCP. A dropped segment at the tail of a burst often has no later segments behind it to trigger fast retransmit, so it waits for a retransmission timeout. Linux's minimum RTO is 200 ms. In a data centre with a 100 µs round trip, one lost segment can make a request 2,000 times slower than its RTT. This is the TCP incast problem. It is why data-centre operators care about ECN marking thresholds, buffer tuning and congestion control (DCTCP and its descendants) far more than about link speed.

Link aggregation: a hash decides, per flow, forever

A LAG (IEEE 802.1AX, which used to be 802.3ad) bundles several physical links into one logical port. LACP keeps the bundle honest. Each side sends LACPDUs to the slow-protocols multicast address 01:80:c2:00:00:02 (EtherType 0x8809), every 30 s in slow mode or every 1 s in fast mode, and declares a partner dead after three missed intervals (90 s or 3 s).

The part people misunderstand is how frames are spread. The switch does not round-robin frames across members. Doing so would reorder frames within a TCP flow, and TCP reads reordering as loss. Instead it hashes fields that are constant for a flow — MACs, IPs, protocol, ports — and uses the hash to pick a member. Every frame of a flow takes the same member. Different flows usually take different ones.

The consequences follow directly:

  • One flow never exceeds one member's speed. A 4 × 25 Gb/s LAG is not a 100 Gb/s pipe for a single TCP connection. It is four 25 Gb/s pipes.
  • Balance is statistical. Thousands of small flows spread nearly evenly. A handful of large flows can land on the same member by chance.
  • Changing the member count moves flows. With "hash modulo N", going from 4 to 5 members changes the member for most flows, which briefly reorders their in-flight packets. Resilient hashing uses a fixed table of buckets and reassigns only the buckets the new member takes over.
  • Same hash, same answer. If two tiers of switches use the same hash function on the same fields, the second tier sees only flows that already share a hash property, and sends them all one way. This is hash polarisation.

The script below shows all four effects using CRC-32 (a hash many switch ASICs offer):

"""How a LAG (or ECMP group) spreads flows: hash the 5-tuple, pick a member.

Uses CRC-32 from zlib as the hash, as many switch ASICs offer CRC-based hashes.
"""
import random
import struct
import zlib
from collections import Counter

random.seed(7)

def five_tuple(i):
    src = f"10.0.{i // 250}.{i % 250 + 1}"
    return (src, "10.9.0.10", 6, random.randint(32768, 60999), 443)

def flow_hash(t, seed=0):
    src, dst, proto, sport, dport = t
    key = (bytes(map(int, src.split("."))) + bytes(map(int, dst.split(".")))
           + struct.pack("!BHH", proto, sport, dport))
    return zlib.crc32(key, seed)

flows = [five_tuple(i) for i in range(10_000)]

print("1) 10,000 small flows over 4 members (flow counts):")
c = Counter(flow_hash(f) % 4 for f in flows)
print("   ", [c[m] for m in range(4)])

print("2) 6 elephant flows of 10 Gb/s over 4 x 25 Gb/s members (Gb/s per member):")
eleph = flows[:6]
load = Counter()
for f in eleph:
    load[flow_hash(f) % 4] += 10
print("   ", [load[m] for m in range(4)], "-> busiest member", max(load.values()), "Gb/s")

print("3) Add a 5th member. Fraction of flows that change member:")
moved = sum(flow_hash(f) % 4 != flow_hash(f) % 5 for f in flows)
print(f"    modulo hashing          : {100 * moved / len(flows):.1f}%")
# Resilient hashing: a fixed table of buckets; a new member takes over only
# a fair share of buckets, everything else stays where it was.
BUCKETS = 256
table = [b % 4 for b in range(BUCKETS)]
new = table[:]
per_member = BUCKETS // 5
taken = 0
for b in range(BUCKETS):
    if taken < per_member and Counter(new)[new[b]] > per_member:
        new[b] = 4
        taken += 1
moved = sum(table[flow_hash(f) % BUCKETS] != new[flow_hash(f) % BUCKETS] for f in flows)
print(f"    resilient bucket table  : {100 * moved / len(flows):.1f}%")

print("4) Polarisation: two tiers, same hash function and seed, 2 links each:")
tier1 = Counter()
tier2 = Counter()
for f in flows:
    a = flow_hash(f) % 2
    tier1[a] += 1
    if a == 0:                      # flows that went to spine 0
        tier2[flow_hash(f) % 2] += 1
print("    tier 1 split     :", [tier1[0], tier1[1]])
print("    tier 2 (spine 0) :", [tier2[0], tier2[1]], " <- one link idle")
tier2 = Counter(flow_hash(f, seed=0x5EED) % 2 for f in flows if flow_hash(f) % 2 == 0)
print("    tier 2, new seed :", [tier2[0], tier2[1]], " <- CRC is linear: a seed only flips bits")
tier2 = Counter((flow_hash(f) >> 16) % 2 for f in flows if flow_hash(f) % 2 == 0)
print("    tier 2, bit 16   :", [tier2[0], tier2[1]], " <- different hash bits fix it")

2) 6 elephant flows of 10 Gb/s over 4 x 25 Gb/s members (Gb/s per member):
    [20, 0, 10, 30] -> busiest member 30 Gb/s
3) Add a 5th member. Fraction of flows that change member:

    tier 1 split     : [4907, 5093]

Case 2 is the one that bites in production. Six 10 Gb/s flows is only 60 % of the bundle's 100 Gb/s, yet one member is asked for 30 Gb/s and drops, while another sits idle.

Case 4 has a lesson of its own. With a CRC, changing the seed does not decorrelate the tiers. A CRC is linear, so a different seed only XORs every hash with the same constant: the tier-2 split flipped from "all on link 0" to "all on link 1". Real fixes use different hash functions or different output bits per tier, which is what vendors' "hash seed / hash offset" knobs do under the hood.

The same mechanism, with a different name, spreads traffic across equal-cost IP routes (ECMP). Everything above applies to a leaf-spine fabric as much as to a two-cable LAG.

Deep dive: what the bridge actually does — a Linux lab

You can watch learning, ageing and flooding with nothing but a Linux machine. The Linux bridge is a software switch with the same learning algorithm, and it is the switch under Docker's docker0 and many Kubernetes CNI plugins. The lab below builds a bridge with three hosts, each in its own network namespace. It needs root on Linux (a Linux VM on your Mac works). It does not run on macOS directly.

#!/bin/bash
# Linux only, needs root. Bridge d03br with hosts d03A d03B d03C.
cleanup(){ for n in d03A d03B d03C; do ip netns del $n 2>/dev/null; done; ip link del d03br 2>/dev/null; }
cleanup
for n in d03A d03B d03C; do ip netns add $n; done
ip link add d03br type bridge ageing_time 1000   # 10 s for the demo (centiseconds)
ip link set d03br up
i=1
for n in A B C; do
  ip link add v03$n type veth peer name eth0 netns d03$n
  ip link set v03$n master d03br up
  ip -n d03$n link set eth0 address 02:00:00:00:00:0$i
  ip -n d03$n addr add 10.0.0.$i/24 dev eth0
  ip -n d03$n link set eth0 up
  i=$((i+1))
done
# Static ARP entries, so ARP broadcasts do not refresh the table behind our back
ip -n d03A neigh replace 10.0.0.2 lladdr 02:00:00:00:00:02 dev eth0 nud permanent
ip -n d03B neigh replace 10.0.0.1 lladdr 02:00:00:00:00:01 dev eth0 nud permanent
ip netns exec d03A ping -c1 -W1 10.0.0.2 >/dev/null
bridge -s fdb show br d03br | grep -v permanent          # learned entries + timers
sleep 4;  bridge -s fdb show br d03br | grep -v permanent
sleep 8;  bridge -s fdb show br d03br | grep -v permanent # aged out by now
# Silent receiver: B listens on UDP 5000 but never sends; A streams to it; C captures
ip netns exec d03B timeout 4 python3 -c "
import socket; s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM); s.bind(('10.0.0.2',5000))
while True: s.recv(2000)" &
ip netns exec d03C timeout 3 tcpdump -e -nn -i eth0 -c 4 udp &
sleep 1
ip netns exec d03A python3 -c "
import socket,time
s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM)
for i in range(4): s.sendto(b'x'*100,('10.0.0.2',5000)); time.sleep(0.25)"
sleep 2.5; bridge -s fdb show br d03br | grep -v permanent
cleanup

Every one of A's datagrams reached C, even though the destination MAC is B's. That is unknown-unicast flooding, captured on a bystander. The table at the end explains it: the bridge learned A (A transmits) but never relearned B (B is silent). As long as B stays quiet, every frame to B goes to every port. The length 142 is the frame without its 4-byte FCS: 14 Ethernet + 20 IP + 8 UDP + 100 data.

An earlier version of this lab made a revealing mistake. Without the listener on B, B's kernel answered each datagram with ICMP port unreachable. That single reply taught the bridge where B was, and the flooding stopped after the first frame. One flooded frame is normal: it is how learning starts. A steady stream of them is a symptom.

The filter for finding this on any host is simple: capture frames that are neither to you nor broadcast/multicast. If you see any, something upstream is flooding.

# Linux: frames on this NIC that are not for us (needs root)
sudo tcpdump -e -nn -i eth0 'not ether host '"$(cat /sys/class/net/eth0/address)"' and not broadcast and not multicast'

# run on your Mac — your output will differ (en0 is often Wi-Fi; flooding is a wired-LAN symptom)
sudo tcpdump -e -nn -i en0 "not ether host $(ifconfig en0 | awk '/ether/{print $2}') and not broadcast and not multicast"

A worked check on the packet-rate row. A 64-byte frame occupies 64 + 8 + 12 = 84 bytes of wire time, or 672 bits. At 10 Gb/s, 10¹⁰ / 672 = 14,880,952 frames per second. A switch advertised as "line rate at 64 bytes" must make one forwarding decision every 67 ns per 10 G port. On a 128-port 100 G switch, the pipeline handles about 19 billion decisions per second. That is why the work is done in fixed-function silicon and not in software.

Deep dive: production failure modes

Unicast flooding from asymmetric routing

Symptom. Hosts on a VLAN see traffic that is not theirs. Uplinks show elevated utilisation that no application accounts for. Sometimes a server's NIC drops packets because it is processing other servers' traffic.

Mechanism. Return traffic for a server enters the VLAN through router R1, but the server sends its outbound traffic through router R2. That asymmetry is common with two first-hop routers and load sharing. R1 holds an ARP entry for the server for hours, because router ARP timeouts are long. The switch near R1 never sees the server's MAC as a source, because the server talks to R2. After 300 s the MAC ages out on that switch. R1 keeps sending to a MAC the switch does not know, and every frame floods the VLAN.

Prove it. On a bystander host, run the "not for me" capture above. The flooded frames will have the router's MAC as source and the server's MAC as destination. On the switch facing R1, look up the server's MAC; it will be missing while traffic is flowing (show mac address-table address <mac> on most vendor CLIs; bridge fdb show | grep <mac> on Linux).

Fix. Make the timers agree. Set the router's ARP timeout below the switch's MAC ageing time, so the router re-ARPs and the server's reply refreshes the table. Or raise MAC ageing above the ARP timeout. Or remove the asymmetry.

MAC flapping: a loop, a duplicate, or a misbehaving host

Symptom. Intermittent loss for one or a few hosts. Switch logs complain that a MAC is "moving" or "flapping" between two ports (the exact message is vendor-specific).

Mechanism. Learning trusts the source address. If frames with the same source MAC arrive on two ports, the entry flips between them, and frames destined for that MAC follow whichever port won last. The causes, roughly in order of how often they turn up: a Layer 2 loop (the same broadcast arrives on two ports); two VMs or containers cloned with the same MAC; a server bonding mode that sends the same MAC out of two switch ports without the switch knowing they form a bundle; and plain spoofing.

Prove it. Watch the table entry over a few seconds; on Linux, watch -n 0.5 'bridge fdb show | grep <mac>'. Check broadcast counters on the two ports. A loop shows a broadcast rate climbing fast. A duplicate MAC does not.

Fix. For loops, STP/RSTP or physically removing the loop; storm control limits the damage meanwhile. For duplicates, fix the MAC assignment. For bonding, match the server's mode to the switch config: LACP on both sides, or active-backup with no LAG on the switch.

Microburst drops on an "idle" link

Symptom. Application p99 latency spikes, often in clean multiples of 200 ms. Interface graphs show 5–20 % utilisation. Drop counters on one egress port rise slowly.

Mechanism. The incast arithmetic above. Short bursts overflow the port's share of the shared buffer, and TCP recovers through retransmission timeouts.

Prove it. Correlate three numbers. First, egress discard counters on that port's queues (on Linux hosts, ip -s link show dev eth0 and ethtool -S eth0 | grep -i drop; on switches, the per-queue drop counters). Second, retransmission counters on the senders: nstat -az TcpRetransSegs TcpExtTCPTimeouts on Linux, netstat -s -p tcp | grep -i retrans on macOS. Third, buffer high-water marks or microburst telemetry if the switch has it; many recent switches can export queue depth at sub-millisecond granularity. Utilisation graphs will not help, as the simulation showed.

Fix. In rough order of preference: let the switch mark ECN instead of dropping, and use a congestion control that reacts to it (DCTCP-style); spread the fan-in (stagger requests, limit concurrency); raise the queue's dynamic-threshold factor or give the traffic class its own buffer pool; move to a switch with more buffer per port. Faster links help less than you would expect, because the fan-in ratio stays the same.

One LAG member hot, the others cold

Symptom. A 4 × 25 G LAG at 40 % total load drops packets. One member shows 100 % utilisation.

Mechanism. A few large flows hashed onto the same member (case 2 above). Or the hash uses only MAC addresses. Linux bonding's default xmit_hash_policy is layer2, and between a host and its single router every frame has the same pair of MACs, so every flow lands on one member.

Prove it. Per-member counters (cat /proc/net/bonding/bond0, and ip -s link show on each member, on Linux; the per-interface counters of the port-channel members on a switch). Check the configured hash policy on both ends; each side hashes only its own transmit direction.

Fix. Hash on L3+L4 fields (xmit_hash_policy=layer3+4 on Linux bonding; the equivalent load-balance setting on the switch). If the traffic really is a few elephants, a LAG cannot fix it. Use faster single links, split the work into more flows, or use a fabric that sprays packets and reorders at the receiver.

CRC errors on a link that tests clean

Symptom. A port shows rising FCS/CRC errors. You replace the optic and cable; the errors continue.

Mechanism. In a cut-through path, a frame corrupted on an upstream link is forwarded with a stomped CRC. The error appears on the first store-and-forward hop (or end host) downstream, not on the link that caused it.

Prove it. Follow the errors upstream. The true source is the port with input errors that are not stomped. Some platforms count stomped frames separately, which makes this quick; on others you walk the path port by port.

Fix. Replace the optic or cable on the link where the errors originate.

Deep dive: 2026 context

Cloud VPCs do not switch. AWS, Google Cloud and Azure virtual networks do not run flood-and-learn at all. The hypervisor or smart NIC knows every VM's MAC and IP from the control plane. It answers ARP on the VM's behalf and delivers frames directly. Broadcast and multicast are not supported in a standard VPC (AWS offers multicast only through a Transit Gateway feature). Everything in this deep dive about MAC ageing and unknown-unicast flooding simply does not happen inside a VPC. That also means old L2 tricks — gratuitous ARP failover, a floating IP moved by sending ARP — do not work there. You move the IP through the cloud API instead.

Kubernetes and containers do switch, in software. A node using a bridge-based CNI has a Linux bridge (cni0, docker0) with the same learning table and the same 300 s ageing you saw in the lab. Overlay CNIs that use VXLAN (Flannel, Calico in VXLAN mode, others) usually avoid flood-and-learn across nodes. The agent programs static forwarding entries, visible with bridge fdb show dev flannel.1, each mapping a remote MAC to a remote node's IP. Learning by flooding across an IP fabric would be too expensive.

Data-centre fabrics replaced flooding with a control plane. Large fabrics run VXLAN with an EVPN control plane (RFC 7432, RFC 8365). Switches advertise the MACs they learn locally in BGP, so remote switches install them without ever flooding. LAG's multi-switch cousin — one server dual-homed to two switches — is done with EVPN multihoming instead of vendor-specific MLAG in newer designs.

AI training clusters made buffers and hashing first-class problems. GPU-to-GPU traffic is a few huge, synchronised flows: the worst case for both microbursts and per-flow hashing. RoCEv2 fabrics traditionally rely on Priority Flow Control (IEEE 802.1Qbb) to avoid drops. That brings its own failure mode: pause frames that spread congestion backwards and, in bad cases, deadlock. The newer approach — in hyperscaler fabrics and in the Ultra Ethernet Consortium's specification released in 2025 — sprays a flow's packets across all paths and lets the receiver reorder. It abandons the "one flow, one path" rule this section explained. When you hear "packet spraying" or "adaptive routing", this is the problem it solves.

Speeds keep rising; the buffer per port does not. Each switch generation roughly doubles throughput. On-chip buffer grows more slowly, so the microseconds of buffering per port tend to shrink. Microburst behaviour gets harder, not easier, as links get faster.

Deep dive: senior interview questions

Q1: A switch's MAC table is half full, yet it is flooding traffic to a host that is actively receiving. Give two independent explanations.

First, the host may be silent. Ageing refreshes on source addresses only, so a host that only receives ages out after 300 s and every frame to it is flooded, however busy the stream. Second, the table is a hash table with fixed-size buckets. If the host's (VLAN, MAC) hashes into a full bucket, the switch cannot learn it, even with half the table free. You tell them apart by checking whether the host ever transmits on that port, and whether the switch reports learning failures or hash collisions.

Q2: Why can a cut-through switch not drop a frame with a bad FCS, and what does that do to troubleshooting?

The FCS is the last 4 bytes of the frame. A cut-through switch has started transmitting long before those bytes arrive. When the check fails, the frame is already half-sent, so the switch can only end it with a deliberately bad CRC. The next store-and-forward device drops it and counts an error. The counter therefore increments one or more hops away from the faulty link, and swapping optics on the reporting port does nothing.

Q3: Interface utilisation is 10 %, yet the switch is dropping packets on that port. How is that possible, and how would you prove it?

Utilisation is an average over seconds or minutes, and drops happen over microseconds. When several ports send to one port at once, the queue grows at the excess rate, and a buffer share of around a megabyte fills in tens of microseconds. Proof comes from correlation, not averages: egress discard counters on that queue, TCP retransmission-timeout counters on the senders, and sub-millisecond buffer telemetry if the switch has it. Latency outliers in multiples of the minimum RTO (200 ms on Linux) are a strong hint.

Q4: You add a fifth member to a busy four-member LAG. What happens to the traffic, and how would you avoid it?

With modulo-N hashing, around four out of five flows change member. Packets already queued on the old member and new ones on the new member can arrive out of order, and TCP may treat that as loss. Resilient (consistent) hashing keeps a fixed bucket table and moves only the buckets the new member takes, around a fifth of the flows. Doing the change in a quiet period also helps.

Q5: Why does a single iperf3 stream over a 4 × 10 G LAG top out near 10 Gb/s, and what changes with -P 8?

The LAG hashes per flow so it never reorders packets within a flow. One TCP stream is one flow, so it uses one 10 G member. With eight parallel streams there are eight different source ports. They hash to different members with reasonable probability, but the spread is not guaranteed to be even. Eight flows over four members often leaves one member with three flows and another with one.

Q6: Two tiers of switches both hash with CRC-32 over the same fields. You change the seed on the second tier, and nothing improves. Why?

CRC is linear over GF(2). For fixed-length input, changing the initial value XORs every output with the same constant. If tier 1 sent all flows with hash bit 0 equal to 0 to one spine, those flows still share bit 0 at tier 2, just possibly inverted. They all go one way. You need a different function, or different output bits, at each tier — not a different seed of the same CRC.

Q7: You run a VM cluster that fails over by moving a virtual IP and sending gratuitous ARP. It works on-premises and fails in the cloud. Why?

On-premises, the gratuitous ARP is a broadcast that floods the VLAN, so it refreshes every host's ARP cache and every switch's MAC table. In a cloud VPC there is no flooding and no learning. The virtual network's control plane decides which VM owns an IP, and it answers ARP itself, so a guest's gratuitous ARP changes nothing. The failover must call the cloud API to move the IP (or update a route), or use a load balancer.
