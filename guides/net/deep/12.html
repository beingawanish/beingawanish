Deep dive: what "request/response over a byte stream" hides

The module's model is correct: a client sends a message, a server sends one back, usually on the same connection. What it hides is that the connection is the expensive, stateful object, and the message is cheap. Before the first byte of GET leaves your machine, a client has resolved a name, completed a TCP handshake, run a TLS 1.3 key exchange, validated a certificate chain against a trust store, and negotiated an HTTP version through ALPN. Each step has its own state, its own timers and its own way to fail. Every layer above it, from connection pools to HTTP/2 streams, exists to pay that setup cost as rarely as possible.

This deep dive follows one HTTPS request through its whole life. It shows where the time goes, measured with curl and with a localhost script you can run. It then covers what pools and keep-alive actually keep, why HTTP/1.1, HTTP/2 and HTTP/3 block differently when a packet is lost, what TLS 1.3 sends field by field (and what 0-RTT gives away), how a client really validates a certificate chain, and the production failures that come out of each piece. QUIC has its own module, Module 20 — QUIC & HTTP/3; here it appears only where HTTP/3 needs it.

Deep dive: the real mental model — a connection is a pooled, stateful object

The lifecycle, phase by phase

A cold HTTPS request has four phases before any useful data arrives. curl exposes a cumulative timer at the end of each one, and the diagram maps them onto the round trips underneath.

On a path with round-trip time R, the arithmetic is simple:

  • Name lookup: zero if cached in-process; one RTT to the resolver if the resolver has it; more on a cold walk (Module 11's deep dive).
  • TCP: one RTT. The SYN goes out, the SYN-ACK comes back, and the client can send right away with its ACK.
  • TLS 1.3: one RTT. ClientHello out, the server's whole flight back, and the client's Finished leaves together with the first request.
  • Request to first byte: one RTT plus whatever the server spends thinking.

So a cold request costs roughly 3 RTT + DNS + server time before the first response byte. A reused connection costs 1 RTT + server time. At R = 80 ms that is about 160 ms of pure waiting saved on every request that finds a warm connection, plus the DNS time. That's why pools matter more than almost any server-side optimisation.

What a connection actually holds

A pooled connection is not just a file descriptor. Each side keeps:

  • TCP state: sequence numbers, congestion window, RTT estimate, send and receive buffers. A connection that has been busy has a large congestion window; a fresh one starts slow (Module 10). That's a second reason reuse is fast.
  • TLS state: the negotiated cipher, the client and server traffic keys, per-direction record sequence numbers used to build nonces, and any session tickets received for later resumption.
  • HTTP/2 state (when negotiated): the stream table, both HPACK dynamic tables, a flow-control window per stream plus one per connection, and the peer's SETTINGS such as MAX_CONCURRENT_STREAMS.
  • Pool bookkeeping: the key the connection is filed under, its idle-since timestamp, and whether a request is in flight.

The pool key is the origin (scheme, host, port), extended by anything that changes the connection: proxy, client certificate, TLS settings. Browsers cap HTTP/1.1 at six connections per origin. For HTTP/2 they normally keep one per origin. They may also coalesce several origins onto it when the certificate covers both names and the names resolve to the same address (RFC 9113 §9.1.1). A server that receives a coalesced request it can't serve answers 421 Misdirected Request, and the client retries on a fresh connection.

Keep-alive is two timers that must agree

Either side may close an idle connection at any time, and neither warns the other. That creates a race. The server's idle timer fires and it sends a FIN. At nearly the same instant the client takes the connection from its pool and writes a request. The request hits a closed socket, and the client sees a reset or an empty response.

Two rules contain it:

  1. Order the idle timeouts. Whoever reuses a connection must give it up before the other side does. A client pool's idle timeout must be shorter than the server's keep-alive timeout. A load balancer's idle timeout towards its backends must be shorter than the backend's keep-alive timeout.
  2. Retry only what is safe. RFC 9110 §9.2.2 allows a client to retry a request automatically after a connection failure only when the method is idempotent. Libraries do this silently for GET. They must not for POST.

Measuring it on localhost

The script below runs an HTTPS server on 127.0.0.1 with a real three-level PKI (root → intermediate → leaf). It times each phase, compares full and resumed TLS handshakes, and compares 50 requests on 50 connections with 50 requests on one. Finally it serves the leaf without its intermediate. First build the PKI. These commands were run with OpenSSL 3.0; they use only options LibreSSL (macOS /usr/bin/openssl) also documents, but if your version rejects one, use Homebrew's openssl@3.

#!/bin/sh
# Build a three-level PKI for localhost: root CA -> intermediate CA -> leaf.
# Works with OpenSSL 3 (Linux, Homebrew) and LibreSSL (macOS /usr/bin/openssl).
set -e
mkdir -p pki && cd pki
cat > ext.cnf <<'CNF'
[root]
basicConstraints = critical, CA:TRUE
keyUsage = critical, keyCertSign, cRLSign
subjectKeyIdentifier = hash
[ca]
basicConstraints = critical, CA:TRUE, pathlen:0
keyUsage = critical, keyCertSign, cRLSign
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid
[leaf]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature
extendedKeyUsage = serverAuth
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid
subjectAltName = DNS:localhost, IP:127.0.0.1
CNF
for k in root inter leaf; do openssl ecparam -genkey -name prime256v1 -noout -out $k.key; done
openssl req -new -key root.key -subj "/CN=Demo Root CA" -out root.csr
openssl x509 -req -in root.csr -signkey root.key -days 30 -extfile ext.cnf -extensions root -out root.pem
openssl req -new -key inter.key -subj "/CN=Demo Intermediate CA" -out inter.csr
openssl x509 -req -in inter.csr -CA root.pem -CAkey root.key -CAcreateserial \
        -days 30 -extfile ext.cnf -extensions ca -out inter.pem
openssl req -new -key leaf.key -subj "/CN=localhost" -out leaf.csr
openssl x509 -req -in leaf.csr -CA inter.pem -CAkey inter.key -CAcreateserial \
        -days 7 -extfile ext.cnf -extensions leaf -out leaf.pem
cat leaf.pem inter.pem > fullchain.pem
openssl verify -CAfile root.pem -untrusted inter.pem leaf.pem
"""Time each phase of an HTTPS request on localhost (name lookup, TCP, TLS 1.3, TTFB),
compare full vs resumed handshakes and new vs reused connections, then show the
missing-intermediate failure. Needs pki/ from d12_make_pki.sh. Stdlib only."""
import socket, ssl, statistics, sys, threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

NODELAY = "--nodelay" in sys.argv                   # disable Nagle on the server side too

class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"                       # keep-alive on
    def do_GET(self):
        body = b'{"ok": true}\n'
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *a): pass
    def setup(self):
        super().setup()
        if NODELAY:
            self.connection.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

class Quiet(ThreadingHTTPServer):
    def handle_error(self, *a): pass                    # clients hang up abruptly; ignore

def serve(chainfile):
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    ctx.minimum_version = ssl.TLSVersion.TLSv1_3
    ctx.load_cert_chain(chainfile, "pki/leaf.key")
    srv = Quiet(("127.0.0.1", 0), Handler)
    srv.socket = ctx.wrap_socket(srv.socket, server_side=True)
    threading.Thread(target=srv.serve_forever, daemon=True).start()
    return srv.server_address[1]

client = ssl.create_default_context(cafile="pki/root.pem")   # trust only the demo root
REQ = b"GET / HTTP/1.1\r\nHost: localhost\r\n\r\n"

def connect(port, session=None):
    t0 = time.perf_counter()
    addr = socket.getaddrinfo("localhost", port, socket.AF_INET, socket.SOCK_STREAM)[0][4]
    t1 = time.perf_counter()
    raw = socket.create_connection(addr)
    raw.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
    t2 = time.perf_counter()
    tls = client.wrap_socket(raw, server_hostname="localhost", session=session)
    t3 = time.perf_counter()
    return tls, (t1 - t0, t2 - t1, t3 - t2)

def request(tls):
    t = time.perf_counter()
    tls.sendall(REQ)
    tls.recv(4096)                                      # status line, headers and the tiny body
    return time.perf_counter() - t

med = lambda xs: f"{1000*statistics.median(xs):5.2f} ms"
port = serve("pki/fullchain.pem")
request(connect(port)[0])                               # warm-up: server thread, code paths

lookup, tcp, full, resumed, ttfb = [], [], [], [], []
for _ in range(30):
    tls, (d, c, hs) = connect(port)
    lookup.append(d); tcp.append(c); full.append(hs)
    ttfb.append(request(tls))                           # recv() also pulled in the session ticket
    proto = f"{tls.version()} {tls.cipher()[0]}"
    sess = tls.session; tls.close()
    tls2, (_, _, hs2) = connect(port, session=sess)
    assert tls2.session_reused
    resumed.append(hs2); tls2.close()
print(f"{proto}, medians of 30 runs on loopback:")
print(f"  name lookup {med(lookup)} | tcp connect {med(tcp)} | ttfb {med(ttfb)}")
print(f"  TLS full handshake {med(full)} | resumed (PSK) {med(resumed)}")

N = 50
t = time.perf_counter()
for _ in range(N):
    tls, _ = connect(port); request(tls); tls.close()
cold = time.perf_counter() - t
tls, _ = connect(port)
t = time.perf_counter()
for _ in range(N):
    request(tls)
warm = time.perf_counter() - t
print(f"{N} requests, new connection each: {1000*cold:6.1f} ms; one kept-alive connection: {1000*warm:5.1f} ms")

print("server sends leaf only (intermediate missing):")
try:
    connect(serve("pki/leaf.pem"))
except ssl.SSLCertVerificationError as e:
    print(f"  {type(e).__name__}: {e.verify_message} (verify_code={e.verify_code})")

Look at the first run's TTFB: 43 ms on loopback, where the round trip is microseconds. This is a real production bug, reproduced by accident. Here is the mechanism.

In TLS 1.3 the server sends session tickets right after the handshake (OpenSSL sends two by default). They are unacknowledged data in flight. The client's TCP stack delays its ACK, hoping to piggyback it on data of its own. Then the server writes its response. Nagle's algorithm holds back a small write while earlier data is still unacknowledged. So the response sits in the server's buffer until the client's delayed-ACK timer fires, and Linux's minimum delayed-ACK time is 40 ms.

Turn Nagle off with TCP_NODELAY and TTFB drops to 0.62 ms. Setting num_tickets = 0 on the server context removes the stall too, which confirms that the tickets are the unacknowledged data. Most production HTTP servers set TCP_NODELAY for exactly this reason; Python's http.server does not. The kept-alive figure in the first run (46.7 ms for 50 requests) is that one 43 ms stall on the first request plus well under 0.1 ms for each later one.

With the stall removed, the rest reads cleanly. A full handshake costs about 1.7–2.1 ms of CPU on loopback. PSK resumption cuts that by roughly a third, because it skips the certificate and the signature check (it still does a fresh key exchange). Fifty fresh connections cost 126 ms; fifty requests on one connection cost 6.3 ms. On a real network, add two RTTs to every fresh connection and the gap grows enormously. The last line is the missing-intermediate failure, which gets its own section below.

HTTP/1.1: head-of-line blocking by design

HTTP/1.1 has no message IDs. Responses on a connection must come back in request order, because the only way to tell them apart is their position in the byte stream. Pipelining (sending request 2 before response 1 arrives) is in the spec. Browsers never turned it on widely: a slow first response blocks every response behind it, and buggy intermediaries mixed responses up. So in practice an HTTP/1.1 connection carries one request at a time. Concurrency comes from opening more connections, which is where the six-per-origin limit comes from. Domain sharding and sprite sheets were workarounds for exactly this.

HTTP/2: streams, frames and flow control

HTTP/2 (RFC 9113) splits every message into frames with a 9-byte header and interleaves frames from many streams on one connection. The script below decodes the first bytes a client sends, then computes the throughput ceiling that flow control imposes. Real output:

"""Decode the first bytes a client sends on an HTTP/2 connection (RFC 9113),
then do the flow-control arithmetic that caps a single stream's throughput."""
import struct

TYPES = {0: "DATA", 1: "HEADERS", 3: "RST_STREAM", 4: "SETTINGS", 6: "PING", 7: "GOAWAY", 8: "WINDOW_UPDATE"}
SETTINGS = {1: "HEADER_TABLE_SIZE", 2: "ENABLE_PUSH", 3: "MAX_CONCURRENT_STREAMS",
            4: "INITIAL_WINDOW_SIZE", 5: "MAX_FRAME_SIZE", 6: "MAX_HEADER_LIST_SIZE"}

def frame(ftype, flags, stream, payload):
    # 9-byte header: Length(24) Type(8) Flags(8) R(1)+Stream Identifier(31)
    return struct.pack("!I", len(payload))[1:] + bytes([ftype, flags]) + struct.pack("!I", stream) + payload

preface = b"PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n"
settings = frame(4, 0, 0, b"".join(struct.pack("!HI", k, v) for k, v in
                                   [(2, 0), (3, 100), (4, 10 * 1024 * 1024)]))
window = frame(8, 0, 0, struct.pack("!I", 1 << 30))        # raise the connection window
# HEADERS for GET https://api.example.com/v1/orders, HPACK-encoded:
# 0x82 = :method GET, 0x87 = :scheme https (static table indices 2 and 7);
# 0x41/0x44 = literal :authority / :path, added to the dynamic table (plain strings)
hpack = (b"\x82\x87" + b"\x41" + bytes([15]) + b"api.example.com"
         + b"\x44" + bytes([10]) + b"/v1/orders")
headers = frame(1, 0x05, 1, hpack)                          # END_STREAM | END_HEADERS, stream 1
wire = preface + settings + window + headers

print(f"preface: {preface!r} ({len(preface)} bytes)")
pos = len(preface)
while pos < len(wire):
    length = int.from_bytes(wire[pos:pos + 3], "big")
    ftype, flags = wire[pos + 3], wire[pos + 4]
    stream = struct.unpack("!I", wire[pos + 5:pos + 9])[0] & 0x7FFFFFFF
    body = wire[pos + 9:pos + 9 + length]
    print(f"{wire[pos:pos+9].hex(' ')} | {TYPES[ftype]:13} len={length:<3} flags={flags:#04x} stream={stream}")
    if ftype == 4:
        for i in range(0, length, 6):
            k, v = struct.unpack("!HI", body[i:i + 6])
            print(f"    {SETTINGS[k]} = {v:,}")
    if ftype == 8:
        print(f"    window increment = {struct.unpack('!I', body)[0]:,}")
    if ftype == 1:
        print(f"    HPACK block: {body.hex(' ')}")
        # same request again: both literals now sit in the dynamic table (62 = :path, 63 = :authority)
        print(f"    repeat request encodes as {bytes([0x82, 0x87, 0x80 | 62, 0x80 | 63]).hex(' ')} (4 bytes)")
    pos += 9 + length

print("\nflow control: one stream can have at most `window` unacknowledged bytes in flight")
for window in (65_535, 1 << 20, 6 << 20):
    for rtt_ms in (20, 100):
        mbps = window * 8 / (rtt_ms / 1000) / 1e6
        print(f"  window {window:>9,} B, RTT {rtt_ms:3d} ms -> max {mbps:7.1f} Mbit/s per stream")
bdp = 1e9 / 8 * 0.100
print(f"  to fill 1 Gbit/s at 100 ms you need a window >= BDP = {bdp:,.0f} B")

What to take from the bytes:

  • The preface is a fixed 24-byte string. It was chosen so an HTTP/1.1 server rejects it as garbage instead of misreading it.
  • Every frame header is length (24 bits), type, flags, and a 31-bit stream ID. Stream 0 is the connection itself; client-initiated streams are odd (1, 3, 5…).
  • SETTINGS are per-direction limits. INITIAL_WINDOW_SIZE defaults to 65,535 bytes for every stream until a peer raises it. MAX_CONCURRENT_STREAMS caps in-flight requests; servers commonly advertise somewhere between 100 and 250.
  • The connection-level window also starts at 65,535 bytes and can only grow through WINDOW_UPDATE on stream 0. That's why real clients send one immediately.
  • HPACK (RFC 7541) is stateful compression. The first request spends 31 bytes on its headers; the identical second one spends 4, because both sides added the literals to a dynamic table (4,096 bytes by default). That shared table is also why HPACK is order-dependent: HEADERS frames must be decoded in exactly the order they were sent.

Flow control is credit-based and applies only to DATA frames. The receiver grants a window. The sender may have at most that many bytes outstanding that the receiver hasn't yet credited back. WINDOW_UPDATE frames return the credit. A stream's throughput is therefore capped at window ÷ RTT: 5.2 Mbit/s for the 65,535-byte default at 100 ms. That's the classic "HTTP/2 download is slow over long distance but fine locally" bug. It stacks with TCP's own limits. A transfer runs at the minimum of the HTTP/2 stream window, the HTTP/2 connection window, the TCP receive window and the congestion window.

HTTP/2 fixes HTTP/1.1's application-level head-of-line blocking: a slow response no longer blocks the others. It leaves transport-level blocking in place, and concentrates it. All streams share one TCP byte stream. If one segment is lost, TCP holds back every byte after it, for every stream, until the retransmission arrives. With six HTTP/1.1 connections, one loss stalls one of six. With one HTTP/2 connection, it stalls all of them. On clean networks HTTP/2 wins comfortably. On lossy mobile links the gap narrows and can reverse.

HTTP/3: moving streams below the loss

HTTP/3 (RFC 9114) keeps HTTP/2's model of streams and frames, but it runs on QUIC, which implements streams itself over UDP. Loss recovery is per stream: a lost packet carrying stream 5's data stalls only stream 5. QUIC also folds the transport and TLS 1.3 handshakes into one round trip, so a cold HTTP/3 request costs about 2 RTT instead of 3. HPACK's strict ordering doesn't survive independent streams, so HTTP/3 uses QPACK (RFC 9204), which carries dynamic-table updates on dedicated encoder and decoder streams.

Clients learn that a server speaks HTTP/3 in one of two ways. An Alt-Svc: h3=":443" response header works, but only from the second connection on, so the first visit is HTTP/2. A DNS HTTPS record (Module 11's deep dive) works before the first connection. Module 20 covers the transport itself: connection IDs, migration, packet number spaces and loss recovery.

TLS 1.3, field by field

The module gave the message flow. Here is what is inside the first two messages, roughly as a capture tool shows it (constructed and trimmed; typical values):

TLSv1.3 Record: Handshake, ClientHello
  legacy_version: 0x0303 (TLS 1.2)          # frozen for middleboxes; the real version is in an extension
  random: 32 bytes
  legacy_session_id: 32 bytes               # random, also for middlebox compatibility
  cipher_suites: 0x1301 TLS_AES_128_GCM_SHA256, 0x1302 TLS_AES_256_GCM_SHA384,
                 0x1303 TLS_CHACHA20_POLY1305_SHA256
  extensions:
    server_name: api.example.com            # SNI, plaintext unless ECH is used
    supported_versions: 0x0304 (TLS 1.3), 0x0303
    supported_groups: X25519MLKEM768 (0x11ec), x25519 (0x001d), secp256r1 (0x0017)
    key_share: X25519MLKEM768 (1216 bytes), x25519 (32 bytes)
    signature_algorithms: ecdsa_secp256r1_sha256, rsa_pss_rsae_sha256, ...
    application_layer_protocol_negotiation: h2, http/1.1
    psk_key_exchange_modes: psk_dhe_ke

TLSv1.3 Record: Handshake, ServerHello
  legacy_version: 0x0303
  random: 32 bytes
  cipher_suite: 0x1301 TLS_AES_128_GCM_SHA256
  extensions:
    supported_versions: 0x0304
    key_share: X25519MLKEM768 (1120 bytes)  # ML-KEM ciphertext (1088) + x25519 share (32)

Several things here explain real behaviour:

  • The version disguise. Both hellos claim TLS 1.2 in the legacy field; the real negotiation happens in the supported_versions extension. Middleboxes that inspected the old field broke TLS 1.3 during its rollout, and this disguise was the fix.
  • The speculative key share is the 1-RTT trick. The client guesses which groups the server will accept and sends public keys for them up front. If the guess is wrong, the server answers with a HelloRetryRequest naming a group, and the handshake costs an extra RTT.
  • Post-quantum hybrids are the browser default in 2026. X25519MLKEM768 combines classical X25519 with ML-KEM-768. Its client share alone is 1216 bytes, so the ClientHello grows past 1.5 KB and no longer fits in one TCP segment. Middleboxes that assumed the whole ClientHello arrives in one packet broke when browsers turned this on, and some still do.
  • The key schedule. After ServerHello, both sides run HKDF over the shared secret and the transcript hash to derive handshake traffic keys. Those encrypt everything from EncryptedExtensions through Finished. After Finished they derive application traffic keys. Every key depends on the transcript, so tampering with any earlier message breaks the Finished check.
  • Records. Application data travels in records of at most 2^14 (16,384) bytes of plaintext. Each record adds a 5-byte header, a 1-byte inner content type and a 16-byte AEAD tag: 22 bytes of overhead.

0-RTT, and what it gives away

On resumption, a client can send application data in its very first flight, encrypted under a key derived from the session ticket's pre-shared key. The server can act on it before any round trip completes. Three costs come with that:

  1. Replay. The early data is a self-contained, valid ciphertext. An attacker who records it can send it again, and another server instance holding the same ticket key will accept it. RFC 8446 §8 describes mitigations (single-use tickets, recording ClientHellos, freshness windows), but none of them works fully across a globally distributed fleet.
  2. No forward secrecy for the early data. Only the PSK protects it. Whoever later obtains the ticket-encryption key can decrypt recorded early data.
  3. Retries become the application's problem. A server may reject early data. The client must then resend it after the handshake, so the same request can arrive twice by different paths.

RFC 8470 defines how HTTP copes. A terminator that forwards early data adds Early-Data: 1 to the request. A backend that won't accept the replay risk for that request answers 425 Too Early, and the client retries after the handshake. The safe policy is to allow 0-RTT only for safe methods (GET, HEAD) on endpoints without side effects. Many deployments simply leave it off.

Certificate chain validation, as the client does it

"The client verifies the chain" is really a list of specific checks: RFC 5280 path validation plus RFC 9525 name matching.

  1. Build a path. Start at the leaf. Find an issuer whose subject matches the leaf's issuer name (and whose Subject Key Identifier matches the leaf's Authority Key Identifier). Look first among the certificates the server sent, then in the local trust store. Repeat until you reach a trusted root. Cross-signed intermediates can create several candidate paths, and different libraries pick differently.
  2. Check each signature with the issuer's public key.
  3. Check validity periods of every certificate against the local clock.
  4. Check CA constraints. Each issuer needs basicConstraints CA:TRUE, keyUsage keyCertSign, and a path length the chain doesn't exceed. Name constraints, where present, must allow the leaf's names.
  5. Check the leaf's purpose. Its extendedKeyUsage must include serverAuth.
  6. Match the name. The hostname must match a subjectAltName DNS entry (or an IP entry, for an IP). Modern clients ignore the Common Name. A wildcard matches exactly one label: *.example.com covers api.example.com, but not example.com or a.b.example.com.
  7. Check revocation and transparency, depending on the client. Browsers use pushed revocation data (Chrome's CRLSets, Firefox's CRLite) and require Certificate Transparency proofs. Many non-browser clients check neither.
  8. Verify possession. The CertificateVerify signature over the handshake transcript proves the server holds the leaf's private key. Without it, a copied certificate, which is public, would be enough to impersonate the site.

The demo PKI above was built to pass these checks. Python 3.13's default context enables strict X.509 checking. An earlier version of the demo root, made without an explicit keyUsage, failed with CA cert does not include key usage extension, which is why the script now sets one.

Deep dive: production failure modes

Intermittent 502s from the load balancer, a few per thousand requests, nothing in the app logs. Mechanism: the backend's keep-alive timeout is shorter than the load balancer's idle timeout. The classic pairing is Node.js (5 s) behind an AWS ALB (60 s). The backend closes an idle connection; the ALB still considers it reusable, sends the next request into it and gets a reset. Prove it: the 502s land on connections that sat idle for more than 5 s. A capture on the backend, tcpdump -nn 'tcp[tcpflags] & (tcp-fin|tcp-rst) != 0', shows the backend's FIN just before the ALB's request. Fix: make the backend's keep-alive timeout longer than the LB's idle timeout. For Node, raise headersTimeout above it as well.

ConnectionResetError or "Remote end closed connection without response" on the first request after a quiet period. Mechanism: the same race on the client side. The pool kept a connection longer than the server allows. Prove it: the failures cluster after idle gaps longer than the server's keep-alive timeout. Fix: set the client pool's idle timeout below the server's; enable the library's retry for idempotent requests; never auto-retry POST.

Works in the browser, fails in curl, Python, Java and mobile apps with "unable to get local issuer certificate". Mechanism: the server sends only its leaf. Browsers often paper over this. They fetch the intermediate from the certificate's AIA URL, or already have it cached from another site. Most other clients do neither. Prove it: openssl s_client -showcerts lists only certificate 0, with verify errors 20 and 21. Fix: configure the server with the full chain (fullchain.pem, not cert.pem).

Mass TLS failures on old clients, with a perfectly valid certificate. Mechanism: path building chose an expired root or cross-sign. The well-known case was September 2021, when an old cross-signing root expired. OpenSSL 1.0.2 clients failed even though a valid path existed, because they built the expired one. Prove it: run openssl s_client with the failing client's library version and read the path it reports. Fix: update the client's trust store or library; serve a chain that doesn't steer old clients onto the expired path.

Certificate errors on a few machines only. Mechanism: the local clock is wrong, so every certificate looks "not yet valid" or "expired". Common on VMs restored from snapshots and on devices without a clock battery. Prove it: compare date -u with a trusted source; the error names validity, not trust. Fix: NTP.

A flat ~40 ms added to some responses. Mechanism: Nagle's algorithm plus delayed ACK, as in the localhost demo. Any pattern of "small write, then another small write" with data still unacknowledged can trigger it. Prove it: a packet capture shows the response leaving exactly when the peer's delayed ACK arrives. Fix: TCP_NODELAY on the server socket; coalesce headers and body into one write.

Large HTTP/2 downloads are slow from far away and fast nearby. Mechanism: the flow-control window is smaller than the bandwidth-delay product, so throughput = window ÷ RTT. Prove it: in a capture, the sender pauses until each WINDOW_UPDATE arrives, and throughput scales inversely with RTT. Fix: raise the initial stream window and send a large connection-level WINDOW_UPDATE. Most proxies and servers have a setting for both.

Requests queue in the client although the server is idle. Mechanism: every request shares one HTTP/2 connection and the server's MAX_CONCURRENT_STREAMS (say 100) is reached, so request 101 waits for a stream to finish. Common with gRPC clients that hold a single channel. Prove it: client metrics show pending streams while the server shows exactly 100 concurrent. Fix: a small pool of connections, or a higher server limit.

One backend pod at 90% CPU, the rest idle, behind a Kubernetes Service. Mechanism: an L4 load balancer (kube-proxy, a cloud network LB) balances connections, and gRPC or HTTP/2 clients each hold one long-lived connection. Whichever pod got the busy client's connection gets all its requests. Prove it: compare per-pod request rates with per-pod connection counts. Fix: L7 balancing (a mesh or an HTTP/2-aware proxy), client-side balancing, or a server-side maximum connection age that forces periodic reconnects.

EADDRNOTAVAIL ("Cannot assign requested address") under load. Mechanism: no connection reuse. Every request opens a new connection to the same ip:port, and each closed connection sits in TIME_WAIT on the side that closed first. At around 470 new connections per second, Linux runs out of ephemeral ports for that destination. Prove it: ss -tan state time-wait | wc -l is close to 28,000 on Linux; on macOS, netstat -an -p tcp | grep -c TIME_WAIT. Fix: pooling first; more source IPs or destination ports second; net.ipv4.tcp_tw_reuse for outbound connections.

Some users behind one corporate network can't connect after a browser update. Mechanism: a post-quantum hybrid key share made the ClientHello span two TCP segments, and a middlebox that expects the whole ClientHello in one packet drops or resets the connection. Prove it: a capture shows the reset right after the second ClientHello segment, and the failure disappears when the hybrid group is disabled. Fix: update the middlebox. Disabling post-quantum key exchange is a stopgap, not a fix.

Deep dive: 2026 context

HTTP/3 is mainstream at the edge. Major browsers and CDNs speak it, and discovery increasingly comes from DNS HTTPS records rather than Alt-Svc. Inside data centres HTTP/2 over TCP still dominates, because loss is rare and TCP tooling is mature. Networks that block UDP/443 push clients back to HTTP/2, so every HTTP/3 deployment needs a working TCP fallback.

Browser TLS is post-quantum by default. Hybrid X25519MLKEM768 key exchange protects today's traffic against "record now, decrypt later". Certificates and signatures are still classical; post-quantum authentication isn't deployed at scale yet. The visible cost is the bigger ClientHello.

Encrypted ClientHello hides the last plaintext name. With ECH, the real SNI travels encrypted inside an outer ClientHello addressed to a shared front-end name, using a key published in the DNS HTTPS record. Major browsers and some CDNs support it. It moves name visibility from the network path to the resolver and the CDN, which matters for networks that filter by SNI.

Certificates are getting short-lived, and revocation is changing. The CA/Browser Forum cut the maximum lifetime of public certificates to 200 days from March 2026, on a path to 47 days by 2029. Let's Encrypt issues 90-day certificates and moved from OCSP to CRLs in 2025. Manual renewal is no longer a workable process. Monitor expiry for every certificate in a chain, including internal CAs and mTLS client certificates, which have their own lifetimes.

HTTP/2 has an abuse history worth knowing. "Rapid Reset" (CVE-2023-44487, 2023) opened streams and cancelled them immediately with RST_STREAM. Cancelled streams don't count against MAX_CONCURRENT_STREAMS, so a single connection could make a server start unbounded work. Servers now limit reset rates. When you expose HTTP/2 directly rather than behind a CDN, those limits become your configuration to get right.

Zero trust makes TLS the identity layer inside the network. Service meshes terminate mutual TLS in sidecars or node proxies, using short-lived workload certificates (SPIFFE IDs in the SAN) rotated within hours. The chain-validation rules above apply in both directions, and an expired mesh CA fails every service at once. In-cluster latency budgets now include mTLS handshakes, so connection reuse between services matters as much as it does at the edge.

Deep dive: senior interview questions

Q1: Count the round trips for a first HTTPS request over HTTP/2, then for a second request to the same host. First: DNS (zero to several RTTs), TCP 1, TLS 1.3 1, request 1, so 3 RTT plus DNS and server time. Second, on the pooled connection: 1 RTT plus server time. Over HTTP/3 the first drops to about 2 RTT, because QUIC merges the transport and crypto handshakes.

Q2: HTTP/2 multiplexes. Why can it be slower than HTTP/1.1 on a lossy network? All its streams share one TCP byte stream, and TCP delivers in order. One lost segment stalls every stream until the retransmission arrives. Six HTTP/1.1 connections lose packets independently, so a loss stalls only one of them. HTTP/3 fixes this by doing loss recovery per stream inside QUIC.

Q3: A single large HTTP/2 download tops out around 5 Mbit/s across an ocean but is fast in-region. Why? Flow control. With the default 65,535-byte window, at most 64 KB can be outstanding per stream, so throughput ≤ window ÷ RTT, about 5.2 Mbit/s at 100 ms. Raise the stream and connection windows to at least the bandwidth-delay product.

Q4: Your service shows intermittent 502s behind a load balancer, never under steady load. Diagnose. A keep-alive timeout mismatch. When the backend's idle timeout is shorter than the LB's, the backend closes connections the LB still thinks are reusable, and requests sent into them fail. The fix is ordering: the side that reuses connections must time out first, so the backend's keep-alive must exceed the LB's idle timeout.

Q5: What exactly does TLS 1.3 0-RTT risk, and how would you allow it safely? Replay: an attacker can resend early data, and another server instance will accept it. It also lacks forward secrecy, since only the resumption PSK protects it. Allow it only for safe, idempotent requests; have the terminator mark it with Early-Data: 1; have backends answer 425 Too Early for anything else.

Q6: Where does TLS 1.3 save its round trip compared with TLS 1.2? The client sends key shares speculatively in the ClientHello, so the server can finish the key exchange in its first reply and encrypt everything after ServerHello. TLS 1.2 spent a full round trip agreeing on parameters before the key exchange. If the client guesses the wrong group, a HelloRetryRequest costs the round trip back.

Q7: A site works in Chrome but curl says "unable to get local issuer certificate". What's wrong, and who's right? The server sends only its leaf. Chrome fetched or remembered the intermediate; curl won't. curl is right: the server must send the chain. openssl s_client -showcerts proves it, and serving fullchain.pem fixes it.

Q8: Beyond "signed by a trusted CA", what does a client check on a certificate chain? Every link's signature; validity dates against the local clock; CA:TRUE, keyCertSign and path-length constraints on each issuer; name constraints; the serverAuth EKU on the leaf; the hostname against the SAN (not the CN, and wildcards cover one label); revocation and Certificate Transparency in browsers; and CertificateVerify, which proves the server holds the private key.

Q9: Why does a gRPC service behind a Kubernetes Service show one hot pod? kube-proxy balances connections, not requests. gRPC multiplexes all calls over one long-lived HTTP/2 connection per client, so each client's whole load lands on one pod. Fix it with L7 balancing, client-side balancing, or a maximum connection age.

Q10: What does curl -w '%{time_appconnect}' measure, and how do you turn the timers into phases? The time from the start of the transfer until the TLS handshake completed; all the timers are cumulative. Subtract neighbours: time_connect − time_namelookup is TCP, time_appconnect − time_connect is TLS, time_starttransfer − time_appconnect is request-to-first-byte, and time_total − time_starttransfer is the transfer.
