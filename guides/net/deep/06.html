Deep dive: what the notebook hid

The notebook picture — shout, write down the answer, forget it after a while — is right about the protocol and wrong about the cache. The kernel's neighbour table is not a notebook with an expiry date. It is a state machine. Every entry has a state, a few timestamps and a probe counter, plus a queue of packets waiting for it. The state decides whether the next packet goes out at once, waits, or is dropped.

That state machine is the reason a failover takes 3 seconds on one network and 50 on another. It explains why "flush the ARP cache" sometimes works and why it sometimes doesn't. And it is why an incident can show "No route to host" when the routing table is fine.

The notebook also hid who else keeps one. A frame's path depends on at least three caches: the sender's neighbour table, the switch's MAC address table, and often a router's ARP table. Each has its own timers. In a cloud VPC there is a fourth party, the hypervisor, which answers ARP itself and ignores everything you say. The sections below cover the state machine, what it looks like on the wire, its numbers, how it fails, and the places in 2026 where ARP is quietly faked.

Deep dive: the real mental model — a state machine per neighbour

RFC 4861 (section 7.3.2) defines neighbour unreachability detection for IPv6. Linux, Windows and the BSDs' IPv6 stacks implement it. Linux and Windows also run the same machine for IPv4 ARP. On Linux it lives in the generic neighbour subsystem (net/core/neighbour.c), with one table for ARP and one for NDP.

Each entry holds roughly this:

Field What it is
state INCOMPLETE, REACHABLE, STALE, DELAY, PROBE, or Linux's FAILED (plus PERMANENT and NOARP for static and point-to-point entries)
lladdr the cached MAC address, if any
confirmed last time something proved the neighbour is alive
used last time a packet was sent through this entry
updated last time the state or address changed
probes solicitations sent in the current round
queue packets waiting for resolution, bounded by unres_qlen_bytes

The states mean exactly this:

  • INCOMPLETE. A packet needs this neighbour and there is no MAC. The kernel queues the packet and broadcasts a request (multicast for NDP). It retries every retrans_time (1 s) up to mcast_solicit (3) times.
  • REACHABLE. The neighbour was confirmed less than reachable_time ago. Packets go straight out with no further checks. reachable_time is randomised between 0.5 and 1.5 × base_reachable_time (30 s), so 15 to 45 seconds. The randomness stops every host on a LAN from re-probing in lockstep.
  • STALE. The MAC is still believed but nobody has confirmed it recently. Nothing happens in this state. No probe is sent until a packet actually needs the entry. An idle STALE entry costs no traffic at all.
  • DELAY. A packet was just sent on a STALE entry. The packet goes out at once to the cached MAC, and the kernel waits delay_first_probe_time (5 s) for proof of life from upper layers before spending a probe.
  • PROBE. No proof arrived. The kernel sends unicast requests to the cached MAC, ucast_solicit (3) of them, one second apart. Packets keep flowing to the cached MAC meanwhile.
  • FAILED (Linux). Probing got no answer. Queued packets are dropped. Local senders get EHOSTUNREACH ("No route to host"), and ping prints Destination Host Unreachable from your own address. The next packet starts a new INCOMPLETE round.

The subtle part is confirmation. A neighbour is confirmed by a reply to a solicitation. It is also confirmed by upper-layer hints. When TCP sees new data acknowledged, it tells the neighbour layer that the next hop must be alive, because packets are getting through. That is why a busy TCP connection never generates ARP traffic after the first resolution: every ACK resets confirmed. UDP has no such signal unless the application passes MSG_CONFIRM to sendmsg. So a UDP-only flow on Linux walks REACHABLE → STALE → DELAY → PROBE about once per reachable_time, which costs one unicast ARP exchange each time.

Two other inputs move entries, and both matter for failover. An ARP request from a neighbour updates its existing entry with the sender's MAC; if the MAC changed, the entry goes to STALE with the new address. A gratuitous ARP is exactly such a request. So on Linux a GARP updates an existing entry, and the next packet goes to the new MAC at once. It does not create an entry unless arp_accept is set (default 0). And locktime (1 s by default) blocks a second change within one second of the last one, so when two hosts answer, the first answer holds.

The ladder hides a trap. Confirmation is about the IP, not the MAC. If the gateway's IP moves to a new box with a new MAC and nobody sends a GARP, the old entry stays REACHABLE until its timer runs out. Packets go to a dead MAC the whole time, because nothing in REACHABLE checks anything. The simulator below plays that out with the Linux defaults.

"""Simulate the Linux/RFC 4861 neighbour state machine for one gateway entry.

Constants are Linux defaults (net.ipv4.neigh.default.*), which match RFC 4861.
Scenario: resolve, talk, go idle, reuse, then the gateway's MAC changes with
no gratuitous ARP. How long are packets sent to a dead MAC?
"""
import random

BASE_REACHABLE = 30.0    # base_reachable_time_ms / 1000
DELAY_FIRST    = 5.0     # delay_first_probe_time
RETRANS        = 1.0     # retrans_time_ms / 1000
MCAST_SOLICIT  = 3
UCAST_SOLICIT  = 3
TICK           = 0.01

rng = random.Random(4861)
reachable_time = rng.uniform(0.5, 1.5) * BASE_REACHABLE   # re-randomised periodically in Linux
print(f"reachable_time this run: {reachable_time:.1f} s (uniform 15..45 s)\n")

gw_mac = "52:54:00:00:00:01"     # who really owns 10.0.0.1 right now
gw_alive = {gw_mac}

class Entry:
    state, mac, confirmed, used, timer, probes = "NONE", None, 0.0, 0.0, None, 0

e = Entry()
log = []
def go(t, state, why):
    if state != e.state:
        log.append(f"t={t:7.2f}  {e.state:<10} -> {state:<10} {why}")
    e.state = state

def solicit(t, unicast):
    """Send a solicitation; return the MAC that answered (or None)."""
    if unicast:
        return e.mac if e.mac in gw_alive else None   # only the cached MAC hears it
    return gw_mac if gw_mac in gw_alive else None      # broadcast: current owner answers

def answer(t, mac):
    note = " (MAC changed!)" if e.mac and mac != e.mac else ""
    e.mac, e.confirmed, e.probes = mac, t, 0
    go(t, "REACHABLE", f"reply from {mac}{note}")
    e.timer = t + reachable_time

sent_to = {"ok": 0, "dead": 0, "dropped": 0}
def app_send(t):
    e.used = t
    if e.state in ("NONE", "FAILED"):
        go(t, "INCOMPLETE", "packet queued, broadcast solicit #1")
        e.probes, e.timer = 1, t + RETRANS
        mac = solicit(t, False)
        if mac: answer(t + 0.0004, mac)
        return
    if e.state == "INCOMPLETE":
        return                      # queued behind resolution
    if e.state == "STALE":
        go(t, "DELAY", "packet sent on stale entry; wait for confirmation")
        e.timer = t + DELAY_FIRST
    if e.mac in gw_alive:
        sent_to["ok"] += 1
        e.confirmed = t + 0.002     # reply arrives -> TCP progress confirms neighbour
    else:
        sent_to["dead"] += 1

def timers(t):
    if e.timer is None or t < e.timer:
        return
    if e.state == "REACHABLE":
        if t < e.confirmed + reachable_time:
            e.timer = e.confirmed + reachable_time
        elif t < e.used + DELAY_FIRST:
            go(t, "DELAY", "reachable_time expired, recently used"); e.timer = t + DELAY_FIRST
        else:
            go(t, "STALE", "reachable_time expired, idle"); e.timer = None
    elif e.state == "DELAY":
        if e.confirmed >= e.timer - DELAY_FIRST:
            go(t, "REACHABLE", "upper layer confirmed"); e.timer = e.confirmed + reachable_time
        else:
            go(t, "PROBE", f"unicast solicit #1 to {e.mac}")
            e.probes, e.timer = 1, t + RETRANS
            mac = solicit(t, True)
            if mac: answer(t + 0.0003, mac)
    elif e.state in ("PROBE", "INCOMPLETE"):
        limit = UCAST_SOLICIT if e.state == "PROBE" else MCAST_SOLICIT
        if e.probes >= limit:
            go(t, "FAILED", f"{e.probes} solicits unanswered"); e.timer = None
            return
        e.probes += 1
        log.append(f"t={t:7.2f}  {e.state:<10}    {'unicast' if e.state == 'PROBE' else 'broadcast'} solicit #{e.probes}")
        e.timer = t + RETRANS
        mac = solicit(t, e.state == "PROBE")
        if mac: answer(t + 0.0003, mac)

def traffic(t):
    if 0 <= t < 10:   return True       # busy for 10 s
    if abs(t - 120) < TICK / 2: return True   # one packet after a long idle
    if t >= 150:      return round(t * 100) % 50 == 0   # steady stream, every 0.5 s
    return False

last_dead = None
first_dead = None
for i in range(int(320 / TICK)):
    t = i * TICK
    if abs(t - 200) < TICK / 2:
        gw_mac = "52:54:00:00:00:02"; gw_alive = {gw_mac}
        log.append(f"t={t:7.2f}  ** failover: 10.0.0.1 moves to {gw_mac}, no gratuitous ARP **")
    timers(t)
    if traffic(t):
        before = sent_to["dead"]
        app_send(t)
        if sent_to["dead"] > before:
            first_dead = first_dead or t
            last_dead = t

print("\n".join(log))
print(f"\npackets to dead MAC: {sent_to['dead']}, from t={first_dead:.2f} to t={last_dead:.2f}"
      f" -> blackhole {last_dead - first_dead + 0.5:.1f} s")

Real output on CPython 3.13:

t=   0.00  INCOMPLETE -> REACHABLE  reply from 52:54:00:00:00:01
t=  52.82  REACHABLE  -> STALE      reachable_time expired, idle
t= 120.00  STALE      -> DELAY      packet sent on stale entry; wait for confirmation
t= 125.00  DELAY      -> REACHABLE  upper layer confirmed
t= 200.00  ** failover: 10.0.0.1 moves to 52:54:00:00:00:02, no gratuitous ARP **
t= 242.33  REACHABLE  -> DELAY      reachable_time expired, recently used
t= 247.33  DELAY      -> PROBE      unicast solicit #1 to 52:54:00:00:00:01
t= 248.33  PROBE         unicast solicit #2

t= 250.33  PROBE      -> FAILED     3 solicits unanswered
t= 250.50  FAILED     -> INCOMPLETE packet queued, broadcast solicit #1

Follow the timeline. The entry spent t=10 to t=120 going quietly STALE and costing nothing. At t=120 one packet went out at once on the stale MAC, and the reply confirmed it within the 5-second DELAY window, so no probe was ever sent. Then the failover. The entry had just been confirmed, so it stayed REACHABLE for another 42.3 s, the full reachable_time measured from the last confirmation at about t=199.5. Then came 5 s of DELAY and 3 s of unicast probes to a MAC that no longer exists. Only FAILED forced a broadcast, and the broadcast found the new owner.

Worst case with Linux defaults is about 45 + 5 + 3 = 53 s. Best case, if the entry happened to be STALE at failover, is about 5 + 3 = 8 s. One gratuitous ARP from the new owner would have updated the entry at t=200 and cut the blackhole to a few milliseconds. That gap is the whole argument for GARP.

The simulator is a model, not the kernel. It skips the periodic re-randomisation of reachable_time, the garbage collector and app_solicit. The shape of the timeline is the real one.

Deep dive: what the wire and the kernel actually show

The neighbour table, with its timers

On Linux, ip -s neigh prints each entry's state and its three ages (illustrative, from a host at 10.0.0.11 — your output will differ):

$ ip -s neigh show dev eth0
10.0.0.1 lladdr 52:54:00:00:00:01 ref 1 used 0/0/0 probes 1 REACHABLE
10.0.0.21 lladdr 52:54:00:aa:00:21 used 412/407/377 probes 0 STALE
10.0.0.30 lladdr 52:54:00:aa:00:30 ref 1 used 2/38/2 probes 0 DELAY
10.0.0.99  used 9/1209/6 probes 3 FAILED

used a/b/c is seconds since the entry was last used, last confirmed and last updated. Read 10.0.0.30: used 2 s ago, confirmed 38 s ago. A packet just went out on an old confirmation, so it is in DELAY and will probe in about 3 s unless TCP confirms it first. 10.0.0.99 has no lladdr and three probes spent: something keeps trying to reach a host that isn't there. ip monitor neigh streams the transitions live, which is the best way to watch a failover.

The knobs are per interface, under /proc/sys/net/ipv4/neigh/<dev>/ (and ipv6):

$ sysctl net.ipv4.neigh.eth0 | grep -E 'reach|delay|retrans|solicit|locktime'
net.ipv4.neigh.eth0.app_solicit = 0
net.ipv4.neigh.eth0.base_reachable_time_ms = 30000
net.ipv4.neigh.eth0.delay_first_probe_time = 5
net.ipv4.neigh.eth0.locktime = 100
net.ipv4.neigh.eth0.mcast_resolicit = 0
net.ipv4.neigh.eth0.mcast_solicit = 3
net.ipv4.neigh.eth0.retrans_time_ms = 1000
net.ipv4.neigh.eth0.ucast_solicit = 3

locktime is in hundredths of a second, so 100 is the 1 s mentioned above.

macOS is simpler for IPv4. Its ARP entries just expire, after net.link.ether.inet.max_age seconds (1200 by default, so 20 minutes), with a refresh attempt before expiry. Its IPv6 table does run the RFC 4861 machine, and ndp -an shows the state letter (run on your Mac — your output will differ):

$ arp -an
? (192.168.1.1) at a0:36:bc:12:34:56 on en0 ifscope [ethernet]
? (192.168.1.40) at 8c:3b:ad:11:22:33 on en0 ifscope [ethernet]
$ ndp -an
Neighbor                        Linklayer Address  Netif Expire    S Flags
fe80::a236:bcff:fe12:3456%en0   a0:36:bc:12:34:56    en0 23h59m58s S R
fe80::1c2b:3aff:fe4d:5e6f%en0   1e:2b:3a:4d:5e:6f    en0 4s        R

S is the state column: R reachable, S stale, D delay, P probe, I incomplete. The trailing R in Flags marks a router. The long expiry on the stale router entry is typical: a stale entry sits until it is used or garbage-collected.

Line by line:

  1. Broadcast request from an INCOMPLETE entry. length 42 is 14 bytes of Ethernet header plus 28 of ARP. Outgoing frames are captured before the NIC pads them, so they show 42.
  2. Unicast reply, 412 µs later. Received frames show length 60 (padded to the Ethernet minimum, FCS not counted) and an ARP length 46 that includes the 18 padding bytes. Mismatched lengths between your own and others' frames are normal, not corruption.
  3. Unicast request at 10:02:05. The destination is the gateway's MAC, not broadcast. This is the PROBE state re-checking a cached MAC: it went STALE, a packet put it in DELAY at 10:02:00, and nothing confirmed it within 5 s. Seeing unicast ARP to the gateway every minute or so from a UDP-heavy host is normal.
  4. The probe's reply moves the entry back to REACHABLE.
  5. Gratuitous ARP from router B: sender IP equals target IP, broadcast destination, target MAC zero (tcpdump prints the target MAC in parentheses only when it is non-zero). This is the RFC 5227 "ARP announcement" form. Every host with a 10.0.0.1 entry rewrites it to …:00:02 and goes STALE. The switches learn …:00:02's port from the source MAC at the same moment.
  6. A second announcement one second later. Keepalived and most VRRP stacks repeat GARPs on purpose, because one broadcast is easy to lose during exactly the kind of event that causes a failover.
  7. An RFC 5227 probe from a host that just got 10.0.0.77 from DHCP. tell 0.0.0.0 is the tell: the host asks whether anyone already has 10.0.0.77 without claiming it, so nobody's cache is touched. Its own MAC still appears as the Ethernet source and in the ARP sender hardware field. If a reply comes back, the DHCP client declines the lease.

The same frames, built byte by byte, show how little separates them. The "GARP reply form" is the older style some devices send instead of an announcement; RFC 5227 recommends the request form, but receivers accept both:

"""Build the three 'special' ARP frames, then run an arpwatch-style detector."""
import ipaddress
import struct
from collections import defaultdict

BCAST, ZERO = b"\xff" * 6, b"\x00" * 6
def mac(s): return bytes.fromhex(s.replace(":", ""))
def ip4(s): return ipaddress.IPv4Address(s).packed
def hexmac(b): return ":".join(f"{x:02x}" for x in b)

def arp_frame(eth_dst, sha, spa, tha, tpa, oper):
    eth = eth_dst + sha + struct.pack("!H", 0x0806)
    arp = struct.pack("!HHBBH6s4s6s4s", 1, 0x0800, 6, 4, oper, sha, spa, tha, tpa)
    frame = eth + arp
    return frame + b"\x00" * (60 - len(frame))   # pad to Ethernet minimum (FCS not shown)

me, vip = mac("52:54:00:aa:00:02"), "10.0.0.50"
frames = {
    "RFC 5227 probe":        arp_frame(BCAST, me, ip4("0.0.0.0"), ZERO, ip4(vip), 1),
    "announcement (GARP-rq)": arp_frame(BCAST, me, ip4(vip), ZERO, ip4(vip), 1),
    "GARP reply form":        arp_frame(BCAST, me, ip4(vip), me, ip4(vip), 2),
}
for name, f in frames.items():
    oper, sha, spa, tha, tpa = struct.unpack("!H6s4s6s4s", f[20:42])
    print(f"{name:<23} {len(f)} B  oper={oper} spa={ipaddress.IPv4Address(spa)!s:<9} "
          f"tha={hexmac(tha)} tpa={ipaddress.IPv4Address(tpa)}")
print("bytes 14..41 of the announcement:", frames["announcement (GARP-rq)"][14:42].hex(" "))

# --- detector: (seconds, sender IP, sender MAC) as a sniffer would log them ---
OBS = [
    (0.0,  "10.0.0.1",  "52:54:00:00:00:01"),   # real gateway
    (0.4,  "10.0.0.21", "52:54:00:aa:00:21"),
    (31.0, "10.0.0.1",  "52:54:00:00:00:01"),
    (60.2, "10.0.0.66", "52:54:00:bb:00:66"),   # attacker's own address
    (61.0, "10.0.0.1",  "52:54:00:bb:00:66"),   # forged: gateway is at attacker
    (61.2, "10.0.0.1",  "52:54:00:00:00:01"),   # real gateway answers a request
    (62.0, "10.0.0.1",  "52:54:00:bb:00:66"),
    (63.0, "10.0.0.1",  "52:54:00:bb:00:66"),
    (90.0, "10.0.0.50", "52:54:00:aa:00:01"),   # VIP on node A
    (95.0, "10.0.0.50", "52:54:00:aa:00:02"),   # failover to node B, then quiet
]
last, flips, owners = {}, defaultdict(list), defaultdict(set)
for t, ip_, m in OBS:
    owners[m].add(ip_)
    if ip_ in last and last[ip_][1] != m:
        flips[ip_].append(t)
        print(f"t={t:5.1f} CHANGE  {ip_:<10} {last[ip_][1]} -> {m}")
    last[ip_] = (t, m)
for ip_, ts in flips.items():
    verdict = "FLIP-FLOP: two live claimants (spoofing or duplicate IP)" if len(ts) >= 2 else "single move (failover?)"
    print(f"{ip_:<10} {len(ts)} change(s): {verdict}")
for m, ips in owners.items():
    if len(ips) > 1:
        print(f"{m} claims {sorted(ips)} -> one MAC, many IPs (router, proxy ARP, or attacker)")

The detector half is how arpwatch and switch-side tools think. A failover changes an IP's MAC once and then goes quiet. Spoofing changes it back and forth, because the real owner keeps answering and the attacker keeps re-poisoning. One MAC claiming several IPs is the other signal. It is normal for a router or a proxy-ARP box, and suspicious for anything else, especially when one of the IPs is the gateway.

NDP on the wire

IPv6 does the same job over ICMPv6. A Neighbor Solicitation to the solicited-node group and its advertisement, abridged from tcpdump -nn -v icmp6 (illustrative):

IP6 (hlim 255, next-header ICMPv6 (58) payload length: 32) 2001:db8:7::11 > ff02::1:ff00:1: [icmp6 sum ok] ICMP6, neighbor solicitation, length 32, who has 2001:db8:7::1
      source link-address option (1), length 8 (1): 52:54:00:aa:00:0b
IP6 (hlim 255, next-header ICMPv6 (58) payload length: 32) 2001:db8:7::1 > 2001:db8:7::11: [icmp6 sum ok] ICMP6, neighbor advertisement, length 32, tgt is 2001:db8:7::1, Flags [router, solicited, override]
      destination link-address option (2), length 8 (1): 52:54:00:00:00:01

Two details carry real weight. The hop limit is 255, and receivers must drop NDP with any other value (RFC 4861). A packet that crossed a router would have 254 or less, so a remote attacker cannot inject NDP. And the Flags line is the state machine's input: solicited makes the entry REACHABLE, while an unsolicited NA with override just updates the MAC and leaves the entry STALE, which is NDP's version of a gratuitous ARP.

Deep dive: by the numbers

Parameter RFC 4861 Linux default Notes
Base reachable time 30 s base_reachable_time_ms = 30000 actual value random in 15–45 s; Windows uses the same base
Delay before first probe 5 s delay_first_probe_time = 5
Retransmit interval 1 s retrans_time_ms = 1000 an IPv6 RA can override it per link
Broadcast/multicast solicits 3 mcast_solicit = 3
Unicast solicits 3 ucast_solicit = 3
Flap lock n/a locktime = 100 (1 s)
GC soft limits n/a gc_thresh1 128, gc_thresh2 512 below thresh1, nothing is collected
Hard table limit n/a gc_thresh3 = 1024 per table (ARP, NDP), per network namespace
macOS ARP lifetime n/a net.link.ether.inet.max_age = 1200 s

Defaults vary by kernel version and distribution, and many cloud images raise the GC thresholds. Treat the table as "what you get if nobody changed anything" and check with sysctl.

Worked: how long does a failover take? VRRP is defined in RFC 3768 (v2) and RFC 5798 (v3). The backup declares the master dead after the master down interval: 3 × advertisement interval + skew time. With a 1 s interval, skew = (256 − priority) / 256 seconds. With a 1 s interval and priority 100, that is 3 + 156/256 = 3.61 s. The new master then sends GARPs. Hosts with an existing entry switch on the first GARP. So the outage is about 3.6 s plus a GARP round, and none of it is ARP timeout. Without the GARP, add 8–53 s from the simulator on Linux hosts, and up to 20 minutes on a stack that only expires entries. VRRP also uses a virtual MAC, 00:00:5e:00:01:VRID, so with VRRP the MAC doesn't even change on failover. The GARP's real job there is teaching the switches which port the virtual MAC now lives on.

Worked: the cost of broadcast. A flat /21 with 2,000 hosts, each sending one ARP broadcast every 30 s on average, produces about 67 broadcasts per second. Every host's NIC passes every one of them up to the kernel. At 60 bytes each that is about 32 kbit/s, which is nothing on the wire, but 67 interrupts per second on every sleeping laptop, phone and IoT device is not nothing. That is the real reason big L2 domains are a bad idea. It is also why NDP uses solicited-node multicast. A 2,000-host IPv6 LAN spreads its solicitations over many multicast groups, and a NIC filters out groups it hasn't joined in hardware.

Worked: the queue. While an entry is INCOMPLETE, packets wait in its queue. Linux bounds it by unres_qlen_bytes, which defaults to roughly the default socket buffer size, around 200 KB on most systems. A fast sender hitting an unresolved neighbour fills that in milliseconds, and the excess is dropped silently. ip -s ntable show reports it as unresolved discards. After three seconds of no reply the whole queue is dropped on the way to FAILED.

Deep dive: production failure modes

1. Failover that takes a minute instead of seconds

Symptom. Keepalived, Pacemaker or a load balancer pair fails over and the logs say the new node took the VIP in 2 s, but clients see 30–60 s of timeouts. Some clients recover early and some late.

Mechanism. The new owner didn't send a GARP, sent it before its interface was up, or sent it into a network that dropped it. Clients with REACHABLE entries keep sending to the old MAC until their own state machine walks through DELAY and PROBE, and that takes 8–53 s depending on where each client was in its cycle. That spread is why "some recover early." Routers and firewalls are often worse: many ignore GARP for entries they didn't ask for, as anti-spoofing policy.

Prove it. Capture on a client during a test failover: sudo tcpdump -nn -e -i eth0 arp and host 10.0.0.50. No who-has 10.0.0.50 tell 10.0.0.50 from the new MAC means no GARP. On a client, ip monitor neigh shows whether the entry changed on the GARP or only after PROBE → FAILED.

Fix. Make the new owner announce: keepalived does it by default and its vrrp_garp_* settings control repeats and delays, and arping -U -c 3 -I eth0 10.0.0.50 (iputils) does it by hand. Use a virtual MAC where the platform supports it, so caches never need to change. Check whether the upstream router honours GARP.

2. "neighbor table overflow"

Symptom. Random connection failures on a busy host, and dmesg shows neighbour: arp_cache: neighbor table overflow! (ndisc_cache for IPv6). Often a Kubernetes node, a NAT gateway VM or a host on a huge flat subnet.

Mechanism. The table hit gc_thresh3 (1024 by default). A Kubernetes node on a routed CNI may have an entry for every local pod's veth peer and every peer node. A host on a /16 talking to thousands of neighbours can blow through 1,024 entries. Once the table is full, new neighbours can't be resolved, and packets to them fail as if the host were down.

Prove it. ip -4 neigh show | wc -l (and ip -6) against sysctl net.ipv4.neigh.default.gc_thresh3. The overflow message is rate-limited, so its absence isn't proof; count entries.

Fix. Raise the thresholds with headroom over the real neighbour count, for example gc_thresh1=8192, gc_thresh2=32768, gc_thresh3=65536. Many managed Kubernetes node images already do. Then ask why one host has that many L2 neighbours.

3. ARP flux: the wrong interface answers

Symptom. A host with two NICs on the same subnet, or an LVS direct-routing real server with the VIP on loopback, receives traffic on the wrong interface. Or the load balancer is bypassed and every client hits one real server.

Mechanism. Linux treats IP addresses as belonging to the host, not the interface. With the default arp_ignore=0, it answers an ARP request for any local address on any interface, including a VIP on lo. With arp_announce=0, it may use any local address as the source of its own ARP requests, which teaches neighbours the wrong mapping.

Prove it. tcpdump -e arp on the real server shows it replying 10.0.0.50 is-at <its own NIC MAC> for the VIP it should never claim.

Fix. On LVS-DR real servers, the classic settings are net.ipv4.conf.all.arp_ignore=1 (reply only if the target address is on the receiving interface) and arp_announce=2 (always use the best local address for the outgoing interface). For multi-NIC hosts, combine them with policy routing so each NIC's traffic leaves by its own interface.

4. ARP spoofing on a "trusted" LAN

Symptom. Intermittent TLS certificate errors, slow throughput through one host, or the detector above reporting the gateway's MAC flip-flopping. Often there is no symptom at all, which is the point.

Mechanism. ARP has no authentication. An attacker on the segment sends unsolicited replies, "10.0.0.1 is-at attacker-MAC", every second or two. On Linux, an unsolicited reply only updates an existing entry, but every host on the LAN has an entry for the gateway. The victim's cache flips to the attacker, the attacker forwards traffic on to the real gateway to stay invisible, and it now sits in the middle. The repeated sending beats the real gateway's occasional replies and locktime's one-second window.

Prove it. arp -an (or ip neigh) shows two IPs, one of them the gateway, with the same MAC. tcpdump -e arp shows a stream of unsolicited replies for the gateway's IP from a MAC that isn't the gateway. arpwatch logs flip flop.

Fix. At the switch: DHCP snooping plus Dynamic ARP Inspection (DAI) drops ARP whose IP/MAC pair isn't in the snooping binding table. For IPv6, RA Guard (RFC 6105) and ND inspection do the same job. On the hosts, a static ARP entry for the gateway helps on small, fixed networks. And above all, end-to-end encryption: TLS, SSH and WireGuard turn a successful spoof into a denial of service instead of a data leak. That is the zero-trust stance: assume the LAN is hostile, because ARP makes it so.

5. Proxy ARP hides a misconfiguration until it doesn't

Symptom. A host with the wrong subnet mask, say /16 on a /24 network, has worked for years. Then a router is replaced or hardened and the host can reach only its own /24.

Mechanism. With the /16, the host thinks 10.10.5.9 is on-link and ARPs for it directly. The old router had proxy ARP on (Cisco IOS enables it by default on interfaces; Linux has net.ipv4.conf.<dev>.proxy_arp) and answered with its own MAC for any address it had a route to. The host's mistake was silently routed. The new router doesn't proxy, nobody answers, and the entries go FAILED.

Prove it. On the host, arp -an shows many different off-subnet IPs all mapped to the router's MAC: the one-MAC-many-IPs signal again. After the change, those same IPs show (incomplete).

Fix. Correct the mask. Turn proxy ARP off on routers unless something depends on it on purpose, and find out what does before you turn it off.

Something does depend on it on purpose in many Kubernetes clusters. Calico gives each pod a default route to 169.254.1.1, an address that exists nowhere, and enables proxy_arp on the host side of each pod's veth. The pod ARPs for 169.254.1.1, and the host answers with its veth MAC, ee:ee:ee:ee:ee:ee. Every packet the pod sends goes to the host, where ordinary routing takes over. Proxy ARP as an architectural choice, not an accident.

6. Neighbour-cache exhaustion from scanning

Symptom. A router's CPU spikes, legitimate new neighbours fail to resolve, and the logs show huge numbers of INCOMPLETE entries.

Mechanism. Traffic arrives for addresses in a connected subnet that nobody is using. The router must ARP or NDP for each one ("glean"), which creates an INCOMPLETE entry and queues the packet. On IPv4 a /24 bounds the damage at 254 entries. On an IPv6 /64, a scanner can name 2^64 different addresses, and every one of them costs the router an entry and three solicitations. RFC 6583 describes the attack.

Prove it. The router's neighbour table full of incomplete entries for sequential or random addresses; on Linux, ip -6 neigh show nud incomplete | wc -l.

Fix. Control-plane policing that rate-limits glean traffic, platform limits on unresolved entries per interface, and longer prefixes on links that don't need a /64: /127 for point-to-point (RFC 6164) is partly motivated by exactly this.

Deep dive: 2026 context — where ARP is faked

Most packets in 2026 never meet a real ARP responder. They meet a hypervisor or a smart NIC that answers from a database. If you carry the LAN mental model into a cloud VPC, failover designs break in confusing ways.

Cloud VPCs answer ARP themselves. An AWS VPC, an Azure virtual network and a Google Cloud VPC are not broadcast domains. There is no broadcast and, by default, no multicast. When a VM ARPs, the host's virtual switch (on AWS, the Nitro card) intercepts the request and answers from the VPC's mapping of IP to instance. The target VM never sees it. Azure makes this obvious: neighbours, including the gateway, show up with the MAC 12:34:56:78:9a:bc, the host's stand-in. AWS answers with the MAC of the destination's network interface. Google Cloud has historically configured guests with a /32 address and a route via the gateway, so a guest sends everything to the gateway's MAC and on-link ARP to peers barely happens.

So gratuitous ARP moves nothing. A keepalived pair in a VPC can send GARPs all day. The mapping database doesn't learn from them, and the hypervisor drops or ignores them. Moving a VIP in the cloud is an API call: reassign the secondary private IP to the other instance's interface, move an Elastic IP, or rewrite a route table entry to point at the new instance. That is what Pacemaker's AWS resource agents and keepalived notify scripts do. Failover time is then API latency plus propagation, typically seconds, and it should be measured, not assumed. The managed alternative is to put a cloud load balancer in front and stop moving IPs at all.

Source/destination checks are ARP's cousin. The hypervisor also drops packets whose source or destination IP isn't assigned to the VM's interface. A VM acting as a router or NAT must have that check disabled, or its forwarded packets vanish. It is the same database answering a different question: does this address belong here?

Data-centre fabrics suppress ARP. In EVPN-VXLAN fabrics, each leaf switch learns IP/MAC bindings from its local ports and distributes them in BGP (EVPN type-2 routes). When a host ARPs, its own leaf answers from that table and the broadcast never crosses the fabric. This ARP suppression is how a "stretched L2" across hundreds of racks avoids becoming one enormous broadcast domain. It also means a GARP after a VM moves is turned into a BGP update, and how fast that update converges is your failover time.

Kubernetes uses ARP in three different ways. Calico's proxy ARP (above) makes every pod's first hop the host. MetalLB and kube-vip in L2 mode do the opposite: one node answers ARP for a Service's external IP and sends GARPs when leadership moves, so they inherit every LAN failover issue in this section. Those issues include upstream routers that ignore GARP and the 8–53 s tail on Linux clients. And overlay CNIs (VXLAN, Geneve) often pre-populate neighbour entries as PERMANENT from the control plane, so ARP for remote pods is never sent at all.

IPv6 closes one old gap. Routers traditionally ignored unsolicited NAs for neighbours they had no entry for. A new host's first inbound packets waited on the router's own resolution, or were dropped. RFC 9131 (2021) lets routers create STALE entries from unsolicited NAs, so a host can announce itself the way GARP always allowed. Support is growing in router software; check yours.

Deep dive: senior interview questions

Q1: Name the neighbour states and say which ones send packets on the wire.

INCOMPLETE sends broadcast (or solicited-node multicast) solicitations, 3 at 1 s intervals. PROBE sends unicast solicitations to the cached MAC, also 3 at 1 s. REACHABLE, STALE and DELAY send no ARP at all. STALE costs nothing until a packet uses it. DELAY waits 5 s for an upper-layer confirmation before spending a probe. FAILED (Linux) sends nothing; it drops the queue and reports unreachable.

Q2: Why does a long-lived TCP connection generate no ARP traffic, but a UDP metrics sender generates a unicast ARP exchange about every 30 seconds?

TCP confirms the neighbour whenever acknowledgements show forward progress, so the entry stays REACHABLE indefinitely. UDP gives the kernel no such signal unless the application uses MSG_CONFIRM. The entry expires to STALE, the next send moves it to DELAY, and after 5 s without confirmation a unicast probe goes out and the reply confirms it.

Q3: A VIP fails over and clients take 40 seconds to follow. The new node "definitely" sent a GARP. What could be going on?

Clients only update entries they already have, and a GARP sent before the interface was up, or into a VLAN they're not on, never reached them. The upstream router may ignore unsolicited ARP as anti-spoofing policy, so off-subnet clients wait for the router's cache. Or this is a cloud VPC, where GARP is ignored entirely and the IP has to be moved by API. Capture on a client, and use ip monitor neigh to see when the entry actually changed.

Q4: What does arp_accept=0 mean for gratuitous ARP on Linux?

The host won't create a new entry from a GARP. It will still update an existing entry with the new MAC, putting it in STALE. Failover works for hosts that were talking to the VIP, which are the ones that matter. Hosts that weren't simply resolve normally on their next packet.

Q5: How does ARP spoofing actually work against a Linux host that ignores unsolicited replies for unknown IPs?

The attacker doesn't need to create an entry. Every host already has one for the gateway, and unsolicited replies or requests update existing entries. The attacker repeats the forged mapping every second or two, which outlasts the 1 s locktime and outnumbers the real gateway's answers. Defences: DAI with DHCP snooping on the switch, static gateway entries where practical, and encryption so a man in the middle gains nothing.

Q6: Why does an AWS VPC ignore your gratuitous ARP, and how do you build an HA VIP there?

The VPC isn't a broadcast domain. The Nitro host answers ARP from the VPC's own IP-to-interface mapping, and nothing a guest broadcasts changes that mapping. You move the IP through the API: reassign a secondary private IP, move an Elastic IP, or rewrite a route table entry to point at the new instance. Or you use a managed load balancer and don't move IPs.

Q7: What is Calico doing with 169.254.1.1?

It is a fake gateway. Every pod's default route points at it. The host side of each pod's veth has proxy ARP enabled, so the host answers for 169.254.1.1 with its own veth MAC (ee:ee:ee:ee:ee:ee). All pod traffic therefore lands in the host's routing table, which is where Calico's real routes live. No bridge, no shared L2 between pods.

Q8: Why is a /64 on a router-to-router link a security problem that a /127 isn't?

Packets to unused addresses in a connected subnet force the router to create INCOMPLETE neighbour entries and send solicitations. A /64 has 2^64 such addresses, so a scanner can exhaust the neighbour cache and the CPU (RFC 6583). A /127 has two addresses, both in use, so there is nothing to glean. RFC 6164 recommends /127 for exactly this kind of reason.
