Deep dive: a host is a stack of queues and tables

The five-layer diagram is a map of responsibilities. It tells you who answers which question. It does not tell you what the machine is made of, and that is what you need at 2 AM.

On a real host every layer is built from two kinds of state. Tables answer a question for each packet: which next hop, which MAC address, which socket, is this flow already known. Queues sit wherever one side can produce faster than the other side can consume: your process versus TCP, TCP versus the NIC, the NIC versus the CPU, the kernel versus your process again. A packet's life is a walk through about a dozen of these structures. Each one has a size, a default, a counter that ticks when it overflows, and a command that shows it.

That is the senior engineer's version of "think in layers." When checkout fails for some customers, they don't ask "is the network down?" They ask "which queue is full, or which table is wrong?" Then they read the counter that answers it. The rest of this deep dive builds that picture. It uses Linux, because that is what your servers, containers and cloud VMs run, and it gives the macOS equivalent where one exists.

Deep dive: the real mental model — tables answer, queues wait

Start with the distinction, because it predicts how each part fails.

A table is looked up once per packet (or once per flow). It fails in three ways. It can be wrong: a stale route, or an old MAC address after a failover. It can be missing an entry, so the packet waits while the kernel goes to find one, as with ARP. Or it can be full: when the conntrack or neighbour table hits its limit, new flows get dropped while old ones work fine.

A queue absorbs a rate mismatch. It fails in two ways, and the second is the sneaky one. It can overflow, and then something is dropped and a counter goes up. Or it can stay full. A full queue drops nothing, but every packet now waits behind it. That is latency with no loss, and no error log will ever mention it.

Here is the whole machine on one page.

The transmit path, step by step

Follow one send() of 10 KB on an established TCP connection.

  1. Socket send buffer. send() copies your bytes into the socket's send buffer and returns. It does not mean anything was transmitted. TCP keeps these bytes until they are acknowledged, because it may need to retransmit them. So the send buffer is both the outgoing queue and the retransmit queue. If it is full, a blocking send() sleeps and a non-blocking one returns EAGAIN.
  2. TCP decides how much may leave now. The congestion window (cwnd) and the peer's advertised receive window cap the bytes in flight. Anything beyond that cap waits in the send buffer. On Linux, TCP Small Queues also limits how many bytes one socket may have parked in the layers below, so a single bulk flow cannot fill the device queue.
  3. Route lookup. IP looks up the destination in the FIB (Linux stores it as a compressed trie). The answer is a next hop, an output device and a source address. ip route get runs exactly this lookup for you. The result also carries per-destination exceptions, such as a learned path MTU (Module 2's deep dive uses that).
  4. Conntrack. If netfilter connection tracking is loaded (it is on any host running Docker, kube-proxy in iptables mode, or a stateful firewall), the packet is matched against the conntrack table. A new flow gets an entry. NAT decisions are stored here too.
  5. Neighbour lookup. The next hop's IP must become a MAC address. The neighbour table (ARP for IPv4, ND for IPv6) holds that mapping with a state. If the entry is missing, the kernel sends an ARP request and parks the packet in a small per-entry queue until the reply arrives. If the reply never comes, the parked packets are dropped and you get EHOSTUNREACH.
  6. Qdisc. The packet joins the device's queueing discipline. This is the queue you can configure: fq_codel (the default on most current distros, set by systemd), fq (common on servers using pacing), or the old kernel default pfifo_fast. Its length limit is txqueuelen, 1000 packets by default.
  7. Driver TX ring. The driver moves packets from the qdisc into a ring of descriptors that the NIC reads by DMA. Typical rings hold 256 to 4096 descriptors. Byte Queue Limits (BQL) cap how many bytes sit in the ring, so the backlog stays in the qdisc, where a smart scheduler can manage it.
  8. NIC. The NIC fetches the bytes, can fill in checksums, can cut one large TCP send into MSS-sized segments (TSO, Module 2's deep dive), and puts bits on the wire.

The receive path, step by step

  1. RX ring. The NIC writes arriving frames by DMA into pre-allocated buffers on a receive ring. If the CPU does not refill the ring fast enough, the NIC has nowhere to put the next frame and drops it. That shows up as rx_missed or a similar driver-specific counter.
  2. NAPI poll, GRO, backlog. An interrupt wakes a softirq. The softirq then polls the ring, up to netdev_budget packets (300) or netdev_budget_usecs (2 ms) per round, instead of taking one interrupt per packet. GRO merges consecutive segments of the same flow into one large buffer. If Receive Packet Steering hands packets to another CPU, they wait in that CPU's backlog queue (netdev_max_backlog, 1000).
  3. Conntrack (PREROUTING). Same table as before. Replies match the entry created on the way out. That match is what makes a stateful firewall "stateful."
  4. Route: is it for me? The routing lookup runs again, this time against the local table. If the destination is one of the host's addresses, the packet goes up. If not, it is forwarded (if forwarding is on) or dropped.
  5. Socket lookup. TCP hashes the 4-tuple into the established-connections table. If nothing matches and the segment is a SYN, it tries the listening sockets.
  6. SYN queue and accept queue. A SYN creates a small request entry (the SYN queue). When the handshake's final ACK arrives, the connection moves to the listener's accept queue. It waits there until your process calls accept(). Its size is the smaller of the listen() backlog and net.core.somaxconn.
  7. Socket receive buffer. Data for an established connection lands here, in order, and the kernel ACKs it. The advertised window tells the sender how much room is left. If your process stops reading, the buffer fills, the window drops toward zero, and the sender stalls.
  8. read(). Your process copies the bytes out. Only now has the application "received" anything.

Notice what this does to the phrase "the server got my request." The server's kernel may have ACKed it, and the bytes may sit in a receive buffer or an accept queue for seconds. Meanwhile the application has seen nothing. Half of all "but the network says it was delivered" arguments end right here.

Deep dive: what the kernel actually shows you

The outputs below are real. They come from a small lab of Linux network namespaces: a client at 192.168.1.50, a router at 192.168.1.1, and a server at 203.0.113.10, joined by virtual Ethernet (veth) pairs. Kernel 6.18, iproute2 6.1. Your output will differ in details, not in shape.

The route lookup, done for you

$ ip route get 203.0.113.10
203.0.113.10 via 192.168.1.1 dev d02c0 src 192.168.1.50 uid 0
    cache

That one line is step 3 of the transmit path, run on demand. The destination is off-link, so the next hop is the gateway 192.168.1.1, leaving through device d02c0 with source address 192.168.1.50. The cache line is where per-destination exceptions appear. After a path-MTU event it reads cache expires 596sec mtu 1400, as Module 2's deep dive shows.

The neighbour table, with state

$ ip -s neigh show
192.168.1.1 dev d02c0 lladdr 02:00:00:00:01:01  ref 1 used 2/1/2 probes 4 REACHABLE

REACHABLE means the kernel has recent proof that the gateway is alive. That proof can be an ARP reply or, more often, TCP progress: forward progress on a connection counts as confirmation. Entries age out of REACHABLE after a randomised 15–45 s (half to one and a half times base_reachable_time_ms, default 30,000). They then go STALE, but stay usable. The next packet sent through a STALE entry moves it to DELAY (5 s), then PROBE (unicast ARP, 3 tries), and finally FAILED. The used 2/1/2 field gives seconds since last use, last confirmation and last update.

This state machine is why a failover that moves an IP to a new MAC address can take seconds to be noticed. A host keeps using the old MAC until the entry goes stale and a probe fails. That is, unless the new owner sends a gratuitous ARP, which overwrites the entry at once.

A full receive buffer, caught in the act

This is the most useful ss output you will ever read. The client is downloading a 1 MiB file with curl --limit-rate 100k, so the application reads slowly on purpose.

$ ss -tmin                                   # on the client

CLOSE-WAIT 820301 0       192.168.1.50:47170 203.0.113.10:443

     cwnd:13 bytes_sent:701 bytes_acked:702 bytes_received:1051479 ...

$ ss -tmin                                   # on the server, same instant
State      Recv-Q Send-Q Local Address:Port Peer Address:Port
FIN-WAIT-2 0      0       203.0.113.10:443  192.168.1.50:47170

Read it slowly. The server has sent everything, received the ACKs, and closed its side. As far as the server is concerned, the response is delivered. It is in FIN-WAIT-2 with nothing queued. Yet the client's kernel still holds 820,301 bytes in the receive queue (Recv-Q) that curl has not read. r926764 is the memory those bytes occupy, including per-packet overhead. rb3068538 is the buffer limit that receive autotuning grew to, about 3 MB.

Two lessons sit in this output. First, "delivered" in TCP means "in the peer's kernel," never "processed." Second, CLOSE-WAIT with a large Recv-Q is the fingerprint of an application that is not reading. That is a bug in the app, and no network change will fix it.

(This lab runs bbr as its congestion control. Most distributions default to cubic.)

The ring here is small (256) and cannot grow; the hypervisor fixes the maximum. The qdisc has dropped nothing and holds no backlog right now, which is what an idle link looks like. Column 3 is "time squeeze": the softirq ran out of budget with work still waiting. A rising column 3 is the earliest sign that a host can't keep up with its receive rate.

The accept queue, overflowed on purpose

This Python 3.13 script (stdlib only) fills two queues from user space. First it calls listen(2) and never calls accept(). Then it writes into a connection whose receiver never reads.

code/d01/host_queues.py:

"""Two kernel queues you can fill from Python: the accept queue and the socket buffers.

    python3.13 host_queues.py
Runs on localhost only. Numbers depend on OS and kernel settings.
"""
import socket
import time

# --- 1. The accept queue: finished handshakes waiting for accept() ---------
srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 0))
srv.listen(2)                      # backlog 2, and we never call accept()
port = srv.getsockname()[1]

clients, done = [], 0
for i in range(6):
    c = socket.socket()
    c.settimeout(0.5)
    try:
        c.connect(("127.0.0.1", port))
        done += 1
        result = "connected (handshake finished, sits in accept queue)"
    except (TimeoutError, socket.timeout):
        result = "timed out (server dropped the SYN: queue full)"
    clients.append(c)
    print(f"client {i}: {result}")
print(f"listen(2) held {done} finished connections before it started dropping\n")
for c in clients:
    c.close()
srv.close()

# --- 2. Socket buffers: how much a sender can write before blocking --------
lst = socket.create_server(("127.0.0.1", 0))
snd = socket.create_connection(lst.getsockname())
rcv, _ = lst.accept()
print("SO_SNDBUF (sender)  :", snd.getsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF))
print("SO_RCVBUF (receiver):", rcv.getsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF))

snd.setblocking(False)
chunk, written = b"x" * 65536, 0
deadline = time.monotonic() + 2
while time.monotonic() < deadline:
    try:
        written += snd.send(chunk)
    except BlockingIOError:      # EAGAIN: send buffer full, peer not reading
        time.sleep(0.05)         # give the receiver's autotuning a moment
        try:
            written += snd.send(chunk)
        except BlockingIOError:
            break
print(f"send() accepted {written:,} bytes with the receiver never calling recv()")
print("those bytes now live in two kernel queues: the receiver's receive buffer")
print("and the sender's send buffer. The application on each side sees none of it.")

Three details are worth a second look. Linux accepts backlog + 1 connections, so listen(2) held 3. When the queue is full, Linux silently drops the incoming SYN; it does not send a RST. So the client sees a timeout, not "connection refused." And four overflows were counted for three failed clients. The counter records every dropped handshake packet, retries included, so read it as a rate of drops rather than a count of victims. Deep dive: by the numbers

A queue's delay is its depth divided by its drain rate. This is Little's law applied to bytes, and it is the single most useful formula on this page. A txqueuelen of 1000 full-size frames is 1000 × 1514 = 1.51 MB. Draining at 10 Gbit/s, that is 1.2 ms of delay. Draining into a 20 Mbit/s home uplink, the same 1000 packets are 606 ms. The queue did not change. The drain rate did. That is bufferbloat, and it is why fq_codel and cake exist. Both watch how long packets sit (CoDel targets 5 ms) rather than how many there are.

The per-packet time budget shrinks with link speed. A full-size frame occupies 1538 byte-times on the cable (1514 + 4 FCS + 8 preamble + 12 inter-frame gap). At 10 Gbit/s that is 812,744 frames per second, or 1.23 µs per frame. At 100 Gbit/s it is 8.1 million per second, or 123 ns — about the cost of one cache miss to DRAM. No CPU core handles a separate interrupt, lookup chain and socket wake-up per frame at that rate. That is why the receive path batches (NAPI), merges (GRO), and spreads work over cores (RSS: one RX ring per queue, hashed by 4-tuple).

A socket buffer must hold one bandwidth-delay product. To keep a path full, the receive window has to cover bandwidth × RTT. For 1 Gbit/s and 80 ms that is 125,000,000 × 0.08 = 10 MB. A common distro tcp_rmem maximum is 6 MiB, and only part of the buffer becomes window, since some pays for packet overhead. So a single flow on that path tops out at roughly 6 MiB × (window share) / 0.08 s, often a few hundred Mbit/s, while the link and the far end are idle. "We have a 1 Gbit link and get 400 Mbit/s to the other region" is very often this, not the network.

Accept-queue math. A server that accepts 2,000 connections per second, with the queue capped at 128 (the pre-5.4 Linux default, and still macOS's default), has 64 ms of slack. A 100 ms garbage-collection pause or a slow accept() loop overflows it. With somaxconn = 4096 the slack is about 2 s. Remember that the effective cap is the smaller of somaxconn and the backlog your server passes to listen(). Many frameworks still pass 128 or 511.

Retransmission timing tells you which queue dropped. A dropped SYN is retried after 1 s, then 2 s, 4 s and so on (Linux's initial RTO is 1 s, per RFC 6298). So a client that sees connects take just over 1 s or just over 3 s is almost certainly losing SYNs. Usually that is an accept queue or SYN queue overflow, or a firewall. Data-segment loss on an established connection retransmits after roughly RTT + 4 × RTT variance, with a 200 ms minimum on Linux. So a request that "sometimes takes an extra 200 ms" points at a loss after the handshake.

Neighbour and conntrack limits are smaller than people think. gc_thresh3 = 1024 means a host cannot keep more than 1024 neighbour entries. A Kubernetes node with hundreds of pods on a flat network, or a router on a large /16, can hit that. Conntrack's default maximum scales with RAM and is often 65,536 to 262,144 entries. An established TCP entry lives for 5 days by default (nf_conntrack_tcp_timeout_established = 432,000 s). A busy NAT gateway or kube-proxy node can fill the table with entries for connections that ended long ago.

Deep dive: production failure modes

Each entry runs symptom → mechanism → proof → fix.

1. Connects take one second, sometimes three

Symptom. Latency graphs show a cluster at ~1,000 ms and ~3,000 ms for new connections only. Established connections are fine. CPU looks normal on average.

Mechanism. The accept queue overflows during bursts, because the app calls accept() too slowly or the backlog is small. Linux drops the SYN (or the final ACK), and the client retransmits on its 1 s timer.

Prove it.

ss -ltn 'sport = :443'          # Recv-Q = queued now, Send-Q = the cap
nstat -az TcpExtListenOverflows TcpExtListenDrops
# macOS: netstat -Lan | grep 443

Recv-Q near Send-Q on a listening socket, plus a rising ListenOverflows, is a confession.

Fix. Make accept() faster (more acceptor threads, or SO_REUSEPORT to spread one port over several listeners). Then raise both net.core.somaxconn and the application's listen() backlog. Raising only one does nothing, because the effective cap is the smaller of the two.

2. New connections fail at random; existing ones are fine

Symptom. A NAT gateway, Docker host or kube-proxy node drops a fraction of new flows. Retries usually succeed. dmesg shows nf_conntrack: table full, dropping packet.

Mechanism. The conntrack table is full. Every new flow needs an entry, so new flows die while tracked flows keep working.

Prove it.

cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
conntrack -S | head            # per-CPU insert_failed / drop counters

Fix. Raise nf_conntrack_max (and the hash size with it). Shorten timeouts for short-lived traffic. Exempt high-volume flows that need no state, such as DNS to a local cache, with a notrack rule.

3. "Neighbor table overflow" on a big flat network

Symptom. Intermittent unreachability to some hosts on the same subnet. dmesg prints neighbour: arp_cache: neighbor table overflow!.

Mechanism. More live neighbours than gc_thresh3 (1024 by default). The kernel can't create entries for new next hops, so packets to them are dropped while it tries to free some.

Prove it. ip -4 neigh | wc -l near 1024, and the message in dmesg.

Fix. Raise net.ipv4.neigh.default.gc_thresh1/2/3 (and the ipv6 equivalents) together. Or make the L2 domain smaller, which is usually the better design answer.

4. Latency spikes whenever someone uploads

Symptom. Video calls stutter and SSH lags while a backup or large upload runs. No packet loss is reported.

Mechanism. Bufferbloat. A deep FIFO sits at the bottleneck, usually the uplink of a home router or a VPN concentrator. It is full and stays full. From the numbers section: 1000 packets at 20 Mbit/s is 606 ms of standing queue.

Prove it. Run ping to the gateway's next hop before and during the upload. RTT jumping from 10 ms to hundreds of ms with no loss is the signature. On a Linux box you control, tc -s qdisc shows a large, persistent backlog.

Fix. Put an AQM qdisc (fq_codel or cake) at the bottleneck. If the bottleneck sits in a device you can't configure, shape your own egress slightly below the link rate, so the queue forms where you manage it.

5. Throughput collapses, the network graphs are clean

Symptom. A consumer falls behind. The producer's sends start blocking. Captures show win 0 from the receiver.

Mechanism. The receiving application isn't reading. Its receive buffer fills, the window closes, and TCP flow control stops the sender. This is TCP working exactly as designed.

Prove it. On the receiver, ss -tmi shows a large Recv-Q (as in the CLOSE-WAIT example above). tcpdump shows zero-window advertisements and the sender's zero-window probes.

Fix. It's the application: a blocked event loop, a slow downstream, a missing read(). Profiling the consumer will find it. Packet tuning won't.

6. Drops at high packet rates, with CPU to spare

Symptom. Under load, a receiver loses packets even though total CPU looks moderate. One core sits at 100% in softirq.

Mechanism. All receive work lands on one CPU: one RX queue, or one flow hashed to one queue. That CPU's ring or backlog overflows.

Prove it. softnet_stat columns 2 and 3 rising on one row. ethtool -S eth0 | grep -iE 'drop|miss|fifo'. mpstat -P ALL 1 showing one core high in %soft.

Fix. Use more RX queues with RSS (ethtool -L) or RPS in software, spread IRQ affinity, and enlarge the ring (ethtool -G) where the hardware allows it.

Deep dive: 2026 context

Kubernetes multiplies every table. Each pod is a network namespace with its own routing table, neighbour table, sockets and qdiscs, joined to the node by a veth pair. The node, meanwhile, holds the shared conntrack table that kube-proxy's iptables or IPVS rules depend on. So a node with 100 pods has 101 copies of most of the structures in the diagram, and one conntrack table under all of them. eBPF data planes such as Cilium replace kube-proxy's iptables rules with BPF hash maps, and often keep their own connection-tracking map. The lesson carries over directly: find that map's size limit and its "map full" counter before an incident does.

In the cloud, some queues belong to someone else. A VM's virtio, ENA or gVNIC rings are the queues you can see. Behind them sit hypervisor and SmartNIC queues and per-instance policers that you can't see. AWS's ENA driver exposes some of these as counters, with names like bw_in_allowance_exceeded, pps_allowance_exceeded and conntrack_allowance_exceeded in ethtool -S. When those rise, the drops happened outside your kernel, and no sysctl will help.

QUIC moves transport state into your process. With HTTP/3, the congestion window, the retransmit queue and the per-stream buffers live in the application's QUIC library, not in the kernel. ss shows one UDP socket with a receive queue and nothing else. The tables and queues are still there; you just debug them with the library's own stats or with qlog files instead of kernel counters.

eBPF lets you observe every box. Tools in the bcc and bpftrace collections hook the drop points directly. For example, tcpdrop, or a bpftrace probe on the skb:kfree_skb tracepoint, which since kernel 5.17 carries a drop reason. That is the modern answer to "which queue dropped it": ask the kernel to tell you at the moment of the drop.

Zero trust adds tables to every host. When a mesh sidecar or a per-host agent enforces policy, every connection passes through an extra user-space proxy. That adds one more accept queue, one more pair of socket buffers, and one more connection table per hop. Count them when a "simple" service call is slow.

Deep dive: senior interview questions

Q1: send() returned success. What do you actually know?

Only that the kernel copied your bytes into the socket's send buffer. Nothing may have left the host yet: the congestion window, the peer's receive window, or a full qdisc can all hold it back. Even after the peer ACKs the bytes, they are only in the peer's kernel receive buffer, not in its application. If you need to know the application processed something, the application has to say so. That is the end-to-end argument from Module 1, applied to one system call.

Q2: Clients report connects taking about one second under load, never 200 ms. Where do you look?

One second is the initial SYN retransmission timeout. So a SYN, or the handshake's final ACK, is being dropped. On the server, check ss -ltn for the listener's Recv-Q against its cap, and nstat for ListenOverflows/ListenDrops and TCPReqQFullDrop. If those are clean, look at conntrack (table full in dmesg) and any firewall or load balancer in the path. A loss after the handshake would show up as roughly 200 ms+ retransmissions instead, which is how you tell the two apart.

Q3: A listening socket shows Recv-Q 0 and Send-Q 4096. What do those mean? They don't mean what they mean on a connected socket.

On a listening socket, Recv-Q is the number of fully established connections waiting for accept(), and Send-Q is the accept queue's maximum. On an established socket they are bytes: unread received data and unacknowledged sent data. Mixing the two up is a common way to misread ss.

Q4: Where does latency come from on a link with zero packet loss?

From queues that are full but not overflowing. Each packet waits behind the queue's depth divided by the drain rate. A 1000-packet FIFO in front of a 20 Mbit/s uplink adds about 600 ms with no drops at all. Loss-based congestion control makes it worse, because it keeps filling the buffer until it overflows. The fixes are AQM (fq_codel, cake), delay-based or model-based congestion control, and putting the queue where you control it.

Q5: Why does Linux poll the NIC instead of taking one interrupt per packet?

At high rates, interrupt overhead alone would consume the CPU. At 10 Gbit/s with full-size frames you have about 1.2 µs per frame, and an interrupt plus context switch eats a large slice of that. NAPI takes one interrupt, disables further interrupts for that queue, and polls up to a budget (300 packets) per round. It re-enables interrupts once the ring is empty. Under load it behaves like polling; when idle, like interrupts. GRO then cuts per-packet work further by merging segments before the stack sees them.

Q6: After a database failover the VIP moved, but some app servers keep timing out for about a minute. Explain.

Those servers still have the old MAC address for the VIP in their neighbour tables. Normal traffic keeps confirming the entry as long as TCP makes progress. Once it stops, the entry still has to age to STALE, then pass through DELAY and PROBE before it fails and is re-resolved. That can take tens of seconds. The standard fix is for the new owner to send gratuitous ARP (or an unsolicited IPv6 Neighbor Advertisement) at takeover, which overwrites the entry everywhere on the segment at once. Cloud VPCs don't run real ARP this way; there, the equivalent is the provider's API remapping the address, and it has its own propagation delay.

Q7: Name a table whose overflow breaks only new connections, and explain why old ones survive.

The conntrack table (also the neighbour table for new next hops, and the accept queue for new connections to one listener). Packets of an existing flow match an entry that already exists, so they need no new allocation. Only the first packet of a new flow needs a free slot. That asymmetry — "existing users fine, new users fail" — should send you straight to tables with a fixed maximum.
