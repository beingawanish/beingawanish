Deep dive: what the street-address picture hid

The street-address model gets you through the arithmetic. It hides two things that matter the moment you run real infrastructure.

The first is the data structure. A router does not "check which street an address is on." It walks a tree of bits, keeps a finger on the most specific prefix it has passed, and stops when the bits run out. That walk is longest-prefix match, and it runs once per packet on every router, switch, kernel, and cloud hypervisor between you and the other end. Once you see the tree, a whole class of production surprises stops being surprising: the VPN that "steals" your traffic, the /32 that overrides a whole subnet, the Kubernetes service range that swallows an office.

The second is that real address plans are not one /16 carved neatly into VLANs. They are dozens of VPCs, a few clusters with pod and service ranges, a corporate network, a partner's VPN, and Docker on every laptop. All of them share one 32-bit space, and nobody owns the whole map. The hard part of subnetting in 2026 is not computing a broadcast address. It is keeping those ranges from colliding, because a collision turns into a routing decision you never meant to make.

The sections below go under Module 05's model: the trie and how kernels and ASICs implement it, what the tools print, the numbers that bound cloud and Kubernetes plans, how plans fail, and what IPv6 changes.

Deep dive: the real mental model — prefixes as a binary trie

Write every prefix as a string of bits. 10.0.0.0/8 is the 8-bit string 00001010. 10.10.0.0/16 is that string followed by 00001010 again. 0.0.0.0/0, the default route, is the empty string. Now put all the strings in a binary tree: start at the root, go left on a 0 and right on a 1, and mark the node where each prefix ends. That tree is a binary trie, and it is the honest picture of a routing table.

Lookup is a walk. Take the destination address, read its bits from the top, and follow them down the tree. Every time you pass a marked node, remember it — it is a prefix that contains the address. When the next bit has no child to follow, stop. The last marked node you passed is the answer. No sorting, no comparing prefix lengths, no "check all routes": the longest match is simply the deepest marked node on your path.

That one picture explains the rules people memorise separately:

  • The default route always matches because it sits at the root, and every walk starts at the root.
  • A more specific route wins because it is deeper on the same path. You pass the /16 before you reach the /23, so the /23 is what you remember last.
  • Route order in the table is irrelevant. The trie has no order, only depth.
  • Equal prefixes are the same node. Two routes for exactly 10.10.0.0/16 land on one node. Something else must break the tie: a metric, an administrative distance, a policy. Longest-prefix match itself has nothing to say.

A naive trie spends one node per bit, which is wasteful. The six-prefix table below needs 33 nodes, most of them single-child links. Real implementations compress those chains. A PATRICIA trie (path-compressed, also called a radix tree) stores a whole run of bits on one edge and only branches where two prefixes actually diverge. BSD and macOS route lookup uses a radix tree of this kind. Linux goes further for IPv4. Since the 2.6 era its tables have been an LC-trie (level-compressed, fib_trie). A dense node can index several bits at once and have 2^k children, so a typical lookup touches only a handful of nodes. Linux IPv6 routes live in a separate radix tree (fib6).

Hardware does the same job a different way. A switch or router ASIC holds routes in TCAM (ternary content-addressable memory). Each TCAM entry is a value plus a mask, and the chip compares the destination against every entry in parallel in one clock. Several entries can match. The chip returns the first match by physical position, so software keeps the entries sorted longest-prefix-first. That sort is where the work hides: inserting a /23 into a TCAM full of /24s and /16s may mean shuffling entries to open a slot. TCAM is fast, power-hungry and small, so modern ASICs mix it with algorithmic LPM in ordinary SRAM. Capacity varies widely by chip, and "how many routes fit" is a real purchasing question.

Here is the walk in Python. It is the one-node-per-bit version, which is slow but makes every step visible, and it is checked against a brute-force "test every prefix, keep the longest" lookup.

"""Longest-prefix match with a binary trie, checked against brute force."""
import ipaddress
import random

class Node:
    __slots__ = ("child", "route")
    def __init__(self):
        self.child = [None, None]   # next node for bit 0 / bit 1
        self.route = None           # next hop if a prefix ends here

class Trie:
    def __init__(self):
        self.root, self.nodes = Node(), 1

    def insert(self, prefix, nexthop):
        net = ipaddress.ip_network(prefix)
        bits, node = int(net.network_address), self.root
        for i in range(net.prefixlen):
            b = (bits >> (31 - i)) & 1
            if node.child[b] is None:
                node.child[b] = Node()
                self.nodes += 1
            node = node.child[b]
        node.route = (prefix, nexthop)

    def lookup(self, addr, trace=False):
        bits, node, best = int(ipaddress.ip_address(addr)), self.root, None
        depth = 0
        while node is not None:
            if node.route:
                best = node.route          # remember the deepest match so far
                if trace:
                    print(f"  depth {depth:2}: match {node.route[0]:<18} -> {node.route[1]}")
            if depth == 32:
                break
            node = node.child[(bits >> (31 - depth)) & 1]
            depth += 1
        if trace:
            print(f"  fell off the trie at depth {depth}; answer = {best[0]}")
        return best

TABLE = [
    ("0.0.0.0/0",       "igw (default)"),
    ("10.0.0.0/8",      "tgw (corp)"),
    ("10.10.0.0/16",    "local VPC"),
    ("10.10.0.0/23",    "eng VLAN"),
    ("10.10.3.128/27",  "mgmt"),
    ("10.10.3.164/30",  "WAN B"),
]

t = Trie()
for p, nh in TABLE:
    t.insert(p, nh)

for a in ("10.10.1.200", "10.10.3.166", "10.20.0.1", "192.0.2.7"):
    print(f"lookup {a}")
    t.lookup(a, trace=True)

# brute force: every matching prefix, keep the longest
nets = [(ipaddress.ip_network(p), nh) for p, nh in TABLE]
def brute(addr):
    a = ipaddress.ip_address(addr)
    m = [(n.prefixlen, (str(n), nh)) for n, nh in nets if a in n]
    return max(m)[1]

rng = random.Random(7)
probes = [str(ipaddress.ip_address(rng.getrandbits(32))) for _ in range(20000)]
probes += [str(ipaddress.ip_address(0x0A0A0000 + rng.getrandbits(10))) for _ in range(20000)]
bad = sum(t.lookup(a) != brute(a) for a in probes)
print(f"\n{len(probes)} random lookups, {bad} disagreements with brute force")
print(f"trie nodes for {len(TABLE)} prefixes: {t.nodes} (uncompressed, one per bit)")

Read the 10.10.1.200 trace against Module 05's "Worked 7". The trap answer there was "10.10.1.200 is unallocated." The trie shows why it isn't: the /23 node sits at depth 23, and the address's 24th bit is never consulted. Look at 10.20.0.1 too. It matches 10.0.0.0/8, then 10.10 and 10.20 part ways after 11 matching bits, and the walk ends at depth 12. That is the whole of LPM: walk until you can't, answer with what you last saw.

Deep dive: what the kernel actually does

You never need to guess which route wins. Every OS will run the lookup for you and print the result. On Linux, ip route get asks the kernel's FIB the exact question a packet would (illustrative output from a host at 10.10.0.5 — your output will differ):

$ ip route show
default via 10.10.0.1 dev eth0 proto dhcp src 10.10.0.5 metric 100
10.0.0.0/8 via 10.10.0.254 dev eth0
10.10.0.0/23 dev eth0 proto kernel scope link src 10.10.0.5
10.10.3.128/27 via 10.10.0.254 dev eth0

$ ip route get 10.10.1.200
10.10.1.200 dev eth0 src 10.10.0.5 uid 1000
    cache
$ ip route get 10.20.0.1
10.20.0.1 via 10.10.0.254 dev eth0 src 10.10.0.5 uid 1000
    cache
$ ip route get 192.0.2.7
192.0.2.7 via 10.10.0.1 dev eth0 src 10.10.0.5 uid 1000
    cache

The first answer has no via: 10.10.1.200 matched the connected /23, so the host will ARP for the destination itself (Module 06). The second matched the /8 and goes to the corporate router at .254. The third fell through to the default. Same table, three depths in the trie.

You can look at the trie itself. Linux exposes its LC-trie in /proc/net/fib_trie. An abridged, illustrative excerpt for the table above:

Main:
  +-- 0.0.0.0/4 1 0 0
     |-- 0.0.0.0
        /0 universe UNICAST
     +-- 10.0.0.0/12 1 0 0
        |-- 10.0.0.0
           /8 universe UNICAST
        +-- 10.10.0.0/22 1 0 0
           |-- 10.10.0.0
              /23 link UNICAST
           |-- 10.10.3.128
              /27 universe UNICAST

Lines starting +-- are internal nodes, and each one sits exactly where two keys first differ. 0.0.0.0 and 10.0.0.0 differ in bit 4, so the root branches at /4. 10.0.0.0 and 10.10.0.0 differ in bit 12, so the next node is a /12. The first number after the prefix is how many bits that node indexes at once. Here it is 1 everywhere, a plain binary branch, because the table is tiny. In a real table with thousands of routes you see nodes with 3, 4 or more bits (8, 16 or more children): that is the level compression. Lines starting |-- are leaves, keyed by an address, and each leaf lists every prefix length that shares that key. If you had both 10.10.0.0/16 and 10.10.0.0/23, they would hang off the same 10.10.0.0 leaf as /16 and /23. The exact layout depends on the table and kernel version; what matters is the shape.

Two Linux details are worth knowing. Since kernel 3.6 there is no global route cache. Every packet that lacks a cached socket route does this trie lookup. The cache line in ip route get output refers to per-destination exceptions such as a learned PMTU, not to a cache of lookups. And longest-prefix match runs per routing table. ip rule policy rules pick the table first, and only then does LPM run inside it. That is how VPN clients, Kubernetes CNIs and multi-homed hosts get different answers for the same destination.

macOS has the same question with a different spelling (run on your Mac — your output will differ):

$ route -n get 10.10.1.200
   route to: 10.10.1.200
destination: 10.10.0.0
       mask: 255.255.254.0
  interface: en0
      flags: <UP,DONE,CLONING>
 recvpipe  sendpipe  ssthresh  rtt,msec    rttvar  hopcount      mtu     expire
       0         0         0         0         0         0      1500         0

destination plus mask is the prefix that won: 10.10.0.0 with 255.255.254.0, the /23. CLONING marks a connected route, which spawns per-host entries as ARP resolves neighbours. netstat -rn -f inet prints the whole table.

The /1 trick: LPM as a weapon

Full-tunnel VPN clients need to send everything through the tunnel without deleting your default route, which they would have to restore later. They exploit the trie. Here is a Linux laptop on Wi-Fi with an OpenVPN-style full tunnel up (illustrative):

$ ip route
0.0.0.0/1 via 10.8.0.1 dev tun0
default via 192.168.1.1 dev wlan0 proto dhcp metric 600
10.8.0.0/24 dev tun0 proto kernel scope link src 10.8.0.6
128.0.0.0/1 via 10.8.0.1 dev tun0
192.168.1.0/24 dev wlan0 proto kernel scope link src 192.168.1.23 metric 600
198.51.100.10 via 192.168.1.1 dev wlan0

The two /1 routes together cover all of IPv4, exactly like the /0. But each is one bit deeper in the trie, so it beats the default for every destination. The /32 for 198.51.100.10 — the VPN server itself — is deeper still, and it is load-bearing. Without it, packets to the VPN server would match a /1 and enter the tunnel they are supposed to carry, and the tunnel would collapse. The local /24 survives too: 192.168.1.0/24 is longer than /1, which is why you can still reach the printer. Split-tunnel VPNs and "local network access" settings are all just this: which prefixes, at which depths.

Cloud route tables are tries too

An AWS VPC route table, an Azure UDR table and a GCP VPC route list all resolve by longest-prefix match. The VPC's own CIDR appears as a local route. For a long time it was effectively unbeatable. Since 2021 AWS lets you add a route more specific than the local route, to push traffic between subnets through a firewall appliance, and the trie rules apply as you'd expect. Where prefixes tie, each provider has its own tie-break rules (AWS prefers static routes over propagated ones, for example). Those rules are the part to look up, not to assume.

Deep dive: by the numbers

Global table size. The IPv4 default-free zone carried roughly a million prefixes by 2025–26, and IPv6 over 200,000 (bgp.potaroo.net tracks the live figures). A full-table router needs both in its FIB, plus internal routes. Most of the IPv4 table is /24s, because /24 is the longest prefix most networks will accept from a peer; announce a /25 and much of the internet will drop it. For IPv6 the equivalent boundary is /48.

Trie depth. A one-bit-per-node trie has depth at most 32 for IPv4 and 128 for IPv6. Path compression cuts the nodes visited to the number of real branch points. Level compression in Linux's LC-trie cuts it further, so a lookup in a large table touches a few nodes, not dozens. For capacity planning, the important number is not depth. It is that a software lookup costs a few cache misses, while a TCAM lookup is constant-time but bounded by entries.

Cloud subnet overhead. Every provider reserves a few addresses per subnet on top of the network and broadcast addresses:

Provider Reserved per subnet Which ones
AWS 5 network, .1 VPC router, .2 DNS, .3 future use, last (broadcast)
Azure 5 network, .1 gateway, .2 and .3 Azure DNS mapping, last
Google Cloud 4 network, .1 gateway, second-to-last, last

A /28 is AWS's smallest subnet: 16 addresses, 11 usable. On AWS, VPC CIDR blocks range from /16 to /28. Secondary CIDRs can be added later (five per VPC by default, raisable by quota), but the primary block cannot be changed. That last fact is why VPC sizing is a one-way door: pick too small and you will be bolting on secondary ranges forever.

Kubernetes ranges. A cluster has three address ranges that must not collide with each other or with anything the cluster needs to reach:

  • Node range: the VPC subnets the nodes sit in.
  • Pod range (--cluster-cidr): the controller manager hands each node a slice of this, sized by --node-cidr-mask-size (default /24 for IPv4, /64 for IPv6). With the kubelet's default of 110 pods per node, a /24 gives each node 256 addresses — roughly double what it needs, so addresses freed by dying pods aren't reused instantly.
  • Service range (--service-cluster-ip-range): virtual IPs that exist only in kube-proxy or eBPF rules on each node, never on any interface. kubeadm defaults to 10.96.0.0/12. The API server refuses an IPv4 service range larger than a /12.

The node count falls straight out of the prefix arithmetic: a /14 pod range with /24 per node is 2^(24−14) = 1,024 nodes. A /16 pod range gives 256 nodes, and the 257th node joins the cluster with no pod CIDR and never goes Ready.

Managed Kubernetes changes the formula. Google Kubernetes Engine (VPC-native) also allocates about twice the pod count per node: /24 for 110 pods, /28 for 8. The AWS VPC CNI is different: pods get real VPC addresses from the node's network interfaces (ENIs), so the limit is per instance type. Without prefix delegation, max pods = ENIs × (IPs per ENI − 1) + 2. With prefix delegation, each ENI slot holds a /28 instead of a single address, and the practical cap becomes the kubelet's max-pods setting (often 110). The script below runs those numbers and also checks a realistic plan for overlaps:

"""Check a cloud + Kubernetes address plan for overlaps and capacity."""
import ipaddress as ip
from itertools import combinations

PLAN = {
    "vpc-prod":        "10.20.0.0/16",
    "vpc-staging":     "10.21.0.0/16",
    "on-prem":         "10.0.0.0/14",
    "k8s-pods (prod)": "100.64.0.0/14",
    "k8s-svc (prod)":  "10.96.0.0/12",     # kubeadm's default
    "docker0 default": "172.17.0.0/16",
    "partner VPN":     "10.16.0.0/12",
    "branch office":   "10.100.8.0/22",
}

print("overlaps:")
for (a, pa), (b, pb) in combinations(PLAN.items(), 2):
    na, nb = ip.ip_network(pa), ip.ip_network(pb)
    if na.overlaps(nb):
        inner, outer = (na, nb) if na.prefixlen >= nb.prefixlen else (nb, na)
        print(f"  {a:<16} {pa:<15} x {b:<16} {pb:<15} shared {inner.num_addresses:>9,} addrs")

# Per-node pod ranges: controller-manager hands each node a /node_mask
cluster, node_mask, max_pods = ip.ip_network(PLAN["k8s-pods (prod)"]), 24, 110
nodes = 2 ** (node_mask - cluster.prefixlen)
print(f"\npods {cluster}: /{node_mask} per node -> {nodes} nodes, "
      f"{2 ** (32 - node_mask)} addrs/node for max {max_pods} pods")

# AWS VPC CNI without prefix delegation: max pods = ENIs * (IPs per ENI - 1) + 2
for itype, enis, ips in [("m5.large", 3, 10), ("m5.xlarge", 4, 15), ("c5.4xlarge", 8, 30)]:
    print(f"  {itype:<11} ENIs={enis} IPs/ENI={ips:<2} -> max pods {enis * (ips - 1) + 2}")

# AWS reserves 5 addresses in every subnet
for p in ("10.20.0.0/28", "10.20.0.0/24", "10.20.64.0/18"):
    n = ip.ip_network(p)
    print(f"  AWS subnet {p:<14} {n.num_addresses:>6} addrs, {n.num_addresses - 5:>6} usable")

# IPv6: a /56 VPC holds how many /64 subnets?
v6 = ip.ip_network("2001:db8:1200::/56")
subs = list(v6.subnets(new_prefix=64))
print(f"\n{v6} -> {len(subs)} x /64; first {subs[0]}, last {subs[-1]}")
print(f"one /80 per node (EKS IPv6 style) inside a /64: {2 ** (80 - 64):,} nodes")

Three findings, and none of them is an arithmetic slip. Both VPCs sit inside the partner's 10.16.0.0/12 (10.16 through 10.31), so that VPN can never be routed to either VPC without NAT. The kubeadm default service range 10.96.0.0/12 runs from 10.96.0.0 to 10.111.255.255 and quietly contains a branch office. And an m5.large on the default VPC CNI runs 29 pods, not 110, however big your subnets are. That one surprises people because it has nothing to do with the CIDR.

A note on the worked plan's pod range. 100.64.0.0/10 is RFC 6598 "shared address space", reserved for carrier-grade NAT. Using it for pods (the EKS custom networking pattern) is a widespread convention that buys address space no corporate network uses. It is not free, though. Tailscale hands out tailnet addresses from that same /10, and some ISPs number customer CGNAT from it. Check before you claim it.

Worked: sizing a VPC for a cluster. Suppose 200 nodes at 110 pods each, with pods on VPC addresses (AWS CNI with prefix delegation). Pods need 200 × 110 = 22,000 addresses, but prefix delegation allocates in /28 chunks, so plan for 200 nodes × 7 chunks × 16 = 22,400, plus warm-pool headroom. Spread over three availability zones, each zone's pod subnet needs about 7,500 addresses before slack, which means a /19 (8,192) per zone. That is three /19s for pods alone — 24,576 addresses, more than a third of a /16. Add node subnets, load balancer subnets and growth, and the honest answer is "a /16 per cluster, or put pods in a secondary 100.64 range." Run this before you create the VPC, not after.

Deep dive: production failure modes

Each entry runs symptom → mechanism → proof → fix. Every one of them is longest-prefix match doing exactly what it was told.

1. Two VPCs won't peer, or peer and route wrong

Symptom. The peering request is rejected, or a Transit Gateway attachment is accepted but some destinations are unreachable from one side.

Mechanism. Both sides chose 10.0.0.0/16, the console default. A route table cannot hold two different next hops for the same prefix at the same depth: the trie has one node for 10.0.0.0/16, and the local route already owns it. AWS VPC peering refuses overlapping CIDRs outright. Transit gateways accept the attachments, but only one of the overlapping routes can be active.

Prove it. List every CIDR in play (aws ec2 describe-vpcs --query 'Vpcs[].CidrBlockAssociationSet[].CidrBlock', plus the equivalent for on-prem and partners) and run them through an overlap check like the script above.

Fix. Renumber one side if you can. If you can't: put a private NAT gateway in front of the overlapping range so it appears as a non-overlapping one, expose only the services needed through PrivateLink-style endpoints, or move the traffic to IPv6. The durable fix is organisational: one IPAM, one allocator, and no team picking its own 10.0.0.0/16.

2. The laptop that can't reach the VPN since Docker was installed

Symptom. After installing Docker Desktop (or starting a compose project), a developer can't reach a corporate host in 172.17.x.x or 172.18.x.x. Everything else works.

Mechanism. Docker's default bridge is 172.17.0.0/16, and new compose networks are cut from its default pools (172.17–172.31 as /16s, then 192.168.0.0/16 as /20s). Creating a network adds a connected route. A connected /16 is longer than the VPN's /12 for 172.16.0.0, so the trie sends the traffic to a local bridge with nobody on it.

Prove it. On Linux, ip route get 172.17.4.20 shows dev docker0 (or a br-… bridge) instead of the tunnel, and ip route | grep -E 'docker|br-' lists the stolen prefixes. On a Mac the bridges live inside Docker Desktop's Linux VM, not in the host's routing table, so this exact clash is rarer there. The VM's own subnet can still collide with a corporate range; route -n get <addr> shows whether it does.

Fix. Set default-address-pools (and bip) in Docker's daemon.json to a range nobody routes, then recreate the networks. Put that range in the IPAM so the next team doesn't take it.

3. Kubernetes service range swallows a real network

Symptom. Pods can't reach a database at 10.100.9.15, but nodes can. No firewall logs show a drop.

Mechanism. The service CIDR is the default 10.96.0.0/12, which covers 10.96.0.0–10.111.255.255. kube-proxy (iptables or IPVS) or an eBPF dataplane intercepts traffic to service IPs before routing. Even where nothing matches a real service, the CNI's own routes may treat the whole range as cluster-internal. Packets from pods never reach the VPC route table.

Prove it. kubectl cluster-info dump | grep -m1 service-cluster-ip-range, or read the API server manifest. Then python3 -c "import ipaddress as i; print(i.ip_address('10.100.9.15') in i.ip_network('10.96.0.0/12'))" prints True. From a node, ip route get 10.100.9.15 looks fine, which is exactly why this takes hours to find.

Fix. Move to a service range that is truly unused. Recent Kubernetes versions can add service ranges through the ServiceCIDR API, but getting existing services off the old range is still a migration, and for many teams a rebuild is simpler. Choose service and pod ranges from the IPAM before the first cluster, and never accept the defaults on a network you don't control end to end.

4. Pod IP exhaustion with plenty of addresses

Symptom. New pods sit in ContainerCreating with failed to assign an IP address to container (AWS VPC CNI) or the node reports no free addresses. Meanwhile the VPC has thousands of free addresses.

Mechanism. Two different limits. On AWS without prefix delegation, the node hit its ENI × IP limit (29 pods on an m5.large). Or the subnet is fragmented: prefix delegation needs a free, aligned /28, and a subnet full of scattered single-address assignments may have plenty of free addresses but no free aligned /28. That is the same alignment rule as Module 05's "a /26 must start on a multiple of 64", now causing an outage.

Prove it. kubectl describe node shows Allocatable: pods. The CNI logs (/var/log/aws-routed-eni/ipamd.log on EKS nodes) say which limit failed. Compare the subnet's free count with whether a /28 is free.

Fix. Enable prefix delegation on fresh subnets, or use subnet CIDR reservations to keep aligned space free for /28s. Move pods to a secondary range if the node subnets are small.

5. A more-specific route hijacks traffic

Symptom. Traffic to a service suddenly goes somewhere else, often with higher latency or not at all. Nothing in your own config changed.

Mechanism. Someone announced a longer prefix covering part of your space. On the internet that is a BGP hijack or route leak: your /22 is beaten everywhere by someone else's /24, because every router's trie prefers the deeper node. Inside a company it is a stray static /32 or /24 on a core router, left from a migration. Either way, the walk passes your prefix and keeps going.

Prove it. Internally, ip route get <addr> or show ip route <addr> on the router names the winning prefix. On the internet, check what the world sees with a public looking glass or RIPEstat, not your own router.

Fix. Internally: delete the stray route and add a config check for routes more specific than the ranges in your IPAM. Externally: RPKI route-origin validation with ROAs that set a sensible max-length, plus announcing your own /24s (the longest the internet accepts) so nobody can be more specific.

6. Wrong mask, half the subnet unreachable

Symptom. A host reaches some local peers but not others. Usually the ones in the "upper half".

Mechanism. The host is configured 10.10.0.20/24 while the subnet is really a /23. Its connected route covers 10.10.0.0–10.10.0.255 only. For 10.10.1.x it falls through to the default route and sends to the gateway. Depending on the gateway, that hairpins, gets an ICMP redirect, or dies at a stateful firewall that sees only half of each conversation.

Prove it. ip -4 addr show or ifconfig en0 shows the mask. ip route get 10.10.1.30 shows via <gateway> where you expected a direct route.

Fix. Correct the mask in DHCP or the static config. If a router "fixed" it with proxy ARP, see Module 06's deep dive for why that makes it worse later.

Deep dive: address planning for real VPCs and Kubernetes in 2026

Module 05 carved one /16 for one office. Real plans are hierarchical, and the hierarchy is what keeps tries small and ranges disjoint. A plan that survives contact with production looks something like this:

Level Example Rule
Organisation 10.0.0.0/8 (plus 100.64.0.0/10 for pods) One owner, one IPAM, nothing allocated outside it
Region 10.16.0.0/12 per region Aggregates to one route per region in the core
Environment / account 10.20.0.0/16 per VPC Never reuse a /16, even in "isolated" sandboxes
Zone 10.20.0.0/18 per AZ Three AZs plus a spare /18 for growth
Subnet role /20 private, /22 public, /24 endpoints Size for scaling events, not average load

Four rules turn that table into practice.

Assume everything will eventually be connected. The "isolated" dev VPC gets peered next quarter. The acquired company's network gets a VPN. The partner wants a private link. Every reused range becomes NAT, and NAT is where debugging goes to die. Allocate as if every range will someday be in one routing table, because one day it will be.

Reserve the ranges you don't own. Docker's pools, kubeadm's defaults, your VPN client pools, RFC 6598 and any provider-specific ranges all go in the IPAM as "reserved — do not allocate." Overlaps with them are the most common failures above, and they are entirely preventable.

Size for the burst, not the steady state. Autoscaling groups, blue/green deploys and node upgrades briefly double the address count. A subnet that runs at 60% full fails at the worst moment: during the rollout.

Use IPv6 where it removes the problem. IPv6 doesn't make you smarter about overlap. It makes overlap nearly impossible, and the planning rules are different and simpler:

  • Every LAN is a /64. Not because hosts need 2^64 addresses, but because SLAAC builds 64-bit interface identifiers (RFC 4291 and RFC 7421 explain why the boundary stuck). Android devices configure only via SLAAC, so a non-/64 client subnet breaks them. Don't make client subnets longer than /64.
  • Sites get /48s, smaller sites /56s (RFC 6177's guidance). Carve on nibble boundaries (/52, /56, /60, /64) so prefixes stay readable in hex.
  • Point-to-point links: /127 (RFC 6164), usually with a whole /64 reserved per link so the plan stays regular. Loopbacks are /128s.
  • In the cloud: AWS gives a VPC a /56 from Amazon's pool and subnets are /64s, so the 256 /64s in the script output is your subnet budget. EKS in IPv6 mode delegates a /80 to each node and pods take addresses from it, which removes pod address exhaustion as a failure mode.
  • Private v6 space is ULA, fd00::/8, with a 40-bit random Global ID (RFC 4193). The random part is the point. Two organisations that follow the rule collide with probability about 1 in 2^40, so mergers stop requiring renumbering. Picking fd00::/48 by hand throws that away.

IPv6-only clusters with NAT64/DNS64 at the edge are a serious 2026 option, and dual-stack Kubernetes has been stable for years. The remaining v4 is often just the edge plus a few legacy dependencies. Even then, the v4 plan still has to be clean, because the edge and those dependencies are where the incidents happen.

Deep dive: senior interview questions

Q1: How does a router actually find the longest matching prefix? Don't say "it compares them."

It walks a trie keyed by the destination's bits, remembering the last node that terminated a prefix, and stops when no child matches the next bit. The remembered prefix is the answer. Software uses compressed tries: PATRICIA/radix in BSD and macOS, an LC-trie for Linux IPv4. Hardware uses TCAM, which compares all entries in parallel and returns the first match by position, so entries are stored longest-first. Lookup cost depends on branch points or TCAM width, not on the number of routes.

Q2: Two routes, 10.0.0.0/8 via A and 10.1.0.0/16 via B. Where does 10.1.2.3 go? What if I add 10.1.0.0/16 via C with a lower metric?

B, because /16 is deeper on the path than /8. Adding a second /16 doesn't change the depth; it creates a tie at the same node, and the metric (or administrative distance across protocols) breaks it. So C. Prefix length is compared first, metric only among equal lengths. People who answer "C, it has the lower metric" for the first case have the order backwards.

Q3: A full-tunnel VPN adds 0.0.0.0/1 and 128.0.0.0/1. Why not just replace the default route? And what breaks if it forgets one more route?

The two /1s cover everything and beat the /0 by one bit, so the original default stays in place and comes back untouched when the VPN drops. The client must also install a /32 for the VPN server via the physical gateway. Without it, the tunnel's own packets match a /1 and get routed into the tunnel, and the connection collapses.

Q4: Our EKS nodes are m5.large and pods are stuck in ContainerCreating, but the subnet is 80% free. What do you check?

The per-node limit first. With the VPC CNI without prefix delegation, an m5.large gets 3 ENIs × 10 IPs, which is 29 pods however large the subnet is. With prefix delegation, check whether the subnet still has a free aligned /28; scattered single-IP allocations can leave free addresses but no free /28. The ipamd log says which.

Q5: Why is kubeadm's default service CIDR dangerous in an enterprise, and why doesn't ip route get on the node reveal the problem?

10.96.0.0/12 spans 10.96 through 10.111, a range many enterprises already use. Service IPs are implemented in kube-proxy or eBPF rules that rewrite or capture traffic before the node's routing table matters, so the node's FIB looks innocent. You find it by comparing the configured range against your real networks, not by tracing routes.

Q6: Why must IPv6 client subnets be /64, and when is something other than /64 correct?

SLAAC forms a 64-bit interface identifier, so a client LAN with a longer prefix breaks address autoconfiguration — and some platforms, Android notably, support only SLAAC. Non-/64 is right where SLAAC isn't used: /127 on router-to-router links (RFC 6164, which avoids neighbour-cache exhaustion attacks), /128 on loopbacks, and delegated prefixes like EKS's per-node /80.

Q7: Two companies merge. Both used 10.0.0.0/16 for their main VPC. Give me the options in order of preference.

Renumber one side. It is painful once and then over. If you can't, expose services across the boundary with load balancer endpoints, so nobody needs the other side's raw range. Failing that, NAT the overlapping range into a unique one at the boundary, accepting that logs, ACLs and DNS now carry translated addresses. Long term, IPv6 with random-ID ULA or global space avoids the problem entirely. The wrong answer is "add more specific routes": a trie can't hold two next hops for the same addresses, so more-specifics just pick which half of each network becomes unreachable.

Q8: Why do internet providers filter announcements longer than /24, and what does that do to hijack defence?

Accepting longer prefixes would blow up every full-table router's FIB: roughly a million IPv4 prefixes is already the budget. So /24 is the de-facto floor, and a /25 is dropped by most networks. For defence, that means announcing your space as /24s leaves no more-specific for a hijacker to win with. Combine it with RPKI ROAs whose max-length matches what you actually announce.
