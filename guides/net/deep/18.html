Deep dive: what the ladder hid

The dependency ladder is the right method. Scope, then climb, then bisect. But it quietly assumes each rung is a yes-or-no question: the gateway pings or it doesn't, the port connects or it doesn't. The incidents that eat whole days rarely look like that. They are partial. Small requests work and large ones stall. Lookups succeed, but one in twenty takes five seconds. New connections fail while old ones are fine. Traffic works from one subnet and not another.

Partial failures live in state: a cached path MTU, a resolver's search list, a full connection-tracking table, a routing decision that differs by source address. The module's tools answer "is it up?" This deep dive is about the tools that read that state, and about four incidents, worked end to end, where reading state is the only way through.

The commands are Linux first, because that's where production servers, containers and cloud nodes run. Where macOS differs, the text says so.

Deep dive: the real mental model

A packet's trip through a host is a fixed sequence of stages. Each stage keeps its own state and its own counters, and each one can drop a packet for its own reasons. Socket buffers, the routing table and its cache of path MTUs, netfilter rules and the connection-tracking table, the neighbour (ARP/ND) table, the queueing discipline, the NIC's rings. Every troubleshooting tool reads exactly one of these stages. That is the real mental model: a symptom is a drop or a delay in one stage, and a tool is a window onto one stage.

The single most useful fact in that diagram is where tcpdump sits. On Linux, packet capture taps the path at the device. Inbound packets are copied to the capture before netfilter and before the reverse-path check. Outbound packets are copied after routing, netfilter and the qdisc, just before the driver. So two common inferences are wrong:

  • "I can see the SYN in tcpdump, so the server received it." It reached the interface. The firewall, rp_filter or a full queue can still discard it, and only counters will tell you.
  • "My packet isn't in the capture, so the app never sent it." It may have been dropped by an OUTPUT rule or failed routing before it reached the tap.

macOS works the same way in spirit: BPF taps at the interface, and pf filters on either side of it. The difference is tooling. macOS has no ip, ss or conntrack. You use netstat -rn, route -n get, arp -an, ndp -an, netstat -an -p tcp, lsof -i and nettop.

The second piece of the model is that timers are fingerprints. Networking stacks retry on fixed schedules, so a delay of a suspiciously round size usually names its own cause before you've run a single command. You'll find the table in the "by the numbers" section. Learn it, and half your hypotheses come for free.

Deep dive: the toolbox, with real output

Each tool below is shown with output and read line by line. The curl and openssl outputs are real, captured against a local TLS server running on this guide's build machine. The others are constructed to be consistent with the incidents later in this section, using documentation and private address ranges. Your output will differ.

ip: addresses, routes, neighbours

$ ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             10.0.1.20/24 fe80::4a3:9ff:fe2c:11a0/64

$ ip route
default via 10.0.1.1 dev eth0 proto dhcp src 10.0.1.20 metric 100
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.20 metric 100

$ ip route get 172.20.4.11
172.20.4.11 via 10.0.1.1 dev eth0 src 10.0.1.20 uid 1000
    cache expires 412sec mtu 1400

$ ip neigh
10.0.1.1 dev eth0 lladdr 02:42:0a:00:01:01 REACHABLE
10.0.1.31 dev eth0 lladdr 02:42:0a:00:01:1f STALE
10.0.1.44 dev eth0  FAILED

ip route shows the table you configured. ip route get shows the decision the kernel makes for one destination right now, including the route cache. The cache expires 412sec mtu 1400 line means this host received an ICMP "fragmentation needed" for that destination and has learned a smaller path MTU. That exception lasts 600 seconds by default (net.ipv4.route.mtu_expires). Seeing it is direct proof that PMTU discovery is working toward that host.

ip route get also takes a source address: ip route get 192.168.50.10 from 10.1.0.5. That form is how you prove asymmetric routing, as the fourth incident shows. The macOS equivalent of the plain form is route -n get 172.20.4.11.

In ip neigh, REACHABLE means the entry was confirmed recently (the base time is 30 seconds, randomised). STALE means it's still usable but will be re-verified on next use. FAILED means ARP or neighbour discovery got no answer. A FAILED next hop is a layer-2 fault that no amount of IP debugging will fix.

ss: sockets and TCP internals

$ ss -tni dst 172.20.4.11
State  Recv-Q Send-Q   Local Address:Port    Peer Address:Port
ESTAB  0      0           10.0.1.20:51022    172.20.4.11:443
     cubic wscale:7,7 rto:232 rtt:31.4/0.9 ato:40 mss:1348 pmtu:1400 rcvmss:1348
     advmss:1448 cwnd:10 bytes_sent:517 bytes_acked:518 bytes_received:4132
     segs_out:9 segs_in:8 data_segs_out:1 data_segs_in:4 send 3.4Mbps
     lastsnd:2210 lastrcv:2180 lastack:2180 delivery_rate 1.1Mbps rcv_space:14480

This is the tcp_info structure the kernel keeps for every connection. The fields that answer real questions:

  • rtt:31.4/0.9: smoothed RTT and its variation, in milliseconds. Compare it with ping. If TCP's RTT is far above ICMP's, the delay is in queues, not distance.
  • rto:232: the current retransmission timeout. Linux uses RTT plus a variance term with a 200 ms floor.
  • mss:1348 pmtu:1400: the path MTU TCP is using for this connection, and the resulting segment size (1400 minus 40 bytes of headers and 12 of timestamps).
  • retrans: (absent here) shows retransmissions in flight and in total. cwnd collapsing to 1 or 2 with a large backoff means repeated timeouts.
  • Send-Q on an established socket is bytes sent but not yet acknowledged, plus bytes not yet sent. If it's large and not moving, the peer or the path has stopped acknowledging.

ss -s gives a one-screen summary of socket counts by state, and ss -lnt shows listeners with their accept-queue length (Recv-Q) and limit (Send-Q). On macOS, netstat -an -p tcp lists sockets and netstat -s -p tcp prints protocol counters. There's no direct tcp_info view.

tcpdump: filters worth knowing by heart

tcpdump -nn -i any 'host 172.20.4.11 and tcp port 443'      # one conversation, all interfaces
tcpdump -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'          # only handshakes and resets
tcpdump -nn 'icmp[icmptype] == icmp-unreach and icmp[icmpcode] == 4'   # IPv4 "frag needed"
tcpdump -nn 'icmp6 and ip6[40] == 2'                          # ICMPv6 Packet Too Big (no ext hdrs)
tcpdump -nn 'ip[6:2] & 0x4000 != 0 and greater 1400'          # DF set and big: PMTU suspects
tcpdump -nn 'udp port 53'                                     # every DNS query and answer
tcpdump -nn -i any -w /tmp/x.pcap -C 100 -W 5 'port 5432'     # ring buffer: 5 files of 100 MB

Three habits matter more than any filter. Always pass -nn, or tcpdump does reverse DNS for every address and the capture itself becomes DNS traffic. Capture on -i any when you suspect asymmetry: on current tcpdump versions each line is tagged with the interface and the direction (In / Out). And capture on both ends when you can, because a packet that leaves one side and never arrives at the other has been dropped by something in between.

mtr: a path, measured over time

$ mtr -rwzbc 100 172.20.4.11
Start: 2026-10-16T10:12:03+0000
HOST: build-07                           Loss%   Snt   Last   Avg  Best  Wrst StDev
  1. AS???    10.0.1.1                    0.0%   100    0.5   0.4   0.3   1.1   0.1
  2. AS???    169.254.10.1                0.0%   100    1.9   1.6   1.2   4.0   0.4
  3. AS???    100.64.12.9                38.0%   100   12.4  12.9  12.1  19.8   1.1
  4. AS???    169.254.10.2                0.0%   100   28.8  29.1  28.4  33.0   0.7
  5. AS???    172.20.4.11                 0.0%   100   30.1  30.3  29.8  34.2   0.6

Read mtr from the bottom. The destination shows 0% loss. So the 38% at hop 3 is not packet loss on the path. That router is rate-limiting the ICMP time-exceeded replies it generates, because generating ICMP runs on its control-plane CPU, while forwarding your traffic runs in hardware. Loss is real only if it starts at some hop and persists to the end. The same rule applies to latency: a jump that persists to the destination is real, and a spike at one hop that disappears at the next is that router being slow to answer.

Use -r for report mode, -w for wide names, -z/-b for AS numbers and both names and IPs. -T -P 443 sends TCP SYNs instead of ICMP, which follows the same path and firewall rules your application does. On macOS, install it with Homebrew; it needs sudo.

dig: what DNS says, and what it doesn't

$ dig api.partner.example A

; <<>> DiG 9.18.28 <<>> api.partner.example A
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 30981
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;api.partner.example.       IN  A

;; ANSWER SECTION:
api.partner.example.    27  IN  A   198.51.100.40

;; Query time: 14 msec
;; SERVER: 10.96.0.10#53(10.96.0.10) (UDP)
;; WHEN: Fri Oct 16 11:20:03 UTC 2026
;; MSG SIZE  rcvd: 64

status is the verdict (NOERROR, NXDOMAIN, SERVFAIL). The flags tell you who answered: no aa flag means a recursive resolver answered from cache or recursion, not the authoritative server. The TTL of 27 is the remaining cache time. Run it again and it counts down, which proves you're hitting a cache. SERVER shows which resolver actually answered.

Then remember what dig doesn't do. It doesn't use your resolver library. It ignores /etc/nsswitch.conf, /etc/hosts, and, unless you pass +search, the search and ndots settings. So "dig works but the app can't resolve" is a real and common split. To test what the application sees, use the system resolver: getent ahosts api.partner.example on Linux, dscacheutil -q host -a name api.partner.example on macOS.

curl -w: where the milliseconds go

curl can print a timestamp for every phase of a request. All values are cumulative seconds since the start. This run is real, against a local TLS server whose handler sleeps 120 ms to stand in for application work:

$ curl -s -o /dev/null --cacert cert.pem --resolve api.internal.test:8443:127.0.0.1 \
    -w '    time_namelookup:  %{time_namelookup}s\n       time_connect:  %{time_connect}s\n    time_appconnect:  %{time_appconnect}s\n time_starttransfer:  %{time_starttransfer}s\n         time_total:  %{time_total}s\n          http_code:  %{http_code}\n' \
    https://api.internal.test:8443/health
    time_namelookup:  0.000026s
       time_connect:  0.001026s
    time_appconnect:  0.009440s
 time_starttransfer:  0.132682s
         time_total:  0.132750s
          http_code:  200

Subtract adjacent values to get each phase. DNS took nothing (--resolve skipped it). The TCP handshake took 1.0 ms. TLS took 8.4 ms, which on loopback is pure CPU for key exchange and signatures. Then 123 ms passed between the end of the handshake and the first response byte: that's the application's 120 ms sleep plus a little. Over a real network, each phase also includes round trips. With a 30 ms RTT and TLS 1.3 you'd expect roughly: connect ≈ DNS + 30 ms, appconnect ≈ connect + 30 ms, starttransfer ≈ appconnect + 30 ms + server time.

That gives you a sharp triage rule. Big time_namelookup: DNS. Big gap to time_connect: path or SYN loss (look for exactly 1 s or 3 s, the SYN retransmit timers). Big gap to time_appconnect: TLS, a slow handshake, an OCSP fetch, or a PMTU problem with the certificate chain. Big gap to time_starttransfer: the server. The same -w string works on macOS.

Deep dive: by the numbers

Timer fingerprints

When a delay has a round number in it, look it up here before you form any other hypothesis. These are defaults and they vary by OS and version; the point is the shape.

Delay you see Usual cause Where it comes from
~40 ms or ~200 ms extra per exchange Nagle's algorithm meeting delayed ACK Linux delayed-ACK minimum 40 ms; many stacks up to 200 ms
1 s, then 3 s, 7 s, 15 s to connect SYN lost, retransmitted Initial RTO 1 s (RFC 6298), doubling. Linux gives up after tcp_syn_retries = 6, about 127 s
3 s to connect SYN lost on an older stack Initial RTO 3 s (old RFC 2988 value)

~200 ms+ then recovery mid-transfer Retransmission timeout Linux RTO floor 200 ms
60 s idle, then the connection dies Idle timeout on a NAT or load balancer Many cloud LBs and NAT gateways default to 60 s to 350 s; varies by product

Two budgets: MTU and conntrack

Two numbers cause more partial outages than any others: how many bytes fit through a tunnel, and how many flows a stateful box can remember. Both are simple arithmetic.

d18_budgets.py:

"""Two budgets every troubleshooter should be able to compute on paper."""

# 1. MTU budget: what fits inside a tunnel on a 1500-byte path.
IP4, IP6, TCP, TS_OPT = 20, 40, 20, 12
overheads = {                       # bytes added in front of the inner packet
    "none (plain Ethernet)": 0,
    "GRE over IPv4": IP4 + 4,
    "VXLAN over IPv4": IP4 + 8 + 8 + 14,   # outer IP + UDP + VXLAN + inner Ethernet
    "WireGuard over IPv4": IP4 + 8 + 32,   # outer IP + UDP + WG header and tag
    "WireGuard over IPv6": IP6 + 8 + 32,
}
print(f"{'encapsulation':<24}{'inner MTU':>10}{'TCP MSS':>9}{'payload/seg':>13}")
for name, oh in overheads.items():
    mtu = 1500 - oh
    mss = mtu - IP4 - TCP
    print(f"{name:<24}{mtu:>10}{mss:>9}{mss - TS_OPT:>13}")

# 2. Conntrack budget: entries = arrival rate x lifetime (Little's law).
print()
max_entries = 262_144
flows = [  # (label, new flows per second, seconds each entry lives)
    ("HTTP, pooled keep-alive",        5, 600),             # 10-min conn lifetime
    ("HTTP, new conn per request",  2_500, 120),            # TIME_WAIT 120 s
    ("DNS over UDP to CoreDNS",     4_000, 30),             # UDP, answered < 2 s
]
total = 0
for label, rate, life in flows:
    n = rate * life
    total += n
    print(f"{label:<28} {rate:>6}/s x {life:>6.0f} s = {n:>9,.0f} entries")
print(f"{'total':<28} {'':>21} {total:>11,.0f}  vs nf_conntrack_max {max_entries:,}"
      f"  -> {total / max_entries:.0%} full")

Real output:

encapsulation            inner MTU  TCP MSS  payload/seg
none (plain Ethernet)         1500     1460         1448
GRE over IPv4                 1476     1436         1424
VXLAN over IPv4               1450     1410         1398
WireGuard over IPv4           1440     1400         1388
WireGuard over IPv6           1420     1380         1368

HTTP, pooled keep-alive           5/s x    600 s =     3,000 entries
HTTP, new conn per request     2500/s x    120 s =   300,000 entries
DNS over UDP to CoreDNS        4000/s x     30 s =   120,000 entries
total                                                  423,000  vs nf_conntrack_max 262,144  -> 161% full

The MTU table is why "small things work, big things hang" points at tunnels. Every encapsulation steals bytes. If nobody tells TCP about the smaller MTU, full-size 1500-byte packets don't fit. (WireGuard's default interface MTU is 1420 precisely because it budgets for an IPv6 outer header.)

The conntrack line is Little's law: entries in the table equal the rate of new flows times how long each entry lives. The killer is the row in the middle. A client that opens a new TCP connection per request, at only 2,500 requests per second, holds 300,000 entries, because each closed connection lingers in conntrack's TIME_WAIT state for 120 seconds. Switch to pooled keep-alive connections and the same traffic needs a few thousand.

Search-list amplification

Kubernetes sets ndots:5 in every pod's /etc/resolv.conf so that short names like payments-db.data resolve inside the cluster. The side effect is that any name with fewer than five dots — which is nearly every external hostname — is first tried with every search domain appended. This script applies the resolver's rules from resolv.conf(5):

d18_ndots.py:

"""What glibc's stub resolver sends for one getaddrinfo() call, per resolv.conf.

Rules (resolv.conf(5)): a name ending in "." is absolute. Otherwise, if it has
at least `ndots` dots it is tried as-is first; if fewer, the search list is
tried first. Each candidate is asked for A and AAAA (sent in parallel).
"""
SEARCH = ["payments.svc.cluster.local", "svc.cluster.local", "cluster.local",
          "eu-west-1.compute.internal"]


def candidates(name, ndots, search=SEARCH):
    if name.endswith("."):
        return [name]
    expanded = [f"{name}.{d}." for d in search]
    if name.count(".") >= ndots:
        return [name + "."] + expanded
    return expanded + [name + "."]


EXISTS = {"api.partner.example.", "payments-db.data.svc.cluster.local."}


def lookup(name, ndots):
    tries = []
    for c in candidates(name, ndots):
        tries.append(c)
        if c in EXISTS:                  # first positive answer ends the walk
            break
    return tries


for name, nd in [("api.partner.example", 5), ("api.partner.example", 2),
                 ("api.partner.example.", 5), ("payments-db.data", 5)]:
    tries = lookup(name, nd)
    print(f"{name!r} ndots:{nd} -> {len(tries)} attempt(s), {2 * len(tries)} queries")
    for t in tries:
        print(f"    A+AAAA {t}")

# Tail latency: each attempt is one UDP round trip pair. If either packet of
# the pair is lost, glibc waits `timeout` (default 5 s) before retrying.
print("\nchance that one lookup hits a 5 s retry, per-attempt loss p:")
for p in (0.001, 0.01):
    for n in (1, 5):
        print(f"  p={p:<5}  attempts={n}:  {1 - (1 - p) ** n:6.2%}")

    A+AAAA api.partner.example.svc.cluster.local.
    A+AAAA api.partner.example.cluster.local.
    A+AAAA api.partner.example.eu-west-1.compute.internal.
    A+AAAA api.partner.example.

    A+AAAA api.partner.example.

    A+AAAA api.partner.example.

    A+AAAA payments-db.data.payments.svc.cluster.local.
    A+AAAA payments-db.data.svc.cluster.local.

chance that one lookup hits a 5 s retry, per-attempt loss p:
  p=0.001  attempts=1:   0.10%
  p=0.001  attempts=5:   0.50%
  p=0.01   attempts=1:   1.00%
  p=0.01   attempts=5:   4.90%

One external lookup becomes ten queries, eight of them for names that don't exist but still have to be answered. Two fixes remove the amplification entirely: a lower ndots, or a trailing dot on the name. The tail-latency lines matter more than the query count. Every attempt is another chance for a UDP packet to be lost, and each loss costs a fixed 5 seconds. At 1% loss per attempt, five attempts put almost one lookup in twenty into a 5-second stall. That's exactly what a p95 or p99 graph shows.

Deep dive: four incidents, end to end

Each incident follows the same shape: symptom → hypothesis → proof → fix. The proof step is the part to copy. A hypothesis isn't done until a command shows the mechanism directly.

Incident 1: the PMTU black hole

Symptom. After the office's traffic to the cloud VPC moved onto a new site-to-site tunnel, engineers in the office can still SSH to the internal Git server 172.20.4.11 and run small API calls against it. But git clone over HTTPS hangs. So does curl https://git.internal, and it hangs after the TCP connect, during the TLS handshake. From a laptop on home Wi-Fi, through the client VPN, everything works.

Hypothesis. Small packets pass and large ones vanish, and a path just changed. That points at MTU. The tunnel takes bytes from each packet, so full-size 1500-byte packets from the server don't fit. The router at the tunnel should send an ICMP "fragmentation needed" back to the server, and the server should shrink its packets. Something is eating that ICMP. A TLS handshake fails first because the server's first flight (certificate chain included) is several kilobytes: its full-size packets are the first ones that don't fit. An interactive SSH session sends mostly small packets, so it gets away with it.

Proof, step 1: the capture on the client.

$ sudo tcpdump -nn -i eth0 'host 172.20.4.11 and tcp port 443'
10:02:11.400112 IP 10.0.1.20.51022 > 172.20.4.11.443: Flags [S], seq 2087211001, win 64240, options [mss 1460,sackOK,TS val 1123 ecr 0,nop,wscale 7], length 0
10:02:11.431507 IP 172.20.4.11.443 > 10.0.1.20.51022: Flags [S.], seq 914822337, ack 2087211002, win 65160, options [mss 1460,sackOK,TS val 77120 ecr 1123,nop,wscale 7], length 0
10:02:11.431566 IP 10.0.1.20.51022 > 172.20.4.11.443: Flags [.], ack 1, win 502, options [nop,nop,TS val 1155 ecr 77120], length 0
10:02:11.432010 IP 10.0.1.20.51022 > 172.20.4.11.443: Flags [P.], seq 1:518, ack 1, win 502, options [nop,nop,TS val 1156 ecr 77120], length 517
10:02:11.463702 IP 172.20.4.11.443 > 10.0.1.20.51022: Flags [.], ack 518, win 507, options [nop,nop,TS val 77152 ecr 1156], length 0
10:02:11.464120 IP 172.20.4.11.443 > 10.0.1.20.51022: Flags [P.], seq 2897:4133, ack 518, win 507, options [nop,nop,TS val 77153 ecr 1156], length 1236
10:02:11.464151 IP 10.0.1.20.51022 > 172.20.4.11.443: Flags [.], ack 1, win 502, options [nop,nop,TS val 1188 ecr 77153,nop,nop,sack 1 {2897:4133}], length 0
              ... 30 s of silence; curl eventually times out ...

Read it in order. Both sides advertise MSS 1460, so both think the path carries 1500-byte packets. Nobody clamped the MSS at the tunnel. The ClientHello (517 bytes) goes out and is acknowledged. Then the server sends its 4,132-byte first flight as three segments: 1448 + 1448 + 1236 bytes of payload. Only the third one arrives. With its IP and TCP headers it's 1,288 bytes, small enough to fit the tunnel. The client says so with a SACK: "I have 2897–4133, I'm missing everything before it." The two full-size segments, and every retransmission of them, never arrive.

That capture is close to a signature by itself: small segments delivered, a SACK hole exactly the size of the full-size segments, and nothing else.

Proof, step 2: measure the path MTU from the client side. The client's direction is healthy, so the router's ICMP reaches it:

$ tracepath -n 172.20.4.11
 1?: [LOCALHOST]                      pmtu 1500
 1:  10.0.1.1                                              0.512ms
 1:  10.0.1.1                                              0.401ms
 2:  10.0.1.1                                              0.388ms pmtu 1400
 2:  169.254.10.2                                         28.914ms
 3:  172.20.4.11                                          30.122ms reached
     Resume: pmtu 1400 hops 3 back 3

$ ping -M do -s 1372 -c 1 172.20.4.11      # 1372 + 8 ICMP + 20 IP = 1400: fits
$ ping -M do -s 1373 -c 1 172.20.4.11      # 1401: the router answers "frag needed (mtu = 1400)"

On macOS the don't-fragment flag is -D: ping -D -s 1372 172.20.4.11.

Proof, step 3: find who eats the ICMP. On the server, watch for the one ICMP message that should be arriving:

$ sudo tcpdump -nn -i eth0 'icmp[icmptype] == icmp-unreach and icmp[icmpcode] == 4'
(nothing, while the client retries)

$ ip route get 10.0.1.20
10.0.1.20 via 172.20.4.1 dev eth0 src 172.20.4.11 uid 0
    cache

No ICMP arrives, and the server's route has no learned MTU: it still believes 1500 is fine. A capture on the tunnel router's VPC-facing interface shows it sending those ICMP messages. So the drop sits between the router and the server. Here it was the cloud firewall in front of the server, which allowed tcp/443 inbound and nothing else. Some stateful firewalls pass ICMP errors that relate to an existing flow. Several cloud security-group implementations need an explicit rule for them.

Fix. Do two things, because each covers the other's gap.

  1. Clamp the MSS on the tunnel router, so TCP never sends packets that don't fit. On Linux: iptables -t mangle -A FORWARD -o tun0 -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu. This rewrites the MSS option in SYNs entering the tunnel to 1360 (1400 − 40), so the server never builds a segment bigger than the tunnel can carry. It only helps TCP.
  2. Allow ICMP "fragmentation needed" (IPv4 type 3 code 4) and ICMPv6 "Packet Too Big" (type 2) through every firewall on the path, so PMTU discovery works for everything else: UDP, QUIC, and any TCP that bypasses the clamp. Blocking ICMPv6 Packet Too Big breaks IPv6 outright, because IPv6 routers never fragment.

On servers you can also set net.ipv4.tcp_mtu_probing=1. It enables packetization-layer PMTU discovery (RFC 4821), where TCP probes with smaller segments after repeated losses instead of relying on ICMP. It's a safety net, not a fix. Verify the fix with the same curl and capture: the handshake completes, and the server's capture shows the client's SYN arriving with mss 1360.

Incident 2: the 5-second DNS tail in Kubernetes

Symptom. A checkout service calls a payment partner's API at api.partner.example. Median latency is 40 ms. p99 is just over 5 seconds, and the spikes cluster at 5.0x seconds. The partner's own dashboards show nothing slower than 50 ms. Curling the API from the node itself is always fast.

Hypothesis. A delay of exactly 5 s matches the resolver timeout in the timer table. Pods and nodes resolve differently: pods get ndots:5 and a cluster search list. So each lookup becomes many queries, and losing any one of them costs 5 seconds.

Proof, step 1: the resolver configuration the application actually uses.

$ kubectl exec deploy/checkout -- cat /etc/resolv.conf
search payments.svc.cluster.local svc.cluster.local cluster.local eu-west-1.compute.internal
nameserver 10.96.0.10
options ndots:5

api.partner.example has two dots, fewer than five, so the search list runs first. d18_ndots.py above predicts ten queries.

Proof, step 2: count them on the wire. Capture inside the pod's network namespace, or on the node filtering by pod IP:

$ sudo tcpdump -nn -i any 'udp port 53 and host 10.244.3.17'
11:20:03.101220 IP 10.244.3.17.40312 > 10.96.0.10.53: 18211+ A? api.partner.example.payments.svc.cluster.local. (64)
11:20:03.101243 IP 10.244.3.17.40312 > 10.96.0.10.53: 52144+ AAAA? api.partner.example.payments.svc.cluster.local. (64)
11:20:03.101871 IP 10.96.0.10.53 > 10.244.3.17.40312: 18211 NXDomain*- 0/1/0 (118)
11:20:03.101902 IP 10.96.0.10.53 > 10.244.3.17.40312: 52144 NXDomain*- 0/1/0 (118)
      ... the same pair for svc.cluster.local, cluster.local, eu-west-1.compute.internal ...
11:20:03.104410 IP 10.244.3.17.40312 > 10.96.0.10.53: 30981+ A? api.partner.example. (37)
11:20:03.104433 IP 10.244.3.17.40312 > 10.96.0.10.53: 41207+ AAAA? api.partner.example. (37)
11:20:03.118802 IP 10.96.0.10.53 > 10.244.3.17.40312: 30981 1/0/0 A 198.51.100.40 (53)
      ... 5.0 s: no AAAA answer ...
11:20:08.109921 IP 10.244.3.17.40312 > 10.96.0.10.53: 30981+ A? api.partner.example. (37)
11:20:08.110514 IP 10.96.0.10.53 > 10.244.3.17.40312: 30981 1/0/0 A 198.51.100.40 (53)
11:20:08.110602 IP 10.244.3.17.40312 > 10.96.0.10.53: 41207+ AAAA? api.partner.example. (37)
11:20:08.121377 IP 10.96.0.10.53 > 10.244.3.17.40312: 41207 0/1/0 (88)

The numbers in parentheses are DNS message sizes, and they check out: a 12-byte header, the encoded name, and 4 bytes of type and class give 37 bytes for api.partner.example. and 64 for the longest search-list name. The * marks an authoritative answer: CoreDNS owns cluster.local, so it answers NXDOMAIN itself, instantly. glibc sends A and AAAA in parallel from the same socket. On the final attempt the A answer came back, the AAAA answer never did, and after 5 seconds glibc retried. Note the shape of the retry. After a timeout in which one answer did arrive, glibc switches to sending the two queries one after the other — a built-in workaround for exactly this kind of loss.

Proof, step 3: where was the packet lost? Both queries share one 5-tuple. On the node, the Service IP 10.96.0.10 is DNAT-ed to a CoreDNS pod by conntrack. Two packets of a new flow arriving at the same moment race to create the same conntrack entry, and the loser can be dropped:

$ sudo conntrack -S | head -2
cpu=0       found=0 invalid=1253 ignore=0 insert=0 insert_failed=8841 drop=8841 early_drop=0 error=0 search_restart=0
cpu=1       found=0 invalid=1190 ignore=0 insert=0 insert_failed=9102 drop=9102 early_drop=0 error=0 search_restart=0

insert_failed climbing in step with DNS traffic is the race. Newer kernels resolve most of these clashes (they show up in a separate clash_resolve counter instead), so on a current node the loss may be elsewhere. The other usual suspects are CoreDNS CPU throttling under its limits, and per-interface packet limits on the cloud provider's DNS endpoint. On AWS, the ENA driver counts those drops as linklocal_allowance_exceeded in ethtool -S. Either way the mechanism is the same: loss times attempts.

Fix. Remove the amplification first, because it multiplies every other problem:

  • Set ndots lower for workloads that mostly call external names. In the pod spec: dnsConfig: {options: [{name: ndots, value: "2"}]}. Short in-cluster names like payments-db.data still work, because they have fewer than two dots.
  • Use fully qualified names with a trailing dot (api.partner.example.) in configuration where you can.
  • Run NodeLocal DNSCache, so every pod queries a cache on its own node. That shortens the path, and in its usual setup it reaches the cluster DNS over TCP, which sidesteps the UDP conntrack race.
  • Where you can't change the image or the platform, options single-request-reopen in resolv.conf makes glibc use a separate socket for the second query.

Verify by counting again: two queries per lookup in the capture, and the p99 step at 5 s disappears from the latency histogram.

Incident 3: conntrack exhaustion

Symptom. On one group of Kubernetes nodes, roughly 1 in 50 new outbound connections times out. Established connections are fine. Retries usually work. It started right after a deploy of a new HTTP client library, and it gets worse at the hourly traffic peak.

Hypothesis. "New connections fail, existing ones are fine" means a per-new-flow resource is exhausted. The timing points at a change in connection behaviour. If the new library stopped reusing connections, each request now creates a new flow, and every flow occupies a conntrack entry for 120 seconds after it closes.

Proof.

$ dmesg -T | grep conntrack | tail -2
[Fri Oct 16 14:00:12 2026] nf_conntrack: nf_conntrack: table full, dropping packet
[Fri Oct 16 14:00:12 2026] nf_conntrack: nf_conntrack: table full, dropping packet

$ cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
262144
262144

$ sudo conntrack -L -p tcp -o extended 2>/dev/null | awk '{print $6}' | sort | uniq -c | sort -rn | head -4
 214877 TIME_WAIT
  27160 ESTABLISHED
   1806 CLOSE
    412 SYN_SENT

$ sudo conntrack -L -p tcp --state TIME_WAIT | head -1
tcp      6 117 TIME_WAIT src=10.244.3.17 dst=10.96.112.40 sport=48812 dport=8080 src=10.244.7.9 dst=10.244.3.17 sport=8080 dport=48812 [ASSURED] mark=0 use=1

The table is exactly full, and more than four-fifths of it is TCP TIME_WAIT entries for connections that already finished. (The remaining 17,889 entries are UDP.) The sample entry shows both directions of the flow: the original tuple to the Service IP, and the reply tuple from the backend pod after DNAT. The 117 is seconds left before it expires. A packet the kernel can't track is dropped. For a new connection, that's a SYN, which the client retransmits after 1 s — hence "retries usually work."

To tie it to the deploy, compare the connection rate before and after: nstat -az TcpActiveOpens sampled twice, a minute apart, gives new outbound connections per second. A jump from tens to thousands per second at the same request rate is the missing connection pool. The Little's-law budget from earlier is the arithmetic: 2,500 new connections per second times 120 seconds is 300,000 entries, more than the table holds.

Fix. In order of preference:

  1. Fix the cause. Restore connection pooling and keep-alive in the client. This cuts the entry count by orders of magnitude and saves a TCP and TLS handshake on every request.
  2. Buy headroom. Raise net.netfilter.nf_conntrack_max and the hash table size together (/sys/module/nf_conntrack/parameters/hashsize), so lookups stay short chains. Budget memory: each entry costs a few hundred bytes of kernel memory (check the nf_conntrack line in /proc/slabinfo), so a million entries is a few hundred megabytes.
  3. Shorten the lifetime. net.netfilter.nf_conntrack_tcp_timeout_time_wait can come down from 120 s. Lowering it moderately is safe, since the endpoints keep their own TIME_WAIT state.
  4. Don't track what doesn't need tracking. High-volume flows that need no NAT or stateful filtering can skip conntrack with a notrack rule in the raw table. Node-local DNS caches often do this for their own traffic.

Then add an alert on nf_conntrack_count / nf_conntrack_max above 75%. The table full message arrives only after users are already affected.

The second table. On cloud VMs there may be another connection table you don't control. AWS security groups are stateful and enforced in the hypervisor, with a per-interface limit on tracked connections. When that fills, the ENA driver's conntrack_allowance_exceeded counter climbs in ethtool -S eth0, while the kernel's table looks fine. Same symptom, different table, different fix: a larger instance size, or security-group rules that let the provider skip tracking for those flows.

Incident 4: asymmetric routing

Symptom. A PostgreSQL server db-07 has two interfaces. eth0 is on the management network, 10.0.0.0/24, and carries the default route. eth1 is on the data network, 10.1.0.0/24, and the database listens on 10.1.0.5:5432. Application servers in the same data subnet connect fine. A new analytics cluster in 192.168.50.0/24, routed in through the data network's firewall, gets connection timeouts. nc -vz 10.1.0.5 5432 from an analytics host hangs and never says "refused."

Hypothesis. Timeout, not refused: packets are being swallowed. Same-subnet clients work and routed clients don't. The difference between them is the return path. Replies to 192.168.50.10 don't match any connected route on db-07, so they follow the default route out of eth0. They leave through a different interface, and a different firewall, from the one the SYN came in on. The management firewall never saw the SYN, so it treats the SYN-ACK as an invalid packet and drops it.

Proof, step 1: watch both interfaces at once.

$ sudo tcpdump -nn -i any 'host 192.168.50.10 and tcp port 5432'
10:14:02.331207 eth1  In  IP 192.168.50.10.53344 > 10.1.0.5.5432: Flags [S], seq 3011849210, win 64240, options [mss 1460,sackOK,TS val 99120 ecr 0,nop,wscale 7], length 0
10:14:02.331251 eth0  Out IP 10.1.0.5.5432 > 192.168.50.10.53344: Flags [S.], seq 1201733905, ack 3011849211, win 65160, options [mss 1460,sackOK,TS val 51117 ecr 99120,nop,wscale 7], length 0
10:14:03.355190 eth1  In  IP 192.168.50.10.53344 > 10.1.0.5.5432: Flags [S], seq 3011849210, win 64240, options [mss 1460,sackOK,TS val 100144 ecr 0,nop,wscale 7], length 0
10:14:03.355226 eth0  Out IP 10.1.0.5.5432 > 192.168.50.10.53344: Flags [S.], seq 1201733905, ack 3011849211, win 65160, options [mss 1460,sackOK,TS val 52141 ecr 100144,nop,wscale 7], length 0

There it is in two lines: the SYN arrives on eth1, the SYN-ACK leaves on eth0. The client never gets the SYN-ACK, so it retransmits the SYN after about one second (the first timer fingerprint). The server answers each one again, out of the wrong door.

Proof, step 2: ask the kernel why.

$ ip route get 192.168.50.10 from 10.1.0.5
192.168.50.10 from 10.1.0.5 via 10.0.0.1 dev eth0 uid 0
    cache

Linux routes by destination. The source address 10.1.0.5 doesn't change the decision, so replies follow the default route. The management firewall's logs confirm it with a run of "invalid state" drops for SYN-ACKs from 10.1.0.5:5432.

A variation you'll also meet. If net.ipv4.conf.eth1.rp_filter is 1 (strict), the symptom changes. Now no SYN-ACK appears at all. The capture still shows the SYN arriving on eth1, because the tap runs before the reverse-path check, as the diagram above shows. The kernel then drops it: the best route back to 192.168.50.10 points out eth0, not the interface the SYN came in on. The only evidence is a counter:

$ nstat -az TcpExtIPReversePathFilter
TcpExtIPReversePathFilter       1873               0.0

This is Module 17's uRPF (the BCP 38 mechanism), running on a single host and doing exactly what it was designed to do.

Fix. Make replies leave through the interface their address belongs to, with source-based policy routing:

# a routing table for traffic sourced from the data address
sudo ip route add 10.1.0.0/24 dev eth1 src 10.1.0.5 table 101
sudo ip route add default via 10.1.0.1 dev eth1 table 101
sudo ip rule add from 10.1.0.5/32 lookup 101 priority 1000

$ ip route get 192.168.50.10 from 10.1.0.5
192.168.50.10 from 10.1.0.5 via 10.1.0.1 dev eth1 table 101 uid 0
    cache

Make it persistent in the host's network configuration (netplan, NetworkManager and systemd-networkd all support routing policy rules). If rp_filter is strict, either set it to 2 (loose) on both interfaces or rely on the policy routes. The policy routes satisfy the strict check too, because the kernel's reverse lookup for traffic to 10.1.0.5 now finds eth1. Verify with the same tcpdump -i any: SYN in on eth1, SYN-ACK out on eth1.

The same failure shows up all over the cloud: VMs with a second network interface, which typically need the same policy routing; Kubernetes services where a load balancer sends traffic to a node that replies directly; and hybrid links where BGP prefers one path out and another path in. Any stateful device that sees only one direction of a flow will drop it.

Deep dive: 2026 context

Most of your vantage points are virtual. On a Kubernetes node, a packet can cross a pod's veth, a bridge or eBPF program, iptables or nftables rules for Services, an overlay encapsulation and the host NIC before it leaves. Capture at more than one of these points. With eBPF-based networking, the iptables view is empty and the state lives in eBPF maps. Use the CNI's own tooling: Cilium, for example, has cilium monitor and Hubble to show verdicts and drops per flow, with a reason.

Cloud networks hide the middle of the path. You can't run tcpdump on the VPC router or the managed NAT gateway. Your evidence is flow logs (which record accept or reject per flow, without payloads), provider metrics, and per-interface counters like ENA's bw_in_allowance_exceeded, pps_allowance_exceeded, conntrack_allowance_exceeded and linklocal_allowance_exceeded. Learn which counters your platform exposes before an incident. They are often the only proof that the provider dropped the packet and not you.

QUIC changes the toolbox. HTTP/3 runs over UDP with almost every header encrypted, so tcpdump shows you sizes and timing, not sequence numbers or ACKs. To see inside QUIC you need endpoint data: qlog files from the client or server, or a key log (SSLKEYLOGFILE) loaded into Wireshark. QUIC also changes the PMTU story. It needs at least 1,200 bytes per datagram, and it discovers the path MTU itself with probes (RFC 9000 and RFC 8899). When UDP is blocked or black-holed, browsers fall back to TCP, so "HTTP/3 is broken" often looks like slightly slower page loads rather than an outage. Compare curl --http3 against curl --http2 to tell the two apart.

Encrypted DNS moves the evidence. With DNS over HTTPS or TLS on the client, tcpdump 'udp port 53' shows nothing, and the resolver your app actually uses may not be the one in resolv.conf. Check the application's or browser's DNS settings. On macOS, look at scutil --dns for per-domain resolvers that VPN and MDM profiles install.

The one-command answer is still the packet. None of this changes the module's last word: captures don't lie. What changes is where you have to stand to take one, and how often the honest answer is a counter rather than a capture.

Deep dive: senior interview questions

Q1: tcpdump on the server shows the client's SYN arriving, but no SYN-ACK goes out. List the places it could have died, and how you'd tell them apart.

The capture tap is before the firewall, so the SYN can still be dropped by netfilter (check rule counters with nft list ruleset or iptables -L -v, or add a log rule), by the reverse-path filter (TcpExtIPReversePathFilter), or by a full conntrack table (table full in dmesg, drops in conntrack -S). It can die at the listener when the accept queue is full (TcpExtListenOverflows). Or the SYN-ACK was generated and an OUTPUT rule dropped it before the tap. (No listener at all would produce a RST, which you'd see.) Each of these has its own counter. Read the counter; don't guess.

Q2: Why does a PMTU black hole break TLS handshakes and git clone but not SSH logins or small API calls?

Only packets larger than the path MTU are dropped. Small requests and interactive SSH fit. The server's TLS first flight, with its certificate chain, and any bulk transfer fill full-size segments, so they're the first to vanish. It shows up as a stall right after the ClientHello, with SACK holes in the capture.

Q3: curl -w shows time_connect at 31 ms and time_appconnect at 3.1 s. What are your hypotheses?

The TCP handshake was fine, so the path works for small packets. Three seconds inside TLS points to one of three things. A packet in the server's large flight was lost and retransmission timeouts followed (PMTU, or plain loss on a congested link). The server did slow work during the handshake, such as a remote key operation or an OCSP fetch. Or a TLS-inspecting middlebox was slow to fetch and mint certificates. openssl s_client from the same host plus a capture separates them: missing segments versus a quiet server.

Q4: mtr shows 40% loss at hop 6 and 0% at the destination. Is there a problem?

Not at hop 6. That router rate-limits the ICMP time-exceeded messages it generates, because they're handled by its control-plane CPU, while transit traffic is forwarded in hardware. Real loss starts at a hop and continues to the destination. The same goes for latency spikes that don't persist.

Q5: Latency spikes of exactly 5 seconds appear in a service's p99, only from inside Kubernetes pods. Walk me through it.

5 seconds is the glibc resolver timeout, so the first suspect is a lost DNS packet. Pods use ndots:5 with a long search list, so external names generate around ten queries per lookup, multiplying the chance of a loss. Prove it by reading /etc/resolv.conf in the pod and counting queries in a capture. Then find the drop: conntrack insert_failed, CoreDNS throttling, or provider DNS packet limits. Fix by lowering ndots or using FQDNs, and add a node-local DNS cache.

Q6: The conntrack table is full. Why isn't raising nf_conntrack_max the whole answer?

It treats the symptom. Entries equal new-flow rate times lifetime, so you need to know which of those changed: usually lost connection reuse, or a flood of short UDP flows. Raising the max costs kernel memory and needs a matching hash table size, and the alert must fire well before the table is full. The durable fixes are connection pooling, shorter timeouts where safe, and notrack for flows that don't need state.

Q7: How do you prove asymmetric routing on a single Linux host?

Capture on -i any and look at the interface tags: request in on one interface, reply out of another. Then ip route get <client> from <server-address> shows the kernel's choice and why. If rp_filter is strict you may see no reply at all, and TcpExtIPReversePathFilter climbing is the evidence. Fix with source-based policy routing (ip rule plus a per-interface table).

Q8: A colleague says "ping works and dig works, so it's not the network." What would you ask?

Which protocol, which size, and which resolver. Ping proves small ICMP packets get through, not large TCP ones (PMTU) or this TCP port (firewall). dig bypasses the system resolver, its search list and /etc/hosts, so test with getent ahosts or dscacheutil. Then I'd ask for the curl -w breakdown, which names the slow phase in one command.
