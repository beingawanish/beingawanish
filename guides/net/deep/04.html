Deep dive: what a router does to every packet

The module treated IP addresses as street addresses and the headers as forms with labelled boxes. That is a fine way to learn the fields. It hides what happens to those boxes in transit.

A router is a loop that runs billions of times a second. It checks a packet, looks up the destination, decrements the TTL, patches the checksum, checks the size against the next link, rewrites the Ethernet header and queues the frame. Most packets take that fast path entirely in hardware. A few fall off it: the ones whose TTL runs out, the ones too big for the next link, the ones carrying options. They land in a slow path run by a CPU that is a thousand times slower and deliberately rate-limited. Almost every confusing IP behaviour you will meet in production lives on that boundary: traceroute hops that show * * *, PMTUD black holes, IPv6 packets with extension headers that vanish, fragments that never reassemble.

The second half of this deep dive is about the endpoint. A dual-stack host has two Internets to choose from, and the choice is made by a timer race called Happy Eyeballs. When that race hides a broken IPv6 path, you get a 250 ms penalty on some connections and a two-minute hang on others.

Deep dive: the real mental model — the forwarding loop and its exits

Here is the per-packet sequence for IPv4, in the order a router performs it. RFC 1812 is the requirements document for IPv4 routers; RFC 8200 and RFC 4443 cover IPv6.

  1. Accept the frame. The destination MAC must be the router's own interface MAC, or a multicast/broadcast address it listens to. The NIC has already checked the FCS.
  2. Sanity-check the header. Version is 4, IHL is at least 5, Total Length fits within the frame, and the header checksum verifies. A packet that fails is dropped and counted (InHdrErrors on Linux). In hardware routers this check happens in the pipeline at no extra cost.
  3. Is it for me? If the destination is one of the router's own addresses, the packet goes up to the router's local stack (routing protocols, SSH, ping replies). This path is policed by control-plane policing, so a flood of packets to the router cannot starve BGP. TTL is not checked for packets addressed to the router.
  4. Look up the destination. Longest-prefix match in the FIB returns a next hop and an egress interface. No match and no default route: drop, and generate ICMP Destination Unreachable (type 3, code 0, net unreachable).
  5. Check and decrement TTL. If TTL is 1 or 0, the packet cannot be forwarded: drop it and generate ICMP Time Exceeded (type 11, code 0). Otherwise TTL becomes TTL − 1.
  6. Patch the checksum. The TTL changed, so the header checksum must change. Routers do not recompute it over 20 bytes; they apply an incremental update (RFC 1624). Decrementing TTL by one adds exactly 0x0100 to the checksum, in ones'-complement arithmetic. The code below proves it.
  7. Check the size. If the packet is bigger than the egress MTU and DF is set, drop it and send ICMP Destination Unreachable, code 4, fragmentation needed, with the next-hop MTU in the message (RFC 1191). If DF is clear, fragment it. Fragmentation is usually done by the slow path.
  8. Resolve the next hop. Look up the next hop's MAC in the ARP table (IPv4) or neighbor cache (IPv6). In hardware this is an adjacency entry, precomputed with the full new Ethernet header. If there is no entry, the packet is held (or dropped) while the CPU sends an ARP request.
  9. Rewrite and queue. New source MAC (the router's egress interface), new destination MAC (the next hop), and the packet joins the egress queue.

IPv6 is the same loop with three differences. There is no header checksum to patch. The field is called Hop Limit, and the error is ICMPv6 Time Exceeded (type 3, code 0). And step 7 has only one branch: an IPv6 router never fragments. It drops the packet and sends ICMPv6 Packet Too Big (type 2), carrying the MTU.

The fast path and the slow path

Steps 1–9 for an ordinary packet run in the forwarding ASIC, or in a tight software loop such as Linux's forwarding path or a DPDK forwarder. Anything that requires generating a new packet, or doing unusual work, is punted to the router's CPU:

  • generating any ICMP error (Time Exceeded, Unreachable, Packet Too Big);
  • fragmenting an IPv4 packet;
  • processing IPv4 options and, on many platforms, IPv6 Hop-by-Hop options;
  • packets addressed to the router itself;
  • packets whose next hop has no ARP/ND entry yet.

A hardware router may forward hundreds of millions of packets per second. Its control-plane CPU may handle thousands to tens of thousands per second for all the punted work combined, and the punt path is rate-limited on purpose. Linux does the same in software. Its defaults, read from a fresh network namespace on a 6.18 kernel, rate-limit ICMP errors per destination with a token bucket, plus a global cap:

net.ipv4.icmp_ratelimit = 1000        <- ms per token, per destination host
net.ipv4.icmp_ratemask = 6168         <- bits 3,4,11,12: Unreachable, Source Quench, Time Exceeded, Param Problem
net.ipv4.icmp_msgs_per_sec = 1000     <- global cap for all destinations
net.ipv4.icmp_msgs_burst = 50

Two consequences follow, and both matter for troubleshooting.

  • Traceroute measures the slow path. The RTT printed for an intermediate hop is the time that router's CPU took to generate a Time Exceeded message, not the time to forward through it. A middle hop showing 200 ms while the final hop shows 20 ms means that router's CPU was busy or rate-limiting. It does not mean the path is slow.
  • * * * is often policy, not failure. A hop that never answers has usually been told not to generate Time Exceeded, or its answers were rate-limited. If later hops answer, the path through it works.

What goes into an ICMP error

An ICMP error is a new packet, sent from the router to the source of the packet that caused it. It carries a copy of the offending packet's IP header plus at least the first 8 bytes of its payload (RFC 792). That is enough for the source to find the TCP or UDP ports and match the error to a socket. RFC 1812 lets routers include more, up to a 576-byte total, and Linux does exactly that, as the capture below shows. ICMPv6 errors carry as much of the original as fits in 1,280 bytes.

Hosts and routers must not send an ICMP error in response to another ICMP error, a packet sent to a broadcast or multicast address, a non-first fragment, or a packet whose source address is not a single host. These rules exist to stop error storms and amplification.

The source address of the error is one of the router's own addresses. Vendors differ on which one; Linux, by default, uses the address of the interface its route back to the sender points at. That is why traceroute shows interface addresses, and why the same router can appear under different addresses on different paths.

TTL decrement and the checksum, proved

The checksum is the ones'-complement of the ones'-complement sum of the header's 16-bit words. TTL sits in the high byte of the word it shares with Protocol. Decrementing TTL subtracts 0x0100 from that word. The sum drops by 0x0100, so its complement — the checksum — rises by 0x0100. RFC 1624 gives the general update formula, which is safe in every corner case (an earlier version in RFC 1141 was not):

"""What a router does to an IPv4 header: decrement TTL, patch the checksum.

Full recompute (RFC 791/1071) versus incremental update (RFC 1624, eqn. 3):
    HC' = ~(~HC + ~m + m')      all in 16-bit ones'-complement arithmetic
"""
import random
import struct

def csum(data: bytes) -> int:
    s = sum(struct.unpack(f"!{len(data)//2}H", data))
    while s >> 16:
        s = (s & 0xFFFF) + (s >> 16)
    return ~s & 0xFFFF

def add1c(a, b):
    s = a + b
    return (s & 0xFFFF) + (s >> 16)

def incremental(hc, old_word, new_word):
    return ~add1c(add1c(~hc & 0xFFFF, ~old_word & 0xFFFF), new_word) & 0xFFFF

def header(ttl, ident=0x97E5, src="10.1.1.10", dst="10.2.2.20"):
    a = bytes(map(int, src.split(".")))
    b = bytes(map(int, dst.split(".")))
    h = struct.pack("!BBHHHBBH4s4s", 0x45, 0, 84, ident, 0x4000, ttl, 1, 0, a, b)
    return h[:10] + struct.pack("!H", csum(h)) + h[12:]

h = header(64)
print("arriving header :", h.hex(" ", 2))
hc = struct.unpack("!H", h[10:12])[0]
old = struct.unpack("!H", h[8:10])[0]          # word holding TTL and Protocol
new = old - 0x0100                              # TTL - 1 lives in the high byte
fast = incremental(hc, old, new)
slow = csum(h[:8] + struct.pack("!H", new) + b"\0\0" + h[12:])
print(f"TTL/proto word  : {old:#06x} -> {new:#06x}")
print(f"checksum        : {hc:#06x} -> {fast:#06x} (incremental), {slow:#06x} (full)")
print(f"difference      : {fast - hc:+#x}  <- TTL-1 adds 0x0100 to the checksum")

# Brute check over many random headers and every TTL from 2 to 255.
random.seed(1)
bad = 0
for _ in range(2000):
    ident = random.getrandbits(16)
    for ttl in range(2, 256):
        h = header(ttl, ident)
        hc = struct.unpack("!H", h[10:12])[0]
        w = struct.unpack("!H", h[8:10])[0]
        nh = h[:8] + struct.pack("!H", w - 0x100) + b"\0\0" + h[12:]
        bad += incremental(hc, w, w - 0x100) != csum(nh)
print(f"checked {2000*254:,} decrements, mismatches: {bad}")

Output from a real run (Python 3.13):

arriving header : 4500 0054 97e5 4000 4001 8ba3 0a01 010a 0a02 0214
TTL/proto word  : 0x4001 -> 0x3f01
checksum        : 0x8ba3 -> 0x8ca3 (incremental), 0x8ca3 (full)
difference      : +0x100  <- TTL-1 adds 0x0100 to the checksum
checked 508,000 decrements, mismatches: 0

So IPv6 dropping the checksum was less about CPU cycles than it sounds: the incremental update is one add. The bigger win was removing a field that every router had to touch, and that every middlebox rewriting addresses (NAT) had to patch too.

The source then fragments its next packet itself, adding an 8-byte Fragment header: 40 + 8 + 1,352 = 1,400 bytes on the wire, where 1,352 is the largest multiple of 8 that fits. Compare the IPv4 case. There, a router in the middle did this work. Here, only the host may.

The arithmetic for all of these comes from a small calculator:

"""Fragment sizes a router (IPv4) or a source host (IPv6) must produce."""

def ipv4_fragments(total_len, mtu, ihl=20):
    payload = total_len - ihl
    per_frag = (mtu - ihl) // 8 * 8          # offsets count 8-byte units
    out, off = [], 0
    while off < payload:
        size = min(per_frag, payload - off)
        mf = off + size < payload
        out.append((off // 8, off, size, ihl + size, mf))
        off += size
    return out

def ipv6_fragments(payload_len, mtu, unfrag=40):
    per_frag = (mtu - unfrag - 8) // 8 * 8   # 8-byte Fragment header
    out, off = [], 0
    while off < payload_len:
        size = min(per_frag, payload_len - off)
        out.append((off // 8, off, size, unfrag + 8 + size, off + size < payload_len))
        off += size
    return out

def show(title, frags):
    print(title)
    print("  offset-field  byte-offset  data  on-wire-len  MF")
    for f in frags:
        print(f"  {f[0]:>12}  {f[1]:>11}  {f[2]:>4}  {f[3]:>11}  {int(f[4])}")

show("IPv4: 1500-byte datagram, next-hop MTU 1400 (the lab capture)", ipv4_fragments(1500, 1400))
show("IPv4: 4000-byte datagram, next-hop MTU 1500", ipv4_fragments(4000, 1500))
show("IPv6: 1500-byte echo request (payload 1460) sent by the host, path MTU 1400",
     ipv6_fragments(1460, 1400))

# IPv4 Identification wrap: how fast does a 16-bit ID repeat?
rate_bps = 1e9
frag_pps = rate_bps / (1500 * 8)
datagrams_ps = frag_pps / 2                  # 2 fragments per datagram
print(f"\nIPv4 ID wrap at 1 Gb/s of 2-fragment datagrams: "
      f"{65536 / datagrams_ps:.2f} s (reassembly timeout on Linux: 30 s)")

The last line is a real hazard, described in RFC 4963. The 16-bit Identification field repeats every 65,536 datagrams. At 1 Gb/s of fragmented traffic between one pair of hosts, it wraps in 1.6 seconds, while a reassembly buffer holds fragments for 30 seconds. If a fragment is lost and a later datagram reuses its ID, the receiver can stitch together pieces of two different datagrams. The UDP checksum catches most of these, but a 16-bit checksum lets roughly one in 65,536 through. High-rate fragmented UDP can silently corrupt data. IPv6's Fragment header uses a 32-bit identification for this reason.

Deep dive: IPv6 extension headers, and why the Internet drops them

The module described extension headers as a tidy linked list: each header's Next Header field names the one after it, and routers skip what they do not need. On paper that is true. In practice, packets carrying extension headers are dropped on a significant fraction of Internet paths. RFC 7872 measured this in 2016 and found loss rates from around a tenth to over half of destinations, depending on the header type and the data set. Later operational documents (RFC 9098, RFC 9288) explain why, and when, transit networks filter them.

RFC 8200 recommends this order when several are present:

Next Header value Header Who processes it
0 Hop-by-Hop Options Every router on the path (in principle; see below)
60 Destination Options (before Routing) Each destination listed in the Routing header
43 Routing Nodes named in it (e.g. SRv6 segment endpoints)
44 Fragment Final destination only
51 Authentication Header Final destination
50 ESP Final destination
60 Destination Options Final destination
6 / 17 / 58 TCP / UDP / ICMPv6 Final destination
59 No Next Header —

Four mechanisms explain the drops.

1. Hop-by-Hop means slow path. Hop-by-Hop options were meant to be examined by every router. Forwarding ASICs did not want to parse variable TLVs, so routers punted these packets to the CPU. That made them a cheap way to attack a router's control plane, and operators responded by dropping or rate-limiting them. RFC 8200 relaxed the rule: routers may ignore Hop-by-Hop options unless explicitly configured to process them. Old habits remain in filters.

2. The parser window. As Module 03's deep dive showed, a switch or router parser reads a fixed number of bytes. ACLs that match TCP or UDP ports need those ports inside the window, and every extension header pushes them further out. When a device cannot find the L4 header, it can let the packet through unchecked (unsafe) or drop it (safe). Most choose drop. The script below walks a chain and reports where the ports land:

"""Walk an IPv6 extension-header chain and find where the TCP ports sit.

Hardware parsers read a fixed window of bytes. If the ports fall outside it,
an ACL that matches on port cannot be evaluated, and many devices drop.
"""
import struct

NAMES = {0: "Hop-by-Hop", 43: "Routing", 44: "Fragment", 60: "Dest Options",
         6: "TCP", 17: "UDP", 58: "ICMPv6", 59: "No Next Header"}

def opts_header(next_hdr, total_len):
    """Generic TLV header (HBH / DestOpts): len field = 8-octet units minus 1."""
    assert total_len % 8 == 0
    pad = total_len - 2
    body = bytes([1, pad - 2]) + bytes(pad - 2)       # one PadN option fills it
    return bytes([next_hdr, total_len // 8 - 1]) + body

def frag_header(next_hdr, offset_units, more, ident):
    return struct.pack("!BBHI", next_hdr, 0, (offset_units << 3) | more, ident)

def build(chain):
    """chain: list of (kind, size) for extension headers, then TCP."""
    kinds = [k for k, _ in chain] + [6]
    body = b""
    for i, (kind, size) in enumerate(chain):
        nxt = kinds[i + 1]
        body += frag_header(nxt, 0, 1, 0x1234) if kind == 44 else opts_header(nxt, size)
    tcp = struct.pack("!HHIIBBHHH", 51000, 443, 1, 0, 0x50, 0x02, 65535, 0, 0)
    payload = body + tcp
    fixed = struct.pack("!IHBB16s16s", 6 << 28, len(payload), kinds[0], 64,
                        bytes(16), bytes(16))
    return fixed + payload

def walk(pkt):
    nxt, off, hops = pkt[6], 40, []
    while nxt in (0, 43, 60, 44):
        size = 8 if nxt == 44 else (pkt[off + 1] + 1) * 8
        hops.append(f"{NAMES[nxt]}({size})")
        nxt, off = pkt[off], off + size
    return hops, NAMES.get(nxt, nxt), off

cases = {
    "plain TCP": [],
    "HBH 8 + Fragment": [(0, 8), (44, 8)],
    "HBH 8 + DestOpts 64 + Fragment": [(0, 8), (60, 64), (44, 8)],
    "DestOpts 256 (padding abuse)": [(60, 256)],
}
print(f"{'chain':34} {'L4 at':>5} {'ports end':>9}  fits 64B? fits 128B?")
for name, chain in cases.items():
    pkt = build(chain)
    hops, l4, off = walk(pkt)
    end = off + 4                            # source + destination port
    sport, dport = struct.unpack("!HH", pkt[off:off + 4])
    assert (sport, dport) == (51000, 443)
    print(f"{name:34} {off:>5} {end:>9}  {str(end <= 64):>9} {str(end <= 128):>9}")

Output from a real run. Offsets count from the start of the IPv6 header; a real parser window also has to hold the 14-byte Ethernet header (18 with a VLAN tag):

chain                              L4 at ports end  fits 64B? fits 128B?
plain TCP                             40        44       True      True
HBH 8 + Fragment                      56        60       True      True
HBH 8 + DestOpts 64 + Fragment       120       124      False      True
DestOpts 256 (padding abuse)         296       300      False     False

A Destination Options header can legally be up to 2,048 bytes long. An attacker can push the TCP header past any fixed parser window with padding alone. That is a real filter-evasion technique, not a theoretical one, and it is why "drop if the L4 header is not found" is the safe default.

3. Fragments hide the ports. A non-first fragment has no L4 header at all, as the IPv4 capture showed, so stateless ACLs cannot classify it. RFC 7112 at least requires the first fragment to carry the entire header chain through the L4 header, so a filter can decide on the first fragment. Many networks still drop all IPv6 fragments at the edge. IPv6 also forbids overlapping fragments outright (RFC 5722), closing an evasion trick that IPv4 still permits.

4. History. The Type 0 Routing header let a sender list many intermediate addresses, so a single packet could bounce between two routers dozens of times — a traffic amplifier. RFC 5095 deprecated it in 2007. Filters written then often drop every Routing header, including the legitimate Type 4 Segment Routing Header (RFC 8754) used by SRv6.

The practical result: do not design an Internet-facing protocol that depends on IPv6 extension headers arriving. Inside a single operator's network, where you control every device, SRv6 and other extension-header uses work fine. Across the Internet, the robust choices are plain TCP, UDP, or QUIC over UDP, with no fragmentation.

Deep dive: dual stack and Happy Eyeballs

A dual-stack host has two complete network stacks: two sets of addresses, two default routes and two sets of firewall rules. Either one can be broken while the other works. The classic failure: the host gets an IPv6 address and a default route from a router advertisement, but IPv6 is broken somewhere upstream. A client that tries IPv6 first, and waits for that connection to time out before trying IPv4, hangs. On Linux that is 127 seconds with the default tcp_syn_retries = 6 (six SYN retransmissions after waits of 1, 2, 4, 8, 16 and 32 s, then a final 64 s wait). On macOS it is about 75 s.

Happy Eyeballs (RFC 8305, "version 2") replaces "try one, then the other" with a race:

  1. Send the AAAA and A DNS queries in parallel, AAAA first. If A answers first, wait up to 50 ms (the Resolution Delay) for AAAA before starting.
  2. Sort the addresses (RFC 6724 rules, plus any history the client keeps) and interleave the families: v6, v4, v6, v4.
  3. Start a connection to the first address. If it has not completed within the Connection Attempt Delay — 250 ms recommended, with RFC-recommended bounds of 100 ms to 2 s — start the next one without cancelling the first. If an attempt fails outright, start the next one immediately.
  4. The first connection to complete wins. Cancel the rest.

The simulation below runs that race with real asyncio timers against three scripted network conditions:

"""Happy Eyeballs v2 (RFC 8305) connection racing, with simulated paths.

Each address has a scripted outcome: ("ok", rtt) completes after rtt seconds,
("refused", t) fails after t, ("blackhole", None) never answers.
Real asyncio timers run the race; only the network is simulated.
"""
import asyncio
import time

ATTEMPT_DELAY = 0.250        # RFC 8305 recommended Connection Attempt Delay

async def connect(addr, outcome, log, t0):
    kind, t = outcome
    log.append(f"{(time.monotonic()-t0)*1000:6.0f} ms  try {addr}")
    if kind == "blackhole":
        await asyncio.sleep(3600)
    await asyncio.sleep(t)
    if kind == "refused":
        log.append(f"{(time.monotonic()-t0)*1000:6.0f} ms  {addr} refused")
        raise ConnectionRefusedError(addr)
    return addr

def interleave(v6, v4):
    out = []
    for i in range(max(len(v6), len(v4))):
        out += v6[i:i+1] + v4[i:i+1]
    return out

async def happy_eyeballs(addrs, paths):
    t0, log, tasks = time.monotonic(), [], []
    failed = asyncio.Event()
    winner = None
    for addr in addrs:
        task = asyncio.create_task(connect(addr, paths[addr], log, t0))
        task.add_done_callback(lambda _t: failed.set())
        tasks.append(task)
        failed.clear()
        try:
            await asyncio.wait_for(failed.wait(), ATTEMPT_DELAY)
        except TimeoutError:
            pass
        done = [t for t in tasks if t.done() and not t.exception()]
        if done:
            break
    while winner is None:
        pending = [t for t in tasks if not t.done()]
        ok = [t for t in tasks if t.done() and not t.exception()]
        if ok:
            winner = ok[0].result()
            break
        if not pending:
            break
        await asyncio.wait(pending, return_when=asyncio.FIRST_COMPLETED)
    for t in tasks:
        t.cancel()
    log.append(f"{(time.monotonic()-t0)*1000:6.0f} ms  connected via {winner}")
    return log

V6 = ["[2001:db8::10]", "[2001:db8::11]"]
V4 = ["192.0.2.10", "192.0.2.11"]
scenarios = {
    "healthy IPv6 (20 ms)": {V6[0]: ("ok", .020), V6[1]: ("ok", .020),
                             V4[0]: ("ok", .018), V4[1]: ("ok", .018)},
    "IPv6 black-holed":     {V6[0]: ("blackhole", None), V6[1]: ("blackhole", None),
                             V4[0]: ("ok", .018), V4[1]: ("ok", .018)},
    "IPv6 refused fast":    {V6[0]: ("refused", .005), V6[1]: ("refused", .005),
                             V4[0]: ("ok", .018), V4[1]: ("ok", .018)},
}
order = interleave(V6, V4)
print("attempt order:", ", ".join(order))
for name, paths in scenarios.items():
    print(f"\n== {name}")
    for line in asyncio.run(happy_eyeballs(order, paths)):
        print(line)

The middle case is the important one. A black-holed IPv6 path costs 250 ms on every new connection, not two minutes. That is a huge improvement. It is also a trap, because the breakage becomes invisible. Nobody files a ticket for "every page load is a quarter-second slower". Some clients also remember which family worked recently and skip the losing one for a while, which hides the problem further.

You can watch the race with curl, which implements Happy Eyeballs with a 200 ms default delay (--happy-eyeballs-timeout-ms). The output below is an annotated illustration of curl 8.x against a host whose IPv6 path is black-holed:

# run on your Mac — your output will differ
$ curl -sv -o /dev/null https://www.example.net/ 2>&1 | head -6

* IPv4: 192.0.2.10
*   Trying [2001:db8::10]:443...        <- t = 0

To test each family on its own, force it: curl -6 -sv -o /dev/null https://… and curl -4 …. A dual-stack host where curl -6 hangs and curl -4 works has a broken IPv6 path that Happy Eyeballs is hiding.

Not everything races. In Python, socket.create_connection() tries addresses one at a time in getaddrinfo order, waiting for each to fail. asyncio's open_connection() races only when you pass happy_eyeballs_delay (0.25 is the recommended value). Plain connect() loops in C, old Java, and many health-check scripts do not race either. They are the ones that hang.

On Linux, getaddrinfo sorts addresses with the RFC 6724 rules, adjustable in /etc/gai.conf. On macOS, the system's Network framework (used by URLSession and Safari) does its own Happy Eyeballs, while programs that use BSD sockets directly get the raw getaddrinfo order.

A worked MTU budget, because it comes up constantly. A VXLAN overlay on a 1,500-byte underlay adds an outer IPv4 header (20), UDP (8), VXLAN (8) and the inner Ethernet header (14): 50 bytes. The inner MTU must be 1,450. Inner TCP over IPv4 then has an MSS of 1,450 − 20 − 20 = 1,410 bytes. Put that overlay inside a WireGuard tunnel with a 1,420-byte MTU and the inner MTU drops to 1,370. If any layer advertises 1,500 to the layer above, packets will be too big somewhere. The only thing that saves you then is an ICMP message getting back to the sender.

Deep dive: production failure modes

The PMTUD black hole

Symptom. SSH logs in, then hangs on ls of a big directory. A web page loads its HTML and stalls on images. TLS handshakes fail on some sites, because the server's certificate chain is the first large packet. Small requests always work.

Mechanism. Some link on the path has a smaller MTU: a tunnel, a PPPoE line, a cloud interconnect. The sender sets DF. The router at the small link drops the full-size packets and sends ICMP frag needed (or ICMPv6 Packet Too Big). Something on the way back — a firewall, a security group, a load balancer — drops that ICMP. The sender never learns, and keeps retransmitting the same full-size segment.

Prove it. Find the largest packet that gets through with DF set. On macOS, ping -D -s 1472 host (1,472 + 8 ICMP + 20 IP = 1,500), then shrink until replies arrive. On Linux, ping -M do -s 1472 host, or tracepath host, which reports the PMTU hop by hop. Capture on the sender with sudo tcpdump -nn -i en0 'icmp[icmptype]=3 and icmp[icmpcode]=4 or icmp6[0]=2'. In the black-hole case you see big segments being retransmitted and no ICMP coming back. On Linux, ip route get <dst> shows whether a PMTU was ever learned.

Fix. Let ICMP type 3 code 4 and ICMPv6 type 2 through every firewall (RFC 4890 is the guide for ICMPv6 filtering). Where you cannot, clamp the TCP MSS at the tunnel edge (iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu on Linux). On end hosts, enable packetization-layer PMTU discovery (RFC 4821), which finds the size by probing with TCP itself and needs no ICMP: sysctl -w net.ipv4.tcp_mtu_probing=1 on Linux (the default is 0).

Traceroute shows loss or latency at a middle hop

Symptom. Someone pastes a traceroute where hop 6 shows 40 % loss and 300 ms, and asks you to escalate to that ISP.

Mechanism. Traceroute's answers come from each router's slow path, which is rate-limited and low priority. If hops 7 to 12 show no loss and normal latency, traffic is being forwarded through hop 6 fine. Only the ICMP generation there is slow.

Prove it. Look at the final hop. Loss or latency that is real persists to the destination. Use mtr to see per-hop statistics over many probes. With ECMP in the path, classic traceroute varies the probe's ports, so different probes take different paths and the hop list mixes routers. Paris-traceroute-style probing keeps the flow fields constant (for example traceroute -U on Linux, which uses a fixed destination port).

Fix. Nothing on hop 6. Escalate only loss that appears at a hop and continues through every hop after it.

Fragments dropped, or reassembled wrong

Symptom. DNS works for most names but fails for some, usually DNSSEC-signed names or large TXT records. UDP-based VPNs or game traffic fail on some networks. Rarely, silent data corruption in high-rate UDP.

Mechanism. A response larger than the path MTU is fragmented, and a firewall drops non-first fragments (they carry no ports) or the reassembly buffer evicts them. For DNS, the client then waits for a timeout before retrying over TCP. Corruption is the ID wrap described above.

Prove it. Compare dig +bufsize=4096 +dnssec <name> with dig +bufsize=1232 … and dig +tcp …; the large-buffer query fails and the others work. On the receiver, Linux counts reassembly failures in nstat -az IpReasmFails IpReasmTimeout; macOS reports them in netstat -s -p ip.

Fix. Avoid fragmentation. DNS resolvers now default to an EDNS buffer size of 1,232 bytes (the "DNS flag day 2020" value) so responses fit in one IPv6 packet, and fall back to TCP for larger ones. UDP applications should size their datagrams to the path MTU, as QUIC does.

Broken IPv6 hidden by Happy Eyeballs

Symptom. Browsers are fine. A cron job, a health check or a Python script hangs for two minutes against the same hostname. Or: p50 connect time to a service rose by exactly 200–300 ms after a network change.

Mechanism. IPv6 is configured but does not work end to end: a missing route, a security group with IPv4 rules only, a load balancer with an AAAA record but no IPv6 listener. Racing clients lose a quarter of a second; non-racing clients time out.

Prove it. Compare curl -6 and curl -4 against the same URL, adding -w '%{time_connect}\n'. Check the AAAA record (dig AAAA name) and whether the service actually listens on IPv6. In Kubernetes, kubectl get svc <name> -o jsonpath='{.spec.ipFamilies}' shows which families a Service has.

Fix. Fix the IPv6 path, or stop publishing the AAAA record until it works. Do not "fix" it by disabling IPv6 on clients; that just moves the problem to the next person.

Deep dive: 2026 context

IPv6 is now the majority path for many networks. Google's public statistics have shown close to half of its users reaching it over IPv6 in recent years, and mobile networks are often IPv6-only underneath. Many phones on those networks run 464XLAT (RFC 6877): the phone has an IPv6-only connection, a local translator (CLAT) presents IPv4 to apps, and the carrier's NAT64 (RFC 6146) translates to IPv4 at the edge. DNS64 (RFC 6147) synthesises AAAA records inside the well-known prefix 64:ff9b::/96 (RFC 6052) for names that only have A records. Apple has required iOS apps to work on IPv6-only networks since 2016, for exactly this reason.

Public IPv4 has a price tag. AWS has charged for every public IPv4 address since February 2024 ($0.005 per hour). That turned "should we go IPv6?" from an architecture debate into a cost line. IPv6-only subnets, IPv6 EKS clusters and dual-stack load balancers are now ordinary choices, which makes the dual-stack failure modes above ordinary too.

Kubernetes has two address families to get right. Dual-stack networking has been stable since Kubernetes 1.23. Pods get one address per family, Services declare ipFamilies and ipFamilyPolicy, and NetworkPolicies need rules for both. A SingleStack IPv4 Service behind an ingress that publishes AAAA records is a black hole waiting to happen.

Overlays and tunnels make MTU everyone's problem. VXLAN and Geneve CNIs, WireGuard (and the meshes built on it), IPsec and cloud interconnects each take tens of bytes per packet. Inside AWS a VPC carries 9,001-byte frames, but traffic leaving through an Internet gateway is limited to 1,500. Google Cloud's VPC default is 1,460. Path MTU problems that were rare on a flat LAN now turn up all the time in clusters.

QUIC does PMTU discovery itself. QUIC (RFC 9000) runs over UDP, sets DF, and requires every path to carry UDP payloads of at least 1,200 bytes. It then probes for larger sizes with its own packets (datagram PLPMTUD, RFC 8899), so it does not depend on ICMP arriving. It never relies on IP fragmentation. HTTP/3's growth is one reason fragmentation is becoming rarer on the Internet.

Happy Eyeballs keeps evolving. A version 3 is being worked on as an IETF draft. It adds the DNS HTTPS/SVCB records (which can advertise HTTP/3 support and address hints), and racing QUIC against TCP, to the version 2 algorithm. Browsers already do much of this in practice.

Extension headers live inside operator domains. SRv6, which carries a list of segments in a Routing header, is deployed by some large carriers and in some data-centre fabrics — inside networks that control every router. Across the open Internet, the advice from the extension-header section stands.

Deep dive: senior interview questions

Q1: A router decrements TTL. What else must it change in the packet, and how expensive is that?

For IPv4, the header checksum. It does not recompute it over the whole header. The RFC 1624 incremental update adjusts the old checksum by the difference in the changed word, and a TTL decrement of one adds 0x0100 in ones'-complement arithmetic: a single add with end-around carry. The router also rewrites the Ethernet header (new source and destination MACs), and the NIC computes a new FCS. For IPv6, only the Hop Limit changes; there is no header checksum.

Q2: Traceroute shows 300 ms at hop 5 and 25 ms at hops 6 to 10. Is hop 5 congested?

Almost certainly not. The hop-5 RTT measures how quickly that router's CPU generated an ICMP Time Exceeded message, which happens on a rate-limited, low-priority slow path. Packets forwarded through hop 5 take the fast path, and hops 6–10 show they arrive promptly. Real congestion or loss at hop 5 would show up at every hop after it.

Q3: Why can't a firewall filter a non-first IPv4 fragment by port, and what do firewalls do about it?

Only the first fragment carries the TCP or UDP header; non-first fragments contain raw payload with no ports. A stateless filter can either pass them (risky: overlapping-fragment tricks have been used to sneak data past filters) or drop them (which breaks large UDP). Stateful firewalls reassemble, or virtually reassemble by tracking fragments per (source, destination, protocol, ID), and apply the first fragment's decision to the rest. That costs memory per datagram, which is why fragment floods are a DoS attack against firewalls.

Q4: An IPv6 packet with a 72-byte Destination Options header and a Fragment header is dropped by a transit network. Give three reasons it might be.

One: the network's routers or ACLs parse a fixed number of bytes and cannot find the TCP/UDP header past the extension headers, so they drop rather than pass unclassified traffic. Two: policy drops IPv6 fragments at the border, because non-first fragments cannot be classified and fragments are a common attack tool. Three: the device filters packets with any extension headers at all, a common blanket rule (RFC 7872 measured how common). A Hop-by-Hop header would add a fourth: it is often punted to the CPU, so it is rate-limited or dropped to protect the control plane.

Q5: Why does IPv6 forbid router fragmentation but still require a minimum MTU of 1,280 bytes?

Removing router fragmentation pushes the job to the source, which then needs Path MTU Discovery to work. The 1,280-byte floor gives the source a size it may always send without waiting for discovery. It also bounds how much of a packet an ICMPv6 error can quote, so the error itself never needs fragmenting. Links that cannot carry 1,280 bytes must fragment and reassemble below IPv6, at the link layer.

Q6: A Python service calling an internal API sometimes takes exactly 127 seconds to fail. Browsers hitting the same hostname are fine. What is going on?

127 seconds is Linux's default TCP connect timeout: six SYN retransmissions after waits of 1, 2, 4, 8, 16 and 32 seconds, then a final 64-second wait. The hostname has an AAAA record, but IPv6 to it is black-holed. Browsers use Happy Eyeballs, start an IPv4 attempt after about 250 ms, and win on IPv4. The Python code uses socket.create_connection, which tries addresses in order and waits for each to time out before trying the next. Fix the IPv6 path or the AAAA record. As a mitigation, set a short connect timeout, or use asyncio with happy_eyeballs_delay.

Q7: Your SSH session works, but cat of a large file freezes the terminal — only on the VPN. Walk through the diagnosis.

Small packets work and large ones vanish, so suspect MTU. The VPN reduces the path MTU, and the ICMP that would tell the sender is being dropped somewhere. Confirm with DF-set pings of decreasing size (ping -D -s on macOS, ping -M do -s on Linux) to find the largest size that works, and capture to check that no ICMP frag needed comes back. Fixes: let that ICMP through, clamp the MSS on the VPN gateway, lower the tunnel interface MTU, or enable TCP MTU probing on the hosts.

Q8: Fragments of two different datagrams get reassembled together. How is that possible, and why is IPv6 less exposed?

IPv4's Identification field is 16 bits. A busy sender of fragmented traffic to one destination can cycle through all 65,536 values in a second or two, while the receiver keeps incomplete datagrams for up to 30 seconds (Linux). So an old fragment can match a new datagram with the same ID. The 16-bit transport checksum catches most such mixes, but not all (RFC 4963). IPv6's Fragment header carries a 32-bit identification, which pushes wraparound out by a factor of 65,536.
