Deep dive: what the "nearest copy" picture hid

The module's picture is a user, an edge, and an origin, with a cache in the middle that either has the copy or doesn't. That picture is right, and it hides almost everything that goes wrong in production.

Four things sit under it. First, "nearest" is decided by a routing system, either BGP or a DNS mapping service, and neither one measures distance. Second, "the copy" is not one object. It is a primary key plus a list of variants, each with its own clock. Third, a miss rarely goes straight to your origin. It passes through a coalescing table and a second cache tier, and those two structures decide what your origin actually sees. Fourth, "purge" is a message fanned out to thousands of machines, not a delete.

This deep dive walks through that machine: the state it keeps, what it looks like on the wire, the arithmetic of hit ratios, how it fails, and what a senior interviewer will push on.

Deep dive: the real mental model

Hold a CDN in your head as three systems stacked on top of each other. A steering system picks a PoP for each client. A cache hierarchy inside and between PoPs decides whether the bytes already exist. A control plane pushes configuration and purges to every node. Each has its own state and its own failure modes.

Request routing: anycast versus DNS mapping

Anycast puts the same prefix (say 192.0.2.0/24) into BGP from every PoP. Your packets go wherever your ISP's BGP best-path selection sends them. That selection compares local preference first, then AS-path length, then a handful of tie-breakers. Local preference usually encodes business policy: customer routes beat peer routes, and peer routes beat transit. Latency appears nowhere in that list. So "nearest" really means "best according to your ISP's policy". That is usually close, and occasionally a different country. The set of clients that land on a given PoP is called its catchment. CDNs shape catchments with selective announcements, AS-path prepending, and BGP communities. That is engineering work, not physics.

DNS mapping gives each customer hostname a CNAME into the CDN's namespace. The CDN's authoritative servers answer with the unicast addresses of a PoP chosen for that query. The mapping system only sees the resolver's address, not yours. If your resolver forwards EDNS Client Subnet (RFC 7871), it also sees a truncated client prefix, typically a /24 for IPv4. Some large public resolvers deliberately do not send ECS, for privacy. Answers carry short TTLs, often 20–60 seconds, so the mapping can move load quickly. Failover is bounded by that TTL plus the resolvers and clients that hold answers longer than they should.

The trade-off is control versus speed of reaction.

Anycast DNS mapping
Who chooses the PoP Your ISP's BGP policy The CDN's mapping system
Granularity Per network path Per resolver, or per ECS subnet
Failover Route withdrawal; BGP reconverges in seconds to a minute or so TTL expiry, plus stale resolver caches
Load shedding from a hot PoP Coarse: prepend or withdraw, which moves whole catchments Fine: change the answer for some fraction of queries
Main blind spot Path policy is not latency Resolver location is not client location

Most large CDNs run both. A common shape is anycast for the DNS servers and the edge, with DNS mapping layered on for products that need fine-grained load control, such as large video or software downloads.

Inside the PoP there is a second routing layer that the module did not show. The border router spreads packets for the anycast address across several layer-4 load balancers using ECMP, which hashes the 5-tuple. Each load balancer then picks a proxy server, again by consistent hashing. Hashing keeps every packet of one TCP connection on the same machine. QUIC complicates this: a client's address and port can change mid-connection, so QUIC-aware load balancers route on the connection ID, which the server encoded with routing information when it issued it.

The proxy that terminates TLS is often not the machine that stores the object. Many CDNs hash the cache key to choose a storage node within the PoP. That turns forty servers into one large cache instead of forty small copies of the same popular objects. Hot objects get replicated anyway, so one node doesn't melt.

Cache keys and Vary: a two-level lookup

RFC 9111 (§4.1) describes the lookup in two stages, and real caches follow it closely.

  1. The primary key is the method plus the target URI. CDNs normalise it first: lowercase the host, maybe sort query parameters, maybe drop utm_* parameters, maybe ignore the query string entirely. Each of those choices is configuration, and each one changes which requests share an entry.
  2. Under that primary key sits a list of stored variants. Each stored response carries its own Vary header, which names request headers. The cache saved the values those headers had on the request that produced the response. A new request matches a variant only if its values for those headers match the saved ones. Caches may normalise values first, for example collapsing Accept-Encoding into "br", "gzip", or "identity". Vary: * never matches, which makes the response effectively uncacheable for reuse.

So the true key is primary key plus the secondary key built from Vary. Two consequences follow.

Variant count multiplies. Vary: Accept-Encoding, Accept-Language across 3 encodings and 20 languages gives up to 60 copies of each URL. Each copy has to be fetched, stored, and kept fresh on its own. Vary: User-Agent gives one copy per distinct browser build string, which means thousands. Vary: Cookie gives roughly one copy per user, which is a private cache wearing a shared cache's clothes.

The key must match the response. This is the rule behind almost every cache security bug. Every input that changes the response must be in the key, and every part of the key should change the response. Break the first half and you get poisoning or data leaks. Break the second half and your hit ratio collapses.

Freshness is a per-variant clock

Each stored variant carries a few timestamps and the directives that came with it. From those, the cache computes the response's current age (RFC 9111 §4.2.3):

apparent_age          = max(0, response_time - date_value)
corrected_age_value   = age_value + (response_time - request_time)
corrected_initial_age = max(apparent_age, corrected_age_value)
current_age           = corrected_initial_age + (now - response_time)

age_value is the Age header the response arrived with. That detail matters in a tiered CDN. When an edge fetches from a shield that has held the object for 40 seconds, the response arrives with Age: 40. With max-age=60, the edge's copy is fresh for only 20 more seconds. Edge copies therefore expire in lockstep with the shield's copy, not on their own schedule.

When max-age (or s-maxage for shared caches) is absent, a cache may use a heuristic. RFC 9111 suggests a typical value of 10% of the time since Last-Modified. A file last modified 30 days ago gets about 3 days of heuristic freshness. That is how "we never set caching headers" turns into "users saw a stale file for three days".

With stale-while-revalidate and stale-if-error (RFC 5861), every variant moves through a small state machine:

Current age (for max-age=60, stale-while-revalidate=30, stale-if-error=600) Origin healthy Origin failing
0–59 s Hit, fresh Hit, fresh
60–89 s Serve stale now, revalidate in the background Serve stale
90–659 s Block on revalidation Serve stale (stale-if-error)
660 s and older Block on revalidation Error to the client

must-revalidate switches off the stale paths. Once stale, the cache must revalidate or return 504. Use it on content where stale is worse than an error, and nowhere else.

Misses: coalescing and the shield

A miss is not one fetch. Each cache node keeps a pending-fetch table keyed by cache key. The first request for a cold key creates an entry and starts one upstream fetch. Every later request for that key joins the entry as a waiter. When the response arrives, the cache stores it once and answers all the waiters. Vendors call this request collapsing or coalescing.

There is a catch. Coalescing only works if the response turns out to be cacheable. If it comes back private or no-store, the waiters cannot share it. Each one has to be sent upstream again, one after another, unless the cache remembers "this key is uncacheable" for a while. Varnish calls that memory a hit-for-pass object. Without it, a single uncacheable hot URL turns coalescing into a serial queue.

The shield (also called a tier-2 cache or origin shield) is the same machinery one level up. An edge that misses asks the shield chosen for that key, usually by hashing it, rather than asking the origin. The shield coalesces misses from every edge. A cold object requested by 300 PoPs at once becomes one origin fetch, not 300.

Some CDNs choose one shield region per origin. Others hash keys across several upper-tier PoPs. Either way, the origin's load becomes a function of the global request rate per object, not the per-PoP rate. The numbers section shows why that matters so much.

Purge semantics: invalidation is a message

A purge request reaches the CDN's API. The control plane fans it out to every PoP and tier, and each node applies it to its local index. Three things follow from that.

There are two kinds of purge. A hard purge deletes the entry, so the next request is a full miss. A soft purge marks it stale, so the next request revalidates. If the origin answers 304, the body never moves. Under stale-while-revalidate or stale-if-error, the stale copy can still be served while that happens. Soft purge is the safer default because it cannot cause a stampede of full-body fetches.

There are several ways to name what to purge. Purge-by-URL maps directly to a primary key, and normally removes all of that key's variants. Purge-by-tag needs an index: the origin labels responses with tags (vendor headers such as Surrogate-Key or Cache-Tag), and each node keeps a map from tag to keys. Purge-everything and prefix purges are rarely implemented by walking the cache. A cheaper trick is to bump a generation number that is part of every key, or to add a rule that lookups check lazily (Varnish calls these bans). The old objects become unreachable and age out on their own.

Tiers can race. Suppose an edge processes the purge before the shield does. The next request misses at the edge, goes to the shield, and gets the old object back, often with plenty of TTL left. The edge has been purged and refilled with stale content within the same second. CDNs order or retry purges to avoid this, but you should verify it with Age and Cache-Status after any critical purge.

And one limit no CDN can lift: you cannot purge a browser. A max-age=86400 that reached a user's browser stays there for a day, whatever you do at the edge. That is why HTML usually gets a short max-age for browsers and a longer s-maxage, or CDN-Cache-Control, for the edge you can purge.

The machine in Python

The script below is a toy shared cache. It is small enough to read in one sitting and follows the same rules: normalised primary keys, Vary matching against saved request headers, the freshness state machine from the table above, and one poisoning bug. Run it: ~/.local/bin/python3.13 d13_cache_key.py

"""A toy shared cache: primary key, Vary secondary key, freshness states, and a poisoning bug."""
from urllib.parse import urlsplit, parse_qsl, urlencode

def primary_key(method: str, url: str, keep_params=None) -> str:
    u = urlsplit(url)
    params = sorted(parse_qsl(u.query))                     # normalise order
    if keep_params is not None:
        params = [(k, v) for k, v in params if k in keep_params]
    return f"{method} {u.scheme}://{u.hostname.lower()}{u.path}?{urlencode(params)}"

def norm_ae(value: str) -> str:                            # Accept-Encoding -> 3 buckets
    v = value.lower()
    return "br" if "br" in v else "gzip" if "gzip" in v else "identity"

class Cache:
    def __init__(self, normalise=True):
        self.store, self.normalise = {}, normalise          # pkey -> list of variants
    def _secondary(self, vary, req):
        out = []
        for h in vary:
            v = req.get(h, "")
            out.append(norm_ae(v) if self.normalise and h == "accept-encoding" else v)
        return tuple(out)
    def lookup(self, pkey, req):
        for vary, sec, resp in self.store.get(pkey, []):
            if self._secondary(vary, req) == sec:
                return resp
        return None
    def put(self, pkey, req, resp):
        vary = [h.strip().lower() for h in resp.get("vary", "").split(",") if h.strip()]
        self.store.setdefault(pkey, []).append((vary, self._secondary(vary, req), resp))
    def variants(self):
        return sum(len(v) for v in self.store.values())

def freshness(age, max_age, swr, sie, origin_up):
    if age < max_age:
        return "HIT fresh"
    if age < max_age + swr:
        return "HIT stale, serve now + background revalidate"
    if not origin_up and age < max_age + sie:
        return "HIT stale-if-error (origin down)"
    return "MISS must fetch/revalidate" if origin_up else "ERROR 5xx to client"

print("1) Query normalisation")
a = primary_key("GET", "https://Shop.example/p?id=7&utm_source=mail")
b = primary_key("GET", "https://shop.example/p?utm_source=ad&id=7")
c = primary_key("GET", "https://shop.example/p?utm_source=ad&id=7", keep_params={"id"})
for k in (a, b, c):
    print("  ", k)

print("\n2) Vary: Accept-Encoding vs Vary: User-Agent over 1,000 requests")
agents = [f"Mozilla/5.0 (build {i % 400})" for i in range(1000)]     # 400 distinct UAs
encodings = ["br, gzip", "gzip, deflate, br, zstd", "gzip", "identity"]
for vary, normalise in (("Accept-Encoding", False), ("Accept-Encoding", True),
                        ("User-Agent", False)):
    cache, misses = Cache(normalise), 0
    for i, ua in enumerate(agents):
        req = {"user-agent": ua, "accept-encoding": encodings[i % 4]}
        pk = primary_key("GET", "https://shop.example/app.js")
        if cache.lookup(pk, req) is None:
            misses += 1
            cache.put(pk, req, {"vary": vary, "body": "..."})
    print(f"   Vary: {vary:<15} normalise={normalise!s:<5}"
          f" variants={cache.variants():>4}  hit ratio={1 - misses / 1000:.1%}")

print("\n3) Freshness for max-age=60, stale-while-revalidate=30, stale-if-error=600")
for age, up in ((10, True), (75, True), (200, True), (200, False), (900, False)):
    print(f"   age={age:>3}s origin_up={up!s:<5} -> {freshness(age, 60, 30, 600, up)}")

print("\n4) Poisoning: origin reflects an unkeyed header into a cacheable body")
def origin(req):
    host = req.get("x-forwarded-host", "shop.example")
    return {"body": f'<script src="https://{host}/app.js">', "cache-control": "max-age=300"}
cache = Cache()
pk = primary_key("GET", "https://shop.example/")
attacker = {"x-forwarded-host": "evil.example"}
cache.put(pk, attacker, origin(attacker))                  # attacker's request fills the slot
victim = {}
print("   victim receives:", cache.lookup(pk, victim)["body"])

The User-Agent row is the real lesson. Only 400 distinct agents, and the hit ratio already falls to 60%. Real traffic carries thousands of distinct strings. Deep dive: by the numbers

Hit ratio from first principles

Take one object with requests arriving at rate λ per second at one cache, and a TTL of T seconds. Each miss starts a freshness window. During that window, about λT more requests arrive and hit. So every window holds one miss and λT hits:

hit ratio = λT / (1 + λT)        origin fetch rate = λ / (1 + λT)

This assumes Poisson arrivals, no eviction, and a full refetch on expiry. It is crude, but it explains why CDNs behave the way they do. The script checks the formula against a simulation, then applies it to a Zipf-distributed catalogue spread across 50 PoPs. Run it: ~/.local/bin/python3.13 d13_hit_math.py

"""Hit-ratio math for a TTL cache, per PoP and behind a shield (Python 3.13 stdlib)."""
import random

def ttl_hit_ratio(rate: float, ttl: float) -> float:
    # Poisson arrivals at `rate`/s; a miss fetches and starts a TTL window.
    # Each window holds 1 miss + on average rate*ttl hits.
    return rate * ttl / (1 + rate * ttl)

def simulate(rate: float, ttl: float, requests: int, seed: int = 7) -> float:
    rng, t, expires, hits, total = random.Random(seed), 0.0, -1.0, 0, 0
    while total < requests:
        t += rng.expovariate(rate)
        total += 1
        if t < expires:
            hits += 1
        else:
            expires = t + ttl          # miss: fetch, store, start freshness
    return hits / total

print("1) One object, one PoP, TTL = 60 s")
for rate in (0.01, 0.1, 1.0, 10.0):
    print(f"   {rate:>5} req/s  formula {ttl_hit_ratio(rate, 60):6.1%}"
          f"   simulated {simulate(rate, 60, 200_000):6.1%}")

# 2) A Zipf catalogue spread over many PoPs, with and without a shield.
OBJECTS, POPS, TOTAL_RPS, TTL, S = 200_000, 50, 20_000, 300, 0.9
weights = [1 / (k ** S) for k in range(1, OBJECTS + 1)]
norm = sum(weights)
obj_rps = [TOTAL_RPS * w / norm for w in weights]      # global rate per object

edge_miss = sum(POPS * (r / POPS) / (1 + (r / POPS) * TTL) for r in obj_rps)
shield_miss = sum(r / (1 + r * TTL) for r in obj_rps)  # misses collapse at shield

print(f"\n2) {OBJECTS:,} objects, Zipf s={S}, {TOTAL_RPS:,} req/s over {POPS} PoPs, TTL={TTL}s")
print(f"   edge hit ratio            : {1 - edge_miss / TOTAL_RPS:6.1%}")
print(f"   origin req/s, no shield   : {edge_miss:8.0f}")
print(f"   origin req/s, one shield  : {shield_miss:8.0f}"
      f"   (shield hit ratio on edge misses {1 - shield_miss / edge_miss:.1%})")
print(f"   origin offload with shield: {1 - shield_miss / TOTAL_RPS:6.2%}")

print("\n3) Origin load vs hit ratio at 100,000 req/s")
for h in (0.90, 0.95, 0.99, 0.999):
    print(f"   hit {h:6.1%} -> origin {100_000 * (1 - h):>7,.0f} req/s")

Three lessons are in that output.

The long tail decides your hit ratio. An object requested once every 100 seconds at a PoP gets a 37.5% hit ratio, even with a 60-second TTL. Popular objects are easy. The tail is where the misses live, and spreading traffic across more PoPs pushes more objects into the tail, because each PoP sees only its own share.

A shield turns per-PoP rates back into global rates. In the Zipf run, the edges alone hit 67.3%, leaving 6,535 req/s for the origin. With one shield in front of the origin, that falls to 594 req/s. The model ignores Age inheritance, which makes the real edge numbers slightly worse. The shape holds anyway. That is the case for tiered caching in one number.

Each extra nine is worth more than the last. Going from 95% to 99% cuts origin traffic by a factor of five. Going from 99% to 99.9% cuts it by another factor of ten. That is why teams fight over the last percent.

Tail latency follows the miss rate

Expected time to first byte is a weighted average: E[TTFB] = h × t_hit + (1 − h) × t_miss. With a 20 ms hit, a 220 ms miss, and h = 0.95, the mean is 30 ms. That sounds fine.

Percentiles tell a different story. With 5% misses, the p99 request is a miss, because more than 1% of requests pay 220 ms. Your p99 is therefore your miss latency until the miss rate drops below 1%. When a dashboard shows a great mean and an ugly p99 behind a CDN, look at the miss path first.

Deep dive: production failure modes

Each failure below follows the same pattern: what you see, what is actually happening, how to prove it, and how to fix it. Test only against systems you own, and always use a cache-busting query parameter. That way a poisoning test can only ever poison a key nobody else requests.

1. Cache poisoning through an unkeyed header. Symptom: users intermittently load scripts or redirects pointing at a host you don't own. Mechanism: the origin builds absolute URLs from a header such as X-Forwarded-Host or X-Forwarded-Scheme. The CDN forwards that header but leaves it out of the key, so one attacker request fills the shared entry. Prove it:

# run on your Mac against your own site; cb= makes a throwaway key
curl -s -H 'X-Forwarded-Host: canary.example' 'https://www.shop.example/?cb=8812' | grep -c canary.example
curl -s 'https://www.shop.example/?cb=8812' | grep -c canary.example    # non-zero = poisoned

Fix: stop trusting forwarded headers at the origin unless your own proxy set them. Strip them at the edge. If a header genuinely changes the response, put it in the key.

2. Web cache deception. Symptom: one user's account page is served to others. Mechanism: the CDN caches "anything ending in .css" by rule. Meanwhile the origin's router serves /account/x.css as /account, because it ignores the trailing segment. An attacker lures a victim to that URL, the victim's private page gets cached under a public key, and the attacker fetches it. Prove it: request /account/nonexistent.css with a session cookie, then again without one, and compare Cache-Status and the body. Fix: cache on the origin's Cache-Control, not on file extensions. Make the origin return 404 for paths it doesn't recognise. Mark account pages private or no-store. Some CDNs also check that the Content-Type matches the extension before caching.

3. Cached error pages (cache-poisoned denial of service). Symptom: a page returns 400 or 404 for everyone, but works fine when you hit the origin directly. Mechanism: a request with an oversized header, a stray meta character, or a method-override header makes the origin fail. The CDN stores that error under the normal key. Researchers documented this class in 2019 as CPDoS. Remember too that 404 is heuristically cacheable. Prove it: curl -s -o /dev/null -w '%{http_code} %header{cache-status}\n' URL shows a hit on an error status. (%header{} needs curl 7.84 or newer; recent macOS ships curl 8.) Fix: cache error statuses for seconds at most, or not at all, and reject malformed requests at the edge rather than forwarding them.

4. Thundering herd after a purge. Symptom: origin CPU and connection count spike within seconds of a deploy, and latency follows. Mechanism: a hard purge-everything, combined with weak coalescing or no shield, sends every PoP's next miss straight to the origin. Synchronised TTLs cause the same thing on a schedule: everything published at 09:00 with max-age=3600 expires at 10:00. Prove it: origin request rate lines up exactly with the purge timestamp. Cache-Status shows fwd=uri-miss from many PoPs, and collapsed is absent. Fix: use soft purges, purge by tag rather than everything, put a shield in front of the origin, keep stale-while-revalidate on, and add jitter to TTLs.

5. Hit ratio collapse from key fragmentation. Symptom: the hit ratio drops after a release, and nothing about content popularity changed. Mechanism: the release added Vary: User-Agent or Vary: Cookie, or a new tracking parameter now appears in the URL. The working set multiplied. Prove it: count distinct keys per URL path in the CDN logs. fwd=vary-miss dominates when Vary is the cause. Fix: normalise in the key (an allowlist of query parameters, bucketed headers), use Vary only on low-cardinality headers, and move personalisation to the client or into a separate uncached request.

6. Wrong-region users. Symptom: users in one country see two or three times the latency of their neighbours. Mechanism: with DNS mapping, their resolver sits elsewhere and sends no ECS. With anycast, their ISP's policy routes them to a distant PoP. Prove it: compare dig answers with and without +subnet. Read the vendor's PoP identifier header. Run traceroute -n (or mtr -rw on Linux) to the edge address from an affected network. Fix: for DNS, the CDN can map on ECS where resolvers send it. For anycast, it is a peering and traffic-engineering problem on the CDN's side. Send them traceroutes and RTTs, not adjectives.

7. Stale content you cannot purge. Symptom: the purge succeeded, the edge shows a fresh Age, and users still report the old page. Mechanism: the browser holds its own copy under max-age. Prove it: DevTools shows "(disk cache)" or "(memory cache)" for the request. Fix: give HTML a short browser lifetime (max-age=0, must-revalidate, or a short max-age) and a long edge lifetime (s-maxage, or CDN-Cache-Control). Fingerprint the assets.

Deep dive: 2026 context

HTTP/3 at the edge. Most large CDNs terminate QUIC. Clients learn about it from Alt-Svc or from DNS HTTPS records (RFC 9460). Anycast and QUIC fit well together. Load balancers inside the PoP route on connection IDs, so a client whose NAT rebinding changes its port still reaches the same proxy. Moving a live connection between PoPs is still not something you can count on.

Standard debugging headers. Cache-Status (RFC 9211) and CDN-Cache-Control (RFC 9213) replace a decade of vendor headers. CDN-Cache-Control lets you give the CDN a different lifetime from browsers without abusing s-maxage. Adoption is uneven, so check what your vendor emits and obeys.

New key dimensions. Compression Dictionary Transport (the Use-As-Dictionary and Available-Dictionary headers) lets a browser decompress a new bundle against the old one, so deploys ship deltas. That adds a dictionary dimension to the key, and caches must vary on it. Separately, a proposed No-Vary-Search header lets the origin declare which query parameters don't affect the response, moving key normalisation out of CDN configuration and into the response.

Encrypted Client Hello. With ECH, the TLS SNI is encrypted. On-path networks can no longer see which CDN-fronted site you visit. The CDN still sees everything, because it terminates TLS.

Edge compute owns the key. Workers and edge functions let code rewrite requests before lookup. That is powerful, and it is also how key bugs ship. A function that reads a cookie to personalise must also put that cookie, or a bucket of it, into the key.

Origin protection is a zero-trust problem. Allowlisting the CDN's published IP ranges at the origin only proves "some customer of this CDN". Anyone else on the same CDN can reach your origin. Authenticate the CDN to the origin with mTLS (often sold as authenticated origin pulls), a signed header, or private connectivity into the VPC.

Kubernetes and cloud egress. In clusters, the CDN usually fronts an ingress or gateway. Two operational facts follow. The client address arrives in X-Forwarded-For, and you must trust only the hop you control. And cloud egress is billed per gigabyte, so a shield's offload ratio shows up directly on the invoice.

Deep dive: senior interview questions

Q1: The CDN dashboard says 95% hit ratio, but origin traffic barely dropped. How is that possible?

A: Several ways, and I'd check each one. The ratio may be per request while the origin pain is in bytes, because large objects miss more often. It may count shield hits as hits, which says nothing about the edges. Revalidations that end in 304 often count as hits at the edge, yet each one still reaches the origin. Requests that bypass the cache (no-store, POST, cookie rules) may be left out of the denominator. I'd measure origin offload directly: one minus origin requests over edge requests, in requests and in bytes.

Q2: When would you choose DNS mapping over anycast?

A: When I need fine-grained, load-aware steering. Large video or download delivery is the classic case: I want to send 10% of one region's users to a second PoP without moving everyone. Anycast moves whole catchments, and its only levers are BGP announcements. Anycast wins on failover speed and on not depending on resolver location. Many CDNs combine them.

Q3: What is in a cache key, exactly?

A: The primary key is the method and target URI after the CDN's normalisation rules. The secondary key comes from the stored response's Vary: the values of the named request headers, often normalised. A lookup matches the primary key, then walks that key's variants. Vary: * never matches. The design rule is that the key must contain every input that changes the response, and nothing that doesn't.

Q4: Explain cache poisoning versus web cache deception.

A: In poisoning, the attacker controls an input the key ignores, so their malicious response gets served to others. In deception, the attacker controls the URL so that a victim's private response lands under a cacheable key, and the attacker reads it. The first is the key missing an input. The second is caching policy not following the origin's Cache-Control. Both are fixed by making the key and the caching decision follow what the response actually depends on.

Q5: You purged a URL. Why might users still get the old version?

A: Browser caches can't be purged. Propagation isn't atomic, so some PoPs flip later than others. An edge that refills from a shield before the shield processes the purge gets the old object back. The purge may also have named a different key, for example a different query string or host normalisation. I'd check Age and Cache-Status from several PoPs, and look at the browser's cache.

Q6: An object with max-age=60 keeps getting re-fetched at the edge every 20 seconds. Why?

A: The edge inherits Age from the shield. If the shield's copy is already 40 seconds old when the edge fetches it, the edge has only 20 seconds of freshness left. Edge and shield expire together, and every edge revalidates at the same moment.

Q7: How do you raise the hit ratio on long-tail content without raising TTLs?

A: Raise the request rate each cache sees per key. A shield or tiered cache aggregates misses across PoPs. Consistent hashing inside a PoP makes forty servers behave like one cache. Cutting variants (normalised query strings, bucketed headers) concentrates traffic onto fewer keys. With λT/(1+λT), raising λ works just as well as raising T, and it doesn't make content staler.

Q8: Why is stale-while-revalidate safer than a long max-age?

A: It bounds staleness differently. With max-age=60, stale-while-revalidate=30, no user ever sees content more than 90 seconds old, and almost no user waits on the origin, because the refresh happens in the background after the first stale hit. A long max-age gives the same latency with much worse staleness. Pair it with stale-if-error and an origin outage turns into slightly old pages rather than errors.

Standards cited in this deep dive: RFC 9111 (HTTP Caching), RFC 9110 (HTTP Semantics), RFC 5861 (stale-while-revalidate, stale-if-error), RFC 9211 (Cache-Status), RFC 9213 (CDN-Cache-Control), RFC 7871 (EDNS Client Subnet), RFC 9460 (SVCB and HTTPS records), RFC 4786 (Operation of Anycast Services). Surrogate-Key and Cache-Tag are vendor headers, and Compression Dictionary Transport and No-Vary-Search are newer IETF work. Check your vendor's support before relying on them.
