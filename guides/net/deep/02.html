Deep dive: one HTTPS request, byte by byte

The postal analogy is right about the nesting. It hides three things you meet the moment you open a real capture.

First, a "request" is not one envelope. Fetching a 1,257-byte page over HTTPS took 17 frames and 4,630 bytes in the lab below, and a quarter of those bytes were headers. Second, the 1500-byte budget from section 4 is not a single rule. It is enforced by three separate mechanisms, MSS, fragmentation and path MTU discovery, and each one fails in its own recognisable way. Third, the packets in your capture are often not the packets on the wire. Modern hosts build 16 KB or 64 KB "packets" in software and let the NIC cut them up, so tcpdump happily shows you a 16,458-byte IP packet on a 1500-byte link.

This deep dive walks one real HTTPS request frame by frame with exact byte counts, then breaks the MTU on purpose, then explains the giant packets.

Deep dive: the real mental model — big units inside, small units on the wire

Hold three size limits apart, because people blur them all the time.

  • MTU is a property of one link: the largest IP packet a frame on that link can carry. Standard Ethernet is 1500.
  • Path MTU is the smallest MTU of every link between two hosts. No single device knows it. It has to be discovered or assumed.
  • MSS is a TCP number each side announces in its SYN: "don't send me segments with more than this much payload." It is derived from the announcing host's own interface MTU, so it says nothing about the links in between.

The sender's real segment size is the smallest of three things: the peer's MSS, the path MTU minus IP and TCP headers, and the TCP options it carries on every segment. With timestamps on, which is the default on Linux and macOS, every segment carries 12 bytes of options. So a full segment on a 1500-byte path holds 1448 bytes of data, not the 1460 from section 4.

Now the part that explains your captures. The software stack does not work in 1500-byte units. TLS writes records of up to 16,384 bytes of plaintext. TCP builds buffers (skbs) of up to 64 KB. Segmentation into wire-sized pieces is pushed as late as possible: ideally into the NIC itself (TCP Segmentation Offload, TSO). Reassembly on the receiving side is pulled as early as possible: the driver merges consecutive segments before the stack sees them (Generic Receive Offload, GRO). Both exist for one reason: per-packet work is what costs CPU, so the stack handles one big unit instead of a dozen small ones.

Packet capture taps the stack between those two points.

On the sender, the tap sits after the qdisc but before the NIC. With hardware TSO, it sees the big buffer. On the receiver, the tap sits after GRO, so it sees the merged buffer. The frames that actually crossed the cable never appear in either capture. Keep that picture in mind; the offload section below shows it in real captures.

The byte budget

This stdlib script reads the pcap, splits every frame into Ethernet, IP and TCP headers and payload, and tracks TLS record boundaries across segments. TLS record headers (type, version, length) travel in clear even in TLS 1.3, so it can find them without any keys.

code/d02/wire_budget.py:

"""Walk a pcap with the stdlib only: per-frame byte budget and TLS record boundaries.

    python3.13 wire_budget.py capture.pcap
Expects a classic pcap of one TCP connection to port 443 over Ethernet (tcpdump -w).
"""
import struct
import sys

TLS_TYPES = {20: "ChangeCipherSpec", 21: "Alert", 22: "Handshake", 23: "AppData"}
HS_TYPES = {1: "ClientHello", 2: "ServerHello"}


def frames(path):
    with open(path, "rb") as f:
        magic = f.read(24)[:4]
        endian = "<" if magic in (b"\xd4\xc3\xb2\xa1", b"\x4d\x3c\xb2\xa1") else ">"
        while hdr := f.read(16):
            _, _, caplen, wirelen = struct.unpack(endian + "IIII", hdr)
            yield f.read(caplen), wirelen


def main(path):
    isn, pending = {}, {}   # per direction: initial sequence number, unparsed TLS bytes
    n_frames = wire = payload = 0
    print(f"{'#':>2} {'dir':<3} {'frame':>5} = eth + ip + tcp + data   flags  rel seq  TLS records completed")
    for n, (buf, wirelen) in enumerate(frames(path), 1):
        ihl = (buf[14] & 0x0F) * 4
        tcp = buf[14 + ihl:]
        sport, dport, seq = struct.unpack("!HHI", tcp[:8])
        thl = (tcp[12] >> 4) * 4
        flags = tcp[13]
        data = tcp[thl:]
        key = (sport, dport)
        if flags & 0x02:                 # SYN: remember the initial sequence number
            isn[key] = seq
        rel = (seq - isn.get(key, seq)) % 2**32
        stream = pending.get(key, b"") + data
        recs = []
        while len(stream) >= 5 and len(stream) >= 5 + struct.unpack("!H", stream[3:5])[0]:
            ctype, rlen = stream[0], struct.unpack("!H", stream[3:5])[0]
            name = TLS_TYPES.get(ctype, hex(ctype))
            if ctype == 22:
                name = HS_TYPES.get(stream[5], name)
            recs.append(f"{name}({5 + rlen})")
            stream = stream[5 + rlen:]
        pending[key] = stream
        n_frames, wire, payload = n_frames + 1, wire + wirelen, payload + len(data)
        d = "C>S" if dport == 443 else "S>C"
        flag_s = "".join(c for c, bit in zip("SFRPA", (2, 1, 4, 8, 16)) if flags & bit)
        print(f"{n:>2} {d:<3} {wirelen:>5} = {14:>3} + {ihl:>2} + {thl:>3} + {len(data):>4}   "
              f"{flag_s:<5} {rel:>7}  {' '.join(recs) or '-'}")
    over = wire - payload
    print(f"\n{n_frames} frames, {wire} bytes captured, {payload} bytes of TCP payload, "
          f"{over} bytes of headers ({over / wire:.0%})")
    # Each frame also costs 4 B FCS + 8 B preamble/SFD + 12 B inter-frame gap on the cable.
    print(f"Line cost adds {24 * n_frames} bytes (FCS + preamble + gap): "
          f"{wire + 24 * n_frames} byte-times on the cable")


if __name__ == "__main__":
    main(sys.argv[1])

Reading it frame by frame

Frames 1–3: the TCP handshake, 214 bytes. The SYN is 74 bytes: 14 Ethernet + 20 IPv4 + 20 TCP + 20 bytes of options. Those options are MSS (4 bytes), SACK-permitted (2), timestamps (10), one NOP for alignment (1) and window scale (3). Both sides announce mss 1460, because both have 1500-byte interfaces. Both announce wscale 10, so the "win 63" you see later means 63 × 1024 = 64,512 bytes. The third packet, the ACK, is 66 bytes: it carries only the 12-byte timestamp option (two NOPs plus 10 bytes). Every later packet in this connection carries those 12 bytes too. macOS orders and pads its SYN options differently, so a Mac's SYN is usually a few bytes longer.

Frame 4: ClientHello, 517 bytes in one segment. That fits easily today. With a post-quantum key share it would not, as the 2026 section explains.

Frame 6: the server's whole first flight, 783 bytes in one segment. The records are ServerHello (127), a 6-byte ChangeCipherSpec, and four encrypted records of 50, 426, 100 and 74 bytes. TLS 1.3 labels every encrypted record "application data" on the outside and hides the real type inside. RFC 8446 fixes the order, though, so they are EncryptedExtensions, Certificate, CertificateVerify and Finished. The ChangeCipherSpec does nothing in TLS 1.3. It is sent only so that middleboxes that expect TLS 1.2 don't drop the connection ("middlebox compatibility mode"). The certificate is small here because the lab uses one self-signed P-256 certificate. A real site sends a chain of two or three certificates, typically 2.5–5 KB, which spans several segments, and that matters for the MTU failures below.

Frame 8: client Finished, 80 bytes. A 6-byte ChangeCipherSpec plus a 74-byte record. The 74 adds up exactly: 4-byte handshake header + 48-byte verify_data (the suite is TLS_AES_256_GCM_SHA384, so SHA-384) + 1 byte of inner content type + 16-byte AEAD tag + 5-byte record header.

Frames 9 and 11: two NewSessionTicket records, 255 bytes each. OpenSSL servers send two tickets by default. The client can use them to resume later without a full handshake.

Frame 10: the HTTP request, 107 bytes. The plaintext is 85 bytes: GET /index.html HTTP/1.1, Host, User-Agent and Accept headers, and the CRLFs. Every TLS 1.3 record over AES-GCM costs exactly 22 bytes: 5 header + 1 inner type + 16 tag. So 85 + 22 = 107.

Frames 12 and 14: the response. The headers are one record of 204 bytes (182 plaintext). The body is one record of 1,279 bytes (1,257 + 22). Frame 12 is a full segment: 1,448 bytes of payload, 1,514 bytes on the frame. It holds the header record and the first 1,244 bytes of the body record. Frame 14 carries the remaining 35. A record split across segments is normal. TCP is a byte stream and knows nothing about TLS records.

Frames 15–17: the close. The server sends FIN. The client answers with a 24-byte TLS close_notify alert (2 bytes of alert + 22 of overhead). By then the server has fully closed its socket, so the kernel answers the alert with a RST. That RST is harmless here, and very common with simple servers. In general, though, a RST throws away any data still unread at the receiving side. That is why careful servers do a "lingering close" instead of slamming the socket shut.

Two things that look wrong and aren't. Every packet the client sent shows cksum ... (incorrect -> ...). The kernel left the TCP checksum for the NIC to fill in (checksum offload), and the capture tap sits before the NIC. In this lab the "received" packets show it too, because veth passes the unfinished checksum along. On a physical NIC, received packets show correct checksums. And every packet from the server arrives with TTL 63: it left the server at 64 and crossed one router. The server's own capture of the same SYN shows TTL 63 there too, and different MAC addresses (02:00:00:00:02:01 → 02:00:00:00:02:02), while the ports, sequence numbers and options match byte for byte. That is section 3's hop-by-hop rule, seen in real bytes.

The bottom line. 1,257 bytes of page cost 4,630 bytes of capture: 27% useful. Headers alone are 1,126 bytes (24%). Handshakes, tickets and TLS framing account for most of the rest. On the cable, the 17 frames also pay 24 bytes each for FCS, preamble and inter-frame gap, for 5,038 byte-times in total. This is why connection reuse (HTTP keep-alive, HTTP/2 multiplexing) and TLS resumption matter far more for small requests than any header shaving.

All three fragments share IP ID 17314. That ID is the only thing that ties them together. The first two have the More Fragments flag ([+]) and carry 1,480 bytes of payload each. The last carries 1,048. 1,480 + 1,480 + 1,048 = 4,008 = UDP header plus data. tcpdump prints offsets in bytes. The header field itself counts in 8-byte units, so it holds 0, 185 and 370, and that is why every fragment except the last must carry a multiple of 8 bytes. Only the first fragment has the UDP header, so only it shows ports. The ICMP "port unreachable" at the end quotes a 4,028-byte datagram: the server reassembled all three fragments before looking for a socket on port 9999.

Fragmentation is a misery for four concrete reasons:

  • Loss multiplies. Lose any fragment and the whole datagram is lost. With 1% fragment loss, a three-fragment datagram is lost about 3% of the time.
  • The receiver holds state. Partial datagrams wait in a reassembly queue, up to 30 s by default on Linux (net.ipv4.ipfrag_time) and within a memory cap (ipfrag_high_thresh). That queue is a classic denial-of-service target.
  • Middleboxes are blind. Non-first fragments carry no ports, so firewalls, load balancers and NAT either reassemble (expensive) or drop them.
  • The ID field is only 16 bits. At 1 Gbit/s of 1500-byte packets, 65,536 IDs are used up in about 0.79 s. The reassembly timeout is 30 s, so a fragment from an old datagram can be stitched into a new one with the same ID. RFC 4963 describes this misassembly problem.

IPv6 took the obvious lesson. Routers never fragment IPv6. Only the sending host may, using a Fragment extension header. Every IPv6 link must carry at least 1280 bytes (RFC 8200), which gives everyone a safe floor.

TCP avoids all of this. It sets Don't Fragment (flags [DF] on every packet in the capture above) and sizes its segments to fit. Which raises the question: fit what? The sender only knows its own MTU.

The router can't forward a 1,500-byte packet with DF set onto a 1,400-byte link. So it drops the packet and sends back ICMP type 3, code 4, "fragmentation needed," with the next-hop MTU (1400) in the message (RFC 1191). It quotes the dropped packet's headers, so the server knows which connection to fix. The server's kernel records the MTU against the destination and retransmits at once with 1,348-byte segments: 1400 − 20 IP − 20 TCP − 12 options. The learned value is visible in the route cache, and it expires after 10 minutes (net.ipv4.route.mtu_expires = 600 s):

$ ip route get 192.168.1.50          # on the server
192.168.1.50 via 203.0.113.1 dev d02s0 src 203.0.113.10 uid 0
    cache expires 596sec mtu 1400

The whole correction took 0.35 ms in the lab, roughly one round trip. On a real path it costs one RTT plus the retransmission.

Path MTU discovery broken: the black hole

Now the server drops incoming ICMP "fragmentation needed", the way an over-eager firewall does:

ip netns exec d02s iptables -A INPUT -p icmp --icmp-type fragmentation-needed -j DROP
curl: (28) Operation timed out after 20002 milliseconds with 0 bytes received
curl: http=000 connect=0.000340s tls=0.003820s total=20.002612s

Look at those timings. The TCP connect took 0.34 ms and the TLS handshake finished in 3.8 ms, because every handshake packet in this lab is smaller than 1400 bytes. Then the first full-size response segment vanished, and so did every retransmission of it, because each one was 1,500 bytes again. The server never learned why. That is the signature of a PMTUD black hole: small things work, big things hang forever, and nothing logs an error. With a real certificate chain, the server's handshake flight is already bigger than one segment. So the symptom you usually see is "the TLS handshake hangs after ClientHello."

There are three ways out, and the lab tried each one.

Packetization-layer probing (RFC 4821). With net.ipv4.tcp_mtu_probing=1, Linux notices repeated timeouts on full-size segments and falls back to tcp_base_mss (1024 by default):

curl: http=200 connect=0.000264s tls=0.003634s total=3.159643s
...
21:35:29.804673 IP 203.0.113.10.443 > 192.168.1.50.34496: Flags [.], seq 1019:2043, ack 705, win 64, options [nop,nop,TS val 2286491710 ecr 2303093507], length 1024
21:35:29.804730 IP 203.0.113.10.443 > 192.168.1.50.34496: Flags [.], seq 2043:2467, ack 705, win 64, options [nop,nop,TS val 2286491710 ecr 2303093507], length 424

It works, but only after about 3.15 s of retransmission timeouts (TcpExtTCPTimeouts went up by 4). That is a terrible user experience. It is also off by default.

MSS clamping on the router. The router rewrites the MSS option in SYN packets it forwards, so neither end ever offers a segment size the path can't carry:

ip netns exec d02r iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --clamp-mss-to-pmtu
01:12:22.258544 IP 203.0.113.10.443 > 192.168.1.50.46620: Flags [S.], seq 539327135, ack 3307917238, win 65160, options [mss 1360,sackOK,TS val 718839559 ecr 226474446,nop,wscale 10], length 0
curl: http=200 connect=0.000917s tls=0.009552s total=0.018884s

The server sent mss 1460. The client received mss 1360, because the router rewrote it in flight (and fixed the TCP checksum). The server's data segments were 1,348 bytes, which proves the client's SYN was clamped the same way on its way out. Linux's --clamp-mss-to-pmtu uses the smaller of the two route MTUs it sees. Zero retransmissions, 19 ms total. Every VPN concentrator, PPPoE router and many cloud gateways do exactly this. It is a layering violation, a router editing a TCP option, and it only helps TCP. UDP and QUIC get nothing from it.

Not breaking ICMP in the first place. This is the actual fix. ICMP type 3 code 4 (and ICMPv6 type 2, "Packet Too Big") are control traffic that PMTUD depends on. RFC 4890 says plainly that ICMPv6 Packet Too Big must not be filtered. Blocking "all ICMP" for security is how black holes are made.

Deep dive: segmentation offload and the giant packets in your capture

These four captures come from the same 1 MiB download over the same 1500-MTU path. Only the offload settings changed.

Sender, TSO on (the default). Captured on the server's own interface:

21:33:34.335221 IP (tos 0x0, ttl 64, id 3002, offset 0, flags [DF], proto TCP (6), length 16458)
    203.0.113.10.443 > 192.168.1.50.53392: Flags [P.], seq 497569118:497585524, ack 1882282286, win 64, options [nop,nop,TS val 950299288 ecr 2162843027], length 16406

A 16,458-byte IP packet on a 1500-byte link. Its TCP payload is 16,406 bytes, which is exactly one full TLS record: 16,384 bytes of plaintext + 22. TCP handed the whole record down as one buffer, the tap recorded it, and the NIC (here, veth) was trusted to cut it into 11 × 1,448 + 1 × 478 bytes. Across the whole download the capture showed 77 such packets instead of 773 wire-sized ones. The device advertises how big these may get:

$ ip -d link show d02s0 | grep -o 'gso_max_size [0-9]* gso_max_segs [0-9]*'
gso_max_size 65536 gso_max_segs 65535

Sender, TSO and GSO off. ethtool -K d02s0 tso off gso off, same download:

21:33:38.386282 IP (tos 0x0, ttl 64, id 39074, offset 0, flags [DF], proto TCP (6), length 1500)
    203.0.113.10.443 > 192.168.1.50.53406: Flags [.], seq 3323386110:3323387558, ack 1628058525, win 64, options [nop,nop,TS val 4203593786 ecr 2462780421], length 1448

Now TCP itself builds MSS-sized segments. The capture matches the wire: 704 segments of 1,448 bytes, 63 of 478 and a few odd sizes.

Sender, TSO off but GSO on. The capture still shows 1,448-byte segments. Generic Segmentation Offload is TSO done in software, just before the driver. That point is upstream of the capture tap, so the tap already sees the cut-up segments. GSO saves most of the per-packet cost (one trip through the stack per 64 KB) without hiding anything from tcpdump. So "giant" packets in an outgoing capture mean hardware TSO, specifically.

Receiver, GRO on. With TSO still off on the server, so that 1,448-byte segments genuinely arrive, GRO is turned on at the receiving interface:

21:33:42.459005 IP (tos 0x0, ttl 64, id 43617, offset 0, flags [DF], proto TCP (6), length 16458)
    203.0.113.10.443 > 192.168.1.50.32962: Flags [P.], seq 1044885956:1044902362, ack 1586781324, win 64, options [nop,nop,TS val 2585550317 ecr 3863586525], length 16406

Twelve real 1,448/478-byte segments went in. GRO merged them into one 16,406-byte buffer before the tap. It stopped at the PSH flag at the end of the TLS record, which is one of GRO's flush conditions. The receiving TCP then processes one buffer and makes one ACK decision instead of twelve.

What this means for everyday work:

  • A capture is a view of the host, not the wire. To see true wire packets, capture on a switch SPAN port or a network tap. Or, on a test box only, turn the offloads off (ethtool -K eth0 tso off gso off gro off), at a real CPU cost.
  • "Bad checksum" on outgoing packets is checksum offload. Use tcpdump -K (--dont-verify-checksums), or turn off checksum validation in Wireshark.
  • Wireshark's "packet size limited during capture" and odd-looking giant segments are not network errors. Before you file a ticket about "jumbo frames on our 1500 network," check ethtool -k.
  • macOS does TSO too (sysctl net.inet.tcp.tso), so an outgoing capture on a Mac can show oversized segments as well.

Deep dive: by the numbers

MTU and MSS budgets you should know cold. The MSS figures assume IPv4 with a 20-byte TCP header. Subtract 12 more when timestamps are on, which is almost always.

Link or encapsulation MTU seen by the inner IP packet IPv4 TCP MSS Overhead and notes
Ethernet 1500 1460 (1448 with timestamps) baseline
IPv6 over Ethernet 1500 1440 (1428 with timestamps) 40-byte IPv6 header
PPPoE (DSL, some fibre) 1492 1452 8-byte PPPoE header
VXLAN on a 1500 underlay 1450 1410 50 bytes: outer Ethernet 14 + IPv4 20 + UDP 8 + VXLAN 8
WireGuard default 1420 1380 sized for the worst case: IPv6 outer 40 + UDP 8 + WireGuard 32
IPsec ESP tunnel about 1400–1440 varies depends on cipher, padding and NAT traversal
Jumbo frames 9000 8960 data centre only; AWS uses 9001 inside a VPC
IPv6 minimum 1280 — every IPv6 link must carry it (RFC 8200)
QUIC ≥ 1200 UDP payload — QUIC requires paths to carry 1200-byte datagrams (RFC 9000)

Line-rate goodput. A full-size frame costs 1,538 byte-times on the cable: 1,514 + 4 FCS + 8 preamble + 12 inter-frame gap. With 1,448 bytes of TCP data per frame, the best possible goodput is 1448 / 1538 = 94.1%. On gigabit Ethernet that is 941 Mbit/s, which is exactly the number iperf3 reports on a healthy 1 GbE link. If you see 941, the link is perfect. Don't chase the missing 59.

Small packets cost the same fixed overhead. A minimum Ethernet frame is 64 bytes, or 84 byte-times with preamble and gap. That gives the famous 14.88 million packets per second at 10 Gbit/s. A bare ACK in the capture above is 66 bytes on the frame; padding, FCS, preamble and gap still bring it to 84 byte-times on the cable.

TLS framing is cheap only in big records. 22 bytes of overhead on a 16,406-byte record is 0.13%. The same 22 bytes on the 107-byte request record is 21%.

Offload saves trips through the stack, not bytes. In the lab download, TSO turned 773 trips through the stack into 77. At 100 Gbit/s with 1,500-byte frames you have about 123 ns per packet. That budget is the reason Linux added BIG TCP, which lets these super-packets exceed 64 KB (up to 512 KB) on fast NICs, for IPv6 from kernel 5.19 and IPv4 from 6.3.

Fragment ID wraparound. IPv4's ID field is 16 bits. At 1 Gbit/s of full-size packets, 65,536 IDs last about 0.79 s. Reassembly waits up to 30 s. That mismatch is why high-rate fragmented UDP can silently corrupt data unless the application checks integrity itself.

Deep dive: production failure modes

1. Small requests work; large responses hang (PMTUD black hole)

Symptom. curl connects, maybe completes TLS, then hangs. SSH logs in but freezes when you cat a big file. Often it is only for users on a VPN, PPPoE or a tunnel.

Mechanism. Something on the path has a smaller MTU, and the ICMP "fragmentation needed" (or ICMPv6 "packet too big") never reaches the sender. That is the black hole demonstrated above.

Prove it. Find the largest DF packet that gets through.

# macOS: -D sets Don't Fragment; 1472 + 8 ICMP + 20 IP = 1500
ping -D -s 1472 example.com
ping -D -s 1372 example.com
# Linux
ping -M do -s 1472 example.com
tracepath example.com                  # reports "pmtu" hop by hop
ss -ti dst example.com | grep -o 'pmtu:[0-9]*'

If 1472 fails silently while 1372 works, and tcpdump -n icmp shows no "need to frag", you have a black hole.

Fix. Allow ICMP type 3 code 4 and ICMPv6 type 2 through every firewall. Clamp MSS on the tunnel or edge router. Set the tunnel interface MTU correctly. Enable tcp_mtu_probing=1 on servers as a safety net.

2. Cross-node pod traffic hangs on large payloads

Symptom. In Kubernetes, pod-to-pod calls on the same node work. Across nodes, small requests work and large POSTs or responses hang.

Mechanism. The overlay (VXLAN, GENEVE, IPIP or WireGuard) adds 20–80 bytes per packet. If the pod interface MTU equals the node's MTU, full-size pod packets no longer fit once encapsulated. The node tries to fragment or drop them, and the ICMP often goes nowhere useful.

Prove it. From inside a pod, run ping -M do -s <MTU-28> to a pod on another node and step the size down. Compare the pod's MTU (ip link inside the pod) with the node's.

Fix. Set the CNI's MTU to the underlay MTU minus the encapsulation overhead (1450 for VXLAN on 1500), or let a CNI that detects it do so. On cloud networks with 9001-byte MTU, the overlay can keep a comfortable 8951.

3. DNS times out for some names (fragmented UDP)

Symptom. Lookups for DNSSEC-signed or record-heavy names time out or are slow. Other names are fine.

Mechanism. The response is larger than the path MTU, so it arrives as IP fragments, and a firewall or NAT drops non-first fragments. The resolver retries, eventually over TCP.

Prove it. dig +dnssec +bufsize=4096 example.com against dig +dnssec +bufsize=1232 example.com and dig +tcp. If only the large buffer size fails, it is fragmentation.

Fix. Use an EDNS buffer size of 1232 bytes. That was the 2020 DNS Flag Day recommendation, chosen to fit the IPv6 minimum MTU with headroom. Responses that don't fit come back truncated and are retried over TCP.

4. A jumbo/standard mismatch on one segment

Symptom. Interactive sessions work, bulk copies stall, but only between certain hosts. Switch counters show "giants" or rx_length_errors.

Mechanism. One side has MTU 9000, the other 1500, on the same L2 segment. No router sits between them, so nobody sends ICMP. Oversized frames are simply discarded by the receiver's NIC or the switch.

Prove it. ping -M do -s 8972 (9000 − 28) between the two hosts, plus interface error counters (ip -s link, ethtool -S).

Fix. One MTU per L2 domain. No exceptions.

5. Chasing ghosts in captures

Symptom. An engineer reports "our servers send 60 KB packets" or "every outgoing checksum is wrong" from a tcpdump on the server.

Mechanism. TSO and checksum offload, as shown above. Nothing is wrong.

Prove it. ethtool -k eth0 | grep -E 'tcp-segmentation|tx-checksumming|generic-receive'. Then capture again with offloads off on a test host, or on a SPAN port, and the giants disappear.

Fix. Teach the team where the tap sits. Real offload bugs do exist, usually in virtual NICs or tunnel devices that mishandle segmentation of encapsulated traffic. The test for one is the same: turn that offload off (ethtool -K) and see if the corruption stops.

Deep dive: 2026 context

Post-quantum key exchange made the ClientHello bigger than a packet. Browsers and major CDNs now negotiate the hybrid X25519MLKEM768 key exchange by default. Its client key share is 1,216 bytes (an ML-KEM-768 public key of 1,184 bytes plus 32 bytes of X25519). That pushes a browser's ClientHello to roughly 1.8 KB, which needs two TCP segments. Frame 4 above becomes frames 4 and 5. Some middleboxes assumed a ClientHello always fits in one packet, and they broke when this rolled out. If a TLS-inspecting firewall drops "only modern browsers," look here first. The server's reply share is 1,120 bytes (an 1,088-byte ML-KEM ciphertext plus 32), so the server's first flight grows too.

QUIC owns its own MTU logic. HTTP/3 runs over UDP, so there is no MSS and no router clamping. QUIC sets DF, requires the path to carry 1,200-byte datagrams, and pads every client Initial packet to at least that size. Then it probes upward with its own packetization-layer PMTUD (DPLPMTUD, RFC 8899). A post-quantum ClientHello simply spans two Initial packets. Because QUIC lives in user space, Linux added UDP GSO and GRO (UDP_SEGMENT, and the tx-udp-segmentation feature you can see in ethtool -k). So QUIC captures show "giant" UDP datagrams for the same reason TCP captures show giant segments.

Cloud MTUs differ by path, not by host. AWS supports 9001 within a VPC, but traffic through an internet gateway, and most VPN paths, is limited to 1500. GCP VPCs default to 1460, configurable up to 8896. Overlays, service meshes and zero-trust tunnels each take another slice. One request can cross four different MTUs, and an MTU black hole at any one of them looks exactly like an application hang.

Encrypted Client Hello (ECH) hides the real server name inside an encrypted extension, and clients pad it so its size doesn't leak the name. That is one more reason a ClientHello no longer fits into an old firewall's idea of "one small packet."

Deep dive: senior interview questions

Q1: Every textbook says the MSS on Ethernet is 1460. Your capture shows 1448-byte segments. Why?

1460 is the MSS: the MTU minus 20 bytes of IP and 20 of TCP fixed header. But TCP timestamps (RFC 7323) add 12 bytes of options to every segment after the handshake, and they are on by default on Linux and macOS. So the data per segment is 1460 − 12 = 1448. The SYN announces 1460 because the announced MSS doesn't count options. A senior answer also notes that the path MTU, not the announced MSS, sets the real ceiling.

Q2: tcpdump on a server shows a 16,458-byte IP packet leaving an interface with MTU 1500. Is something broken?

No. That is TCP Segmentation Offload. The kernel hands the NIC one large buffer with a gso_size, and the NIC cuts it into MSS-sized segments with correct headers. The capture tap sits before the NIC, so it sees the big buffer. On the receive side, GRO does the reverse before the tap. Software GSO, by contrast, segments before the tap, so its captures look normal. To see the true wire, capture off-host or disable offloads on a test machine.

Q3: Explain path MTU discovery, how it fails, and how TCP survives the failure.

TCP sends with DF set. A router that can't forward a packet onto a smaller link drops it and returns ICMP "fragmentation needed" (IPv4) or "packet too big" (IPv6), carrying the next-hop MTU. The sender caches the lower MTU per destination and resends smaller segments. It fails when that ICMP is filtered, which creates a black hole: small packets pass, full-size ones vanish, and connections hang after the handshake. TCP survives in three ways. Routers can clamp MSS in SYNs. Hosts can use packetization-layer probing (RFC 4821; Linux tcp_mtu_probing), which falls back to a smaller MSS after timeouts. And operators can stop filtering ICMP, which is the real fix.

Q4: Why can't IPv6 routers fragment, and what did that cost?

Router fragmentation costs router CPU, multiplies loss, forces receivers to hold reassembly state, and blinds middleboxes to ports. IPv6 moved fragmentation to the source host only (a Fragment extension header) and guaranteed a 1280-byte minimum MTU. The cost is that IPv6 depends completely on ICMPv6 Packet Too Big reaching the sender. That is why RFC 4890 says never to filter it, and why IPv6 black holes are worse than IPv4 ones.

Q5: What does MSS clamping do, where does it run, and why is it a hack?

A router or firewall rewrites the MSS option in TCP SYNs passing through it, down to what the path can carry, and fixes the checksum. Both ends then never send segments that need PMTUD. It runs on VPN gateways, PPPoE routers and tunnel endpoints. It's a hack because a network device edits a transport-layer header, which breaks the layering, and it does nothing for UDP or QUIC. It also only works if the clamp point actually knows the path's bottleneck MTU.

Q6: Why did a GET for a 1.2 KB page take 17 frames and about 4.6 KB?

Count them: three frames of TCP handshake, then the ClientHello, the server's TLS flight and the client Finished. Then two session tickets, the request, and the response split across two segments. ACKs fill the gaps, and three frames close the connection. Each frame pays 66 bytes of Ethernet, IP and TCP headers (with timestamps), and each TLS record pays 22. Header bytes alone were 24% of the capture. Connection reuse, TLS resumption or 0-RTT, and HTTP/2 or HTTP/3 multiplexing exist to amortise exactly this fixed cost.

Q7: Why must QUIC client Initial packets be at least 1200 bytes?

Two reasons. First, it proves the path can carry 1,200-byte UDP datagrams before the connection depends on that size. Second, it limits amplification. A server may send at most three times the bytes it has received from an unvalidated client address (RFC 9000). A large first packet from the client lets the server send its handshake without becoming a useful tool for reflection attacks.
