1. Why it matters

Most of the networks you will debug in the next ten years have no cables you can touch. They are VPCs. Somebody typed a CIDR into a form, clicked "create", and a network appeared. It has subnets, route tables, gateways and firewalls. It looks like the networks in Modules 3 through 15, and that resemblance is exactly the trap.

A VPC is not a switch with routers attached. It is a program. Every packet your instance sends is caught by the host it runs on, checked against your rules, looked up in a mapping table, wrapped in another packet and sent across a physical network you will never see. Broadcast does not exist. ARP never leaves the server. The "router" at .1 is not a box anywhere. When you hold the old mental model, cloud failures look random. When you hold the real one, they look obvious.

The stakes are practical. A forgotten route sends 40 TB a month of S3 traffic through a NAT gateway and adds a four-figure line to the bill. A "tightened" network ACL breaks every database connection in a subnet while the security group looks perfect. A NAT gateway silently resets long-idle connections at 350 seconds, and an ORM's connection pool starts throwing errors once an hour. None of these show up as "the network is down." They show up as weird.

This module uses AWS as the concrete example, because it is the one you are most likely to meet. Where Google Cloud (GCP) and Azure do the same job under a different name, the text names the equivalent. The ideas carry over. The defaults and limits do not, so treat every number here as "true at the time of writing, check the current docs."

2. The mental model

The analogy that works best is not a building. It is a spreadsheet.

Picture one giant table, owned by the cloud provider, with a row for every network interface in the region. Each row says: this interface belongs to VPC vpc-0a1b, has private IP 10.20.3.17, lives on physical server host-4471, and carries security groups sg-app. Next to it sit smaller tables: your route tables, your ACLs, your security group rules. Your VPC is those rows. Nothing else.

When your instance sends a packet, the software on its host consults the tables and decides three things. Is this packet allowed out? Where does its destination live? How do I get it there? If the destination is another instance, the host wraps the packet in an outer header addressed to the other physical server and sends it across the provider's ordinary data-centre network. The receiving host unwraps it, checks its rules, and hands it to the destination instance. The two instances believe they share a LAN. They share a lookup table.

That is what "software-defined overlay" means. Your network (the overlay) is a set of addressing and policy rules. The provider's physical network (the underlay, or substrate) carries the wrapped packets. The two never mix: your 10.20.0.0/16 can overlap with a million other customers' 10.20.0.0/16 because the outer headers carry the provider's own addresses and a VPC identifier.

Three consequences fall straight out of this model, and you should be able to recite them.

There is no broadcast and no real ARP. An ARP request is a broadcast. In a VPC there is nobody to broadcast to, so the host intercepts the request and answers it itself from the table. Gratuitous ARP tricks — the kind keepalived or Pacemaker use to move a floating IP between two servers — do nothing. To move an IP in a VPC you call an API that edits the table.

Every rule is enforced at the edge, per interface. There is no central firewall box your traffic passes through. Security groups are evaluated on the source host and the destination host. That is why they scale with your fleet, and why "the firewall is overloaded" is almost never the answer in a VPC.

The gateways are not boxes either — mostly. The VPC router at .1 is a behaviour of every host. The internet gateway is a horizontally scaled translation service. The NAT gateway, the Network Load Balancer and PrivateLink run on a shared, scaled-out AWS system called Hyperplane. They have limits, but they are throughput and connection limits, not "the router CPU is at 100%."

Keep one more distinction ready: region, availability zone, subnet. A region (us-east-1) is a metro area of data centres. An availability zone (AZ) is one or more data centres inside it, with independent power and networking. A VPC spans a whole region. Each subnet lives in exactly one AZ. That last rule decides your failure domains, your NAT layout and a surprising share of your bill.

3. How it works

The layout everyone builds

Almost every production VPC starts from the same shape: subnets in at least two AZs, split into public and private tiers.

Read the diagram from the route tables, not the boxes. A subnet is "public" for one reason only: its route table has a 0.0.0.0/0 route pointing at the internet gateway. There is no "public" checkbox. A subnet is "private" because its default route points at a NAT gateway (outbound only) or at nothing at all.

Route tables: longest prefix match, one table per subnet

Each subnet is associated with exactly one route table. A route table can serve many subnets. If you never associate one, the subnet uses the VPC's main route table, which is a quiet source of surprises — change the main table and every unassociated subnet changes with it.

Lookup is longest prefix match, exactly as in Module 9. Every table starts with a local route for the VPC's CIDR (and each secondary CIDR) with target local. It means "deliver inside the VPC" and it is why instances in different subnets can talk without you adding anything. Since 2021 AWS has allowed routes more specific than the local route, so you can force traffic between two subnets through a firewall appliance. That is the only common reason to touch it.

Targets you will see: local, an internet gateway (igw-), a NAT gateway (nat-), a VPC peering connection (pcx-), a Transit Gateway (tgw-), a virtual private gateway for VPN (vgw-), a gateway endpoint for S3 or DynamoDB (a prefix list pl- pointing at vpce-), or a specific network interface (eni-) for an appliance.

GCP works differently on one point worth knowing. Its routes belong to the VPC network as a whole and can be scoped to instances by network tag. There is no per-subnet route table. Azure uses user-defined routes (UDRs) in route tables attached to subnets, which feels close to AWS.

Internet gateway: a 1:1 NAT you never see

An internet gateway (IGW) attaches to one VPC. It does two jobs. It is the route target for internet-bound traffic. And it performs one-to-one NAT between an instance's private IP and its public IPv4 address.

That second job surprises people. Run ip addr on an EC2 instance with a public IP and you will see only the private one. The public address is never configured on the instance. The IGW rewrites the source 10.20.108.10 to 54.x.y.z on the way out and reverses it on the way in. It is static NAT from Module 15, one address per instance, no port rewriting.

For an instance to reach the internet through an IGW, four things must be true. It needs a public IPv4 (auto-assigned or an Elastic IP). Its subnet's route table needs 0.0.0.0/0 → igw-. Its security group must allow the traffic. Its subnet's NACL must allow it in both directions. Miss any one and it fails, usually as a timeout.

For IPv6 there is no NAT. Addresses are globally unique, so the IGW just routes. If you want "outbound only" for IPv6, you use an egress-only internet gateway, which is a stateful "replies only" gate rather than a translator.

NAT gateway: many-to-one, with a port budget

Private-subnet instances have no public IP, so the IGW cannot translate them. A NAT gateway fills the gap. It sits in a public subnet with an Elastic IP, and private route tables point 0.0.0.0/0 at it. It does PAT, the many-to-one translation from Module 15: it rewrites the source to its own private IP and source port, and the IGW then translates that private IP to the NAT's Elastic IP.

Four properties of the NAT gateway matter in production.

It is zonal. A NAT gateway lives in one AZ. If that AZ fails, every subnet routing through it loses outbound access. The standard design is one NAT gateway per AZ, with each AZ's private route table pointing at its own.

It has a port budget per destination. AWS documents a NAT gateway as supporting up to 55,000 simultaneous connections to each unique destination — a destination being the combination of destination IP, destination port and protocol. Thousands of connections spread across many destinations are fine. Fifty-five thousand connections to one API endpoint on 443 are the limit for one NAT IP. Past it, new connections fail and the ErrorPortAllocation CloudWatch metric goes up. You can attach secondary IPs to a NAT gateway to multiply the budget.

It times out idle connections at 350 seconds. A TCP connection with no traffic for 350 seconds is dropped from the NAT's table. When the instance next sends on it, the NAT gateway answers with a RST. Linux's default TCP keepalive starts after 7,200 seconds, far too late to help.

It costs per hour and per gigabyte. Every byte through a NAT gateway is billed as "data processed" on top of any transfer charge. That includes traffic to AWS's own services, such as S3, unless you give them a different path.

GCP's Cloud NAT is different under the hood: there is no gateway in the data path. The NAT is programmed into each VM's host, and every VM gets a block of source ports (64 by default, more with dynamic port allocation). Azure NAT Gateway gives each public IP 64,512 SNAT ports and lets you attach up to 16 public IPs. Same idea, different accounting.

Security groups vs network ACLs: stateful vs stateless

This is Module 15's stateful-versus-stateless filtering, made concrete.

A security group (SG) attaches to a network interface. It has allow rules only — there is no deny. All rules are evaluated together, so order does not matter: if any rule matches, the packet is allowed. It is stateful. When it allows a connection in one direction, it records the flow in a connection-tracking table, and the replies are allowed automatically without consulting any rule. Rules can name another security group as the source, as in "allow 5432 from sg-app." That rule means "from any interface carrying sg-app", and it follows instances as they scale up and down. It is the most useful single feature in cloud networking.

A network ACL (NACL) attaches to a subnet. It has numbered rules, evaluated lowest number first, and the first match wins. It can allow and deny. It ends with an implicit * rule that denies everything. And it is stateless. A reply packet is just another packet, judged on its own five-tuple against the rules for its direction.

That last property is where people get hurt. A client connects from ephemeral port 48812 to a database on 5432. The request passes the database subnet's inbound rule for 5432. The reply leaves the database subnet with destination port 48812. If the outbound NACL rule only allows port 5432, the reply dies. The SYN arrives, the SYN-ACK never makes it back, and the client times out. NACL rules for return traffic must allow the client's ephemeral range. Linux uses 32768–60999 by default, Windows 49152–65535, and AWS's own NAT gateways and load balancers use 1024–65535, which is why AWS's examples allow 1024–65535.

The practical rule most teams settle on: put real policy in security groups, leave NACLs at allow-all, and use NACLs only for coarse subnet-wide denies, such as blocking a known-bad CIDR in an incident. GCP and Azure have no stateless subnet ACL at all. Their firewall rules and NSGs are stateful, with numeric priorities and both allow and deny.

Connecting VPCs: peering, Transit Gateway, PrivateLink

Sooner or later one VPC is not enough. There are three ways to connect them, and they solve different problems.

VPC peering joins two VPCs so their CIDRs can route to each other directly. You add a route in each side's route table pointing at the pcx- connection. It is not transitive. If A peers with B and B peers with C, A cannot reach C through B. Nor can A use B's internet gateway, NAT gateway or VPN. The CIDRs must not overlap. There is no hourly charge, and traffic within one AZ is free while cross-AZ traffic pays the normal cross-AZ rate. Peering is the cheapest and fastest path, and it turns into a mesh nightmare at around a dozen VPCs: n VPCs need n(n−1)/2 connections.

Transit Gateway (TGW) is a regional router you attach VPCs, VPNs and Direct Connect to. It has its own route tables, so you can build hub-and-spoke designs, segment environments, and route everything through an inspection VPC. It is transitive by design. It costs per attachment-hour and per gigabyte processed, and it adds a hop. For dozens or hundreds of VPCs, it is the default answer.

PrivateLink does not connect networks at all. It publishes one service from a provider VPC into consumer VPCs. The provider puts the service behind a Network Load Balancer. The consumer creates an interface endpoint, which is a network interface with a private IP in the consumer's own subnet. Traffic to that IP is carried to the provider's NLB. Nothing else in either VPC is reachable. CIDRs can overlap freely. Connections are one-way: consumers can open connections to the service, never the reverse. This is how most AWS services and many SaaS vendors are reached privately.

S3 and DynamoDB also offer gateway endpoints, which are older and simpler. A gateway endpoint adds a prefix-list route to your route tables. It costs nothing. It only works for traffic that originates in that VPC — not from peered VPCs or from on-premises.

DNS inside the VPC

Every VPC has a built-in DNS resolver, the Route 53 Resolver (historically "AmazonProvidedDNS"). Instances reach it at the VPC CIDR's base address plus two (10.20.0.2 for 10.20.0.0/16) or at the link-local address 169.254.169.253. It answers three kinds of question: AWS's internal names (ip-10-20-3-17.ec2.internal), records in private hosted zones you have associated with the VPC, and everything else by recursing out to the public internet.

A private hosted zone is a DNS zone that only answers for the VPCs it is associated with. You can create internal.example.com in a private zone and the same name in a public zone with different answers. That is split-horizon DNS. Two VPC attributes, enableDnsSupport and enableDnsHostnames, must both be true for private zones to work. When one is off, names simply fail to resolve, and the error looks like a DNS outage.

For hybrid networks you add Resolver endpoints. An inbound endpoint gives on-premises DNS servers IP addresses in your VPC to forward queries to. An outbound endpoint, plus forwarding rules, lets VPC instances resolve on-premises zones such as corp.example.com. GCP does the same with Cloud DNS private zones and forwarding zones; Azure uses Private DNS zones and the Azure DNS Private Resolver.

Hybrid: VPN and Direct Connect

Two ways to reach your data centre.

Site-to-Site VPN runs IPsec over the internet (Module 16). Each AWS VPN connection has two tunnels, terminating on two different AWS endpoints. You are expected to configure both. AWS takes tunnel endpoints down for maintenance, and a one-tunnel setup turns that routine event into an outage. Routing is static or, better, BGP. Per-tunnel throughput has historically been capped around 1.25 Gbps, and you scale past that with ECMP across several VPNs on a Transit Gateway. Check current limits; this is an area AWS keeps changing.

Direct Connect is a physical cross-connect from your router to AWS's router in a colocation facility, at 1, 10 or 100 Gbps (with higher speeds at some locations), or a smaller hosted connection through a partner. On top of the physical link you create virtual interfaces (VIFs), each an 802.1Q VLAN with its own BGP session. A private VIF reaches VPCs, a transit VIF reaches Transit Gateways, and a public VIF reaches AWS public endpoints. Direct Connect is not encrypted by default. Teams that need encryption run IPsec over it or use MACsec on supported ports.

The typical production pattern: Direct Connect as primary, VPN as backup, BGP deciding between them.

4. The exact structure

Addresses: what AWS takes from every subnet

A VPC's primary IPv4 CIDR can be anywhere from /16 to /28. A subnet's CIDR must sit inside it and can be as small as /28. AWS reserves five addresses in every subnet:

Address (in 10.20.108.0/24) Reserved for
10.20.108.0 network address
10.20.108.1 the VPC router (your default gateway)
10.20.108.2 DNS (only the VPC base +2 actually answers; AWS reserves +2 in every subnet)
10.20.108.3 reserved for future use
10.20.108.255 last address; VPCs have no broadcast, but it is reserved anyway

So a /24 gives you 251 usable addresses and a /28 gives you 11. Azure also reserves five per subnet. GCP reserves four in each subnet's primary range.

The default VPC that AWS creates in every region uses 172.31.0.0/16 with a /20 per AZ. It has an internet gateway and public subnets. It is fine for experiments and wrong for production, mostly because its CIDR will collide with someone else's default VPC the day you need to peer.

A security group and a NACL, side by side

security group sg-db  (attached to the database ENIs)
  inbound   tcp 5432   source sg-app                 # any ENI carrying sg-app
  outbound  (none)                                    # replies still flow: stateful

network ACL acl-data  (associated with the three data subnets)
  inbound   100  tcp 5432         10.20.0.0/19   ALLOW
  inbound   *    all  all         0.0.0.0/0      DENY
  outbound  100  tcp 1024-65535   10.20.0.0/19   ALLOW   # replies to ephemeral ports
  outbound  *    all  all         0.0.0.0/0      DENY

The security group has no outbound rule at all, and replies still work, because the inbound connection created a tracking entry. The NACL needs the explicit outbound rule for ports 1024–65535 or every reply dies. Notice also that NACL rules can only say 10.20.0.0/19. They cannot say "from the app tier" the way the security group can.

A VPC flow log record

Flow logs record one line per flow per aggregation interval (10 minutes by default, 1 minute if you ask) per network interface. The default format, version 2, has fourteen space-separated fields:

version account-id   interface-id srcaddr     dstaddr     srcport dstport protocol packets bytes start      end        action log-status
2       123456789012 eni-0db5e1   10.20.3.17  10.20.97.40 48812   5432    6        3       180   1792134000 1792134060 ACCEPT OK
2       123456789012 eni-0db5e1   10.20.97.40 10.20.3.17  5432    48812   6        3       180   1792134000 1792134060 REJECT OK

(Constructed records, internally consistent.) Protocol 6 is TCP. Three packets of 180 bytes total are three 60-byte SYNs: a 20-byte IP header plus a 40-byte TCP header with options. start and end are Unix seconds, one minute apart here. The first line says the database's interface accepted three incoming SYNs. The second says its three SYN-ACK replies were rejected on the way out. A security group never does that — its replies are tracked. An ACCEPT followed by a REJECT of the exact reverse five-tuple is the fingerprint of a stateless NACL.

Flow logs are not packet captures. They do not record payloads, flags (unless you add the tcp-flags field in a custom format), or traffic to a few special destinations: the Amazon DNS resolver, the instance metadata service at 169.254.169.254, the Time Sync service, DHCP, and the reserved router address.

5. A realistic example

A payments company runs a three-tier service in us-east-1. The VPC is 10.20.0.0/16 across three AZs. Each AZ has a public /24 (load balancer, NAT gateway), a private /19 (application containers) and a data /22 (Postgres replicas, Redis). On-premises is reached over Direct Connect, with a VPN as backup. A shared-services VPC (10.30.0.0/16) is peered in for logging and CI.

Monday, 09:40. A security engineer "tightens" the data-tier NACL. The old rules were allow-all. The new rules allow inbound 5432 from the app /19 and outbound 5432 to the app /19. The change looks symmetrical and careful. Within a minute, new database connections from every app pod start timing out. Existing connections die too. NACLs keep no state, so every reply on an open connection is also going to an ephemeral port, and every one is now denied. The pool's health checks fail and the service degrades in all three AZs at once.

The on-call engineer checks the security groups first. They are perfect. sg-db allows 5432 from sg-app, and nothing changed there. She opens the flow logs for one database interface and sees the pattern from section 4: incoming SYNs ACCEPT, outgoing SYN-ACKs to port 48812 REJECT. Two minutes later the NACL has an outbound rule for 1024–65535 and the service recovers. The postmortem's lesson is the one Module 15 already taught: a stateless filter must be told about replies.

Wednesday. Finance asks why the NAT gateway line on the bill is $2,000 a month. Flow logs on the NAT gateway's interface, aggregated by destination, show 90% of its bytes going to 52.216.0.0/16 — S3. The app writes batch files to S3 through the NAT, paying the NAT's per-gigabyte processing fee on 40 TB a month. A gateway endpoint for S3, one route-table change, makes that path free. The worked numbers are in the deep dive.

Friday. A partner integration starts failing once an hour with connection reset by peer. The integration keeps a pool of TCP connections to the partner's API and sometimes leaves one idle for ten minutes. The NAT gateway forgets any connection idle for 350 seconds. The next request on that socket gets a RST from the NAT gateway. The fix is a TCP keepalive interval under 350 seconds on the pool, or a pool idle timeout shorter than that.

None of these three incidents involved a broken network. Each one was the network doing exactly what its tables said.

6. Misconceptions & common mistakes

"The VPC is like a big switch." It is closer to a distributed database of addresses and rules. There is no shared Layer 2 segment. Broadcast and multicast do not work (except multicast through Transit Gateway's specific multicast feature). Tools that rely on them — gratuitous ARP failover, broadcast discovery, most VRRP setups — need cloud-specific replacements, usually an API call that moves an IP or rewrites a route.

"A public subnet is a setting." It is a route. A subnet is public if and only if its route table sends 0.0.0.0/0 to an internet gateway. An instance in that subnet still needs a public IP to be reachable.

"Security groups are evaluated in order." They are not. They are a set of allow rules, and any match allows. Order matters for NACLs, GCP firewall priorities and Azure NSG priorities, not for AWS security groups.

"Removing a security group rule cuts existing connections." Usually not. A connection already tracked by the security group keeps flowing until it closes or idles out, and established TCP flows have a long default tracking timeout (five days on AWS at the time of writing). If you are cutting off an attacker, a NACL deny takes effect immediately because NACLs track nothing.

"us-east-1a is the same data centre for everyone." AZ names are mapped per account. Your us-east-1a may be someone else's us-east-1c. When you coordinate with another account — a vendor, a sister team — use AZ IDs such as use1-az1.

"Traffic between my instances is free." Inside one AZ, mostly yes. Across AZs, AWS charges per gigabyte in each direction. Chatty services spread across three AZs can pay more for cross-AZ transfer than for compute.

"NAT gateway traffic to AWS services stays inside AWS, so it is free." It may stay inside AWS, but the NAT gateway still bills every gigabyte it processes. Gateway endpoints (S3, DynamoDB) and interface endpoints (most other services) exist to take that traffic off the NAT.

"Peering is transitive if I add the routes." It is not. AWS will not forward traffic that enters through one peering connection and leaves through another, whatever your route tables say. You need a Transit Gateway or an appliance.

"Overlapping CIDRs can be fixed later." They cannot be fixed cheaply. Peering and Transit Gateway routing both refuse or misroute overlapping ranges, and re-addressing a live VPC means rebuilding its subnets. Plan CIDRs across the whole company, including on-premises and every developer's Docker default (172.17.0.0/16), before the first VPC exists.

7. Interview Q&A

Q1: What makes a subnet "public" in AWS?

A route. If the subnet's route table has a 0.0.0.0/0 (or ::/0) route whose target is an internet gateway, the subnet is public. Nothing else. An instance in it still needs a public IPv4 or an IPv6 address, and security groups and NACLs must allow the traffic. A private subnet has its default route pointing at a NAT gateway, at a Transit Gateway, or at nothing.

Q2: Security group versus NACL — what is the difference, and which do you use?

A security group attaches to a network interface, is stateful, has allow rules only, and evaluates all rules together. A NACL attaches to a subnet, is stateless, has numbered allow and deny rules evaluated in order, and needs explicit rules for return traffic on ephemeral ports. Use security groups for real policy, especially security-group-to-security-group references that follow instances as they scale. Use NACLs sparingly, for coarse subnet-wide denies.

Q3: Your instance has a public IP but ip addr only shows 10.20.108.10. Why?

Because the public IPv4 is never configured on the instance. The internet gateway does one-to-one NAT between the private address and the public one. Outbound packets leave with the private source; the IGW rewrites it. Inbound packets arrive at the public address; the IGW rewrites the destination back to the private one. To find the public address from inside, ask the instance metadata service.

Q4: Why do instances in a private subnet need a NAT gateway to download packages, and what does the NAT gateway cost you?

They have no public IP, so the internet gateway has nothing to translate them to. The NAT gateway does PAT: it rewrites their source to its own address and a unique port, then the IGW translates its address to its Elastic IP. The costs are an hourly charge per NAT gateway, a per-gigabyte processing charge on every byte (including traffic to AWS services), cross-AZ charges if a subnet uses another AZ's NAT gateway, and normal internet egress charges.

Q5: When would you choose VPC peering, Transit Gateway or PrivateLink?

Peering for a handful of VPCs that need full, low-latency, cheap connectivity and have non-overlapping CIDRs. Transit Gateway when the number of VPCs grows, when you need transitive routing to VPN or Direct Connect, or when traffic must pass through a central inspection VPC. PrivateLink when the goal is to expose one service, not a network — especially across accounts or organizations, or when CIDRs overlap.

Q6: A private hosted zone exists for internal.example.com, but an instance gets NXDOMAIN. What do you check?

That the zone is associated with this VPC (association is per VPC, and in another account requires an authorization step). That enableDnsSupport and enableDnsHostnames are both true on the VPC. That the instance is actually using the VPC resolver (base +2 or 169.254.169.253) and not a custom resolver in /etc/resolv.conf. And whether a Resolver forwarding rule for an overlapping domain is sending the query to on-premises DNS instead.

Q7: Why does AWS give you two tunnels per Site-to-Site VPN connection?

The two tunnels terminate on two different AWS endpoints, so the connection survives the failure or maintenance of one. AWS performs routine maintenance that takes a tunnel down. If you configured only one tunnel, that maintenance is an outage. With BGP over both, the routing moves on its own.

Planning CIDRs before they bite

The worst cloud networking mistakes happen on day one, when someone picks a CIDR. This script carves a /16 into per-AZ tiers, accounts for AWS's five reserved addresses, and checks the plan against every network the VPC might ever need to route to.

"""Plan a VPC: carve one CIDR into per-AZ tiers, show AWS's five
reserved addresses per subnet, and check for overlap with every network
you might ever need to route to (on-prem, peers, other regions)."""
import ipaddress as ip

VPC = ip.ip_network("10.20.0.0/16")
AZS = ["us-east-1a", "us-east-1b", "us-east-1c"]
# Tier name -> prefix length. Big private tier for pods/tasks, small public tier.
TIERS = [("private", 19), ("data", 22), ("public", 24)]

def reserved(subnet):
    """AWS reserves the first four addresses and the last one in every subnet."""
    n = subnet.network_address
    return {
        "network": n,
        "vpc-router": n + 1,
        "dns (reserved)": n + 2,
        "future use": n + 3,
        "last (no broadcast)": subnet.broadcast_address,
    }

def carve(vpc, tiers, azs):
    free = [vpc]
    plan = []
    for tier, plen in tiers:
        for az in azs:
            # first free block that can hold this prefix length
            for i, block in enumerate(free):
                if block.prefixlen <= plen:
                    sub = next(block.subnets(new_prefix=plen))
                    free.pop(i)
                    free[i:i] = list(block.address_exclude(sub)) if block != sub else []
                    free.sort(key=lambda b: (b.network_address, b.prefixlen))
                    plan.append((tier, az, sub))
                    break
    return plan, free

Following a packet through the filters

This script is a toy version of what Reachability Analyzer does: evaluate a flow against the configuration, step by step, without sending a packet. It walks the forward path and then the return path, where stateful and stateless filters part ways.

code/m22/path_check.py:

"""A toy reachability analyzer. It evaluates a flow the way the VPC data
plane does: source security group (egress), source subnet NACL (out),
route table (longest prefix match), destination NACL (in), destination
security group (ingress) -- and then the RETURN packet, where stateful
and stateless filters behave differently."""
import ipaddress as ip

def net(c): return ip.ip_network(c)

ROUTES = {  # subnet -> route table
    "app-a":  [("10.20.0.0/16", "local"), ("0.0.0.0/0", "nat-0a1")],
    "data-a": [("10.20.0.0/16", "local")],
    "pub-a":  [("10.20.0.0/16", "local"), ("0.0.0.0/0", "igw-07f")],
}
SUBNETS = {"app-a": "10.20.0.0/19", "data-a": "10.20.96.0/22", "pub-a": "10.20.108.0/24"}

# NACL rules: (number, direction, proto, port range, cidr, action); lowest number wins.
NACL = {
    "app-a":  [(100, "out", "tcp", (0, 65535), "0.0.0.0/0", "allow"),
               (100, "in",  "tcp", (0, 65535), "0.0.0.0/0", "allow")],
    # A "tightened" data-tier NACL: someone allowed 5432 in and 5432 out.
    "data-a": [(100, "in",  "tcp", (5432, 5432), "10.20.0.0/19", "allow"),
               (100, "out", "tcp", (5432, 5432), "10.20.0.0/19", "allow")],
}
# Security groups: allow-only; any match allows. Rules may reference SGs.
SG = {
    "sg-app": {"egress": [("tcp", (0, 65535), "0.0.0.0/0")], "ingress": []},
    "sg-db":  {"egress": [], "ingress": [("tcp", (5432, 5432), "sg-app")]},
}
ENIS = {  # ip -> (subnet, security group)
    "10.20.3.17": ("app-a", "sg-app"),
    "10.20.97.40": ("data-a", "sg-db"),
}

def nacl_ok(subnet, direction, proto, port, peer):
    for num, d, p, (lo, hi), cidr, action in sorted(NACL.get(subnet, [])):
        if d == direction and p == proto and lo <= port <= hi and ip.ip_address(peer) in net(cidr):
            return action == "allow", f"rule {num} {action}"
    return False, "rule * deny (implicit)"

def sg_ok(sg, direction, proto, port, peer):
    for p, (lo, hi), src in SG[sg][direction]:
        if src.startswith("sg-"):
            match = peer in ENIS and ENIS[peer][1] == src
        else:
            match = ip.ip_address(peer) in net(src)
        if p == proto and lo <= port <= hi and match:
            return True, f"{direction} rule {p}/{lo}-{hi} {'to' if direction == 'egress' else 'from'} {src}"
    return False, "no allow rule"

def route(subnet, dst):
    best = max((r for r in ROUTES[subnet] if ip.ip_address(dst) in net(r[0])),
               key=lambda r: net(r[0]).prefixlen, default=None)
    return best

def check(src, sport, dst, dport, proto="tcp"):
    s_sub, s_sg = ENIS[src]
    d_sub, d_sg = ENIS[dst]
    print(f"\nflow {src}:{sport} -> {dst}:{dport}/{proto}")
    steps = [
        ("SG egress   " + s_sg, *sg_ok(s_sg, "egress", proto, dport, dst)),
        ("NACL out    " + s_sub, *nacl_ok(s_sub, "out", proto, dport, dst)),
    ]
    r = route(s_sub, dst)
    steps.append(("route       " + s_sub, r is not None, f"{r[0]} -> {r[1]}" if r else "no route"))
    steps += [
        ("NACL in     " + d_sub, *nacl_ok(d_sub, "in", proto, dport, src)),
        ("SG ingress  " + d_sg, *sg_ok(d_sg, "ingress", proto, dport, src)),
    ]
    for name, ok, why in steps:
        print(f"  {'pass' if ok else 'DROP'}  {name:20} {why}")
        if not ok:
            return
    print("  return path (dst -> src, ports swapped):")
    print(f"  pass  SG {d_sg:17} tracked connection, no rule consulted")
    ok, why = nacl_ok(d_sub, "out", proto, sport, src)
    print(f"  {'pass' if ok else 'DROP'}  NACL out    {d_sub:8} dport {sport}: {why}")
    if not ok:
        return
    ok, why = nacl_ok(s_sub, "in", proto, sport, dst)
    print(f"  {'pass' if ok else 'DROP'}  NACL in     {s_sub:8} dport {sport}: {why}")
    print(f"  pass  SG {s_sg:17} tracked connection, no rule consulted")

check("10.20.3.17", 48812, "10.20.97.40", 5432)
print("\nfix: allow the client's ephemeral range outbound on the data NACL")
NACL["data-a"].append((110, "out", "tcp", (1024, 65535), "10.20.0.0/19", "allow"))

Deep dive: what the console hides

The console shows you boxes: a VPC, subnets, gateways, firewalls. It invites you to picture a data-centre network in miniature. The rest of this module goes under that picture. It covers the actual machinery that moves a packet between two instances, what you can observe of it from inside, the numbers that bound it, and the ways it fails that have no equivalent in a physical network.

Deep dive: the real mental model

Start with one packet, from an app instance at 10.20.3.17 to a database at 10.20.97.40, in a different subnet and a different AZ.

Here is the sequence, as far as AWS has described it publicly. The details of the encapsulation are proprietary, so this is the model, not the wire format.

  1. The guest kernel routes the packet. 10.20.97.40 is outside the instance's own /19, so Linux sends it to the default gateway, 10.20.0.1. It needs the gateway's MAC address, so it sends an ARP request.
  2. The host answers the ARP. On current EC2 instances, the network interface the guest sees is presented by the Nitro card, a dedicated card in the physical server. The ARP request never leaves that card. The card replies with a MAC address for the gateway. There is no router at 10.20.0.1; the address is a convention the card honours.
  3. The card enforces the source security group. It checks egress rules against the packet's five-tuple, and records a new entry in its connection-tracking table. It also checks source/destination: the packet's source IP must belong to this interface, unless you disabled the check (as you must for NAT instances and firewall appliances).
  4. The card applies the subnet's NACL and route table. The NACL outbound rules run, in number order. The route table lookup finds 10.20.0.0/16 → local.
  5. The card asks where the destination lives. For local routes it needs to know which physical server hosts 10.20.97.40 in this VPC. That answer comes from a mapping service — a regional database of "VPC + private IP → physical host" — and is cached on the card.
  6. The card encapsulates and sends. The original packet goes inside an outer packet addressed from host A to host B on the provider's physical network, tagged with the VPC's identity. Your 10.20.x.x addresses never appear on the physical network as routable addresses.
  7. Host B's card reverses the process. It checks the packet came from a host that is genuinely authorised to send for that source IP and VPC — this is what makes spoofing impossible. It applies the destination subnet's NACL inbound rules and the destination security group's ingress rules. Then it delivers the inner packet to the database instance.

The reply follows the mirror-image path. The destination card finds the flow in its tracking table, so the security group lets the reply out without consulting rules. The NACLs, holding no state, judge the reply on its own.

GCP's version of this machine is called Andromeda and Azure's is built on its Virtual Filtering Platform (VFP). The shape is the same: a programmable switch on every host, a central control plane pushing tables, and encapsulation over a physical fabric. Two visible differences are worth knowing. GCP has historically configured VMs with a /32 address, so the guest sends everything, even same-subnet traffic, to the gateway. Azure answers every ARP request with the same well-known MAC address, 12:34:56:78:9a:bc. Both are clues that the "LAN" is an illusion.

Where the gateways actually live

The local route is handled entirely by the two hosts' cards. The other targets are services the card hands packets to.

The internet gateway is a scaled-out edge service that holds the private-to-public one-to-one mappings. Because it is static NAT, it keeps no per-connection state, and AWS documents it as having no bandwidth limit of its own.

The NAT gateway is stateful. It holds a translation table, port allocations and idle timers — so it is built on Hyperplane, AWS's internal service for scaled, stateful packet processing. Hyperplane also runs Network Load Balancers and PrivateLink. When your packet's route says nat-…, the source card encapsulates it toward the Hyperplane nodes serving that NAT gateway in that AZ.

Peering is just the mapping service knowing about a second VPC. When 10.30.0.0/16 → pcx-… matches, the card looks up the destination in the peer VPC's mappings and sends the packet straight to the right host. There is no gateway in the path, which is why peering adds no hop and has no bandwidth limit beyond the instances' own. It is also why peering is not transitive: the card only ever looks one VPC away.

Transit Gateway is a real hop. Packets go from the source host to TGW's infrastructure in the AZ, get looked up in a TGW route table, and go out to the destination attachment. That hop has a cost per gigabyte and a small latency penalty, and it is a point where routing can become asymmetric.

Read it field by field.

  • length 60: 20 bytes of IP header and 40 of TCP header. Three of these are the "3 packets, 180 bytes" in the flow log record from section 4.
  • mss 8961: the interface MTU is 9001, minus 20 bytes of IP and 20 of TCP. Inside a VPC, instances on current types use 9001-byte jumbo frames. The overlay's own encapsulation overhead is absorbed by the provider's fabric; you never see it.
  • win 62727: Linux sizes the initial receive window as a multiple of the MSS. 7 × 8961 = 62,727.
  • cksum … (incorrect -> …): checksum offload. The kernel leaves the checksum for the NIC to fill in, and tcpdump sees the packet before that happens. It is not an error.
  • The timing: the retransmissions arrive about 1 second and then 2 more seconds later. That is Linux's SYN backoff, starting from a 1-second initial RTO (RFC 6298). The same seq number each time confirms these are retries of one SYN.
  • What is missing: any SYN-ACK. The database host did receive these SYNs — its flow log says ACCEPT — and did reply. The replies were dropped by the NACL at the database's side before they could enter the overlay.

At the NAT gateway: two addresses per flow

The default flow-log fields describe the packet as the interface sees it. For a NAT gateway's interface, that hides who is really talking. A custom format with pkt-srcaddr and pkt-dstaddr adds the original packet's addresses:

interface-id  srcaddr      dstaddr       pkt-srcaddr  pkt-dstaddr   srcport dstport bytes     action flow-direction
eni-0nat1a2b  10.20.3.17   10.20.108.75  10.20.3.17   52.216.8.13   41220   443     590000000 ACCEPT ingress
eni-0nat1a2b  10.20.108.75 52.216.8.13   10.20.108.75 52.216.8.13   61833   443     590000000 ACCEPT egress

(Constructed; abbreviated custom format.) The first record is the app instance's traffic arriving at the NAT gateway's private address 10.20.108.75; pkt-dstaddr shows the real destination, an S3 address. The second is the same bytes leaving, translated: the source is now the NAT gateway's own address and a new source port, 61833. The IGW will translate 10.20.108.75 to the NAT's Elastic IP after this. Summing bytes on the NAT interface by pkt-dstaddr is the fastest way to answer "what is my NAT gateway actually processing?"

The counters that tell you a limit was hit

Every EC2 instance type has network allowances: maximums on bandwidth, packets per second, tracked connections and link-local traffic. When you exceed one, packets are queued or dropped by the host, and the guest sees only timeouts and retransmissions. The ENA driver exposes counters for each:

$ ethtool -S ens5 | grep -E 'allowance'
     bw_in_allowance_exceeded: 0
     bw_out_allowance_exceeded: 0
     pps_allowance_exceeded: 0
     conntrack_allowance_exceeded: 18342
     linklocal_allowance_exceeded: 0
     conntrack_allowance_available: 0

(Illustrative; field names are the ENA driver's, values invented. conntrack_allowance_available needs a recent driver.) These counters are cumulative since the driver loaded. A non-zero value that is growing is the signal. Here the instance has run out of connection-tracking capacity: every new flow that its security group needs to track is being dropped. Nothing in CPU, memory or the application's own metrics would tell you that.

MTU budget across a hybrid path

Inside one VPC an instance sends 9001-byte packets. The moment traffic leaves for somewhere with a smaller MTU, Path MTU Discovery (Module 4) must work, or large transfers hang while small requests succeed.

path                              link MTU   max TCP payload (MSS)
same VPC, instance to instance     9001       9001 - 40 = 8961
through Transit Gateway            8500       8500 - 40 = 8460
out through internet gateway       1500       1500 - 40 = 1460
over Site-to-Site VPN (IPsec)      ~1446*     1446 - 40 = 1406

* AWS's VPN documentation gives 1446 as the supported MTU and 1406 as the matching MSS. The exact inner MTU depends on the cipher and encapsulation, which is why it is lower than 1500 and not a round number.

When an instance sends a 9001-byte packet with the DF bit set toward a 1500-byte path, the hop that cannot forward it should send back ICMP "fragmentation needed" (type 3, code 4). A security group that does not allow that ICMP message in breaks PMTUD. AWS's own guidance is to add an inbound rule for it. The alternative is lowering the instance MTU to 1500 for interfaces that mostly talk off-VPC, or relying on MSS clamping at the VPN or appliance.

The shape of an egress bill

Prices are us-east-1 list prices at the time of writing (USD). They change
and vary by region -- the point is the SHAPE of the bill, not the cents."""
HOURS = 730                      # hours in an average month
P = {
    "natgw_hour": 0.045, "natgw_gb": 0.045,      # NAT gateway: per hour + per GB processed
    "internet_gb": 0.09,                          # first paid tier (ignores the free 100 GB)
    "cross_az_gb": 0.01,                          # charged on EACH side of the AZ boundary
}
TB = 1000                        # GB per TB, as billed

def bill(s3_tb, internet_tb, nat_count, s3_path, cross_az_share):
    lines = []
    lines.append(("NAT gateway hours", nat_count * HOURS * P["natgw_hour"]))
    nat_gb = internet_tb * TB + (s3_tb * TB if s3_path == "nat" else 0)
    lines.append(("NAT data processed", nat_gb * P["natgw_gb"]))
    lines.append(("internet egress", internet_tb * TB * P["internet_gb"]))
    # traffic from other AZs hairpinning into one zone's NAT gateway
    lines.append(("cross-AZ to NAT", nat_gb * cross_az_share * 2 * P["cross_az_gb"]))
    return lines

def show(title, lines):
    print(title)
    for name, usd in lines:
        print(f"  {name:24} ${usd:>10,.2f}")
    print(f"  {'total':24} ${sum(u for _, u in lines):>10,.2f}\n")

# Same-region EC2 <-> S3 transfer itself is free; only the NAT hop costs.
# 40 TB/month of S3 reads/writes, 5 TB/month to third-party APIs.
show("A) one NAT gateway in AZ-a, all 3 AZs route to it, S3 via NAT:",
     bill(40, 5, nat_count=1, s3_path="nat", cross_az_share=2/3))
show("B) one NAT gateway per AZ, S3 still via NAT:",
     bill(40, 5, nat_count=3, s3_path="nat", cross_az_share=0))
show("C) one NAT per AZ, S3 via gateway endpoint (free, route-table entry):",
     bill(40, 5, nat_count=3, s3_path="gateway", cross_az_share=0))

print("NAT gateway source-port budget (documented: 55,000 simultaneous")
print("connections per unique destination ip:port:proto, per NAT IP):")
for dests, conns in [(1, 30_000), (1, 70_000), (4, 70_000)]:

Three lessons sit in those numbers.

First, the NAT gateway's hourly charge is noise. Even three of them cost under $100 a month. The per-gigabyte processing charge is the bill.

Second, design A — one NAT gateway for all three AZs — is both the least resilient and not the cheapest. It saves $65 of hourly charges and spends $600 on cross-AZ transfer, because two-thirds of the traffic crosses an AZ boundary to reach the NAT, paying on each side. And when that one AZ fails, the whole VPC loses outbound access.

Third, the S3 gateway endpoint (design C) removes $1,800 a month with one route-table change, because same-region traffic between EC2 and S3 is free once the NAT is out of the path. Internet egress is unchanged; there is no trick for bytes that really leave AWS, except sending fewer of them (compression, caching, a CDN).

The NAT port budget at the bottom is a different kind of number. Seventy thousand connections spread over four destinations fit in one NAT IP. Seventy thousand to one destination need two. That is why a load test against a single endpoint can exhaust a NAT gateway that has carried far more traffic for months.

Latency, roughly

Within an AZ, instance-to-instance round trips are typically well under a millisecond. Across AZs in one region, they are typically around a millisecond or two; AWS describes AZs as separated by meaningful distance (up to roughly 100 km) but connected with low-latency links. Cross-region is governed by the speed of light in fibre: about 1 ms of round trip per 100 km of path. These are typical values, not guarantees, and they vary by region and instance type.

Deep dive: production failure modes

Each entry follows the same shape: what you see, why it happens, how to prove it, and how to fix it.

NAT gateway port exhaustion

  • Symptom. New outbound connections from private subnets fail or time out, often to one particular API, while existing connections are fine.
  • Mechanism. More than 55,000 simultaneous connections to one destination IP, port and protocol through one NAT IP. Short-lived connections make it worse, because closed connections hold their port for a while.
  • Prove it. The NAT gateway's ErrorPortAllocation CloudWatch metric is non-zero. Its ActiveConnectionCount is high. Flow logs with pkt-dstaddr show one destination dominating.
  • Fix. Reuse connections (HTTP keep-alive, connection pooling). Add secondary IPs to the NAT gateway. Spread traffic across destinations, or reach AWS services through endpoints instead of the NAT.

The 350-second idle reset

  • Symptom. ECONNRESET or "connection reset by peer" on the first request after a quiet period, through a NAT gateway. Often hourly or overnight. Database and message-queue clients are typical victims.
  • Mechanism. The NAT gateway drops idle translations after 350 seconds. When the client next sends on that socket, the NAT gateway answers with a RST. The server never hears about it and keeps its half-open connection until its own timeout.
  • Prove it. Note the idle time before the failing request. On the instance, ss -tio shows the socket's keepalive timer (or lack of one). sysctl net.ipv4.tcp_keepalive_time reads 7200 on a default Linux host.
  • Fix. Enable TCP keepalive with an interval under 350 seconds on the client (or set tcp_keepalive_time lower system-wide). Or set the pool's idle timeout below 350 seconds so it discards connections first.

NACL return-path drop

  • Symptom. TCP connects time out. Security groups look correct. Often begins right after a "hardening" change.
  • Mechanism. A stateless NACL allows the request but not the reply to the client's ephemeral port.
  • Prove it. Flow logs on the server's interface: inbound ACCEPT, reverse five-tuple REJECT. A client-side tcpdump shows only retransmitted SYNs. Reachability Analyzer names the NACL as the blocking component.
  • Fix. Allow 1024–65535 for return traffic in the relevant direction, or go back to allow-all NACLs and keep the policy in security groups.

Connection-tracking exhaustion on busy instances

  • Symptom. A high-connection server — a proxy, a busy API node, a DNS forwarder — starts dropping new connections under load. CPU looks fine. The problem disappears when you scale out.
  • Mechanism. Each instance type has a maximum number of flows its host will track for security groups. Long tracking timeouts (five days for established TCP by default) let dead-but-not-closed flows pile up.
  • Prove it. conntrack_allowance_exceeded growing in ethtool -S.
  • Fix. Use a larger instance type or more instances. Shorten the tracked-connection timeouts on the interface. Where the security posture allows it, make flows untracked: AWS skips tracking for TCP and UDP flows when rules allow all traffic in both directions, which is a design choice to make deliberately, not a reflex.

DNS throttling at 1,024 packets per second

  • Symptom. Intermittent DNS timeouts under load, especially from containers or from apps that resolve a name on every request.
  • Mechanism. Each interface may send 1,024 packets per second to the VPC resolver and other link-local services combined. A Kubernetes node with dozens of pods and no local cache can hit that easily.
  • Prove it. linklocal_allowance_exceeded growing in ethtool -S. Resolver latency spikes in the application's own metrics.
  • Fix. Cache locally — NodeLocal DNSCache in Kubernetes, systemd-resolved or dnsmasq on hosts. Lower ndots so pods do not try five search domains before the real name.

Path MTU black hole across Transit Gateway or VPN

  • Symptom. SSH connects but hangs on large output. HTTP works for small responses and stalls on large ones. Only across TGW, VPN or to on-premises.
  • Mechanism. The instance's 9001-byte packets exceed the path MTU. The ICMP "fragmentation needed" messages are blocked or never sent, so TCP keeps retransmitting the too-big segment.
  • Prove it. ping -M do -s 1418 <host> succeeds and ping -M do -s 8000 <host> fails silently (Linux syntax; on macOS use ping -D -s). tracepath <host> on Linux reports the path MTU.
  • Fix. Allow ICMP type 3 code 4 inbound in security groups. Clamp MSS on the VPN or appliance. Or lower the instance MTU on those interfaces.

Asymmetric routing through an inspection VPC

  • Symptom. Traffic between two VPCs through a central firewall works for some flows and fails for others, apparently at random.
  • Mechanism. Transit Gateway normally keeps traffic in the AZ it arrived from. The request may enter the firewall in AZ a, and the reply — arriving from a VPC attachment in AZ b — reaches the firewall instance in AZ b. A stateful firewall that never saw the SYN drops the reply.
  • Prove it. Firewall logs show the reply rejected as "no session." Flow logs on the two firewall instances each show only one direction of the flow.
  • Fix. Enable appliance mode on the Transit Gateway attachment for the inspection VPC. TGW then pins both directions of a flow to the same AZ for that attachment.

Overlapping CIDRs discovered late

  • Symptom. A peering request fails to create, or a Transit Gateway route silently prefers one attachment over another. Some on-premises addresses become unreachable after a new VPC is attached.
  • Mechanism. Two networks claim the same addresses. Longest prefix match can only send a destination one way.
  • Prove it. List every CIDR in every VPC, on-premises network and VPN client pool, and check them pairwise (section 9's script does this).
  • Fix. For a single service, PrivateLink sidesteps the overlap. For full connectivity, a private NAT gateway can translate one side into a non-overlapping range. The real fix is an organization-wide IP plan, maintained in one place (AWS's IPAM, a spreadsheet, anything that is actually kept up to date).

"The rule is gone but the attacker is still connected"

  • Symptom. You remove an inbound security group rule during an incident. An active session continues.
  • Mechanism. Removing a security group rule does not tear down flows already being tracked.
  • Prove it. Flow logs keep showing ACCEPT for the flow after the rule change.
  • Fix. Add a NACL DENY for the source; NACLs keep no state, so it applies to the next packet. Or isolate the instance by replacing its security groups — be aware that flows already tracked can still persist, so the NACL is the reliable cut.

Deep dive: 2026 context

IPv4 now costs money by itself. Since February 2024, AWS charges for every public IPv4 address, attached or not ($0.005 per hour at the time of writing). That has pushed teams toward fewer public IPs, more load balancers and NAT, and real IPv6 adoption: dual-stack subnets, IPv6-only subnets with DNS64 and NAT64 on the NAT gateway for reaching IPv4-only services, and egress-only internet gateways. Azure has also been retiring the implicit "default outbound access" that used to give VMs internet access without an explicit NAT, so explicit egress design is now the norm on both.

Kubernetes eats addresses. The AWS VPC CNI gives every pod a real VPC IP from the node's subnet. That makes pods first-class citizens for security groups and flow logs. It also exhausts a /24 in an afternoon. The answers are big private subnets (the /19s in section 9's plan), prefix delegation (assigning /28 blocks to nodes), and secondary CIDRs from 100.64.0.0/10 for pods. GKE and AKS have their own versions of the same trade-off. If you take one planning lesson from this module, make the pod subnets bigger than you think.

Service-to-service networking is moving up a layer. VPC Lattice (AWS), Private Service Connect (GCP) and Private Link (Azure) let teams connect services across VPCs and accounts without connecting networks. That reduces the blast radius of a flat, fully-routed network, and it fits zero-trust designs where identity, not IP address, decides access. The VPC underneath does not go away. It becomes plumbing that fewer people touch.

Inspection is an architecture, not a box. Centralized egress and east-west inspection through Gateway Load Balancer (which carries traffic to appliances over GENEVE, UDP 6081) or a managed firewall is now a standard hub pattern. It brings back problems a pure VPC design avoided: asymmetric routing, MTU budgets, and a per-gigabyte cost on every inspected byte.

Multi-cloud is mostly a routing and DNS problem. Connecting AWS, GCP and Azure means BGP over interconnects or VPNs, non-overlapping CIDRs across all three, and a DNS design where each cloud's private zones are resolvable from the others. The concepts in this module transfer cleanly. The quotas, prices and defaults do not, which is the strongest argument for writing them down per provider rather than from memory.

Deep dive: senior interview questions

Q1: There is no ARP broadcast in a VPC, yet ip neigh on an instance shows a MAC for the gateway. Where did it come from, and what follows from that?

The host's virtualization layer (the Nitro card on EC2) intercepts the ARP request and answers it from its own tables. Nothing is broadcast. It follows that Layer 2 tricks don't work: gratuitous ARP cannot move an IP, broadcast discovery finds nothing, and you cannot sniff other instances' traffic in promiscuous mode. Moving an IP means an API call (reassigning a secondary IP or an Elastic IP, or changing a route target). Seeing other traffic means Traffic Mirroring, which sends copies over VXLAN to a target.

Q2: Why can two customers both use 10.0.0.0/16, but you cannot peer two of your own VPCs that both use it?

Isolation between customers is done by the overlay: every packet is encapsulated with the provider's own addresses and tagged with the VPC, so customer addresses never meet. Peering is different. It merges two address spaces into one routing domain, where a route table must decide by destination address alone. If both sides claim 10.0.5.9, longest prefix match has no way to choose. The overlay hides overlap between tenants; it cannot resolve overlap you deliberately join together.

Q3: An application in a private subnet sees intermittent ECONNRESET talking to an external Postgres, roughly once per hour. Walk me through it.

First question: is there a NAT gateway in the path? If yes, check idle time. NAT gateways drop translations after 350 seconds idle and answer the next packet with a RST. Connection pools that keep sockets idle longer will hit it. Linux's default keepalive (7,200 s) does not help. Prove it by correlating failures with socket idle time, or capture on the client and see a RST arriving with no prior FIN. Fix with keepalives under 350 s or a pool idle timeout under 350 s. If there is no NAT gateway, look at the other stateful middleboxes: load balancer idle timeouts and the server's own tcp_keepalive settings.

Q4: You remove the only inbound rule from a security group. Does an established SSH session drop? What would make it drop immediately?

No, generally not. The session is in the security group's connection-tracking table, and replies and further packets for tracked flows are allowed until the flow closes or times out. A NACL DENY on the source applies immediately, because NACLs judge every packet with no memory. The subtlety: if the rule set was fully open in both directions, the flow may have been untracked, and then removing the rule does stop it. That is a good follow-up to raise yourself.

Q5: Design egress for 300 microservices in 40 accounts. What do you worry about?

Resilience: one NAT gateway per AZ, never a single shared one, so an AZ failure stays in its AZ. Cost: per-gigabyte NAT processing dominates, so S3 and DynamoDB get gateway endpoints and heavily-used AWS APIs get interface endpoints. A centralized egress VPC behind Transit Gateway reduces the number of NAT gateways and allows inspection, but adds TGW processing charges on every byte. Run the numbers before assuming centralization is cheaper. Port budget: watch ErrorPortAllocation and add NAT IPs for high-fan-in destinations. Visibility: flow logs with pkt-dstaddr on NAT interfaces, so you can attribute bytes to destinations. IP planning across all 40 accounts, so the hub can route without overlap.

Q6: Flow logs say ACCEPT, but the application says it never received the request. How can both be true?

Flow logs record the decision of the security group and NACL at the interface for a time window, not delivery to a socket. ACCEPT means the filters allowed the packets. The guest can still drop them: a host firewall (iptables, nftables), a full accept queue, a process listening on a different address, or kernel conntrack dropping invalid packets. Also check timing: records are aggregated over 1 or 10 minutes and delivered late, so the ACCEPT may belong to a different attempt. The next step is tcpdump on the instance and ss -ltn to see the listener and its queue.

Q7: Why is a GCP subnet regional when an AWS subnet is zonal, and what does it change?

They are different design choices for the same overlay idea. In AWS, the subnet is the unit you place in an AZ, so AZ-level resilience is expressed by having one subnet per AZ, and anything zonal (NAT gateways, route tables pointing at them) is usually duplicated per AZ. In GCP, a subnet spans every zone in its region, and Cloud NAT is implemented in each VM's host rather than as a zonal gateway, so there is no "NAT gateway in the wrong AZ" problem. What it changes is how you write designs: in AWS, you think in AZ-sized slices of the address space; in GCP, you think in regional ranges and let zones be a placement detail.
