Module 19 — Load Balancing

Networking Mastery Guide · Module 19 of 23

1. Why it matters

Every service you have ever called at scale had a load balancer in front of it. Usually several. A request to a large site might cross an anycast edge, a DNS-based global balancer, a cloud network load balancer, an HTTP proxy, and a sidecar before it reaches a process that does any work. Each one made a choice about where your bytes should go.

Most engineers treat the load balancer as a box that "spreads traffic." That model holds right up until the first incident. Then the questions get specific. Why does one pod get half the traffic after a deploy? Why did the backend log the load balancer's IP instead of the customer's? Why do 0.1% of requests fail with a 502 that nobody can reproduce? Why did removing one cache node wipe out the hit rate on all of them?

Each of those has a precise answer. The answers live in four places: which layer the balancer works at, how it forwards packets, which algorithm it uses to pick a backend, and how it learns that a backend is sick. This module covers all four, then the global and cloud versions you will meet in practice.

It is also one of the most reliable topics in system-design interviews. "Put a load balancer in front" is the most common sentence in those interviews. The follow-up — "which kind, doing what, and how does it fail?" — is where people separate.

2. The mental model

Picture a restaurant host at the door. Guests arrive. The host looks at the floor, picks a table, and walks the guest over. A good host notices that one waiter is drowning and stops seating his section. A good host also stops seating a section whose waiter has gone home sick.

That is the whole job: pick a backend, keep picking well, stop picking dead ones. The analogy is fine for the first ten minutes. Then you need the real thing.

The real thing is a function plus some state. On every new connection (or every new request), the load balancer computes:

backend = choose(flow_or_request, healthy_backends, algorithm_state)

The interesting parts are the arguments.

What it can see. A layer-4 balancer sees IP addresses, ports, and the protocol. That is all. A layer-7 balancer has parsed the HTTP request, so it sees the method, path, host, headers, and cookies. What you can see decides what you can route on.

What state it keeps. A connection table mapping each flow's 5-tuple to the backend it chose, so every later packet of that flow goes to the same place. A backend table with addresses, weights, health status, and counters such as active connections. Algorithm state: a round-robin cursor, or a precomputed hash table.

How the packet physically gets there. The balancer can rewrite the destination address (NAT), open a second connection of its own (proxy), or hand the packet on untouched and let the backend reply directly to the client (direct server return). This one choice decides whether the backend sees the client's IP, whether replies flow back through the balancer, and how much traffic the balancer can carry.

How it learns about health. Active probes it sends on a timer, and passive observation of real traffic: resets, timeouts, 5xx responses.

Hold those four pieces and almost every load-balancing question becomes answerable. The rest of this module fills them in.

3. How it works

L4 vs L7: what each one can see

A layer-4 load balancer decides per connection (per flow, for UDP). It looks at the first packet — a TCP SYN, say — picks a backend, records the choice, and sends every later packet of that 5-tuple the same way. It never reassembles the byte stream. It does not know whether the bytes are HTTP, Postgres, or TLS.

A layer-7 load balancer terminates the client's TCP connection (and usually TLS), reads the request, and decides per request. Two requests on the same client connection can go to two different backends. It opens its own connections to the backends, usually from a pool it keeps warm.

The table hides one important point. An L4 balancer that balances connections is blind to how much work each connection carries. One HTTP/2 or gRPC connection can carry thousands of requests per second for hours. Balance those connections perfectly and the requests can still be badly skewed. That single fact explains a whole class of Kubernetes incidents; section 5 walks through one.

Forwarding modes: NAT, proxy, and direct server return

How the packet reaches the backend matters as much as which backend is chosen. There are three common modes, and they differ in exactly what each hop rewrites.

NAT mode (IPVS calls it "masquerading"). The balancer rewrites the destination address from the virtual IP (VIP) to the chosen backend. The source stays the client's address, so the backend sees the real client IP. The catch: the backend's reply goes to the client's address, and it must pass back through the balancer to have its source rewritten from the backend's address to the VIP. If the reply takes any other path, the client receives a SYN-ACK from an address it never contacted and drops it — the same failure as hairpin NAT in Module 15. In practice the backends' default gateway must be the balancer, and the balancer carries both directions of traffic.

Proxy mode (also "full proxy" or "SNAT mode"). The balancer accepts the client's connection and opens a brand-new one to the backend from its own address. There are two TCP connections with two sets of sequence numbers, two congestion windows, and two sets of timeouts. Every L7 balancer works this way, and many L4 ones do too (HAProxy in mode tcp, AWS NLB for some target types). The backend sees the balancer's address as the client. The real client IP has to travel some other way: an HTTP header for L7, or a PROXY protocol line prepended to the stream for L4. Replies return naturally, because the backend is replying to the balancer.

Direct server return (DSR). The balancer forwards the client's packet without changing its destination IP — it is still addressed to the VIP. There are two ways to get it to the backend. The balancer can rewrite only the destination MAC address; IPVS calls this "direct routing", and it needs the balancer and backend on the same L2 segment. Or it can wrap the packet in an outer IP header (IP-in-IP or GUE), which works across routed networks. The backend has the VIP configured on a loopback interface, so it accepts the packet. It replies from the VIP straight to the client, skipping the balancer entirely.

DSR exists because traffic is asymmetric. A web request is a few hundred bytes. The response can be megabytes. With DSR, the balancer handles only the small inbound half. That is why the largest software L4 balancers — Google's Maglev, Meta's Katran, GitHub's GLB — all use DSR with encapsulation. The cost: the balancer never sees replies, so it cannot do anything that depends on them. No TLS termination, no response-based health signals, no L7 features at all.

Choosing a backend: the algorithms

Round robin. Hand out backends in order: 1, 2, 3, 1, 2, 3. One integer of state. Perfectly fair by count, which is the problem: it assumes every request costs the same and every backend is equally fast. Neither holds in production. Weighted round robin gives a backend with weight 3 three turns per cycle. NGINX uses a "smooth" variant that interleaves the turns (A A B A, not A A A B) so a heavy backend doesn't get bursts.

Random. Pick uniformly at random. Statistically the same as round robin over many requests, with one advantage: many independent balancer instances need no shared state to be fair.

Least connections. Send the new connection to the backend with the fewest active ones. This is the first algorithm that reacts. A slow backend holds its connections longer, its count rises, and it gets fewer new ones. "Least request" is the L7 version, counting outstanding requests rather than connections. The weakness shows up with many balancer instances: each only knows its own counts, and if they all see the same "least loaded" backend at the same moment they all pile onto it. That is the herd effect.

Power of two choices (P2C). Pick two backends at random and send to the less loaded of the two. It sounds like a hack. It is one of the best-understood results in load balancing (Mitzenmacher's work in the 1990s). With purely random placement of n jobs into n bins, the fullest bin grows like log n / log log n. With two choices, it drops to about log log n — an exponential improvement from one extra comparison. P2C also defeats the herd: two balancers rarely draw the same pair. Envoy's LEAST_REQUEST policy is P2C by default, NGINX offers random two least_conn, and HAProxy has balance random(2).

Hashing. Compute a hash of some key — client IP, 5-tuple, a header, a user ID — and map it to a backend. The same key always lands on the same backend, which matters for caches and for any L4 balancer fleet where several balancer nodes must agree without talking to each other. The naive version, hash(key) mod N, has a fatal flaw: change N by one and nearly every key moves. Removing one backend out of ten remaps about 90% of keys. For a cache tier, that is a full cold start.

Consistent hashing fixes that. The ring hash (Karger et al., 1997) places each backend at many points ("virtual nodes") on a circle of hash values. A key goes to the next backend clockwise from its own hash. Remove a backend and only the keys it owned move; everything else stays put. Maglev hashing (Google, NSDI 2016) builds a lookup table — 65,537 slots is the common size, a prime — where each backend fills slots in its own pseudo-random order until the table is full. Lookup is one array index, the load spread is near-perfect, and removing a backend moves only slightly more keys than the theoretical minimum. Rendezvous hashing (highest random weight) scores each backend as hash(key, backend) and picks the highest score; it is simple and also minimally disruptive, at O(N) per lookup.

Consistent hashing has a weakness the module's simulation makes vivid: it balances keys, not load. One hot key — a celebrity's profile, a big tenant — sends all its traffic to one backend no matter how good the hash is. Consistent hashing with bounded loads (Mirrokni, Thorup and Zadimoghaddam, 2017) caps each backend at c × the average load (c = 1.25 is a typical choice). When a key's home is over the cap, the key walks clockwise to the next backend with room. HAProxy exposes this as hash-balance-factor.

Health checks and outlier detection

A balancer that keeps sending traffic to a dead backend is worse than no balancer. There are two ways to find out a backend is sick.

Active health checks. The balancer probes each backend on a timer: a TCP connect, an HTTP GET /healthz expecting a 2xx, or a gRPC grpc.health.v1.Health/Check. A backend is marked down after fall consecutive failures and back up after rise consecutive successes. The thresholds are there for hysteresis, so one dropped probe doesn't flap a backend in and out. HAProxy's defaults are a 2 s interval, rise 2, fall 3. AWS ALB target groups default to a 30 s interval, 5 s timeout, 5 healthy and 2 unhealthy checks. These defaults vary by product and version, so check yours.

Passive health checks / outlier detection. The balancer watches real traffic. If a backend returns five 5xx responses in a row (Envoy's default consecutive_5xx), it is ejected for a base time (30 s by default), and the ejection time grows each time the same host is ejected again. Passive detection reacts in milliseconds under load, needs no extra probe traffic, and catches failures a /healthz endpoint can't see. It also needs traffic to work: an idle backend never fails a request.

Two safety valves matter more than any threshold. Max ejection percent (Envoy defaults to 10%) stops outlier detection from ejecting most of the fleet when the real problem is downstream. Panic mode (Envoy's threshold is 50% healthy by default) makes the balancer ignore health status and spread across all hosts once too few are healthy. The reasoning: if half your fleet looks dead, the health check is more likely wrong than the fleet. Concentrating all traffic on the "healthy" half would kill it too.

Connection draining

Removing a backend cleanly is a two-step move. First, stop sending it new connections or requests. Second, let existing ones finish, up to a deadline, and only then remove it. AWS calls this the deregistration delay (300 s by default); others call it draining or graceful shutdown.

L4 and L7 drain differently. An L4 balancer can only stop assigning new flows; existing flows run until they close or the deadline cuts them off. An L7 balancer can do better, because it can tell the client to go elsewhere. In HTTP/1.1 it sends Connection: close on the next response. In HTTP/2 it sends a GOAWAY frame naming the last stream it will process, and the client opens a new connection for the rest.

In Kubernetes there is a race worth knowing by heart. When a pod is deleted, two things happen in parallel: the kubelet sends the container SIGTERM, and the endpoint removal propagates to every kube-proxy, ingress controller, and cloud balancer. Propagation takes time — often a few seconds. A process that exits on SIGTERM immediately will refuse connections that balancers are still sending it. The standard fix is a preStop hook that sleeps for a few seconds before the shutdown begins, plus an app that stops accepting new work and finishes in-flight requests within terminationGracePeriodSeconds (30 s by default).

Sticky sessions

Session affinity sends the same client to the same backend. It exists because some applications keep per-user state in process memory: a shopping cart, a WebSocket subscription, a server-side session.

There are three ways to do it. Source-IP affinity hashes the client IP. It is available at L4, and it breaks badly behind carrier-grade NAT, where thousands of users share one address and all land on one backend. Cookie affinity is L7: the balancer sets a cookie naming the backend (AWS ALB's is AWSALB, duration-based stickiness defaults to one day) or honours an application cookie. Hash on a header or user ID gives affinity without a cookie, and with consistent hashing it survives scaling events reasonably well.

Stickiness costs you three things. Load becomes uneven, because a heavy user stays on one host. Draining gets slow, because sessions pin clients to the host you want to remove. And when a sticky backend dies, its users lose their state anyway. Treat affinity as a performance optimisation (warm caches) rather than a correctness mechanism. State that must survive belongs in a shared store.

TLS: termination, passthrough, re-encryption

Termination. The balancer holds the certificate and private key, completes the TLS handshake, and sees plaintext. This is required for any L7 routing on HTTPS, and it centralises certificate management. Traffic to the backend is then plain HTTP — fine inside a trusted network, not fine under zero trust.

Re-encryption (also "TLS bridging"). Terminate, inspect, then open a new TLS connection to the backend. You keep L7 features and encrypt every hop. The cost is a second handshake (amortised by connection pooling) and the backend's own certificate to manage. Service meshes do this with mutual TLS by default.

Passthrough. The balancer never decrypts. It forwards the TCP stream as-is, so the backend holds the key and does the handshake. The balancer can still peek at one thing: the SNI (Server Name Indication) field in the unencrypted ClientHello, which names the hostname the client wants. HAProxy does this with tcp-request inspect-delay and req.ssl_sni. That gives you hostname-based routing without holding any keys. Encrypted Client Hello (ECH) hides the real SNI inside an encrypted extension, so as ECH spreads, SNI-based passthrough routing only sees the outer, public name.

Global load balancing: DNS and anycast

Everything so far balances inside one site. Spreading users across regions uses two different tools.

DNS-based global load balancing. The authoritative DNS server answers differently depending on who asks: the nearest healthy region's address, weighted answers for a migration, or only the regions that pass health checks. It is cheap and works with any protocol. It is also coarse in two ways. The server sees the recursive resolver's address, not the user's, so "nearest" means nearest to the resolver. EDNS Client Subnet (RFC 7871) lets resolvers pass a truncated client prefix to fix that, though not every resolver sends it. And failover is only as fast as caches expire. A 60 s TTL means most clients move within a minute or two. Some clients and middleboxes hold records longer, and long-lived connections never re-resolve at all.

Anycast. Announce the same IP prefix over BGP from many sites. Each user's packets follow BGP to the topologically nearest announcing site (Module 13 covers this for CDNs; RFC 4786 is the operational guide). Failover is a BGP withdrawal, which converges in seconds rather than waiting on DNS caches. The risk is that a routing change can move a flow from one site to another mid-connection. The new site has no state for that TCP connection and resets it. For short connections this almost never matters. For long-lived ones it can, and it is why anycast front ends pair with stateless or consistently hashed L4 tiers.

Large providers combine both: anycast to reach the nearest edge, then an L4 tier and an L7 tier inside it, with DNS steering for whole-region traffic moves.

Cloud load balancers

Cloud balancers are the same machinery with a product wrapper. The behaviours that bite are worth knowing by name. The examples use AWS terms because they are the most common; GCP and Azure have equivalents.

Network Load Balancer (NLB style): L4, TCP/UDP/TLS. It picks a target per flow with a hash over the 5-tuple, so a flow stays on one target. It preserves the client IP by default for instance targets, and supports PROXY protocol v2 when it doesn't. It gets one static IP per availability zone, which matters for allow-lists. The TCP idle timeout defaults to 350 s, after which the flow entry is silently dropped (newer NLBs let you configure it). Cross-zone balancing is off by default, so each zone's balancer node only sends to targets in its own zone. A zone with 2 targets and a zone with 8 targets each get half the traffic, and the 2 targets in the small zone carry four times the per-target load of the others.

Application Load Balancer (ALB style): L7 full proxy. HTTP/1.1, HTTP/2, gRPC, and WebSockets; routing on host, path, header, and query string. It adds X-Forwarded-For, X-Forwarded-Proto, and X-Forwarded-Port. The idle timeout defaults to 60 s. Its node IPs change as it scales, so you point DNS at its name and never pin its addresses. Cross-zone balancing is on.

Google Cloud's external passthrough network load balancer is built on Maglev; its global application load balancer runs on Google Front Ends behind a single anycast IP. The pattern is the same everywhere: an L4 layer that scales by hashing, and an L7 layer that terminates.

Kubernetes Services are an L4 balancer distributed onto every node. In iptables mode, kube-proxy writes a chain per Service that picks an endpoint with the statistic match in random mode: the first rule matches with probability 1/n, the next with 1/(n−1), and so on, which makes the overall choice uniform. IPVS mode uses real IPVS schedulers (rr, lc, sh, mh and others). Either way it is DNAT in the kernel, decided per connection, at connect time. One setting decides the client IP story: externalTrafficPolicy: Cluster (the default) lets any node forward to any pod, which SNATs the packet and loses the client IP. Local only sends to pods on the receiving node, which keeps the client IP but can unbalance traffic when pods are unevenly spread across nodes.

4. The exact structure

The connection table entry

Every stateful L4 balancer keeps a table keyed on the flow. On Linux IPVS you can read it directly:

$ sudo ipvsadm -Lnc          # run on a Linux IPVS director — your output will differ
IPVS connection entries
pro expire state       source               virtual            destination
TCP 14:58  ESTABLISHED 198.51.100.23:51514  203.0.113.10:80    10.0.2.41:80
TCP 01:52  FIN_WAIT    198.51.100.77:60212  203.0.113.10:80    10.0.2.42:80
TCP 00:57  SYN_RECV    192.0.2.140:44310    203.0.113.10:80    10.0.2.43:80

Each row is the decision, remembered: this 5-tuple goes to that backend, and the entry expires after a state-dependent idle timer. IPVS's defaults are 900 s for an established TCP flow, 120 s after a FIN, and 300 s for UDP (ipvsadm -L --timeout shows yours). Those timers are why expire 14:58 appears two seconds after the last packet. The state column is the balancer's guess at the TCP state, built from the flags it has seen. In DSR mode it never sees the backend's packets, so the guess is based on one direction only.

The service and backend table sits beside it:

Prot LocalAddress:Port Scheduler Flags
  -> RemoteAddress:Port           Forward Weight ActiveConn InActConn
TCP  203.0.113.10:80 mh
  -> 10.0.2.41:80                 Tunnel  1      1834       2210

mh is the Maglev-hashing scheduler (in the kernel since 4.18). Tunnel is IP-in-IP DSR; the other values are Masq (NAT) and Route (DSR by MAC rewrite). ActiveConn counts established flows and InActConn counts everything else, mostly TIME_WAIT and FIN states. The third backend has weight 0: it is draining. It gets no new flows while its 412 existing ones finish.

The backend health state machine

Each backend has a small state machine driven by probe results:

           fail (count < fall)         ok (count < rise)
             ┌──────────┐               ┌──────────┐
             ▼          │               ▼          │
  ┌──────────────┐  fall consecutive  ┌──────────────┐
  │     UP       │ ─────────────────▶ │    DOWN      │
  │ gets traffic │ ◀───────────────── │  no traffic  │
  └──────────────┘  rise consecutive  └──────────────┘
         │                ok                  ▲
         │ admin drain / weight 0             │
         ▼                                    │
  ┌──────────────┐  deadline or last conn  ──┘
  │  DRAINING    │  closes → removed
  │ old flows    │
  │ only         │
  └──────────────┘

Detection time is roughly interval × fall + timeout. With HAProxy defaults (2 s, fall 3) that is about 6 s. With ALB defaults (30 s, 2 unhealthy) it is about a minute. Recovery takes interval × rise: 4 s for HAProxy, 150 s for ALB. Those defaults suit very different worlds, and you should set them deliberately.

Carrying the client address: headers and PROXY protocol

A full proxy hides the client's address from the backend. Three formats carry it across.

X-Forwarded-For is a de facto HTTP header. Each proxy appends the address it received the connection from:

X-Forwarded-For: 198.51.100.23, 10.0.1.17
                 └ client as seen   └ added by the second proxy (the first proxy's address)
                   by the first proxy

The leftmost value is whatever the client sent, and a client can send anything. Trust only the entries added by proxies you control, counting from the right.

Forwarded (RFC 7239) is the standardised version: Forwarded: for=198.51.100.23;proto=https;by=10.0.1.17. It is cleaner and less widely used.

PROXY protocol (HAProxy's specification) does the same job for L4 proxies, where there are no headers. The proxy writes one preamble before the client's first byte. Version 1 is a single text line of at most 107 bytes:

PROXY TCP4 198.51.100.23 203.0.113.10 51514 443\r\n
      │    │             │            │     └ destination port
      │    │             │            └ source port
      │    │             └ destination address (the VIP)
      │    └ source address (the real client)
      └ TCP4, TCP6 or UNKNOWN

Version 2 is binary. It starts with a fixed 12-byte signature (0D 0A 0D 0A 00 0D 0A 51 55 49 54 0A), then a version/command byte, an address-family byte, a 2-byte length, the addresses, and optional TLVs (AWS uses one to carry the VPC endpoint ID). The backend must be configured to expect it. A server that isn't will treat PROXY TCP4 … as the start of the request and fail it. A server that requires it will reject health checks that don't send it.

The Maglev lookup table

The Maglev table is an array of M slots (M prime, 65,537 by default in IPVS and Envoy). To build it, each backend gets two hashes of its name: an offset in [0, M) and a skip in [1, M). Its preference list is (offset + j × skip) mod M for j = 0, 1, 2…; because M is prime, that visits every slot exactly once. Backends take turns. Each claims the next slot on its own list that is still empty, until all M slots are full. Each backend ends up with ⌊M/N⌋ or ⌈M/N⌉ slots.

Lookup is table[hash(5-tuple) mod M]. When a backend leaves, the table is rebuilt from the remaining backends. Most slots keep their owner, because each surviving backend walks the same preference list as before. The paper recommends M larger than 100 × N to keep load imbalance under about 1%.

5. A realistic example

A team runs a gRPC service on Kubernetes: 6 pods behind a plain ClusterIP Service, called by 40 client pods. Each client opens one HTTP/2 connection to the Service at startup and multiplexes every call onto it. That is gRPC's default behaviour, and it is efficient.

The service is scaled from 6 to 12 pods for a launch. The dashboards are odd. Six pods are at 85% CPU. The six new ones are at 2%. Latency is up. Nothing is unhealthy.

Here is the mechanism. kube-proxy balances connections, and it chose a backend once — when each client connected, back when there were only 6 pods. The 40 connections are still open, because HTTP/2 connections live for hours. No new connections means no new decisions, so the 6 new pods only ever see the occasional reconnect.

You prove it on one of the busy pods by counting established connections from clients:

$ kubectl exec orders-7d9c-abcde -- ss -tn state established '( sport = :50051 )' | wc -l
# run in your cluster — your output will differ
8

The new pods show 0 or 1. The load is per request, but the balancing was per connection.

There are three fixes, from least to most invasive:

  • Cap connection age on the server. gRPC servers support MAX_CONNECTION_AGE (for example, 5 minutes plus a grace period). The server sends GOAWAY when the age is reached, the client reconnects, and kube-proxy makes a fresh choice. Load converges within one age period.
  • Balance per request in the client. gRPC's client-side round_robin policy, pointed at a headless Service (which returns every pod IP in DNS), opens a connection to each pod and spreads calls across them. Proxyless gRPC with xDS takes this further.
  • Put an L7 balancer in the path. A mesh sidecar or an Envoy-based gateway terminates HTTP/2 and balances each stream with least-request P2C.

The team ships the first fix the same day and the second the next sprint. The lesson they wrote down: an L4 balancer cannot balance work that it never sees as separate connections.

6. Misconceptions & common mistakes

"Round robin is fair." It is fair by request count, which is not what you care about. One slow backend gets exactly the same share as a fast one, and its queue grows until requests time out. The simulation in section 9 shows round robin pushing a backend that is three times slower into unbounded queueing at 75% overall load.

"Least connections is always best." It is good in a single balancer. In a fleet of balancers it herds: every instance sees the same idle backend and sends to it at once. And when a new or recovered backend joins with zero connections, least-connections floods it while its caches and JIT are cold. Use slow start (ramp its weight over 30–60 s) or P2C.

"The balancer sees the client IP." Only in NAT or DSR mode. A full proxy — every L7 balancer and many L4 ones — replaces it with its own address. You get it back from X-Forwarded-For, Forwarded, or PROXY protocol, and only if you configure the backend to read them and trust the right hop.

"Health check passing means the service works." A /healthz that returns 200 from a process that can't reach its database tells the balancer nothing useful. The opposite mistake is just as bad. A deep health check that fails whenever a shared dependency is slow marks every backend down at once, and your outage gets larger. Check what the backend itself controls. Let outlier detection catch the rest.

"Consistent hashing balances load." It balances keys. A hot key still lands on one backend. Use bounded loads, or split hot keys deliberately.

"Sticky sessions keep user state safe." They keep it convenient. When the backend dies or is drained, the state goes with it.

"DNS failover is instant." It is bounded below by TTLs and above by whatever clients and resolvers actually do. Long-lived connections never re-resolve.

"The cloud balancer has infinite capacity." Managed balancers scale by adding nodes, and that takes minutes. A sudden 10× spike can see errors while it happens. Some providers offer pre-warming or capacity reservations for exactly this reason.

7. Interview Q&A

Q1: What's the difference between an L4 and an L7 load balancer, and when would you choose each?

An L4 balancer decides per connection using addresses, ports and protocol. It never parses the payload, so it is fast, protocol-agnostic, and can preserve the client IP. An L7 balancer terminates the connection, parses HTTP, and decides per request on path, host, headers or cookies. Choose L4 for raw throughput, non-HTTP protocols, TLS passthrough, or as the scalable first tier. Choose L7 when you need content routing, per-request balancing of multiplexed protocols like HTTP/2 and gRPC, retries, or header manipulation. Large systems use both: L4 in front, scaling the L7 fleet behind it.

Q2: How does direct server return work, and why would you use it?

The balancer forwards the client's packet with its destination still set to the VIP, either by rewriting only the MAC address or by encapsulating it in an outer IP header. The backend has the VIP on a loopback interface, accepts the packet, and replies from the VIP directly to the client. The balancer only carries the inbound direction. Responses are usually far larger than requests, so this multiplies the balancer's capacity. The cost is that the balancer never sees replies, so no TLS termination or L7 features.

Q3: Why do we need consistent hashing? Why not hash mod N?

With hash mod N, changing N by one moves almost every key: removing one of ten backends moves about 90% of keys. For caches or sharded state that means a near-total miss storm. Consistent hashing (ring, Maglev, rendezvous) moves only the keys that belonged to the changed backend, about 1/N of them.

Q4: What is the power of two choices?

Pick two backends at random and send to the less loaded one. It needs no global state, avoids the herding that pure least-connections suffers across many balancers, and cuts the worst-case load dramatically compared with random choice. Envoy's least-request balancer uses it by default.

Q5: A user reports that their session keeps getting lost. You use sticky sessions. What could be wrong?

Several things. The sticky backend was drained or failed, so the client was re-routed. Cookie stickiness can break if the cookie isn't returned (cross-site cookie rules, a client that drops cookies). Source-IP stickiness breaks when the client's IP changes, for example on mobile networks or behind rotating carrier-grade NAT. And an L4 tier in front with no affinity can send the client to a different L7 node with different sticky state. The real fix is to move session state to a shared store and keep stickiness only for cache warmth.

"""What does the backend see behind an L4 proxy vs an L7 proxy? Python 3.13 stdlib, localhost only."""
import asyncio

BACKEND, L4, L4_PROXYPROTO, L7 = 9001, 9101, 9102, 9103


async def backend(reader, writer):
    # Reports what it saw: the TCP peer, plus whatever bytes arrived first.
    peer = writer.get_extra_info("peername")
    head = await reader.readuntil(b"\r\n\r\n")
    lines = head.decode().split("\r\n")
    report = [f"TCP peer      : {peer[0]}:{peer[1]}"]
    if lines[0].startswith("PROXY "):
        report.append(f"PROXY v1 line : {lines[0]}")
        lines = lines[1:]
    report.append(f"request line  : {lines[0]}")
    report += [f"header        : {l}" for l in lines[1:] if l.lower().startswith(("x-forwarded", "host"))]
    body = "\n".join(report).encode()
    writer.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n" % len(body) + body)
    await writer.drain(); writer.close()


async def pipe(r, w):
    try:
        while data := await r.read(65536):
            w.write(data); await w.drain()
    finally:
        w.close()


async def l4_proxy(reader, writer, proxy_protocol=False):
    # Layer 4: opens its own TCP connection to the backend and copies bytes blindly.
    up_r, up_w = await asyncio.open_connection("127.0.0.1", BACKEND)
    if proxy_protocol:   # HAProxy PROXY protocol v1: one text line before the client's bytes
        c, s = writer.get_extra_info("peername"), writer.get_extra_info("sockname")
        up_w.write(f"PROXY TCP4 {c[0]} {s[0]} {c[1]} {s[1]}\r\n".encode())
    await asyncio.gather(pipe(reader, up_w), pipe(up_r, writer))


async def l7_proxy(reader, writer):
    # Layer 7: parses the HTTP request, can route on it, and rewrites headers.
    head = await reader.readuntil(b"\r\n\r\n")
    client = writer.get_extra_info("peername")[0]
    lines = head.decode().split("\r\n")[:-2]
    lines.append(f"X-Forwarded-For: {client}")
    lines.append("X-Forwarded-Proto: http")
    up_r, up_w = await asyncio.open_connection("127.0.0.1", BACKEND)
    up_w.write(("\r\n".join(lines) + "\r\n\r\n").encode())
    await asyncio.gather(pipe(reader, up_w), pipe(up_r, writer))


async def client(port, label):
    r, w = await asyncio.open_connection("127.0.0.1", port)
    mine = w.get_extra_info("sockname")
    w.write(b"GET /api/cart HTTP/1.1\r\nHost: shop.example\r\nConnection: close\r\n\r\n")
    await w.drain()
    resp = (await r.read()).decode().split("\r\n\r\n", 1)[1]
    print(f"--- {label} (client is {mine[0]}:{mine[1]})\n{resp}\n")
    w.close()


async def main():
    servers = [
        await asyncio.start_server(backend, "127.0.0.1", BACKEND),
        await asyncio.start_server(l4_proxy, "127.0.0.1", L4),
        await asyncio.start_server(lambda r, w: l4_proxy(r, w, True), "127.0.0.1", L4_PROXYPROTO),
        await asyncio.start_server(l7_proxy, "127.0.0.1", L7),
    ]
    await client(BACKEND, "direct to backend")
    await client(L4, "through L4 proxy")
    await client(L4_PROXYPROTO, "through L4 proxy + PROXY protocol")
    await client(L7, "through L7 proxy")
    for s in servers:
        s.close()

asyncio.run(main())

9. Code: comparing algorithms under skewed load

This simulation puts six balancing policies (plus one fix) against the same workload, built to look like production rather than a textbook:

  • 10 backends with 4 workers each and a FIFO queue. Backend b3 runs 3× slower than the rest — a noisy neighbour, a bad disk, an older instance type.
  • Service times are lognormal: median 10 ms, mean about 20.5 ms, with a long tail.
  • Requests come from 50,000 users with Zipf-skewed popularity (exponent 1.1). The hottest user sends 13.9% of all requests; the top ten send 37%.
  • Arrivals are Poisson at 75% of total capacity. 200,000 requests, fixed seed, deterministic.

Least-connections here has perfect, instant knowledge of in-flight counts. That is the best case. P2C only looks at two random backends. The hash policies key on the user ID.

code/m19/lb_sim.py:

"""Compare load-balancing algorithms under skewed load. Python 3.13 stdlib only.

Ten backends, one of them three times slower (a noisy neighbour).
Request service times are heavy-tailed (most are fast, a few are huge).
Each backend runs 4 workers with a FIFO queue. Offered load is ~75% of capacity.
"""
import hashlib
import heapq
import random
import statistics
from bisect import bisect

N_BACKENDS = 10
WORKERS = 4
SLOW = 3                 # backend index that runs 3x slower
N_REQ = 200_000
SEED = 7


def h64(s: str, salt: str = "") -> int:
    return int.from_bytes(hashlib.blake2b((salt + s).encode(), digest_size=8).digest(), "big")


class Backend:
    def __init__(self, idx: int):
        self.idx = idx
        self.speed = 1 / 3 if idx == SLOW else 1.0
        self.free = [0.0] * WORKERS          # heap: when each worker frees up
        self.done = []                      # heap: finish times of accepted requests
        self.served = 0

    def inflight(self, now: float) -> int:
        while self.done and self.done[0] <= now:
            heapq.heappop(self.done)
        return len(self.done)

    def accept(self, now: float, work: float) -> float:
        start = max(now, heapq.heappop(self.free))
        finish = start + work / self.speed
        heapq.heappush(self.free, finish)
        heapq.heappush(self.done, finish)
        self.served += 1
        return finish - now


# ---------- hashing tables ----------
def build_ring(names, vnodes=100):
    pts = sorted((h64(f"{n}#{v}"), n) for n in names for v in range(vnodes))
    return [p for p, _ in pts], [n for _, n in pts]


def ring_lookup(ring, key):
    keys, owners = ring
    return owners[bisect(keys, h64(key)) % len(keys)]


def build_maglev(names, m=65537):
    perms = []
    for n in names:
        offset = h64(n, "off") % m
        skip = h64(n, "skip") % (m - 1) + 1
        perms.append((offset, skip))
    table = [None] * m
    nxt = [0] * len(names)
    filled = 0
    while True:
        for i, n in enumerate(names):
            offset, skip = perms[i]
            c = (offset + nxt[i] * skip) % m
            while table[c] is not None:
                nxt[i] += 1
                c = (offset + nxt[i] * skip) % m
            table[c] = n
            nxt[i] += 1
            filled += 1
            if filled == m:
                return table


def maglev_lookup(table, key):
    return table[h64(key) % len(table)]


# ---------- workload ----------
def workload(rng):
    # Lognormal service times (median 10 ms, long tail) at ~75% utilisation.
    mean_work = 10 * (2.718281828 ** (1.2 ** 2 / 2))       # mean of lognormal(ln10, 1.2)
    capacity = WORKERS * (N_BACKENDS - 1 + 1 / 3) / mean_work   # req per ms
    rate = 0.75 * capacity
    # Zipf-ish users: user k has weight 1/k^1.1 over 50,000 users
    users = 50_000
    weights = [1 / (k ** 1.1) for k in range(1, users + 1)]
    user_ids = rng.choices(range(users), weights=weights, k=N_REQ)
    t = 0.0
    for i in range(N_REQ):
        t += rng.expovariate(rate)
        yield t, rng.lognormvariate(2.302585, 1.2), f"user-{user_ids[i]}"


def run(policy, seed=SEED):
    rng = random.Random(seed)
    pick_rng = random.Random(seed + 1)
    backends = [Backend(i) for i in range(N_BACKENDS)]
    names = [f"b{i}" for i in range(N_BACKENDS)]
    by_name = dict(zip(names, backends))
    ring = build_ring(names)
    maglev = build_maglev(names)
    rr = 0
    lat = []
    for now, work, key in workload(rng):
        if policy == "round-robin":
            b = backends[rr % N_BACKENDS]; rr += 1
        elif policy == "random":
            b = pick_rng.choice(backends)
        elif policy == "least-conn":
            b = min(backends, key=lambda x: (x.inflight(now), pick_rng.random()))
        elif policy == "p2c":
            a, c = pick_rng.sample(backends, 2)
            b = a if a.inflight(now) <= c.inflight(now) else c
        elif policy == "ring-hash":
            b = by_name[ring_lookup(ring, key)]
        elif policy == "ring-bounded":
            # Consistent hashing with bounded loads (Mirrokni et al., 2017), c = 1.25:
            # walk clockwise past any backend already above 1.25x the average in-flight.
            total = sum(x.inflight(now) for x in backends) + 1
            cap = -(-1.25 * total // N_BACKENDS)
            keys, owners = ring
            i = bisect(keys, h64(key))
            while True:
                b = by_name[owners[i % len(keys)]]
                if b.inflight(now) < cap:
                    break
                i += 1
        elif policy == "maglev":
            b = by_name[maglev_lookup(maglev, key)]
        lat.append(b.accept(now, work))
    lat.sort()
    q = lambda p: lat[int(p * len(lat)) - 1]
    share = [x.served / N_REQ * 100 for x in backends]
    return q(0.50), q(0.99), q(0.999), share[SLOW], max(share)


def remap_fraction():
    names = [f"b{i}" for i in range(N_BACKENDS)]
    fewer = [n for n in names if n != "b3"]
    keys = [f"user-{k}" for k in range(20_000)]
    mod = lambda ns, k: ns[h64(k) % len(ns)]
    r1, r2 = build_ring(names), build_ring(fewer)
    m1, m2 = build_maglev(names), build_maglev(fewer)
    res = {}
    for label, f in (("hash mod N", lambda: [mod(names, k) != mod(fewer, k) for k in keys]),
                     ("ring-hash", lambda: [ring_lookup(r1, k) != ring_lookup(r2, k) for k in keys]),
                     ("maglev", lambda: [maglev_lookup(m1, k) != maglev_lookup(m2, k) for k in keys])):
        res[label] = sum(f()) / len(keys) * 100
    # Spread of the key space before removal
    ring_share = [sum(ring_lookup(r1, k) == n for k in keys) / len(keys) * 100 for n in names]
    mag_share = [m1.count(n) / len(m1) * 100 for n in names]
    return res, ring_share, mag_share


if __name__ == "__main__":
    print(f"{N_BACKENDS} backends x {WORKERS} workers, b{SLOW} is 3x slower, "
          f"{N_REQ:,} requests, ~75% load\n")
    print(f"{'policy':<12} {'p50 ms':>8} {'p99 ms':>9} {'p99.9 ms':>10} "
          f"{'slow b3 %':>10} {'busiest %':>10}")
    for p in ("round-robin", "random", "least-conn", "p2c", "ring-hash", "ring-bounded", "maglev"):
        p50, p99, p999, slow, top = run(p)
        print(f"{p:<12} {p50:>8.1f} {p99:>9.1f} {p999:>10.1f} {slow:>10.1f} {top:>10.1f}")
    res, ring_share, mag_share = remap_fraction()
    print("\nRemove backend b3: share of 20,000 keys that move to a different backend")
    for k, v in res.items():
        print(f"  {k:<11} {v:5.1f}%   (ideal: {100 / N_BACKENDS:.1f}%)")
    print("\nKey-space share per backend before removal (min / max %)")
    print(f"  ring-hash   {min(ring_share):5.2f} / {max(ring_share):5.2f}   (100 vnodes each)")
    print(f"  maglev      {min(mag_share):5.2f} / {max(mag_share):5.2f}   (table size 65537)")

Deep dive: what the box diagram hid

The sections above describe load balancing as choices: which layer, which mode, which algorithm. Under them sits a machine with real limits. A balancer is a packet processor with a flow table that can fill, a proxy with a finite set of source ports, a set of timers that must agree with the timers on both sides of it, and a fleet of nodes that must reach the same answer without talking. The rest of this module is about that machine.

Deep dive: the real mental model

A production L4 tier is not one box. It is several identical nodes behind a router, all announcing the same VIP.

Follow one packet. The edge router has the VIP as a /32 route learned over BGP from every balancer node, so it has several equal-cost next hops. It picks one with an ECMP hash over the packet's 5-tuple. Every packet of the flow hashes the same way and reaches the same node.

On that node, the packet hits the data path. At Meta and in Cilium it is XDP, running in the NIC driver before the kernel allocates a socket buffer; in IPVS it is a netfilter hook. The node hashes the 5-tuple and looks it up in its connection table. On a hit, it uses the recorded backend. On a miss — a new flow — it looks up the Maglev table, records the result, and forwards. Forwarding means building a new outer IP header (balancer → backend) around the untouched original packet. The backend's kernel decapsulates it, delivers the inner packet (client → VIP) to the socket listening on the VIP, and replies from the VIP straight to the client.

Now the part the box diagram hid. Why keep a connection table at all, if Maglev already gives a deterministic answer? Because the backend set changes. When a backend is added, a few percent of Maglev slots change owner. Without the table, established flows whose slot moved would be sent to a backend that has never seen them. That backend answers with a RST. The connection table pins existing flows to their original backend; only new flows follow the new table.

And why use Maglev at all, if there is a table? Because the ECMP hash can change too. Add or remove a balancer node and the router reshuffles some flows to different nodes. The new node has no table entry for them. If every node used round robin, the new node would pick an arbitrary backend and break the connection. With Maglev, every node computes the same answer from the same backend list. A flow that lands on a new node is usually sent to the same backend it was already using. The connection table handles backend churn; consistent hashing handles balancer churn. You need both, and neither one alone is enough.

The L7 tier behind it is a different machine. Each proxy node owns sockets: a listening socket, one accepted socket per client connection, and a pool of upstream sockets per backend. Its state is per connection and per request: TLS session state, HTTP/2 stream tables, request buffers, retry budgets, and per-backend counters (active requests, recent errors for outlier detection). The proxy's health view is usually pushed to it by a control plane (xDS for Envoy), merged with what the proxy observes itself.

  • Two handshakes, two sequence spaces. The client's ISN is 3954022801; the proxy's ISN toward the backend is 702114583. Nothing in one connection's numbering relates to the other. A retransmission on one leg is invisible on the other.
  • Different MSS on each leg. The client leg uses 1460 (internet path, 1500 MTU). The backend leg uses 8961, because AWS VPCs run a 9001-byte MTU inside the VPC. The proxy re-segments the stream. This is why a full proxy hides path-MTU problems on one side from the other side.
  • The request grew from 83 to 162 bytes. The proxy added X-Forwarded-For: 198.51.100.23, X-Forwarded-Proto: http and X-Forwarded-Port: 80 (79 bytes with their CRLFs). The backend logs 10.0.1.17 as its TCP peer.
  • RTTs are separate. The client handshake took 27 ms (104512 → 131877, internet latency). The backend handshake took 0.34 ms (in-region). The backend spent 8.6 ms on the request (132431 → 141006). A proxy's timing logs that separate "upstream connect", "upstream response" and "total" give you exactly this split.
  • The backend connection was new only because the pool was cold. On a warm proxy, the request would go out on an existing pooled connection and the backend leg would have no SYN at all.

DSR with IP-in-IP: the packet the backend receives

Now the same client connecting through an L4 DSR balancer at 10.0.0.5, which encapsulates to backend 10.0.2.41. VIP 203.0.113.10 is configured on the backend's loopback. Captured on the backend with -v (checksum fields trimmed):

# tcpdump -nn -v -i eth0 'ip proto 4 or host 198.51.100.23'
10:15:40.200118 IP (tos 0x0, ttl 63, id 0, offset 0, flags [DF], proto IPIP (4), length 80)
    10.0.0.5 > 10.0.2.41: IP (tos 0x0, ttl 52, id 0, offset 0, flags [DF], proto TCP (6), length 60)
    198.51.100.23.51514 > 203.0.113.10.80: Flags [S], seq 3954022801, win 64240, options [mss 1460,sackOK,TS val 1840213 ecr 0,nop,wscale 7], length 0 (ipip-proto-4)
10:15:40.200171 IP (tos 0x0, ttl 64, id 0, offset 0, flags [DF], proto TCP (6), length 60)
    203.0.113.10.80 > 198.51.100.23.51514: Flags [S.], seq 2271019934, ack 3954022802, win 65160, options [mss 1440,sackOK,TS val 99120411 ecr 1840213,nop,wscale 7], length 0

Read it from the outside in:

  • Outer header: 10.0.0.5 > 10.0.2.41, protocol 4 (IPIP), length 80. That is the inner 60-byte packet plus a 20-byte outer IPv4 header. TTL 63: the balancer sent it with 64 and one router hop decremented it.
  • Inner header: exactly what the client sent. Source is the client, destination is the VIP, TTL 52 from the client's own hops. The balancer did not touch it. That is why the backend's socket sees the real client address with no headers or PROXY protocol needed.
  • The reply is not encapsulated. It goes from 203.0.113.10 (the VIP, sourced from the loopback) straight to the client via the backend's normal default route. The balancer never sees it.
  • The SYN-ACK advertises MSS 1440, not 1460. That is deliberate, and it is the most important line here. Every client segment will grow by 20 bytes of encapsulation on the way in. If the client sent 1460-byte segments (1500-byte packets), the balancer would produce 1520-byte packets on a 1500-byte network. The backend clamps its advertised MSS (on Linux, ip route ... advmss 1440) so the client's segments fit after encapsulation. Google and Meta avoid the issue another way: they run a larger MTU inside the data centre than at the edge.

The backend side of DSR

For DSR to work, the backend must accept packets for the VIP but must not claim the VIP on the LAN. If it answered ARP requests for the VIP, the upstream router could start sending client traffic directly to one backend, bypassing the balancer. On Linux:

# run on each Linux DSR backend — values shown are the standard settings
ip addr add 203.0.113.10/32 dev lo                    # accept packets for the VIP
sysctl -w net.ipv4.conf.all.arp_ignore=1              # answer ARP only for addresses on the receiving interface
sysctl -w net.ipv4.conf.all.arp_announce=2            # never use the VIP as ARP source
ip link set tunl0 up                                  # IPIP decapsulation (tunnel mode only)
sysctl -w net.ipv4.conf.tunl0.rp_filter=0             # inner source is the client; don't drop as "martian"
sysctl -w net.ipv4.conf.all.rp_filter=0               # effective rp_filter is the max of all and the interface

The rp_filter lines are the ones people forget. Reverse-path filtering checks that a packet's source address would be routed back out the interface it arrived on. The decapsulated packet arrives on tunl0 with a source of 198.51.100.23, which routes out eth0. Strict rp_filter drops it silently. The symptom: SYNs show up in tcpdump on eth0, but the application never sees a connection.

Deep dive: by the numbers

Source ports in a full proxy. A proxy connecting to a backend needs a unique 4-tuple (proxy IP, proxy port, backend IP, backend port). With one proxy IP and one backend IP:port, the only free variable is the proxy's source port. Linux's default ephemeral range is 32768–60999: 28,232 ports. macOS uses 49152–65535: 16,384. So one proxy address can hold at most 28,232 concurrent connections to one backend socket. The fixes are more source IPs on the proxy, more backend ports or IPs, or connection pooling so you need fewer connections in the first place.

TIME_WAIT makes it worse. The side that closes first holds the 4-tuple in TIME_WAIT for 60 s on Linux. If the proxy closes each backend connection after one request, its steady-state rate per backend tuple is capped near 28,232 / 60 ≈ 470 new connections per second. That is low enough to hit in a load test. net.ipv4.tcp_tw_reuse=1 lets Linux reuse TIME_WAIT ports for new outgoing connections when timestamps make it safe. Keep-alive pooling avoids the problem.

Flow table memory. A connection-tracking entry costs a few hundred bytes (it varies by kernel and build). Ten million concurrent flows is therefore several gigabytes. On Linux nf_conntrack_max caps the table; when it fills, the kernel logs nf_conntrack: table full, dropping packet and new connections fail while existing ones carry on. A SYN flood at a stateful L4 balancer attacks exactly this table. Stateless designs such as Maglev-only lookup, or SYN cookies at the balancer, exist to blunt it.

Health-check traffic. It scales as balancers × backends / interval. Ten HAProxy nodes checking 200 backends every 2 s is 1,000 checks per second — trivial. A service mesh where 2,000 sidecars each actively check 300 endpoints every 5 s is 120,000 checks per second, a real load on small backends. This is why meshes rely on a control plane's view of endpoint health plus passive outlier detection, and keep active checks to a minimum.

Detection and recovery time, from the formulas in section 4:

Settings Mark down after Mark up after
HAProxy defaults: 2 s, fall 3, rise 2 ~6 s ~4 s

Draining arithmetic. If p99.9 request time is 2 s and your longest legitimate request (an upload, a report) is 90 s, then a 300 s deregistration delay wastes four minutes per instance per deploy. Set the delay a little above the longest request you're willing to wait for. Long-lived connections (WebSockets, gRPC streams) never finish on their own; they need the server to close them, for example with GOAWAY or a reconnect message.

Hashing quality. For ring hashing, the spread of key ownership shrinks roughly as 1/√(virtual nodes). With 100 virtual nodes per backend the simulation saw 8.77%–12.46% around a 10% ideal; Envoy's ring hash defaults to a minimum ring size of 1,024 entries. Maglev with M = 65,537 and N = 10 gives each backend 6,553 or 6,554 slots, an imbalance under 0.02%.

Idle timeouts must nest. The rule is: each hop's idle timeout must be shorter than the hop behind it. A client should give up before the balancer does, and the balancer should close idle backend connections before the backend does. Typical defaults: ALB 60 s idle; NLB 350 s; Node.js server.keepAliveTimeout 5 s; NGINX keepalive_timeout 75 s; Linux TCP keepalive first probe 7,200 s. Note Node's 5 s against ALB's 60 s. That pair is the classic random 502, covered next.

Deep dive: production failure modes

Random 502s at low rate behind an L7 balancer

Symptom. 0.01%–0.5% of requests fail with 502. They don't correlate with load, and you can't reproduce them with curl.

Mechanism. The balancer keeps idle pooled connections to the backend for up to 60 s. The backend closes idle connections after 5 s. At some moment the backend decides to close a connection that has been idle for 5 s. In the same millisecond, the balancer picks that connection for a new request. The request arrives just as the FIN is sent; the backend answers with a RST. The balancer cannot safely retry a request that may have been processed (unless it is idempotent and the proxy is configured to), so it returns 502.

Prove it. The balancer's access log shows the 502 with zero bytes received from the backend and a backend response time near zero. On the backend, capture resets on the backend port:

# run on the backend (Linux) — your output will differ
sudo tcpdump -nn -i eth0 'tcp port 8080 and (tcp[tcpflags] & (tcp-rst|tcp-fin) != 0)'

You will see the backend's FIN, then a data segment from the balancer, then the backend's RST, all within a millisecond or two.

Fix. Make the backend's idle timeout longer than the balancer's: Node.js server.keepAliveTimeout = 65_000 (and headersTimeout above it), or the equivalent in your server. Now the balancer always closes first, and it never sends on a connection it has already closed.

Proxy source-port exhaustion

Symptom. Under load, the proxy logs connect() failed (99: Cannot assign requested address) (EADDRNOTAVAIL), and errors climb for one backend while others are fine.

Mechanism. The 28,232-port budget for one proxy-IP → backend-IP:port tuple is exhausted, often by TIME_WAIT sockets from short-lived upstream connections.

Prove it.

# run on the proxy (Linux) — your output will differ
ss -tan state time-wait '( dport = :8080 )' | wc -l       # sockets stuck in TIME_WAIT to the backend
sysctl net.ipv4.ip_local_port_range                       # your ephemeral range
nstat -az | grep -i -E 'TcpExtTW|ListenOverflows'         # TIME_WAIT churn counters

Fix. Turn on upstream keep-alive pooling (in NGINX, keepalive in the upstream block plus proxy_http_version 1.1 and an empty Connection header). Add source IPs, or spread backends across more ports. Enable tcp_tw_reuse for outgoing connections.

New pods get no traffic (or all of it)

Symptom A. After a scale-up, new pods stay idle — the gRPC story from section 5. Long-lived connections pinned by an L4 decision.

Symptom B. After a scale-up or a restart, the new pod gets flooded and falls over, then the next one does. Least-connections sees zero active connections on the newcomer and sends it everything, while its caches, connection pools, and JIT are cold.

Prove it. Per-pod request rate against per-pod connection count, side by side on a dashboard. A newcomer at 0 connections and 5× the request rate of its peers is case B.

Fix. Slow start: HAProxy slowstart 60s on the server line, Envoy slow_start_config, AWS target-group slow start. Or P2C, which sends a newcomer only the traffic it wins in random pairwise comparisons, not all of it.

Health checks that cause the outage

Symptom. A shared dependency (a database, an auth service) gets slow. Within a minute, every backend is marked unhealthy and the balancer returns 503 for everything. The dependency recovers; the service doesn't, because the checks now time out under the thundering reconnect.

Mechanism. The health endpoint checked the dependency. When the dependency slowed, every backend failed the check at the same time.

Prove it. The balancer's health-check log shows all targets flipping to unhealthy within one or two intervals of each other, with the same reason (timeout).

Fix. Health checks test what the instance controls: the process is up, it can serve a trivial request. Dependency trouble shows up as errors in real traffic, which outlier detection handles — capped by max-ejection-percent. Keep panic mode on so a mass "unhealthy" falls back to spreading traffic everywhere.

Cross-zone imbalance on an L4 balancer

Symptom. In an NLB-fronted service, targets in one availability zone run hot while others idle.

Mechanism. Cross-zone balancing is off. DNS for the NLB returns one IP per zone, and clients spread roughly evenly across zones. Each zone's node only sends to its own zone's targets. Uneven target counts per zone mean uneven per-target load. With zones of 2, 4, and 6 targets, each zone gets a third of traffic, so a target in the 2-target zone carries three times the load of one in the 6-target zone.

Fix. Balance target counts across zones (a topology spread constraint in Kubernetes), or enable cross-zone balancing and accept the inter-zone data transfer cost it brings.

DSR: SYNs arrive, connections never complete

Symptom. In a new DSR deployment, tcpdump on the backend shows encapsulated SYNs arriving; clients time out.

Causes, in order of likelihood. rp_filter dropping the decapsulated packet. The VIP is missing from the loopback, so the kernel drops packets for an address it doesn't own. The reply is leaving with the backend's own address as source instead of the VIP. Or an upstream anti-spoofing filter is dropping replies whose source is the VIP, because they come from a host that "shouldn't" use that address.

Prove it. nstat -az | grep -i rpfilter on the backend; ip addr show lo; capture the outgoing SYN-ACK and check its source address.

And the slow version: connections establish, small requests work, large uploads hang. That is the encapsulation MTU problem from the capture section. Lower the backend's advmss, or raise the MTU on the balancer-to-backend path.

Deep dive: 2026 context

eBPF and XDP have taken over software L4. Katran (Meta) and Cilium's load balancer run the whole data path in XDP: hash, connection-table lookup in a BPF map, Maglev lookup, encapsulate, transmit, all before the kernel builds an skb. A single commodity server can forward millions of packets per second per core. In Kubernetes, Cilium's kube-proxy replacement does the Service DNAT at the socket layer for pod-to-Service traffic: it rewrites the destination at connect() time, so there is no per-packet NAT for that path at all.

L7 balancing moved into the client and the mesh. Envoy's xDS APIs became the common language for pushing endpoints, weights, and health to proxies. gRPC clients speak xDS directly ("proxyless" mesh), balancing per request with no sidecar. Sidecar-less meshes such as Istio's ambient mode split the job: a per-node L4 proxy for mTLS and a per-namespace L7 proxy only where L7 policy is needed.

Kubernetes Gateway API replaced Ingress for new work. It separates the infrastructure owner (Gateway) from the app owner (HTTPRoute, GRPCRoute), with weighted backends and header matches written down in the API instead of controller-specific annotations.

QUIC breaks the 5-tuple assumption. A QUIC connection survives a client address change (connection migration), so the 5-tuple can change mid-connection. An L4 balancer hashing on the 5-tuple will then send the migrated connection to a different backend. The fix being standardised in the IETF's QUIC-LB draft is to route on the connection ID, encoding the backend's identity into the server-chosen connection ID so any balancer node can route it without state. Until that is common, many deployments hash QUIC on the destination connection ID with consistent hashing, or terminate QUIC at the edge and speak HTTP/2 or HTTP/1.1 behind it.

Zero trust changes the TLS question. "Terminate at the edge, plain HTTP inside" no longer passes most security reviews. The default is re-encryption, with mTLS between proxy and workload and workload identities (SPIFFE IDs in a mesh) instead of IP allow-lists. The balancer has become a policy point as much as a traffic spreader.

ECH weakens SNI routing. As Encrypted Client Hello spreads in browsers and CDNs, TLS-passthrough balancers that route on SNI see only the outer public name. Hostname routing for passthrough traffic increasingly needs the balancer to be the ECH-terminating party, or a different routing key.

Deep dive: senior interview questions

Q1: Your L4 balancer tier uses Maglev hashing. Why does it still need a connection table, and what breaks without one?

Maglev gives every node the same answer for a given backend set, which handles balancer churn: a flow moved to another node by an ECMP change still hashes to the same backend. But when the backend set changes, a few percent of table slots change owner. Without a connection table, established flows in those slots are sent to a backend that has no socket for them, and it answers with RST. The table pins existing flows to their original backend; only new flows follow the new mapping. You need both mechanisms.

Q2: With DSR, how does the backend accept a packet addressed to the VIP, and what stops it from stealing the VIP on the LAN?

The VIP is configured on the loopback, so the kernel treats it as local. ARP is suppressed for it (arp_ignore=1, arp_announce=2 on Linux), so the backend never answers "who has VIP?" and the router keeps sending VIP traffic to the balancer. In tunnel mode, rp_filter must allow the decapsulated packet, whose source is the remote client.

Q3: You see a steady trickle of 502s behind an ALB with Node.js backends. What's your first hypothesis, and how do you prove it?

An idle-timeout race. Node's default keep-alive timeout of 5 s is shorter than the ALB's 60 s idle timeout, so the backend closes pooled connections that the ALB is about to reuse. Prove it with ALB access logs (502 with no backend response bytes) and a tcpdump of FIN/RST on the backend port, showing a request arriving immediately after the backend's FIN. Fix by setting the backend's keep-alive above the balancer's idle timeout.

Q4: Why can P2C outperform least-connections in practice, when least-connections has strictly more information?

Because in a fleet of balancers, the information is local and goes stale. Every balancer instance only sees its own counts, and they all pick the same apparently idle backend at once — herding. P2C's randomness decorrelates the instances. Its worst-case load is about log log n above average, against log n / log log n for pure random. It needs no global state, and it doesn't flood a newly added backend.

Q5: You remove one of twenty cache nodes and the database load spikes by 20× for ten minutes. What happened?

Client-side hash(key) mod N sharding. Going from 20 to 19 nodes remaps about 95% of keys, so nearly every lookup missed and fell through to the database. Consistent hashing (ring, Maglev, or rendezvous) would remap only the removed node's ~5%. Add bounded loads if the key popularity is skewed.

Q6: A service sits behind an NLB with client-IP preservation, and the security team wants per-client rate limits in the app. Then the platform team moves it behind an ALB. What breaks, and how do you fix it safely?

The app now sees the ALB's addresses as the TCP peer, so every client looks like a handful of IPs and rate limits trigger for everyone. Read the client address from X-Forwarded-For instead, but take the rightmost entry added by your trusted proxies, not the leftmost, which the client controls. Otherwise anyone can bypass rate limits by sending a fake header.

Q7: How would you drain a backend that serves long-lived gRPC streams and WebSockets during a deploy?

Stop new assignments first: set the weight to zero, or remove the endpoint and wait for it to propagate (a preStop sleep in Kubernetes). Then have the server signal clients to move. For HTTP/2 and gRPC that is GOAWAY; for WebSockets, an application-level "reconnect" message followed by a close. Give clients jittered reconnect delays so they don't stampede the remaining backends. Hard-close whatever remains at the deadline. A balancer-side deregistration delay alone doesn't help, because these connections never end by themselves.

Q8: When is DNS-based global load balancing the wrong tool, and what do you use instead?

When you need failover in seconds, when clients hold long-lived connections, or when the resolver's location is a poor proxy for the user's (large public resolvers without ECS). DNS answers are cached for at least the TTL and often longer, and connections never re-resolve. Anycast moves traffic at BGP speed instead and naturally reaches the nearest site. The usual design uses anycast to the edge, regional balancing inside, and DNS for deliberate whole-region moves.
