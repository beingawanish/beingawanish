Networking Mastery Guide · Module 23 of 23

1. Why it matters

Most of the services you will build in the next few years run in containers, and most of those containers run on Kubernetes. Every module before this one still applies there: Ethernet frames, ARP, routing tables, NAT, conntrack, DNS, TCP. Kubernetes did not invent a new network. It wires the old pieces together in a dense, automated, and slightly surprising way.

That is exactly why it confuses people. A pod has an IP address that no physical interface owns. A Service has an IP address that no interface owns at all — it exists only as rules in the kernel. A DNS lookup for api.stripe.com turns into several queries before it reaches the internet. A NetworkPolicy that "allows everything from the frontend" silently blocks DNS. None of this is magic. Each one has a mechanism you can read with ip, iptables-save, conntrack and tcpdump.

The payoff for learning it is concrete. "The service is slow" in Kubernetes is often a 5-second DNS stall from a conntrack race. "It works from my laptop but not from the pod" is often MTU on an overlay. "The client IP in my logs is wrong" is a NodePort SNAT. Once you can trace one packet from a pod, through a Service, to a backend on another node, you can debug all of these from first principles. This module builds that trace, then walks it hop by hop with real captures.

2. The mental model

Hold one picture: every node is a router, and every pod is a tiny host plugged into it.

A pod is a network namespace — a private copy of the kernel's network stack with its own interfaces, routes, ARP table and sockets. The pod's eth0 is one end of a virtual cable (a veth pair). The other end sits in the node's own namespace, usually plugged into a software switch (a Linux bridge) or straight into the node's routing table. From the pod's point of view, it is a host on a small LAN with a default gateway. From the node's point of view, it is a router with one directly attached host per pod.

Between nodes, pod traffic either rides the real network as-is (routed), gets wrapped in an outer packet (overlay), or uses addresses the cloud network already knows about (native VPC addressing). That choice is the CNI plugin's job. It decides your MTU, your performance, and what your packet captures look like.

Then Kubernetes adds one layer of indirection on top: Services are destination NAT done in every node's kernel. A ClusterIP like 10.96.0.50 is not a machine. When a packet to it leaves a pod, the node it enters rewrites the destination to one real pod IP, records that rewrite in conntrack, and routes the packet like any other. The reply gets the rewrite undone on the way back. That is the whole trick. kube-proxy (or Cilium's eBPF programs) is just the agent that keeps those NAT rules in sync with the API server.

Everything else in this module hangs off those two ideas. DNS gives Services names. NetworkPolicy is a stateful firewall in the same kernel path. Ingress and Gateway API are L7 proxies that sit in front. A service mesh moves TLS and L7 routing into proxies next to (or near) each pod.

3. How it works

Network namespaces: a private copy of the stack

Linux keeps networking state per network namespace: the interface list, IP addresses, routing tables and rules, the neighbour (ARP) table, netfilter rules, the conntrack table, the socket port space, and most net.* sysctls. A process lives in exactly one network namespace and sees only that namespace's state. A new namespace starts with nothing but a loopback interface, and even that is down.

That one fact explains a lot of container behaviour. Two containers can both listen on port 80 because their port spaces are separate. A container's iptables -L is empty even though the host has hundreds of rules. ss -tn inside a pod shows only that pod's sockets.

In Kubernetes, all containers in a pod share one network namespace. The runtime creates it first, held open by a tiny "pause" (sandbox) container, then starts your containers inside it. That is why containers in the same pod reach each other on localhost and must not collide on ports.

macOS has no network namespaces. Docker Desktop, Colima and OrbStack all run a Linux VM, and every namespace lives inside it. That is why the commands in this module run in a Linux shell, not your Mac's.

veth pairs: a cable with two ends

A namespace with only loopback is useless. A veth pair connects it to something. It is two virtual Ethernet interfaces created together: a frame transmitted on one end is received on the other, like a patch cable. You move one end into the pod's namespace and rename it eth0. The other end stays on the node with a name like veth3f2a91c0 (bridge plugin) or cali1a2b3c4d5e6 (Calico).

The kernel exposes the pairing. In the pod, eth0@if4 means "my peer is interface index 4 in another namespace". On the node, veth3f2a91c0@if2 points back at the pod's index 2. When you need to find which host-side veth belongs to which pod, this is how you match them.

The Linux bridge: a switch in the kernel

A Linux bridge is a learning Ethernet switch in software (Module 3). It has ports (the host-side veths), a forwarding database of MAC → port, and it floods unknown destinations. It can also have its own IP address. When it does, the bridge is also an interface on the node's routing stack, which makes it the pods' default gateway. Docker's docker0 and the CNI bridge plugin's cni0 are both this.

The detail that matters later: traffic between two pods on the same bridge is bridged (Layer 2), not routed. It never passes through the node's IP stack unless you ask for it. Traffic from a pod to anything off its subnet — another node's pods, a Service IP, the internet — goes to the gateway MAC, gets handed up to the node's IP stack, and is routed. Netfilter hooks, NAT and conntrack live on the routed path.

Docker's bridge network: NAT out, DNAT in

Docker's default network is the plainest version of this picture. Every container gets a veth into docker0 and an address from 172.17.0.0/16; docker0 itself is 172.17.0.1. Two kinds of iptables rule do the rest.

Outbound uses MASQUERADE (source NAT to the host's address, Module 15). A container at 172.17.0.2 talking to the outside world leaves with the host's IP as its source.

Inbound uses port publishing. docker run -p 8080:80 installs a DNAT rule: anything arriving for the host's port 8080 has its destination rewritten to 172.17.0.2:80. Here is the real nat table from a lab host with one published container. It uses the Docker 27-era layout; newer releases restructure the filter chains.

-A PREROUTING -m addrtype --dst-type LOCAL -j DOCKER
-A OUTPUT ! -d 127.0.0.0/8 -m addrtype --dst-type LOCAL -j DOCKER
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
-A POSTROUTING -s 172.17.0.2/32 -d 172.17.0.2/32 -p tcp -m tcp --dport 80 -j MASQUERADE
-A DOCKER -i docker0 -j RETURN
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80

And here is conntrack after one inbound and one outbound connection. Each line holds the original tuple and the reply tuple. The difference between them is the NAT.

tcp 6 119 TIME_WAIT src=192.168.10.50 dst=192.168.10.20 sport=58388 dport=8080 src=172.17.0.2 dst=192.168.10.50 sport=80 dport=58388 [ASSURED]
tcp 6 119 TIME_WAIT src=172.17.0.2 dst=192.168.10.50 sport=33936 dport=9000 src=192.168.10.50 dst=192.168.10.20 sport=9000 dport=33936 [ASSURED]

The first line is the published port: the client asked for .20:8080, and the reply comes from 172.17.0.2:80. The second is masquerade: the container's connection appears to the outside as 192.168.10.20:33936. MASQUERADE kept the source port because it was free on the host.

Two practical consequences follow. First, published ports bypass host firewalls that only filter the INPUT chain. DNAT happens in PREROUTING, and the packet then goes through FORWARD, not INPUT. That is the famous "ufw says deny, but my Docker port is open" surprise, and Docker's answer is the DOCKER-USER chain. Second, user-defined bridge networks (docker network create) get an embedded DNS server at 127.0.0.11 that resolves container names. The default docker0 network does not.

The Kubernetes network model: three rules

Kubernetes does not ship a network. It states requirements, and a plugin meets them. The rules are short:

  1. Every pod gets its own IP address, unique across the cluster.
  2. Pods can reach all other pods, on any node, without NAT. The source IP a pod sees is the real pod IP of the sender.
  3. Agents on a node (kubelet, system daemons) can reach all pods on that node.

Rule 2 is the one that shapes everything. It rules out Docker's design, where every container hides behind its host's address. It means the network between nodes has to carry pod IPs end to end, either natively or inside a tunnel. And it means an application can trust the source address of a pod-to-pod connection, which NetworkPolicy and service meshes depend on.

Services are layered on top, and they do use NAT. The model only promises NAT-free pod-to-pod traffic. Once a ClusterIP is involved, DNAT happens on the client's node, and some paths (NodePort, external traffic) also SNAT.

CNI: who builds the plumbing

The Container Network Interface (CNI) is a small contract between the container runtime and a network plugin. It is not a daemon. It is an executable, called once per event. When kubelet asks containerd or CRI-O to start a pod sandbox, the runtime creates the namespace and then runs the plugin binary from /opt/cni/bin. The config from /etc/cni/net.d arrives on stdin, along with these environment variables:

CNI_COMMAND=ADD            # also DEL, CHECK, VERSION; spec 1.1 adds STATUS and GC
CNI_CONTAINERID=4f0c...    # sandbox ID
CNI_NETNS=/var/run/netns/cni-7c1e...   # the pod's namespace
CNI_IFNAME=eth0
CNI_PATH=/opt/cni/bin

An ADD has to leave the pod with a working interface, an IP and routes, and print a JSON result with the assigned address. Most plugins chain an IPAM plugin for the address itself. The simplest, host-local, hands out addresses from the node's pod CIDR and records each lease as a file under /var/lib/cni/networks/<network>/. A DEL has to undo it all. When DEL fails or never runs, those lease files leak. Eventually a node runs out of pod IPs with far fewer than 254 pods on it.

Real plugins (Calico, Cilium, Flannel, the AWS VPC CNI, Azure CNI, GKE's dataplane) also run a node agent to program routes, tunnels, eBPF maps or cloud ENIs. The binary is the per-pod hook. The agent keeps the node-wide state.

Three ways to connect nodes

Pod A on node 1 sends to pod B on node 2. Node 1's routing table needs an answer for 10.244.2.0/24. There are three families of answers.

Overlay (VXLAN, Geneve, IP-in-IP). Node 1 wraps the pod packet in an outer packet addressed node to node. VXLAN (RFC 7348) adds an inner Ethernet header plus outer IPv4, UDP and an 8-byte VXLAN header: 50 bytes in all. Geneve (RFC 8926) is similar, with variable-length options. The underlay network only ever sees node IPs, so it needs no knowledge of pods. The costs are 50 bytes of MTU, encap/decap CPU (largely offloaded on modern NICs), and captures that need decoding. Flannel's default, Calico's VXLAN mode and Cilium's tunnel mode all work this way.

Routed (native routing, BGP). Node 1 has a plain route: 10.244.2.0/24 via <node 2>. Packets cross the wire with pod IPs visible. This needs every hop to know pod routes. On a shared L2 segment, a static route per node is enough (Flannel's host-gw). Across L3, nodes announce their pod CIDRs with BGP (Calico, Cilium with BGP, kube-router). There is no encapsulation and you keep the full MTU, but the network team must accept pod routes. In a cloud VPC the instance must also be allowed to send packets whose source IP is not its own. AWS calls this disabling the source/destination check.

Cloud-native addressing (ENI, alias IP). Pods get real VPC addresses, so the cloud's network routes them with no help. The AWS VPC CNI attaches extra ENIs to each instance and assigns their secondary IPs to pods. GKE's VPC-native mode gives each node an alias IP range. Azure CNI can allocate pod IPs from a VNet subnet. Pod IPs are then first-class in security groups, flow logs and peered VPCs. The price is address consumption and per-instance limits. On AWS without prefix delegation, max pods = ENIs × (IPs per ENI − 1) + 2. An m5.large (3 ENIs, 10 IPv4 each) gets 3 × 9 + 2 = 29 pods.

Services: a virtual IP that exists only as rules

Pods come and go, and their IPs change every time. A Service gives a stable name and IP to a set of pods chosen by a label selector. The control plane watches pods matching the selector and writes their ready addresses into EndpointSlice objects (up to 100 endpoints per slice by default). Every node's kube-proxy watches Services and EndpointSlices and programs its kernel.

There are four types, and each builds on the previous one:

  • ClusterIP (default). A virtual IP from the service CIDR (kubeadm default 10.96.0.0/12), reachable only from inside the cluster. No interface owns it.
  • NodePort. ClusterIP, plus a port from 30000–32767 opened on every node's addresses. Traffic to any node's IP on that port reaches the Service.
  • LoadBalancer. NodePort, plus a cloud load balancer provisioned by a controller. Older integrations target the NodePorts. Newer ones (AWS Load Balancer Controller in IP mode, GKE container-native load balancing) target pod IPs directly and skip the NodePort hop.
  • Headless (clusterIP: None). No virtual IP and no NAT at all. DNS returns the pod IPs directly. StatefulSets use this so each replica has a stable DNS name.

ExternalName is a fifth type, but it is only a DNS CNAME.

kube-proxy modes and eBPF

kube-proxy does not proxy traffic in any modern mode. It writes rules and leaves the kernel to do the work.

iptables mode (the long-time default). For each Service it writes a chain that matches the ClusterIP and port, picks a backend with the statistic match in random mode, then DNATs to it. With n endpoints, rule i matches with probability 1/(n−i+1), so the picks come out uniform. Only the first packet of a connection walks these rules. Conntrack remembers the choice for the rest. Section 4 shows the real chains. The weakness is scale. Rules are evaluated as a list, so the first packet of each connection walks past every Service ahead of it, and rewriting a large ruleset after an endpoint change takes noticeable time.

IPVS mode uses the kernel's L4 load balancer (the same IPVS that LVS used). Services become IPVS virtual servers, looked up in a hash table, with real schedulers (round-robin, least-connection, and others). It binds every ClusterIP to a dummy interface called kube-ipvs0, so — unlike iptables mode — a ClusterIP answers ping. It still uses iptables (via ipsets) for masquerade and NodePort edge cases. Upstream now steers clusters away from it.

nftables mode (GA in Kubernetes v1.33) writes the same logic as nftables verdict maps. Lookups are map-based rather than linear, and updates are incremental. It is the direction upstream is moving for kernel-native Services.

eBPF (Cilium's kube-proxy replacement, Calico eBPF). BPF programs look up Services in BPF hash maps. They attach at the socket layer, at tc ingress/egress on interfaces, and optionally at XDP. For pod-originated traffic, Cilium can translate the ClusterIP at connect() time. The socket is connected straight to the backend, so no packet ever carries the ClusterIP and no per-packet NAT happens on that node. eBPF dataplanes also keep their own connection tracking in BPF maps instead of using netfilter's conntrack.

CoreDNS and the ndots:5 trap

Every Service gets a DNS name: <service>.<namespace>.svc.cluster.local. CoreDNS runs as a Deployment behind a Service, conventionally at 10.96.0.10. It answers those names from its view of the API and forwards everything else upstream. With the default dnsPolicy: ClusterFirst, kubelet writes this into every pod:

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

The search list is what lets you type web instead of the full name. ndots:5 decides when the search list is tried first: any name with fewer than five dots is treated as relative. web has zero dots, so it gets web.default.svc.cluster.local first. Good. But api.example.com has only two dots, so it is also tried against every search domain before the real name. Each candidate costs one query per record type, and each wrong one is an NXDOMAIN round trip. Section 9 counts them.

The trap is that this is invisible. Lookups succeed. They are just several times slower and several times more load on CoreDNS. On cloud nodes the host's own search domains (such as ec2.internal or <project>.internal) are appended too, which makes the list longer still.

There are three fixes, in the order I would reach for them. Write external names fully qualified with a trailing dot (api.example.com.), which skips the search list entirely. Lower ndots per pod with dnsConfig.options. And run NodeLocal DNSCache, so the misses are answered from a cache on the same node.

Ingress and Gateway API

Services are L4. To route HTTP by host and path, terminate TLS or split traffic by weight, you need an L7 proxy. Ingress is the original API: one object type with host and path rules, implemented by a controller (NGINX, HAProxy, Traefik, cloud load balancers). It was underspecified. Anything beyond host and path — timeouts, rewrites, header matching, canaries — ended up in controller-specific annotations that did not port between implementations.

Gateway API (v1.0 in October 2023) replaces it with a role-split set of resources. A GatewayClass names an implementation and belongs to the platform. A Gateway is a listener — address, ports, TLS certificates — and belongs to the cluster operator. HTTPRoute, GRPCRoute, TLSRoute and friends attach to a Gateway and describe routing. They belong to app teams, and header matching, weights and filters live in the spec itself.

The data path is the same as Ingress. A proxy fleet receives traffic, terminates TLS, picks a backend pod (usually by pod IP from EndpointSlices, not via the ClusterIP), and opens a new connection to it. Your backend sees the proxy's IP as the TCP source. The real client IP travels in X-Forwarded-For or the PROXY protocol.

NetworkPolicy

By default every pod can reach every other pod. A NetworkPolicy selects pods by label and lists what is allowed in (ingress) and out (egress). Its semantics surprise people, so they are worth memorising:

  • A pod selected by no policy is wide open.
  • Once any policy selects a pod for a direction, that pod is isolated in that direction: only traffic some policy allows gets through. Policies are additive allow-lists. The v1 API has no "deny" rule.
  • It is stateful. Allowing ingress to port 8080 implicitly allows the replies.
  • It is enforced by the CNI plugin, not by Kubernetes. A plugin that does not implement it (plain Flannel, for example) accepts the objects and enforces nothing.
  • An egress policy that forgets DNS breaks every name lookup. You almost always need an explicit allow to the kube-dns pods on UDP and TCP 53.

Enforcement lives on the node where the pod runs. It is either iptables/ipset chains (Calico's classic dataplane) or BPF programs on the pod's veth that look up a numeric identity derived from labels (Cilium). A denied connection is dropped, not rejected. The client sees a timeout rather than "connection refused", and the failure-modes deep dive below shows the capture.

Service mesh: sidecar vs ambient, and mTLS

A service mesh adds mutual TLS, L7 retries, timeouts, traffic splitting and telemetry between workloads without changing application code. It does this by putting a proxy in the path.

Sidecar model (Istio classic, Linkerd). Every pod gets a proxy container. An init container (or a CNI plugin) installs iptables REDIRECT rules inside the pod's namespace. In Istio, outbound TCP goes to Envoy on port 15001 and inbound to 15006. The proxy's own traffic runs as UID 1337 and is exempted, so it does not loop. The app talks plaintext to what it thinks is the destination, the sidecar opens an mTLS connection to the destination's sidecar, and the far sidecar delivers plaintext to its app. The cost is one proxy per pod (memory, CPU, and a startup-ordering problem that native sidecar containers, GA in Kubernetes 1.33, finally fixed), plus two extra proxy hops per request.

Ambient model (Istio ambient, GA in Istio 1.24). A per-node L4 proxy called ztunnel captures pod traffic and carries it to the destination node's ztunnel over HBONE: HTTP/2 CONNECT tunnels inside mTLS on port 15008. That gives mTLS and L4 policy with no sidecars. When a service needs L7 features, you deploy a waypoint proxy (an Envoy) for it, and its traffic is routed through the waypoint.

In both models, identity comes from the Kubernetes service account. It is encoded as a SPIFFE ID such as spiffe://cluster.local/ns/default/sa/web in a short-lived X.509 certificate (24 hours by default in Istio) issued by the mesh's CA. Authorization policy keys off that identity, not the pod IP. That is the zero-trust point: an IP is a location, a certificate is a workload.

Read it top to bottom as a program:

  • Entry. Packets from pods enter at PREROUTING. Packets from processes on the node itself enter at OUTPUT. Both jump to KUBE-SERVICES.
  • Match. One rule per Service port matches the ClusterIP and port. The last rule catches anything addressed to one of the node's own IPs and checks NodePorts.
  • Choose. KUBE-SVC-… picks an endpoint: 50% to the first, the rest to the second. With three endpoints the probabilities would be 0.333…, then 0.5, then unconditional.
  • Rewrite. KUBE-SEP-… DNATs to the pod IP and target port.
  • Mark for SNAT, decide later. Some paths need source NAT too: traffic from outside the pod CIDR (! -s 10.244.0.0/16), NodePort traffic (KUBE-EXT), and a pod reaching itself through its own Service (the -s 10.244.2.7/32 hairpin rule). Those packets get mark 0x4000. In POSTROUTING, marked packets are masqueraded and everything else returns untouched.

The first tuple is what the client sent. The second tuple is the reply the kernel expects. On node 1 they disagree: the client sent to 10.96.0.50:80, and the reply will come from 10.244.2.7:8080. That mismatch is the DNAT, and it is how the kernel knows to rewrite the reply's source back to the ClusterIP. On node 2 the tuples mirror each other exactly, because node 2 never saw the ClusterIP. Only the client's node knows a Service was involved.

5. A realistic example: debugging a pod-to-Service path

A ticket arrives: "checkout pods intermittently can't reach payments. Timeouts, not errors." Here is the ladder I would climb, from the top of the stack down, with the command at each rung. Each rung either clears a layer or names the problem. Names are from this example; your output will differ.

Rung 1 — does the Service have endpoints? A Service whose selector matches nothing has a ClusterIP and no backends. In iptables mode kube-proxy installs a REJECT for it, so you get "connection refused" rather than a timeout. Always check this first.

kubectl -n shop get svc payments -o wide
kubectl -n shop get endpointslices -l kubernetes.io/service-name=payments -o wide
# ENDPOINTS shows ready pod IPs. Empty, or fewer than expected? Check readiness:
kubectl -n shop get pods -l app=payments -o wide

Rung 2 — does the name resolve, and how fast? Run the lookup from inside a client pod, because the pod's resolv.conf is what matters.

kubectl -n shop exec deploy/checkout -- cat /etc/resolv.conf
kubectl -n shop exec deploy/checkout -- getent hosts payments
# image has no tools? attach an ephemeral debug container that shares the pod's netns:
kubectl -n shop debug -it pod/checkout-6b8f9d7c4-x2k9q --image=nicolaka/netshoot --target=checkout -- \
  dig +search +stats payments

Watch the query time. A lookup that sometimes takes exactly 5 seconds is the resolver's default retry timeout. It points at dropped UDP (see the conntrack race in the failure-modes deep dive).

Rung 3 — split Service from pod. Connect to a backend pod IP directly, then to the ClusterIP. If the pod IP works and the ClusterIP does not, the problem is in the Service layer on the client's node. If neither works, it is pod networking or policy.

kubectl -n shop exec deploy/checkout -- curl -sS -m 3 -o /dev/null -w '%{http_code} %{time_connect}\n' http://10.244.2.7:8080/healthz
kubectl -n shop exec deploy/checkout -- curl -sS -m 3 -o /dev/null -w '%{http_code} %{time_connect}\n' http://payments.shop.svc.cluster.local./healthz

Note the trailing dot on the second name. It skips the search list, so you are testing the Service and not DNS expansion.

Rung 4 — read the rules on the client's node. Find the node, get a root shell on it, and look for the Service.

kubectl -n shop get pod -l app=checkout -o wide          # which node?
kubectl debug node/worker-1 -it --profile=sysadmin --image=nicolaka/netshoot
# the node debug pod runs with hostNetwork and hostPID; then:
iptables-save -t nat | grep -E 'shop/payments'           # iptables mode
nft list table ip kube-proxy | grep -A3 payments          # nftables mode
ipvsadm -Ln -t 10.96.33.12:443                            # IPVS mode
cilium-dbg service list | grep 10.96.33.12                # Cilium (run in the cilium agent pod)

You are checking that the ClusterIP is present and that the endpoint list matches rung 1. A stale endpoint here — a pod IP that no longer exists — explains "intermittent" perfectly. One pick in n lands on a dead address, and that SYN goes nowhere.

Rung 5 — follow the connection in conntrack.

conntrack -L -d 10.96.33.12 2>/dev/null | head
conntrack -S | grep -E 'insert_failed|drop'               # per-CPU error counters

An entry stuck in SYN_SENT with [UNREPLIED] names the backend that is not answering. A rising insert_failed points at the DNS race or a full table.

Rung 6 — capture at both ends. Enter the pod's namespace from the node, so you can use the node's tools, then capture on the node's uplink too.

PID=$(crictl inspect --output go-template --template '{{.info.pid}}' $(crictl ps -q --name checkout | head -1))
nsenter -t "$PID" -n tcpdump -nn -i eth0 'tcp port 8080 or tcp port 443 or port 53'
tcpdump -nn -i eth0 'host 10.244.2.7'                      # routed: pod IPs on the wire
tcpdump -nn -i eth0 'udp port 4789 or udp port 8472'       # overlay: VXLAN between nodes

If SYNs leave the client's node and never arrive on the backend's node, look at the network between them: cloud security groups, source/destination checks, a missing BGP route. If they arrive and get no answer, look at NetworkPolicy and the backend itself. If small requests work and large ones hang, it is MTU.

The point of the ladder is the order. DNS, Service, pod, node, wire. Each rung is cheaper than the one below it, and each rules out a whole layer.

6. Misconceptions & common mistakes

"kube-proxy is a proxy." It was, in the long-gone userspace mode. Today it only writes kernel rules (iptables, IPVS or nftables). If kube-proxy crashes, existing Services keep working. Only changes stop being applied.

"You can ping a ClusterIP." In iptables and nftables modes, nothing matches ICMP to a ClusterIP and no interface owns the address. Ping fails even when the Service is healthy. IPVS mode binds ClusterIPs to kube-ipvs0, so there it answers. Test Services with a TCP connection, not ping.

"Pods on the same node talk through iptables." Same-bridge pod-to-pod traffic is bridged at Layer 2. It only hits iptables because kubeadm requires br_netfilter with net.bridge.bridge-nf-call-iptables=1. Without that, a pod calling a Service whose backend sits on the same bridge gets a reply straight from the backend's IP, which it does not recognise. The Try it section reproduces exactly this.

"NetworkPolicy is enforced by Kubernetes." The API server only stores policies. Your CNI plugin enforces them, or ignores them. Check that your plugin supports policy before you rely on it.

"A NetworkPolicy can deny a specific source." The v1 API is allow-only. You express "deny X" by allowing everything except X. Cluster-wide admin policies with explicit deny are a separate, newer API that only some plugins implement.

"Overlay networks are slow." On modern NICs with VXLAN offload, the encapsulation cost is small. The real costs are the 50-byte MTU reduction (and the breakage when someone forgets it) and the loss of pod-IP visibility on the underlay. Choose routed or native modes for visibility and simplicity, not because VXLAN is inherently slow.

"externalTrafficPolicy: Local is free." It preserves client IPs and removes a hop. But a node without a local backend pod fails the load balancer's health check and gets no traffic, so load spreads per node, not per pod. Three pods on node 1 and one on node 2 still get 50/50 from the load balancer.

"The service mesh encrypts everything." It encrypts traffic between mesh-enrolled workloads. Traffic to the internet, to databases outside the mesh, or from un-enrolled pods is outside its reach, unless strict mode rejects the plaintext.

7. Interview Q&A

Q1: What exactly is a ClusterIP, physically?

Nothing physical. No interface or MAC owns it, except in IPVS mode, where it sits on a dummy interface purely so the kernel accepts it as local. It is a match condition in DNAT rules or BPF maps that exist on every node. A packet addressed to it is rewritten to a real pod IP by the first node it enters, before routing. That is why it works from any node. It is also why it can't be reached from outside the cluster: no router outside knows the service CIDR, and no node advertises it.

Q2: Walk me through what happens when pod A curls a Service whose backend is on another node.

Pod A resolves the name through CoreDNS, gets the ClusterIP, and sends a SYN to its default gateway on the node. On node 1, the packet traverses PREROUTING. kube-proxy's rules (or eBPF) pick a backend and DNAT the destination to that pod's IP and port, and conntrack records the mapping. Node 1 routes the packet to node 2, natively or through a tunnel. Node 2 delivers it to the backend pod over its veth, and never sees the ClusterIP. The reply goes back toward pod A's IP and passes through node 1, where pod A lives. There conntrack rewrites the source back to the ClusterIP. Pod A sees a reply from the address it called.

Q3: Why does the Kubernetes network model forbid NAT between pods?

So that a pod's IP is its identity everywhere in the cluster. Applications see true peer addresses, NetworkPolicy can match on source pod IPs, and nothing needs per-application port mapping the way Docker's bridge did. It moves the complexity into the network: every node must be able to route every pod CIDR. That is why CNI plugins exist.

Q4: When would you pick an overlay CNI over routed or VPC-native?

When you can't make the underlay carry pod routes: you don't control the routers, BGP is off the table, or VPC route-table limits bite. An overlay needs only node-to-node IP reachability. You pay 50 bytes of MTU and lose pod-IP visibility in flow logs. If the cloud supports native pod addressing and you have the address space, I'd take that instead. Pod IPs then work with security groups, flow logs and peering.

Q5: What does ndots:5 do, and why does it hurt?

It tells the stub resolver to try the search domains first for any name with fewer than five dots. Cluster-internal short names benefit. External names like api.example.com pay for three or more NXDOMAIN round trips (times A and AAAA) before the real query. The fixes are a trailing dot on external names, a lower ndots for the pod, or NodeLocal DNSCache on each node.

Q6: Sidecar vs ambient mesh — what's the trade-off?

Sidecars give every pod a full L7 proxy, so every request gets L7 policy and telemetry. The cost is a proxy per pod and two proxy hops per call. Ambient splits L4 from L7. A per-node ztunnel does mTLS and L4 policy for all pods, and you add a waypoint only where you need L7 features. Ambient cuts resource cost and means mesh upgrades no longer restart app pods. The cost is a shared per-node component in the data path and a less mature ecosystem.

9. Code: watching ndots:5 multiply your DNS queries

This script runs a toy DNS server on 127.0.0.1 that knows three names. It then resolves names the way glibc's stub resolver does with a pod's resolv.conf: the search list plus the ndots rule. Every query is a real UDP packet, and the server logs each one. It runs anywhere Python 3.13 runs, including your Mac.

code/m23/ndots_demo.py:

"""ndots_demo.py - why one lookup in a pod becomes many DNS queries."""
import socket, struct, threading

ZONE = {  # name -> IPv4 answer (A only; AAAA gets an empty NOERROR for known names)
    "web.default.svc.cluster.local.": "10.96.0.50",
    "kube-dns.kube-system.svc.cluster.local.": "10.96.0.10",
    "api.example.com.": "203.0.113.10",
}
SEARCH = ["default.svc.cluster.local", "svc.cluster.local", "cluster.local"]
QTYPES = {1: "A", 28: "AAAA"}

def encode_name(name):
    out = b""
    for label in name.rstrip(".").split("."):
        out += bytes([len(label)]) + label.encode()
    return out + b"\x00"

def decode_name(buf, off):
    labels = []
    while buf[off]:
        n = buf[off]; labels.append(buf[off + 1:off + 1 + n].decode()); off += 1 + n
    return ".".join(labels) + ".", off + 1

def build_query(qid, name, qtype):
    header = struct.pack("!HHHHHH", qid, 0x0100, 1, 0, 0, 0)  # RD=1, one question
    return header + encode_name(name) + struct.pack("!HH", qtype, 1)

def answer(packet, log):
    qid = struct.unpack("!H", packet[:2])[0]
    name, off = decode_name(packet, 12)
    qtype, _qclass = struct.unpack("!HH", packet[off:off + 4])
    question = packet[12:off + 4]
    ip = ZONE.get(name.lower())
    known = ip is not None or any(n.endswith("." + name.lower()) for n in ZONE)
    rcode = 0 if known else 3                      # 3 = NXDOMAIN
    ans = b""
    if ip and qtype == 1:
        ans = b"\xc0\x0c" + struct.pack("!HHIH", 1, 1, 30, 4) + socket.inet_aton(ip)
    log.append((name, QTYPES.get(qtype, qtype), "NOERROR" if rcode == 0 else "NXDOMAIN",
                ip if ans else "-"))
    flags = 0x8180 | rcode                         # QR, RD, RA + rcode
    return struct.pack("!HHHHHH", qid, flags, 1, 1 if ans else 0, 0, 0) + question + ans

def serve(sock, log, stop):
    while not stop.is_set():
        try:
            data, peer = sock.recvfrom(512)
        except socket.timeout:
            continue
        sock.sendto(answer(data, log), peer)

def candidates(name, ndots):
    """glibc order: absolute names are tried as-is; names with >= ndots dots are tried
    as-is first, then with the search list; shorter names try the search list first."""
    if name.endswith("."):
        return [name]
    expanded = [f"{name}.{d}." for d in SEARCH]
    return [name + "."] + expanded if name.count(".") >= ndots else expanded + [name + "."]

def resolve(server, name, ndots, qtypes=(1, 28)):
    c = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); c.settimeout(2)
    qid, sent = 0x1000, 0
    for cand in candidates(name, ndots):
        found = None
        for qt in qtypes:
            qid += 1; sent += 1
            c.sendto(build_query(qid, cand, qt), server)
            resp, _ = c.recvfrom(512)
            ancount, rcode = struct.unpack("!H", resp[6:8])[0], resp[3] & 0x0F
            if rcode == 0 and ancount and qt == 1:
                found = socket.inet_ntoa(resp[-4:])
        if found:
            return found, sent
    return None, sent

srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); srv.bind(("127.0.0.1", 0))
srv.settimeout(0.2)
log, stop = [], threading.Event()
threading.Thread(target=serve, args=(srv, log, stop), daemon=True).start()
for name, ndots in [("web", 5), ("api.example.com", 5), ("api.example.com.", 5), ("api.example.com", 2)]:
    log.clear()
    ip, sent = resolve(srv.getsockname(), name, ndots)
    print(f"lookup {name!r:22} ndots:{ndots} -> {ip}   ({sent} queries)")
    for qname, qt, rc, a in log:
        print(f"    {qt:4} {qname:48} {rc:8} {a}")
stop.set()

Deep dive: what the Service abstraction hides

The module so far gave you the shapes: namespaces, veths, bridges, DNAT rules, conntrack. The YAML hides how those shapes behave per packet. A Service object looks like a load balancer, but there is no load balancer anywhere. There is a decision made once, on the client's node, on the first packet, and then remembered. Everything that goes wrong with Services in production — stale backends, uneven spread, 5-second DNS stalls, broken client IPs, MTU black holes — comes from that one design.

The sections below follow a single connection through the lab from Section 4, at four vantage points, and then go after the numbers and failure modes that fall out of it.

Deep dive: the real mental model

Think of the path as a list of kernel decision points, each with its own state:

  1. Pod A's stack. Its routing table (one default route), its ARP table (one entry, the gateway), its socket. Pod A picks an ephemeral port and sends a SYN to 10.96.0.50:80.
  2. The veth. Not a decision point at all. A frame written to the pod's eth0 appears on veth3f2a91c0 in node 1's namespace, unchanged.
  3. The bridge. The destination MAC is the bridge's own MAC (pod A ARPed for its gateway), so the bridge hands the frame up to node 1's IP stack instead of switching it.
  4. Netfilter PREROUTING, conntrack first. Conntrack sees a packet with no matching entry and creates one, unconfirmed. Then the nat table runs, because this is the first packet of a new connection. KUBE-SERVICES → KUBE-SVC-… → a random draw → KUBE-SEP-… → DNAT. The packet's destination is now 10.244.2.7:8080, and the conntrack entry records both tuples.
  5. Routing. After DNAT, so the lookup is for 10.244.2.7, not the ClusterIP. That is why the ClusterIP needs no route. Node 1 finds 10.244.2.0/24 via 192.168.10.12 and decrements TTL.
  6. FORWARD and POSTROUTING. NetworkPolicy egress rules (if pod A has any) run in FORWARD or in BPF on the veth. KUBE-POSTROUTING checks for mark 0x4000. Pod-to-Service traffic is unmarked, so there is no SNAT. The conntrack entry is confirmed into the hash table as the packet leaves.
  7. The wire. Routed mode: the IP packet goes out as-is, inside an Ethernet frame addressed to node 2's MAC. Overlay mode: the route points at a VXLAN device, which wraps the frame in UDP to node 2.
  8. Node 2. Its own conntrack creates a plain entry (no NAT). Routing finds 10.244.2.0/24 dev cni0, TTL drops again, FORWARD runs pod B's ingress policy, and the bridge switches the frame to veth8c1d0e47 and on into pod B.
  9. The reply. Pod B answers 10.244.1.5. Node 2 routes it back to node 1. On node 1, conntrack matches the packet against the entry's reply tuple and applies the reverse rewrite: source 10.244.2.7:8080 becomes 10.96.0.50:80. Pod A's socket accepts it.

Two invariants make this work, and you should be able to say both out loud. The DNAT state lives only on the client's node. And the reply must come back through that node, or the reverse rewrite never happens. With pod A living on node 1, routing guarantees that. Break it — with asymmetric routing, a direct-server-return trick, or a bridged shortcut like the Try it section's — and pod A receives a SYN-ACK from an address it never called.

  • The source never changes. 10.244.1.5.51314 arrives at pod B intact. That is the network model's "no NAT between pods" rule in action, and it is why pod B's HTTP server logged podB saw client 10.244.1.5:51314.
  • TTL counts routers, and nodes are routers. 64 leaving pod A, 63 after node 1, 62 after node 2. The SYN-ACK makes the same two hops back: it leaves pod B at 64 and reaches pod A at 62.
  • Sequence numbers and IP IDs are identical end to end (seq 3380397683, id 4298). Nothing terminated the TCP connection. This is L4 NAT, not a proxy. An Ingress controller or a sidecar would show two different connections with different sequence spaces.
  • The SYN-ACK at (1) comes "from" 10.96.0.50. That is conntrack's reverse rewrite, applied on node 1 before the packet re-entered pod A's veth.

The timestamps are tight because this is one machine: the SYN crossed both nodes in about 1 ms. Real clusters add the underlay RTT, typically tens to hundreds of microseconds inside one zone.

And the FDB says frames for that MAC go to underlay IP 192.168.10.12. Here is the SYN on node 1's uplink, tcpdump -nn -e -v:

The outer frame is node-to-node: underlay MACs, node IPs, UDP to port 8472. tcpdump labels it "OTV" because 8472 is also registered to Cisco OTV. Flannel uses the Linux kernel's historical VXLAN port rather than IANA's 4789 (RFC 7348). instance 1 is the VNI. The inner frame is pod-to-pod, between the two VTEP MACs, with the inner TTL already decremented by node 1.

The byte budget adds up exactly. Inner IP packet: 60 bytes. Plus inner Ethernet, 14: 74. Plus VXLAN header, 8: 82. Plus outer UDP, 8: 90. Plus outer IPv4, 20: 110, the outer IP length. Plus outer Ethernet, 14: 124 on the wire. The 50 bytes between 74 and 124 are the overlay tax.

Look at the MSS, too: 1410, not 1460. The pod's eth0 MTU is 1450 here (1500 − 50), and the kernel derives MSS from it (1450 − 20 − 20). The SYN-ACK from pod C also carried mss 1410. When both ends know the reduced MTU, TCP never sends a segment that cannot be encapsulated. You can see the limit directly with DF-set pings from pod A:

$ ping -c1 -M do -s 1422 10.244.2.7
PING 10.244.2.7 (10.244.2.7) 1422(1450) bytes of data.
1430 bytes from 10.244.2.7: icmp_seq=1 ttl=62 time=1.64 ms
$ ping -c1 -M do -s 1423 10.244.2.7

ping: local error: message too long, mtu=1450

1422 bytes of payload + 8 ICMP + 20 IP = 1450 fits; one more byte fails locally, before anything is sent.

A worked example ties three rows together. A cluster has 2,000 Services averaging 10 endpoints. In iptables mode that is roughly 2,000 SVC chains plus 20,000 SEP chains, each with two rules: about 40,000+ rules in nat. A new connection to the last Service in KUBE-SERVICES walks past ~2,000 match rules on its first packet. That is microseconds, not milliseconds, but it is paid per connection. The bigger cost is updates: every endpoint change used to mean regenerating and iptables-restore-ing the whole table, which took seconds at this size. That is the main reason nftables and eBPF modes exist.

A second: DNS load from ndots. Say 500 pods each make 20 external lookups per second without caching in the app. With three search domains, A and AAAA, and a cache-miss path, that is 500 × 20 × 8 = 80,000 queries per second at CoreDNS instead of 20,000. Adding a trailing dot cuts it by 4×. NodeLocal DNSCache does not reduce the count, but it answers the NXDOMAINs from a cache on the same node, and its traffic skips conntrack.

Deep dive: production failure modes

1. The 5-second DNS stall. Symptom: some requests take 5.0x seconds; p99 latency has a spike at exactly +5 s. Mechanism: glibc sends A and AAAA queries in parallel from the same UDP socket, so both packets share one 5-tuple. Both race through conntrack on the node at once, and both create unconfirmed entries. If they were DNATed to different CoreDNS pods, the second insert fails and that packet is dropped. Older kernels drop it even when both pick the same pod. The resolver waits its 5-second timeout and retries. Prove it: conntrack -S on the node and watch insert_failed climb; capture port 53 in the pod and look for a query with no answer followed by a retry 5 s later. Fix: NodeLocal DNSCache (its traffic is NOTRACKed), or dnsConfig.options: single-request-reopen for glibc, or a CNI whose eBPF dataplane does not use netfilter conntrack for this path. Newer kernels fixed parts of the race but not every variant.

2. Overlay MTU black hole. Symptom: health checks and small API calls work; large responses, image pulls through a pod proxy, or TLS handshakes with big certificate chains hang. Mechanism: something in the path assumes 1500 bytes. The usual case is a pod or node configured with MTU 1500 on a VXLAN network, or an underlay that is itself smaller (some cloud links, VPN-connected nodes). Encapsulated packets exceed the underlay MTU, and if ICMP "fragmentation needed" is filtered, TCP never learns. Prove it: the ping -M do -s probe above from inside a pod to a pod on another node, stepping the size; compare ip link MTUs on pod eth0, the tunnel device and the node uplink. Fix: set the CNI MTU to underlay minus overhead (most plugins auto-detect; verify), or move to routed mode, or raise the underlay to jumbo frames (9001 on AWS within a VPC).

3. Stale endpoints after a node dies. Symptom: for a minute or more after a node failure, a fraction of connections to a Service time out. Mechanism: the pod IPs on the dead node stay in EndpointSlices until the node is marked NotReady and the pods are evicted or marked not-ready, which depends on node-monitor and eviction timers (tens of seconds by default). Meanwhile every node's kube-proxy keeps DNATing 1-in-n new connections to unreachable IPs. Prove it: kubectl get endpointslices still shows IPs from the dead node; conntrack -L -d <clusterIP> shows SYN_SENT [UNREPLIED] entries to those IPs. Fix: readiness probes plus client-side retries with short connect timeouts; tune node-monitor grace periods with care; a mesh or L7 proxy with outlier detection ejects dead backends in seconds.

4. Uneven load across pods with long-lived connections. Symptom: one gRPC backend pod is at 90% CPU while others idle. Mechanism: the Service balances connections, once, at connect time. gRPC and HTTP/2 multiplex all requests over a few long-lived connections, so whoever got those connections gets the load forever. Scaling up does not help: new pods get no existing connections. Prove it: ss -tn in each backend pod and count established connections; compare to per-pod request rates. Fix: client-side load balancing over a headless Service, an L7 proxy (Gateway, mesh) that balances per request, or MAX_CONNECTION_AGE on the server to force periodic reconnects.

5. Lost client IPs. Symptom: access logs and rate limiters see node IPs or load balancer IPs instead of real clients. Mechanism: NodePort and externalTrafficPolicy: Cluster SNAT to the node IP (shown above); an L7 proxy opens a new TCP connection. Prove it: compare the TCP peer in the backend with the client you tested from. Fix: externalTrafficPolicy: Local with an LB that health-checks the node's healthCheckNodePort, or LB-to-pod-IP mode, or read X-Forwarded-For / PROXY protocol at an L7 hop you trust.

6. Pod IP exhaustion. Symptom: new pods stick in ContainerCreating with CNI errors like "failed to allocate for range" or "no available IP addresses", while the node has room for more pods. Mechanism: leaked IPAM leases from failed CNI DEL calls (bridge/host-local), or, on AWS VPC CNI, the per-instance ENI/IP limit or an exhausted subnet. Prove it: count files in /var/lib/cni/networks/<net>/ against running pods on that node; on AWS, compare kubectl describe node allocatable pods against the ENI formula and check the subnet's free addresses. Fix: clean up leaked leases (or upgrade to a plugin with CNI GC), enable prefix delegation, and size pod subnets with room for surge.

7. Egress policy that kills DNS. Symptom: right after applying an egress NetworkPolicy "allow only to the database", every outbound call fails with name-resolution errors. Mechanism: once a pod is selected for egress, everything not allowed is dropped, including UDP/TCP 53 to CoreDNS. Prove it: getent hosts kubernetes.default from the pod fails while curl to the database's IP works. Fix: add an egress rule to the kube-dns pods (namespaceSelector kube-system plus podSelector k8s-app: kube-dns) on UDP and TCP 53 in every egress policy, or in a cluster-wide baseline.

8. Conntrack table full. Symptom: random new connections fail on one busy node; dmesg shows nf_conntrack: table full, dropping packet. Mechanism: every connection through a Service, plus every NodePort and SNAT flow, holds an entry until it times out. Short-lived connections in TIME_WAIT (120 s in conntrack) add up fast. Prove it: compare /proc/sys/net/netfilter/nf_conntrack_count to nf_conntrack_max. Fix: raise the limit (kube-proxy's --conntrack-max-per-core), reuse connections in clients, or move to an eBPF dataplane with its own sized maps.

Deep dive: 2026 context

kube-proxy is being hollowed out from both sides. nftables mode went GA in v1.33 and is where upstream's kernel-native work goes; IPVS mode is on its way out. At the same time, many managed and self-run clusters now run an eBPF dataplane (Cilium most visibly, also Calico eBPF) that replaces kube-proxy entirely. If you debug a cluster in 2026, the first question is which Service implementation it runs. The commands differ: iptables-save, nft list ruleset, or cilium-dbg service list and hubble observe.

Gateway API is the default L7 API. Ingress still works and is not going away soon, but new features land in Gateway API. The community's ingress-nginx controller, the most widely deployed Ingress implementation, was retired, with best-effort maintenance ending in March 2026, which pushed many teams onto Gateway API implementations. Gateway API also covers east-west traffic for meshes (its GAMMA work), so the same HTTPRoute can describe routing at the edge and between services.

Meshes are getting lighter. Istio's ambient mode removed the per-pod sidecar for the common case of "mTLS plus L4 policy". Cilium offers mTLS and L7 policy from its node agent and per-node Envoy. Native sidecar containers (GA in Kubernetes 1.33) fixed the start/stop ordering problems that plagued sidecar meshes in Jobs and init containers.

Zero trust inside the cluster means identity, not IPs. Pod IPs churn by design. Policy written against IPs or even labels is a proxy for the real question: which workload is this? Mesh mTLS with SPIFFE identities, and eBPF dataplanes that tag packets with label-derived security identities, both answer it directly. The interview-ready framing is "the network model gives you reachability; identity gives you authorization."

IPv6 and dual-stack are normal now. Dual-stack Services and pods have been stable since v1.23. IPv6-only clusters avoid pod IP exhaustion entirely (a /64 or /80 per node) and remove most NAT. The DNS caveat from the deep dive applies: IPv6-capable pods send AAAA queries too, which doubles ndots expansion.

Cloud CNIs keep closing the gap with on-prem routing. AWS VPC CNI prefix delegation (a /28 per ENI slot) raised per-node pod counts. GKE Dataplane V2 is Cilium-based. Azure CNI offers both overlay and VNet-routable pod IPs. The overlay-vs-routed choice is increasingly a choice of which IP space you want pods to consume, not of performance.

Deep dive: senior interview questions

Q1: Where does the DNAT for a ClusterIP happen, and what breaks if the reply takes a different path?

On the client's node, in PREROUTING (or in BPF at connect()/tc), on the first packet. The conntrack entry that can undo it exists only there. Sometimes the reply reaches the client without passing through that node's conntrack: asymmetric routing, a bridged same-node path without br_netfilter, or a backend replying directly to an external client. Then the client gets a packet from the backend's pod IP. It matches no socket, so the client resets or ignores it. That is exactly why NodePort SNATs by default.

Q2: A pod's DNS lookups are slow but always succeed. Walk me through finding the cause.

Check /etc/resolv.conf in the pod for ndots and the search list. Time a lookup with and without a trailing dot. If the trailing dot is fast, it's search-list expansion. If both are sometimes slow by exactly 5 s, it's dropped UDP — look at conntrack -S insert_failed on the node and the A/AAAA same-socket race. If it's uniformly slow, look at CoreDNS itself: its CPU, its upstream forwarder, and whether it is being throttled.

Q3: Why does tcpdump on the backend pod show the client pod's real IP, but tcpdump on the client pod shows replies from the ClusterIP?

Because the only rewrite is DNAT on the client's node. Outbound, the destination changes and the source does not, so the backend sees the true client. Inbound, conntrack reverses the destination rewrite as a source rewrite before the packet re-enters the client's veth. Both captures are correct views of the same connection at different points.

Q4: What would make you choose IPVS or nftables over iptables mode, or eBPF over all three?

Scale and update churn. iptables mode's first-packet cost grows with the number of Services, and full-table rewrites get slow in the tens of thousands of rules. IPVS fixed lookup cost but kept iptables for edge cases and is being deprecated; nftables mode fixes both lookup and incremental updates with a supported path. eBPF goes further: socket-level translation removes per-packet NAT for pod clients, it brings its own conntrack and policy, and it gives flow visibility (Hubble). The trade is a more complex, plugin-specific dataplane to operate and debug.

Q5: A VXLAN cluster works except that some HTTPS calls between pods hang after the TLS ClientHello. What's your hypothesis and test?

MTU. The ClientHello is small, but the ServerHello plus certificate chain fills full-size segments. If a pod or node thinks the MTU is 1500 on a 1450 path, those segments get dropped and PMTUD may be broken by filtered ICMP. Test with ping -M do -s stepping across 1422/1423 between pods on different nodes, compare interface MTUs, and look at the MSS in the SYNs. Fix the CNI MTU, or clamp MSS as a stopgap.

Q6: What does a default-deny NetworkPolicy look like on the wire, and how do you tell it apart from a dead backend?

A drop, not a reject: the SYN is retransmitted with the same sequence number until the client gives up. To tell it apart, capture on the backend's node. A policy drop shows the SYN arriving at the node (and the policy counter or hubble observe --verdict DROPPED incrementing) but never reaching the pod's veth. A dead backend's IP either never arrives on any node, or arrives and gets an ICMP host-unreachable from the node because no veth owns it.

Q7: Explain how Istio ambient gets traffic into ztunnel without a sidecar, and what HBONE carries.

The Istio CNI component configures redirection inside each enrolled pod's network namespace so that the pod's traffic is captured by the node's ztunnel instead of leaving directly. ztunnel then opens an mTLS connection to the destination node's ztunnel, using the source workload's SPIFFE identity, and tunnels the original TCP stream inside an HTTP/2 CONNECT on port 15008. That is HBONE. The destination ztunnel authorizes on identity and delivers the plaintext stream to the target pod. L7 policy only happens if the destination has a waypoint, which the traffic is routed through first.
