# ADR-0014: Testing strategy: pure domain tests, contract tests on golden messages, Testcontainers, chaos drills

- **Status:** Accepted
- **Date:** 2026-11-21
- **Related:** ADR-0004, ADR-0006, ADR-0008, docs/implementation-guide.md "Test checklist", docs/architecture.md §11

## Context

The riskiest bugs in this system are not inside one function. They are in the seams: a Java producer and a Python consumer disagreeing about a field; a handler that is not idempotent under redelivery; a saga that gets stuck when replies arrive out of order; trace context lost between outbox and consumer. End-to-end tests over nine services are slow and flaky if used as the main safety net.

## Decision

Five layers, each with a clear job:

1. **Domain unit tests (most tests).** The saga transition functions, refund calculation, reservation rules and status ranking are pure functions. Test every row of the transition tables in architecture §5.2 and §6.1, including late, duplicate and out-of-order events. Property-based tests (Hypothesis / jqwik) shuffle reply orders and assert that every saga ends in a terminal or NEEDS_ATTENTION state with consistent compensations.
2. **Contract tests on golden messages.** `contracts/examples/*.json` and `*.bin` are generated from the schemas. Each implementation must (a) decode every `.bin` with its own generated or generic Avro code and get the `.json` values, and (b) encode the `.json` and get identical bytes. Each producer also has a test that serialises the events it emits and validates them against the bundled schema. This is the cross-language interoperability guarantee, and it runs in milliseconds. `make contracts-check` and the Schema Registry compatibility check run in CI for every contract change.
3. **Integration tests with Testcontainers.** Per service: real Postgres, real Kafka (KRaft), real Schema Registry, MinIO where needed. Run migrations, publish a command, assert the reply event and the database state. These tests use the **polling relay** (`OUTBOX_RELAY=polling`) so they do not need Kafka Connect; one dedicated test per language runs Debezium in a container to prove the connector config.
4. **Component end-to-end test.** The whole system via docker compose plus both builds: place an order with `tok_visa_ok` and assert `DELIVERED`; with `tok_decline` and assert `CANCELLED(PAYMENT_DECLINED)` and stock restored; a return with partial refund. Run nightly and before releases, not on every commit.
5. **Chaos drills.** The table in architecture §11, run under load against a running stack. Each drill has pass criteria. They run at least once per build (Day 9 of the plan) and before major releases.

Consumer-driven contract testing with Pact (message pacts) is **not** used by default. The schema registry with FULL_TRANSITIVE plus golden messages covers structural compatibility. Pact would add semantic expectations ("payment-svc must emit PaymentDeclined when…"), which our component tests cover.

## Alternatives considered

| Option | Why it is attractive | Why we did not pick it |
|---|---|---|
| Pact message contracts | Consumer expectations are explicit and versioned; broker shows who depends on what | A broker to run; overlaps with registry compatibility; two languages × nine services of pacts is a lot of upkeep for a capstone |
| Embedded Kafka / in-memory fakes | Fast | Behaviour differs from real Kafka (rebalances, transactions, headers); false confidence |
| Mostly end-to-end tests | Test what users see | Slow, flaky, poor failure localisation |
| Mocks of the database | Fast | Idempotency and locking bugs live in real SQL; Testcontainers Postgres starts in seconds |

## Consequences

- The domain layer must stay pure (no I/O), or layer 1 collapses into integration tests. The hexagonal layout enforces it (implementation guide).
- CI needs Docker for layers 3 and 4.
- Golden examples are regenerated by `make contracts`; a test failing on them means either a schema change or a serialisation bug, and the diff says which.
- Every service passes the same checklist (implementation guide), so a reviewer can compare the Python and Java builds item by item.

## Trade-offs

We gain fast feedback on the seams that matter (serialisation, idempotency, ordering) and realistic integration tests without a heavy end-to-end suite. We pay with Docker in CI, golden-file maintenance, and the discipline of keeping the domain pure.

## When to revisit

- Several independent teams consume each other's events and semantic breakages slip through: add Pact message contracts for those pairs.
- The component suite grows beyond 15 minutes: split by flow and run in parallel.
