# returns-svc (port 8109)

Return eligibility, RMA numbers, and the **returns saga** orchestrator (architecture §6): a forward-recovery saga on the same edacommon saga kit as order-svc.

**Owns:** `eligibility_view`, `return_request`, `return_line`, `rma_counter` (`V2__returns.sql`) and the shared `saga_instance` / `saga_transition`.
**Consumes:** `order.events.v1` (OrderPlaced, OrderConfirmed, OrderDelivered, OrderCancelled -> eligibility view), `fulfilment.events.v1` (FulfilmentAccepted -> warehouse; ReturnReceived, ReturnInspected), `shipping.events.v1` (ShipmentCreated RETURN -> label), `inventory.events.v1` (ItemsRestocked), `payment.events.v1` (RefundSucceeded, RefundFailed). **Publishes:** `returns.events.v1` (ReturnRequested, ReturnAuthorized, ReturnRejected, ReturnRefunded, ReturnClosed; aggregate Return/returnId), `shipping.commands.v1` (IssueReturnLabel), `fulfilment.commands.v1` (ExpectReturn), `inventory.commands.v1` (RestockItems), `payment.commands.v1` (RefundPayment). Everything is keyed by orderId; the flow's correlation id is the returnId.
**HTTP:** `POST /returns` (Idempotency-Key), `GET /returns/{id}`, `GET /returns/{id}/label` (302 to a 5-minute pre-signed URL), `GET /orders/{orderId}/returns`, `POST /ops/returns/{id}/decision` (Idempotency-Key), `GET /ops/sagas/{id}`, `POST /ops/sagas/{id}/retry-step`, `/ops/dlq`.
**Config:** `RETURN_WINDOW_DAYS` (30), `RETURN_AUTO_APPROVE_LIMIT_MINOR` (50000), `RETURN_PARCEL_DUE_DAYS` (14).

**Patterns:** DB-backed saga (ADR-0008): `domain/ReturnSaga` is a pure function `(state, data, trigger, now) -> decision`; `ReturnsService` runs it through `SagaEngine` in one transaction with the inbox, the outbox and the return's query row. Business ids (rmaNumber, shipmentId, restockId, refundId) are minted when a step starts and reused on every resend; the same refundId on every attempt means a "failed" refund that went through at the PSP can never refund twice. Refund rule in the domain (`RefundPolicy`, architecture §6.2). CQRS (ADR-0010): the eligibility view is a commutative projection with a version guard on the status.

States: REQUESTED -> AUTHORIZED (value <= limit) or MANUAL_REVIEW -> AWAITING_PARCEL (IssueReturnLabel + ExpectReturn, deadline parcelDueBy) -> AWAITING_INSPECTION -> SETTLING (RestockItems + RefundPayment) -> CLOSED (REFUNDED / PARTIALLY_REFUNDED), with REJECTED, EXPIRED and REFUND_REVIEW branches as drawn in §6.1.

## Decisions and trade-offs

- **Forward recovery, not compensation (§6.2).** After inspection every step is retried until it succeeds or a human decides: RefundFailed(retryable) is resent after 1 min, 10 min, 1 h (the saga deadline is the backoff); the fourth failure, or a non-retryable one, enters REFUND_REVIEW (counted as MANUAL_REVIEW). SETTLING also chases lost replies every 10 minutes. A RefundSucceeded arriving in REFUND_REVIEW closes the return without the human.
- **Transient states are passed through in one transaction.** AUTHORIZED, REJECTED and EXPIRED need no outside input, so the service applies a `Continue` trigger right after entering them; the transition log still shows every state of the diagram (`REQUESTED -> AUTHORIZED -> AWAITING_PARCEL`).
- **Eligibility is answered from returns-svc's own projection,** locked per order so two concurrent returns cannot both take the last unit. The window is RETURN_WINDOW_DAYS from `deliveredAt` (returns-svc owns the rule; order-svc's `returnWindowEndsAt` uses the same 30-day default). A return that ended without the parcel coming back (EXPIRED, rejected in review) frees its quantities.
- **Refund rule details not fixed by the design:** a partial refund is any return where some inspected unit was refunded below its price; the shipping fee (OrderPlaced total minus line totals) is added only when something is refunded, the reason is merchant fault and it is the order's first return; units the warehouse did not report count as MISSING.
- **API status mapping:** AWAITING_INSPECTION -> RECEIVED, SETTLING -> REFUNDING, REFUND_REVIEW -> MANUAL_REVIEW; a return closed by staff without a refund (ReturnClosed outcome MANUAL_REVIEW) reports REJECTED, because returns.yaml has no CLOSED status. INSPECTED is never reported: inspection and the start of settling happen in one transition.
- **A parcel that arrives after expiry is ignored by the saga** (the warehouse still records it); that is a case for a human, not for code.
- **No personal data in saga data.** The pickup address for the label is read from the eligibility view when the command is written.
- **Contract issue:** returns.yaml `refundAmount` is `oneOf: [Money, {type: 'null'}]` (OpenAPI 3.1); the Java response validator matches both branches for any value, so the returns IT switches off only that rule.
